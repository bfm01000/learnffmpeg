小鹏汇天预览流延时问题分析

一、小鹏汇天预览流延时问题分析
1️⃣ 问题背景
- 目标：定位并解决小鹏汇天项目中 预览流延时较高的问题
- 排查方法：
  - 提供 保存视频流数据的接口
  - 提供 测试 AAR 包，用于统计解码渲染pipiline中耗时异常的部分：
    - 解码耗时
    - 渲染耗时
- 测试方式：
  - 小鹏团队在 真机环境（小米11） 运行测试
  - 采集不同预览流链路的性能数据并进行分析
2️⃣ 关键发现
通过对 播放链路时钟同步逻辑 的分析，发现当前系统存在以下特征：
当前播放器的 播放时钟（Playback Clock）
是以 首帧渲染完成时间 作为时间轴基准建立的。

具体表现为：
- 首帧完成渲染时，会记录当前延迟并建立播放时钟
- 后续所有帧的调度都会基于该时间轴进行同步

因此，当 首帧解码或渲染耗时较长 时：
- 这个延迟会被直接带入整个播放时间轴
- 后续帧即使按照正常节奏播放
- 但由于时间轴已经存在偏移，最终表现为 整体播放延迟持续存在

3️⃣ 问题结论
当前系统的建钟策略为：
以首帧为参考建立播放时间轴
如果首帧在解码或渲染阶段已经产生较大延迟：
- 该偏移会被带入整个播放调度体系
- 后续播放将始终沿着该偏移运行
- 在性能边缘设备上更容易暴露

结合当前日志分析：
- 当前设备从 相机输入到首帧渲染前
- 链路耗时约 ~1s

因此系统建立播放时钟后：
- 后续播放都沿着该偏移执行
- 用户体感上会看到 固定延时

4️⃣ 优化方案
为降低预览延时，提供新的控制接口：
setRenderAtOnce(true)
该接口的作用是：
关闭 CameraVideoQueue 中基于时间戳的渲染等待逻辑
原有逻辑：
- renderAtOnce == false
  - 根据 waitTimeMs 执行 Wait(...)
  - 按照 PTS 节拍（约 30fps）进行渲染

优化逻辑：
- renderAtOnce == true
  - 跳过 Wait(...)
  - 有帧即立即渲染

5️⃣ 影响评估
优点：
- 显著降低预览延时
- 加快积压帧的追赶速度

潜在影响：
- 帧间隔可能不均匀
- 画面平滑性可能略有下降
- CPU / GPU 负载可能增加
