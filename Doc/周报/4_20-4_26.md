直播性能优化专项
一、性能测试与数据验证（小米10）
针对直播链路中的长期掉帧与卡顿问题，进行了专项性能测试与链路分析，重点验证零拷贝架构（硬件帧）对整体性能的改善效果。
测试条件
设备：小米10
 场景：稳定运行后进行持续直播测试，对比不同链路模式下的帧率表现

二、测试结论与性能分析
1. 零拷贝架构显著突破系统性能瓶颈（提升 30% ~ 118%）
通过对比“软件帧直播”与“硬件帧直播”：
- 初始稳定状态下，硬件零拷贝方案将帧率从 23fps 提升至满帧 30fps，性能提升约 30%
- 长时间高负载（10分钟）后：
  - 软件帧直播下降至 11fps
  - 硬件帧直播仍可维持在 24fps
相对提升达到 118%
这充分证明：
彻底剥离 CPU 回读（glReadPixels / ReadPixels）操作后，系统算力得到显著释放，有效延缓性能衰减。

---
2. 长时直播掉帧的核心瓶颈在于网络链路（控制变量验证）
通过控制变量对比：
- 硬件帧直播（10分钟后：24fps）
- 硬件帧本地写入（10分钟后：29fps）
在 GPU 渲染与 VPU 编码压力完全一致的情况下：
仅仅去掉网络发送环节，帧率几乎不再衰减。
结合底层耗时日志可确认：
长时直播的性能瓶颈并不在渲染或编码，而主要集中在网络发送链路。

---
3. 掉帧深层机制分析：温控降频 + 网络反压双重影响
直播掉帧并非单点问题，而是由网络引发的系统级连锁反应：
（1）物理层面：发热导致系统全局降频
直播推流持续高负载运行：
- GPU：实时渲染
- VPU：硬件编码
- 基带芯片：长时间高功率网络上行
三者叠加后：
手机温度快速上升，触发系统温控机制，导致：
- GPU 降频
- VPU 降频
- 整体处理能力下降
最终表现为：
帧率持续下降

---
（2）架构层面：网络反压（Backpressure）导致链路堵塞
当前 BMG 编码与网络发送流程为：
编码 → 同步网络发送（串行执行）
一旦网络发生轻微抖动：
- Mux / Network Send 耗时飙升
- 编码线程被阻塞
- 编码器出口被堵
- 编码器入口被反压
- Java 层缓冲队列快速堆积
- 最终触发强制丢帧
这也是长时间直播后帧率快速下降的重要原因。

当前问题

串行阻塞式执行

网络发送耗时会直接影响编码器工作效率。
优化方向

四、解决方案设计

---
方案一：架构解耦 —— 引入异步发送队列（Asynchronous Send Queue）
当前痛点
编码器输出数据后：
直接同步执行：
Mux / Network Send
一旦网络抖动（哪怕仅 100ms）：
整个线程立即阻塞。
导致：
- VPU 被迫停工等待
- 网络反压传导至编码器
- 最终反压至 Java 层并触发丢帧

---
优化方案
在编码器与网络发送之间：
建立：
独立发送线程 + 发送缓冲队列
具体实现：
1. 创建独立的网络发送线程（Send Thread）
2. 建立线程安全的发送队列（Send Queue）
3. 编码器仅负责快速将 H264 数据包写入队列
4. 网络发送线程异步消费数据

---
预期收益
编码器写队列耗时：
从几十毫秒 → 降低至约 0.1ms
效果：
- 编码器持续稳定工作
- 网络抖动由内存缓冲吸收
- 彻底消除网络反压对编码器的影响

---
方案二：动态自适应降级（ABR + Thermal Downgrade）
当前痛点
无论：
- 网络环境多差
- 手机温度多高
系统始终强制维持：
4K + 高码率 + 高帧率
最终导致：
系统崩溃式掉帧（11fps甚至更低）

---
优化方案
1. 弱网自适应码率（ABR）
监控：
- Send Queue 水位
- TCP RTT 延迟
当发现积压严重时：
动态调用：
MediaCodec.setParameters()
实时降低目标码率：
例如：
10Mbps → 5Mbps
网络恢复后：
缓慢回调码率。

---
2. 温控主动降级（Thermal Management）
接入：
- PowerManager.getThermalHeadroom()
- ACTION_THERMAL_STATUS_CHANGED
当检测到：
- MODERATE（中度发热）
- SEVERE（严重发热）
主动降级：
例如：
- 4K@30fps → 2.7K@24fps
- 或 → 1080P@30fps

---
预期收益
在系统触发强制降频前：
主动降低系统功耗
实现：
用适度画质妥协，换取长时直播的稳定流畅
