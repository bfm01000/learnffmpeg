四、小鹏汇天专项问题处理
24 小时压测内存泄漏问题分析
- 小鹏反馈长时间压测场景下出现 OOM 与内存泄漏问题
- 对 Heap Dump 与引用链进行分析，定位问题根因
排查结论
从 Dump 分析结果来看：
本次 OOM 的主要原因并非 SDK 侧预览流缓存未释放，
而是：
Activity 生命周期未正常结束导致对象持续被持有

---
SDK 侧分析结果
当前堆内：
- StreamProcess 仅 1 个实例
- H264Parser 仅 1 个实例
说明：
预览流“创建 → 释放”流程整体正常
不存在明显 SDK 内部泄漏。
但：
- ConnectStrategyImpl 有 5 个实例
- OneDriver 有 4 个实例
这类对象通常与 Activity 生命周期绑定。
因此可以基本确认：
部分 Activity 未被正常 GC 回收。

---
主要内存占用分析
当前最大内存占用来自：
PanoAlbumWork
实例数量：
90,926 个
引用链如下：
PanoAlbumWork
← ArrayList (panoAlbumWorks)
← PanoAlbumGroup
← MutableLiveData.mData
← LiveData$LifecycleBoundObserver
← LifecycleRegistry.observerMap
← Activity.mLifecycleRegistry
← LoadedApk.mReceivers
← ActivityThread

---
问题根因分析
引用链最终指向：
LoadedApk.mReceivers
该情况通常意味着：
registerReceiver 后未正确 unregisterReceiver
由于：
LoadedApk 属于进程级全局对象，
一旦其持有 Activity：
- Activity 无法被 GC
- LiveData Observer 无法解绑
- panoAlbumWorks 持续累积
- 最终导致 Java Heap OOM

---
给用户的排查建议
建议重点确认：
1. Receiver 生命周期是否完整
重点检查：
- 匿名 Receiver
- 注册到 ApplicationContext 的 Receiver
- 非 onCreate / onDestroy 成对生命周期中的注册逻辑
确保：
所有 registerReceiver 均有对应 unregisterReceiver

---
2. panoAlbumWorks 更新逻辑
确认是否存在：
list.add(...)
持续追加逻辑。
建议改为：
setValue(newList)
整体替换。
否则：
在 Observer 未解绑情况下，
极易导致列表无限累积。

---
3. 使用 Android Profiler / MAT 定位
建议：
直接搜索 Activity 实例数量，
并使用：
“Show nearest GC root only”
快速定位：
具体被哪个 Receiver 持有。
