## 一、JNI 线程模型（来自 01）

### Q1-1：JNIEnv 和 JavaVM 的区别？

> `JNIEnv` 是线程私有的 JNI 函数表指针，绝对不能跨线程传递。`JavaVM` 是进程全局唯一的 JVM 入口，可以保存到全局变量。子线程需要 JNI 能力时，通过 `JavaVM->AttachCurrentThread` 获取自己的 `JNIEnv`。

### Q1-2：AttachCurrentThread 之后为什么必须 Detach？不 Detach 会怎样？

> 每次 Attach 都会在 JVM 内部为该线程分配资源（局部引用表等）。不 Detach 这些资源永久不释放，累积后导致 JVM 内部资源泄漏，最终崩溃。主线程（Java 创建的线程）已经 Attach，不需要手动 Detach。

### Q1-3：静态注册和动态注册有什么区别？为什么推荐动态注册？

> 静态注册按 `Java_包名_类名_方法名` 命名，JVM 首次调用时按名字搜索绑定——函数名又长又丑、性能稍差、易被反编译。动态注册在 `JNI_OnLoad` 里用 `RegisterNatives` 直接把 Java 方法名和 C++ 函数指针绑定——函数名自由、直接指针跳转、更安全。

### Q1-4：`JNI_OnLoad` 里一般做哪三件事？

> ① 保存全局 `JavaVM`。② 动态注册 native 方法（`RegisterNatives`）。③ 返回 `JNI_VERSION_1_6`。

## 二、引用管理（来自 02）

### Q2-1：LocalRef、GlobalRef、WeakGlobalRef 的区别？

> - **LocalRef**：函数返回自动失效，默认类型。局部引用表上限约 512 个。
> - **GlobalRef**：手动管理的强引用，阻止 GC。必须 `DeleteGlobalRef` 释放。
> - **WeakGlobalRef**：手动管理的弱引用，**不阻止 GC**。用前必须 `IsSameObject` 检查对象是否已被 GC。凭证本身仍须 `DeleteWeakGlobalRef` 释放。

### Q2-2：为什么循环里创建 LocalRef 会崩溃？

> 局部引用表有固定上限（~512 个）。循环内不释放 LocalRef，引用的个数很快超限 → `JNI ERROR: local reference table overflow`。解决：每次迭代 `DeleteLocalRef`，或使用 `PushLocalFrame`/`PopLocalFrame`。

### Q2-3：GetStringUTFChars 为什么必须配对 ReleaseStringUTFChars？

> `GetStringUTFChars` 底层可能发生内存拷贝（JVM 在 Native 堆上分配一块空间把 Java 字符串拷过来）。`ReleaseStringUTFChars` 告诉 JVM "我用完了"，JVM 释放那块临时内存。不调就泄漏。同理 `GetByteArrayElements` / `ReleaseByteArrayElements`。

### Q2-4：为什么不推荐用 WeakGlobalRef 保存回调对象？

> 如果 Java 层传的是匿名内部类，没有强引用保活。WeakGlobalRef 不阻止 GC → 触发一次 GC 后对象被杀 → 回调静默消失，无日志无崩溃，排查成本极高。业界主流用 GlobalRef 强锁 + `release()` 强制清理。

### Q2-5：shared_ptr 管理 GlobalRef 比裸指针好在哪里？

> ① **多线程安全**：回调前 `auto safeRef = g_sharedRef` 让引用计数 +1，即使此时其他线程调了 `release()`，对象也不会立即析构。② **异常安全**：函数退出时栈展开自动调用析构，不会因为异常跳过 DeleteGlobalRef。

## 三、TLS 回调架构（来自 03）

### Q3-1：为什么用 TLS 而不是每次都 Attach/Detach？

> ① **性能**：频繁 Attach/Detach 开销大，TLS 缓存让每个线程只 Attach 一次。② **防泄漏**：手动 Detach 容易因异常/提前 return 遗漏，TLS 析构函数由 OS 在线程死亡时自动调用，100% 触发。

### Q3-2：TLS 析构函数是在什么时候被调用的？谁调的？

> 线程死亡时（正常 return、pthread_exit、pthread_cancel），由**操作系统**在底层线程清理流程中遍历 TLS Key 并主动调用注册的析构函数。无论线程怎么死的都会走到。

### Q3-3：线程池里的线程复用，TLS 方案还有效吗？

> 线程池里的线程不会死 → 析构函数不会触发 → JVM 资源不会泄漏（因为线程一直 Attach 着），但线程池回收时可能累积过多 Attach 线程。线程池场景建议在线程归还池时手动清理 TLS 或设置时间上限。

### Q3-4：完整的 C++ 子线程回调 Java 的流程是怎样的？

> ① `JNI_OnLoad` 保存 `JavaVM` + 创建 TLS Key（注册析构函数含 `DetachCurrentThread`）。② 回调对象保存为 `GlobalRef`（用 `shared_ptr` 包裹）。③ 回调时 `getJniEnv()`：先查 TLS → 没有则 Attach → 存入 TLS → 返回。④ 通过 `GlobalRef` 调 Java 方法。⑤ 线程退出时 OS 自动调析构函数 → Detach。⑥ 引擎销毁时 `shared_ptr` 归零 → `DeleteGlobalRef`。

## 四、零拷贝（来自 04）

### Q4-1：DirectByteBuffer 为什么能做到零拷贝？

> 它背后是 Native 内存，C++ 通过 `GetDirectBufferAddress` 直接拿到内存指针，Java 和 C++ 操作的是同一块物理内存，没有 Java 堆 ↔ Native 堆之间的拷贝。而 `byte[]` 在 Java 堆上，JNI 访问时通常需要拷贝。

### Q4-2：`NewDirectByteBuffer(data, size)` 包装后，C++ 能立即 `delete[] data` 吗？

> 不能。`NewDirectByteBuffer` 只是创建了一个 Java ByteBuffer 对象指向这块 Native 内存，分配和释放仍然由 C++ 负责。如果 Java 还在用，C++ 就释放了 → 野指针。必须等 Java 确实不再访问之后才能释放。

### Q4-3：flip() 和 clear() 的区别？

> `flip()`：写完切读（`limit=position; position=0`）。`clear()`：准备重写（`position=0; limit=capacity`），**不清空底层数据**。

### Q4-4：什么时候用 DirectByteBuffer 什么时候用 byte[]？

> 小数据（<1KB）、纯 Java 处理 → `byte[]`。大块二进制（音视频帧）、高频跨 JNI、Socket/MediaCodec I/O → `DirectByteBuffer` + Buffer Pool。

## 五、综合场景题

### Q5-1：设计一个 C++ 音视频 SDK 的 JNI 回调架构，要处理视频帧（1280×720 YUV, ~1.4MB/帧, 30fps）的回调。你会怎么设计？重点关注什么？

> **线程模型**：TLS + AttachCurrentThread 缓存 `JNIEnv`（见 03），每个回调线程只 Attach 一次。
> **回调对象**：`GlobalRef` + `shared_ptr` 管理生命周期（见 02），确保多线程释放安全。
> **数据传递**：`DirectByteBuffer` 零拷贝（见 04）——C++ 分配帧内存，用 `NewDirectByteBuffer` 包装传给 Java。配合 Buffer Pool 复用（预分配 5-8 块），避免 30fps 场景下频繁分配/释放 Native 内存导致性能抖动。
> **关键风险**：① Buffer 所有权——Java 端不可在回调外持有 buffer，C++ 必须在确保 Java 不用后才回收。② 多线程——解码线程和 release 线程竞争 GlobalRef 时靠 `shared_ptr` 保证安全。

### Q5-2：线上 crash，堆栈显示 `JNI ERROR: local reference table overflow`。什么原因？怎么修？

> 在循环（遍历大量帧/文件/列表）中创建了 LocalRef 但没有释放，超出了局部引用表上限（~512）。修复：每次迭代调用 `DeleteLocalRef`，或用 `PushLocalFrame`/`PopLocalFrame` 限定引用作用域。

### Q5-3：用户反馈 App 使用一段时间后变慢，最后 OOM 崩溃。用 JNI 可能是什么原因？

> ① 忘记 `DeleteGlobalRef`：Java 对象永不 GC → 累积泄漏。② Attach 后忘记 Detach：JVM 内部线程资源累积。③ `GetXXX` 不 `ReleaseXXX`：Native 临时内存泄漏。④ 频繁 `allocateDirect`：Native 堆碎片化 → 分配变慢 → OOM。排查方法：加引用计数日志、监控 Native 内存（`mallinfo`/`dumpsys meminfo`）。
