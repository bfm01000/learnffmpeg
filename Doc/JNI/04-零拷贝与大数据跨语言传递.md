## 面试速答模板（30 秒口语化回答）

### Q：音视频数据（YUV/PCM/H264）怎么在 Java 和 C++ 之间高效传递？

> "绝对不能用 `byte[]`。用 **DirectByteBuffer**——它在 Native 内存上分配，C++ 可以通过 `GetDirectBufferAddress` 直接拿到指针，Java 和 C++ 操作同一块物理内存，实现零拷贝。C++ 分配数据后还可以用 `NewDirectByteBuffer` 包装成 ByteBuffer 传给 Java。配合 Buffer Pool 复用，避免频繁分配释放。"

### Q：DirectByteBuffer 和普通 byte[] 有什么区别？什么时候用哪个？

> "`byte[]` 在 Java 堆上，小数据、纯 Java 逻辑够用。DirectByteBuffer 在 Native 内存上，适合大块二进制数据、高频跨 JNI 传递、Socket/MediaCodec I/O。但 DirectByteBuffer 分配成本高，生命周期管理更复杂——谁分配谁释放，必须明确所有权。"

## 一、ByteBuffer 读写模型（避坑基础）

`ByteBuffer` 最容易混的是 `position`、`limit`、`capacity` 三个指针。

### 状态机

```text
初始状态（刚 allocate）：
  capacity = 8
  position = 0
  limit    = 8

写入 3 个字节后：
  position = 3    ← 写到哪里了
  limit    = 8    ← 最多写到哪里
  capacity = 8    ← 总容量（固定）

调用 flip() 切到读模式：
  limit    = 3    ← old position（只读写过的部分）
  position = 0    ← 从头读

读完后调用 clear() 准备重写：
  position = 0
  limit    = 8    ← 恢复到 capacity（注意：并不清空数据！）
```

### 核心 API

| API | 作用 |
| :--- | :--- |
| `put()` | 写数据，`position` 后移 |
| `get()` | 读数据，`position` 后移 |
| `flip()` | 写完切读：`limit=position; position=0` |
| `clear()` | 准备重写：`position=0; limit=capacity`（**不清空数据**） |
| `rewind()` | 重新读：`position=0`（不改 limit） |
| `remaining()` | 还剩多少可读：`limit - position` |

### 最容易踩的坑

```java
ByteBuffer buf = ByteBuffer.allocate(8);
buf.put((byte) 1);
buf.put((byte) 2);
// 忘记 flip()！此时 position=2，直接 get() 会从 position=2 开始读，什么都读不到

// ✅ 正确
buf.flip();  // position→0, limit→2
byte val = buf.get();  // 读到 1
```

## 二、DirectByteBuffer：零拷贝的核心

### HeapByteBuffer vs DirectByteBuffer

| 类型 | 内存位置 | 创建方式 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- | :--- |
| HeapByteBuffer | Java 堆 | `ByteBuffer.allocate(n)` | 分配快，GC 管理 | JNI 访问可能发生拷贝 |
| DirectByteBuffer | Native 内存 | `ByteBuffer.allocateDirect(n)` | JNI 零拷贝访问 | 分配/释放成本高 |

### C++ 访问 Java 分配的 DirectByteBuffer

```cpp
// Java: ByteBuffer buf = ByteBuffer.allocateDirect(1024 * 1024);
// C++:
extern "C" JNIEXPORT void JNICALL
Java_com_demo_Native_fillBuffer(JNIEnv* env, jobject /*thiz*/, jobject buffer) {
    auto* data = static_cast<uint8_t*>(env->GetDirectBufferAddress(buffer));
    jlong capacity = env->GetDirectBufferCapacity(buffer);
    if (!data || capacity <= 0) return;

    // C++ 直接写入 DirectByteBuffer 的底层 Native 内存——没有拷贝
    data[0] = 0x00;
    data[1] = 0x01;
}
```

### C++ 分配、Java 使用

```cpp
// C++ 分配 Native 内存，包装成 ByteBuffer 给 Java
void sendFrameToJava(JNIEnv* env, jobject callback, uint8_t* frameData, int size) {
    // 包装 C++ 指针为 ByteBuffer（零拷贝！Java 直接读 C++ 内存）
    jobject buffer = env->NewDirectByteBuffer(frameData, size);

    jclass clazz = env->GetObjectClass(callback);
    jmethodID mid = env->GetMethodID(clazz, "onFrame", "(Ljava/nio/ByteBuffer;)V");
    env->CallVoidMethod(callback, mid, buffer);

    env->DeleteLocalRef(buffer);
    env->DeleteLocalRef(clazz);
}
```

Java 端：
```java
@Override
public void onFrame(ByteBuffer buffer) {
    // buffer 指向的是 C++ 内存，直接读，无需拷贝
    // ⚠️ 注意：不要在 onFrame 之外持有这个 buffer！
    // 它的生命周期由 C++ 管理，函数返回后可能被释放
}
```

## 三、Native 内存生命周期管理（关键）

### 所有权铁律

> **谁分配，谁释放。释放前必须确保对方不再使用。**

### 四种常见模式

```text
模式 1：Java 分配，Java 释放（最简单）
  Java: ByteBuffer.allocateDirect(N)
  Java → C++: C++ 临时使用
  Java: buffer = null (GC 负责释放)

模式 2：Java 分配，C++ 释放（危险）
  不推荐——Java 对象和 Native 内存的生命周期绑定在 Java 端更好

模式 3：C++ 分配，C++ 释放（回调场景）
  C++: new uint8_t[N]
  C++: NewDirectByteBuffer(data, N) → 回调 Java
  Java: 读取，函数返回
  C++: delete[] data （等 Java 函数返回后！）

模式 4：Buffer Pool（高频场景推荐）
  C++: 预分配 N 块 DirectByteBuffer，组成池
  取用 → 归还 → 复用，避免频繁 alloc/free
```

### 最危险的场景

```text
C++ 线程 A: new data → NewDirectByteBuffer(data) → 回调 Java
C++ 线程 B: 同时 delete[] data
Java 线程 : 正在 onFrame 里读 buffer
              ↑ 野指针！崩溃！
```

**解法**：明确所有权或使用引用计数（见 02 的 shared_ptr 模式）。

## 四、音视频实战：MediaCodec + ByteBuffer

Android `MediaCodec` 的 Buffer 也是 ByteBuffer：

```java
// 编码器输入
int index = codec.dequeueInputBuffer(timeoutUs);
if (index >= 0) {
    ByteBuffer input = codec.getInputBuffer(index);
    input.clear();
    input.put(frameData);  // 填入 YUV 数据
    codec.queueInputBuffer(index, 0, frameSize, ptsUs, 0);
}

// 编码器输出
int index = codec.dequeueOutputBuffer(info, timeoutUs);
if (index >= 0) {
    ByteBuffer output = codec.getOutputBuffer(index);
    output.position(info.offset);
    output.limit(info.offset + info.size);
    // 从 output 中读取 H264/H265 数据
    codec.releaseOutputBuffer(index, false);
}
```

MediaCodec 的 Input/Output Buffer 通常是 DirectByteBuffer，可以直接通过 JNI 给 C++ 层。如果 C++ 层需要处理，用 `GetDirectBufferAddress` 零拷贝访问。

## 五、选型指南

| 场景 | 推荐方案 |
| :--- | :--- |
| 小数据（< 1KB）、纯 Java 处理 | `byte[]` |
| 大块数据（帧）、高频 JNI | `DirectByteBuffer` + Buffer Pool |
| C++ 产生数据，Java 只读 | C++ 分配 + `NewDirectByteBuffer`（明确声明生命周期） |
| Java 产生数据，C++ 处理 | `ByteBuffer.allocateDirect` + Buffer Pool 复用 |
| 需要 Java ↔ C++ 双向读写同一块内存 | DirectByteBuffer + 所有权明确为 Java |

## 踩过的坑

| 坑 | 现象 | 正确做法 |
| :--- | :--- | :--- |
| 忘记 `flip()` | `get()` 读不到数据 | 写完数据后调用 `flip()` |
| 以为 `clear()` 会清空数据 | 旧数据残留，造成"幽灵数据" | `clear()` 只重置指针，需要时手动 `memset` 或覆盖 |
| C++ 释放后 Java 还在读 | Native 野指针崩溃 | 明确所有权，或用 Buffer Pool 控制释放时机 |
| 频繁 `allocateDirect` | Native 内存压力大，分配慢 | Buffer Pool 复用 |
| `NewDirectByteBuffer` 后立即 `delete[]` | Java 拿到的 buffer 底层是野指针 | C++ 释放必须等 Java 确实用完 |
| Java 层长期持有回调中的 DirectByteBuffer | 阻止 C++ 释放 Native 内存 | 文档说明"不可在回调外持有"；Java 需要长期持有时主动拷贝一份 |

## 自检一问

> C++ 用 `NewDirectByteBuffer` 把一块 Native 内存传给 Java 后，C++ 什么时候能释放这块内存？

**答案**：必须在**Java 不再访问这块内存之后**。如果是同步回调（C++ → Java → 返回），Java 函数返回后就能释放。如果是异步的（Java 保存了引用），需要明确告知 Java 方"这个 buffer 的生命周期"并约定释放时机，或者让 Java 方主动拷贝一份自己管理。
