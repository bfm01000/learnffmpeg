## 面试速答模板（30 秒口语化回答）

### Q：JNI 三种引用类型有什么区别？

> "JNI 有三种引用：**LocalRef** 是函数返回就自动失效的临时引用；**GlobalRef** 是手动管理的强引用，阻止 GC，用来跨线程/跨函数保存 Java 对象；**WeakGlobalRef** 是不阻止 GC 的弱引用，用于防泄漏兜底，但用前必须检查对象是否已被 GC 杀掉。GlobalRef 和 WeakGlobalRef 用完都必须手动 Delete。"

### Q：除了忘记 DeleteGlobalRef，JNI 还有哪些常见内存泄漏？

> "一是 Get/Release 不成对——`GetStringUTFChars`、`GetByteArrayElements` 等操作底层有内存拷贝，必须配对 `ReleaseXXX`；二是局部引用表溢出——在循环里创建大量 LocalRef 不释放，超出 JVM 局部引用表上限（通常 512 个）会崩溃；三是线程 Attach 后忘记 Detach——JVM 内部资源泄漏。"

## 一、三种引用类型深度对比

JVM 的 GC 需要知道"C++ 层是否还在使用某个 Java 对象"。这就要引入"引用凭证"——它告诉 JVM 这个对象能不能回收。

| 类型 | 创建方式 | 阻止 GC | 生命周期 | 释放方式 |
| :--- | :--- | :--- | :--- | :--- |
| **LocalRef** | 默认（函数参数/返回值/JNI 函数创建） | ✅ 在作用域内阻止 | 当前 JNI 函数返回后自动失效 | 自动，也可手动 `DeleteLocalRef` |
| **GlobalRef** | `NewGlobalRef` | ✅ 永久阻止 | 直到手动释放 | **必须** `DeleteGlobalRef` |
| **WeakGlobalRef** | `NewWeakGlobalRef` | ❌ 不阻止 | 直到手动释放（但指向的对象可能已被 GC） | **必须** `DeleteWeakGlobalRef` |

### LocalRef：自动管理的临时凭证

```cpp
jclass clazz = env->FindClass("java/lang/String");  // 创建 LocalRef
// ... 使用 clazz ...
// 函数返回时 JVM 自动释放 clazz 的 LocalRef
```

**关键限制**：
- 局部引用表上限通常是 **512 个**（不同 JVM 实现不同）
- **在循环内创建大量 LocalRef 会导致引用表溢出** → `JNI ERROR: local reference table overflow`

```cpp
// ❌ 错误：循环内不释放 LocalRef
for (int i = 0; i < 1000; i++) {
    jstring str = env->NewStringUTF("hello");  // 每次创建 LocalRef
    // 512 次后崩溃！
}

// ✅ 正确：用完立即释放
for (int i = 0; i < 1000; i++) {
    jstring str = env->NewStringUTF("hello");
    // ... 使用 str ...
    env->DeleteLocalRef(str);  // 用完立即释放
}
```

### GlobalRef：跨线程/跨函数保存 Java 对象的唯一方式

```cpp
// ❌ 错误：局部引用在函数返回后失效
static jobject g_callback = nullptr;
void setCallback(JNIEnv* env, jobject callback) {
    g_callback = callback;  // callback 是 LocalRef！函数返回后失效！
}

// ✅ 正确：转成 GlobalRef
void setCallback(JNIEnv* env, jobject callback) {
    if (g_callback) env->DeleteGlobalRef(g_callback);  // 释放旧的
    g_callback = env->NewGlobalRef(callback);          // 创建新的
}
```

### WeakGlobalRef：防泄漏兜底

`WeakGlobalRef` 不阻止 GC 回收它指向的 Java 对象。但由于它不阻止 GC，用前必须先检查对象是否还活着：

```cpp
jweak weakRef = env->NewWeakGlobalRef(localObj);

// 使用时检查
if (env->IsSameObject(weakRef, nullptr)) {
    // 对象已被 GC 回收，不能再用了
    env->DeleteWeakGlobalRef(weakRef);
    return;
}
// 对象还活着，可以正常使用
env->CallVoidMethod(weakRef, methodId);
```

> ⚠️ **WeakGlobalRef 的双层"回收"陷阱**：虽然它不阻止 Java 对象被 GC，但**弱引用凭证本身**会一直占用 JNI 引用表空间。即使 Java 对象被 GC 了，C++ 层仍然必须调用 `DeleteWeakGlobalRef` 释放凭证。否则引用表终将塞满失效凭证 → **JNI global reference table overflow** 崩溃。

## 二、RAII 封装：让 C++ 自动管理 JNI 资源

手动调 `DeleteGlobalRef` 极易遗漏——异常提前 return、多线程竞争释放时都是坑。RAII 封装是标准解法。

### GlobalRef RAII 包装类

```cpp
class JniGlobalRef {
private:
    JavaVM* jvm_;
    jobject globalRef_;

public:
    // 构造：从 LocalRef 创建 GlobalRef
    JniGlobalRef(JNIEnv* env, jobject localRef)
        : globalRef_(nullptr) {
        env->GetJavaVM(&jvm_);
        if (localRef) {
            globalRef_ = env->NewGlobalRef(localRef);
        }
    }

    // 析构：自动 DeleteGlobalRef
    ~JniGlobalRef() {
        if (globalRef_) {
            JNIEnv* env = getEnvForCurrentThread();  // 见 01
            if (env) env->DeleteGlobalRef(globalRef_);
        }
    }

    jobject get() const { return globalRef_; }

    // 禁用拷贝（Rule of 5）
    JniGlobalRef(const JniGlobalRef&) = delete;
    JniGlobalRef& operator=(const JniGlobalRef&) = delete;
    JniGlobalRef(JniGlobalRef&& other) noexcept
        : jvm_(other.jvm_), globalRef_(other.globalRef_) {
        other.globalRef_ = nullptr;
    }
};
```

### 结合 shared_ptr 实现多线程安全释放

这是区分"懂 JNI"和"精通 JNI"的关键点。

**场景**：Java 层调了 `release()`，C++ 要释放 GlobalRef。但此时解码线程可能正在回调中途拿着这个 ref。纯手动管理 → 野指针崩溃。

**解法**：`shared_ptr` 引用计数保证最后一个使用者退出后才释放。

```cpp
std::shared_ptr<JniGlobalRef> g_smartCallback;

// Java 层 setCallback
void setCallback(JNIEnv* env, jobject callback) {
    if (callback) {
        g_smartCallback = std::make_shared<JniGlobalRef>(env, callback);
    } else {
        g_smartCallback = nullptr;  // 引用计数 -1，引用归零时自动析构
    }
}

// C++ 子线程回调
void notifyJava() {
    // 拷贝 shared_ptr，引用计数 +1——即使此时 release 被调用，对象也不会析构
    auto safeRef = g_smartCallback;
    if (!safeRef) return;

    JNIEnv* env = getEnvForCurrentThread();
    // safeRef->get() 安全——只要 safeRef 在栈上，GlobalRef 就不会被释放
    env->CallVoidMethod(safeRef->get(), onEventMethod);
    // safeRef 离开作用域，引用计数 -1
}
```

## 三、Get/Release 配对：另一种常见泄漏

当 C++ 要从 Java 数组/字符串读取数据时，JNI 提供了 `GetXXX` 系列 API。它们底层可能发生**内存拷贝**，必须用 `ReleaseXXX` 归还。

| Get 操作 | Release 操作 | 用途 |
| :--- | :--- | :--- |
| `GetStringUTFChars` | `ReleaseStringUTFChars` | Java String → C++ `const char*` |
| `GetStringChars` | `ReleaseStringChars` | Java String → C++ `const jchar*` (UTF-16) |
| `GetByteArrayElements` | `ReleaseByteArrayElements` | Java `byte[]` → C++ `jbyte*` |
| `GetIntArrayElements` | `ReleaseIntArrayElements` | Java `int[]` → C++ `jint*` |
| `GetPrimitiveArrayCritical` | `ReleasePrimitiveArrayCritical` | 零拷贝访问（但会暂停 GC） |

```cpp
// ❌ 错误：忘记 Release
void processString(JNIEnv* env, jstring javaStr) {
    const char* cstr = env->GetStringUTFChars(javaStr, nullptr);
    // 使用 cstr...
    // 忘记 ReleaseStringUTFChars → 泄漏！
}

// ✅ 正确：RAII 自动释放
class JStringRef {
    JNIEnv* env_;
    jstring jstr_;
    const char* cstr_;
public:
    JStringRef(JNIEnv* env, jstring jstr)
        : env_(env), jstr_(jstr),
          cstr_(env->GetStringUTFChars(jstr, nullptr)) {}
    ~JStringRef() {
        if (cstr_) env_->ReleaseStringUTFChars(jstr_, cstr_);
    }
    const char* c_str() const { return cstr_; }
};
```

## 四、业界实践：GlobalRef vs WeakGlobalRef 怎么选

### 大厂偏好：GlobalRef + 强制释放

WebRTC、ExoPlayer 等顶级项目极少用 `WeakGlobalRef` 作为回调对象首选。原因：

- **回调神秘消失**：如果 Java 层传了匿名内部类 `engine.setListener(new Listener(){...})`，WeakGlobalRef 不阻止 GC → 触发一次 GC 这个匿名对象就被杀掉了 → 回调静默消失，无日志无崩溃，排查成本极高。

### 业界标准做法

1. **底层用 GlobalRef 强锁**：传过来的回调对象，无条件 `NewGlobalRef`，确保回调不消失
2. **提供强制释放接口**：不依赖上层零散的 `setListener(null)`，提供 `engine.release()` 做一键清理
3. **不替业务方擦屁股，但会报警**：如果 Java 层忘了调 `release()`，在 `finalize()` 或 `Cleaner` 里打印醒目的错误日志

## 踩过的坑

| 坑 | 现象 | 正确做法 |
| :--- | :--- | :--- |
| 局部引用保存到全局变量 | 函数返回后野指针，随机崩溃 | 转成 GlobalRef 再保存 |
| 忘记 DeleteGlobalRef | Java 对象永不 GC → 内存泄漏，严重时 OOM | RAII 封装 + shared_ptr 自动管理 |
| 循环内不释放 LocalRef | 引用表溢出崩溃（~512 个） | `DeleteLocalRef` 或 `PushLocalFrame`/`PopLocalFrame` |
| Get 不 Release | JVM 内部 Native 内存泄漏 | 配对调用，或 RAII 包装 |
| WeakGlobalRef 不 Delete | 失效凭证塞满引用表 → overflow 崩溃 | DeleteWeakGlobalRef 仍然必须调用 |
| 多线程下释放 GlobalRef | 解码线程还在用，野指针崩溃 | shared_ptr 引用计数保护，见 [[03-跨线程回调架构与TLS优化]] |
| GetPrimitiveArrayCritical 中做重操作 | 暂停 GC，长时间卡顿 | Critical 区域极短，做完立刻 Release；或在 04 中改用 DirectByteBuffer 零拷贝 |

## 自检一问

> 为什么实际 SDK 开发中，回调对象不用 `WeakGlobalRef` 而用 `GlobalRef`？既然用 GlobalRef，怎么防止 Java 层忘记解绑导致泄漏？

**答案**：WeakGlobalRef 不阻止 GC——如果 Java 层传的是匿名内部类，GC 一触发回调就静默消失，排查成本极高。所以用 GlobalRef 强锁，同时提供 `release()` 接口做强制清理，并在 `finalize()` 中报日志警告。多线程安全则靠 `shared_ptr` 引用计数保证。
