# 端到端采集编码推流管线：从 Camera2 到 RTMP

## 0. 本篇定位

- 面试复习：先背熟 `Camera2 -> SurfaceTexture/OES -> FBO/滤镜 -> MediaCodec Surface -> H.264 -> RTMP` 这条主链路。
- 深入学习：重点看线程模型、时间戳来源、SPS/PPS 发送时机、JNI 边界和渲染抽象层带来的性能权衡。
- 工程落点：端到端问题通常不是某个 API 写错，而是采集、渲染、编码、网络四个队列之间的背压和时钟没有设计好。
> **适用方向**：Android 直播推流/RTC
> **难度**：⭐⭐⭐⭐（1-5 星）
> **预计阅读**：速记 10 分钟｜全文 30 分钟

## 二、核心 Demo：LiveStreamer

```java
// LiveStreamer.java — Android 端到端推流器
package com.example.livestream;

public class LiveStreamer {
    private Camera2CaptureManager camera;
    private MediaCodecEncoder videoEncoder;
    private AudioCapture audioCapture;
    private AudioEncoder audioEncoder; // MediaCodec AAC or FFmpeg
    private NativePusher nativePusher; // C++ RTMP (JNI bridge)
    private HandlerThread streamThread;

    private int width = 720, height = 1280;
    private int fps = 30, videoBitrate = 2_000_000;
    private int audioSampleRate = 48000, audioBitrate = 96000;

    public LiveStreamer() {
        streamThread = new HandlerThread("StreamThread");
        streamThread.start();
        nativePusher = new NativePusher(); // JNI 加载 C++ so 库
    }

    // ============================================================
    // 启动推流
    // ============================================================
    public void startPushing(String rtmpUrl) {
        // ④ 连接 RTMP (C++ 层)
        nativePusher.connect(rtmpUrl, width, height, fps, videoBitrate);

        // ③ 初始化解码器
        videoEncoder = new MediaCodecEncoder(width, height, fps, videoBitrate,
            (data, info, isKeyFrame) -> {
                // ★ Android 编码输出已是 Annex-B, 直接推!
                int ptsMs = (int)(info.presentationTimeUs / 1000);
                if (isKeyFrame) {
                    // 确认 SPS/PPS 已在 IDR 前面 (Annex-B 自动带)
                    nativePusher.sendVideoKeyFrame(data, info.size, ptsMs);
                } else {
                    nativePusher.sendVideoFrame(data, info.size, ptsMs);
                }
            });
        videoEncoder.start();

        // ③ 初始化音频编码器 (MediaCodec AAC)
        audioEncoder = new AudioEncoder(audioSampleRate, audioBitrate,
            (aacData, length, ptsMs) -> {
                nativePusher.sendAudioFrame(aacData, length, ptsMs);
            });
        audioEncoder.start();

        // ② 启动音频采集
        audioCapture = new AudioCapture((pcm, length) -> {
            audioEncoder.encodePCM(pcm, length);
        });

        // ① 启动视频采集 (最后启动, 因为一启动就开始回调)
        camera = new Camera2CaptureManager(context);
        camera.choosePreviewSize(getBackCameraId(), width, height);
        camera.openCamera(getBackCameraId(), (yuvData, w, h, yStride, uvStride, uvPixel, ts) -> {
            long ptsUs = ts / 1000; // nano → micro
            videoEncoder.encodeNV12(yuvData, ptsUs);
        });
    }

    // ============================================================
    // 动态控制
    // ============================================================
    public void adjustBitrate(int newBitrate) {
        videoEncoder.setBitrate(newBitrate);
    }

    public void forceKeyFrame() {
        videoEncoder.forceKeyFrame();
    }

    // ============================================================
    // 停止 (★正确的停止顺序★)
    // ============================================================
    public void stopPushing() {
        // ① 先停采集 (不再有新帧)
        if (camera != null) camera.close();

        // ② 停编码器 (flush + release)
        if (videoEncoder != null) videoEncoder.stop();
        if (audioEncoder != null) audioEncoder.stop();

        // ③ 停音频
        if (audioCapture != null) audioCapture.stop();

        // ④ 断开推流
        nativePusher.disconnect();
    }
}
```

## 三、JNI 桥接（C++ 推流引擎）

```cpp
// native_pusher.cpp — JNI 桥接
#include <jni.h>
#include "rtmp_pusher.h"  // 你的 C++ RTMP 推流引擎

static RTMPPusher *g_pusher = nullptr;

extern "C"
JNIEXPORT void JNICALL
Java_com_example_livestream_NativePusher_connect(JNIEnv *env, jobject thiz,
    jstring url, jint w, jint h, jint fps, jint bitrate) {
    const char *cUrl = env->GetStringUTFChars(url, nullptr);
    g_pusher = new RTMPPusher();
    g_pusher->connect(cUrl, w, h, fps, bitrate);
    env->ReleaseStringUTFChars(url, cUrl);
}

extern "C"
JNIEXPORT void JNICALL
Java_com_example_livestream_NativePusher_sendVideoFrame(JNIEnv *env, jobject thiz,
    jobject data, jint size, jint ptsMs) {
    // ★ 零拷贝：用 DirectByteBuffer
    uint8_t *buf = (uint8_t *)env->GetDirectBufferAddress(data);
    if (buf && g_pusher) {
        g_pusher->sendVideoFrame(buf, size, ptsMs);
    }
}

extern "C"
JNIEXPORT void JNICALL
Java_com_example_livestream_NativePusher_sendAudioFrame(JNIEnv *env, jobject thiz,
    jobject data, jint size, jint ptsMs) {
    uint8_t *buf = (uint8_t *)env->GetDirectBufferAddress(data);
    if (buf && g_pusher) {
        g_pusher->sendAudioFrame(buf, size, ptsMs);
    }
}
```

## 五、常见坑

### 坑 1：采集分辨率 ≠ MediaCodec 分辨率

Camera2 选的 size 和 MediaCodec configure 的分辨率不一致 → 编码失败或画面变形。**两个值必须一致**。

### 坑 2：Annex-B 数据里的起始码和长度前缀混淆

Android 输出 Annex-B，但 `bufferInfo.size` 和读取方式如果用错（当成 AVCC 按长度前缀读），会切错 NALU 边界。**Android 直接用起始码切 NALU，不要按长度前缀切**。

### 坑 3：音频和视频不在同一时钟域

AudioRecord 的 timestamp 和 Camera2 的 timestamp 来自不同硬件时钟，长时间运行会漂移。**对同步要求高的场景用 AudioRecord 的 timestamp 作为时钟基准**。

### 坑 4：Surface 编码状态下不能换码率？

有些厂商设备在 Surface 输入模式下 `setParameters(KEY_VIDEO_BITRATE)` 不生效——要换回 ByteBuffer 模式。**查厂商适配文档**。

## 六、跨平台渲染架构：RHI 与 Oryol

> 这一节适用于项目使用跨平台渲染引擎（如 Oryol、Unity、Unreal）的面试场景。核心问题是：「跨平台引擎很方便，但在极限性能场景下它怎么变成瓶颈的？」

### 6.1 RHI（Render Hardware Interface）是什么

RHI 是业务代码和底层图形 API（OpenGL/Metal/Vulkan）之间的一层**纯抽象 C++ 接口**。它的核心价值是「一套渲染算法，到处运行」：

```text
业务层 C++ 渲染逻辑（全景拼接/美颜/滤镜）
        │
        ▼
    RHI 抽象层 (gfx().Draw() / gfx().BeginPass() / ...)
        │
    ┌───┴───┬───────┐
    ▼       ▼       ▼
  glRenderer  mtlRenderer  vkRenderer
 (Android)    (iOS/macOS)  (跨平台)
```

- Android 编译 → 链接 `glRenderer` → 翻译成 `glDrawArrays`
- iOS 编译 → 链接 `mtlRenderer` → 翻译成 Metal `[renderEncoder drawPrimitives:]`

### 6.2 RHI 的「兼容性诅咒」

跨平台引擎为了保证 100% 兼容，在 **I/O 边缘地带**（数据进出 GPU）往往采用最保守的方案：

- 引擎提供 `ReadFrame()` 接口导出渲染结果
- 底层为确保在所有破设备上都能跑，用的是阻塞式 `glReadPixels`
- 4K 场景下单帧 30ms → 整条链路被拖垮

**结论：跨平台引擎在「画图指令翻译」上完美，在「内存零拷贝流转」上是盲区**——因为 `AHardwareBuffer`（Android）/ `IOSurface`（iOS）属于 OS 媒体流转机制，不在标准图形 API 范畴。

### 6.3 工程上的解法：击穿黑盒，平台定制

不抛弃 RHI（保留算法跨平台复用），但在流转边缘做**针对性特化**：

```text
核心算法层：继续用 RHI 的 gfx().Draw() — 跨平台零改动
    │
流转输出层：击穿 RHI 黑盒
    ├── Android: AHardwareBuffer + Surface → MediaCodec
    └── iOS:     CVPixelBuffer → VideoToolbox
```

面试话术：
> 「跨平台引擎的 ReadFrame 在 Android 底层是 glReadPixels，4K 下直接 30ms。我的优化不是在引擎内部改，而是在渲染管线的输出端和编码器输入端之间，用 Android NDK 专属的 AHardwareBuffer + Surface 机制搭了一座零拷贝天桥。核心算法继续跨平台，I/O 流转做平台特化——这是架构通用性与极限性能之间的最佳折中。」

### 6.4 iOS vs Android 零拷贝对比（跨平台视野加分项）

| | Android | iOS |
|---|---|---|
| 共享内存机制 | `AHardwareBuffer` / Gralloc | `IOSurface` / `CVPixelBuffer` |
| 硬件编码器 | MediaCodec | VideoToolbox |
| GPU 纹理桥接 | EGLImage → OES Texture | `CVMetalTextureCache` |
| 开发者体验 | 需精细控制 USAGE 标志位、处理碎片化 | 系统自动协商最优内存布局、API 统一 |
| 核心差异 | Google 无法控制硬件 → 开发者自己谈判 | Apple 软硬一体 → 底层硬件 MMU Unswizzler 透明处理 De-tiling |

**Apple 的「黑魔法」没有打破物理定律**：`CVPixelBufferLockBaseAddress` 背后同样要 De-tiling，只是 Apple 用硬件 MMU + Unswizzler 在几百 GB/s 带宽下瞬间完成，开发者感知不到而已。

## 一句话总结
> Android 端到端推流 = Camera2 采 YUV → MediaCodec 编 H.264(Annex-B, 无需格式转换) → JNI 桥接 C++ RTMP 推流引擎。音频 AudioRecord 采 PCM → MediaCodec 编 AAC → 同一条推流通道。停止顺序：采集→编码→音频→断开。
