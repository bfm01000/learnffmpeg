## 一、内联函数 inline

### 1. 什么是内联函数？为什么引入？

普通函数调用底层有压栈、跳转、执行、弹栈、返回一系列开销。若函数极短小又被频繁调用（如大循环里），调用开销就成了瓶颈。`inline` 建议编译器在**编译期**把函数体**直接在调用点展开**，省去调用开销——典型的**空间换时间**。

### 2. inline 和宏定义 `#define` 的本质区别（🔥 必考）

`inline` 是用来全面取代宏函数的，四大区别：

| 维度 | 宏定义 `#define` | 内联函数 `inline` |
| :--- | :--- | :--- |
| 处理阶段 | **预处理**阶段纯文本替换 | **编译**阶段处理 |
| 类型安全 | 不检查参数类型，极易出错 | 真正的函数，严格类型检查 |
| 参数副作用 | 参数可能被多次求值（`MAX(a++,b++)`） | 先算出参数值再传入，安全 |
| 作用域/调试 | 无作用域、全局污染、不能单步调试 | 遵守类访问控制、可单步调试 |

**宏的致命副作用示例：**

```cpp
#define MAX_MACRO(a, b) ((a) > (b) ? (a) : (b))
inline int maxInline(int left, int right) { return left > right ? left : right; }

int counter = 5;
int result = MAX_MACRO(counter++, 1);
// 替换为 ((counter++) > (1) ? (counter++) : (1))
// counter(5) > 1 成立，于是又执行一次 counter++，counter 被自增两次！逻辑崩溃

int value = 5;
int safe = maxInline(value++, 1); // value++ 先算出 5 传入，value 只 +1，符合直觉
```

### 3. 加了 inline 就一定会内联吗？

**不是。** `inline` 对编译器只是**强烈建议，不是命令**。若函数体含复杂循环、递归、或代码量较大，编译器会判断“代码膨胀（可执行文件变大、降低 CPU 缓存命中率）”的代价大于省下的调用开销，于是无视 `inline`，当普通函数编译。

### 4. 深挖：虚函数可以是内联函数吗？（inline + virtual）

> 这是 inline 与多态的交叉点，[08-继承、多态、虚函数与对象模型](08-继承、多态、虚函数与对象模型.md) 只给结论，原理在此。

**语法上可以，效果取决于调用方式**——因为 `inline` 是编译期静态展开，`virtual` 是运行期动态绑定，逻辑上冲突：

1. **用对象本身（按值）调用**：`Foo obj; obj.func();` 编译期已确定真实类型，静态绑定，若该虚函数标了 `inline`，**会**内联展开。
2. **用指针/引用调用**：`Foo* p = ...; p->func();` 发生多态，必须运行期查虚表才知道调谁，编译期都不知道调用目标，**无法**内联，`inline` 失效。
3. **（加分）去虚化 Devirtualization**：现代 GCC/Clang 若能推断指针绝不可能指向其它子类（或类被 `final` 修饰），会把动态绑定优化成静态绑定，此时也能内联。

### 5. 深挖：为什么内联函数的实现通常必须写在头文件？

由 **单一定义规则（ODR）** 和分文件编译机制决定。C++ 按编译单元（Translation Unit）独立编译：若内联函数声明在 `.h`、实现在 `a.cpp`，那么 `b.cpp` 包含头文件调用它时，编译器**只看得到声明、看不到实现**，自然无法在调用点展开；而 `a.cpp` 因 `inline` 可能已就地展开、没生成独立符号，最终链接时 `b.cpp` 找不到该函数，报 **未解析的外部符号（LNK2019）**。所以内联函数实现必须放头文件，让每个 `#include` 它的编译单元都能看到完整代码、各自展开。

### 6. 类内定义隐式内联

```cpp
class Sample {
public:
    int getValue() const { return value; }   // 类内定义 → 隐式 inline，无需手写关键字
    void setValue(int newValue);              // 仅声明
private:
    int value = 0;
};
// 类外实现若想内联，必须显式加 inline，且与类定义同在一个头文件
inline void Sample::setValue(int newValue) { value = newValue; }
```

### 7. 何时该用 inline

- **推荐**：极短函数（1~5 行）、被极频繁调用的函数（getter/setter、热循环里的数学计算）、替代所有宏函数。
- **不要**：函数体很长、含复杂 `while/for`、递归函数、含大量 I/O 的函数（I/O 耗时远大于调用开销，内联无意义）。

## 二、explicit：禁止隐式构造与隐式类型转换

### 1. 为什么需要 explicit？

单参数构造函数会被编译器拿去做**隐式类型转换**：

```cpp
class LiveConfig {
public:
    LiveConfig(int bitrate) : bitrate_(bitrate) {}  // 单参构造
private:
    int bitrate_ = 0;
};

LiveConfig config = 8000000;     // 编译器偷偷调用 LiveConfig(8000000)——看起来像赋值，实则构造

void startLive(const LiveConfig& config);
startLive(8000000);              // 更危险：int 被自动构造成配置对象，调用方可能毫无察觉
```

这种“看起来不是构造、却偷偷构造”的行为可读性差、易藏 Bug。

### 2. 加上 explicit 后

```cpp
class LiveConfig {
public:
    explicit LiveConfig(int bitrate) : bitrate_(bitrate) {}
private:
    int bitrate_ = 0;
};

// LiveConfig config = 8000000; // ❌ 编译失败：禁止隐式构造
// startLive(8000000);          // ❌ 编译失败：不能把 int 偷偷转成 LiveConfig
LiveConfig config(8000000);                 // ✅ 必须显式
startLive(LiveConfig(8000000));             // ✅ 意图清晰
```

### 3. 实践建议

- **单参数构造函数尽量加 `explicit`**，尤其是 `FrameId`、`Bitrate`、`Url`、`LiveConfig` 这类有明确业务语义的强类型，避免普通整数/字符串被误传进去。
- 只有当你**确实希望**类型间自然转换时才不加（如某些轻量包装、数学类型）。
- C++11 列表初始化后，多参数构造也可能通过 `{}` 触发隐式构造，必要时多参构造也加 `explicit`；面试重点掌握单参情形即可。

## 三、volatile：是什么？为什么不能替代锁？（完整版）

> 并发相关文档（[01-多线程与锁](01-多线程与锁.md)、[02-原子操作与内存序](02-原子操作与内存序.md)、[03-无锁队列](03-无锁队列.md)）只给“`volatile` 不是同步工具”的结论与对比表，完整论证在这里。

### 1. volatile 的真正含义

> 告诉编译器：这个变量可能被“程序正常控制流之外”的因素改变，所以每次访问都必须真的去内存读写，不要优化掉。

典型场景：**内存映射硬件寄存器**、**信号处理函数会改的变量**、**特殊底层 I/O**。

```cpp
volatile int* statusRegister = reinterpret_cast<volatile int*>(0x1000);
while ((*statusRegister & 0x1) == 0) {
    // 每次循环都必须重新读硬件寄存器；没有 volatile，编译器可能缓存其值导致死循环
}
```

它限制的只是**编译器优化**：保证每次都发起读写指令。但这**不代表多线程下读写就安全**。

### 2. 为什么不能替代锁？

多线程安全要解决三件事，`volatile` 一件都没完整解决：

1. **原子性**：操作能否被切到一半。
2. **可见性**：一个线程写入后其它线程能否可靠看到。
3. **有序性**：读写顺序会不会被 CPU/编译器重排。

**不保证原子性**：

```cpp
volatile int counter = 0;
void increase() { ++counter; } // 底层是 读-改-写 三步
// 两线程同时各读到 0、各写回 1，执行两次后结果是 1 而非 2 —— 数据竞争
```
正确做法用 `std::atomic`（见 [02-原子操作与内存序](02-原子操作与内存序.md)）：`counter.fetch_add(1, std::memory_order_relaxed);`

**不保证线程间同步语义（happens-before）**：

```cpp
volatile bool ready = false;
int data = 0;
void producer() { data = 42; ready = true; }
void consumer() {
    while (!ready) {}
    use(data); // 标准不保证看到 ready==true 时一定看到 data==42
}
```
`volatile` 不能建立 happens-before。正确做法用 atomic 的 acquire/release，或直接 `mutex` + `condition_variable`（见 [01-多线程与锁](01-多线程与锁.md)、[02-原子操作与内存序](02-原子操作与内存序.md)）。

### 3. 三者对比

| 工具 | 解决什么 | 典型用途 |
| :--- | :--- | :--- |
| `volatile` | 防止编译器优化掉对特殊内存的访问 | 硬件寄存器、内存映射 I/O、信号变量 |
| `std::atomic` | 原子操作 + 线程间内存序 | 计数器、状态标志、无锁同步 |
| `std::mutex` | 保护临界区，同一时间只有一个线程进入 | 容器、复杂对象、多步业务逻辑 |

一句话判断：**和硬件/特殊内存打交道用 `volatile`；多线程共享简单变量用 `std::atomic`；保护复杂对象或多步逻辑用 `std::mutex`**。`volatile` 管的是编译器优化，不是线程安全。

### 4. 与 Java volatile 的区别（Android 面试常踩）

| | C++ `volatile` | Java `volatile` |
| :--- | :--- | :--- |
| 主要目的 | 防止编译器优化对“特殊内存”的访问 | 保证多线程可见性 + 禁止部分重排序 |
| 能否当线程同步 | **不能** | **可以**（对单一变量） |
| C++ 等价物 | 无直接等价：MMIO 用 `volatile`，线程同步用 `atomic` | — |

背一句：**“C++ 的 volatile ≠ Java 的 volatile；在 C++ 里做线程同步请用 atomic / mutex。”**

### 5. 双重检查锁定（DCL）不能用 volatile 指针

经典的单例 DCL 需要 release/acquire 语义保证“对象构造完成”与“指针发布”的顺序，C++ 的 `volatile` 不提供这些语义。正确做法：用 `std::atomic` 指针 + `memory_order`（见 [02-原子操作与内存序](02-原子操作与内存序.md)），或直接用 `std::call_once` / C++11 起线程安全的函数内静态局部变量（Meyers' Singleton）。

```cpp
// ✅ 最简单正确的线程安全单例：函数内静态局部变量，C++11 保证初始化只发生一次且线程安全
Singleton& instance() {
    static Singleton only;
    return only;
}
```
