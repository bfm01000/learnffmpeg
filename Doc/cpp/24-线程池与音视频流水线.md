## 一、为什么要线程池？

### 1. 裸 `std::thread` 的代价

很直觉的写法是：来一个任务就开一个线程。

```cpp
// 反面教材：每个任务都新建线程
void handleFrame(Frame frame) {
    std::thread worker([frame = std::move(frame)] {
        decode(frame);
    });
    worker.detach();
}
```

这在高频场景里有三个硬伤：

1. **创建/销毁成本**：一个线程通常要分配栈（默认 1~8MB）、向内核注册调度实体、初始化 TLS。创建和销毁都是系统调用，微秒级开销。30fps 视频每秒 30 帧、每帧又拆成多个任务，频繁建销线程的开销会非常可观。
2. **线程数量失控**：任务来得比处理快时，线程数会暴涨。几千个线程会让调度器疯狂上下文切换，内存被线程栈吃光，最终 OOM 或卡死。这点和 [[04-信号量]] 里「限流并发」要解决的问题是一回事。
3. **没有解耦**：任务的「提交」和「执行」绑死在一起，提交方被迫关心线程生命周期，无法做排队、优先级、背压。

### 2. 线程池解决什么

> **面试标准回答：**
> 线程池预先创建固定数量的 worker 线程，让它们循环地从一个共享任务队列里取任务执行。好处有三点：一是**复用线程**，把创建销毁成本摊销到整个生命周期，几乎为零；二是**控制并发度**，线程数固定，不会因为任务暴涨而把机器拖垮；三是**解耦提交与执行**，提交方只管把任务丢进队列拿一个 `future`，至于哪个线程、什么时候跑，由池子调度。本质就是一个「生产者-消费者模型」：提交方是生产者，worker 是消费者，中间是带锁的任务队列。

### 3. 线程数与 CPU 核数的关系

| 任务类型 | 推荐线程数 | 原因 |
|---|---|---|
| CPU 密集（纯计算、软解码、像素处理） | ≈ 物理核数（或核数 +1） | 再多线程也没有空闲核去跑，只会增加上下文切换 |
| IO / 阻塞密集（网络拉流、磁盘读写） | 远大于核数（核数 × N） | 线程多数时间在阻塞等待，多开线程才能压满 CPU |
| 混合型 | `核数 × (1 + 等待时间/计算时间)` | 经典经验公式，按阻塞比例放大 |

```cpp
const unsigned int coreCount = std::thread::hardware_concurrency(); // 注意可能返回 0
const unsigned int workerCount = std::max(1u, coreCount);
```

> 音视频场景里，软解码/编码是 CPU 密集，线程数贴近核数；但播放器里渲染线程、音频回调线程、网络线程通常**单独固定**，不放进通用计算池，避免计算任务抢占实时线程的时间片。`hardware_concurrency()` 可能返回 0（无法探测），必须做兜底。

## 二、线程池完整实现（核心，可编译）

下面给一个生产可用的线程池。它包含：任务队列、worker 循环、`submit` 返回 `future`、完美转发、优雅停止。机制层（mutex / 条件变量 / 谓词防虚假唤醒）见 [[01-多线程与锁]]，这里只讲怎么拼装。

### 1. 类定义与数据成员

```cpp
#include <atomic>
#include <condition_variable>
#include <functional>
#include <future>
#include <memory>
#include <mutex>
#include <queue>
#include <stdexcept>
#include <thread>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(std::size_t workerCount);
    ~ThreadPool();

    // 禁止拷贝：池子持有线程和锁，拷贝语义没有意义
    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    // 提交任务，返回 future 以便拿到返回值（实现见下文）
    template <typename Func, typename... Args>
    auto submit(Func&& func, Args&&... args)
        -> std::future<std::invoke_result_t<Func, Args...>>;

    void shutdown(); // 优雅停止：处理完已入队任务再退出

private:
    std::vector<std::thread> workerThreads;          // worker 线程集合
    std::queue<std::function<void()>> taskQueue;     // 任务队列（类型擦除后的可调用对象）

    std::mutex queueMutex;                           // 保护 taskQueue 和 stopRequested
    std::condition_variable taskAvailable;           // 「有任务 / 该退出」的通知
    bool stopRequested = false;                      // 停止标志（锁内置位，故用普通 bool）
};
```

> **为什么 `stopRequested` 用普通 `bool` 而不是 `std::atomic<bool>`？** 因为它的读写**始终在 `queueMutex` 保护下**进行——mutex 本身就提供了互斥和 happens-before 可见性（见 [[02-原子操作与内存序]]）。如果停止标志要在锁外被读取（例如 worker 在长循环里频繁查），那就改用 `std::atomic<bool>` 更合适。这里所有访问都在锁内，普通 bool 就够，且能和谓词检查在同一临界区原子完成。

### 2. worker 线程循环 + 构造函数

worker 的核心是一个死循环：**抢锁 → 等到「有任务」或「该退出」→ 取任务 → 解锁 → 执行**。注意执行任务必须在**锁外**，否则一个慢任务会卡住整个队列。

```cpp
ThreadPool::ThreadPool(std::size_t workerCount) {
    if (workerCount == 0) {
        workerCount = 1; // 至少一个 worker，避免空池吞任务
    }
    workerThreads.reserve(workerCount);

    for (std::size_t index = 0; index < workerCount; ++index) {
        workerThreads.emplace_back([this] {
            for (;;) {
                std::function<void()> task;
                {
                    std::unique_lock<std::mutex> lock(queueMutex);
                    // 谓词防虚假唤醒（机制见 [[01-多线程与锁]]）：
                    // 队列非空 → 取任务干活；已请求停止 → 跳出
                    taskAvailable.wait(lock, [this] {
                        return stopRequested || !taskQueue.empty();
                    });

                    // 已请求停止且队列已空 → 退出。
                    // 注意：先把存量任务排干，再退出（优雅停止语义）
                    if (stopRequested && taskQueue.empty()) {
                        return;
                    }

                    task = std::move(taskQueue.front());
                    taskQueue.pop();
                } // 出作用域释放锁，关键：执行任务时不持锁

                task(); // 在锁外执行，慢任务不阻塞其他 worker 取任务
            }
        });
    }
}
```

> **面试标准回答（worker 为什么在锁外执行任务）：**
> worker 只在「读写队列」这段极短的临界区内持锁，取出任务后立刻解锁再执行。如果在持锁状态下执行任务，那这个任务跑多久，其他 worker 就被挡多久，线程池退化成串行。所以临界区只做「判断队列状态 + 取任务」，执行放在锁外，这也呼应 [[01-多线程与锁]] 里「临界区尽量短、锁里不做耗时操作」的原则。

### 3. 优雅停止：`shutdown` 与析构

停止线程池最容易写出 bug 的地方是**退出死锁**：worker 卡在 `wait` 上没人唤醒，主线程在 `join` 上永远等。正确做法是「置位停止标志 → `notify_all` 把所有 worker 从 `wait` 里叫醒 → `join`」。

```cpp
void ThreadPool::shutdown() {
    {
        std::lock_guard<std::mutex> lock(queueMutex);
        if (stopRequested) {
            return; // 幂等：重复调用安全
        }
        stopRequested = true;
    }
    taskAvailable.notify_all(); // 唤醒所有 wait 的 worker，让它们重新检查谓词

    for (std::thread& worker : workerThreads) {
        if (worker.joinable()) {
            worker.join(); // 等所有 worker 把存量任务跑完并退出
        }
    }
}

ThreadPool::~ThreadPool() {
    shutdown(); // RAII：析构时确保线程都被 join，不会 std::terminate
}
```

> **三个关键点**：① 置位 `stopRequested` 必须**在锁内**，否则可能和 worker 的谓词检查产生竞态导致丢唤醒（lost wakeup，见 [[01-多线程与锁]]）；② `notify_all` 而非 `notify_one`——要唤醒**每一个** worker，否则只有一个醒来退出，其余继续睡；③ `notify` 放在锁外，减少「被唤醒线程立刻又抢不到锁」的无谓切换。

### 4. `submit`：返回 `future` 的模板实现（难点）

这是面试官最爱追问的部分，考点集中在三个：**完美转发参数**、**用 `packaged_task` 把任意返回值类型擦除进 `function<void()>`**、**返回 `future` 给调用方拿结果**。

```cpp
template <typename Func, typename... Args>
auto ThreadPool::submit(Func&& func, Args&&... args)
    -> std::future<std::invoke_result_t<Func, Args...>> {

    using ReturnType = std::invoke_result_t<Func, Args...>; // C++17 推导返回类型

    // 1. 用 bind 把函数和参数打包成一个无参可调用对象（完美转发，见 [[07-移动语义与右值引用]]）
    //    包成 packaged_task：调用它时会把返回值塞进关联的 future（见 [[09-现代C++特性（C++11到17）]]）
    auto packagedTask = std::make_shared<std::packaged_task<ReturnType()>>(
        std::bind(std::forward<Func>(func), std::forward<Args>(args)...)
    );

    // 2. 先拿到 future，调用方靠它拿结果 / 等待 / 接异常
    std::future<ReturnType> resultFuture = packagedTask->get_future();

    // 3. 把 packaged_task 包进 function<void()> 放进队列（类型擦除，见 [[10-可调用对象-Lambda与std-function]]）
    {
        std::lock_guard<std::mutex> lock(queueMutex);
        if (stopRequested) {
            throw std::runtime_error("submit on stopped ThreadPool"); // 拒绝策略：停止后不再收任务
        }
        taskQueue.emplace([packagedTask] { (*packagedTask)(); });
    }
    taskAvailable.notify_one(); // 只来了一个任务，唤醒一个 worker 即可

    return resultFuture;
}
```

逐点拆解面试要点：

- **为什么用 `shared_ptr` 包 `packaged_task`？** `packaged_task` 只能 move 不能 copy，而 `std::function` 要求被包装的可调用对象**可拷贝构造**。lambda 捕获一个 move-only 对象会让 lambda 也变成 move-only，塞不进 `std::function`。用 `shared_ptr` 包一层，lambda 捕获的是可拷贝的指针，绕过这个限制。（C++23 的 `std::move_only_function` 可以省掉这层 `shared_ptr`。）
- **`std::invoke_result_t<Func, Args...>`**：C++17 在编译期推导「用这些参数调用 `func` 的返回类型」（C++11 是 `std::result_of`，C++17 起废弃）。模板与类型推导见 [[14-模板与泛型编程]]。
- **完美转发 `std::forward`**：保留实参的值类别（左值/右值），右值实参能被 move 进任务而非拷贝，对大对象（如持有 `AVFrame` 的仿函数）很关键。原理见 [[07-移动语义与右值引用]]。
- **返回 `future` 的价值**：调用方 `future.get()` 既能拿返回值，也能**接住任务里抛出的异常**——`packaged_task` 会把异常存进共享状态，`get()` 时重新抛出。这是比裸 `std::thread` 优越的地方（裸线程里抛异常直接 `std::terminate`）。

### 5. 使用示例

```cpp
ThreadPool pool(4);

// 提交带返回值的任务
std::future<int> decoded = pool.submit([](int packetId) {
    return packetId * 2; // 假装这是解码结果
}, 42);

// 提交带多参数的任务，参数被完美转发
auto sum = pool.submit([](int a, int b) { return a + b; }, 3, 4);

std::cout << decoded.get() << "\n"; // 阻塞直到结果就绪，输出 84
std::cout << sum.get() << "\n";     // 输出 7
// pool 析构时自动 shutdown，join 所有 worker
```

## 三、线程池的设计权衡

会写一个能跑的线程池只是及格线，高级岗要能讲清**取舍**。

### 1. 队列满了怎么办？（拒绝策略）

上面的实现用的是**无界队列**——`taskQueue` 想多大就多大。这在音视频里很危险：解码任务提交速度若长期快于消费，队列无限增长直接 OOM。生产级线程池要支持**有界队列 + 拒绝策略**：

| 策略 | 行为 | 适用场景 |
|---|---|---|
| **阻塞提交（背压）** | 队列满时 `submit` 阻塞，直到有空位 | 离线转码：不能丢任务，宁可让上游慢下来 |
| **丢弃任务** | 队列满直接丢掉新任务（或丢最旧的） | 实时预览：丢一帧比卡顿延迟好 |
| **拒绝抛异常** | 满时抛异常 / 返回失败，由调用方决策 | 需要上层感知过载、做降级 |
| **调用方自己跑** | 满时让提交线程直接执行该任务 | Java `CallerRunsPolicy` 思路，天然降速 |

有界队列做背压的实现，就是在 `submit` 里再加一个「队列不满」的条件变量等待，或者直接用 [[04-信号量]] 里的计数信号量表示「剩余空槽数」：`submit` 前 `acquire`，worker 取走任务后 `release`。

### 2. 有界 vs 无界队列

> **面试标准回答：**
> 无界队列实现简单、提交永不阻塞，但把「过载」这个问题藏起来了——内存会悄悄涨到爆。有界队列强制你正面回答「满了怎么办」，并且天然形成背压：队列满→上游阻塞→上游的上游也慢下来，整条流水线自动限速。音视频流水线我一定用**有界队列**，因为帧数据很大（一帧 1080p YUV 约 3MB），堆积几百帧就是 GB 级内存，必须靠有界队列卡住。

### 3. 单队列 vs 每线程队列 + work stealing（点到为止）

- **单全局队列**（本篇实现）：所有 worker 抢同一把锁、同一个队列。实现简单，但高并发下这把锁是**竞争热点**。
- **每线程本地队列 + work stealing**：每个 worker 有自己的队列，先消费本地的；本地空了再去「偷」别人队列尾部的任务。减少锁竞争、缓存局部性更好。这是 Go runtime、Java `ForkJoinPool`、Intel TBB 的做法。

> 面试点到为止即可：「全局队列在 worker 多、任务碎的时候锁竞争明显，更进阶的方案是每线程本地队列加 work stealing，用更细的锁或无锁 deque 降低争用，但实现复杂度高很多，没有性能证据时我不会上。」体现的是判断力而非炫技（呼应 [[03-无锁队列]] 的选型观）。

## 四、音视频多线程流水线架构（重点）

这是高级岗最能拉开差距的部分：**怎么把一个播放器/转码器拆成多线程，阶段间怎么传数据、怎么协调**。

### 1. 经典播放器三段式流水线

一个典型的软件播放器，数据从文件/网络流到屏幕，要经过三个阶段，每个阶段一条（或多条）独立线程，阶段之间用队列解耦：

```
                     packetQueue                      videoFrameQueue
                   (有界, 存 AVPacket)              (有界, 存 AVFrame)
                  ┌──────────────┐                ┌──────────────┐
   ┌──────────┐   │ ░░░░░░       │   ┌─────────┐  │ ░░░          │   ┌──────────┐
   │  Demux   │──▶│ packet packet│──▶│ Decode  │─▶│ frame frame  │─▶│  Render  │
   │ 解封装线程 │   │ packet ...   │   │ 解码线程  │  │ ...          │   │ 视频渲染   │
   └──────────┘   └──────────────┘   └─────────┘  └──────────────┘   └────┬─────┘
        │                                  │                               │
   读文件/网络                          视频解码                       上屏(VSync)
   拆音视频流                              │          audioFrameQueue        │
        │                                 │        ┌──────────────┐         ▼
        │                                 └───────▶│ pcm pcm ...  │─▶┌──────────┐
        └─ 音频包进 audioPacketQueue ...            └──────────────┘  │  Audio   │
                                                                     │ 音频回调  │──▶ 扬声器
                                                                     └────┬─────┘
                                                                          │
                                                                    audioClock(主时钟)
```

- **Demux（解封装）线程**：调 `av_read_frame` 从文件/网络读 `AVPacket`，按流类型（音/视频/字幕）分发到不同的 packet 队列。它是整条流水线的**总生产者**。
- **Decode（解码）线程**：通常音视频**各一条**。从 packet 队列取 `AVPacket`，送解码器（`avcodec_send_packet`/`receive_frame`），产出 `AVFrame` 放进 frame 队列。软解是 CPU 密集，可以再拆成多线程或用线程池；硬解则受硬件解码器实例数限制。
- **Render（渲染/播放）线程**：视频渲染线程按显示时间戳（PTS）在合适的 VSync 时刻把帧上屏；音频回调线程从 PCM 队列取数据喂给声卡。

> **面试标准回答（你怎么拆线程）：**
> 我会按「阶段」拆，而不是按「帧」拆。解封装、解码、渲染各一个阶段，阶段之间用有界队列连起来，形成生产者-消费者链。这样每个阶段可以独立按自己的节奏跑：解封装受 IO 速度限制，解码受 CPU/硬件限制，渲染受屏幕刷新率限制，三者速率不一样，正好靠中间的队列做缓冲和解耦。音频和视频解码一定要拆开成两条线程，因为它们的时钟和节奏完全独立，绝不能让视频解码卡住音频。

### 2. 阶段间队列选型：无锁 vs 有界阻塞

阶段间这根「管子」用什么队列，是核心设计决策。对比见 [[03-无锁队列]]，这里讲**在流水线里怎么选**：

| 维度 | SPSC 无锁队列（[[03-无锁队列]]） | 有界阻塞队列（mutex + cv） |
|---|---|---|
| 适用拓扑 | 严格一个生产者 + 一个消费者 | 任意，多生产多消费也行 |
| 满/空时行为 | 返回 false，调用方决定重试/丢帧 | 阻塞等待，天然背压 |
| 背压 | 要自己在调用方实现 | **内建**，满则阻塞上游 |
| 延迟 | 极低，不进内核 | 有锁和唤醒开销 |
| 复杂度 | 高（内存序、伪共享） | 低，易做 flush/唤醒 |

> **面试标准回答（流水线队列怎么选）：**
> 默认我用**有界阻塞队列**，因为播放器流水线最需要的不是极限低延迟，而是**背压**和**可控的内存**。有界阻塞队列满了自动阻塞上游，这正是我想要的限速行为，而且 flush、停止唤醒都好实现。只有在那种「单生产单消费、且对延迟极度敏感」的链路——比如音频回调线程从队列取 PCM，回调里绝对不能阻塞、不能抢锁——我才上 SPSC 无锁队列，回调取不到数据就填静音，绝不阻塞。所以是**按链路特性分别选型**，不是全局一种。

### 3. 为什么必须用有界队列做背压（backpressure）

这是音视频流水线的命门。设想队列**无界**：

```
解码速度 200 帧/秒  ──▶  [ 无界队列 ]  ──▶  渲染速度 30 帧/秒（受屏幕刷新率限制）
```

解码比渲染快 6 倍，每秒净堆积 170 帧。一帧 1080p 的 YUV420 约 3MB，几秒钟队列就涨到 GB 级，**内存爆炸**。

有界队列把这个问题挡住：队列满（比如限 16 帧）时，解码线程在 `push` 上**阻塞**，自动把解码速率压到和渲染一致。背压会沿着流水线**逐级回传**——渲染慢 → 解码 frame 队列满 → 解码阻塞 → 解封装 packet 队列满 → 解封装阻塞 → 停止读流。整条管子自动限速到最慢的那一级。

```cpp
// 有界阻塞队列：push 满则阻塞（背压），支持停止唤醒和 flush
template <typename T>
class BoundedQueue {
public:
    explicit BoundedQueue(std::size_t capacity) : capacity(capacity) {}

    // 返回 false 表示队列已被 stop（用于优雅退出）
    bool push(T value) {
        std::unique_lock<std::mutex> lock(mutex);
        notFull.wait(lock, [this] { return stopped || buffer.size() < capacity; });
        if (stopped) {
            return false;
        }
        buffer.push(std::move(value));
        notEmpty.notify_one();
        return true;
    }

    bool pop(T& out) {
        std::unique_lock<std::mutex> lock(mutex);
        notEmpty.wait(lock, [this] { return stopped || !buffer.empty(); });
        if (buffer.empty()) { // 仅在 stopped 且已排空时为真
            return false;
        }
        out = std::move(buffer.front());
        buffer.pop();
        notFull.notify_one();
        return true;
    }

    // seek / 切流时清空旧数据，防止旧帧污染（见下文第 5 点）
    void flush() {
        std::lock_guard<std::mutex> lock(mutex);
        std::queue<T> empty;
        buffer.swap(empty);
        notFull.notify_all(); // 清空后上游可以继续 push
    }

    // 停止：唤醒所有卡在 push/pop 的线程，让它们带着 false 返回
    void stop() {
        std::lock_guard<std::mutex> lock(mutex);
        stopped = true;
        notFull.notify_all();
        notEmpty.notify_all();
    }

private:
    const std::size_t capacity;
    std::queue<T> buffer;
    std::mutex mutex;
    std::condition_variable notFull;   // 「队列不满」——给生产者等
    std::condition_variable notEmpty;  // 「队列非空」——给消费者等
    bool stopped = false;
};
```

> 用了**两个条件变量** `notFull` / `notEmpty`：生产者等「不满」，消费者等「非空」，避免用单个 cv + `notify_all` 把不相干的线程也吵醒（精准唤醒，减少惊群）。限并发的另一种等价表达是 [[04-信号量]] 的双信号量法：`emptySlots` 初始为 capacity、`filledSlots` 初始为 0。

### 4. 音视频同步点：线程间如何协调（简述）

流水线里音频和视频是两条独立线程，速率不一样，必须有个**共同的时间基准**让它们对齐，否则就是音画不同步。主流做法是**音频时钟为主时钟（master clock），视频追音频**：

```
音频回调线程：每喂出一段 PCM，就更新 audioClock = 已播放样本数 / 采样率
                            │ (atomic 发布当前播放时间)
                            ▼
视频渲染线程：取出一帧，比较 frame.pts 与 audioClock：
   frame.pts  > audioClock + 阈值  → 这帧太早，sleep 等一会再上屏
   frame.pts  < audioClock - 阈值  → 这帧太晚（落后了），丢帧追赶
   两者接近                          → 立刻上屏
```

- **为什么以音频为主**：人耳对音频的卡顿、变速极其敏感（爆音、变调），而视频丢一两帧人眼几乎无感。所以让音频匀速播放，视频去迁就音频。
- **线程间怎么传时钟**：`audioClock` 就是一个跨线程共享的时间值，音频线程写、视频线程读，用 `std::atomic<double>`（或加锁的结构）发布即可，正是 [[02-原子操作与内存序]] 里「单变量状态用 atomic 发布」的典型用法——音频线程 `store(release)`，视频线程 `load(acquire)`。

> 详细的 PTS/DTS、时间基转换、同步算法不在本篇展开（属于音视频专业知识）。本篇的重点是：**同步本质是「一个线程发布时钟、另一个线程读时钟做决策」的线程协调问题**，用一个原子变量或一把短锁就能解决跨线程的时钟共享。

### 5. 暂停 / seek / 停止的线程协调

这是流水线最容易出 bug 的地方，三个动作都要协调多条线程。

**暂停（pause）**：用一个原子标志 + 条件变量。各线程在循环顶部检查 `paused`，为真则在一个 cv 上 wait；`resume` 时清标志并 `notify_all`。

```cpp
std::atomic<bool> paused{false}; // 跨线程读，用 atomic（见 [[02-原子操作与内存序]]）

// 渲染线程循环里
{
    std::unique_lock<std::mutex> lock(pauseMutex);
    pauseCond.wait(lock, [&] { return !paused.load() || stopRequested.load(); });
}
```

**seek（跳转）**：最关键的是**清掉所有队列里的旧数据**，否则 seek 到新位置后，队列里还残留着旧位置的帧，会先把旧画面播出来（**旧帧污染**）。标准流程：

```
1. 置 seeking 标志，让各解码/渲染线程暂停产出
2. flush 所有队列（packetQueue / videoFrameQueue / audioFrameQueue 全部清空）
3. 调 avcodec_flush_buffers 清解码器内部缓存（解码器自己也存了参考帧）
4. demux 线程 av_seek_frame 到目标时间戳
5. 清 seeking 标志，各线程恢复，从新位置重新生产
```

**停止（stop）**：和线程池 `shutdown` 同理，核心是**避免退出死锁**。退出时两种卡死要同时解：

- worker/消费者卡在队列的 `pop`（空队列 wait）→ 靠 `queue.stop()` 里的 `notEmpty.notify_all()` 唤醒，让 `pop` 返回 false。
- 上游生产者卡在队列的 `push`（满队列 wait）→ 靠 `notFull.notify_all()` 唤醒，让 `push` 返回 false。

```cpp
void Player::stop() {
    stopRequested.store(true);          // 1. 原子标志：让各线程循环条件失败
    packetQueue.stop();                 // 2. 唤醒所有卡在该队列 push/pop 的线程
    videoFrameQueue.stop();
    audioFrameQueue.stop();
    pauseCond.notify_all();             // 3. 唤醒可能卡在暂停 wait 的线程

    if (demuxThread.joinable())  demuxThread.join();   // 4. 逐个 join
    if (decodeThread.joinable()) decodeThread.join();
    if (renderThread.joinable()) renderThread.join();
}
```

> **面试标准回答（停止时为什么会死锁，怎么破）：**
> 停止时最经典的死锁是：消费者线程卡在空队列的 `pop` 上睡着了，等不到数据；而生产者已经被我置位停止、不再 push，于是没人来唤醒消费者，主线程 `join` 就永远卡住。反过来也一样，生产者可能卡在满队列的 `push` 上。破解办法是给队列一个 `stop()`：置位 stopped 标志后 `notify_all` 把卡在 push 和 pop 上的线程**全部叫醒**，让它们重新检查谓词、发现 stopped 为真就带着 false 返回、跳出循环。所以停止的口诀是「**置原子标志 + 队列 stop 唤醒两端 + 逐个 join**」，缺一个都可能死锁。

### 6. 背压与限流：和信号量的关系

第 3 点的有界阻塞队列已经实现了背压。如果想**显式限制并发解码任务数**（比如硬解码器只有 2 个实例，或限制同时占用的显存），用 [[04-信号量]] 的计数信号量最直接：

```cpp
std::counting_semaphore<> decoderSlots{2}; // 最多 2 个并发解码任务（硬件限制）

void decodeOnePacket(AVPacket packet) {
    decoderSlots.acquire();                 // 占一个槽，满了就阻塞（限流）
    // ... 调用硬件解码器 ...
    decoderSlots.release();                 // 用完释放，唤醒等待者
}
```

> 队列的有界容量是「**缓冲深度**」的背压，信号量是「**并发实例数**」的限流，两者经常同时用：队列限制堆积多少帧，信号量限制同时有多少个解码在跑。

## 五、流水线常见问题排查

| 现象 | 根因 | 排查 / 解法 |
|---|---|---|
| 内存持续上涨 | 用了无界队列，或有界容量过大；下游慢于上游 | 改有界队列做背压；定容量；监控各队列水位 |
| 端到端延迟越来越大 | 队列堆积（buffer 里积压几百帧，每帧都要排队等播） | 减小队列容量；实时场景丢旧帧只保最新；low-latency 模式 |
| 停止时卡死（`join` 不返回） | worker 卡在空队列 `pop`，或上游卡在满队列 `push`，没人唤醒 | `queue.stop()` 里 `notify_all` 唤醒两端；原子停止标志 |
| seek 后先闪一下旧画面 | 旧帧污染：队列/解码器内还残留旧位置数据 | seek 时 flush 所有队列 + `avcodec_flush_buffers` |
| 音画不同步、越来越偏 | 视频没追音频时钟，或时钟发布有竞态 | 音频为主时钟，视频按 PTS 比对追赶；时钟用 atomic 发布 |
| 偶发崩溃 / 数据错乱 | 多个线程往同一队列 push 却用了 SPSC 无锁队列 | SPSC 只支持单生产单消费，多生产改用阻塞队列或 MPMC（见 [[03-无锁队列]]） |
| CPU 跑满但帧率上不去 | 线程数远超核数，全在上下文切换；或忙等轮询 | 线程数贴近核数；用条件变量阻塞而非 `sleep` 轮询 |
| 暂停后无法恢复 | resume 没 `notify` 卡在 wait 的线程 | resume 清标志后必须 `notify_all` |

## 六、C++20 `jthread` 简化优雅停止

前面手写的「原子停止标志 + 析构里 join」是 C++11/17 的标准套路。C++20 的 `std::jthread` 把这两件事内建了（详见 [[17-C++20与协程]]）：

- **自动 join**：`jthread` 析构时自动 `join()`，不用手写，也不会因为忘记 join 而 `std::terminate`。
- **协作式取消**：内建 `std::stop_token` / `std::stop_source`，线程函数可以接一个 `stop_token` 参数，外部调 `request_stop()` 就能通知它该退出了。

```cpp
#include <thread>
#include <stop_token>

void renderLoop(std::stop_token stopToken, BoundedQueue<Frame>& frameQueue) {
    while (!stopToken.stop_requested()) { // 协作检查取消请求
        Frame frame;
        if (!frameQueue.pop(frame)) {     // 队列 stop 后返回 false
            break;
        }
        renderFrame(frame);
    }
}

void run(BoundedQueue<Frame>& frameQueue) {
    std::jthread renderThread(renderLoop, std::ref(frameQueue)); // 自动传入 stop_token
    // ...
    renderThread.request_stop(); // 请求停止；析构时自动 request_stop + join
    // 离开作用域：jthread 析构自动 join，无需手写
}
```

> **面试标准回答（jthread 好在哪）：**
> `jthread` 解决两个老问题。一是忘记 join：`std::thread` 析构时如果还 joinable 会直接 `std::terminate`，`jthread` 析构会自动 join。二是没有标准的取消机制：以前要自己搞 `atomic<bool> stop`，现在 `jthread` 自带 `stop_token`，`request_stop()` 是协作式的——它不会强杀线程，只是把 token 置位，线程函数自己在循环里检查 `stop_requested()` 决定何时退出。注意它只解决「通知 + join」，**队列里卡在 wait 的线程还是要靠队列自己的 stop 唤醒**，`stop_token` 也可以注册回调（`stop_callback`）在 `request_stop` 时顺便去 `notify` 条件变量，把两件事接起来。

## 七、音视频场景小结

- **播放器**：demux / 音频解码 / 视频解码 / 音频回调 / 视频渲染，5 类线程，阶段间有界队列；音频主时钟，视频追。
- **推流/编码器**：采集 → 编码 → 打包 → 网络发送，编码线程和网络线程用 mutex+cv 队列解耦（见 [[01-多线程与锁]] 的 `DispatchQueue2` 实战），弱网时靠队列水位做 ABR 降码率。
- **转码**：解码 → 滤镜 → 编码，CPU 密集，适合用**线程池**把多个独立分片/多路任务并行起来，有界队列防止某一级堆积。
- **通用计算池 vs 实时线程**：把可并行的 CPU 计算（缩放、滤镜、软解）丢线程池；音频回调、视频渲染这类**实时性强、有截止时间**的线程**单独固定**，不混进通用池，避免被计算任务抢时间片导致爆音/丢帧。

## 常见坑

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | worker 持锁执行任务，线程池退化成串行 | 临界区只取任务，执行放锁外 |
| 2 | 停止只 `notify_one`，只有一个 worker 醒来退出 | 停止用 `notify_all` 唤醒全部 |
| 3 | 停止标志在锁外置位，与谓词检查竞态丢唤醒 | 改标志和 notify 配合，标志在锁内或用 atomic |
| 4 | `packaged_task` 直接塞 `std::function`（move-only 编译失败） | 用 `shared_ptr` 包一层，或 C++23 `move_only_function` |
| 5 | 流水线用无界队列，解码快于渲染导致内存爆炸 | 有界队列做背压，满则阻塞上游 |
| 6 | 多个生产者往 SPSC 无锁队列 push | SPSC 仅单生产单消费，多生产用阻塞/MPMC 队列 |
| 7 | seek 不 flush，旧帧污染先播旧画面 | flush 所有队列 + `avcodec_flush_buffers` |
| 8 | 停止时 `join` 死锁（线程卡在 push/pop 的 wait） | 队列 `stop()` + `notify_all` 唤醒两端再 join |
| 9 | 用 `sleep` 轮询队列代替条件变量 | 用 cv 阻塞等待，省 CPU、低延迟、无丢唤醒 |
| 10 | 线程数远超核数（CPU 密集） | CPU 密集贴近核数，`hardware_concurrency()` 兜底 0 |
| 11 | 析构没 join 线程，`std::thread` 直接 `terminate` | RAII 在析构里 join，或用 `jthread` |
| 12 | 时钟变量普通 bool/double 跨线程读写 | 用 `std::atomic` 发布（release/acquire） |

---

> **一句话面试总结：**
> 线程池的本质是「固定 worker + 共享任务队列」的生产者-消费者模型，关键在 `submit` 用 `packaged_task` 返回 `future`、worker 锁外执行任务、停止时 `notify_all` + `join` 防退出死锁；而音视频流水线则是把它放大成 demux→decode→render 的多级生产者-消费者链，阶段间用**有界阻塞队列做背压**控制内存和速率，音频主时钟做同步，seek 靠 flush 清旧帧，停止靠原子标志加队列两端唤醒。会写线程池是基础，能讲清楚「队列满了怎么办、停止为什么死锁、seek 怎么不污染、线程数怎么定」才是高级岗的区分点。
