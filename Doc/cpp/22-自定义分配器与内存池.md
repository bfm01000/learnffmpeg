# C++ 自定义分配器、内存池与对象池

> 高级岗硬核考点：本篇讲**怎么自己实现**内存池、对象池、STL 分配器和 C++17 `std::pmr`。逐帧 `new/delete` 是音视频热路径大忌——一帧解码可能分配上百个临时对象，走系统 `malloc` 会带来系统调用、锁竞争、碎片和不可预测的尾延迟。能把这块讲透，是区分中级和高级 C++ 工程师的分水岭。
>
> 前置：`operator new/delete` 两步走机制、placement new 语法、内存碎片定义见 [[05-内存管理与对象生命周期]]；分配器与容器的关系见 [[12-STL容器底层]]；对齐处理见 [[21-内存对齐、SIMD与缓冲管理]]；线程安全见 [[01-多线程与锁]] 与 [[03-无锁队列]]。

## 📌 面试速记（考前 5 分钟扫一遍）

- **为什么要自定义内存管理**：系统 `malloc` 有**系统调用、全局锁竞争、外部碎片、不可预测的尾延迟**四宗罪，音视频要的是**低延迟 + 确定性**，所以热路径绝不逐帧 `new/delete`。
- **固定大小内存池 = free list**：一次性 `malloc` 大块，切成等大小块串成**空闲链表**，分配=**摘头**、释放=**插头**，都是 **O(1) 且零外部碎片**。
- **对象池复用对象本身**：用完**不析构**，归还到池子下次 `acquire` 直接复用（解码帧池、`AVFrame` 复用），省构造/析构开销。
- **内存池 vs 对象池**：内存池管**裸内存块**（配 placement new 重建对象），对象池管**已构造的对象**（复用对象状态）。
- **STL 自定义分配器很麻烦**：要写 `allocate/deallocate/rebind`、处理**有状态分配器的拷贝与比较语义**，C++11 后 `allocator_traits` 帮你补默认实现，但坑仍多。
- **现代答案是 C++17 `std::pmr`**：`memory_resource` + `polymorphic_allocator`，用 **`monotonic_buffer_resource`** 做每帧 arena（只分配不单独释放、整体回收），还能挂**栈上 buffer 实现零堆分配**。
- **arena/bump allocator**：指针 bump 式分配，帧结束 `release()` 整体重置，最适合「每帧分配一堆临时对象、帧末统一释放」。
- **池子必须处理对齐**：块大小要向上取整到 `alignof(max_align_t)` 或对象对齐值，SIMD 缓冲还要对齐到 16/32 字节（见 [[21-内存对齐、SIMD与缓冲管理]]）。

## 一、为什么需要自定义内存管理

`new/delete` 的两步走（`operator new` 分配 + 构造函数）机制见 [[05-内存管理与对象生命周期]]。这里只谈**它在音视频热路径上为什么不够用**。

一次 `new` 最终落到系统 `malloc`，代价来自四个方面：

1. **系统调用开销**：当线程本地的内存不够时，`malloc` 要向内核要内存（`brk`/`mmap`），这是用户态到内核态的切换，几百到几千个时钟周期。
2. **全局锁竞争**：传统 glibc `malloc` 用全局或分 arena 的锁保护空闲链表，多解码线程同时分配时互相阻塞（这也是 TCMalloc/Jemalloc 用线程本地缓存优化的点，见 [[05-内存管理与对象生命周期]]）。
3. **外部碎片**：长时间运行后堆变成「瑞士奶酪」，大块连续内存申请失败（碎片定义见 [[05-内存管理与对象生命周期]]）。
4. **不可预测的尾延迟**：`malloc` 内部可能触发空闲块的拆分、合并、甚至整理，单次分配耗时方差很大。

> **面试标准回答（为什么音视频热路径不能逐帧 new/delete）**：
> 「视频按 25~60fps 跑，每帧留给我们的时间只有 16~40ms，而一帧解码、滤镜、渲染过程里会分配大量临时对象——packet、frame、中间缓冲。如果每个都走系统 `malloc`，会带来系统调用、多线程锁竞争和外部碎片，最致命的是 `malloc` 的耗时不可预测，偶尔一次慢分配就会让这一帧超时、画面卡顿。所以热路径上我们用**预分配 + 池化复用**：内存池一次性拿大块内存自己切，对象池复用对象本身，让每次分配都是确定的 O(1)，把延迟方差压到最低。」

核心思想就一句：**把不确定的、慢的系统分配，换成确定的、快的自管理分配**。手段是预分配大块内存 + 自己管理切割回收。

## 二、重载 operator new/delete：让对象从池子取内存

最直接的接入点是**重载类内 `operator new`/`operator delete`**。这样这个类的所有 `new` 都自动走我们的池子，业务代码一行不用改。

注意区分（机制见 [[05-内存管理与对象生命周期]]）：`new Frame` 这个 **new 表达式** = `operator new` 取内存 + 构造函数；我们能重载的是 `operator new` 函数，不是 new 表达式本身。

```cpp
#include <cstddef>
#include <new>

class FixedBlockPool;                 // 前置声明，实现见第三节
extern FixedBlockPool& framePool();   // 返回该类型专属的池子

// 一个固定大小的解码帧描述对象
class Frame {
public:
    int    width  = 0;
    int    height = 0;
    int    format = 0;
    // ... 其它字段

    // 类内重载：单对象版本
    static void* operator new(std::size_t size);
    static void  operator delete(void* address) noexcept;

    // 数组版本（重载了单对象版就最好把数组版一起处理，否则 new Frame[n] 仍走全局）
    static void* operator new[](std::size_t size);
    static void  operator delete[](void* address) noexcept;
};
```

实现把内存请求转发给池子（`framePool()` 返回的 `FixedBlockPool` 见第三节）：

```cpp
void* Frame::operator new(std::size_t size) {
    // size 由编译器传入，等于 sizeof(Frame)；池子按固定块大小分配
    void* address = framePool().allocate(size);
    if (address == nullptr) throw std::bad_alloc{}; // 语义对齐标准 operator new
    return address;
    // 注意：这里只分配裸内存，构造函数由 new 表达式在返回后自动调用
}

void Frame::operator delete(void* address) noexcept {
    // 析构函数已由 delete 表达式先行调用，这里只回收裸内存
    framePool().deallocate(address);
}

void* Frame::operator new[](std::size_t size)            { return framePool().allocate(size); }
void  Frame::operator delete[](void* address) noexcept   { framePool().deallocate(address); }
```

用起来和普通 `new` 完全一样，但内存来自池子：

```cpp
Frame* frame = new Frame();   // 走 Frame::operator new → 池子；再调构造函数
// ... 使用 frame
delete frame;                 // 先调 ~Frame()，再走 Frame::operator delete → 归还池子
```

> **面试标准回答（类内重载 operator new 的意义）**：
> 「我在类里重载 `operator new`/`operator delete`，让它从预分配的内存池取内存而不是走系统 `malloc`。好处是业务代码完全不用改，照样写 `new Frame` / `delete frame`，编译器自动把取内存这步路由到我的池子，分配变成 O(1) 摘链表。注意重载的是 `operator new` 函数，构造和析构仍由 new/delete 表达式负责。如果重载了单对象版，一般要把数组版 `operator new[]` 也一起重载，否则 `new Frame[n]` 会漏到全局去。」

**全局重载 `::operator new`/`::operator delete` 的风险**：影响进程内**所有** `new`，包括第三方库、标准库内部分配。一旦你的全局分配器有 bug、不处理某些大小、或对齐假设不成立，整个进程崩溃，且极难定位。**生产中优先类内重载或 `std::pmr`，避免全局重载。**

## 三、固定大小内存池：free list 空闲链表

这是最经典、最实用的内存池。思想：**一次性 `malloc` 一大块连续内存，切成等大小的块，把这些块串成一条「空闲链表」（free list）。分配就是摘链表头，释放就是把块插回链表头，全是 O(1)，且因为所有块等大，永远不会产生外部碎片。**

关键技巧：空闲块本身不存数据，所以**直接把「下一个空闲块的指针」写在空闲块的前 8 字节里**——free list 是「侵入式」的，不需要额外的链表节点内存。

### 1. 完整实现（含对齐处理）

```cpp
#include <cstddef>
#include <cstdint>
#include <cstdlib>
#include <new>

// 固定大小块内存池：所有块大小相同，分配/释放 O(1)，无外部碎片
class FixedBlockPool {
public:
    // blockSize：单块字节数；blockCount：预分配多少块
    FixedBlockPool(std::size_t blockSize, std::size_t blockCount)
        : blockCount_(blockCount) {
        // 1) 块大小至少要能放下一个指针（空闲链表把 next 写在块内）
        std::size_t usableSize = blockSize < sizeof(void*) ? sizeof(void*) : blockSize;
        // 2) 向上取整到 max_align_t 的对齐边界，保证每块首地址对齐合法（见 [[21-内存对齐、SIMD与缓冲管理]]）
        constexpr std::size_t alignment = alignof(std::max_align_t);
        blockSize_ = (usableSize + alignment - 1) / alignment * alignment;

        // 3) 一次性申请整块连续内存（按对齐分配，C++17 aligned 版本）
        poolMemory_ = static_cast<std::uint8_t*>(
            ::operator new(blockSize_ * blockCount_, std::align_val_t{alignment}));

        // 4) 把整块切成 blockCount 个等大小块，串成空闲链表
        freeListHead_ = nullptr;
        for (std::size_t blockIndex = 0; blockIndex < blockCount_; ++blockIndex) {
            std::uint8_t* blockAddress = poolMemory_ + blockIndex * blockSize_;
            pushFront(blockAddress);   // 头插，串成链表
        }
    }

    ~FixedBlockPool() {
        ::operator delete(poolMemory_, std::align_val_t{alignof(std::max_align_t)});
    }

    FixedBlockPool(const FixedBlockPool&) = delete;            // 池子持有裸资源，禁止拷贝
    FixedBlockPool& operator=(const FixedBlockPool&) = delete;

    // 分配：摘下链表头，O(1)
    void* allocate(std::size_t /*size*/) noexcept {
        if (freeListHead_ == nullptr) return nullptr;          // 池子耗尽（可在此扩容或返回 nullptr）
        FreeNode* takenBlock = freeListHead_;
        freeListHead_ = takenBlock->next;                      // 头指针前移
        return takenBlock;
    }

    // 释放：把块插回链表头，O(1)
    void deallocate(void* address) noexcept {
        if (address == nullptr) return;
        pushFront(address);
    }

private:
    // 空闲块内部复用：空闲时块的前 8 字节存「下一块地址」
    struct FreeNode { FreeNode* next; };

    void pushFront(void* address) noexcept {
        FreeNode* node = static_cast<FreeNode*>(address);
        node->next = freeListHead_;
        freeListHead_ = node;
    }

    std::uint8_t* poolMemory_   = nullptr; // 整块连续内存的起点
    FreeNode*     freeListHead_ = nullptr; // 空闲链表头
    std::size_t   blockSize_    = 0;       // 对齐后的单块大小
    std::size_t   blockCount_   = 0;       // 总块数
};
```

### 2. 为什么 O(1) 且无外部碎片

- **分配 = 摘头，释放 = 插头**：只动一个指针，与池子大小无关，恒定 O(1)。
- **所有块等大**：释放出来的块和需要的块大小完全一致，任何空闲块都能满足任何请求，**不存在「有总量却没连续块」的外部碎片**。代价是只能装固定大小对象——这正好契合音视频里「同一种帧/包结构反复创建」的模式。

### 3. 配合 placement new + 显式析构

内存池只给**裸内存**，对象的构造/析构要自己用 placement new 和显式析构调用接管（语法见 [[05-内存管理与对象生命周期]]）：

```cpp
FixedBlockPool pool(sizeof(Frame), 256);   // 预分配 256 个 Frame 大小的块

// 取裸内存 → placement new 原地构造
void* rawMemory = pool.allocate(sizeof(Frame));
Frame* frame = new (rawMemory) Frame();    // 在池内存上构造，不再分配

// ... 使用 frame

// 显式调析构 → 归还裸内存（注意：不能用 delete，那会调用 ::operator delete 还给系统）
frame->~Frame();
pool.deallocate(frame);
```

> **面试标准回答（固定大小内存池怎么实现）**：
> 「我一次性 `malloc` 一大块连续内存，按对象大小切成等大小的块，用一条侵入式的空闲链表串起来——空闲块自己的前 8 字节就存下一块的地址，不额外占内存。分配就是摘链表头、释放就是头插回去，都是 O(1)。因为所有块等大，释放的块能满足任意请求，所以完全没有外部碎片。要注意块大小得向上取整到对齐边界、并且至少能放下一个指针。对象的构造析构我用 placement new 和显式调析构来接管，归还时只回收内存不还给系统。」

> ⚠️ 上面的 `FixedBlockPool` 是**单线程**版本。多解码线程共享时，`allocate`/`deallocate` 对 `freeListHead_` 的读改写要加锁，或用无锁 CAS（见第四节线程安全部分与 [[03-无锁队列]]）。

## 四、对象池（Object Pool）：复用对象本身

内存池管的是**裸内存块**（每次拿出来还要 placement new 重新构造）。对象池更进一步：**复用已经构造好的对象本身**——对象用完不析构、不释放，重置状态后归还池子，下次 `acquire` 直接拿来用。

这在音视频里极其常见：`AVFrame`/`AVPacket` 的内部缓冲分配很贵，FFmpeg 自己也用引用计数池化复用；解码出的帧对象用完归还「帧池」，渲染线程消费完再还回来循环转。

### 1. 基础对象池：acquire / release

```cpp
#include <vector>
#include <memory>

// T 需要可默认构造、可 reset。这里复用「对象」，归还时不析构而是重置状态
template <typename T>
class ObjectPool {
public:
    explicit ObjectPool(std::size_t poolCapacity) {
        storage_.reserve(poolCapacity);
        freeObjects_.reserve(poolCapacity);
        for (std::size_t objectIndex = 0; objectIndex < poolCapacity; ++objectIndex) {
            storage_.push_back(std::make_unique<T>()); // 预先全部构造好
            freeObjects_.push_back(storage_.back().get());
        }
    }

    // 取一个可用对象；池空返回 nullptr（也可选择动态扩容）
    T* acquire() {
        if (freeObjects_.empty()) return nullptr;
        T* object = freeObjects_.back();
        freeObjects_.pop_back();
        return object;
    }

    // 归还：不析构，调用方负责把对象重置成「干净」状态后还回来
    void release(T* object) {
        if (object == nullptr) return;
        freeObjects_.push_back(object);
    }

private:
    std::vector<std::unique_ptr<T>> storage_;     // 持有对象、负责最终析构
    std::vector<T*>                 freeObjects_; // 当前空闲对象指针栈
};
```

### 2. 音视频帧池 + RAII 自动归还

裸 `acquire/release` 容易忘记归还，最好用 RAII 包装（智能指针的自定义删除器，见 [[06-智能指针与资源管理]]）让出作用域自动还池：

```cpp
struct DecodedFrame {
    int width = 0, height = 0;
    std::vector<std::uint8_t> pixelBuffer;   // 内部缓冲被复用，避免每帧重新分配
    void reset() { width = height = 0; /* 不清空 pixelBuffer 容量，复用其已分配内存 */ }
};

class FramePool {
public:
    explicit FramePool(std::size_t poolCapacity) : pool_(poolCapacity) {}

    // 返回带自定义删除器的 unique_ptr：析构时自动 reset 并归还池子
    using FrameHandle = std::unique_ptr<DecodedFrame, std::function<void(DecodedFrame*)>>;

    FrameHandle acquire() {
        DecodedFrame* frame = pool_.acquire();
        if (frame == nullptr) return {nullptr, [](DecodedFrame*){}};
        return FrameHandle(frame, [this](DecodedFrame* used) {
            used->reset();          // 归还前重置状态
            pool_.release(used);    // 还回池子（不析构）
        });
    }

private:
    ObjectPool<DecodedFrame> pool_;
};

// 使用：出作用域自动归还，热路径上零分配
void decodeLoop(FramePool& framePool) {
    auto frame = framePool.acquire();   // 复用对象，不 new
    if (!frame) return;
    frame->width = 1920;
    // ... 解码填充、送渲染
}                                       // frame 析构 → 自动 reset + release 回池
```

### 3. 线程安全版本

解码线程取帧、渲染线程还帧，跨线程共享池子时必须同步。两种做法：

```cpp
#include <mutex>

// 方案 A：mutex 保护空闲列表（实现简单，竞争激烈时锁开销明显，见 [[01-多线程与锁]]）
template <typename T>
class LockedObjectPool {
public:
    T* acquire() {
        std::lock_guard<std::mutex> lock(mutex_);
        if (freeObjects_.empty()) return nullptr;
        T* object = freeObjects_.back();
        freeObjects_.pop_back();
        return object;
    }
    void release(T* object) {
        std::lock_guard<std::mutex> lock(mutex_);
        freeObjects_.push_back(object);
    }
private:
    std::mutex      mutex_;
    std::vector<T*> freeObjects_;
};
```

- **方案 A（mutex）**：实现简单，绝大多数场景够用。每帧才取还一次，锁粒度不细，竞争通常可忽略。
- **方案 B（无锁）**：把空闲链表做成无锁栈（`std::atomic` 头指针 + CAS 头插/摘头），避免锁但要处理 **ABA 问题**（用带标记的指针或 hazard pointer，见 [[03-无锁队列]]）。只有在每秒百万级取还、锁成为瓶颈时才值得，否则 mutex 更稳。

> **面试标准回答（内存池 vs 对象池）**：
> 「内存池管的是裸内存块——分配出来还得自己 placement new 构造。对象池更进一步，复用对象本身：对象用完不析构也不释放，重置状态后归还池子，下次直接拿来用，连构造析构的开销都省了。音视频里典型就是帧池，`AVFrame` 这种内部缓冲很贵的对象，复用对象就能复用它已经分配好的像素缓冲，热路径零分配。我一般用 RAII handle 包一层，出作用域自动重置归还，避免忘记还池；跨线程共享就加 mutex，竞争极端时才上无锁栈。」

## 五、STL 自定义分配器（Allocator）

STL 容器（见 [[12-STL容器底层]]）的第二个模板参数就是分配器，默认 `std::allocator<T>`。我们可以替换它，让 `std::vector`、`std::list` 从自己的池子取内存。

### 1. Allocator 接口要求

一个能用的分配器至少要提供：

- `value_type`：元素类型。
- `allocate(n)`：分配能放 `n` 个 `T` 的**裸内存**（不构造），返回 `T*`。
- `deallocate(pointer, n)`：回收 `allocate(n)` 拿到的内存。
- **`rebind`**：容器内部往往不直接分配 `T`，而是分配「节点」（如 `list` 的节点、`map` 的红黑树节点）。`rebind<U>::other` 让容器从「`T` 的分配器」得到「`U` 的分配器」。C++11 后 `std::allocator_traits` 会用 `Allocator<U>` 自动推导，不必手写 `rebind`。
- C++11 后，构造/析构、`max_size`、`pointer` 类型等都由 **`std::allocator_traits<Alloc>` 提供默认实现**，所以分配器本身可以写得很精简——这是「为什么现代写 allocator 比 C++98 简单很多」的关键。

### 2. 一个接到 vector 的 pool/arena allocator

```cpp
#include <cstddef>
#include <new>

// 简易竞技场分配器：从外部传入的 FixedBlockPool 取内存
template <typename T>
class PoolAllocator {
public:
    using value_type = T;

    explicit PoolAllocator(FixedBlockPool* backingPool) noexcept
        : backingPool_(backingPool) {}

    // 关键：从「T 的分配器」拷贝构造出「U 的分配器」（容器分配节点时用）
    template <typename U>
    PoolAllocator(const PoolAllocator<U>& other) noexcept
        : backingPool_(other.backingPool_) {}

    T* allocate(std::size_t count) {
        void* address = backingPool_->allocate(count * sizeof(T));
        if (address == nullptr) throw std::bad_alloc{};
        return static_cast<T*>(address);
    }

    void deallocate(T* address, std::size_t /*count*/) noexcept {
        backingPool_->deallocate(address);
    }

    // 有状态分配器必须定义相等比较：两个分配器「相等」表示一方分配的内存可由另一方释放
    template <typename U>
    bool operator==(const PoolAllocator<U>& other) const noexcept {
        return backingPool_ == other.backingPool_;   // 指向同一个池子才相等
    }
    template <typename U>
    bool operator!=(const PoolAllocator<U>& other) const noexcept {
        return !(*this == other);
    }

    FixedBlockPool* backingPool_;   // 有状态：持有指向池子的指针
    template <typename U> friend class PoolAllocator;
};

// 接到 vector（注意：vector 一次分配 capacity 个连续 T，定长块池未必合适，arena 更典型）
// std::vector<int, PoolAllocator<int>> values{ PoolAllocator<int>(&pool) };
```

### 3. 有状态分配器的坑

- **拷贝/比较语义**：分配器可以「有状态」（持有指向池子的指针）。但容器在拷贝、`swap`、移动时会按 `propagate_on_container_*` traits 决定是否搬运分配器。如果 `a.deallocate` 释放的内存其实是 `b` 分配的，而 `a != b`，就是未定义行为。**所以 `operator==` 必须如实反映「内存可互相释放」**。
- **`swap` 的传播**：默认 `propagate_on_container_swap` 为 `false`，两个分配器不等的容器互换会是 UB。有状态分配器要谨慎处理这些 traits。
- **容器要求连续/特定大小**：`vector` 要一段连续内存且容量翻倍增长，定长块池满足不了，更适合 arena allocator；`list`/`map` 每次分配一个固定大小节点，才是定长块池的理想搭档。

> **面试标准回答（写 STL allocator 为什么麻烦）**：
> 「STL allocator 麻烦在它不是单纯分配 `T`：容器内部要通过 `rebind` 把它转成分配内部节点的分配器，还要正确处理有状态分配器的拷贝、移动、swap 传播语义和 `operator==`——`==` 的含义是『一方分配的内存能否由另一方释放』，写错就是 UB。C++11 之后 `allocator_traits` 帮我们补齐了大部分默认实现，分配器本身只需写 `value_type`、`allocate`、`deallocate` 和相等比较，简化了很多。但要真正接管容器内存，现在更推荐用 C++17 的 `std::pmr`，把这些复杂度交给标准库。」

## 六、C++17 `std::pmr`：现代答案（重点）

C++98 的分配器是**模板参数**，类型不同分配器不同（`vector<int, A>` 和 `vector<int, B>` 是不同类型，不能互相赋值）。C++17 的 `std::pmr`（polymorphic memory resource，多态内存资源）用**运行时多态**解决：分配策略放进 `memory_resource` 虚接口，容器统一用 `polymorphic_allocator`，**不同策略的 `pmr::vector` 是同一个类型**。这是现在写自定义内存管理的首选答案。

### 1. 三个核心组件

- **`std::pmr::memory_resource`**：抽象基类，虚函数 `do_allocate`/`do_deallocate`/`do_is_equal`。所有内存策略都是它的子类。自定义策略只要继承它、实现这三个虚函数。
- **`std::pmr::polymorphic_allocator<T>`**：薄包装，内部持有一个 `memory_resource*`，把 STL 的 allocator 接口转发给该 resource。`std::pmr::vector<T>` 就是 `std::vector<T, polymorphic_allocator<T>>`。
- **标准库自带的几种 resource**：`monotonic_buffer_resource`、`unsynchronized_pool_resource`、`synchronized_pool_resource`、`new_delete_resource()`（默认，走全局 new/delete）。

### 2. `monotonic_buffer_resource`：每帧 arena 的最佳拍档

**只分配、从不单独释放，析构时整块一次性回收。** 这正是 arena 语义：每帧分配一堆临时对象，帧结束整体丢弃。

```cpp
#include <memory_resource>
#include <vector>
#include <string>

void processFrame() {
    // 每帧用一个独立的 arena；这里先用堆做后备缓冲（也可挂栈 buffer，见下）
    std::pmr::monotonic_buffer_resource frameArena{64 * 1024};  // 初始 64KB

    // 所有容器都从这个 arena 取内存，分配几乎就是指针 bump，O(1) 无锁无系统调用
    std::pmr::vector<int>         scanLine{&frameArena};
    std::pmr::vector<std::pmr::string> labels{&frameArena};

    scanLine.reserve(1920);
    for (int columnIndex = 0; columnIndex < 1920; ++columnIndex)
        scanLine.push_back(columnIndex);
    labels.emplace_back("macroblock");

    // ... 处理这一帧
}   // frameArena 析构 → 整块内存一次性归还，所有对象内存随之释放，无逐个 deallocate
```

> `monotonic_buffer_resource` 的 `do_deallocate` 是**空操作**——它不回收单个块，靠析构整体回收。所以它分配极快（指针 bump），但只适合「生命周期一致、一起销毁」的场景，典型就是**每帧 arena**。

### 3. 栈上 buffer + monotonic：零堆分配技巧

把后备缓冲放在**栈上**，小规模数据全程不碰堆——延迟最低、最确定：

```cpp
#include <array>
#include <memory_resource>

void parseHeader(const std::uint8_t* data, std::size_t size) {
    std::array<std::byte, 8192> stackBuffer;          // 8KB 栈缓冲
    std::pmr::monotonic_buffer_resource arena{
        stackBuffer.data(), stackBuffer.size()};      // arena 直接用栈内存

    std::pmr::vector<int> markers{&arena};            // 只要不超过 8KB，全程零堆分配
    // ... 解析；超出 stackBuffer 后 monotonic 才回退到上游（默认 new）申请新块
}                                                     // 栈 buffer 随函数返回自动回收
```

### 4. pool resource：可单独释放的池

- **`unsynchronized_pool_resource`**：按大小分档管理多个空闲块池，**支持单独释放并复用块**，适合「频繁创建销毁、大小不一、生命周期参差」的对象。非线程安全。
- **`synchronized_pool_resource`**：同上但**内部带锁**，可多线程共享。

可以把上游设成 `monotonic_buffer_resource` 或自定义 resource，层层组合（resource 可以指定 upstream）。

```cpp
std::pmr::synchronized_pool_resource sharedPool;   // 多线程安全的池
std::pmr::vector<int> values{&sharedPool};         // 该容器从池里分配
```

### 5. 自定义 memory_resource（接你自己的池子）

把第三节的 `FixedBlockPool` 包成 `memory_resource`，就能喂给任何 `pmr` 容器：

```cpp
class FixedBlockResource : public std::pmr::memory_resource {
public:
    explicit FixedBlockResource(FixedBlockPool* backingPool) : backingPool_(backingPool) {}
private:
    void* do_allocate(std::size_t bytes, std::size_t /*alignment*/) override {
        void* address = backingPool_->allocate(bytes);
        if (address == nullptr) throw std::bad_alloc{};
        return address;
    }
    void do_deallocate(void* address, std::size_t, std::size_t) override {
        backingPool_->deallocate(address);
    }
    bool do_is_equal(const std::pmr::memory_resource& other) const noexcept override {
        return this == &other;   // 同一对象才相等（语义同有状态分配器的 ==）
    }
    FixedBlockPool* backingPool_;
};
```

> **面试标准回答（C++17 pmr 是什么、为什么是现代答案）**：
> 「`std::pmr` 用运行时多态重做了分配器。分配策略全做成 `memory_resource` 的子类，容器统一用 `polymorphic_allocator`，所以不同策略的 `pmr::vector` 是**同一个类型**，能互相赋值、能在运行时换策略，避免了老式 allocator 那种模板类型污染。最常用的是 `monotonic_buffer_resource`，它只分配不单独释放、析构整体回收，就是天然的每帧 arena；还能把后备缓冲放在栈上实现零堆分配。需要单独释放复用就用 `pool_resource`，多线程用 synchronized 版。要接自己的池子，只需继承 `memory_resource` 实现三个虚函数。现在做自定义内存管理我首选 pmr，把传播语义这些复杂度交给标准库。」

## 七、arena / bump allocator（线性分配器）

最简单的分配器：一块连续缓冲 + 一个偏移指针。**分配就是把偏移往前 bump，整个 arena 不支持释放单个对象，只能 `release()` 把偏移归零、整块复用。** `monotonic_buffer_resource` 内部就是这个思路。

```cpp
class BumpAllocator {
public:
    BumpAllocator(void* buffer, std::size_t capacity)
        : bufferStart_(static_cast<std::uint8_t*>(buffer)),
          capacity_(capacity), usedOffset_(0) {}

    void* allocate(std::size_t bytes, std::size_t alignment) noexcept {
        // 把当前偏移向上对齐到 alignment
        std::size_t alignedOffset = (usedOffset_ + alignment - 1) / alignment * alignment;
        if (alignedOffset + bytes > capacity_) return nullptr;   // 缓冲用尽
        usedOffset_ = alignedOffset + bytes;                      // 指针 bump
        return bufferStart_ + alignedOffset;
    }

    void reset() noexcept { usedOffset_ = 0; }   // 帧末整体重置，O(1) 回收全部

private:
    std::uint8_t* bufferStart_;
    std::size_t   capacity_;
    std::size_t   usedOffset_;
};
```

用法就是「每帧分配一堆临时对象，帧末 `reset()` 统一释放」：

```cpp
BumpAllocator perFrameArena(buffer, 256 * 1024);
while (decoding) {
    perFrameArena.reset();                 // 新一帧开始，整体清空（不逐个释放）
    void* a = perFrameArena.allocate(1024, alignof(std::max_align_t));
    void* b = perFrameArena.allocate(2048, 32);   // 给 SIMD 缓冲对齐到 32
    // ... 用这些临时内存做这一帧的滤镜/中间计算
}   // 下一轮 reset，内存复用，零碎片、零系统调用
```

适用：临时对象多、生命周期统一、不需要单独回收的「每帧计算」场景。不适用：对象寿命参差、需要单独释放的情况（那用 pool resource）。

## 八、内存对齐在池子里的处理

池子分配的内存**必须满足所分配对象的对齐要求**，否则在 ARM 上可能直接硬件异常，在 x86 上降速（对齐原理见 [[21-内存对齐、SIMD与缓冲管理]]）。要点：

- **块大小向上取整到对齐边界**：第三节 `FixedBlockPool` 用 `(usableSize + alignment - 1) / alignment * alignment` 把块大小补齐，保证每块首地址都对齐（因为整块起点对齐 + 块大小是对齐的倍数）。
- **整块内存按最大对齐申请**：用 `::operator new(size, std::align_val_t{alignment})`（C++17）或 `posix_memalign`/`std::aligned_alloc` 拿对齐的大块。
- **SIMD 缓冲要 16/32 字节对齐**：放像素/采样数据供 SSE/NEON 处理时，块对齐值要设成 16 或 32，对齐 `bump` 偏移也要按 32 取整。FFmpeg 的 `av_malloc` 默认按 32 字节对齐就是这个原因（见 [[21-内存对齐、SIMD与缓冲管理]]）。
- **bump allocator 每次分配都按传入 alignment 取整**：见第七节 `alignedOffset` 计算，不同对象可要求不同对齐。

## 九、音视频场景小节

- **解码帧池 / `AVFrame` 复用**：解码线程从帧池 `acquire`、渲染线程消费后 `release`，复用对象连同其内部像素缓冲，热路径零分配（第四节）。
- **每帧 arena**：滤镜链、运动估计等每帧产生大量临时中间数据，用 `monotonic_buffer_resource` 或 `BumpAllocator`，帧末整体 `reset`，分配是指针 bump、延迟确定（第六、七节）。
- **packet/帧队列节点**：`std::list`/无锁队列的节点是固定大小，用 `FixedBlockPool` 当节点分配器，O(1) 无碎片（第三、五节）。
- **栈 buffer 解析头部**：解析 SPS/PPS、容器头等小数据，栈上 8KB buffer + monotonic resource，全程零堆分配（第六节）。
- **多线程共享池**：多解码线程共享分配时用 `synchronized_pool_resource` 或加锁的对象池，极端高频再考虑无锁（第四节、[[03-无锁队列]]）。

## 常见坑

| 坑 | 后果 | 正确做法 |
| :--- | :--- | :--- |
| 全局重载 `::operator new` 处理不周 | 影响进程内所有分配（含三方库），崩溃难定位 | 优先类内重载或 `std::pmr`，避免全局重载 |
| 池子块大小没向上对齐 / 没到 `sizeof(void*)` | 对象未对齐（ARM 崩溃）、空闲链表写指针越界 | 块大小取 `max(对象大小, sizeof(void*))` 再向上对齐 |
| 从池子拿的内存用 `delete` 释放 | `delete` 走 `::operator delete` 还给系统堆，破坏池子 | placement new 构造 + 显式 `~T()` 析构 + 池子 `deallocate` |
| placement new 后只 `deallocate` 不调析构 | 对象析构没执行，资源泄漏（如内部 `vector`/句柄） | 归还前先显式 `obj->~T()` 再回收内存 |
| 对象池归还时不重置状态 | 下次 `acquire` 拿到脏数据，难复现 bug | `release` 前 `reset()`，或用 RAII handle 自动重置 |
| 有状态 allocator 的 `operator==` 写错 | 一方释放另一方分配的内存，UB | `==` 如实反映「内存能否互相释放」（同池才相等） |
| `monotonic_buffer_resource` 当通用池用 | 只增不减，长生命周期对象撑爆内存 | 仅用于生命周期一致、整体回收的每帧 arena |
| 多线程共享单线程池不加锁 | 空闲链表数据竞争、双重分配、崩溃 | 加 mutex / 用 `synchronized_pool_resource` / 无锁栈（[[03-无锁队列]]） |
| 池子耗尽后未处理 `nullptr` | 解引用空指针崩溃 | 预估容量、耗尽时扩容或回退到上游 resource |

> **一句话面试总结**：「音视频热路径不能逐帧 `new/delete`，因为系统 `malloc` 有系统调用、锁竞争、碎片和不可预测的尾延迟。我用**预分配 + 池化**解决：固定大小内存池用侵入式空闲链表做到 O(1) 无碎片，对象池复用对象本身连构造析构都省，每帧临时数据用 arena/`monotonic_buffer_resource` 整体回收。要接 STL 容器，现代做法是 C++17 的 `std::pmr`，把分配策略做成 `memory_resource`、容器统一用 `polymorphic_allocator`，既灵活又把传播语义的复杂度交给标准库。全程注意块对齐和线程安全。」
