# C++ 异常与异常安全

> 高级岗高频。重点不是“怎么 try-catch”，而是**异常发生时资源不泄漏、对象状态不损坏**——即异常安全保证，以及它与 RAII、`noexcept`、移动语义的关系。
>
> 相关：RAII 是异常安全的基石，见 [[05-内存管理与对象生命周期]]；`noexcept` 与移动见 [[07-移动语义与右值引用]]、[[15-拷贝消除与三五零法则]]。

---

## 📌 面试速记

- **栈展开（stack unwinding）**：异常抛出后，从抛出点到捕获点之间，所有已构造的**栈对象按逆序自动析构**——这正是 RAII 保证资源释放的机制。
- **三种异常安全保证**：
  - **基本保证**：不泄漏资源，对象仍处于**有效但未指定**的状态。
  - **强保证**：操作要么完全成功，要么**回滚到调用前的状态**（事务语义）。
  - **不抛保证（nothrow）**：操作绝不抛异常，用 `noexcept` 标记。
- **析构函数绝不能抛异常**：栈展开期间若析构再抛，会触发 `std::terminate` 直接终止程序。
- **`noexcept` 的双重作用**：①承诺不抛（违背则 `terminate`）②让 `vector` 扩容等优先用移动而非拷贝。
- **RAII > try-catch**：优先用对象生命周期管理资源，而不是手写 try-catch 释放。

## 一、栈展开：异常如何保证资源释放

异常抛出后，运行时会沿调用栈向上查找匹配的 `catch`，途中把每一层**已经构造完成的局部对象按构造逆序析构**——这就是“栈展开”。RAII 对象（锁、智能指针、文件）的析构在此时被自动调用，所以资源不会泄漏。

```cpp
void process() {
    std::lock_guard<std::mutex> lock(mtx);     // 构造时加锁
    auto buffer = std::make_unique<int[]>(1024);
    mayThrow();                                 // 即使这里抛异常……
    // ……栈展开也会自动析构 buffer（释放内存）和 lock（解锁）
}
```

> 对比 C 风格手动释放：任何一条提前 `return` 或异常都可能跳过 `free`/`unlock`。RAII 把释放绑定到析构，杜绝这种泄漏（见 [[05-内存管理与对象生命周期]]）。

## 二、三种异常安全保证

以“给容器追加元素”为例说明三个层级：

### 1. 基本保证（Basic Guarantee）

抛异常后**不泄漏资源**，对象仍**可析构、可赋值**，但具体内容不保证。这是最低要求，几乎所有代码都应至少做到。

### 2. 强保证（Strong Guarantee）—— 事务语义

操作**要么成功，要么完全不改变状态**。经典实现手法是 **copy-and-swap**：先在副本上完成所有可能抛异常的操作，最后用**不抛异常的 `swap`** 一次性提交。

```cpp
class Config {
    std::vector<int> data_;
public:
    // 强保证的赋值：copy-and-swap
    Config& operator=(Config other) {   // 注意：按值传参，拷贝在这里发生（可能抛，但还没碰 this）
        swap(*this, other);             // swap 不抛，提交点
        return *this;                   // 旧数据随 other 析构释放
    }
    friend void swap(Config& a, Config& b) noexcept {
        using std::swap;
        swap(a.data_, b.data_);         // vector::swap 不抛
    }
};
```

若拷贝阶段抛异常，`this` 还原封未动——这就是强保证。

### 3. 不抛保证（Nothrow Guarantee）

操作**绝不抛异常**，用 `noexcept` 标记。析构函数、`swap`、移动操作、内存释放都应满足这一级。

## 三、为什么析构函数不能抛异常

如果一个异常正在传播（栈展开进行中），此时某个对象的析构函数又抛出**第二个**异常，C++ 运行时无法同时处理两个异常，直接调用 `std::terminate()` 终止程序。

```cpp
class Bad {
public:
    ~Bad() { throw std::runtime_error("boom"); } // ❌ 析构抛异常
};
// 若 Bad 在栈展开期间被析构 → terminate
```

**实践**：

- 析构函数默认隐式 `noexcept`，**不要**在里面抛异常。
- 析构里若有可能失败的操作（如 `close` 刷盘），**就地 try-catch 吞掉或记录日志**，绝不外抛。

## 四、noexcept 的作用与代价

```cpp
void fastPath() noexcept;                 // 承诺不抛；若真抛了 → terminate
Buffer(Buffer&& other) noexcept;          // 移动构造标 noexcept
```

1. **契约**：告诉调用方和编译器“我不抛”。违背承诺不是抛出去，而是 `std::terminate`。
2. **性能**：编译器可省去异常处理的栈展开登记，生成更紧凑的代码。
3. **关键联动**：`std::vector` 扩容搬迁元素时，**只有元素的移动构造是 `noexcept`，才会用移动**；否则为保证扩容的强异常安全，退回**拷贝**（见 [[07-移动语义与右值引用]]、[[12-STL容器底层]]）。这是“移动构造一定要写 `noexcept`”的根本原因。

## 五、异常 vs 错误码（工程权衡）

| | 异常 | 错误码 / `std::optional` / `std::expected` |
| :--- | :--- | :--- |
| 适用 | 真正“异常”、不该常发生的错误 | 高频可预期的失败（查找未命中、解析失败） |
| 开销 | 不抛时几乎零开销；抛出时较重 | 恒定、可预测 |
| 音视频实践 | 初始化、打开设备等少数路径 | **解码热路径多用错误码/返回值**，避免每帧抛异常的开销 |

> 很多音视频/嵌入式项目（含 FFmpeg 这类 C 库）甚至**全程关异常**（`-fno-exceptions`），用返回值传递错误。面试可提：“是否用异常要看团队规范和性能约束；热路径我倾向返回值/`expected`，异常留给真正异常的初始化路径。”

## 六、常见坑

- **在析构里抛异常** → `terminate`（见上）。
- **移动构造忘了 `noexcept`** → 容器扩容退化为拷贝，性能损失。
- **裸 new 后到 delete 之间可能抛异常** → 用智能指针 / RAII，别裸管理。
- **catch 时按值捕获异常对象** → 可能切片（见 [[08-继承、多态、虚函数与对象模型]] 对象切片）；应 `catch (const std::exception& e)` 按 const 引用捕获。
- **构造函数抛异常**：对象未完成构造，其**析构函数不会被调用**，但**已构造完成的成员/基类会被析构**——所以成员用 RAII 类型仍然安全。

> 面试一句话：“异常安全的核心是 RAII + 栈展开：异常传播时栈对象自动逆序析构，资源不漏。我会按基本/强/不抛三级要求接口，强保证常用 copy-and-swap，移动和 swap 标 `noexcept`。析构绝不抛异常，否则栈展开期间会 terminate。性能热路径（如逐帧解码）我倾向用返回值而非异常。”
