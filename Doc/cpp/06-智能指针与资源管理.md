# C++ 智能指针：原理、实战与面试避坑指南

在现代 C++（C++11 及以后）中，裸指针（Raw Pointer）和手动的 `new/delete` 已经被视为“坏味道”。取而代之的是智能指针（Smart Pointers），它们利用 RAII（资源获取即初始化）机制，极大地降低了内存泄漏和野指针的风险。

面试中，智能指针是必考题，考察重点通常集中在：**底层原理、循环引用问题、以及生命周期管理的安全性**。

---

## 一、 智能指针的三剑客

C++11 提供了三种核心的智能指针，它们都定义在 `<memory>` 头文件中。

### 1. `std::unique_ptr`：独占所有权

**核心思想**：这块内存**只属于我一个人**。我生它生，我死它死。

- **特点**：
  - **禁止拷贝**：你不能把一个 `unique_ptr` 赋值给另一个（编译器直接报错）。
  - **允许移动**：你可以通过 `std::move()` 把所有权“转让”给别人。转让后，原来的指针变成 `nullptr`。
  - **零开销**：在默认情况下，`unique_ptr` 的大小和裸指针一模一样，没有任何性能损耗。
- **适用场景**：局部变量、类的独占成员、工厂模式的返回值。

```cpp
#include <memory>

void testUnique() {
    // 推荐使用 make_unique (C++14 引入)
    std::unique_ptr<int> p1 = std::make_unique<int>(100);
    
    // std::unique_ptr<int> p2 = p1; // ❌ 编译报错！禁止拷贝
    
    std::unique_ptr<int> p3 = std::move(p1); // ✅ 允许移动
    // 此时 p1 变成了 nullptr，p3 拥有了那块内存
} // 函数结束，p3 离开作用域，内存自动释放
```

### 2. `std::shared_ptr`：共享所有权

**核心思想**：这块内存**大家一起用**。只要还有一个人在用，它就不销毁；当最后一个人离开时，自动销毁。

- **特点**：
  - **引用计数**：底层维护了一个“控制块（Control Block）”，里面有一个强引用计数（Strong Count）。
  - **允许拷贝**：每次拷贝，引用计数 +1；每次销毁，引用计数 -1。
  - **线程安全**：引用计数的增减是**原子操作（Atomic）**，所以多线程拷贝/销毁 `shared_ptr` 是安全的。（但多个线程同时读写它**指向的数据**是不安全的，需要加锁）。
- **适用场景**：多线程数据共享、复杂的对象图（如 DAG）。

```cpp
void testShared() {
    // 强烈推荐使用 make_shared！(原因见后文)
    std::shared_ptr<int> p1 = std::make_shared<int>(200); // 引用计数 = 1
    
    {
        std::shared_ptr<int> p2 = p1; // 拷贝，引用计数 = 2
        std::cout << p1.use_count() << std::endl; // 输出 2
    } // p2 离开作用域，引用计数 = 1
    
} // p1 离开作用域，引用计数 = 0，内存真正释放
```

### 3. `std::weak_ptr`：弱观察者

**核心思想**：我只是**看看**，我不干涉它的寿命。

- **特点**：
  - **不增加强引用计数**：把它指向一个 `shared_ptr` 时，不会增加强引用计数（但会增加弱引用计数）。
  - **不能直接访问数据**：它没有重载 `->` 和 `*` 运算符。
  - **必须提升（Lock）后使用**：想访问数据时，必须调用 `.lock()` 方法，尝试把它提升为一个临时的 `shared_ptr`。如果对象已经被销毁了，`lock()` 会返回一个空的 `shared_ptr`。
- **适用场景**：打破循环引用、观察者模式（Observer Pattern）、缓存（Cache）。

#### 弱引用：C++ 有没有这个概念？

**结论**：C++ **没有**像 Java / C# 那样、由 GC 驱动的标准「弱引用」类型；但 **`std::weak_ptr` 就是配合 `std::shared_ptr` 的弱引用机制**，语义上最接近其他语言里的弱引用。

| | Java `WeakReference` | C++ `std::weak_ptr` |
|---|---|---|
| 内存管理 | GC 回收对象 | 引用计数（`shared_ptr`）归零时析构 |
| 是否阻止回收/析构 | 弱引用不阻止 GC | 不增加强引用计数（`use_count`） |
| 典型用途 | 打破循环引用、缓存 | 打破 `shared_ptr` 循环引用、观察者、缓存 |

C++ 没有 GC，所以「弱」的含义是：**不持有对象的所有权，也不阻止 `shared_ptr` 管理的对象被销毁**。使用前必须 `lock()`（或检查 `expired()`），因为对象可能随时被析构；多线程下尤其要注意 TOCTOU，一般 **`lock()` 一次拿到 `shared_ptr` 再使用**，不要在 `expired()` 和 `lock()` 之间拆开用。

**其他相关但不等同的东西**：

- **裸指针 / 引用**：语言层面没有「弱/强」语义，生命周期全靠约定，用错了就是悬空指针。
- **`std::enable_shared_from_this` 内部的 `weak_ptr`**：见后文考点 3，本质是复用同一块控制块，而不是另建一套弱引用体系。
- **自定义弱引用**：可维护注册表 + 裸指针，在析构时通知置空，本质是手写的观察者模式；若不用 `shared_ptr`，就没有标准库级的弱引用。

```cpp
void testWeak() {
    std::shared_ptr<int> sp = std::make_shared<int>(300);
    std::weak_ptr<int> wp = sp; // 强引用计数依然是 1
    
    // 必须提升后才能使用
    if (std::shared_ptr<int> tempSp = wp.lock()) {
        std::cout << "对象还活着: " << *tempSp << std::endl;
    } else {
        std::cout << "对象已销毁" << std::endl;
    }
}
```

#### 当 `shared_ptr` 全部释放后，`weak_ptr` 里会发生什么？

当所有指向该对象的 `shared_ptr` 都销毁或 `reset()`，**强引用计数变为 0** 时：

1. **被管理的对象 `T` 会立刻析构**——堆上的对象内存已无效，不能再通过任何 `shared_ptr` 访问。
2. **`weak_ptr` 本身不会变成悬空指针**。它内部通常不直接保存对象地址，而是指向**控制块（control block）**。强引用归零后，控制块**仍然保留**（只要还有 `weak_ptr` 指着它），此时 `weak_ptr` 变为 **expired（已过期）**，但变量本身仍然合法。
3. **可观察到的行为**：

| 操作 | 对象已析构、控制块仍在时 |
|---|---|
| `wp.expired()` | `true` |
| `wp.use_count()` | `0`（强引用计数） |
| `wp.lock()` | 返回**空的** `shared_ptr`，不会访问已析构对象 |
| `*wp` / `wp->` | ❌ 未重载，编译不过 |

```cpp
auto sp = std::make_shared<Foo>();
std::weak_ptr<Foo> wp = sp;

sp.reset();  // 最后一个 shared_ptr 释放，Foo 析构

wp.expired();   // true
wp.use_count(); // 0
wp.lock();      // 空 shared_ptr，安全
// wp 不会自动变成 nullptr，仍绑定控制块，只是所观察的对象已死
```

4. **控制块何时真正释放？** 要等**最后一个 `weak_ptr` 也销毁**（或 `reset()`），弱引用计数归零，控制块才从堆上释放。这也是 `make_shared` 的副作用：对象与控制块在同一块连续内存时，即使 `T` 已析构，只要还有 `weak_ptr`，整块内存也可能暂时无法还给操作系统（见考点 1）。

5. **多线程注意**：`expired()` 为 `false` 之后、调用 `lock()` 之前，别的线程可能刚好释放最后一个 `shared_ptr`（TOCTOU）。稳妥写法是一次 `lock()` 拿到 `shared_ptr` 再用，不要拆开 `expired()` 和 `lock()`。

## 二、 面试核心考点深度解析

### 考点 1：为什么强烈推荐使用 `std::make_shared`？

面试官经常问：“`shared_ptr<T> p(new T())` 和 `make_shared<T>()` 有什么区别？”

**答：有两大核心区别：性能（内存分配次数）和异常安全性。**

1. **性能差异（核心原理）**：
  - **传统写法 `shared_ptr<Widget> p(new Widget());`**：需要分配**两次**内存。
    - 第一次：`new Widget()` 在堆上为对象本身分配内存。
    - 第二次：`shared_ptr` 构造时，在堆上为“控制块（存放引用计数的地方）”再分配一块内存。
    - **缺点**：两次分配开销大，且两块内存物理上不连续，容易造成内存碎片，CPU 缓存命中率低（Cache Miss）。
  - **现代写法 `make_shared<Widget>()`**：只分配**一次**连续的内存。
    - 它会计算好对象和控制块所需的总大小，向系统一次性申请一块足够大的连续内存。
    - **优点**：分配快，内存紧凑，CPU 读取对象时能顺便把旁边的控制块读进缓存，性能极佳。
2. **异常安全性**：
  - 假设有这样一个调用：`process(std::shared_ptr<Widget>(new Widget()), computePriority());`
  - C++ 编译器可能会这样安排执行顺序：1. `new Widget()` -> 2. 执行 `computePriority()` -> 3. 构造 `shared_ptr`。
  - **致命隐患**：如果在第 2 步 `computePriority()` 抛出了异常，那么第 1 步 `new` 出来的内存就永远泄露了（因为还没来得及交给 `shared_ptr` 管理）。
  - 使用 `make_shared` 可以完美避开这个问题，因为它将对象的创建和智能指针的绑定合并成了一个原子操作。

*(面试加分项：`make_shared` 的唯一缺点是，因为对象和控制块在同一块连续内存上，如果有一个生命周期极长的 `weak_ptr` 盯着它，即使强引用归零对象析构了，这整块大内存也必须等到弱引用归零后才能还给操作系统。)*

### 考点 2：致命的循环引用（Circular Reference）

这是 `shared_ptr` 最大的痛点，也是必考题。

**场景**：A 拥有一个指向 B 的 `shared_ptr`，B 也拥有一个指向 A 的 `shared_ptr`。
**结果**：A 等着 B 销毁，B 等着 A 销毁。两者的引用计数永远降不到 0，导致**内存泄漏**。

```cpp
class NodeB; // 前向声明

class NodeA {
public:
    std::shared_ptr<NodeB> ptrB;
    ~NodeA() { std::cout << "A 销毁" << std::endl; }
};

class NodeB {
public:
    std::shared_ptr<NodeA> ptrA; // ❌ 导致循环引用
    ~NodeB() { std::cout << "B 销毁" << std::endl; }
};

void testLeak() {
    auto a = std::make_shared<NodeA>();
    auto b = std::make_shared<NodeB>();
    a->ptrB = b;
    b->ptrA = a;
} // 函数结束，A 和 B 都没有被销毁，发生内存泄漏！
```

**解法**：将其中一个指针改为 `std::weak_ptr`。

```cpp
class NodeB {
public:
    std::weak_ptr<NodeA> ptrA; // ✅ 改为 weak_ptr，打破循环
};
```

在实际开发中（如树、图结构），通常的原则是：**父节点对子节点用 `shared_ptr`（拥有所有权），子节点对父节点用 `weak_ptr`（只观察不拥有）。**

### 考点 3：`std::enable_shared_from_this` 的底层逻辑与使用场景

当一个已经被 `shared_ptr` 管理的对象，想在自己的成员函数内部，把 `this` 指针安全地传递给其他线程或回调函数时，**绝对不能直接写 `std::shared_ptr<T>(this)`**。

**为什么不能直接用 `shared_ptr<T>(this)`？**
如果你这样做，系统会为这个裸指针 `this` **新建一个全新的控制块（Control Block）**。这意味着同一个对象拥有了两个互不相干的引用计数系统。当其中一个归零时，对象会被 `delete` 一次；当另一个归零时，对象会被**再次 `delete`**，直接导致严重的 Double Free 崩溃。

**正确做法**：

1. 让类公开继承 `std::enable_shared_from_this<T>`。
2. 在类内部调用 `shared_from_this()`。

**底层逻辑（原理）——`weak_ptr` 是怎么塞进去的**：

`enable_shared_from_this` 的简化实现大致长这样：

```cpp
template<typename T>
class enable_shared_from_this {
private:
    // 关键：内部藏了一个 mutable weak_ptr
    // mutable 使得即使 const 成员函数里也能修改它（首次初始化）
    mutable std::weak_ptr<T> __weak_this_;

public:
    // shared_from_this() 本质上就是对内部的 weak_ptr 调 lock()
    std::shared_ptr<T> shared_from_this() {
        return __weak_this_.lock();       // lock 成功 → 返回共享控制块的 shared_ptr
    }

    std::shared_ptr<const T> shared_from_this() const {
        return __weak_this_.lock();       // const 版本同上
    }

    // 注意：没有任何地方在构造时自动初始化 __weak_this_
    //       __weak_this_ 出生就是一个"空"的 weak_ptr（不指向任何控制块）
};
```

**那 `__weak_this_` 什么时候被赋值？** ——答案在 `shared_ptr` 的构造函数里。

当 `shared_ptr<T>` 构造时，它会用模板元编程（`std::is_convertible<T*, enable_shared_from_this<T>*>`）检测你的类是否继承了 `enable_shared_from_this`。如果检测通过，就调用从 `enable_shared_from_this` 继承来的一个隐藏方法，把 `__weak_this_` 指向当前的控制块：

```cpp
// 简化的 shared_ptr 构造函数逻辑（核心部分）：
template<typename T>
shared_ptr<T>::shared_ptr(T* ptr) {
    // ...分配控制块...

    // 编译期判断：T 继承自 enable_shared_from_this 吗？
    if constexpr (std::is_base_of_v<enable_shared_from_this<T>, T>) {
        // 是 → 把内部的 weak_ptr 初始化，指向我刚刚创建的控制块
        ptr->__init_weak_this(control_block);  // 如果控制块不存在，则析构实参并抛出异常
    }
}
```

`__init_weak_this` 做的事很简单：

```cpp
void __init_weak_this(const std::shared_ptr<T>& sp) {  // 非标准内部名称
    if (__weak_this_.expired()) {       // 幂等保护：只初始化一次
        __weak_this_ = sp;              // weak_ptr = shared_ptr → 不增加强引用计数
    }
}
```

`__weak_this_ = sp;` 这一行是关键——`weak_ptr` 从 `shared_ptr` 赋值：**不增加强引用计数**（`use_count` 不变），但 `weak_ptr` 从此绑定到了同一个控制块。后续 `shared_from_this()` 调 `lock()` 时就能拿到指向该控制块的有效 `shared_ptr`。

**整个链条串起来**：

```
std::make_shared<TcpConnection>()
  │
  ├─ 1. operator new(sizeof(TcpConnection) + sizeof(控制块))
  ├─ 2. 在这块内存上构造 TcpConnection 对象
  │       └─ enable_shared_from_this 的构造函数：__weak_this_ = {}（空）
  │
  ├─ 3. shared_ptr 构造函数
  │       ├─ 构建控制块（强引用计数=1, 弱引用计数=1）
  │       └─ 检测到 TcpConnection 继承了 enable_shared_from_this
  │            └─ 调用 __init_weak_this(控制块的 shared_ptr 视图)
  │                 └─ __weak_this_ = 该视图       ← 初始化发生在这里！
  │
  └─ 4. 返回 shared_ptr<TcpConnection>

之后任意成员函数里:
  shared_from_this()
    → __weak_this_.lock()
    → weak_ptr 已绑定控制块 → 返回强引用计数+1 的 shared_ptr ✓
```

**对照：不经过 `shared_ptr` 构造时**：

```
TcpConnection conn;        // 栈变量，或 TcpConnection* p = new TcpConnection;
  └─ enable_shared_from_this 的构造函数：__weak_this_ = {}（空）
  └─ 没有任何 shared_ptr 来触发 __init_weak_this
  └─ __weak_this_ 永远为空

conn.shared_from_this()
  → __weak_this_.lock()
  → weak_ptr 是空的 → lock() 返回空的 shared_ptr
  → C++17: 抛 std::bad_weak_ptr；C++11/14: 未定义行为
```

**经典使用场景举例：异步网络回调**
假设你写了一个 `TcpConnection` 类，负责收发数据。

```cpp
#include <memory>
#include <iostream>
#include <thread>

class TcpConnection : public std::enable_shared_from_this<TcpConnection> {
public:
    void startRead() {
        // ❌ 错误示范：std::shared_ptr<TcpConnection>(this) 会导致崩溃！
        
        // ✅ 正确示范：把自己的生命周期安全地交给异步回调
        auto self = shared_from_this(); 
        
        // 假设这是一个异步线程
        std::thread([self]() {
            std::cout << "异步线程正在处理数据..." << std::endl;
            // 只要这个回调还在执行，self 就会让控制块引用计数 +1
            // 保证外面的对象哪怕释放了，这块内存也活着，避免崩溃
        }).detach();
    }
};

void testConnection() {
    auto conn = std::make_shared<TcpConnection>();
    conn->startRead();
} // conn 离开作用域，但由于异步线程里还有一个 self (shared_ptr) 引用着，对象不会立刻销毁
```

在这个场景中，如果没有 `shared_from_this()` 帮忙”续命”，`testConnection` 函数一结束，`conn` 对象就被销毁了。此时异步线程里如果再尝试访问 `this` 的成员，就会触发野指针崩溃。

---

### ⚠️ 关键约束：对象必须已被 `shared_ptr` 接管

`enable_shared_from_this` 不是”自动生效”的——它内部有一个 `weak_ptr` 成员变量，**这个 `weak_ptr` 只有当你用 `shared_ptr`（或 `make_shared`）创建对象时才会被初始化**。

**不初始化的后果**：调 `shared_from_this()` 会直接崩。

```cpp
// ❌ 栈对象——内部 weak_ptr 从未初始化，调 shared_from_this() 一定崩
void bad_stack() {
    TcpConnection conn;            // 普通栈变量，没有 shared_ptr 管它
    conn.startRead();              // startRead 里调 shared_from_this()
                                   //   → weak_ptr 是空的 → std::bad_weak_ptr 异常或 crash
}

// ❌ 裸指针 new 出来，但没有 shared_ptr 接管——同样崩
void bad_raw() {
    TcpConnection* conn = new TcpConnection();  // 只有裸 new，没有 shared_ptr
    conn->startRead();                          // 同样崩，内部 weak_ptr 没被初始化
}

// ❌ 用 shared_ptr<T>(this) 也不行——会创建第二个控制块，导致 double free
void TcpConnection::bad_manual() {
    std::shared_ptr<TcpConnection> bad(this);  // 新建控制块！跟外层不是同一个
    // 外层 shared_ptr 归零 → delete 一次
    // 这个 bad 归零 → 再 delete 一次 → double free
}

// ✅ 唯一正确用法：对象必须通过 shared_ptr / make_shared 创建
void good() {
    auto conn = std::make_shared<TcpConnection>();  // make_shared 初始化内部 weak_ptr
    conn->startRead();                               // shared_from_this() 安全返回
}
```

**初始化链条**：

```
std::make_shared<TcpConnection>()
  ├─ 分配内存（对象 + 控制块）
  ├─ 调用 TcpConnection 构造函数
  └─ shared_ptr 构造函数检测到”继承了 enable_shared_from_this”
       └─ 访问 TcpConnection 内部的 weak_ptr 成员
       └─ 让这个 weak_ptr 指向当前的控制块      ← 初始化发生在这里

之后:
  shared_from_this()
    └─ 内部 weak_ptr.lock()
         └─ weak_ptr 已指向控制块 → lock 成功 → 返回 shared_ptr ✓
```

**如果不走这个链条**（栈变量、裸 `new`、`shared_ptr<T>(this)`），内部 `weak_ptr` 始终是空的，`shared_from_this()` 等价于对一个空 `weak_ptr` 调 `lock()`——C++17 起抛 `std::bad_weak_ptr` 异常，C++11/14 是未定义行为。

**一句话总结**：`enable_shared_from_this` 不魔法——它只是一个被动的”挂钩”。**`shared_ptr` 构造时才给它装上钩子，不用 `shared_ptr` 它就是空的。**

---

## 三、 智能指针的选择流程图（实战指南）

在实际写代码时，遇到指针该怎么选？遵循以下决策树：

1. **这个指针拥有这块内存吗？（负责它的生死吗？）**
  - **不负责**：使用裸指针（`T*`）或引用（`T&`）。（是的，现代 C++ 依然大量使用裸指针，只要你不去 `delete` 它）。
  - **负责**：进入下一步。
2. **这块内存是独占的，还是大家共享的？**
  - **独占的**（90% 的情况）：毫不犹豫地使用 `**std::unique_ptr`**。
  - **共享的**：进入下一步。
3. **共享的场景下，你是要干涉它的寿命，还是只旁观？**
  - **干涉寿命**（我还在用，它就不能死）：使用 `**std::shared_ptr`**。
  - **只旁观**（如果它死了，我能知道就行）：使用 `**std::weak_ptr`**。

## 四、智能指针常用方法

### 1. `std::unique_ptr` 常用方法

`unique_ptr` 表示独占所有权，最常用的方法是 `get`、`reset`、`release`、`std::move`。

```cpp
#include <memory>
#include <iostream>

struct Foo {
    void hello() {
        std::cout << "hello\n";
    }
};

void testUniquePtrMethods() {
    auto p = std::make_unique<Foo>();

    p->hello();        // 像普通指针一样访问成员
    (*p).hello();      // 解引用后访问对象

    Foo* raw = p.get(); // 只借用裸指针,不转移所有权
    raw->hello();

    if (p) {
        std::cout << "p is not null\n";
    }

    auto p2 = std::move(p); // 转移所有权,p 变成 nullptr

    p2.reset(new Foo());    // 释放旧对象,接管新对象
    p2.reset();             // 释放当前对象,p2 变成 nullptr
}
```

几个方法的含义：

- `get()`：拿到底层裸指针，只是借用，不要手动 `delete`。
- `reset(ptr)`：释放当前对象，并接管新的裸指针。
- `reset()`：释放当前对象，智能指针变空。
- `release()`：放弃所有权并返回裸指针，智能指针变空，但不会释放对象。
- `std::move(p)`：把所有权转移给另一个 `unique_ptr`。
- `operator bool()`：判断当前是否持有对象。
- `operator->` / `operator*`：像普通指针一样访问对象。

`release()` 最容易用错：

```cpp
auto p = std::make_unique<Foo>();

Foo* raw = p.release(); // p 不再管理对象

// 现在必须手动 delete,否则泄漏
delete raw;
```

所以普通业务代码里很少需要 `release()`。它通常只在把对象所有权交给老 C API 或第三方库时使用。

### 2. `std::shared_ptr` 常用方法

`shared_ptr` 表示共享所有权，常用方法是 `use_count`、`reset`、`get`、拷贝和移动。

```cpp
#include <memory>
#include <iostream>

void testSharedPtrMethods() {
    auto p1 = std::make_shared<int>(100);
    std::cout << *p1 << "\n";

    std::shared_ptr<int> p2 = p1; // 共享所有权,引用计数 +1
    std::cout << p1.use_count() << "\n"; // 通常输出 2

    int* raw = p1.get(); // 只借用,不要 delete
    std::cout << *raw << "\n";

    p2.reset();          // p2 放弃所有权,引用计数 -1
    std::cout << p1.use_count() << "\n"; // 通常输出 1

    p1.reset();          // 最后一个 shared_ptr 释放,对象析构
}
```

几个方法的含义：

- `use_count()`：返回当前强引用计数，调试可以用，业务逻辑不要强依赖它。
- `unique()`：C++20 已移除，老代码里表示 `use_count() == 1`。
- `get()`：拿到底层裸指针，只借用，不要手动 `delete`。
- `reset()`：放弃当前所有权，引用计数减 1。
- `reset(ptr)`：放弃当前对象，接管新的裸指针并创建新的控制块。
- `operator bool()`：判断是否持有对象。
- `operator->` / `operator*`：访问对象。

注意：`shared_ptr` 的引用计数增减是线程安全的，但它指向的对象本身不是自动线程安全的。

```cpp
auto p = std::make_shared<int>(0);

// 多线程拷贝 p 本身通常没问题
// 多线程同时修改 *p 仍然需要锁
```

### 3. `std::weak_ptr` 常用方法

`weak_ptr` 不拥有对象，只观察由 `shared_ptr` 管理的对象。常用方法是 `lock`、`expired`、`use_count`、`reset`。

```cpp
#include <memory>
#include <iostream>

void testWeakPtrMethods() {
    std::weak_ptr<int> wp;

    {
        auto sp = std::make_shared<int>(42);
        wp = sp;

        if (auto locked = wp.lock()) {
            std::cout << *locked << "\n";
        }
    }

    if (wp.expired()) {
        std::cout << "object destroyed\n";
    }
}
```

几个方法的含义：

- `lock()`：尝试提升为 `shared_ptr`。对象还活着就返回有效 `shared_ptr`，否则返回空。
- `expired()`：判断对象是否已经析构。
- `use_count()`：返回强引用计数。
- `reset()`：清空当前观察关系。

多线程场景里，推荐直接用 `lock()`：

```cpp
if (auto sp = wp.lock()) {
    sp->doSomething();
}
```

不要先 `expired()` 再 `lock()` 分开写，因为两步之间对象可能被其他线程释放。

## 五、自定义 Deleter：用智能指针管理 C 资源

智能指针不只能管理 `new` 出来的 C++ 对象，也可以管理 C 库返回的资源。关键是告诉智能指针：**释放时应该调用哪个函数**。

### 1. 为什么需要自定义 deleter

默认情况下：

```cpp
std::unique_ptr<Foo> p(new Foo());
```

`p` 析构时会调用：

```cpp
delete p;
```

但很多 C 库不是用 `delete` 释放资源，而是有自己的释放函数。例如 FFmpeg：

```cpp
AVFrame* frame = av_frame_alloc();
av_frame_free(&frame);

AVPacket* pkt = av_packet_alloc();
av_packet_free(&pkt);
```

如果直接用默认 `unique_ptr`：

```cpp
std::unique_ptr<AVFrame> frame(av_frame_alloc()); // 错误思路
```

析构时会调用 `delete frame`，这和 FFmpeg 的分配/释放规则不匹配，可能导致崩溃或资源泄漏。

### 2. FFmpeg 常用写法

可以给 `unique_ptr` 配一个自定义 deleter：

```cpp
extern "C" {
    #include <libavcodec/packet.h>
    #include <libavutil/frame.h>
}

#include <memory>

struct AVFrameDeleter {
    void operator()(AVFrame* frame) const {
        av_frame_free(&frame);
    }
};

using AVFramePtr = std::unique_ptr<AVFrame, AVFrameDeleter>;

struct AVPacketDeleter {
    void operator()(AVPacket* pkt) const {
        av_packet_free(&pkt);
    }
};

using AVPacketPtr = std::unique_ptr<AVPacket, AVPacketDeleter>;
```

使用时：

```cpp
AVFramePtr frame(av_frame_alloc());
AVPacketPtr pkt(av_packet_alloc());

if (!frame || !pkt) {
    return;
}

// 正常使用 frame.get() / pkt.get() 传给 FFmpeg C API
av_packet_unref(pkt.get());

// 函数退出时自动调用 av_frame_free / av_packet_free
```

这里有两个关键点：

- `unique_ptr` 负责外层生命周期，离开作用域自动释放。
- `get()` 只是把裸指针借给 C API，不转移所有权。

### 3. FFmpeg 的 `*_free` 为什么要传二级指针

FFmpeg 很多释放函数长这样：

```cpp
void av_frame_free(AVFrame **frame);
void av_packet_free(AVPacket **pkt);
```

它们需要二级指针，是因为释放后还会把原指针置为 `nullptr`，避免悬空指针。

但 `unique_ptr` 的 deleter 收到的是裸指针副本：

```cpp
void operator()(AVFrame* frame) const
```

所以 deleter 里写：

```cpp
av_frame_free(&frame);
```

这里把局部变量 `frame` 的地址传进去即可。真正的底层对象会被释放；`unique_ptr` 自己马上也要析构了，不需要再关心它内部保存的指针是否被置空。

### 4. `get()`、`release()`、`reset()` 在 C API 场景里的区别

调用只借用指针的 C API，用 `get()`：

```cpp
AVPacketPtr pkt(av_packet_alloc());

av_read_frame(fmtCtx, pkt.get()); // FFmpeg 往这个 packet 壳子里填数据
av_packet_unref(pkt.get());       // 循环里释放内部引用,packet 壳子仍由 unique_ptr 管
```

需要提前释放并换一个新对象，用 `reset()`：

```cpp
pkt.reset(av_packet_alloc()); // 先 av_packet_free 旧 packet,再接管新 packet
```

只有在把所有权交给外部系统时，才考虑 `release()`：

```cpp
AVPacket* raw = pkt.release();

// 从这里开始 unique_ptr 不再负责释放 raw
// 必须保证后续有人调用 av_packet_free(&raw)
```

如果 `release()` 后没有其他代码负责释放，就是内存泄漏。

### 5. 其他常见 C 资源包装

文件句柄：

```cpp
#include <cstdio>
#include <memory>

struct FileDeleter {
    void operator()(FILE* fp) const {
        if (fp) {
            fclose(fp);
        }
    }
};

using FilePtr = std::unique_ptr<FILE, FileDeleter>;

FilePtr file(fopen("test.txt", "rb"));
```

数组：

```cpp
std::unique_ptr<int[]> arr(new int[10]);
arr[0] = 1;
```

不过现代 C++ 里，动态数组通常优先用 `std::vector`。

自定义 lambda deleter：

```cpp
auto deleter = [](FILE* fp) {
    if (fp) {
        fclose(fp);
    }
};

std::unique_ptr<FILE, decltype(deleter)> file(fopen("test.txt", "rb"), deleter);
```

### 6. 面试回答版本

可以这样说：

> 智能指针的核心是 RAII。`unique_ptr` 用于独占所有权，常用 `get/reset/release/std::move`；`shared_ptr` 用引用计数管理共享所有权，常用 `use_count/reset/get`；`weak_ptr` 不拥有对象，常用 `lock/expired` 观察对象是否还活着。对于 FFmpeg 这类 C 库资源，不能让 `unique_ptr` 默认 `delete`，而是要提供自定义 deleter，在析构时调用 `av_frame_free`、`av_packet_free` 这类库提供的释放函数。
