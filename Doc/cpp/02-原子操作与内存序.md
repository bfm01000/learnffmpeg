# C++ 原子操作与内存序（std::atomic / memory_order）

> 这是音视频高级岗与并发岗的**核心区分点**。锁讲“互斥”，本篇讲“在不加锁的前提下，如何让多线程对共享变量的读写既原子、又有正确的可见性与顺序”。
>
> 前置：互斥与条件变量见 [[01-多线程与锁]]；本篇内存序是 [[03-无锁队列]] 的理论基础；`volatile` 为何不能替代 atomic 的完整论证见 [[13-语言基础关键字]]。

---

## 📌 面试速记（考前 10 分钟扫一遍）

- **atomic 不是锁的平替**：它保证**单个变量**的读-改-写不可分割；多个变量之间的一致性约束（复合不变量）该用 mutex。
- **三件事**：多线程正确性要同时解决①**原子性**②**可见性**③**有序性**。`std::atomic` 通过原子指令解决原子性，通过 `memory_order` 解决可见性与有序性。
- **memory_order 五档**（常用三档）：`relaxed`（只保证原子性，不保证顺序）、`acquire`/`release`（配对建立 happens-before，最常用）、`seq_cst`（全局单一顺序，最强也最贵，是默认值）。
- **release-acquire 配对**：写线程 `store(release)`，读线程 `load(acquire)`；一旦读线程读到了写线程 release 的值，写线程在 release **之前**的所有写入对读线程都可见。这是无锁同步的基石。
- **CAS**：`compare_exchange_weak/strong`，无锁数据结构的核心原语；要警惕 **ABA 问题**（见 [[03-无锁队列]]）。
- **默认 `seq_cst` 最安全**：拿不准内存序就用默认值，先正确再优化。

## 一、atomic 和锁是什么关系？

### 1. atomic 适合保护“单个变量”

停止标记、状态位、引用计数这类单变量场景，用 atomic 比 mutex 更轻：

```cpp
std::atomic<bool> stop{false};

void requestStop() { stop.store(true, std::memory_order_release); }
void worker()      { while (!stop.load(std::memory_order_acquire)) { /* do work */ } }
```

### 2. “多变量复合不变量”更适合锁

```cpp
std::queue<Packet> queue;
size_t count;          // 约束：count 必须 == queue 真实元素数
```

`queue` 和 `count` 要始终一致，这是**复合不变量**，单靠 atomic 很难维护，应该用 mutex 把它们一起保护：

```cpp
std::mutex mtx;
void push(Packet packet) {
    std::lock_guard<std::mutex> lock(mtx);
    queue.push(std::move(packet));
    count = queue.size();
}
```

### 3. 易混边界：`shared_ptr` 的线程安全

`shared_ptr` 的**引用计数**是原子的（多线程拷贝同一个 `shared_ptr` 安全），但它**指向的对象本身不是线程安全的**：

```cpp
auto sharedVec = std::make_shared<std::vector<int>>();
// 多线程拷贝 sharedVec：安全（引用计数原子增减）
// 多线程同时 sharedVec->push_back(1)：不安全，vector 本身要另行加锁
```

> 面试标准回答：“atomic 适合单个变量——停止标记、引用计数、状态位；mutex 适合一组有一致性约束的共享状态。别因为 atomic 看着轻量就硬写 lock-free，复杂 lock-free 极易写错内存序，维护成本很高。”

## 二、std::atomic 常用操作

```cpp
std::atomic<int> value{0};

value.store(10, std::memory_order_release);     // 原子写
int snapshot = value.load(std::memory_order_acquire); // 原子读
int old = value.exchange(20);                   // 原子交换，返回旧值
value.fetch_add(1, std::memory_order_relaxed);  // 原子 +1，返回旧值（计数器常用）
value.fetch_sub(1);                             // 原子 -1

// CAS：比较并交换
int expected = 20;
bool ok = value.compare_exchange_strong(expected, 30);
// 若 value == expected，则 value = 30 返回 true；
// 否则把 value 的当前值写回 expected，返回 false
```

- **`++value` / `value += 1`** 对 atomic 是原子的（等价 `fetch_add`），默认 `seq_cst`。
- **`is_lock_free()`**：查询该类型是否真的用无锁指令实现。大对象的 `atomic<T>` 可能退化为内部加锁。
- **`std::atomic<T>` 对自定义类型**：要求 T 是 trivially copyable；大对象通常不划算。

## 三、memory_order 详解（核心中的核心）

为什么需要内存序？因为编译器和 CPU 都会**重排**指令以提速。单线程下重排不影响结果，但多线程下，一个线程看到另一个线程写操作的**顺序**可能和源码不一致。`memory_order` 就是约束“一个原子操作周围的普通读写，能否被重排到它的另一侧”。

### 1. relaxed —— 只保证原子性，不保证顺序

```cpp
std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed); // 仅保证自增不丢失
```

`relaxed` 保证操作本身原子（不会丢更新），但**不与其它内存操作建立任何先后关系**。典型用途：**纯计数器**（如统计帧数），各线程只管累加、不依赖累加顺序与其它数据的可见性。

### 2. acquire / release —— 配对建立 happens-before（最常用）

这是无锁同步的主力。把它想成“一扇单向门”：

- **`release`（写侧）**：该 store 之前的所有读写，不能被重排到这个 store **之后**。相当于“把前面的工作打包，盖上发布章”。
- **`acquire`（读侧）**：该 load 之后的所有读写，不能被重排到这个 load **之前**。相当于“先验收，再用货”。

**配对规则**：当 `acquire` 的 load **读到了**对应 `release` 的 store 写入的值，就建立了 **happens-before**——release 之前的所有写入，对 acquire 之后的代码都可见。

```cpp
std::atomic<bool> ready{false};
int payload = 0;                       // 普通变量

void producer() {
    payload = 42;                                       // ① 普通写
    ready.store(true, std::memory_order_release);       // ② 发布：① 不会重排到 ② 之后
}
void consumer() {
    while (!ready.load(std::memory_order_acquire)) {}   // ③ 验收
    assert(payload == 42);                              // ④ 一旦 ③ 读到 true，必然看到 ①
}
```

> 这正是 `volatile` 做不到的事——`volatile` 没有 happens-before 语义（详见 [[13-语言基础关键字]]）。

### 3. acq_rel —— 读-改-写两头都要（如 CAS、fetch_add 充当锁）

对 `compare_exchange`、`fetch_add` 这种“既读又写”的操作，若它同时需要 acquire（看到别人发布的数据）和 release（发布自己的修改），用 `memory_order_acq_rel`。

### 4. seq_cst —— 全局单一顺序（默认值，最强最贵）

`seq_cst`（顺序一致）在 acquire/release 之上再加一条：**所有 `seq_cst` 操作存在一个全局一致的总顺序，所有线程看到的顺序相同**。它是所有原子操作的**默认内存序**，语义最直观，但在多核上可能插入更重的内存屏障（如 x86 的 `mfence`），开销最大。

**建议：拿不准就用默认 `seq_cst`，先保证正确，profiling 确认是热点后再下放到 acquire/release/relaxed。**

### 5. consume（了解即可）

`memory_order_consume` 本想做比 acquire 更轻的数据依赖序，但各编译器实现困难、实际都退化成 acquire，C++17 起标准建议不要使用。面试知道“它被废弃、用 acquire 代替”即可。

### 内存序强弱总览

| memory_order | 保证 | 典型场景 |
| :--- | :--- | :--- |
| `relaxed` | 仅原子性，无顺序 | 纯计数器、统计量 |
| `acquire` / `release` | 配对建立 happens-before | 标志位发布数据、自旋锁、无锁队列 |
| `acq_rel` | 读-改-写两侧都约束 | CAS、引用计数释放 |
| `seq_cst` | 全局单一总顺序（默认） | 拿不准时的安全默认 |

## 四、CAS 与无锁编程基石

CAS（Compare-And-Swap）是几乎所有无锁数据结构的核心原语：

```cpp
std::atomic<Node*> head{nullptr};

void push(Node* newNode) {
    Node* oldHead = head.load(std::memory_order_relaxed);
    do {
        newNode->next = oldHead;                 // 先假设链到当前头
    } while (!head.compare_exchange_weak(        // 失败则 oldHead 被刷新为最新值，重试
                 oldHead, newNode,
                 std::memory_order_release,      // 成功：发布 newNode
                 std::memory_order_relaxed));    // 失败：仅重读
}
```

- **`compare_exchange_weak` vs `strong`**：`weak` 允许“伪失败”（实际相等却返回 false），但在循环里更高效，常用于 CAS 重试循环；`strong` 不会伪失败，用于不便重试的单次判断。
- **ABA 问题**：值从 A 变成 B 又变回 A，CAS 误以为“没变过”。解决方案有版本号 tag、`atomic<shared_ptr>`、hazard pointer 等，详见 [[03-无锁队列]]。

## 五、音视频场景

- **停止/暂停标志**：`std::atomic<bool> stopRequested`，解码/渲染线程用 `acquire` 轮询，控制线程用 `release` 置位——零锁、低延迟。
- **统计量**：已解码帧数、丢帧数用 `atomic<uint64_t>` + `relaxed` 累加，UI 线程读取展示。
- **SPSC 无锁队列的读写指针**：用 acquire/release 配对在解码线程与渲染线程间传帧，是 [[03-无锁队列]] 的核心。
- **双缓冲切换**：用 atomic 指针 `exchange`/CAS 切换前后台缓冲，避免渲染时加锁。

## 六、常见坑

| 坑 | 后果 | 正确做法 |
| :--- | :--- | :--- |
| 用 atomic 维护多变量一致性 | 中间态被别的线程看到 | 复合不变量用 mutex |
| 到处用 `relaxed` 图快 | 数据竞争、可见性丢失 | 默认 `seq_cst`，确认安全再下放 |
| 以为 atomic 能让指向的对象线程安全 | `shared_ptr` 指向的 vector 仍需加锁 | 对象本身另行同步 |
| 用 `volatile` 代替 atomic | 无原子性、无 happens-before | 用 `std::atomic` + 内存序（见 [[13-语言基础关键字]]） |
| CAS 忽略 ABA | 链表/栈逻辑被破坏 | 版本号 tag / hazard pointer |

> 面试一句话：“atomic 解决单变量的原子性，memory_order 解决可见性和有序性。最常用的是 release-acquire 配对：写侧 release 发布、读侧 acquire 验收，一旦读到就建立 happens-before。拿不准内存序就用默认的 seq_cst，先正确再谈优化。”
