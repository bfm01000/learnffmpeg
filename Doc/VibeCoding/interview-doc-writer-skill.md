# Skill: 面试技术文档生成器（interview-doc-writer）

## 0. 用户岗位画像（写文档时必须代入）

> ⚠️ 这是本 skill 最重要的"知识库"。所有"🗣️ 面试标准回答"和"💡 实战案例补充"都必须以这个画像为前提进行个性化定制，不能写成通用的网文。

**目标岗位**：FFmpeg 音视频开发工程师（Android 优先，移动端/嵌入式音视频 SDK 方向）

**核心能力标签**：
- 音视频 **Pipeline 流程优化**（采集→编码→封装→推流 / 拉流→解码→渲染 全链路）
- **延时优化**（端到端延时降低、首帧延时、解码渲染调度）
- **异构硬件调度**（CPU / GPU / VPU / NPU 并行流水线）
- **内存与带宽优化**（零拷贝、Surface 直通、AHardwareBuffer、Tiled vs Linear 布局）
- **弱网与 QoS 策略**（ABR 动态码率、AJB 自适应抖动缓冲、Smart Drop GOP）
- **FFmpeg 底层**（AVFrame / AVPacket 生命周期、Seek 优化、stss Box、index_entries、Codec 封装）
- **JNI / NDK 跨语言桥接**（MediaCodec、Surface、DirectByteBuffer、Hardware Sync Fence）

**已沉淀的项目实战案例库**（生成实战补充时优先匹配下列场景）：

### 项目 A：Android 4K 全景直播全链路性能优化与重构（`av_interview/项目/核心-直播性能优化.md`）
- **痛点**：4K RTMP 直播 22fps 起步，10 分钟后掉到 5fps，手机严重发热
- **关键优化点**：
  - **GPU→VPU 物理级零拷贝**：用 `AHardwareBuffer`（`USAGE_GPU_FRAMEBUFFER | USAGE_VIDEO_ENCODE`，刻意不加 `CPU_READ_OFTEN` 以保留 AFBC/UBWC 硬件无损压缩）+ `Surface` 直通，干掉 `glReadPixels`（30ms）+ `libyuv::ABGRToI420`
  - **Tiled vs Linear 内存布局**：解释为什么 GPU 显存是块状/Z 字形 Morton order，CPU 要的是线性数组，`glReadPixels` 强制 De-tiling 才是 30ms 真凶
  - **Hardware Sync Fence 流水线并行**：`glFinish`（阻塞）→ `glFlush`（非阻塞）+ Fence FD，把"CPU 死等"换成"GPU 渲染与 VPU 编码异步等待"
  - **GPU Blit 折中**：`AV_PIX_FMT_AHARDWAREBUFFER` 自定义格式 + `SurfaceWriter` 用 `GL_TEXTURE_EXTERNAL_OES` 重画到编码器 Surface（多 1-2ms 但避开 30ms CPU 拷贝）
  - **异步发送队列**：`DispatchQueue2`（`std::condition_variable` + `std::mutex`）解耦编码与网络 I/O，队列容量 90 帧（约 3 秒）
  - **Lambda 值捕获保活**：`auto muxer = muxer_;` 强制 `shared_ptr` 引用计数 +1，防 muxer 析构后 Crash
  - **动态码率 ABR**：高水位 60 帧降 20%、低水位 15 帧升 20%、底线 1/4 目标码率，通过 JNI 调 Java 的 `MediaCodec.setParameters(Bundle)` 而非 NDK 的 `AMediaCodec_setParameters`（兼容性 + API 19 vs API 26）
  - **Smart Drop GOP 兜底**：弱网极端时整 GOP 丢弃，避免 P/B 帧缺失花屏
  - **参数化路由**：`enableLiveZeroCopy` / `enableAsyncSendAndABR` 双独立开关，旧业务 100% 向后兼容

### 项目 B：自动剪辑性能优化（`av_interview/项目/核心-自动剪辑性能优化.md`）
- **痛点**：自动剪辑 3.0 算法送帧频率提升 3 倍（600ms→200ms），整体耗时无法满足产品要求
- **核心流程**：选视频 → 抽帧 → 算法分析（出高光片段） → 拼接 + 转场 + 滤镜 + BGM → 输出成片
- **关键优化点**：
  - **Smart Seek**：识别"下一目标在当前帧后且同一 GOP 内"，跳过 `av_seek_frame`，直接顺解+丢帧；避免每次 Seek 都从关键帧重解
  - **MP4 stss Box 解析**：通过 `AVStream->index_entries` 数组（FFmpeg 解析 moov atom 时已填好）O(1) 拿全部关键帧索引，无需 ffprobe 也无需手撸 MP4 解析器
  - **异构硬件并行流水线**：抽帧(VPU) ‖ 渲染(GPU) ‖ 推理(NPU/CPU)，生产者-消费者队列解耦，总耗时 ≈ max(各阶段)，抽帧/渲染时间被隐藏
  - **帧 ID 单向映射**：把帧 ID 作为绝对索引贯穿始终，避免 2.0 时代浮点时间戳双向转换的精度误差（999ms vs 1001ms 抽不同帧）
  - **GPU 并行的辩护**：即使推理也用 GPU，Compute Shader / Draw Call 在不同队列底层仍可并发；CPU 准备指令的时间也能 overlap

### 项目 C：车载相机预览低时延优化（`av_interview/项目/核心-预览延时优化.md`）
- **痛点**：X5 相机 1.5s 延时 vs X3 的 0.5s（同样 30fps 但 High Profile vs Main Profile）
- **场景**：相机 WiFi 传 H.264 流到手机 → 解码 → 渲染到屏幕预览
- **关键优化点**：
  - **首帧延时固化缺陷**：旧逻辑用首帧 PTS 与本地时间差当永久基准，首帧网络抖动 1s 被继承到所有后续帧
  - **AJB（自适应抖动缓冲）"快升慢降"非对称 EMA**：
    - 延时变大（拥塞）→ α=0.8 快速升高 `targetBuffer`（防卡顿）
    - 延时变小（恢复）→ α=0.1~0.2 缓慢回收（防呼吸效应）
    - Deadband 防抖：误差 < 2ms 不更新
    - clamp(10ms, 120ms) 兜底
  - **时间轴映射**：建立 `(basePts, baseMono)` 锚点，把媒体时间投影到 `steady_clock` 单调时钟坐标系；**严禁直接 PTS - nowMs**（时钟源不同 + 晶振漂移）
  - **时间戳透传**：解码前打 `network_receive_time` 戳，跟着 packet 透传到 YUV 帧，剥离解码器 I 帧/P 帧耗时波动对抖动计算的污染
  - **背压追赶**：`pendingLeft > 0` 时 `waitTime` 强压到 ≤2ms，追上积压
  - **适度丢帧**：严重迟到 + 队列积压 → 丢弃过期帧，换"可恢复实时性"
  - **Resync**：`waitTime > 250ms` 触发时间轴基线重建
  - **AJB 放在解码后 YUV 而非解码前 H264 的 Trade-off**：直击历史债务、硬件黑盒不可控、解码后丢帧不破坏依赖
  - **EMA vs SMA**：EMA 空间 O(1) + 一个 if-else 就实现非对称滤波，SMA 要动态改队列长度极易出 Bug

**用户写作偏好观察**：
- 喜欢用 STAR 法则（背景痛点 / 任务 / 行动 / 结果），每一段都带量化数字
- 喜欢在回答中体现"控制变量法"排查思路（如本地录制 vs 推流对比、关闭 wait 逻辑验证）
- 喜欢"先讲假设再讲证伪再讲根因"的递进结构
- 喜欢用引用块 `>` 包裹可背诵话术，台词感强
- 喜欢在结尾抛"为什么不用 X 方案"反向论证（如为什么不用 PBO、为什么不用 NDK MediaCodec）
- 喜欢追问深挖型的"避坑指南"和"灵魂拷问"小节

- 指向已有 Doc/ 下分类的话题（C++ / JNI / OC / 设计模式 / 音视频 / FFmpeg 等）
- 指向 `av_interview/项目/` 里出现过的关键词（零拷贝 / AJB / Smart Seek / 异构并行 / ABR / Sync Fence / stss）

⚠️ 不要在以下场景错误触发：纯 bug 修复、代码实现请求、API 用法查询、环境配置类问题、跑 demo 类请求。

## 二、动作流程（按顺序执行）

### Step 1：澄清边界（仅当必要）

如果用户的请求**模糊到无法确定核心范围**，**最多**用 `AskUserQuestion` 问一次，澄清以下任一点（不要全问）：

- 文档侧重（速记应付明天面试 / 深入吃透原理 / 两者兼顾，默认两者兼顾）
- 是否关联用户的具体项目（若关联，是 4K 直播 / 自动剪辑 / 车载预览 中的哪个）
- 文档目标长度（速读 ~3000 字 / 详读 ~8000 字 / 详读 ~15000 字 ）

如果用户给的话题已经足够具体（比如「讲一下 AHardwareBuffer」、「FFmpeg Seek 优化」），**直接跳过澄清，开写**。岗位方向不需要澄清——默认就是 FFmpeg 音视频 Pipeline 方向，所有实战案例从上面项目库取材。

### Step 2：确定文件路径与命名

按下面的对应关系选目录：

| 话题分类 | 目标目录 |
|---|---|
| C++ 语言特性、内存、模板、STL、多线程 | `Doc/cpp/` |
| Objective-C、Runtime、ARC、Block | `Doc/OC/` |
| JNI、NDK、Java↔Native 互操作、TLS | `Doc/JNI/` |
| 设计模式、SOLID、架构 | `Doc/设计模式/` |

| 音视频通用（采集 / 编解码 / 推流 / Pipeline / 调度 / 编码标准 H.264/H.265） | `Doc/音视频/`（不存在则新建） |
| 零拷贝、AHardwareBuffer、Surface、DMA-BUF、Sync Fence | `Doc/零拷贝/` |
| 自动剪辑、Smart Seek、stss、index_entries | `Doc/自动剪辑/` |

| 不属于现有任何分类 | 新建合适的中文目录，告知用户 |

文件命名规则（中文，体现"面试导向"）：
- `XX面试速记与原理详解.md`（默认）
- `XX高频考点与标准回答.md`（偏速记型话题）
- `XX原理与面试要点.md`（偏底层原理型话题）

写入前先用 `ls` 确认目录存在，并检查是否已有同名/近似主题文档 — 若存在，先 `Read` 旧文档，**优先在原文上增补/重构**，而不是另写一份。**特别注意**：`av_interview/项目/` 下已有的 STAR 法则文档不能覆盖，那是用户的原始项目复盘，是 skill 的"输入"而不是"输出"。

### Step 3：按模板产出文档

文档**必须**采用下面的两段式结构。结构是硬约束，内部话术风格强制对齐：
- `Doc/JNI/JNI面试高频考点与标准回答大全.md` 的口语化标准回答风格

### Step 4：写完后简短汇报

输出一句话即可：文档路径 + 包含的考点数量 + 关联了哪些用户项目。不要复述文档内容。

例：「已生成 `Doc/零拷贝/AHardwareBuffer面试速记与原理详解.md`，包含 7 个高频考点 + 6 节原理深讲，实战补充关联了 [[核心-直播性能优化]] 的 GPU→VPU 零拷贝重构案例。」

## 四、写作风格硬约束

### 必须遵守

1. **中文为主**：所有解释、回答用中文，代码和专有名词保留英文（如 `AHardwareBuffer`、`AVFrame`、`Sync Fence`）。
2. **口语化但不口水**：「我们的做法是…」「这里有个坑…」可以；「然后呢然后呢」「就是说嘛」不行。
3. **回答必须可背诵**：`🗣️ 面试标准回答` 部分要像写台词，3-8 句，节奏自然，能一口气念完。
4. **底层原理必须给"为什么"**：不要只说"是什么"，要说"为什么这样设计 / 不这样会怎样"。
5. **代码示例必须能跑**：伪代码标注 `// 伪代码`；真代码要能编译，变量名要有意义。
6. **实战案例锁定 FFmpeg / Android 音视频**：用推流、解码、Seek、AJB、JNI 回调、零拷贝场景，**绝对不要**举 Web 后端 CRUD、电商秒杀、社交 IM 这种不相关例子。
7. **数字优于形容词**：「性能好」改成「单次约 50ns」；「内存占用低」改成「比 X 节省 40% 堆分配」；用户项目里的真实数字（40ms→10ms、1.5s→0.5s、22fps→30fps、600MB/s 总线带宽）能用就用。
8. **控制变量法 + 假设证伪叙述**：复杂排查类考点优先用"先提假设 → 实验证伪 → 锁定根因"的递进结构，对齐用户项目文档风格。
9. **追问应对兜底**：每个考点末尾给 1-2 个面试官常追问的方向，避免回答完就冷场。

### 禁止事项

1. ❌ **禁止 emoji 滥用**：模板中已有的 📌📚🎯🔥🗣️💡⚠️❌✅⛳🚧🔗👨‍💻 是结构标记，可以用；正文段落里**不要**额外加 emoji。
2. ❌ **禁止凑字数**：每个考点的 `🗣️ 面试标准回答` 不超过 8 行。讲透即可。
3. ❌ **禁止"假深度"**：不要为了显得深入塞无关知识点。如果某个考点和主题关系不大，宁可不写。
4. ❌ **禁止照搬 cppreference / 官方文档**：要消化成"面试官能听懂、面试者能背下来"的形式。
5. ❌ **禁止编造**：不确定的 API 行为、性能数字、版本特性，明确标注"需验证"或不写。
6. ❌ **禁止虚构项目**：实战案例只能从用户三大项目库（4K 直播 / 自动剪辑 / 车载预览）取材。如果话题确实和这三个项目无关，就用"在我之前的 Android 音视频开发中"这种泛化表述，**不要瞎编不存在的项目**。
7. ❌ **禁止把 `av_interview/项目/` 当输出目录**：那是用户原始素材，skill 只读不写。

## 五、增量更新场景

如果目标文件已存在：

1. 先 `Read` 现有文档，识别其结构（是否已是两段式）。
2. **若已是两段式**：在对应段落内增补考点 / 原理小节，保持编号连续。
3. **若是旧风格（如单一长文）**：和用户确认是否重构为两段式。除非用户明确说"重写"，否则**保守增补**，不要删旧内容。
4. 重构时保留旧文档的实战案例和项目话术 — 那是用户的真实经验，最有价值。
5. **追加项目实战补充**：如果旧文档没有引用用户的三大项目案例而新话题正好能挂上，主动追加 `💡 实战案例补充` 段落。
