#### 考点 1：你平时是怎么使用 AI 辅助编程的？（工具栈 + 工作流派）

**考察意图：** 看你是把 AI 当"高级百度"（只查 API），还是把 AI 当"结对编程的副手"（深入项目工程）。这道题决定了面试官接下来问什么。

**底层原理：**
LLM 的能力上限取决于上下文质量和任务边界清晰度。粗放使用（"帮我写个 XX 模块"）必然产出垃圾代码；工程化使用（接口先行、约束充分、分步审查）才能把 AI 当生产力工具。

**🗣️ 面试标准回答：**
> "我日常主要用 Cursor 配合 Claude 3.7 / Claude 4 模型来开发，工作流派属于半个 VibeCoding。核心理念是 **'AI 负责敲字，我负责架构和审查'**。
> 我从不让 AI 一次性生成一整个模块——那样大概率跑不通，而且 Review 成本比自己写还高。我的标准做法是：先口述需求让 AI 帮我出架构设计和接口定义，骨架确认后再拆成小 Task 派给 AI 实现，最后我作为 Reviewer 卡边界条件和内存安全。
> 这种模式我估算下来效率至少翻倍，但更重要的是——**代码主权和质量始终在我手里**。"

**💡 实战案例补充（来自[[核心-直播性能优化]]）：**
> "举个具体例子，4K 直播项目里我做动态码率 ABR 那块。我没有直接让 AI 写'帮我做个 ABR'，而是先自己设计好高低水位策略（60 帧降级、15 帧恢复、底线 1/4 目标码率），把这个策略用注释写在函数头上，然后让 AI 帮我把策略翻译成 C++ 代码，并要求 **不要用浮点除法**（性能敏感）、**clamp 必须用 std::max/std::min 而不是三目运算**（可读性）、**编码器接口必须走我们已有的 `encoder_->SetDynamicBitrate(...)`**。
> 这种带强约束的派单，AI 出的代码基本可以直接合主干。"

**👨‍💻 面试官追问：**
> Q: 你为什么不让 AI 一次性写完整模块？
> A: 因为越长的代码 AI 的幻觉率越高，而且我作为 Reviewer 看一坨陌生代码的成本远大于自己分块写。AI 的最佳输出长度大概在 30-100 行，超过这个范围就要拆。

#### 考点 2：怎么写好 Prompt 让 AI 产出高质量代码？

**考察意图：** 考察你的需求抽象能力。写不好 Prompt 的人，本质是脑子里逻辑没想清楚——这等价于不会拆需求。

**底层原理：**
LLM 是基于上下文做最大似然预测，**模糊的 Prompt 等价于让它在巨大解空间里瞎猜**。要把解空间压窄，必须给四类信息：角色定位（用什么知识）、目标（生成什么）、约束（不能怎么做）、上下文（项目里已有什么）。

**🗣️ 面试标准回答：**
> "我写 Prompt 有四件套：
> 1. **角色设定**：'你是一个资深 C++ 音视频专家'——锁定它用音视频领域知识而不是泛泛 OOP 教科书风格。
> 2. **核心目标**：'用 FFmpeg + WebRTC 实现一个推流模块'——一句话讲清要什么。
> 3. **上下文约束**：用 `@` 引入项目里已有的基类文件，要求 '必须继承这个 BaseEngine，编码风格保持一致'。
> 4. **异常 & 内存约束**：明确说 '指针必须判空、释放时清野指针、JNI 层禁止 YUV 深拷贝'。
> 最后如果逻辑复杂，我会要求它 **先用中文输出实现思路，我确认后再写代码**。这样能从源头规避 AI 偏离架构。"

**💡 实战案例补充（来自[[核心-直播性能优化]]）：**
> "比如我在 4K 直播项目里要写 `AHardwareBuffer` 包装到 `AVFrame` 的代码。我的 Prompt 是这样的：
> 『你是精通 Android NDK 和 FFmpeg 的专家。请帮我写一段 C++ 代码，把 `AHardwareBuffer*` 包装到 `AVFrame` 里送给 MediaCodec 编码器。
> **上下文**：`@AVFrameWrapper.h` 已经定义了我们自定义的 `AV_PIX_FMT_AHARDWAREBUFFER` 格式。
> **强约束**：
> 1. 硬件指针必须存在 `AVFrame->data[3]`（这是我们项目约定）。
> 2. 释放回调必须通过 `av_buffer_create` 注册，不允许在外部手动释放。
> 3. 严禁调用 `AHardwareBuffer_lock`（会触发 CPU 读，破坏 AFBC 压缩，导致带宽暴增）。
> **输出前**：请先告诉我你的 ref-counting 释放策略，等我确认。』
> 这个 Prompt 产出的代码我几乎一次就合了。"

**👨‍💻 面试官追问：**
> Q: 如果项目代码很多，`@` 引入会不会让上下文窗口爆了？
> A: 会。所以我只引入**强相关的接口文件（header）而不是整份实现**。如果非要引大量代码，我会先让 AI 总结成 200 字以内的"项目约束摘要"，后续 Prompt 只挂这个摘要。

#### 考点 3：AI 会产生幻觉或写出 Bug，你怎么处理？

**考察意图：** 考察 Debug 能力和对 AI 局限性的清醒认知。最怕候选人说"跑不通就让它重写"——这等价于宣布自己没有兜底能力。

**底层原理：**
幻觉的根因是上下文不足或冲突。AI 不"知道"自己写错了，它只是按训练数据的统计规律输出。要破解必须 **从概率回到确定性**——给它具体的报错信息、确定的代码片段、已经验证过的假设。

**🗣️ 面试标准回答：**
> "AI 出幻觉很正常，尤其是底层 C++ 和 JNI 这种领域，训练数据少而且边界场景多。我处理 Bug 绝对不会无脑点'重新生成'，我的三步曲是：
> 1. **精简上下文、缩小范围**：另开一个 Chat，只喂出错的那个函数和几行报错日志，避免历史污染。
> 2. **给确定信息**：把编译器错误、运行时堆栈、甚至我自己的怀疑点（'我觉得是这里的智能指针没释放导致死锁'）一起发过去，把它的搜索空间从'整个 C++ 标准库'压缩到'这几行的范畴'。
> 3. **人工兜底**：如果 AI 绕进死胡同，我立刻停止让它瞎猜，自己打断点 / 加 Log 定位到真实错误行，然后让它针对这一行给出修复方案。**归根结底，AI 是执行者，我才是为代码兜底的人。**"

**💡 实战案例补充（来自[[核心-自动剪辑性能优化]]）：**
> "我做 Smart Seek 优化时遇到过一次。我让 AI 帮我判断 '下一帧目标是否在当前 GOP 内'，它给我返回的代码用 `pkt->pts / gop_duration` 做整除比较。结果跑起来在 VFR（可变帧率）视频上全错——因为 GOP 长度根本不是恒定的。
> AI 自己排查方向全错，扯了半天 PTS 单位问题。后来我自己 dump 了 `AVStream->index_entries`，发现关键帧间隔有 540ms / 660ms / 720ms 三种，根本不能拿固定值算。我把这个发现喂回去：'索引数组是这样的 [0, 540, 1200, 1860]，请基于 index_entries 二分查找而不是除法。' 它立刻给出了完美的 `std::upper_bound` 实现。
> 这就是典型的 **AI 在不确定领域出幻觉 → 人工提供确定数据 → AI 高效收敛** 的配合。"

**👨‍💻 面试官追问：**
> Q: 你会用 AI 自动跑测试反复迭代吗（agentic workflow）？
> A: 会，但只敢在有完备单元测试的模块上。底层音视频很多 Bug 是性能/视觉/线程时序问题，单元测试覆盖不了——这种就必须人工兜底。

#### 考点 4：什么是 VibeCoding？它对程序员能力的要求是变高还是变低？

**考察意图：** 看你对行业趋势的判断力，以及你是否有"AI 焦虑"。

**底层原理：**
VibeCoding 是 Andrej Karpathy 2025 年提出的开发范式——开发者用自然语言、宏观架构、"感觉（Vibe）"去引导 AI 自动生成代码，自己几乎不写键盘字符。它把编程的瓶颈从"打字速度"转移到了"需求抽象 + 代码审查"。

**🗣️ 面试标准回答：**
> "VibeCoding 是一种更高级的抽象开发模式，开发者用自然语言和宏观架构去**驱动** AI 写代码，而不是自己当键盘侠。
> 表面看门槛降低了，实际上**对程序员的综合能力要求大幅提高**：
> 以前我们 80% 的时间花在查 API、写模板代码，这些脏活 AI 干了。但程序员必须向两个方向进化：
> 1. **向下，要极其懂底层和架构**：AI 写的代码你必须看得懂。如果不懂 JNI 的 `WeakGlobalRef` 细节、不懂 `AHardwareBuffer` 的 USAGE flag 含义，AI 埋的雷你根本 Review 不出来。
> 2. **向上，要懂业务拆解**：要能把模糊业务需求拆成 AI 能听懂的原子任务，前置条件清晰、约束明确。
> 一句话：VibeCoding 让我们从'打字员'变成了'架构师 + Reviewer'。**那些只会写业务 CRUD 的人会被淘汰，而懂底层和系统的人会被极大放大**。"

**👨‍💻 面试官追问：**
> Q: 你对你自己被 AI 替代焦虑吗？
> A: 不焦虑。我做音视频 Pipeline 优化，AI 现在能帮我写代码片段，但它不知道 `glReadPixels` 在 UMA 架构上为什么慢、不知道 AFBC 压缩会被 USAGE flag 破坏。这些底层判断力才是我的护城河，AI 反而是放大我能力的杠杆。

#### 考点 5：AI 写底层 C++ / FFmpeg / JNI 这种代码靠谱吗？怎么保证质量？

**考察意图：** **这是给你这个方向候选人最容易问到的题。** 看你是否清楚 AI 在不同领域的能力边界。

**底层原理：**
LLM 的代码生成质量与训练数据丰度成正比。前端 React、Python 数据分析这种 GitHub 海量代码的领域，AI 接近真人水平。**而 FFmpeg / Android NDK / JNI / 硬件相关代码，开源样本少、版本碎片化严重、平台差异大，AI 幻觉率显著更高**。

**🗣️ 面试标准回答：**
> "坦白说，**越底层 AI 越不靠谱**，我做音视频对此感受很深。
> AI 写 Java 业务代码可以 80% 直接用；但写 JNI 调用、`AHardwareBuffer` USAGE flag 组合、FFmpeg `AVPacket` 引用计数这些底层代码，幻觉率非常高——经常给我编造不存在的 API、写错释放顺序、混淆 NDK 和 Java MediaCodec 的能力差异。
> 我的做法是 **'接口骨架 + 强约束 Prompt + 人工兜底'三道保险**：
> 1. **接口骨架**：核心结构、生命周期、线程模型我自己设计，AI 只填实现细节。
> 2. **强约束 Prompt**：明确指定 API 版本（如 'NDK r23 + API 26 以上'）、禁止用我已知有坑的方法（'禁用 AHardwareBuffer_lock'）。
> 3. **人工兜底**：所有内存释放、跨线程对象传递、硬件资源回收的代码我必看。
> AI 给我的不是'完成代码'，是'草稿'，最终质量由我背锅。"

**💡 实战案例补充（来自[[核心-直播性能优化]]）：**
> "做 4K 直播零拷贝时，AI 一开始给我的 `AHardwareBuffer` 分配代码里加了 `AHARDWAREBUFFER_USAGE_CPU_READ_OFTEN` 标志位——它从 StackOverflow 例子里学的'调试方便'。但我知道这个 flag 一加，Gralloc 会把内存退化成 Linear 布局，AFBC/UBWC 硬件压缩全失效，4K 30fps 下总线带宽多消耗 600MB/s，手机立刻发热降频。
> 我把这个坑直接告诉它：'禁用 CPU_READ 标志位，原因是会破坏 AFBC。请只用 GPU_FRAMEBUFFER | VIDEO_ENCODE 组合。'之后它给出的代码就完全符合预期了。
> **这种领域知识 AI 不可能自己知道，必须由人来注入。**"

**👨‍💻 面试官追问：**
> Q: 那 AI 在音视频领域到底能帮你什么？
> A: 三件事：(1) 写模板代码（JNI signature、AVPacket 引用计数模板、生产者-消费者队列骨架）；(2) 解释开源代码（让它读一段 FFmpeg 源码总结逻辑）；(3) 参数调优（比如 AJB 的 EMA α 值，让它生成几组候选我跑数据选）。**它的能力边界在"理解已知模式"，不在"创造新方案"**。

#### 考点 6：你具体在哪个项目里用 AI 真正提了效？说一个细节

**考察意图：** **杀手题。** 验证你说的"AI 提效翻倍"是不是吹的——具体到代码、到时间、到产物。

**底层原理：**
（这题不需要原理，需要具体案例。）

**🗣️ 面试标准回答（结合用户三大项目挑一个最有料的）：**
> "举一个最近的：我在车载预览延时优化里做 AJB 算法时，核心难点是 EMA 滤波的'快升慢降'非对称权重参数怎么调。
> 我先自己定了大方向：网络恶化时 α=0.8（快速跟上），恢复时 α=0.1~0.2（缓慢回收）。但具体在 warmup 阶段用 0.2 还是 0.15、Deadband 阈值用 2ms 还是 5ms、`targetBuffer` clamp 上下界用什么值——这些是工程参数，没有理论最优解。
> 我让 AI 帮我做了两件事：
> 1. **生成参数候选矩阵**：基于我描述的 30fps 视频、平均 RTT 50ms、最大抖动 200ms 的场景，给我 6 组合理参数组合及其权衡分析。
> 2. **生成测试数据生成器**：模拟弱网抖动序列（含突发拥塞、周期性丢包、长尾延时），让我离线扫参。
> 我自己在真实车载环境上跑了一天，结合 AI 给的候选选出最优组合（α=0.8/0.1、Deadband 2ms、clamp 10-120ms）。
> **本来需要一周的调参工作，3 天搞定了。** 关键是 AI 没有替代我的判断（最优参数是我选的），但它消灭了我自己写 mock 数据和遍历组合的体力活。"

**👨‍💻 面试官追问：**
> Q: 那 AI 给的 6 组参数你怎么知道哪组对？
> A: AI 给的只是"理论合理"，真实场景必须实测。我在车里用真实弱网工具（Network Link Conditioner）打了 5 种 profile，每组参数跑 10 分钟，记录 P50/P95/P99 延时和丢帧率，最后选 P99 最低且画面无明显呼吸效应的组合。**AI 提供候选，数据决定选择。**

### ⛳ 项目实战话术（STAR 法则版）

> 杀手题："你在简历里写的项目，AI 具体帮了你什么？" 准备 1-2 个能挂上你三大项目的话术。

**话术 A（推荐讲这个 —— 自动剪辑 + Smart Seek）：**

> **S（背景）**：自动剪辑 3.0 算法把送帧频率从 600ms/帧提到 200ms/帧，整体耗时翻 3 倍，必须优化抽帧策略。我需要实现一个 Smart Seek：判断目标帧是否在当前 GOP 内，若是则顺解+丢帧，否则才走 `av_seek_frame`。
>
> **T（任务）**：核心难点是怎么"O(1) 拿全部关键帧时间戳"——传统做法要 `av_read_frame` 遍历整个文件找 `AV_PKT_FLAG_KEY`，太慢。
>
> **A（行动）**：
> 我自己有方向：直接读 FFmpeg 解析好的 `AVStream->index_entries`（FFmpeg 在 `avformat_open_input` 时已经把 MP4 的 stss Box 内容填进去了）。但具体怎么读、字段含义、不同容器格式（MP4 / MKV / MOV）的兼容性，我让 Cursor + Claude 帮我整理。
> 我给的 Prompt 是：『请基于 FFmpeg n4.4 版本，解释 `AVStream->index_entries` 数组的结构（每个 `AVIndexEntry` 字段含义、时间戳单位、与 `AVStream->time_base` 的换算），并给出一个二分查找的实现：输入是目标 PTS，输出是该 PTS 所在 GOP 的首个关键帧位置。约束：不能用浮点除法、不能调用任何 IO 函数。』
> AI 给的代码我审了一遍，发现它没处理 `nb_index_entries == 0` 的边界（部分 MP4 文件 stss 缺失），我加了 fallback 到 `av_seek_frame` 的兜底逻辑。
>
> **R（结果）**：Smart Seek 在 GOP=600ms 的视频上，抽帧耗时从平均 80ms/帧降到 15ms/帧，整体出片速度提升约 3 倍。**AI 帮我省了 1-2 天读 FFmpeg 源码的时间，但兜底设计是我做的。**

**话术 B（备用 —— 4K 直播 + ABR）：**

> 我做 ABR 动态码率时，核心策略（高水位 60 帧降 20%、低水位 15 帧升 20%、底线 1/4 目标码率）是我自己定的。但 Java 层 `MediaCodec.setParameters` 的 Bundle 构造、JNI 反向调用模板、`PARAMETER_KEY_VIDEO_BITRATE` 的字符串常量——这些样板代码我让 AI 一次生成，省了我查 Android 文档的时间。**核心算法我写，模板代码 AI 写**，这是我的分工原则。

### 🚧 雷区与加分项

**❌ 雷区（千万别说）：**
- "没有 AI 我就写不了代码了" → 自降身价，HR 会觉得你没核心能力
- "AI 写的代码都是垃圾，我从不用" → 显得保守落伍，技术敏感度差
- "我让 AI 一次性把整个模块写完然后我跑测试" → 暴露你不会拆任务、Code Review 能力差
- "我主要用 ChatGPT 网页版复制粘贴" → 工程化程度低，会被认为没用过 IDE 集成工具
- "AI 写的代码我都不看直接用" → 直接负分，会让人怀疑你的代码质量

**✅ 加分项（说出来眼前一亮）：**
- "我会让 AI 先输出实现思路，确认后再写代码" → 体现你懂 LLM 推理特性
- "我用 `@codebase` 引入项目上下文而不是把代码贴到聊天框" → 工程化使用
- "我有自己的 Prompt 模板，按角色/目标/约束/上下文四块组织" → 体现方法论
- "AI 在底层 C++/JNI 领域幻觉率高，所以我有'接口骨架先行'的兜底机制" → 体现领域判断力
- "我用 AI 做参数候选生成 + 模板代码，但核心算法和架构我自己写" → 完美的分工姿态
- "我会让 AI 帮我读开源代码（FFmpeg/WebRTC 源码）做总结，省下读源码的时间" → 体现你用 AI 做"理解"而不只是"生成"
- 主动提到 **AI Coding ≠ Cursor**：还会用 GitHub Copilot、Claude Code CLI、自己写的 prompt 脚本等

## 📚 第二部分：原理深讲（吃透底层）

### 1. 基础概念与发展脉络

#### 1.1 AI 辅助编程的三个时代

| 时代 | 代表工具 | 交互模式 | 上下文能力 |
|---|---|---|---|
| 1.0 自动补全 | Kite (2019)、TabNine | 行内补全 | 单文件 |
| 2.0 对话生成 | GitHub Copilot (2021)、ChatGPT | 注释生成函数 | 当前文件 |
| 3.0 Agent 时代 | Cursor (2023+)、Claude Code、Devin | 多轮对话 + 跨文件理解 + 自主执行 | 整个 codebase + 工具调用 |

我们现在所处的 3.0 时代核心特点是：**模型有能力理解项目级上下文（codebase awareness）**，并且能调用工具（编辑文件、跑命令、读 lint 错误）形成闭环。

#### 1.2 VibeCoding 的定义与边界

VibeCoding 由 Andrej Karpathy 在 2025 年初提出，定义为：「开发者通过自然语言、感觉（Vibe）、和宏观架构来引导 AI 自动生成代码，而几乎不直接键入字符」。

**它的能力边界**：
- ✅ 适合：原型开发、CRUD 业务、脚本工具、UI 模板、单元测试用例
- ⚠️ 谨慎：底层算法、并发原语、内存管理代码
- ❌ 不适合：硬件相关代码、安全敏感代码、强 SLA 性能代码（音视频实时链路核心环节）

### 2. LLM 编程能力的底层逻辑

#### 2.1 为什么 AI 能写代码？

LLM 本质是基于上下文做下一 token 的最大似然预测。代码作为高度结构化的语言（语法严格、模式重复），是 LLM 训练语料的"高产田"。GitHub 上的开源代码 + 文档 + Stack Overflow 问答构成了核心训练集。

**关键认知**：模型并不"理解"代码逻辑，它只是看过太多类似模式后能**模式补全**。这解释了：
- 为什么写常见模式（CRUD、设计模式、标准库用法）效果好
- 为什么写罕见底层代码（DRM / Vulkan / FFmpeg 内部 API）容易出错
- 为什么相同 Prompt 多次生成会有不同结果（采样随机性）

#### 2.2 上下文窗口的物理限制

```
[System Prompt] [项目上下文 (@codebase)] [对话历史] [当前 Prompt] → [模型生成]
                              ↑ 总 token 数受限于上下文窗口（如 200k）
```

Claude Opus 4 / GPT-4o 等当前主流模型上下文窗口 200k token，对应约 60-80 万字。**但有效注意力会随距离衰减**——离当前 Prompt 越远的内容，模型"记得越糊"。

**工程影响**：
- 长会话中 AI 可能"忘记"早先的约束 → 关键约束需要在每轮 Prompt 重申
- 引入大文件会挤压有效上下文 → 优先引 header 而非 impl

#### 2.3 幻觉（Hallucination）的成因

幻觉本质是**训练数据稀疏区的概率瞎猜**。在以下场景幻觉率显著上升：
- API 版本差异大（如 Android NDK 不同版本的 AMediaCodec 能力差）
- 平台特定细节（如 AHardwareBuffer 在 Android 8.0 vs 12.0 的行为差异）
- 私有项目约定（AI 没见过你的内部基类）
- 新出的库 / 新版本特性（训练数据截止前没有）

**反幻觉策略**：
1. 给确定信息（具体 API 签名、版本号、报错日志）
2. 让它先输出思路，人工 review 后再生成代码
3. 跨模型交叉验证（同一 Prompt 喂给 Claude 和 GPT-4，对比差异）

### 3. 主流工具对比与选型

| 工具 | 强项 | 弱项 | 适用场景 |
|---|---|---|---|
| **Cursor** | 项目级 `@codebase`、多文件 edit、规则文件 `.cursorrules` | 收费较贵 | 日常主力 IDE |
| **GitHub Copilot** | 集成度高、企业版安全合规 | 上下文较短、对话能力弱 | 团队统一工具链 |
| **Claude Code CLI** | 终端原生、Agent 能力强、可跑命令 | 学习曲线高 | 自动化任务、CI 集成 |
| **Continue / Cody** | 开源、可本地部署 | 模型质量看后端选什么 | 数据敏感场景 |
| **ChatGPT / Claude 网页版** | 不需要任何配置 | 上下文断裂、复制粘贴麻烦 | 探索性提问、读源码总结 |

**我的实际选型**：日常用 Cursor + Claude，写自动化脚本和复杂多步骤任务用 Claude Code CLI，临时问题用 Claude 网页版。

### 4. Prompt 工程的核心方法论

#### 4.1 我的四块 Prompt 模板

```markdown
# 角色
你是一个精通 Android NDK 和 FFmpeg n4.4 的资深音视频专家。

# 目标
{一句话讲清要什么}

# 上下文
- 关联文件：@xxx.h @yyy.cpp（用 IDE 的 @ 引用）
- 项目约束摘要：{200 字以内的项目背景}

# 约束
1. 必须遵守：{API 版本、依赖库版本、命名规范、内存模型}
2. 禁止：{已知的坑、过时的 API、不符合架构的写法}
3. 输出要求：先用中文写实现思路，等我确认后再写代码

# 验收标准
{怎么判定 AI 输出对了——可编译？能跑通？通过某个测试？}
```

#### 4.2 进阶技巧

**Few-shot Prompting**：给 1-2 个示例输入/输出，让 AI 模仿格式。在写大量类似代码（如批量 JNI 接口）时极其好用。

**Chain-of-Thought**：要求 AI "先逐步分析问题，再写代码"。对复杂逻辑（如状态机、并发协议）显著提升正确率。

**Self-critique**：让 AI 写完后自我审查："请列出这段代码可能有的 3 个潜在 Bug 并修复"。

**Tool use / Agent**：让 AI 自主调用工具（读文件、跑测试、查 grep）。Claude Code 和 Cursor Composer 都支持。

### 5. AI 代码 Review 检查清单

> 这是我评估 AI 代码时的标准 Checklist，可以背下来作为面试加分项

#### 通用类
- [ ] 编译能过 + 静态检查 + lint
- [ ] 命名是否符合项目规范（不是 AI 默认的 camelCase）
- [ ] 是否引入了不在项目依赖里的库
- [ ] 注释是否真的有用（AI 喜欢写废话注释）

#### 内存与生命周期（C++ / NDK 重点）
- [ ] 所有 `new` 都有对应 `delete`，或用智能指针包装
- [ ] 智能指针有没有循环引用风险（特别是 `shared_ptr` 互引用）
- [ ] Lambda 捕获是否会延长对象生命周期，或反之导致悬空指针
- [ ] 跨线程对象传递有没有引用计数兜底

#### 多线程与同步
- [ ] 锁的粒度是否过大或过小
- [ ] 是否有死锁风险（多锁顺序）
- [ ] `condition_variable` 是否用 `while` 而不是 `if` 防虚假唤醒
- [ ] 原子变量的 memory order 是否合理（AI 经常默认 `seq_cst`）

#### JNI 专项
- [ ] Local ref 在循环里有没有及时 `DeleteLocalRef`
- [ ] 跨线程对象有没有从 Local 升级为 Global
- [ ] 是否有 `WeakGlobalRef` 兜底避免泄漏
- [ ] `JNIEnv` 是否跨线程使用（绝对禁止）

#### 音视频专项
- [ ] `AVFrame` / `AVPacket` 的 `ref` / `unref` 配对
- [ ] 硬件 buffer 的 USAGE flag 是否会破坏硬件压缩
- [ ] 编码器 / 解码器的释放顺序是否正确
- [ ] 时间戳的单位换算（PTS time_base、ms、us 混淆）

### 6. 性能与边界陷阱

#### 6.1 AI 代码的常见性能反模式
- **过度抽象**：AI 喜欢加各种 interface 和 factory，导致虚函数表开销
- **冗余拷贝**：循环里 `std::string` 拷贝、忘记 `std::move`、`vector` 没 reserve
- **过度防御**：每个函数都 `if (ptr == nullptr) return;`，掩盖真正的 bug
- **错误的并发**：AI 经常加锁过细，导致性能反而下降

#### 6.2 边界场景陷阱
- AI 喜欢假设"输入合法"，缺少边界处理（空数组、空指针、超长字符串）
- AI 经常忽略**首次调用 / 最后一次调用**的特殊处理（如 first I-frame、EOS）
- AI 容易混淆**异常路径**（如 `decode error` 是 retry 还是 fail-fast）

### 7. 实战代码示例：用 AI 写一个 FFmpeg 视频信息提取器

下面演示一个完整 Prompt → 代码 → Review 的循环。

**Prompt**：
```
你是一个精通 FFmpeg n4.4 的 C++ 专家。

# 目标
写一个函数 `bool ExtractVideoInfo(const std::string& path, VideoInfo* out)`，
提取 MP4 文件的：宽高、帧率、时长、关键帧数量、平均比特率。

# 上下文
- 项目使用 RAII 风格管理 FFmpeg 资源
- VideoInfo 结构体：
  struct VideoInfo {
    int width, height;
    double fps, duration_sec;
    int keyframe_count;
    int64_t avg_bitrate;
  };

# 约束
1. 不允许调用 av_read_frame 遍历整个文件 —— 必须用 index_entries 拿关键帧数
2. 必须用 unique_ptr + 自定义 deleter 管理 AVFormatContext
3. 错误必须返回 false 并填日志，不能抛异常

# 输出
先用中文写实现思路（5 行内），等我确认后再写代码。
```

**AI 思路（确认阶段）**：
1. `avformat_open_input` 打开文件 → `unique_ptr` 包装
2. `avformat_find_stream_info` 解析流信息
3. 遍历 streams 找 video stream index
4. 从 `AVStream` 读 width/height/avg_frame_rate/duration
5. `AVStream->nb_index_entries` 即关键帧数（前提是 MP4 有 stss）

**Review 重点（人工兜底）**：
- 第 5 步要加 fallback：如果 `nb_index_entries == 0`，标记 "unknown" 而不是返回 0
- `avg_frame_rate` 是 `AVRational`，要 `av_q2d` 转 double
- duration 单位是 `AV_TIME_BASE_Q`，需要换算成秒

### 8. 进阶问题与延伸阅读

- **AI Coding 与代码安全**：AI 代码的供应链风险（生成的依赖是否真实存在？版本是否有 CVE？）
- **AI Coding 与团队协作**：怎么把个人的 AI 工作流推广到团队？`.cursorrules` / 团队 prompt 模板沉淀
- **Agent-based Coding 的未来**：Devin / Claude Code / Cursor Composer 的自主性边界在哪
- **AI 重构 vs AI 新建**：AI 在 brownfield 项目（老代码迁移）的能力远弱于 greenfield，原因是什么
- **延伸阅读**：
  - Andrej Karpathy 的 VibeCoding 推文与演讲（2025-02）
  - Anthropic 的 [Building Effective Agents](https://www.anthropic.com/research/building-effective-agents) 论文
