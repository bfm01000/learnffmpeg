# AI Coding 面试自我总结

## 2 分钟总回答

如果面试官问我平时是怎么使用 AI Coding 的，我会这样回答：

> 我现在使用 AI 的核心原则不是“让 AI 替我写代码”，而是“我负责拆解问题、设计方案、提供上下文和做最终 Review，AI 负责提高编码和文档产出的效率”。
>
> 尤其我做的是 C++ 音视频、FFmpeg、JNI、OC 这一类偏底层的工作，AI 的幻觉风险其实比普通业务代码更高。所以我不会直接跟 AI 说“帮我做一个播放器”或者“帮我写一个音视频模块”。这种问题太大，AI 很容易按它自己的理解乱写，最后 Review 成本比自己写还高。
>
> 我一般会把 AI 用在三个场景：第一是优化局部代码，比如某个函数重构、性能优化、内存释放、边界条件补齐；第二是从 0 到 1 做一个相对完整的项目或模块，这时我会先让 AI 帮我做方案设计和任务拆解，而不是直接写代码；第三是 JNI、OC 对 C++ 的接口封装，这类代码模板性比较强，但生命周期、线程、内存和异常边界很容易出问题，所以我会让 AI 负责生成重复性代码，我负责把控跨语言边界的正确性。
>
> 总结来说，我认为 AI Coding 的价值不是降低工程师能力要求，而是把工程师从“写模板代码”里解放出来，让我们把更多精力放到架构判断、性能分析、边界条件和代码质量上。AI 是执行者，我才是代码质量和最终结果的负责人。

## 场景一：优化局部代码

### 面试时可以这样说

> 在优化局部代码时，我不会让 AI 接触太大的上下文，而是把问题压缩到一个非常明确的小范围里。
>
> 比如我在做 FFmpeg 解码、seek、内存释放或者 C++ 类重构时，我会先自己判断问题大概在哪一层，是性能问题、内存问题、线程问题，还是代码可维护性问题。然后我会把相关函数、头文件、调用关系和必要的日志喂给 AI，并明确告诉它当前架构是什么、不能改哪些接口、性能上有什么约束。
>
> 我常用的方式是先让 AI 给出 2 到 3 种方案，分别说明优缺点，而不是一上来就让它改代码。比如一个局部性能优化，我会问它：当前逻辑有哪些可能的优化方向？哪些方案改动小、风险低？哪些方案收益大但可能影响调用方？我会先根据项目实际情况选一个方案，再让它输出具体修改步骤。
>
> 真正让 AI 写代码时，我会限制它只改指定文件和指定函数，并要求保持原有代码风格。写完之后，我一定会自己 Review，重点看几个地方：有没有破坏已有接口、有没有引入额外内存拷贝、有没有遗漏 `unref/free/release`、异常路径是否也能释放资源、线程回调有没有竞态问题。
>
> 所以在局部代码优化上，AI 对我最大的帮助是提高“提出方案 + 写样板代码 + 补边界条件”的速度，但最终优化方向和代码正确性还是由我把控。

### 我常用的 Prompt 思路

> 你是一个资深 C++ 音视频开发工程师。  
> 当前我在优化一段 FFmpeg 相关代码，背景是：这里存在性能瓶颈 / 内存释放风险 / 可维护性问题。  
> 请先不要直接改代码，先基于我提供的函数和调用关系，给出 2 到 3 种优化方案，并说明每种方案的收益、风险和适用场景。  
> 约束条件：  
> 1. 不允许修改对外接口。  
> 2. 不允许引入额外的帧数据拷贝。  
> 3. 必须考虑异常返回和资源释放。  
> 4. 代码风格要和当前文件保持一致。  
> 我确认方案后，你再帮我输出具体修改。

### 面试官可能追问

**Q1：你为什么不直接让 AI 帮你改？**

> 因为 AI 最大的问题是不知道项目里的隐含约束。比如某个接口虽然看起来可以改，但实际上被 Android 和 iOS 双端共同依赖；某个拷贝看起来无所谓，但在 4K 视频链路里可能直接导致带宽和发热上升。所以我会先让 AI 出方案，我先做架构判断，确认不会破坏系统边界后再让它写代码。

**Q2：如果 AI 给出的方案看起来很合理，但你不确定对不对，怎么办？**

> 我会回到数据和源码本身验证。比如性能优化一定要有前后耗时对比，内存问题要看释放路径和工具结果，FFmpeg 相关问题要看源码或官方文档确认 API 语义。AI 的解释只能作为参考，不能当成结论。

**Q3：AI 写出来的代码有 Bug，你怎么处理？**

> 我不会一直点重新生成。我会先缩小问题范围，只保留出错函数、编译错误、Crash 堆栈或关键日志，让 AI 针对确定信息分析。如果它连续两次方向不对，我会停止让它猜，自己打断点或加日志定位真实原因，再把明确结论喂给 AI，让它辅助修复。

## 场景二：从 0 开始设计并写完一个项目

### 面试时可以这样说

> 如果是从 0 开始做一个项目或一个相对完整的模块，我更不会直接让 AI 写代码，而是先让它参与“方案设计”和“任务拆解”。
>
> 我的流程一般分四步。第一步，我会先把业务目标、技术背景、输入输出、性能要求、平台限制说清楚。比如这是 Android 还是 iOS，核心逻辑是否要放在 C++ 层，是否涉及 FFmpeg、OpenGL、MediaCodec，是否需要跨平台复用。
>
> 第二步，我会让 AI 先输出设计文档，而不是代码。文档里必须包含模块边界、核心类设计、数据流、线程模型、错误处理和测试方案。这个阶段我主要把 AI 当成“架构讨论助手”，让它帮我把可能遗漏的点列出来。
>
> 第三步，我会自己 Review 设计。比如我会重点看职责是否拆清楚了，有没有某个类承担太多事情，C++ 层和 Java/OC 层边界是否合理，数据流里有没有不必要的拷贝，线程切换是否清晰。如果方案有问题，我会直接指出某一段让 AI 重写，而不是全盘接受。
>
> 第四步才是编码。我会把完整项目拆成很多小任务，例如先写接口定义，再写核心数据结构，再写单元测试或 demo，再接入平台层。每个任务我都会给 AI 明确输入、输出、依赖文件和不能改的范围。这样即使 AI 某一步写错了，影响面也比较小，方便回滚和 Review。
>
> 所以我从 0 到 1 使用 AI 的重点不是“一次性生成完整项目”，而是让 AI 帮我快速完成方案草稿、接口草稿、重复代码和文档沉淀。我自己负责把项目拆成 AI 能稳定完成的小任务，并且在每个阶段做验收。

### 我常用的 Prompt 思路

> 你是一个资深 C++ 音视频架构师。  
> 我现在要从 0 设计一个模块，目标是：XXX。  
> 技术背景：核心能力放在 C++ 层，对 Android 通过 JNI 暴露，对 iOS 通过 OC/OC++ 暴露。  
> 请先不要写代码，先输出一份设计文档，包含：  
> 1. 模块职责和不负责的事情。  
> 2. 核心类和接口设计。  
> 3. 数据流和线程模型。  
> 4. 资源生命周期管理。  
> 5. 可能的风险点和测试方案。  
> 输出后请列出 3 个你认为最需要我确认的架构问题。

### 面试官可能追问

**Q1：从 0 写项目时，AI 生成很多代码，你怎么保证整体质量？**

> 我不会让它一次性生成很多代码。我会把任务拆到足够小，比如一次只生成一个接口、一个类、一个函数或一个测试 demo。每一块都要能单独编译、单独验证。这样代码质量不是靠“相信 AI”，而是靠任务边界、阶段验收和人工 Review 保证。

**Q2：AI 设计的架构和你的想法不一样，你会听谁的？**

> 我会把 AI 的方案当成候选方案，而不是最终方案。如果它提出的点能补充我的盲区，我会吸收；但如果和项目约束冲突，比如引入了不必要的抽象、破坏跨平台边界、增加线程复杂度，我会坚持自己的判断。AI 在这里像一个讨论对象，不能替代工程负责人。

**Q3：你怎么避免 AI 过度设计？**

> 我会在 Prompt 里明确要求“优先简单可落地，不要为了扩展性引入复杂抽象”。同时我会检查每个类是否有明确职责，每个抽象是否真的有两个以上使用场景。如果只是为了看起来高级，我会删掉。对业务项目来说，可维护和可验证比架构花哨更重要。

## 场景三：JNI、OC 对 C++ 的接口封装

### 面试时可以这样说

> JNI 和 OC 对 C++ 的接口封装，是我觉得 AI 最适合提效、但也最需要人工兜底的场景。
>
> 适合提效，是因为这类代码有很多模板化内容，比如 Java 方法和 native 方法映射、参数转换、错误码转换、OC wrapper、回调接口、对象持有关系等。AI 对这些重复代码生成很快，可以明显减少手写样板代码的时间。
>
> 但风险也很高，因为跨语言边界最容易出问题。比如 JNI 里 `JNIEnv*` 不能跨线程直接使用，子线程回调 Java 要先 attach；Java 对象如果长期持有要考虑 `GlobalRef` 或 `WeakGlobalRef`；C++ 回调到 Java/OC 时要考虑页面销毁后的生命周期；大块视频帧数据不能随便深拷贝；异常也不能直接穿透 C++/Java/OC 边界。
>
> 所以我使用 AI 的方式是：让它先根据 C++ 头文件生成 JNI 或 OC wrapper 的初版，但我会在 Prompt 里强约束生命周期、线程和内存策略。比如 Android 侧要求不能缓存裸 `JNIEnv*`，回调必须处理线程 attach/detach，listener 要用弱引用避免页面销毁后泄漏；iOS 侧要求 OC wrapper 不拥有底层裸指针，释放时要和 C++ 对象生命周期对齐，回调回主线程时要明确 dispatch。
>
> 最后我会重点 Review 四类问题：第一是线程是否正确，第二是对象生命周期是否安全，第三是大数据传递有没有多余拷贝，第四是异常和错误码有没有被正确转换。AI 可以帮我提高封装速度，但跨语言边界的坑必须由我自己兜底。

### 我常用的 Prompt 思路

> 你是一个精通 Android NDK、JNI、Objective-C++ 和 C++17 的跨平台音视频开发工程师。  
> 现在我有一个 C++ 类，需要分别封装给 Android 和 iOS 使用。  
> 请根据我提供的 C++ 头文件，先设计 JNI/OC wrapper 的接口，不要直接写完整实现。  
> 约束条件：  
> 1. JNI 层不能缓存裸 `JNIEnv*`。  
> 2. 子线程回调 Java 必须处理 attach/detach。  
> 3. listener 生命周期要避免 Java/OC 对象销毁后的悬空回调。  
> 4. 视频帧、音频 PCM 这类大数据尽量避免深拷贝。  
> 5. C++ 异常不能直接跨语言抛出，要转换成错误码或回调。  
> 请先说明你的生命周期设计和线程回调策略，我确认后再写代码。

### 面试官可能追问

**Q1：JNI 封装里你最担心 AI 写错什么？**

> 最担心的是线程和生命周期。比如 AI 很容易把 `JNIEnv*` 存成成员变量，或者在 C++ 子线程里直接用主线程的 `JNIEnv*` 回调 Java，这在运行时可能直接崩。还有就是 listener 的引用，如果用强全局引用又不释放，会泄漏；如果直接存局部引用，函数返回后就失效。所以这些地方我一定会人工 Review。

**Q2：OC 封装里 AI 容易忽略什么？**

> OC/OC++ 这边容易忽略对象所有权和线程切换。比如 C++ 对象释放后 OC wrapper 还在调用，或者 C++ 回调直接更新 UI，没有切回主线程。还有 block 捕获 `self` 时可能造成循环引用。所以我会要求 AI 明确 weak/strong dance、析构顺序和回调线程。

**Q3：视频帧数据跨 JNI/OC 传递时，你会怎么约束 AI？**

> 我会明确告诉它大块数据不能默认深拷贝。比如 YUV、PCM、纹理、硬件 buffer 这类数据，如果每帧都拷贝一次，性能和发热都会很差。Android 侧可以考虑 `DirectByteBuffer`、硬件 buffer 或 native handle；iOS 侧可以考虑 `CVPixelBufferRef`、Metal texture 或只传 native 指针句柄。但具体用哪种方式，要结合生命周期和调用方是否同步消费来判断，不能只为了零拷贝牺牲安全性。

## 最后可以拔高总结

如果面试最后让我总结 AI Coding，我会这样说：

> 我觉得 AI Coding 对工程师的要求其实更高了。因为以前我只要自己写对代码就行，现在我还要能把模糊需求拆成 AI 能理解的小任务，要能给它正确上下文，要能识别它写出来的代码哪些是看起来对、实际有坑。
>
> 尤其是音视频和跨平台 C++ 这种方向，很多问题不是语法问题，而是性能、线程、生命周期、平台差异和历史架构问题。AI 可以帮我更快地产出方案和代码，但它不能替我对线上质量负责。
>
> 所以我对 AI 的定位是一个效率很高的结对助手。它能帮我节省重复劳动，让我把更多精力放在架构、性能和风险控制上。但最终能不能把事情做好，还是取决于工程师自己的技术判断和 Review 能力。

## 面试前速记关键词

- 不要说：我让 AI 帮我写一个播放器。
- 要说：我先拆需求、定边界、给上下文，再让 AI 做小任务。
- 核心姿态：AI 负责执行，我负责架构、约束、Review 和结果。
- 局部优化：小范围上下文、先方案后代码、用数据验证。
- 从 0 到 1：先设计文档，再任务拆解，分阶段实现和验收。
- JNI/OC 封装：AI 写模板，人兜底线程、生命周期、内存和异常边界。
- 最重要的一句话：AI 提高的是产出效率，不替代工程判断。
