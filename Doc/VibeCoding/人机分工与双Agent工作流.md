# 人机分工与双 Agent 工作流总结

这几张图的核心不是“让 AI 全自动写代码”，而是把 AI Coding 拆成一个可控的人机协作系统：

> **人负责方向、边界、决策和兜底；AI 负责扩写、测试、review、记忆和重复执行。**

---

## 一、人机分工全景

可以把 AI Coding 看成三层：

```text
人
  负责定方向、提供上下文、做关键决策、最终验收

协作通道
  spec -> plan -> memory -> commit

AI Agent
  负责扩写、测试、review、记忆、执行具体任务
```

### 1. 人负责什么

人不是把任务丢给 AI 后等结果，而是要做四件事：

- **定方向**：明确目标、约束、优先级，决定要解决什么问题。
- **把关决策**：判断方案是否符合项目现实，而不是只看 AI 写得是否顺。
- **踩坑兜底**：识别 AI 忽略的平台差异、生命周期、性能、兼容性问题。
- **最终验收**：review 代码、跑测试、确认行为符合预期。

一句话：

> **人负责“做什么、为什么做、做到什么程度”；AI 负责“怎么快速展开和执行”。**

### 2. AI Agent 负责什么

AI Agent 更适合处理明确边界内的工作：

- **扩写**：根据人给的方向，把方案、代码、文档展开。
- **测试**：生成测试用例、补充边界条件、跑基础验证。
- **review**：从代码质量、风险点、遗漏场景角度做二次检查。
- **记忆**：沉淀项目上下文、规则、历史决策和踩坑记录。

AI 的强项是执行和扩展，不是最终判断。

---

## 二、协作通道：spec -> plan -> memory -> commit

图中间的协作通道可以理解为一条稳定工作流：

```text
spec
  明确需求和边界

plan
  拆分任务和执行路径

memory
  记录上下文、规则、历史决策

commit
  收敛变更、提交结果、形成闭环
```

### 1. spec：先写清楚任务

`spec` 不是形式主义，而是为了防止 AI 自己脑补。

需要讲清楚：

- 当前目标是什么。
- 输入输出是什么。
- 哪些文件可以改。
- 哪些接口不能动。
- 性能、兼容性、平台限制是什么。

适合的表达：

```text
我要优化 FFmpeg 解码链路中的资源释放问题。
只允许改 xxx.cpp 和 xxx.h。
不能改变外部接口。
必须保持 av_packet_unref / av_frame_unref 的生命周期正确。
先给方案，不要直接改代码。
```

### 2. plan：先拆任务，再执行

复杂任务不要直接让 AI 写完整实现，应该先拆成小步骤：

```text
1. 读现有代码和文档。
2. 总结现有链路。
3. 找风险点。
4. 给改动方案。
5. 人确认。
6. 再逐步改代码。
7. 跑测试和 review。
```

计划的价值是降低 AI 一次性跑偏的风险。

#### spec -> plan -> execute 流水线

图里的 `spec -> plan -> execute` 可以理解成一条从抽象到具体的 AI Coding 流水线：

```text
需求澄清
  -> Spec 设计
      -> Plan 拆解
          -> Execute 执行
```

它的核心思想是：

> **不要从一句模糊需求直接跳到写代码，而是每一阶段都产出一个可检查、可复用、可追踪的中间产物。**

整体流向：

```text
抽象、冷启动
  需求还不清楚，需要人补背景、AI 帮澄清

        ↓

半结构化
  形成 spec，明确背景、目标、设计、任务清单

        ↓

结构化
  形成 plan，把任务拆成可执行步骤

        ↓

具体、可执行
  按 task 执行、测试、commit、更新 memory
```

##### 1. 需求澄清

这一阶段解决的是：

```text
到底要做什么？
为什么要做？
边界在哪里？
哪些信息还不清楚？
```

输入可能是：

- PDF。
- Excel。
- 现有代码。
- 口头需求。
- issue / bug 描述。
- 模糊想法。

适合用的能力：

```text
brainstorming
需求澄清
问题拆解
```

产出不是代码，而是：

- 核心问题清单。
- 关键约束。
- 不确定点。
- 需要人工确认的问题。

例子：

```text
用户说：我想优化播放器卡顿。

需求澄清后应该变成：
- 卡顿发生在起播、seek 后，还是长时间播放后？
- 是解码慢、渲染慢、网络慢，还是队列阻塞？
- 目标是降低首帧时间，还是降低平均延迟？
- 当前平台是 Android/iOS/Linux？
- 是否允许改线程模型和缓存策略？
```

这一阶段最重要的是：**每轮必须带着明确问题进入下一轮，不要让 AI 自由发挥。**

##### 2. Spec 设计

`spec` 是把需求变成设计文档。

这一步的核心是：

> **动代码前，先写清楚这件事要做成什么样，别让 AI “猜”。**

它应该包含：

```text
Background
  为什么做

Goal / Non-Goal
  做什么，也写清不做什么

Detailed Design
  数据模型、API、伪码、流程、边界

File Manifest
  具体改哪些文件
```

输入：

- 上游需求澄清结果。
- 架构讨论结论。
- 现有代码或文档。

产出：

```text
specs/YYYY-MM-DD-xxx-design.md
```

适合记录：

- 当前问题。
- 设计目标。
- 不做什么。
- 模块边界。
- 数据结构。
- 线程和生命周期。
- 风险点。
- 测试方向。

例子：

```text
specs/2026-06-03-ffmpeg-player-stutter-design.md

Background:
  seek 后偶发卡顿，怀疑 packet queue / frame queue 清理不完整。

Goal / Non-Goal:
  降低 seek 后恢复播放耗时，避免旧帧残留。
  不重构整个播放器线程模型。
  不改变现有对外 API。

Detailed Design:
  明确 demux/decode/render 三段队列清理策略。
  seek 开始时暂停消费，清空 packet queue 和 frame queue。
  调用 avcodec_flush_buffers 清掉解码器内部状态。
  恢复后从目标时间戳附近重新送 packet。

File Manifest:
  project/player/Player.cpp
  project/player/Decoder.cpp
  project/player/PacketQueue.h
  project/player/FrameQueue.h
```

`spec` 的价值是：**让 AI 和人对同一件事有同一份上下文。**

更具体地说，四段模板各自解决不同问题。

###### Background：为什么做

`Background` 负责交代背景和动机。

它要回答：

- 现在的问题是什么。
- 为什么现在要改。
- 现有系统大概怎么工作。
- 有哪些历史约束。
- 这个问题影响谁。

不要只写：

```text
优化 seek。
```

应该写成：

```text
当前播放器 seek 后偶发卡顿，表现为 seek 完成后 1-2 秒才恢复画面。
现有链路是 demux -> packet queue -> decoder -> frame queue -> render。
怀疑 seek 时旧 packet/frame 没有完全清空，导致解码器还在消费旧数据。
这次优化只处理 seek 后恢复慢和旧帧残留问题。
```

`Background` 写得越清楚，AI 越不容易自己脑补背景。

###### Goal / Non-Goal：做什么，也写清不做什么

`Goal` 负责定义成功标准。

`Non-Goal` 负责划边界，告诉 AI 哪些事不要顺手做。

例子：

```text
Goal:
- seek 后不再显示旧帧。
- seek 后首帧恢复时间降低。
- 保证 packet/frame/decoder 三层 flush 顺序清晰。

Non-Goal:
- 不重写整个播放器架构。
- 不引入新的线程模型。
- 不修改对外 API。
- 不处理网络缓冲策略。
```

`Non-Goal` 很重要，因为 AI 经常会“顺手优化”：

- 顺手重构类。
- 顺手改接口。
- 顺手引入新抽象。
- 顺手改无关文件。

这些都会增加 review 成本。

###### Detailed Design：数据模型、API、伪码

`Detailed Design` 是 spec 里最关键的一段。

它要把“想法”落到工程结构上：

- 数据模型。
- 关键 API。
- 核心流程。
- 状态机。
- 线程边界。
- 资源生命周期。
- 错误处理。
- 必要伪码。

例子：

```text
Detailed Design:

1. seek 请求进入 Player::seekTo(ms)
2. Player 暂停 demux 和 decode 消费
3. PacketQueue::clear() 清空未解码 packet
4. FrameQueue::clear() 清空未渲染 frame
5. Decoder::flush() 内部调用 avcodec_flush_buffers(codecCtx)
6. Demuxer seek 到目标时间戳附近关键帧
7. 恢复 demux/decode/render
```

如果有关键伪码，也可以写进去：

```cpp
void Player::seekTo(int64_t ms) {
    pausePipelines();
    packetQueue.clear();
    frameQueue.clear();
    decoder.flush();
    demuxer.seek(ms);
    resumePipelines();
}
```

这不是最终代码，而是让 AI 知道你希望代码长什么样。

###### File Manifest：具体改哪些文件

`File Manifest` 负责限制修改范围。

它要回答：

- 哪些文件需要改。
- 每个文件大概改什么。
- 哪些文件只读不改。
- 哪些文件不能碰。

例子：

```text
File Manifest:

需要修改：
- Player.cpp：增加 seek 总控流程。
- Decoder.cpp：补充 flush 封装。
- PacketQueue.h/.cpp：确认 clear 释放 packet 引用。
- FrameQueue.h/.cpp：确认 clear 释放 frame 引用。

只读参考：
- Demuxer.cpp：确认 seek 接口语义。
- Renderer.cpp：确认旧帧显示逻辑。

禁止修改：
- PublicPlayerAPI.h：不能改对外接口。
```

这段对 AI 特别有用，因为它把任务边界从“整个项目”缩小到“这几个文件”。

###### Spec 的判断标准

一份好的 spec 应该做到：

```text
看到 Background，知道为什么做。
看到 Goal / Non-Goal，知道做什么和不做什么。
看到 Detailed Design，知道大致怎么实现。
看到 File Manifest，知道具体动哪些文件。
```

如果 spec 写完后，AI 仍然需要猜：

- 目标是什么。
- 哪些文件能改。
- 接口能不能动。
- 成功标准是什么。

说明 spec 还不合格，应该继续补，而不是进入编码。

##### 3. Plan 拆解

`plan` 是把 spec 变成可执行任务。

输入：

```text
spec 中的 File Manifest / Task Manifest
```

产出：

```text
plans/YYYY-MM-DD-xxx.md
```

好的 plan 应该满足：

- 每个 task 足够小。
- 每个 task 有明确输入和输出。
- 每个 task 最好 3-4 个步骤。
- 每个 task 可以单独验证。
- 每个 task 尽量对应一个小 commit。

例子：

```text
Task 1: 梳理 packet/frame queue 生命周期
Step 1: 阅读 Player::seek / Decoder::flush / Queue::clear。
Step 2: 画出 seek 前后的数据流。
Step 3: 标记旧 packet/frame 可能残留的位置。
Step 4: 输出风险清单，不改代码。

Task 2: 实现 seek flush 修复
Step 1: 在 seek 开始时停止 demux/decode 消费。
Step 2: 清空 packet queue 和 frame queue。
Step 3: 调用 avcodec_flush_buffers。
Step 4: 恢复解码并验证首帧。
```

plan 的价值是：**把“我要优化卡顿”变成 AI 可以稳定执行的小任务。**

##### 4. Execute 执行

`execute` 阶段才开始真正改代码或产出文档。

输入：

```text
Plan 中的某一个 Task
```

适合用的能力：

- `executing-plans`
- `subagent-driven-dev`
- 测试工具
- lint / build / run

产出：

- 代码改动。
- 测试结果。
- 文档更新。
- commit。
- memory 更新。

执行阶段要注意：

```text
每次只执行一个明确 task。
task 完成后要测试或人工验收。
不要在执行中临时扩大范围。
如果发现 plan 有问题，回到 plan 阶段修正，而不是硬写。
```

##### 5. 每阶段都要更新 memory

图里有一条横向的 `memory 更新`，这很关键。

意思是：每个阶段结束时，都要把稳定结论沉淀进 memory：

```text
需求澄清后：
  记录用户真正目标和偏好。

Spec 设计后：
  记录架构边界和关键设计。

Plan 拆解后：
  记录任务顺序和禁止事项。

Execute 执行后：
  记录已完成、踩坑、废弃方案。
```

这样下次 AI 接着做时，不会重新猜。

##### 6. 流水线原则

这条流水线有四个原则：

```text
1. 输入清晰
   每轮必须带着明确输入进入下一阶段，否则禁止进入下一段。

2. 产出可追踪
   Spec / Plan 落地成文档，文件名带日期和语义。

3. 粒度可控
   Task 拆到 3-4 step，最好能独立测试和独立 commit。

4. 闭环沉淀
   每轮结论更新 memory，同类需求下次可以复用。
```

面试表达可以这样说：

> 我不会让 AI 从一句模糊需求直接开始写代码，而是按 `需求澄清 -> Spec 设计 -> Plan 拆解 -> Execute 执行` 走。需求阶段先明确目标和边界，Spec 阶段沉淀背景、目标、设计和任务清单，Plan 阶段把任务拆成可执行步骤，Execute 阶段才让 AI 改代码、跑测试和提交结果。每个阶段都有可检查的中间产物，并且会把关键结论更新到 memory，保证长任务不会因为上下文漂移而跑偏。

### 3. memory：让 AI 记住项目规则

`memory` 适合记录长期稳定的信息：

- 项目目录结构。
- 编码规范。
- 禁止事项。
- 常见坑。
- 平台约束。
- 关键业务背景。

例如：

```text
本项目禁止自动 push 代码。
涉及音视频帧数据时，默认不允许每帧深拷贝。
JNI 层不能缓存裸 JNIEnv*。
FFmpeg Packet/Frame 循环复用时用 unref，最终退出才 free。
```

#### memory-project.md 分层结构

图里的 `memory-project.md` 可以理解成 **AI 的备忘录，不是给人看的正式文档**。

它的目标不是写得漂亮，而是让 AI 在长期任务中稳定记住：

```text
偏好是什么
架构是什么
哪些决策已经定了
还有哪些事要提醒
```

可以分成四层：

```text
memory-project.md
├── User Preferences
│   ├── 作者画像
│   ├── 语言偏好
│   └── 汇报风格
│
├── Architecture Notes
│   ├── 三层缓存架构
│   ├── 核心类设计
│   ├── 读写流程
│   └── 并发策略
│
├── Key Decisions
│   ├── 缓存策略
│   ├── 内存压力分级
│   ├── 异常处理原则
│   └── 命名规范
│
└── Reminders
    ├── 已完成事项
    ├── 待办事项
    ├── 暂缓事项
    └── 已废弃事项
```

##### 1. User Preferences：用户偏好

记录“这个用户希望 AI 怎么工作”。

适合写：

- 作者画像：比如“移动端音视频开发，关注面试表达和工程落地”。
- 语言偏好：比如“中文解释，关键术语保留英文”。
- 汇报风格：比如“先结论，再解释；少废话；适合面试复述”。

例子：

```text
User Preferences
- 使用中文回答，关键英文术语保留。
- 文档偏面试导向：先高频问答，再原理，再常见坑。
- 代码解释要结合 FFmpeg / C++ / 移动端音视频场景。
```

##### 2. Architecture Notes：架构笔记

记录项目里相对稳定的架构信息。

适合写：

- 模块分层。
- 核心类职责。
- 数据流。
- 并发模型。
- 缓存策略。
- 平台差异。

例子：

```text
Architecture Notes
- 解码链路：demux -> decode -> frame queue -> render。
- FFmpeg Packet/Frame 生命周期：循环内 unref，退出时 free。
- Android 硬解走 MediaCodec，iOS 硬解走 VideoToolbox。
```

这类信息能减少 AI 每次重新读代码的成本，也能减少它乱猜架构。

##### 3. Key Decisions：关键决策

记录“已经定下来的选择”，避免 AI 反复推翻。

适合写：

- 为什么选某个方案。
- 明确不做什么。
- 关键边界。
- 命名规范。
- 异常处理原则。

例子：

```text
Key Decisions
- 文档风格统一采用“面试高频问答 + 原理详解 + 常见坑 + 自检”。
- 不自动 push 代码，提交必须人工确认。
- 大块音视频数据默认不深拷贝，除非明确说明生命周期安全。
- 跨 JNI 回调不能缓存裸 JNIEnv*。
```

这部分很重要，因为 AI 容易在长任务里忘掉前面已经讨论过的结论。

##### 4. Reminders：提醒事项

记录当前阶段的状态和待办。

适合写：

- 已完成。
- 进行中。
- 暂缓。
- 已废弃。
- 下次继续时先看什么。

例子：

```text
Reminders
- 已完成：RTMP Chunk / Message / FLV Tag 关系整理。
- 进行中：FFmpeg 硬件编解码专题。
- 暂缓：WebRTC 深入源码阅读。
- 已废弃：不要再把 AVCC 和 avcC 混成同一个概念。
```

##### 关键区分

`memory-project.md` 不是正式文档，也不是给面试官看的总结。

它更像：

```text
给 AI 自己看的项目备忘录
```

所以它应该：

- 信息精准。
- 结构清晰。
- 偏结论。
- 少写长篇解释。
- 只记录稳定规则和关键决策。

不应该：

- 把所有聊天过程都塞进去。
- 记录未经确认的猜测。
- 写成面向人的教程。
- 记录已经失效的临时状态。

### 4. commit：人来收口

AI 可以帮忙整理变更摘要、生成 commit message，但是否提交应该由人决定。

尤其要遵守：

- 不自动 push。
- 不跳过 review。
- 不把 AI 生成内容直接当最终结论。
- 提交前看 diff、跑测试、确认无敏感信息。

## 三、Claude Code 能力层：subagent / skill / hooks / memory

图里把 Claude Code 的能力拆成四类：

```text
subagent
skill
hooks
memory
```

它们分别解决不同问题。

### 1. subagent：适合并行和隔离上下文

`subagent` 适合复杂任务中的子任务拆分。

适合场景：

- 长任务拆解。
- 多文件分析。
- 方案讨论。
- 代码 review。
- 多个方向并行探索。

例子：

```text
主 Agent：负责总控和最终决策。
subagent A：分析 FFmpeg 硬解链路。
subagent B：整理 Android MediaCodec 文档。
subagent C：整理 iOS VideoToolbox 文档。
```

好处：

- 每个 subagent 有独立上下文，不容易互相污染。
- 可以并行处理多个方向。
- 主 Agent 只做汇总和判断。

风险：

- subagent 可能写重复内容。
- 子任务结果需要主 Agent 或人统一 review。
- 不适合让多个 agent 同时改同一文件。

#### 多 agent 并行 review 编队

图里的“多 agent 并行 review 编队”适合用在代码已经完成、准备合并前。

核心原则：

> **多个专家 agent 独立 review，互相不沟通；主会话负责调度、汇总、去重和最终决策。**

结构可以这样理解：

```text
                         主会话
                调度 / 汇总 / 去重 / 决策
                           │
     ┌───────────────┬─────┴─────┬───────────────┐
     │               │           │               │
 架构专家 agent   并发性能专家   可靠性专家     测试专家
     │               │           │               │
  架构 issue       性能 issue   可靠性 issue    测试 issue
     │               │           │               │
     └───────────────┴─────┬─────┴───────────────┘
                           │
                      API 设计专家
                           │
                      API issue 清单
                           │
                           ↓
                     主会话统一汇总
```

### 1. 为什么要并行 review

单个 agent review 很容易有盲区。

不同专家 agent 可以从不同角度看同一份改动：

- **架构专家**：看层次、职责、抽象、依赖方向。
- **并发性能专家**：看锁、竞态、队列、内存拷贝、热点路径。
- **可靠性专家**：看异常路径、资源释放、边界条件、降级策略。
- **测试专家**：看测试覆盖、回归用例、边界输入。
- **API 设计专家**：看接口命名、参数语义、兼容性、一致性。

这样比让一个 agent 泛泛 review 更容易发现真实问题。

### 2. 五个 agent 之间不要互相沟通

图里的红线是：

```text
5 个 agent 相互不沟通，对方不存在。
```

原因是：

- 避免观点互相污染。
- 避免一个 agent 的错误结论带偏其他 agent。
- 保留独立视角。
- 方便主会话比较不同 agent 是否发现同类问题。

每个 agent 只知道：

```text
自己的审查范围
自己的 prompt
自己的输入 diff / 代码 / spec
自己的输出格式
```

不要让 agent 之间互相引用、互相总结、互相争论。

### 3. 每个专家 agent 只输出 issue 清单

专家 agent 不应该直接改代码。

它只输出：

```text
Issue 清单
  - 问题描述
  - 严重等级
  - 证据位置
  - 风险说明
  - 建议修复方向
```

例如：

```text
并发性能专家输出：
- P1：Decoder::flush 与 decode loop 并发访问 packetQueue，缺少互斥保护。
  证据：flush 在 UI 线程触发，decode loop 在工作线程持续消费。
  风险：seek 时可能出现旧 packet 残留或 crash。
  建议：flush 前暂停 decode loop，或给 queue clear/consume 加状态同步。
```

这样做的好处是：**review 和修改分离**。

### 4. 主会话统一汇总和定级

主会话不是简单复制五份结果，而是要做：

- 去重。
- 合并同类问题。
- 判断是否真实。
- 分级。
- 决定修不修。
- 决定谁来修。

推荐分级：

```text
P0 Critical
  必须马上修。会导致崩溃、数据损坏、严重安全问题、核心功能不可用。

P1 Major
  应该修。会导致明显错误、性能退化、兼容性问题、重要边界缺失。

P2 Minor
  可选修。代码风格、命名、轻微可维护性问题。
```

主会话最终输出应该像这样：

```text
Review 汇总：

P0:
- 无

P1:
- Decoder flush 竞态问题。
- PacketQueue clear 后旧 frame 可能残留。

P2:
- API 命名不够清晰。
- 测试缺少 seek 到文件尾的边界用例。

决定：
- 本轮修 P1。
- P2 记录到后续任务。
```

### 5. 跨专家共识定严重度

并行 review 的一个关键价值是：**用多个独立视角交叉验证单个 AI 的判断**。

如果一个问题只有一个专家发现，可能是该专家视角下的局部担忧；如果多个专家在互不知道对方存在的情况下独立发现同一个问题，说明这个问题的可信度和优先级都应该提高。

图里的核心规则是：

> **3 位以上专家独立发现同一个问题，直接按 P0 处理。**

原因是：

```text
5 个角色互相不知道对方存在。
每个角色只从自己的专业维度 review。
如果 3 个以上角色都命中同一个问题，说明它不是单个 AI 的幻觉。
共识越多，优先级越高。
```

可以用一个二维矩阵理解：

```text
                         共识度
                 1 位专家发现       3+ 位专家独立发现

严重度高          需要复核              P0 Critical
                  可能是真问题          必须优先处理

严重度中          P2 / Suggestion       P1 Major
                  可记录                应该修

严重度低          Suggestion            可降级
                  可选优化              视成本处理
```

这里的判断不是只看“严重度”，也看“共识度”：

- **严重度高 + 多专家共识**：直接 P0，优先修。
- **严重度高 + 单专家发现**：不能忽略，但要主会话复核证据。
- **严重度中 + 多专家共识**：通常升到 P1。
- **严重度低 + 单专家发现**：多半是建议或风格问题，记录即可。

例子：

```text
架构专家：
  发现 Decoder::flush 可能破坏解码状态机。

并发性能专家：
  发现 flush 与 decode loop 并发访问 queue。

可靠性专家：
  发现异常路径下旧 frame 可能残留。

测试专家：
  指出缺少 seek 中途再次 seek 的回归用例。
```

如果这些 issue 最终都指向同一个核心问题：

```text
seek/flush 状态切换不安全
```

那主会话应该把它合并成一个高优先级问题，而不是当成四条普通建议。

汇总时可以这样写：

```text
P0 Critical:
- seek/flush 状态切换不安全。
  共识来源：架构专家、并发性能专家、可靠性专家、测试专家。
  证据：flush 与 decode loop 存在并发访问；旧 packet/frame 清理顺序不明确；缺少回归测试。
  决策：本轮必须修复，修复前不合并。
```

注意：多专家共识不是让 AI 自动决定，而是给人一个风险信号。

最终仍然要由主会话和人判断：

- 问题是否真实存在。
- 证据是否充分。
- 是否阻塞合并。
- 本轮修还是后续修。

这套机制的价值是：

> **单个 AI 的幻觉可以被交叉验证过滤；多个独立专家的共识可以作为优先级提升依据。**

### 6. 独立性保证和并行编队前提

并行 review 要有几个前提：

```text
1. 独立上下文
   每个 agent 只拿自己的 diff 和 prompt，不看其他 agent 输出。

2. 禁止交叉阅读
   不允许 agent 读取其他 agent 的结论。

3. 并行而非串行
   多个 agent 同时 review，减少先入为主。

4. 只在主会话合流
   所有交叉验证、定级和取舍都在主会话完成。
```

### 7. 什么时候适合用

适合：

- 大 PR 合并前。
- 复杂模块改动。
- 涉及并发、性能、生命周期的代码。
- 音视频、JNI、硬件编解码这类高风险边界。
- 上线前做一次多角度风险扫描。

不适合：

- 改一个错别字。
- 改一行注释。
- 很小的局部重命名。
- 需求还没定清楚的早期阶段。

### 8. 面试表达版本

可以这样说：

> 对复杂代码 review，我不会只让一个 AI 泛泛检查。我会把 review 拆成多个专家视角，比如架构、并发性能、可靠性、测试和 API 设计。每个 agent 独立拿同一份 diff 做 review，互相不沟通，只输出 issue 清单。最后由主会话统一汇总、去重、按 P0/P1/P2 定级，再由我判断哪些问题真实、哪些必须修。这里我会特别看“跨专家共识”：如果 3 个以上独立专家都发现同一个问题，我会直接按 P0 风险处理，优先验证和修复。这样既能利用 AI 的并行能力，又不会让多个 agent 互相带偏。最终决策和代码修改仍然由人控制。

### 2. skill：适合沉淀固定流程

`skill` 适合把重复流程固化下来。

适合场景：

- TDD 流程。
- 代码 review 模板。
- 文档生成模板。
- 面试题总结模板。
- 项目特定的执行步骤。

例子：

```text
interview-doc-writer skill：
  先生成面试高频问答
  再生成原理详解
  再生成常见坑
  最后生成自检题
```

skill 的价值是让 AI 输出更稳定，而不是每次从零解释规则。

### 3. hooks：适合守底线

`hooks` 适合做自动化守卫。

适合场景：

- 提交前检查。
- 禁止自动 push。
- 检查是否改了敏感文件。
- 格式化或 lint。
- 防止危险命令。

例子：

```text
PreCommit hook：
  检查是否有 .env、密钥、token。
  检查是否执行了测试。
  检查是否修改了不该修改的文件。
```

hooks 不负责创造内容，而是负责守住工程边界。

### 4. memory：适合长期上下文

`memory` 适合保存稳定规则，而不是保存每次临时任务。

适合记录：

- 项目约定。
- 个人偏好。
- 常见错误。
- 技术路线。
- review 标准。

不适合记录：

- 一次性任务细节。
- 尚未确认的猜测。
- 临时 debug 过程。

## 四、Cursor 与 Claude Code 双 Agent 分工

图里的重点是：

> **两个平台分工不能混，同一个场景只用一个 Agent，避免上下文各活一半。**

### 1. Cursor 更适合什么

Cursor 更适合：

- 架构讨论。
- 贴近 IDE 的代码阅读。
- 小范围修改。
- 边写边问。
- 快速解释当前文件。
- 和编辑器强绑定的操作。

可以理解为：

```text
Cursor = 近场协作 + 代码编辑器里的 AI
```

适合的问题：

```text
解释这个函数。
这段 FFmpeg 生命周期有没有问题？
把这个小节补到当前文档。
帮我改这个类的一个函数。
```

### 2. Claude Code 更适合什么

Claude Code 更适合：

- 长任务。
- TDD。
- 多 subagent 并行。
- 大范围文档生成。
- 长时间上下文任务。
- CLI 自动化流程。

可以理解为：

```text
Claude Code = 长任务执行 + agentic coding
```

适合的问题：

```text
按这个目录生成一组硬件编解码专题文档。
帮我拆一个模块的 TDD 实现计划。
并行 review 这几个子系统。
长期维护一个任务清单并逐步推进。
```

### 3. 平台切换是阶段选择，不是随手切

不要同一个任务一会儿让 Cursor 改，一会儿让 Claude Code 改。这样容易出现：

- 上下文丢失。
- 两边都不知道对方改了什么。
- 决策分散。
- 文件冲突。
- review 成本变高。

更好的方式：

```text
讨论和小改：Cursor
长任务执行：Claude Code
最终 review 和合并：人
```

如果要切换平台，应该先做交接：

```text
当前目标：
已完成：
未完成：
关键决策：
不能改的文件：
下一步：
```

## 五、五类任务应该怎么分工

### 1. 长任务编码

推荐：

```text
Claude Code 主导
人定 spec / plan / review
必要时用 subagent 并行
```

原因：

- 长任务需要持续上下文。
- 需要分阶段执行。
- 适合用 Todo、subagent、memory 管理。

### 2. 架构 / 方案讨论

推荐：

```text
Cursor 或 Claude Code 都可以，但同一阶段只选一个。
人主导判断，AI 提供方案。
```

更适合 Cursor 的情况：

- 需要结合当前打开文件。
- 需要边看代码边问。
- 讨论后马上做小范围修改。

更适合 Claude Code 的情况：

- 讨论会进入长任务。
- 需要后续让 agent 持续执行。

### 3. 代码 review

推荐：

```text
AI 先 review，人最终 review。
```

AI 可以负责：

- 找明显 bug。
- 找遗漏测试。
- 找异常路径。
- 找资源释放问题。
- 找代码风格不一致。

人必须负责：

- 判断问题是否真实。
- 判断是否符合业务目标。
- 决定是否修改。

### 4. 并行批量任务

推荐：

```text
Claude Code + subagent
```

适合：

- 多篇文档并行生成。
- 多模块并行分析。
- 多方案并行比较。

注意：

- 不要让多个 subagent 写同一个文件。
- 最终由主 Agent 或人统一合并风格。

### 5. 快问快答

推荐：

```text
Cursor
```

适合：

- 某个 API 是什么。
- 某段代码什么意思。
- 这个术语怎么理解。
- 当前文档补一句说明。

## 六、面试表达版本

如果面试官问“你怎么使用 AI Coding”，可以这样回答：

> 我不会把 AI 当成自动写代码的黑盒，而是把它当成一个执行能力很强的协作者。我的分工原则是：人负责方向、约束、关键决策和最终 review，AI 负责扩写、测试、review 辅助和重复性执行。
>
> 实际使用时，我会先写 spec，把目标、边界、不能改的接口、性能要求说清楚；然后让 AI 出 plan，把任务拆小；执行过程中，适合并行的任务会交给 subagent，重复流程会沉淀成 skill，安全边界用 hooks 兜住，长期项目规则用 memory 记录。
>
> 工具分工上，Cursor 更适合贴着 IDE 做架构讨论、小范围修改和快速问答；Claude Code 更适合长任务、TDD、批量文档和多 subagent 并行。我不会在同一个场景里随意混用两个 Agent，否则上下文容易各活一半。平台切换时我会先做任务交接，说明已完成、未完成、关键决策和不能改的范围。
>
> 所以我的核心观点是：AI 提高的是执行效率，不替代工程判断。最终代码质量、架构边界和线上风险还是由工程师负责。

## 七、速记关键词

- 人负责：方向、边界、决策、兜底、验收。
- AI 负责：扩写、测试、review 辅助、记忆、执行。
- 协作通道：`spec -> plan -> memory -> commit`。
- `subagent`：并行任务、独立上下文、长任务拆分。
- `skill`：沉淀固定流程，让输出稳定。
- `hooks`：守底线，防危险操作。
- `memory`：记录长期项目规则和偏好。
- Cursor：IDE 内近场协作，小范围修改，快速问答。
- Claude Code：长任务、TDD、批量生成、多 agent 并行。
- 不要混用：同一场景只用一个 Agent，切换平台要做交接。
- 最重要：**AI 是执行者，人是负责人。**
