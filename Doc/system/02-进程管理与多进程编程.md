## 📌 第一部分：面试速记（考前 12 分钟扫一遍）

### 一句话核心

> **进程是操作系统资源分配的基本单位，拥有独立的虚拟地址空间；`fork` 通过写时复制（COW）复制出一个几乎一样的子进程并返回两次，`exec` 把当前进程的内存映像整个换成新程序，`wait/waitpid` 负责回收子进程残骸——「fork + exec + wait」就是 Linux 上一切「跑起另一个程序并管好它生死」的基石。**

### 面试官常问问题 + 标准口语化回答

---

#### 开场题：进程和线程到底有什么本质区别？

**🗣️ 面试标准回答：**

> "一句话：**进程是资源分配单位，线程是 CPU 调度单位**。
>
> 最本质的差别在**地址空间**：每个进程有自己独立的虚拟地址空间，A 进程的指针在 B 进程里毫无意义，物理上彼此隔离；同一进程里的多个线程**共享**同一份地址空间（共享代码段、数据段、堆，各自只有独立的栈和寄存器）。
>
> 但在 Linux 内核眼里其实很统一——**进程和线程都是 `task_struct`**，区别只是 `clone` 时共享了多少东西：`fork` 几乎什么都不共享（写时复制），创建线程的 `clone` 则带上 `CLONE_VM | CLONE_FILES | CLONE_FS` 这些标志共享地址空间和文件表。所以 Linux 里『线程』本质是『共享了地址空间的轻量级进程』，调度的最小单位是这个 task。"

**👨‍💻 面试官追问：**

> Q: 那为什么物联网/智能硬件项目里反而常用多进程，而不是图省事全用多线程？
> A: 核心是**隔离性换稳定性**。智能硬件 7×24 跑，最怕一个模块的野指针/段错误把整个程序拖崩。多进程下采集子进程崩了，主进程还活着、能监控到子进程退出并自动把它拉起来；多线程里任何一个线程段错误，整个进程直接挂。再加上多进程权限可以分别降权、内存泄漏限定在单个进程内，所以网关类程序常用『主进程 + 若干职责子进程』架构。

#### 必考题：fork() 之后会发生什么？为什么说它「返回两次」？

**考察意图：** 这是多进程的命根子，答不清楚后面全白搭。

**🗣️ 面试标准回答：**

> "`fork` 调用一次、返回两次：在**父进程里返回子进程的 PID（大于 0）**，在**新创建的子进程里返回 0**，失败返回 -1。之所以『返回两次』，是因为 `fork` 内部把父进程整个复制出一个子进程，复制完成后两个进程都从 `fork` 的返回点继续往下跑，只是拿到的返回值不同——我们正是靠这个返回值写 `if (childPid == 0) { 子进程逻辑 } else { 父进程逻辑 }`。
>
> 子进程几乎复制了父进程的一切：地址空间内容、打开的文件描述符、信号处理设置、当前工作目录。但**不是物理拷贝**，现代 Linux 用**写时复制（Copy-On-Write）**：父子一开始共享同一批物理页，页表标记为只读，谁先写哪一页才触发缺页异常、内核才真正复制那一页。所以 `fork` 很轻，不会因为父进程占了 1GB 内存就真的拷 1GB。"

**👨‍💻 面试官追问：**

> Q: 那 `fork` 之后子进程拿到的文件描述符，和父进程是什么关系？
> A: 描述符的**数值被复制**，但父子的同名 fd 指向**同一个内核打开文件表项（同一个 file struct）**，所以共享同一个读写偏移量。父子都写同一个文件且不加同步，偏移会互相影响；这也是为什么 `fork` 前一般要 `fflush`，否则 stdio 用户态缓冲区会被复制进子进程、最后双双 flush 导致内容重复。

#### 高频题（陷阱）：这段代码会打印几次 "hello"？

**🗣️ 面试标准回答：**

> "经典陷阱题，关键看 `fork` 的个数和缓冲区。
>
> - **`n` 个连续 `fork()`** 会产生 **2ⁿ 个进程**（每个现有进程都一分为二）。`fork(); fork(); fork();` 之后共 8 个进程，循环体后面的语句执行 8 次。
> - 如果题目里是 `printf("hello")` **不带 `\n`** 且输出重定向到文件（全缓冲），那么 `fork` 时用户态缓冲里的 "hello" 还没刷出去，会被连同缓冲区一起复制给子进程，最终打印次数会**翻倍**——这是面试最爱埋的坑。带 `\n` 且输出到终端时是行缓冲，一般不会翻倍。
>
> 答这类题先数进程数（2ⁿ），再看有没有 stdio 缓冲被复制的陷阱。"

#### 必考题：什么是僵尸进程？什么是孤儿进程？怎么避免？

**🗣️ 面试标准回答：**

> "两个都是子进程退出后的状态，但完全不同：
>
> - **僵尸进程（Zombie，状态 Z）**：子进程已经退出了，但父进程**还没调用 `wait/waitpid` 回收它**。内核必须保留这个子进程的退出码、PID 等少量信息，等父进程来取，所以它变成一具『尸体』占着一个 PID 表项。危害是**耗尽 PID**——系统 PID 是有限的，僵尸堆多了会 fork 不出新进程。注意：`kill` 杀不掉僵尸，因为它已经死了，解决办法是让父进程去 `wait`，或者父进程先退出。
> - **孤儿进程（Orphan）**：父进程先于子进程退出，子进程没了爹。这个**没危害**，内核会让 `init`（PID 1，现代系统是 systemd）自动『收养』它，由 init 负责将来给它收尸。daemon 守护进程正是利用这一点。
>
> **避免僵尸的三种标准做法**：① 父进程用 `wait/waitpid` 主动回收；② 注册 `SIGCHLD` 信号处理函数，子进程一退出就在处理函数里 `waitpid(-1, ..., WNOHANG)` 循环收尸；③ 如果根本不关心子进程退出码，可以 `signal(SIGCHLD, SIG_IGN)` 显式忽略，内核就会自动回收不留僵尸。"

**👨‍💻 面试官追问：**

> Q: 为什么 `SIGCHLD` 处理函数里要用 `while` 循环加 `WNOHANG`，而不是只 `waitpid` 一次？
> A: 因为信号会**合并**——多个子进程几乎同时退出，可能只递达一次 `SIGCHLD`。如果只 `waitpid` 一次，就只收了一个，剩下的全变僵尸。所以惯用法是 `while (waitpid(-1, &status, WNOHANG) > 0);` 一次性把所有已退出的子进程全收掉，`WNOHANG` 保证没有更多可收时立即返回不阻塞。

---

**📝 三种避免僵尸的代码示例：**

**方法一：父进程阻塞式 `wait/waitpid`（最简单，适合子进程会很快退出的场景）**

```c
#include <sys/wait.h>
#include <unistd.h>
#include <stdio.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        // 子进程：干完活就退
        printf("child working...\n");
        _exit(42);   // 退出码 42
    }

    // 父进程：阻塞等子进程结束
    int status;
    waitpid(pid, &status, 0);   // 阻塞；换成 wait(&status) 也行，等任意一个子进程

    if (WIFEXITED(status))
        printf("child exited with code %d\n", WEXITSTATUS(status));
    // waitpid 返回后，子进程的僵尸残骸被内核回收，不再占 PID
    return 0;
}
```

> ⚠️ 缺点：父进程**卡在 `waitpid` 上什么都干不了**，不适合要同时处理多个子进程或主循环有自己活的场景。

**方法二：`SIGCHLD` 异步回收（最常用，父进程不阻塞）**

```c
#include <signal.h>
#include <sys/wait.h>
#include <unistd.h>
#include <errno.h>
#include <stdio.h>

// 信号处理函数：只调 async-signal-safe 的函数
static void sigchld_handler(int sig) {
    (void)sig;
    int saved_errno = errno;   // 保存 errno，避免干扰主流程
    // ★ 关键：while + WNOHANG，一次性收完所有已退出的子进程
    while (waitpid(-1, NULL, WNOHANG) > 0) {
        // waitpid(-1, ...): 等任意子进程
        // WNOHANG: 没有已退出的子进程就立刻返回 0，不阻塞
    }
    errno = saved_errno;
}

int main(void) {
    struct sigaction sa;
    sa.sa_handler = sigchld_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART | SA_NOCLDSTOP;  // SA_NOCLDSTOP: 子进程被 STOP 时不触发 SIGCHLD
    sigaction(SIGCHLD, &sa, NULL);

    // 主循环：正常干自己的活，子进程退出由信号处理函数自动收尸
    for (int i = 0; i < 10; i++) {
        if (fork() == 0) {
            sleep(i);       // 模拟不同子进程不同耗时
            _exit(0);
        }
    }
    // 主进程继续干别的事...
    sleep(15);   // 等所有子进程退完
    return 0;
}
```

> 🤔 **为什么必须用 `while` 循环？** 假设同时 fork 了 5 个子进程，它们几乎同时退出。信号是**不排队的**——内核发现"有子进程退出"这个事件发生，就给父进程递达**一次** `SIGCHLD`。如果只调一次 `waitpid`，只收了第一个退出的，剩下 4 个无人认领 → 变僵尸。`while` + `WNOHANG` 保证把当时所有已退出的全部收掉。

**方法三：`SIG_IGN` 显式忽略（最省事，不关心退出码时用）**

```c
#include <signal.h>
#include <unistd.h>

int main(void) {
    signal(SIGCHLD, SIG_IGN);   // 告诉内核：我不关心子进程怎么退的，你自己处理

    for (int i = 0; i < 10; i++) {
        if (fork() == 0) {
            sleep(1);
            _exit(0);
        }
    }
    // 子进程退出后内核自动回收，不留僵尸，父进程甚至不需要 wait
    sleep(5);
    return 0;
}
```

> ⚠️ 注意：`signal(SIGCHLD, SIG_IGN)` 的自动回收行为是 **POSIX.1-2001 标准规定的**，Linux 上可靠，但某些古老 Unix 可能不支持。生产代码建议用 `sigaction` + `SA_NOCLDWAIT` 标志替代，语义更明确：
> ```c
> struct sigaction sa;
> sa.sa_handler = SIG_DFL;          // SIG_DFL 配合 SA_NOCLDWAIT 即自动回收
> sigemptyset(&sa.sa_mask);
> sa.sa_flags = SA_NOCLDWAIT;
> sigaction(SIGCHLD, &sa, NULL);
> ```

**三种方法怎么选？**

| 场景 | 推荐方法 |
|------|---------|
| 只 fork 一个子进程，要等它干完再继续 | 方法一（阻塞 wait） |
| 主进程有自己的活要干，同时管理多个子进程 | 方法二（SIGCHLD + while） |
| 完全不关心子进程退出码，纯粹 fire-and-forget | 方法三（SIG_IGN） |
| 智能硬件/网关：子进程崩了要**立刻知道并重启** | 方法二，在 while 里记录退出码，主循环检查后决策 |

#### 高频题：怎么创建一个守护进程（daemon）？为什么要 fork 两次？

**🗣️ 面试标准回答：**

> "守护进程是脱离终端、后台长跑的进程（智能硬件的常驻服务就是它）。标准创建步骤：
>
> 1. **`fork` 一次，父进程退出**：让子进程变成孤儿被 init 收养，同时保证后面调用 `setsid` 时自己不是进程组组长。
> 2. **`setsid()`**：新建一个会话，子进程成为新会话和新进程组的组长，**彻底脱离原来的控制终端**——这样终端关闭时不会再收到 SIGHUP 而被杀。
> 3. **再 `fork` 一次（关键）**：第二次 fork 出的孙子进程不再是会话组长，**永远无法重新获得控制终端**，更安全。这就是『fork 两次』的原因。
> 4. **`chdir("/")`**：把工作目录切到根目录，避免占用某个挂载点导致它无法卸载。
> 5. **`umask(0)`**：重设文件权限掩码，让 daemon 创建文件的权限可控。
> 6. **关闭/重定向 stdin、stdout、stderr 到 `/dev/null`**：守护进程没有终端，留着这三个 fd 容易出问题。
>
#### 必考题：signal 和 sigaction 有什么区别？信号处理函数里能干什么？

**🗣️ 面试标准回答：**

> "**`signal` 老、`sigaction` 新，工程上应该用 `sigaction`**。`signal` 的行为在不同 Unix 实现上不一致（有的处理一次后会重置回默认动作），而且不能精细控制；`sigaction` 通过 `struct sigaction` 能指定 `sa_flags`（比如 `SA_RESTART` 让被中断的系统调用自动重启、`SA_NOCLDWAIT` 自动回收子进程），还能在执行处理函数时用 `sa_mask` 屏蔽其他信号，语义明确、可移植。
>
> **信号处理函数里只能调用 async-signal-safe（异步信号安全）的函数**。因为信号是异步打断主流程的，如果主流程正卡在 `malloc` 中途持有内部锁，处理函数里又调 `malloc` 就会死锁。安全的只有 `write`、`_exit`、`signal` 等一小撮；`printf`、`malloc`、`free` 全不安全。
>
> 所以工业级惯用法是：**信号处理函数里只设一个 `volatile sig_atomic_t` 标志位（或用 `write` 写一字节到自管道），主循环再去检查标志做真正的处理**。这就是所谓 self-pipe trick / 标志位模式，把异步信号转成同步事件处理，既安全又好测。"

**👨‍💻 面试官追问：**

> Q: 说几个必须记住的信号，以及哪些杀不掉？
> A: `SIGKILL`(9) 和 `SIGSTOP` 这两个**不能被捕获、不能被忽略、不能被阻塞**，是终极手段；`SIGTERM`(15) 是『礼貌地请你退出』，可被捕获用来做优雅关闭（清理资源再退）；`SIGINT`(2) 是 Ctrl+C；`SIGCHLD` 是子进程状态变化；`SIGSEGV` 段错误；`SIGPIPE` 写一个对端已关闭的管道/socket——这个在网络程序里必须处理或忽略，否则进程会被默认动作直接干掉。

#### 高频题：进程的 D 状态是什么？为什么 kill 不掉？

**🗣️ 面试标准回答：**

> "`ps`/`top` 里看到的进程状态主要有：**R**（运行/就绪）、**S**（可中断睡眠，等事件，能被信号唤醒）、**D**（不可中断睡眠）、**Z**（僵尸）、**T**（被信号 STOP 暂停或被调试器停住）。
>
> **D 状态（Uninterruptible Sleep）**是面试常考点：进程正卡在某个**不能被信号打断**的内核操作里，最典型是**等待磁盘/底层 I/O 完成**。这时候连 `SIGKILL` 都送不进去——内核为了保证 I/O 操作的一致性，故意屏蔽了信号响应，必须等 I/O 返回。所以现象就是『一个进程 `kill -9` 都杀不掉，CPU 还不高』，往往说明底层硬件/存储/NFS 卡住了。智能硬件上如果 Flash 或外设驱动有问题，就容易出现进程卡在 D 状态。"

## 二、原理详解

### 1. 进程的虚拟地址空间布局

每个进程都以为自己独占整个内存，这套幻觉由虚拟地址空间提供（物理映射的细节见 [[03-Linux内存管理机制]]）。一个典型的 64 位进程地址空间从低到高：

```text
  高地址 ┌────────────────────────┐
         │   内核空间（用户态不可见）  │
         ├────────────────────────┤ ← 栈顶
         │   栈 stack（向下增长）↓    │  局部变量、函数调用帧、返回地址
         │          ...           │
         │   （空洞）               │
         │          ...           │
         │   mmap 区（动态库/匿名映射）│  共享库、mmap 的文件、大块 malloc
         │          ...           │
         │   堆 heap（向上增长）↑     │  malloc/new 分配，brk/sbrk 调整边界
         ├────────────────────────┤
         │   BSS 段（未初始化全局）    │  未初始化或初值为 0 的全局/静态变量
         ├────────────────────────┤
         │   数据段 data（已初始化）   │  初值非 0 的全局/静态变量
         ├────────────────────────┤
         │   .rodata（只读数据段）     │  字符串字面量、const 全局变量、虚函数表
         ├────────────────────────┤
         │   代码段 text（只读可执行）  │  机器指令，多进程可共享同一份物理页
  低地址 └────────────────────────┘
```

要点：**代码段只读，多个跑同一程序的进程共享同一份物理代码页**；栈和堆相向生长，中间的大片空洞留给 mmap；`fork` 出的子进程拥有一份逻辑上完全相同的布局，但物理上靠 COW 共享直到写入。

### 2. fork 与写时复制（COW）全过程

#### 2.1 先搞懂三个前置概念

在看 COW 之前，必须理解三个东西，否则图就是天书：

**① 虚拟地址 vs 物理地址**

每个进程看到的都是"假地址"（虚拟地址），比如变量 `int x` 在地址 `0x7fff1234`。CPU 真正读写内存时，要通过一张叫**页表（Page Table）**的映射表，把虚拟地址翻译成物理内存上真实的地址。不同进程的 `0x7fff1234` 映射到的物理地址完全不同——这就是"地址空间隔离"的硬件基础。

> 类比：每个进程有自己的"门牌号系统"，`0x7fff1234` 在 A 进程是 3 号楼，在 B 进程可能是 7 号楼。页表就是翻译字典。

**② 页（Page）**

内存不是按字节管理的，是按**页**——通常每页 4KB（4096 字节）。页表里的每一项对应一整个页，不是一个变量。即使你只改了页里面的 1 个字节，整个 4KB 的页都要被复制。

**③ 缺页异常（Page Fault）**

CPU 访问某个虚拟地址时，如果页表里这项标记为"不可写"但你尝试了写操作，CPU 就会触发一个硬件异常，把控制权交给内核。内核检查：这个页是不是 COW 的只读标记？是 → 复制一页新的、恢复可写、重新执行那条写指令。整个过程对用户程序完全透明。

> **🤔 为什么 COW 要用「标记只读 + 缺页异常」这套机制？**
>
> 这个问题触及了 COW 设计的精髓。要实现"写的时候才复制"，内核必须能**拦截每一次写操作**。问题是：CPU 每条指令都在疯狂读写内存，C 代码里一行 `*p = 1` 编译后只是一条 `mov` 指令，纯软件层面根本拦截不了——你不可能在每次内存写入前都调一个检查函数，那性能直接归零。
>
> 所以内核借用了硬件的力量——**MMU（Memory Management Unit，内存管理单元）**。CPU 执行**每一条**访存指令时，MMU 都会自动查页表、做权限检查，这个过程是硬件级的、零额外开销的。把页表项标记为只读后，任何写入都会被 MMU 在硬件层面当场抓包，然后硬件自动触发缺页异常，把 CPU 控制权交给内核。
>
> 换句话说：**只读标记是布在硬件通路上的"触发线"，缺页异常是唯一能在写操作发生的那个精确时刻拦截它的机制**。没有这套硬件+异常的组合，内核不可能知道"哪一页被写了、什么时候写的"。
>
> 还有一个细节常被忽略：**为什么连父进程的页也要标成只读？** fork 之前父进程明明是可写的。原因是：父子此时共享同一块物理页 A。如果只把子进程的页表标只读、父进程保持可写，那么父进程写 `counter = 1` 时根本不会触发任何异常——写操作直接穿透到物理页 A，而子进程的页表还指着同一块物理页 A，它"看到"的 `counter` 会凭空变成 1。这违背了"父子地址空间互相隔离"的根本语义。所以**两边都要暂时降级为只读**，谁先写谁触发 COW，互不干扰。

---

#### 2.2 COW 全过程，分四步走

假设父进程有一个全局变量 `int counter = 0;`，它落在物理页 A 上。

**第 0 步：fork 之前**

```
父进程视角：
  虚拟地址 0x601000 (counter)  ──页表──▶  物理页 A（内容: counter=0, 可读写）
```

只有父进程，一切正常。父进程的页表项标记为 **R+W（可读可写）**。

**第 1 步：fork 那一刻（内核做了什么）**

`fork` 系统调用进入内核后，核心动作不是复制数据，而是：

| 复制什么 | 不复制什么 |
|----------|-----------|
| ✅ 复制父进程的**页表**（所有页表项，逐条复制一份给子进程） | ❌ **不复制物理页**里的实际数据 |
| ✅ 复制 `task_struct`（PID、文件描述符表、信号表等元信息） | |
| ✅ 给子进程分配一个新的 PID | |

关键操作：内核把**父子两边的页表项全部标记为只读（Read-Only）**——哪怕这一页原来在父进程里是可写的，现在父子都变成只读了。

```
fork 刚完成：
  父进程                                    子进程
  页表                                      页表
  ┌──────────────────────┐                 ┌──────────────────────┐
  │ 0x601000 → 物理页 A   │                 │ 0x601000 → 物理页 A   │
  │           权限: 只读   │                 │           权限: 只读   │
  └──────────┬───────────┘                 └──────────┬───────────┘
             └──────────────── 物理页 A ──────────────┘
                              内容: counter = 0
                              权限: 只读（两边都是）
```

此时父子**共享同一块物理页 A**，但谁写谁炸（触发缺页异常）。

**第 2 步：没人写 → 风平浪静**

如果父子都只是**读** `counter` 的值（比如 `printf("%d", counter)`），什么都不发生。只读权限足够读操作，共享物理页完全没问题——这就是 COW 省内存的核心：读多写少的场景下，大多数页永远不会被复制。

**第 3 步：有人写了 → COW 触发**

假设父进程执行 `counter = 1;`：

```
① CPU 要写 0x601000
② 查页表：这条映射是只读的！❌
③ CPU 触发缺页异常（Page Fault），跳进内核
④ 内核检查："这是个 COW 页——只读是因为 fork 共享，不是真的只读"
⑤ 内核分配一页新的物理页 A'（4KB），把物理页 A 的内容原样复制过去
⑥ 内核把父进程的页表项更新：0x601000 → 物理页 A'，权限恢复为 可读写
⑦ 内核把子进程的页表项更新：0x601000 → 物理页 A，权限恢复为 可读写
    （因为现在只有子进程在用物理页 A 了，可以放心恢复可写）
⑧ 内核返回用户态，CPU 重新执行那条 "counter = 1" 指令——这次成功写入 A'
```

```
COW 触发后（父进程写入了 counter）：
  父进程                                    子进程
  页表                                      页表
  ┌──────────────────────┐                 ┌──────────────────────┐
  │ 0x601000 → 物理页 A'  │                 │ 0x601000 → 物理页 A   │
  │           权限: 可读写  │                 │           权限: 可读写  │
  └──────────┬───────────┘                 └──────────┬───────────┘
             │                                       │
          物理页 A'                                  物理页 A
          内容: counter = 1 ✏️                        内容: counter = 0（没变）
          （新分配的，只有父进程在用）                    （原来的页，只有子进程在用）
```

**关键结论：只复制了被写的那一页（4KB），其他几百 MB 的共享页纹丝不动。**

---

#### 2.3 为什么 COW 跟 `fork+exec` 是绝配

这是 COW 设计最精妙的地方。考虑最常见的进程创建模式：

```c
pid_t pid = fork();
if (pid == 0) {
    execlp("ls", "ls", "-l", NULL);  // 子进程马上 exec，换掉整个地址空间
}
```

- **fork 时**：父子共享所有物理页，标记只读。父进程假设占 500MB，子进程只复制了页表（约 1~2MB 的元信息），物理内存没多占。
- **exec 时**：子进程加载 `ls` 的新程序映像，内核直接把子进程的整个旧地址空间**丢弃**（页表清空，物理页引用计数减 1）。
- **结果**：父进程那 500MB 的物理页**一页也没被真正复制过**——fork 时没拷，exec 时直接扔了。

**如果没有 COW**，fork 就必须把父进程全部 500MB 物理内存实打实复制一份给子进程，然后 exec 又立刻扔掉——白白复制了 500MB。这就是为什么现代 Unix 全部用 COW，也解释了为什么有人说 `vfork`（不复制地址空间的古老变体）在 COW 出现后基本被淘汰了。

---

#### 2.4 一个具体数字例子

| | 无 COW（假设） | 有 COW（实际） |
|---|---|---|
| 父进程占用 | 500MB | 500MB |
| fork 时复制的数据量 | 500MB（全量物理复制） | ~2MB（仅页表和元信息） |
| 子进程 exec 前改了多少 | 假设改了 1MB 的栈变量 | 只复制了被改的页 ≈ 1MB |
| exec 后实际拷贝开销 | 500MB 全白复制了 | ~1MB（只有真正被写过的页） |

---

#### 2.5 面试一句话总结

> "COW 就是 fork 时只复制页表不复制物理页，把父子两边的页表都标成只读。谁先写某一页，触发缺页异常，内核才真正分配新页、复制数据、恢复可写。好处是 fork 极快、内存极省，尤其是跟 exec 搭配时——fork 完立刻 exec 的场景下，旧地址空间一页都没被真正复制过。"

### 3. fork / vfork / posix_spawn 怎么选

| 接口 | 行为 | 适用 |
|---|---|---|
| `fork` | COW 复制完整地址空间，返回两次 | 通用，最常用；要在子进程里跑一段自己的逻辑 |
| `vfork` | 不复制地址空间，子进程借用父进程空间且父进程挂起，只能紧接着 `exec` 或 `_exit` | 历史遗留，COW 出现后基本被取代，易误用 |
| `posix_spawn` | 把 `fork+exec` 封装成一个调用，内部更高效 | 只想「启动一个外部程序」、不需要在子进程里写复杂逻辑 |

记忆：**要在子进程里干自己的活 → `fork`；只是单纯启动另一个程序 → `posix_spawn` 更省心；`vfork` 了解即可、新代码别用。**

### 4. exec 家族：替换进程映像

`exec` 不创建新进程，而是把**当前进程的整个内存映像（代码、数据、堆栈）换成新程序**，PID 不变，执行成功后**不会返回**（返回了就说明失败）。

```c
// exec 家族命名规律：l=参数列表, v=参数数组, p=用 PATH 找, e=自带 environ
execl("/bin/ls", "ls", "-l", NULL);          // 列出参数
execv("/bin/ls", argv);                       // 参数用数组
execlp("ls", "ls", "-l", NULL);               // p: 在 PATH 里找 ls
execvp("ls", argv);                            // p + 数组（最常用）
execvpe("ls", argv, envp);                     // 额外指定环境变量
```

经典的 **fork + exec 模式**——父进程 `fork`，子进程里 `exec` 换成目标程序，父进程 `wait` 收尸：

```c
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>

int main(void) {
    pid_t childPid = fork();
    if (childPid < 0) {
        perror("fork");               // fork 失败
        return 1;
    }
    if (childPid == 0) {
        // 子进程：把自己换成 /bin/ls
        execlp("ls", "ls", "-l", (char *)NULL);
        perror("execlp");             // 只有 exec 失败才会执行到这里
        _exit(127);                   // 子进程失败用 _exit，不跑 atexit
    }
    // 父进程：等子进程结束并取退出码
    int exitStatus = 0;
    waitpid(childPid, &exitStatus, 0);
    if (WIFEXITED(exitStatus)) {
        printf("子进程正常退出，退出码 = %d\n", WEXITSTATUS(exitStatus));
    }
    return 0;
}
```

### 5. wait / waitpid 与状态判断宏

#### 5.1 函数签名与基本用法

```c
#include <sys/wait.h>

pid_t wait(int *status);                                    // 最简形式
pid_t waitpid(pid_t pid, int *status, int options);         // 完整控制
```

父进程靠 `wait`/`waitpid` 取回子进程退出信息，并让内核释放僵尸残骸：

```c
int exitStatus = 0;

// wait：阻塞等任意一个子进程退出
pid_t endedPid = wait(&exitStatus);

// waitpid：可指定 PID、可非阻塞
//   childPid > 0 等指定子进程；-1 等任意子进程
//   WNOHANG：没有子进程退出就立刻返回 0，不阻塞
pid_t result = waitpid(-1, &exitStatus, WNOHANG);
```

#### 5.2 `wait` vs `waitpid` 到底有什么区别？

**一句话：`wait` 是 `waitpid` 的简化特例。** `wait(&status)` 完全等价于 `waitpid(-1, &status, 0)`——"等任意子进程，阻塞，不关心 STOP/继续事件"。`waitpid` 多给了你三个维度的控制。

| | `wait` | `waitpid` |
|---|---|---|
| **指定等哪个子进程** | ❌ 不能，来谁算谁 | ✅ `pid > 0` 等特定 PID；`pid == -1` 等任意；`pid == 0` 等同进程组的；`pid < -1` 等指定进程组的 |
| **非阻塞轮询** | ❌ 不支持，永远阻塞到有子进程退出 | ✅ `WNOHANG` 标志：没有子进程退出就立刻返回 0 |
| **处理 STOP/继续** | ❌ 不支持 | ✅ `WUNTRACED`（子进程被 STOP 也返回）、`WCONTINUED`（子进程被 SIGCONT 继续也返回） |
| **本质** | `waitpid(-1, &status, 0)` 的特例 | 完整接口 |

**`pid` 参数的四种取值：**

```c
waitpid(-1, &status, 0);      // -1：等任意子进程 ← 等同于 wait
waitpid(1234, &status, 0);    // >0：只等 PID=1234 的那个子进程
waitpid(0, &status, 0);       //  0：等和调用进程同进程组的所有子进程
waitpid(-5678, &status, 0);   // <-1：等进程组 ID = 5678 的所有子进程（取绝对值）
```

**`options` 常用标志（可按位或组合）：**

```c
waitpid(-1, &status, WNOHANG);            // 非阻塞轮询
waitpid(-1, &status, WUNTRACED);          // 子进程被 STOP（如 SIGSTOP）也返回
waitpid(-1, &status, WNOHANG | WUNTRACED | WCONTINUED);  // 全面监控
```

#### 5.3 什么时候必须用 `waitpid` 而不是 `wait`？

| 场景 | 为什么必须 `waitpid` |
|------|---------------------|
| **信号处理函数里** | 只能用 `waitpid` + `WNOHANG`——处理函数里绝对不能阻塞 |
| **管理多个子进程，需要等特定的那一个** | `wait` 不知道给你返回的是哪个子进程 |
| **有多个子进程，不想漏收** | `wait` 每次只收一个，刚收完一个返回，另一个也退出了但 `wait` 不知道——你已经退出等待了；`waitpid(-1, ..., WNOHANG)` 配合 `while` 循环能全收 |
| **主循环每帧轮询"子进程退了吗"但不卡住** | `WNOHANG` 是 `wait` 没有的 |
| **需要知道子进程是退出还是被 STOP 了**（调试器场景） | `WUNTRACED` / `WCONTINUED` 必须通过 `waitpid` 的 options 传 |

> 💡 记忆技巧：**面试速记部分提到的三种避免僵尸的方法，方法二（SIGCHLD 异步回收）只能在信号处理函数里用 `waitpid` + `WNOHANG`，换成 `wait` 就炸了——因为 `wait` 会阻塞，信号处理函数一阻塞，整个进程直接卡死。**

#### 5.4 状态判断宏

`exitStatus` 是个被编码的整数，必须用宏解读，不能直接当退出码：

| 宏 | 含义 |
|---|---|
| `WIFEXITED(status)` | 子进程是否正常 `exit` 退出 |
| `WEXITSTATUS(status)` | 取正常退出的退出码（仅在 WIFEXITED 为真时有效） |
| `WIFSIGNALED(status)` | 是否被信号杀死 |
| `WTERMSIG(status)` | 取杀死它的信号编号 |
| `WIFSTOPPED(status)` | 是否被信号暂停（配合 WUNTRACED / 调试） |

### 6. 用 SIGCHLD 异步回收子进程（避免僵尸的标准写法）

主进程不可能一直阻塞在 `wait` 上，所以惯用法是注册 `SIGCHLD` 处理函数，子进程一退出就异步收尸：

```c
#include <signal.h>
#include <sys/wait.h>
#include <unistd.h>
#include <errno.h>

// 信号处理函数：只调用 async-signal-safe 的 waitpid，循环收掉所有已退出的子进程
static void onChildExit(int signalNumber) {
    (void)signalNumber;
    int savedErrno = errno;           // 处理函数应保存/恢复 errno
    while (waitpid(-1, NULL, WNOHANG) > 0) {
        // 循环是因为多个 SIGCHLD 可能被合并成一次递达
    }
    errno = savedErrno;
}

int main(void) {
    struct sigaction action;
    action.sa_handler = onChildExit;
    sigemptyset(&action.sa_mask);
    action.sa_flags = SA_RESTART | SA_NOCLDSTOP;  // 自动重启被打断的系统调用
    sigaction(SIGCHLD, &action, NULL);
    // ... 主循环：fork 子进程、干自己的活，僵尸由信号处理函数自动清理 ...
    return 0;
}
```

### 7. 信号处理：只设标志、主循环处理的惯用法

因为处理函数里能做的事极少（只能调 async-signal-safe 函数），工业级做法是**信号里只翻一个标志，真正的逻辑放回主循环**（比如收到 `SIGTERM` 后优雅退出）：

```c
#include <signal.h>

static volatile sig_atomic_t shouldStop = 0;   // 唯一能在处理函数里安全改的类型

static void onTerm(int signalNumber) {
    (void)signalNumber;
    shouldStop = 1;                  // 只设标志，不做任何复杂操作
}

int main(void) {
    signal(SIGTERM, onTerm);
    signal(SIGINT, onTerm);
    while (!shouldStop) {
        // ... 正常工作：处理一帧、收一条消息 ...
    }
    // 跳出循环后在这里安全地清理资源、刷盘、关闭连接，再退出
    return 0;
}
```

### 8. 进程退出：exit / _exit / return / atexit

要理解这几个退出方式的区别，必须先搞懂两个前置概念——**stdio 缓冲**和 **atexit 回调**。它们正是 `fork` 陷阱的根源。

---

#### 8.1 前置概念一：stdio 缓冲是什么？

你写 `printf("hello")`，数据并不是立刻写到屏幕或文件的——它先存在一块**用户态内存缓冲区**里，满足某个条件后才真正通过 `write()` 系统调用交给内核。这套缓冲机制是 C 标准库（stdio）在用户态做的，**和内核无关**。

**为什么要缓冲？** 因为系统调用很贵。`write()` 要从用户态陷进内核态，内核再把数据拷到自己的缓冲区、最终写到磁盘或终端。如果每 `printf` 一个字符就调一次 `write`，性能直接崩。所以 stdio 先把数据攒在用户态缓冲区，攒够了再一次 `write`，用批量换效率。

**三种缓冲模式**（stdio 自动根据输出目标选择）：

| 缓冲模式 | 什么时候刷新（把缓冲数据真正写出去） | 典型场景 |
|----------|-------------------------------------|---------|
| **全缓冲（fully buffered）** | 缓冲区满了（通常 4096 或 8192 字节）才 `write` | 输出重定向到普通文件：`./a.out > file.txt` |
| **行缓冲（line buffered）** | 遇到 `\n` 换行符就 `write`，或者缓冲区满了 | 输出到终端（屏幕） |
| **无缓冲（unbuffered）** | 每写一个字符立刻 `write` | `stderr` 默认无缓冲，保证错误信息立刻可见 |

**关键实验**——同一段代码，输出到终端 vs 重定向到文件，行为完全不同：

```c
// demo.c
#include <stdio.h>
#include <unistd.h>

int main(void) {
    printf("hello");      // 注意：没有 \n
    fork();               // fork 时，缓冲区里的 "hello" 还没写出去！
    return 0;
}
```

```bash
$ ./a.out              # 输出到终端（行缓冲）→ "hello" 里没 \n，也不刷新 → 被 fork 复制！
hellohello             # 父子各刷一次，打印两次！

$ ./a.out > file.txt   # 重定向到文件（全缓冲）→ 同样被复制
$ cat file.txt
hellohello             # 也是两次！
```

```c
// 加上 \n 的版本
printf("hello\n");     // 有 \n + 输出到终端 → 行缓冲，遇到 \n 立刻刷
fork();                // fork 时缓冲区已经空了
// 结果：只打印一次 hello
```

> **核心认知**：`printf` 写到的是 **FILE * 结构体里的用户态缓冲区**，不是内核。`fork` 会完整复制进程的地址空间，**包括这个还没刷出去的缓冲区**。子进程拿到一份完全相同的缓冲区副本，里面也躺着同样的 "hello" 数据。之后不管是父进程还是子进程调用 `exit` 或 `return`，都会各自把缓冲区刷一遍——同样的内容输出两次。

---

#### 8.2 前置概念二：atexit 是什么？

`atexit` 是 **"进程退出前最后要做的事"** 的注册机制。你可以注册多个回调函数，进程正常退出时，C 运行时会**按注册的逆序（后注册先执行）**逐个调用它们。

```c
#include <stdio.h>
#include <stdlib.h>    // atexit, exit

void cleanup_db(void)  { printf("关闭数据库连接\n"); }
void cleanup_log(void) { printf("关闭日志文件\n");   }

int main(void) {
    atexit(cleanup_db);   // 先注册
    atexit(cleanup_log);  // 后注册

    // ... 程序正常跑 ...

    return 0;   // 或 exit(0)
    // 退出时自动执行：
    //   cleanup_log()  ← 后注册的先跑
    //   cleanup_db()   ← 先注册的后跑
}
// 输出：
// 关闭日志文件
// 关闭数据库连接
```

**atexit 的典型用途**：关闭数据库连接、写日志尾部、删除临时文件、释放跨函数的全局资源——这些清理动作不适合放在某个具体函数的末尾，因为进程可能在多个地方退出。

**关键点：什么时候 atexit 不会被调用？**

| 退出方式 | atexit 回调执行吗？ | stdio 缓冲刷新吗？ |
|----------|:---:|:---:|
| `return`（从 main） | ✅ 是 | ✅ 是 |
| `exit(n)` | ✅ 是 | ✅ 是 |
| `_exit(n)` / `_Exit(n)` | ❌ 否 | ❌ 否 |
| 被信号杀死（SIGKILL、段错误等） | ❌ 否 | ❌ 否 |
| `abort()` | ❌ 否 | ❌ 否 |

#### 8.3 fork 陷阱：为什么子进程必须用 `_exit` 而不是 `exit`

现在把 8.1 和 8.2 组合起来，就自然得出这个面试高频坑：

**陷阱一：stdio 缓冲被复制，导致输出重复**

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>

int main(void) {
    printf("正在初始化...");         // ① 输出到终端，没有 \n → 留在 stdio 缓冲区
    // 此时缓冲区内容：["正在初始化..."]

    pid_t pid = fork();              // ② fork！子进程复制了整个地址空间
                                     //    包括 stdio 缓冲区里的 "正在初始化..."

    if (pid == 0) {
        // 子进程
        printf("子进程工作中\n");
        exit(0);                     // ③ exit → 刷新 stdio 缓冲！
    }                              //    输出: "正在初始化...子进程工作中"
    // exit 还会跑父进程注册的 atexit（见陷阱二）

    // 父进程
    printf("父进程工作中\n");
    return 0;                        // ④ return → 也刷新 stdio 缓冲！
}                                    //    输出: "正在初始化...父进程工作中"

// 实际屏幕输出（父子各自刷了自己的缓冲区副本）：
//   正在初始化...子进程工作中
//   正在初始化...父进程工作中
//         ↑ 这行重复出现了！
```

修正方式：**fork 前 `fflush(NULL)` 把 stdio 缓冲清空**，或者子进程用 `_exit` 退出（不刷新缓冲、不跑 atexit）。

```c
printf("正在初始化...");
fflush(NULL);    // ★ fork 前强制刷新所有 stdio 缓冲区
fork();
// 此时缓冲区是空的，子进程不会复制到残留数据
```

**陷阱二：atexit 回调被复制，导致清理动作重复执行**

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>

static int *global_buf = NULL;

void cleanup(void) {
    printf("[清理] 释放 global_buf\n");
    free(global_buf);                    // 第二次 free → 双重释放，未定义行为！
    global_buf = NULL;
}

int main(void) {
    global_buf = malloc(1024 * 1024);    // 分配 1MB
    atexit(cleanup);                     // 注册清理回调

    pid_t pid = fork();                  // fork 把 atexit 注册表也复制了！

    if (pid == 0) {
        // 子进程：继承了父进程的 atexit 回调注册表
        // 也继承了 global_buf 指针（指向共享的物理内存...COW 后会指向副本）
        printf("子进程退出\n");
        exit(0);                         // ★ 触发 cleanup()，free 子进程的 global_buf 副本
    }

    printf("父进程退出\n");
    return 0;                            // ★ 也触发 cleanup()，free 父进程的 global_buf
    // 两个进程各自跑了一遍 cleanup()
    // 如果 cleanup 里是 close(fd)、删除临时文件等有副作用操作
    // → 资源被关两次、文件被删两次
}
```

修正方式：**子进程退出一律用 `_exit`**，只让父进程去做清理。

```c
if (pid == 0) {
    // 子进程：要退出？用 _exit，不跑 atexit、不刷缓冲
    _exit(0);    // 干净利落，什么清理都不做
}
```

> **为什么子进程不该"帮"父进程做清理？**
>
> atexit 回调是父进程注册的，回调里的资源（fd、内存、临时文件）**属于父进程**。子进程 fork 后虽然拿到了这些资源的副本（fd 表、内存地址空间），但这是 COW 的"假共享"——一旦子进程 free 掉内存、close 掉 fd，父进程那边的对应资源还在用，不会受影响（因为 COW 已经隔离了）。
>
> 真正有破坏性的是那些**不通过 fd 管理的副作用**：比如删除临时文件（`unlink`），子进程跑 atexit 删了，父进程的文件就没了——因为文件系统只有一个，父子共享的是**同一个文件名**，不是同一个 fd 副本。
>
> 所以铁律是：**子进程异常/完成路径一律用 `_exit`，清理工作留给父进程的 `exit` 或 `return`。**

#### 8.4 总结对照表

| 方式 | 跑 atexit 回调 | 刷新 stdio 缓冲 | 调 `_exit` 系统调用 | 典型用途 |
|---|---|---|---|---|
| `return`（从 main） | 是 | 是 | 是（由 C 运行时最后调用） | 正常结束 main |
| `exit(n)` | 是 | 是 | 是（在回调全部跑完后） | 任意位置正常退出，会做清理 |
| `_exit(n)` / `_Exit(n)` | **否** | **否** | 是（直接陷入内核） | fork 后子进程退出、exec 失败后的错误路径 |
| `abort()` | **否** | 否（可能刷也可能不刷，取决于实现） | 否（产生 SIGABRT + core dump） | 程序逻辑严重错误，生成 core dump 用于调试 |
| 被信号杀死、段错误 | **否** | **否** | 否（内核直接终止进程） | 不在程序控制范围内 |

**面试一句话版**：

> "`exit` 是正常退出——先逆序跑完所有 `atexit` 回调、把 stdio 缓冲刷干净，再调 `_exit` 系统调用进内核。`_exit` 是硬退出——跳过这一切直接进内核。fork 出的子进程如果用 `exit` 退出，会重复跑父进程的 atexit 回调、刷父亲遗留在 stdio 缓冲里的数据，所以子进程退出一律用 `_exit`。"

### 9. 守护进程 daemon 化代码骨架

把前面速记里的步骤落成代码（对照看为什么 fork 两次、为什么 setsid）：

```c
#include <unistd.h>
#include <stdlib.h>
#include <fcntl.h>
#include <sys/stat.h>

void becomeDaemon(void) {
    if (fork() > 0) exit(0);          // ① 第一次 fork，父进程退出 → 子进程被 init 收养
    setsid();                         // ② 新建会话，脱离控制终端，成为会话组长
    if (fork() > 0) exit(0);          // ③ 第二次 fork，孙子进程不再是会话组长，永不再获取终端
    umask(0);                         // ④ 重设权限掩码
    chdir("/");                       // ⑤ 切到根目录，不占用挂载点
    // ⑥ 关闭并把标准三件套重定向到 /dev/null
    int nullFd = open("/dev/null", O_RDWR);
    dup2(nullFd, STDIN_FILENO);
    dup2(nullFd, STDOUT_FILENO);
    dup2(nullFd, STDERR_FILENO);
    if (nullFd > STDERR_FILENO) close(nullFd);
}
```

## 三、智能硬件实战：主进程 + 采集子进程，崩溃自动拉起

这正是 [[01-Linux系统编程全景导读]] 里那个网关程序的核心骨架——主进程当『看门狗』，子进程负责采集；子进程崩了，主进程通过 `waitpid` 发现并立刻重新 `fork` 拉起：

```c
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>

static pid_t spawnCollector(void) {
    pid_t childPid = fork();
    if (childPid == 0) {
        // 子进程：采集逻辑（读传感器 / 摄像头），异常就退出让父进程拉起
        runCollectorLoop();           // 假设的采集主循环
        _exit(0);
    }
    return childPid;                  // 父进程拿到子进程 PID
}

int main(void) {
    pid_t collectorPid = spawnCollector();
    for (;;) {
        int exitStatus = 0;
        pid_t endedPid = waitpid(collectorPid, &exitStatus, 0);  // 阻塞等子进程
        if (endedPid == collectorPid) {
            // 子进程没了（正常退出或被信号杀死），记录后立即重启
            if (WIFSIGNALED(exitStatus)) {
                fprintf(stderr, "采集进程被信号 %d 杀死，重启\n", WTERMSIG(exitStatus));
            }
            sleep(1);                 // 退避，避免崩溃风暴把 CPU 打满
            collectorPid = spawnCollector();
        }
    }
    return 0;
}
```

> 真实工程里子进程和主进程还要通过**共享内存传图像帧**（零拷贝）、用**信号量/管道做同步**——这些 IPC 细节见 [[05-进程间通信IPC]]，进程内多线程采集与调度见 [[04-多线程与Linux调度]]。

## 四、常见坑与面试加分点

| 坑 | 说明 |
|---|---|
| `fork` 前不 `fflush` | 用户态 stdio 缓冲被复制进子进程，父子各刷一次导致输出重复 |
| 子进程异常退出用 `exit` | 会跑 atexit + 刷父进程缓冲，应该用 `_exit` |
| 不回收子进程 | 堆积僵尸（Z 状态）占满 PID，最终 fork 不出新进程 |
| `SIGCHLD` 处理只 `waitpid` 一次 | 信号会合并，必须 `while + WNOHANG` 循环收 |
| 信号处理函数里调 `printf`/`malloc` | 非 async-signal-safe，可能死锁，只能调 `write`/`_exit` 这类 |
| 网络程序不处理 `SIGPIPE` | 对端断开后写 socket，默认动作直接杀进程 |
| 以为 `kill -9` 万能 | D 状态（等 I/O）和僵尸都杀不掉，要找根因 |
| `fork` 后忘了文件偏移共享 | 父子共享同一 file 表项偏移，并发写会互相串 |
| 用 `vfork` 写复杂逻辑 | 共享父进程空间且父进程挂起，只能紧接 `exec`/`_exit`，否则未定义行为 |

**加分一句（智能硬件稳定性）：**

> "我们网关程序就是『主进程 watchdog + 采集子进程』架构：用多进程把采集模块的崩溃隔离在子进程里，主进程 `waitpid` 监控、崩溃后退避重启，并用 `SIGCHLD` + `WNOHANG` 循环收尸防僵尸。这样单个外设驱动的偶发段错误不会拖垮整机，符合硬件 7×24 的可用性要求。"

## 五、速记对照表

| 主题 | 一句话记忆 |
|---|---|
| 进程 vs 线程 | 进程=资源分配单位（独立地址空间），线程=调度单位（共享地址空间），内核里都是 task_struct |

| 信号处理函数 | 只调 async-signal-safe，惯用法是只设标志位 |
| SIGKILL/SIGSTOP | 不可捕获/忽略/阻塞 |
| D 状态 | 等 I/O 的不可中断睡眠，kill -9 也杀不掉 |

## 六、自测 8 题

1. 用一句话说清进程和线程的本质区别，并说明在 Linux 内核里它们是什么。
2. `fork()` 为什么返回两次？父子各拿到什么返回值？
3. 什么是写时复制（COW）？它解决了什么开销问题？
4. `fork(); fork(); fork();` 之后一共有几个进程？
5. 僵尸进程和孤儿进程分别是怎么产生的？哪个有危害、怎么避免？
6. 创建守护进程为什么要 `fork` 两次？`setsid` 起什么作用？
7. 信号处理函数里为什么不能调用 `printf`/`malloc`？工程上怎么处理？
8. 一个进程 `kill -9` 都杀不掉，可能是什么状态、什么原因？

<details>
<summary>参考答案</summary>

1. 进程是资源分配单位、有独立虚拟地址空间；线程是 CPU 调度单位、共享所在进程的地址空间。内核里两者都是 `task_struct`，区别仅在 `clone` 时共享了多少资源。
2. 因为 `fork` 复制出一个子进程后，父子都从返回点继续执行。父进程返回子进程 PID（>0），子进程返回 0，失败返回 -1。
3. fork 时父子共享同一批物理页并标记为只读，任一方第一次写某页才触发缺页异常、内核才复制那一页。避免了 fork 后立刻 exec 这种场景下白白整体拷贝地址空间的开销。
4. 2³ = 8 个进程。
5. 僵尸：子进程退出但父进程未 `wait` 回收，占着 PID 表项，有危害（耗尽 PID），让父进程 `wait` 或 `signal(SIGCHLD, SIG_IGN)` 避免。孤儿：父进程先退出，子进程被 init/systemd 收养，无危害。
6. 第一次 fork 让子进程脱离父进程并保证不是进程组组长，才能成功 `setsid` 新建会话脱离控制终端；第二次 fork 出的进程不再是会话组长，永远无法重新获得控制终端，更安全。`setsid` 的作用就是新建会话、脱离原控制终端。
7. 信号异步打断主流程，若主流程正持有 `malloc`/`stdio` 内部锁，处理函数再调同类函数会死锁——它们非 async-signal-safe。工程惯用法：处理函数里只设一个 `volatile sig_atomic_t` 标志（或 self-pipe），主循环再做真正处理。
8. 多半是 D 状态（不可中断睡眠），进程卡在等待磁盘/外设 I/O 的内核路径里，内核屏蔽了信号响应，连 SIGKILL 都送不进去，要排查底层存储/驱动；僵尸（Z）同样杀不掉，但那是因为它已经死了。

</details>
