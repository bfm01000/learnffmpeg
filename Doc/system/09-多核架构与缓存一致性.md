## 📌 第一部分：面试速记（考前 8 分钟扫一遍）

### 一句话核心

> **现代多核 CPU 每个核有私有 L1/L2、共享 L3，缓存以 cache line（通常 64 字节）为单位加载；多个核缓存同一份数据时，靠 MESI 缓存一致性协议 + 总线嗅探保证「一个核改了，别的核能看到」；而内存乱序（编译器重排 + CPU 乱序执行）让多线程下需要内存屏障来约束可见性顺序。真正拖慢多核程序的两大隐形杀手是「伪共享」和「跨核共享数据」。**

### 面试官常问问题 + 标准口语化回答

---

#### 开场题：简单讲讲现代多核 CPU 的缓存结构？

**🗣️ 面试标准回答：**

> "现在主流是 **SMP 对称多处理**：多个对等的核心共享同一块主存。每个核心有自己**私有的 L1（分指令 cache 和数据 cache）和 L2**，所有核**共享一个 L3**，再往下是主存。
>
> 关键是**访问延迟差几个数量级**：寄存器是 1 个周期，L1 大概 4 周期，L2 十几个周期，L3 四五十个周期，主存要两三百个周期。所以**让数据待在离核近的缓存里**是性能的核心，这也是 cache 命中率重要的原因。
>
> 缓存不是按字节加载的，而是按 **cache line（一般 64 字节）**为单位，访问一个字节会把整行拉进来，这是空间局部性优化的基础，也是伪共享问题的根源。"

**👨‍💻 面试官追问：**

> Q: 为什么按行加载而不是按需要的字节加载？
> A: 程序有空间局部性——访问一个变量后大概率访问它旁边的，按行批量加载摊薄了访存开销；而且 cache 的标签（tag）管理也是按行做的，按字节管理元数据开销太大。

---

#### 必考题：多个核各自缓存了同一个变量，一个核改了，别的核怎么知道？

**考察意图：** 这是缓存一致性（cache coherence）的核心，是多核架构的「灵魂问题」。

**🗣️ 面试标准回答：**

> "靠**缓存一致性协议**，最经典的是 **MESI**。每条 cache line 在每个核里有四种状态：
>
> - **M (Modified)**：我改过、和内存不一致，且只有我有这份。
> - **E (Exclusive)**：只有我有、和内存一致，还没改。
> - **S (Shared)**：多个核都有这份、和内存一致，只读共享。
> - **I (Invalid)**：这行作废了，不能用。
>
> 核之间通过**总线嗅探（bus snooping）**互相监听：当一个核要写一行数据时，它先发广播让**其他核把这行置为 Invalid**，自己升到 Modified 再改。别的核下次读这行发现是 Invalid，就会触发一次 miss，从持有 Modified 的核或内存重新拿最新值。
>
> 所以一句话：**硬件用 MESI + 总线嗅探，保证任何时刻一份数据不会有两个核同时持有可写的、冲突的副本，读到的总是最新值。** 一致性是硬件自动保证的，程序员不用手动同步缓存——但这套机制不是免费的，频繁跨核写同一行会产生大量失效广播，这就是伪共享性能问题的来源。"

**👨‍💻 面试官追问：**

> Q: 缓存一致性（coherence）和内存一致性（consistency）是一回事吗？
> A: 不是。**coherence** 管的是「单个地址在多核间的副本最终一致、写有全局顺序」；**consistency（内存模型）** 管的是「不同地址的读写操作，在别的核看来以什么顺序发生」。前者硬件 MESI 保证，后者要靠内存屏障/内存序约束（详见 cpp 库的 02-原子操作与内存序）。

#### 高频考点：什么是伪共享（false sharing）？怎么解决？

**考察意图：** 这是多核性能调优最经典、面试最爱问的点，能讲清楚直接加分。

**🗣️ 面试标准回答：**

> "**伪共享**是指：两个变量逻辑上互不相关，但**恰好落在同一条 cache line（64 字节）里**，被两个不同的核分别频繁写。从程序逻辑看它们没共享数据，但从硬件看它们共享了同一条 cache line——A 核写自己的变量会让整行失效，B 核读自己的变量就 miss，B 写又让 A 失效，**cache line 在两个核之间反复弹来弹去（cache line ping-pong）**，一致性协议疯狂发失效广播，性能可能下降几倍到几十倍。
>
> 解决办法是**让冲突的变量分到不同的 cache line**：
>
> 1. **填充对齐（padding）**：在变量之间塞够 64 字节的占位，或用 `alignas(64)` 让每个热点变量独占一行。
> 2. **C++17 的 `std::hardware_destructive_interference_size`**：标准提供的「避免伪共享的最小对齐」，通常是 64。
> 3. **结构体布局**：把多线程各自写的字段拆到不同行，把只读共享的字段单独放。
>
> 典型场景：每个线程一个计数器的数组 `counters[threadCount]`，如果紧挨着放，多个线程各更新各的下标，照样伪共享；要把每个计数器 padding 到独占一行。完整可运行代码和无锁队列里的应用见 cpp 库的 03-无锁队列。"

**👨‍💻 面试官追问：**

> Q: 怎么定位线上程序的伪共享？
> A: 用 `perf c2c`（cache-to-cache）专门分析跨核 cache line 竞争，能定位到哪条 line、哪些变量在 ping-pong；也可以看 `perf stat` 里的 cache miss 率异常升高。

#### 高频题：单线程跑得好好的代码，多线程为什么会因为「乱序」出错？

**🗣️ 面试标准回答：**

> "有两层乱序：
>
> 1. **编译器重排**：编译器为了优化，会在**不改变单线程语义**的前提下调整指令顺序。
> 2. **CPU 乱序执行**：现代 CPU 流水线、写缓冲（store buffer）会让指令的**实际生效顺序**和程序顺序不同，比如写操作先进 store buffer 再慢慢刷到缓存。
>
> 单线程下硬件和编译器保证『看起来像顺序执行』（as-if 规则），所以没事。**但多线程下，A 核眼里的操作顺序，到 B 核看可能是乱的**——比如 A 先写 data 再写 flag，B 看到 flag 已置位却读到旧 data，因为两个写在别的核看来顺序颠倒了。
>
> 解决靠**内存屏障**约束顺序，或者直接用 `std::atomic` 配合合适的内存序（acquire/release），让编译器和 CPU 都不许跨屏障重排。具体语义见 cpp 库的 02-原子操作与内存序。"

---

#### 原理题：原子操作在多核下底层是怎么实现的？代价在哪？

**🗣️ 面试标准回答：**

> "x86 上原子操作（比如 `lock add`、CAS 对应的 `lock cmpxchg`）靠 **LOCK 前缀**实现。早期是**总线锁（bus lock）**——锁住整条内存总线，其他核全停，代价极大；现代 CPU 优化成 **cache line 锁**：只要数据在一条 cache line 内、且本核能拿到这行的独占（Exclusive/Modified）所有权，就只锁这一行，通过 MESI 协议保证原子性，不必锁总线。
>
> 代价在于：原子操作要**先把 cache line 拿成独占状态**，这意味着要让其他核的副本失效，本质上是一次跨核同步。所以**高频对同一变量做 CAS/原子自增，在多核下会变成 cache line ping-pong**，核越多越慢——这也是为什么无锁不等于高性能，竞争激烈时原子操作的扩展性可能还不如减少共享。
>
> 一句话：**原子操作不是魔法，它是把『拿独占所有权 + 改 + 一致性广播』压进一条指令，竞争下的瓶颈仍是跨核缓存同步。**"

**👨‍💻 面试官追问：**

> Q: 那为什么还推荐无锁？
> A: 无锁的价值在**无竞争或低竞争**时避免了系统调用和上下文切换；高竞争下要靠**减少共享、分片（per-core 数据）、批处理**来降低跨核同步频率，而不是无脑上原子。

---

#### 进阶题：什么是 NUMA？对多核编程有什么影响？

**🗣️ 面试标准回答：**

> "**NUMA（非一致内存访问）**是多路服务器的内存架构：内存被分成多个节点，每个节点挂在某些 CPU（socket）旁边。**核访问本节点内存快，访问其他节点的远程内存慢**（要走 socket 间互联），延迟差可能一两倍。
>
> 影响：线程在哪个核跑、内存在哪个节点分配，要**对齐**。如果绑核绑到 node0 但内存分配在 node1，每次访存都走远程，性能就差。Linux 下用 `numactl --cpunodebind --membind` 控制，代码里有 `libnuma`，内核默认有 **first-touch 策略**（谁第一个写这页，就分配在那个核的本地节点）。
>
> 不过**嵌入式/物联网多核芯片绝大多数是 UMA（一致访问，单一内存节点）**，NUMA 主要出现在多路 x86 服务器，所以智能硬件方向了解概念即可；真正落地多的是下一条——CPU 亲和性绑核。"

---

#### 实战题：多核多任务程序怎么设计才能发挥多核性能？

**🗣️ 面试标准回答：**

> "核心思路是**减少跨核共享、让每个核尽量独立干活**：
>
> 1. **任务拆分到多核**：按数据分片（data parallel）或按流水线阶段分（pipeline），让多核并行。
> 2. **CPU 亲和性绑核**：把固定任务绑到固定核（`sched_setaffinity`/`pthread_setaffinity_np`），减少线程迁移导致的 cache 失效，详见 [[04-多线程与Linux调度]]。
> 3. **减少共享、消除伪共享**：每个核用自己的局部数据（per-core / thread-local），最后再汇总；热点变量 cache line 对齐。
> 4. **用消息传递替代共享内存**：核间通过无锁队列传递消息，而不是抢同一把锁改同一块数据，把同步频率降下来（无锁队列见 cpp 库的 03-无锁队列）。
>
> 落到音视频/智能硬件：采集、编码、推理这些阶段分到不同核，跑成流水线；每个阶段内部用 per-core 缓冲，阶段之间用无锁队列传帧；绝对避免两个核频繁写同一条 cache line 把帧处理拖慢。"

## 二、原理详解

### 1. 多核缓存层级与访问延迟

典型双核 SMP 结构（每核私有 L1/L2，共享 L3）：

```text
   ┌─────────── Core 0 ───────────┐   ┌─────────── Core 1 ───────────┐
   │   寄存器                       │   │   寄存器                       │
   │   L1 (指令 cache + 数据 cache) │   │   L1 (指令 cache + 数据 cache) │  ← 私有
   │   L2                          │   │   L2                          │  ← 私有
   └───────────────┬──────────────┘   └──────────────┬───────────────┘
                   │                                  │
                   └──────────────┬───────────────────┘
                          ┌───────┴────────┐
                          │   共享 L3       │   ← 所有核共享
                          └───────┬────────┘
                          ┌───────┴────────┐
                          │   主存 DRAM     │
                          └────────────────┘
```

各级存储访问延迟（数量级对比，具体值因 CPU 而异）：

| 存储层级 | 大致延迟（CPU 周期） | 容量数量级 | 是否私有 |
|---|---|---|---|
| 寄存器 | < 1 | 几十个 | 私有 |
| L1 cache | ~4 | 32~64 KB | 每核私有 |
| L2 cache | ~12 | 256 KB~1 MB | 每核私有（或小簇共享） |
| L3 cache | ~40 | 几 MB~几十 MB | 多核共享 |
| 主存 DRAM | ~200~300 | GB 级 | 全局共享 |

> 记忆点：**每往下一级，延迟大约涨一个数量级。** 一次主存访问 ≈ 几十次 L1 访问，所以提升 cache 命中率（见本目录《CPU缓存命中率》）和避免无谓的跨核失效，是多核性能的关键。

### 2. cache line：缓存的基本单位

```text
内存地址按 64 字节切成一条条 cache line：
┌──────────────── 一条 cache line = 64 字节 ────────────────┐
│ byte0 byte1 ... 你只读了 byte0，整条 64 字节都被拉进 cache │
└───────────────────────────────────────────────────────────┘
```

- 读/写任何一个字节，硬件都按**整条 64 字节**加载/管理。
- 好处：**空间局部性**——顺序访问数组时，一次加载覆盖接下来好几个元素。
- 副作用：**伪共享**——不相关的变量挤在同一行会互相拖累（见下文）。

查看本机 cache line 大小：

```bash
# 方法一：sysfs
cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size   # 通常输出 64
# 方法二：getconf
getconf LEVEL1_DCACHE_LINESIZE
```

### 3. MESI 缓存一致性协议

每条 cache line 在每个核里处于四种状态之一：

| 状态 | 含义 | 与内存一致？ | 其他核是否有副本 |
|---|---|---|---|
| **M** Modified | 本核改过，脏数据 | 否（内存是旧的） | 否，仅本核独有 |
| **E** Exclusive | 本核独有，未改 | 是 | 否 |
| **S** Shared | 多核只读共享 | 是 | 可能有 |
| **I** Invalid | 本行已失效 | —— | —— |

核心状态转换（简述）：

```text
读未命中：从内存/其他核取 → 若别人也有则进 S，独享则进 E
本核写入：必须先获得独占 → 广播让其他核置 I → 本核升到 M
其他核要写我持有的行：我收到失效广播 → 把该行置 I
其他核要读我的 M 行：我把脏数据回写/转发 → 双方降到 S
```

一句话：**写之前必须独占（让别人失效），保证任意时刻不会有两个核同时持有可写的冲突副本。** 这套广播协调通过**总线嗅探（bus snooping）**完成——每个核监听总线上其他核的读写请求，发现涉及自己缓存的行就响应。

### 4. 伪共享 false sharing：多核性能隐形杀手

```text
        Core 0 频繁写 counterA        Core 1 频繁写 counterB
                  │                            │
                  ▼                            ▼
   ┌──────────────────────── 同一条 cache line (64B) ───────────────────────┐
   │  [ counterA(8B) ][ counterB(8B) ][ ............. 其余 48B ............ ] │
   └────────────────────────────────────────────────────────────────────────┘
   逻辑上互不相关，物理上同一行：
   Core0 写 counterA → 广播失效 → Core1 的这行变 I → Core1 读 counterB 时 miss
   Core1 写 counterB → 广播失效 → Core0 的这行变 I → 反复 ping-pong，性能暴跌
```

下面用代码对比「伪共享」和「cache line 对齐后」的差别（原子/无锁的完整版见 cpp 库的 03-无锁队列）：

```cpp
#include <atomic>
#include <cstddef>
#include <new>      // std::hardware_destructive_interference_size (C++17)

constexpr std::size_t cacheLineSize = 64;  // 也可用上面的标准常量

// ❌ 反例：两个计数器挨着放，多线程各写一个 → 落在同一 cache line → 伪共享
struct CountersBad {
    std::atomic<long> counterForCore0;   // 这两个字段大概率在同一条 cache line
    std::atomic<long> counterForCore1;
};

// ✅ 正例：用 alignas 让每个计数器独占一条 cache line，彻底隔离
struct alignas(cacheLineSize) PaddedCounter {
    std::atomic<long> value{0};
    // 编译器会把整个结构体补齐到 64 字节，下一个对象从新行开始
};

struct CountersGood {
    PaddedCounter counterForCore0;
    PaddedCounter counterForCore1;
};
```

要点：**`alignas(64)` 让每个热点变量独占一条 cache line**，A 核写自己的行不会让 B 核的行失效，ping-pong 消失。代价是内存占用变大（每个计数器从 8 字节涨到 64 字节），所以只对**多核高频写的热点字段**做对齐，不要无脑对齐所有东西。

### 5. 内存乱序与内存屏障（系统视角，深讲见 cpp 库 02）

```text
程序里写的顺序：       store data;  store flag;
                              │
        编译器重排 ───────────┤
        CPU 乱序 + store buffer ┘
                              ▼
别的核实际观察到的顺序可能是：store flag;  store data;   ← 顺序颠倒！
```

屏障分两类：

| 屏障类型 | 作用 | 例子 |
|---|---|---|
| **编译屏障** | 只阻止编译器重排，不生成 CPU 指令 | `asm volatile("":::"memory")`、`std::atomic_signal_fence` |
| **CPU 内存屏障** | 阻止 CPU 乱序，约束写缓冲刷新顺序 | x86 `mfence/lfence/sfence`、`std::atomic_thread_fence` |

C++ 里用 `std::atomic` 的内存序表达，不必手写汇编屏障：

```cpp
std::atomic<bool> ready{false};
int payload = 0;

// 生产者核
payload = 42;                                   // ① 准备数据
ready.store(true, std::memory_order_release);   // ② release：保证 ① 不会被排到 ② 之后

// 消费者核
if (ready.load(std::memory_order_acquire)) {    // acquire：与上面的 release 配对
    // 这里一定能看到 payload == 42（① 对本核可见）
    use(payload);
}
```

> **release/acquire 的完整语义、relaxed/seq_cst 的区别、为什么这样能保证可见性，见 cpp 库的 02-原子操作与内存序。** 本篇只强调：屏障约束的是「不同地址操作在别的核看来的顺序」，是 consistency 层面的事，和 MESI 的 coherence 是两回事。

### 6. NUMA：非一致内存访问

```text
   ┌──────── NUMA Node 0 ────────┐      ┌──────── NUMA Node 1 ────────┐
   │  Core0 Core1 ...            │      │  Core4 Core5 ...            │
   │        │                    │      │        │                    │
   │   本地内存(快, ~100ns) ◄────┤      ├────► 本地内存(快)            │
   └────────┬────────────────────┘      └────────┬───────────────────┘
            └──── socket 互联(慢, 远程访问) ──────┘
   Node0 的核访问 Node1 的内存 = 远程访问，延迟可能高一两倍
```

常用命令：

```bash
numactl --hardware                       # 查看 NUMA 拓扑、各节点内存
numactl --cpunodebind=0 --membind=0 ./app  # 绑到 node0 的核 + node0 的内存（对齐！）
```

> **嵌入式/物联网多核芯片通常是 UMA（单一内存节点），没有 NUMA 问题，了解概念即可。** NUMA 主要出现在多路 x86 服务器，绑核时务必让「核」和「它访问的内存」在同一节点。

### 7. CPU 亲和性与多核 cache 命中

绑核能让线程一直在同一个核上跑，**避免迁移后 L1/L2 全部冷掉重新加载**：

```cpp
#include <pthread.h>

// 把当前线程绑定到 coreIndex 号核
void bindToCore(int coreIndex) {
    cpu_set_t cpuSet;
    CPU_ZERO(&cpuSet);
    CPU_SET(coreIndex, &cpuSet);
    pthread_setaffinity_np(pthread_self(), sizeof(cpuSet), &cpuSet);
}
```

> 绑核的调度细节、`sched_setaffinity` vs `pthread_setaffinity_np`、隔离核（isolcpus）见 [[04-多线程与Linux调度]]。在 NUMA 机器上还要保证绑的核和分配的内存在同一节点。

### 8. 多核多任务设计：音视频/智能硬件落地

```text
       采集核(Core0)        编码核(Core1)         推理核(Core2)
          │ 抓帧               │ H.264/265          │ NPU/CPU 推理
          ▼                    ▼                    ▼
      [无锁队列] ──传帧──► [无锁队列] ──传帧──► [无锁队列] ──► 输出
   每个阶段绑一个核，阶段间用无锁队列传消息，而不是抢同一把锁改同一块帧缓冲
```

设计原则落地：

- **阶段拆分到不同核**：采集 / 编码 / 推理各占一个核，流水线并行，吞吐 ≈ 最慢一级。
- **核间用消息传递**：用无锁队列（cpp 库的 03-无锁队列）在阶段间传帧指针，避免多核抢锁改同一缓冲。
- **每核局部缓冲 + cache line 对齐**：每个阶段的统计计数、状态字段用 `alignas(64)` 隔离，防止伪共享拖慢帧率。
- **绑核绑稳**：把实时性要求高的编码/推理绑到隔离核，减少被其他任务抢占和迁移导致的 cache 抖动。

## 三、常见坑与面试加分点

| 坑 / 误区 | 说明与正解 |
|---|---|
| 以为缓存一致性要程序员手动维护 | 错。MESI 是**硬件自动**保证 coherence；程序员要管的是 consistency（内存序/屏障） |
| 把 coherence 和 consistency 混为一谈 | coherence 管单地址多副本一致；consistency 管多地址操作的可见顺序 |
| per-thread 计数器数组紧挨着放 | 经典伪共享，要每个元素 `alignas(64)` padding 到独占一行 |
| 无脑对所有结构体 `alignas(64)` | 浪费内存、撑爆 cache，只对**多核高频写的热点字段**对齐 |
| 以为无锁/原子一定比锁快 | 高竞争下原子操作触发 cache line ping-pong，扩展性可能更差，要减少共享 |
| 在嵌入式 UMA 芯片上纠结 NUMA | UMA 没有远近内存之分，NUMA 是多路服务器的事 |
| 绑了核却没绑对 NUMA 节点 | 核在 node0、内存在 node1，每次访存走远程，白绑 |
| 用 `volatile` 当多线程同步 | `volatile` 不提供原子性和内存序，多线程要用 `std::atomic`（见 cpp 库 02） |

**加分一句（智能硬件流水线）：**

> "我会用 `perf c2c` 先确认有没有跨核 cache line 竞争。曾经遇到过编码线程和统计线程各更新一个计数器，恰好同一条 cache line，帧处理掉了一截；把统计计数器 `alignas(64)` 隔离后吞吐立刻回来。这说明多核优化第一步不是上无锁，而是先消除伪共享、减少跨核共享。"

## 四、速记对照表

| 概念 | 一句话记忆 |
|---|---|
| SMP | 多个对等核共享主存，私有 L1/L2、共享 L3 |
| cache line | 缓存最小单位，通常 64 字节，整行加载 |
| MESI | Modified/Exclusive/Shared/Invalid，写前必须独占 |
| 总线嗅探 | 各核监听总线，发现涉及自己的行就响应失效/转发 |
| coherence | 单地址多副本最终一致（硬件保证） |
| consistency | 多地址操作的可见顺序（靠内存序/屏障） |
| 伪共享 | 不相关变量挤同一 cache line，跨核写 ping-pong |
| 解决伪共享 | `alignas(64)` / padding / `hardware_destructive_interference_size` |
| 内存屏障 | 编译屏障防编译器重排，CPU 屏障防乱序执行 |
| LOCK 前缀 | x86 原子实现，现代是 cache line 锁而非总线锁 |
| NUMA | 非一致内存访问，本地快远程慢，嵌入式多为 UMA |
| 绑核 | 固定核跑，保 cache 热；NUMA 上要连内存节点一起对齐 |
| 多核设计 | 拆任务、减共享、消息传递替代共享内存、消除伪共享 |

## 五、自测 8 题

1. 现代多核 CPU 哪几级 cache 是私有的、哪级是共享的？从寄存器到主存延迟大致差几个数量级？
2. cache line 一般多大？为什么按行而不是按字节加载？
3. 说出 MESI 四个状态各代表什么，写操作前 cache line 必须处于什么前提？
4. 缓存一致性（coherence）和内存一致性（consistency）有什么区别？分别靠什么保证？
5. 什么是伪共享？给一个会触发伪共享的代码场景，并说出两种解决办法。
6. 单线程没问题的代码，多线程为什么会因乱序出错？编译屏障和 CPU 屏障有什么不同？
7. x86 原子操作靠什么实现？为什么高竞争下原子操作扩展性反而差？
8. NUMA 是什么？嵌入式多核为什么一般不用关心？绑核时 NUMA 上要注意什么？

<details>
<summary>参考答案</summary>

1. L1、L2 每核私有，L3 多核共享，主存全局共享；从寄存器(<1 周期)到主存(~200~300 周期)，每往下一级延迟约涨一个数量级。
2. 通常 64 字节；因为程序有空间局部性，整行加载摊薄访存开销，且 cache 标签按行管理元数据开销更小。
3. M 改过且独有/脏；E 独有未改且与内存一致；S 多核只读共享；I 失效。写前必须先取得该行的**独占**（让其他核副本置 I），再升到 M 才能改。
4. coherence 管「单个地址在多核间副本最终一致、写有全局顺序」，由硬件 MESI 保证；consistency 管「不同地址的读写在别的核看来的顺序」，靠内存序/内存屏障保证。
5. 不相关的变量落在同一条 cache line，被不同核分别频繁写，导致该行在核间反复失效（ping-pong）。如每线程一个紧挨排列的计数器数组。解决：`alignas(64)` 让热点变量独占一行；或在变量间插入 padding；或用 `std::hardware_destructive_interference_size`。
6. 编译器重排和 CPU 乱序执行（store buffer 等）让操作的实际生效顺序与程序顺序不同；单线程有 as-if 保证看起来顺序，多线程下别的核会观察到颠倒的顺序。编译屏障只阻止编译器重排、不生成指令；CPU 屏障生成真实指令阻止硬件乱序、约束写缓冲刷新。
7. 靠 LOCK 前缀（如 `lock cmpxchg`）；现代实现是 cache line 锁（拿到该行独占所有权即可，不锁总线）。高竞争下每次原子操作都要把 cache line 抢成独占、让其他核失效，变成跨核 ping-pong，核越多越慢。
8. NUMA 是非一致内存访问，内存分节点，核访问本地内存快、远程慢；嵌入式多核多为 UMA（单一内存节点）没有远近之分，故不必关心。NUMA 上绑核时要让线程所在核与它访问的内存在同一节点，否则走远程访问白绑。

</details>
