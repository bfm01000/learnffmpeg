## 📌 第一部分：面试速记（考前 12 分钟扫一遍）

### 一句话核心

> **Linux 给每个进程一份独立的「虚拟地址空间」，靠 MMU + 多级页表把虚拟地址翻译成物理地址，物理内存以「页（4KB）」为单位按需分配（缺页时才真正给物理页）。所以「申请了内存」和「占了物理内存」是两回事——这就是 VSZ（虚拟）和 RSS（物理）差很多的根因，也是排查内存问题的总纲。**

### 面试官常问问题 + 标准口语化回答

---

#### 开场题：用一句话说清楚 Linux 的内存管理在管什么？

**🗣️ 面试标准回答：**

> "它管两件事：一是**地址隔离**——每个进程看到的都是从 0 开始、连续完整的虚拟地址空间，互相看不见对方，靠页表各自映射到不同的物理页；二是**按需供给**——物理内存以 4KB 的页为单位，进程 `malloc` 或映射时只是登记了虚拟地址，真正访问到某一页时才触发缺页中断、分配物理页。中间的翻译由硬件 MMU 完成，TLB 缓存最近的翻译结果加速。"

---

#### 必考题：虚拟地址和物理地址什么关系？为什么要搞虚拟内存？

**考察意图：** 这是整篇的地基，答不清楚后面 RSS/缺页/COW 全说不明白。

**🗣️ 面试标准回答：**

> "程序里所有指针拿到的都是**虚拟地址**，CPU 执行访存时，MMU 拿这个虚拟地址查页表，翻译成真正的**物理地址**再去访问内存条。三个核心好处：
>
> 1. **隔离与安全**：每个进程一套独立页表，进程 A 的虚拟地址 0x400000 和进程 B 的同一个地址映射到完全不同的物理页，进程之间踩不到对方，内核空间也映射成用户态不可访问。
> 2. **按需分配 + 超额承诺**：虚拟空间可以开得很大（64 位下 128TB 用户空间），但只在真正访问时才分物理页，物理内存可以「超卖」。
> 3. **灵活映射**：同一份物理页可以映射进多个进程（共享库、共享内存、COW），磁盘文件可以映射进地址空间（mmap），物理内存碎片也能用页表拼成连续的虚拟地址。
>
> 一句话：**虚拟内存是物理内存之上的一层间接，换来了隔离、按需、共享这三件事。**"

**👨‍💻 面试官追问：**

> Q: 虚拟地址空间那么大，页表不会很大吗？
> A: 所以用**多级页表**——只有真正用到的那部分虚拟地址才建立对应的页表项，没映射的区域连页表中间层都不创建，页表本身也是按需分配的。

---

#### 必考题：什么是分页？MMU 怎么把虚拟地址翻译成物理地址？

**🗣️ 面试标准回答：**

> "内存被切成固定大小的**页**（Linux 默认 4KB），物理内存对应叫**页框**。页表是「虚拟页号 → 物理页框号」的映射表。翻译时，MMU 把虚拟地址拆成『页号 + 页内偏移』，用页号查页表拿到物理页框号，再拼上偏移得到物理地址。
>
> 64 位实际用**多级页表**（x86-64 常见 4 级：PGD/PUD/PMD/PTE），逐级查下去，避免一张大表浪费空间。每次访存都查页表太慢，所以有 **TLB（快表）**——缓存最近用过的『虚拟页→物理页』翻译结果，命中就一步到位，不用走多级页表。"

**👨‍💻 面试官追问：**

> Q: TLB 命中率为什么重要？换页表（进程切换）时 TLB 怎么办？
> A: TLB 未命中要走多级页表（一次翻译多次访存），命中率直接影响访存速度。进程切换换了页表，TLB 整体失效（除非用 PCID/ASID 给 TLB 项打进程标签来避免全刷）。**大页（HugePage，2MB）**能让一个 TLB 项覆盖更大范围，提高命中率，常用于数据库、大缓冲场景。

---

#### 必考题：缺页中断（page fault）是什么？minor 和 major 有什么区别？

**🗣️ 面试标准回答：**

> "访问一个虚拟地址，但它在页表里没有对应的有效物理页时，MMU 触发**缺页中断**，陷入内核由缺页处理程序补救。分两种：
>
> - **minor fault（次缺页）**：物理页其实已经在内存里，只是当前进程页表还没建立映射。比如刚 `malloc` 后第一次写、共享库已被别的进程加载进内存、COW 触发复制——不用读磁盘，只改页表，很快。
> - **major fault（主缺页）**：内容还在磁盘上，必须发起磁盘 I/O 读进来。比如 mmap 的文件页第一次访问、被换出到 swap 的页又被访问——慢，因为有磁盘 I/O。
>
> 排查时 `ps -o min_flt,maj_flt` 或 `/proc/pid/stat` 能看两类计数，**major fault 飙高**往往意味着内存不够在颠簸（swap）或大量冷文件读。"

---

#### 必考题：VSZ、RSS、PSS 有什么区别？（高频中的高频）

**🗣️ 面试标准回答：**

> "都是 `top`/`ps` 里的内存指标，区别在『算的是虚拟还是物理、共享怎么摊』：
>
> - **VSZ（虚拟内存大小）**：进程虚拟地址空间总和，包括 `malloc` 了还没用的、mmap 的文件、未触发缺页的部分。**VSZ 大不代表占了那么多物理内存**，参考价值有限。
> - **RSS（常驻内存）**：实际占用的物理页大小（`top` 的 RES 列）。但有个坑——**共享内存/共享库被多个进程各自的 RSS 重复计算**，把所有进程 RSS 加起来会超过实际物理内存。
> - **PSS（按比例摊分）**：私有页全算自己的，共享页按共享进程数平摊。比如一个 4KB 页被 4 个进程共享，每个进程的 PSS 只算 1KB。**统计整机真实内存占用、做容量规划时 PSS 最准。**
>
> 口诀：**VSZ 是『画了多大的饼』，RSS 是『真吃了多少（但共享重复算）』，PSS 是『公平摊分后真正属于我的那份』。** PSS 在 `/proc/pid/smaps` 里看。"

**👨‍💻 面试官追问：**

> Q: 那看一个进程到底「私有占了多少」看哪个？
> A: smaps 里的 **`Private_Dirty` + `Private_Clean`**（USS，私有常驻）最能反映「杀掉这个进程能直接回收多少物理内存」。

---

#### 必考题：`malloc` 是怎么实现的？brk 和 mmap 各管什么？

**🗣️ 面试标准回答：**

> "`malloc` 是 C 库（glibc 用 ptmalloc）的用户态分配器，它向内核要的是『大块内存』，再切小块给你。两条拿内存的路：
>
> - **小块（默认 < 128KB，`M_MMAP_THRESHOLD`）**：在**堆**上分配，通过 `brk`/`sbrk` 移动堆顶指针扩展堆，或直接从 glibc 维护的 **arena（空闲链表 / bins）** 里复用已经释放的小块。
> - **大块（≥ 阈值）**：直接 `mmap` 向内核要一段匿名映射，`free` 时直接 `munmap` 还给内核。
>
> 关键点：**`free` 不等于把内存还给操作系统**。小块 free 后通常只是回收进 glibc 的空闲链表等着复用，堆顶（brk）不一定下移，所以**进程 RSS 释放后不降是正常的**。多线程下 glibc 还会开多个 arena 减少锁竞争。"

**👨‍💻 面试官追问：**

> Q: 那为什么我 `free` 了一大堆内存，`top` 里 RES 还是不降？是泄漏吗？
> A: 不一定是泄漏。glibc 把空闲小块留在自己的 bins 里复用，只有堆顶连续的大段空闲才可能通过 `malloc_trim` 或 brk 回缩还给 OS；中间被占着的块导致堆顶下不去（外部碎片）。真要还可以调 `malloc_trim(0)`。**判断泄漏要看『长期持续增长且不回落』，而不是『free 后没立刻降』。**

---

#### 必考题：怎么区分「内存泄漏」和「内存只是没还给 OS / 正常占用」？

**🗣️ 面试标准回答：**

> "看三个维度：
>
> 1. **趋势**：泄漏是**单调持续增长、压力下不回落**；正常占用会随负载涨跌、稳定在一个水位。盯一段时间的 RSS 曲线比看一个瞬时值有用。
> 2. **工具定位**：`valgrind --leak-check` 或编译时开 **ASan/LSan**，能直接报『哪行分配的内存没释放』。这是真泄漏（指针丢了，永远 free 不掉）的铁证。
> 3. **区分『没还 OS』**：如果 valgrind 说没泄漏，但 RSS 高，那多半是 glibc 没把空闲块还给 OS，或者是 page cache（不算进程的）。可以 `malloc_trim` 看能不能降一部分。
>
> 一句话：**真泄漏 = 程序再也访问不到、也 free 不掉的内存（工具能抓）；假泄漏 = free 了但留在分配器/缓存里，可被复用。**"

---

#### 高频题：`free` 命令里 buff/cache 占了很多，是内存泄漏吗？

**🗣️ 面试标准回答：**

> "**不是，那是 page cache，是内核拿空闲内存帮你缓存文件加速 I/O，属于『可回收』内存。** `free -h` 里要看 **available** 那一列才是真正还能用的——它已经把可回收的 cache 算进去了。`used` 高、`free` 低但 `available` 充足，完全正常。内存一紧张，内核会自动回收 page cache。所以『buff/cache 高』恰恰说明内存被有效利用了，不是泄漏。新手常被 `free` 列吓到，记住**看 available 不看 free**。"

---

#### 高频题：mmap 是什么？为什么能「零拷贝」？一定比 read 快吗？

**🗣️ 面试标准回答：**

> "`mmap` 把一段内容映射进进程虚拟地址空间，之后像访问数组一样用指针读写。分类两个维度：
>
> - **文件映射 vs 匿名映射**：文件映射关联磁盘文件（读文件、共享库加载）；匿名映射没有后备文件（大块 malloc、`MAP_ANONYMOUS`）。
> - **共享（MAP_SHARED）vs 私有（MAP_PRIVATE）**：共享映射的写会回写到文件、对其他映射者可见（IPC 用）；私有映射的写触发 COW，不影响原文件。
>
> **为什么算零拷贝**：普通 `read` 是『磁盘 → page cache → 用户缓冲区』两次拷贝；mmap 直接把 page cache 的页映射进用户地址空间，省掉了内核到用户的那次拷贝，用户指针直接指向 page cache。
>
> **但不一定比 read 快**：mmap 第一次访问每页都触发缺页中断（major fault + 建页表），随机小量访问时缺页开销可能比 read 的顺序大块拷贝还高。**大文件随机访问、需要多进程共享同一份文件**时 mmap 划算；顺序流式读小文件，`read`/`pread` 往往更简单更快。"

**👨‍💻 面试官追问（音视频向）：**

> Q: 处理大视频文件你会用 mmap 吗？
> A: 看场景。需要在文件里跳着随机 seek（如索引、关键帧定位）、或多进程/线程共享同一份只读资源时，mmap 省一次拷贝又省内存；但纯顺序解码、边读边丢的流式场景，`read` + 自己的环形缓冲更可控，还能避免缺页抖动。详见下文 page cache 与音视频。

#### 高频题：什么是写时复制 COW？fork 怎么用它？

**🗣️ 面试标准回答：**

> "**Copy-On-Write**：fork 出子进程时，不真的复制父进程的物理内存，而是让父子的页表都指向**同一批物理页，并把这些页标记为只读**。读没事，照常共享；任何一方**写**某页时触发缺页中断，内核这才**复制那一页**、改成可写、各自映射自己的副本。
>
> 好处：fork 几乎是瞬时的（只复制页表，不复制几 GB 数据），而且 `fork + exec` 场景下子进程马上换掉整个地址空间，复制了纯属浪费——COW 完美匹配。代价是 fork 后第一次写会有一波缺页。
>
> 调用侧细节在 [[02-进程管理与多进程编程]]，这里只讲原理：**COW = 共享 + 只读标记 + 写时触发缺页复制。**"

---

#### 高频题：swap 和 OOM killer 是什么？嵌入式为什么常关 swap？

**🗣️ 面试标准回答：**

> "**swap** 是把不常用的物理页换出到磁盘，腾出物理内存，需要时再换回（换回就是 major fault）。物理内存够时 swap 用得少，紧张时靠它续命，但频繁换进换出会**颠簸（thrashing）**，性能断崖。
>
> **OOM killer**：当物理内存和 swap 都耗尽、内核实在分不出页时，会选一个进程杀掉来保命。选谁看 **oom_score**——大致是『占内存越多、越不重要的越容易被杀』，可以通过 `/proc/pid/oom_score_adj` 调整（设很低保护关键进程，设很高让它优先被杀）。
>
> **嵌入式/智能硬件常关 swap**：一是很多设备用 eMMC/Flash，swap 频繁写会**磨损寿命**且慢；二是要**确定性延迟**，swap 引入的不可预测停顿对实时性是灾难。所以嵌入式更倾向『内存用满就明确 OOM，而不是偷偷 swap 拖慢』，靠精打细算内存预算 + 内存池来兜底。"

#### 原理题：进程地址空间从低到高是怎么布局的？

**🗣️ 面试标准回答：**

> "从低地址到高地址：**代码段（.text，只读可执行）→ 数据段（.data 已初始化全局/静态变量、.bss 未初始化清零）→ 堆（向上增长，brk 管）→ mmap 区（共享库、文件映射、大块 malloc）→ 栈（向下增长）→ 内核空间（用户态不可访问）**。堆和栈相向增长，中间是巨大的未映射空洞。`.bss` 不占文件体积（只记大小，加载时清零）。详细 ASCII 图见下文原理详解。"

## 二、原理详解

### 1. 虚拟地址 → 物理地址：MMU + 多级页表 + TLB

#### 1.1 先理解「为什么需要翻译」

程序里所有指针（`int *p = malloc(...)` 里的 `p`、栈上的局部变量地址 `&x`、函数指针）拿到的全部是**虚拟地址**。但 CPU 最终要从物理内存条上的某个位置读写数据——所以 CPU 每一次访存（取指令、读数据、写数据），都必须把虚拟地址翻译成物理地址。

做这个翻译的硬件叫 **MMU（Memory Management Unit，内存管理单元）**，它集成在 CPU 内部。翻译的依据是一张叫**页表（page table）**的映射表，操作系统负责建立和维护页表，MMU 负责查表翻译。

**核心思想**：虚拟内存 = 加一层间接。程序只跟虚拟地址打交道，物理内存的分配、回收、换出全部由 OS + MMU 在底下透明完成。

---

#### 1.2 地址是怎么拆的——页号与页内偏移

内存被切成固定大小的小块：**页（page）**，Linux 默认 **4KB（4096 字节）**。物理内存叫**页框（frame）**，也是 4KB。页表做的事情就是：**虚拟页号 → 物理页框号**。

翻译时偏移不变——只把页号换成页框号，页内偏移原样保留：

```text
虚拟地址 = [ 虚拟页号(VPN)  │  页内偏移(offset)  ]
              ▲                      ▲
              │                      │
         查页表翻译                  原样复制
              │                      │
              ▼                      ▼
物理地址 = [ 物理页框号(PFN) │  页内偏移(offset)  ]
```

在 x86-64 上，4KB 页的偏移占低 12 位（2^12 = 4096），所以：

```text
虚拟地址(48位有效) = [ 页号: bit 47..12 (共 36 位) | 偏移: bit 11..0 (共 12 位) ]
```

> **为什么 48 位而不是 64 位？——x86-64 的「规范地址」约定**
>
> 虽然通用寄存器是 64 位的，但**MMU 硬件只实现了 48 条地址线**——高 16 位（bit 63..48）根本不存在于地址翻译电路里。这不是 bug，而是刻意的工程设计。
>
> **那高 16 位填什么？** 硬件强制要求：**bit 63..48 必须全部等于 bit 47 的值**。满足这个条件的地址叫 **canonical address（规范地址）**，不满足的直接被 MMU 拒绝、触发异常。所以 bit 47 决定了高 16 位——bit 47 = 0 则高 16 位全 0；bit 47 = 1 则高 16 位全 1。
>
> 这天然把 2^64 的数值空间切成三段：
>
> ```text
> 完整的 64 位地址空间:
>
> 0xFFFF_FFFF_FFFF_FFFF  ─┐
> 0xFFFF_8000_0000_0000   ├── 内核空间 (128TB)
>                         │   bit 47=1, 高16位全1
>                         │   内核代码/数据/页表都在这里
> 0xFFFF_7FFF_FFFF_FFFF  ─┐
>                         │   非规范地址区域 (非法!)
> 0x0000_8000_0000_0000   ┘   访问这里 → CPU 直接抛异常
>                         │
> 0x0000_7FFF_FFFF_FFFF  ─┐
>                         ├── 用户空间 (128TB)
>                         │   bit 47=0, 高16位全0
>                         │   你的程序、堆、栈、mmap 都在这里
> 0x0000_0000_0000_0000  ─┘
> ```
>
> **bit 47 就是分界线**——它一翻，整个地址从「用户态」跳到了「内核态」：
> - 用户空间所有地址看起来都是 `0x0000_...`（bit 47 = 0），最高有效地址是 `0x0000_7FFF_FFFF_FFFF`
> - 内核空间所有地址看起来都是 `0xFFFF_...`（bit 47 = 1），最低有效地址是 `0xFFFF_8000_0000_0000`
> - 中间 `0x0000_8000_0000_0000` 到 `0xFFFF_7FFF_FFFF_FFFF` 是巨大的非法空洞，任何访存都会触发异常
>
> **为什么要这样设计？三个原因：**
>
> 1. **省硅片、省功耗**。实现 64 位全地址翻译需要页表支持到 2^64 范围（目前 4 级页表只覆盖 2^48），芯片面积和功耗全花在永远不会用到的电路上。48 位 = 256TB，即便是最大的数据中心服务器也用不完。
> 2. **未来可扩展，而且不破坏现有软件**。规范地址约定在中间留了一个巨洞——以后扩展更多位时（如 Intel 的 5 级页表支持 57 位虚拟地址），只需「缩小中间的非法区域」，原来合法的高/低区域边界向外推。已有的用户地址（高 16 位全 0）和内核地址（高 16 位全 1）不受影响，因为新加的译码位仍然遵循「等于 bit 47」的规则。
> 3. **一眼就能判断是用户还是内核地址**。不用查额外寄存器和权限表：地址最高 16 位全 0 = 用户态，全 1 = 内核态。内核代码里 `if (addr >= 0xFFFF_8000_0000_0000)` 就能判内核地址，调试 core dump 时看指针值也能秒判。
>
> **实际操作体验**：你在 gdb 里打断点看到 `0x00007FFFF777A010`（用户空间 libc 地址）和 `0xFFFFFFFF80200000`（内核代码段地址），区别一目了然。尝试把指针的值改到 `0x0000800000000000`（刚好卡在非法区域），CPU 当场抛异常。

> **⚠️ 常见误解澄清：内核用的也是虚拟地址，不是物理地址**
>
> 看到「内核空间地址高 16 位全 1」，很容易产生一个直觉：**「高 16 位被内核占用了，那内核是不是直接走物理地址、不用虚拟地址了？」** ——这个推论是错的。
>
> **规范地址规则的本质是「符号扩展」，不是「地址空间分配」。** bit 47=1 时高 16 位填全 1，是为了让内核地址在数值上看起来像 `0xFFFF_...`——这和「内核占用了这段编码空间所以直接用物理地址」完全是两码事。内核空间的地址同样是**虚拟地址**，访问时同样要走 MMU → TLB → 多级页表翻译，一步不少。
>
> **那内核怎么访问物理内存？——直接映射区（direct mapping）**
>
> Linux 在 x86-64 上把**全部物理内存**通过页表线性映射到内核虚拟地址空间的一个连续区域里：
>
> ```text
> 内核虚拟地址 = 物理地址 + PAGE_OFFSET
>
> 例如（具体值取决于内核配置）：
>   PAGE_OFFSET = 0xFFFF 8880 0000 0000  （或 0xFFFF 8000 0000 0000 等）
>
>   物理地址 0x0000 0000 5A00 0000
>       ↕ 一一对应，只差一个常量偏移
>   内核虚拟地址 0xFFFF 8880 005A 0000
> ```
>
> 这不叫「直接用物理地址」，而是页表里建立了一条**恒等偏移映射**——虚拟地址和物理地址之间只差一个固定的 `PAGE_OFFSET`，但访问时依然经过 MMU、TLB、页表翻译的完整流程。只是因为这个映射是线性的，内核代码用 `__va(pa)` / `__pa(va)` 两个宏做加减偏移就能互转，不需要像用户空间那样查页表。
>
> **为什么容易混淆？** 因为内核代码里确实能看到「物理地址」——但只在特定场景：
>
> | 场景 | 用什么地址 | 为什么 |
> | :--- | :--- | :--- |
> | 普通内核代码访问内存（`kmalloc`、访问数据结构、栈） | **内核虚拟地址** | 走正常 MMU 翻译，受页表保护 |
> | 遍历页表本身（PGD/PUD/PMD/PTE 条目里存的下一级表地址） | **物理地址** | MMU 硬件读页表时直接当物理地址用，如果用虚拟地址会死循环（翻译页表又要查页表） |
> | 设置 DMA 传输地址 | **物理地址**（或 IOMMU 映射后的地址） | DMA 控制器不走 CPU 的 MMU，它只认识总线上的物理地址 |
> | 访问 MMIO（内存映射 I/O，设备寄存器） | **内核虚拟地址**（ioremap 后） | 物理总线地址先通过 ioremap 建立页表映射，然后当虚拟地址访问 |
>
> **一句话**：内核日常访问的所有内存（代码、数据、堆、栈、`kmalloc` 的缓冲区、`vmalloc` 的区域）全是虚拟地址。物理地址只在「和硬件打交道」的边界处才出现——设置页表条目、配置 DMA、ioremap 之前的那一步。规范地址的高 16 位全 1 是 MMU 要求的编码规则，不等于内核绕过了 MMU。

#### 1.3 为什么必须「多级」页表——单级的问题

如果只有**一级页表**，那就是一个大数组：

```text
虚拟页号 → 页表[虚拟页号] → 物理页框号
```

问题很大：48 位地址空间，虚拟页号有 2^36 个条目（约 680 亿）。每条页表项 8 字节，单级页表就要 **512GB**——每个进程一份，完全不可能。

**但实际上一个进程根本用不到那么多地址。** 一个普通进程实际用到的虚拟地址可能只有几百 MB 到几 GB，也就是几百万个页——相比 680 亿个可能的页号，绝大多数区域是空的。

---

**💡 关键洞察：为什么树状结构能省空间？**

你可能会想——「拆成 4 级，每级不还是那些条目吗？换棵树上挂而已，总数又没少。」

不是的。**单级数组和多级树根本不是同一种东西，差别在于空洞区域的存储成本：**

| | 单级页表（数组） | 多级页表（树） |
|:---|:---|:---|
| 一个 512GB 的空洞区域怎么存？ | **必须为空洞里的每个 VPN 都分配 8 字节条目**（标"无效"但不能跳过——数组下标是连续的） | **上层 1 个条目标"不存在"，整个子树砍掉**（后面三层一个字节都不分） |
| 数据结构约束 | VPN 就是数组下标 → 数组必须覆盖 0..2^36，中间不能有洞 | 树的分支独立存在 → 一条分支不存在不影向其他分支 |
| 内存占用 | **O(全部可能 VPN)** = 512GB，固定 | **O(实际使用的区域 × 深度)** ≈ 几 MB |

用沙漠地图来类比：

> **单级** = 一张 10 亿像素的卫星图，99% 是荒漠，但地图必须完整画出来——荒漠的每个像素都占存储。
>
> **多级** = 分层地图：顶层切成 512 格。某格是荒漠 → 直接标"空"，不再展开。某格里有城镇 → 才展开更精细的地图。荒漠区域在顶层就终止了，后面几层根本不存在。

用文档 1.4 节的具体数字算一笔账：假设一个进程只用 2GB 虚拟内存（典型值）：

```
单级页表:  2^36 条目 × 8B = 512GB — 必须全部分配，没有选择

4 级页表:
  PGD:           512 条目 =     4KB  (顶层总是完整一张)
  PUD:   2GB/512GB × 512 ≈ 2 个 PUD 表 =     8KB  (只有用到的 512GB 区域才展开)
  PMD:   实际用到的 2MB 块才创建     ≈   100KB
  PTE:   实际映射的 4KB 页才创建     ≈     2MB
  ─────────────────────────────────────────
  合计:                                  ~2.5MB
```

**512GB vs 2.5MB**——这不是"把 512GB 拆碎重排"，而是 **99.9995% 的空洞在树的上层就被剪枝了**，根本没有对应的中间层和叶子节点。

这就是多级页表的核心思想：把页表本身也分页存储，**只在实际用到的虚拟地址范围才创建对应的页表层级**。没映射的空洞区域连页表中间层都不存在，省掉了大量空间。

#### 1.4 四级页表的完整结构（x86-64）

x86-64（4KB 页）使用 **4 级页表**。把 36 位虚拟页号再切成 4 段，每段 9 位：

```text
虚拟地址 (48 bits):
┌──────────┬──────────┬──────────┬──────────┬─────────────┐
│  PGD     │  PUD     │  PMD     │  PTE     │   offset    │
│  9 bits   │  9 bits   │  9 bits   │  9 bits   │   12 bits   │
│ 47...39  │ 38...30  │ 29...21  │ 20...12  │   11...0    │
└──────────┴──────────┴──────────┴──────────┴─────────────┘
    ▲           ▲          ▲          ▲           ▲
    │           │          │          │           └─ 页内偏移(不变)
    │           │          │          └─ 第4级索引: Page Table Entry
    │           │          └─ 第3级索引: Page Middle Directory
    │           └─ 第2级索引: Page Upper Directory
    └─ 第1级索引: Page Global Directory
```

每一级都是一个 **4KB 的表**，里面有 **512 个条目**（512 × 8 字节 = 4KB，9 位正好索引 512 个）。每一级的条目里存的是**下一级表的物理地址**（不是虚拟地址，否则就死循环了），最后一级 PTE 里存的是**目标物理页框号**。

> **为什么每级恰好 4KB？** 因为页大小就是 4KB——页表本身也用页来存放，完美自洽。页表页本身也可以被换出到 swap（虽然内核页表通常常驻）。

**结构示意**（箭头 = "条目里存的物理地址指向"）：

```text
CR3 寄存器(存 PGD 物理地址)
  │
  ▼
┌──────────┐
│   PGD    │  4KB, 512 条目
│  (一级)   │  每条指向一个 PUD 表
└────┬─────┘
     │ PGD[索引] ──▶ ┌──────────┐
     │               │   PUD    │  4KB, 512 条目
     │               │  (二级)   │  每条指向一个 PMD 表
     │               └────┬─────┘
     │                    │ PUD[索引] ──▶ ┌──────────┐
     │                    │               │   PMD    │  4KB, 512 条目
     │                    │               │  (三级)   │  每条指向一个 PTE 表
     │                    │               └────┬─────┘
     │                    │                    │ PMD[索引] ──▶ ┌──────────┐
     │                    │                    │               │   PTE    │  4KB, 512 条目
     │                    │                    │               │  (四级)   │  每条指向一个物理页框
     │                    │                    │               └────┬─────┘
     │                    │                    │                    │ PTE[索引]
     │                    │                    │                    ▼
     │                    │                    │               ┌──────────┐
     │                    │                    │               │ 物理页框  │  4KB
     │                    │                    │               │ (目标数据) │
     │                    │                    │               └──────────┘
```

**关键性质**：
- 每个进程有自己的 PGD（CR3 指向当前进程的 PGD），进程切换时 CR3 切到新进程的 PGD 物理地址——这就实现了地址空间隔离。
- 未使用的虚拟地址区间，对应的条目标记为「不存在」，后面的表根本就不分配。一个 PGD 条目覆盖 512GB 虚拟地址范围（9+9+9+9+12=48，PGD 每项管 2^(9+9+9+12) = 512GB），绝大多数 PGD 条目都是空的。

#### 1.5 一次完整的翻译过程（带具体数字）

假设程序访问虚拟地址 `0x00007F_A1B2_C000`，走一遍完整翻译：

**第 0 步：拆地址**

```
0x00007F_A1B2_C000 的二进制（只关心低 48 位）:

0000 0000 0000 0000  0111 1111  1010 0001  1011 0010  1100 0000 0000 0000
├─────────────────┼──────────┼──────────┼──────────┼──────────┼────────────┤
│  高16位(全0)     │  PGD     │  PUD     │  PMD     │  PTE     │  offset    │
│  符号扩展        │ 9 bits   │ 9 bits   │ 9 bits   │ 9 bits   │  12 bits   │
└─────────────────┴──────────┴──────────┴──────────┴──────────┴────────────┘
```

手工拆（每 9 位一组从高往低）：
- PGD 索引 = bits 47..39 = `0 0111 1111` = **0x0FF**（十进制 255）
- PUD 索引 = bits 38..30 = `1 1010 0001` = **0x1A1**（十进制 417）
- PMD 索引 = bits 29..21 = `1 0110 0101` = **0x165**（十进制 357）
- PTE 索引 = bits 20..12 = `1 0000 0000` = **0x100**（十进制 256）
- offset = bits 11..0 = `0x000`

**第 1 步：查 PGD（一级）**

```text
CR3 → PGD 表物理地址（如 0x1000_0000）
PGD[255] = 读物理地址 0x1000_0000 + 255 × 8 = 0x1000_07F8 处的 8 字节
         → 得到 PUD 表的物理地址（如 0x2000_0000）
         → 同时检查: P 位(存在位)? R/W 位? U/S 位(用户/内核)?
           如果 P=0 → 缺页中断！
```

**第 2 步：查 PUD（二级）**

```text
PUD 表物理地址 = 0x2000_0000（从 PGD 条目获得）
PUD[417] = 读物理地址 0x2000_0000 + 417 × 8 = 0x2000_0D08 处的 8 字节
         → 得到 PMD 表的物理地址（如 0x3000_0000）
         → 同样检查各项权限位
```

**第 3 步：查 PMD（三级）——这是两条路的分叉口**

```text
PMD 表物理地址 = 0x3000_0000（从 PUD 条目获得）
PMD[357] = 读物理地址 0x3000_0000 + 357 × 8 = 0x3000_0B28 处的 8 字节

此时 MMU 检查 PMD 条目的 PS（Page Size）位，决定接下来走哪条路：
```

PMD 是翻译流水线的**分叉口**——内核建立映射时就写死了走哪条路。PS 位是开关：

| PS 位 | PMD 条目里存的是什么 | MMU 下一步 | 最终物理页大小 |
|:---|:---|:---|:---|
| **PS = 0** | 下一级 PTE 表的物理地址 | 继续第 4 步，查 PTE 表 | **4KB**，PTE 指向物理页框 |
| **PS = 1** | 2MB 大页的物理起始地址 | **到此为止，不查 PTE** | **2MB**，PTE 表根本不存在 |

也就是同样的 PMD 条目，可以扮演两种角色：

```text
PS = 0（普通 4KB 页）:           PS = 1（2MB 大页 / HugePage）:
                                 
PGD ──→ PUD ──→ PMD ──→ PTE ──→ 4KB 物理页    PGD ──→ PUD ──→ PMD ──→ 2MB 物理页
                 ↑ 中间节点                  ↑ 叶子节点
                 指向下一级表                 直接指向物理页
```

**2MB 大页时，虚拟地址的解读也不同：**

```text
4KB 页地址拆分:                  2MB 大页地址拆分:
┌─────┬─────┬─────┬─────┬──────┐  ┌─────┬─────┬─────┬──────────────┐
│ PGD │ PUD │ PMD │ PTE │ off  │  │ PGD │ PUD │ PMD │    offset     │
│ 9b  │ 9b  │ 9b  │ 9b  │ 12b  │  │ 9b  │ 9b  │ 9b  │    21 bits    │
└─────┴─────┴─────┴─────┴──────┘  └─────┴─────┴─────┴──────────────┘
        PTE 索引 + 页内偏移 = 12 位        原来的 PTE 索引(9b) + 页内偏移(12b) = 21 位
        各管各的                            全部合并做大偏移
```

**什么场景用哪种？**

| 场景 | 页大小 | 谁决定的 |
|:---|:---|:---|
| 普通 `malloc`、栈、常规 `mmap` | 4KB | 默认，内核分配 4KB 页，PMD 条目 PS=0 |
| `mmap(..., MAP_HUGETLB)` | 2MB（或 1GB） | 程序显式申请大页 |
| 透明大页（THP） | 2MB | 内核后台自动把连续 512 个 4KB 页合并成 1 个 2MB 大页，修改 PMD 条目：PS 设 1，指向合并后的 2MB 物理块，原来的 PTE 表释放掉 |

> **为什么 THP 要"合并"？** 比如一个进程 `malloc` 了 2MB 内存并频繁随机访问，内核起初按 4KB 页分配（PS=0，有完整 PTE 表）。后台 khugepaged 线程发现这 512 个 4KB 页在物理内存里恰好连续，就把它升级：修改 PMD 条目直接指向 2MB 物理起始地址、PS 置 1、释放原来的 PTE 表。效果：TLB 一个条目覆盖 2MB（vs 512 个条目覆盖同样范围），翻译少走一级，TLB 命中率显著提高。

> **PUD 级别也有完全相同的机制——1GB 大页**：PUD 条目 PS=1 时直接指向 1GB 物理页，PMD 和 PTE 表都不存在，offset 占 30 位。常用于数据库、虚拟机等超大内存场景。

**第 4 步：查 PTE（四级，最后一层）——只在 PS=0 时走这一步**

```text
PTE 表物理地址 = 0x4000_0000（从 PMD 条目获得）
PTE[256] = 读物理地址 0x4000_0000 + 256 × 8 = 0x4000_0800 处的 8 字节
         → 得到目标物理页框号（如 0x0005_A000，即物理页框 0x5A00）
         → 检查: P 位? 如果 P=0 → 缺页中断(minor/major)
         → 检查: Dirty 位? 如果是写操作且 D=0 → 第一次写，置 D=1
         → 检查: Accessed 位? MMU 自动置 A=1（用于 LRU 换页决策）
```

**第 5 步：拼出最终物理地址**

```text
物理页框号 = 0x5A00  ← 这是页框号，实际物理地址 = 页框号 << 12
页内偏移   = 0x000（原样从虚拟地址复制）

物理地址 = (0x5A00 << 12) | 0x000 = 0x05A0_0000
         = [ 物理页框号 0x5A00 | 页内偏移 0x000 ]
```

于是 CPU 用物理地址 `0x05A0_0000` 去内存总线上读写数据。

#### 1.6 页表项（PTE）里到底存了什么

每个 8 字节（64 位）的页表项不光是物理地址，还打包了权限和控制位。以 x86-64 PTE 为例：

```text
PTE 64 bits:
┌──────┬────┬─────┬─────┬───┬───┬───┬───┬───┬───┬───┬────────────────────┐
│ NX   │ 保留│ PFN │ 保留 │ G │ 0 │ D │ A │PCD│PWT│U/S│R/W│ P │           │
│bit63 │     │(高位)│     │   │   │   │   │   │   │   │   │   │           │
└──────┴────┴─────┴─────┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───────────┘
```

| 位 | 名称 | 含义 |
| :--- | :--- | :--- |
| P（bit 0） | Present（存在位） | **1 = 该页在物理内存中；0 = 不在，触发缺页中断** |
| R/W（bit 1） | Read/Write | 1 = 可写；0 = 只读。写只读页 → 缺页（COW 靠这个实现） |
| U/S（bit 2） | User/Supervisor | 0 = 只有内核能访问；1 = 用户态也能访问 |
| A（bit 5） | Accessed | MMU 每次访问自动置 1，OS 可清零来追踪「最近有没有被用」（LRU 依据） |
| D（bit 6） | Dirty | 写访问时 MMU 自动置 1，「这一页被改过」。换出时：D=1 要写回磁盘，D=0 直接丢弃 |
| G（bit 8） | Global | 全局页，进程切换时不刷掉 TLB 中此项（内核页常用） |
| NX（bit 63） | No eXecute | 1 = 这页不可执行代码（栈/heap 上防 shellcode 注入） |
| PFN（高 bits） | Page Frame Number | **物理页框号的物理地址高位**（最多 40 位，支持 1TB 物理内存） |

> **关键认知**：`Present` 位 = 0 不代表「从来没分过物理页」——它只代表「页表项当前无效」。物理页可能已经在内存里（minor fault 只是还没建映射），也可能还在磁盘上（major fault 要读盘）。区分靠的是 PTE 中 P=0 时剩余位的复用编码（内核用它们记录 swap 位置或文件偏移）。

#### 1.7 TLB（Translation Lookaside Buffer）——翻译的「快表」

查 4 级页表，**每次访存都要额外读 4 次内存**（PGD → PUD → PMD → PTE），最后才读/写第 5 次目标数据——如果不加缓存，CPU 访存要慢 5 倍。

**TLB 就是 MMU 内部的硬件缓存**，专门缓存「虚拟页号 → 物理页框号 + 权限位」的翻译结果：

```text
TLB 条目结构（简化）:
┌──────────────────┬──────────────────┬──────────┬───────┐
│  虚拟页号(VPN)    │  物理页框号(PFN)  │  权限位   │  ASID │
│  (用于匹配)       │  (翻译结果)       │ (R/W等)  │(标签) │
└──────────────────┴──────────────────┴──────────┴───────┘
```

**TLB 的工作流程：**

```text
  CPU 发出虚拟地址
        │
        ▼
  ┌─────────────┐
  │ 查 TLB       │  用虚拟页号并行比对 TLB 所有条目（硬件相联查找，1 个周期）
  └──┬──────────┘
     │
   ┌─┴──────────┐
   │ 命中?       │
   └─┬──────────┘
     │
  YES│                          NO (TLB miss)
     ▼                            ▼
  ┌──────────────┐        ┌──────────────────┐
  │ 直接拿到 PFN  │        │ 走多级页表翻译     │
  │ + 检查权限位  │        │ (前面 1.5 的过程)  │
  │ (1 个周期)   │        │ 至少 4 次内存读     │
  └──────────────┘        └────────┬─────────┘
                                   │
                                   ▼
                          ┌──────────────────┐
                          │ 翻译结果写入 TLB   │  (替换掉一条旧条目，如 LRU)
                          │ 下次同样 VPN 就命中│
                          └──────────────────┘
```

**TLB 的核心特性：**

| 特性 | 说明 |
| :--- | :--- |
| **大小极小** | 通常几十到几百条（L1 TLB 约 64 条，L2 TLB 几百到上千条）。所以只缓存「最近用过的」翻译 |
| **命中很快** | 硬件并行比对，1~2 个 CPU 周期；未命中走页表要几十到上百周期 |
| **进程切换代价** | CR3 一换，旧进程的 TLB 条目全部失效（除非用 PCID/ASID 打标签区分进程） |
| **大页的价值** | 一个 2MB 大页 = 512 个 4KB 小页，一个 TLB 条目覆盖 512 倍范围，TLB 命中率大幅提升 |

> **TLB miss → 查页表 → 填 TLB → 重试访问**：整个过程由 **MMU 硬件自动完成**，不需要操作系统介入（只要页表项 P=1 且权限 OK）。OS 只在**缺页中断**（P=0 或权限违规）时才介入。

#### 1.8 完整翻译流程总览（汇总）

把前面所有步骤串起来，CPU 发出一次访存的完整路径：

```text
                        程序访问虚拟地址(如 mov rax, [0x7FA1B2C000])
                                       │
                                       ▼
                              ┌──────────────────┐
                              │   MMU 接管翻译    │
                              └────────┬─────────┘
                                       │
                                 ┌─────▼─────┐
                                 │  查 TLB    │
                                 └─────┬─────┘
                                  ┌────┴────┐
                                  │ 命中?    │
                                  └────┬────┘
                               ┌───────┴───────┐
                               │               │
                              YES             NO
                               │               │
                               ▼               ▼
                    ┌──────────────────┐  ┌──────────────────────────────┐
                    │ 拿到 PFN + 权限   │  │ 逐级查页表:                   │
                    │ 检查权限通过?     │  │ CR3→PGD→PUD→PMD→PTE         │
                    └────────┬─────────┘  │ 每级检查 P 位 + 权限          │
                         ┌───┴───┐        └──────────────┬───────────────┘
                         │通过?   │                  ┌────┴────┐
                         └───┬───┘                  │ PTE.P=1? │
                      ┌──────┴──────┐               └────┬────┘
                      │              │             ┌──────┴──────┐
                     YES            NO            │              │
                      │              │           YES             NO
                      │              │            │              │
                      ▼              ▼            ▼              ▼
               ┌──────────┐  ┌──────────┐ ┌──────────┐  ┌──────────────┐
               │拼物理地址 │  │段错误     │ │翻译结果   │  │触发缺页中断   │
               │PFN+offset│  │SIGSEGV   │ │填入 TLB  │  │CPU 陷入内核   │
               │送内存总线 │  │(如写只读)│ │然后重试   │  │内核处理完后   │
               │读写数据   │  └──────────┘ │(下次TLB命中)│ │重新执行指令   │
               └──────────┘               └──────────┘  └──────────────┘
```

**三个关键延迟的量级感**：

| 路径 | 延迟（近似） | 说明 |
| :--- | :--- | :--- |
| TLB 命中 | ~1-2 CPU 周期 | 硬件并行匹配，不额外访存 |
| TLB miss + 页表全在 cache | ~20-50 周期 | 4 次额外内存读，但如果页表数据在 L1/L2 cache 里还算快 |
| TLB miss + 页表不在 cache | ~100-200 周期 | 4 次内存读都要访问 DRAM |
| 缺页中断（minor） | ~数微秒 | 内核建映射，不读盘 |
| 缺页中断（major） | ~数毫秒 | 要读磁盘/SSD |

#### 1.9 一句话总结

> **MMU 做硬件翻译（查 TLB → 未命中走多级页表 → 缺页时陷入内核），多级页表用「层级索引 + 按需创建」节省页表本身的空间，TLB 缓存翻译结果让绝大多数访存只需 1 个周期完成翻译。三者配合，让虚拟内存的开销低到几乎可以忽略。**

| 名词 | 含义 | 一句话 |
| :--- | :--- | :--- |
| 页 page | 虚拟内存的分配单位，默认 4KB | 软件视角的内存块 |
| 页框 frame | 物理内存的分配单位，4KB | 硬件/内存条上的内存块 |
| 页表 page table | 「虚拟页号 → 物理页框号」的多级映射表 | 每进程一套，OS 建立、MMU 查 |
| PGD/PUD/PMD/PTE | 四级页表各层的名称 | x86-64 4KB 页的 4 级索引 |
| MMU | Memory Management Unit | CPU 内部的地址翻译硬件 |
| TLB | Translation Lookaside Buffer | 翻译结果的高速缓存，查页表前先查它 |
| CR3 | 控制寄存器，存当前进程 PGD 物理地址 | 进程切换时改它 = 换整套页表 |
| P 位（Present） | 页表项的「有效位」 | 0 = 该页不可直接访问（触发缺页中断） |
| HugePage | 2MB / 1GB 大页 | 减少页表层数 + 提高 TLB 覆盖率 |
| PCID/ASID | 给 TLB 条目打进程标签 | 避免进程切换时全刷 TLB |

### 2. 进程地址空间布局（32 位经典视图，64 位空洞更大）

```text
  高地址 ┌─────────────────────────┐ 0xFFFFFFFF...
        │      内核空间 kernel      │  用户态不可访问
        ├─────────────────────────┤
        │         栈 stack         │  ↓ 向下增长(函数调用帧、局部变量)
        │            ↓             │
        │                          │
        │      (未映射的空洞)        │  ← 缺页访问这里 → 段错误 SIGSEGV
        │                          │
        │            ↑             │
        │   mmap 区 (mmap region)   │  共享库.so、文件映射、大块malloc
        ├─────────────────────────┤
        │            ↑             │
        │          堆 heap         │  ↑ 向上增长(malloc/brk)
        ├─────────────────────────┤
        │     .bss (未初始化全局)    │  不占文件体积，加载清零
        ├─────────────────────────┤
        │     .data (已初始化全局)   │  占文件体积
        ├─────────────────────────┤
        │     .text (代码,只读)      │  指令,常多进程共享同一份物理页
  低地址 └─────────────────────────┘ 0x00000000
```

查看真实布局：`cat /proc/self/maps` 或 `pmap <pid>`。

### 3. malloc 的两条路与「free 不还 OS」

```text
malloc(size)
   │
   ├─ size <  M_MMAP_THRESHOLD(默认128KB) ─▶ 堆: 先查 arena 空闲bins
   │                                          有则复用; 无则 brk 抬高堆顶
   │                                          free → 放回 bins (RSS 通常不降!)
   │
   └─ size >= 阈值 ──────────────────────▶ mmap 一段匿名映射
                                            free → munmap 直接还 OS (RSS 降)
```

**为什么 free 小块后 RSS 不降**：堆是连续的，只有紧贴堆顶的空闲块能通过下移 brk 还给 OS；中间块被占着，堆顶下不去（外部碎片），空闲块只能留在 bins 里复用。`malloc_trim(0)` 可主动尝试回缩。

### 4. 内存碎片：内部 vs 外部

| 碎片类型 | 成因 | 例子 |
| :--- | :--- | :--- |
| 内部碎片 internal | 分配器按规格对齐取整，给的比要的多 | 要 33 字节，分配器给 48 字节的规格块，浪费 15 |
| 外部碎片 external | 空闲块总量够，但被切得太碎、不连续，凑不出大块 | free 出很多 16 字节空隙，却分不出一个 1KB |

智能硬件长跑进程最怕外部碎片累积，**内存池 / 定长对象池**（见 cpp 库 [[22-自定义分配器与内存池]]）就是为了消灭碎片、避免 malloc 抖动。

### 5. COW 写时复制时序

```text
fork() 后:
  父页表 ─┐
          ├──▶ 同一物理页 (标记为只读 read-only, 引用计数=2)
  子页表 ─┘

子进程写这一页:
  写只读页 → 缺页中断(minor fault) → 内核复制该页 → 子页表指向新副本(可写)
  父页表仍指原页; 若引用计数回到1, 原页恢复可写
```

### 6. page cache 与脏页回写

```text
write(fd,...) ─▶ 数据先进 page cache (标记脏页 dirty)
                      │
                      ├─ 后台 pdflush/writeback 线程按策略刷盘
                      ├─ fsync()/fdatasync() 强制刷盘
                      └─ 内存紧张时回收干净页(clean直接丢, dirty先刷再丢)

read(fd,...)  ─▶ 命中 page cache 直接返回(无磁盘IO)
                 未命中 → major fault 读盘 → 填进 page cache → 返回
```

**与音视频大文件的关系**：连续读写大媒体文件会把 page cache 撑满（`free` 里 buff/cache 飙高，正常）。但在内存受限的盒子上，一次性顺序读完即弃的大文件，page cache 全留着没意义还挤占内存——可用 `posix_fadvise(POSIX_FADV_DONTNEED)` 或 `O_DIRECT` 绕过 page cache，避免缓存污染。

## 三、代码与命令示例

### 1. 观察缺页：第一次写才真正占物理页

```c
#include <stdlib.h>
#include <string.h>

int main(void) {
    const size_t totalBytes = 256 * 1024 * 1024;   // 申请 256MB
    char *buffer = malloc(totalBytes);              // 此刻 VSZ 涨, RSS 几乎不动
                                                    // 内核只登记虚拟区间, 没给物理页
    // 逐页写第一个字节 → 每页触发一次 minor fault, 真正分配物理页
    const size_t pageSize = 4096;
    for (size_t offset = 0; offset < totalBytes; offset += pageSize) {
        buffer[offset] = 1;                         // 写访问触发缺页, RSS 此刻才涨
    }
    free(buffer);                                   // 大块 → munmap, RSS 降回去
    return 0;
}
```

```bash
# 编译后用 /usr/bin/time -v 看 "Maximum resident set size" 和缺页次数
/usr/bin/time -v ./a.out
# Minor (reclaiming a frame) page faults: 65536   ← 256MB/4KB ≈ 6.5万次缺页
```

### 2. 关键排查命令速查

```bash
# ── 进程级 ──
top                         # RES 列 = RSS(物理常驻); VIRT = VSZ(虚拟)
ps -o pid,vsz,rss,cmd       # 一眼看 VSZ vs RSS 差距
pmap -x <pid>               # 各段映射明细 + RSS/Dirty 分布
cat /proc/<pid>/status      # VmSize(VSZ)/VmRSS(RSS)/VmSwap 等
cat /proc/<pid>/smaps       # 最细: Pss/Private_Dirty/Shared_Clean ... 算 PSS/USS
ps -o min_flt,maj_flt <pid> # 次缺页/主缺页计数, maj 高=在颠簸或冷读盘

# ── 整机级 ──
free -h                     # 看 available(真正可用), 别被 used/buff/cache 吓到
cat /proc/meminfo           # MemAvailable / Dirty / Writeback / SwapFree ...
vmstat 1                    # si/so 列 = swap in/out, 非零且持续=在颠簸
dmesg | grep -i oom         # 查是否发生过 OOM kill 及被杀进程

# ── 内存问题定位 ──
valgrind --leak-check=full ./a.out     # 抓真泄漏(慢, 离线用)
# 编译期开 Sanitizer(快, 推荐):
gcc -fsanitize=address -g app.c        # ASan, 越界/UAF/泄漏
gcc -fsanitize=leak    -g app.c        # LSan, 专抓泄漏
```

### 3. mmap 文件映射示例（零拷贝读）

```c
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>

int fileDescriptor = open("video.dat", O_RDONLY);
off_t fileSize = lseek(fileDescriptor, 0, SEEK_END);

// 文件私有映射: 内容直接映射 page cache, 访问指针即读文件(省一次拷贝)
char *mapped = mmap(NULL, fileSize, PROT_READ, MAP_PRIVATE, fileDescriptor, 0);
// 第一次访问每页 → major fault 读盘填 page cache; 之后命中 cache 很快
char firstByte = mapped[0];

munmap(mapped, fileSize);
close(fileDescriptor);
```

匿名共享映射可用于父子进程通信（配合 fork），细节见 [[05-进程间通信IPC]]。

## 四、常见坑与面试加分点

| 坑 / 误区 | 真相 |
| :--- | :--- |
| 看 VSZ 判断内存占用 | VSZ 是虚拟空间总和，含没用的，看 RSS/PSS |
| `free` 后 RSS 不降就说泄漏 | glibc 不一定还 OS，小块留 bins 复用，正常 |
| `free -h` 里 used 高就慌 | 看 **available**；buff/cache 是可回收的 page cache |
| 把所有进程 RSS 相加估内存 | 共享页被重复计，应该用 PSS |
| 以为 mmap 一定比 read 快 | 随机小访问缺页开销可能更大，看场景 |
| malloc 大数组立刻占物理内存 | 不写就不占，缺页时才分页（overcommit） |
| 栈上开几 MB 大数组 | 栈通常 8MB 上限，爆栈直接 SIGSEGV，大缓冲用堆 |
| 嵌入式开 swap 求稳 | 反而磨损 Flash、引入抖动，多数关 swap + 内存池兜底 |

**加分句（智能硬件 + 音视频）：**

> "内存受限的盒子上，我不依赖 swap，而是给视频帧缓冲做**定长内存池**：启动时预分配一批帧 buffer 循环复用，避免每帧 `malloc/free` 带来的缺页和外部碎片，既消除了运行时的内存抖动，又让内存占用有明确上界，配合 `oom_score_adj` 保护采集主进程不被误杀。内存对齐到 cache line 的细节走 [[09-多核架构与缓存一致性]] 和 cpp 库 [[21-内存对齐、SIMD与缓冲管理]]。"

## 六、自测 8 题

1. VSZ、RSS、PSS 三者区别？统计整机真实占用看哪个？
2. minor fault 和 major fault 的本质区别是什么？
3. 为什么 `malloc` 完一大块、`top` 里 RSS 没怎么涨？
4. `free` 了内存但 RSS 不降，一定是泄漏吗？怎么判断真泄漏？
5. `free -h` 里 buff/cache 很大、used 很高，是问题吗？看哪一列？
6. mmap 为什么能少一次拷贝？什么情况下它反而不如 read？
7. fork 用了什么机制避免复制整个地址空间？写的时候发生什么？
8. 嵌入式设备为什么常关 swap？不关会有什么问题？

<details>
<summary>参考答案</summary>

1. VSZ 是虚拟地址空间总和（含未用）；RSS 是实际物理常驻（但共享页被各进程重复计）；PSS 把共享页按进程数平摊。整机真实占用看 **PSS**。
2. minor：物理页已在内存，只是没建当前进程页表映射，不读盘；major：内容在磁盘（mmap 文件页首访问、swap 换回），必须发起磁盘 I/O。
3. malloc 只登记了虚拟地址区间（overcommit），没真正分物理页；**只有写访问触发缺页时**才逐页分配物理页，RSS 那时才涨。
4. 不一定。glibc 把空闲小块留在 bins 里复用、不一定还 OS，堆顶被占下不去也降不了。判断真泄漏看**持续单调增长不回落**，并用 valgrind / ASan-LSan 抓「分配了却 free 不掉」的点。
5. 不是问题。buff/cache 是 page cache，内核拿空闲内存缓存文件加速 I/O，可回收。看 **available** 列才是真正可用内存。
6. 普通 read 是「磁盘→page cache→用户缓冲区」两次拷贝，mmap 把 page cache 页直接映射进用户空间省掉后一次。随机小量访问时每页缺页（major fault + 建页表）开销可能比 read 顺序大块拷贝更高，此时不如 read。
7. **COW（写时复制）**：fork 只复制页表，父子共享同一批物理页并标记只读；任一方写某页时触发缺页中断，内核复制那一页、改可写，各自指向自己的副本。
8. 设备多用 eMMC/Flash，swap 频繁写**磨损寿命**且慢，还引入**不可预测的延迟停顿**破坏实时性。不关：内存紧张时颠簸（thrashing）导致性能断崖、卡顿。多数选择关 swap + 内存池控上界 + 明确 OOM。

</details>
