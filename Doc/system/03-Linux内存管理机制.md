## 📌 第一部分：面试速记（考前 12 分钟扫一遍）

### 一句话核心

> **Linux 给每个进程一份独立的「虚拟地址空间」，靠 MMU + 多级页表把虚拟地址翻译成物理地址，物理内存以「页（4KB）」为单位按需分配（缺页时才真正给物理页）。所以「申请了内存」和「占了物理内存」是两回事——这就是 VSZ（虚拟）和 RSS（物理）差很多的根因，也是排查内存问题的总纲。**

### 面试官常问问题 + 标准口语化回答

---

#### 开场题：用一句话说清楚 Linux 的内存管理在管什么？

**🗣️ 面试标准回答：**

> "它管两件事：一是**地址隔离**——每个进程看到的都是从 0 开始、连续完整的虚拟地址空间，互相看不见对方，靠页表各自映射到不同的物理页；二是**按需供给**——物理内存以 4KB 的页为单位，进程 `malloc` 或映射时只是登记了虚拟地址，真正访问到某一页时才触发缺页中断、分配物理页。中间的翻译由硬件 MMU 完成，TLB 缓存最近的翻译结果加速。"

---

#### 必考题：虚拟地址和物理地址什么关系？为什么要搞虚拟内存？

**考察意图：** 这是整篇的地基，答不清楚后面 RSS/缺页/COW 全说不明白。

**🗣️ 面试标准回答：**

> "程序里所有指针拿到的都是**虚拟地址**，CPU 执行访存时，MMU 拿这个虚拟地址查页表，翻译成真正的**物理地址**再去访问内存条。三个核心好处：
>
> 1. **隔离与安全**：每个进程一套独立页表，进程 A 的虚拟地址 0x400000 和进程 B 的同一个地址映射到完全不同的物理页，进程之间踩不到对方，内核空间也映射成用户态不可访问。
> 2. **按需分配 + 超额承诺**：虚拟空间可以开得很大（64 位下 128TB 用户空间），但只在真正访问时才分物理页，物理内存可以「超卖」。
> 3. **灵活映射**：同一份物理页可以映射进多个进程（共享库、共享内存、COW），磁盘文件可以映射进地址空间（mmap），物理内存碎片也能用页表拼成连续的虚拟地址。
>
> 一句话：**虚拟内存是物理内存之上的一层间接，换来了隔离、按需、共享这三件事。**"

**👨‍💻 面试官追问：**

> Q: 虚拟地址空间那么大，页表不会很大吗？
> A: 所以用**多级页表**——只有真正用到的那部分虚拟地址才建立对应的页表项，没映射的区域连页表中间层都不创建，页表本身也是按需分配的。

---

#### 必考题：什么是分页？MMU 怎么把虚拟地址翻译成物理地址？

**🗣️ 面试标准回答：**

> "内存被切成固定大小的**页**（Linux 默认 4KB），物理内存对应叫**页框**。页表是「虚拟页号 → 物理页框号」的映射表。翻译时，MMU 把虚拟地址拆成『页号 + 页内偏移』，用页号查页表拿到物理页框号，再拼上偏移得到物理地址。
>
> 64 位实际用**多级页表**（x86-64 常见 4 级：PGD/PUD/PMD/PTE），逐级查下去，避免一张大表浪费空间。每次访存都查页表太慢，所以有 **TLB（快表）**——缓存最近用过的『虚拟页→物理页』翻译结果，命中就一步到位，不用走多级页表。"

**👨‍💻 面试官追问：**

> Q: TLB 命中率为什么重要？换页表（进程切换）时 TLB 怎么办？
> A: TLB 未命中要走多级页表（一次翻译多次访存），命中率直接影响访存速度。进程切换换了页表，TLB 整体失效（除非用 PCID/ASID 给 TLB 项打进程标签来避免全刷）。**大页（HugePage，2MB）**能让一个 TLB 项覆盖更大范围，提高命中率，常用于数据库、大缓冲场景。

---

#### 必考题：缺页中断（page fault）是什么？minor 和 major 有什么区别？

**🗣️ 面试标准回答：**

> "访问一个虚拟地址，但它在页表里没有对应的有效物理页时，MMU 触发**缺页中断**，陷入内核由缺页处理程序补救。分两种：
>
> - **minor fault（次缺页）**：物理页其实已经在内存里，只是当前进程页表还没建立映射。比如刚 `malloc` 后第一次写、共享库已被别的进程加载进内存、COW 触发复制——不用读磁盘，只改页表，很快。
> - **major fault（主缺页）**：内容还在磁盘上，必须发起磁盘 I/O 读进来。比如 mmap 的文件页第一次访问、被换出到 swap 的页又被访问——慢，因为有磁盘 I/O。
>
> 排查时 `ps -o min_flt,maj_flt` 或 `/proc/pid/stat` 能看两类计数，**major fault 飙高**往往意味着内存不够在颠簸（swap）或大量冷文件读。"

---

#### 必考题：VSZ、RSS、PSS 有什么区别？（高频中的高频）

**🗣️ 面试标准回答：**

> "都是 `top`/`ps` 里的内存指标，区别在『算的是虚拟还是物理、共享怎么摊』：
>
> - **VSZ（虚拟内存大小）**：进程虚拟地址空间总和，包括 `malloc` 了还没用的、mmap 的文件、未触发缺页的部分。**VSZ 大不代表占了那么多物理内存**，参考价值有限。
> - **RSS（常驻内存）**：实际占用的物理页大小（`top` 的 RES 列）。但有个坑——**共享内存/共享库被多个进程各自的 RSS 重复计算**，把所有进程 RSS 加起来会超过实际物理内存。
> - **PSS（按比例摊分）**：私有页全算自己的，共享页按共享进程数平摊。比如一个 4KB 页被 4 个进程共享，每个进程的 PSS 只算 1KB。**统计整机真实内存占用、做容量规划时 PSS 最准。**
>
> 口诀：**VSZ 是『画了多大的饼』，RSS 是『真吃了多少（但共享重复算）』，PSS 是『公平摊分后真正属于我的那份』。** PSS 在 `/proc/pid/smaps` 里看。"

**👨‍💻 面试官追问：**

> Q: 那看一个进程到底「私有占了多少」看哪个？
> A: smaps 里的 **`Private_Dirty` + `Private_Clean`**（USS，私有常驻）最能反映「杀掉这个进程能直接回收多少物理内存」。

---

#### 必考题：`malloc` 是怎么实现的？brk 和 mmap 各管什么？

**🗣️ 面试标准回答：**

> "`malloc` 是 C 库（glibc 用 ptmalloc）的用户态分配器，它向内核要的是『大块内存』，再切小块给你。两条拿内存的路：
>
> - **小块（默认 < 128KB，`M_MMAP_THRESHOLD`）**：在**堆**上分配，通过 `brk`/`sbrk` 移动堆顶指针扩展堆，或直接从 glibc 维护的 **arena（空闲链表 / bins）** 里复用已经释放的小块。
> - **大块（≥ 阈值）**：直接 `mmap` 向内核要一段匿名映射，`free` 时直接 `munmap` 还给内核。
>
> 关键点：**`free` 不等于把内存还给操作系统**。小块 free 后通常只是回收进 glibc 的空闲链表等着复用，堆顶（brk）不一定下移，所以**进程 RSS 释放后不降是正常的**。多线程下 glibc 还会开多个 arena 减少锁竞争。"

**👨‍💻 面试官追问：**

> Q: 那为什么我 `free` 了一大堆内存，`top` 里 RES 还是不降？是泄漏吗？
> A: 不一定是泄漏。glibc 把空闲小块留在自己的 bins 里复用，只有堆顶连续的大段空闲才可能通过 `malloc_trim` 或 brk 回缩还给 OS；中间被占着的块导致堆顶下不去（外部碎片）。真要还可以调 `malloc_trim(0)`。**判断泄漏要看『长期持续增长且不回落』，而不是『free 后没立刻降』。**

---

#### 必考题：怎么区分「内存泄漏」和「内存只是没还给 OS / 正常占用」？

**🗣️ 面试标准回答：**

> "看三个维度：
>
> 1. **趋势**：泄漏是**单调持续增长、压力下不回落**；正常占用会随负载涨跌、稳定在一个水位。盯一段时间的 RSS 曲线比看一个瞬时值有用。
> 2. **工具定位**：`valgrind --leak-check` 或编译时开 **ASan/LSan**，能直接报『哪行分配的内存没释放』。这是真泄漏（指针丢了，永远 free 不掉）的铁证。
> 3. **区分『没还 OS』**：如果 valgrind 说没泄漏，但 RSS 高，那多半是 glibc 没把空闲块还给 OS，或者是 page cache（不算进程的）。可以 `malloc_trim` 看能不能降一部分。
>
> 一句话：**真泄漏 = 程序再也访问不到、也 free 不掉的内存（工具能抓）；假泄漏 = free 了但留在分配器/缓存里，可被复用。**"

---

#### 高频题：`free` 命令里 buff/cache 占了很多，是内存泄漏吗？

**🗣️ 面试标准回答：**

> "**不是，那是 page cache，是内核拿空闲内存帮你缓存文件加速 I/O，属于『可回收』内存。** `free -h` 里要看 **available** 那一列才是真正还能用的——它已经把可回收的 cache 算进去了。`used` 高、`free` 低但 `available` 充足，完全正常。内存一紧张，内核会自动回收 page cache。所以『buff/cache 高』恰恰说明内存被有效利用了，不是泄漏。新手常被 `free` 列吓到，记住**看 available 不看 free**。"

---

#### 高频题：mmap 是什么？为什么能「零拷贝」？一定比 read 快吗？

**🗣️ 面试标准回答：**

> "`mmap` 把一段内容映射进进程虚拟地址空间，之后像访问数组一样用指针读写。分类两个维度：
>
> - **文件映射 vs 匿名映射**：文件映射关联磁盘文件（读文件、共享库加载）；匿名映射没有后备文件（大块 malloc、`MAP_ANONYMOUS`）。
> - **共享（MAP_SHARED）vs 私有（MAP_PRIVATE）**：共享映射的写会回写到文件、对其他映射者可见（IPC 用）；私有映射的写触发 COW，不影响原文件。
>
> **为什么算零拷贝**：普通 `read` 是『磁盘 → page cache → 用户缓冲区』两次拷贝；mmap 直接把 page cache 的页映射进用户地址空间，省掉了内核到用户的那次拷贝，用户指针直接指向 page cache。
>
> **但不一定比 read 快**：mmap 第一次访问每页都触发缺页中断（major fault + 建页表），随机小量访问时缺页开销可能比 read 的顺序大块拷贝还高。**大文件随机访问、需要多进程共享同一份文件**时 mmap 划算；顺序流式读小文件，`read`/`pread` 往往更简单更快。"

**👨‍💻 面试官追问（音视频向）：**

> Q: 处理大视频文件你会用 mmap 吗？
> A: 看场景。需要在文件里跳着随机 seek（如索引、关键帧定位）、或多进程/线程共享同一份只读资源时，mmap 省一次拷贝又省内存；但纯顺序解码、边读边丢的流式场景，`read` + 自己的环形缓冲更可控，还能避免缺页抖动。详见下文 page cache 与音视频。

---

#### 高频题：什么是写时复制 COW？fork 怎么用它？

**🗣️ 面试标准回答：**

> "**Copy-On-Write**：fork 出子进程时，不真的复制父进程的物理内存，而是让父子的页表都指向**同一批物理页，并把这些页标记为只读**。读没事，照常共享；任何一方**写**某页时触发缺页中断，内核这才**复制那一页**、改成可写、各自映射自己的副本。
>
> 好处：fork 几乎是瞬时的（只复制页表，不复制几 GB 数据），而且 `fork + exec` 场景下子进程马上换掉整个地址空间，复制了纯属浪费——COW 完美匹配。代价是 fork 后第一次写会有一波缺页。
>
> 调用侧细节在 [[02-进程管理与多进程编程]]，这里只讲原理：**COW = 共享 + 只读标记 + 写时触发缺页复制。**"

---

#### 高频题：swap 和 OOM killer 是什么？嵌入式为什么常关 swap？

**🗣️ 面试标准回答：**

> "**swap** 是把不常用的物理页换出到磁盘，腾出物理内存，需要时再换回（换回就是 major fault）。物理内存够时 swap 用得少，紧张时靠它续命，但频繁换进换出会**颠簸（thrashing）**，性能断崖。
>
> **OOM killer**：当物理内存和 swap 都耗尽、内核实在分不出页时，会选一个进程杀掉来保命。选谁看 **oom_score**——大致是『占内存越多、越不重要的越容易被杀』，可以通过 `/proc/pid/oom_score_adj` 调整（设很低保护关键进程，设很高让它优先被杀）。
>
> **嵌入式/智能硬件常关 swap**：一是很多设备用 eMMC/Flash，swap 频繁写会**磨损寿命**且慢；二是要**确定性延迟**，swap 引入的不可预测停顿对实时性是灾难。所以嵌入式更倾向『内存用满就明确 OOM，而不是偷偷 swap 拖慢』，靠精打细算内存预算 + 内存池来兜底。"

---

#### 原理题：进程地址空间从低到高是怎么布局的？

**🗣️ 面试标准回答：**

> "从低地址到高地址：**代码段（.text，只读可执行）→ 数据段（.data 已初始化全局/静态变量、.bss 未初始化清零）→ 堆（向上增长，brk 管）→ mmap 区（共享库、文件映射、大块 malloc）→ 栈（向下增长）→ 内核空间（用户态不可访问）**。堆和栈相向增长，中间是巨大的未映射空洞。`.bss` 不占文件体积（只记大小，加载时清零）。详细 ASCII 图见下文原理详解。"

## 二、原理详解

### 1. 虚拟地址 → 物理地址：MMU + 多级页表 + TLB

```text
   程序里的指针(虚拟地址)
          │
          ▼
  ┌───────────────┐  命中  ┌──────────────┐
  │     TLB       │ ─────▶ │  物理页框号    │  (快路径,一步到位)
  │ (虚拟页→物理页) │        └──────────────┘
  └───────┬───────┘
          │ 未命中(TLB miss)
          ▼
  多级页表逐级查找 (x86-64: PGD→PUD→PMD→PTE)
          │
   ┌──────┴───────┐
   │ 页表项有效?   │
   └──────┬───────┘
     有效 │        │ 无效 → 缺页中断(page fault) → 内核补页/读盘
          ▼
   物理页框号 + 页内偏移 = 物理地址
```

地址拆分（页大小 4KB，偏移占低 12 位，因为 2^12 = 4096）：

```text
虚拟地址(48位有效) = [ 页号 virtualPageNumber (高36位) | 页内偏移 offset (低12位) ]
物理地址            = [ 页框号 frameNumber          | 页内偏移 offset (原样保留) ]
```

| 名词 | 含义 | 一句话 |
| :--- | :--- | :--- |
| 页 page | 虚拟内存的分配单位，默认 4KB | 软件视角的内存块 |
| 页框 frame | 物理内存的分配单位，4KB | 硬件视角的内存块 |
| 页表 page table | 页号 → 页框号 的映射 | 每进程一套 |
| MMU | 做翻译的硬件 | CPU 里的地址翻译器 |
| TLB | 翻译结果的缓存 | 命中则跳过查页表 |
| HugePage | 2MB/1GB 大页 | 一个 TLB 项覆盖更大，减 miss |

### 2. 进程地址空间布局（32 位经典视图，64 位空洞更大）

```text
  高地址 ┌─────────────────────────┐ 0xFFFFFFFF...
        │      内核空间 kernel      │  用户态不可访问
        ├─────────────────────────┤
        │         栈 stack         │  ↓ 向下增长(函数调用帧、局部变量)
        │            ↓             │
        │                          │
        │      (未映射的空洞)        │  ← 缺页访问这里 → 段错误 SIGSEGV
        │                          │
        │            ↑             │
        │   mmap 区 (mmap region)   │  共享库.so、文件映射、大块malloc
        ├─────────────────────────┤
        │            ↑             │
        │          堆 heap         │  ↑ 向上增长(malloc/brk)
        ├─────────────────────────┤
        │     .bss (未初始化全局)    │  不占文件体积，加载清零
        ├─────────────────────────┤
        │     .data (已初始化全局)   │  占文件体积
        ├─────────────────────────┤
        │     .text (代码,只读)      │  指令,常多进程共享同一份物理页
  低地址 └─────────────────────────┘ 0x00000000
```

查看真实布局：`cat /proc/self/maps` 或 `pmap <pid>`。

### 3. malloc 的两条路与「free 不还 OS」

```text
malloc(size)
   │
   ├─ size <  M_MMAP_THRESHOLD(默认128KB) ─▶ 堆: 先查 arena 空闲bins
   │                                          有则复用; 无则 brk 抬高堆顶
   │                                          free → 放回 bins (RSS 通常不降!)
   │
   └─ size >= 阈值 ──────────────────────▶ mmap 一段匿名映射
                                            free → munmap 直接还 OS (RSS 降)
```

**为什么 free 小块后 RSS 不降**：堆是连续的，只有紧贴堆顶的空闲块能通过下移 brk 还给 OS；中间块被占着，堆顶下不去（外部碎片），空闲块只能留在 bins 里复用。`malloc_trim(0)` 可主动尝试回缩。

### 4. 内存碎片：内部 vs 外部

| 碎片类型 | 成因 | 例子 |
| :--- | :--- | :--- |
| 内部碎片 internal | 分配器按规格对齐取整，给的比要的多 | 要 33 字节，分配器给 48 字节的规格块，浪费 15 |
| 外部碎片 external | 空闲块总量够，但被切得太碎、不连续，凑不出大块 | free 出很多 16 字节空隙，却分不出一个 1KB |

智能硬件长跑进程最怕外部碎片累积，**内存池 / 定长对象池**（见 cpp 库 [[22-自定义分配器与内存池]]）就是为了消灭碎片、避免 malloc 抖动。

### 5. COW 写时复制时序

```text
fork() 后:
  父页表 ─┐
          ├──▶ 同一物理页 (标记为只读 read-only, 引用计数=2)
  子页表 ─┘

子进程写这一页:
  写只读页 → 缺页中断(minor fault) → 内核复制该页 → 子页表指向新副本(可写)
  父页表仍指原页; 若引用计数回到1, 原页恢复可写
```

### 6. page cache 与脏页回写

```text
write(fd,...) ─▶ 数据先进 page cache (标记脏页 dirty)
                      │
                      ├─ 后台 pdflush/writeback 线程按策略刷盘
                      ├─ fsync()/fdatasync() 强制刷盘
                      └─ 内存紧张时回收干净页(clean直接丢, dirty先刷再丢)

read(fd,...)  ─▶ 命中 page cache 直接返回(无磁盘IO)
                 未命中 → major fault 读盘 → 填进 page cache → 返回
```

**与音视频大文件的关系**：连续读写大媒体文件会把 page cache 撑满（`free` 里 buff/cache 飙高，正常）。但在内存受限的盒子上，一次性顺序读完即弃的大文件，page cache 全留着没意义还挤占内存——可用 `posix_fadvise(POSIX_FADV_DONTNEED)` 或 `O_DIRECT` 绕过 page cache，避免缓存污染。

## 三、代码与命令示例

### 1. 观察缺页：第一次写才真正占物理页

```c
#include <stdlib.h>
#include <string.h>

int main(void) {
    const size_t totalBytes = 256 * 1024 * 1024;   // 申请 256MB
    char *buffer = malloc(totalBytes);              // 此刻 VSZ 涨, RSS 几乎不动
                                                    // 内核只登记虚拟区间, 没给物理页
    // 逐页写第一个字节 → 每页触发一次 minor fault, 真正分配物理页
    const size_t pageSize = 4096;
    for (size_t offset = 0; offset < totalBytes; offset += pageSize) {
        buffer[offset] = 1;                         // 写访问触发缺页, RSS 此刻才涨
    }
    free(buffer);                                   // 大块 → munmap, RSS 降回去
    return 0;
}
```

```bash
# 编译后用 /usr/bin/time -v 看 "Maximum resident set size" 和缺页次数
/usr/bin/time -v ./a.out
# Minor (reclaiming a frame) page faults: 65536   ← 256MB/4KB ≈ 6.5万次缺页
```

### 2. 关键排查命令速查

```bash
# ── 进程级 ──
top                         # RES 列 = RSS(物理常驻); VIRT = VSZ(虚拟)
ps -o pid,vsz,rss,cmd       # 一眼看 VSZ vs RSS 差距
pmap -x <pid>               # 各段映射明细 + RSS/Dirty 分布
cat /proc/<pid>/status      # VmSize(VSZ)/VmRSS(RSS)/VmSwap 等
cat /proc/<pid>/smaps       # 最细: Pss/Private_Dirty/Shared_Clean ... 算 PSS/USS
ps -o min_flt,maj_flt <pid> # 次缺页/主缺页计数, maj 高=在颠簸或冷读盘

# ── 整机级 ──
free -h                     # 看 available(真正可用), 别被 used/buff/cache 吓到
cat /proc/meminfo           # MemAvailable / Dirty / Writeback / SwapFree ...
vmstat 1                    # si/so 列 = swap in/out, 非零且持续=在颠簸
dmesg | grep -i oom         # 查是否发生过 OOM kill 及被杀进程

# ── 内存问题定位 ──
valgrind --leak-check=full ./a.out     # 抓真泄漏(慢, 离线用)
# 编译期开 Sanitizer(快, 推荐):
gcc -fsanitize=address -g app.c        # ASan, 越界/UAF/泄漏
gcc -fsanitize=leak    -g app.c        # LSan, 专抓泄漏
```

### 3. mmap 文件映射示例（零拷贝读）

```c
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>

int fileDescriptor = open("video.dat", O_RDONLY);
off_t fileSize = lseek(fileDescriptor, 0, SEEK_END);

// 文件私有映射: 内容直接映射 page cache, 访问指针即读文件(省一次拷贝)
char *mapped = mmap(NULL, fileSize, PROT_READ, MAP_PRIVATE, fileDescriptor, 0);
// 第一次访问每页 → major fault 读盘填 page cache; 之后命中 cache 很快
char firstByte = mapped[0];

munmap(mapped, fileSize);
close(fileDescriptor);
```

匿名共享映射可用于父子进程通信（配合 fork），细节见 [[05-进程间通信IPC]]。

## 四、常见坑与面试加分点

| 坑 / 误区 | 真相 |
| :--- | :--- |
| 看 VSZ 判断内存占用 | VSZ 是虚拟空间总和，含没用的，看 RSS/PSS |
| `free` 后 RSS 不降就说泄漏 | glibc 不一定还 OS，小块留 bins 复用，正常 |
| `free -h` 里 used 高就慌 | 看 **available**；buff/cache 是可回收的 page cache |
| 把所有进程 RSS 相加估内存 | 共享页被重复计，应该用 PSS |
| 以为 mmap 一定比 read 快 | 随机小访问缺页开销可能更大，看场景 |
| malloc 大数组立刻占物理内存 | 不写就不占，缺页时才分页（overcommit） |
| 栈上开几 MB 大数组 | 栈通常 8MB 上限，爆栈直接 SIGSEGV，大缓冲用堆 |
| 嵌入式开 swap 求稳 | 反而磨损 Flash、引入抖动，多数关 swap + 内存池兜底 |

**加分句（智能硬件 + 音视频）：**

> "内存受限的盒子上，我不依赖 swap，而是给视频帧缓冲做**定长内存池**：启动时预分配一批帧 buffer 循环复用，避免每帧 `malloc/free` 带来的缺页和外部碎片，既消除了运行时的内存抖动，又让内存占用有明确上界，配合 `oom_score_adj` 保护采集主进程不被误杀。内存对齐到 cache line 的细节走 [[09-多核架构与缓存一致性]] 和 cpp 库 [[21-内存对齐、SIMD与缓冲管理]]。"

## 六、自测 8 题

1. VSZ、RSS、PSS 三者区别？统计整机真实占用看哪个？
2. minor fault 和 major fault 的本质区别是什么？
3. 为什么 `malloc` 完一大块、`top` 里 RSS 没怎么涨？
4. `free` 了内存但 RSS 不降，一定是泄漏吗？怎么判断真泄漏？
5. `free -h` 里 buff/cache 很大、used 很高，是问题吗？看哪一列？
6. mmap 为什么能少一次拷贝？什么情况下它反而不如 read？
7. fork 用了什么机制避免复制整个地址空间？写的时候发生什么？
8. 嵌入式设备为什么常关 swap？不关会有什么问题？

<details>
<summary>参考答案</summary>

1. VSZ 是虚拟地址空间总和（含未用）；RSS 是实际物理常驻（但共享页被各进程重复计）；PSS 把共享页按进程数平摊。整机真实占用看 **PSS**。
2. minor：物理页已在内存，只是没建当前进程页表映射，不读盘；major：内容在磁盘（mmap 文件页首访问、swap 换回），必须发起磁盘 I/O。
3. malloc 只登记了虚拟地址区间（overcommit），没真正分物理页；**只有写访问触发缺页时**才逐页分配物理页，RSS 那时才涨。
4. 不一定。glibc 把空闲小块留在 bins 里复用、不一定还 OS，堆顶被占下不去也降不了。判断真泄漏看**持续单调增长不回落**，并用 valgrind / ASan-LSan 抓「分配了却 free 不掉」的点。
5. 不是问题。buff/cache 是 page cache，内核拿空闲内存缓存文件加速 I/O，可回收。看 **available** 列才是真正可用内存。
6. 普通 read 是「磁盘→page cache→用户缓冲区」两次拷贝，mmap 把 page cache 页直接映射进用户空间省掉后一次。随机小量访问时每页缺页（major fault + 建页表）开销可能比 read 顺序大块拷贝更高，此时不如 read。
7. **COW（写时复制）**：fork 只复制页表，父子共享同一批物理页并标记只读；任一方写某页时触发缺页中断，内核复制那一页、改可写，各自指向自己的副本。
8. 设备多用 eMMC/Flash，swap 频繁写**磨损寿命**且慢，还引入**不可预测的延迟停顿**破坏实时性。不关：内存紧张时颠簸（thrashing）导致性能断崖、卡顿。多数选择关 swap + 内存池控上界 + 明确 OOM。

</details>
