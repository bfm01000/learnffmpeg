## 二、场景引入：一个智能硬件程序的一生

假设你入职后接手一个真实的物联网网关程序：一台边缘盒子，上面跑着你的 C++ 程序，它要做这些事——

> 开机自启动 → 连上 MQTT 服务器等云端下发指令 → 同时通过串口读传感器数据 → 把数据缓存到本地、定时通过 HTTPS 上报 → 还要 fork 一个子进程专门管摄像头采集，主进程和子进程通过**共享内存**传图像帧 → 程序要 7×24 跑，崩了能自动拉起，内存不能越用越多。

就这么一个"不起眼"的程序，背后全是 Linux 系统编程的硬骨头。抛几个问题，你先感受一下水有多深：

1. 主进程 `fork` 出采集子进程，子进程崩了，主进程不收尸会怎样？（→ 僵尸进程，[[02-进程管理与多进程编程]]）
2. 两个进程怎么共享一帧 3MB 的图像而**不发生拷贝**？（→ 共享内存 + 同步，[[05-进程间通信IPC]]）
3. 程序跑三天，`top` 看 RSS 一直涨，但代码里 `new` 都 `delete` 了，问题出在哪？（→ 内存碎片 / page cache / glibc 不还内存给 OS，[[03-Linux内存管理机制]]）
4. MQTT 长连接、HTTPS 上报、串口读取要同时进行，一个线程怎么管这么多 fd？（→ epoll 事件驱动，[[06-文件IO与IO多路复用]][[07-Linux网络编程]]）
5. 程序偶尔卡死，没有任何日志，怎么定位卡在哪一行？（→ `gdb attach` 看线程栈，[[10-工具链与调试]]）

这些问题，**移动端开发几乎碰不到**（平台 SDK 都帮你封好了），但在 Linux 上你是直接面对操作系统的。这就是你要补的东西。

## 三、Linux 系统编程到底在解决哪几个核心问题

整个领域可以拆成 **5 个大问题**。每个用"类比 + 技术现实 + 解法 + 一句话"四段式讲清。

### 问题 1：一个程序怎么"分身"去同时做几件事？

- **类比**：开一家餐馆，老板一个人忙不过来，要么招几个**伙计**（线程，共用同一个厨房/账本），要么开几家**分店**（进程，各有各的厨房，互不影响）。
- **技术现实**：CPU 要同时跑解码、采集、上报。串行做延迟受不了；要么多线程（共享地址空间、切换快、但一个崩全崩），要么多进程（地址空间隔离、一个挂了不影响别人、但通信贵）。
- **解法**：线程用 pthread / `std::thread`；进程用 `fork`/`exec`。怎么选、怎么同步、怎么不互相踩，是核心。
- **一句话**：**进程是隔离单位，线程是调度单位**；要稳定隔离用进程，要高频共享用线程。→ [[02-进程管理与多进程编程]][[04-多线程与Linux调度]]

### 问题 2：这些"分身"之间怎么传数据、怎么不打架？

- **类比**：伙计之间靠**喊话**（pipe）、**共用一块白板**（共享内存）、或者**互相寄信**（socket/消息队列）传信息；同时要约定"白板同一时刻只能一个人写"（锁/信号量），否则字会叠在一起。
- **技术现实**：线程间共享内存天然能传数据，但要加锁防数据竞争；进程间地址空间隔离，得靠 IPC（管道、共享内存、socket、信号）显式搬运。大数据（图像帧）走拷贝太贵。
- **解法**：小数据/控制命令走管道或 UDS；大数据走共享内存 + 信号量同步（零拷贝）；跨机走 socket。
- **一句话**：**通信方式按"数据量 + 是否跨机"选**，共享内存最快但要自己管同步和生命周期。→ [[05-进程间通信IPC]]

### 问题 3：内存从哪来、到哪去、为什么会"漏"和"涨"？

- **类比**：每个进程都以为自己独占一整栋大楼（虚拟地址空间），实际操作系统才是房东，按需（缺页）才给你真房间（物理内存），还可能把不常用的房间挪到仓库（swap）。
- **技术现实**：`malloc` 拿到的是虚拟地址，真正用到才映射物理页；free 了 glibc 也未必还给 OS，所以 RSS 不降；读文件会进 page cache，`free` 命令里大半是缓存不是泄漏。
- **解法**：理解虚拟内存/分页/page cache/COW，会用 `valgrind`/ASan 查真泄漏，会用内存池避免碎片和抖动。
- **一句话**：**你看到的地址都是假的（虚拟的），理解这层映射，内存涨/漏/碎片才不会一脸懵**。→ [[03-Linux内存管理机制]]

### 问题 4：怎么和外界（网络、设备）打交道？

- **类比**：Linux 把一切都当成**文件**——网络连接是文件、串口是文件、摄像头是文件。你用同一套 `read`/`write`/`close` 应付所有东西，只是开门的方式（`open`/`socket`/`ioctl`）不同。
- **技术现实**：一个程序要同时盯几百个连接 + 几个设备 fd，一个线程一个连接扛不住（C10K 问题）。
- **解法**：文件描述符（fd）抽象一切；`epoll` 让一个线程高效监听海量 fd（事件驱动 / Reactor 模型）；设备通过 `ioctl` 控制。
- **一句话**：**"一切皆文件" + epoll 事件驱动**，是 Linux 高并发后台的命脉。→ [[06-文件IO与IO多路复用]][[07-Linux网络编程]][[11-Linux驱动与内核基础]]

### 问题 5：跑在多个 CPU 核上，怎么不"假并行"、不互相拖后腿？

- **类比**：四个伙计各管一个收银台（核），但他们都要翻同一本账本（共享数据）。每人手边还有一份账本的复印件（CPU cache），一个人改了账本，别人手里的复印件就过期了——得有人吼一声"作废重抄"（缓存一致性）。
- **技术现实**：多核下，缓存一致性（MESI）、伪共享（两个核抢同一 cache line）、内存乱序，会让"看起来并行"的代码实际很慢甚至出错。
- **解法**：理解 cache line / 伪共享 / 内存屏障，用原子操作和合理的数据布局，必要时绑核（CPU 亲和性）。
- **一句话**：**多核的难点不是"开几个线程"，而是"它们共享数据时的缓存和内存可见性"**。→ [[09-多核架构与缓存一致性]]

## 五、一条端到端主线：跟着一帧数据走完全程

光看分层图还是抽象。我们选**第二节那个网关程序里"摄像头采集子进程把一帧图像交给主进程上报"**这条最典型的主线，从头走一遍，把各模块串起来：

```text
① 主进程启动
   main() → 解析配置 → 此时它是个普通进程，有自己的虚拟地址空间 [[03-Linux内存管理机制]]

② 准备共享内存（为零拷贝传帧做准备）
   shm_open() + mmap() 映射一块 3MB 的共享内存
   再建一个信号量做"帧就绪"通知                      [[05-进程间通信IPC]]

③ fork 出采集子进程
   fork() → 返回两次：父进程拿到子 pid，子进程拿到 0  [[02-进程管理与多进程编程]]
   子进程 COW 复制父进程地址空间，但共享内存区是真正共享的 [[03-Linux内存管理机制]]

④ 子进程采集
   open("/dev/video0") → ioctl 设格式 → mmap 拿驱动 buffer [[06-文件IO与IO多路复用]][[11-Linux驱动与内核基础]]
   读到一帧 YUV，memcpy 进共享内存，sem_post 通知主进程

⑤ 主进程被唤醒拿帧
   主进程在 sem_wait 上阻塞，被唤醒 → 直接读共享内存里的帧
   全程没拷贝过这 3MB（除了④那次入共享内存）        [[05-进程间通信IPC]]

⑥ 主进程上报
   把帧/数据塞进发送队列（多线程，mutex 保护）        [[04-多线程与Linux调度]]
   网络线程用 epoll 管着 MQTT 长连接 + HTTPS 连接      [[06-文件IO与IO多路复用]][[07-Linux网络编程]]
   通过 TLS 加密后 send() 出去                       [[08-网络协议原理]]

⑦ 收尸与稳定运行
   子进程退出 → 主进程 waitpid 回收，避免僵尸          [[02-进程管理与多进程编程]]
   程序作为 systemd 服务运行，崩溃自动拉起

⑧ 出问题时
   卡死 → gdb attach 看每个线程栈在哪
   CPU 高 → perf top 看热点
   内存涨 → valgrind / 看 /proc/pid/smaps             [[10-工具链与调试]]
```

**这条线几乎覆盖了 JD 的每一条要求。** 你现在不需要看懂每一步的代码——只要建立"哦，原来这些知识点是这样咬合在一起的"这个认知就够了。后续每篇下钻文档，都是在放大这条线上的某一环。

## 六、关键技术点：建立直觉（点到为止，不深挖）

挑 6 个最重要的概念，每个用"是什么 + 为什么需要 + 一句话"讲，深挖留给下钻文档。

### 6.1 文件描述符（fd）：一切皆文件

- **是什么**：一个小整数，内核用它索引你打开的"东西"——文件、socket、管道、设备，统统是 fd。
- **为什么需要**：有了这层统一抽象，你才能用同一套 `read`/`write`/`epoll` 应付五花八门的资源，不用为每种资源学一套 API。
- **一句话**：**fd 是 Linux 给你的"万能遥控器"，理解它是理解 IO/网络/IPC 的前提。** → [[06-文件IO与IO多路复用]]

### 6.2 虚拟内存：你看到的地址都是假的

- **是什么**：每个进程都以为自己独占整个地址空间，实际由内核 + MMU 把虚拟地址按页（4KB）映射到物理内存，按需分配。
- **为什么需要**：进程隔离（你改不了别人的内存）、按需分配（malloc 不立刻占物理内存）、COW（fork 不立刻复制）都靠它。内存涨/漏/碎片的所有谜题都从这里解开。
- **一句话**：**先有虚拟内存这层"地址翻译"，才能理解为什么 free 了 RSS 不降、fork 为什么快。** → [[03-Linux内存管理机制]]

### 6.3 进程 vs 线程：隔离单位 vs 调度单位

- **是什么**：进程有独立地址空间（隔离），线程共享所在进程的地址空间（共享）。Linux 内核里其实都是 `task_struct`，靠"共享了哪些资源"区分。
- **为什么需要**：稳定性要隔离（一个模块崩不拖垮全局）→ 多进程；高频共享数据、切换要快 → 多线程。智能硬件里常见"主进程 + 若干隔离子进程"的架构。
- **一句话**：**要稳用进程隔离，要快用线程共享，代价是进程通信贵、线程一崩全崩。** → [[02-进程管理与多进程编程]][[04-多线程与Linux调度]]

### 6.4 epoll：一个线程盯住成千上万个连接

- **是什么**：Linux 特有的 IO 多路复用机制，注册一堆 fd，内核在哪个 fd 就绪时只告诉你那一个，不用你轮询所有。
- **为什么需要**：`select`/`poll` 每次都要遍历全部 fd，连接一多就慢（O(n)）；epoll 是 O(就绪数)，是解决 C10K（单机万连接）的标准答案。
- **一句话**：**epoll = 事件驱动后台的发动机，配 Reactor 模型，是 Linux 网络编程面试的必考点。** → [[06-文件IO与IO多路复用]][[07-Linux网络编程]]

### 6.5 共享内存：最快的 IPC，但要自己管同步

- **是什么**：两个进程把同一块物理内存映射到各自地址空间，一方写另一方立刻可见，零拷贝。
- **为什么需要**：传一帧 3MB 图像，走 socket/管道要拷贝两次（用户态→内核态→用户态），走共享内存零拷贝。但"立刻可见"也意味着会数据竞争，必须配信号量/互斥同步。
- **一句话**：**共享内存快在零拷贝，难在同步和生命周期管理——这正是面试官想听你讲的权衡。** → [[05-进程间通信IPC]]

### 6.6 用户态 vs 内核态：syscall 是过路口

- **是什么**：CPU 有特权级，你的代码跑在用户态，碰硬件/改内核数据要陷入内核态，靠系统调用（syscall）这道关卡切换。
- **为什么需要**：理解这个，你才懂"为什么系统调用比函数调用贵"、"为什么零拷贝/mmap 能提速"（少了用户↔内核的数据搬运）、"为什么 strace 能抓到程序行为"（它拦截 syscall）。
- **一句话**：**用户态/内核态的边界，是理解性能（syscall 开销）和调试（strace）的关键分界线。** → [[03-Linux内存管理机制]][[10-工具链与调试]]

## 七、新人最容易踩的坑（错觉 → 事实 → 避坑）


| #   | 错觉                            | 事实                               | 避坑                                                     |
| --- | ----------------------------- | -------------------------------- | ------------------------------------------------------ |
| 1   | "`fork` 之后父子是两份完全独立的内存"       | 是 **COW**：fork 瞬间不复制，谁先写哪页才复制哪页  | 别假设 fork 很贵；但也别假设子进程改内存父进程看得见（共享内存除外）                  |
| 2   | "`free`/`delete` 了内存就还给操作系统了" | glibc 常把小块内存留在自己的池里，RSS 不一定降     | 看 RSS 涨不等于泄漏；用 valgrind/ASan 才能定真泄漏 [[03-Linux内存管理机制]]             |
| 3   | "子进程结束就没了"                    | 父进程不 `wait`，子进程变**僵尸**占着 PID     | 父进程必须 `waitpid` 收尸，或处理 `SIGCHLD` [[02-进程管理与多进程编程]]                |
| 4   | "多线程比多进程一定好"                  | 线程一崩全进程挂；进程隔离更稳，智能硬件常用多进程        | 按"隔离 vs 共享开销"选，别无脑上多线程 [[02-进程管理与多进程编程]][[04-多线程与Linux调度]]                    |
| 5   | "共享内存映射好就能直接读写"               | 没有同步，两进程同时读写就是数据竞争               | 共享内存必须配信号量/互斥 + 设计好生命周期 [[05-进程间通信IPC]]                         |
| 6   | "epoll 用就完事了"                 | ET（边缘触发）模式下不一次读干净会丢事件            | 搞清 LT/ET 区别、非阻塞 fd 下处理 `EAGAIN` [[06-文件IO与IO多路复用]]                 |
| 7   | "TCP 是消息流，发一次收一次"             | TCP 是**字节流**，会粘包/拆包              | 应用层自己定边界（长度前缀/分隔符）[[07-Linux网络编程]][[08-网络协议原理]]                         |
| 8   | "`volatile` 能解决多线程可见性"        | volatile 不保证原子性也不是内存屏障           | 多线程用 `std::atomic` / 锁，别用 volatile [[09-多核架构与缓存一致性]]              |
| 9   | "信号处理函数里啥都能干"                 | 信号是异步打断，只能调 async-signal-safe 函数 | 信号处理函数里只设个 flag，主循环再处理 [[02-进程管理与多进程编程]]                          |
| 10  | "程序在我机器上能跑就行"                 | 交叉编译到 ARM、运行时动态库找不到是常态           | 学会 `ldd`、`LD_LIBRARY_PATH`、rpath、toolchain file [[10-工具链与调试]] |

## 十二、自检题（读完应该能回答）

不用写代码，能用大白话讲清楚就算过：

1. 这个 JD 反复强调的两块能力是什么？为什么说它们权重最高？
2. 进程和线程的本质区别是什么？智能硬件为什么常用多进程架构？
3. 为什么 `free` 了内存，`top` 看 RSS 不一定下降？
4. 两个进程要传一帧 3MB 图像，为什么共享内存比 socket 快？代价是什么？
5. 一个线程要同时盯 MQTT 连接、HTTPS 连接、串口，用什么机制？为什么不用 select？
6. `fork` 出的子进程崩了、父进程不管，会发生什么？
7. 你现在能力地图上，"明显欠缺"的前两项是什么？
8. 画出从应用程序到硬件的分层图，说出系统调用在哪一层。

参考答案要点（先自己答，再展开）

1. 内存管理机制 + 多进程管理机制（JD 第 5、6 条各出现一次）；是"直接面对 OS"的核心，区分"会调库"和"懂系统"的分水岭。
2. 进程有独立地址空间（隔离单位），线程共享地址空间（调度单位）；多进程一模块崩不拖垮全局，稳定性高，适合 7×24 的硬件设备。→ [[02-进程管理与多进程编程]]
3. glibc 的 malloc 常把释放的小块内存留在自己的内存池里不还给 OS；且 page cache 也算进内存占用。→ [[03-Linux内存管理机制]]
4. 共享内存零拷贝（一方写另一方直接可见），socket 要经过用户态→内核态→用户态两次拷贝；代价是必须自己做同步（信号量）和生命周期管理。→ [[05-进程间通信IPC]]
5. epoll（IO 多路复用 / 事件驱动）；select/poll 每次要遍历所有 fd（O(n)），连接多就慢，epoll 只返回就绪的 fd。→ [[06-文件IO与IO多路复用]]
6. 子进程变僵尸进程，占用 PID 表项，PID 耗尽后无法创建新进程。→ [[02-进程管理与多进程编程]]
7. 多进程编程（fork/exec/wait）和 Linux 虚拟内存机制。→ [[02-进程管理与多进程编程]][[03-Linux内存管理机制]]
8. 应用 → 系统调用接口（syscall，用户态/内核态边界）→ 内核（内存/调度/网络栈/驱动）→ 硬件。
