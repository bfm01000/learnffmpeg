## 📌 第一部分：面试速记（考前 10 分钟扫一遍）

### 一句话核心

> **工具链就是一条流水线：`gcc` 把源码变成可执行文件（预处理→编译→汇编→链接四步），`cmake` 负责跨平台地组织这条流水线（描述依赖、生成 Makefile/Ninja），`gdb` 在出问题时把程序停下来看现场（断点、调用栈、变量）。再往外，`perf`/`strace`/`valgrind`/`ASan` 解决"跑得对但跑不好"的问题——CPU 高、内存涨、卡死、内存越界各有专门工具。**

### 面试官常问问题 + 标准口语化回答

---

#### 开场题：gcc 编译一个 C++ 程序，中间经历了哪几步？

**🗣️ 面试标准回答：**

> "四个阶段，对应四类产物：
>
> 1. **预处理**（`-E`）：展开 `#include`、宏替换、处理条件编译，产出还是文本的 `.i`；
> 2. **编译**（`-S`）：把预处理后的代码翻译成**汇编**，产出 `.s`，语法检查、优化大多发生在这一步；
> 3. **汇编**（`-c`）：汇编器把 `.s` 变成**目标文件** `.o`（机器码 + 符号表，但地址还没定）；
> 4. **链接**：链接器把多个 `.o` 和库（`.a`/`.so`）拼起来，**解析符号引用、重定位地址**，产出最终可执行文件。
>
> 平时一条 `g++ main.cpp -o app` 是把四步一次跑完；排查问题时常拆开，比如 `-E` 看宏展开成了什么、`-S` 看编译器生成的汇编。"

**👨‍💻 面试官追问：**

> Q: `undefined reference` 是哪一步报的错？
> A: **链接阶段**。说明某个符号有声明、被用到了，但链接器在所有 `.o` 和库里都找不到它的定义——常见原因是漏链了库（少写 `-l`）、库的链接顺序不对，或函数只声明没实现。编译阶段只看声明，不关心实现在哪。

#### 必考题：静态库和动态库有什么区别？怎么选？

**🗣️ 面试标准回答：**

> "**静态库 `.a`** 本质是一堆 `.o` 打的包（`ar` 工具）。链接时，链接器把**用到的目标文件直接拷进可执行文件**，运行时不再依赖这个库。优点是部署简单、无运行时查找开销；缺点是每个程序都拷一份，体积大，库升级必须重新编译。
>
> **动态库 `.so`** 在链接时只记录"我依赖某个 so 里的某些符号"，**真正的代码加载推迟到运行时**由动态链接器（`ld.so`）完成。优点是多个进程共享同一份内存代码段、库可独立升级（只要 ABI 不变）；缺点是运行时要能找到 so（经典的 `cannot open shared object file`），还有一点点加载和符号解析开销。
>
> 工程选择：**基础组件、要独立升级/被多个程序共用 → 动态库；想要单文件部署、版本强绑定、嵌入式怕 so 找不到 → 静态库。** 嵌入式智能硬件经常静态链接图省事。"

**👨‍💻 面试官追问：**

> Q: 动态库为什么能被多个进程共享内存？
> A: so 的**代码段（.text）是只读的，且编译成位置无关代码（`-fPIC`）**，物理内存里只需一份，被映射进各进程的虚拟地址空间。可写的数据段才每进程一份（写时复制）。底层就是 mmap + 页共享，见 [[03-Linux内存管理机制]]。

---

#### 必考题：动态库运行时找不到（cannot open shared object），怎么排查？

**🗣️ 面试标准回答：**

> "标准三步：
>
> 1. **`ldd ./app`** 看依赖了哪些 so、哪个显示 `not found`，先定位是哪个库；
> 2. 想清楚 so 在哪、运行时去哪找。动态链接器的查找顺序大致是：可执行文件里写死的 **rpath/runpath**（`-Wl,-rpath`）→ 环境变量 **`LD_LIBRARY_PATH`** → `/etc/ld.so.cache`（由 `ldconfig` 根据 `/etc/ld.so.conf` 生成）→ 默认 `/lib`、`/usr/lib`；
> 3. 对症下药：临时调试用 `LD_LIBRARY_PATH` 指过去；要随程序走、可移植，编译时写 **rpath**（`-Wl,-rpath,'$ORIGIN/lib'` 让它相对可执行文件找）；系统级安装就把目录加进 `ld.so.conf` 再 `sudo ldconfig`。
>
> 一句话：**`ldd` 先看谁缺，再按"rpath → LD_LIBRARY_PATH → ldconfig 缓存 → 默认路径"这个顺序去补。**"

#### 高频题：gdb 怎么调一个段错误（Segmentation fault）？

**🗣️ 面试标准回答：**

> "看现场是哪一行、调用栈是什么。两种姿势：
>
> 1. **能复现就直接跑**：`gdb ./app` → `run`，程序崩在哪 gdb 就停在哪，敲 **`bt`（backtrace）** 看完整调用栈，`frame N` 跳到某一帧，`print 变量` 看当时的值——通常一眼能看出是空指针、越界还是野指针。
> 2. **线上崩了拿到 core 文件**：先确保开了 core dump（`ulimit -c unlimited`），崩溃后用 **`gdb ./app core`** 加载，同样 `bt` 看栈。
>
> 前提是编译带 **`-g`**（调试符号），否则栈里只有地址没有函数名行号。Release 包可以单独保留符号表（split debug）来事后定位。"

**👨‍💻 面试官追问：**

> Q: 程序卡死（不崩，就是不动）怎么用 gdb 看？
> A: 这是最实用的一招——**`gdb -p <pid>` attach 到活进程**，然后 **`thread apply all bt`** 一次性打印所有线程的调用栈。死锁就能看到两个线程互相等对方的锁；卡在 IO 就能看到栈顶停在某个 `read`/`recv`/`futex`。配合 `strace -p` 看卡在哪个系统调用。

#### 高频题：内存泄漏 / 内存越界用什么工具？valgrind 和 ASan 怎么选？

**🗣️ 面试标准回答：**

> "两类工具：
>
> - **Valgrind（memcheck）**：不用重新编译，直接 `valgrind ./app` 就能查泄漏、越界、用未初始化内存。代价是**慢 10～50 倍**，它本质是把程序跑在一个虚拟 CPU 上模拟每条指令。
> - **AddressSanitizer（ASan）**：编译期加 `-fsanitize=address -g` 插桩，**只慢 2 倍左右**，报错信息更精确（直接给出越界的读写位置和分配栈）。还有 `-fsanitize=thread`（数据竞争）、`-fsanitize=leak`（纯查泄漏）、`-fsanitize=undefined`（UB）。
>
> 选型：**开发/CI 阶段优先 ASan**（快、信息好，但要能改编译选项、会改变内存布局）；**拿到的是不能重编的二进制、或要查的是和真实分配器相关的问题，用 Valgrind。** 注意 ASan 和 Valgrind 不能同时开。内存泄漏为什么会发生、RSS 为什么涨，原理见 [[03-Linux内存管理机制]]。"

#### 实战题：线上服务 CPU 突然 100%，你怎么定位？

**🗣️ 面试标准回答：**

> "自顶向下缩小范围：
>
> 1. **`top`** 先确认是不是这个进程吃满了 CPU；
> 2. **`top -H -p <pid>`**（或 `pidstat -t`）看是**哪个线程**在烧 CPU，记下线程 ID；
> 3. **`perf top -p <pid>`** 看热点函数——哪个函数占的 CPU 周期最多，一眼定位是死循环、还是某个算法/正则/序列化太重；
> 4. 想要完整的调用关系就 **`perf record -g -p <pid>`** 采样一段，再 `perf report` 或生成**火焰图**（folded stack → flamegraph），横轴是占比、越宽越热。
>
> 一句话：**top 定进程 → top -H 定线程 → perf 定函数。**"

---

#### 实战题：CMake 项目找不到头文件 / 找不到库，分别怎么修？

**🗣️ 面试标准回答：**

> "对应编译的两个阶段：
>
> - **找不到头文件**（`fatal error: xxx.h: No such file`）：是**编译阶段**缺 `-I`。CMake 里用 `target_include_directories(目标 PUBLIC 头文件目录)` 把目录加进去。
> - **找不到库 / undefined reference**：是**链接阶段**。先确认库找到了（`find_package` 或 `find_library`），再用 `target_link_libraries(目标 PRIVATE 库)` 链接上。
>
> `PUBLIC`/`PRIVATE` 的区别要会说：**`PRIVATE` 只我自己用、不传染给依赖我的人；`PUBLIC` 我用、并且我的头文件暴露了它（依赖我的目标也得跟着带上）；`INTERFACE` 我自己不用、只传给下游。** 选错不影响能不能编过本目标，但会让依赖链上的其它目标缺/多包含路径。"

---

#### 收尾题：给 ARM 智能硬件编译程序，和本机编译有什么不同？

**🗣️ 面试标准回答：**

> "本机编译（x86 上编 x86）用系统自带的 gcc；给 ARM 设备编叫**交叉编译**——在 x86 开发机上用一套**目标是 ARM 的工具链**（比如 `arm-linux-gnueabihf-gcc`、`aarch64-linux-gnu-gcc`）生成 ARM 指令的二进制，拷到板子上跑。
>
> 关键点：编译器、链接器、C 库（sysroot）都得是目标平台那一套，不能链到本机的 `/usr/lib`。CMake 里通过 **toolchain file** 指定 `CMAKE_C_COMPILER`、`CMAKE_SYSROOT`、`CMAKE_SYSTEM_NAME=Linux`、`CMAKE_SYSTEM_PROCESSOR=aarch64` 等。
>
> 验证产物对不对就用 **`file ./app`** 看是不是 `ARM aarch64`，`readelf -h` 看 Machine 字段。交叉编译工具链、设备树、内核态那一套见 [[11-Linux驱动与内核基础]]。"

## 二、原理详解

### 1. gcc/g++：从源码到可执行文件

#### 1.1 编译四阶段与产物

```bash
# 一步到位（四阶段一次跑完）
g++ main.cpp -o app

# 拆开看每一步的中间产物
g++ -E main.cpp -o main.i    # ① 预处理：展开头文件/宏，产出文本 .i
g++ -S main.i  -o main.s     # ② 编译：翻译成汇编 .s
g++ -c main.s  -o main.o     # ③ 汇编：变成目标文件 .o（机器码+符号表）
g++ main.o     -o app        # ④ 链接：拼接 .o 与库，解析符号、重定位
```

| 阶段 | 选项 | 输入 → 产物 | 干了什么 | 典型报错 |
|---|---|---|---|---|
| 预处理 | `-E` | `.cpp` → `.i` | 展开 `#include`、宏替换、条件编译 | 头文件找不到 |
| 编译 | `-S` | `.i` → `.s` | 语法/语义检查、生成汇编、优化 | 语法错、类型不匹配 |
| 汇编 | `-c` | `.s` → `.o` | 汇编成机器码 + 符号表 | 极少 |
| 链接 | （默认） | `.o`+库 → 可执行 | 解析符号引用、重定位地址 | `undefined reference` |

#### 1.2 常用编译选项速查

```bash
g++ main.cpp -o app \
    -std=c++17 \          # 语言标准
    -Wall -Wextra \       # 打开常用 + 额外警告（强烈建议）
    -g \                  # 生成调试符号（gdb/core 需要）
    -O2 \                 # 优化等级：-O0 调试用 / -O2 发布常用 / -O3 激进
    -I./include \         # 头文件搜索路径（编译期）
    -L./lib \             # 库搜索路径（链接期）
    -lfoo \               # 链接 libfoo.so 或 libfoo.a
    -DDEBUG_LOG=1 \       # 定义宏（等价源码里 #define DEBUG_LOG 1）
    -fPIC                 # 位置无关代码（编动态库必需）
```

| 选项 | 作用 | 备注 |
|---|---|---|
| `-Wall -Wextra` | 开警告 | 工程基本必开，很多 bug 是警告级别 |
| `-Werror` | 警告当错误 | CI 里常开，强制零警告 |
| `-g` | 调试符号 | 不影响优化，可与 `-O2` 共存 |
| `-O0`/`-O2`/`-O3` | 优化等级 | 调试用 `-O0`，发布 `-O2`，`-O3` 慎用（可能变慢/变大） |
| `-std=c++17` | 语言标准 | 和实际用到的特性匹配 |
| `-I` / `-L` / `-l` | 头/库路径、链接库 | `-I` 编译期、`-L`/`-l` 链接期 |
| `-D` | 定义宏 | 控制条件编译 |
| `-fPIC` | 位置无关代码 | 编 `.so` 必需 |

> 编译选项、ODR、链接顺序、内联与符号这些**编译链接的深水区**，见 cpp 库 [[18-编译链接与构建]]，这里只覆盖工具用法。

#### 1.3 静态库 vs 动态库：制作与链接

```bash
# ---------- 静态库 .a ----------
g++ -c mathutil.cpp -o mathutil.o          # 先编成目标文件
ar rcs libmathutil.a mathutil.o            # ar 打包成静态库（r 替换 c 创建 s 索引）
g++ main.cpp -L. -lmathutil -o app         # 链接：代码被拷进 app，运行时不再依赖

# ---------- 动态库 .so ----------
g++ -fPIC -c mathutil.cpp -o mathutil.o    # 必须 -fPIC
g++ -shared mathutil.o -o libmathutil.so   # -shared 生成动态库
g++ main.cpp -L. -lmathutil -o app         # 链接时只记录依赖
./app                                       # 运行时由 ld.so 加载 libmathutil.so
```

| 维度 | 静态库 `.a` | 动态库 `.so` |
|---|---|---|
| 代码去向 | 链接时拷进可执行文件 | 运行时由 ld.so 加载 |
| 可执行文件体积 | 大 | 小 |
| 多进程共享 | 否（各拷一份） | 是（代码段共享内存） |
| 库升级 | 要重新链接 | 换 so 即可（ABI 不变） |
| 运行时依赖 | 无 | 需找得到 so |
| 嵌入式取舍 | 部署简单、首选 | 省内存、但怕路径问题 |

#### 1.4 动态库运行时找不到：查找顺序与修法

```bash
ldd ./app                       # 列出依赖的 so，看哪个 not found
# 运行时查找顺序（从先到后）：
#   ① 可执行文件内嵌的 RPATH/RUNPATH
#   ② 环境变量 LD_LIBRARY_PATH
#   ③ /etc/ld.so.cache（ldconfig 根据 /etc/ld.so.conf 生成）
#   ④ 默认 /lib、/usr/lib

# 临时调试：把 so 目录加进环境变量
export LD_LIBRARY_PATH=/path/to/lib:$LD_LIBRARY_PATH && ./app

# 随程序走、可移植：编译时写 rpath，$ORIGIN 表示可执行文件所在目录
g++ main.cpp -L./lib -lmathutil -Wl,-rpath,'$ORIGIN/lib' -o app

# 系统级安装：注册目录并刷新缓存
echo "/opt/myapp/lib" | sudo tee /etc/ld.so.conf.d/myapp.conf
sudo ldconfig                   # 重建 ld.so.cache
ldconfig -p | grep mathutil     # 确认已进缓存
```

#### 1.5 看符号：定位 undefined reference

```bash
nm -C libmathutil.a             # 看库里有哪些符号，-C 解 demangle（C++ 名字还原）
                                # T=本库定义的、U=未定义（依赖外部）、W=弱符号
nm -DC libmathutil.so           # 看动态库的动态符号表
readelf -d ./app                # 看动态段：NEEDED（依赖哪些so）、RPATH/RUNPATH
objdump -d mathutil.o           # 反汇编看具体指令
file ./app                      # 看架构（x86-64 / ARM aarch64）、是否 stripped
```

**`undefined reference` 排查清单：**

| 现象 | 原因 | 修法 |
|---|---|---|
| 符号在某库里 `U`，可执行里也 `U` | 漏链了那个库 | 补 `-lxxx` |
| 库写了但还是报错 | **链接顺序**：被依赖的库要放后面 | `-lmain -lutil`（util 被 main 用就放后） |
| C++ 调 C 函数报错 | 名字修饰不一致 | C 头文件加 `extern "C"` |
| 函数只声明没定义 | 真的没实现 | 补实现或链上实现所在库 |

### 2. CMake：组织构建

**为什么用 CMake**：手写 Makefile 跨平台麻烦、依赖管理弱。CMake 是**元构建系统**——你用 `CMakeLists.txt` 描述"有哪些目标、依赖什么"，它再生成对应平台的实际构建文件（Linux 上是 Makefile/Ninja，Windows 上是 VS 工程）。同一份描述，到处编译。

#### 2.1 最简 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.16)
project(myapp LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)          # C++17
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# 自己的库
add_library(mathutil STATIC src/mathutil.cpp)
target_include_directories(mathutil PUBLIC include)  # 用我的人也要这个头目录

# 可执行文件
add_executable(myapp src/main.cpp)
target_link_libraries(myapp PRIVATE mathutil)        # 链接自己的库
```

#### 2.2 out-of-source build 与构建类型

```bash
# 在独立的 build 目录里构建，不污染源码树（强烈推荐）
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release   # 配置阶段：生成构建文件
cmake --build build -j                            # 构建阶段：并行编译

# 调试包用 Debug（带 -g、不优化）；发布用 Release（-O2、NDEBUG）
cmake -S . -B build-debug -DCMAKE_BUILD_TYPE=Debug
```

| `CMAKE_BUILD_TYPE` | 等价编译选项 | 用途 |
|---|---|---|
| `Debug` | `-g -O0` | 开发调试，gdb 看变量准 |
| `Release` | `-O2 -DNDEBUG` | 发布，关 assert |
| `RelWithDebInfo` | `-O2 -g` | 优化 + 保留符号，线上 core 定位 |
| `MinSizeRel` | `-Os` | 体积优先，嵌入式 |

#### 2.3 find_package 与 PUBLIC/PRIVATE 传播

```cmake
find_package(Threads REQUIRED)              # 找系统库（如 pthread）
target_link_libraries(myapp PRIVATE Threads::Threads)

# PUBLIC/PRIVATE/INTERFACE 决定"依赖是否传染给下游"
# PRIVATE   : 仅本目标编译用，不传给依赖我的目标
# PUBLIC    : 本目标用 + 我的头文件暴露了它 → 下游也得带上
# INTERFACE : 本目标不用，只传给下游（典型：header-only 库）
target_include_directories(mathutil
    PUBLIC  include          # 公开头，用 mathutil 的人需要
    PRIVATE src)             # 内部实现头，外人不需要
```

**CMake 两类常见报错对照：**

| 报错 | 阶段 | 修法 |
|---|---|---|
| `fatal error: xxx.h: No such file` | 编译 | `target_include_directories` 补头路径 |
| `undefined reference` / `cannot find -lxxx` | 链接 | `find_package`/`find_library` + `target_link_libraries` |

### 3. gdb：把程序停下来看现场（重点）

前提：编译带 **`-g`**，否则栈里没有函数名和行号。

#### 3.1 三种启动方式

```bash
gdb ./app                       # ① 从头调，常用于能复现的 bug
gdb ./app core                  # ② 拿 core 文件做事后剖析（postmortem）
gdb -p <pid>                    # ③ attach 到正在跑的进程（调卡死/死锁神器）
```

开启 core dump（默认很多系统是关的）：

```bash
ulimit -c unlimited             # 当前 shell 不限制 core 大小
cat /proc/sys/kernel/core_pattern   # 看 core 落到哪（可能交给 systemd-coredump）
coredumpctl list                # systemd 系统：列出捕获的 core
coredumpctl gdb <pid或程序名>    # 直接拉起 gdb 加载对应 core
```

#### 3.2 常用命令速查

```text
break main / b file.cpp:42   设断点（按函数 / 按文件行号）
break func if x==0           条件断点
run / r                      启动运行
continue / c                 继续到下个断点
next / n                     单步（不进函数）
step / s                     单步（进函数）
finish                       跑完当前函数返回
print 变量 / p 变量          打印变量值（p/x 十六进制）
backtrace / bt               打印调用栈 ← 看崩溃第一命令
frame N / f N                切到第 N 帧（再 print 看那一帧的局部变量）
info locals                  当前帧所有局部变量
watch 变量                   数据断点：变量被改写时停下
info threads                 列出所有线程
thread N                     切到第 N 个线程
thread apply all bt          所有线程都打印栈 ← 调死锁/卡死第一命令
```

#### 3.3 看崩溃（段错误）

```bash
gdb ./app core
(gdb) bt                      # 看崩在哪个调用链
(gdb) frame 1                 # 跳到业务代码那一帧
(gdb) info locals             # 看当时局部变量，常一眼看出空指针/越界
(gdb) print some_pointer      # 若是 0x0 即空指针解引用
```

#### 3.4 多线程调试（面试高频实战）

死锁、卡死的根因往往在"线程互相等"。一条命令看全貌：

```bash
gdb -p <pid>
(gdb) thread apply all bt     # 所有线程的栈一次打出
# 读栈技巧：
#   - 两个线程栈顶都停在 __lll_lock_wait / pthread_mutex_lock → 互等锁，死锁
#   - 多数线程停在 futex_wait / cond_wait → 在等条件，可能是没人唤醒
#   - 某线程停在 recv / read → 卡在 IO，配合 strace -p 看具体 fd
(gdb) thread 3                # 切到可疑线程
(gdb) bt                      # 细看它的栈
(gdb) frame 2                 # 进到持锁那一帧，看它在等什么
```

> 多线程、锁、调度的原理见 [[04-多线程与Linux调度]]；死锁的成因（顺序不一致）见信号量/锁相关文档。

### 4. 性能与排查工具

#### 4.1 perf：找 CPU 热点

```bash
perf top -p <pid>             # 实时看哪个函数最烧 CPU（类似 top 但到函数级）
perf record -g -p <pid> -- sleep 20   # 采样 20 秒，-g 记录调用栈
perf report                   # 交互式看采样结果，按占比排序
# 火焰图：把采样栈折叠后画图，横轴=占比（越宽越热），纵轴=调用深度
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
```

#### 4.2 strace / ltrace：跟踪调用

```bash
strace -p <pid>               # 跟踪进程正在执行的系统调用（卡死时看停在哪个 syscall）
strace -f -e trace=network ./app   # -f 跟子进程/线程，只看网络相关 syscall
strace -c ./app               # 统计各 syscall 次数/耗时（看哪类调用最频繁/最慢）
ltrace -p <pid>               # 跟踪库函数调用（如 malloc/free，看内存分配行为）
```

#### 4.3 valgrind / Sanitizer：内存与并发问题

```bash
# Valgrind：不用重编，慢但全面
valgrind --leak-check=full --show-leak-kinds=all ./app   # 查泄漏/越界/未初始化
valgrind --tool=helgrind ./app                            # 查数据竞争/锁顺序问题

# Sanitizer：编译期插桩，快、报错精确
g++ -fsanitize=address -g main.cpp -o app && ./app   # ASan：越界 + 泄漏
g++ -fsanitize=thread  -g main.cpp -o app && ./app   # TSan：数据竞争
g++ -fsanitize=leak    -g main.cpp -o app && ./app   # LSan：只查泄漏
g++ -fsanitize=undefined -g main.cpp -o app          # UBSan：未定义行为
```

| 维度 | Valgrind (memcheck) | AddressSanitizer |
|---|---|---|
| 是否重编 | 否，直接跑二进制 | 是，加 `-fsanitize` |
| 速度 | 慢 10～50 倍 | 慢约 2 倍 |
| 报错精度 | 好 | 更好（给分配栈+越界位置） |
| 适用 | 拿不到源码/不能重编 | 开发与 CI 首选 |
| 数据竞争 | helgrind | ThreadSanitizer |

> 内存泄漏、RSS 为什么涨、堆/栈/mmap 的底层，见 [[03-Linux内存管理机制]]。

#### 4.4 系统观测工具

```bash
top / htop                    # 总览：CPU、内存、各进程占用
top -H -p <pid>               # 看进程内各线程的 CPU（定位是哪个线程）
pidstat -t -p <pid> 1         # 按线程逐秒统计 CPU/上下文切换
pmap -x <pid>                 # 进程内存映射明细（看哪段映射在涨）
cat /proc/<pid>/smaps         # 更细的内存分段（RSS/PSS/脏页）
vmstat 1                      # 系统级：内存、swap、上下文切换、IO 趋势
iostat -x 1                   # 磁盘 IO 利用率/await
ss -tanp                      # 看 TCP 连接状态（替代 netstat，更快）
tcpdump -i eth0 port 8080 -w cap.pcap   # 抓包，丢 Wireshark 分析
```

> 网络相关排查（连接状态、抓包、丢包）配合 [[07-Linux网络编程]]、[[08-网络协议原理]]。

## 三、实战排查思路（按现象套路走）

面试最爱问"线上出了 X 问题你怎么查"。核心是**自顶向下、先定位再深挖**，每类问题都有固定套路。

### 3.1 CPU 飙高

| 步骤 | 工具/命令 | 看什么 |
|---|---|---|
| ① 定进程 | `top` | 哪个进程 CPU 高 |
| ② 定线程 | `top -H -p <pid>` / `pidstat -t` | 哪个线程在烧 |
| ③ 定函数 | `perf top -p <pid>` | 哪个函数占周期最多 |
| ④ 看调用链 | `perf record -g` → `perf report` / 火焰图 | 是谁调到这个热点 |

**常见原因**：死循环/自旋、忙等（该阻塞却轮询）、正则/序列化/加解密太重、锁竞争导致大量自旋。

### 3.2 内存持续上涨

| 步骤 | 工具/命令 | 看什么 |
|---|---|---|
| ① 确认 | `top` 看 RSS / `cat /proc/<pid>/status` | 是否真的在涨、涨多快 |
| ② 看分布 | `pmap -x <pid>` / `smaps` | 是堆涨、还是 mmap/某段涨 |
| ③ 抓泄漏 | `valgrind --leak-check=full` 或 ASan/LSan | 泄漏点的分配栈 |

**常见原因**：忘 free/delete、容器只增不减、缓存无淘汰、句柄/连接泄漏（间接撑大内存）。原理见 [[03-Linux内存管理机制]]。

### 3.3 程序卡死 / 无响应

| 步骤 | 工具/命令 | 看什么 |
|---|---|---|
| ① 看线程栈 | `gdb -p <pid>` → `thread apply all bt` | 线程停在哪、是否互等锁 |
| ② 看系统调用 | `strace -p <pid>` | 卡在哪个 syscall（read/futex/connect） |
| ③ 判定类型 | 结合两者 | 死锁？等不到的条件变量？阻塞 IO？ |

**常见原因**：死锁（加锁顺序不一致）、条件变量没人唤醒、同步等一个永远不回的网络/磁盘 IO。

### 3.4 段错误（Segmentation fault）

| 步骤 | 工具/命令 | 看什么 |
|---|---|---|
| ① 开 core | `ulimit -c unlimited`（事前） | 让崩溃留下现场 |
| ② 加载 | `gdb ./app core` | 进入崩溃现场 |
| ③ 看栈 | `bt` → `frame N` → `info locals` | 崩在哪行、哪个指针非法 |

**常见原因**：空指针解引用、数组/`vector` 越界、use-after-free、栈溢出（深递归）、未初始化指针。能复现的话直接 `gdb ./app run` + ASan 更快。

## 四、常见坑与面试加分点

| 坑 / 误区 | 说明 |
|---|---|
| Release 包没符号没法调 | 用 `RelWithDebInfo` 或单独保留 split debug，线上才能 `gdb core` 定位 |
| `-O2` 下 gdb 变量显示"optimized out" | 优化把变量寄存器化/消除了，调试期临时降到 `-O0` |
| 编 `.so` 忘 `-fPIC` | 链接报错（重定位 R_X86_64_PC32），动态库必须位置无关 |
| 链接顺序写反 | 被依赖的库要放命令行后面，否则 `undefined reference` |
| 改了头文件没重编依赖它的 cpp | CMake/Make 靠时间戳，正常会重编；手敲命令容易漏 |
| ASan 和 Valgrind 同时开 | 互相冲突，二选一 |
| `LD_LIBRARY_PATH` 当长期方案 | 调试可以，发布应该用 rpath 或 ldconfig，否则换环境就崩 |
| core 没产生还以为没崩 | 多半是 `ulimit -c` 是 0，或被 systemd-coredump 接管，去 `coredumpctl` 找 |

**加分点（结合智能硬件/音视频）：**

> "嵌入式板子上常**没有 gdb、perf**，我会用**交叉编译版 gdbserver**：板子上 `gdbserver :1234 ./app`，开发机 `gdb` 远程连过去调；或者编 ASan 版本在板子上跑一遍抓内存问题。音视频管线 CPU 高就 `perf top` 看是不是编解码/缩放函数热，内存涨就重点查 AVFrame/AVPacket 有没有 `unref`。"

## 六、自测 8 题

1. gcc 编译四阶段分别用什么选项触发？各自产物是什么？
2. `undefined reference` 是哪个阶段报的？最常见的两个原因？
3. 静态库和动态库，可执行文件体积和运行时依赖各有什么不同？
4. 动态库运行时 `cannot open shared object`，按什么顺序排查和修？
5. 编动态库为什么必须 `-fPIC`？
6. 调一个卡死（不崩）的多线程程序，你敲哪两条 gdb 命令？
7. CPU 100% 的定位三步是什么？分别用什么工具？
8. Valgrind 和 AddressSanitizer 怎么选？

<details>
<summary>参考答案</summary>

1. 预处理 `-E`(.i)、编译 `-S`(.s)、汇编 `-c`(.o)、链接（默认，可执行文件）。
2. **链接阶段**；常见原因：漏链库（少 `-l`）、链接顺序不对（被依赖库要放后面），或函数只声明没定义。
3. 静态库代码拷进可执行文件，体积大、运行时无依赖；动态库运行时加载，体积小、可多进程共享，但要找得到 so。
4. `ldd` 看谁 not found → 按 rpath → `LD_LIBRARY_PATH` → `ldconfig` 缓存 → 默认路径定位 → 对应用 rpath / 环境变量 / `ldconfig` 修。
5. 动态库代码段要被多个进程映射到不同虚拟地址且共享同一物理页，必须位置无关；否则重定位报错。
6. `gdb -p <pid>` attach，再 `thread apply all bt` 看所有线程栈（互等锁=死锁）。
7. `top` 定进程 → `top -H -p <pid>` 定线程 → `perf top -p <pid>` 定热点函数。
8. 能改编译选项、开发/CI 阶段用 ASan（快、报错精确）；拿到的是不能重编的二进制用 Valgrind。二者不能同时开。

</details>
