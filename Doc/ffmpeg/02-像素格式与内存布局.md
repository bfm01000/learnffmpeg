# 02 - 像素格式与内存布局

> 对应导读第 3.3 节"解释问题"、第 6.4 节"Planar vs Packed"。
> 这一篇覆盖视频帧的像素格式（YUV / RGB）、三大内存排布流派、命名混乱与避坑，以及色彩空间和色彩范围（BT.601 vs BT.709、Full vs Limited Range）这两个引发"色偏 / 发灰"经典 bug 的概念。

---

## 一、为什么视频不用 RGB 而用 YUV

这是入门第一道分水岭。理解这一点，才能理解后面所有的"为什么有 4:2:0、为什么有 NV12、为什么硬件解码偏好某种格式"。

### 1.1 RGB 和 YUV 的根本差别

- **RGB**：红、绿、蓝三原色，加色混合。屏幕真正显示像素时用的就是 RGB。
- **YUV**：Y 是亮度（Luma，相当于灰度图），U/V 是色度（Chroma，颜色信息）。

### 1.2 利用人眼的"缺陷"做压缩

**生理学事实**：人眼对亮度（Y）极其敏感，对颜色（U/V）的变化不敏感。

视频领域据此做**色度子采样（Chroma Subsampling）**——保留所有的 Y，但大幅减少 U/V 的数量：

| 子采样格式 | 含义 | 数据量 |
|---|---|---|
| 4:4:4 | 不压缩。1 个 Y 配 1 个 U 和 1 个 V | 100% |
| 4:2:2 | 每 2 个 Y 共享 1 组 UV | 67% |
| **4:2:0** | **每 4 个 Y 共享 1 组 UV**（绝对主流） | **50%** |

YUV 4:2:0 每像素 1.5 字节，RGB24 每像素 3 字节。**仅这一步就把原始数据砍掉一半，而人眼几乎看不出差别**。

### 1.3 历史包袱也帮了 YUV 一把

YUV 最早是为兼容黑白电视设计的——只传输 Y 信号，黑白电视照样显示，彩电额外接收 UV 还原颜色。这个历史决定了所有现代视频编码（MPEG-2 / H.264 / HEVC / AV1）底层都基于 YUV 设计。

## 二、三大内存排布流派

在确定用 YUV 4:2:0 之后，4 个 Y、1 个 U、1 个 V 在物理内存里**到底怎么排列**，分成了三个流派。

### 2.1 Packed（打包 / 交错）

各分量绑在一起交错存放：

```
RGB24:   R G B  R G B  R G B  ...
YUYV:    Y U Y V  Y U Y V  ...
```

特点：

- 所有数据放在 `data[0]` 一块内存里
- 硬件声卡 / 显示器一路扫过去就能用
- **YUV 4:2:0 几乎从不使用 Packed**

为什么 4:2:0 不用 Packed？三个原因：

1. **无法优雅排布**：Y 和 UV 数量是 4:1，强行交错（`Y1 U1 Y2 V1 Y3 U2 Y4 V2`）寻址极其复杂。
2. **污染 CPU 缓存**：视频编码的运动搜索几乎只用 Y。如果 UV 混进来，每次读 Y 都被迫把 UV 也加载进缓存，浪费带宽。
3. **不利于灰度提取**：很多算法只要 Y 分量（人脸识别、运动检测），Packed 格式提取 Y 要跳跃读取。

### 2.2 Planar（平面）

三个分量完全分开放在三块独立内存：

```
data[0]:  Y Y Y Y Y Y Y Y ...       <- 全部 Y
data[1]:  U U U U ...               <- 全部 U
data[2]:  V V V V ...               <- 全部 V
```

代表格式：**`YUV420P` / `I420` / `YV12`**。

优势：Y 分量绝对纯净，视频编码器像推土机一样线性读取，效率最高。

### 2.3 Semi-Planar（半平面）

Y 一个平面，UV **交错**在第二个平面：

```
data[0]:  Y Y Y Y Y Y Y Y ...       <- 全部 Y
data[1]:  U V U V U V U V ...       <- UV 交错
```

代表格式：**`NV12` / `NV21`**。

**为什么 NVIDIA 要发明 NV12**（这是面试加分项）：

硬件解码 / 渲染时，**GPU 取一个像素的颜色总是同时需要 U 和 V**。

- Planar 格式中 U 和 V 相距甚远，分别读取导致两次 Cache Miss。
- Semi-Planar 中 U 和 V 紧邻，读 U 时旁边的 V **被同一条 Cache Line 顺便加载**，命中率大幅提升。

这就是为什么 Android MediaCodec、iOS VideoToolbox、绝大多数硬件编解码器都偏好 NV12。

## 三、命名大乱斗与避坑

不同生态对同一种格式有不同叫法，是工程里最让人头疼的部分。

### 3.1 I420 vs YUV420P：完全相同

- **`YUV420P`**：FFmpeg 命名（`AV_PIX_FMT_YUV420P`），强调"4:2:0 + Planar"。
- **`I420`**：FOURCC 规范命名，常见于 libyuv、WebRTC。

**字节排列 100% 一致**：先存完 Y，再存完 U，最后存完 V。

### 3.2 YV12：I420 的镜像兄弟

排布是 **Y → V → U**（注意 V 在前）。

记忆法：名字里带 V 在前，说明 V 排在前。

### 3.3 NV12 vs NV21：Android 开发的天坑

| 格式 | 第二平面 | 谁用 |
|---|---|---|
| **NV12** | `U V U V U V ...` | iOS VideoToolbox、大多数硬编码器、MediaCodec 标准输入 |
| **NV21** | `V U V U V U ...` | **Android Camera1 API 的 `onPreviewFrame` 默认输出** |

**经典 bug**：Android 用 Camera1 采集，直接把 NV21 喂给配置为 NV12 的 MediaCodec，画面**红蓝反色**（俗称"阿凡达脸"）。

解决方案：

- 用 libyuv 的 `NV21ToNV12` 或 GPU shader 转一次。
- 或配置 MediaCodec 时查询 `COLOR_FormatYUV420Flexible` 并动态适配。

## 四、linesize：图像里最隐蔽的坑

详见 [01-数据结构与生命周期.md](./01-数据结构与生命周期.md) 第 3.3 节，这里只强调结论：

`AVFrame->linesize[]` 是每个分量"一行"实际占的字节数。**它不一定等于 `width × 字节数`**——因为 FFmpeg 为了 SIMD（AVX/SSE/NEON）效率，按 16 或 32 字节对齐分配内存，行末常有 padding。

```
width = 100 字节
linesize = 128 字节 (32 字节对齐)
内存里:  [真实像素 100 bytes] [padding 28 bytes]
```

凡是按行操作图像（拷贝、scale、写文件），**永远按 `linesize` 偏移，不要按 `width` 算**。

YUV420P 三个平面 linesize 还不相等：Y 一行是 width 字节，U / V 各只有 width/2 字节（因为 4:2:0 在水平方向也减半采样）。

## 五、色彩空间与色彩范围

像素格式（YUV420P / NV12 / RGB24）描述的是**数据怎么排**。色彩空间和色彩范围描述的是**这些数值代表的颜色到底是多少**。

打个比方：**像素格式是"杯子的形状"，色彩空间是"杯子里装的饮料是可乐还是雪碧"**。同一个 NV12 内存块，里面的数值既可能是 BT.601 算出来的，也可能是 BT.709 算出来的，内存层面看不出差别。

### 5.1 BT.601 vs BT.709：两套不同的 RGB ↔ YUV 公式

- **BT.601**：标清电视标准。常用于 480p / 576p。
- **BT.709**：高清电视标准。常用于 720p / 1080p。
- **BT.2020**：4K / 8K / HDR 标准。

它们的根本差别是**亮度公式里 R / G / B 的权重不同**：

```
BT.601:  Y = 0.299  * R + 0.587  * G + 0.114  * B
BT.709:  Y = 0.2126 * R + 0.7152 * G + 0.0722 * B
```

为什么权重变了？两个原因：

1. **显示设备进化**：BT.601 时代是 CRT 大头电视，BT.709 时代是 LCD，红蓝荧光纯度提高，G 在亮度里的权重从 0.587 提升到 0.7152。
2. **色域更广**：BT.709 定义了更精确的 RGB 原色坐标，能表现更纯的颜色。

### 5.2 色偏 bug 的成因

一个 1080p 视频按 BT.709 编码，但你写 OpenGL shader 时**错误地套用了 BT.601 公式**：

- 因为 BT.601 给红色的权重（0.299）比 709 高（0.2126）
- 解出来的画面会**红色偏暗、绿色偏亮，整体灰蒙蒙**

正解：解码时读取流的 `colorspace` 字段（`AVColorSpace`），动态选择对应的转换矩阵。

### 5.3 Full Range vs Limited Range（0-255 vs 16-235）

8-bit 色彩深度下，每个通道理论上能表示 0~255。但实际分两种标准：

| 标准 | 别名 | Y 范围 | U/V 范围 | 用于 |
|---|---|---|---|---|
| **Full Range** | PC Range / JPEG Range | 0 ~ 255 | 0 ~ 255 | 电脑显示器、JPEG、游戏 |
| **Limited Range** | TV Range / Video Range / MPEG Range | 16 ~ 235 | 16 ~ 240 | 电视、电影、大多数视频文件 |

### 5.4 为什么有 16-235 这种限制

历史遗留。早期 CRT 模拟电视信号会过冲 / 欠冲。如果把 0 设为纯黑，一旦信号负向波动设备就无法处理（没有负数颜色）。所以工程师人为定义 16 为纯黑、235 为纯白：

- 0~15 是**脚趾区（Toeroom）**，吸收信号下冲。
- 236~255 是**头部区（Headroom）**，吸收信号过冲。

### 5.5 "发灰"和"死黑"两个经典 bug

YUV → RGB 时除了选 601 还是 709，**必须同时判断 Full 还是 Limited**：

- **视频是 Limited，播放器当 Full 处理**：播放器认为 0 才是纯黑，但视频最黑只有 16。结果——**画面发灰，像蒙了一层白纱（Washed out）**。
- **视频是 Full，播放器当 Limited 处理**：播放器把 ≤16 全当纯黑、≥235 全当纯白。结果——**暗部细节全丢（Crushed Blacks），亮部细节过曝（Clipping）**。

正解：解码时读取流的 `color_range`（`AVColorRange`），动态应用对应的渲染矩阵。

### 5.6 AVFrame 上的字段与枚举（落地用）

上面说的"读流的字段动态选矩阵"，具体是这两个字段：

| 字段（在 `AVFrame` / `AVCodecParameters` 上） | 类型 | 常见取值 |
|---|---|---|
| `colorspace` | `AVColorSpace` | `AVCOL_SPC_BT470BG`/`SMPTE170M`(≈BT.601)、`AVCOL_SPC_BT709`、`AVCOL_SPC_BT2020_NCL`(HDR) |
| `color_range` | `AVColorRange` | `AVCOL_RANGE_MPEG`(Limited)、`AVCOL_RANGE_JPEG`(Full) |

在 `sws_scale` 这一层怎么按这两个字段正确转换（而不是用它默认的 BT.601），见 [03-SwsContext-图像缩放与格式转换.md](./03-SwsContext-图像缩放与格式转换.md) §七点五 `sws_setColorspaceDetails`。

> **HDR / 10bit 的钩子**：本节通篇是 8-bit + BT.601/709。再往上是 **HDR**——色域 `AVCOL_SPC_BT2020_NCL`、传输函数 PQ/HLG（`color_trc` 字段）、10bit 像素格式如 `P010`（10bit 版 NV12）、`YUV420P10LE`。移动端 HDR 见 [10-移动端硬件编解码.md](./10-移动端硬件编解码.md)。本系列暂不深入,先知道 YUV 不止 8bit。

## 六、AVSampleFormat 枚举的命名规则（小结放这里）

音频的格式枚举命名也是一套"拼积木"规则。完整音频细节见 [04-音频PCM-采样-重采样.md](./04-音频PCM-采样-重采样.md)，这里只贴公式让你对照像素格式理解：

```
AV_SAMPLE_FMT_ + [数据类型/符号] + [位深] + [排布后缀]
```

- 数据类型：`U`（无符号）、`S`（有符号）、`FLT`（float）、`DBL`（double）
- 位深：`8` / `16` / `32` / `64`
- 排布：无后缀 = Packed，后缀 `P` = Planar

例：`AV_SAMPLE_FMT_S16` = 16 位有符号整数，Packed；`AV_SAMPLE_FMT_FLTP` = 浮点 Planar。

### 6.1 枚举末尾的 NB 千万别用

```c
enum AVSampleFormat {
    // ...
    AV_SAMPLE_FMT_NB   ///< DO NOT USE if linking dynamically
};
```

`NB` 是 Number，等于前面所有有效项的数量。但**动态链接时绝对不要用它做数组大小**——你编译时 `NB=10`，用户那边动态库升级到 `NB=12`，你的数组只有 10 个位置，访问越界直接 Segfault。这是 ABI 兼容性的经典反例。

## 七、常见 bug 对照表

| 现象 | 根因 |
|---|---|
| 画面倾斜 / 花屏 / 绿屏 | `linesize ≠ width × 字节数`，按 width 偏移导致 |
| 画面发灰，黑色不纯 | Limited Range 视频被当 Full Range 渲染 |
| 暗部 / 亮部细节丢失 | Full Range 视频被当 Limited Range 渲染 |
| 整体色偏，红色偏暗绿色偏亮 | 用了错的 BT.601 / BT.709 矩阵 |
| Android 摄像头红蓝反色 | NV21 被当 NV12 处理 |
| 解码后送 GPU 直接黑屏 | 硬件解码帧没下载到内存就传给 `sws_scale`（见 [07-硬件编解码.md](./07-硬件编解码.md)：先 `av_hwframe_transfer_data` 或用硬件滤镜） |
