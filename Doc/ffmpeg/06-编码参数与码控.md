## 一、面试速记卡

**Q：H.264 中决定压缩率和延迟的核心参数有哪些？**

> "H.264 的压缩效果由三个独立维度的参数决定：
>
> 1. **Profile**：决定算法复杂度。实时低延时场景倾向 `Constrained Baseline`（无 B 帧、低复杂度，解编快）；高清点播用 `High`（算法复杂，压缩率最高）。
> 2. **Preset**：决定 CPU 算力与压缩率的兑换关系。`ultrafast` → `veryslow` 共 10 档，越慢压缩率越高。实时场景选 `ultrafast` 配合 `tune=zerolatency`。
> 3. **码率控制（CRF / Bitrate）**：直接决定画质和文件大小。点播用 CRF 控制恒定质量，直播用 CBR / VBR 控制带宽上限。"

---

## 二、错误认知：H.264 没有"高 / 低"压缩率开关

很多新手以为 H.264 有一个叫 `High` 或 `Low` 的参数控制压缩率。**实际上压缩效果是三组独立参数共同决定的**：

- **画质 / 码率维度**（Bitrate / CRF）：直接控制文件大小
- **算法复杂度维度**（Profile / Level）：算法上限
- **算力 / 时间维度**（Preset / Tune）：花多少 CPU 时间搜索最优解

理解这三个维度独立后，所有参数搭配都能想明白。

## 三、第一层：码率控制（最直观影响"压缩率"）

### 3.1 CRF：相对控制（x264 最常用模式）

不指定码率，告诉编码器"我想要什么样的视觉质量"。

- **取值范围**：`0 ~ 51`
- **规则**：**数值越低画质越好压缩率越低（文件越大）**，反之亦然
- **甜点区**：`18 ~ 28`（默认 23）
  - `18`：视觉上基本无损
  - `23`：默认
  - `28+`：能看出马赛克

CRF 模式下文件大小完全不确定，但画质稳定。**点播首选 CRF**。

#### 3.1.1 CRF 与 CBR/VBR/ABR 互斥：源码证据与选型决策

**CRF 和 CBR/VBR/ABR 是互斥的**——它们共享同一个 `i_rc_method` 字段，是二选一的关系。

##### 源码证据

在 FFmpeg 的 `libx264.c: X264_init()` 中，两套方法的设置是**先后执行、后写的覆盖先写的**：

```c
// === libx264.c: X264_init() ===

// 第一步：如果用户设了 -b:v，默认走 ABR（即 CBR/VBR/ABR 的共同基类）
if (avctx->bit_rate) {
    x4->params.rc.i_bitrate   = avctx->bit_rate / 1000;
    x4->params.rc.i_rc_method = X264_RC_ABR;    // ← 先设为 ABR (2)
}

// ... 若干代码 ...

// 第二步：如果用户设了 -crf，直接覆盖上面的 ABR
if (avctx->flags & AV_CODEC_FLAG_PASS2) {
    x4->params.rc.b_stat_read = 1;
} else {
    if (x4->crf >= 0) {
        x4->params.rc.i_rc_method   = X264_RC_CRF;   // ← 覆盖为 CRF (1)
        x4->params.rc.f_rf_constant = x4->crf;
    } else if (x4->cqp >= 0) {
        x4->params.rc.i_rc_method   = X264_RC_CQP;   // ← 或覆盖为 CQP (0)
        x4->params.rc.i_qp_constant = x4->cqp;
    }
}
```

x264 内部只有 **3 种** `i_rc_method`，CBR 和 VBR 根本不在枚举里：

```c
// === x264.h ===
#define X264_RC_CQP  0   // 恒定 QP
#define X264_RC_CRF  1   // 恒定质量（画质优先）
#define X264_RC_ABR  2   // 平均码率（码率优先）—— CBR 和 VBR 都是它
```

**结论**：如果你同时设了 `-b:v 4000k -crf 23`，CRF 会赢（因为后执行），但这是"意外获胜"，不是设计意图。`i_bitrate` 字段可能残留非零值，在 x264 某些路径（如 VBV 初始化）中读到后会导致行为**不保证、不一致、不同版本表现不同**。

##### 为什么必须互斥：两套完全不同的码控哲学

| | CRF（`X264_RC_CRF`） | ABR 系列（`X264_RC_ABR`） |
|---|---|---|
| **目标** | 画质恒定 | 码率收敛 |
| **输入参数** | `-crf 23`（质量值） | `-b:v 4000k`（比特数） |
| **每帧决策依据** | 帧复杂度 → 选 QP 保证视觉质量一致 | 帧复杂度 + VBV 桶水位 → 选 QP 保证码率收敛 |
| **输出码率** | **不可预测**（看内容复杂度） | **可控**（看 VBV 约束松紧） |
| **输出画质** | **稳定** | **波动**（码率紧张时画质变差） |
| **VBV 桶** | 无（或仅作为上限保护 `crf_max`） | 核心驱动机制 |
| **场景** | 点播、本地归档 | 直播、带宽受限传输 |

用空调类比：

> - CRF = **恒温空调**：不管耗多少电，室温死守 23°C。画质恒定，码率是结果。
> - ABR = **定频空调**：不管室温多高，每小时只能用 2 度电。码率恒定，画质是结果。
>
> 你没法同时告诉空调"死守 23°C"**和**"每小时只能用 2 度电"——这两个目标在物理上会冲突。复杂的视频帧就像 40°C 高温天——要么多花电费保温度（CRF → 码率飙升），要么忍室温上升（ABR → 画质下降）。

##### CBR / VBR / ABR 三者之间不互斥

这一点容易混淆。从上面源码可以看到，CBR 和 VBR 不是独立的 `i_rc_method`，它们和 ABR 共用 `X264_RC_ABR`。三者是**一条连续谱**，由 VBV 参数决定你在谱上的位置（详见 [§3.2.3 的"三者关系"](#323-abraverage-bitrate平均码率)）：

```
CBR  = X264_RC_ABR + bufsize 极小 + vbv_max_bitrate <= i_bitrate
ABR  = X264_RC_ABR + bufsize 中等 + vbv_max_bitrate >  i_bitrate
VBR  = X264_RC_ABR + bufsize 极大（或干脆不加 maxrate/bufsize）
```

##### 选型决策树

```
你的场景需要码率可控吗？
│
├── 不需要（点播/归档）→ CRF
│   └── ffmpeg -i in.mp4 -c:v libx264 -crf 23 -preset slow out.mp4
│
└── 需要（直播/带宽受限）→ ABR 系列（详见 §3.2）
    │
    ├── 必须码率绝对平稳 → CBR
    │   └── -b:v 4000k -maxrate 4000k -bufsize 2000k
    │
    ├── 允许一定波动，峰值可控 → VBV 约束的 VBR（推荐）
    │   └── -b:v 4000k -maxrate 4500k -bufsize 8000k
    │
    └── 只关心文件总大小，不关心瞬时波动 → ABR
        └── -b:v 4000k -maxrate 8000k -bufsize 16000k
```

##### 相关踩坑：§7.2

> 开了 CRF 就别再设 `codecCtx->bit_rate`——CRF（恒定质量）和目标码率（恒定码率）是两套互斥的码控目标，同时设会互相打架、行为难以预测。要么 CRF（点播），要么 bit_rate + maxrate/bufsize（直播），二选一。

### 3.2 Bitrate：绝对控制

直接告诉编码器"我希望每秒数据量是多少"。三种模式的核心区别：

```
CBR:  码率 │━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━│  死死卡在目标值
                    → 时间轴

VBR:  码率 │  ╱╲     ╱╲╲╲╲     ╱╲    │  剧烈波动，每帧按复杂度自由分配
                    → 时间轴

ABR:  码率 │  ╱╲  ╱╲  ╱╲╲╲  ╱╲  ╱╲ │  帧间有波动，但长时间窗口
          │ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │  ← 平均值严格逼近目标
                    → 时间轴
```

#### 3.2.1 CBR（Constant Bitrate，固定码率）

**一句话**：无论画面是静止的蓝天还是满屏爆炸特效，**每一帧的码率都被死死控制在目标值附近**，波动极小。

**编码器内部怎么做的**：CBR 模式下，编码器先收到一个目标值（比如 4000kbps），然后每编码一帧就问自己——"上一帧有没有超支？"如果上一帧用了太多比特，这一帧就提高 QP（降低画质），把码率压回去；如果上一帧用得少，这一帧可以稍微放松。这个反馈循环**逐帧运行**，所以码率曲线近乎一条直线。

**优点**：
- 带宽可预测——CDN 节点和播放端可以精确预测每一秒的流量
- 不会因为画面突然剧烈运动码率飙升、撑爆观众的网络
- 适合公网传输这种"带宽像固定马路"的场景

**代价**：
- 静态画面（主播坐着不动）：明明 1500kbps 就够，编码器却必须塞满 4000kbps——**浪费带宽**
- 复杂画面（游戏爆炸特效）：编码器被上限卡死，只能疯狂提高 QP、**满屏马赛克**

```bash
# FFmpeg: 标准 CBR
ffmpeg -i input.mp4 -c:v libx264 \
    -b:v 4000k \          # 目标码率
    -minrate 4000k \      # 下限 = 上限 = 目标，强制 CBR
    -maxrate 4000k \      # 上限
    -bufsize 2000k \      # 小 buffer，盯得紧
    -f flv rtmp://...
```

**什么时候用 CBR**：传统 RTMP 直播（OBS 推流）、视频会议（每一帧延迟敏感）、卫星/有线电视广播。

#### 3.2.2 VBR（Variable Bitrate，可变码率）

**一句话**：**画质优先**。编码器先定一个质量目标，再根据每帧画面的复杂度分配码率——简单的帧少给点，复杂的帧多给点。码率是**结果**，不是目标。

**编码器内部怎么做的**：VBR 模式下，编码器的首要指令是"保持质量稳定"——通常由 `-qmin` / `-qmax` 这样的 QP 范围控制。遇到静态画面，少量比特就能维持质量，编码器自然用低码率；遇到剧烈运动，需要大量比特才能维持同等质量，码率就飙上去。**编码器不关心平均码率是多少**——如果整段视频都很复杂，平均码率可能远超预期。

**纯 VBR 的危险**：没有上限的 VBR，码率可以短时间内暴涨 3~5 倍。直播场景下这是致命的——CDN 无法预测瞬时流量，观众带宽可能被打爆，缓冲转圈。**直播中纯 VBR 绝对禁止。**

**什么时候用 VBR**：
- 本地录制/归档（追求最佳画质，不担心码率峰值）
- 视频后期中间码（需要保留质量给下一步处理）
- 配合 VBV 约束后用于现代直播（见 §3.2.5）

```bash
# FFmpeg: 纯 VBR（-b:v 在 x264 中设为 0 并配合 -crf 即为 VBR）
ffmpeg -i input.mp4 -c:v libx264 \
    -crf 23 \             # ★ 恒定质量，码率自适应
    -preset medium \
    output.mp4

# FFmpeg: 目标码率的 VBR（-b:v 配合 maxrate，但 bufsize 很大 = VBR 倾向）
ffmpeg -i input.mp4 -c:v libx264 \
    -b:v 4000k \          # 目标码率（宽松）
    -maxrate 12000k \     # 峰值给了 3× 的空间
    -bufsize 16000k \     # 大 buffer，不太约束
    output.mp4
```

#### 3.2.3 ABR（Average Bitrate，平均码率）

**一句话**：**平均码率是目标**。在 VBR 的自由分配基础上，加了一个"长时间窗口平均值"的紧箍咒——允许帧间波动，但整个窗口（几秒到几十秒）的平均值必须严格收敛到目标。

**⚠️ 面试重名陷阱**：ABR 在音视频领域有两个完全不同的意思，千万不能搞混：

| | ABR 编码 | ABR 传输 |
|--|---------|---------|
| 全称 | **A**verage **B**itrate Encoding | **A**daptive **B**itrate **R** Streaming |
| 是什么 | 编码器的码率控制算法（本节内容） | 播放器根据网络动态切码率档位的技术（HLS/DASH） |
| 发生在哪 | 编码阶段 | 传输/播放阶段 |
| 控制什么 | 编码器内部怎么分配比特 | 播放器选哪个码率档的流 |

**编码器内部怎么做的**：ABR 维护一个 VBV 缓冲模型：

```
┌──────────────────────────────────────┐
│  VBV 缓冲桶 (bufsize = 8000kbit)      │
│                                      │
│  进水口: 编码器每产出 1 帧 →          │
│          桶水位 += 该帧的实际比特数     │
│                                      │
│  出水口: 时间每流逝 1 秒 →            │
│          桶水位 -= 目标码率 × 1 秒     │
│                                      │
│  ★ 桶快满了 → 后面帧压更狠（提高 QP）  │
│  ★ 桶快空了 → 后面帧多给些（降低 QP）  │
└──────────────────────────────────────┘
```

编码器不是在内存里存过去 N 秒的帧数据——那样内存早爆了。靠的就是这个"桶"：**桶的水位 = 历史的码率消耗 vs 目标码率之间的累积偏差**。水位高了说明"过去花太多了"，后面得省着点；水位低了说明"过去花少了"，后面可以大方些。

**ABR 和 VBR 的本质区别**：

VBR 编码器每帧独立决策——"这帧复杂，多给码率；下帧简单，少给"。它没有一个全局的"平均窗口"概念。ABR 编码器每帧决策时要回头看一眼桶水位——"这帧虽然复杂，但我过去 5 秒已经超支了，必须勒紧腰带"。

**ABR 和 CBR 的本质区别**：

CBR 每帧都盯。ABR 盯的是窗口——允许某几帧超支、某几帧省着，只要窗口内的平均在目标附近就行。所以 ABR 的瞬时码率曲线有波动，CBR 几乎是一条直线。

```bash
# FFmpeg: ABR 编码
ffmpeg -i input.mp4 -c:v libx264 \
    -b:v 4000k \          # ★ 目标平均码率
    -maxrate 6000k \      # 峰值上限（防止瞬时飙太高）
    -bufsize 8000k \      # 桶容量（控制平均窗口大小）
    -preset veryfast \
    output.mp4
```

**三者关系**：`CBR → ABR → VBR` 本质上是 `bufsize` 从 0 到 ∞ 的连续谱，不是三个离散档位：

```
bufsize 极小 (≈ 0.5× maxrate) → 桶很浅，每帧都被盯死 → 接近 CBR
bufsize 中等 (≈ 2× maxrate)   → 允许几秒波动 → ABR
bufsize 很大 (≈ 10× maxrate)  → 几乎不约束 → 接近 VBR
bufsize = ∞                    → 纯 VBR
```

> **⚠️ CBR / ABR / VBR 三者同属 `X264_RC_ABR` 方法，与 CRF 互斥**——详见 [§3.1.1](#311-crf-与-cbrvbrabr-互斥源码证据与选型决策) 的源码级分析。简单说：CRF 目标是画质恒定，ABR 系列目标是码率收敛，你只能选一个。

**什么时候用 ABR**：
- HLS/DASH 分片（保证每个 .ts/.m4s 分片大小一致，观众切档体验平滑）
- 视频上传平台（控制文件总大小的同时保留复杂画面的质量）
- 24×7 监控录像（存储空间可预测 + 关键帧不被压糊）

#### 3.2.4 maxrate 与 bufsize：VBV 缓冲模型的深入解析

前面多次出现了 `-maxrate` 和 `-bufsize`，但都作为"配套参数"一笔带过。这两个参数是理解 CBR/ABR/VBR 连续谱的**核心旋钮**，值得单独深入。

##### 两个参数各自的含义

**`-maxrate`（最大码率）**：

不是"每秒数据量的硬上限"，而是 **VBV 模型的注水速率**——解码端以这个速率从 VBV 缓冲区里**取数据**。在 x264 源码中：

```c
// === ratecontrol.c ===
rc->vbv_max_rate = h->param.rc.i_vbv_max_bitrate;  // 就是 -maxrate
rc->buffer_rate  = vbv_max_bitrate / rc->fps;       // 每帧的"预算"
```

关键认知：编码器**可以在某一帧瞬间超过 maxrate**——只要 VBV 桶里还有水。maxrate 约束的是"一段时间的平均"，不是"某一帧的瞬时"。

**`-bufsize`（缓冲区大小）**：

**VBV 桶的容量**。单位是 kbits（和码率相同单位但含义不同——这是容量，不是速率）。

```c
// === ratecontrol.c ===
rc->buffer_size = h->param.rc.i_vbv_buffer_size;  // 就是 -bufsize
```

把 VBV 模型想象成一个**底部有洞的水桶**：

```
                    编码器输出（灌水）
                         │
                         ▼
┌──────────────────────────────────────┐
│                                      │
│   VBV 桶 (bufsize = 8000 kbits)       │
│   当前水位 = buffer_fill              │
│                                      │
│   ═══════════════════════════════    │  ← 满了 → 塞 filler 或等待
│   ║░░░░░░░░░░░░░░░░░░░░░░░░░░░║    │
│   ║░░░░░ 当前水位 ░░░░░░░░░░░░║    │
│   ║░░░░░░░░░░░░░░░░░░░░░░░░░░░║    │
│   ═══════════════════════════════    │  ← 空了 → VBV underflow! QP 飙升
│                                      │
└──────────────────┬───────────────────┘
                   │
                   ▼  以 maxrate 的速率漏水（解码端取走）
```

每编码一帧：桶水位 **+= 该帧实际比特数**（灌水）。时间流逝：桶水位 **-= maxrate × 时间**（漏水）。桶的容量 = `bufsize`。

##### 两者配合的核心公式

```
bufsize / maxrate = VBV 缓冲窗口（秒）
```

这个时间窗口是**一切码控行为的根源**：

| 窗口大小 | bufsize 设置 | 效果 |
|---------|-------------|------|
| ~0.5 秒 | `bufsize = 0.5× maxrate` | 桶极浅 → 每帧都受强约束 → **CBR** |
| ~2 秒 | `bufsize = 2× maxrate` | 桶适中 → 允许几秒波动 → **ABR** |
| ~10 秒 | `bufsize = 10× maxrate` | 桶很深 → 几乎不约束 → **接近 VBR** |
| ∞ | 不设 maxrate/bufsize | 无桶 → **纯 VBR** |

##### 源码怎么用这两个参数：逐帧控制

这是 x264 `ratecontrol.c` 中帧编码完成后的核心逻辑：

```c
// === ratecontrol.c: update_vbv() ===

// 第一步：桶水位减去本帧消耗的比特
rct->buffer_fill_final -= (uint64_t)bits * time_scale;
rct->buffer_fill_final_min -= (uint64_t)bits * time_scale;

// 第二步：underflow 检测
if (rct->buffer_fill_final_min < 0) {
    // ★ 桶被打爆了！编码器"花超了"，钳位到 0
    rct->buffer_fill_final = rct->buffer_fill_final_min = 0;
}

// 第三步：以 maxrate 速率向桶里"注水"（时间流逝的等效）
rct->buffer_fill_final += (uint64_t)maxrate * cpb_duration;
rct->buffer_fill_final_min += (uint64_t)maxrate * cpb_duration;

// 第四步：overflow 处理——桶满了说明编码器"太省了"
// 要么塞 filler 数据（硬 CBR），要么钳位到 buffer_size（自然 VBR）
```

而在**帧编码前**，x264 会用 `update_vbv_plan()` 模拟未来几帧的桶水位变化，如果预判会溢出或掏空，就提前调整 QP：

```c
// === ratecontrol.c: VBV 约束下的 QP 调整 ===

// 桶快空了 (< 50%) → 提高 QP，降低画质，省比特
if (rcc->buffer_fill / rcc->buffer_size < 0.5)
    q /= x264_clip3f(2.0 * rcc->buffer_fill / rcc->buffer_size, 0.5, 1.0);

// 硬约束：预测的本帧比特数 > 桶剩余容量 → 必须提 QP
if (bits > rcc->buffer_fill / max_fill_factor) {
    double qf = x264_clip3f(rcc->buffer_fill / (max_fill_factor * bits), 0.2, 1.0);
    q /= qf;  // qf < 1 → q 增大 → QP 增大 → 码率降低
}
```

**本质**：`-maxrate` + `-bufsize` 定义了一个**虚拟的恒定码率信道**。编码器的任务是在这个信道约束下尽可能保持画质。桶水位是"历史偏差"的积分——它回答"过去一段时间我花多了还是花少了"。

##### 实战参数选择指南

**场景 1：纯 CBR（带宽绝对可预测）**

```bash
-b:v 4000k -maxrate 4000k -bufsize 2000k
# bufsize/maxrate = 0.5 秒 ← 桶极浅，逐帧盯死
# 适用：卫星广播、传统 RTMP 推流、硬件编码器
```

**场景 2：VBV 约束的 VBR（直播推荐）**

```bash
-b:v 4000k -maxrate 4500k -bufsize 8000k
# bufsize/maxrate = 1.78 秒 ← 桶适中，允许短期波动
# maxrate 只比 bitrate 高 12.5% ← 峰值可控
# 适用：现代商业直播、游戏直播
```

**场景 3：宽松 ABR（存储优先）**

```bash
-b:v 4000k -maxrate 8000k -bufsize 16000k
# bufsize/maxrate = 2 秒，maxrate = 2× bitrate
# 适用：监控录像、视频上传平台
```

**场景 4：CRF + VBV 安全网（点播+带宽约束兼顾）**

```bash
-crf 23 -maxrate 8000k -bufsize 16000k
# 正常画面用 CRF 保证画质，极端复杂场景用 VBV 兜底
# 适用：在线视频平台（YouTube 风格）
```

##### 常见误区

**误区 1："maxrate 是每秒硬上限"**

❌ 编码器可以在某一帧瞬间产出 3× maxrate 的码率，只要 VBV 桶还没空。
✅ maxrate 是桶的**出水速率**，约束的是**时间窗口内的平均**，不是逐秒截断。

**误区 2："bufsize 设得越大画质越好"**

❌ bufsize 越大 → 桶越深 → 瞬时波动约束越松 → 画质越稳定。
✅ 但桶越深 → 解码端要先填到一定水位才能开播 → **首帧延迟更高**。直播场景要在画质和延迟之间做权衡。

**误区 3："bufsize 应该等于 maxrate"**

❌ 如果 `-bufsize 4000k -maxrate 4000k`，桶只有 1 秒的缓冲，而且 CBR 的 `b_vbv_min_rate` 会被激活，码率被逼成一条直线。
✅ 只有当你确实需要硬 CBR 时才这样设。大多数场景下 `bufsize = 1.5~2× maxrate` 更合理。

**误区 4："不设 maxrate/bufsize 就是 VBR"**

✅ 字面上对——没有 VBV 约束，编码器按 `i_bitrate` 做 ABR，波动自由。
⚠️ 但 x264 的 ABR 即使不设 maxrate，内部也有一套收敛算法保证**长时间窗口**的平均码率趋近目标。它不像纯 CRF 那样完全不管码率。

##### 延迟 vs 画质：bufsize 是旋钮

```
bufsize 小 ──────────────────────── bufsize 大
    │                                      │
  CBR 侧                               VBR 侧
    │                                      │
  桶浅，每帧盯死                        桶深，允许波动
  QP 频繁调整                           QP 稳定
  码率曲线 ≈ 直线                      码率曲线有波峰波谷
  画质波动大                            画质稳定
  解码端秒开快                          解码端要预填缓冲
    │                                      │
    └──── 直播/低延迟 ───────┴────── 点播/画质优先 ────┘
```

> 这一节的 VBV 概念和 §6.3 中 [bufsize 背后的 VBV / HRD 缓冲模型](#bufsize-背后的-vbv--hrd-缓冲模型) 是同一件事的不同视角——本节侧重"编码器内部怎么用"，§6.3 侧重"对解码端首帧延迟的影响"。

#### 3.2.5 直播场景的码控选型：CBR vs VBV 约束的 VBR

前面讲清楚了三种模式各自是什么，这里讲实战中"直播到底用什么"。

**方案 1：标准 CBR——传统 RTMP 直播的默认选项**

OBS 推流到 CDN，默认就是 CBR。码率曲线接近一条直线（雷打不动的 4000kbps）。

为什么是默认：
- 直播走公网，网络带宽像一条固定宽度的马路。CBR 让 CDN 节点、推流端、播放端都能**精准预测带宽消耗**。
- 不会因为画面突然剧烈运动而码率飙升、撑爆观众的宽带。

代价：静态画面浪费带宽，复杂画面牺牲画质（§3.2.1 已讲）。

**方案 2：VBR + maxrate + bufsize（VBV 约束）——现代商业直播的黄金方案**

完全不加限制的 VBR 在直播里是**绝对禁止的**——CDN 无法预测瞬时码率、观众带宽可能被打爆。但聪明的工程师在 VBR 基础上加了"紧箍咒"——**VBV 缓冲模型**（即 `-maxrate` + `-bufsize`）。

它的行为：
- 主播坐着不动时 → 码率自动降到 ~1500 kbps，**省带宽**
- 画面激烈打斗/特效 → 码率开始飙升
- 触碰到 `-maxrate` 上限（比如 4500 kbps）→ **被死死卡住**，绝不越雷池一步
- 同时受 `-bufsize` 约束——即使瞬时越过 maxrate，也不能持续超过

```bash
# 商业直播黄金组合
ffmpeg -i ... -c:v libx264 \
    -b:v 4000k \            # 目标码率
    -maxrate 4500k \        # 峰值上限（只比目标高一点）
    -bufsize 8000k \        # 桶容量 ≈ 2× maxrate（约 2 秒缓冲）
    -preset veryfast \
    -tune zerolatency \
    -f flv rtmp://...
```

**一句话总结**：

> 完全自由的 VBR → 直播禁止。标准 CBR → 传统直播标配，但静态浪费、动态糊。**VBR + maxrate + bufsize（VBV 约束）→ 现代商业直播的黄金方案**——既省带宽又保清晰度，带宽峰值可预测。

#### 3.2.6 WebRTC 用的是什么码控？

WebRTC 的码控思路和前面讲的 CBR/ABR/VBR **完全不在一个维度上**——它不是"编码器内部固定一个策略"，而是**网络状况实时驱动编码器改变目标码率**。

```
传统直播 (RTMP):
  编码器目标码率 = 你写死的 4000kbps
  网络变差 → 推流卡、丢帧、但码率不变

WebRTC:
  编码器目标码率 = 拥塞控制算法实时计算出来的值
  网络变差 → GCC 检测到丢包/延迟增加
           → 降低目标码率 (比如 4000→2000)
           → 通知编码器: "你现在按 2000kbps 编码"
  网络恢复 → 慢慢加回 4000
```

**两层结构**：

**上层：拥塞控制（GCC）——决定"允许发多快"**

Google 的标准实现是 **GCC（Google Congestion Control）**，每 ~100ms 跑一次，输出动态变化的 `target_bitrate`：
- **基于延迟的估计**（delay-based）：看 RTP 单向延迟的变化趋势。延迟持续上升 → 队列排队了 → 降码率。用 Kalman Filter 做趋势检测。
- **基于丢包的估计**（loss-based）：看 RTCP 反馈的丢包率。丢包 > 阈值（2~10%）→ 链路拥塞 → 快速降码率。

**下层：编码器执行——"怎么发"**

- **libvpx（VP8/VP9，WebRTC 主力软件编码器）**：在 target_bitrate 约束下做 VBR 风格的帧级分配——简单帧少用、复杂帧多用，整体收敛在目标附近。效果接近**"目标值实时变化的 ABR"**。
- **硬件编码器（MediaCodec / VideoToolbox）**：大多数设为 CBR 模式，目标值由 GCC 动态更新。

**一句话**：前面讲的 CBR/VBR/ABR 是**固定目标的编码策略**，WebRTC 的码控是**动态目标的编码策略**——目标值由网络状况决定，编码器只是执行器。面试时不要回答"CBR"或者"VBR"，要回答**"两层结构：GCC 定目标 → 编码器执行"**。


## 四、第二层：编码工具集与性能上限（Profile / Level）

这就是新手以为存在的"High / Low"参数。Profile 规定了编码器**允许使用多么复杂的数学算法**。

### 4.1 Profile

级别越高，**同等画质下文件越小，但解码算力要求越高、延迟越大**。

#### Baseline / Constrained Baseline Profile（基础级别）

- **算法**：最简单。**不支持 B 帧**，不支持 CABAC（高级算术编码）
- **压缩率**：最低
- **核心优势**：**极低延迟**。没有 B 帧意味着解码器不需要等待后续帧
- **典型场景**：车载实时预览、安防监控、老旧低端手机

> **关于 WebRTC 与 Baseline 的常见误解**：很多资料说"WebRTC 必须用 Baseline"——这是过时的简化。现代 WebRTC（libwebrtc、各浏览器）普遍优先 **Constrained Baseline（CBP）**，且很多场景已支持 **Constrained High / Main**。本质诉求是"**无 B 帧的低延迟取向**"，不是硬性锁死 Baseline。具体走哪个 Profile 由两端 SDP 的 `profile-level-id` 协商决定（见 [08-网络协议与流媒体.md](./08-网络协议与流媒体.md) 的 WebRTC 实时栈）。

#### Main Profile（主流级别）

- **算法**：引入 B 帧和 CABAC
- **压缩率**：中等
- **典型场景**：标清电视广播、网页视频点播

#### High Profile（高级别）

- **算法**：引入 8×8 帧内预测、自定义量化矩阵等复杂技术
- **压缩率**：**最高**
- **核心劣势**：编 / 解码极耗 CPU，大量使用 B 帧带来天然延迟
- **典型场景**：蓝光光盘、4K / 1080P 高清电影点播

### 4.2 Level：性能上限

如果 Profile 限制"算法"，Level 限制"性能"——最大分辨率、最大帧率、最大码率、解码端缓冲帧数（DPB）。**Level 与是否用 B 帧无关**（用不用 B 帧由 Profile 决定），别把两者混在一起。

换句话说：

```text
Profile = 允许使用哪些编码工具
Level   = 这条码流的规模/复杂度上限，解码设备扛不扛得住
```

所以 Profile 不是单纯的"压缩率等级"。高级 Profile 通常压缩率更好，是因为它允许使用 B 帧、CABAC、8×8 变换等更复杂工具；真正限制 720p/1080p/4K、码率、帧率和 DPB 的是 Level。


| Level | 典型支持                 |
| ----- | -------------------- |
| 3.1   | 720p @ 30fps         |
| 4.0   | 1080p @ 30fps        |
| 4.1   | 1080p @ 30fps（蓝光最常用） |
| 5.0   | 1080p @ 60fps        |
| 5.1   | 4K @ 30fps           |
| 5.2   | 4K @ 60fps           |


硬件解码芯片会标明最高支持的 Profile + Level。

## 五、第三层：算力与时间的交易（Preset / Tune）

选定 Profile（算法上限）和 CRF（目标画质）后，编码器还要做一件事：**在限制内搜索最优编码方案**。

### 5.1 Preset：编码速度预设

决定编码器花多少 CPU 时间搜索最优解。x264 提供 10 档：

```
ultrafast -> superfast -> veryfast -> faster -> fast ->
medium (默认) ->
slow -> slower -> veryslow -> placebo
```

核心逻辑：

- `**ultrafast**`：编码器随便选一个差不多的方案就输出。CPU 占用极低、速度极快、**同等画质下文件大**（压缩率低）。
- `**veryslow`**：编码器穷举各种可能性找到最高效压缩。CPU 满载、速度极慢、**同等画质下文件极小**（压缩率极高）。
- `**placebo`**：比 veryslow 还慢、收益微乎其微的档位，**几乎只用于研究**。x264 官方建议不要在生产用。

### 5.2 Tune：场景调优

告诉编码器视频类型，对症下药。


| Tune              | 用途                                       |
| ----------------- | ---------------------------------------- |
| `film`            | 真实电影（保留胶片颗粒感）                            |
| `animation`       | 动画（大面积纯色、线条锐利）                           |
| `grain`           | 颗粒感强的素材（保留噪点）                            |
| `stillimage`      | 单张图像 / 幻灯片                               |
| `psnr` / `ssim`   | 优化客观质量指标（不优化主观观感，慎用）                     |
| `**zerolatency`** | **零延迟！强制关闭编码器内部 lookahead 缓冲、强制不使用 B 帧** |


`zerolatency` 是低延迟场景的关键。即使你选了 Baseline（已经无 B 帧），还是建议明确加上 `tune=zerolatency`，因为它会同时关闭其他向前看（lookahead）相关的缓冲。

## 六、典型业务场景的参数组合

### 6.1 车载相机低延迟预览 / 视频会议

**诉求**：绝对不能有延迟，画质和带宽次要。

```bash
ffmpeg -i input.mp4 \
    -c:v libx264 \
    -profile:v baseline \
    -preset ultrafast \
    -tune zerolatency \
    -b:v 2000k \
    output.mp4
```

### 6.2 离线高清电影压制 / 短视频存储

**诉求**：文件尽可能小（省 CDN 流量），画质尽可能高，压制慢无所谓。

```bash
ffmpeg -i input.mp4 \
    -c:v libx264 \
    -profile:v high \
    -preset slow \
    -crf 18 \
    output.mp4
```

### 6.3 直播推流（实时性 + 兼容性兼顾）

**诉求**：1-3 秒延迟可接受，带宽要稳定可控，所有客户端要能播。

```bash
ffmpeg -re -i input.mp4 \
    -c:v libx264 \
    -profile:v main \
    -preset veryfast \
    -tune zerolatency \
    -b:v 2500k -maxrate 2500k -bufsize 5000k \
    -g 50 -keyint_min 50 \
    -f flv rtmp://server/live/streamKey
```

注意几点：

- `-g 50` 是 GOP 长度 50 帧 = 2 秒（25fps）。GOP 与 IDR/关键帧、首屏秒开的关系见 [05-H264-MP4-NALU.md](./05-H264-MP4-NALU.md) 的 GOP 小节（那里用 `M/N` 描述，`N≈-g`、`M-1≈bframes`）
- `-maxrate` + `-bufsize` 是 CBR 风格的码率上限控制
- `-tune zerolatency` 关闭内部缓冲

#### `-bufsize` 背后的 VBV / HRD 缓冲模型

`-bufsize` 不是随手填的，它就是 **VBV（Video Buffering Verifier，H.264 里也叫 HRD）** 的缓冲区大小。直觉模型：把码流想象成往一个"漏桶"里灌水——编码器灌、解码端按码率漏，`bufsize` 是桶的容量。

- 桶越大 → 瞬时码率可以"借"得越多（运动场景短时冲高、静止时还回来），画质更稳，但**解码端要先把桶填到一定水位才能开播，首帧延迟更高**。
- 桶越小 → 码率被卡得越死（越接近严格 CBR），延迟越低，但复杂画面容易掉质量。

所以直播常把 `bufsize` 设成 `1~2 × maxrate`（约 1~2 秒缓冲）：既约束带宽峰值、又不让首屏等太久。设成 `maxrate` 就接近硬 CBR、低延迟；设很大则接近 VBR、画质优先但秒开变慢。这正是"延迟 vs 画质稳定"在码控层的旋钮。

> 关于 `-maxrate` + `-bufsize` 在编码器内部的完整工作原理（VBV 桶的源码实现、QP 调整逻辑、各场景的参数选择表），详见 [§3.2.4](#324-maxrate-与-bufsizevbv-缓冲模型的深入解析)。

### 6.4 直播行业三大技术架构方案

码控解决的是「单条流怎么压」的问题，但整个直播链路的延迟和成本由**技术架构**决定。当前行业主要有三种方案，根据业务诉求选择：

#### 方案 1：传统流媒体方案（RTMP 推流 + HTTP-FLV/HLS 播放）——市场份额最高

```
主播 ──RTMP(H.264+AAC)──▶ CDN 服务器 ──HTTP-FLV/HLS──▶ 百万观众
```

- **延迟**：3 秒 ~ 15 秒左右（受 GOP 长度和 HLS 切片时长影响）。
- **适用场景**：游戏直播、大咖秀、不需要频繁连麦互动的普通带货直播。
- **优点**：技术极其成熟，CDN 成本非常低，并发支撑能力极强——几百万人同时看轻轻松松。RTMP 推流 + FLV/HLS 分发的组合经过十几年大规模验证，基础设施完善到牙齿。
- **缺点**：延迟高，无法做实时互动（连麦、抢单），观众看到的画面比主播实际慢好几秒。

#### 方案 2：超低延迟 / 快直播方案（WebRTC 协议栈）——正在颠覆行业的方案

```
主播 ◀─── WebRTC (UDP + SRTP + Opus/H.264) ───▶ SFU 服务器 ───▶ 观众
```

- **延迟**：**低于 1 秒**（典型 500ms ~ 800ms）。电商带货场景下"3、2、1 上链接"时观众和主播完全同步。
- **适用场景**：电商抢单、秀场打赏互动、直播连麦 PK、在线教育 1v1。
- **优点**：互动体验极佳，观众感觉就在台下。UDP 天然无队头阻塞，丢包不重传、用 FEC 和 PLC 恢复。
- **缺点**：CDN 不兼容（WebRTC 走 UDP，传统 CDN 是 TCP/HTTP 设施），大规模分发成本高，观众数上限受限于 SFU 服务器的带宽和算力。

#### 方案 3：混合转码方案（WebRTC/SRT 进 + RTMP/HLS 出）——兼顾互动与成本

```
主播 ──WebRTC/SRT──▶ 流媒体网关 ──(转码: Opus→AAC)──▶ CDN ──RTMP/FLV──▶ 百万观众
                       │
                       └── 同一 SFU ──WebRTC──▶ 连麦对端（低延迟互动）
```

- **架构核心**：主播端为了连麦和低延迟，使用 WebRTC 或 SRT 协议推流到流媒体网关。网关在后端把音频从 Opus 转成 AAC、视频维持 H.264，再用传统 RTMP/FLV 分发给百万普通观众。同时 SFU 把连麦双方的低延迟流直接转发，不经过转码。
- **适用场景**：大型直播活动（需要连麦互动 + 海量围观观众）。
- **优点**：**主播端互动不卡顿，观众端享受便宜的传统 CDN 带宽**。这是目前性价比最高的企业级架构——抖音、快手、淘宝直播都在这个思路上。
- **缺点**：网关转码引入额外延迟（~1-2 秒）和成本（需要 GPU/ASIC 转码集群），架构复杂度高。

**三种方案一句话选型**：

> 单向直播、海量观众 → 方案 1（RTMP+FLV，CDN 成本最低）。
> 实时互动、小房间 → 方案 2（纯 WebRTC，延迟最优）。
> 需要连麦互动 + 大规模分发 → 方案 3（混合转码，性价比最优）。

### 6.5 商业直播推流编码器配置总结

如果你要配置一个商业级的直播推流编码器，记住这四条铁律：

1. **码率控制**：选 **CBR**（传统稳妥），或 **VBR + 明确的 `-maxrate` + `-bufsize`**（现代优化）。**绝对不要用纯 VBR 或纯 CRF**——瞬时码率不可预测会导致 CDN 分发链路崩溃。

2. **关键帧间隔**：强制 `-g`（GOP 长度）= **2 秒**（25fps 即 50 帧），且帧类型**全为 IDR 帧**。GOP 越短首屏秒开越快、seek 越快、抗丢包越好；太长则压缩率高但互动体验差。2 秒是商业直播的经验甜点。

3. **音频**：推流用 **AAC-LC**（传统 RTMP/FLV 链路），或 **Opus**（WebRTC 实时链路）。RTMP 只能用 AAC/Speex，不要尝试推 Opus 到传统 CDN。

4. **编码器预设**：`preset=veryfast`（x264）是直播的性价比甜点——比 `ultrafast` 压缩率高不少，比 `faster` 只快一点点，CPU 占用可接受。

```bash
# 商业直播推流的标准命令模板
ffmpeg -re -i input \
    -c:v libx264 \
    -preset veryfast \
    -tune zerolatency \
    -profile:v main \
    -b:v 4000k -maxrate 4500k -bufsize 8000k \
    -g 50 -keyint_min 50 -sc_threshold 0 \
    -c:a aac -b:a 128k -ar 48000 -ac 2 \
    -f flv rtmp://server/live/streamKey
```

> **参数解释**：`-maxrate 4500k` 比 `-b:v 4000k` 略高 12.5%，给瞬时运动场景留一点喘息空间。`-bufsize 8000k` 约 2 秒缓冲（4000kbps×2s=8000kb），平衡延迟与画质。`-sc_threshold 0` 关闭场景切换自动插关键帧（避免 GOP 被意外打断、码率波动）。

## 七、C++ API 设置方式

### 7.1 设置 Bitrate

```cpp
codecCtx->bit_rate = 2000000;          // 2 Mbps
codecCtx->rc_max_rate = 2500000;       // VBR 最大码率
codecCtx->rc_min_rate = 1500000;       // VBR 最小码率
codecCtx->rc_buffer_size = 2000000;    // 缓冲区大小,配合 max_rate
```

### 7.2 设置 CRF（x264 私有参数）

CRF 是 x264 内部参数，必须通过 `av_opt_set` 操作 `priv_data`：

```cpp
extern "C" {
    #include <libavutil/opt.h>
}

av_opt_set(codecCtx->priv_data, "crf", "23", 0);
```

> **踩坑**：开了 CRF 就别再设 `codecCtx->bit_rate`——CRF（恒定质量）和目标码率（恒定码率）是两套互斥的码控目标，同时设会互相打架、行为难以预测。要么 CRF（点播），要么 bit_rate + maxrate/bufsize（直播），二选一。源码层面的原因详见 [§3.1.1](#311-crf-与-cbrvbrabr-互斥源码证据与选型决策)。

### 7.3 设置 Profile

两种方式都行：

```cpp
// 方式 1: 使用 FFmpeg 宏定义
codecCtx->profile = FF_PROFILE_H264_BASELINE;
// codecCtx->profile = FF_PROFILE_H264_MAIN;
// codecCtx->profile = FF_PROFILE_H264_HIGH;

// 方式 2: 字符串 opt
av_opt_set(codecCtx->priv_data, "profile", "baseline", 0);
```

### 7.4 设置 Preset 和 Tune

```cpp
av_opt_set(codecCtx->priv_data, "preset", "ultrafast", 0);
av_opt_set(codecCtx->priv_data, "tune", "zerolatency", 0);
```

### 7.5 完整：初始化一个低延时编码器

```cpp
bool initLowLatencyEncoder(AVCodecContext*& codecCtx) {
    const AVCodec* codec = avcodec_find_encoder(AV_CODEC_ID_H264);
    if (!codec) return false;

    codecCtx = avcodec_alloc_context3(codec);

    // 基本参数
    codecCtx->width = 1920;
    codecCtx->height = 1080;
    codecCtx->time_base = {1, 30};
    codecCtx->framerate = {30, 1};
    codecCtx->pix_fmt = AV_PIX_FMT_YUV420P;
    codecCtx->bit_rate = 2000000;

    // 低延迟核心三件套
    codecCtx->profile = FF_PROFILE_H264_CONSTRAINED_BASELINE;
    av_opt_set(codecCtx->priv_data, "preset", "ultrafast", 0);
    av_opt_set(codecCtx->priv_data, "tune", "zerolatency", 0);

    // 显式表达低延迟意图(zerolatency 已会这么做,显式更清晰)
    codecCtx->max_b_frames = 0;            // 不要 B 帧,消除重排序延迟
    codecCtx->gop_size = 30;               // 短 GOP,1 秒一个关键帧便于秒开/抗丢包

    if (avcodec_open2(codecCtx, codec, nullptr) < 0) {
        return false;
    }
    return true;
}
```

## 八、bit_rate_tolerance 是什么

```cpp
codecCtx->bit_rate = 2000000;
codecCtx->bit_rate_tolerance = 100000;  // 100 kbps
```

`bit_rate_tolerance` 表示**允许码率围绕目标值波动的范围**。

什么时候需要：

- CBR / ABR 模式下，希望严格控制码率波动
- 一些直播链路要求带宽稳定，方便 CDN 调度

什么时候不需要：

- CRF / QP 模式下码率本来就在变，这字段不是核心
- 大多数情况留默认即可

这个字段是 FFmpeg 的通用接口，**具体实现取决于编码器**。x264 / x265 等不同编码器对它的响应程度不同。

## 九、不只是 H.264

H.265 / HEVC 的参数体系几乎完全平行——profile（Main / Main10 / Main12 / Main 4:4:4）、preset、tune、CRF（默认 28，因为压缩更狠所以推荐值更高）。

AV1 也有类似的速度档位（`-cpu-used 0-8`）和 CRF 范围。

学一次 H.264 的码控思路，迁移到其他编码几乎免费。H.264 与 H.265 在**比特流结构**上的关键差异（CTU、2 字节 NAL header、多出来的 VPS 参数集、`hevc_mp4toannexb`）见 [05-H264-MP4-NALU.md](./05-H264-MP4-NALU.md) 的"H.264 → H.265 差异速查"；两者的**编码原理、架构、使用场景与专利授权、面试速记和常考题**的系统讲解见专题 [11-H264与H265详解.md](./11-H264与H265详解.md)。
