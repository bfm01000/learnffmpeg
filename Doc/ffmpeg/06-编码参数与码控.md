# 06 - 编码参数与码控（Profile / Preset / Tune / CRF / CBR / VBR）

> 对应导读第 3.1 节"压缩问题"。
> 这一篇覆盖 H.264 编码里**控制画质 / 体积 / 速度 / 延迟**的核心参数，以及它们如何映射到 FFmpeg 命令行和 C++ API。

---

## 一、面试速记卡

**Q：H.264 中决定压缩率和延迟的核心参数有哪些？**

> "H.264 的压缩效果由三个独立维度的参数决定：
>
> 1. **Profile**：决定算法复杂度。实时低延时场景倾向 `Constrained Baseline`（无 B 帧、低复杂度，解编快）；高清点播用 `High`（算法复杂，压缩率最高）。
> 2. **Preset**：决定 CPU 算力与压缩率的兑换关系。`ultrafast` → `veryslow` 共 10 档，越慢压缩率越高。实时场景选 `ultrafast` 配合 `tune=zerolatency`。
> 3. **码率控制（CRF / Bitrate）**：直接决定画质和文件大小。点播用 CRF 控制恒定质量，直播用 CBR / VBR 控制带宽上限。"

---

## 二、错误认知：H.264 没有"高 / 低"压缩率开关

很多新手以为 H.264 有一个叫 `High` 或 `Low` 的参数控制压缩率。**实际上压缩效果是三组独立参数共同决定的**：

- **画质 / 码率维度**（Bitrate / CRF）：直接控制文件大小
- **算法复杂度维度**（Profile / Level）：算法上限
- **算力 / 时间维度**（Preset / Tune）：花多少 CPU 时间搜索最优解

理解这三个维度独立后，所有参数搭配都能想明白。

---

## 三、第一层：码率控制（最直观影响"压缩率"）

### 3.1 Bitrate：绝对控制

直接告诉编码器"我希望每秒数据量是多少"。


| 模式      | 全称                     | 行为                        | 场景                       |
| ------- | ---------------------- | ------------------------- | ------------------------ |
| **CBR** | Constant Bitrate（固定码率） | 无论画面静止还是剧烈运动，码率死死卡在固定值    | 严格的网络传输（早期直播），防止突发流量冲爆带宽 |
| **VBR** | Variable Bitrate（可变码率） | 静止画面用低码率，运动画面用高码率，平均接近目标值 | 大多数流媒体点播                 |
| **ABR** | Average Bitrate（平均码率）  | 类似 VBR，但更严格地约束平均值         | HLS / DASH 自适应切片         |


### 3.2 CRF：相对控制（x264 最常用模式）

不指定码率，告诉编码器"我想要什么样的视觉质量"。

- **取值范围**：`0 ~ 51`
- **规则**：**数值越低画质越好压缩率越低（文件越大）**，反之亦然
- **甜点区**：`18 ~ 28`（默认 23）
  - `18`：视觉上基本无损
  - `23`：默认
  - `28+`：能看出马赛克

CRF 模式下文件大小完全不确定，但画质稳定。**点播首选 CRF**。

## 四、第二层：编码工具集与性能上限（Profile / Level）

这就是新手以为存在的"High / Low"参数。Profile 规定了编码器**允许使用多么复杂的数学算法**。

### 4.1 Profile

级别越高，**同等画质下文件越小，但解码算力要求越高、延迟越大**。

#### Baseline / Constrained Baseline Profile（基础级别）

- **算法**：最简单。**不支持 B 帧**，不支持 CABAC（高级算术编码）
- **压缩率**：最低
- **核心优势**：**极低延迟**。没有 B 帧意味着解码器不需要等待后续帧
- **典型场景**：车载实时预览、安防监控、老旧低端手机

> **关于 WebRTC 与 Baseline 的常见误解**：很多资料说"WebRTC 必须用 Baseline"——这是过时的简化。现代 WebRTC（libwebrtc、各浏览器）普遍优先 **Constrained Baseline（CBP）**，且很多场景已支持 **Constrained High / Main**。本质诉求是"**无 B 帧的低延迟取向**"，不是硬性锁死 Baseline。具体走哪个 Profile 由两端 SDP 的 `profile-level-id` 协商决定（见 [08-网络协议与流媒体.md](./08-网络协议与流媒体.md) 的 WebRTC 实时栈）。

#### Main Profile（主流级别）

- **算法**：引入 B 帧和 CABAC
- **压缩率**：中等
- **典型场景**：标清电视广播、网页视频点播

#### High Profile（高级别）

- **算法**：引入 8×8 帧内预测、自定义量化矩阵等复杂技术
- **压缩率**：**最高**
- **核心劣势**：编 / 解码极耗 CPU，大量使用 B 帧带来天然延迟
- **典型场景**：蓝光光盘、4K / 1080P 高清电影点播

### 4.2 Level：性能上限

如果 Profile 限制"算法"，Level 限制"性能"——最大分辨率、最大帧率、最大码率、解码端缓冲帧数（DPB）。**Level 与是否用 B 帧无关**（用不用 B 帧由 Profile 决定），别把两者混在一起。

换句话说：

```text
Profile = 允许使用哪些编码工具
Level   = 这条码流的规模/复杂度上限，解码设备扛不扛得住
```

所以 Profile 不是单纯的"压缩率等级"。高级 Profile 通常压缩率更好，是因为它允许使用 B 帧、CABAC、8×8 变换等更复杂工具；真正限制 720p/1080p/4K、码率、帧率和 DPB 的是 Level。


| Level | 典型支持                 |
| ----- | -------------------- |
| 3.1   | 720p @ 30fps         |
| 4.0   | 1080p @ 30fps        |
| 4.1   | 1080p @ 30fps（蓝光最常用） |
| 5.0   | 1080p @ 60fps        |
| 5.1   | 4K @ 30fps           |
| 5.2   | 4K @ 60fps           |


硬件解码芯片会标明最高支持的 Profile + Level。

## 五、第三层：算力与时间的交易（Preset / Tune）

选定 Profile（算法上限）和 CRF（目标画质）后，编码器还要做一件事：**在限制内搜索最优编码方案**。

### 5.1 Preset：编码速度预设

决定编码器花多少 CPU 时间搜索最优解。x264 提供 10 档：

```
ultrafast -> superfast -> veryfast -> faster -> fast ->
medium (默认) ->
slow -> slower -> veryslow -> placebo
```

核心逻辑：

- `**ultrafast**`：编码器随便选一个差不多的方案就输出。CPU 占用极低、速度极快、**同等画质下文件大**（压缩率低）。
- `**veryslow`**：编码器穷举各种可能性找到最高效压缩。CPU 满载、速度极慢、**同等画质下文件极小**（压缩率极高）。
- `**placebo`**：比 veryslow 还慢、收益微乎其微的档位，**几乎只用于研究**。x264 官方建议不要在生产用。

### 5.2 Tune：场景调优

告诉编码器视频类型，对症下药。


| Tune              | 用途                                       |
| ----------------- | ---------------------------------------- |
| `film`            | 真实电影（保留胶片颗粒感）                            |
| `animation`       | 动画（大面积纯色、线条锐利）                           |
| `grain`           | 颗粒感强的素材（保留噪点）                            |
| `stillimage`      | 单张图像 / 幻灯片                               |
| `psnr` / `ssim`   | 优化客观质量指标（不优化主观观感，慎用）                     |
| `**zerolatency`** | **零延迟！强制关闭编码器内部 lookahead 缓冲、强制不使用 B 帧** |


`zerolatency` 是低延迟场景的关键。即使你选了 Baseline（已经无 B 帧），还是建议明确加上 `tune=zerolatency`，因为它会同时关闭其他向前看（lookahead）相关的缓冲。

## 六、典型业务场景的参数组合

### 6.1 车载相机低延迟预览 / 视频会议

**诉求**：绝对不能有延迟，画质和带宽次要。

```bash
ffmpeg -i input.mp4 \
    -c:v libx264 \
    -profile:v baseline \
    -preset ultrafast \
    -tune zerolatency \
    -b:v 2000k \
    output.mp4
```

### 6.2 离线高清电影压制 / 短视频存储

**诉求**：文件尽可能小（省 CDN 流量），画质尽可能高，压制慢无所谓。

```bash
ffmpeg -i input.mp4 \
    -c:v libx264 \
    -profile:v high \
    -preset slow \
    -crf 18 \
    output.mp4
```

### 6.3 直播推流（实时性 + 兼容性兼顾）

**诉求**：1-3 秒延迟可接受，带宽要稳定可控，所有客户端要能播。

```bash
ffmpeg -re -i input.mp4 \
    -c:v libx264 \
    -profile:v main \
    -preset veryfast \
    -tune zerolatency \
    -b:v 2500k -maxrate 2500k -bufsize 5000k \
    -g 50 -keyint_min 50 \
    -f flv rtmp://server/live/streamKey
```

注意几点：

- `-g 50` 是 GOP 长度 50 帧 = 2 秒（25fps）。GOP 与 IDR/关键帧、首屏秒开的关系见 [05-H264-MP4-NALU.md](./05-H264-MP4-NALU.md) 的 GOP 小节（那里用 `M/N` 描述，`N≈-g`、`M-1≈bframes`）
- `-maxrate` + `-bufsize` 是 CBR 风格的码率上限控制
- `-tune zerolatency` 关闭内部缓冲

#### `-bufsize` 背后的 VBV / HRD 缓冲模型

`-bufsize` 不是随手填的，它就是 **VBV（Video Buffering Verifier，H.264 里也叫 HRD）** 的缓冲区大小。直觉模型：把码流想象成往一个"漏桶"里灌水——编码器灌、解码端按码率漏，`bufsize` 是桶的容量。

- 桶越大 → 瞬时码率可以"借"得越多（运动场景短时冲高、静止时还回来），画质更稳，但**解码端要先把桶填到一定水位才能开播，首帧延迟更高**。
- 桶越小 → 码率被卡得越死（越接近严格 CBR），延迟越低，但复杂画面容易掉质量。

所以直播常把 `bufsize` 设成 `1~2 × maxrate`（约 1~2 秒缓冲）：既约束带宽峰值、又不让首屏等太久。设成 `maxrate` 就接近硬 CBR、低延迟；设很大则接近 VBR、画质优先但秒开变慢。这正是"延迟 vs 画质稳定"在码控层的旋钮。

## 七、C++ API 设置方式

### 7.1 设置 Bitrate

```cpp
codecCtx->bit_rate = 2000000;          // 2 Mbps
codecCtx->rc_max_rate = 2500000;       // VBR 最大码率
codecCtx->rc_min_rate = 1500000;       // VBR 最小码率
codecCtx->rc_buffer_size = 2000000;    // 缓冲区大小,配合 max_rate
```

### 7.2 设置 CRF（x264 私有参数）

CRF 是 x264 内部参数，必须通过 `av_opt_set` 操作 `priv_data`：

```cpp
extern "C" {
    #include <libavutil/opt.h>
}

av_opt_set(codecCtx->priv_data, "crf", "23", 0);
```

> **踩坑**：开了 CRF 就别再设 `codecCtx->bit_rate`——CRF（恒定质量）和目标码率（恒定码率）是两套互斥的码控目标，同时设会互相打架、行为难以预测。要么 CRF（点播），要么 bit_rate + maxrate/bufsize（直播），二选一。

### 7.3 设置 Profile

两种方式都行：

```cpp
// 方式 1: 使用 FFmpeg 宏定义
codecCtx->profile = FF_PROFILE_H264_BASELINE;
// codecCtx->profile = FF_PROFILE_H264_MAIN;
// codecCtx->profile = FF_PROFILE_H264_HIGH;

// 方式 2: 字符串 opt
av_opt_set(codecCtx->priv_data, "profile", "baseline", 0);
```

### 7.4 设置 Preset 和 Tune

```cpp
av_opt_set(codecCtx->priv_data, "preset", "ultrafast", 0);
av_opt_set(codecCtx->priv_data, "tune", "zerolatency", 0);
```

### 7.5 完整：初始化一个低延时编码器

```cpp
bool initLowLatencyEncoder(AVCodecContext*& codecCtx) {
    const AVCodec* codec = avcodec_find_encoder(AV_CODEC_ID_H264);
    if (!codec) return false;

    codecCtx = avcodec_alloc_context3(codec);

    // 基本参数
    codecCtx->width = 1920;
    codecCtx->height = 1080;
    codecCtx->time_base = {1, 30};
    codecCtx->framerate = {30, 1};
    codecCtx->pix_fmt = AV_PIX_FMT_YUV420P;
    codecCtx->bit_rate = 2000000;

    // 低延迟核心三件套
    codecCtx->profile = FF_PROFILE_H264_CONSTRAINED_BASELINE;
    av_opt_set(codecCtx->priv_data, "preset", "ultrafast", 0);
    av_opt_set(codecCtx->priv_data, "tune", "zerolatency", 0);

    // 显式表达低延迟意图(zerolatency 已会这么做,显式更清晰)
    codecCtx->max_b_frames = 0;            // 不要 B 帧,消除重排序延迟
    codecCtx->gop_size = 30;               // 短 GOP,1 秒一个关键帧便于秒开/抗丢包

    if (avcodec_open2(codecCtx, codec, nullptr) < 0) {
        return false;
    }
    return true;
}
```

## 八、bit_rate_tolerance 是什么

```cpp
codecCtx->bit_rate = 2000000;
codecCtx->bit_rate_tolerance = 100000;  // 100 kbps
```

`bit_rate_tolerance` 表示**允许码率围绕目标值波动的范围**。

什么时候需要：

- CBR / ABR 模式下，希望严格控制码率波动
- 一些直播链路要求带宽稳定，方便 CDN 调度

什么时候不需要：

- CRF / QP 模式下码率本来就在变，这字段不是核心
- 大多数情况留默认即可

这个字段是 FFmpeg 的通用接口，**具体实现取决于编码器**。x264 / x265 等不同编码器对它的响应程度不同。

## 九、不只是 H.264

H.265 / HEVC 的参数体系几乎完全平行——profile（Main / Main10 / Main12 / Main 4:4:4）、preset、tune、CRF（默认 28，因为压缩更狠所以推荐值更高）。

AV1 也有类似的速度档位（`-cpu-used 0-8`）和 CRF 范围。

学一次 H.264 的码控思路，迁移到其他编码几乎免费。H.264 与 H.265 在**比特流结构**上的关键差异（CTU、2 字节 NAL header、多出来的 VPS 参数集、`hevc_mp4toannexb`）见 [05-H264-MP4-NALU.md](./05-H264-MP4-NALU.md) 的"H.264 → H.265 差异速查"；两者的**编码原理、架构、使用场景与专利授权、面试速记和常考题**的系统讲解见专题 [11-H264与H265详解.md](./11-H264与H265详解.md)。
