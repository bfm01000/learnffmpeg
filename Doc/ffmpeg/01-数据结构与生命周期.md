## 一、四个核心结构体的关系

```
AVFormatContext     <-- 解封装/封装上下文,统领全局
   |
   +-- AVStream[0]  <-- 一路视频流
   |     |
   |     +-- codecpar     <-- 解码参数描述(宽高、像素格式、SPS/PPS)
   |     |
   |     +-- AVCodecContext  <-- 解码器/编码器的工作环境(由 codecpar 拷贝得到)
   |              |
   |              +-- AVCodec  <-- 算法本体(全局共享,无状态)
   |
   +-- AVStream[1]  <-- 一路音频流
         |
         +-- (同上)

   数据沿这条流水线流动:
   AVPacket(压缩) -> AVCodecContext -> AVFrame(原始) -> 加工 -> AVFrame -> AVCodecContext -> AVPacket
```

记住一句话：`**AVPacket` 进出编码器/解码器是分水岭，进去前是压缩包，出来后是原始数据。**

## 二、AVPacket（压缩包）

`AVPacket` 存放编码后的数据，例如 H.264 的 NALU 字节、AAC 的压缩帧。它体积小，适合存储和网络传输，**不能直接显示或播放**。

### 2.1 视频包和音频包的一个关键区别

- **视频 AVPacket**：通常 1 个包对应 1 帧画面（一个 H.264 NALU）。
- **音频 AVPacket**：1 个包可能包含 1 帧也可能包含多帧。一个 AAC packet 可能打包了多个音频帧。

**推论**：写音频解码时，`avcodec_send_packet` 后必须用 `while` 循环 `avcodec_receive_frame` 直到返回 `EAGAIN`，否则会丢音频。

### 2.2 核心字段


| 字段                 | 含义                                          |
| ------------------ | ------------------------------------------- |
| `uint8_t *data`    | 指向压缩字节的指针                                   |
| `int size`         | 字节数                                         |
| `int64_t pts`      | 显示时间戳（刻度，不是秒）                               |
| `int64_t dts`      | 解码时间戳。无 B 帧时 pts == dts                     |
| `int stream_index` | 流编号。读 MP4 时靠它分辨这个包属于视频流还是音频流                |
| `int flags`        | 关键位是 `AV_PKT_FLAG_KEY`，标识 I 帧。拖动进度条只能跳到 I 帧 |


DTS 和 PTS 为什么会分开？因为有 B 帧。B 帧需要参考它后面的 P 帧才能解码——**解码顺序和显示顺序错开了**。

## 三、AVFrame（原始数据）

`AVFrame` 存放解码后的原始像素或 PCM。它体积庞大，1080P 的 RGB 一帧约 6 MB。这是显卡和声卡真正能消费的格式。

### 3.1 内存布局：data[] 是一个数组而非单指针

很多新手在这里栽跟头。`AVFrame->data[AV_NUM_DATA_POINTERS]` 是一个指针数组：

- **Packed 格式**（如 `RGB24`、`S16` 音频）：所有数据交错存在 `data[0]`，其他指针为空。
- **Planar 格式**（如 `YUV420P`、`FLTP` 音频）：分量分开存放，`data[0]` 是 Y / 左声道，`data[1]` 是 U / 右声道，`data[2]` 是 V。

详见 [02-像素格式与内存布局.md](./02-像素格式与内存布局.md)。

### 3.2 核心字段


| 字段                                   | 含义                                                    |
| ------------------------------------ | ----------------------------------------------------- |
| `int linesize[AV_NUM_DATA_POINTERS]` | 每个分量"一行"实际占的字节数。**不一定等于 `width × 字节数`**，可能有对齐 padding |
| `int width / height`                 | 视频实际像素宽高                                              |
| `int format`                         | 视频对应 `AVPixelFormat`，音频对应 `AVSampleFormat`            |
| `int64_t pts`                        | 显示时间戳。音视频同步靠它                                         |
| `int64_t best_effort_timestamp`      | 当 `pts` 是 `AV_NOPTS_VALUE` 时的兜底值                      |
| `int nb_samples`                     | 音频专属。每个声道的采样点数（不是总采样点）                                |
| `int sample_rate`                    | 音频专属。采样率                                              |


> 关于 `pkt_dts` 等 `pkt_*` 字段：在 FFmpeg 6.0 之后正在被废弃。逻辑上 Frame 不该再持有 Packet 的属性（Frame 也可能是滤镜凭空生成的），新代码尽量避免依赖。

### 3.3 linesize 经典翻车现场

```cpp
// 错误：直接整块拷贝,会因为 padding 导致画面倾斜或花屏
memcpy(dst, frame->data[0], width * height);

// 正确：逐行拷贝,按 linesize 偏移源,按 dstLinesize 偏移目的
for (int row = 0; row < height; row++) {
    memcpy(
        dst + row * dstLinesize,
        frame->data[0] + row * frame->linesize[0],
        width
    );
}
```

例：真实画面宽 100 字节，为 32 字节对齐 `linesize` 被分配成 128 字节。每行末尾有 28 字节 padding。对齐填充的因果链、偏差累积表、RGB24/PPM/SDL 踩坑详见 [02-像素格式与内存布局.md](./02-像素格式与内存布局.md) 第 4 节。

## 四、AVCodec vs AVCodecContext

这是 ffmpeg 设计里最容易让人困惑的一对——为什么编解码要分成两个结构体？

### 4.1 AVCodec：算法本体（无状态）

- **本质**：底层是一堆函数指针（`init / decode / encode / close`）的结构体。
- **无状态**：不保存任何特定流的进度、宽高、帧率。**全局只需要一个实例**，例如全局只有一个 H.264 解码器 `AVCodec`。
- **能力声明**：定义当前算法支持哪些特性（支持的像素格式 `pix_fmts`、采样率、硬件加速能力等）。
- **类比**：菜谱本身，或者面向对象里的"类的方法"。

### 4.2 AVCodecContext：工作环境（有状态）

- **本质**：解码器/编码器的实例，装载参数和动态状态。
- **有状态**：保存当前流的宽高、像素格式、解码进度、内部参考帧缓冲。
- **类比**：正在炖肉的那口锅（记录了放了多少盐、炖了多久）；或者面向对象里的"对象属性"。

### 4.3 初始化分三步的原因

```cpp
// 1. 分配上下文(传入算法本体)
AVCodecContext* codecCtx = avcodec_alloc_context3(codec);

// 2. 把流的实际参数(从文件读出来的 codecpar)填进去
avcodec_parameters_to_context(codecCtx, stream->codecpar);

// 3. 启动底层引擎
avcodec_open2(codecCtx, codec, nullptr);
```

为什么不一步到位？因为第 1 步和第 3 步之间，**开发者有机会自定义参数**。比如想强制开启 B 帧、想换硬件解码器、想覆盖某些 codec 私有选项——这些都要在 `open2` 之前完成。

`open2` 这一步真正干的事：

- 校验你填的参数合不合法（这个 codec 支不支持这个宽高、格式）
- 分配 codec 内部的 `priv_data`（参考帧缓冲、内部状态）
- 把底层函数指针挂载好，准备被调用

### 4.4 alloc 和 open2 传入不同 codec 会怎样

`open2` 的源码逻辑大致是：

```c
int avcodec_open2(AVCodecContext *avctx, const AVCodec *codec, AVDictionary **options) {
    if (codec) {
        // 显式传了,覆盖 alloc 时绑定的
        avctx->codec = codec;
        avctx->codec_id = codec->id;
    } else if (avctx->codec) {
        // 没传,用 alloc 时绑定的
        codec = avctx->codec;
    } else {
        return AVERROR(EINVAL);
    }
    // ...
}
```

三种情况：

- **两个 codec ID 相同**：`open2` 覆盖。典型用法是 `alloc` 时绑了软解 H.264，`open2` 时强制换成 `h264_cuvid` 硬解。
- **ID 不同**（视频 vs 音频）：内部校验失败，返回 `AVERROR(EINVAL)`。
- `**open2` 传 nullptr**：用 `alloc` 时的绑定。

### 4.5 AVCodecContext 既能编码也能解码吗

是。`AVCodecContext` 是通用容器。它到底承载编码状态还是解码状态，取决于你绑定的 codec：

- 解码：`avcodec_find_decoder()` + `avcodec_send_packet` + `avcodec_receive_frame`
- 编码：`avcodec_find_encoder()` + `avcodec_send_frame` + `avcodec_receive_packet`

一个具体的 `AVCodecContext` 实例通常只承担一种角色。

## 五、资源生命周期：alloc / ref / unref / free / uninit / close

这套命名是 ffmpeg 设计里最值得花时间理解的——它通过 API 名字本身传达资源所有权和释放责任。

### 5.1 六个动词的语义层级


| 动词                     | 操作什么                       | 比喻            |
| ---------------------- | -------------------------- | ------------- |
| `*_alloc`              | 分配壳子（结构体本身）。数据缓冲区还没分配      | 买一个空信封        |
| `*_ref`                | 引用计数 +1，浅拷贝                | 给信件加把锁        |
| `*_unref`              | 引用计数 -1，归零才真正释放数据。**壳子保留** | 倒掉信件，信封留着     |
| `*_free`               | 销毁整个对象（壳子也扔）               | 信封进垃圾桶        |
| `*_uninit`             | 清理内部状态，**对象本身（栈变量）还在**     | 清掉家具，房子还在     |
| `*_close` / `*_closep` | 关闭一个已经打开的资源/句柄/文件          | 关门 / 关门并把地址擦掉 |


### 5.2 最容易混淆的一组：unref 和 free

```cpp
av_packet_unref(pkt);   // pkt 这个壳还能继续用,装下一个包
av_packet_free(&pkt);   // pkt 整个销毁,指针也置空
```

`AVFrame` 完全同理。**循环里反复处理的对象只用 unref，循环外才 free**——这是 ffmpeg 代码的肌肉记忆。

```cpp
// 错误写法:每帧都 alloc+free,性能极差
while (av_read_frame(fmtCtx, pkt) >= 0) {
    AVPacket *pkt = av_packet_alloc();
    // ... 处理 ...
    av_packet_free(&pkt);
}

// 正确写法:外面 alloc 一次,循环内 unref 复用,结束 free
AVPacket *pkt = av_packet_alloc();
while (av_read_frame(fmtCtx, pkt) >= 0) {
    // ... 处理 ...
    av_packet_unref(pkt);
}
av_packet_free(&pkt);
```

如果循环里不写 `av_packet_unref(pkt)`，`AVPacket` 这个外壳虽然被复用了，但它每次读到的底层数据引用没有被及时释放，长时间处理文件或直播流时就容易出现内存持续上涨。

底层真正做引用计数的不是 `AVPacket` 本身，而是它里面的 `AVBufferRef *buf` 指向的 `AVBuffer`：

```text
AVPacket
  └── AVBufferRef *buf
        └── AVBuffer
              ├── data
              ├── size
              └── refcount
```

可以把关系理解成：

```text
AVPacket* pkt         = 可复用的包外壳
pkt->data / pkt->buf = 当前这一包压缩数据的引用
AVBuffer.refcount    = 真正决定底层数据何时释放的引用计数
```

`av_packet_unref(pkt)` 内部会释放 `pkt` 当前持有的数据引用，并把 `pkt` 清回可复用状态；引用计数减到 0 时，底层压缩数据才真正释放。也就是说：

```text
av_packet_alloc/free 管 AVPacket 外壳生命周期
av_packet_ref/unref  管 AVPacket 内部数据引用生命周期
```

### 5.3 `av_packet_free` 时引用计数没归零会泄漏吗

一般不会因为 `av_packet_free(&pkt)` 本身导致泄漏。

`av_packet_free(&pkt)` 语义上等价于：

```text
先 av_packet_unref(pkt)
再释放 AVPacket 外壳
最后把 pkt 指针置空
```

也就是说，它会释放当前这个 `AVPacket` 持有的那一份数据引用。如果底层 `AVBuffer` 的引用计数没有归零，说明还有其他合法持有者在引用同一份压缩数据。

例如：

```cpp
AVPacket *pkt1 = av_packet_alloc();
AVPacket *pkt2 = av_packet_alloc();

av_read_frame(fmtCtx, pkt1);
av_packet_ref(pkt2, pkt1);   // pkt2 和 pkt1 引用同一份底层数据,refcount +1

av_packet_free(&pkt1);       // 只释放 pkt1 这份引用和 pkt1 外壳
                              // 底层数据还不能释放,因为 pkt2 仍然持有引用

av_packet_free(&pkt2);       // 最后一份引用释放后,底层数据才真正释放
```

所以关键判断是：

```text
引用计数没归零,且还有其他对象能继续 unref/free -> 正常,不是泄漏
引用计数没归零,但你已经丢失所有持有者 -> 泄漏
```

真正危险的是这种情况：

```cpp
AVPacket *pkt1 = av_packet_alloc();
AVPacket *pkt2 = av_packet_alloc();

av_read_frame(fmtCtx, pkt1);
av_packet_ref(pkt2, pkt1);

av_packet_free(&pkt1);

// 忘记 av_packet_unref(pkt2) 或 av_packet_free(&pkt2)
// 如果后面也丢失了 pkt2 指针,pkt2 外壳和它引用的底层 buffer 都泄漏
```

一句话：`**free` 当前 packet 只会释放当前 packet 持有的引用；底层 buffer 是否释放由引用计数决定。引用计数没归零不等于泄漏，丢失最后的持有者才是泄漏。**

### 5.4 uninit 和 close 的语义差别

`uninit` 强调"清空内容，对象本身还在"。最典型的就是 `AVChannelLayout`——它经常作为栈变量出现，不是堆上分配出来的独立对象：

```cpp
AVChannelLayout layout;
av_channel_layout_default(&layout, 2);
// ... 使用 ...
av_channel_layout_uninit(&layout);   // layout 这个栈变量还在,只清内部资源
```

`close` 强调"结束打开状态"，对应"已经打开了文件/网络连接/编码流程"的场景。`closep` = `close` + 把指针置空，避免悬空指针和重复关闭。

```cpp
avio_closep(&ofmtCtx->pb);   // 关闭输出 IO,顺手把指针置空
```

### 5.5 常见对象的清理速查表


| 对象                     | 标准清理                                                            |
| ---------------------- | --------------------------------------------------------------- |
| 输入 `AVFormatContext`   | `avformat_close_input(&ifmtCtx)`                                |
| 输出 `AVFormatContext`   | `avio_closep(&ofmtCtx->pb)` 然后 `avformat_free_context(ofmtCtx)` |
| `AVCodecContext`       | `avcodec_free_context(&codecCtx)`                               |
| `AVPacket` 循环复用        | `av_packet_unref(pkt)`                                          |
| `AVPacket` 彻底销毁        | `av_packet_free(&pkt)`                                          |
| `AVFrame` 循环复用         | `av_frame_unref(frame)`                                         |
| `AVFrame` 彻底销毁         | `av_frame_free(&frame)`                                         |
| `SwrContext`           | `swr_free(&swrCtx)`                                             |
| `SwsContext`           | `sws_freeContext(swsCtx)`                                       |
| `AVAudioFifo`          | `av_audio_fifo_free(fifo)`                                      |
| `AVFilterGraph`        | `avfilter_graph_free(&graph)`                                   |
| `AVChannelLayout`（栈变量） | `av_channel_layout_uninit(&layout)`                             |


### 5.6 三类对象的记忆方法

写完整 demo / 转码器时，按这三类来记，几乎不会漏：

1. **循环里反复复用的**：`AVPacket`、`AVFrame`。重点是 `unref`。
2. **初始化建、退出销毁的**：`AVCodecContext`、`AVFormatContext`、`SwrContext`、`SwsContext`。重点是 `free` / `close`。
3. **临时栈变量 / 中间配置**：`AVChannelLayout`。重点是 `uninit`。

## 六、几个高频陷阱

### 6.1 send_packet 之后立刻修改 packet

```cpp
avcodec_send_packet(codecCtx, pkt);
// ❌ 此时强行修改 pkt->data 或释放底层内存,解码器异步处理时会段错误
```

`avcodec_send_packet` 默认是浅拷贝（引用计数）。解码器后续异步使用底层数据，你必须用 `av_packet_unref(pkt)` 安全地减计数。

### 6.2 音频 receive_frame 只读一次

```cpp
// ❌ 一个 AAC packet 可能含多帧,只读一次会丢帧
avcodec_send_packet(codecCtx, pkt);
avcodec_receive_frame(codecCtx, frame);

// ✅ 必须 while 循环到 EAGAIN
avcodec_send_packet(codecCtx, pkt);
while (avcodec_receive_frame(codecCtx, frame) >= 0) {
    // 处理音频帧
}
```

### 6.3 直接用 = 给 AVChannelLayout 赋值

```cpp
// ❌ 语法上不报错,但语义不安全。内部资源可能共享,二次释放就崩
encCtx->ch_layout = outChLayout;

// ✅ 用专用的 copy 函数
av_channel_layout_copy(&encCtx->ch_layout, &outChLayout);
```

## 七、AVPacket 必须 unref，但 AVFrame 有时看似自动清空

经常有人会问：`av_read_frame` 拿到的 `AVPacket` 要手动 `av_packet_unref`，但 `avcodec_receive_frame` 拿到的 `AVFrame` 好像不用？

差别在于**这两个函数对参数的使用方式不同**：

- `av_read_frame(fmtCtx, pkt)`：把数据**填进 pkt**。数据所有权交给调用者，你必须自己 `unref`。
- `avcodec_receive_frame(codecCtx, frame)`：把 frame **当作输出槽位**。FFmpeg 在每次往里面填数据前会**先自动清掉旧的**，所以看起来"自动释放"。

但这不是说 `AVFrame` 永远不用 `unref`——只是 `avcodec_receive_frame` 这个特定 API 的行为。`av_buffersink_get_frame`（滤镜输出）、`av_frame_ref`（自己增引用）这些场景下，frame 同样需要手动管理。

## 八、C++ 工程化要点

### 8.1 C 库 + C++ 项目：必须 extern "C"

FFmpeg 是 C 库，符号是 C 风格。在 `.cpp` 文件里包含必须包一层 `extern "C"`，否则 C++编译器会按 C++ name mangling 找符号，链接时报 `undefined reference`：

```cpp
extern "C" {
    #include <libavformat/avformat.h>
    #include <libavcodec/avcodec.h>
    #include <libavutil/opt.h>
}
```

举个更小的例子。假设有一个 C 库头文件：

```c
// add.h
int add(int a, int b);
```

C 源文件里实现：

```c
// add.c
int add(int a, int b) {
    return a + b;
}
```

如果在 C++ 文件里直接包含：

```cpp
// main.cpp
#include "add.h"

int main() {
    return add(1, 2);
}
```

C++ 编译器可能会把 `add(int, int)` 这个函数名改编成类似 `_Z3addii` 这样的符号名，用来支持函数重载。而 `add.c` 编译出来的 C 符号名仍然只是 `add`。

链接时就会出现这种逻辑：

```text
main.o 想找: _Z3addii
add.o  只有: add
结果: undefined reference
```

所以 C++调 C 库时，要告诉 C++ 编译器：这些函数按 C 规则处理，不要做 C++ name mangling。

```cpp
extern "C" {
    #include "add.h"
}
```

FFmpeg 的头文件也是同理。`.c` 文件里直接 `#include <libavformat/avformat.h>` 就行；`.cpp` 文件里要用 `extern "C"` 包起来，保证链接时找的是 FFmpeg 暴露的 C 符号。

### 8.2 RAII 包装常用对象

C++ 项目里推荐用 `std::unique_ptr` + 自定义 deleter，避免异常路径泄漏：

```cpp
struct AVFrameDeleter {
    void operator()(AVFrame* frame) const {
        av_frame_free(&frame);
    }
};
using AVFramePtr = std::unique_ptr<AVFrame, AVFrameDeleter>;

struct AVPacketDeleter {
    void operator()(AVPacket* pkt) const {
        av_packet_free(&pkt);
    }
};
using AVPacketPtr = std::unique_ptr<AVPacket, AVPacketDeleter>;
```

注意 FFmpeg 的 `*_free` 函数都要求传入二级指针，写 deleter 时取地址即可。

### 8.3 CMake 接入 FFmpeg 的标准写法

Linux / macOS 上最常见的接法是 pkg-config：

```cmake
project(myapp CXX)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)  # clangd/Cursor 跳转必备

find_package(PkgConfig REQUIRED)
pkg_check_modules(FFMPEG REQUIRED
    libavformat
    libavcodec
    libavutil
    libswscale
    libswresample
)

add_executable(myapp main.cpp)
target_include_directories(myapp PRIVATE ${FFMPEG_INCLUDE_DIRS})
target_link_libraries(myapp PRIVATE ${FFMPEG_LIBRARIES})
```

几个常被问到的点：

- `project(myapp CXX)`：`CXX` 是 CMake 对 C++的内部标识。写了它 CMake 才会启用 C++ 编译器检测和 `CMAKE_CXX_STANDARD`。
- `CMAKE_EXPORT_COMPILE_COMMANDS ON`：生成 `compile_commands.json`，clangd / Cursor / VSCode 靠它做补全和跳转。
- `find_package(PkgConfig REQUIRED)`：加载 PkgConfig 模块，找不到 `pkg-config` 工具就立刻失败。这一步不是在找 FFmpeg，而是在为后面的 `pkg_check_modules` 铺路。
- `pkg_check_modules(FFMPEG REQUIRED ...)` 里的 `FFMPEG` 不是库名而是结果变量前缀，执行后生成 `FFMPEG_INCLUDE_DIRS` / `FFMPEG_LIBRARIES` 等。
- 为什么 OpenGL 常用 `find_package(OpenGL REQUIRED)` 而 FFmpeg 用 pkg-config？两者差别不在"哪个高级"，而在"这个库在当前系统上怎么被发现"。OpenGL 在 CMake 里有原生 imported target，FFmpeg 在 Linux/macOS 上由 pkg-config 暴露元信息。

## 十、`avformat_find_stream_info`：打开文件时 FFmpeg 在探测什么

`avformat_find_stream_info` 的作用不是“打开文件”，而是在已经 `avformat_open_input` 之后，继续读取一小段数据，补齐每路流的 codec、分辨率、采样率、时长、帧率、extradata 等信息。

典型内部逻辑可以理解为：

```text
读 packet
  -> 根据 stream_index 归类
  -> 尝试解析 codec 参数 / extradata
  -> 必要时打开临时 decoder 看解码结果
  -> 估算帧率、时长、bitrate
  -> 达到 probe 限制或信息足够后停止
```

面试要点：

| 问题 | 回答抓手 |
|---|---|
| 为什么它可能慢 | 网络流、损坏文件、缺少头信息、VFR 帧率估算都会让它多读数据 |
| 能不能不调 | 能，但你可能拿不到准确 codecpar、duration、fps 或 extradata |
| 怎么调优 | 控制 `probesize`、`analyzeduration`，或者业务侧提前知道格式时减少探测 |
| 和 `avformat_open_input` 的区别 | open 负责打开容器，find_stream_info 负责补齐流信息 |

中高级回答要讲清楚：它是“为了让后续解码/转码更可靠而付出的启动探测成本”，不是无意义的慢。
