## 〇、面试速答模板（口语化，开口就能用）

> 这八个是高级岗的"深水区"题，初中级很少问、高级几乎必问。话术练顺嘴，要点版在 §九。

**Q：弱网丢包了要恢复画面，除了发 IDR 关键帧还有别的办法吗？**

> 有，而且高级做法**恰恰是避免发 IDR**。因为 IDR 是个完整帧、特别大，弱网下你再砸一个大关键帧进去，码率瞬间尖峰、更堵，越救越死。更聪明的两招：一是 **LTR 长期参考帧**——编码器留几个"确认对端收到了"的老帧当锚点，丢包后让新帧去参考那个**确定没丢的老帧**，不用从零来个 IDR；二是 **Intra-Refresh（帧内刷新）**——不发整张关键帧，而是每帧刷新一个条带，几帧之内滚动刷完整画面，把一个大尖峰摊成几个小包。这俩 NVENC、MediaCodec、VideoToolbox 都支持，是 RTC 弱网的核心手段。

**Q：多人视频会议，一个人要同时满足高清看的人和弱网看的人，编码侧怎么做？**

> 两条路：**Simulcast（联播）**和 **Temporal SVC（时域分层）**。Simulcast 是同一路画面**编码出几条独立码流**（比如 720p/360p/180p），SFU 服务器按每个接收者的网络挑一条转给他。SVC 更精巧，是**一条码流内部分层**——时域分层最常用也最好做，编码时让帧分成 T0/T1/T2 几层，T0 自己能解、丢掉 T2 只是帧率降一半但画面不崩。SFU 想给弱网降帧率，**直接丢高层的包就行，不用编码器重编**。WebRTC 移动端硬件编码器就支持产时域分层。

**Q：你说硬编画质"够用",凭什么？怎么量化证明？**

> 不能靠肉眼说"看着差不多",要用**客观指标**。最常用的是 **VMAF**（Netflix 搞的、最贴近人眼主观感受，0-100 分），辅以 PSNR（纯信号误差）和 SSIM（结构相似度）。比较两个编码器优劣用 **BD-rate**——它算的是"达到同样画质，A 比 B 省了百分之多少码率"，是论文和选型的硬通货。实操就是固定一批测试片源，跑不同 preset/码率，画 **码率-VMAF 曲线（RD 曲线）**对比。高级岗想听的是你**有这套方法论**，而不是拍脑袋。

**Q：给你一台带卡的服务器，怎么估它能跑多少路转码？**

> 不能看显卡跑分，要**实测吞吐 + 看约束木桶**。先明确单路规格（分辨率/帧率/编码），然后逐步加并发路数，盯三个瓶颈：① **编解码引擎吞吐**（NVENC/NVDEC 的 fps 上限，nvidia-smi 看 ENC/DEC 利用率）；② **并发 session 数硬限制**（消费卡驱动锁 3-5 路，见 [13 §4.2](./13-NVIDIA硬件编解码.md)）；③ **显存**（每路解码器+帧池吃显存，路数多了 OOM）。最先撞到的那个就是上限。规划时留 20-30% 余量给突发。

**Q：播放 Netflix 这种付费内容，硬件解码有什么特殊的？**

> 走的是**安全解码路径（secure decode）**。受 DRM 保护的内容（Widevine L1 / FairPlay），解码出来的画面**全程待在受保护内存里、CPU 碰不到**——你 readback 会拿到黑屏或直接被拒。整条链路解码→合成→上屏都在 TEE（可信执行环境，比如 ARM TrustZone）或硬件保护的 secure buffer 里完成，截屏也是黑的。所以"受保护内容不能 `av_hwframe_transfer_data` 拉回 CPU、不能截图"是设计使然，不是 bug。Widevine 分 L1/L2/L3，L1 是全硬件 TEE、画质最高，L3 是软件、只能 SD。

## 一、LTR：长期参考帧（弱网恢复的第一招）

### 1.1 解决什么问题

普通编码里，P 帧只参考**前一帧**（或最近几帧）。一旦某帧丢包，后面所有参考它的帧全跟着烂——**错误扩散（error propagation）**，画面持续花屏，直到来一个 IDR 才止血。

但 IDR 很贵：它是完整帧，体积是 P 帧的几倍到几十倍。弱网下本来就堵，你再砸个大 IDR 进去，**码率瞬间尖峰**，更容易丢、更卡——越救越死。

**LTR（Long-Term Reference，长期参考帧）的思路**：编码器额外保留几个"标记为长期"的参考帧，不被普通滑动窗口挤掉。配合一条反馈信道，做到：

```
正常: P 帧参考前一帧 ──┐
                      ↓ 某帧丢包,对端检测到并反馈"我最后收全的是第 100 帧"
恢复: 新的 P 帧 ──参考──▶ 第 100 帧(已确认收到的 LTR)
      跳过中间烂掉的帧, 不发 IDR, 体积小得多, 码率不尖峰
```

一句话：**LTR 让"丢包恢复"从"砸一个大 IDR"变成"参考一个确定没丢的老帧",省码率、不尖峰。**

### 1.2 三平台 API 对照

| 平台 | 怎么开 / 怎么用 |
|---|---|
| **NVENC** | Video Codec SDK 层：`NV_ENC_INITIALIZE_PARAMS` 里开 LTR、设 `maxNumRefFramesInDPB`/LTR 帧数，编码时用 picture params 标记某帧为 LTR、后续帧指定参考它。FFmpeg 暴露有限，深度用要走原生 SDK |
| **Android MediaCodec** | 能力查 `FEATURE_*`；编码 `MediaFormat` 设 LTR 帧数，运行时 `setParameters` 用 vendor/标准 key 标记与使用 LTR（厂商扩展多，需按设备查能力） |
| **iOS VideoToolbox** | 帧级 `kVTEncodeFrameOptionKey_*` 配合 session 属性；libwebrtc iOS 封装里有 LTR 路径 |
| **WebRTC** | 上层 RPSI / 反馈机制驱动编码器选 LTR——RTC 弱网恢复的标准武器（[08 §10.6](./08-网络协议与流媒体.md) GCC 旁路的丢包恢复） |

### 1.3 面试要点

- **核心价值**：丢包恢复不发 IDR → 不产生码率尖峰 → 弱网更稳。
- **依赖反馈信道**：要对端告诉你"哪帧确认收到了",编码器才能安全地参考它（没反馈就退化成盲猜）。
- **和 IDR 的取舍**：完全恢复（画面彻底重置）还得靠 IDR；LTR 是"已知有个干净锚点时"的优选。

## 二、Intra-Refresh / GDR：帧内刷新（削平码率毛刺）

### 2.1 解决什么问题

低延迟直播 / 云游戏里，周期性 IDR 会造成**码率毛刺**：平时码率平稳，每到 GOP 边界突然蹦一个大 IDR，网络层看到的是规律的尖峰——抖动大、易丢包、延迟不稳。

**Intra-Refresh（帧内刷新，也叫 GDR — Gradual Decoder Refresh，渐进解码刷新）**：干脆**不发整张 IDR**，而是把"刷新"摊到连续若干帧里——每帧只用帧内编码（intra）刷新画面的一个**条带（一列或一行宏块）**，条带逐帧滚动，N 帧之后整幅画面都被刷新过一遍，等效于完成了一次"软关键帧"。

```
帧内刷新条带逐帧滚动(竖条从左扫到右):
 帧1   帧2   帧3   帧4   帧5
┌─┬──┐ ┌──┬─┐ 略  ┌────┬┐ 整幅刷完
│▓│  │ │  │▓│ ... │   │▓│  = 一次"软 IDR"
└─┴──┘ └──┴─┘     └────┴┘
 ▓ = 这一帧用 intra 刷新的条带
```

一句话：**把一个大 IDR 尖峰,摊成连续几帧的小鼓包,码率平稳、延迟稳定——代价是压缩率略降、随机接入点变"模糊"。**

### 2.2 和 IDR / LTR 的关系

| 手段 | 恢复方式 | 码率特征 | 典型场景 |
|---|---|---|---|
| **IDR** | 一帧完整重置 | 周期性大尖峰 | 点播、需要精确 seek 点 |
| **Intra-Refresh / GDR** | 几帧滚动刷新 | 平稳、无尖峰 | 低延迟直播、云游戏、RTC |
| **LTR** | 参考确认收到的老帧 | 恢复帧很小 | 弱网丢包恢复（需反馈） |

实战里 **Intra-Refresh + LTR 常一起用**：平时靠 Intra-Refresh 抗错误扩散、保持码率平稳，丢包了再用 LTR 精准恢复。

### 2.3 三平台 API 对照

| 平台 | 开关 |
|---|---|
| **NVENC** | `-intra-refresh 1`（FFmpeg 暴露了）；SDK 里 `enableIntraRefresh` + `intraRefreshPeriod` / `intraRefreshCnt` |
| **Android MediaCodec** | `MediaFormat.KEY_INTRA_REFRESH_PERIOD`（以"多少帧刷完一轮"为单位），设备支持度需查 |
| **iOS VideoToolbox** | 无直接公开的 GDR 属性，主要靠短 GOP + RealTime；底层 Apple 编码器在 RealTime 下自有平滑策略 |
| **WebRTC** | 部分实现用它替代周期 IDR 来平滑码率 |

### 2.4 面试要点

- **本质**：用空间（条带滚动）换时间（无尖峰），把关键帧的码率冲击摊平。
- **代价**：压缩率略降；解码端"随机接入"不再是单帧（要等刷完一轮才保证画面全新），所以**点播/精确 seek 不用它，低延迟实时才用**。
- **关联 [06](./06-编码参数与码控.md)**：和 `zerolatency`、短 GOP 是一套低延迟组合拳。

## 三、时域分层（Temporal SVC）与 Simulcast：一对多分发的编码地基

### 3.1 问题：一个主播，观众网络千差万别

多人会议 / 大型直播里，同一路画面要同时喂给：千兆网的人（要 1080p60）、4G 的人（要 360p）、地铁里弱网的人（能动就行）。编码侧两种解法——**Simulcast** 和 **SVC**。

### 3.2 Simulcast（联播）：编几条独立流

同一路采集，**编码器同时编出 2-3 条完全独立的码流**（如 720p / 360p / 180p），都推给 SFU 服务器（[08 §10.7](./08-网络协议与流媒体.md)）。SFU 按每个接收者的实时带宽，**选一条转给他**。

```
采集 ──┬─ 编码720p ─┐
       ├─ 编码360p ─┼─▶ SFU ──按订阅者网络挑一条──▶ 各接收者
       └─ 编码180p ─┘
```

- 优点：实现简单、兼容性好、每条流独立解码。
- 缺点：**编码算力 ×N、上行带宽 ×N**（要同时发好几条）。

### 3.3 SVC（可伸缩编码）：一条流内部分层

一条码流内部分成多层，**丢掉高层不影响低层解码**。最常用、最好落地的是**时域分层（Temporal SVC）**：

```
时域分层 T0/T1/T2 (帧率逐层翻倍):
T0: ●───────●───────●        只解 T0 = 7.5fps  (基本层,自己能解)
T1: ●───●───●───●───●        + T1   = 15fps
T2: ●─●─●─●─●─●─●─●─●        + T2   = 30fps   (丢了只降帧率,画面不崩)
```

- **关键性质**：高层帧只被同层或更高层参考，**绝不被低层参考**。所以 SFU 想降帧率，**直接丢 T2 的 RTP 包就行**——不通知编码器、不重编，低层照常解。
- 还有**空域分层（分辨率）**和**质量分层（SNR）**，但硬件支持差、复杂，工程上时域分层用得最多。
- AV1 / VP9 / H.264（部分）支持；**移动端硬件编码器（MediaCodec / VideoToolbox）能产时域分层**，这是 WebRTC 用它的前提。

### 3.4 三平台 / 框架对照

| 平台 | 时域分层支持 |
|---|---|
| **NVENC** | 支持 temporal layers（`-temporal-aq` 是另一回事，别混；分层走 SDK 的 temporal layer 配置） |
| **Android MediaCodec** | `KEY_TEMPORAL_LAYERING`（schema 如 `android.generic.2`，表示 2 层时域）；WebRTC Android 用它 |
| **iOS VideoToolbox** | `kVTCompressionPropertyKey_BaseLayerFrameRate` 等，配置基本层帧率实现 2 层时域分层；WebRTC iOS 用它 |
| **WebRTC** | Simulcast 和 SVC 都内建，SDP 协商，SFU 按层/流转发 |

### 3.5 Simulcast vs SVC 怎么选（面试高频）

| 维度 | Simulcast | 时域 SVC |
|---|---|---|
| 编码开销 | 高（编 N 条） | 低（编 1 条） |
| 上行带宽 | 高（发 N 条） | 低（发 1 条，含所有层） |
| SFU 适配 | 选流 | 丢高层包 |
| 分辨率档位 | 任意（独立编） | 时域只调帧率，要调分辨率得空域 SVC（硬件支持差） |
| 落地难度 | 低、最成熟 | 中（时域好做，空域难） |

一句话：**要不同分辨率档、求稳，用 Simulcast；要省上行带宽、只需帧率自适应，用时域 SVC。** 实际大型系统常两者结合。

## 四、客观质量评估：VMAF / PSNR / SSIM / BD-rate

### 4.1 为什么要它

[07 §7](./07-硬件编解码.md) 说"同码率硬编画质不如软编"——但**你怎么证明、怎么量化"差多少"**？高级岗不接受"肉眼看着差不多",要客观指标。这也是选编码器、调码控、写技术结论的方法论基础。

### 4.2 四个指标

| 指标 | 全称 / 含义 | 特点 | 用途 |
|---|---|---|---|
| **PSNR** | 峰值信噪比（dB） | 纯逐像素误差，算得快，但**和人眼主观感受相关性一般** | 快速回归、传统论文基线 |
| **SSIM** | 结构相似度（0-1） | 考虑结构/亮度/对比，比 PSNR 更贴人眼 | 比 PSNR 进一步 |
| **VMAF** | Netflix 的视频多维评估融合（0-100） | 机器学习融合多个特征，**最贴近主观 MOS**，业界主流 | 编码器选型、质量监控 |
| **BD-rate** | Bjøntegaard Delta rate（%） | "达到同等质量，A 比 B 省/费多少码率" | **编码器/preset 横向对比的硬通货** |

### 4.3 怎么测（实操方法论）

```
1. 选代表性测试集(不同复杂度: 静止/运动/纹理/动画)
2. 同一片源, 用待比的两个编码器/preset, 跑多个码率点
3. 每个输出对原片算 VMAF/PSNR
4. 画 RD 曲线(横轴码率, 纵轴 VMAF), 曲线越靠左上越好
5. 两条曲线之间用 BD-rate 量化差距
```

```bash
# FFmpeg 自带 libvmaf 滤镜 (需编译启用)
ffmpeg -i distorted.mp4 -i reference.mp4 \
    -lavfi "[0:v][1:v]libvmaf=log_path=vmaf.json" -f null -
```

### 4.4 面试要点

- **VMAF 是当前事实标准**，但记住它是**为流媒体场景训练的**，极端内容（强 HDR、屏幕内容、动画）可能不准——别迷信单一指标。
- **BD-rate 是比较两个编码器的正确姿势**，不能只比单个码率点（容易被"挑点"误导）。
- 主观测试（MOS，真人打分）才是金标准，VMAF 是它的工程近似。
- **硬编调参的闭环**：改 preset/AQ/码率 → 测 VMAF → 看 RD 曲线 → 找"画质够用且码率最省"的工作点，而不是拍脑袋。

## 五、端到端延迟拆解（glass-to-glass）

### 5.1 什么是 glass-to-glass

实时系统的延迟指标是 **glass-to-glass（玻璃到玻璃）**：从**镜头玻璃**捕获到画面，到对端**屏幕玻璃**显示出来的总时间。面试系统设计题最爱问"延迟从哪来、怎么降"。要能把它拆成环节、each 给量级。

### 5.2 延迟预算拆解

```
采集 → 编码 → 打包发送 → 网络 → 接收抖动缓冲 → 解码 → 渲染上屏
```

| 环节 | 延迟来源 | 量级（实时优化后） | 怎么降 |
|---|---|---|---|
| **采集** | 相机曝光 + ISP 处理 + 帧间隔 | 一帧时间（30fps≈33ms） | 提帧率、相机低延迟模式 |
| **编码** | 编码器流水线 + B 帧重排 + look-ahead | 关 B 帧后 ~1 帧；不关可达数帧 | 关 B 帧、RealTime/ull、关 look-ahead（[06](./06-编码参数与码控.md)、[15 §5](./15-iOS硬件编解码.md)） |
| **发送/打包** | RTP 分包、pacing | 几 ms | pacer 别攒太久 |
| **网络** | RTT + 排队 | 几 ms ~ 上百 ms | 选路、QUIC/UDP |
| **抖动缓冲** | Jitter Buffer 等包重排 | 动态，几十 ms（**延迟与抗抖动的核心权衡**） | 自适应 jitter buffer（[04](./04-音频PCM-采样-重采样.md) §同步、[08](./08-网络协议与流媒体.md)） |
| **解码** | 解码器流水线 | ~1 帧 | 低延迟解码模式 |
| **渲染** | 合成 + 显示器 VSync | 一个 VSync（60Hz≈16ms） | 零拷贝直通、别多缓冲 |

### 5.3 关键认知

- **编码侧最大的延迟杀手是 B 帧和 look-ahead**——它们要"等未来帧",和低延迟天然冲突。这就是为什么实时编码全都关 B 帧（[15 §5](./15-iOS硬件编解码.md) `AllowFrameReordering=false`、[14 §9](./14-Android硬件编解码.md) `KEY_LOW_LATENCY`、NVENC `-tune ull`）。
- **抖动缓冲是"延迟 vs 流畅"的旋钮**：缓冲越大越抗抖动但延迟越高，自适应算法在两者间动态找平衡。
- **零拷贝不只是省 CPU，也降延迟**：每次 readback 的 GPU stall（[10 §4.5.3](./10-移动端硬件编解码.md)）都加进 glass-to-glass。
- 量级感：硬件全链路优化后，**WebRTC 实时通话能做到 ~100-200ms glass-to-glass**；云游戏追求 <50ms 编码+网络。

## 六、吞吐与容量规划（一台机器跑多少路）

### 6.1 为什么不能看跑分

云转码 / 直播服务器选型，问的是"**这台机器能同时转多少路**"。不能看显卡理论性能，因为真实上限是被**最先撞到的那个约束**卡死的——是个木桶问题。

### 6.2 三个瓶颈（按出现频率）

| 瓶颈 | 怎么看 | 撞到的表现 |
|---|---|---|
| **并发 session 数硬限制** | 消费级 GeForce 驱动锁 NVENC 并发会话（3-5 路），数据中心卡放开（[13 §4.2](./13-NVIDIA硬件编解码.md)） | 第 N+1 路直接创建失败 |
| **编解码引擎吞吐** | NVENC/NVDEC 的 fps 上限；`nvidia-smi dmon` 看 ENC/DEC 利用率（**不是 GPU-Util 那列**） | 利用率打满，帧率掉、积压 |
| **显存** | 每路解码器 + 帧池 + 滤镜缓冲都吃显存 | 路数加上去 OOM / 分配失败 |

> 移动端没有"并发 session 上限"这个商业限制，但有**硬件解码器实例数有限**（[14 §十二](./14-Android硬件编解码.md)、[10 §七](./10-移动端硬件编解码.md)）——画中画/多路播放撞到就 codec 创建失败。

### 6.3 容量规划方法

```
1. 定义单路规格 (1080p30 H.264 转 720p 这种)
2. 从 1 路开始, 逐步加并发, 每档测: 实际 fps 是否达标 + ENC/DEC 利用率 + 显存占用
3. 找到"还能稳定达标"的最大路数 = 单卡容量
4. 留 20-30% 余量 (突发、关键帧尖峰、抖动)
5. 多卡 / 多机线性外推, 注意 PCIe 和 CPU 侧(解封装/封装/调度) 别成新瓶颈
```

### 6.4 面试要点

- **先问约束再算数**：消费卡 session 限制常是第一个撞到的，别一上来算 fps。
- **看对利用率列**：`nvidia-smi` 默认那个 GPU-Util 是 CUDA 占用，编解码要看 ENC/DEC 专列（`nvidia-smi dmon -s u`）。
- **CPU 不是局外人**：解封装、封装、AVPacket 调度、上下行 IO 都在 CPU，高密度转码时它可能先于 GPU 打满。

## 七、安全解码路径（DRM / Widevine L1 / FairPlay）

### 7.1 受保护内容的硬约束

播放 Netflix、Disney+、爱奇艺会员这类付费内容，走的是**安全解码（secure decode）**：受 DRM 保护的码流，解码后的画面**全程待在受保护内存（secure buffer）里，普通 CPU / 应用层碰不到**。

- 你 `av_hwframe_transfer_data` / `glReadPixels` / 截屏 → 拿到**黑屏**或直接被拒。
- 整条链路解码 → 合成 → 上屏，都在 **TEE（可信执行环境，如 ARM TrustZone）** 或硬件保护的 secure 路径里完成。
- 这是**设计使然，不是 bug**——防止内容被录制/盗取。

### 7.2 Widevine 三个安全级别（必背）

| 级别 | 解码与密钥处理 | 最高画质 | 典型设备 |
|---|---|---|---|
| **L1** | 解码 + 密钥全在 TEE 硬件里 | HD / 4K / HDR | 正规安卓旗舰、Apple 设备 |
| **L2** | 密钥在 TEE，解码在 TEE 外 | 受限 | 少见 |
| **L3** | 全软件，无硬件 TEE | 通常仅 SD（≤480p/540p） | 模拟器、改机、部分低端/无 TEE 设备 |

> 经典现象：**root 过的手机 / 模拟器掉到 L3，Netflix 只能放标清**——因为厂商对非 L1 设备限制高清。Apple 生态用 **FairPlay**，思路一致（Secure Enclave + 硬件路径）。

### 7.3 三平台机制

| 平台 | 安全解码机制 |
|---|---|
| **Android** | `MediaDrm` + `MediaCrypto`，`MediaCodec.configure` 传 `MediaCrypto`；输出走 **secure Surface**（`createInputSurface` 的 secure 变体），ByteBuffer 路径直接禁用 |
| **iOS** | FairPlay Streaming + AVContentKeySession，解码在 Secure Enclave / 硬件路径，VT 不直接暴露明文 |
| **桌面/NVIDIA** | Windows 上 PlayReady SL3000 / Widevine L1 走 GPU 的受保护视频路径（PVP）、受保护内存；解码输出不可被普通进程读取 |

### 7.4 面试要点

- **"为什么受保护内容截屏是黑的 / 不能 readback？"** → secure decode 路径，画面在 TEE/secure buffer，CPU 无访问权，零拷贝渲染也走 secure 通路。
- **"L1 和 L3 区别？"** → L1 全硬件 TEE、可放 HD/4K；L3 全软件、通常限 SD。root / 模拟器掉 L3 是高频现象。
- **关联零拷贝**：安全解码是"被迫且强制"的零拷贝——不是为性能，是为安全，连你想 readback 都不行。

## 八、错误恢复与健壮性（生产环境的活儿）

写 demo 跑通是一回事，**线上不崩**是另一回事。高级岗会问你"出了问题怎么办"。

### 8.1 常见故障与对策

| 故障 | 根因 | 对策 |
|---|---|---|
| **解码器收到坏帧 / 丢了参考帧** | 网络丢包、参考帧没到 | 检测错误 → 向对端请求关键帧（PLI/FIR）或用 LTR 恢复（§一）；别让花屏一直扩散 |
| **动态分辨率切换** | 弱网自适应降分辨率、横竖屏切 | 大多硬件 codec 要 **reconfigure / flush 重建**；少数支持动态分辨率（查能力）。WebRTC 降档常触发 |
| **App 切后台 / 来电** | iOS 丢 VT session、Android 丢 codec（[10 §七](./10-移动端硬件编解码.md)、[15 §十一](./15-iOS硬件编解码.md)） | 监听生命周期，回前台**重建会话 + 重发 SPS/PPS + 强制关键帧** |
| **硬件不支持该格式/profile** | HEVC/AV1/HDR 设备参差 | 能力查询（`MediaCodecList` / VT 查询）→ **软解兜底**，别假定支持 |
| **buffer pool 耗尽** | 持有 buffer 不释放（[10 §4.5.9](./10-移动端硬件编解码.md)） | 用完立刻 release / 归还，别跨多帧攒 |
| **解码器 hang / 超时** | 驱动 bug、坏码流 | 设超时 → reset / 重建 codec；记录设备型号（碎片化） |

### 8.2 健壮性设计原则

- **能力优先查询，永远留软解兜底**：硬件路径不可用时优雅降级，而不是崩。
- **会话可重建**：把"创建会话 + 配 CSD + 首个关键帧"封装成可重入的初始化，故障时整体重来。
- **错误不扩散**：解码端检测到参考链断了，主动请求恢复（关键帧 / LTR），而不是把花屏一路放下去。
- **跨设备测试**：Android 尤其，不同 SoC 行为差异大（[14 §十二](./14-Android硬件编解码.md)），坑大多在真机才暴露。

## 九、面试高频问答（要点速记版）

> §〇 是口语化展开，这里是临场背要点版，两套配合。

- **LTR 是什么、解决什么？** 长期参考帧；丢包后参考"已确认收到的老帧"恢复，不发 IDR、不产生码率尖峰。依赖反馈信道。
- **Intra-Refresh / GDR？** 不发整张 IDR，每帧 intra 刷一个条带、滚动刷完一轮 = 软关键帧；码率平稳无尖峰，代价是压缩率略降 + 不适合精确 seek。低延迟实时场景用。
- **Simulcast vs SVC？** Simulcast 编 N 条独立流、SFU 选流（编码/带宽 ×N）；时域 SVC 编 1 条分层流、SFU 丢高层包降帧率（省带宽，高层不被低层参考）。要分辨率档用 Simulcast，要省上行用时域 SVC。
- **VMAF / PSNR / SSIM / BD-rate？** VMAF 最贴主观、流媒体事实标准；PSNR 纯误差、SSIM 看结构；BD-rate 量化"同质量省多少码率"，是横向比编码器的正确姿势。画 RD 曲线。
- **glass-to-glass 延迟拆解？** 采集→编码→打包→网络→抖动缓冲→解码→渲染。编码侧最大杀手是 B 帧 + look-ahead；抖动缓冲是延迟 vs 流畅旋钮；零拷贝也降延迟。
- **一台机器跑多少路？** 木桶：并发 session 硬限制 / 编解码引擎 fps / 显存，最先撞到的为准。`nvidia-smi` 看 ENC/DEC 专列不是 GPU-Util。留 20-30% 余量。
- **安全解码 / Widevine L1 vs L3？** 受保护内容解码后在 TEE/secure buffer，CPU 不可读、截屏黑屏。L1 全硬件 TEE 可放 HD/4K，L3 全软件限 SD（root/模拟器常掉 L3）。
- **生产环境怎么保证不崩？** 能力查询 + 软解兜底；会话可重建（切后台/来电重发 SPS/PPS+关键帧）；错误不扩散（请求关键帧/LTR）；跨真机测。
