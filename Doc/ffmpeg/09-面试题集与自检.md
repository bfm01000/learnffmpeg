# 09 - 面试题集与自检

> 这份文档不只是"题目列表"。每道题都给你四样东西：**问题 / 答题要点 / 加分项 / 翻车回答**。
> 你能不能去面试音视频岗位，不是看你做完多少题，而是看你**能否流畅口述、能否抛出加分项、能否避开翻车回答**。
> 读法：从必答（⭐）开始，每题先盖住答案口述一遍，再对照。能流畅讲对算"通过"。

---

## 0. 怎么用这份文档

### 0.1 分级说明

| 档位 | 含义 | 你应该的状态 |
|---|---|---|
| ⭐ **必答** | 面试官的"筛人题"。答错或卡壳 = 直接不通过 | **100% 必须流畅口述** |
| ⭐⭐ **进阶** | 区分"懂"和"略懂"。讲清楚 = 加分 | **80% 能讲清楚** |
| ⭐⭐⭐ **高级** | 区分"懂"和"专家"。讲清楚 = 拿高薪 | **能讲一半就很强** |

### 0.2 自评打分法

每道题口述完，给自己打一个分：

- **A**：能流畅口述、能抛 1-2 个加分项 → 真懂
- **B**：能答上大方向，但讲不清细节 → 半懂
- **C**：完全答不上来 → 不懂

**面试通过的最低标准**：所有 ⭐ 题 A、⭐⭐ 题 ≥ 80% A 或 B、⭐⭐⭐ 题不强求。

### 0.3 通用答题模板（强烈推荐先内化）

任何技术题，按这个四段式回答几乎不会翻车：

```
【1. 先给结论 / 定义】       (10 秒)
【2. 类比 / 直觉解释】       (20 秒)
【3. 技术现实 / 实现细节】   (30 秒)
【4. 工程影响 / 踩坑经验】   (15 秒)
```

面试官最讨厌的回答是上来就堆 API 名字。**先给结论，再展开细节**——这一条做到位就甩开 70% 的候选人。

## 1. 数据结构与生命周期（对应 [01](./01-数据结构与生命周期.md)）

### Q1.1 ⭐ AVPacket 和 AVFrame 的区别是什么？

**答题要点**：

- 一句话：`AVPacket` 装**压缩后**的字节（H.264 NALU、AAC 帧），`AVFrame` 装**解压后**的原始数据（YUV / PCM）。
- 流水线位置：`AVPacket → 解码器 → AVFrame`，进出解码器是分水岭。
- 体积差：一个压缩 packet 几 KB，一帧 1080P RGB 约 6 MB。

**加分项**：

- 主动提"视频包通常一包一帧、音频包可能一包多帧"——这是音频解码必须 while 循环的原因。
- 提引用计数：两者都用 `AVBufferRef` 管理底层数据，零拷贝设计。

**翻车回答**：

- "AVPacket 是音频，AVFrame 是视频"——完全错。两者都既能装音频也能装视频。
- 只提字段不提流水线位置——说明不理解 ffmpeg 的数据流。

---

### Q1.2 ⭐ `av_packet_unref` 和 `av_packet_free` 有什么区别？什么时候用哪个？

**答题要点**：

- `unref`：释放底层数据引用，但 `AVPacket` 这个**壳**保留，可继续装下一个 packet。
- `free`：连壳带数据一起销毁，指针置空。
- 循环里反复处理一万帧，**只用 unref**，循环外才 free。

**加分项**：

- 抛出真实代码对比："循环里每帧 alloc/free 性能极差，正确写法是循环外 alloc 一次，循环内 unref 复用"。
- 提引用计数底层是 `AVBufferRef` 指向的 `AVBuffer`，refcount 归零才真正释放。

**翻车回答**：

- "都是释放内存，差不多"——这种答法直接被淘汰。
- 说不出"壳和数据分开管理"的设计。

---

### Q1.3 ⭐⭐ `AVCodec` 和 `AVCodecContext` 为什么要分开？

**答题要点**：

- `AVCodec` = 算法本体（一堆函数指针的结构体）、**无状态**、全局只需一个实例。
- `AVCodecContext` = 工作环境、**有状态**、保存当前流的宽高、帧率、解码进度。
- 类比：`AVCodec` 是"类的方法"，`AVCodecContext` 是"对象的属性"。

**加分项**：

- 初始化为什么分三步（`alloc_context3` → `parameters_to_context` → `open2`）：留给开发者**自定义参数的机会**。
- 提"`open2` 之前可以强制替换 codec"——典型场景是把默认 H.264 软解换成 `h264_cuvid` 硬解。

**翻车回答**：

- "为什么这样设计我不知道"——直接暴露没读过 ffmpeg 设计。
- 把 `AVCodecContext` 当成全局唯一——这样多路解码就崩了。

---

### Q1.4 ⭐⭐ ffmpeg 的 `unref / uninit / free / close / closep` 这堆 API 怎么区分？

**答题要点**：

| 动词 | 操作什么 |
|---|---|
| `unref` | 释放底层数据引用，壳保留可复用 |
| `free` | 整个对象销毁 |
| `uninit` | 清内部状态，**栈变量本身还在**（典型如 `AVChannelLayout`） |
| `close` | 关闭已打开的资源（文件 / IO） |
| `closep` | close + 把指针置空，防悬空 |

**加分项**：

- 主动提"这套命名是 ffmpeg 通过 API 名字传达资源所有权和释放责任"——体现你看过整套设计。
- 给一个 `AVChannelLayout` 的具体例子说明为什么 `uninit` 而非 `free`。

**翻车回答**：

- 都答成"释放内存"——五个动词差别完全混淆。

---

### Q1.5 ⭐⭐⭐ `av_packet_unref` 在内部具体做了什么？引用计数怎么落到底层？

**答题要点**：

- `AVPacket` 自己不直接管引用计数，而是通过 `AVBufferRef *buf` 指向一个 `AVBuffer`。
- `AVBuffer` 里有 `data + size + refcount`，**真正的引用计数在这里**。
- `av_packet_unref` 内部释放 `pkt->buf` 的引用，refcount 减到 0 时才真正释放底层数据；然后把 `pkt` 字段清零，回到可复用状态。

**加分项**：

- 画出三层结构（`AVPacket → AVBufferRef → AVBuffer`）。
- 提"这是为什么 `av_packet_ref(dst, src)` 能浅拷贝——`AVBufferRef` 加引用而不真正复制数据"。

**翻车回答**：

- 答不出 `AVBuffer` 层——说明只是"用过 API"，没读过底层。

## 2. 像素格式与内存布局（对应 [02](./02-像素格式与内存布局.md)）

### Q2.1 ⭐ 为什么视频编解码不用 RGB 而用 YUV？

**答题要点**：

- 主要是**数据压缩**。
- 人眼对亮度（Y）敏感，对色度（U/V）不敏感。
- 利用这个生理学事实做**色度子采样**（4:2:0：4 个 Y 共享 1 组 UV）。
- 直接把数据量从 RGB 的每像素 3 字节砍到每像素 1.5 字节——**减半**。

**加分项**：

- 提历史包袱：YUV 最早是为兼容黑白电视（只传 Y）设计的，所以现代视频编码（MPEG-2 / H.264 / HEVC / AV1）底层都基于 YUV。
- 算一笔账：1080p 30fps 不压缩 = 178 MB/s，一分钟 10GB。

**翻车回答**：

- "因为 YUV 是行业标准"——废话，问的是为什么是行业标准。

---

### Q2.2 ⭐ I420 / NV12 / NV21 三者的区别？

**答题要点**：

| 格式 | 排布 | 谁用 |
|---|---|---|
| I420 (= YUV420P) | Planar，Y / U / V 三个独立平面 | x264 软编、ffmpeg 默认 |
| NV12 | Semi-Planar，Y 一平面 + UV 交错 | iOS VideoToolbox、大多数硬编 |
| NV21 | Semi-Planar，Y 一平面 + **VU** 交错（反） | **Android Camera1 默认** |

**加分项**：

- 解释为什么 NVIDIA 发明 NV12：**硬件取色总是同时需要 U 和 V，Semi-Planar 让 UV 落在同一条 Cache Line**，命中率大幅提升。
- 抛 Android 红蓝反色 bug：NV21 喂给配置成 NV12 的 MediaCodec → 阿凡达脸。

**翻车回答**：

- "都差不多"——立刻扣分。
- 答不出 NV21 默认在哪——说明没做过 Android 开发。

---

### Q2.3 ⭐ `linesize` 一定等于 `width × 字节数` 吗？

**答题要点**：

- **不一定**。FFmpeg 为了 SIMD（AVX/SSE/NEON）效率，按 16 或 32 字节对齐分配内存。
- 行末常有 padding。例：width=100 字节，linesize 可能被分配成 128 字节。
- 凡是按行操作图像，**永远按 `linesize` 偏移**，不要按 `width` 硬算。

**加分项**：

- 给翻车现场代码：`memcpy(dst, frame->data[0], width × height)` 会因为 padding 导致画面倾斜或花屏，**主动说出正确写法是逐行 memcpy 按 linesize 偏移**。
- 提 YUV420P 三个平面 linesize 不相等（Y 是 width，UV 各是 width/2）。

**翻车回答**：

- "应该相等吧"——你大概率没真写过 sws_scale 的代码。

---

### Q2.4 ⭐⭐ BT.601 和 BT.709 的区别是什么？

**答题要点**：

- 它们是 **RGB ↔ YUV 转换矩阵**的两套标准。BT.601 是标清（480/576p），BT.709 是高清（720/1080p）。
- 公式不同：BT.709 把绿色的权重从 0.587 提到了 0.7152。
- 用错矩阵会导致**色偏**：典型现象是用 601 公式解 709 的视频 → 红色偏暗、绿色偏亮、画面灰蒙蒙。

**加分项**：

- 提"像素格式 vs 色彩空间"的差别：**像素格式是杯子形状，色彩空间是杯子里装的饮料**。同一块 NV12 内存里既可能是 601 也可能是 709 编码的数值。
- 还有 BT.2020（4K / HDR）。

**翻车回答**：

- "都是 YUV 格式"——把色彩空间和像素格式混为一谈。

---

### Q2.5 ⭐⭐ Full Range 和 Limited Range（0-255 vs 16-235）是怎么回事？

**答题要点**：

- **Full Range**：Y/U/V 全用 0-255。用于电脑显示器、JPEG。
- **Limited Range**：Y 用 16-235，U/V 用 16-240。用于电视、大多数视频文件。
- 16-235 来自模拟电视时代——给信号过冲 / 欠冲留缓冲（0-15 是 Toeroom，236-255 是 Headroom）。

**加分项**：

- 主动抛两个经典 bug：
  - Limited 视频按 Full 渲染 → **画面发灰**（最黑只有 16）。
  - Full 视频按 Limited 渲染 → **暗部死黑、亮部过曝**。
- 提解决方法：读 `AVColorRange` 字段动态选矩阵。

**翻车回答**：

- "没听说过"——直接 -10 分。

---

### Q2.6 ⭐⭐⭐ 为什么 YUV 4:2:0 几乎不用 Packed 格式？

**答题要点**：

- 三个原因：

  1. **数量不对等**：4 个 Y 配 1 组 UV，强行交错（`Y1 U1 Y2 V1 Y3 U2 Y4 V2`）寻址极其复杂。
  2. **缓存污染**：视频编码的运动搜索几乎只用 Y。UV 混进来导致每次读 Y 都加载没用的 UV，浪费带宽。
  3. **不利于灰度提取**：很多算法只要 Y（人脸识别、运动检测），Packed 提取 Y 要跳跃读取。

**加分项**：

- 对比 4:2:2 的 Packed（YUYV / UYVY）——4:2:2 数量是 2:1，可以优雅交错，所以这两个格式确实存在。

## 3. SwsContext（对应 [03](./03-SwsContext-图像缩放与格式转换.md)）

### Q3.1 ⭐ SwsContext 用来做什么？

**答题要点**：

- `libswscale` 模块的图像转换上下文。
- 同时做两件事：**像素格式转换 + 尺寸缩放**。
- 用法两步：`sws_getContext` 配规则，`sws_scale` 执行。

**加分项**：

- 主动说"它**主要不是缩放**"——`YUV420P → RGB24` 但分辨率不变才是最常见使用方式。
- 提性能要点：格式和尺寸不变时 `SwsContext` 必须复用，不要每帧重建。

---

### Q3.2 ⭐⭐ 写音视频抽帧存 JPEG 的代码，会涉及到 SwsContext 吗？为什么？

**答题要点**：

- 会。流程是：解码 → SwsContext 转 YUVJ420P（MJPEG 编码器要求）→ MJPEG 编码器 → 写 .jpg 文件。
- 关键点：`AVFrame` 是原始像素，**JPEG 是压缩文件**，中间必须经过 MJPEG 编码器。

**加分项**：

- 主动提为什么是 YUVJ420P 而不是 YUV420P——J 表示 JPEG 的 Full Range，MJPEG 编码器要求这个。
- 对比 PPM：PPM 极简（文件头 + RGB 字节），所以保存 PPM 只要 sws_scale 转 RGB24 后直接写文件，不需要二次编码。

---

### Q3.3 ⭐⭐⭐ 多线程场景下能多个解码线程共用一个 SwsContext 吗？

**答题要点**：

- **不能**。`SwsContext` 内部有状态，**不是线程安全**。
- 每个线程要么各自创建一个 SwsContext，要么用锁串行化。
- 工程上常用：每个解码线程绑一个 SwsContext。

**加分项**：

- 提 `sws_getCachedContext`——比对参数是否变化，没变就复用，变了重建。

---

## 4. 音频 PCM 与重采样（对应 [04](./04-音频PCM-采样-重采样.md)）

### Q4.1 ⭐ PCM 播放必须知道哪几个参数？少任何一个会怎样？

**答题要点**：

- **五个**：采样率、采样格式（位深+类型）、声道数、声道布局、内存排列（Planar/Packed）。
- 任何一个错都会导致问题：
  - 采样率错 → 变速变调
  - 采样格式错 → 杂音
  - 声道数错 → 速度异常
  - 声道布局错 → 左右反 / 5.1 错位
  - Planar/Packed 错 → 杂音 / 只有一边

**加分项**：

- 一句话总结："PCM 是裸字节流，没头信息，必须靠外部参数告诉它怎么解读"。

---

### Q4.2 ⭐ 为什么 FFmpeg 解码 AAC 后直接送 SDL 播放是刺耳杂音？

**答题要点**：

- AAC 解码默认输出 **FLTP**（32 位浮点、Planar）。
- SDL 默认期望 **S16**（16 位整数、Packed）。
- 数值类型和声道排列**同时全错**，必然杂音。
- 解决：插一个 `SwrContext` 做格式转换 + 重采样。

**加分项**：

- 解释为什么 AAC 解码默认 FLTP——AAC 编码内部做频域变换和心理声学分析，浮点不会溢出，Planar 让左右声道独立计算。
- 同样解释为什么 SDL 要 S16 Packed——硬件声卡爱交错排列、一路扫过去就能用。

---

### Q4.3 ⭐ 音频解码为什么 `avcodec_send_packet` 之后必须 while 循环 `avcodec_receive_frame`？

**答题要点**：

- 一个音频 packet（特别是 AAC）**可能包含多帧**。
- 只 receive 一次会丢音频帧——听感就是断断续续。
- 正确写法：

```cpp
avcodec_send_packet(ctx, pkt);
while (avcodec_receive_frame(ctx, frame) >= 0) {
    // 处理音频帧
}
```

**加分项**：

- 主动对比视频——视频通常一包一帧，写成单次 receive 也没事，但**音频不能偷懒**。

---

### Q4.4 ⭐⭐ 重采样输出 buffer 大小怎么算？为什么不能简单按比例？

**答题要点**：

- **不能简单按 `in_samples × out_rate / in_rate`** 算。
- 因为 `SwrContext` 内部有缓存和滤波延迟。
- 正确公式：

  ```
  out_samples = av_rescale_rnd(swr_get_delay + in_nb_samples, out_rate, in_rate, AV_ROUND_UP)
  ```

- 工程上通常用 `av_samples_alloc_array_and_samples` 自动分配。

**加分项**：

- 提算错会发生什么：**buffer 不够 → 丢尾音或偶发爆音**。

---

### Q4.5 ⭐⭐ 为什么音视频同步通常以音频为主时钟？

**答题要点**：

- 人耳对音频卡顿、断裂、变速极其敏感（耳朵秒辨）。
- 人眼对视频丢一两帧不敏感（视觉残留 + 大脑脑补）。
- 让音频自由跑，视频追音频——代价最小。

**加分项**：

- 提同步策略：

  ```
  视频 PTS < audio_clock - 阈值 → 丢帧追
  视频 PTS > audio_clock + 阈值 → 延迟显示
  ```

- 进阶：精确音频时钟要扣除设备 buffer 延迟（写进 buffer ≠ 真正播出）。

**翻车回答**：

- "可以以视频为主时钟"——技术上能，但工程上几乎没人这么做。

---

### Q4.6 ⭐⭐⭐ AAC 编码为什么需要 `AVAudioFifo`？

**答题要点**：

- 麦克风采集回调每次给出的样本数（比如 480 @ 10ms）和 AAC 编码器要求的 frame_size（1024）**不一致**。
- 需要用 FIFO 攒够 1024 samples 才能调一次编码。
- ffmpeg 提供 `AVAudioFifo` 专门做这件事。

**加分项**：

- 提**末尾 flush**：编码结束时 FIFO 里可能剩 < 1024 样本，要 flush 出来。
- 对比 Opus 编码器——Opus 支持 2.5/5/10/20/40/60ms 多档帧长，相对灵活。

---

### Q4.7 ⭐⭐⭐ AEC（回声消除）为什么必须有"远端播放参考信号"？

**答题要点**：

- 通话时扬声器播远端声音，本地麦克风把这个声音又采进去，传回远端 → 远端听到自己的回声。
- AEC 要从麦克风信号里**估计并减去回声分量**，必须知道远端原本播的是什么——这就是参考信号。
- 同时还要估计"播放到采集"的延迟，否则参考信号和回声对不齐。

**加分项**：

- 提 WebRTC 的音频处理模块（APM）：AEC + NS + AGC + VAD 一整套，很多 RTC 项目直接复用。

## 5. H.264 / MP4 / NALU（对应 [05](./05-H264-MP4-NALU.md)）

### Q5.1 ⭐ MP4 转 H.264 是不是转码？

**答题要点**：

- **通常不是**。前提是 MP4 视频轨本身就是 H.264。
- 做的事是**解封装 + 码流重打包**：
  1. 按 `moov` 索引从 `mdat` 取视频样本
  2. AVCC → Annex-B 转换
  3. 从 `avcC` 提取 SPS/PPS 注入
- 不涉及 decode + encode，画质不损失。

**加分项**：

- 主动说 `ffmpeg -i a.mp4 -c:v copy -bsf:v h264_mp4toannexb a.h264` 是怎么干的。
- 提"只有当编码不一致（HEVC → H.264）或要改编码参数（分辨率 / 码率 / 帧率）才需要真正转码"。

**翻车回答**：

- "是的，转码"——直接扣分。

---

### Q5.2 ⭐ AVCC 和 Annex-B 的差别一句话怎么说？

**答题要点**：

- **AVCC**：每个 NALU 前加 **4 字节长度字段**。MP4 / FLV / MKV 用。
- **Annex-B**：每个 NALU 前加 **起始码** `00 00 00 01`。RTMP / TS / RTP / 裸 .h264 用。
- SPS/PPS：AVCC 集中放在 `avcC` extradata；Annex-B 作为普通 NALU 混在流里。

**加分项**：

- 抛经典 bug：MP4 里的 H.264 字节直接喂 Android MediaCodec 会黑屏，因为硬解只认 Annex-B。
- 用 `h264_mp4toannexb` bitstream filter 解决。

---

### Q5.3 ⭐ 为什么有 PTS 和 DTS 两个时间戳？

**答题要点**：

- 因为有 **B 帧**。
- B 帧需要参考后面的 P 帧才能解码 → **解码顺序 ≠ 显示顺序**。
- DTS（Decoding Time Stamp）告诉解码器什么时候解码。
- PTS（Presentation Time Stamp）告诉渲染器什么时候显示。
- 无 B 帧时 PTS == DTS。

**加分项**：

- 抛例子：

  ```
  显示顺序: I B B P B B P
  解码顺序: I P B B P B B
  ```

- 提 ffmpeg 里所有时间戳是**整数刻度**而非秒，要靠 `time_base` 换算。

---

### Q5.4 ⭐⭐ 为什么直播场景要在每个 IDR 前注入 SPS/PPS？

**答题要点**：

- 解码器**必须先拿到 SPS/PPS 才能解码任何帧**。
- 直播观众随时切入，如果只在文件头注入一次，**中途加入的观众没拿到 SPS/PPS → 黑屏 / 花屏直到下一次出现**。
- 每个 IDR 前注入：体积略增（每个 IDR 多几十字节），但中途入会成功率大幅提升。

**加分项**：

- 提"SPS 描述整段视频的宽高 / profile / level，PPS 描述编码细节"。
- 提 IDR ≠ I 帧：IDR 是特殊的 I 帧，**强制清空之前所有参考帧缓冲**，所以 seek / 切入只能跳到 IDR。

---

### Q5.5 ⭐⭐ AAC 在 MP4 里和在 TS 直播流里格式有什么差别？

**答题要点**：

- **MP4 里是裸 AAC**：参数（采样率、声道）集中在文件头的 `esds` box，每帧不重复携带，省空间。
- **TS 直播里是 ADTS**：每帧前加 7 字节 ADTS header，包含同步字 `0xFFF`、采样率、声道、帧长。
- 设计动机和视频的 AVCC vs Annex-B **完全对应**：存储优化 vs 传输鲁棒性。

**加分项**：

- 解释为什么直播要 ADTS：观众随时切入，每帧必须自带说明书，否则无法立刻开始解码。

---

### Q5.6 ⭐⭐⭐ 普通 B 帧和参考 B 帧弱网时能丢哪个？怎么判断？

**答题要点**：

- **普通 B 帧**：不被任何帧参考，**可以随意丢**，顶多画面不流畅。
- **参考 B 帧**（分层 B / Hierarchical B）：被其他 B 帧参考，**绝对不能丢**，丢了依赖它的子帧会花屏。
- 判断方法：解析 NALU header 里的 `nal_ref_idc` 字段。

**加分项**：

- 提这是 H.264 / H.265 的高级特性，用于极致压缩。
- 提工程意义：直播弱网降帧策略**必须分辨这两种**——丢错就花屏。

---

## 6. 编码参数与码控（对应 [06](./06-编码参数与码控.md)）

### Q6.1 ⭐ H.264 决定压缩率的核心参数有哪些？

**答题要点**：

- 三个**独立维度**：
  1. **Profile**（算法复杂度）：Baseline / Main / High
  2. **Preset**（CPU 算力 vs 压缩率）：ultrafast → veryslow 共 10 档
  3. **码率控制**：CRF（恒定质量）/ CBR（固定码率）/ VBR（可变码率）

**加分项**：

- 强调"三个维度独立可组合"——破除"H.264 有个高低开关"的误解。
- 给一个典型组合：低延迟直播 = Baseline + ultrafast + tune=zerolatency。

---

### Q6.2 ⭐ WebRTC / 视频会议为什么必须用 Baseline Profile？

**答题要点**：

- Baseline **不支持 B 帧**。
- 没有 B 帧 → 解码器不需要等待后续帧 → **延迟极低**。
- High Profile 虽然压缩率最高，但天然引入 B 帧，延迟不可接受。

**加分项**：

- 同时配合 `tune=zerolatency` 关闭编码器内部 lookahead 缓冲——双保险。
- 提 "WebRTC SDP 协商时常见 `profile-level-id=42e01f` 就是 Baseline + Level 3.1"。

---

### Q6.3 ⭐⭐ CRF 数值越大画质越好还是越差？甜点区在哪？

**答题要点**：

- **数值越大画质越差**。CRF 范围 0-51。
- 甜点区 18-28（默认 23）。
- 18 视觉上基本无损，28+ 能看出马赛克。

**加分项**：

- 解释为什么用 CRF 而非 Bitrate：**CRF 模式下画质稳定但文件大小不确定**，适合点播；**Bitrate 模式适合带宽受限的直播**。
- 提 H.265 / HEVC 的 CRF 推荐值更高（默认 28），因为压缩更狠。

---

### Q6.4 ⭐⭐ 为什么直播推流命令里要同时设 `-maxrate` 和 `-bufsize`？

**答题要点**：

- `-maxrate`：限制瞬时码率峰值，防止突发流量冲爆 CDN 带宽配额。
- `-bufsize`：决定**峰值能持续多久**——越大越能容忍长峰，但累积延迟也越大。
- 工程经验：`bufsize` 通常设为 `maxrate × 1-2 秒` 比较合适。

**加分项**：

- 提这是 x264 / x265 的 VBV（Video Buffering Verifier）模型——模拟解码端缓冲区。

---

### Q6.5 ⭐⭐⭐ 设置 CRF 为什么必须用 `av_opt_set`，不能直接赋值给 codecCtx 的字段？

**答题要点**：

- CRF 是 **x264 编码器的私有参数**，不在 `AVCodecContext` 的公共字段里。
- 私有参数存在 `codecCtx->priv_data` 里，通过 `av_opt_set` 接口操作。
- 对比 `bit_rate` 是公共字段，可以直接 `codecCtx->bit_rate = 2000000`。

**加分项**：

- 解释这是 ffmpeg 的通用设计——通过 `priv_data` + `AVOption` 系统允许每个 codec 暴露独有参数。
- 提其他常用的 `av_opt_set` 调用：`preset` / `tune` / `profile`。

---

## 7. 硬件编解码（对应 [07](./07-硬件编解码.md)）

### Q7.1 ⭐ 硬件编码画质为什么通常不如同档软件编码？

**答题要点**：

- 硬件编码器为了**流水线效率**，省略了软件编码里"耗时但增益小"的高级搜索算法。
- 同等码率下，软编（x264 slow / veryslow）画质优于硬编（nvenc / videotoolbox）。
- 想让硬编画质追平，**得给更高的码率**。

**加分项**：

- 提 NVENC 在 Turing / Ampere / Ada 几代硬件上画质大幅追平 x264 medium，但极致质量仍输 x264 slow。
- 给工程权衡：

  - 直播 / 大批量转码（吞吐和成本）→ 硬编
  - 电影 / 高质量点播（压缩比）→ 软编
  - 移动端录制（功耗）→ 硬编

---

### Q7.2 ⭐ 硬件解码出来的 AVFrame，能直接喂给 `sws_scale` 吗？

**答题要点**：

- **不能**。`sws_scale` 是纯 CPU 实现，需要 CPU 指令读 `data[]`。
- 硬件帧的 `data[0]` 指向的是 **GPU 显存或硬件句柄**——CPU 直接读要么 segfault，要么走极慢的 PCIe 回读。
- 正确做法两种：
  1. `av_hwframe_transfer_data` 下载到 CPU 内存
  2. 用硬件滤镜（`scale_cuda` / `scale_videotoolbox`）在 GPU 上做

**加分项**：

- 提"硬件帧的 format 是 `AV_PIX_FMT_CUDA` / `AV_PIX_FMT_VIDEOTOOLBOX` 等特殊格式"，CPU 不认识。
- 给真实命令：`-hwaccel cuda -hwaccel_output_format cuda` + `scale_cuda` 滤镜实现全 GPU 转码。

---

### Q7.3 ⭐⭐⭐ macOS 上做硬件编解码学什么 API？

**答题要点**：

- 苹果的 **VideoToolbox**。
- 编码：`VTCompressionSession`
- 解码：`VTDecompressionSession`
- API 风格是 CoreFoundation C 接口，异步 + 回调。

**加分项**：

- 提"M 系列芯片的 Media Engine 编 4K 不烫手不耗电"——能耗比是 Apple Silicon 的核心优势之一。
- 提 FFmpeg 的 `h264_videotoolbox` 编 / 解码器是参考实现。

---

### Q7.4 ⭐⭐ 移动端怎么做硬件编解码？Android 和 iOS 有什么不同？（对应 [10](./10-移动端硬件编解码.md)）

**答题要点**：

- **Android**：`MediaCodec`（Java）/ `AMediaCodec`（NDK）。输入/输出**双缓冲区队列**模型，output buffer 用完必须 `releaseOutputBuffer`。解码前用 **CSD（csd-0=SPS、csd-1=PPS）** 喂参数集。
- **iOS**：`VideoToolbox`（`VTCompressionSession` / `VTDecompressionSession`），数据载体是 `CVPixelBuffer` / `CMSampleBuffer`。
- 两端都优先走**零拷贝**：Android 用 `Surface`/`SurfaceTexture`，iOS 用 `CVPixelBuffer`（IOSurface）直通 GPU。

**加分项**：

- 点出**比特流格式坑**：VideoToolbox 编码输出是 **AVCC（长度前缀），SPS/PPS 在 `CMVideoFormatDescription` 里**；推 RTP/裸流要转 **Annex-B 起始码 + 补 SPS/PPS**（接 [05](./05-H264-MP4-NALU.md)）。漏了对端只有声音没画面。
- 点出 **FFmpeg 在 Android 没有 MediaCodec 编码 wrapper**（只有 `h264_mediacodec` 解码），Android 硬编必须直接调系统 API——这是最容易答错的点。
- 点出 Android `ByteBuffer` 模式颜色格式因芯片而异、有 stride/slice-height 对齐，能用 Surface 就别碰 ByteBuffer。
- 点出 libwebrtc 移动端视频底座就是 VideoToolbox / MediaCodec。
- **零拷贝是这块最深的拉分点**（采集→编码 / 解码→渲染全程不下 CPU；UMA 下拷贝为何仍慢＝tiling+缓存一致性+同步 stall；Android dma-buf/gralloc/Surface vs iOS IOSurface/CVPixelBuffer）。完整原理 + 坑 + 面试问答见 [10 §四点五](./10-移动端硬件编解码.md#四点五ios-与-android-的零拷贝核心考点)。

## 8. 网络协议与流媒体（对应 [08](./08-网络协议与流媒体.md)）

### Q8.1 ⭐ TCP 和 UDP 在音视频场景下最关键的差别是什么？

**答题要点**：

- TCP 严谨可靠，但有**队头阻塞**——丢一个包，后续所有包都被扣留等待重传。
- UDP 不可靠但**无队头阻塞**——丢就丢了，下一个包立刻到应用层。
- 音视频里"实时性 >> 完整性"，所以 WebRTC 选 UDP；RTMP / HLS / HTTP-FLV 选 TCP 是历史包袱。

**加分项**：

- 主动抛"只要底层是 TCP（有序可靠交付），就跑不掉队头阻塞——这是协议层面无法绕过的限制"。
- 提 QUIC：Google 在 UDP 之上自己实现可靠传输，绕过 TCP 队头阻塞。

---

### Q8.2 ⭐ RTMP、HLS、HTTP-FLV、WebRTC 各自的延迟量级和典型场景？

**答题要点**：

| 协议 | 底层 | 延迟 | 场景 |
|---|---|---|---|
| RTMP | TCP / 1935 | 1-3 秒 | **推流端事实标准** |
| HLS | HTTP / TCP / 443 | 10-30 秒 | **大规模分发**（CDN 极友好） |
| HTTP-FLV | HTTP / TCP / 443 | 1-3 秒 | **国内观众端主力** |
| WebRTC | UDP / 动态 | < 500ms | **视频会议、连麦** |

**加分项**：

- 解释**行业黄金架构**：主播 RTMP 推流 → 服务器边缘节点换壳成 HTTP-FLV → 观众拉 FLV 看。
- 主动说为什么 RTMP 在浏览器消亡：Flash 死了，但推流端因为生态成熟（OBS）依然是 RTMP。

---

### Q8.3 ⭐⭐ 为什么 HLS 能扛千万级并发？

**答题要点**：

- HLS 把直播变成**下载静态切片文件**。
- CDN 最擅长的就是缓存和分发静态文件。
- 1000 万人请求同一个 `.ts` 切片，**请求根本到不了核心服务器**——文件早已缓存在离用户最近的 CDN 节点。
- 长连接协议（RTMP / FLV）要维持千万根连接，单机扛不住。

**加分项**：

- 主动说 HLS 是公开行业标准（不是苹果私有），云厂商 CDN 天然支持。
- 提 LL-HLS（Low-Latency HLS）可以把延迟降到 2-3 秒，但还是不如 HTTP-FLV / WebRTC。

---

### Q8.4 ⭐⭐ HTTP-FLV 是怎么把直播伪装成 HTTP 请求的？

**答题要点**：

- 用 HTTP/1.1 的 **`Transfer-Encoding: chunked`** 机制。
- 服务器响应头加 `chunked`，等于告诉浏览器"这文件多大我也不知道，会一块块发，发个 0 大小空块才算结束"。
- 服务器**永远不发空块**，HTTP 请求就永远不结束，变成"披着 HTTP 外衣的长连接水管"。

**加分项**：

- 抛 B 站开源的 `flv.js`——浏览器 JavaScript 拆 FLV 喂给 HTML5 `<video>`，完美绕过 Flash。
- 强调 HTTP-FLV 和 RTMP **内部的 FLV Tag 几乎二进制一致**，所以服务器换壳几乎不耗 CPU。

---

### Q8.5 ⭐⭐⭐ 为什么 1935 端口经常被防火墙封，但 80 / 443 不会？

**答题要点**：

- 网管的"最小权限原则"：除了上网必备端口（80 / 443），其他冷门端口一律封杀，减少攻击面。
- 80 / 443 是"正门"，敞开但部署最严密的安全设施（WAF）。1935、3306、22 是"偏门"，背后软件防攻击能力弱，索性焊死。
- 把所有偏门封掉**强迫攻击者必须从防守最严密的正门进**——这叫"收缩攻击面"。

**加分项**：

- 提现代防火墙是七层（WAF），不只看端口还看协议格式。试图把 RTMP 数据强发到 80 端口会被识别为非 HTTP 流量直接 reset。
- 这就是为什么 HTTP-FLV / 微信都要"协议伪装"成 HTTP。
- 行业事实：全球互联网流量 85%-90% 走 80 / 443。

---

### Q8.6 ⭐⭐⭐ WebRTC 怎么解决 UDP 丢包问题？

**答题要点**：

- 应用层自己造轮子。机制：
  1. **FEC（前向纠错）**：发 10 个包附带 2 个校验包，丢 1 个直接用校验包算回来，**不用重传**。空间换时间。
  2. **NACK（选择性重传）**：按 **RTP 序列号**重传丢失的那个**包**（粒度是包，不是帧），适合少量偶发丢包。
  3. **PLI / FIR（请求关键帧）**：丢太多、参考链崩了，NACK 补不回来时，请求对端**立刻产一个 IDR**（粒度是整帧）重新起步。
  4. **拥塞控制**（GCC）：估计网络容量，动态调整发送速率。

**加分项**：

- 强调 **NACK vs PLI/FIR 的区别**："NACK 补丢的那个小包，PLI/FIR 直接要一张完整关键帧"——两者都是 RTCP 反馈，粒度和触发场景不同。这是高频追问点。
- 提**Jitter Buffer**——接收端缓存包按时间戳重排序、抗抖动、必要时做 PLC（丢包隐藏）。
- 提这套机制是 WebRTC 的**核心价值**，不是"用了 UDP"这件事本身。

---

### Q8.7 ⭐⭐⭐ 讲一下 WebRTC 的建连流程和传输栈（对应 [08 §十](./08-网络协议与流媒体.md)）

**答题要点**（按"信令 → 连通 → 媒体"三段答）：

1. **信令 + 协商**：两端通过自建的信令通道（WebSocket 等，**不属于 WebRTC 标准**）交换 **SDP offer/answer**（协商 codec、分辨率、`profile-level-id`）和 **ICE candidate**。
2. **连通（NAT 穿透）**：**ICE** 框架收集 candidate，借 **STUN** 打洞尝试端到端直连，直连失败用 **TURN** 中继兜底。
3. **媒体传输**：媒体走 **UDP 上的 RTP**（序列号/时间戳/负载类型），**RTCP** 回报 SR/RR（丢包率、抖动、RTT）并承载 NACK / PLI/FIR；全程 **DTLS-SRTP** 强制加密；**GCC** 靠 transport-cc/REMB 反馈做带宽估计、动态调码率。

**加分项**：

- 多人会议提 **SFU（转发不解码）vs MCU（混流）**，并解释 WebRTC 自建 CDN 比 HLS 贵——有状态实时会话 vs 无状态静态缓存。
- 提 GCC 把**延迟梯度**当主信号，比"等丢包才降速"更早反应。

## 9. 综合 / 系统设计题

### Q9.1 ⭐⭐ 让你写一个最简播放器，你会怎么做？

**答题要点**（按四段式答）：

【1. 先给结论】"最小可行播放器是 demux + decode + render 三步。"

【2. 整体流程】

```
avformat_open_input("input.mp4")
  → 找到视频流 / 音频流
avcodec_send_packet → avcodec_receive_frame
  → 视频:用 SwsContext 转 RGB,送 SDL/OpenGL 渲染
  → 音频:用 SwrContext 转 S16,送 SDL Audio Callback
音视频同步:以音频为主时钟,视频按 PTS 决定显示或丢帧
```

【3. 关键技术点】

- AVPacket → AVFrame 流转
- `time_base` 跨模块换算
- 引用计数循环复用（unref 而非 free）
- linesize 按行偏移
- audio callback 不能阻塞

【4. 踩坑预案】

- MP4 转 H.264 需要 `h264_mp4toannexb` bitstream filter
- AAC 输出 FLTP 必须转 S16
- 硬件解码帧不能直接 swscale
- seek 后所有 buffer / decoder 都要 flush

**加分项**：

- 主动提**三线程模型**：demux 线程 → packet queue → decode 线程 → frame queue → render 线程
- 提**资源管理**：用 RAII + std::unique_ptr 包装 AVFrame / AVPacket
- 提**性能优化**：SwsContext / SwrContext 必须复用

---

### Q9.2 ⭐⭐ 直播首屏秒开怎么优化？

**答题要点**：

- 多管齐下：

  1. **协议层**：HTTPS 改 TLS 1.3 / 0-RTT；用 HTTP-FLV 代替 HLS（HLS 至少 2-3 秒）
  2. **GOP 层**：缩短 GOP（1-2 秒一个），让新用户更快遇到 I 帧
  3. **传输层**：服务器**预先缓存** GOP，新用户连上立刻推最近的 I 帧
  4. **客户端层**：先解前几帧并立刻渲染，不等够 3 帧 buffer 才播
  5. **DNS 层**：DNS 预解析、HTTPDNS、连接复用

**加分项**：

- 主动提"首屏 vs 卡顿率 vs 延迟"是个三角，优化首屏可能拉高卡顿率。
- 提**预连接**和**预拉流**：App 启动时就建好 TCP 连接，用户点击瞬间立刻可拉流。

---

### Q9.3 ⭐⭐⭐ 弱网下视频卡顿怎么诊断和优化？

**答题要点**：

- **诊断**：
  - 区分是网络丢包还是带宽不足
  - 看 RTT、丢包率、抖动、平均码率
  - 客户端打印接收 buffer 水位 / 解码耗时 / 渲染耗时
- **优化方向**：
  1. **协议**：TCP 改 UDP（WebRTC）规避队头阻塞
  2. **编码**：降码率 / 降分辨率自适应（ABR）
  3. **冗余**：FEC 前向纠错对抗丢包
  4. **重传**：NACK 按序列号重传丢失的包；参考链崩了则 PLI/FIR 请求关键帧
  5. **拥塞控制**：GCC / BBR 动态调整发送速率
  6. **缓冲**：jitter buffer 抗抖动
- **降级**：丢普通 B 帧保流畅（但参考 B 帧不能丢）

**加分项**：

- 提音视频降级**策略不同**——视频可以丢帧，音频通常用 PLC 而非简单丢。
- 提弱网测试工具：iOS Network Link Conditioner、Linux tc、Mac Network Link Conditioner。

## 12. 你现在能去面试什么级别

把上面打分表填完后，对照下面的标准。

### 12.1 校招 / 1-3 年初级（音视频方向）

**门槛**：

- 所有 ⭐ 题 ≥ 90% A
- ⭐⭐ 题 ≥ 60% B 以上
- ⭐⭐⭐ 题随便

**你现在能不能去**：

### 12.2 3-5 年中级（音视频工程师 / 流媒体 / RTC）

**门槛**：

- 所有 ⭐ 题 100% A
- ⭐⭐ 题 ≥ 80% A
- ⭐⭐⭐ 题至少 30% A 或 B
- **必须**：写过最简播放器 + 转码器 + 至少一个真实工程经验（不一定是公司的，开源贡献 / 个人项目都算）

**你现在能不能去**：

- 至少要先把最简播放器代码跑通、解决过至少 3-5 个真实坑、对 PTS/DTS 跨模块换算有亲手代码经验。
- **目前看你的笔记深度够中级理论门槛**，但工程实践还差关键一环——写代码。

### 12.3 5 年以上高级 / 资深（音视频架构师 / RTC 引擎核心）

**门槛**：

**你现在能不能去**：

- 笔记和题目只能保证你"讲清楚"，但拿到 offer 还需要"做过事"。

## 13. 检验流程建议

读完这份文档不等于会面试。建议按这个流程检验自己：

```
第一遍:盖住答案,口述每一道 ⭐ 题
       → 错的 / 卡壳的 / 漏加分项的标记出来
       → 回到对应主题文档复习

第二遍:对着镜子讲 10.2 的 3 分钟自述
       → 录音听一遍,看自己讲得流畅吗、有没有干瘪堆术语

第三遍:找一个真懂音视频的朋友 / 学长,让他随机抽 10 道题问你
       → 抗住实战压力

第四遍:写完最简播放器代码后,对着代码再过一遍 Q9.1
       → 这时你的回答会从"读过"变成"做过",质感完全不同
```

**核心心法**：面试不是考记忆力，是**考你能不能在压力下流畅讲清楚自己懂的东西**。这份文档里所有的"答题要点"和"加分项"，**必须经过你嘴讲一遍才算掌握**——光读完没用。
