## 一、为什么需要硬件编解码

软件编解码（`libx264` / `libfdk_aac` 等）是把编码算法用 CPU 指令实现。优点是跨平台、灵活、可调参数多；缺点是**CPU 占用高、功耗高、单机吞吐有限**。

硬件编解码把编码算法实现在专用芯片里（GPU 上的视频引擎，或者独立 ASIC）。优点是：

- **CPU 占用极低**：编 4K 视频时 CPU 几乎不动
- **功耗低**：手机录 4K 不烫手就是因为走硬件
- **吞吐高**：一张 NVIDIA 显卡能并发编码几十路 1080p 直播
- **延迟可控**：硬件流水线天然支持低延迟模式

缺点：

- **画质 / 压缩率不如同档 CPU 软编**（同等码率下软编画质更好）
- **参数可调性有限**（厂商只暴露部分参数）
- **驱动 / SDK 复杂**，调试难度高
- **跨平台需要写三套代码**（每个平台一套硬件 API）

## 二、三大平台对比

### 2.1 NVIDIA：NVENC / NVDEC（首选学习目标）

**为什么推荐先学**：

- **生态最完善**：NVIDIA Video Codec SDK 是工业界最广泛、文档最全、社区支持最好的方案
- **FFmpeg 集成最成熟**：`h264_cuvid` / `hevc_cuvid`（解码）、`h264_nvenc` / `hevc_nvenc`（编码）几乎是 ffmpeg 硬件加速的事实参考
- **应用面最广**：云游戏、OBS 直播推流、NVIDIA DeepStream AI 视频分析

学习路径：

1. **命令行**：先用 ffmpeg 跑硬编硬解，观察 CPU / GPU 占用变化
2. **官方 SDK**：下载 [NVIDIA Video Codec SDK](https://developer.nvidia.com/nvidia-video-codec-sdk)，跑通 Sample Code
3. **读 ffmpeg 源码**：研究 `libavcodec/nvenc.c` 看 FFmpeg 是怎么封装底层 SDK 的

### 2.2 Apple：VideoToolbox

**为什么必学（如果你做 Mac / iOS）**：

- M 系列芯片的 Media Engine 能耗比极高，硬编 4K 不发热
- API 设计现代，CoreFoundation 风格，异步 + 回调

学习路径：

1. 读 [VideoToolbox 框架文档](https://developer.apple.com/documentation/videotoolbox)
2. 学 `VTCompressionSession` 和 `VTDecompressionSession`
3. FFmpeg 的 `h264_videotoolbox` 编 / 解码器是参考实现

**你的项目相关**：你在 macOS 上做 WebRTC + ffmpeg 学习，VideoToolbox 是你硬件加速的唯一选择（M 系列 Mac 没法装 NVIDIA 卡）。

### 2.3 Intel：Quick Sync Video（QSV）

**为什么了解**：

- 普及率最高——几乎所有带核显的 Intel CPU 都支持
- 在没有独显的轻薄本 / 低成本服务器上是唯一硬件方案
- 性能优秀，画质和速度都很能打

学习路径：

- Intel 官方的 [oneVPL](https://www.intel.com/content/www/us/en/developer/tools/oneapi/onevpl.html)（以前叫 Media SDK）
- FFmpeg 的 `h264_qsv` / `hevc_qsv`

### 2.4 三家对比一眼版

| 平台 | 编 / 解码器名 | 典型场景 | 上手难度 |
|---|---|---|---|
| NVIDIA | `h264_nvenc` / `h264_cuvid` | 云游戏、直播服务器、AI 视频 | 中（生态完善） |
| Apple | `h264_videotoolbox` | Mac / iOS 应用、本地编辑 | 中（API 现代） |
| Intel | `h264_qsv` / `hevc_qsv` | 核显轻薄本、低成本服务器 | 高（文档相对少） |
| 通用 | `vaapi`（Linux） / `dxva2` `d3d11va`（Windows） | 跨平台抽象层 | 高 |

## 三、学习路径（推荐三阶段）

### 阶段 1：先用命令行建立直观感受

不要一上来啃底层 API。先把概念跑通：

```bash
# NVIDIA
ffmpeg -i input.mp4 -c:v h264_nvenc output.mp4

# Apple
ffmpeg -i input.mp4 -c:v h264_videotoolbox output.mp4

# Intel
ffmpeg -i input.mp4 -c:v h264_qsv output.mp4
```

观察 CPU 占用、GPU 占用、编码速度的变化。这一步建立"硬件加速到底快多少 / 省多少 CPU"的直觉。

### 阶段 2：用 FFmpeg 的 HWAccel API 写 C++ 代码

**强烈推荐这个切入点**——不要直接调 NVIDIA / Apple 的原生 API，先学 FFmpeg 封装好的硬件抽象。

核心 API：

```cpp
av_hwdevice_ctx_create(&hwDeviceCtx, AV_HWDEVICE_TYPE_CUDA, nullptr, nullptr, 0);
// 创建硬件设备上下文(连接 GPU)

av_hwframe_ctx_alloc(hwDeviceCtx);
av_hwframe_ctx_init(...);
// 初始化硬件帧上下文(在显存中分配内存池)

av_hwframe_transfer_data(swFrame, hwFrame, 0);
// 在 CPU 内存和 GPU 显存之间拷贝数据
```

**实战目标**：写一个 C++ 程序，用 ffmpeg API 调 GPU 解码视频，把硬件帧下载到 CPU 内存保存成图片。参考 ffmpeg 源码 `doc/examples/hw_decode.c`。

走完这一步，你就理解了"硬件帧不能直接当软件帧用"这个核心约束。

### 阶段 3：进阶到原生 SDK

当 FFmpeg 抽象不能满足极致性能要求时（云游戏、零延迟推流），再去啃原生 SDK：

- NVIDIA：直接调 `cuvidDecodePicture` 和 `NvEncEncodePicture`
- Apple：直接操作 `CVPixelBuffer` 和 `VTCompressionSession`
- Intel：调 oneVPL 的 mfx API

## 四、硬件帧的特殊性（最重要的概念）

这是硬件编解码学习里**必须建立的核心直觉**：硬件解码出的 `AVFrame` **和软件解码出的 `AVFrame` 在内存模型上完全不同**。

### 4.1 软件解码的 AVFrame

```
AVFrame
  +-- data[0] -> 系统内存(RAM)中的 Y 平面
  +-- data[1] -> 系统内存中的 U 平面
  +-- data[2] -> 系统内存中的 V 平面
```

CPU 可以直接读写 `data[]`。`sws_scale` 在 CPU 上跑 AVX / SSE / NEON 指令处理这些数据。

### 4.2 硬件解码的 AVFrame

```
AVFrame
  +-- data[0] -> 硬件表面句柄(Handle) 或映射到 GPU 显存的特殊地址
  +-- format  -> AV_PIX_FMT_CUDA / AV_PIX_FMT_VIDEOTOOLBOX / AV_PIX_FMT_QSV ...
```

**CPU 不能（直接）读这块地址**。强行 memcpy 要么：

- 触发段错误（Segfault）直接崩
- 触发 PCIe 总线回读，极其缓慢

## 五、sws_scale 为什么不能处理硬件帧

详见 [03-SwsContext-图像缩放与格式转换.md](./03-SwsContext-图像缩放与格式转换.md)，这里展开讲。

**`sws_scale` 是纯软件实现**。它需要 CPU 指令逐字节读 `AVFrame->data` 指向的内存。

如果你的 `AVFrame` 是硬件帧，`data` 指针指向 GPU 显存——`sws_scale` 内部执行 `*ptr = ...` 操作时要么崩溃，要么走非常慢的 PCIe 回读路径。

### 5.1 方案一：先下载到 CPU 内存（简单但有性能损耗）

```cpp
AVFrame* swFrame = av_frame_alloc();
int ret = av_hwframe_transfer_data(swFrame, hwFrame, 0);
if (ret >= 0) {
    // swFrame 现在在 CPU 内存,通常是 NV12 格式
    // 可以安全交给 sws_scale 处理
    sws_scale(swsCtx,
              swFrame->data, swFrame->linesize, 0, swFrame->height,
              dstFrame->data, dstFrame->linesize);
}
av_frame_free(&swFrame);
```

什么时候用这种方案：

- 抽帧存图（一秒钟才取一帧，性能不敏感）
- 算法分析（需要 CPU 上的图像）
- 调试 / 验证流程

### 5.2 方案二：全程在 GPU 上处理（推荐，性能最高）

数据已经在 GPU 上了，让 GPU 顺便把缩放和格式转换也做了。FFmpeg 提供硬件滤镜：

| 滤镜 | 平台 |
|---|---|
| `scale_cuda` / `hwupload_cuda` / `hwdownload` | NVIDIA |
| `scale_qsv` | Intel |
| `scale_vt` / `scale_videotoolbox` | Apple |
| `scale_vaapi` | Linux VA-API |

工作流：

```
硬件解码 -> 硬件帧 -> 硬件滤镜图 (scale_cuda 等) -> 硬件编码
                       |
                       v (可选)
              硬件 -> CPU (hwdownload) -> 保存文件
```

完全不占用 CPU。云转码集群、零延迟推流都用这套架构。

## 六、命令行实战：硬件转码完整链路

### 6.1 NVIDIA 硬解硬编（数据全程在 GPU）

```bash
ffmpeg -hwaccel cuda -hwaccel_output_format cuda \
    -i input.mp4 \
    -vf "scale_cuda=1280:720" \
    -c:v h264_nvenc -preset p4 \
    output.mp4
```

- `-hwaccel cuda`：启用 CUDA 硬件加速
- `-hwaccel_output_format cuda`：让解码器输出留在 GPU
- `scale_cuda`：GPU 上做缩放
- `h264_nvenc`：GPU 上做编码

这条命令 CPU 占用接近 0。

### 6.2 Apple VideoToolbox 硬解硬编

```bash
ffmpeg -hwaccel videotoolbox \
    -i input.mp4 \
    -c:v h264_videotoolbox -b:v 4M \
    output.mp4
```

M1 / M2 / M3 上跑 4K 转码飞快，几乎不耗电。

## 七、硬件编码的画质问题

硬件编码器为了硬件流水线效率，**通常省略了 CPU 软编里那些"耗时但增益小"的搜索算法**。所以：

- **同等码率下，软编（x264 slow / veryslow）画质优于硬编（nvenc / videotoolbox）**
- **想让硬编画质追上软编，需要给硬编更高的码率**

NVENC 在最新几代显卡（Turing / Ampere / Ada）上画质大幅追平 x264 medium，但极致质量仍然不如 x264 slow。

### 7.1 为什么软编能追极致画质（背后的原理）

> 上面只给了结论"软编画质更高"。这里讲透为什么——理解这层，硬编的取舍就全通了。

一句话本质：

> **画质 = 在给定码率下，把每一个编码决策做到最优。而"最优决策"靠的是海量搜索和计算。软编可以不计时间成本地穷举、去算；硬编被固定流水线的时间 / 功耗预算和固化在硅片里的算法卡死，只能用便宜的近似。**

拆成四点：

**(1) 软编可以"慢"，硬编不能。**
软编是跑在 CPU 上的代码，`-preset veryslow` 能让它花几秒甚至几十秒编一帧。离线场景（电影母带、VOD 转码）没有实时约束——慢没关系，画质好就行。这是软编最大的本钱：**用时间换质量**。硬编是为实时 + 低功耗而生的固定功能电路，每帧只有固定的时钟周期预算，不可能为一帧多花 100 倍时间。

**(2) 核心杠杆：穷举搜索 + 率失真优化（RDO）。**
编码质量取决于一连串"选择题"答得准不准——运动估计（参考帧里最像的位置在哪、子像素精修到多细）、模式决策（帧内还是帧间、切多大的子块）、量化（每个系数怎么量化最划算）。"最优答案"要靠 **RDO**：把每个候选方案真的试编一遍，算代价 `J = 失真 D + λ × 码率 R`，选 J 最小的。这极其耗算力——软编可以对几乎每个决策都跑 RDO、做大范围运动搜索、试遍所有切块形状；硬编只能用便宜的启发式、缩小搜索窗、跳过或粗略近似 RDO。**这是软硬画质差距的根本来源。**

**(3) 软编特有的几样"重武器"：**

| 手段 | 软编 | 硬编 |
|---|---|---|
| 运动搜索范围 / 子像素精度 | 可以很大、很精 | 受限的小搜索窗 |
| 多参考帧 / B 帧金字塔 | 充分使用 | 常限制参考数和 B 帧深度 |
| Trellis 量化（RDOQ） | 支持 | 多为近似 |
| 多遍 / 长 look-ahead（2-pass、MB-tree） | 可分析整段内容再最优分配码率 | look-ahead 很浅 |
| 心理视觉优化（psy-RD、AQ 自适应量化） | x264 的"看家秘方"，按人眼感知调 | 基本没有 |

尤其**多遍编码 + 长 look-ahead**：软编能先把整段内容扫一遍，知道哪段是高潮打斗、哪段是静止字幕，再把码率智能倾斜过去；硬编受流水线限制，看不了那么远。

**(4) 软件能升级，硬件冻结。**
x264 / x265 一直出新版、算法在变好；硬件编码器在流片时就定死了。所以新版软编常能反超几年前的硬件编码器。

> 关联 [06-编码参数与码控.md](./06-编码参数与码控.md)：`-preset` 慢档之所以更清晰，本质就是放开了上面这些搜索和 RDO；`-tune zerolatency` 之所以掉画质，是因为它关掉了 look-ahead / B 帧这些"要等未来帧"的手段。硬编相当于天生就被钉在"快但浅"这一端。

实际工程取舍：

- 直播 / 转码（追求吞吐和成本）：硬编
- 电影 / 高质量点播（追求极致压缩比）：软编
- 移动端录制：硬编（功耗优先）

## 八、常见陷阱

| 陷阱 | 真相 |
|---|---|
| 硬件帧直接喂 `sws_scale` | 崩溃或极慢，必须先 `av_hwframe_transfer_data` 或用硬件滤镜 |
| 硬件帧直接 memcpy 出去 | `data[]` 是不透明句柄，不是连续内存 |
| 多个解码器共享硬件帧 pool | 帧引用计数管理不当会导致显存泄漏 |
| 假设硬件编码画质等于软编 | 同码率下硬编画质通常稍逊，需要给更高码率 |
| 跨硬件平台共享代码 | 每个平台的硬件帧格式都不一样，业务层必须抽象 |
