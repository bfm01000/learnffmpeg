## 面试速答模板（30 秒口语化回答）

### Q：音视频同步是怎么做的？

> "音视频同步的核心是**选一个主时钟（Master Clock），另一个流向它看齐**。业界几乎都选音频时钟做主时钟——因为人对声音断续极其敏感，音频必须按固定节拍播放不能变，视频可以丢帧或重复。
>
> 具体做法三句话：第一，播放循环前先选主时钟，通常设音频时钟为 master。第二，视频帧解码出来后，拿自己的 PTS 和音频时钟的当前播放时间做差——如果视频落后超过阈值（比如 20ms），直接丢弃当前帧、去取下一帧；如果视频超前超过阈值，sleep 等一等；如果在阈值内，就正常渲染。第三，计算差值的那个音频时钟，是通过音频回调里把已经送入声卡播放的样本数累积换算出来的，这个时钟单调递增、天然稳定。
>
> 这是**视频同步到音频**的标准方案。反过来，音视频都同步到**系统时钟**的玩法更多用在直播场景——直播的源是实时产生的，没有"参考流"可以跟随，所以两边都追系统墙钟。"

### Q：推流端和播放端的同步有什么区别？

> "推流端是**产生时间线**，播放端是**消费时间线**。推流端要保证的是音视频 PTS 从同一源头产生、互相对齐，推上去的流本身就是同步的；播放端要保证的是解码渲染跟上 PTS 时间线。推流端出问题，播放端再怎么做同步也没用——源头就歪了。"

## 一、为什么需要音视频同步——问题的本质

### 1.1 同一个时间戳，两个物理意义

核心矛盾一句话就能说清楚：

```
视频帧 PTS = 1000ms → 要在第 1000ms 显示这一帧画面
音频帧 PTS = 1000ms → 要在第 1000ms 把这段声音送入扬声器

但谁来保证这俩"第 1000ms"是同一个时刻？
```

没有同步机制时：

```
墙钟时间:  0ms    16ms    32ms    48ms    64ms
视频解码:  帧0    帧1     帧2     帧3     帧4
视频渲染:  帧0    帧1     帧2     帧3     帧4   ← 按 GPU 能力全速输出

音频解码:          帧0             帧1             帧2
音频播放:          帧0━━━━━━━━━━━━帧1━━━━━━━━━━━━帧2
                   ↑ 每帧 23ms 音频，必须匀速播放

结果: 视频早就跑到 64ms 了，音频还在 23ms → 声画错位
```

### 1.2 为什么不同步是常态而不是意外

音视频从采集到播放，经过的路径完全不同：

```
采集端:
  摄像头 ──→ ISP ──→ 采集回调 ──→ 帧队列 ──→ 编码器 ──→ 网络发送
      ⬆ 可能因为光照/曝光延迟
                                                       └── 两个独立的 RTC
  麦克风 ──→ ADC ──→ 采集回调 ──→ 帧队列 ──→ 编码器 ──→ 网络发送
      ⬆ 可能因为 AudioFlinger 缓冲区延迟

播放端:
  网络接收 ──→ 解复用 ──→ 视频解码队列 ──→ 解码器 ──→ 渲染队列 ──→ GPU渲染
                                            ↕ 耗时不对称
  网络接收 ──→ 解复用 ──→ 音频解码队列 ──→ 解码器 ──→ 播放队列 ──→ 声卡播放
```

**每一步都在积累时间差**。采集时音频和视频触发时刻就不一样，编码耗时不一样（视频一帧几到几十毫秒，音频不到一毫秒），网络传输的抖动也不一样，解码速度更不一样——如果不主动做同步，播放出来一定是错位的。

### 1.3 推流端和播放端的根本区别

| | 推流端（你产生数据） | 播放端（你消费数据） |
|:---|:---|:---|
| **职责** | 给音视频打上正确的时间戳 | 按照时间戳正确渲染 |
| **时钟来源** | 系统墙钟（`gettimeofday` / `clock_gettime`） | 主时钟（通常是音频时钟） |
| **关键问题** | 采集时的时间戳对齐 | 解码渲染时的追赶/等待策略 |
| **出错表现** | 整个流就是歪的，播放端怎么修都修不回来 | 画面卡/跳/音画不同步 |

面试里被问到"你做的推流有没有音画不同步问题"，首先要确认对方问的是**推流端产生的时间戳**还是**播放端渲染**——两回事，技术方案完全不同。

## 二、播放端的三种经典同步策略

这是音视频面试最核心的理论考点。三种策略的本质区别在于：**选谁当主时钟（Master Clock）**。

### 2.1 策略一：音频主时钟（Audio Master）——业界绝对主流

**一句话**：音频按自己的节奏播，视频追赶音频。

**为什么选音频**：

| 对比维度 | 音频 | 视频 |
|:---|:---|:---|
| 播放约束 | 必须匀速，不能变速（会变调/爆音） | 可以丢帧、可以重复、可以快进 |
| 人对异常的敏感度 | 极高——几毫秒的断音/变调就能察觉 | 相对低——偶尔跳一帧几乎注意不到 |
| 时钟稳定性 | 声卡有硬件 DMA 驱动，回调准时 | GPU 渲染时间波动大，不稳定 |
| 数据密度 | 每 ~21ms（1024 samples @ 48kHz）一帧 | 每 ~33ms（30fps）一帧 |

**机制**：

```
音频时钟 = 声卡已经播放的样本数 / 采样率 × 1000 (转换为毫秒)

音频回调执行时：
    已播放样本数 += 本次回调送入的样本数
    音频时钟 = 已播放样本数 / 48000 * 1000
```

时钟是**自然递增**的——声卡一个样本一个样本往外吐，有硬件保证节奏。不存在"漏掉"或"跳变"。

**视频追赶算法（核心）**：

```
对每一帧解码后的视频帧：
    video_pts = frame->pts * time_base * 1000      // 转为毫秒
    audio_clock = GetAudioClock()                    // 当前音频播放到哪了
    diff = video_pts - audio_clock                   // 正 = 视频超前，负 = 视频落后

    if diff < -THRESHOLD:          // 视频落后太多，追不上了
        丢弃这帧，去取下一帧         // 宁可跳帧也要追
    elif diff > THRESHOLD:         // 视频超前，等一下音频
        sleep(diff - 阈值)          // 精确等，不忙等
    else:                          // 在阈值范围内
        正常渲染                     // 它就是对的
```

**阈值怎么定**：通常 10~30ms。太大——人眼能察觉声画不同步；太小——频繁 sleep/丢帧反而引入抖动。经验值：高质量播放用 10ms，普通播放用 20ms，弱网/低端机用 30ms。

**ffplay 源码印证**（`ffplay.c` 的 `video_refresh()` 函数）：

```c
// ffplay 的核心音视频同步逻辑（简化）
static void video_refresh(void *opaque, double *remaining_time)
{
    VideoState *is = opaque;
    double time;

    if (is->video_st) {
retry:
        if (frame_queue_nb_remaining(&is->pictq) == 0) {
            // 没帧可显示，什么都不做
        } else {
            Frame *vp = frame_queue_peek_last(&is->pictq);
            Frame *lastvp = frame_queue_peek(&is->pictq);

            // 计算视频帧的显示延迟 = 视频帧PTS - 音频主时钟
            last_duration = vp_duration(is, vp, lastvp);
            delay = compute_target_delay(last_duration, is);

            time = av_gettime_relative() / 1000000.0;
            if (time < is->frame_timer + delay) {
                // 还没到显示时间，等
                *remaining_time = FFMIN(is->frame_timer + delay - time, *remaining_time);
                goto display;  // 显示当前帧
            }

            // 时间到了，更新 frame_timer
            is->frame_timer += delay;
            if (delay > 0 && time - is->frame_timer > AV_SYNC_THRESHOLD_MAX)
                is->frame_timer = time;  // 差距太大：重置时间线

            frame_queue_next(&is->pictq);

            // 关键：如果视频落后音频太多，连续丢帧追赶
            if (frame_queue_nb_remaining(&is->pictq) > 1) {
                Frame *nextvp = frame_queue_peek(&is->pictq);
                duration = vp_duration(is, vp, nextvp);
                if (time > is->frame_timer + duration) {
                    frame_queue_next(&is->pictq);  // 丢帧！
                    goto retry;
                }
            }
        }
    }
display:
    // 渲染
}
```

核心逻辑：
1. 计算当前帧的 PTS 与音频时钟的差值 → 得出 delay
2. 如果还没到时间 → sleep（返回 `remaining_time` 给主循环）
3. 如果已经过时 → 检查下一帧：如果下一帧也过时了 → 直接丢当前帧，继续检查下一帧（连续丢帧追赶）
4. `AV_SYNC_THRESHOLD_MAX` 是兜底——差距太大、追不上了，直接重置时间线

#### 🔬 深入：`AV_SYNC_THRESHOLD_MAX` 时间线重置详解

面试官很可能追问这一行逻辑，因为它暴露了候选人对"时钟域"和"追赶边界"的理解深度。

**第一步：音频同步到底发生在哪里？——在 `delay` 里**

很多人以为 `frame_timer` 和音频时钟直接比较，其实不是。音视频同步发生在 `compute_target_delay()` 这个函数里，它调整的是 `delay`：

```c
// compute_target_delay 的核心逻辑（简化）
static double compute_target_delay(double duration, VideoState *is) {
    // diff = 视频帧的 PTS - 音频当前播放到的 PTS
    //       两者都在"流时间"域（stream time），单位秒
    double diff = is->video_clock - audio_clock_get(&is->audio_clock);

    if (fabs(diff) < sync_threshold) {
        // 差距在阈值内：delay = 原始帧间隔，不做调整
        return duration;                    // 例: 33ms
    } else if (diff < -sync_threshold) {
        // 视频落后音频：缩小 delay → 这一帧提前结束
        return 0;                           // 立刻显示下一帧（变相丢帧）
    } else {
        // 视频超前音频：拉长 delay → 等多一会儿
        return 2 * duration;                // 例: 66ms
    }
}
```

**音频时钟只在这一步起作用**——它和视频 PTS 做差，算出一个矫正量，融进 `delay` 里。`delay` 已经"携带"了音频同步的信息。

**第二步：`frame_timer` 是什么——"音频节奏"在墙钟上的投影**

`frame_timer` 的值是系统时间（和 `av_gettime_relative()` 同域），但它的**每一步推进量**是上面那个被音频矫正过的 `delay`：

```
概念对应:
  音频时钟  → 速度计（决定快慢节奏）
  delay    → 每一步的步长（由速度计调整：落后了就跑快点，超前了就慢点）
  frame_timer → 累计走出的距离（每一步都踩在系统时间的地面上）

简单类比:
  音频是节拍器（tempo），delay 是每一步跨多大，
  frame_timer 是你每一步落地时墙钟指向的时刻。
  节拍器的节奏透过步长，体现在你的落地时刻上。
```

正常播放时的递推：

```
帧#0:
  diff = video_pts - audio_clock ≈ 0   → delay = 33ms（正常帧间隔）
  time = 当前系统时间 = 1000ms
  time < frame_timer + delay ? → 1000 < 1033 → 等 33ms
  frame_timer += delay          → frame_timer = 1033ms

帧#1:
  diff = video_pts - audio_clock ≈ 0   → delay = 33ms
  time ≈ 1033ms
  frame_timer += delay          → frame_timer = 1066ms
  → 逐帧递推，frame_timer 按音频矫正过的步长稳定前进
  → 只要音频不断、不暂停、不 seek，frame_timer 和系统时间几乎同步
```

注意：`time vs frame_timer` 的比较**不是在做音视频同步**——同步已经在 `delay` 里做完了。这一步只是在做**"到没到这一帧该显示的时刻"**的检查，本质是**帧率控制**（按目标帧率间隔均匀显示）。

**第三步：那 `AV_SYNC_THRESHOLD_MAX` 在兜什么底**

兜的是"音频节奏还在，但投影坐标系歪了"的情况。具体说：

```
正常时:
  音频clock:  ────────────────────────────→  持续推进
  delay:      33, 33, 33, 33, 33, ...      稳定步长
  frame_timer: ────────────────────────────→  按音频节奏推进
  系统time:    ────────────────────────────→  几乎重合

暂停恢复/Seek/Rebuffer 后:
  音频clock:  ──────╯           ╰──────→  重新推进，PTS 从新位置开始
  delay:      ... 33, 33,       33, 33, ... 步长重新正常
  frame_timer: ──────╯           ↑
                      这里断了！frame_timer 还蹲在暂停前
                      而系统 time 已经跑出去 5 秒了
  系统time:    ────────────────────────────→  无情地继续走

  → delay 里算出的 diff = video_pts - audio_clock ≈ 0
    （因为视频 PTS 和音频时钟在新位置是对齐的）
  → 但 time - frame_timer = 5000ms
  → 音频矫正的"节拍"是对的，但起跑线歪了 5 秒
```

**这就是 `AV_SYNC_THRESHOLD_MAX` 要修的东西——不是修复音视频同步（那由 `delay` 保证），而是修复 `frame_timer` 这个累计器本身的"起跑线"**。

**第四步：没有重置 vs 有重置，逐行对比**

暂停 5 秒后恢复，音视频 PTS 本身是对齐的（`diff ≈ 0`），`delay` 返回正常 33ms：

```c
// 共同的起点:
time = 5000ms
frame_timer = 165ms  // 还指着暂停前
delay = 33ms         // 音频矫正后正常步长

// ──── 没有重置 ────
frame_timer += delay  → frame_timer = 198ms

// time(5000) - frame_timer(198) = 4802ms，远超 100ms
// → 触发连续丢帧（丢帧条件: time > frame_timer + duration）
// → 下一帧: frame_timer = 231ms，还落后 4769ms → 继续丢
// → 再下一帧: frame_timer = 264ms，还落后 4736ms → 继续丢
// → 要丢掉 4800/33 ≈ 145 帧 才能追上
// → 用户看到 5 秒高速"快进"——而这 145 帧的画面本来就是对齐的，不需要追！

// ──── 有重置 ────
frame_timer += delay  → frame_timer = 165 + 33 = 198ms

if (delay > 0 && time - is->frame_timer > AV_SYNC_THRESHOLD_MAX)
    //  33 > 0 ✓    5000 - 198 = 4802ms > 100ms ✓
    is->frame_timer = time;  // frame_timer = 5000ms ← 拉到"现在"

// 效果: 暂停前的最后一帧被跳过，恢复后的第一帧获得正确的起跑线
//   帧#0: frame_timer = 5000ms，正常渲染
//   帧#1: frame_timer = 5033ms，正常渲染
//   ... 每一帧正常间隔，用户看到"直接从当前位置继续播"
//   不需要丢 145 帧——因为根本没东西需要追
```

关键认识：**这 145 帧不是"该丢的视频帧"，它们是暂停期间本就不该存在的帧。** 没有重置时，播放器误以为它们存在（`frame_timer` 蹲在 165ms → 系统已经 5000ms），于是产生了一场本不该有的疯狂追赶。重置消除了这个虚假的"追赶需求"。

**第五步：条件里为什么有个 `delay > 0`**

```
delay = 0 → 这帧本身已被音频同步逻辑判了"要丢"（video落后audio）→ 不重置
delay > 0 → 这是一帧"要正常显示的帧" → 如果起跑线还歪着，重置

不加这个判断的 bug:
  丢帧循环里 delay=0，frame_timer += 0，每帧都触发 reset
  → frame_timer 被反复设为 time
  → time - frame_timer 永远 = 0
  → 后面的丢帧条件 (time > frame_timer + duration) 永远不触发
  → 真正该丢的落后帧也丢不掉了，全都渲染出来
```

**完整流程图**

```
                          帧到达
                            │
                            ▼
         ┌──── compute_target_delay(duration) ────┐
         │  diff = video_pts - audio_clock         │
         │  diff ≈ 0  → delay = duration (33ms)    │
         │  diff < 0  → delay = 0 (丢帧)           │   ← 音视频同步在此!
         │  diff > 0  → delay = 2*duration (等待)  │
         └────────────────────────────────────────┘
                            │
                            ▼
                    delay > 0 ?
                    /        \
                  YES         NO
                   │           │
                   ▼           ▼
          正常显示这一帧    丢帧 → 取下一帧
          frame_timer += delay
                   │
                   ▼
         time - frame_timer > 100ms ?   ← 检查的是"起跑线歪没歪"
            /              \
          YES               NO
           │                 │
           ▼                 ▼
 frame_timer = time      正常继续
（重置起跑线，不丢帧）   （起跑线没歪，什么也不做）
```

**三种触发场景**

| 场景 | 根本原因 | 为什么 `delay` 救不了 |
|:---|:---|:---|
| **暂停恢复** | 暂停期间渲染循环停止，`frame_timer` 停在旧值，系统时间继续走 | `delay` 里的 diff≈0（AV是对齐的），`delay`=33ms 正常，它不知道起跑线歪了 |
| **Seek 跳转** | Seek 后 decoder flush，新帧 PTS 和音频都跳到新位置，但 `frame_timer` 是旧值 | AV PTS 对齐，但 `frame_timer` 是 seek 前的位置 |
| **网络 rebuffer** | 数据断流期间渲染循环在空转（或阻塞），`frame_timer` 不变，系统时间在走 | 同上——AV PTS 对齐，起跑线歪了 |

三个场景的共同点：**音视频 PTS 本身已经对齐（`delay` 返回正常值），但 `frame_timer` 这个"在系统时间地上的累计步数"和系统时间之间出现了一条巨大鸿沟。** 这条鸿沟不是音视频同步问题，是暂停/跳转造成的人为断层。`AV_SYNC_THRESHOLD_MAX` 就是专门填这条鸿沟的。

**总结一句话**

> `AV_SYNC_THRESHOLD_MAX` 不管音视频同步——那是 `delay` 的活。它管的是一类特殊问题：**音视频已经对齐了，但 `frame_timer` 被暂停/Seek/Rebuffer 甩在了过去**。这种情况下逐帧追赶不仅是浪费（帧本来就不需要丢），更是灾难（145 帧快进）。重置就是一句话：`frame_timer = time` ——过去的帧全部作废，从现在这一帧、这个时刻，重新开始。

#### delay1 公式化总结：三大场景

面试时如果被要求用公式或伪代码精确描述，这样回答最清晰：

$$\text{delay1} = \text{compute\_target\_delay}(\text{delay}, \text{is})$$

其中 $\text{delay} = \text{PTS}_{\text{current}} - \text{PTS}_{\text{last}}$（物理帧间隔），$\text{diff} = \text{Clock}_{\text{video}} - \text{Clock}_{\text{audio}}$（视频时钟与音频时钟的偏差）。

| 场景 | 条件 | `delay1` 取值 | 效果 |
|:---|:---|:---|:---|
| **音画同步** | $\vert\text{diff}\vert < \text{threshold}$ | `delay1 = delay` | 按原帧率正常播放（如 33ms） |
| **视频跑快了** | $\text{diff} \ge \text{threshold}$ | `delay1` 被拉长（最多翻倍或累加 diff） | 视频暂停/卡顿，等音频追上 |
| **视频跑慢了** | $\text{diff} \le -\text{threshold}$ | `delay1` 被压缩（甚至降为 0ms） | 视频快速刷帧或丢帧，追赶音频 |

代码映射：

```c
// compute_target_delay 的三种返回值
static double compute_target_delay(double duration, VideoState *is) {
    double diff = is->video_clock - audio_clock_get(&is->audio_clock);

    if (fabs(diff) < AV_SYNC_THRESHOLD_MIN)      // 场景1: 同步 → delay不变
        return duration;

    if (diff >= AV_SYNC_THRESHOLD_MIN)            // 场景2: 视频超前 → 拉长等待
        return 2 * duration;                      //   delay翻倍

    // diff <= -AV_SYNC_THRESHOLD_MIN             // 场景3: 视频落后 → 压缩追赶
    return 0;                                     //   delay归零（立刻显示下一帧）
}
```

**本质一句话**：FFmpeg 是"音频为主、视频为辅"。音频卡顿断流，视频通过放大 `delay1` 定格等待；音频跳变，视频将 `delay1` 归零加速追赶。

### 2.2 策略二：视频主时钟（Video Master）——几乎不用

**一句话**：视频按自己的节奏播，音频追赶视频。

**为什么几乎不用**：音频不能变速（变速会变调），追不了视频。唯一能做的是**丢音频帧**或**插入静音**——这比丢视频帧影响大得多，一段 20ms 静音人耳立刻察觉。

**唯一会用的场景**：纯音频文件音画同步，或者视频本身就是可变帧率（VFR）且音频不重要（监控）。

不要在这种方案上花太多篇幅——面试一笔带过就行，重点讲音频主时钟。

### 2.3 策略三：外部时钟（External Clock / System Clock）——直播专用

**一句话**：音视频都不当主时钟，两者都同步到系统墙钟。

```
系统时钟:  单调递增，不依赖任何帧
音频：根据系统时钟决定播放速度（必要时可丢样本/插静音）
视频：根据系统时钟决定渲染或丢弃
```

**为什么直播要选这个**：

直播和点播的核心差异在于"时间线的源头是谁"：

```
点播:
  时间线在文件里 → PTS 是写死的 → 音视频对得上就行
  用音频主时钟完全 OK

直播:
  时间线在现实世界里 → PTS 是从采集时刻的墙钟推算的
  没有"正确的 PTS"可以参照——你先收到哪帧不知道
  唯一客观的参照系是系统墙钟
```

**直播的典型场景**：
- 网络抖动导致音频先到视频后到
- 推流端编码器卡了一下，一段视频帧延迟到达
- GOP 内关键帧延迟，后面的帧先到了

这些问题在点播里不存在（数据都在本地），但直播里是常态。外部时钟的方案是：**不管你是哪个流、什么时候到的，按系统时钟来——该你播的时候你没到，就跳过去；你提前到了，就缓冲等一等。**

**ffplay 的外部时钟实现**（`ffplay.c`）：

```c
// 外部时钟：每次取帧时更新时间
static double get_external_clock(VideoState *is)
{
    // 如果暂停了，返回暂停时刻的时钟
    // 否则 = 上次更新的时间 + (当前系统时间 - 上次更新的系统时间) × 速度
    return is->extclk_pts +
           (av_gettime_relative() - is->extclk_serial) / 1000000.0 * is->extclk_speed;
}
```

实质上是一个**以系统墙钟驱动的虚拟时钟**。

### 2.4 三种策略全景对比

```
                    选谁当 Master？
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
    音频 Master      视频 Master      外部/系统 Clock
   （点播首选）      （几乎不用）       （直播首选）
        │                │                │
  音频匀速播放      视频匀速播放      以系统墙钟为准
  视频追赶/等待     音频追赶          音视频都追赶系统时钟
        │                │                │
   追赶手段：        追赶手段：        追赶手段：
   · 视频丢帧       · 音频丢帧        · 音视频都可以丢
```

## 三、时钟系统设计与实现（工程落地）

### 3.1 音频时钟的精确实现

音频时钟不能简单地"拿 PTS"——PTS 是压缩包的起始时间，但你真正要知道的是**PCM 样本已经播放到哪了**。

```c
// 音频时钟的核心数据结构
typedef struct AudioClock {
    // 从 av_gettime_relative() 获取，微秒精度
    int64_t last_updated_sys_time;   // 上次更新时的系统时间(us)

    // 上次更新时，声卡已经播放到这个 PTS(秒)
    double last_pts;

    // 上次更新时，声卡已经播放到的样本位置
    int64_t last_serial;

    // 当前播放速度
    double speed;

    // 是否暂停
    int paused;
} AudioClock;

// 获取当前音频时钟（秒）
double audio_clock_get(AudioClock *ac) {
    if (ac->paused) {
        return ac->last_pts;  // 暂停时时钟不动
    }

    // 核心计算：
    // 当前时钟 = 上次记录的PTS + 从上次记录到现在经过的时间 × 速度
    int64_t now = av_gettime_relative();  // 微秒
    double elapsed = (now - ac->last_updated_sys_time) / 1000000.0;
    return ac->last_pts + elapsed * ac->speed;
}

// 音频回调里更新时钟（每次回调都调）
void audio_clock_update(AudioClock *ac, double pts, int64_t serial) {
    ac->last_pts = pts;                     // 这个 pts 是根据样本数推算的
    ac->last_serial = serial;
    ac->last_updated_sys_time = av_gettime_relative();
}
```

**音频 PTS 的推算**：

```c
// 每次音频回调送数据后，推算当前播放位置
// 假设回调送了 1024 个样本，采样率 48000Hz
// 本次回调覆盖的时间 = 1024 / 48000 = 0.02133 秒 = 21.33ms

void audio_callback(void *userdata, uint8_t *stream, int len) {
    // ... 填充音频数据到 stream ...

    // len 是字节数，换算成样本数
    int samples = len / (channels * av_get_bytes_per_sample(sample_fmt));

    // 换算成时间（秒）
    double duration = (double)samples / sample_rate;

    // 更新时钟
    audio_clock_update(&is->audio_clock,
                       audio_clock_get(&is->audio_clock) + duration,
                       audio_serial);
}
```

**关键细节**：音频时钟的精度取决于两个因素——

1. **回调频率**：回调越频繁，时钟更新越及时。典型回调 buffer 填 512~2048 samples（10~40ms @ 48kHz）。buffer 太大会导致时钟"跳跃式"更新，同步精度下降。
2. **声卡 DMA 位置**：高阶实现会查询声卡硬件 DMA 指针，精确到"已经播放到第几个样本了"。SDL2 的 `SDL_GetAudioDeviceStatus` 和 AudioUnit 的 `mSampleTime` 都支持。

### 3.2 视频帧的显示时间计算

```c
// 计算视频帧应该在什么时候显示
// 不是简单的"PTS - 音频时钟"，还要考虑帧间隔和渲染管线延迟

static double compute_target_delay(double duration, VideoState *is) {
    double sync_threshold, diff = 0;

    // 如果以音频为主时钟
    if (is->av_sync_type == AV_SYNC_AUDIO_MASTER) {
        // diff = 视频帧PTS - 音频主时钟
        // 正 = 视频超前（要等），负 = 视频落后（要追）
        diff = is->video_clock - audio_clock_get(&is->audio_clock);

        // 计算同步阈值
        // 不是固定值！根据帧间隔动态调整
        sync_threshold = FFMAX(AV_SYNC_THRESHOLD_MIN,
                               FFMIN(AV_SYNC_THRESHOLD_MAX, duration));
        // AV_SYNC_THRESHOLD_MIN = 0.01  (10ms)
        // AV_SYNC_THRESHOLD_MAX = 0.1   (100ms)

        if (fabs(diff) < sync_threshold) {
            // 差距在阈值内：认为同步，delay 就是帧间隔
            // 微调一点点让 diff 慢慢归零
            delay = duration;
        } else if (diff < -sync_threshold) {
            // 视频落后：减小 delay，让下一帧早点显示
            delay = 0;  // 甚至是 0——立刻丢当前帧
        } else if (diff > sync_threshold) {
            // 视频超前：增加 delay，多等一下
            delay = 2 * duration;  // 拉长一倍的帧间隔来等音频
        }
    }

    return delay;
}
```

这里的精髓是 `sync_threshold` 不是固定值——它取**帧间隔的某个范围**：最小不低于 10ms（太敏感会频繁微调引入抖动），最大不超过 100ms（差太多直接丢帧不等了）。

### 3.3 无音频流的降级方案

如果视频流没有音轨（比如无声监控视频）：

```c
// 降级到外部时钟
if (!is->audio_st) {
    is->av_sync_type = AV_SYNC_EXTERNAL_CLOCK;
}

// 外部时钟由视频帧自身推进，本质是"按帧率匀速播放"
static void video_refresh_external_clock(VideoState *is) {
    // frame_timer 由每一帧的显示周期累加推进
    // 这就是"按目标帧率匀速播放"
    is->frame_timer += duration;
    // 不依赖任何音频时钟
}
```

## 四、推流端的音视频同步——被忽视的关键

面试大部分人都在讲播放端同步，但**推流端的时间戳打得对，播放端才可能同步**。

### 4.1 推流端时间戳从哪来

```
采集回调触发时刻 → 记录系统墙钟 → 作为这一帧的 PTS

视频:
  camera.onFrameAvailable(timestamp) {
      video_pts = timestamp;  // Camera2 的 Sensor Timestamp，或自己打的 clock_gettime
  }

音频:
  AudioRecord.read(pcm_buffer) {
      audio_pts = last_recorded_time;
      last_recorded_time += pcm_samples / sample_rate;
  }
```

**关键陷阱一：音视频 PTS 必须同源**

```cpp
// 错误：音频和视频各打各的时间戳
// 两个 gettimeofday() 之间的时间差就是误差源

void OnVideoFrame() {
    gettimeofday(&tv, NULL);
    video_pts = tv.tv_sec * 1000000LL + tv.tv_usec;  // 用 realtime
}

void OnAudioFrame() {
    clock_gettime(CLOCK_MONOTONIC, &ts);               // 用 monotonic
    audio_pts = ts.tv_sec * 1000000LL + ts.tv_nsec / 1000;  // 两种时钟不一致！
}

// 正确做法：统一用 CLOCK_MONOTONIC，且启动时记录一个共同 offset
// pub_start_time_ = clock_gettime(CLOCK_MONOTONIC) at stream start
// 所有 PTS = 当前 MONOTONIC - pub_start_time_
// 这样 PTS 都是从 0 开始、用同一时钟源算出的相对时间
```

**关键陷阱二：采集回调的延迟不可忽略**

Android Camera2 的帧回调不是"照到就回调"——中间有 ISP 处理、框架层转发，延迟可能 20~60ms。真正的曝光时刻是 `CaptureResult.SENSOR_TIMESTAMP`，而不是回调触发的时刻。

```
实际场景:
  t=0    光线进入镜头
  t=15ms ISP 处理完
  t=22ms 安卓框架层回调到你的代码
  t=22ms 你用 gettimeofday() 打 PTS  → 差了 22ms！

  t=0    麦克风收到声音
  t=3ms  AudioFlinger 回调过来
  t=3ms  你打了 audio_pts            → 只差 3ms

  视频 PTS 和音频 PTS 已经天生差了 ~19ms
```

解决方案：
- Android：用 Camera2 `SENSOR_TIMESTAMP`（必须用 `clock_gettime(CLOCK_MONOTONIC)` 对齐）
- iOS：用 `AVCaptureVideoDataOutput` 的 `timestamp`（基于 `mach_absolute_time`）
- 兜底：无论如何，用同一个时钟源（`CLOCK_MONOTONIC`）做所有 PTS 计算

### 4.2 推流端的 PTS 校验与修复

成熟的推流端应该有 PTS 校验逻辑：

```cpp
// 推流端 PTS 完整性检查
class PTSValidator {
public:
    enum PTSStatus {
        PTS_OK,
        PTS_GAP,        // PTS 跳变（可能丢帧了）
        PTS_BACKWARD,   // PTS 倒退（帧乱序了）
        PTS_STALL,      // PTS 长时间不推进（编码器卡了）
    };

    PTSStatus FeedVideoPTS(int64_t pts) {
        if (pts < last_video_pts_) {
            // 时间倒退——不可接受，必须修正
            LOG_WARN("Video PTS went backward! %lld -> %lld", last_video_pts_, pts);
            return PTS_BACKWARD;
        }

        int64_t gap = pts - last_video_pts_;
        if (gap > 500) {  // 超过 500ms 的空隙
            LOG_WARN("Video PTS gap detected: %lldms", gap);
            return PTS_GAP;
        }

        if (gap == 0) {
            // 重复 PTS——可能编码器输出了多 slice
            // 需要做 PTS 递增处理
            pts = last_video_pts_ + 1;
        }

        last_video_pts_ = pts;
        // 同时检查 AV 同步
        int64_t av_diff = pts - last_audio_pts_;
        if (abs(av_diff) > 200) {  // 超过 200ms 就要告警
            LOG_WARN("AV PTS drift: %lldms", av_diff);
        }

        return PTS_OK;
    }

private:
    int64_t last_video_pts_ = -1;
    int64_t last_audio_pts_ = -1;
};
```

## 五、AV 同步的经典 Bug 与排查

### 5.1 音视频渐进式漂移（Drift）

**表现**：刚开始同步，播着播着越来越歪，5 分钟后口型完全对不上。

**原因**：

```
音频时钟用 48000Hz 推算 → 实际声卡是 48001Hz（晶振偏差）
视频帧率用 30fps 推算    → 实际显示器可能是 60Hz 刷新

每秒差 1/48000 ≈ 0.02ms → 累积 5 分钟 = 0.02 × 300 = 6ms
表面看不多，但如果同时有采集端 PTS 源不统一的问题
实际误差可能达到几百毫秒
```

**根治方法**：音频时钟不要用"假设的采样率"推算，而是用**声卡已播放样本数的硬件反馈**。AudioUnit（iOS）的 `mSampleTime`、AAudio（Android）的 `getTimestamp()` 都能拿到硬件级别的精确播放位置。

### 5.2 音视频差一个固定偏移（Offset）

**表现**：从第一秒开始就一直差 100ms，始终对不上。

**原因**：采集端音频和视频的"零时刻"定义不一致。

```
场景:
  视频第一帧: 摄像头打开 → 启动预览 → 第一帧到达 = t=200ms → PTS=200ms
  音频第一帧: AudioRecord.startRecording() → 第一帧到达 = t=100ms → PTS=100ms

  结果: 视频 PTS 整体偏移了 100ms，所有帧都晚
```

**修复**：记录一个全局的 `base_pts_offset`，用第一帧音频的 PTS 作为基准，视频 PTS 全部减去偏移。

```cpp
// 初始化: 以第一个到达的帧为时间原点
void OnFirstFrame(AVMediaType type, int64_t raw_pts) {
    if (!base_pts_set_) {
        base_pts_ = raw_pts;
        base_pts_set_ = true;
    }
    int64_t normalized_pts = raw_pts - base_pts_;
    // 两者都减去同一个 base_pts，保证从 0 开始对齐
}
```

### 5.3 丢帧后同步断裂

**表现**：一段 GOP 丢帧后，画面和声音彻底对不上了。

这就是我们之前在 [[核心-直播性能优化]] 里讨论过的问题。**丢视频 GOP 必须同时丢对齐的音频帧**，否则播放端收到的是"缺了一段视频的时间线"，音频时钟领先视频时钟一段距离，永远追不回来。

```
正常:  A0 A1 A2 A3 A4 A5 A6 A7 A8 ...
       V0 V1 V2            V6 V7 V8 ...

丢了 GOP(V3~V5):  音频 PTS 推进到 A6，视频还在 V2
         → 视频落后 ~100ms
         → 播放端疯狂丢视频帧追赶
         → 用户看到"画面快进"或"画面跳变"

正确:
丢了 GOP(V3~V5) + 对齐丢弃 A4~A5:
       A0 A1 A2 A3 -- -- A6 A7 A8 ...
       V0 V1 V2      -- -- V6 V7 V8 ...

         → 短暂静音 + 画面正常
         → 用户感受: 轻微卡了一下，但声画同步
```

### 5.4 暂停/恢复后的同步

**表现**：暂停后再播放，声画错位。

**原因**：暂停期间只有系统时钟在走，音频时钟和视频时钟都停了。恢复后，你怎么把两个时钟"续上"是个问题——如果音频先恢复、视频后恢复，两者之间的间隙就是新的偏移。

**修复**：暂停时记录"暂停了多久"，恢复时统一补偿：

```c
void pause_clock(AudioClock *ac) {
    ac->pause_time = av_gettime_relative();
    ac->paused = 1;
}

void resume_clock(AudioClock *ac) {
    // 把暂停期间的时间加到 last_updated_sys_time 上
    // 这样 audio_clock_get() 不会把暂停时间算进去
    int64_t now = av_gettime_relative();
    int64_t paused_duration = now - ac->pause_time;
    ac->last_updated_sys_time += paused_duration;
    ac->paused = 0;
}
```

## 六、大厂的音视频同步方案

### 6.1 抖音/快手——推流端为主的"一锤子买卖"

短视频录制场景，**推流端搞定同步，播放端几乎不管**。

**做法**：

- 录制时，音频和视频帧的 PTS 全部基于同一个 `mach_absolute_time()` / `clock_gettime(CLOCK_MONOTONIC)` 打出来
- 编码前做一次 **PTS 对齐校验**：如果音视频首帧 PTS 不一致，统一 offset
- 编码器输出后，FFmpeg 的 Muxer（或自研 FLV Muxer）按 PTS 交织
- 写到 FLV/MP4 后，文件中已经包含了正确的、对齐的时间戳

播放端下载这个 FLV/MP4 后，用**标准的音频主时钟方案**就够了，不需要额外做同步。

**为什么这么省事**：短视频是**录制 + 上传 + 播放**的异步链路，时间线完全由录制端决定。录制端打得对，播放端就天然同步。

### 6.2 直播平台（淘宝/抖音直播）——多层同步

直播比短视频复杂得多——是**边采集、边编码、边传输、边播放**的实时链路。

**推流端侧（主播端）**：

```
采集:
  视频: Camera2 SENSOR_TIMESTAMP / AVCaptureDevice timestamp
  音频: AudioRecord 累计样本数 / AudioUnit mSampleTime
      ↓
  两者统一对齐到 CLOCK_MONOTONIC
      ↓
PTS 校验层:
  · 首帧 PTS 对齐: 视频第一帧和音频第一帧的 PTS 必须对齐到同一原点
  · 运行时 drift 监控: 如果 AV PTS diff > 100ms 连续 3 次，触发告警
  · 异常帧丢弃: PTS 倒退的帧直接丢弃，不写入
      ↓
编码:
  视频: MediaCodec 硬编，保留原始 PTS
  音频: MediaCodec AAC，保留原始 PTS
      ↓
发送:
  单线程 Writer + av_interleaved_write_frame
  详见 [[24-音视频同步详解#六、大厂的音视频同步方案]] ← 你就在这
```

**播放端侧（观众端）**：

```
网络接收:
  · Jitter Buffer: 缓存 200~500ms，吸收网络抖动
  · 丢包重传或 FEC 前向纠错
      ↓
解码:
  · 音频和视频独立解码
  · 解码后队列各保持 3~5 帧
      ↓
同步（外部时钟 + 音频辅助）:
  · 主时钟: 系统墙钟（因为直播没有"绝对正确"的 PTS）
  · 显示: 视频 PTS vs 系统时钟 → 追赶/等待
  · 播放: 音频 PTS vs 系统时钟 → 必要时做微量变速（12~25ms 的静音插入/丢弃）
  · 缓冲水位: Jitter Buffer 水位低于阈值 → 减速播放（拉长帧间隔）
```

**直播为什么不用纯粹的音频主时钟**：
- 直播流可能因为弱网、重连等原因，音频可能短暂断流
- 如果音频断了，音频时钟停转，画面也停了——不行
- 所以直播用的是**外部时钟为主，音频时钟为辅**：

```cpp
// 直播场景的混合策略
if (audioStreamHealthy) {
    // 音频正常时，参考音频时钟做同步
    // 但强制限制: diff 不超过 200ms，否则切到系统时钟
    diff = video_pts - audio_clock_get();
    if (fabs(diff) > 200) {
        reference_clock = system_clock_get();  // 切回系统时钟兜底
    }
} else {
    // 音频断了: 纯用系统时钟
    reference_clock = system_clock_get();
}
```

### 6.3 WebRTC —— Audio 驱动 + NTP 同步

WebRTC 用了一套**跨网络的时钟同步方案**——NTP（Network Time Protocol）对齐。

**核心概念**：

```
发送端:
  每一帧 RTP 包带两个时间戳:
    · RTP Timestamp: 采样时钟（音频 48000Hz, 视频 90000Hz）
    · NTP Timestamp: 绝对时间（微秒精度，钟表时间）

接收端:
  用 RTCP SR（Sender Report）里的 NTP-RTP 映射关系，
  推算出每个 RTP 包对应的"发送端真实时间"，
  再对比自己的系统时间，决定播放时机。
```

**WebRTC 的 AudioProcessing 模块内置同步**：
- `SyncBuffer` 维护音视频的对齐状态
- NetEQ（音频抖动缓冲）会根据视频时钟调整自己的目标延迟
- 在 Chrome 里，`HTMLMediaElement` 的 `currentTime` 由音频时钟驱动

### 6.4 大厂方案全景对比

| 场景 | 主时钟 | 同步策略 | 特色技术 |
|:---|:---|:---|:---|
| 抖音录制 | 不需要播放端同步 | 录制端 PTS 同源 | Camera2 SENSOR_TIMESTAMP |
| 直播推流 | 系统墙钟 + 音频辅助 | 外部时钟为主 | Jitter Buffer 自适应 |
| 点播播放 | 音频主时钟 | ffplay 经典算法 | 丢帧追赶 + sleep 等待 |
| WebRTC | NTP 时间 + 音频驱动 | NTP 对齐 + NetEQ | RTCP SR 包做时钟同步 |
| 剪辑/Seek | 音频主时钟 | 重同步 | 全量 demux 建索引 |
| 短视频播放 | 音频主时钟 | 标准 ffplay 算法 | 无特殊处理 |

## 七、车载低延时预览：从 Static Jitter Buffer 到 AJB 架构演进

> 上一章的大厂方案都是"播放已存在的流"——点播文件的音频时钟、直播流的系统时钟，时间线是确定的。但车载 Wi-Fi 图传这类场景不同：**视频帧是实时采集、实时编码、实时传输、实时渲染的，没有"正确的 PTS 文件"可以参照**。延时要求极高（端到端 < 500ms），而网络是抖动的。

### 7.1 场景的特殊性——为什么不能直接套用之前的方案

| 对比维度 | 点播/直播播放器 | 车载实时图传 |
|:---|:---|:---|
| 时间线来源 | 文件里的 PTS（已确定） | 采集瞬间的墙钟（实时生成） |
| 主时钟选择 | 音频时钟或系统时钟 | **无天然主时钟**，需要自建 |
| 核心矛盾 | 音视频之间的对齐 | **端到端延时 vs 播放平滑** 的平衡 |
| 网络特征 | 有缓冲（秒级），偶发抖动 | **持续抖动**，Wi-Fi 干扰、遮挡频繁 |
| 延时要求 | 秒级可接受 | **< 500ms**，否则倒车影像失去意义 |
| 音频 | 必须播放 | 可能不涉及（纯视频预览），或仅用于报警提示音 |

### 7.2 方案 A（Static Jitter Buffer）——首帧锚点 + 固定等待

**做法**：记录首帧 PTS 与首帧到达时的系统时间作为固定锚点，后续每帧的显示时刻 = 锚点 + (当前帧 PTS - 首帧 PTS)。

```
首帧到达: PTS=1000ms, 系统时间=5000ms
  → 锚点: PTS_base=1000ms, Sys_base=5000ms

后续帧: PTS=1033ms
  → 预期系统时间 = Sys_base + (PTS - PTS_base) = 5000 + 33 = 5033ms
  → 如果当前系统时间=5030ms → 等 3ms
  → 如果当前系统时间=5040ms → 已经晚了 7ms，立刻渲染
```

**致命缺陷——延时继承（Latency Inheritance）**：

```
首帧因为某种原因（网络抖动、解码慢）延迟了 1 秒才到:
  首帧: PTS=0ms,  系统时间=6000ms  ← 本该 5000ms 到，晚了 1000ms
  → 锚点: PTS_base=0ms, Sys_base=6000ms

之后所有帧都按照"首帧晚了 1000ms"这个事实来排时间表:
  帧#1: PTS=33ms  → 预期 = 6000 + 33 = 6033ms
  帧#2: PTS=66ms  → 预期 = 6000 + 66 = 6066ms
  ...

首帧卡了 1 秒 → 整个播放链路永久晚 1 秒。
这 1 秒的延时被"固化"进锚点里，永远消不掉。
```

**行业术语**：**Static Jitter Buffer（静态抖动缓冲）** / **Absolute PTS Alignment**。

### 7.3 方案 C（Zero-Buffer）——完全不等，来就渲

**做法**：彻底去掉等待逻辑，解码完成立即渲染。

```
每一帧: Decode → Render Immediately
        waitTime = 0（恒为 0）
```

**优点**：延时最低，理论上接近编解码+传输的物理下限。

**致命缺陷——呼吸效应（Jitter/Breathing）**：

```
网络稳定时:
  帧间隔: 33ms  33ms  33ms  33ms  33ms  → 画面匀速，完美

网络抖动时:
  帧到达间隔: 33ms  50ms  20ms  33ms  47ms  18ms
                   ↑     ↑                 ↑     ↑
                 慢了  快了(追回)         慢了   快了
  渲染出来的帧率: 忽快忽慢 → 画面像在"呼吸"
```

没有缓冲吸收抖动，网络每一微秒的波动都直接体现在画面上。车载场景下 Wi-Fi 穿墙/遮挡频繁，呼吸效应非常明显。

**行业术语**：**Zero-Buffer Mode（零缓冲模式）** / **Render Immediately**。

### 7.4 方案 B（Adaptive Jitter Buffer, AJB）——快升慢降 + 非对称滤波

这是工业界的标准解法。核心思想：**维护一个动态调整的目标缓冲水位，网络抖动大时水位自动升高（吸收更多抖动），网络恢复时水位缓慢下降（逐步逼近最低延时）。**

#### 7.4.1 为什么叫"快升慢降"

```
网络恶化 → 抖动加剧 → 需要更大的缓冲区来吸收抖动 → 水位快速升高（快升）
网络恢复 → 抖动减小 → 可以减少缓冲来降低延时   → 水位缓慢下降（慢降）

"快升"防止卡顿: 宁可瞬间牺牲一点延时，也要保住流畅
"慢降"防止振荡: 如果水位降得太快，下一个抖动来的时候又要升回去
                 → 来回振荡 → 画面反复卡顿
```

这正是**非对称 EMA（Exponential Moving Average）滤波**的设计动机。

#### 7.4.2 核心算法实现

```cpp
// ============ 第一步: 时间轴映射 ============
// 消除发送端和接收端时钟不同步与漂移
// PTS 是发送端的 monotonic 时间，nowMs 是接收端的系统时间
// 用首帧做一次映射，把 PTS 域映射到接收端系统时间域
double expectedMonoMs = queue3BaseMonoMs_ + (sampleTimeMs - queue3BasePtsMs_);

// expectedMonoMs: "按照发送端节奏，这一帧应该在接收端几点显示"
// observedDelayMs: "实际上它现在的系统时间比预期晚了多少"（即当前网络延时）
double observedDelayMs = nowMs - expectedMonoMs;

// ============ 第二步: 非对称 EMA 滤波 ============
double errMs = observedDelayMs - queue3TargetBufferMs_;

if (std::abs(errMs) > kDeadbandMs) {
    // 死区: 小波动不管，防止频繁微调引入抖动

    if (errMs > 0.0) {
        // 【快升】网络恶化: observedDelay > target
        // 用高权重 (0.8) 快速拉高目标水位，防止丢帧卡顿
        queue3TargetBufferMs_ = 0.8 * observedDelayMs + 0.2 * queue3TargetBufferMs_;
    } else {
        // 【慢降】网络恢复: observedDelay < target
        // 用低权重 (0.1~0.2) 缓慢拉低目标水位，逼近最低延时
        double alpha = queue3WarmupFrames_ < 10 ? 0.2 : 0.1;
        //                             启动阶段: 稍快        稳定后: 更慢
        queue3TargetBufferMs_ = alpha * observedDelayMs + (1.0 - alpha) * queue3TargetBufferMs_;
    }
}

// ============ 第三步: 计算等待时间 + 背压追赶 ============
double deadlineMs = expectedMonoMs + queue3TargetBufferMs_ - smoothDeltaMs_;
double waitTimeMs = deadlineMs - nowMs;

// 背压: 如果队列积压还没消掉，强压等待时间，加速消耗积压
if (pendingLeft > 0) {
    waitTimeMs = std::min(waitTimeMs, 2.0);  // 最多等 2ms
}

if (waitTimeMs > 0) {
    sleep(waitTimeMs);  // 还没到显示时刻，等
}
// waitTimeMs <= 0 → 已经晚了 → 立刻渲染（同时这一帧的延时会被 EMA 吸收进水位的升高）
```

#### 7.4.3 水位变化的可视化

```
网络延时 (observedDelay):
  80ms  ┤
  60ms  ┤    ╭╮
  40ms  ┤   ╱  ╲    ╭╮
  20ms  ┤──╱    ╲──╱  ╲──────  ← 一直在抖动
        └────────────────────────→ 时间

目标水位 (targetBufferMs):
  50ms  ┤         ╭────╮
  40ms  ┤        ╱      ╲
  30ms  ┤  ╭────╱        ╲
  20ms  ┤─╱                ╲───  ← 快升(陡坡) 慢降(缓坡)
        └────────────────────────→ 时间

等待时间 (waitTimeMs):
  >0    ┤  ██████      ██████    ← 水位高，等得久（吸收抖动）
  =0    ┤██      ██████      ██  ← 水位低，不等（零缓冲拍到底）
        └────────────────────────→ 时间
```

关键观察：即使水位在 20ms 的低位，只要网络突然抖到 80ms，水位立即（0.8 权重）拉到 ~68ms → 下一帧的等待时间拉长 → 平滑吸收了这次抖动，画面不卡。

### 7.5 方案对比总结

| 维度 | 方案 A（Static JB） | 方案 C（Zero-Buffer） | 方案 B（AJB） |
|:---|:---|:---|:---|
| **行业标准名称** | Static Jitter Buffer / Absolute PTS Alignment | Zero-Buffer Mode / Render Immediately | Adaptive Jitter Buffer / Dynamic Watermark |
| **核心逻辑** | 首帧锚点 + 固定偏移 | 不等，直接渲 | 非对称 EMA + 动态水位 |
| **延时** | 中等但不可控（首帧决定） | 最低 | 自适应（网络好→低，网络差→高） |
| **抗抖动** | 差（固定 buffer 太小不够用、太大浪费延时） | 极差（直接暴露） | 好（快升慢降自适应） |
| **致命缺陷** | **延时继承**：首帧卡 1s → 永久晚 1s | **呼吸效应**：画面忽快忽慢 | 逻辑相对复杂 |
| **适用场景** | 网络极稳定的局域网 | 有线直连、USB 摄像头 | **车载 Wi-Fi 图传**、弱网实时预览 |

## 八、深水区：GPU 渲染打点与音频变速同步

### 8.1 如何精准测量 GPU 渲染耗时

这是面试中体现"你真的做过性能优化"和"你只是看过博客"的分水岭。

**❌ 错误做法：`glDrawArrays` / `glDrawElements` 前后 CPU 打点**

```cpp
// 这样打点得到的是假数据
clock_gettime(CLOCK_MONOTONIC, &start);
glDrawArrays(GL_TRIANGLES, 0, count);   // 几乎立刻返回！
clock_gettime(CLOCK_MONOTONIC, &end);
// 耗时可能显示 0.02ms——但这只是 CPU 把命令塞进命令缓冲区的耗时
// GPU 实际渲染可能花了 10ms
```

**为什么不行**：GPU 采用 **TBDR（Tile-Based Deferred Rendering）异步架构**。CPU 调用 `glDrawArrays` 时只是把渲染命令写入命令缓冲区（Command Buffer），GPU 在后台异步执行。CPU 打点只能测到"写命令"的耗时，完全测不到 GPU 真正执行的耗时。

**✅ 正确方案（分三个精度等级）**

| 精度等级 | 方法 | 原理 | 适用场景 |
|:---|:---|:---|:---|
| **粗粒度（快速排除）** | 测量包含 `eglSwapBuffers` 的帧边界耗时 | SwapBuffers 会阻塞等 GPU 完成当前帧（含 VSYNC），给出了 GPU 执行时间上界 | 快速定位"是不是 GPU 的问题" |
| **精细度（精确定位）** | GPU 时间戳查询（Timer Query） | 在 GPU 命令流里插入时间戳标记，GPU 自己记录执行到标记点时的硬件时钟 | 定位具体是哪个 DrawCall/Pass 耗时 |
| **系统级（全局视图）** | Android FrameMetrics API / `dumpsys gfxinfo` / Xcode Metal System Trace | 系统层统计整帧各阶段耗时（输入、动画、测量、布局、绘制、GPU） | 区分"自己的代码"和"系统开销" |

**精细度方案——GPU Timer Query 示例**：

```cpp
// OpenGL ES: GL_EXT_disjoint_timer_query
GLuint queries[2];
glGenQueriesEXT(2, queries);

glQueryCounterEXT(queries[0], GL_TIMESTAMP_EXT);  // 记录 GPU 起始时刻
glDrawArrays(GL_TRIANGLES, 0, count);              // 要测量的渲染命令
glQueryCounterEXT(queries[1], GL_TIMESTAMP_EXT);  // 记录 GPU 结束时刻

// ... 等几帧让 GPU 执行完 ...

GLuint64 startTime, endTime;
glGetQueryObjectui64vEXT(queries[0], GL_QUERY_RESULT_64, &startTime);
glGetQueryObjectui64vEXT(queries[1], GL_QUERY_RESULT_64, &endTime);

double gpuTimeMs = (endTime - startTime) / 1000000.0;  // GPU 真实耗时
```

```swift
// Metal: MTLCommandBuffer 的 GPUStartTime / GPUEndTime
commandBuffer.addCompletedHandler { buf in
    let gpuStart = buf.gpuStartTime   // GPU 开始执行的时间
    let gpuEnd   = buf.gpuEndTime     // GPU 执行完成的时间
    let gpuTime  = gpuEnd - gpuStart  // GPU 真实耗时
}
```

**面试时的标准回答**：

> "测 GPU 耗时不能直接在 `glDrawArrays` 前后打 CPU 时间戳——GPU 是异步执行的，CPU 打点只能测到命令提交耗时。正确的做法分三级：粗粒度用 `eglSwapBuffers` 前后的帧边界耗时（含 VSYNC，给出上界），精细度用 GPU Timer Query（`GL_EXT_disjoint_timer_query` 的 `glQueryCounter`，或 Metal 的 `GPUStartTime`/`GPUEndTime`），系统级用 Android FrameMetrics API 或 Xcode Metal System Trace 做全局分析。"

### 8.2 实时预览中开启音频的同步与变速策略

车载场景中以视频预览为主，但如果有音频（比如倒车雷达报警音、导航提示），音频和视频延时不同步会非常违和。而且视频 AJB 在追赶时会快速丢帧/加速——如果音频不变，立刻音画撕裂。

**问题一：视频追赶时音频怎么办**

视频 AJB 降水位时，积压的视频帧被快速消耗——相当于视频突然加速（从 30fps 暂态到 50fps+）。音频如果仍按正常速度播放，就形成音画不同步。

**解法：切换 Master + 音频变速不变调**

```
原来:  音频 Master → 视频追音频
现在:  视频 AJB 的水位作为虚拟 Master → 音频追视频 AJB
```

当视频 AJB 追赶（快速消耗积压）时，音频也要同步加速。但**音频绝对不能直接丢帧**：

```
直接丢音频帧（20ms 的 PCM）:
  → 波形在丢弃点断裂 → 相位不连续 → 听到"咔哒"一声爆音（Pop/Click）
  → 丢多了变成"嘎嘎嘎"的断续声
```

正确的做法是**变速不变调（Time-Scale Modification, TSM）**：

```
WSOLA（Waveform Similarity Overlap-Add）算法:
  把音频切成小块（如 20ms 帧）
  在相邻块的重叠区域找波形最相似的位置做拼接
  通过调整块与块之间的步进距离来改变速度
  但不改变每个块的基频 → 变快但不变调
```

**工程落地**：集成轻量级音频变速库（如 Android 平台的 Sonic 库，或 iOS 的 AVAudioUnitVarispeed），在视频追赶时将音频动态加速至 1.05× ~ 1.15× 播放。人在这个范围内基本感知不到变调。

```cpp
// 视频追赶时: 音频微加速，无感追回
if (videoIsCatchingUp) {
    sonicSetSpeed(sonicStream, 1.10);  // 10% 加速，基本无感
} else {
    sonicSetSpeed(sonicStream, 1.0);   // 正常速度
}
```

**问题二：断流恢复时的边缘处理**

网络断流几秒，音频静默。恢复时如果第一帧音频突然从正常波形开始播放，听到的是一个突然的"波"——断点处波形从 0 跳到高幅值 → 爆音。

**解法：淡入淡出（Fade-in/out）**

```cpp
// 断流恢复时，对音频帧前端做 5~10ms 淡入
void ApplyFadeIn(float* samples, int sampleCount, int fadeSamples) {
    for (int i = 0; i < fadeSamples && i < sampleCount; i++) {
        float gain = (float)i / fadeSamples;  // 0.0 → 1.0
        samples[i] *= gain;
    }
}

// 断流前对最后几帧做 5ms 淡出
void ApplyFadeOut(float* samples, int sampleCount, int fadeSamples) {
    int start = sampleCount - fadeSamples;
    for (int i = start; i < sampleCount; i++) {
        float gain = (float)(sampleCount - i) / fadeSamples;  // 1.0 → 0.0
        samples[i] *= gain;
    }
}
```

5~10ms 的淡入淡出窗口人耳几乎感知不到，但完全消除了 Pop 爆音。

## 九、面试高频追问与回答

### Q1：为什么音视频同步选音频做主时钟，而不是视频？

> "三个原因。第一，**声卡有硬件 DMA**，音频播放是匀速的、不可变的——你不能让声卡快进慢放，变调人耳立刻察觉。视频没有这个约束，丢一帧跳过一帧，用户几乎无感。
>
> 第二，**人对音频敏感度远超视频**。几十毫秒的音频断续能被察觉，但视频卡一下、跳一帧经常被忽略。
>
> 第三，**工程上的稳定性**。音频回调是硬件触发的、周期精准，误差通常在微秒级。GPU 渲染看负载，时间波动在毫秒级。拿一个不稳定的时钟当 master 会让整个系统抖起来。"

### Q2：ffplay 的音视频同步代码你看过吗？核心逻辑是什么？

> "看过，核心在 `ffplay.c` 的 `video_refresh()` 函数。它用的是经典的**音频主时钟方案**。
>
> 核心流程：获取视频帧 PTS → 获取音频时钟（= 已播放样本数 / 采样率 + 上次记录的系统时间差值）→ 算 `diff = video_pts - audio_clock`。如果 diff < `-sync_threshold`（视频落后）：`frame_queue_next()` 丢帧。如果 diff > `sync_threshold`（视频超前）：延长 `delay`，sleep 等待。sync_threshold 不是固定值，是 `FFMAX(10ms, FFMIN(100ms, 帧间隔))`，保证自适应。
>
> 还有一个细节：如果视频落后太多（超过 100ms），会触发**连续丢帧**——丢完一帧看下一帧还落后，继续丢，直到追上为止。这就是为什么播放器处理卡顿时你会看到画面"快进"——它其实是在疯狂丢帧追赶音频。"

### Q3：如果视频帧率不固定（VFR），同步怎么做？

> "VFR 下每一帧的间隔都不固定，不能假设帧间隔为 33ms。解决方案是用**真实的 PTS 差值**替代公式计算。
>
> 具体说：拿下一帧的真实 PTS 减去当前帧的真实 PTS = 这一帧应该显示多久。这个值可能在 10ms~100ms 不等。同步逻辑不变，只是 `duration` 的来源从 `1/fps` 公式变成了 '查表/算差值'。ffplay 在 VFR 模式下也是这么做的——`vp_duration()` 函数会判断 `frame->duration` 是否存在，存在则直接用，不存在才用帧间隔推算。
>
> 更多 VFR 的内容看 [[22-VFR与CFR详解]]。"

### Q4：直播推流怎么保证音视频同步？

> "分两段讲：推流端和播放端。
>
> **推流端**要保证音视频 PTS 从同一时钟源产生。关键三点：第一，统一用 `CLOCK_MONOTONIC` 打时间戳，绝不混用 `gettimeofday` 和 `clock_gettime`。第二，视频 PTS 必须用 Camera 的 SENSOR_TIMESTAMP 而不是回调触发时刻，消除框架转发延迟。第三，启动时设一个共同的 `base_pts`，所有帧 PTS 都减去它，保证从 0 对齐。
>
> **播放端**用外部时钟为主、音频时钟为辅的混合策略。直播流的 PTS 在推流端已经打过，但不是绝对可靠的（网络可能存在乱序、延迟），所以主时钟设为系统墙钟。音频时钟作为辅助：音频正常就参考音频节奏，音频断了切回系统时钟兜底。Jitter Buffer 维持 200~500ms 延迟，吸收网络抖动。"

### Q5：你工作中遇到过的音画不同步问题，怎么排查的？

> 这是一个开放题，你挑自己最熟悉的讲。推荐的回答路线：
>
> "我遇到过一个很典型的问题：推流端推出去的流，用 ffplay 播放发现声画差 150ms 左右，而且是从第一秒就偏——不是渐进漂移，是固定偏移。
>
> 排查过程：先排除播放端的问题——用同一份流在 ffplay、VLC、ExoPlayer 上播放，都偏，说明问题在推流端。接着排查时间戳来源——发现音频 PTS 用的 `gettimeofday` 从 `AudioRecord.read()` 结束处打的，视频 PTS 用的是 Camera2 的 `onFrameAvailable` 回调触发时刻打的。两个完全不同的时间基准——音频早 150ms 开始记录。最后加了统一的 `CLOCK_MONOTONIC` 基准和 `base_pts_offset`，问题解决。
>
> 这个问题给我的教训是：推流端的 PTS 源头统一是最基本也是最容易被忽略的事。"

### Q6：音视频同步的精度能做到多少？人眼的察觉阈值是多少？

> "人眼对声画同步的感知阈值大约是 **+45ms（音频超前）到 -125ms（视频超前）**。注意这个阈值是**不对称的**——人能更容忍视频超前（声音还没到，画面先到了），不能容忍音频超前（先听到声音再看到画面）。你想想现实中，声音比光慢是常识（打雷先看到闪电再听到声音），但光比声音慢就很诡异。
>
> 工程上，优秀播放器的同步精度控制在 **±20ms** 以内，直播因为实时性要求可以放宽到 **±50ms**。再往上到 ±100ms 以上，多数用户能察觉到口型对不上。带蓝牙耳机时还要额外补偿蓝牙的传输延迟（通常 100~250ms），这个要用操作系统的音频延迟 API 拿到精确值做补偿。"

### 8.1 音频时钟

```c
double audio_clock_get(AudioClock *ac) {
    if (ac->paused) return ac->last_pts;
    int64_t now = av_gettime_relative();
    double elapsed = (now - ac->last_updated_sys_time) / 1000000.0;
    return ac->last_pts + elapsed * ac->speed;
```

### 8.2 视频同步到音频

```c
void video_sync(AVFrame *video_frame) {
    double video_pts = video_frame->pts * video_time_base;  // 秒
    double audio_clock = audio_clock_get(&ac);
    double diff = video_pts - audio_clock;

    double threshold = 0.02;  // 20ms

    if (diff < -threshold) {
        // 视频落后: 丢帧追赶
        av_frame_free(&video_frame);
        return;  // 这个帧不渲染了
    } else if (diff > threshold) {
        // 视频超前: 精确 sleep
        int sleep_us = (int)((diff - threshold) * 1000000);
        usleep(sleep_us);
    }
    // 在阈值内: 正常渲染
    render_frame(video_frame);
}
```

### 8.3 推流端 PTS 产生

```cpp
// 推流端: 绝对不要这样做！
// ❌ 音频用 gettimeofday, 视频用 clock_gettime → 两个时钟源，天生不同步

// ✅ 统一方案
class PTSGenerator {
    int64_t base_time_us_;  // CLOCK_MONOTONIC at stream start

public:
    void Start() {
        struct timespec ts;
        clock_gettime(CLOCK_MONOTONIC, &ts);
        base_time_us_ = ts.tv_sec * 1000000LL + ts.tv_nsec / 1000;
    }

    int64_t GetPTS() {
        struct timespec ts;
        clock_gettime(CLOCK_MONOTONIC, &ts);
        int64_t now_us = ts.tv_sec * 1000000LL + ts.tv_nsec / 1000;
        return now_us - base_time_us_;  // 从 0 开始的微秒级 PTS
    }
};

// 音频和视频帧都用同一个 PTSGenerator::GetPTS() 打时间戳
```

## 九、总结与记忆口诀

**面试核心三句话**：

1. **播放端**：音频做主时钟（声卡硬件驱动，稳定匀速），视频追音频（差太多丢帧、差一点 sleep、刚好播）

2. **推流端**：所有 PTS 出自同一时钟源（`CLOCK_MONOTONIC`），首帧对齐，运行时校验 drift

3. **直播加一层**：外部时钟兜底（音频不稳定时切系统时钟），Jitter Buffer 吸收抖动

**速记口诀**：

> 音频为主不可变，
> 视频追赶丢或等。
> 推流 PTS 要同源，
> 直播还需墙钟稳。
