## 二、核心问题详解

### 2.1 面试官说"介绍一下 H.264"，怎么回答？

这是面试最高频的"第一题"，也是道开放题——面试官其实在考察你**能不能把一个技术讲清楚**，而不是在考你背概念。所以不要像背书一样念定义，要用"为什么"串出一条逻辑链。整体节奏：**先一句话定调 → 然后解释"为什么能压这么小"（拉开差距的地方）→ 挑两三个亮点深入 → 最后收一下、点出局限和大局观**。控制 3-5 分钟，看面试官反应随时调整。

---

**第一层：一句话定调（上来就要脱口而出，不用想）**

"H.264 也叫 AVC或MPEG-4。它是目前部署最广的视频编码标准——你日常看到的蓝光碟、网页视频、手机录像、直播推流、WebRTC 视频通话、监控探头，底层大概率都是 H.264。它不一定是压缩率最高的，但一定是兼容性最好的，哪都能用。"

这一层的要点就一个：**告诉面试官你知道这东西是什么、为什么重要**。一句话就够了，不要展开。

---

**第二层：讲原理——"为什么 H.264 能把视频压那么小？"（这是拉开差距的地方）**

面试官听完第一层大概率会点头，然后等你往下说。这时候你主动把话题引到原理上——**不要等他问"为什么"，你自己接上去**。可以这么说：

"那它为什么能把视频压这么小呢？其实 H.264 的思路说起来也简单，就是想办法消除视频里天然存在的四种冗余。

第一种是**空间冗余**。你想啊，一帧画面里，相邻的像素是不是颜色都差不多？天空一片蓝，墙壁一片白——这些像素之间是有规律的，没必要每个都独立存一遍。H.264 的做法叫帧内预测：编码当前这个 16×16（大块：16，小块3，中快8） 的宏块的时候，先看看它周围已经编好的块长什么样，猜一个方向往外推，然后只存预测值和实际值之间的差值，也就是残差。这样一来数据量就小多了。对比一下 JPEG 就清楚了——JPEG 是把画面切成 8×8 的块，每个块关起门来自己做 DCT 变换、量化、熵编码，块和块之间没有任何交流。这就导致一个问题：就算左边那块和当前这块颜色几乎一样，JPEG 还是会把当前块完完整整再编一遍，因为它根本不知道左边那块长什么样。H.264 的 I 帧不一样——它编码当前块的时候，会先偷看周围已经编好的块（左边、上边、左上角这些），沿着某个方向把像素值外推过来当预测值，然后只编实际值和预测值之间的差值。因为相邻块通常很相似，这个差值非常小，编起来就省很多 bit。所以同样是"帧内编码"，H.264 的 I 帧比 JPEG 高效得多——这就是帧内预测的价值。

第二种是**时间冗余**。这才是视频压缩的大头。相邻两帧画面，大部分内容其实没变——背景不动，只有人在动。那为什么要每帧都完整编一遍？H.264 的做法叫帧间预测加运动估计：编码当前帧的时候，去前面的参考帧里搜，找最像的那个块在哪，然后只记两样东西——
* 运动矢量，就是'这个块往右移了 5 个像素，往下移了 3 个像素'；
* 加上残差，就是挪过去之后还差的那一点点。这个思路是视频压缩率比图片序列高一个数量级的根本原因，也是 P 帧和 B 帧为什么比 I 帧小那么多的底层逻辑。

第三种是**视觉冗余**。人眼对亮度敏感，对色度迟钝；对低频的平滑区域敏感，对高频的细节纹理迟钝。那高频信息就可以丢一些，反正人眼也不容易察觉。H.264 的做法是先把残差做整数 DCT 变换——变换本身不丢信息啊，它只是把像素能量从空间域搬到频率域，能量会集中在左上角那几个低频系数上。然后到了量化这一步，用一个量化参数 QP 把高频系数狠狠除一下、很多直接变零了。**整个编码链路里，质量损失就只发生在量化这一步**，前面预测和变换都是无损的。所以我们调 CRF、调 QP，本质就是在调量化的粗细——QP 越大、量化越粗、丢得越多、画质越差但码率越低。

> **💡 补充：高频/低频、QP、CRF 到底是什么？**
>
> 这几个概念面试经常被追问，单独捋一下：
>
> **高频 vs 低频——拿一张照片来想**
>
> 你可以把图像想象成由不同"变化速度"的波形叠起来的。低频就是画面里变化慢的部分——大块大块的蓝天、墙面、皮肤，像素值和邻居差别很小，变化平缓。高频就是变化快的部分——草地的纹理、树叶的边缘、毛衣的纹路、人的头发丝，像素值在很小范围内剧烈跳变。
>
> DCT 变换做的事情，就是把你眼前这块 4×4 或 8×8 的像素，分解成一系列"基底图案"的加权和。左上角的系数对应那种整块一个色、没什么变化的基底——这是低频；越往右下角，基底图案的条纹越密、变化越快——这就是高频。变换完之后，能量通常全堆在左上角低频区，右下角高频区一片接近零的小数字。所以你一眼就能看出哪些信息重要、哪些可以丢。
>
> 为什么人眼对高频不敏感？你试试看：盯着一张人脸照片，如果我把皮肤磨皮磨得很光滑（丢高频），你看着觉得"嗯挺好看的"；但如果我把整张脸的亮度整体调暗一大截（动了低频），你马上就觉得不对劲。这就是量化敢对高频下狠手的底气。
>
> **QP——量化参数，最底层的旋钮**
>
> QP 全称 Quantization Parameter，一个整数，通常范围 0~51。它直接控制量化步长：QP 每增加 6，量化步长翻一倍。QP=0 的时候基本无损（步长极小，系数几乎原样保留），QP=51 的时候步长最大，大部分系数都被除成零了。所以 QP 越小画质越好码率越高，QP 越大画质越差码率越低。
>
> 你可以把 QP 理解为"一刀切"的参数——编码器里每个宏块用的都是这个 QP（或者在这个 QP 附近微调），简单粗暴。早期编码器调画质就是直接设 QP。
>
> **CRF——恒定质量因子，比 QP 更聪明的选择**
>
> CRF 全称 Constant Rate Factor，是 x264/x265 里最常用的画质控制方式。它解决的问题是：QP 一刀切太笨了——高速运动的画面需要更多码率才能维持同样画质，静态画面不需要那么多。CRF 的思路是"**保持画质恒定，码率随内容浮动**"：编码器会动态调整每一帧、甚至每个宏块的 QP——人眼敏感的场景给多点 bit（降 QP），人眼不敏感的场景（高速运动、暗场）就省点 bit（升 QP）。
>
> CRF 取值范围 0~51，**值越小画质越好、文件越大**。常用值：x264 默认 CRF 23（一般认为视觉无损的分界线），18 左右接近视觉无损，28 以上画质开始明显下降。注意：CRF 不跨编码器可比——x265 默认 CRF 28，和 x264 的 CRF 23 画质差不多，因为 H.265 编码效率本身就高。面试说"CRF 23 画质好"一定要带上前缀"在 x264 下"。
>
> 简单记：**QP 是直接调量化步长，一刀切；CRF 是调"恒定画质"目标，QP 由编码器自动帮你调。** 实际项目里 99% 的场景用 CRF，只有做码控分析或者调试时才手动设 QP。

第四种是**统计冗余**。前面几步已经把数据量砍下来了，但剩下的符号里还是有不均匀的——有些符号出现概率高、有些低。那就用熵编码再压一道：高频符号给短码、低频给长码，类似霍夫曼编码的思路。H.264 有两套方案：Baseline 用 CAVLC，就是上下文自适应的变长码，简单快；Main 和 High 用 CABAC，上下文自适应的算术编码，压缩率能再高 10% 到 15%，就是计算量大不少。

所以整体流水线走下来就是：**预测去冗余 → 算残差 → DCT 变换把能量集中 → 量化丢高频（这步有损）→ 熵编码再压一把 → 输出码流**。解码端倒着来，中间多一步去块滤波——因为分块编码在块边界会有马赛克效应，编码器在重建帧上先滤波再拿去当参考帧，这样后续帧预测更准。这就是所谓的环路滤波，in-loop 的意思就是它在编解码环路里面、会影响参考帧，不是显示时才做的后处理。"

这一层是整段回答里最能拉开差距的地方。要点就一个：**不要只报菜名，要解释"为什么"**——为什么有帧内预测？因为相邻像素相似。为什么有运动估计？因为相邻帧大部分没变。为什么有量化？因为人眼对高频不敏感。

### 2.2 视频防抖（EIS）中，帧与 IMU 数据是怎样对齐的？时间单位选什么？

#### 核心问题

IMU（陀螺仪+加速度计）采样率 100~800Hz（手机常见 200Hz），视频帧率只有 24/30/60fps。每帧曝光周期内包含了 6~7 个 IMU 采样点。对齐就是把"高频物理运动读数"和"低频画面帧"在时间轴上进行配对。

```text
视频帧:  ████████████████████████████████        ← 30fps → 每 33.33ms 一帧
IMU:     |||||||||||||||||||||||||||||||||||||||  ← 200Hz → 每 5ms 一个采样
```

#### 时间单位：推荐 ns，至少 μs，绝不能用 ms

`ms` 精度不够，直接算一下——200Hz 的 IMU 邻点间隔 5ms，1ms 的时间戳误差意味着积分时 **20% 的时间增量不确定**。帧率还会抖动（28ms、35ms、50ms 都常见），`ms` 取整直接丢掉这一信息。

| 平台 | API | 精度 |
|------|-----|------|
| Android | `SystemClock.elapsedRealtimeNanos()` / `SensorEvent.timestamp` | **ns** |
| iOS | `CMTime`（`value/timescale`） | **ns** 级 |
| FFmpeg | `AVFrame.pts × time_base`（常用 1/90000） | **~11μs**，够用 |

#### 帧的时间戳取哪个瞬间？

一帧不是瞬间产生的——它有曝光时间。IMU 必须对齐**曝光中心时刻**，不是 App 回调时刻（后者天然延迟 1~2 帧）。

```
[曝光开始] ──曝光时长──> [曝光结束] ──Readout──> [回调到 App]
     ↑                          ↑
  曝光中心                    不要用这个!
  (IMU 对齐目标)
```

- Android：`CaptureResult.SENSOR_TIMESTAMP` + 曝光时长/2 → `ns`
- iOS：`AVCaptureSynchronizedSampleBufferData.timestamp` → `CMTime`

#### 对齐方法：窗口积分（推荐）

找到帧曝光窗口内的**全部 IMU 采样点**，对陀螺仪角速度做积分得到该帧的相机姿态：

```
Δθ = ∫ 陀螺仪角速度(t) dt   →  梯形/Simpson 数值积分
```

为什么只用陀螺仪不用加速度计？加速度计要**二次积分**才得到位移（`Δx = ∫∫ a dt²`），噪声随时间平方增长，0.5 秒就偏到几十 cm——EIS 基本只做旋转补偿（3-DoF）。

其他策略：最近邻（取最近的单个 IMU 点，简单但噪声敏感）、插值（取前后两点线性插，折中方案）。

#### 完整流程（6 步）

```
① 统一时钟域（Android: elapsedRealtimeNanos vs BOOTTIME 有固定偏移，必须对齐）
② 每帧取曝光中心 t，窗口 = [t - 曝光时长/2, t + 曝光时长/2]
③ 对窗口内 IMU 点做积分 → 帧姿态
④ 帧间差分 → Δ姿态（相机晃动）
⑤ 低通/Kalman 滤波 → 分离"运镜"和"抖动"
⑥ 反向补偿 → 旋转/裁切画面 → 稳后输出
```

#### 一句收口

> 帧与 IMU 对齐：每帧取**曝光中心（ns 精度）**，对曝光窗口内的**陀螺仪采样点做积分**求姿态，帧间差分后**低通滤波分离抖动**，反向补偿输出。ms 不够——200Hz IMU 下邻点 5ms、1ms 误差 = 20% 积分不确定性。

### 2.3 MediaCodec 解码到渲染全链路（Android 硬解上屏实战）

这是 Android 音视频岗**几乎必问**的一道题。先给结论，面试时开口就能用——

> "MediaCodec 解码到渲染，生产环境走 **OpenGL ES + SurfaceTexture 零拷贝**：解码器把 gralloc buffer 通过 BufferQueue 推到 SurfaceTexture，GL 线程 `updateTexImage()` 把这块 dma-buf 内存直接绑定为 OES 外部纹理，全程数据不下 CPU。然后在 fragment shader 里做 YUV→RGB 转换、叠加滤镜/美颜/水印，最后 `glDrawArrays` 渲染上屏。整条链路的核心是 **gralloc → dma-buf fd → EGLImage → OES 纹理** 这一套零拷贝四步——解码画面从硬件解码器到 GL shader 采样，始终是同一块 GPU 内存。"

下面把这段话拆开，逐层讲透。

---

#### 2.3.0 先建全局心智模型

```
压缩码流 (Annex-B H.264)
       │
       ▼
┌──────────────────────────────────────────────┐
│              MediaCodec 解码器                │
│  configure(format, surface, null, 0)          │
│  queueInputBuffer / dequeueOutputBuffer       │
│  releaseOutputBuffer(idx, true) → 推进渲染     │
└──────────────────┬───────────────────────────┘
                   │
       ┌───────────┴────────────┐
       │  SurfaceTexture        │
       │  (BufferQueue 消费者)   │
       │  updateTexImage()      │──── ① acquireBuffer 拿 gralloc handle
       │                        │──── ② eglCreateImageKHR(fd) → EGLImage
       │                        │──── ③ glEGLImageTargetTexture2DOES → OES 纹理
       └───────────┬────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│           OpenGL ES 渲染管线                  │
│                                               │
│   Vertex Shader → 全屏四边形 (两个三角形)       │
│   Fragment Shader:                             │
│     samplerExternalOES → 采样 OES 纹理 (NV12) │
│     YUV→RGB 矩阵变换                           │
│     + 滤镜 LUT / 美颜 blur / 水印叠加          │
│                                               │
│   输出 → EGL Surface (屏幕) 或 FBO (编码输入)   │
└──────────────────────────────────────────────┘
```

整条链路**只有两个跨线程同步点**，没有一次 CPU memcpy：

| 环节 | 传递的是什么 | 物理上发生什么 |
|------|------------|--------------|
| 解码器 → SurfaceTexture | gralloc buffer 的 **dma-buf fd**（文件描述符） | BufferQueue::queueBuffer → 原子地把 fd 所有权交给消费者 |
| SurfaceTexture → OES 纹理 | **EGLImage**（内核 dma-buf 的 EGL 包装） | `eglCreateImageKHR(fd)` → `glEGLImageTargetTexture2DOES` → 纹理直接指向 fd 对应的 GPU 内存页 |
| OES 纹理 → GL shader | GPU 纹理采样器直接读 | GPU 内存控制器走 dma-buf 页表映射，物理上零拷贝 |

---

#### 2.3.1 零拷贝的底层机制（面试深水区，拉开差距的地方）

在写代码之前，必须先把"零拷贝到底怎么零的"讲清楚——这是高级岗和中级岗的分水岭。中级能说"SurfaceTexture 零拷贝"，高级能说"**gralloc → dma-buf → EGLImage → OES 纹理，这四步每一步传的都是 fd、不是数据**"。

##### 第一步：gralloc —— 解码器输出写到哪里

Android 上所有 GPU 相关内存都由 **gralloc**（Graphics Allocator）管理。MediaCodec 硬件解码器不分配 `malloc` 堆内存来存解码画面——它向 gralloc 申请一块 **NV12 格式的图形缓冲区**（通常 128 字节对齐），gralloc 返回一个 `buffer_handle_t`：

```
gralloc buffer 的结构（一块 NV12 YUV 帧，1080p）：

  Y 平面: stride=2048, height=1088 (=sliceHeight, 对齐到 16 的倍数)
  UV 平面: stride=2048, height=544  (半高)
  物理上是一整块连续 GPU 内存，可能有 tiled/swizzled 排布
```

这块内存的排布对 CPU 不友好（tiled、对齐到奇怪边界），但对 GPU 纹理采样器是**最优布局**——这就是为什么 ByteBuffer 路径会花屏而 Surface 路径不会。

##### 第二步：dma-buf —— 怎么让 GL 驱动也访问同一块内存

gralloc buffer 底层是一个 **dma-buf**（内核的 `DMA-BUF` 子系统）。每块 gralloc buffer 在 `/dev/dma_heap` 或厂商私有 heap 上有一个对应的 **文件描述符（fd）**。

关键性质：**dma-buf fd 可以跨进程、跨驱动传递**——解码器进程拿到 fd、把 fd 通过 Binder 发给 SurfaceFlinger 或你的应用进程、接收方通过同一个 fd 就能访问同一块物理内存。传递的是 fd（4 字节整数），不是 memcpy 几百 KB 的像素数据。

```
解码器进程                      你的应用进程 (GL 线程)
    │                                  │
    │  queueBuffer(fd=42)              │
    │ ───────Binder──────►             │ acquireBuffer → fd=42
    │                                  │
    │  ★ 传的是 int fd=42,            │
    │     不是 1920×1080×1.5 字节数据  │
```

##### 第三步：EGLImage —— 把 dma-buf 包装成 EGL 能理解的对象

GL 驱动不认识裸的 dma-buf fd，需要一个中间层来转换。`EGLImageKHR` 就是这个转换器：

```c
// 这是在 SurfaceTexture.updateTexImage() 内部发生的事情（C 层）
EGLint attrs[] = {
    EGL_WIDTH,              1920,
    EGL_HEIGHT,             1080,
    EGL_LINUX_DRM_FOURCC_EXT, DRM_FORMAT_NV12,  // ★ 告诉 EGL 这是 NV12
    EGL_DMA_BUF_PLANE0_FD_EXT,  dma_buf_fd,      // ★ Y 平面 fd
    EGL_DMA_BUF_PLANE0_OFFSET_EXT, 0,             //    Y 起始偏移
    EGL_DMA_BUF_PLANE0_PITCH_EXT, 2048,           //    Y row stride
    EGL_DMA_BUF_PLANE1_FD_EXT,  dma_buf_fd,      // ★ UV 平面 fd（同一块 buffer）
    EGL_DMA_BUF_PLANE1_OFFSET_EXT, 2048*1088,     //    UV 起始偏移
    EGL_DMA_BUF_PLANE1_PITCH_EXT, 2048,           //    UV row stride
    EGL_NONE
};

EGLImageKHR eglImage = eglCreateImageKHR(
    eglDisplay, EGL_NO_CONTEXT,
    EGL_LINUX_DMA_BUF_EXT,    // ★ 关键：直接包装 dma-buf
    NULL, attrs
);
```

`eglCreateImageKHR` 做的事情：在内核的 DRM（Direct Rendering Manager）子系统中，为这个 dma-buf fd 建立一个 GPU 页表映射——**不复制数据，只是让 GPU 的内存管理单元（MMU）知道"虚拟地址 X → 物理页 Y"**。

##### 第四步：GL OES 纹理 —— 让 GL shader 能直接采样

```c
// SurfaceTexture.updateTexImage() 的最后一步
glBindTexture(GL_TEXTURE_EXTERNAL_OES, texId);
glEGLImageTargetTexture2DOES(GL_TEXTURE_EXTERNAL_OES, eglImage);
// ★ 这一行之后，texId 指向的纹理就"别名"了 dma-buf 的内存
//    shader 里 samplerExternalOES 采 texId → GPU 直接读 gralloc buffer
```

`GL_TEXTURE_EXTERNAL_OES` 区别于普通 `GL_TEXTURE_2D` 的关键点：它允许底层数据格式是 **YUV/NV12**（而不强制是 RGBA），GL 驱动知道这个纹理是外部注入的、采样时不做格式转换——**YUV→RGB 的转换交给你自己在 fragment shader 里做**（这就是为什么 OES 纹理的 shader 必须用 `samplerExternalOES` 而非 `sampler2D`）。

##### 完整的零拷贝四步（一图收口）

```
gralloc buffer
   │  GPU 内存页 (NV12 tiled)
   │
   ├─► dma_buf = drm_gem_prime_export(buffer)   → 返回 fd=42
   │      │
   │      └─► eglCreateImageKHR(fd=42, DRM_FORMAT_NV12, …)  → EGLImage
   │             │
   │             └─► glEGLImageTargetTexture2DOES(OES_TEX, eglImage)
   │                    │
   │                    └─► fragment shader:
   │                          texture(samplerExternalOES, texCoord)
   │
   ★ 全程四步，传递的都是 fd / handle / GPU 页表项
   ★ 没有任何 memcpy、没有 CPU 中转、没有格式转换
```

> **面试口诀**：gralloc 管分配、dma-buf 管共享、EGLImage 管包装、OES 纹理给 shader 采样——四个环节，每环传的都是引用，不是数据。

#### 2.3.2 主线代码：SurfaceTexture + OpenGL ES 零拷贝渲染（★★★★★ 生产首选）

现在把上面的零拷贝机制落到代码上。这是**实际项目里最常用的路径**——MediaCodec 输出到 SurfaceTexture，GL 线程拿 OES 纹理做 YUV→RGB 转换和渲染。

##### Step 1：初始化 EGL 环境

在做任何 GL 操作之前，必须先建立 EGL 上下文。生产代码不会依赖 `GLSurfaceView`（它帮你做了但黑盒），而是**自己控 EGL**：

```java
// === EglCore.java —— EGL 环境初始化 ===
public class EglCore {
    private EGLDisplay mDisplay;
    private EGLContext mContext;
    private EGLConfig  mConfig;

    public EglCore() {
        // ① 获取 EGL Display
        mDisplay = EGL14.eglGetDisplay(EGL14.EGL_DEFAULT_DISPLAY);
        if (mDisplay == EGL14.EGL_NO_DISPLAY) {
            throw new RuntimeException("eglGetDisplay failed");
        }

        // ② 初始化 EGL
        int[] version = new int[2];
        if (!EGL14.eglInitialize(mDisplay, version, 0, version, 1)) {
            throw new RuntimeException("eglInitialize failed");
        }

        // ③ 选择 EGL Config（RGBA8888 + 可渲染到窗口 + 支持 EGLImage）
        int[] configAttribs = {
            EGL14.EGL_RENDERABLE_TYPE, EGL14.EGL_OPENGL_ES2_BIT,
            EGL14.EGL_RED_SIZE,   8,
            EGL14.EGL_GREEN_SIZE, 8,
            EGL14.EGL_BLUE_SIZE,  8,
            EGL14.EGL_ALPHA_SIZE, 8,
            EGL14.EGL_SURFACE_TYPE, EGL14.EGL_WINDOW_BIT,
            EGL14.EGL_NONE
        };
        EGLConfig[] configs = new EGLConfig[1];
        int[] numConfigs = new int[1];
        EGL14.eglChooseConfig(mDisplay, configAttribs, 0,
                configs, 0, 1, numConfigs, 0);
        mConfig = configs[0];

        // ④ 创建 EGL Context（OpenGL ES 2.0）
        int[] contextAttribs = {
            EGL14.EGL_CONTEXT_CLIENT_VERSION, 2,
            EGL14.EGL_NONE
        };
        mContext = EGL14.eglCreateContext(mDisplay, mConfig,
                EGL14.EGL_NO_CONTEXT, contextAttribs, 0);
    }

    // 为 SurfaceView/TextureView 的 Surface 创建 EGL Surface（= 渲染目标）
    public EGLSurface createWindowSurface(Object surface) {
        int[] surfaceAttribs = { EGL14.EGL_NONE };
        return EGL14.eglCreateWindowSurface(mDisplay, mConfig, surface,
                surfaceAttribs, 0);
    }

    public void makeCurrent(EGLSurface drawSurface, EGLSurface readSurface) {
        EGL14.eglMakeCurrent(mDisplay, drawSurface, readSurface, mContext);
    }

    public void swapBuffers(EGLSurface surface) {
        EGL14.eglSwapBuffers(mDisplay, surface);
    }

    public void release() {
        EGL14.eglDestroyContext(mDisplay, mContext);
        EGL14.eglTerminate(mDisplay);
        EGL14.eglReleaseThread();
    }
}
```

##### Step 2：创建 SurfaceTexture + 关联解码器

```java
// === 在 GL 线程里执行 ===
private EglCore eglCore;
private EGLSurface eglSurface;
private SurfaceTexture surfaceTexture;
private Surface decodeSurface;
private int oesTextureId;

private void initGLAndSurfaceTexture(Surface renderSurface) {
    // ① 初始化 EGL
    eglCore = new EglCore();
    eglSurface = eglCore.createWindowSurface(renderSurface);
    eglCore.makeCurrent(eglSurface, eglSurface);

    // ② 创建 OES 外部纹理 —— 这是解码画面的"入口"
    int[] textures = new int[1];
    GLES20.glGenTextures(1, textures, 0);
    oesTextureId = textures[0];

    GLES20.glBindTexture(GLES11Ext.GL_TEXTURE_EXTERNAL_OES, oesTextureId);
    GLES20.glTexParameteri(GLES11Ext.GL_TEXTURE_EXTERNAL_OES,
            GLES20.GL_TEXTURE_MIN_FILTER, GLES20.GL_LINEAR);
    GLES20.glTexParameteri(GLES11Ext.GL_TEXTURE_EXTERNAL_OES,
            GLES20.GL_TEXTURE_MAG_FILTER, GLES20.GL_LINEAR);
    // ★ OES 纹理必须 CLAMP_TO_EDGE（NPOT 纹理不支持 REPEAT）
    GLES20.glTexParameteri(GLES11Ext.GL_TEXTURE_EXTERNAL_OES,
            GLES20.GL_TEXTURE_WRAP_S, GLES20.GL_CLAMP_TO_EDGE);
    GLES20.glTexParameteri(GLES11Ext.GL_TEXTURE_EXTERNAL_OES,
            GLES20.GL_TEXTURE_WRAP_T, GLES20.GL_CLAMP_TO_EDGE);

    // ③ 用 OES 纹理构造 SurfaceTexture → 这是解码器和 GL 之间的"桥"
    surfaceTexture = new SurfaceTexture(oesTextureId);
    decodeSurface = new Surface(surfaceTexture);

    // ④ 解码帧就绪回调（在解码器线程执行，只发信号、不做重活）
    surfaceTexture.setOnFrameAvailableListener(new SurfaceTexture.OnFrameAvailableListener() {
        @Override
        public void onFrameAvailable(SurfaceTexture st) {
            // ★ 只是标记"有新帧"，真正的 updateTexImage() 在 GL 线程调
            frameAvailable.set(true);
        }
    });
}
```

##### Step 3：解码器 configure 传入 SurfaceTexture 的 Surface

```java
// === 任意线程（通常是解码线程）===
private MediaCodec decoder;

private void initDecoder() {
    decoder = MediaCodec.createDecoderByType(MediaFormat.MIME_TYPE_VIDEO_AVC);

    MediaFormat format = MediaFormat.createVideoFormat(
            MediaFormat.MIME_TYPE_VIDEO_AVC, 1920, 1080);
    format.setByteBuffer("csd-0", ByteBuffer.wrap(spsBytes));
    format.setByteBuffer("csd-1", ByteBuffer.wrap(ppsBytes));

    // ★ 传的是 SurfaceTexture 的 Surface
    decoder.configure(format, decodeSurface, null, 0);

    decoder.setCallback(new MediaCodec.Callback() {
        @Override
        public void onInputBufferAvailable(MediaCodec codec, int index) {
            ByteBuffer buf = codec.getInputBuffer(index);
            int len = readNalUnit(buf);  // 从网络/文件读 Annex-B 数据
            if (len > 0) {
                codec.queueInputBuffer(index, 0, len, ptsUs, 0);
            } else {
                codec.queueInputBuffer(index, 0, 0, 0,
                        MediaCodec.BUFFER_FLAG_END_OF_STREAM);
            }
        }

        @Override
        public void onOutputBufferAvailable(MediaCodec codec, int index,
                                             MediaCodec.BufferInfo info) {
            // ★ render=true：把这一帧推到 SurfaceTexture 的 BufferQueue
            //    解码器在底层做的是：queueBuffer(dmaBufFd) → 只传 fd
            codec.releaseOutputBuffer(index, true);
            // 之后 SurfaceTexture.onFrameAvailable 回调自动触发
        }

        @Override
        public void onError(MediaCodec codec, MediaCodec.CodecException e) {
            Log.e(TAG, "解码器错误: " + e.getDiagnosticInfo());
        }

        @Override
        public void onOutputFormatChanged(MediaCodec codec, MediaFormat format) {}
    });

    decoder.start();
}
```

##### Step 4：GL 渲染循环（完整版——从 OES 纹理到屏幕）

```java
// === GL 渲染线程 ===
private final AtomicBoolean frameAvailable = new AtomicBoolean(false);

// 编译 shader（见 Step 5）——只需做一次
private int glProgram;
private int uTransformMatrixLoc;
private int uTexSamplerLoc;
private FloatBuffer quadVertices;  // 全屏四边形的顶点坐标 + 纹理坐标

@Override
public void run() {
    initGLAndSurfaceTexture(windowSurface);
    initDecoder();
    compileShaders();

    while (running) {
        // ① ★ 等待解码器产出新帧
        if (frameAvailable.compareAndSet(true, false)) {
            // ② ★ 零拷贝关键调用：把 dma-buf → EGLImage → OES 纹理
            surfaceTexture.updateTexImage();
            //    内部流程:
            //      acquireBuffer() 拿到 dma-buf fd
            //      eglCreateImageKHR(fd, NV12, ...) → EGLImage
            //      glEGLImageTargetTexture2DOES(OES_TEX, eglImage)
            //      releaseBuffer() 归还 buffer 给 BufferQueue
            //    全程无 CPU memcpy

            // ③ 获取变换矩阵（摄像头旋转、视频元数据的矩阵）
            float[] transformMatrix = new float[16];
            surfaceTexture.getTransformMatrix(transformMatrix);

            // ④ 绑定 EGL Surface 为渲染目标
            eglCore.makeCurrent(eglSurface, eglSurface);

            // ⑤ 清屏
            GLES20.glViewport(0, 0, viewportWidth, viewportHeight);
            GLES20.glClearColor(0, 0, 0, 1);
            GLES20.glClear(GLES20.GL_COLOR_BUFFER_BIT);

            // ⑥ 激活 shader
            GLES20.glUseProgram(glProgram);

            // ⑦ 传入变换矩阵
            GLES20.glUniformMatrix4fv(uTransformMatrixLoc, 1, false,
                    transformMatrix, 0);

            // ⑧ 绑定 OES 纹理 —— shader 里用 samplerExternalOES 声明
            GLES20.glActiveTexture(GLES20.GL_TEXTURE0);
            GLES20.glBindTexture(GLES11Ext.GL_TEXTURE_EXTERNAL_OES, oesTextureId);
            GLES20.glUniform1i(uTexSamplerLoc, 0);

            // ⑨ 传入顶点数据（全屏四边形 = 4 个顶点, 2 个三角形, 共 6 个索引）
            quadVertices.position(0);
            GLES20.glVertexAttribPointer(0, 2, GLES20.GL_FLOAT, false,
                    4 * 4, quadVertices);
            GLES20.glEnableVertexAttribArray(0);
            quadVertices.position(2);
            GLES20.glVertexAttribPointer(1, 2, GLES20.GL_FLOAT, false,
                    4 * 4, quadVertices);
            GLES20.glEnableVertexAttribArray(1);

            // ⑩ ★ 渲染！（fragment shader 里做 YUV→RGB）
            GLES20.glDrawArrays(GLES20.GL_TRIANGLE_STRIP, 0, 4);

            // ⑪ 交换缓冲区 → 上屏
            eglCore.swapBuffers(eglSurface);
        } else {
            // 没有新帧，短暂休眠避免忙等
            Thread.sleep(2);
        }
    }

    // 收尾
    decoder.stop(); decoder.release();
    surfaceTexture.release();
    decodeSurface.release();
    eglCore.release();
}
```

##### Step 5：GL Shader（YUV NV12 → RGB，必须用 samplerExternalOES）

```java
// === Vertex Shader ===
private static final String VERTEX_SHADER =
    "uniform mat4 uTransformMatrix;" +      // SurfaceTexture 的变换矩阵
    "attribute vec4 aPosition;" +           // 顶点位置（NDC 坐标）
    "attribute vec4 aTexCoord;" +           // 纹理坐标 (0-1)
    "varying vec2 vTexCoord;" +
    "void main() {" +
    "  gl_Position = aPosition;" +
    "  vTexCoord = (uTransformMatrix * aTexCoord).xy;" +
    "}";

// === Fragment Shader（核心：YUV NV12 → RGB）===
private static final String FRAGMENT_SHADER =
    "#extension GL_OES_EGL_image_external : require\n" +  // ★ 必须声明
    "precision mediump float;" +
    "uniform samplerExternalOES uTexture;" +  // ★ samplerExternalOES，不是 sampler2D
    "varying vec2 vTexCoord;" +
    "" +
    "void main() {" +
    // ① 从 OES 纹理采样 —— GPU 直接读 NV12 gralloc buffer
    //    OES 纹理采样后自动去 tiling——这是 GPU 纹理单元硬件做的，不走 CPU
    "  vec3 yuv;" +
    "  yuv.r = texture2D(uTexture, vTexCoord).r;" +       // Y 分量
    "  yuv.g = texture2D(uTexture, vTexCoord).a;" +       // NV12 的 U 在 alpha 通道
    "  yuv.b = texture2D(uTexture, vTexCoord).a;" +       // ...实际上这段采样方式取决于具体实现
    "" +
    // ★ 实际上 EGLImage 包装 dma-buf 时各平面是独立映射的，所以更准确的做法是：
    //   两个 samplerExternalOES，分别对应 Y 和 UV 平面
    //   上面是简化版，下面是生产可用的 YUV→RGB 矩阵版本：
    "}";

// === 生产级 Fragment Shader：YUV NV12 → RGB（BT.601 Video Range）===
private static final String FRAGMENT_SHADER_PROD =
    "#extension GL_OES_EGL_image_external : require\n" +
    "precision mediump float;\n" +
    "uniform samplerExternalOES uTextureY;" +   // Y 平面
    "uniform samplerExternalOES uTextureUV;" +  // UV 平面（交织）
    "varying vec2 vTexCoord;\n" +
    "\n" +
    "void main() {\n" +
    // NV12: Y 全分辨率，UV 半分辨率、交织
    "  float y = texture2D(uTextureY, vTexCoord).r;\n" +
    "  vec2 uv = texture2D(uTextureUV, vTexCoord).ra;\n" +  // r=U, a=V
    "\n" +
    // BT.601 Video Range → RGB
    "  y = 1.164 * (y - 0.0625);\n" +           //  Y: scale & offset
    "  uv = uv - 0.5;\n" +                       // UV: center around 0
    "  float r = y + 1.596 * uv.y;\n" +          //  R = Y + 1.596*(V-0.5)
    "  float g = y - 0.813 * uv.y - 0.391 * uv.x;\n" + // G = Y - 0.813*(V-0.5) - 0.391*(U-0.5)
    "  float b = y + 2.018 * uv.x;\n" +          //  B = Y + 2.018*(U-0.5)
    "\n" +
    "  gl_FragColor = vec4(r, g, b, 1.0);\n" +
    "}";
```

**注意**：生产代码中，如果 EGLImage 创建时指定了 `DRM_FORMAT_NV12` 且两个平面映射为独立的 dma-buf plane，GL 会创建**两张 OES 纹理**（Y 和 UV 各一张），代码如上所示用两个 sampler。这是最准确的写法。部分设备/驱动支持单 OES 纹理采样 YUV（`GL_TEXTURE_EXTERNAL_OES` 的 YUV 目标），但跨设备兼容性不好——**双纹理方案最稳**。

#### 2.3.4 ByteBuffer CPU readback（确需碰像素时）

> **⚠️ 前置警告**：这条路坑多且深——color format 碎片化（NV12/I420/tiled）、stride ≠ width、slice-height ≠ height（详见 [14 §一/§七](./14-Android硬件编解码.md)）。能用路径 A/B 解决的就别走这条路。

仅在以下场景用：
- 截图存为 JPEG/PNG
- 把某一帧喂给 AI 推理模型（TFLite/NCNN）
- 往非标格式转码

**完整代码**：

```java
// === configure 时不传 Surface ===
MediaFormat format = MediaFormat.createVideoFormat(
        MediaFormat.MIME_TYPE_VIDEO_AVC, width, height);
format.setByteBuffer("csd-0", ByteBuffer.wrap(spsBytes));
format.setByteBuffer("csd-1", ByteBuffer.wrap(ppsBytes));

decoder.configure(format, null, null, 0);  // ★ Surface 传 null

    @Override
    public void onOutputBufferAvailable(MediaCodec codec, int index,
                                         MediaCodec.BufferInfo info) {
        // ① 用 Image 而非裸 ByteBuffer（API 21+）
        Image image = codec.getOutputImage(index);
        if (image != null) {
            processDecodedImage(image);  // 见下方
            image.close();               // ★ 等价 release，必须关
        }
        codec.releaseOutputBuffer(index, false);  // false = 不渲染
    }
    // ...
});
decoder.start();

**处理 Image：按 rowStride/pixelStride 安全读 YUV**

```java
private void processDecodedImage(Image image) {
    Image.Plane[] planes = image.getPlanes();

    // ===== Y 平面 =====
    Image.Plane yPlane = planes[0];
    ByteBuffer yBuf = yPlane.getBuffer();
    int yRowStride   = yPlane.getRowStride();    // 每行字节数（含 padding，通常 > width）
    int yPixelStride = yPlane.getPixelStride();  // Y 恒为 1

    // ===== UV 平面 =====
    Image.Plane uPlane = planes[1];
    ByteBuffer uvBuf = uPlane.getBuffer();
    int uvRowStride   = uPlane.getRowStride();
    int uvPixelStride = uPlane.getPixelStride();  // NV12=2(UVUV), I420=1(U独立)

    // NV12: planes[2] 为 null（UV 在一个平面里交织）
    // I420: planes[1]=U, planes[2]=V, pixelStride 都是 1

    byte[] yData = new byte[width * height];
    for (int row = 0; row < height; row++) {
        yBuf.position(row * yRowStride);        // 跳到每行起点
        yBuf.get(yData, row * width, width);    // 只读 width 有效字节，跳过 padding
    }

    // UV 同理，行数 = height/2，宽度 = width/2
    int uvHeight = height / 2;
    byte[] uvData = new byte[width * height / 2];
    for (int row = 0; row < uvHeight; row++) {
        uvBuf.position(row * uvRowStride);
        uvBuf.get(uvData, row * width, width);  // NV12: UV 交织所以 width 不变
    }

    // 现在 yData + uvData 是紧凑 NV12，可以喂 TFLite / 存文件 / 编码 JPEG
    saveAsJPEG(yData, uvData, width, height);
}
```

**路径 C 再强调一次铁律**：每个 dequeue 到的 output buffer 用完必须 `releaseOutputBuffer(index, false)`（或 `image.close()`），否则 buffer pool 耗尽、解码器永久卡死。

#### 2.3.5 NDK AMediaCodec（C++ 侧全流程）

跨平台播放器（如 ijkplayer、ExoPlayer C++ 内核）通常在 native 层做解码。NDK 提供的 `AMediaCodec` API 和 Java 层一一对应。

```cpp

    AMediaFormat_setInt32(format, AMEDIAFORMAT_KEY_WIDTH, 1920);
    AMediaFormat_setInt32(format, AMEDIAFORMAT_KEY_HEIGHT, 1080);
    AMediaFormat_setBuffer(format, "csd-0", sps, spsLen);
    AMediaFormat_setBuffer(format, "csd-1", pps, ppsLen);

    // ③ configure + 传入 ANativeWindow（= Java Surface 的 native 对等物）
    media_status_t status = AMediaCodec_configure(codec, format, outputWindow,
                                                  nullptr, 0);
    if (status != AMEDIA_OK) {
        AMediaFormat_delete(format);
        AMediaCodec_delete(codec);
        return nullptr;
    }

    AMediaCodec_start(codec);
    AMediaFormat_delete(format);
    return codec;
}

// ---------- 喂数据 + 拿输出 ----------
void decodeLoop(AMediaCodec* codec, ANativeWindow* window) {
    while (running) {
        // ===== 输入侧：喂 Annex-B 数据 =====
        ssize_t inIdx = AMediaCodec_dequeueInputBuffer(codec, 10000);  // 10ms 超时
        if (inIdx >= 0) {
            size_t bufSize;
            uint8_t* buf = AMediaCodec_getInputBuffer(codec, inIdx, &bufSize);

            int nalLen = readNextNalUnit(buf, bufSize);  // 从网络/文件读一帧
            if (nalLen > 0) {
                AMediaCodec_queueInputBuffer(codec, inIdx, 0, nalLen, ptsUs, 0);
            } else {
                // 码流结束
                AMediaCodec_queueInputBuffer(codec, inIdx, 0, 0, ptsUs,
                        AMEDIACODEC_BUFFER_FLAG_END_OF_STREAM);
            }
        }

        // ===== 输出侧 =====
        AMediaCodecBufferInfo info;
        ssize_t outIdx = AMediaCodec_dequeueOutputBuffer(codec, &info, 10000);
        if (outIdx >= 0) {
            if (info.flags & AMEDIACODEC_BUFFER_FLAG_END_OF_STREAM) {
                break;  // EOS，解码结束
            }
            // ★ 传入 ANativeWindow：零拷贝渲染，和 Java 的 releaseOutputBuffer(idx, true) 等价
            AMediaCodec_releaseOutputBuffer(codec, outIdx, true);
            // 不传 window 且 render=false：相当于 ByteBuffer 路径
            // AMediaCodec_releaseOutputBuffer(codec, outIdx, false);
            // 然后通过 AMediaCodec_getOutputBuffer 读数据
        } else if (outIdx == AMEDIACODEC_INFO_OUTPUT_FORMAT_CHANGED) {
            AMediaFormat* newFmt = AMediaCodec_getOutputFormat(codec);
            // 可获取实际解码输出的宽高、颜色格式
            int outWidth, outHeight;
            AMediaFormat_getInt32(newFmt, AMEDIAFORMAT_KEY_WIDTH, &outWidth);
            AMediaFormat_getInt32(newFmt, AMEDIAFORMAT_KEY_HEIGHT, &outHeight);
            AMediaFormat_delete(newFmt);
        }
    }
}

// ---------- 收尾 ----------
void releaseDecoder(AMediaCodec* codec) {
    if (codec) {
        AMediaCodec_stop(codec);
        AMediaCodec_delete(codec);
    }
}
```

**NDK 场景的额外要点**：

- **ANativeWindow 从哪来**：Java 层把 `Surface` 通过 JNI 传给 native 层，用 `ANativeWindow_fromSurface(env, javaSurface)` 转换得到。
- **硬解/软解自动选择**：NDK 创建 codec 和 Java 一样是组件名驱动——`AMediaCodec_createDecoderByType` 自动选硬件 codec（如有）。想强制指定组件名可以用 `AMediaCodec_createCodecByName("c2.qti.avc.decoder")`（高通硬解）。
- **ByteBuffer 路径在 NDK 侧**：不传 `ANativeWindow` → `releaseOutputBuffer(idx, false)` → `AMediaCodec_getOutputBuffer` 拿裸数据 → 颜色格式参考 `AMediaFormat_getInt32(format, AMEDIAFORMAT_KEY_COLOR_FORMAT, &colorFmt)`。

#### 2.3.6 MediaCodec 解码渲染——面试高频追问

**Q1：零拷贝到底怎么零的？一步步说清楚。**

> "四步，每步传的都是引用、不是数据。
> ① **gralloc**：解码器输出不是 malloc 出来的堆内存，是 gralloc 分配的 GPU 内存（NV12 tiled 布局）。gralloc 返回 buffer_handle_t。
> ② **dma-buf**：内核的 DMA-BUF 子系统为这块 gralloc buffer 暴露一个文件描述符（fd）。解码器 `releaseOutputBuffer(idx, true)` 在底层做的是 `BufferQueue::queueBuffer(fd)`——**传的是一个 int fd，不是几百 KB 的像素数据**。
> ③ **EGLImage**：SurfaceTexture 在 `updateTexImage()` 里先 `acquireBuffer()` 拿到 fd，然后调 `eglCreateImageKHR(fd, DRM_FORMAT_NV12, ...)` 把这个 fd 包装成 EGL 能理解的对象。这一步是做 GPU MMU 页表映射——不复制数据。
> ④ **OES 纹理**：`glEGLImageTargetTexture2DOES(GL_TEXTURE_EXTERNAL_OES, eglImage)` 让纹理直接指向 dma-buf 的物理页。shader 里 `samplerExternalOES` 采样这个纹理，GPU 纹理单元直接从同一块内存读——全程物理零拷贝。"

**Q2：`releaseOutputBuffer(index, true)` 和 `releaseOutputBuffer(index, false)` 到底什么区别？**

> `true` = 渲染到 `configure` 时传的 Surface。此时解码器把这一帧对应的 gralloc buffer 通过 BufferQueue **直接推到 Surface 的消费者侧**（SurfaceFlinger 或 SurfaceTexture），全程 GPU 到 GPU，不下 CPU。
>
> `false` = 不渲染，只归还 buffer。此时你必须在 `release` 之前通过 `getOutputBuffer(index)` 或 `getOutputImage(index)` 把数据读走——因为 release 之后这个 buffer index 就回收了、数据不可再访问。
>
> 无论 true 还是 false，`release` 这一步都**必须调**——否则 buffer pool 耗尽。

**Q2：为什么 configure 传了 Surface 了，output buffer 还是能 dequeue 出来？**

> 能 dequeue，但 buffer 里**没有有效的像素数据**——数据已经直接推到 Surface 的 BufferQueue 里了。你仍然需要在拿到 output buffer index 后调 `releaseOutputBuffer(idx, true)`，这是驱动 BufferQueue 出队的触发动作。可以理解为：dequeue → release 这对操作在 Surface 模式下**从"交数据给 App"退化成了"通知 App 渲染完成 + 触发 BufferQueue 推进"**。

**Q3：SurfaceTexture 的 `updateTexImage()` 做了什么？为什么会触发 EGL 消费？**

> `updateTexImage()` 调用时，SurfaceTexture 内部通过 BufferQueue 的 `acquireBuffer` 拿到解码器刚推过来的那个 gralloc buffer，然后通过 EGL `glEGLImageTargetTexture2DOES` 把这块 dma-buf 内存绑定到当前绑定的 OES 纹理上。整块内存的"所有权"从解码器转移到 GL 上下文，但**物理上还是同一块内存**——所以是零拷贝。

**Q4：解码 4K60，Surface 零拷贝够不够？还有什么会掉帧？**

> Surface 零拷贝本身不构成瓶颈——它是 dma-buf fd 传递。但以下环节可能导致掉帧：
> - `SurfaceTexture.setOnFrameAvailableListener` 的 `onFrameAvailable` 回调**是在解码器线程调用的**，你在里面做重活会阻塞解码器出帧。
> - `updateTexImage()` + `glDrawArrays()` 的 VSync 节奏跟解码帧率不匹配：解码器 60fps 出帧，屏幕 60Hz 渲染——每帧只给 16.6ms。如果你在 shader 里做了复杂美颜，单帧 GL 耗时超过 16.6ms，帧就丢了。
> - 解法：解码帧先不做 GL，直接释放（`releaseOutputBuffer(idx, true)` 推进 BufferQueue），只渲染最新的那一帧（类似三重缓冲的"丢弃旧帧"策略）。

**Q5：不用 SurfaceTexture，解码完怎么直接在 NDK 拿 OES 纹理？**

> NDK 没有 `SurfaceTexture` 的 C API。做法是在 Java 层创建一个 `SurfaceTexture`、拿到 `Surface`，JNI 传给 native 层的 `ANativeWindow`。然后在 `onFrameAvailable` 回调里通过 JNI callback 通知 native GL 线程调 `updateTexImage()`。

### 2.4 VideoToolbox 解码到渲染全链路（iOS / macOS 硬解上屏实战）

iOS 的硬解渲染链路在概念上和 Android 对称，但 API 风格完全不同——全部是 CoreFoundation 风格的 C API，callback 驱动，**异步模型贯穿始终**。**VideoToolbox 解码没有同步模式**。

#### 2.4.0 三条路径总览

```
压缩码流 (AVCC H.264)
       │
       ▼
┌──────────────────────────────────────────────┐
│         VTDecompressionSession 解码器          │
│  VTDecompressionSessionCreate(回调)            │
│  VTDecompressionSessionDecodeFrame(喂帧)       │
│  输出: CVPixelBuffer（底层 IOSurface）          │
└──────────┬───────────────────────────────────┘
           │
           ├── 路径 A: AVSampleBufferDisplayLayer 直显（★ 最省事）
           │    enqueue CMSampleBuffer → 系统自动显示

#### 2.4.1 创建 VTDecompressionSession：必须先有 CMVideoFormatDescription

VideoToolbox 解码有一道 Android 没有的**前置门槛**：`VTDecompressionSessionCreate` 需要 `CMVideoFormatDescription`——你必须**先拿到 SPS/PPS**（H.264）或 VPS/SPS/PPS（H.265），才能创建解码会话。

```objc
// === VideoDecoder.m ===
#import <VideoToolbox/VideoToolbox.h>

@interface VideoDecoder : NSObject
@property (nonatomic, assign) VTDecompressionSessionRef session;
@property (nonatomic, assign) CMVideoFormatDescriptionRef formatDesc;
@end

@implementation VideoDecoder

- (BOOL)createSessionWithSPS:(const uint8_t *)sps spsLen:(size_t)spsLen
                         PPS:(const uint8_t *)pps ppsLen:(size_t)ppsLen
                    callback:(VTDecompressionOutputCallback)callback {
    // ① 用 SPS + PPS 构造 CMVideoFormatDescription（HEVC 还要传 VPS）
    const uint8_t *paramSets[2] = {sps, pps};
    size_t paramSizes[2] = {spsLen, ppsLen};

    OSStatus status = CMVideoFormatDescriptionCreateFromH264ParameterSets(
        kCFAllocatorDefault,
        2,                          // 参数集个数（SPS + PPS）
        paramSets,                  // 参数集指针数组 /参数集长度数组
        paramSizes,
        4,                          // NALULengthSize: 4 字节长度前缀
        &_formatDesc                // 出参
    );
    // ⚠️ 对于 H.265: 用 CMVideoFormatDescriptionCreateFromHEVCParameterSets，
    //    传 3 个参数集（VPS + SPS + PPS）

    if (status != noErr) {
        NSLog(@"创建 format desc 失败: %d", (int)status);
        return NO;
    }

    // ② 创建解码会话：需指定输出 CVPixelBuffer 的属性
    //    要点：必须带 IOSurface + Metal compatibility key 才能零拷贝
    CFMutableDictionaryRef dstAttrs = CFDictionaryCreateMutable(
        kCFAllocatorDefault, 4,
        &kCFTypeDictionaryKeyCallBacks,
        &kCFTypeDictionaryValueCallBacks);

    // ★ 关键 key 1：强制 IOSurface 后端（= 零拷贝的物理前提）
    CFDictionarySetValue(dstAttrs,
        kCVPixelBufferIOSurfacePropertiesKey,
        (__bridge CFDictionaryRef)@{});  // 空字典 = 用系统默认 IOSurface 属性

    // ★ 关键 key 2：允许 Metal 兼容（MTLTexture 零拷贝 alias）
    CFDictionarySetValue(dstAttrs,
        kCVPixelBufferMetalCompatibilityKey,
        kCFBooleanTrue);

    // ★ 关键 key 3：像素格式——硬解输出 NV12 即可
    int32_t pixelFormat = kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange;
    CFNumberRef pfNum = CFNumberCreate(kCFAllocatorDefault, kCFNumberSInt32Type,
                                       &pixelFormat);
    CFDictionarySetValue(dstAttrs, kCVPixelBufferPixelFormatTypeKey, pfNum);
    CFRelease(pfNum);

    // ③ 创建 VTDecompressionSession
    VTDecompressionOutputCallbackRecord cbRecord;
    cbRecord.decompressionOutputCallback = callback;    // 解码输出回调
    cbRecord.decompressionOutputRefCon = (__bridge void *)self;

    status = VTDecompressionSessionCreate(
        kCFAllocatorDefault,
        _formatDesc,                // ★ 必须：已注入 SPS/PPS
        NULL,                       // 不指定解码器（让系统自动选硬件）
        dstAttrs,                   // 输出 pixel buffer 属性
        &cbRecord,                  // 回调
        &_session
    );
    CFRelease(dstAttrs);

    if (status != noErr) {
        NSLog(@"创建解码 session 失败: %d", (int)status);
        return NO;
    }

    // ④ 可选：强制硬件解码（不做则系统自动选，可能回退软件）
    VTSessionSetProperty(_session,
        kVTDecompressionPropertyKey_RealTime, kCFBooleanTrue);

    return YES;
}
```

> ⚠️ **两个最容易犯的错误**：
> 1. `CMVideoFormatDescriptionCreateFromH264ParameterSets` 的 `NALULengthSize` 参数必须和实际码流的长度前缀字节数一致——通常填 4（4 字节长度前缀）。填错会导致解码出的画面花屏或直接报错。
> 2. `dstAttrs` 漏掉 `kCVPixelBufferIOSurfacePropertiesKey` 或 `kCVPixelBufferMetalCompatibilityKey`，CVPixelBuffer 会退化成普通内存——后续 Metal 零拷贝直接失效。

#### 2.4.2 喂帧解码：AVCC 格式 CMSampleBuffer

```objc
- (void)decodeNALU:(const uint8_t *)naluData length:(size_t)length
               pts:(CMTime)pts isSync:(BOOL)isSync {
    if (!_session) return;

    // ① 把 AVCC NALU（4 字节长度前缀）包成 CMBlockBuffer
    CMBlockBufferRef blockBuffer = NULL;
    OSStatus status = CMBlockBufferCreateWithMemoryBlock(
        kCFAllocatorDefault,
        (void *)naluData,          // 数据指针
        length,                     // 数据长度
        kCFAllocatorNull,           // 不接管内存管理
        NULL, 0, length, 0,
        &blockBuffer
    );
    if (status != noErr) return;

    // ② 包装成 CMSampleBuffer（= 压缩数据 + 格式 + 时间信息）
    CMSampleBufferRef sampleBuffer = NULL;
    CMSampleTimingInfo timingInfo = {
        .duration   = kCMTimeInvalid,   // 解码帧不需要 duration
        .presentationTimeStamp = pts,   // ★ 展示时间戳
        .decodeTimeStamp       = kCMTimeInvalid
    };

    size_t sampleSizes[] = {length};

    status = CMSampleBufferCreateReady(
        kCFAllocatorDefault,
        blockBuffer,                // 压缩数据
        _formatDesc,                // ★ 格式描述（含 SPS/PPS）
        1, 1,                       // 1 个 sample
        &timingInfo, 1, sampleSizes,
        &sampleBuffer
    );
    CFRelease(blockBuffer);
    if (status != noErr) return;

    // ③ 标记是否为关键帧（解码器用它判断能否从这一帧开始解）
    if (isSync) {
        CFArrayRef attachments = CMSampleBufferGetSampleAttachmentsArray(
            sampleBuffer, true);
        if (attachments && CFArrayGetCount(attachments) > 0) {
            CFMutableDictionaryRef dict = (CFMutableDictionaryRef)
                CFArrayGetValueAtIndex(attachments, 0);
            CFDictionarySetValue(dict,
                kCMSampleAttachmentKey_NotSync, kCFBooleanFalse);  // false = 是同步帧
            CFDictionarySetValue(dict,
                kCMSampleAttachmentKey_DependsOnOthers, kCFBooleanFalse);
        }
    }

    // ④ 喂给解码器（异步——解码结果在回调里拿）
    VTDecodeFrameFlags flags = 0;
    VTDecodeInfoFlags infoFlagsOut;
    status = VTDecompressionSessionDecodeFrame(
        _session,
        sampleBuffer,
        flags,              // 可选 kVTDecodeFrame_EnableAsynchronousDecompression
        NULL,               // 不传出参 frame ref
        &infoFlagsOut
    );
    CFRelease(sampleBuffer);

    if (status != noErr) {
        NSLog(@"解码帧失败: %d", (int)status);
        // -12909 (kVTVideoDecoderBadDataErr): 码流损坏或 SPS/PPS 不匹配
        // -12912 (kVTVideoDecoderMalfunctionErr): 解码器内部状态错，需重建 session
    }
}
```

> ⚠️ **Annex-B → AVCC 转换**：如果你的码流是 Annex-B（`00 00 00 01` 起始码），必须先把起始码替换为 4 字节大端长度前缀、再把 SPS/PPS 从数据里剥离、注入到 `CMVideoFormatDescription`。iOS 侧的转换细节见 [15 §六](./15-iOS硬件编解码.md)。

#### 2.4.3 解码输出回调：拿到 CVPixelBuffer

```objc
// VTDecompressionOutputCallback（C 函数，在解码器内部线程调用）
static void decompressionOutputCallback(
    void *decompressionOutputRefCon,
    void *sourceFrameRefCon,
    OSStatus status,
    VTDecodeInfoFlags infoFlags,
    CVImageBufferRef imageBuffer,    // ★ 就是 CVPixelBuffer（如果成功）
    CMTime presentationTimeStamp,
    CMTime presentationDuration) {

    if (status != noErr || imageBuffer == NULL) {
        // -12909: 参考帧缺失或码流损坏
        // -12905: 帧重排序缓冲区满（常见于解码快于渲染）
        return;
    }

    VideoDecoder *decoder = (__bridge VideoDecoder *)decompressionOutputRefCon;

    // ★★★ 把 CVPixelBuffer 交给渲染层（见 2.4.4） ★★★
    [decoder.renderer renderPixelBuffer:imageBuffer pts:presentationTimeStamp];

    // CVPixelBuffer 持有引用计数——这里不用 CFRelease
    // 解码器的 pixel buffer pool 会自动管理生命周期，你只要不长期持有即可
    // 如果需要跨帧保留，手动 CVPixelBufferRetain / CVPixelBufferRelease
}
```

**关键点**：
- 回调在**解码器的内部线程**上调用，不是主线程——直接在里面调 UIKit/CALayer 操作会 crash。所有渲染操作必须 dispatch 到主线程或 Metal 的 command queue 线程。
- `imageBuffer` 的生命周期由解码器内部的 `CVPixelBufferPool` 管理：你不在这个回调里 retain 它、且回调返回时不持有它，它会被回收到 pool 供下一帧复用。如果你需要把它传给渲染线程，调用 `CVPixelBufferRetain(imageBuffer)`，渲染完再 release。

#### 2.4.4 路径 A：AVSampleBufferDisplayLayer 直显（纯播放，3 行代码）

最省事的方式——适合"我只想看到画面"的场景，不需要后处理。

```objc
// === 初始化 ===
@property (nonatomic, strong) AVSampleBufferDisplayLayer *displayLayer;

- (void)setupDisplayLayer {
    self.displayLayer = [[AVSampleBufferDisplayLayer alloc] init];
    self.displayLayer.videoGravity = AVLayerVideoGravityResizeAspect;
    // 加到 view 的 layer 层级：
    [self.view.layer addSublayer:self.displayLayer];
    self.displayLayer.frame = self.view.bounds;
}

// === 在解码回调里直接 enqueue ===
// 注意：解码回调在解码线程，enqueue 本身是线程安全的
- (void)enqueueSampleBuffer:(CMSampleBufferRef)sampleBuffer {
    if (self.displayLayer.readyForMoreMediaData) {
        [self.displayLayer enqueueSampleBuffer:sampleBuffer];
    }
    // 不够 ready 就丢弃这帧（网络抖动场景的策略）
}

// === 收尾 ===
- (void)stopDisplay {
    [self.displayLayer flush];       // 清空队列
    [self.displayLayer stopRequestingMediaData];
}
```

- 需要做滤镜/美颜/合成（画面被黑盒管着，你拿不到像素）
- 需要精确控制渲染时机（VSync 对齐、游戏引擎合成）
- 需要自定义 YUV→RGB 转换

#### 2.4.5 路径 B：Metal + CVMetalTextureCache 后处理上屏（生产首选）

Metal 是 iOS/macOS 上做视频渲染的最高性能选择。关键桥接件是 `CVMetalTextureCache`——它把 `CVPixelBuffer` 的每个平面**零拷贝 alias** 成 `MTLTexture`。

**完整流程**：

```
解码回调拿到 CVPixelBuffer(NV12)
       │
       ▼
┌─ CVMetalTextureCache ──────────────────────┐
│  CVMetalTextureCacheCreateTextureFromImage │
│  平面 0(Y)  → MTLTexture r8                 │
│  平面 1(UV) → MTLTexture rg8                │
│  ★ 同一块 IOSurface，只是被 GPU 以不同格式重读  │
└────────────────────────────────────────────┘
       │
       ▼
Metal Fragment Shader
  采样 r8Texture → Y
  采样 rg8Texture → UV
  YUV→RGB 转换矩阵
  + 滤镜/美颜处理
       │
       ▼
MTKView.currentDrawable (上屏)
```

**Step 1：初始化 Metal 渲染管线**

```objc
// === MetalRenderer.h ===
#import <Metal/Metal.h>
#import <MetalKit/MetalKit.h>
#import <CoreVideo/CoreVideo.h>

@interface MetalRenderer : NSObject
- (instancetype)initWithDevice:(id<MTLDevice>)device
                     mtkView:(MTKView *)view;
- (void)renderPixelBuffer:(CVPixelBufferRef)pixelBuffer pts:(CMTime)pts;
@end

// === MetalRenderer.m ===
@implementation MetalRenderer {
    id<MTLDevice> _device;
    MTKView *_view;
    id<MTLCommandQueue> _commandQueue;
    id<MTLRenderPipelineState> _pipelineState;
    CVMetalTextureCacheRef _textureCache;  // ★ 核心桥接
    id<MTLBuffer> _vertexBuffer;
    id<MTLBuffer> _colorConvBuffer;        // YUV→RGB 矩阵
}

- (instancetype)initWithDevice:(id<MTLDevice>)device mtkView:(MTKView *)view {
    self = [super init];
    if (!self) return nil;

    _device = device;
    _view = view;
    _commandQueue = [_device newCommandQueue];

    // ★ 创建 CVMetalTextureCache——零拷贝的核心
    //   CVMetalTextureCache 只负责创建 MTLTexture 别名，不管理生命周期
    CVReturn cvRet = CVMetalTextureCacheCreate(
        kCFAllocatorDefault,
        NULL,                    // cache attributes（nil = 默认）
        _device,                 // Metal device
        NULL,                    // texture attributes
        &_textureCache
    );
    if (cvRet != kCVReturnSuccess) {
        NSLog(@"创建 CVMetalTextureCache 失败: %d", cvRet);
        return nil;
    }

    // 编译 shader、创建 pipeline state...
    [self buildPipeline];
    return self;
}
```

**Step 2：每帧渲染——从 CVPixelBuffer 到 Metal 纹理到上屏**

```objc
- (void)renderPixelBuffer:(CVPixelBufferRef)pixelBuffer pts:(CMTime)pts {
    if (!pixelBuffer) return;

    // ① 获取 CVPixelBuffer 的宽高（非 stride，是实际画面宽高）
    size_t width  = CVPixelBufferGetWidth(pixelBuffer);
    size_t height = CVPixelBufferGetHeight(pixelBuffer);

    // ② ★ 为亮度平面(Y) 创建 Metal 纹理别名
    CVMetalTextureRef yTextureRef = NULL;
    CVReturn cvRet = CVMetalTextureCacheCreateTextureFromImage(
        kCFAllocatorDefault,
        _textureCache,
        pixelBuffer,
        NULL,                          // texture attributes
        MTLPixelFormatR8Unorm,         // ★ Y = 单通道 8-bit
        (int)width,                    // full-resolution Y
        (int)height,
        0,                             // plane index: Y = 0
        &yTextureRef
    );
    if (cvRet != kCVReturnSuccess) return;

    // ③ ★ 为色度平面(UV) 创建 Metal 纹理别名
    CVMetalTextureRef uvTextureRef = NULL;
    cvRet = CVMetalTextureCacheCreateTextureFromImage(
        kCFAllocatorDefault,
        _textureCache,
        pixelBuffer,
        NULL,
        MTLPixelFormatRG8Unorm,        // ★ UV = 双通道 8-bit (NV12)
        (int)(width / 2),              // UV 是半分辨率
        (int)(height / 2),
        1,                             // plane index: UV = 1
        &uvTextureRef
    );
    if (cvRet != kCVReturnSuccess) {
        CFRelease(yTextureRef);
        return;
    }

    id<MTLTexture> yTexture  = CVMetalTextureGetTexture(yTextureRef);
    id<MTLTexture> uvTexture = CVMetalTextureGetTexture(uvTextureRef);

    // ④ 编码 Metal 渲染命令
    id<MTLCommandBuffer> commandBuffer = [_commandQueue commandBuffer];
    MTLRenderPassDescriptor *rpd = _view.currentRenderPassDescriptor;

    if (rpd && commandBuffer) {
        id<MTLRenderCommandEncoder> encoder = [commandBuffer
            renderCommandEncoderWithDescriptor:rpd];

        [encoder setRenderPipelineState:_pipelineState];
        [encoder setVertexBuffer:_vertexBuffer offset:0 atIndex:0];

        // ★ 传两张纹理 + 颜色转换矩阵给 fragment shader
        [encoder setFragmentTexture:yTexture  atIndex:0];
        [encoder setFragmentTexture:uvTexture atIndex:1];
        [encoder setFragmentBuffer:_colorConvBuffer offset:0 atIndex:0];

        [encoder drawPrimitives:MTLPrimitiveTypeTriangle
                    vertexStart:0 vertexCount:6];
        [encoder endEncoding];

        [commandBuffer presentDrawable:_view.currentDrawable];
        [commandBuffer commit];
    }

    // ★ 释放 CVMetalTexture（不是 MTLTexture——那由 cache 管理）
    CFRelease(yTextureRef);
    CFRelease(uvTextureRef);
    // CVPixelBuffer 的 retain 由调用方管理，此处不 release
}
```

**Step 3：Metal Shader——YUV(NV12) → RGB**

```metal
// === Shaders.metal ===
#include <metal_stdlib>
using namespace metal;

struct VertexOut {
    float4 position [[position]];
    float2 texCoord;
};

// ★ YUV→RGB 颜色转换矩阵（ITU-R BT.601 Video Range）
//    注意：这是 BT.601 标清矩阵，高清用 BT.709
//    R = 1.164(Y-16) + 1.596(V-128)
//    G = 1.164(Y-16) - 0.813(V-128) - 0.391(U-128)
//    B = 1.164(Y-16) + 2.018(U-128)
constant float3x3 yuvToRGB = float3x3(
    float3(1.164,  1.164,  1.164),    // Y 系数
    float3(0.0,    -0.391,  2.018),   // U 系数
    float3(1.596,  -0.813,  0.0)      // V 系数
);

constant float3 yuvOffset = float3(16.0/255.0, 128.0/255.0, 128.0/255.0);

fragment float4 fragmentShader(
    VertexOut in [[stage_in]],
    texture2d<float> yTexture  [[texture(0)]],   // r8,  平面 0
    texture2d<float> uvTexture [[texture(1)]])   // rg8, 平面 1
{
    constexpr sampler s(filter::linear, address::clamp_to_edge);

    float y  = yTexture.sample(s, in.texCoord).r;
    float2 uv = uvTexture.sample(s, in.texCoord).rg;  // r=U, g=V

    float3 yuv = float3(y, uv.r, uv.g) - yuvOffset;
    float3 rgb = yuvToRGB * yuv;

    return float4(rgb, 1.0);
}
```

**要点**：
- `CVMetalTextureCacheCreateTextureFromImage` 的四个关键参数：`pixelFormat`（`r8`/`rg8`）、`width`/`height`（Y:全分辨率，UV:半分辨率）、`planeIndex`（Y=0, UV=1）。填错任何一个，shader 里采到的就是垃圾数据。
- `CVMetalTexture` 只是一个"壳"——`CVMetalTextureGetTexture` 拿到的 `MTLTexture` 才是 shader 直接用的对象。**物理上还是那块 IOSurface**。
- 不要长期持有 `CVMetalTextureRef`——创建、用 `GetTexture` 拿到 `MTLTexture` 提交 draw call、然后立即 `CFRelease`。要不然 texture cache 的内部池子会被撑满。

#### 2.4.6 路径 C：CPU Readback（确需碰像素时）

```objc
- (void)readbackPixelBuffer:(CVPixelBufferRef)pixelBuffer {
    // ① 锁基地址——★ 这一步会触发 GPU→CPU 同步等待 + detile
    CVPixelBufferLockBaseAddress(pixelBuffer, kCVPixelBufferLock_ReadOnly);

    // ② 读 Y 平面
    size_t yWidth  = CVPixelBufferGetWidthOfPlane(pixelBuffer, 0);
    size_t yHeight = CVPixelBufferGetHeightOfPlane(pixelBuffer, 0);
    size_t yStride = CVPixelBufferGetBytesPerRowOfPlane(pixelBuffer, 0);
    uint8_t *yBase = (uint8_t *)CVPixelBufferGetBaseAddressOfPlane(pixelBuffer, 0);

    // 按行拷贝：只取有效像素，跨过 stride 填充
    uint8_t *yData = malloc(yWidth * yHeight);
    for (int row = 0; row < yHeight; row++) {
        memcpy(yData + row * yWidth, yBase + row * yStride, yWidth);
    }

    // ③ 读 UV 平面（NV12 的 UV 是交织的）
    size_t uvWidth  = CVPixelBufferGetWidthOfPlane(pixelBuffer, 1);
    size_t uvHeight = CVPixelBufferGetHeightOfPlane(pixelBuffer, 1);
    size_t uvStride = CVPixelBufferGetBytesPerRowOfPlane(pixelBuffer, 1);
    uint8_t *uvBase = (uint8_t *)CVPixelBufferGetBaseAddressOfPlane(pixelBuffer, 1);

    size_t uvSize = uvStride * uvHeight;  // 注意用 stride 而非 width
    uint8_t *uvData = malloc(uvSize);
    memcpy(uvData, uvBase, uvSize);

    // ④ ★ 解锁——这一步必须在数据用完之前调用
    CVPixelBufferUnlockBaseAddress(pixelBuffer, kCVPixelBufferLock_ReadOnly);

    // 现在 yData + uvData 是紧凑 NV12，可以喂 TFLite / 存 JPEG
    // ...

    free(yData);
    free(uvData);
}
```

> ⚠️ `CVPixelBufferLockBaseAddress` 的性能代价比 Android 的 `ByteBuffer.get()` 更重：它不仅同步 CPU/GPU，还会触发 **detile**（GPU tiled 布局 → 线性重排）。对于 1080p 帧，单次 lock 可能耗时 2~5ms。热路径里**绝对不要这么做**。

#### 2.4.7 VideoToolbox 解码渲染——面试高频追问

**Q1：VTDecompressionSession 为什么必须先有 CMVideoFormatDescription？**

> 因为 Apple 的解码器在设计上把"格式"和"数据"完全分离——解码会话创建时需要知道 SPS/PPS 来初始化 DPB（解码图像缓冲）、参考帧管理、输出 pixel buffer 的尺寸和格式。这点和 Android 的 `MediaCodec.configure` 要求传 `csd-0/csd-1` 是一样的逻辑，只是 iOS 把它抽取成了一个独立的 `CMVideoFormatDescription` 对象。

**Q2：CVMetalTextureCache 的"零拷贝"到底怎么成立的？**

> 三步：① `CVPixelBuffer` 底层是 **IOSurface**（内核管理的 GPU 内存，有全局 ID）；② `CVMetalTextureCacheCreateTextureFromImage` 内部调 `IOSurfaceLookup` 通过 ID 找到同一块内存，然后创建 `MTLTexture` 把这块内存**重新解释**为另一个像素格式（Y 平面→`r8`、UV 平面→`rg8`）；③ Metal shader 直接对这块内存采样。全程**没有 memcpy、没有 CPU 中转**。这跟 Android 的 `SurfaceTexture` → EGL `glEGLImageTargetTexture2DOES` → GL OES 纹理是同一套零拷贝三件套（共享内存 + 格式重解释 + GPU 直接采样）。

**Q3：怎么强制使用硬件解码？系统会回退到软件吗？**

> 在 `VTDecompressionSessionCreate` 时不指定具体 codec（传 NULL），系统会根据格式自动选择硬件（优先）或软件（硬件不支持该 profile 时回退）。要**强制硬件**，需要在创建时指定：
>
> ```objc
> CFMutableDictionaryRef spec = CFDictionaryCreateMutable(...);
> CFDictionarySetValue(spec,
>     kVTVideoDecoderSpecification_RequireHardwareAcceleratedVideoDecoder,
>     kCFBooleanTrue);
> VTDecompressionSessionCreate(..., spec, dstAttrs, &cbRecord, &_session);
> ```
>
> 强制硬件后如果不支持，`VTDecompressionSessionCreate` 直接返回错误（通常是 -8973），不会默默回退软件。生产环境通常**不强制**、让系统自动选，但要能通过 `VTDecompressionSessionCopySupportedPropertyDictionary` 查询实际选了什么。

**Q4：`CVPixelBufferRetain`/`Release` 和 ARC 的关系是什么？不做 retain 会怎样？**

> `CVPixelBuffer` 是 CoreFoundation 对象，ARC 不管它（除非 bridge 到 ObjC）。在解码回调里，`imageBuffer` 的生命周期由解码器的 pixel buffer pool 管理——回调返回后如果没有任何 retain，它**可能在下一个 callback 发生时被复用/覆盖**。因此：
> - **同线程同步使用**（比如回调里直接调 Metal draw，同步等待 GPU 完成）：不需要 retain——GPU 命令提交后你不再访问这块内存。
> - **跨线程异步使用**（dispatch 到渲染线程，存在"排队"）：**必须**在回调里 `CVPixelBufferRetain(imageBuffer)`，渲染线程用完再 `CVPixelBufferRelease`。否则渲染线程还在读的时候，解码器已经把它复用了——结果画面撕裂或 crash。

**Q5：`AVSampleBufferDisplayLayer` 和 Metal 自渲染怎么选？**

> - `AVSampleBufferDisplayLayer`：不需要后处理（滤镜/美颜/水印），纯粹播放。系统自动处理渲染时机、VSync、画面缩放。码率少、省电。
> - Metal 自渲染：需要后处理或自定义合成。你的 shader 可以是 YUV→RGB + 锐化 + 色彩查找表（LUT）+ 画中画合成。成本是高一些的开发工作量和 GPU 功耗。
> - 两者可以共存：渲染链路上先 Metal 处理好，再上屏或用 `AVSampleBufferDisplayLayer` 做最终呈现。

### 2.5 MediaCodec vs VideoToolbox 解码渲染横向对比

| 维度 | Android MediaCodec | iOS VideoToolbox |
|------|-------------------|------------------|
| **解码输出载体** | Surface（java）/ ByteBuffer | CVPixelBuffer（IOSurface 后端） |
| **零拷贝机制** | gralloc → dma-buf fd → EGLImage → OES 纹理，四步全传引用 | IOSurface ID → CVMetalTextureCache alias → MTLTexture |
| **零拷贝渲染路径** | SurfaceTexture + `updateTexImage()` → GLES `samplerExternalOES` | CVMetalTextureCache → `MTLTexture` alias |
| **GPU API** | OpenGL ES 2.0+（OES 外部纹理 + 自定义 YUV→RGB shader） | Metal（MTLTexture + 自定义 fragment shader） |
| **颜色格式** | NV12（gralloc 内部可能 tiled，但 GL 纹理单元硬件自动处理） | 统一 NV12（`BiPlanarVideoRange`，线性排布） |
| **stride 对齐** | 有，但 Surface 模式系统处理 | 有 `BytesPerRowOfPlane` 显式查询 |
| **驱动模式** | 同步（dequeue 轮询）/ 异步（setCallback） | 只有异步（回调） |
| **纯播放最简方案** | SurfaceView + `releaseOutputBuffer(idx, true)` | `AVSampleBufferDisplayLayer` enqueue |
| **带后处理标准方案** | SurfaceTexture + GLES + OES 纹理 + 自定义 shader | CVMetalTextureCache + Metal + 自定义 fragment shader |
| **解码前配置门槛** | `configure` 传 csd-0/csd-1（SPS/PPS）+ width/height | 先创建 `CMVideoFormatDescription`（含 SPS/PPS）+ 后创建 `VTDecompressionSession` |
| **比特流格式** | 吃 Annex-B（`00 00 00 01`） | 吃 AVCC（4 字节长度前缀） |
| **硬件强制** | 创建 `MediaCodecList` 遍历选厂商 codec（`OMX.qcom.*`/`c2.qti.*`） | `RequireHardwareAcceleratedVideoDecoder = true` |
| **收尾** | `stop()` → `release()` | `VTDecompressionSessionInvalidate` + CFRelease |
| **核心坑** | ByteBuffer 颜色格式碎片化（tiled 无解） | LockBaseAddress 触发 detile + 同步 stall |

### 2.6 面试速答模板（口语化，张嘴就能用）

**Q：MediaCodec 解码到渲染，整个过程是怎样的？**

> "Android 解码到渲染的核心路径是 **OpenGL ES + SurfaceTexture 零拷贝**。先说数据怎么走的：解码器输出的不是 CPU 内存，是 gralloc 分配的 GPU 内存。`releaseOutputBuffer(idx, true)` 在底层做的是把这块内存的 dma-buf fd 通过 BufferQueue 推进去——**只传一个文件描述符、不拷贝像素**。然后 GL 线程调 `SurfaceTexture.updateTexImage()`，里面做了三件事：acquireBuffer 拿到 fd → `eglCreateImageKHR` 把 fd 包成 EGLImage → `glEGLImageTargetTexture2DOES` 把 EGLImage 绑定为 OES 外部纹理。之后在 fragment shader 里用 `samplerExternalOES` 采样这个纹理、做 YUV→RGB 矩阵转换，需要滤镜美颜就在这步一起做。最后 `glDrawArrays` 渲染到 EGL Surface 上屏。整条链路 gralloc → dma-buf → EGLImage → OES 纹理，四步全是引用传递。"

**Q：那零拷贝怎么证明？你怎么知道没有 CPU memcpy？**

> "两个证据。**代码层面**：整条链路没有 `memcpy`、没有 `glTexImage2D`（那个才是上传数据到 GPU）、没有 `ByteBuffer.get()`。`updateTexImage()` 调用的是 `glEGLImageTargetTexture2DOES`——这个函数就是改纹理的页表指向，不搬运数据。**性能层面**：1080p 一帧的 NV12 数据量是 3MB，如果每次都要从解码器 GPU 内存拷到 GL 纹理，在 60fps 下就是 180MB/s 的 DDR 带宽——你用 `systrace` 或 Perfetto 看 memory bus 能直接观测到。SurfaceTexture 模式下这条线上没有对应量级的带宽消耗，就是零拷贝的铁证。"

**Q：为什么非要用 samplerExternalOES 而不能用 sampler2D？**

> "因为数据格式不一样。`sampler2D` 期望纹理内部是 RGBA 排列，如果你把 NV12 的 GPU 内存直接当 RGBA 采样——Y 被当 R 读、U 被当 G 读、V 被当 B 读——颜色全错。`samplerExternalOES` 告诉 GL 驱动'这块内存的格式是外部决定的、采样时别做隐式格式转换'。驱动就会用纹理单元的原始采样能力去读，然后你在 shader 里自己拿 Y、U、V 分量、自己做矩阵乘转 RGB。这就是 EGLImage 的意义——绕过 GL 的格式假设，让你直接操作原始 YUV 内存。"

**Q：VideoToolbox 解码到渲染呢？**

> "VideoToolbox 解码有个前置步骤：必须先拿 SPS/PPS 建 `CMVideoFormatDescription`，然后才能创建 `VTDecompressionSession`。解码是纯异步的——`VTDecompressionSessionDecodeFrame` 喂进去，结果在回调里拿 `CVPixelBuffer`。渲染走 `CVMetalTextureCache`，把 `CVPixelBuffer` 的每个平面零拷贝 alias 成 `MTLTexture`——亮度是 `r8`、色度是 `rg8`——然后在 Metal fragment shader 里做 YUV 转 RGB。全程 IOSurface 同一块内存，不下 CPU。纯播放更简单，用 `AVSampleBufferDisplayLayer` 直接 enqueue 就行。"

**Q：两端最大的共同点和差异点？**

> "共同点：都是硬件解码到 GPU 内存、GPU 驱动直接采样做零拷贝渲染。底层都是同一套模式——**共享 GPU 内存（gralloc / IOSurface）+ 格式重解释（EGLImage / CVMetalTextureCache）+ shader 直读**——物理上数据从来没离开过 GPU 显存。
>
> 差异点：四件事——**第一，零拷贝桥接件**：Android 是 `dma-buf fd → EGLImage → OES 纹理` 这条内核态的路径，iOS 是 `IOSurface ID → CVMetalTextureCache → MTLTexture` 用户态的路径。本质一样，但 Android 多了一层内核 dma-buf 的参与。**第二，颜色格式**，iOS 很统一就是线性 NV12，Android gralloc 内可能是 tiled 排布——但 GL 纹理单元硬件自动 detile，shader 不需要关心。**第三，API 风格**，Android 有同步异步两种模式，iOS 只有异步回调。**第四，比特流格式正好相反**——MediaCodec 吃 Annex-B 吐 Annex-B，VideoToolbox 吃 AVCC 吐 AVCC——跨平台代码在这两个地方的处理逻辑正好是反的，最容易翻车。"

### 2.7 如何用 MediaCodec 在 RTMP 直播时发送 SPS/PPS

这是做 Android 直播推流**必踩的坑**。面试官问这个，本质在考察你对 H.264 码流格式和 RTMP 协议协商的理解深度。

#### 2.7.0 先理解为什么这问题值得单独拿出来考

RTMP 推流有两步关键初始化：

1. **RTMP 握手 + connect + createStream + publish**（信令层）
2. **发送 `AVCDecoderConfigurationRecord`（也叫 `avcC` / sequence header）**——这里面装的就是 SPS 和 PPS。没有这一步，对端解码器根本不知道码流的高宽、profile、level，拿到 I 帧也解不了

而 MediaCodec 编码器**不会自动把 SPS/PPS 内联在编码数据里**——它把 SPS/PPS 当作"元数据"、通过 `MediaFormat` 的 csd-0/csd-1 单独暴露。同时，MediaCodec 输出的码流是 Annex-B（起始码 `00 00 00 01`），而 RTMP/FLV 要的是 AVCC（4 字节长度前缀）。两件事夹在一起，就是这道题的考察点。

#### 2.7.1 完整时序：MediaCodec 编码 → RTMP 推流

```
MediaCodec 状态流转:

  createEncoderByType("video/avc")
       │
       ▼
  [Stopped] ── configure(format,...) ──► [Configured]
                                              │
                                        start() │
                                              ▼
                                         [Running]
                                              │
                    onOutputFormatChanged ◄────┘ ★ SPS/PPS 在这里拿到
                         │
                         ├─► 发送 RTMP sequence header（第一件事，只发一次）
                         │
                    onOutputBufferAvailable ──► 逐个收到编码帧
                         │
                         ├─► 检查 I 帧 → 重新发送 sequence header（部分服务器要求）
                         ├─► Annex-B → AVCC 转换（起始码 → 4 字节长度前缀）
                         ├─► 封装成 FLV Video Tag
                         └─► 通过 RTMP 发送
```

**四个关键时刻**：

| 时刻 | 发生了什么 | 你的动作 |
|---|---|---|
| `onOutputFormatChanged` | 编码器吐出了 SPS/PPS，封装在 MediaFormat 的 csd-0/csd-1 里 | **立即提取 SPS/PPS，组装 avcC sequence header，通过 RTMP 发出去** |
| 每个编码帧 (`onOutputBufferAvailable`) | 拿到编码后的 H.264 Annex-B 码流 | Annex-B → AVCC，封装 FLV Tag，发送 |
| 每次 I 帧/keyframe | 解码器可能需要在 GOP 边界重新初始化 | 部分 CDN/服务器要求在 I 帧前重发 sequence header |
| 编码器重建时（如动态改码率/分辨率） | SPS/PPS 可能变化 | 必须比对新的 csd-0/csd-1，如果变了则重发 sequence header |

#### 2.7.2 第一步：从 onOutputFormatChanged 拿 SPS/PPS

这是最容易翻车的一步——**不是所有编码器都在 start() 之后立刻回调 onOutputFormatChanged**。有些设备（尤其是高通低端芯片）要等第一批编码帧产出后才会回调。

```java
// ==================== 编码器初始化 ====================
MediaCodec encoder = MediaCodec.createEncoderByType("video/avc");

MediaFormat format = MediaFormat.createVideoFormat("video/avc", 1920, 1080);
format.setInteger(MediaFormat.KEY_BIT_RATE,          4000000);
format.setInteger(MediaFormat.KEY_FRAME_RATE,        30);
format.setInteger(MediaFormat.KEY_I_FRAME_INTERVAL,  2);  // 2 秒一个 I 帧
format.setInteger(MediaFormat.KEY_COLOR_FORMAT,
    MediaCodecInfo.CodecCapabilities.COLOR_FormatSurface);

encoder.configure(format, null, null, MediaCodec.CONFIGURE_FLAG_ENCODE);

encoder.setCallback(new MediaCodec.Callback() {
    // ==================== ★ 核心：这里拿 SPS/PPS ====================
    @Override
    public void onOutputFormatChanged(MediaCodec codec, MediaFormat newFormat) {
        // newFormat 是编码器在 start() 之后、产出第一批编码数据时回调的
        // csd-0 = SPS, csd-1 = PPS（H.265 的话还有 csd-2 = VPS）

        ByteBuffer spsBuffer = newFormat.getByteBuffer("csd-0");
        ByteBuffer ppsBuffer = newFormat.getByteBuffer("csd-1");

        if (spsBuffer == null || ppsBuffer == null) {
            Log.e(TAG, "SPS/PPS 为 null——这台设备的编码器还没准备好");
            // ★ 应对：有的设备（尤其是高通早期芯片）第一次 onOutputFormatChanged
            //    不包含 csd。此时需要等第二个 output buffer 出来后再取 SPS/PPS
            return;
        }

        byte[] sps = new byte[spsBuffer.remaining()];
        byte[] pps = new byte[ppsBuffer.remaining()];
        spsBuffer.get(sps);
        ppsBuffer.get(pps);

        // ★ 关键：csd-0/csd-1 拿到的就是裸 SPS/PPS NALU 字节
        //   没有起始码（00 00 00 01），也没有长度前缀。
        //   它是纯粹的 NAL unit body——从 NAL header（sps[0] & 0x1F == 7）开始。

        Log.d(TAG, String.format("SPS: %d bytes, PPS: %d bytes, NAL type SPS=%d PPS=%d",
            sps.length, pps.length, sps[0] & 0x1F, pps[0] & 0x1F));

        // 保存下来——后续每次发 I 帧时可能需要重发
        currentSPS = sps;
        currentPPS = pps;

        // ★★★ 发送 RTMP sequence header（见 2.7.3）★★★
        sendRTMPSequenceHeader(sps, pps);
    }

    // ==================== 编码输出 ====================
    @Override
    public void onOutputBufferAvailable(MediaCodec codec, int index,
                                         MediaCodec.BufferInfo info) {
        ByteBuffer outBuf = codec.getOutputBuffer(index);
        if (outBuf == null) {
            codec.releaseOutputBuffer(index, false);
            return;
        }

        boolean isKeyFrame = (info.flags & MediaCodec.BUFFER_FLAG_KEY_FRAME) != 0;

        // ★ 部分 CDN（如阿里云、腾讯云）要求每个 I 帧前重发 sequence header
        if (isKeyFrame && currentSPS != null && currentPPS != null) {
            sendRTMPSequenceHeader(currentSPS, currentPPS);
        }

        // ★ Annex-B → AVCC + 封装 FLV Tag + 发送（见 2.7.4）
        byte[] encodedData = new byte[info.size];
        outBuf.position(info.offset);
        outBuf.get(encodedData, 0, info.size);

        sendEncodedFrame(encodedData, isKeyFrame, info.presentationTimeUs);

        codec.releaseOutputBuffer(index, false);
    }

    @Override
    public void onError(MediaCodec codec, MediaCodec.CodecException e) {
        Log.e(TAG, "编码器错误: " + e.getDiagnosticInfo());
    }

    @Override
    public void onInputBufferAvailable(MediaCodec codec, int index) {
        // 喂原始帧（从 Camera/GL 拿数据）...
    }
});

encoder.start();
```

#### 2.7.3 第二步：组装 AVCDecoderConfigurationRecord（avcC）

RTMP 的 sequence header 不是直接把 SPS/PPS 字节丢过去——而是封装成 **AVCDecoderConfigurationRecord**（ISO 14496-15，也就是 MP4 文件里 `avcC` box 的结构）。

```
AVCDecoderConfigurationRecord 结构（字节布局）:

 ┌──────────────────────────────────────────────────────────┐
 │  configurationVersion = 0x01          (1 byte)            │
 │  AVCProfileIndication = sps[1]        (1 byte)  ← 从 SPS │
 │  profile_compatibility  = sps[2]      (1 byte)            │
 │  AVCLevelIndication     = sps[3]      (1 byte)            │
 │  lengthSizeMinusOne     = 0xFF        (1 byte)  ← FLV 用 4│
 │  [低 2 位有意义，实际值 3 表示 NALU 长度前缀 = 4 字节]      │
 │  numOfSequenceParameterSets  & 0x1F   (1 byte)  ← SPS 个数│
 │  ┌──────────────────────────────────────────────────────┐ │
 │  │ SPS 长度 (2 bytes, big-endian)                       │ │
 │  │ SPS 数据 (spsLength bytes)  ← 裸 NALU，无起始码       │ │
 │  └──────────────────────────────────────────────────────┘ │
 │  numOfPictureParameterSets           (1 byte)  ← PPS 个数│
 │  ┌──────────────────────────────────────────────────────┐ │
 │  │ PPS 长度 (2 bytes, big-endian)                       │ │
 │  │ PPS 数据 (ppsLength bytes)  ← 裸 NALU，无起始码       │ │
 │  └──────────────────────────────────────────────────────┘ │
 └──────────────────────────────────────────────────────────┘
```

```java
/**
 * 将 SPS/PPS 组装成 RTMP/FLV 用的 AVCDecoderConfigurationRecord (avcC)
 *
 * @param sps  裸 SPS NALU（不含起始码，csd-0 直接就是）
 * @param pps  裸 PPS NALU（不含起始码，csd-1 直接就是）
 * @return 完整的 avcC 字节数组，可直接写入 FLV Video Tag body
 */
public static byte[] buildAVCDecoderConfigurationRecord(byte[] sps, byte[] pps) {
    // avcC 总长度 = 7 字节头部 + 2 字节 SPS 长度 + SPS 数据 + 1 字节 PPS 计数 + 2 字节 PPS 长度 + PPS 数据
    int totalLen = 7 + 2 + sps.length + 1 + 2 + pps.length;
    ByteBuffer buf = ByteBuffer.allocate(totalLen);

    // ① configurationVersion = 1
    buf.put((byte) 0x01);

    // ② AVCProfileIndication（SPS 的第 2 个字节，即 NALU 头之后的第一个字节）
    buf.put(sps[1]);  // profile_idc: 66=Baseline, 77=Main, 100=High

    // ③ profile_compatibility
    buf.put(sps[2]);

    // ④ AVCLevelIndication
    buf.put(sps[3]);

    // ⑤ lengthSizeMinusOne = 0xFF
    //    实际有效值在低 2 位：0xFF & 0x03 = 3 → NALU 长度前缀 = 4 字节
    buf.put((byte) 0xFF);

    // ⑥ numOfSequenceParameterSets: 低 5 位 = 1（E0 = 1110 0000，| 1 = 1110 0001）
    buf.put((byte) (0xE0 | 0x01));

    // ⑦ SPS 长度（2 bytes, big-endian）
    buf.putShort((short) sps.length);

    // ⑧ SPS 数据（裸 NALU）
    buf.put(sps);

    // ⑨ numOfPictureParameterSets = 1
    buf.put((byte) 0x01);

    // ⑩ PPS 长度（2 bytes, big-endian）
    buf.putShort((short) pps.length);

    // ⑪ PPS 数据（裸 NALU）
    buf.put(pps);

    return buf.array();
}
```

**面试常见追问**：

> "为什么 configurationVersion 固定是 1？"——这是 ISO 14496-15 规定的，含义是"这个 avcC 是按标准版本 1 的格式编的"。所有 H.264 的 avcC 都是 1。

> "lengthSizeMinusOne 为什么是 0xFF 而不是 0x03？"——因为 RTMP/FLV 规定只用 **低 2 位** 表示 (NALU 长度字节数 - 1)。0xFF 的低 2 位 = 0x03，表示长度前缀 4 字节。写成 0xFF 是因为其他高位预留。实际只有低 2 位有意义——对端解析时做 `& 0x03`。

> "profile_idc 怎么读？sps[1] 一定对吗？"——SPS 的 NAL header byte 是 `sps[0]`（`forbidden_zero_bit(1) + nal_ref_idc(2) + nal_unit_type(5)`），NAL unit body 的第一个字节从 `sps[1]` 开始。这个字节就是 `profile_idc`。66=Baseline、77=Main、100=High。要记住这三个数，面试时听到就抬手答。

#### 2.7.4 第三步：发送 RTMP sequence header

```java
private void sendRTMPSequenceHeader(byte[] sps, byte[] pps) {
    byte[] avcC = buildAVCDecoderConfigurationRecord(sps, pps);

    // === FLV Video Tag 结构 ===
    // Tag Header (11 bytes):
    //   Tag Type (1 byte):  0x09 = video
    //   Data Size  (3 bytes): body 长度
    //   Timestamp  (3 bytes): sequence header 用 0
    //   TimestampExtended (1 byte): 0
    //   StreamID   (3 bytes): 0
    //
    // Video Tag Body:
    //   Frame Type (4 bits) + CodecID (4 bits): 0x17
    //     0x1 = keyframe, 0x7 = AVC (H.264)
    //   AVCPacketType (1 byte): 0x00 = sequence header
    //     ★ 0x00 = sequence header, 0x01 = NALU, 0x02 = end of sequence
    //   CompositionTime (3 bytes): sequence header 用 0x000000
    //   AVCDecoderConfigurationRecord (avcC 数据)

    int bodySize = 1 + 1 + 3 + avcC.length;  // FrameType+CodecID + AVCPacketType + CompositionTime + avcC

    ByteBuffer flvTag = ByteBuffer.allocate(11 + bodySize);

    // --- FLV Tag Header ---
    flvTag.put((byte) 0x09);           // Tag Type = video
    flvTag.put((byte) ((bodySize >> 16) & 0xFF));  // Data Size (3 bytes, big-endian)
    flvTag.put((byte) ((bodySize >> 8)  & 0xFF));
    flvTag.put((byte) (bodySize & 0xFF));
    flvTag.put((byte) 0x00);           // Timestamp (3 bytes): sequence header = 0
    flvTag.put((byte) 0x00);
    flvTag.put((byte) 0x00);
    flvTag.put((byte) 0x00);           // TimestampExtended
    flvTag.put((byte) 0x00);           // StreamID (3 bytes) = 0
    flvTag.put((byte) 0x00);
    flvTag.put((byte) 0x00);

    // --- Video Tag Body ---
    flvTag.put((byte) 0x17);           // FrameType(4bit)=1(keyframe) + CodecID(4bit)=7(AVC)
    flvTag.put((byte) 0x00);           // AVCPacketType = 0 (sequence header)
    flvTag.put((byte) 0x00);           // CompositionTime (3 bytes) = 0
    flvTag.put((byte) 0x00);
    flvTag.put((byte) 0x00);
    flvTag.put(avcC);                  // AVCDecoderConfigurationRecord

    byte[] tagData = flvTag.array();

    // --- 加上 FLV PreviousTagSize (4 bytes) ---
    int previousTagSize = 11 + bodySize;  // 上一个 Tag 的总大小（包括 Tag Header）

    // 通过 RTMP 发送：tagData + previousTagSize 的 4 字节大端表示
    rtmpConnection.write(tagData);
    rtmpConnection.write(new byte[] {
        (byte) ((previousTagSize >> 24) & 0xFF),
        (byte) ((previousTagSize >> 16) & 0xFF),
        (byte) ((previousTagSize >> 8)  & 0xFF),
        (byte) (previousTagSize & 0xFF)
    });
}
```

#### 2.7.5 第四步：编码帧发送——Annex-B → AVCC 转换 + FLV 封装

MediaCodec 输出的 H.264 码流是 Annex-B 格式（`00 00 00 01` 起始码分隔每个 NALU）。但 RTMP FLV 要求 AVCC（4 字节长度前缀）。**必须转换**。

```java
/**
 * 将 Annex-B 格式的 H.264 编码帧转为 FLV Video Tag 并发送
 *
 * @param annexBData  MediaCodec 输出的 Annex-B 编码数据
 * @param isKeyFrame  是否为关键帧（BUFFER_FLAG_KEY_FRAME）
 * @param ptsUs       presentation timestamp in microseconds
 */
private void sendEncodedFrame(byte[] annexBData, boolean isKeyFrame, long ptsUs) {
    // ===== 第一步：Annex-B → AVCC =====
    // Annex-B:  [00 00 00 01 | NALU1 data] [00 00 00 01 | NALU2 data] ...
    // AVCC:     [4-byte NALU1 length | NALU1 data] [4-byte NALU2 length | NALU2 data] ...
    //
    // 转换：遍历数据，找到每个 00 00 00 01，替换为 4 字节大端 NALU 长度

    List<byte[]> nalUnits = new ArrayList<>();

    int offset = 0;
    while (offset < annexBData.length - 4) {
        // 找下一个起始码
        int startCodeLen = 0;
        if (annexBData[offset] == 0x00 && annexBData[offset + 1] == 0x00
                && annexBData[offset + 2] == 0x00 && annexBData[offset + 3] == 0x01) {
            startCodeLen = 4;  // 4 字节起始码
        } else if (annexBData[offset] == 0x00 && annexBData[offset + 1] == 0x00
                && annexBData[offset + 2] == 0x01) {
            startCodeLen = 3;  // 3 字节起始码（也合法，SPS/PPS 编码器有时用 3 字节）
        } else {
            offset++;
            continue;
        }

        int naluStart = offset + startCodeLen;

        // 找到下一个起始码的位置（= 当前 NALU 的结束位置）
        int naluEnd = naluStart;
        while (naluEnd < annexBData.length - 3) {
            if ((annexBData[naluEnd] == 0x00 && annexBData[naluEnd + 1] == 0x00
                    && annexBData[naluEnd + 2] == 0x01) ||
                (annexBData[naluEnd] == 0x00 && annexBData[naluEnd + 1] == 0x00
                    && annexBData[naluEnd + 2] == 0x00 && annexBData[naluEnd + 3] == 0x01)) {
                break;
            }
            naluEnd++;
        }

        // 截取当前 NALU
        int naluLen = naluEnd - naluStart;
        if (naluLen > 0) {
            byte[] nalu = new byte[naluLen];
            System.arraycopy(annexBData, naluStart, nalu, 0, naluLen);
            nalUnits.add(nalu);
        }

        offset = naluEnd;
    }

    // ===== 第二步：组装 AVCC 格式的编码数据 =====
    int avccLen = 0;
    for (byte[] nalu : nalUnits) {
        avccLen += 4 + nalu.length;  // 4 字节长度前缀 + NALU 数据
    }

    ByteBuffer avccBuf = ByteBuffer.allocate(avccLen);
    for (byte[] nalu : nalUnits) {
        avccBuf.putInt(nalu.length);  // ★ 4 字节大端长度前缀
        avccBuf.put(nalu);
    }
    byte[] avccData = avccBuf.array();

    // ===== 第三步：封装 FLV Video Tag =====
    // Video Tag Body:
    //   FrameType(4) + CodecID(4): keyframe=0x17, non-keyframe=0x27
    //   AVCPacketType: 0x01 = NALU
    //   CompositionTime (3 bytes): PTS - DTS 的偏移，通常 I/P 帧 = 0
    //   Data: AVCC 格式的编码数据

    int bodySize = 1 + 1 + 3 + avccData.length;

    ByteBuffer flvTag = ByteBuffer.allocate(11 + bodySize);

    // FLV Tag Header
    flvTag.put((byte) 0x09);
    flvTag.put((byte) ((bodySize >> 16) & 0xFF));
    flvTag.put((byte) ((bodySize >> 8)  & 0xFF));
    flvTag.put((byte) (bodySize & 0xFF));
    int ts = (int) (ptsUs / 1000);  // FLV timestamp 单位是毫秒
    flvTag.put((byte) ((ts >> 16) & 0xFF));
    flvTag.put((byte) ((ts >> 8)  & 0xFF));
    flvTag.put((byte) (ts & 0xFF));
    flvTag.put((byte) ((ts >> 24) & 0xFF));  // TimestampExtended
    flvTag.put((byte) 0x00);
    flvTag.put((byte) 0x00);
    flvTag.put((byte) 0x00);

    // Video Tag Body
    byte frameTypeAndCodec = isKeyFrame ? (byte) 0x17 : (byte) 0x27;
    // 0x17 = keyframe(1) + AVC(7); 0x27 = inter frame(2) + AVC(7)
    flvTag.put(frameTypeAndCodec);
    flvTag.put((byte) 0x01);           // AVCPacketType = 1 (NALU)
    flvTag.put((byte) 0x00);           // CompositionTime (3 bytes)
    flvTag.put((byte) 0x00);
    flvTag.put((byte) 0x00);
    flvTag.put(avccData);              // ★ AVCC 格式的 NALU 数据

    byte[] tagData = flvTag.array();

    // 发送 FLV Tag
    rtmpConnection.write(tagData);

    // 发送 PreviousTagSize
    int previousTagSize = 11 + bodySize;
    rtmpConnection.write(new byte[] {
        (byte) ((previousTagSize >> 24) & 0xFF),
        (byte) ((previousTagSize >> 16) & 0xFF),
        (byte) ((previousTagSize >> 8)  & 0xFF),
        (byte) (previousTagSize & 0xFF)
    });
}
```

#### 2.7.6 完整流程时序总结

```
时间线:
  t=0     encoder.start()
  t=10ms  onOutputFormatChanged ← SPS/PPS 可能在这里拿到（取决于设备）
            │
            ├─► csd-0 (SPS), csd-1 (PPS)
            ├─► buildAVCDecoderConfigurationRecord(sps, pps)
            └─► 发送 FLV Video Tag [AVCPacketType = 0x00 = sequence header]
                   ★ 这一步必须在任何编码帧之前发完

  t=33ms  onOutputBufferAvailable  ← 第一个编码帧（通常是 I 帧）
            │
            ├─► 检查 BUFFER_FLAG_KEY_FRAME
            ├─► （可选）I 帧前重发 sequence header
            ├─► Annex-B → AVCC 转换
            ├─► 封装 FLV Video Tag [AVCPacketType = 0x01 = NALU]
            └─► 发送

  t=66ms  onOutputBufferAvailable  ← P 帧
            │
            ├─► Annex-B → AVCC 转换
            ├─► 封装 FLV Video Tag [AVCPacketType = 0x01]
            └─► 发送

            │
            ├─► （可选）重发 sequence header
            ├─► Annex-B → AVCC 转换
            └─► 发送

  ...

  结束时:
  encoder.stop()
  encoder.release()
```

#### 2.7.7 三个深度坑（面试加分项）

**坑 1：onOutputFormatChanged 不回调或回调太晚**

> 部分高通低端芯片上，`start()` 之后 `onOutputFormatChanged` 不是立刻回调的——要等第一个 `onOutputBufferAvailable` 出来之后才回调。如果你的代码在 `onOutputFormatChanged` 里才发 sequence header，而此时第一个编码帧已经通过 `onOutputBufferAvailable` 产生了，就容易出现"编码帧到了但 sequence header 还没发"的竞态。解法：**在 `onOutputBufferAvailable` 里检测 `currentSPS == null`，如果是则先不发这帧、等拿到 SPS/PPS 发了 sequence header 之后再发**。或者用一个 `CountDownLatch` / `BlockingQueue` 同步。

**坑 2：SPS/PPS 可能随时间变化**

> 如果编码过程中动态改了分辨率、码率模式、profile，编码器可能会重新生成 SPS/PPS。此时 `onOutputFormatChanged` 会再次回调，**你必须比对旧的 csd 和新的 csd**——如果不同，就立刻重发 sequence header、并在下一个 I 帧前再发一次。否则对端解码器会按旧的 SPS 去解新码流，典型症状是**改分辨率后花屏或画面比例错误**。

**坑 3：不是所有服务器都要在 I 帧前重发 sequence header**

> RTMP 协议规范说的是 sequence header 发一次即可，后续靠 I 帧 + P 帧正常递。但国内的云直播 CDN（阿里云 CDN、腾讯云 CSS）实际实现倾向于"每个 I 帧前重发 sequence header"——因为在弱网丢包时，解码器可能错过第一个 I 帧、进而错过来到服务端的 sequence header。你重发就是给新加入/重连的解码器一个机会。**面试时主动提这一点说明你对线上稳定性有实操经验**。

#### 2.7.8 面试速答模板

**Q：MediaCodec 直播时怎么发 SPS/PPS？**

> "分五步。**第一，拿数据**：编码器回调 `onOutputFormatChanged` 时从 MediaFormat 里取 csd-0（SPS）和 csd-1（PPS）——它们是裸 NALU，没有起始码也没有长度前缀。**第二，组装**：把 SPS/PPS 包成 `AVCDecoderConfigurationRecord`——7 字节头部加 SPS/PPS 各两字节长度前缀再加数据，profile_idc 从 `sps[1]` 读，lengthSizeMinusOne 写 `0xFF`（实际取低 2 位就是 3，表示 4 字节长度前缀）。**第三，封装**：包成 FLV Video Tag，`FrameType=1`、`CodecID=7`、`AVCPacketType=0x00`（sequence header），时间是 0。**第四，发送时机**：必须在第一个编码帧之前发完。如果编码器回调晚于首帧（部分高通芯片有这个行为），要加保护——首帧到了但 SPS/PPS 还没拿到就暂存首帧、等发了 sequence header 再发。**第五，编码帧发送**：MediaCodec 吐出来的是 Annex-B，RTMP 要 AVCC，所以要把 `00 00 00 01` 起始码替换成 4 字节大端 NALU 长度前缀，然后包成 `AVCPacketType=0x01` 的 FLV Video Tag。另外线上做 CDN 兼容时，每个 I 帧前重发一次 sequence header——防止弱网下解码器错过初始 SPS/PPS。"

**Q：为什么序列头叫 avcC 而不是 SPS/PPS？**

> "avcC（AVCDecoderConfigurationRecord）是 ISO 14496-15 定义的一个正式结构名——它不仅仅包含 SPS/PPS 的字节，还包含 profile/level 信息、NAL 长度前缀的字节数、乃至 SPS 的个数和 PPS 的个数。RTMP/FLV 借用了这个结构做 H.264 的参数协商——因为在封装层面，`moov` box 里存 `avcC`、`mdat` 里存编码数据，是一样的设计。把这个结构化名字说对本身就体现你知道规范来源。"

**Q：如果不发 sequence header 会怎样？**

> "从客户端角度：推流端发了 I 帧但没先发 sequence header，服务端的 RTMP ingest 模块收不到有效的 `AVCDecoderConfigurationRecord`，无法初始化 H.264 解码器——它拿到 I 帧数据但没有 SPS/PPS 对照，解码器直接报 `-12909 kVTVideoDecoderBadDataErr` 或 MediaCodec 的 `INFO_OUTPUT_FORMAT_CHANGED` 后的 format 拿不到有效的 csd。从观众角度看：流虽然 publish 成功了，但**黑屏或只有声音没有图像**。从抓包看：wireshark 抓 RTMP 流的第一个 video tag 的 AVCPacketType 是 0x01（NALU）而不是 0x00（sequence header），就是这个问题。"

### 2.8 avcodec_find_stream_info 底层原理是什么？

这是音视频开发中高级岗位的**经典深水区题**。面试官问这个，不是考你知不知道这个函数——是考你**有没有真正看过 FFmpeg 源码、懂不懂探针（probing）和解码器生命周期**。

#### 2.8.0 先定调：这个函数到底在干什么

`avcodec_find_stream_info()` 的职责用一句话说：

> "在不解码整个文件的前提下，**读一小部分数据、尝试解码、然后把解码出来的真实参数（宽高/像素格式/帧率/码率/时长）填回 `AVStream->codecpar`**。因为容器里报的参数经常是错的或者是空白的。"

**为什么容器里的参数不可信？**

| 容器 | 问题 |
|---|---|
| FLV | 老式 FLV 不记录视频宽高、像素格式、profile/level，全是 0 |
| MPEG-TS | 码率、帧率往往不写，或写了错误的估值 |
| Matroska | 写得很完整但 `CodecPrivate` 可能被截断 |
| H.264 Annex-B 裸流 | 根本没有容器头，全靠解析 SPS |
| RTMP 流 | 初始 sequence header 完就不再有元数据，宽高可能在 SPS/PPS 才暴露 |
| 任何格式 | 容器报的是 1920×1080，实际是 1920×1088（编码器对齐填充），不探测就拿错 stride |

**一句话口诀**：容器告诉你"大概是这么个东西"，`avcodec_find_stream_info` 去向实际的编码数据求证——真的打开来解码几帧看看。

#### 2.8.2 四个关键控制参数（面试必问的调优点）

调用 `avcodec_find_stream_info` 之前设 `AVFormatContext` 上的参数，这决定了探针跑多远：

```c
// ==================== 限制探测范围 ====================
// 【probesize】——最多读取多少字节来做探测
//   默认: 5000000 (5 MB)
//   含义: av_read_frame 累计读的字节数超过这个值就不再读新 packet
//   注意: 这是"读入的数据总量"，不是文件偏移量
AVFormatContext *ic = avformat_alloc_context();
ic->probesize = 5000000;

// 【max_analyze_duration】——最多分析多长时间的数据（微秒）
//   默认: 0 (= 内部自动选择，通常是 5 * AV_TIME_BASE = 5 秒)
//   含义: 当探到的 packet pts 超过这个值，停止分析这条 stream
//   ★ 高级知识点：这不是 analyzeduration（见下面的区别）
ic->max_analyze_duration = 5 * AV_TIME_BASE;

// 【fps_probe_size】——用多少帧来估算帧率
//   默认: -1 (= 用 max_analyze_duration / 帧周期 自动算)
//   含义: 必须拿到这么多帧后才停止帧率估算
//   设小一点: 帧率估算不准但更快，设大一点: 帧率更准但更慢
ic->fps_probe_size = 0;  // 0 = 不估算帧率（最快）

// ==================== 用户侧传入的 options（更常用）============
AVDictionary *opts = NULL;

// 【analyzeduration】——和 max_analyze_duration 什么关系?
//   analyzeduration 是用户侧传入的"建议值"（单位微秒）
//   max_analyze_duration 是最终生效的"上限值"
//   如果 analyzeduration < max_analyze_duration → 用用户值
//   如果 analyzeduration = 0 (不设) → 用 max_analyze_duration 的默认值
//   实际代码:
//     av_dict_set(&opts, "analyzeduration", "3000000", 0);  // 限 3 秒
av_dict_set(&opts, "analyzeduration", "3000000", 0);

// 【probesize】——也可以用 option string 传
av_dict_set(&opts, "probesize",   "2000000", 0);  // 限 2 MB

// 【threads】——探测时的解码线程数
av_dict_set(&opts, "threads", "1", 0);  // 探测只用单线程（减少开销）

// 执行探测
avformat_find_stream_info(ic, &opts);
av_dict_free(&opts);
```

**`analyzeduration` vs `max_analyze_duration` 精确区别**（这是能区分真正看过源码和只会调 API 的点）：

```c
// FFmpeg 源码逻辑 (libavformat/utils.c / avformat_find_stream_info):
//
// find_stream_info 内部:
//   if (ic->max_analyze_duration == 0) {
//       max_analyze_duration = 5 * AV_TIME_BASE;  // 默认 5 秒
//   } else {
//       max_analyze_duration = ic->max_analyze_duration;
//   }
//
//   // analyze_duration 由 option "analyzeduration" 传入
//   if (analyze_duration && analyze_duration < max_analyze_duration)
//       max_analyze_duration = analyze_duration;
//
//   最终: duration_limit = max_analyze_duration

// 简单记:
//   AVFormatContext.max_analyze_duration → 代码级默认上限 (5s)
//   option "analyzeduration"            → 用户传入的覆盖值
//   最终取值: min(用户值, 代码上限) 或 代码上限(用户没设)
```

#### 2.8.3 帧率估算算法（内部细节，拉开差距）

这是 `avcodec_find_stream_info` 里最精巧也最容易被问的部分。裸流或 TS 流没有写死帧率，FFmpeg 必须从解码出来的带 pts 的帧反推。

```
帧率估算内部流程:

  解码拿到 N 帧后，记录了三样东西:
    pts_sequence   = [p0, p1, p2, ..., pN]  ← frame->pts
    duration_seq   = [d0, d1, d2, ..., dN]  ← frame->pkt_duration

  四步算法:

  ① compute_frame_duration(ic):
       如果容器写了 tb（time_base）且 frame->pkt_duration > 0:
           用 frame->pkt_duration 直接算帧间隔 → 帧率 = tb.den / (pkt_duration * tb.num)
       如果 frame->duration > 0:
           用 frame->duration
       否则:
           用相邻帧 pts 差分: (p[k+1] - p[k]) * tb

  ② 多数投票 (majority vote):
       收集所有帧间隔（帧间差值），取出现最多的那个作为"标准帧间隔"
       用这个"标准帧间隔"除 AV_TIME_BASE 得到 r_frame_rate

  ③ 异常值剔除:
       丢弃比中位数大 10 倍或小 10 倍的帧间隔（VFR 或编码器丢帧导致）
       丢弃 pts 跳跃超过 100 帧间隔的（seek 点或 gap）

  ④ 写回 AVStream:
       stream->r_frame_rate        = {most_common_interval_den, most_common_interval_num}
       stream->avg_frame_rate       = 总帧数 / 总时长
       stream->codecpar->framerate  = r_frame_rate (如果容器没提供的

  特殊处理:
    - MPEG-TS: 即使容器报了帧率也重新探测（因为 TS 经常错）
    - 变帧率 (VFR): r_frame_rate 设最常见的帧率, avg_frame_rate 是真实平均帧率
    - H.264 编码器内部 frame->pkt_duration 可能为 0 → 靠差分 pts 兜底
```

#### 2.8.4 为什么 avcodec_find_stream_info 这么慢？（三大性能瓶颈）

这也是面试高频追问。在一台普通机器上对 1080p H.264 MP4 调这个函数，典型耗时是**几十到几百毫秒**。

**瓶颈 1：解码器初始化/销毁（最贵）**

```
对每条视频流:
  avcodec_find_decoder   ← 查表，快
  avcodec_alloc_context3 ← 分配，快
  avcodec_open2          ← ★ 慢！软解码器要分配大量内部 buffer、
                           初始化 DSP 函数指针、分配参考帧池(SPS/PPS 缺时还要等)
  [探测循环: 读 N 帧、解码 N 帧]  ← ★ 也慢，但可控
  avcodec_close          ← 释放解码器
  avcodec_free_context   ← 释放 context
```

软解码器（如 H.264）的 `avcodec_open2` 需要几百毫秒。如果文件里有多条视频流（多角度、画中画），每条都要打开关闭解码器一次——时间线性累加。

**瓶颈 2：IO（读取探测数据）**

```
probesize = 5 MB 默认
  如果文件在网络上（HTTP/HLS），5 MB 可能要读 2~3 秒
  如果文件在机械硬盘，5 MB = 5~10 次磁盘 seek
```

这就是为什么在线视频播放器（ijkplayer、ExoPlayer FFmpeg 扩展）通常把 `probesize` 降到 1 MB 甚至 500 KB、`analyzeduration` 降到 1~3 秒。

**瓶颈 3：解码深度不可控**

```
max_analyze_duration = 5 秒 → 对 30fps 的视频就是 150 帧
  每帧 decode 一遍（send_packet → receive_frame）
  150 帧 H.264 1080p 软解 ≈ 150~300ms
```

但编码器可能把第一个 I 帧放在 2 秒的位置（GOP=60、open GOP），这意味着前 59 帧是 P/B 帧、没有 I 帧做参考时解码失败——FFmpeg 会在遇到第一个 I 帧前丢弃解码失败的帧、然后继续读，增加了额外的读取和解码次数。

#### 2.8.5 五大典型坑（面试加分实战经验）

**坑 1：探测出来的宽高和实际容器报的不一样**

> 容器里 AVI/MKV header 写的是 1920×1080，`avcodec_find_stream_info` 解码出来是 1920×1088——因为 H.264 编码时宏块对齐（16×16），1080 % 16 = 8，编码器补了 8 行黑边。解码器从 SPS 里拿到的就是 1088。**不探测你用 1080 去渲染、RGB 转换时行数不对**，画面底部 8 行是垃圾。解法：始终用 `stream->codecpar->width/height`（探测后），而不是容器 header 里的值。显示时再用 `crop` 参数裁掉黑边。

**坑 2：音频流探测后 channel_layout 仍然为 0**

> 很多容器不写 `channel_layout`，只写 `channels`（数量）。探测后 `codecpar->channel_layout` 可能仍然是 0。正确做法：
> ```c
> if (codecpar->channel_layout == 0) {
>     codecpar->channel_layout = av_get_default_channel_layout(codecpar->channels);
> }
> ```

**坑 3：探测多条流时，一条流已经够了、另一条还在等**

> 比如视频流已经拿到了宽高格式，但音频流 0.5 秒内没有完整音频帧（AAC 一帧只有 1024 samples ≈ 23ms @ 44100Hz，但要等 I 帧对齐）。`avcodec_find_stream_info` 是对**所有流的"最晚完成者"**来决定退出时的——你设了 `analyzeduration=3s`，视频 0.1 秒就探完了，但音频可能真要 3 秒。要减少等待：给 `analyzeduration` 精确到刚好覆盖首帧音频的时间。

**坑 4：`avcodec_send_packet` 在探测阶段返回错误——这很正常**

> 探测循环里的 `send_packet` 失败（比如 packet 里没有完整 NALU、还没收到 SPS/PPS），源码内部不是直接放弃——它会**跳过这个 packet、继续读下一个**，直到拿到一个有效帧或者超时。这是预期行为，不是 bug。你在自己的代码里如果写 `if (ret < 0) break;`，就是过早退出了——源码里的循环体是 `if (ret < 0 && ret != AVERROR(EAGAIN) && ret != AVERROR_EOF) break;`。

**坑 5：硬件解码探测比软解更慢甚至失败**

> 如果你在 `codec_ctx->hw_device_ctx` 上提前 attach 了硬件设备上下文，探测循环里的 `avcodec_open2` 会以硬件模式打开解码器——创建 CUDA context、分配显存、初始化 nvdec 等。对 5 秒探测窗口而言，硬件初始化的开销完全盖过了硬解本身的速度优势。更糟的是：某些硬件解码器对不完整帧（探测阶段的第一帧通常就包含不完整 slice）直接报错退出。**推荐做法**：探测阶段用软解码器（不设 hw_device_ctx），探测完拿到参数后关闭，正式解码时再打开硬件解码器。

#### 2.8.6 与 avformat_find_stream_info 的关系

很多人问"`avformat_find_stream_info` 和 `avcodec_find_stream_info` 是一回事吗？"

> `avformat_find_stream_info` 是 FFmpeg 4.x 之后的**新名字**——把旧的 `avformat_find_stream_info` 重写后，底层逻辑大部分移到了 `libavcodec` 里的 `avcodec_find_stream_info`。**现在推荐的调用是 `avformat_find_stream_info`**（libavformat），它会自动调用 `avcodec_find_stream_info` 做解码探测。两者不是一个函数，但调用前者内部会落到后者。面试时你能主动说"旧 API 是 `avformat_find_stream_info`，但内部逻辑是 `avcodec_find_stream_info` 在驱动解码探测"，说明你关注过演进。

实际上，在 FFmpeg 4.0 ~ 5.0 时期，`avformat_find_stream_info` 被标记为 deprecated，推荐用 `avcodec_find_stream_info`。但后来这个 API 变动又被 revert 了，目前在 FFmpeg 6.x/7.x 中两者并存，都用 `avformat_find_stream_info` 作为主入口。真实情况是：`avformat_find_stream_info` 里面会调用 codec 层的探测逻辑。面试时简单说"对外调 `avformat_find_stream_info`，底层会打开解码器做 send/receive 循环来填参数"即可。

#### 2.8.7 有替代方案吗？

如果不需要帧率/时长估算，可以跳过 `avcodec_find_stream_info`，在 `av_read_frame` 之后手动保证参数：

```c
// 方案 1: 完全跳过探测，手动构造参数（仅限你完全了解输入格式）
AVStream *vs = avformat_new_stream(ic, NULL);
vs->codecpar->codec_type = AVMEDIA_TYPE_VIDEO;
vs->codecpar->codec_id   = AV_CODEC_ID_H264;
vs->codecpar->width      = 1920;
vs->codecpar->height     = 1080;
// 不调 avformat_find_stream_info，直接走到 av_read_frame

// 方案 2: 用 avcodec_send_packet / avcodec_receive_frame 自己精准控制
//   只解码一帧，拿到参数后立即 avcodec_close
//   适合实时流场景——延迟 ≥2 帧，比探测 5 秒的延迟可控得多
```

#### 2.8.8 面试速答模板

**Q：avcodec_find_stream_info 底层原理是什么？**

> "这个函数的核心职责是**通过实际解码来验证和填充容器里缺失或不准的编码参数**——因为容器 header 常常不写宽高、像素格式、帧率、码率，或者写的跟实际编码数据不一致。
>
> 内部流程分五步。**第一步，判段**：检查 `codecpar` 里必要参数是否已齐全，如果有了就跳过这条流。**第二步，开解码器**：`avcodec_find_decoder` + `avcodec_open2`——这是最贵的操作，软解 H.264 的 open2 要几百毫秒初始化 DSP 和参考帧池。**第三步，探针循环**：`av_read_frame` 读 packet → `avcodec_send_packet` 送解码 → `avcodec_receive_frame` 收帧，从解码出来的 `AVFrame` 里取真实的 width、height、pix_fmt、sample_rate、channel_layout。循环受 `probesize`（最多读 N 字节上限）和 `analyzeduration`（最多探 N 微秒上限）两个参数控制——前者按 IO 量限、后者按时长限。**第四步，回写**：解码器拿到的参数通过 `avcodec_parameters_from_context` 合并到 `AVStream->codecpar`，然后关闭解码器释放资源。**第五步，帧率估算**：如果容器没给帧率，用已解码帧的 pts 序列做多数投票——去掉异常值后，最常见的帧间隔折算成 `r_frame_rate`。
>
> 最大的性能代价是解码器打开/关闭（每条视频流各一次）加上解码循环。在线播放器一般把 `probesize` 降到 1MB、`analyzeduration` 降到 1~3 秒来减延迟。另外硬件解码在探测阶段是个反模式——初始化 CUDA/VT context 的开销盖过了探测本身，且硬解对不完整帧容忍度差。正确做法是探测阶段用软解、正式播放时再开硬解。"

**Q：如果我不调 avcodec_find_stream_info 直接 read_frame 会怎样？**

> "能读到 packet，但 `stream->codecpar->width/height/pix_fmt` 可能是 0。后续 `avcodec_open2(codec_ctx, codec)` 会因为缺少必要参数直接失败。音频同理——不知道 `sample_rate` 和 `channels`，重采样初始化直接崩。唯一的例外是你完全预先知道编码参数（比如自己做的编码器），可以手动填 `codecpar`，跳过探测。"

**Q：怎么判断是容器报的宽高还是解码出的真实宽高？**

> "FFmpeg 的做法是**解码出的值优先**。`avcodec_find_stream_info` 返回后，`stream->codecpar->width` 是解码器从 SPS 里拿到的真实值。容器原始值是存在 `AVCodecParameters` 内部私有字段里的——源码里用 `internal->orig_width` 保存。你不需要区分，因为你永远应该用解码后的值。唯一需要容器的原始值的场景是：**你想判断解码是否失败**——比较 `internal->orig_width` 和 `codecpar->width`，如果后者是 0 但前者不是，说明解码探测阶段没有拿到有效帧。"

### 2.9 音视频同步（PTS/DTS/时钟选择）——经典深水区

这是音视频开发**最高频的深水区题目**。面试官会从"你怎么做音视频同步"开始，一路往下追问到时钟怎么选、DTS/PTS 为什么要区分的本质原因。

#### 2.9.0 先建立两个前置概念：DTS vs PTS 的本质

**DTS（Decode Time Stamp）——什么时候解码**
**PTS（Presentation Time Stamp）——什么时候显示**

大多数 P 帧、I 帧：DTS ≈ PTS（解码后立刻可显示，没有重排序）。

B 帧：DTS < PTS（解码发生在显示之前的参考帧解码窗口）。

```
一个典型 GOP 的 DTS/PTS 序列（IBBP 模式，display order → decode order）:

  显示顺序 (PTS):  I₀  B₁  B₂  P₃  B₄  B₅  P₆
  解码顺序 (DTS):  I₀  P₃  B₁  B₂  P₆  B₄  B₅
                   ↑     ↑                ↑
                先解 I₀，然后连 P₃ 才能解 B₁ 和 B₂ (B 帧需要双向参考)
                但 P₃ 的显示时刻在 B₁ B₂ 之后 → PTS 更大

  DTS 和 PTS 的差值 = "这一帧在解码后要等多久才能显示"
  同一帧: PTS₃ - DTS₃ = 重排序延迟（reorder delay）
```

**一句话定调 DTS/PTS**：

> "DTS 告诉解码器'这一帧什么时候送进流水线'——保证参考帧已经解出来了。PTS 告诉渲染器'这一帧什么时候上屏'——保证画面以正确的速度播放。B 帧存在时两者分开，因为解码器需要**先解未来的参考帧**，再回过头来解夹在中间的 B 帧。只有 B 帧才会让 DTS ≠ PTS。"

#### 2.9.1 同步的数学模型：三个时钟、两条对齐线

音视频同步的本质是**把两条独立的时间线对到同一个时钟上**。三条时间线分别是：

```
  音频时间线: 音频帧被 DAC 消费的时刻 → audio_clock
  视频时间线: 视频帧被渲染上屏的时刻 → video_clock
  外部时钟:   系统单调时间           → external_clock (sys_clock)
```

**三种同步策略**：

| 策略 | 谁做 Master | 谁做 Slave | 适用场景 | 代价 |
|---|---|---|---|---|
| **音频主时钟** | 音频 | 视频 | 直播、播放器默认 | 音频不能丢/插帧时画质波动 |
| **视频主时钟** | 视频 | 音频 | 录制、纯画面回放 | 音频可能 dropout |
| **外部时钟** | 系统时间 | 两者 | 网络同步、转码 | 两端都可能抖 |

**为什么默认音频做主时钟？**

> 因为人对声音断续的敏感度远超画面丢帧——音频 20ms 的 dropout 你马上听到咔嗒声，而视频 20ms 的丢帧你可能完全没察觉。所以生产环境的默认策略是：**音频以固定节拍往前走，视频去追音频**。

#### 2.9.2 视频追音频的核心算法

每渲染一帧前，算三个数：

```c
// 伪代码——FFmpeg ffplay 的同步逻辑本质就是这个

double audio_clock = get_audio_clock();     // "音频已经播到哪个时刻了"
double video_clock = frame->pts;            // "这一帧应该在哪一时刻显示"
double drift = video_clock - audio_clock;   // 偏差 = 视频相对于音频是超前还是落后

double threshold = 0.01;  // 10ms —— 小于这个不纠

if (fabs(drift) < threshold) {
    // 同步正常，直接渲染
    render_frame(frame);

} else if (drift > 0) {
    // ★ 视频超前了——画面跑在声音前面
    //    策略: 延后渲染 → sleep(drift - threshold) 或等待下一 Vsync
    double delay = drift - threshold;
    // 但不能无限等——上一帧的渲染时刻 + frame_duration 就应该是这帧的最迟时刻
    // 如果 delay > frame_duration → 说明偏差太大，直接丢这帧
    if (delay > frame_duration) {
        av_frame_unref(frame);  // 丢帧——视频太超前了，跳过
    } else {
        schedule_render(frame, delay);  // 延迟渲染
    }

} else {
    // ★ 视频落后了——画面跟不上声音
    //    策略: 立刻渲染（不等）或 丢参考帧、从下一个 I 帧重新起播，或 重复上一帧
    //    worst case: 视频差太多、来不及追 → enter frame drop mode
    double late = -drift;
    if (late > 5 * frame_duration) {
        // 严重落后 (>5 帧): 大 seek 到当前时间点重新起播
        av_seek_frame(ic, audio_clock);
    } else {
        // 轻度落后 (1~3 帧): 立刻渲染当前帧（不等、跳过 sleep）
        render_frame_immediately(frame);
    }
}
```

**视频追音频的三级策略**（面试时能分三级回答是高级）：

```
偏差 < 10ms:   不管（在 JND 阈值内，Just Noticeable Difference）
偏差 10~40ms:  调整渲染延迟（逐帧微调，让视频慢慢赶上或等一等）
偏差 > 40ms:   激进纠偏——丢帧（视频超前）或重复上一帧（视频落后）
偏差 > 200ms:  重新 Seek——重新从当前音频位置找最近的 I 帧起播
```

#### 2.9.3 音频怎么做纠偏？（因为音频不能丢帧）

音频是 Master 的时候视频追音频——**那如果必须视频做主时钟呢？** 音频也要能纠偏。

音频的纠偏手段比视频更精细——不是丢整帧，而是**拉伸/压缩波形**：

```c
// 音频向视频时钟纠偏的做法
// 不能丢音频帧 ← 丢一帧 AAC = 1024 samples ≈ 23ms，就是明显的嗞一声

double audio_diff = audio_clock - video_clock;
// audio_diff > 0 → 音频超前 → 拉长音频（插 sample）
// audio_diff < 0 → 音频落后 → 压缩音频（丢 sample）

if (audio_diff > 0.1) {
    // 音频超前 > 100ms → 插入静音帧
    insert_silence(audio_buffer, audio_diff_ms);
} else if (audio_diff < -0.1) {
    // 音频落后 > 100ms → 丢一个音频帧
    drop_audio_frame();
} else {
    // 微小偏差 → 用重采样器拉伸/压缩（±2% 以内人耳听不出）
    // libswresample: swr_set_compensation(0.02) → 拉伸 2%
    double stretch_ratio = 1.0 + (audio_diff / audio_frame_duration) * 0.01;
    swr_set_compensation(swr_ctx, stretch_ratio, audio_frame_size);
}
```

**面试关键句**："音频纠偏用的是重采样器微调采样率——±2% 以内人耳听不出来。这就是为什么 FFmpeg 的同步代码里频繁调 `swr_set_compensation`。"

#### 2.9.4 时钟模型：ffplay 的三级时钟（FFmpeg 源码视角）

```c
// FFmpeg ffplay.c 的时钟实现（简化）
typedef struct Clock {
    double pts;           // 当前时钟值
    double pts_drift;     // pts 和系统时间的偏移
    double last_updated;  // 上次更新的系统时间
    int    paused;
    int    *queue_serial; // 当前播放队列的序列号（seek 以来）
} Clock;

double get_clock(Clock *c) {
    // ★ 核心公式：时钟的当前值 = pts + 从上次更新以来经过的系统时间
    double time = av_gettime_relative() / 1000000.0;  // 秒
    return c->pts_drift + time;
    // pts_drift = c->pts - c->last_updated
    // 所以: get_clock = pts + (now - last_updated)
}

// 关键：时钟不是直接存当前时间，而是存 "pts - 系统时间" 的差值
// 好处：时钟即使不主动 tick、也能在任何时刻通过 get_clock 取到当前值
//      不需要一个独立线程来更新时钟
```

**面试关键句**：

> "ffplay 的时钟只存一个 `pts_drift`——也就是'pts 和系统时间的差值'。取当前时钟值时，用系统时间 + 差值反算当前 pts。这个设计的好处是**不需要一个独立线程来 tick 时钟**——差值是恒定不变的，系统时间本身就在走，谁调 `get_clock` 谁就能拿到当前时刻的时钟值。"

#### 2.9.5 面试速答模板

**Q：音视频同步怎么做？**

> "核心是选一个主时钟、让另一个去追。默认是音频做主时钟——因为人耳对声音断续的敏感度远高于画面的跳帧。同步算法就是每渲染一帧前算一个偏差：`drift = video_pts - audio_clock`。偏差小于 10ms 不管（在人的感知阈值内）。偏差在 10~40ms 之间，调整渲染延迟——视频超前就多 sleep 一会、延后渲染；视频落后就立刻渲染不等 Vsync。偏差超过 40ms，激进纠偏——超前就丢帧、落后就重复上一帧。偏差到 200ms 以上，直接重新 seek 到音频当前时刻、从最近的 I 帧起播。音频侧如果也要纠偏，用重采样器微调采样率——±2% 以内人耳听不出拉伸。ffplay 的时钟实现是存 pts 和系统时间的差值——`get_clock` = `pts_drift + system_time`，不用独立的时钟 tick 线程。"

**Q：为什么 B 帧会导致 DTS < PTS？**

> "因为 B 帧是双向预测——它要参考**前一帧和后一帧**。所以在解码 B 帧之前，必须先解码它的两个参考帧。这就意味着在解码顺序里，未来的 P 帧要先解出来放 DPB 里等着，等 B 帧来参考。显示时按顺序来——B 帧既然在画面时间上夹在 I 和 P 之间，它的 PTS 就在中间。所以 DTS 是解码顺序（P 在 B 前），PTS 是显示顺序（B 在 P 前），B 帧的 PTS > DTS。没有 B 帧的码流（Baseline Profile、zerolatency）里两者一致。"

### 2.10 直播延迟逐环节拆解——全链路 ms 级分析

这是**高级岗区别于中级岗的标志性问题**。中级能说出"采集→前处理→编码→发送→服务器→分发→播放"，高级能**把每个环节的延迟量级说出来**。

#### 2.10.0 端到端延迟拆解（第一帧采到 → 观众看到）

以 30fps 1080p H.264 直播推流为例，逐个环节的典型延迟：

```
推流端:
  [Camera 采集]         0.5~2ms    ← Sensor 曝光 + 读出（受曝光时间影响）
  [前处理/美颜]          2~8ms     ← OpenGL/Metal shader（GPU 算力决定）
  [编码]                 5~20ms    ← 硬件编码（NVENC/MEC/QCOM HW）
                                     软件编码 x264 veryfast: 10~30ms
  [发送缓冲 + RTT]       10~80ms   ← CDN 边缘节点 RTT（有线 10~20ms, 4G 40~80ms）

                                          ──────── CDN ────────

服务端:
  [Ingest 接收]          1~3ms     ← 收流 + 解 FLV/RTMP
  [转码(可选)]           10~50ms   ← 多码率转码，硬件: 10ms/路，软编: 40ms+/路
  [协议转换(可选)]        2~5ms    ← RTMP→HTTP-FLV/HLS 封装转换
  [分发]                 1~5ms    ← 边缘节点缓存 + 出站

                                          ──────── CDN ────────

播放端:
  [RTT + 接收缓冲]       10~80ms   ← 同推流端的网络延迟
  [Jitter Buffer]        50~500ms  ← ★ 最大的可变延迟源！
  [解码]                 3~15ms    ← 硬件解码 1~5ms, 软件解码 10~30ms
  [后处理/渲染]          2~5ms     ← GL/Metal YUV→RGB + 上屏

═══════════════════════════════════════════════════════════
  总延迟范围（最理想→典型→最差）:
    硬件全链路 + 有线网 + 无 Jitter Buffer:  ~80ms
    典型直播（4G 推 + 正常 Jitter Buffer）:  ~2~5 秒
    HLS 直播（Apple 标准）:                   ~10~30 秒
═══════════════════════════════════════════════════════════
```

#### 2.10.1 Jitter Buffer——整个链路里最大的可变延迟源

Jitter Buffer 是播放端维护的一段**自适应缓冲窗口**。它的逻辑是：

```
网络包到达时间是不均匀的:
理想: █ █ █ █ █ █ (每 33ms 一个 Frame)
实际: █  ██ █   ███ █ (2~50ms 随机间隔)

Jitter Buffer 的做法:
  不收第一个包就直接播——先攒 N 毫秒的数据缓冲
  然后用缓冲吸收网络抖动：
    包来早了 → 放缓冲里 → 按均匀节奏取出
    包来晚了 → 从缓冲里取之前攒的包先顶
    包太久没来超过缓冲长度 → 卡顿/画面停滞

Jitter Buffer 大小 = 网络抖动幅度 × 安全系数

  有线网抖动:  ±5ms  → JB = 50~200ms 就够了
  4G  网抖动:  ±40ms → JB = 200~500ms
  弱网抖动:    ±100ms→ JB = 500~2000ms  ← 此时延迟感知明显
```

**JB 的折中**：JB 越大 → 越不怕抖动但延迟越高。JB 越小 → 延迟越低但容易卡顿。

WebRTC **自适应 JB**：解码器连续 5 帧没有卡顿 → 收缩 JB（减 10ms）。连续 3 次需要等 buffer → 扩张 JB（加 30ms）。所以 WebRTC 通话一开始延迟高一点（JB 在找稳态），稳态后降到 50~200ms。

#### 2.10.2 编码延迟怎么砍——从 500ms 到 50ms

编码延迟的最大贡献者是**lookahead + B 帧 + 帧重排序**：

```
高延迟配置（离线转码）:                     低延迟配置（实时直播/RTC）:
  preset=veryslow                           preset=veryfast/superfast
  lookahead=40 帧                           lookahead=0
  B 帧=3（IBBBPBBBP）                       B 帧=0
  帧并行=8 线程                             帧并行=1 线程
  ──────────────────────                    ──────────────────────
  编码延迟: 200~500ms                       编码延迟: 5~15ms
  压缩率:   极高                            压缩率:   降低 20~30%
```

**面试关键句**：

> "实时直播要把编码延迟从几百毫秒压到十几毫秒，三个旋钮必须一起拧：**关 lookahead**（不提前看帧来算 QP）、**关 B 帧**（消除帧重排序延迟）、**关帧级并行**（多线程并行编码至少带来一帧的延迟）。三个拧完延迟降一个数量级，代价是码率涨 20~30%。x264 的 `-tune zerolatency` 就是一次性把这三个都关了。"

#### 2.10.3 首屏延迟 vs 稳态延迟——面试官常问的区分

| | 首屏延迟（time-to-first-frame） | 稳态延迟（glass-to-glass） |
|---|---|---|
| **定义** | 从"打开流"到"第一帧上屏" | 端到端持续延迟 |
| **主要贡献者** | 信令握手 + DNS → CDN → Jitter Buffer 首次填满 + 等关键帧 | 编码 + 网络 + JB |
| **典型值** | 1~5 秒 | 0.5~3 秒 |
| **优化手段** | 缩短 GOP（让第一个 I 帧尽早出现）、CDN 预热、DNS pre-resolve | 降 JB、低延迟编码、选近 CDN 节点 |

> "面试官让你分析直播延迟，一定要先说清楚你在讲首屏还是稳态——两者的瓶颈和优化方向完全不同。说混了说明你没做过生产优化。"

#### 2.10.4 面试速答模板

**Q：直播延迟从哪里来？**

> "逐环节拆，从推流到播放一共八段延迟。**采集**：sensor 曝光 0.5~2ms。**前处理**：GPU 美颜 2~8ms。**编码**：这是第一个大项——看编码配置。实时配置有 lookahead 和 B 帧时 100~300ms，关了 B 帧和 lookahead 最低能到 5~20ms。**上行网络**：到 CDN 边缘节点的 RTT，有线 10~20ms，4G 40~80ms。**服务端**：转码/转协议再加 10~50ms。**下行网络**：对称的 RTT。**Jitter Buffer**：这是最大的可变项——有线 50~200ms，4G 200~500ms，弱网能到 2 秒。**解码+渲染**：硬件解码 3~15ms，加 GL YUV→RGB 总共不到 20ms。端到端，有线硬编最理想 80ms 左右，典型移动直播 2~5 秒，HLS 10~30 秒。优化找大头——编码看 lookahead 和 B 帧，传输看 RTT 和 JB 适配。"

### 2.11 AVFrame 引用计数：为什么不能直接 memcpy 一帧

这道题考察的是对 FFmpeg **内存模型和零拷贝思想**的理解深度。

#### 2.11.0 直接讲——为什么不能 memcpy 一个 AVFrame

```c
// ❌❌❌ 最经典的错误！
AVFrame *frame = av_frame_alloc();
avcodec_receive_frame(decoder_ctx, frame);

// 你以为 AVFrame 是什么？一个像素 buffer 的头指针？
//   frame->data[0] → 指向某个地方的 Y 数据
//   frame->data[1] → 指向某个地方的 U 数据
//   frame->data[2] → 指向某个地方的 V 数据

// 所以你就:
AVFrame *copy = av_frame_alloc();          // 新分配一个 AVFrame
memcpy(copy, frame, sizeof(AVFrame));      // ★ 结构体的浅拷贝！坑1

uint8_t *yuv_copy = malloc(yuv_size);
memcpy(yuv_copy, frame->data[0], y_size);  // ★ 只拷贝了 data[0] 指针指向的内容……

// 你得到的 copy 是什么？
// copy->data[0] 还是指向 frame 的 data[0]（结构体成员被浅拷贝了！）
// 没有 av_frame_unref(frame) 还好，一 unref 就崩溃——因为 copy->buf[0] 也指向 frame 的结构体
```

**三个层次的为什么**：

**第一层：`AVFrame` 不是只有 `data[]`**

```c
typedef struct AVFrame {
    uint8_t *data[AV_NUM_DATA_POINTERS];   // 8 个数据平面指针
    int linesize[AV_NUM_DATA_POINTERS];    // 每行的字节数（含对齐填充）
    int width, height;
    int format;
    int64_t pts;
    // ... 还有几十个字段

    // ★ 关键：数据由 buf[] 管理生命周期
    AVBufferRef *buf[AV_NUM_DATA_POINTERS]; // 每次 av_frame_get_buffer 创建 AVBufferRef
    // data[] 指针指向的底层内存由 buf[] 中的 AVBufferRef 引用计数管理
} AVFrame;
```

`data[0]` 只是一个**指向底层内存的裸指针**。真正拥有这块内存的是 `buf[0]` 里的 `AVBufferRef`。`memcpy(AVFrame)` 只拷贝了 `data[]` 指针值（浅拷贝），不拷贝 `buf[]` 的引用语义——所以拷贝出来的 `copy->data[0]` 仍然指向原来的内存。

**第二层：多层间接引用——数据可能根本不是 `malloc` 出来的**

```
场景 1: 软解 → data[0] 指向 malloc 的一维线性内存  → buf[0] 是一个 AVBufferRef，refcount=1
场景 2: 硬解 → data[0] 指向 GPU 显存(CUDA/CVPixelBuffer) → buf[0] 是一个 AVBufferRef，底层是 hw_frames_ctx
                                                        → 指针值是 GPU 设备地址，CPU 不可访问
场景 3: 滤镜 → data[0] 指向另一个帧的内存（filtergraph 零拷贝输出的 alias）
              → buf[0] 指向上游帧的 buf[0]，refcount > 1
```

`memcpy(data[0])` 在场景 2（硬解）下会触发**CPU 试图读 GPU 显存地址** —— 直接 segfault。

**第三层：引用计数的目的——让多个对象安全共享底层内存**

```c
// FFmpeg 的引用计数模型（正确做法）

// 正确做法 1: 增加引用（不拷贝数据）
AVFrame *ref_frame = av_frame_alloc();
av_frame_ref(ref_frame, frame);    // ★ refcount +1，data 指向同一块内存
// 你现在可以独立操作 ref_frame，但物理内存还只有一份
// av_frame_unref(ref_frame) 会 refcount -1，到 0 才真正 free 底层内存
// av_frame_unref(frame) 也会 refcount -1，到 0 才释放

// 正确做法 2: 深拷贝（真需要独立副本时才用）
AVFrame *deep_copy = av_frame_alloc();
av_frame_ref(deep_copy, frame);           // 先引用
av_frame_make_writable(deep_copy);        // ★ 如果 refcount > 1，拷贝底层数据
// make_writable 的逻辑: refcount == 1 → 直接标记可写; refcount > 1 → 分配新内存 + memcpy

// 正确做法 3: 只创建一个新的、不共享的帧
AVFrame *new_frame = av_frame_alloc();
new_frame->width  = frame->width;
new_frame->height = frame->height;
new_frame->format = frame->format;
av_frame_get_buffer(new_frame, 0);   // ★ 分配自己的 buf[] → refcount = 1
av_frame_copy(new_frame, frame);     // ★ 拷贝 data 内容（不是指针）
av_frame_copy_props(new_frame, frame); // ★ 拷贝元数据字段
```

#### 2.11.1 AVFrame 引用计数链路（内部模型）

```
AVFrame A                          AVFrame B (av_frame_ref 得到)
    │                                    │
    │ buf[0]   buf[1]   buf[2]           │ buf[0]   buf[1]   buf[2]
    │   │        │        │              │   │        │        │
    └───┼────────┼────────┼──────────────┘   │        │        │
        │        │        │                  │        │        │
        ▼        ▼        ▼                  ▼        ▼        ▼
   ┌─────────────────────────────────────────────────────────┐
   │         AVBufferRef (共享的底层缓冲区引用)                  │
   │                                                         │
   │   AVBufferRef {                                         │
   │     uint8_t *data;       ← 实际的内存块 (malloc/GPU内存)   │
   │     int      size;       ← 块大小                         │
   │     AVBuffer *buffer;    ← 共享的引用计数头                 │
   │       → refcount = 2     ← A 和 B 都引用同一块内存          │
   │   }                                                     │
   └─────────────────────────────────────────────────────────┘
```

**核心规则**：

```
av_frame_ref(B, A):    B.buf[i] = av_buffer_ref(A.buf[i])   → refcount +1
av_frame_unref(A):     av_buffer_unref(A.buf[i])            → refcount -1
                       如果任意 buf[i] 的 refcount 降到 0:
                         av_buffer_pool_get 或 free(buffer->data)
                       A.buf[i] = NULL, A.data[i] = NULL

av_frame_make_writable(A):
  for each buf[i]:
    if av_buffer_is_writable(A.buf[i]):   → 不做任何事情
    else (refcount > 1):
      av_buffer_realloc(&A.buf[i])        → 新分配内存、拷贝数据、refcount=1
```

#### 2.11.2 面试速答模板

**Q：为什么不能 memcpy AVFrame？**

> "三个层次。**第一**，`AVFrame` 的数据所有权不在 `data[]` 裸指针——在 `buf[]` 里的 `AVBufferRef`。你用 `memcpy` 只浅拷贝了 `data[]` 的值（指针地址），拷贝出来的 frame 和原 frame 指向同一块物理内存，但没有增加引用计数。一旦 `av_frame_unref` 原 frame，底层内存被释放，拷贝版 frame 的 `data[]` 变成野指针。**第二**，硬件帧的 `data[]` 指向的是 GPU 显存地址。你用 `memcpy(data[0])` 就是让 CPU 去读 GPU 的设备地址，直接 segfault。**第三**，FFmpeg 很多滤镜和编解码器内部做了零拷贝——多个 frame 可能通过引用计数共享同一块内存。正确做法永远是 `av_frame_ref` + `av_frame_make_writable`，让引用计数替你管理生命周期。"

**Q：av_frame_make_writable 做了什么？**

> "它是'写前确认'的检查点。内部逻辑是：如果这一帧的所有 buf 的引用计数都是 1（只有你一个人在引用这些内存块），就什么都不做、直接标记可写。如果有任何一个 buf 的 refcount > 1（别人也在引用），就 `av_buffer_realloc`——分配一块新内存、**拷贝原数据**、新 buf 的 refcount = 1、更新 `data[]` 指到新内存。这样你就有了自己的独立副本，修改不影响别人。这就是 COW（Copy-On-Write）在 FFmpeg 里的实现。"

### 2.12 sws_scale 为什么不能处理硬件帧

这道题横跨软硬分野，是检验你是否真正理解"硬件帧 vs 软件帧"的标志性问题。

#### 2.12.0 一句话答案

> "`sws_scale` 内部是 CPU SIMD 指令（SSE4/AVX2/NEON）按 `uint8_t` 数组的方式去读源像素、算插值、写目标像素。它期望 `src->data[]` 指向的是 CPU 可访问的系统内存。硬件帧的 `data[]` 是设备内存指针（GPU 显存、内核 IOSurface ID）——CPU **不能直接访问**，所以直接传入会要么 segfault、要么拿到垃圾数据。"

#### 2.12.1 硬件帧 vs 软件帧的内存模型

```
软件帧 (AV_PIX_FMT_YUV420P):
  data[0] → 0x7f8a40000000  ← 系统 RAM（CPU 可读可写）
  data[1] → 0x7f8a40700000  ← 也是系统 RAM
  data[2] → 0x7f8a40a00000  ← 也是系统 RAM
  buf[0]  → AVBufferRef → malloc 内存

硬件帧 (AV_PIX_FMT_CUDA / AV_PIX_FMT_VAAPI / AV_PIX_FMT_VIDEOTOOLBOX):
  data[0] → (CUdeviceptr)0x7f0000000000  ← GPU 显存地址（CPU 不可访问）
  data[1] → (CUdeviceptr)0x7f0000200000  ← GPU 显存地址
  data[2] → 0  (NV12 通常只用了 2 个平面)
  buf[0]  → AVBufferRef → hw_frames_ctx 管理的 GPU 内存

  format = AV_PIX_FMT_CUDA / AV_PIX_FMT_VAAPI / AV_PIX_FMT_VIDEOTOOLBOX
           ↑ sws_scale 看到这个格式直接返回 EINVAL 或跳过
```

**关键机制**：`sws_scale` 的入口第一行代码就是：

```c
// libswscale/swscale.c (简化)
int sws_scale(SwsContext *c, const uint8_t *const srcSlice[],
              const int srcStride[], int srcSliceY, int srcSliceH,
              uint8_t *const dst[], const int dstStride[]) {
    // ★ 第一行就做检查：源和目标必须是 CPU 可访问的系统内存像素格式
    if (av_pix_fmt_desc_get(srcFormat)->flags & AV_PIX_FMT_FLAG_HWACCEL)
        return AVERROR(EINVAL);  // 硬件格式 → 直接拒绝
    if (av_pix_fmt_desc_get(dstFormat)->flags & AV_PIX_FMT_FLAG_HWACCEL)
        return AVERROR(EINVAL);  // 硬件目标 → 直接拒绝
    // ... 然后是 SSE/AVX2/NEON SIMD 核心 ...
}
```

#### 2.12.2 那要处理硬件帧怎么办？两条路

```
路径 A: 转回 CPU → sws_scale（有拷贝）
  硬件帧 → av_hwframe_transfer_data(sw_frame, hw_frame) → 现在 data[] 在系统 RAM
           ↑ 这一步做 GPU→CPU DMA 拷贝, 1080p ≈ 2~5ms
      → sws_scale 可以正常处理 sw_frame
      → 如果目的地又是硬件（比如硬编），还得再拷回 GPU
      → 总共: GPU→CPU→CPU(scale)→GPU = 三次拷贝

路径 B: GPU 原生处理（零拷贝，推荐）
  CUDA: NPP(nppiResize) 或自写 CUDA kernel
  VAAPI: vaDeriveImage + VA surface 间的 blit
  VideoToolbox: VTPixelTransferSession 或 Metal compute shader
  vulkan: vkCmdBlitImage

  → 全程数据在 GPU 显存，不经过 PCIe
```

#### 2.12.3 那你见过的项目里怎么做的？（实战经验加分）

> "流程是 `av_hwframe_transfer_data` 把硬解帧拷到 CPU、`sws_scale` 做缩放格式转换、然后要么 `av_hwframe_transfer_data`（方向反过来）拷回 GPU 给硬编，要么直接软编。对这个流程的优化通常有两层：第一层，如果缩放的目标尺寸和硬解输出差异不大，用解码器的 `avcodec_open2` 阶段配硬件缩放（如 NVDEC 的 `ulTargetWidth/Height`、VT 的 `kVTDecompressionPropertyKey_RealTime`），省掉一次 scale。第二层更彻底——用 CUDA kernel/Metal shader 在 GPU 上做全套（scale + CSC + 后处理），一步 PCIe 拷贝都不做。"

#### 2.12.4 面试速答模板

**Q：sws_scale 为什么不能处理硬件帧？怎么处理？**

> "因为 `sws_scale` 是纯 CPU 代码——它用 SSE/AVX2/NEON 这种 SIMD 指令集直接读 `data[]` 指向的系统内存做插值计算。硬件帧的 `data[]` 存的是 GPU 设备地址，CPU 读不到——函数入口第一行就会检查像素格式的 `HWACCEL` flag 并直接返回 `EINVAL`。**正确处理硬件帧有两种方式**：要么用 `av_hwframe_transfer_data` 把 GPU 上的帧 DMA 拷到系统内存再走 `sws_scale`——1080p 一次拷贝约 2~5ms；要么在 GPU 上原生处理——NPP/CUDA kernel/Metal shader 做缩放和格式转换，全链路零拷贝。生产环境尽量走 GPU 原生的路，拷来拷去一来一回 PCIe 是硬编硬解管道里最大的延迟源。"

### 2.13 H.264 SPS 字节级解析——从裸字节手动算出宽高

这是**真正的深水区**——面试官可能给你一段十六进制的 SPS 字节让你口算宽高。考的不是记忆力，是你对 H.264 码流格式的理解。

#### 2.13.0 SPS 结构的字节布局

```
SPS (Sequence Parameter Set) 标准结构（NAL header 后第一个字节开始）:

Byte 0:  [profile_idc]                          ← 66=Baseline, 77=Main, 100=High
Byte 1:  [constraint_set_flags | reserved]
Byte 2:  [level_idc]                             ← 10*level (e.g. 40 = level 4.0)
Byte 3:  [seq_parameter_set_id]                  ← ue(v): 0 for first SPS
... 之后全是 ue(v) / se(v) (指数哥伦布编码，Exponential-Golomb coded):

ue(v): chroma_format_idc                        ← 1=4:2:0, 2=4:2:2, 3=4:4:4
if (chroma_format_idc == 3) { separate_colour_plane_flag }
ue(v): bit_depth_luma_minus8                    ← 0=8bit, 2=10bit
ue(v): bit_depth_chroma_minus8
ue(v): qpprime_y_zero_transform_bypass_flag
ue(v): seq_scaling_matrix_present_flag
if (seq_scaling_matrix_present_flag) { /* scaling lists */ }

ue(v): log2_max_frame_num_minus4               ← 控制 frame_num 范围
ue(v): pic_order_cnt_type                      ← 0/1/2, 决定 POC 计算方式
if (pic_order_cnt_type == 0) {
    ue(v): log2_max_pic_order_cnt_lsb_minus4
} else if (pic_order_cnt_type == 1) { /* ... */ }

ue(v): max_num_ref_frames                       ← DPB 最大参考帧数
ue(v): gaps_in_frame_num_value_allowed_flag

ue(v): pic_width_in_mbs_minus1                  ← ★ 宽度的宏块数 - 1
ue(v): pic_height_in_map_units_minus1           ← ★ 高度的宏块数 - 1
ue(v): frame_mbs_only_flag                      ← 0=interlaced, 1=progressive

if (!frame_mbs_only_flag) {
    ue(v): mb_adaptive_frame_field_flag
}

ue(v): direct_8x8_inference_flag

ue(v): frame_cropping_flag
if (frame_cropping_flag) {
    ue(v): frame_crop_left_offset               ← 左裁切
    ue(v): frame_crop_right_offset              ← 右裁切
    ue(v): frame_crop_top_offset                ← 上裁切
    ue(v): frame_crop_bottom_offset             ← 下裁切  ★ 关键: 从这算出真实高宽
}

ue(v): vui_parameters_present_flag
if (vui_parameters_present_flag) {
    // VUI: 帧率、宽高比、色彩空间等（可选）
}
```

#### 2.13.1 核心：从 SPS 算出实际宽高

```c
// 手动从 SPS 字节解析宽度和高度的伪代码（基于 H.264 7.3.2.1.1）

int parse_width_height(const uint8_t *sps, int sps_len,
                       int *width, int *height) {
    // sps[0] 是 NAL header 字节: forbidden_zero_bit(1) | nal_ref_idc(2) | nal_unit_type(5)
    // nal_unit_type 应该是 7（SPS）
    // SPS body 从 sps[1] 开始

    const uint8_t *p = sps + 1;  // 跳过 NAL header
    const uint8_t *end = sps + sps_len;

    int profile_idc = *p++;  // Byte 0
    p++;  // Byte 1: constraint_set + reserved
    p++;  // Byte 2: level_idc

    // ★ 从 Byte 3 开始，全部是 ue(v) 指数哥伦布编码
    // 跳过 seq_parameter_set_id (ue(v))
    p += read_ue_golomb_length(p, end);

    // chroma_format_idc
    int chroma_format_idc = read_ue_golomb_value(p, end);
    p += read_ue_golomb_length(p, end);

    // 根据 chroma_format_idc 计算 SubWidthC/SubHeightC
    int sub_width_c  = 1, sub_height_c = 1;
    if (chroma_format_idc == 1) { sub_width_c = 2; sub_height_c = 2; }    // 4:2:0
    if (chroma_format_idc == 2) { sub_width_c = 2; sub_height_c = 1; }    // 4:2:2
    // chroma_format_idc == 3: sub_width_c = 1, sub_height_c = 1 (4:4:4)

    if (chroma_format_idc == 3) {
        p += read_ue_golomb_length(p, end);  // separate_colour_plane_flag
    }

    // 跳过 bit_depth, qpprime, scaling_matrix 等...
    p += read_ue_golomb_length(p, end);  // bit_depth_luma_minus8
    p += read_ue_golomb_length(p, end);  // bit_depth_chroma_minus8
    p += read_ue_golomb_length(p, end);  // qpprime_y_zero_transform_bypass_flag

    int scaling_matrix_present = read_ue_golomb_value(p, end);
    p += read_ue_golomb_length(p, end);
    // 跳过 scaling lists (如果有) ...

    p += read_ue_golomb_length(p, end);  // log2_max_frame_num_minus4

    int pic_order_cnt_type = read_ue_golomb_value(p, end);
    p += read_ue_golomb_length(p, end);
    if (pic_order_cnt_type == 0) {
        p += read_ue_golomb_length(p, end);  // log2_max_pic_order_cnt_lsb_minus4
    }
    // else type 1/2 ...

    p += read_ue_golomb_length(p, end);  // max_num_ref_frames
    p += read_ue_golomb_length(p, end);  // gaps_in_frame_num_value_allowed_flag

    // ★★★ 关键字段 ★★★
    int pic_width_in_mbs  = read_ue_golomb_value(p, end) + 1;   // 宏块个数
    p += read_ue_golomb_length(p, end);

    int pic_height_in_mbs = read_ue_golomb_value(p, end) + 1;   // 宏块个数
    p += read_ue_golomb_length(p, end);

    int frame_mbs_only_flag = read_ue_golomb_value(p, end);
    p += read_ue_golomb_length(p, end);

    // 先按宏块算出原始宽高
    int raw_width  = pic_width_in_mbs * 16;
    int raw_height = pic_height_in_mbs * 16;

    // 如果是逐行扫描(frame_mbs_only=1)，要处理宏块对
    if (!frame_mbs_only_flag) {
        p += read_ue_golomb_length(p, end);  // mb_adaptive_frame_field_flag
        raw_height = pic_height_in_mbs * 16 * 2;  // 隔行: 每个 map unit = 32 pixels tall
    }

    p += read_ue_golomb_length(p, end);  // direct_8x8_inference_flag

    // ★★★ 裁剪窗口——这才是真实显示分辨率 ★★★
    int frame_cropping_flag = read_ue_golomb_value(p, end);
    p += read_ue_golomb_length(p, end);

    int crop_left   = 0, crop_right  = 0;
    int crop_top    = 0, crop_bottom = 0;

    if (frame_cropping_flag) {
        crop_left   = read_ue_golomb_value(p, end); p += read_ue_golomb_length(p, end);
        crop_right  = read_ue_golomb_value(p, end); p += read_ue_golomb_length(p, end);
        crop_top    = read_ue_golomb_value(p, end); p += read_ue_golomb_length(p, end);
        crop_bottom = read_ue_golomb_value(p, end); p += read_ue_golomb_length(p, end);
    }

    // ★★★ 最终显示分辨率 ★★★
    *width  = raw_width  - (crop_left + crop_right)  * sub_width_c;
    *height = raw_height - (crop_top  + crop_bottom) * sub_height_c * (2 - frame_mbs_only_flag);

    return 0;
}
```

**实例：一段 SPS 字节，口算出 1920×1080**

```
SPS NALU = [67] [64 00 1F] [AC 2C A0 20 14 01 6C 12 80]
           ↑    ↑↑↑↑↑                      ↑↑
        NAL header body                   关键字段在这

NAL header = 0x67 → nal_unit_type = 0x67 & 0x1F = 7 → SPS ✓

Body:
  0x64 = profile_idc = 100 → High Profile  ← sps[1]
  0x00 = constraint_set (无约束)
  0x1F = level_idc = 31 → Level 3.1

从 0xAC 开始是 ue(v) 编码的字段：
  seq_parameter_set_id = 0
  chroma_format_idc = 1 → 4:2:0, subWidthC=2, subHeightC=2
  ...

宏块字段区域:
  pic_width_in_mbs  = (1920 / 16) - 1 = 119 (0x77)
  pic_height_in_mbs = (1088 / 16) - 1 = 67 (0x43)    ← 注意: 1088 不是 1080！
  frame_mbs_only_flag = 1

   raw_width  = 120 * 16 = 1920  ← ✓
   raw_height = 68 * 16  = 1088  ← 编码对齐到 16 的倍数

  frame_cropping_flag = 1
    crop_bottom = 4  ← 裁掉底部 4 个 chroma 单元 = 4 * 2 = 8 行
  → 真实高度 = 1088 - 8 = 1080  ← ✓

结论: 这是 1920×1080 High@L3.1 的 SPS
```

#### 2.13.2 面试速答模板

**Q：如果给你一段 H.264 SPS 的裸字节，你怎么确定视频的分辨率？**

> "SPS 是一个字节串，从 NAL header 后的第一个字节开始读。**前三字节是定长**——`profile_idc`（66=Baseline、77=Main、100=High）、constraint byte、`level_idc`。从第四字节开始全部是**指数哥伦布编码**（ue(v)/se(v)）的变长字段——所以不能按固定偏移读，必须逐字段解码。关键字段链：chomra_format_idc → bit_depth → pic_order_cnt → max_num_ref_frames → **pic_width_in_mbs_minus1** → **pic_height_in_map_units_minus1**。拿到宏块数后 `×16` 得到编码分辨率。但编码分辨率不等于显示分辨率——因为有帧裁剪 (`frame_cropping_flag`)。裁剪窗口通过 `frame_crop_left_offset/right_offset/top_offset/bottom_offset` 告诉解码器要把编码帧的哪一块裁出来——真正的显示宽高 = 编码分辨率 − 裁剪像素。所以 1080p 的 SPS 里 raw_height 通常是 1088（对齐到 16 的倍数），`crop_bottom=4`（在 4:2:0 里等于 8 行），裁完才是 1080。"

**Q：什么是 ue(v) 编码？**

> "ue(v) 全称 Unsigned Exponential-Golomb coded，是 H.264 里对大部分语法元素使用的变长编码。它的编码规则是：前面 N 个 0 比特、跟一个 1 比特作为分隔、再跟 N 比特的值。解码公式是 `value = (1 << leadingZeroBits) - 1 + 后面跟着的 N 个值比特`。比如 `0 00110`：前面 4 个 0、分隔 1、后面 4 位值是 0110=6 → value = (1<<4) - 1 + 6 = 15 + 6 = 21。没有固定的字节对齐——这也就是为什么逐字段解析时必须知道前一个字段占了多少比特。"
