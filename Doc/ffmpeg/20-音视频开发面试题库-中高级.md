## 一、数据结构与生命周期

### Q1.1 ⭐ AVPacket 和 AVFrame 有什么区别？

**参考答案**：

> 这个一定要先说清楚——AVPacket 装的是**压缩之后**的数据，比如 H.264 的 NALU 字节、AAC 的压缩帧；AVFrame 装的是**解压之后**的原始数据，比如 YUV 像素、PCM 音频采样。
>
> 从流水线位置来看，进出解码器是个分水岭。解码器吃进去的是 AVPacket，吐出来的是 AVFrame；编码器反过来，吃 AVFrame、吐 AVPacket。
>
> 体积上也差很远——一个压缩 packet 可能就几 KB，但一帧 1080p 的 RGB AVFrame 差不多 6MB。所以 packet 适合存和传，frame 适合渲染和加工。
>
> 还有一个很多人忽略的点：视频通常一个 packet 对应一帧，但**音频一个 packet 可能对应多帧**。这就是为什么音频解码必须用 while 循环 receive，不能只收一次。
>
> 另外，两者都用了引用计数来管理底层内存，这是 FFmpeg 实现零拷贝的关键。

**翻车红线**：说"AVPacket 是音频、AVFrame 是视频"——完全错，两者都能装音频也能装视频。

---

### Q1.2 ⭐ av_packet_unref 和 av_packet_free 有什么区别？循环里该用哪个？

**参考答案**：

> 这俩绝对不能搞混。`unref` 是**把信封里的信倒掉，信封留着**——释放底层数据引用、把字段清零，但 AVPacket 这个壳还在，可以继续装下一个 packet。`free` 是**连信封一起扔了**——整个对象销毁、指针置空。
>
> 循环里处理一万帧，要是在循环里 alloc/free 来来回回，性能直接崩。正确写法是：循环外面 alloc 一次，循环里面每轮只 unref 复用，循环结束了再 free。
>
> 底层原理：AVPacket 内部通过 `AVBufferRef *buf` 指向一个 `AVBuffer`，真正的 refcount 在 AVBuffer 里。`av_packet_ref(dst, src)` 让 dst 的 buf 也指向同一个 AVBuffer，refcount 加一——这就是零拷贝。

**翻车红线**：说"都是释放内存，差不多"——直接出局。

---

### Q1.3 ⭐⭐ AVCodec 和 AVCodecContext 为什么要分开？

**参考答案**：

> 说白了，AVCodec 是**算法本身**，AVCodecContext 是**算法的运行环境**。打个比方——AVCodec 像是菜谱（怎么解码 H.264 的步骤是固定的），AVCodecContext 像是厨房（当前这路流的分辨率是多少、解码到第几帧了、用了什么参数）。
>
> 所以 AVCodec 是无状态的，全局只需要一个实例；AVCodecContext 是有状态的，每路流各一个。你要同时解码两路视频，就创建两个 AVCodecContext，但底层指向同一个 AVCodec。
>
> 还有一个工程细节：初始化分三步——`alloc_context3` 分配壳 → `parameters_to_context` 从 codecpar 拷贝参数 → `open2` 真正打开。中间留了一个窗口让你在 open 之前改参数，比如把默认软解换成硬解。

**翻车红线**：说"为什么这样设计我不知道"。

---

### Q1.4 ⭐⭐ FFmpeg 的 unref / uninit / free / close / closep 怎么区分？

**参考答案**：

> 这套命名非常规律，关键是理解每个动词操作的是哪个层次：

| 动词 | 操作什么 | 比喻 |
|------|---------|------|
| `unref` | 释放底层数据引用，壳保留可复用 | 倒掉信件，信封留着 |
| `free` | 整个对象销毁，指针置空 | 连信封一起扔 |
| `uninit` | 清内部状态，栈变量本身还在 | 清掉家具，房子还在 |
| `close` | 关闭已打开的资源（文件/IO） | 关门 |
| `closep` | close + 把指针置空，防悬空 | 关门并把地址擦掉 |

> 举例：`AVChannelLayout` 在栈上声明，用完要 `uninit` 清理内部动态内存，但不能 `free`——它不是堆分配的。

**翻车红线**：五个动词都说成"释放内存"。

---

### Q1.5 ⭐⭐⭐ AVPacket 的引用计数底层怎么实现的？

**参考答案**：

> 这个问得深了。结构是三层：`AVPacket → AVBufferRef → AVBuffer`。
>
> AVPacket 自己不直接管引用计数，它通过 `AVBufferRef *buf` 指向 `AVBuffer`。AVBuffer 里面有 `data`（实际数据）、`size`、`refcount`（原子计数器）。
>
> `av_packet_ref(dst, src)` 创建新的 AVBufferRef 指向同一个 AVBuffer，refcount 加一——数据不拷贝。
> `av_packet_unref` 释放当前 AVBufferRef 引用，refcount 减一，减到零才真正 free 数据，然后清零 packet 字段，回到可复用状态。
>
> 这个三层结构是整个 FFmpeg 内存管理的基石，AVFrame 也一样。

### Q1.6 ⭐ AVFormatContext 在 FFmpeg 流水线里扮演什么角色？

**参考答案**：

> AVFormatContext 是**一切操作的入口**，代表一个"被打开的音视频文件或网络流"。不管是本地 MP4、网络 RTMP 流、还是摄像头设备，打开后都是它。
>
> 里面装着：文件时长、有几路流、每路流的元数据、AVStream 数组。通过 `avformat_open_input` 创建，`avformat_find_stream_info` 读几帧探测真实编码参数，然后遍历 streams 找视频流和音频流。
>
> 之后所有的 `av_read_frame` 都从它往外套 packet。写文件也一样——`write_header` / `write_frame` / `write_trailer` 都围绕它。
>
> 一句话：AVFormatContext 是**入口 + 管家 + 调度中心**，不参与编解码本身，但安排所有数据怎么流转。

---

### Q1.7 ⭐⭐ AVStream 里的 codecpar 是干什么的？和 AVCodecContext 的关系？

**参考答案**：

> `codecpar` 全称 codec parameters，是流的"身份证"——描述这路流的基本属性：视频宽高、像素格式、编码 ID、extradata（SPS/PPS 或 AudioSpecificConfig）。在 `avformat_find_stream_info` 阶段就被填好了。
>
> 但它不能直接用来解码。需要用 `avcodec_parameters_to_context` 把参数拷到 AVCodecContext，再 `avcodec_open2` 打开。
>
> FFmpeg 把两者分开是因为：codecpar 是**轻量的参数快照**，挂在 AVStream 上由 AVFormatContext 管；AVCodecContext 是**重量级的运行时环境**，有解码器状态、内部缓冲、硬件加速上下文，生命周期独立。

---

### Q1.8 ⭐⭐ FFmpeg 的时间戳到底是什么单位？怎么换算？

**参考答案**：

> 这个坑踩过的人太多了。ffmpeg 里所有时间戳都是**整数刻度**，不是秒。PTS=90000 不意味着 90 秒——它意味着"在某个 time_base 尺子下的 90000 个刻度"。
>
> 每个流有自己的 time_base，是个分数 `{num, den}`，表示一个刻度等于 `num/den` 秒。比如 `time_base = 1/90000`，90000 个刻度 = 1 秒。
>
> 换算：**实际秒数 = pts × av_q2d(time_base)**。
>
> 真正麻烦的是——**不同模块的 time_base 不一样**。解封装用 `1/90000`，编码器用 `1/30`（帧率倒数），滤镜用 `1/1`。跨模块必须用 `av_rescale_q` 换算，否则播放速度完全错乱。
>
> 为什么用整数？三个原因：精度无累积误差；能精确表达 `1001/30000`（NTSC 帧率）；跨平台一致。

**翻车红线**：说"PTS 就是秒"。

### Q1.9 ⭐⭐ 为什么音视频同步通常以音频为主时钟？

**参考答案**：

> 这背后是生理学。人耳对音频卡顿、断裂、变速极其敏感——20 毫秒的断音都能察觉。但人眼对视频丢一两帧不太敏感，有视觉残留。
>
> 所以策略就是"让音频自由跑，视频追音频"：
> - 维护 audio_clock = 当前播放帧 PTS + 已写入设备但未消费的样本时长
> - 视频 PTS < audio_clock - 阈值：丢帧追赶
> - 视频 PTS > audio_clock + 阈值：延迟显示
> - 差值在阈值内：正常显示
>
> 一个关键细节：audio_clock 要**扣除设备缓冲区延迟**。PCM 写进声卡缓冲区 ≠ 用户已听到，缓冲区里可能还堆着几十毫秒数据。
>
> 反过来拉伸音频去追视频基本没人做——人对音频变速太敏感了。

### Q1.10 ⭐⭐ FFmpeg 解码中 send_packet 和 receive_frame 为什么是异步的？

**参考答案**：

> 因为解码器内部有缓冲和重排序。可能的原因：
> - B 帧：解码器拿到 P 帧，但需先解码后面的 B 帧才能输出
> - 内部缓冲：可能需攒几个 packet 才开始输出
> - 音频一包多帧：send 一次要 receive 多次
>
> 正确写法：
> ```c
> avcodec_send_packet(ctx, pkt);
> while (avcodec_receive_frame(ctx, frame) >= 0) {
>     // 处理 frame
> }
> ```
> 返回值：0=成功拿到一帧，EAGAIN=还需喂更多 packet，EOF=流结束。
>
> 这个设计让解码器自由控制内部缓冲和重排序，调用方不需要理解 I/P/B 帧的复杂依赖。

### Q1.11 ⭐⭐ 打开一个 MP4 文件时 FFmpeg 背后做了什么？

**参考答案**：

> 这是考整个初始化流程：
>
> 1. `avformat_open_input`：打开文件，读 ftyp/moov box，识别容器格式，分配 AVFormatContext
> 2. `avformat_find_stream_info`：读前面几帧，探测每路流的真实参数——编码、分辨率、帧率、采样率、声道数。这一步会实际解码少量数据
> 3. 遍历 streams 数组，找到视频流和音频流 index
> 4. 对每路流：`avcodec_find_decoder` → `avcodec_alloc_context3` → `avcodec_parameters_to_context` → `avcodec_open2`
> 5. 管道搭好，开始循环 `av_read_frame` → `avcodec_send_packet` → `avcodec_receive_frame`
>
> 注：步骤 2 有 I/O 和计算开销。只需元数据（时长/分辨率）时可用 `AVFMT_FLAG_FAST` 跳过深度探测。

### Q1.12 ⭐ 如何判断一个 AVPacket 是不是关键帧？怎么查看它的 PTS？

**参考答案**：

> 两个都是直接读 AVPacket 的字段，非常基础，但面试里答不清楚的人不少。
>
> **判断关键帧**：检查 `pkt->flags & AV_PKT_FLAG_KEY`。如果这个位被置 1，说明当前 packet 是一个关键帧（视频 I 帧 / IDR 帧），可以独立解码，不依赖其他帧。
>
> 注意点：这个 flag 是解封装阶段由容器层填的——MP4 来自 stss box，FLV 来自 `AVCVIDEOPACKET` 里的 `AVCPacketType`。如果容器本身不标注关键帧（某些裸流场景），这个 flag 可能永远是 0，即使视觉上看得出是 I 帧。
>
> 代码就一行：
> ```cpp
> bool is_keyframe = (pkt->flags & AV_PKT_FLAG_KEY) != 0;
> ```
>
> **查看 PTS**：直接读 `pkt->pts`，它是一个 `int64_t`，单位是 **当前流 time_base 的刻度数**，不是毫秒也不是微秒。要换算成秒：
> ```cpp
> int64_t pts = pkt->pts;                                                   // time_base 单位
> double pts_sec = pts * av_q2d(video_stream->time_base);                  // 转秒
> int64_t pts_ms  = pts * av_q2d(video_stream->time_base) * 1000;         // 转毫秒
> ```
>
> **两个常见坑**：
> 1. `pkt->pts` 可能是 `AV_NOPTS_VALUE`（即 `int64_t` 最小值，约 -9.2×10¹⁸）。某些容器的 B 帧或特定编码会不给 PTS，直接用会出诡异结果，**必须先判空**。
> 2. `pkt->dts` 不等于 `pkt->pts`。有 B 帧时 DTS（解码顺序）和 PTS（显示顺序）不一致。展示给用户用 PTS，做解码调度用 DTS。
>
> 一句话：**关键帧看 flags，展示时间看 pts，pts 的单位必须乘 time_base 才能变成秒。**

**翻车红线**：说"把 pts 直接除以 1000 就是秒"或"pts 单位是毫秒"——完全错，pts 的单位由 time_base 决定，不同容器、不同流都不一样。

### Q2.1 ⭐ 为什么视频编解码不用 RGB 而用 YUV？

**参考答案**：

> 核心原因是**数据压缩**。RGB 三个分量同等重要，没法偷懒。但人眼有个特点：对亮度（Y）极其敏感，对颜色（U/V）不太敏感——这个生理学事实给了我们巨大的压缩空间。
>
> YUV 把亮度和色度分离之后，就可以做**色度子采样**。最主流的是 4:2:0——每 4 个亮度像素共享 1 组色度信息。结果是：原来 RGB 每像素 3 字节，4:2:0 YUV 相当于每像素只有 1.5 字节，**数据量直接减半**。
>
> 算一笔账：1080p 30fps 不压缩的 RGB = 1080×1920×3×30 ≈ 178 MB/s，一分钟超过 10GB——没人扛得住。所以 YUV 是整个视频压缩体系的起点。
>
> 还有一个历史原因：YUV 最早是为兼容黑白电视设计的——黑白电视只收 Y 信号（亮度），彩色电视收 Y+UV。所以现代所有视频编码（H.264/H.265/AV1）底层都是 YUV。

**翻车红线**：说"因为 YUV 是行业标准"——废话，问的是为什么它成了标准。

### Q2.2 ⭐ I420 / NV12 / NV21 三者的区别？

**参考答案**：

> 三者都是 YUV 4:2:0，差别在内存排布：

| 格式 | 排布 | 谁在用 |
|------|------|--------|
| I420 (=YUV420P) | Planar：Y 一块、U 一块、V 一块，三个独立平面 | x264 软编、FFmpeg 默认 |
| NV12 | Semi-Planar：Y 一平面 + UV 交错 | iOS VideoToolbox、大多数硬编 |
| NV21 | Semi-Planar：Y 一平面 + **VU 交错**（反的）| **Android Camera1 默认** |

> NV12 是 NVIDIA 发明的——硬件取色时总是同时需要 U 和 V，Semi-Planar 让 UV 落在同一条 Cache Line，命中率大幅提升。
>
> 经典坑：Android 摄像头默认吐 NV21，但如果你把它喂给配置成 NV12 的 MediaCodec——画面红蓝反色，俗称"阿凡达脸"。这是移动端最经典的 bug 之一。

**翻车红线**：说"都差不多"、答不出 NV21 默认在哪用。

### Q2.3 ⭐ linesize 一定等于 width × 字节数吗？

**参考答案**：

> **不一定**。FFmpeg 为了 SIMD（AVX/SSE/NEON）效率，按 16 或 32 字节对齐分配内存。行末常有 padding。比如 width=100 字节，linesize 可能被分配成 128 字节。
>
> 凡是按行操作图像，**永远按 linesize 偏移**，不要按 width 硬算。经典翻车代码：
> ```c
> memcpy(dst, frame->data[0], width * height);  // 错！
> ```
> 正确写法是逐行 memcpy，每行按 linesize 偏移。
>
> 另外 YUV420P 三个平面的 linesize 不相等——Y 是 width（对齐后），UV 各是 width/2（对齐后）。

**翻车红线**：说"应该相等吧"——说明没真写过图像处理代码。

### Q2.4 ⭐⭐ BT.601 和 BT.709 有什么区别？

**参考答案**：

> 它们是 **RGB ↔ YUV 转换矩阵**的两套标准。BT.601 是标清时代（480/576p），BT.709 是高清时代（720/1080p）。
>
> 公式不同，最关键的是 BT.709 把绿色权重从 0.587 提到了 0.7152。如果用错矩阵会导致**色偏**：典型现象是用 601 公式解 709 的视频 → 红色偏暗、绿色偏亮、画面灰蒙蒙。
>
> 还有一个重要的区分：**像素格式 vs 色彩空间**。像素格式是"杯子的形状"（NV12/YUV420P），色彩空间是"杯子里装的饮料"（BT.601/BT.709/BT.2020）。同一块 NV12 内存，既可能是 601 也可能是 709 编码的数值。
>
> 还有 BT.2020，给 4K HDR 用的，色域更宽。

**翻车红线**：说"都是 YUV 格式"——把色彩空间和像素格式混为一谈。

### Q2.5 ⭐⭐ Full Range 和 Limited Range（0-255 vs 16-235）是什么？

**参考答案**：

> **Full Range**：Y 用 0-255，U/V 也全用 0-255。电脑显示器、JPEG 图片用这个。
> **Limited Range**：Y 用 16-235，U/V 用 16-240。电视、大多数视频文件用这个。
>
> 16-235 的来源是模拟电视时代——给信号过冲/欠冲留缓冲：0-15 是 Toeroom（比黑还黑），236-255 是 Headroom（比白还白）。
>
> 两个经典 bug：
> - Limited 视频按 Full 渲染 → **画面发灰**（最黑只到 16，不是纯黑）
> - Full 视频按 Limited 渲染 → **暗部死黑、亮部过曝**
>
> 解决方法：读 `AVColorRange` 字段，动态选矩阵。FFmpeg 里可以用 `sws_setColorspaceDetails` 指定。

**翻车红线**：说"没听说过"——直接扣分。

---

### Q2.6 ⭐⭐⭐ 为什么 YUV 4:2:0 几乎不用 Packed 格式？

**参考答案**：

> 三个原因：
>
> 1. **数量不对等**：4 个 Y 配 1 组 UV，强行交错（`Y1 U1 Y2 V1 Y3 U2 Y4 V2`）寻址极其复杂，地址计算比 planar 麻烦得多
> 2. **缓存污染**：视频编码的运动搜索几乎只用 Y 分量。UV 混进来导致每次读 Y 都把没用的 UV 加载进 Cache Line，浪费带宽
> 3. **不利于灰度算法**：很多算法只要 Y（人脸识别、运动检测），Packed 提取 Y 要跳跃读取，planar 直接 `data[0]` 一整块连续读
>
> 对比 4:2:2 的 Packed（YUYV/UYVY）是存在的——因为 4:2:2 数量是 2:1，可以优雅交错。4:2:0 数量是 4:1，交错就非常别扭了。

---

### Q2.7 ⭐ YUV420P 的内存怎么算？三个平面各多大？

**参考答案**：

> 以 1920×1080 YUV420P 为例：
> - Y 平面：1920×1080 字节（每个像素一个 Y）
> - U 平面：960×540 字节（宽高各减半）
> - V 平面：960×540 字节
> - 总大小 = 1920×1080 + 2×960×540 = 1920×1080×1.5 ≈ 3.1 MB
>
> 注意每个平面可能有自己的 linesize（对齐后的行宽），实际内存占用略大于理论值。

---

### Q2.8 ⭐⭐ 什么场景下 YUV420P 要先转 RGB？能绕过去吗？

**参考答案**：

> 当渲染目标只认 RGB 时需要转——比如你要在 OpenGL 里显示纹理，或者做图像处理（OpenCV 很多算法基于 RGB）。
>
> 但能绕过去。现代 GPU 可以直接采样 YUV 纹理（硬件做 YUV→RGB 转换），Apple 的 Metal 和 Android 的 GL_OES_EGL_image_external 都能直接在着色器里处理 YUV。绕过去的好处是省一次 CPU 端的 sws_scale 转换，延迟更低、CPU 占用更少。
>
> 如果必须在 CPU 端转，用 FFmpeg 的 `sws_scale` 或手写 SIMD 加速的转换函数。

---

### Q2.9 ⭐⭐ 视频花屏/绿屏了，怎么排查是不是像素格式的锅？

**参考答案**：

> 花屏/绿屏大概率是像素格式解释错了。排查顺序：
>
> 1. 确认解码输出的真实像素格式——打印 `frame->format`，别猜
> 2. 确认下游（渲染/编码）期望什么格式
> 3. 确认中间的 SwsContext 配置的 src/dst 格式是否正确
> 4. 如果是硬件解码，确认 frame 数据在 GPU 还是 CPU——`sws_scale` 只能处理 CPU 内存
> 5. 检查 linesize 是否被正确使用——用 width 替代 linesize 会导致逐行偏移错位，画面倾斜
> 6. Android 上特别检查 NV12 vs NV21——红蓝反色是 NV21 喂给 NV12 的经典症状

---

### Q2.10 ⭐⭐ stride、linesize、width 分别是什么意思？

**参考答案**：

> - **width**：图像的逻辑像素宽度，比如 1920
> - **linesize / stride**：内存中一行像素实际占用的字节数。因为 SIMD 对齐，可能大于 `width × 字节数`。比如 width=100 的 RGB24（每像素 3 字节），理论行宽 300 字节，但 linesize 可能是 320
> - **stride** 和 **linesize** 基本同义，stride 是更通用的图形学术语，linesize 是 FFmpeg 的命名
>
> 核心原则：遍历一行像素时，指针偏移用 linesize；计算一行有多少有效像素时用 width。两者永远不要互换。
## 三、SwsContext 图像缩放与格式转换

### Q3.1 ⭐ SwsContext 用来做什么？

**参考答案**：

> `SwsContext` 是 `libswscale` 模块的核心上下文，同时做两件事：**像素格式转换 + 尺寸缩放**。
>
> 用法两步：`sws_getContext` 配置规则（源宽高/格式 → 目标宽高/格式 + 缩放算法），`sws_scale` 执行转换。
>
> 有个很多人忽略的点：它**主要不是做缩放的**。最常见的用法其实是 `YUV420P → RGB24` 转格式但分辨率不变，这才是它的高频场景。
>
> 性能要点：SwsContext 必须复用，不要每帧重建——创建开销很大。格式和尺寸不变的情况下，同一个 context 可以一直用。

---

### Q3.2 ⭐⭐ 写音视频抽帧存 JPEG 的代码，会涉及 SwsContext 吗？

**参考答案**：

> **会，大概率会**。因为解码器输出的 AVFrame 通常是 YUV420P/NV12/P010 等视频像素格式，而 JPEG/MJPEG 编码器通常要求特定输入格式（如 YUVJ420P 或 RGB24）。
>
> 典型流程：`解封装 → 解码得 AVFrame → sws_scale 做像素格式/尺寸/颜色范围转换 → MJPEG 编码器 → 写 .jpg`。
>
> 关键点：
> - `SwsContext` 不负责"压成 JPEG"，它只把原始图像转成编码器吃得下的格式
> - `AVFrame->data` 不能直接写成 .jpg 文件——那是裸像素，不是 JPEG 格式
> - 历史上的 `YUVJ420P`（J=JPEG/full range）现在更推荐用 `yuv420p + color_range=pc` 表达
> - 对比 PPM：PPM 极简（文件头 + RGB 字节），保存 PPM 只要 sws_scale 转 RGB24 后写文件，不需要二次编码

**翻车红线**：说"抽帧就是把 AVFrame->data 写到 .jpg"、说"SwsContext 负责 JPEG 压缩"。

---

### Q3.3 ⭐⭐⭐ 多线程场景下能多个解码线程共用一个 SwsContext 吗？

**参考答案**：

> **不能**。SwsContext 内部有状态，**不是线程安全的**。
>
> 每个线程要么各自创建一个 SwsContext，要么用锁串行化。工程上常见做法：每个解码线程绑一个自己的 SwsContext。
>
> 如果想优化创建开销，可以用 `sws_getCachedContext`——它会比对参数是否变化，没变就复用旧的，变了才重建。内部其实是维护了一个 static 的 context 缓存，用参数做 key 查找。

---

### Q3.4 ⭐⭐ SwsContext 的缩放算法怎么选？各有什么 trade-off？

**参考答案**：

> FFmpeg 提供了多种缩放算法，常用的是：

| 算法 | 速度 | 质量 | 场景 |
|------|------|------|------|
| `SWS_FAST_BILINEAR` | 最快 | 一般 | 实时预览、缩略图 |
| `SWS_BILINEAR` | 快 | 尚可 | 默认选项，平衡 |
| `SWS_BICUBIC` | 中等 | 好 | 通用高质量缩放 |
| `SWS_LANCZOS` | 慢 | 最好 | 离线转码、最终输出 |
| `SWS_SPLINE` | 最慢 | 极好 | 极端质量要求 |

> 实时场景选 FAST_BILINEAR，质量优先选 LANCZOS。`sws_getContext` 的 flags 参数里指定。

---

### Q3.5 ⭐⭐ 硬件解码帧能直接喂给 sws_scale 吗？为什么？

**参考答案**：

> **绝对不能**。`sws_scale` 是纯 CPU 实现，它需要 CPU 指令能直接读写 `data[]` 里的内存。
>
> 硬件解码的帧，`data[0]` 指向的是 **GPU 显存或硬件句柄**（`AV_PIX_FMT_CUDA`/`VIDEOTOOLBOX`/`VAAPI` 等特殊格式），CPU 直接读会 segfault 或走极慢的 PCIe 回读。
>
> 正确做法两种：
> 1. `av_hwframe_transfer_data` 把数据从 GPU 下载到 CPU 内存，然后再 sws_scale
> 2. 用硬件滤镜（`scale_cuda`/`scale_videotoolbox`/`scale_vaapi`）在 GPU 上做，全程不下载
>
> 方案 2 性能更好但平台绑定，方案 1 通用但多一次 PCIe 拷贝。
## 四、音频 PCM 与重采样

### Q4.1 ⭐ PCM 播放必须知道哪几个参数？少任何一个会怎样？

**参考答案**：

> **五个**：采样率、采样格式（位深+类型）、声道数、声道布局、内存排列（Planar/Packed）。
>
> 任何一个错都会出问题：
> - 采样率错 → 变速变调
> - 采样格式错 → 杂音（FLTP 当 S16 放 = 刺耳噪音）
> - 声道数错 → 速度异常
> - 声道布局错 → 左右反 / 5.1 错位
> - Planar/Packed 错 → 杂音 / 只有一边有声音
>
> 一句话总结：**PCM 是裸字节流，没头信息，必须靠外部参数告诉它怎么解读**。不像 MP3/AAC 自带帧头描述参数。

---

### Q4.2 ⭐ 为什么 FFmpeg 解码 AAC 后直接送 SDL 播放是刺耳杂音？

**参考答案**：

> 因为格式不匹配。AAC 解码默认输出 **FLTP**（32 位浮点、Planar），而 SDL 默认期望 **S16**（16 位整数、Packed）。数值类型和声道排列**同时全错**，必然是刺耳杂音。
>
> 解决：中间插一个 `SwrContext` 做 `FLTP → S16 Packed` 的转换 + 必要的重采样。
>
> 为什么 AAC 偏偏输出 FLTP？因为 AAC 编码内部做频域变换和心理声学分析，浮点不会溢出、Planar 让左右声道独立计算——对编码器友好。而声卡/SDL 要 S16 Packed——硬件一路扫过去就能用。两边诉求天生不一样。

---

### Q4.3 ⭐ 音频解码为什么 send_packet 后必须 while 循环 receive_frame？

**参考答案**：

> 因为一个音频 packet（特别是 AAC）**可能包含多帧**。只 receive 一次会丢音频帧，听感就是断断续续。
>
> 正确写法：
> ```c
> avcodec_send_packet(ctx, pkt);
> while (avcodec_receive_frame(ctx, frame) >= 0) {
>     // 处理音频帧
> }
> ```
> 对比视频：视频通常一包一帧，写成单次 receive 也没事，但**音频绝对不能偷懒**。

---

### Q4.4 ⭐⭐ 重采样输出 buffer 大小怎么算？为什么不能简单按比例？

**参考答案**：

> **不能简单按 `in_samples × out_rate / in_rate`** 算。因为 SwrContext 内部有缓存和滤波延迟。
>
> 正确公式：
> ```c
> int64_t delay = swr_get_delay(swr, in_sample_rate);
> int out_samples = av_rescale_rnd(delay + in_nb_samples, out_rate, in_rate, AV_ROUND_UP);
> ```
> 算错会发生什么：**buffer 不够 → 丢尾音或偶发爆音**。
>
> 工程上通常用 `av_samples_alloc_array_and_samples` 自动分配，省心又安全。

---

### Q4.5 ⭐⭐ 为什么音视频同步通常以音频为主时钟？（同 Q1.9，略）

**参考答案**：

> 见 Q1.9。核心：人耳比人眼敏感得多，让音频自由跑、视频追音频。

---

### Q4.6 ⭐⭐⭐ AAC 编码为什么需要 AVAudioFifo？

**参考答案**：

> 因为麦克风采集回调每次给出的样本数（比如 480 samples @ 10ms）和 AAC 编码器要求的 frame_size（1024）**不一致**。
>
> 需要用 FIFO 攒够 1024 samples 才能调一次编码：
> ```
> 采集 480 → FIFO（现有 480，不够）
> 采集 480 → FIFO（现有 960，不够）
> 采集 480 → FIFO（现有 1440）→ 取 1024 编码，剩 416
> ```
> FFmpeg 提供 `AVAudioFifo` 专门做这件事。还有一个重要的收尾操作：编码结束时 FIFO 里可能剩 < 1024 的样本，要 flush 出来单独编码。
>
> 对比 Opus 编码器：Opus 支持 2.5/5/10/20/40/60ms 多档帧长，相对灵活，不一定需要 FIFO 攒包。

---

### Q4.7 ⭐⭐⭐ AEC（回声消除）为什么必须有"远端播放参考信号"？

**参考答案**：

> 通话时扬声器播远端声音，本地麦克风把这个声音又采进去传回远端 → 远端听到自己的回声。
>
> AEC 要从麦克风信号里估计并减掉回声分量，必须知道远端原本播的是什么——这就是参考信号（far-end reference）。没有参考信号就只能做抑制/猜测，无法做真正的抵消。
>
> 同时还要估计"播放到采集"的延迟（通常几十到上百毫秒），否则参考信号和回声对不齐，消除效果会很差甚至引入失真。
>
> 类比：就像你要从"人声+背景音乐"的录音里去掉背景音乐——如果你手里有原始背景音乐文件，就能对齐后抵消；没有的话就很难分清楚。
>
> WebRTC 的音频处理模块（APM）内置了成熟的 AEC + NS + AGC + VAD 一整套，很多 RTC 项目直接复用。

**翻车红线**：说"AEC 就是降噪"、说"把麦克风音量调小就能消回声"。

---

### Q4.8 ⭐ Planar 和 Packed 有什么区别？搞错会怎样？

**参考答案**：

> - **Packed（交错）**：`L R L R L R ...`，所有声道交错在一个 `data[0]` 里；声卡/SDL 常见
> - **Planar（平面）**：左声道一整块、右声道一整块，`data[0]`=左、`data[1]`=右；AAC 解码默认 FLTP 就是此类
>
> 搞错的后果：
> - 把 Planar 当 Packed 解读 → **刺耳杂音**
> - 只读 `data[0]` → **只有一边有声音**
>
> 格式后缀规律：`S16` vs `S16P`、`FLT` vs `FLTP`——带 `P` 一般是 Planar。SwrContext 可以同时做 Planar↔Packed 转换，不必手写交错。

**翻车红线**：说"Planar 就是压缩格式"——错，只是内存排列方式。

---

### Q4.9 ⭐⭐ 视频/直播为什么常用 48000 Hz 而不是 44100 Hz？

**参考答案**：

> 44100 来自 CD 历史；48000 在视频、广播、直播、移动端更普及。
>
> 很多设备的硬件原生采样率就是 48k。如果全链路统一 48k——采集、处理、编码、播放——就可以**少一次重采样**，降低延迟和失真风险。
>
> 44100 PCM 按 48000 播放 → 变快变高；反过来变慢变低。
>
> 其他常见采样率：语音/VoIP 用 16000，电话窄带用 8000——按场景选，不是越高越好。

---

### Q4.10 ⭐⭐ 混音为什么会爆音？为什么复杂混音要先转 float？

**参考答案**：

> **爆音 = 削波（Clipping）**：样本超过格式可表示范围被截断，波形顶部被削平。两路 S16 直接相加很容易超过 ±32767 → 立刻削波。
>
> 工程做法：先转 **float 混音**（float 中间值可以 >1.0，不会立刻削波），混音完做 limiter/压缩，最后转回 S16。
>
> float32 的有效精度约 24 bit，对混音通常高于 S16 够用。但 float → S16 转换时硬截断会糙，专业链路会加 dither（进阶）。
>
> 简单公式：`float_sample = s16_sample / 32768.0f`，混完 `s16 = clamp(f, -1.0, 1.0) * 32767`。

**翻车红线**：说"float 精度比 S16 低所以不适合混音"——和事实相反。

---

### Q4.11 ⭐ nb_samples 是总样本数还是每声道样本数？一帧音频多长？

**参考答案**：

> `AVFrame->nb_samples` = **每个声道的样本数**，不是 L+R 总和。
>
> 时长：`duration = nb_samples / sample_rate`。比如 1024 samples @ 48kHz = 1024/48000 ≈ **21.33 ms**。
>
> AAC-LC 常见固定 1024 样本/帧，这也是编码、FIFO、网络分包常见的时间粒度。
>
> Packed 字节数：`nb_samples × channels × bytes_per_sample`，但建议用 `av_samples_get_buffer_size` 更稳。音频的 `linesize[0]` 也可能因对齐大于理论值——和视频 linesize 同类坑。

---

### Q4.12 ⭐⭐ 音频播放回调里为什么不能阻塞？Underrun 是什么？

**参考答案**：

> 回调多在**高优先级实时线程**上执行。阻塞（锁、IO、解码、频繁 malloc、打日志）→ 来不及供数据 → **Underrun**（断音、卡顿）。
>
> 推荐架构：**解码线程**提前生产 PCM 写入环形缓冲 → **回调只 memcpy 从缓冲读**。
>
> - **Underrun**：播放设备要数据，应用没准备好 → 断音
> - **Overrun**：生产太快/消费太慢 → 缓冲堆积、**延迟升高**，最终丢数据
>
> 缓冲太小 → 低延迟但不稳；太大 → 稳但延迟高——永远在两者间权衡。

**翻车红线**：说"在回调里 decode 最省事"——典型线上卡顿来源。

---

### Q4.13 ⭐⭐ Seek 之后为什么容易音画不同步？要清什么？

**参考答案**：

> Seek 后若不清干净，队列/解码器/重采样器里仍残留 seek 前的旧数据 → 先播旧内容再跳新位置 → 不同步。
>
> 正确清单：
> 1. 清空 packet/frame queue
> 2. `avcodec_flush_buffers` 清解码器内部状态
> 3. 重置或 flush SwrContext（有滤波延迟和内部缓存）
> 4. 重置 audio clock
>
> Seek 后时钟也要从新媒体时间重新对齐。

---

### Q4.14 ⭐⭐⭐ 实时互动为什么用 Opus 而不是 AAC？

**参考答案**：

> - **AAC-LC**：帧长固定 1024 样本（48kHz≈21ms）+ 常需 FIFO 攒包 → 延迟高；无内建抗丢包；点播/直播存档/MP4 主力
> - **Opus**：帧长 2.5~60ms 可配（常 20ms），可对齐采集回调；**内建 PLC + in-band FEC** 抗丢包；**免版税**；WebRTC 强制必选，RTP 直载，参数靠 SDP 协商不必每帧 ADTS
>
> 取舍：**在乎几十毫秒延迟和丢包** → Opus；**高码率存档/广电** → AAC。
> Opus 融合了 SILK（语音）和 CELT（音乐）双核，语音/音乐自适应。
>
> PLC = 猜一段填上（听感自然但不恢复真内容）；FEC = 下一包带前一帧冗余，可部分重建丢包。

**翻车红线**：说"Opus 音质一定比 AAC 好"——比的是实时链路指标，不是单纯音质分。

---

### Q4.15 ⭐⭐ 听到某种异常，怎么从 PCM 五参数反查原因？（故障速查）

**参考答案**：

| 听感/现象 | 优先怀疑 |
|-----------|---------|
| 刺耳杂音 | 格式错（FLTP 当 S16）、Planar/Packed 错、采样率错 |
| 变快/变慢/变调 | 采样率解释错（44100↔48000） |
| 断断续续 | 音频 decode 只 receive 一次、网络丢包未 PLC |
| 音画不同步 | 未以音频为主时钟、Seek 未 flush、未扣设备 buffer 延迟 |
| 只有一边 | Planar 只读了 data[0] |
| 爆音 | S16 混音溢出削波、重采样 buffer 不够 |
| 完全没声 | 没音频流/解码失败/没写设备/静音 |

> 排查技巧：用 `ffplay -f s16le -ar 48000 -ac 2 dump.pcm` 验证裸 PCM，快速排除"数据本身坏了还是参数错了"。

---

### Q4.16 ⭐⭐ SwrContext 和 SwsContext 的异同？

**参考答案**：

> 它们是对称的设计——同属 FFmpeg 的"加工车间"层。
> - SwsContext（libswscale）：视频的像素格式转换 + 缩放
> - SwrContext（libswresample）：音频的采样率转换 + 采样格式转换 + 声道布局转换 + Planar↔Packed 转换
>
> 相同的设计模式：get/alloc 创建 → init 初始化 → convert 循环使用 → free 释放。都要复用，不能每帧重建。

---

### Q4.17 ⭐⭐ 如何用 ffplay 验证一段裸 PCM 数据？

**参考答案**：

> 裸 PCM 没有头信息，必须手动指定参数：
> ```bash
> # S16, 双声道, 48000Hz, packed, 小端
> ffplay -f s16le -ar 48000 -ac 2 dump.pcm
>
> # float, 双声道, 44100Hz, packed, 小端
> ffplay -f f32le -ar 44100 -ac 2 dump.pcm
> ```
> 参数写错听到的结果也会错——这本身就是个验证工具：如果改了参数声音正常了，说明原来的参数配置有问题。

---

### Q4.18 ⭐⭐ 音频延迟从采集到播放经过哪些环节？

**参考答案**：

> 完整的端到端延迟链路：
>
> 1. **采集延迟**：麦克风硬件 + 系统音频栈缓冲（通常几 ms 到几十 ms）
> 2. **前处理延迟**：降噪/回声消除/AEC 的帧缓冲
> 3. **编码延迟**：AAC ~20-40ms，Opus 可低至 5ms
> 4. **打包/传输延迟**：网络 RTT + 抖动缓冲（jitter buffer）
> 5. **解码延迟**：通常远小于编码
> 6. **后处理/重采样延迟**：SwrContext 内部滤波延迟
> 7. **播放缓冲延迟**：系统音频 API 的环形缓冲（通常几十到上百 ms）
>
> 降低延迟的核心战场在 3、4、7 三项——选低延迟 codec、缩小 jitter buffer、减小播放缓冲区。
## 五、H.264/H.265/NALU/封装

### Q5.1 ⭐ MP4 转 H.264 是不是转码？

**参考答案**：

> **通常不是**。前提是 MP4 视频轨本身就是 H.264。做的事是**解封装 + 码流重打包**：
> 1. 按 moov 索引从 mdat 取视频样本
> 2. AVCC → Annex-B 转换
> 3. 从 avcC 提取 SPS/PPS 注入
>
> 整个过程**没有 decode + encode**，画质不损失。FFmpeg 命令：`ffmpeg -i a.mp4 -c:v copy -bsf:v h264_mp4toannexb a.h264`。
>
> 只有当编码不一致（HEVC→H.264）或要改编码参数（分辨率/码率/帧率）时才需要真正的转码。

**翻车红线**：说"是的，转码"——直接扣分。

---

### Q5.2 ⭐ AVCC 和 Annex-B 的差别一句话怎么说？

**参考答案**：

> - **AVCC**：每个 NALU 前加 **4 字节长度字段**。MP4/FLV/MKV 用。SPS/PPS 集中在 extradata（avcC box）
> - **Annex-B**：每个 NALU 前加**起始码** `00 00 00 01`（或 `00 00 01`）。RTMP/TS/RTP/裸 .h264 用。SPS/PPS 作为普通 NALU 混在流里
>
> 经典 bug：MP4 里的 H.264 字节直接喂 Android MediaCodec 会**黑屏**，因为硬解只认 Annex-B。用 `h264_mp4toannexb` bitstream filter 解决。这是音视频开发最经典的踩坑现场。
>
> 为什么 MP4 用 AVCC？因为 MP4 已有 moov 索引能精确定位每个 sample，不需要起始码；长度前缀反而解析更快。为什么直播用 Annex-B？直播流没有全局索引，需要靠起始码切 NALU 边界。

---

### Q5.3 ⭐ 为什么有 PTS 和 DTS 两个时间戳？

**参考答案**：

> 因为有 **B 帧**。B 帧需要参考后面的 P 帧才能解码 → **解码顺序 ≠ 显示顺序**。
>
> - DTS（Decoding Time Stamp）：告诉解码器什么时候解码
> - PTS（Presentation Time Stamp）：告诉渲染器什么时候显示
> - 无 B 帧时 PTS == DTS
>
> 例子：
> ```
> 显示顺序: I₀ B₁ B₂ P₃ B₄ B₅ P₆
> 解码顺序: I₀ P₃ B₁ B₂ P₆ B₄ B₅
> ```
> P₃ 必须先解码（因为 B₁ B₂ 依赖它），但 P₃ 要在 B₁ B₂ 之后才显示。

---

### Q5.4 ⭐⭐ 为什么直播场景要在每个 IDR 前注入 SPS/PPS？

**参考答案**：

> 解码器**必须先拿到 SPS/PPS 才能解码任何帧**。直播观众随时切入——如果只在文件头注入一次，中途加入的观众没拿到 SPS/PPS → **黑屏/花屏**直到下一次出现。
>
> 每个 IDR 前注入：体积略增（每个 IDR 多几十字节），但中途入会成功率大幅提升。SPS 描述整段视频的宽高/profile/level，PPS 描述编码细节。两者合在一起是解码器的"启动说明书"。
>
> IDR ≠ I 帧：IDR 是特殊的 I 帧，**强制清空之前所有参考帧缓冲**。所以 seek/切入只能跳到 IDR 上，跳到普通 I 帧不行——它后面的帧可能还在参考它之前的帧。

---

### Q5.5 ⭐⭐ AAC 在 MP4 里和在 TS 直播流里格式有什么差别？

**参考答案**：

> - **MP4 里是 raw AAC**：参数（采样率、声道）集中在文件头的 `esds` box，每帧不重复携带，省空间
> - **TS 直播里是 ADTS**：每帧前加 7 字节 ADTS header，包含同步字 `0xFFF`、采样率、声道、帧长
>
> 设计动机和视频 AVCC vs Annex-B **完全对应**：存储优化 vs 传输鲁棒性。观众随时切入直播，每帧必须自带"说明书"，否则无法立刻开始解码。
>
> 这也是为什么从 FLV/MP4 里直接 dump AAC 数据存成 .aac 文件可能播不了——播放器期望 ADTS 头。

---

### Q5.6 ⭐⭐⭐ 普通 B 帧和参考 B 帧弱网时能丢哪个？怎么判断？

**参考答案**：

> - **普通 B 帧**：不被任何帧参考，**可以随意丢**，顶多画面不流畅
> - **参考 B 帧**（分层 B / Hierarchical B）：被其他 B 帧参考，**绝对不能丢**，丢了依赖它的子帧会花屏
>
> 判断方法：解析 NALU header 里的 `nal_ref_idc` 字段。`nal_ref_idc > 0` 表示这个 NALU 被参考——不管是参考 B 帧还是 I/P 帧都不能丢。
>
> 工程意义：直播弱网降帧策略**必须分辨这两种**——丢错就花屏。这是 H.264/H.265 的高级特性，用于极致压缩。

---

### Q5.7 ⭐⭐ 讲讲 H.264 是怎么把视频压缩这么小的？（开放题）

**参考答案**：

> 按"消除四种冗余"来答：

**空间冗余** → 帧内预测：同一帧里相邻像素颜色差不多，用周围已编码块预测当前块，只编残差（差值）。比 JPEG 高效——JPEG 的 8x8 块各自独立变换，块间不交流；H.264 I 帧会"偷看"邻居。

**时间冗余** → 帧间预测 + 运动估计：相邻两帧大部分内容没变，在参考帧里搜最像的块，记下"运动矢量 + 残差"。这是视频压缩率比图片序列高一个数量级的根本原因。

**视觉冗余** → DCT 变换 + 量化：人眼对高频不敏感。变换把能量集中到低频，量化时对高频系数狠狠除一下——**有损就发生在量化这一步**。QP/CRF 就是调量化粗细的旋钮。

**统计冗余** → 熵编码（CABAC/CAVLC）：高频符号给短码、低频给长码，再压一把。

> 流水线：**预测 → 残差 → 变换 → 量化 → 熵编码**。解码反过来 + 环路滤波（去块效应，防止马赛克在帧间传播）。
>
> 加上 H.265 的改进：CTU 四叉树（最大 64×64 取代固定 16×16 宏块）、35 种帧内预测方向、SAO 滤波——同画质再省约 50% 码率。代价是编码复杂度翻倍 + 专利授权碎片化。

---

### Q5.8 ⭐⭐ 为什么直播用 FLV/TS 而不用普通 MP4？

**参考答案**：

> 普通 MP4 的 `moov` 索引要等录完才能写——每个 sample 的偏移/时序依赖于整个文件的最终布局。直播没有"录完"这一刻，写不出 moov。
>
> **FLV/TS 是流式结构**：
> - FLV：Tag 流，来一片发一片，不需要末尾索引
> - TS：188 字节固定小包 + PAT/PMT，任意位置切入都能对齐
>
> 要用 MP4 系做直播，得用 **fragmented MP4（fMP4）**——`moof`+`mdat` 分片，每个分片有自己的局部索引。这是 HLS/DASH/CMAF 的基础。
>
> MP4 点播要边下边播得用 `-movflags +faststart` 把 moov 挪到文件头。

---

### Q5.9 ⭐ NALU 是什么？怎么解析 NALU type？

**参考答案**：

> NALU（Network Abstraction Layer Unit）是 H.264 的基本数据单元。每个 NALU = 1 字节 header + payload。
>
> NAL header 的低 5 bit 是 `nal_unit_type`：
>
> | type | 名称 | 含义 |
> |------|------|------|
> | 1 | non-IDR slice | 普通 P/B 帧 |
> | 5 | IDR slice | 即时解码刷新帧（特殊 I 帧） |
> | 6 | SEI | 补充增强信息 |
> | 7 | SPS | 序列参数集 |
> | 8 | PPS | 图像参数集 |
> | 9 | AUD | 访问单元分隔符 |
>
> 解析代码：`nal_unit_type = byte & 0x1F`（仅 H.264）。
>
> **迁移警告**：H.265 的 NAL header 是 **2 字节**，type 取 `(byte >> 1) & 0x3F`。把 H.264 的 `& 0x1F` 原样搬到 H.265 是最经典的迁移 bug。

---

### Q5.10 ⭐ IDR 帧和普通 I 帧有什么区别？

**参考答案**：

> - **普通 I 帧**：只用帧内预测，不参考其他帧。但它**不清空参考帧缓冲**——它后面的 P/B 帧仍然可以参考它前面的帧
> - **IDR 帧**（Instantaneous Decoding Refresh）：也是 I 帧，但**强制清空所有参考帧缓冲**。IDR 之后的帧**绝对不能**参考 IDR 之前的帧
>
> 这就是为什么：
> - Seek 只能跳到 IDR——跳到普通 I 帧，后面的帧可能还在参考 seek 点之前的帧，解码器参考链断掉 → 花屏
> - 直播中途切入只能从 IDR 开始——同一个原因
> - IDR 也叫"随机接入点"（Random Access Point）

---

### Q5.11 ⭐⭐ GOP 是什么？短 GOP 和长 GOP 怎么选？

**参考答案**：

> GOP（Group of Pictures）= 两个 I/IDR 帧之间的一组帧。一个 GOP 里通常有 1 个 I 帧 + 若干个 P 帧和 B 帧。
>
> - **短 GOP**（1-2 秒）：seek 快、直播秒开快、抗丢包好——丢了很快能等来下一个 I 帧恢复。代价：I 帧占比高，压缩率略差
> - **长 GOP**（5-10 秒）：压缩率高（更多 P/B 帧），适合点播和存档。代价：seek 慢、丢包后恢复慢
>
> 直播一般用短 GOP（1-2 秒一个 IDR），这样新观众最多等 2 秒就能看到画面。

---

### Q5.12 ⭐⭐ SPS 和 PPS 分别存了什么？H.265 为什么多一个 VPS？

**参考答案**：

> - **SPS（Sequence Parameter Set）**：序列级参数——分辨率、Profile、Level、帧率范围、参考帧数量上限
> - **PPS（Picture Parameter Set）**：图像级参数——熵编码模式（CAVLC/CABAC）、量化参数初始值、slice 分组方式
> - **VPS（Video Parameter Set，仅 H.265）**：视频级参数——描述多层/可分级编码、码流整体的 profile_tier_level。H.265 支持多图层（比如同一个视频有 HD 和 UHD 两个版本在同一个码流里），需要 VPS 描述层级关系
>
> SPS/PPS 在每个 IDR 前注入是直播标配操作。

---

### Q5.13 ⭐ H.264 的防竞争字节（Emulation Prevention Byte）是什么？

**参考答案**：

> Annex-B 靠 `00 00 01` 切 NALU 边界，但编码器输出的压缩数据里**万一刚好出现 `00 00 01` 这个字节序列**怎么办？解码器不就切错了吗？
>
> H.264 用 **防竞争字节 `0x03`** 解决。编码端扫描 NALU payload，发现以下模式就在第二个 `0x00` 后插 `0x03`：
> ```
> 00 00 00 → 00 00 03 00
> 00 00 01 → 00 00 03 01
> 00 00 02 → 00 00 03 02
> 00 00 03 → 00 00 03 03
> ```
> 解码端反过来：看到 `00 00 03` 就把 `03` 丢掉。这样 payload 里绝对不会出现裸的 `00 00 01`，切边界就是安全的。

---

### Q5.14 ⭐⭐ H.264 的 Profile 和 Level 经常被搞混，怎么区分？

**参考答案**：

> - **Profile**：决定**算法复杂度**——能不能用 B 帧、能不能用 CABAC、能不能做 8x8 变换。Baseline 为了低功耗低延迟砍掉 B 帧和 CABAC；Main 加上；High 再加 8x8 变换
> - **Level**：决定**性能上限**——最大分辨率、帧率、码率、参考帧缓冲有多大。比如 Level 4.0 支持 1080p@30fps
>
> 经典错误问题："Level 4.0 支持 B 帧吗"——支不支持 B 帧是 Profile 的事，跟 Level 没关系。
>
> 实时通信用 Baseline Profile（无 B 帧，延迟低）；点播用 High Profile（压缩率最高）。

---

### Q5.15 ⭐⭐ H.264 的起始码 3 字节和 4 字节什么时候用哪个？

**参考答案**：

> `00 00 01`（3 字节）和 `00 00 00 01`（4 字节）都合法。规律：
>
> **必须用 4 字节**的情况：SPS(7)/PPS(8)/SEI(6)/AUD(9) 等参数集和辅助 NALU；slice NALU 且上一个 NALU 末尾是 `0x00` 时（防止边界混淆）。
>
> 其余 slice NALU 用 3 字节即可。
>
> 工程上：x264 按规范混用 3/4；FFmpeg `h264_mp4toannexb` **一律 4 字节**——实现简单、永远合法；自己手写转换也建议统一 4 字节。

---

### Q5.16 ⭐⭐ SEI 是什么？有什么用？

**参考答案**：

> SEI（Supplemental Enhancement Information）是 H.264/H.265 的辅助信息 NALU，type=6。它不是解码必需的——丢了不影响画面，但可以带很多有用信息：
>
> - HDR 元数据（色彩空间、亮度范围）
> - 时间码
> - 私有 metadata（自定义数据透传通道）
> - 缓冲周期、画面定时信息
>
> WebRTC 里经常借 SEI 透传自定义数据或时间戳，因为 SEI 跟视频帧走同一条 RTP 流，天然同步。
>
> 编码时加 SEI：x264 用 `--sei` 参数，或 FFmpeg API 里通过 side_data 注入。

---

### Q5.17 ⭐⭐ MP4 的 moov box 为什么有时在文件头有时在文件尾？

**参考答案**：

> moov 包含了所有 sample 的时间戳和字节偏移——这些信息在编码和封装过程中逐步积累，**只有封装完才知道最终值**。所以默认写在文件末尾（写完 mdat 之后才写 moov）。
>
> 问题：文件尾的 moov 意味着播放器要下载完整个文件才能开始播——不适合在线视频。解决：
> - **faststart**（`-movflags +faststart`）：封装完后把 moov 挪到文件头，播放器一开始就能拿到索引，秒开
> - **fragmented MP4（fMP4）**：不写全局 moov，每个分片有自己的 moof + mdat，适合直播/HLS/DASH
>
> 这就是为什么点播优化里"moov 前置"是基础操作。

### Q5.18 ⭐⭐ Annex-B 的防竞争字节（同 Q5.13，互补展开）

**参考答案**：

> 见 Q5.13。

### Q5.19 ⭐⭐ H.265 相比 H.264 的核心改进有哪些？

**参考答案**：

> 关键改进：
> 1. **CTU 四叉树**：编码块从固定 16×16 宏块 → 最大 64×64 CTU，内容自适应（平坦区域用大块省 header，细节区域细分保质量），对 4K 大画面尤其有效
> 2. **帧内预测**：9 种方向 → 35 种（33 角度 + DC + Planar），预测更准
> 3. **环路滤波**：Deblocking → Deblocking + **SAO**（Sample Adaptive Offset），进一步减少失真
> 4. **熵编码**：只有 CABAC（去掉 CAVLC），压缩率更高
> 5. **NAL header 2 字节**，多一层 **VPS**
> 6. **Tiles 和 WPP**（Wavefront Parallel Processing）：更好的并行编码能力
>
> 最终效果：**同画质省约 50% 码率**，但编码复杂度约翻倍。普及慢的主要原因是专利授权碎片化（多个专利池各自收费），不是技术问题。

---

### Q5.20 ⭐⭐⭐ 为什么 WebRTC 多用 H.264 而不是 H.265？

**参考答案**：

> 不是技术问题——H.265 压缩效率确实更高。但 WebRTC 场景有几重障碍：
>
> 1. **浏览器兼容**：H.264 几乎所有浏览器和设备都支持，H.265 浏览器支持差（Chrome 默认不启用，Safari 支持但限于苹果生态）
> 2. **硬件编解码成熟度**：H.264 硬编硬解几乎每台设备都有，H.265 不是——特别是老设备和低端机
> 3. **专利授权**：H.265 授权混乱（MPEG LA + HEVC Advance + Velos Media 三个池子），WebRTC 开源生态对专利非常敏感。H.264 虽然也要授权，但格局相对清晰
> 4. **延迟**：H.265 编码复杂度高得多，实时编码的延迟压力更大
>
> 在实时通信里，**兼容性 + 延迟 > 压缩率**。AV1 作为免专利费的后起之秀未来可能改变格局，但目前硬件编解码覆盖还不够。
## 六、编码参数与码控

### Q6.1 ⭐ H.264 决定压缩率的核心参数有哪些？

**参考答案**：

> 三个**独立维度**：
>
> 1. **Profile**（算法复杂度）：Baseline/Main/High。Baseline 无 B 帧 + 只用 CAVLC——低延迟低功耗；High 全开——压缩率最高
> 2. **Preset**（CPU 算力 vs 压缩率）：ultrafast → veryslow 共 10 档。越慢压缩率越高，但编码越耗时
> 3. **码率控制**：CRF（恒定质量，适合点播）/ CBR（固定码率，适合直播带宽受限）/ VBR + VBV 约束（现代直播黄金方案）
>
> 三个维度独立可组合。典型配置：低延迟直播 = Baseline + ultrafast + tune=zerolatency + CBR；高质量点播 = High + veryslow + CRF 18。

---

### Q6.2 ⭐ WebRTC/视频会议为什么必须用 Baseline Profile？

**参考答案**：

> Baseline **不支持 B 帧**。没有 B 帧 → 解码器不需要等待后续帧 → **延迟极低**。
>
> 同时配合 `tune=zerolatency` 关闭编码器内部 lookahead 缓冲——双保险。
>
> High Profile 虽然压缩率最高，但天然引入 B 帧 → 解码器需要缓冲重排序 → 延迟不可接受。
>
> WebRTC SDP 协商时常见的 `profile-level-id=42e01f` 就是 Baseline + Level 3.1。

---

### Q6.3 ⭐⭐ CRF 数值越大画质越好还是越差？甜点区在哪？

**参考答案**：

> **数值越大画质越差**。CRF 范围 0-51（x264）。
> - 甜点区 18-28（默认 23）
> - 18：视觉上基本无损，但文件大
> - 23：默认值，画质和体积的平衡点
> - 28+：能看出马赛克
>
> CRF vs Bitrate：**CRF 画质稳定但文件大小不确定**，适合点播；**Bitrate 模式带宽可预测**，适合直播。
>
> 注意：CRF 不跨编码器可比——x265 默认 CRF 28 和 x264 CRF 23 画质差不多。

---

### Q6.4 ⭐⭐ 为什么直播推流要同时设 -maxrate 和 -bufsize？

**参考答案**：

> `-maxrate`：限制瞬时码率峰值，防止突发流量冲爆 CDN 带宽配额。
> `-bufsize`：决定**峰值能持续多久**——越大越能容忍长峰，但累积延迟也越大。本质是 VBV（Video Buffering Verifier）模型——模拟解码端缓冲区。
>
> 工程经验：`bufsize` 通常设为 `maxrate × 1-2 秒`。
>
> 现代商业直播的黄金方案不是纯 CBR，而是 **VBR + maxrate + bufsize（VBV 约束）**——静态省流量、复杂画面保清晰度、带宽峰值可预测。

---

### Q6.5 ⭐⭐⭐ 设置 CRF 为什么必须用 av_opt_set，不能直接赋值给 codecCtx 字段？

**参考答案**：

> 因为 CRF 是 **x264 编码器的私有参数**，不在 AVCodecContext 的公共字段里。私有参数存在 `codecCtx->priv_data` 里，通过 `av_opt_set` 接口操作。
>
> 对比：`bit_rate` 是公共字段，可以直接 `codecCtx->bit_rate = 2000000`。
>
> 这是 FFmpeg 的通用设计——通过 `priv_data` + `AVOption` 系统允许每个 codec 暴露独有参数。其他常用的 `av_opt_set` 调用：`preset`/`tune`/`profile`。

---

### Q6.6 ⭐⭐ Preset 从 ultrafast 到 veryslow 到底调了什么？

**参考答案**：

> Preset 调整的是编码器**搜索最优编码方式的努力程度**：
> - ultrafast：不做亚像素运动估计、不做多参考帧、关闭 B 帧的许多优化——几乎就是把帧"糊"进去。极快但码率高
> - medium：默认档，各项优化适中
> - veryslow：开启所有搜索优化——亚像素精度运动估计、多参考帧、分区决策、率失真优化——每一帧都花了大量 CPU 时间找最优编码方式
>
> 从 ultrafast → veryslow，编码时间可能差 10 倍，码率可能省 30-50%。实时场景用 ultrafast，离线转码用 slow/veryslow。

---

### Q6.7 ⭐⭐⭐ CBR、VBR、ABR 三种码控模式的区别？每种是怎么工作的？

**面试官意图**：中高级岗位不能只回答"CBR 固定码率、VBR 可变码率"——这是初级回答。面试官要听的是每种模式的**编码器内部决策机制**，以及**什么时候用哪个、为什么**。

**参考答案（口语化）**：

> 三种模式的区别，核心看一个问题：编码器每编码一帧时，"目标"是什么？
>
> **CBR（Constant Bitrate，固定码率）**——目标是"每帧的码率都接近同一个值"。
> 编码器内部有一个逐帧运行的反馈循环：每编完一帧，看这帧有没有超支。如果上一帧用了太多比特，这帧就提高 QP（降低画质），把码率压回去；如果上一帧用得少，这帧可以稍微放松。这个循环逐帧运行，所以码率曲线近乎一条直线。
> FFmpeg 里要做纯 CBR 需要同时设 `-b:v`、`-maxrate`、`-minrate` 三个值相同，并且 `-bufsize` 设得很小。只设 `-b:v` 不加约束，x264 默认走的是 ABR 而不是 CBR。
> CBR 的代价很清楚：静态画面浪费带宽（明明 1500kbps 就够，却必须塞满 4000kbps），复杂画面牺牲画质（码率被上限卡死，只能提高 QP，满屏马赛克）。但好处是带宽绝对可预测——CDN 节点和播放端可以精确预测每一秒的流量。传统 RTMP 直播（OBS 推流）、视频会议、卫星/有线电视广播都用 CBR。
>
> **VBR（Variable Bitrate，可变码率）**——目标是"每帧的画质保持稳定"。
> 编码器先定质量目标（通常由 QP 范围控制），然后根据每帧画面复杂度分配码率。静态画面少量比特就能维持质量，自然用低码率；剧烈运动需要大量比特才能维持同等质量，码率就飙上去。**码率是结果，不是目标**——编码器不关心平均码率是多少，只关心质量是否稳定。
> 纯 VBR 的危险在于瞬时码率可以短时间内暴涨 3~5 倍。直播场景下这是致命的——CDN 无法预测瞬时流量，观众带宽可能被打爆。**直播中纯 VBR 绝对禁止。** VBR 适合本地录制/归档、视频后期中间码、或者配合 VBV 约束后用于现代直播。
> FFmpeg 里 `-crf` 本质上就是 VBR 的一种——恒定画质，码率自适应。
>
> **ABR（Average Bitrate，平均码率）**——目标是"一个时间窗口内的平均码率逼近目标值"。
> ABR 在 VBR 的自由分配基础上，加了一个长时间窗口的紧箍咒。编码器内部维护一个 VBV 缓冲模型——一个虚拟的"桶"。每产出 1 帧，桶里增加该帧的比特数；时间每流逝 1 秒，桶里减少（目标码率 × 1 秒）。桶快满了说明"过去花太多"，后面帧要压更狠；桶快空了说明"过去省了"，后面可以大方些。编码器不是在内存里存过去 N 秒的帧数据，靠的就是这个桶水位来间接衡量历史消耗。
> ABR 允许帧间有波动，但长时间窗口的平均值严格收敛到目标。`bufsize` 控制了这个窗口的大小——`bufsize` 越大，窗口越宽，允许的波动越大，画质越好但延时更高。FFmpeg 里只用 `-b:v`（不加 `-minrate`/`-maxrate`）时，x264 默认走的就是 ABR。实战中 ABR 通常配合 `-maxrate` 使用，防止瞬时码率飙太高。
> ABR 最适合 HLS/DASH 分片（保证每个 .ts/.m4s 分片大小一致，观众切档体验平滑）、视频上传平台（控制总大小的同时保留复杂画面的质量）、监控录像（存储空间可预测）。
>
> **三者不是三个离散的档位**——从 CBR → ABR → VBR，本质上是 `bufsize` 从 0 到 ∞ 的连续谱。`bufsize` 极小（≈ 0.5× maxrate）接近 CBR，`bufsize` 中等（≈ 2× maxrate）是 ABR，`bufsize` 很大（≈ 10× maxrate）接近 VBR。

**👨‍💻 追问：ABR 编码和 ABR 传输是一回事吗？**

> 完全不是。这是音视频领域最严重的重名陷阱之一。
> - **ABR 编码**（Average Bitrate Encoding）：编码器的码率控制算法——管的是编码器内部怎么分配比特，发生在编码阶段。
> - **ABR 传输**（Adaptive Bitrate Streaming）：HLS/DASH 那种播放器根据网络状况动态切换码率档位的技术——管的是播放器选哪个码率档的流，发生在传输/播放阶段。
> ABR 传输的每个分片可以用任何码控模式来编码——CBR、VBR、CRF 都行。但业界通常用 ABR 编码来生成分片，因为它天然适合"让整个分片的平均大小一致"这个需求。面试时被问到 ABR，第一件事就是确认对方问的是编码还是传输。

---

### Q6.7-W ⭐⭐⭐ WebRTC 用的是什么码控？和 CBR/VBR/ABR 是什么关系？

**面试官意图**：考察是否理解 WebRTC 的特殊性——它的码控不是"编码器内部固定策略"，而是网络驱动的动态系统。回答"CBR"或"VBR"都暴露了理解不到位。

**参考答案（口语化）**：

> WebRTC 的码控和前面讲的 CBR/VBR/ABR 完全不在一个维度上。前面讲的都是固定目标的编码策略——目标码率是人定的，比如 4000kbps，整个过程不变。WebRTC 是动态目标的编码策略——目标码率由拥塞控制算法根据网络状况实时计算，编码器只是执行器。
>
> WebRTC 的码控是两层结构：
>
> **上层——拥塞控制（GCC，Google Congestion Control），决定"允许发多快"**：
> GCC 每 ~100ms 运行一次，输出一个动态变化的 target_bitrate。它包含两个子模块：基于延迟的估计（看 RTP 单向延迟趋势，延迟持续上升 → 队列排队了 → 降码率，用 Kalman Filter 做趋势检测）和基于丢包的估计（看 RTCP 反馈的丢包率，丢包 > 2~10% → 快速降码率）。
>
> **下层——编码器执行"怎么发"**：
> 拿到 GCC 给的 target_bitrate 后，libvpx（WebRTC 的 VP8/VP9 软件编码器）会在约束下做 VBR 风格的帧级分配——简单帧少用、复杂帧多用，整体收敛在目标附近，效果接近"目标值实时变化的 ABR"。而硬件编码器（Android MediaCodec / iOS VideoToolbox）大多数设为 CBR 模式——因为硬件编码器的码控鲁棒性不如 libvpx 的软件实现，用 CBR 最安全，目标值由 GCC 动态更新。
>
> 面试时如果被问"WebRTC 用的是什么码控"，不要回答"CBR"或者"VBR"——那是只看到了第二层。正确回答是：**"WebRTC 的码控是两层结构：上层 GCC 做拥塞控制动态决定目标码率，下层编码器在目标码率约束下编码——libvpx 做类 ABR 的帧级分配，硬件编码器做 CBR。"**

---

### Q6.8 ⭐⭐ tune 参数有什么用？常用 tune 有哪些？

**参考答案**：

> `tune` 告诉编码器"这段视频是什么类型"，让编码器针对性优化：
> - `film`：电影内容，高画质
> - `animation`：动画，平坦区域多
> - `grain`：胶片颗粒感，保留纹理
> - `stillimage`：静态图像/幻灯片
> - `zerolatency`：零延迟——关闭 lookahead、帧内线程、多线程前瞻等所有增加延迟的特性
> - `fastdecode`：牺牲压缩率换解码速度
>
> 最常用：直播/会议用 `tune=zerolatency`，电影用 `tune=film`。

---

### Q6.9 ⭐⭐ x264 和 x265 同 CRF 值画质一样吗？

**参考答案**：

> **不一样**。H.265 编码效率更高——同样 CRF 值下 H.265 画质更好但码率不一定更低，或者说同样画质下 H.265 码率更低但 CRF 值更大。
>
> 经验值：x265 CRF 28 ≈ x264 CRF 23 画质。所以面试说"CRF 23 画质好"一定要带"在 x264 下"的前缀。不同编码器的 CRF 语义不互通。

---

### Q6.10 ⭐⭐ 编码器支持哪些采样格式是固定的吗？怎么查？

**参考答案**：

> 不是固定的，不同编码器支持不同的输入格式。通过 codec 的 `pix_fmts`（视频）或 `sample_fmts`（音频）字段查询。
>
> 比如 x264 通常只接受 YUV420P（8bit），x264 10bit 接受 YUV420P10LE；AAC 编码器偏好 FLTP 输入。编码前必须查编码器支持的格式，用 sws_scale/swr_convert 转过去。
>
> 不能假设 AAC 编码器一定吃 S16——很多配置下它只接受 FLTP。
## 七、硬件编解码

### Q7.1 ⭐ 硬件编码画质为什么通常不如同档软件编码？

**参考答案**：

> 硬件编码器为了**流水线效率**，省略了软件编码里"耗时但增益小"的高级搜索算法。同等码率下，软编（x264 slow/veryslow）画质优于硬编（NVENC/VideoToolbox）。
>
> 想让硬编画质追平，**得给更高的码率**——用带宽换画质。
>
> 工程权衡：
> - 直播/大批量转码（吞吐和成本优先）→ 硬编
> - 电影/高质量点播（压缩比优先）→ 软编
> - 移动端录制（功耗优先）→ 硬编
>
> NVENC 在 Turing/Ampere/Ada 几代上画质大幅提升，接近 x264 medium，但极致质量仍输 x264 slow。

---

### Q7.2 ⭐ 硬件解码出来的 AVFrame 能直接喂给 sws_scale 吗？

**参考答案**：

> **绝对不能**。sws_scale 是纯 CPU 实现，需要 CPU 指令能直接读 data[] 里的内存。
>
> 硬件帧的 data[0] 指向的是 **GPU 显存或硬件句柄**（`AV_PIX_FMT_CUDA`/`VIDEOTOOLBOX`/`VAAPI` 等），CPU 直接读会 segfault 或走极慢的 PCIe 回读。
>
> 正确做法两种：
> 1. `av_hwframe_transfer_data` 下载到 CPU 内存 → sws_scale（通用但多一次 PCIe 拷贝）
> 2. 用硬件滤镜（`scale_cuda`/`scale_videotoolbox`/`scale_vaapi`）在 GPU 上做（性能好但平台绑定）
>
> 全 GPU 转码命令示例：`-hwaccel cuda -hwaccel_output_format cuda` + `scale_cuda` 滤镜。

---

### Q7.3 ⭐⭐ 三大桌面 OS 的硬件编解码 API 怎么选？

**参考答案**：

| OS | 解码 | 编码 | 厂商直通 |
|------|------|------|---------|
| **Linux** | VAAPI（Intel/AMD 通用）、NVDEC | VAAPI、NVENC、QSV | NVIDIA Video Codec SDK、Intel oneVPL |
| **Windows** | D3D11VA（首选）、DXVA2（旧） | NVENC、QSV、AMF(AMD) | 同上三家 SDK |
| **macOS** | VideoToolbox | VideoToolbox | 无（M 系只有 Media Engine） |

> macOS 最特殊——没有第三方厂商 SDK，只有 VideoToolbox 一条路。但好处是 API 统一、碎片化低。
> Linux 上 VAAPI 是 Intel/AMD 通用抽象层（类似 Windows 的 D3D11VA），NVENC 则是 NVIDIA 直通方案。

---

### Q7.4 ⭐⭐ 硬件编解码的优势和劣势分别是什么？

**参考答案**：

> **优势**：
> - CPU 占用极低（编 4K CPU 几乎不动）
> - 功耗低（手机上录 4K 不烫手）
> - 吞吐高（一张 NVIDIA 卡并发几十路 1080p）
> - 延迟可控（硬件流水线天然低延迟）
>
> **劣势**：
> - 同码率画质不如软编（需更高码率追平）
> - 参数可调性有限（厂商只暴露部分参数）
> - 驱动/SDK 复杂，调试难
> - 跨平台需要写多套代码
>
> 一句话选型：**桌面硬编是优化项，移动硬编是必选项**（功耗决定生死）。

---

### Q7.5 ⭐⭐ FFmpeg 硬件加速的通用接口（hwaccel/hwcontext）怎么用？

**参考答案**：

> FFmpeg 的硬件加速有三层抽象：
>
> 1. **hwaccel**（命令行级别）：`-hwaccel cuda` 让 FFmpeg 自动用硬件解码器替代软件解码器
> 2. **hwdevice**（API 级别）：`av_hwdevice_ctx_create(AV_HWDEVICE_TYPE_CUDA)` 创建硬件设备上下文，管理 GPU 资源
> 3. **hwframe**：硬件 AVFrame（format 为硬件特有的 pixel format），通过 `av_hwframe_transfer_data` 在 GPU↔CPU 之间搬运
>
> API 层的基本流程：
> ```c
> // 1. 创建硬件设备上下文
> av_hwdevice_ctx_create(&hw_device_ctx, AV_HWDEVICE_TYPE_CUDA, NULL, NULL, 0);
> // 2. 给解码器上下文挂上硬件设备
> codec_ctx->hw_device_ctx = av_buffer_ref(hw_device_ctx);
> // 3. 解码得到硬件帧
> // 4. av_hwframe_transfer_data(sw_frame, hw_frame, 0);  // 下载到 CPU
> ```

### Q7.6 ⭐⭐ NVENC 的 P1-P7 Preset 是什么意思？

**参考答案**：

> NVENC 也有自己的 preset 体系（P1-P7），和 x264 preset 思路相同但尺度更粗——只有 7 档。
> - P1：最快、最低质量（实时编码）
> - P7：最慢、最高质量（离线转码）
>
> NVENC 还有 tuning info：`-tune hq`（高质量）、`-tune ll`（低延迟）、`-tune ull`（超低延迟）、`-tune lossless`（无损）。
>
> 和 x264 对比：NVENC P7 ≈ x264 veryfast/faster 档位，仍然达不到 x264 medium 以上的画质。但 Turing 及之后架构差距大幅缩小。

---

### Q7.7 ⭐⭐⭐ 硬件解码 + 硬件滤镜的全 GPU 链路怎么搭？

**参考答案**：

> 目标：从解码到编码全在 GPU 上完成，不经过 CPU。
>
> 命令行：
> ```bash
> ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i input.mp4 \
>   -vf "scale_cuda=1280:720" \
>   -c:v h264_nvenc output.mp4
> ```
>
> 关键点：
> - `-hwaccel_output_format cuda`：让解码器输出 CUDA 硬件帧（而非默认下载到 CPU）
> - `scale_cuda`：GPU 端的缩放滤镜，直接操作显存里的数据
> - `h264_nvenc`：GPU 端编码器，直接消费 GPU 帧
>
> API 层的等价操作：用 `av_hwframe_transfer_get_formats` 查询支持的 format transfer 路径，用 `avfilter_graph_create_filter` 创建硬件滤镜（`scale_cuda`），配置正确的 hw_device_ctx。

---

### Q7.8 ⭐⭐ 什么是零拷贝？硬件编解码的零拷贝路径是什么？

**参考答案**：

> **零拷贝**：数据从采集到编码（或解码到渲染）全程在 GPU 显存里流转，不经过 CPU 内存的拷贝。
>
> 硬件编码零拷贝路径：
> ```
> GPU 采集（NV12 CUDA frame）
>   → GPU 预处理滤镜（scale_cuda）
>   → GPU 编码器（NVENC）
>   → 输出（仍在 GPU，或直接网络发送）
> ```
> 全程没有 `av_hwframe_transfer_data`（那个就是从 GPU 下载到 CPU），也没有 CPU 端的 `sws_scale`。
>
> 为什么省了拷贝还是快？不只是 memcpy 本身省了——更重要的是避免了 PCIe 带宽占用、避免了 GPU→CPU 同步 stall、以及数据不需要离开显存的缓存层次。

---

### Q7.9 ⭐⭐ Intel QSV 和 VAAPI 是什么关系？

**参考答案**：

> - **VAAPI**（Video Acceleration API）：Linux 上的通用硬件加速抽象层，不只 Intel 能用，AMD 也支持。它在各个厂商硬件之上提供统一的接口
> - **QSV**（Intel Quick Sync Video）：Intel 自己的硬件编解码技术，通过 VAAPI 或 Intel Media SDK/oneVPL 调用。`h264_qsv` 编码器比 VAAPI 编码器暴露更多 Intel 特有参数
>
> 简单说：VAAPI 是 Linux 上多厂商的通用层，QSV 是 Intel 专有优化通路。FFmpeg 里 `h264_vaapi` 是通用 VAAPI 编码器，`h264_qsv` 是 QSV 编码器——后者通常画质更好、参数更多。

---

### Q7.10 ⭐⭐ 不同代 NVIDIA 显卡的编码能力有什么区别？

**参考答案**：

> 主要看 NVENC 版本（不是 CUDA 核心数）：
>
> | 架构 | 代 | 编码能力 |
> |------|-----|---------|
> | Kepler | 1st Gen | H.264 |
> | Maxwell | 2nd Gen | H.264/H.265 |
> | Pascal | 3rd Gen | H.264/H.265 10bit |
> | Turing | 4th Gen | + HEVC B-frame |
> | Ampere | 5th Gen | + AV1 解码 |
> | Ada Lovelace | 6th Gen | + **AV1 编码** |
>
> 还有并发 session 数限制：消费卡（GeForce）通常限 3-5 个并发编码 session，专业卡（Quadro/RTX A 系列）不限或上限更高。这是 NVIDIA 通过驱动做的市场分割，不是硬件限制。

---

### Q7.11 ⭐⭐⭐ Linux 上没有 NVIDIA 独显，怎么做硬件编解码？

**参考答案**：

> 三条路：
> 1. **VAAPI**：Intel 核显（几乎所有带核显的 Intel CPU 都支持）→ FFmpeg 的 `h264_vaapi`/`hevc_vaapi`
> 2. **QSV**（oneVPL）：Intel 专有优化通路 → `h264_qsv`/`hevc_qsv`
> 3. **AMF**：AMD 显卡 → `h264_amf`
>
> 如果没有独显也没有核显——那就只能软编。在低成本服务器上，Intel 核显的 QSV 是性价比最高的硬件编码方案。一张消费级 Intel CPU 的核显通常能并发编 2-3 路 1080p。

---

### Q7.12 ⭐⭐ macOS 上硬件编解码的唯一选择是什么？

**参考答案**：

> **VideoToolbox**，苹果的专属 API。M 系列芯片的 Media Engine 能耗比极高——硬件编 4K 不发热不掉电。API 是 CoreFoundation C 接口，异步 + 回调模型。
>
> 编码：`VTCompressionSession`；解码：`VTDecompressionSession`。
>
> FFmpeg 的 `h264_videotoolbox` 编/解码器是很好的参考实现。但 FFmpeg 在 macOS 上没有 NVIDIA 等其他方案可选。
## 八、移动端硬件编解码

### Q8.1 ⭐ 移动端为什么要用硬件编解码？软编不行吗？

**参考答案**：

> 手机上基本不是选择题——**必须硬编硬解**。
>
> 三个硬约束：
> 1. **功耗/发热**：软编 1080p 会让 CPU 满载、迅速发烫、掉电飞快、触发系统降频。硬编走 SoC 里专门的 Video Engine，功耗低一个数量级
> 2. **用户体验**：没人接受"开个视频会议手机烫得拿不住、半小时掉 40% 电"
> 3. **算力天花板**：手机 CPU 软编 1080p60 或 4K 已经吃力，硬编轻松
>
> 一句话：**桌面硬编是优化项，移动硬编是必选项。**

---

### Q8.2 ⭐⭐ Android MediaCodec 的缓冲区队列模型是怎么工作的？

**参考答案**：

> MediaCodec 的心智模型是**两条缓冲区队列**：
>
> ```
> 输入数据 → [input buffer queue] → [硬件编解码芯片] → [output buffer queue] → 输出数据
> ```
>
> 两种驱动方式：
> - **同步模式**：`dequeueInputBuffer` 要一个空输入 buffer → 填数据 → `queueInputBuffer` → `dequeueOutputBuffer` 取处理完的输出 → 消费 → `releaseOutputBuffer`
> - **异步模式**（推荐）：注册 Callback（`onInputBufferAvailable`/`onOutputBufferAvailable`），系统在 buffer 就绪时回调，无忙等
>
> 铁律：每个 output buffer 用完必须 `releaseOutputBuffer` 还回去，否则队列很快耗尽、编解码卡死。

---

### Q8.3 ⭐⭐ Android MediaCodec 解码为什么要喂 CSD？

**参考答案**：

> CSD（Codec-Specific Data）就是 Android 版的 extradata——解码必需的参数集。对于 H.264：
> - `csd-0` = SPS（序列参数集）
> - `csd-1` = PPS（图像参数集）
>
> 在 `MediaCodec.configure()` 时通过 `MediaFormat` 的 `KEY_CSD-0`/`KEY_CSD-1` 传入。解码器必须先拿到 CSD 才能解码任何帧。
>
> 数据来源：MP4 的 `avcC` box（AVCC extradata）→ 提取 SPS/PPS → 分别设进 csd-0/csd-1。
>
> 注意比特流格式：Android MediaCodec 喂入的一般是 **Annex-B**（带起始码）；如果从 MP4 解出来的是 AVCC 格式，需要先用 `h264_mp4toannexb` 转一次。

---

### Q8.4 ⭐⭐ Android 的 Surface 零拷贝是什么？为什么比 ByteBuffer 好？

**参考答案**：

> Surface/SurfaceTexture 是 Android 的**零拷贝渲染通道**。解码器直接把输出渲染到 Surface 上（底层走 dma-buf/gralloc 在 GPU 内部传递），数据从解码器 → 渲染全程在 GPU 侧完成，不经过 CPU。
>
> ByteBuffer 模式则是解码器把数据拷贝到 CPU 可读的内存 → 你再拷贝到 GPU 纹理 → 渲染。多两次拷贝 + 一次 CPU-GPU 同步。
>
> Surface 优势：
> - 零拷贝：省 CPU、省带宽、低延迟
> - 不关心颜色格式：你不用管 NV12/NV21/stride，Surface 自动处理
>
> ByteBuffer 的问题：
> - 颜色格式因芯片而异（高通可能是 NV12、联发科可能是某种私有格式）
> - stride/slice-height 对齐特殊
> - 要多一次 YUV→RGB 或纹理上传
>
> 能用 Surface 就别碰 ByteBuffer——尤其在播放和预览场景里。

---

### Q8.5 ⭐⭐ iOS VideoToolbox 编码输出是什么格式？推流前要做什么？

**参考答案**：

> VideoToolbox 编码输出的是 **AVCC 格式**（长度前缀），SPS/PPS 在 `CMVideoFormatDescription` 里，**不在**裸流数据里。
>
> 推流（RTMP/RTP/裸流）需要：
> 1. **AVCC → Annex-B**：每个 NALU 前加起始码 `00 00 00 01`
> 2. **每个 IDR 前补 SPS/PPS**：从 `CMVideoFormatDescription` 提取参数集 NALU，每个 IDR 前注入
>
> 漏了这一步 → 对端只有声音没画面（最经典的 iOS 推流 bug）。
>
> 比特流格式总结：VideoToolbox 吐 AVCC，MediaCodec 吐 Annex-B——两端格式正好相反，跨平台 SDK 需要统一处理。

---

### Q8.6 ⭐⭐⭐ FFmpeg 在 Android 有 MediaCodec 编码 wrapper 吗？

**参考答案**：

> **只有解码 wrapper，没有编码 wrapper**。FFmpeg 提供了 `h264_mediacodec`/`hevc_mediacodec` 等**解码器**，但没有对应的 MediaCodec 编码器 wrapper。
>
> 也就是说：你可以在 FFmpeg 里用 MediaCodec 做硬件解码，但要做硬件编码必须直接调 Android 系统 API（`MediaCodec`/`AMediaCodec`）——FFmpeg 不帮你封装。
>
> 这是最容易在面试里答错的点。对比 iOS：FFmpeg 的 `h264_videotoolbox` 编解码都有 wrapper。

---

### Q8.7 ⭐⭐ 移动端的零拷贝路径（采集→编码→渲染）怎么走？

**参考答案**：

> **Android**：
> ```
> Camera2(Surface) → MediaCodec(Surface 输入) → 编码 → MediaCodec(Surface 输出) → SurfaceView/TextureView
> ```
> 全程走 dma-buf/gralloc，数据在 GPU/VPU 之间零拷贝传递。
>
> **iOS**：
> ```
> AVCaptureSession(CVPixelBuffer) → VTCompressionSession → 编码 → VTDecompressionSession → CVPixelBuffer → Metal/CoreVideo 渲染
> ```
> 全程走 IOSurface，CVPixelBuffer 是 IOSurface 的包装。
>
> 零拷贝的核心是理解各平台的图形缓冲机制：Android 的 gralloc/dma-buf vs iOS 的 IOSurface。UMA（统一内存架构，CPU 和 GPU 共享物理内存）下"拷贝"的主要开销不是 memcpy，而是 tiling 转换、缓存一致性操作和同步 stall。

---

### Q8.8 ⭐⭐ Android 不同 SoC 的 MediaCodec 行为差异有哪些坑？

**参考答案**：

> 碎片化是 Android 硬编解最大的坑：
>
> 1. **颜色格式**：高通吐 NV12、三星吐 NV12 但 stride 可能不同、联发科可能吐私有 YUV 格式。ByteBuffer 模式下必须查询 `MediaCodecInfo.CodecCapabilities.COLOR_Format*` 不能硬编码
> 2. **stride/slice-height**：硬件帧的实际行宽和行数可能大于逻辑分辨率（对齐到 16/32/64），不正确处理画面会倾斜或花屏
> 3. **支持的 Profile/Level**：低端芯片可能只到 Baseline/Level 3.1，不支持 High Profile
> 4. **并发 session 数**：有些芯片只支持 1-2 个并发编解码 session
> 5. **编码器延迟帧数**：不同芯片 B 帧策略不同
>
> 工程对策：编码前查询 CodecCapabilities，做好 fallback（硬解失败降软解），Surface 模式绕过颜色格式问题。

---

### Q8.9 ⭐⭐ Android Camera1 默认输出 NV21 要注意什么？

**参考答案**：

> Camera1 的预览回调默认吐 **NV21**——Y 一平面 + **VU 交错**（注意是 VU 不是 UV）。
>
> 常见问题：
> - 喂给配置成 NV12 的 MediaCodec → **红蓝反色**（阿凡达脸）
> - 直接用 NV21 喂 H.264 编码器 → 大部分编码器不支持
>
> 解决：要么用 Camera2 + ImageReader 选 NV12，要么手写 NV21→NV12 转换（就是交换 UV 两个字节），要么走 Surface 模式绕过颜色格式问题。

---

### Q8.10 ⭐⭐ 移动端和桌面端硬件编解码最大的不同是什么？

**参考答案**：

> 最大不同不是 API，是**硬件约束和碎片化程度**：
>
> 1. **功耗是第一优先级**：桌面可以风扇呼呼转，手机不行
> 2. **API 碎片化**：桌面有标准的 VAAPI/D3D11VA，Android 的 MediaCodec 行为因 SoC 而异
> 3. **零拷贝必要性**：移动端内存带宽远小于桌面，拷贝代价更高
> 4. **并发能力**：移动端通常只够 1-2 路同时编解码，桌面显卡可以几十路
> 5. **FFmpeg 支持边界**：Android 硬编没有 FFmpeg wrapper 必须调系统 API，iOS 有完整 wrapper
## 九、网络协议与流媒体

### Q9.1 ⭐ TCP 和 UDP 在音视频场景下最关键的差别是什么？

**参考答案**：

> TCP 严谨可靠，但有**队头阻塞**——丢一个包，后续所有包都被扣留等重传。UDP 不可靠但**无队头阻塞**——丢就丢了，下一个包立刻到应用层。
>
> 音视频里"**实时性 >> 完整性**"，所以 WebRTC 选 UDP。RTMP/HLS/HTTP-FLV 选 TCP 是历史原因——它们诞生在浏览器 Flash/HTTP 时代。
>
> 只要底层是 TCP（有序可靠交付），**就跑不掉队头阻塞**——这是协议层面无法绕过的限制。QUIC 在 UDP 之上自己实现可靠传输，就是为了绕过 TCP 的队头阻塞。

---

### Q9.2 ⭐ RTMP、HLS、HTTP-FLV、WebRTC 各自的延迟量级和场景？

**参考答案**：

| 协议 | 底层 | 延迟 | 场景 |
|------|------|------|------|
| RTMP | TCP/1935 | 1-3 秒 | **推流端事实标准**（OBS 推流） |
| HLS | HTTP/TCP/443 | 10-30 秒 | **大规模分发**（CDN 极友好） |
| HTTP-FLV | HTTP/TCP/443 | 1-3 秒 | **国内观众端主力**（穿透防火墙） |
| WebRTC | UDP/动态 | < 500ms | **视频会议、连麦** |

> 行业黄金架构：主播 RTMP 推流 → 服务器转 HTTP-FLV → 观众 HTTP-FLV 拉流。RTMP 在浏览器端已死（Flash 没了），但推流端因为 OBS 生态成熟依然是 RTMP。

---

### Q9.3 ⭐⭐ 为什么 HLS 能扛千万级并发？

**参考答案**：

> HLS 把直播变成了**下载静态切片文件**。CDN 最擅长的就是缓存和分发静态文件——1000 万人请求同一个 .ts 切片，请求根本到不了源站，文件早已缓存在离用户最近的 CDN 节点。
>
> 长连接协议（RTMP/FLV）要维持千万根 TCP 连接，单机连接数有限，内存/CPU 扛不住。
>
> HLS 是公开行业标准（不是苹果私有），云厂商 CDN 天然支持。代价是高延迟（传统 10-30s），LL-HLS 可以降到 2-3s 但仍不如 HTTP-FLV/WebRTC。

---

### Q9.4 ⭐⭐ HTTP-FLV 是怎么把直播伪装成 HTTP 请求的？

**参考答案**：

> 用 HTTP/1.1 的 `Transfer-Encoding: chunked` 机制。服务器响应头加 chunked = 告诉浏览器"文件多大我不知道，会一块块发，发个 0 大小空块才算结束"。
>
> 服务器**永远不发空块**——HTTP 请求就永远不结束，变成"披着 HTTP 外衣的长连接水管"，持续推送 FLV Tag。
>
> B 站开源的 `flv.js` 就是浏览器端 JavaScript 拆 FLV Tag 喂给 HTML5 video 标签（MSE），完美绕过 Flash。
>
> HTTP-FLV 和 RTMP 内部的 FLV Tag **几乎二进制一致**，所以服务器换壳（RTMP→HTTP-FLV）几乎不耗 CPU。

---

### Q9.5 ⭐⭐⭐ 为什么 1935 端口经常被防火墙封，但 80/443 不会？

**参考答案**：

> 网管的"最小权限原则"：除了上网必备端口（80/443），其他冷门端口一律封杀，减少攻击面。
>
> 80/443 是"正门"，敞开但部署了最严密的安全设施（WAF、IDS）。1935（RTMP）、3306（MySQL）、22（SSH）是"偏门"，背后软件防攻击能力弱，索性焊死。把所有偏门封掉**强迫攻击者必须从防守最严密的正门进**——收缩攻击面。
>
> 现代防火墙是七层（WAF），不只看端口还看协议格式。把 RTMP 数据强发到 80 端口会被识别为非 HTTP 流量直接 reset。这就是为什么 HTTP-FLV/WebSocket 要"协议伪装"成 HTTP。

---

### Q9.6 ⭐⭐⭐ WebRTC 怎么解决 UDP 丢包问题？

**参考答案**：

> 应用层自己造轮子。四大机制：
>
> 1. **FEC（前向纠错）**：发 10 个包附带 2 个校验包，丢 1 个直接算回来，不用重传。空间换时间
> 2. **NACK（选择性重传）**：按 RTP 序列号请求重传丢失的那个包——粒度是**包**不是帧。适合少量偶发丢包
> 3. **PLI/FIR（请求关键帧）**：丢太多、参考链崩了，NACK 补不回来时，请求对端**立刻产一个 IDR**（粒度是整帧）重新起步
> 4. **GCC（拥塞控制）**：估计网络容量，动态调整发送速率。以延迟梯度为主信号——比"等丢包才降速"更早反应
>
> 还有 **Jitter Buffer**：接收端缓存包按时间戳重排序、抗抖动、必要时做 PLC（丢包隐藏）。
>
> NACK vs PLI/FIR 的区别是高频追问点——NACK 补丢的那个小包，PLI/FIR 直接要一张完整关键帧。

---

### Q9.7 ⭐⭐⭐ 讲一下 WebRTC 的建连流程和传输栈

**参考答案**：

> 分三段：信令 → 连通 → 媒体。
>
> 1. **信令 + 协商**：两端通过自建信令通道（WebSocket 等，不属于 WebRTC 标准）交换 SDP offer/answer（协商 codec、分辨率、profile-level-id）和 ICE candidate
> 2. **连通（NAT 穿透）**：ICE 框架收集 candidate，借 STUN 打洞尝试端到端直连，直连失败用 TURN 中继兜底
> 3. **媒体传输**：媒体走 UDP 上的 RTP（序列号/时间戳/负载类型），RTCP 回报 SR/RR（丢包率、抖动、RTT）并承载 NACK/PLI/FIR；全程 DTLS-SRTP 强制加密；GCC 做带宽估计
>
> 多人会议提 SFU（转发不解码）vs MCU（混流）。WebRTC 自建 CDN 比 HLS 贵——有状态实时会话 vs 无状态静态缓存。

---

### Q9.8 ⭐⭐ RTSP 是什么？和 RTMP/WebRTC 有什么区别？

**参考答案**：

> RTSP 是**控制协议**（"网络遥控器"），**本身不传媒体**。DESCRIBE（拿 SDP）→ SETUP → PLAY → PAUSE → TEARDOWN；真正的音视频走 RTP（+RTCP），由 SDP 描述。
>
> 两种传输：RTP over UDP（低延迟，易被防火墙挡）/ RTP over TCP interleaved（复用 RTSP 那条 TCP，穿透好）。
>
> 典型场景：**IP 摄像头/安防/NVR** 默认就吐 RTSP 流。
>
> vs RTMP：RTMP 是控制+媒体一体的自带封装协议（偏推流）；RTSP 是控制与媒体分离（偏拉摄像头）。
> vs WebRTC：WebRTC 也用 RTP/RTCP/SDP，但加了 ICE/STUN/TURN（NAT 穿透）+ DTLS-SRTP（强制加密）+ GCC（拥塞控制）。
>
> "摄像头 RTSP 转 WebRTC 上网页"是高频实战题——核心是把 RTP 媒体重新用 WebRTC 封装。

---

### Q9.9 ⭐⭐ 流媒体协议按层次怎么讲？（大局观题）

**参考答案**：

> 按分层 + 用途答，别平铺：
>
> - **传输层**：TCP/UDP/QUIC
> - **媒体承载层**：RTP+RTCP
> - **应用层**：RTMP/RTSP/HLS/HTTP-FLV/DASH/WebRTC
>
> 关键认知：RTSP/WebRTC 不是单一协议，是"控制 + RTP 媒体"的组合；RTMP/HLS/FLV 不走 RTP、自带封装。
>
> 按用途记：**RTMP 推流、RTSP 拉摄像头、HLS/HTTP-FLV/DASH 分发、WebRTC 互动**。
>
> 延迟谱：WebRTC（几百 ms）< RTMP/HTTP-FLV（1-3s）< HLS/DASH（10-30s，LL 版 2-3s）。

---

### Q9.10 ⭐⭐ TLS/HTTPS 握手为什么慢？TLS 1.3 做了什么改进？

**参考答案**：

> TLS 1.2 需要 **2 个 RTT**（两次往返）才能开始传数据：TCP 三次握手（1 RTT）+ TLS 握手（1-2 RTT）= 总共 2-3 RTT。
>
> TLS 1.3 核心改进：
> - 握手精简为 **1-RTT**（甚至 0-RTT 恢复会话）
> - 砍掉了不安全的加密套件和过时的 RSA 密钥交换
> - 默认前向安全的 ECDHE
>
> 对音视频的影响：首屏秒开。把 TLS 1.2 换成 1.3，RTT 60ms 的环境下能省 60-120ms 的建连时间。再加上 0-RTT（PSK 恢复），**第一个视频分片的请求几乎零建连延迟**。

---

### Q9.11 ⭐⭐ QUIC/HTTP3 相比 TCP+TLS 的优势？

**参考答案**：

> QUIC 是 Google 在 UDP 上重新实现的"更好的 TCP"。核心改进：
>
> 1. **0-RTT 建连**：会话恢复时第一个包就能带数据（TCP+TLS 至少 1 RTT）
> 2. **无队头阻塞**：QUIC 的流之间独立——stream 2 丢了只阻塞 stream 2，stream 3 继续跑。TCP 丢包阻塞所有流
> 3. **连接迁移**：从 WiFi 切到 4G，IP 变了但 QUIC connection ID 不变，连接不中断
> 4. **内置加密**：TLS 1.3 级别加密直接集成在 QUIC 协议里，不是额外层
>
> 对音视频的意义：弱网切换不卡顿、首屏更快。目前 HTTP/3 = HTTP over QUIC。

---

### Q9.12 ⭐⭐ CDN 在流媒体里解决什么问题？HLS 为什么是 CDN 的最佳搭档？

**参考答案**：

> CDN 解决的是"如何让一千万人同时看直播不把源站打挂"。核心原理：把内容缓存到离用户最近的边缘节点。
>
> HLS 和 CDN 是天生一对——因为 HLS 的切片就是普通 HTTP 文件。CDN 对静态文件的缓存策略极度成熟（Cache-Control/Etags/预推/分层缓存），命中率极高。RTMP/FLV 这种长连接协议，CDN 只能做 TCP 代理转发，不能缓存——因为每个观众看到的流位置不同。
>
> 一句话：**HLS = 把流变成 CDN 最擅长服务的东西——静态文件。**

---

### Q9.13 ⭐⭐ HLS 的 .m3u8 播放列表长什么样？Master vs Media Playlist？

**参考答案**：

> Media Playlist：直接列切片文件。`#EXTM3U` 开头 → `#EXT-X-TARGETDURATION` 声明切片最大时长 → 每行 `#EXTINF` 跟时长、下一行切片 URL。有 `#EXT-X-ENDLIST` = 点播/完整列表，没有 = 直播中（播放器定时重拉 m3u8）。
>
> Master Playlist（多码率才有）：用 `#EXT-X-STREAM-INF` 列出"这个码率叫什么、带宽多少、子 m3u8 在哪"。播放器先读这个，根据网速选码率，再去拉子 playlist。
>
> 区分：**Master = 菜单（有哪些码率可选），Media = 菜谱（具体哪些切片按什么顺序上）。**

---

### Q9.14 ⭐⭐ 为什么 HLS 延迟高？怎么降到 3 秒以内？

**参考答案**：

> 传统 HLS 延迟 = 切片时长 × 缓冲数。6 秒一切片、攒 3 个开播 = 18 秒。
>
> 优化三层：
> 1. **缩切片**：6 秒变 1 秒，但切片数暴增，CDN 回源压力大
> 2. **LL-HLS**（苹果 2019）：把一个切片内部拆成 partial segments（~200ms），边切边通过 HTTP/2 push 推给播放器 → 2-3 秒
> 3. **CMAF + chunked transfer**：fMP4 moof+mdat 做成 chunk，产一块发一块 → 1-2 秒，和 DASH 共用格式
>
> LL-HLS/CMAF 靠"边切边发"降延迟不伤 CDN，但要求服务器和 CDN 支持 HTTP/2。

---

### Q9.15 ⭐⭐ 切 HLS 时为什么每个分片都要带 SPS/PPS？

**参考答案**：

> 核心是"自包含"——任何一个 .ts 分片都必须能独立解码。观众拖进度条到第 30 分钟，播放器只请求第 30 分钟对应的 .ts，不会下载前面的文件。
>
> 如果这个分片里没有 SPS/PPS（分辨率/Profile/编码参数），解码器拿到数据后根本不知道分辨率、编码档次——**永远黑屏**。CDN 切换、网络重连也是每次都从"当前时刻对应的分片"重新开始。
>
> FFmpeg 保证：`-hls_flags independent_segments` + `-force_key_frames`。
>
> CMAF/fMP4 走了另一条路——把"说明书"单独抽出来叫 init segment，下载一次存着，后面 media segments 共用。

---

### Q9.16 ⭐⭐⭐ 大规模直播系统的架构怎么设计？

**参考答案**：

> 分层架构：
>
> ```
> 主播端: OBS/移动SDK → RTMP 推流 (1935)
>     ↓
> 接入层: 边缘推流节点 (就近接入、抗丢包)
>     ↓
> 源站: 转码(多码率) + 切片(HLS) + 转封装(HTTP-FLV)
>     ↓
> CDN: 缓存 .ts 切片 + .m3u8 + HTTP-FLV 流
>     ↓
> 观众端: HTTP-FLV 拉流(低延迟) 或 HLS(兼容/回退)
> ```
>
> 关键点：
> - 推流和分发解耦——推流用 RTMP（OBS 生态），分发用 HTTP-FLV/HLS（CDN 友好）
> - 多码率转码 + ABR 自适应——卡了就降码率
> - 边缘推流节点就近接入——减少推流端到源站的 RTT
> - 源站录制成 TS/MP4 存档
>
> 延迟要求不同：普通直播 1-3s 够用，秀场连麦 < 500ms 要走 WebRTC。

### Q9.17 ⭐⭐ WebRTC SFU 和 MCU 的区别？什么时候用哪个？

**参考答案**：

> - **SFU（Selective Forwarding Unit）**：转发不解码。收到每个参会者的流，根据每个人的下行带宽选择性转发。服务器不做编解码，只做路由。省 CPU，但客户端要解码多路
> - **MCU（Multipoint Control Unit）**：混流。服务器把所有参会者的流解码 → 混成一路合成画面 → 重新编码发给每个人。客户端只解码一路。服务器 CPU 吃紧
>
> 现代 WebRTC 会议基本都用 SFU——服务器可以水平扩展，客户端能力足够解码多路。MCU 在电话会议网关里还有用。

### Q9.18 ⭐⭐ 弱网下视频卡顿怎么诊断和优化？

**参考答案**：

> 先诊断：区分是丢包还是带宽不足。看 RTT、丢包率、抖动、实时码率。
>
> 优化方向：
> 1. **协议层**：TCP 改 UDP（WebRTC）规避队头阻塞；用 QUIC 代替 TCP
> 2. **编码层**：降码率/降分辨率自适应（ABR）；缩 GOP 加速恢复
> 3. **冗余**：FEC 前向纠错对抗丢包
> 4. **重传**：NACK 按序列号重传丢失的包；参考链崩了 PLI/FIR 请求关键帧
> 5. **拥塞控制**：GCC/BBR 动态调整发送速率
> 6. **缓冲**：jitter buffer 抗抖动
> 7. **降级**：丢普通 B 帧保流畅（参考 B 帧不能丢）
>
> 音视频降级策略不同——视频可以丢帧，音频通常用 PLC 而非简单丢。弱网测试工具：Linux tc netem、iOS Network Link Conditioner。
## 十、Seek 与精准定位

### Q10.1 ⭐ av_seek_frame 和 avformat_seek_file 有什么区别？

**参考答案**：

> `av_seek_frame` 只有一个目标 timestamp + flag，底层搜索范围是没有上限的——`min_ts = INT64_MIN`。如果目标之前的关键帧因索引缺失等原因"失踪"，它可能一路滑到文件开头。
>
> `avformat_seek_file` 提供了 `min_ts`/`max_ts` 范围参数——"在这个区间内帮我找，超出范围就告诉我找不到"。这是控制回退距离的关键。
>
> 工程上：**永远用 avformat_seek_file 而不是 av_seek_frame**。除非你知道文件索引完美（标准 MP4），否则 av_seek_frame 在索引残缺时是不可预测的。

---

### Q10.2 ⭐⭐ av_seek_frame 为什么会"跳太远"——越过多个关键帧？

**参考答案**：

> 不是偶然 bug，是 API 设计、容器索引、音视频交错三者共同导致：
>
> 1. **API 无边界约束**：`min_ts = INT64_MIN`，搜索失败时没有下限拉住
> 2. **索引失效率**：
>    - 未流化的 MP4（moov 在末尾）→ 退化为盲目二分查找
>    - fMP4/DASH/HLS（索引散落在 moof 分片里）→ 跨分片搜寻失控
>    - 录制中断的文件（moov 未写完）→ 索引指向的帧不存在
> 3. **音视频交错连锁反应**：为了起播时音画同步，视频关键帧对应的音频帧可能物理位置在文件前面很远。读指针被拉回 → 顺序读到的第一帧视频离目标好几秒远
>
> 终极方案：`avformat_seek_file` 加 `min_ts` 约束。这就是它比 av_seek_frame 好的根因。

---

### Q10.3 ⭐⭐ 为什么 Seek 只能跳到 IDR 帧？

**参考答案**：

> 因为 IDR 帧强制清空参考帧缓冲，保证 IDR 之后的帧不会参考 IDR 之前的帧。
>
> 如果跳到普通 I 帧：后面的 P/B 帧可能还在参考 seek 点之前的帧，解码器参考链断掉 →**花屏**。
>
> 解码器在 Seek 后必须 `avcodec_flush_buffers` 清内部状态，相当于"重置"。重置后遇到的第一帧必须是独立可解码的 IDR。
>
> 容器的关键帧索引表（MP4 的 stss box、FLV 的 keyframes index）标记的就是 IDR 帧的位置。

---

### Q10.4 ⭐⭐ Seek 后为什么容易音画不同步？需要清什么？

**参考答案**：

> Seek 后旧数据残留是头号原因。必须清理：
> 1. **Packet/Frame Queue**：清空所有已读但未解码的包和已解码未渲染的帧
> 2. **AVCodecContext**：`avcodec_flush_buffers` 清解码器内部缓冲区
> 3. **SwrContext/SwsContext**：重采样器/缩放器有内部滤波延迟和缓存，需要 reset 或 flush
> 4. **Audio Clock**：重置播放时钟为 Seek 目标时间
>
> 缺任何一个步骤，都可能先播一段 seek 前的旧内容再跳到新位置。

---

### Q10.5 ⭐⭐ AVSEEK_FLAG_BYTE / FRAME / BACKWARD / ANY 怎么用？

**参考答案**：

| Flag | 含义 | 使用场景 |
|------|------|---------|
| `AVSEEK_FLAG_BACKWARD` | 找到目标 **之前** 最近的关键帧 | 播放器拖动进度条（默认行为） |
| `AVSEEK_FLAG_BYTE` | 按**文件字节偏移** seek，不按时间戳 | 编辑器、分析工具 |
| `AVSEEK_FLAG_FRAME` | 按**帧序号** seek | 帧精确操作（第 42 帧） |
| `AVSEEK_FLAG_ANY` | 跳到任意帧（可能不可解码） | 编辑器按帧浏览时配合解码到目标帧 |

> `FLAG_BACKWARD` 是默认策略：找到最近关键帧 → 从此开始解码 → 但不输出画面 → 一直解码到目标帧 → 才开始输出。这就是"解码但不显示的追赶期"。

---

### Q10.6 ⭐⭐ 时间和帧精确 Seek 怎么做？（Smart Seek）

**参考答案**：

> "时间 Seek"和"帧精确 Seek"是两回事：
>
> **时间 Seek（普通）**：seek 到目标时间前最近的关键帧，解码追赶但不输出，到目标时间开始输出。可能有 ±几帧的误差。
>
> **帧精确 Seek（Smart Seek）**：先 Seek 到关键帧 → 逐帧解码并计数 → 到目标帧号时返回。100% 精确。
>
> 视频编辑器、AI 抽帧管线需要用帧精确 Seek——不然每次抽的帧号可能漂移。实现上通常需要预建帧索引（记录每个关键帧的 byte offset），线上用 `AVSEEK_FLAG_BYTE` 直接跳到关键帧的字节位置再解码到目标帧号。

---

### Q10.7 ⭐⭐ 为什么 ffplay 拖动进度条有时会卡一下才响应？

**参考答案**：

> ffplay 的 seek 流程：
> 1. 调用 `avformat_seek_file` 跳到目标前最近的关键帧
> 2. `avcodec_flush_buffers` 清解码器
> 3. 解码追赶但不显示（可能几十上百帧要解但不渲染）
> 4. 到达目标显示帧才开始输出
>
> 卡顿来自步骤 3——长 GOP（10 秒）下可能需要追赶几百帧。优化：用短 GOP（1-2 秒）、预建关键帧索引直接跳到最近的 IDR。
>
> 另外 ffplay 的 seek 是同步操作——主线程卡在 seek 里，UI 无法响应。

---

### Q10.8 ⭐⭐⭐ 服务端大规模抽帧（每秒一帧）怎么高效实现？

**参考答案**：

> 循环 `for (t=0; t<duration; t+=1.0)` 每次都从头 seek 是最低效的做法——每次 seek 都要重新打开文件、读 moov、定位。
>
> 高效方案：
> 1. 打开文件一次，预建关键帧索引（扫描 stss 或自建映射表）
> 2. 按时间顺序 seek（不需要 random access），每次都从上次位置继续
> 3. 用 `AVSEEK_FLAG_FRAME` 或 byte offset seek 替代时间戳 seek，消除 float 换算偏差
> 4. 解码器复用，不要每帧重建
> 5. 并行化：按 GOP 切段（每段从 IDR 开始独立解码），多线程各管一段
>
> YouTube 服务端转码就是按 GOP 切段分给多机并行转码——每段从 IDR 开始可以完全独立解码。

---

### Q10.9 ⭐⭐⭐ VFR 视频的 Seek 和 CFR 有什么本质区别？怎么处理 VFR Seek？

**参考答案**：

> 先讲清楚为什么会有区别。**Seek 的本质是"给我第 N 帧"，但底层接口 `av_seek_frame` 吃的是时间戳 PTS，不是帧号。**
>
> 所以 Seek 全链路可以写成：**帧号 → 时间戳 PTS → Seek → 顺解到目标**。CFR 和 VFR 的区别就出在第一步——帧号怎么转成时间戳。
>
> **CFR：** 帧间隔固定，比如 29.97fps，每帧 ≈ 3003 ticks。帧号转 PTS 一个公式搞定：
> ```cpp
> target_pts = frame_id * avg_dur_ticks;   // frame_id×3003，线性
> ```
> 求出来顶多差个 1 tick 的浮点误差，向前最多顺解几帧就到了，实际影响很小。
>
> **VFR：帧间隔不固定，线性公式直接崩。** 比如一段视频的实际帧分布是：
> ```
> frameId      0      1      2      3      4      5
> PTS(ms)      0     33     66    100    133    200
> 帧间隔(ms)      33     33     34     33     67  ← 不是常数！
> ```
> 如果继续用 `frame_id × 平均帧间隔`（比如平均 36ms），算出来的 PTS 跟真实 PTS 偏差越积越大，帧号越靠后差得越离谱，偏几十帧都有可能。
>
> **本质区别一句话：CFR 下帧号和时间戳是线性映射，VFR 下是非线性映射——公式算不出真实值，必须查表。**
>
> **怎么处理 VFR Seek：**
>
> 业界标准做法是**初始化时全量 demux 扫描建索引**，不是公式推导，而是计数：
> ```cpp
> // av_read_frame() 纯 demux，不解码，逐个读 packet
> vector<int64_t> frame_to_pts;   // 下标 = frameId, 值 = pts
> int fid = 0;
> while (av_read_frame(fmt, pkt) >= 0) {
>     if (pkt->stream_index == vidx)
>         frame_to_pts.push_back(pkt->pts);  // fid=0→pts[0], fid=1→pts[1]...
>     av_packet_unref(pkt);
> }
> // Seek 时: target_pts = frame_to_pts[target_fid];  ← O(1) 查表，零计算
> ```
>
> 这个方案 VFR 和 CFR 完全透明——frameId 就是扫描计数器，跟帧间隔毫无关系。这也是 ExoPlayer 的 Mp4Extractor、剪映素材导入分析采用的思路。
>
> **补充——如果用 ffmpeg 命令行怎么办：**
> ```bash
> # ffmpeg 内置的 VFR→CFR 滤镜（会重新采样帧，不是精确 Seek）
> ffmpeg -i input_vfr.mp4 -vf "fps=30" -vsync cfr output_cfr.mp4
>  
> # 实际开发中 —— 也老老实实建索引
> ```
>
> 一条：**VFR 下 `frameId = pts / frame_dur` 这个公式直接扔掉，用扫描建索引替代。**

**翻车红线**：说"多算几帧兜底就行了"——VFR 帧间隔可能从 16ms 跳到 66ms，偏几十帧兜底兜不过来。说"让用户用 CFR 视频"——客户端素材不可控。

### Q11.1 ⭐ 从 FLV/MP4 里拿到 AAC 数据，直接保存能播放吗？为什么？

**参考答案**：

> **通常不能**。容器里是 **raw AAC**（裸 AAC 帧，没有帧头）。播放器打开 .aac 文件时期望的是 **ADTS 格式**（每帧前有 7 字节帧头，含同步字 `0xFFF` 和采样率/声道等参数）。
>
> 要能播放，要么：
> 1. 从 extradata（MP4 的 esds box 或 FLV 的 AAC sequence header）解析出 AudioSpecificConfig，给每帧补 ADTS 头
> 2. 用 FFmpeg 的 ADTS muxer：`ffmpeg -i input.flv -c:a copy -f adts output.aac`
>
> 这和视频的 AVCC→Annex-B 是**完全对称的设计**——容器优化存储（集中参数），传输格式自带"每帧说明书"。

---

### Q11.2 ⭐ ADTS 头的同步字是什么？怎么解析？

**参考答案**：

> 同步字是 **`0xFFF`**（12 bit）——ADTS 头的第 1 字节必定是 `0xFF`，第 2 字节高 4 位必定是 `0xF`。
>
> ADTS 头共 7 字节，关键字段：
> - syncword：12 位，固定 `0xFFF`
> - `sampling_frequency_index`：4 位查表——3=48000, 4=44100, 8=8000
> - `channel_configuration`：3 位——2=stereo
> - `aac_frame_length`：13 位——整个 ADTS 帧的长度（头 + 数据）
>
> 解析代码：`(buf[1] >> 4) & 0x0F` 取采样率 index，`((buf[3] & 0x03) << 11) | (buf[4] << 3) | ((buf[5] >> 5) & 0x07)` 取帧长。

---

### Q11.3 ⭐ AAC 和 Opus 怎么选？各自的定位是什么？

**参考答案**：

| 维度 | AAC | Opus |
|------|-----|------|
| 压缩效率 | 基准 | AAC 的 ~70% 码率达同音质 |
| 编码延迟 | ~20-40ms | **2.5-60ms 可配** |
| 专利 | 需付费（MPEG LA） | **免专利费** |
| 硬件覆盖 | 几乎所有设备 | 中高端设备 |
| 适用场景 | 点播/直播/存档 | **实时通信** |
| 抗丢包 | 无内建 | **PLC + in-band FEC** |

> 一句话选型：**实时通信选 Opus（低延迟+抗丢包），点播/直播选 AAC（兼容性之王），存量兼容用 MP3。**

---

### Q11.4 ⭐⭐ Opus 为什么延迟比 AAC 低？

**参考答案**：

> 三个层面：
>
> 1. **帧长可配**：Opus 支持 2.5/5/10/20/40/60ms，可对齐采集回调（比如 10ms 一次采集直接编 10ms 帧）。AAC-LC 固定 1024 samples（48kHz≈21.3ms）+ 常需 FIFO 攒包 → 编码缓冲延迟
> 2. **无外挂 FIFO**：AAC 固定帧长 1024，采集回调给的样本数（如 480 @ 10ms）不等于 1024，必须 FIFO 攒够才编
> 3. **内建抗丢包**：Opus 内置 PLC + in-band FEC——丢包可以直接隐藏或部分重建，不用等重传。AAC 丢包只能静音或爆音，要么等重传
>
> Opus 融合了 Skype 的 SILK（语音）和 Xiph 的 CELT（音乐）双核，窄带到全频段自适应。

---

### Q11.5 ⭐⭐ AAC 编码时 nb_samples 填什么？怎么知道 frame_size？

**参考答案**：

> 从 `codec_ctx->frame_size` 获取。AAC-LC 固定返回 1024。这个值表示编码器每次期望的输入样本数（每声道）。
>
> 如果 `frame_size == 0`（如 Opus），表示编码器接受任意样本数（有最大限制但非固定值），不需要严格按固定帧长输入。
>
> 填错 nb_samples 的后果：AAC 编码器会直接报错返回或输出异常。必须 `av_buffersrc_add_frame_flags` 前确保 AVFrame 的 nb_samples == codec_ctx->frame_size。

---

### Q11.6 ⭐⭐ 音频编码 PTS 怎么算？

**参考答案**：

> 核心：PTS 是累加的，每帧 PTS = 帧序号 × 每帧样本数。
>
> 当 time_base 用 `1/sample_rate` 时最简单：
> ```c
> frame->pts = total_samples_encoded;  // 已编码的总样本数 = 帧序号 × frame_size
> total_samples_encoded += frame->nb_samples;
> ```
>
> 如果用其他 time_base：
> ```c
> frame->pts = av_rescale_q(total_samples, (AVRational){1, sample_rate}, codec_ctx->time_base);
> ```
>
> VBR 编码（如 MP3 VBR）时注意：decoder 输出的 nb_samples 可能不等于标称值（MP3 标称 1152，但 decoder 可能输出不同值），PTS 重新计算时要基于实际 nb_samples，不能用标称值硬乘。

---

### Q11.7 ⭐⭐ extradata 在音频 codec 里是什么？

**参考答案**：

> 和解码初始化所需的参数集——视频版的 SPS/PPS 的音频等价物：
>
> - **AAC**：extradata = **AudioSpecificConfig**（2 字节），含采样率 index、声道配置、编码类型（AAC-LC/HE-AAC）。从 MP4 的 esds box 或 FLV 的 AAC sequence header 获取
> - **Opus**：extradata = **OpusHead**（19 字节），含版本、声道数、pre-skip、原始采样率
>
> 编码时必须正确设置 extradata，否则解码器不知道参数。FFmpeg 编码器 open 后会自动生成 extradata，可以直接从 `codec_ctx->extradata` 拷贝给 muxer。

---

### Q11.8 ⭐⭐ AAC-LC / HE-AAC / HE-AAC v2 有什么区别？

**参考答案**：

> - **AAC-LC**（Low Complexity）：最基础的 AAC，兼容性最好，所有设备都支持。适合中高码率（≥ 96kbps）
> - **HE-AAC**（High Efficiency，AAC+）：加了 **SBR**（Spectral Band Replication），低频正常编、高频只编轮廓信息，接收端用 SBR 重建高频。适合低码率（32-96kbps）
> - **HE-AAC v2**（eAAC+）：在 HE-AAC 上加 **PS**（Parametric Stereo），立体声只用单声道 + 少量立体声参数表达。适合极低码率（< 48kbps），但立体声感会下降
>
> 选型：高码率用 AAC-LC（音质最好），低码率用 HE-AAC/v2（保持可接受的音质）。

---

### Q11.9 ⭐⭐ FFmpeg 原生 AAC 编码器和 libfdk_aac 有什么区别？

**参考答案**：

> - **FFmpeg 原生 aac**：内置，不需要额外编译依赖。质量尚可，日常够用。中等码率的画质/音质不如 fdk
> - **libfdk_aac**（Fraunhofer）：业界公认最高质量的 AAC 编码器之一。同码率下音质显著优于 FFmpeg 原生 aac。但许可证是"非自由"的，FFmpeg 编译时需手动启用 `--enable-libfdk-aac`。专业音频转码/存档用 libfdk_aac
>
> 面试里提到 FFmpeg 的 AAC 编码器时主动区分这两个，是加分项。

---

### Q11.10 ⭐⭐ MP3 和 AAC 的本质区别在哪？MP3 为什么逐步边缘化？

**参考答案**：

> 本质区别：AAC 是 MP3 的正统继任者，设计上吸收了 MP3 十几年的经验教训。
>
> 技术层面：AAC 支持更多采样率（8-96kHz）、更多声道（最多 48 vs MP3 5.1）、更高效的滤波器组（MDCT vs 混合滤波器组）、更先进的心理声学模型、更好的高频处理。
>
> 效果：**同码率 AAC 音质显著优于 MP3**，尤其在低码率（≤128kbps）下差距明显。
>
> 为什么边缘化但不是完全死掉？MP3 专利在 2017 年已过期，存量内容巨大兼容性无敌。但新内容和新产品基本都选 AAC（点播/直播）或 Opus（实时通信）。AAC 取代 MP3 不是因为有一个决定性时刻，而是润物细无声的全面碾压。
## 十二、综合系统设计

### Q12.1 ⭐⭐ 让你写一个最简播放器，你会怎么做？

**参考答案**：

> 先给结论：最小可行播放器是 **demux + decode + render** 三步。
>
> 整体流程：
> ```
> avformat_open_input("input.mp4")
>   → 找视频流/音频流索引
>   → avcodec_open2 打开解码器
>   → 循环 av_read_frame
>     → avcodec_send_packet → avcodec_receive_frame
>       → 视频：SwsContext 转 RGB → SDL/OpenGL 渲染
>       → 音频：SwrContext 转 S16 → SDL Audio Callback
>       → 音视频同步：以音频为主时钟，视频按 PTS 决定显示或丢帧
> ```
>
> 关键实现点：
> - AVPacket/AVFrame 引用计数——循环内 unref 复用，循环外 free
> - time_base 跨模块用 av_rescale_q 换算
> - linesize 按行偏移，不按 width 硬算
> - 音频 callback 不能阻塞——解码线程写环形 buffer，callback 只读
> - 三线程模型：demux 线程 → packet queue → decode 线程 → frame queue → render 线程
>
> 踩坑预案：MP4→H.264 需 bitstream filter；AAC FLTP 必须转 S16；硬件帧不能直接 sws_scale；Seek 后全链路 flush。

### Q12.2 ⭐⭐ 直播首屏秒开怎么优化？

**参考答案**：

> 多管齐下：
>
> 1. **协议层**：TLS 1.3/0-RTT 减少握手 RTT；HTTP-FLV 代替 HLS（HLS 至少等 2-3 个切片才开播）
> 2. **GOP 层**：缩短 GOP（1-2 秒一个 IDR），新用户更快遇到关键帧
> 3. **服务器缓存 GOP**：边缘节点预先缓存最近一个完整 GOP，新用户连上立刻推最近的 IDR
> 4. **客户端**：不等 buffer 攒够 3 帧才播，解出第一帧立刻渲染
> 5. **连接预热**：DNS 预解析、HTTPDNS、App 启动时预建 TCP 连接
>
> "首屏 vs 卡顿率 vs 延迟"是三角——优化首屏可能拉高卡顿率，需要取平衡。

### Q12.3 ⭐⭐⭐ 设计一个多人视频会议的 SFU 服务端

**参考答案**：

> SFU 的核心：**转发不解码**。
>
> 架构要点：
> 1. **收流**：每个参会者推一路 WebRTC 流到 SFU（UDP/RTP/DTLS-SRTP）
> 2. **路由决策**：根据每个人的下行带宽、分辨率需求，选择性转发——大画面转发高分辨率，小窗转发低分辨率
> 3. **Simulcast/多路编码**：每个推流端同时编码多档分辨率（720p/360p/180p），SFU 按需选择转发哪一档
> 4. **不做转码**：SFU 不解码不重编码，只做 RTP 包级别的转发——改 SSRC/序列号/时间戳后直接投递
> 5. **拥塞控制**：REMB/transport-cc 反馈给发送端降码率
>
> 为什么不用 MCU？每路解码+混流+重编码太吃 CPU，单机并发路数少。SFU 纯转发，单机可撑几百路。

### Q12.4 ⭐⭐ 设计一个视频转码系统（输入 MP4 → 输出多码率 HLS）

**参考答案**：

> ```
> 输入 MP4
>   → 解封装 demux
>   → 解码（硬件加速可选）
>   → 缩放：1920×1080 / 1280×720 / 854×480
>   → 多路并行编码（每路不同码率）
>   → HLS 切片（每码率一路 .ts + .m3u8）
>   → 生成 Master .m3u8
> ```
>
> 工程关键：
> - 缩放用硬件滤镜（scale_cuda/vaapi）省 CPU
> - 编码用硬编（NVENC/QSV）提吞吐
> - 切片必须 `independent_segments` + 每个分片开头 force keyframe
> - 多码率转码可以按 GOP 切段分给多机并行（YouTube 做法）
> - ABR 自适应：Master Playlist 列出 `BANDWIDTH` 参数，播放器自动选

### Q12.5 ⭐⭐ 视频通话中出现了回声，怎么排查和解决？

**参考答案**：

> 排查链路：
>
> 1. 确认 AEC 是否启用——很多 SDK 默认不开启
> 2. 确认远端参考信号是否正确——AEC 拿到的参考信号是不是真正播给扬声器的 PCM
> 3. 确认延迟估计——参考信号和麦克风信号的时间差是否在 AEC 覆盖范围内（通常几十到几百 ms）
> 4. 排除设备问题——是不是外放+麦克风的物理耦合太强（手机扬声器和麦克风离太近）
> 5. 排除软件问题——是不是有多个音频通路同时打开（比如通话和系统提示音各走各的）
>
> 解决：
> - 确保 AEC 开启且拿到正确的远端参考
> - 调整音频路由（通话走听筒而非扬声器）
> - 降低扬声器音量
> - 检查是否有音频回路（比如浏览器里两个 tab 都是同个通话房间）

### Q12.6 ⭐⭐⭐ 设计一个移动端短视频录制 SDK

**参考答案**：

> 核心组件：
>
> 1. **采集**：Camera2（Android）/ AVCaptureSession（iOS）→ Surface/CVPixelBuffer
> 2. **前处理**：美颜/滤镜（OpenGL ES/Metal shader）、磨皮、美白
> 3. **编码**：MediaCodec（Android）/ VideoToolbox（iOS）→ H.264/H.265
> 4. **音频**：AudioRecord/AudioEngine → AAC 编码
> 5. **封装**：MediaMuxer（Android）/ AVAssetWriter（iOS）→ MP4
> 6. **特效**：贴纸、文字、时间戳叠加
>
> 零拷贝路径：
> ```
> Camera(Surface) → GL渲染(美颜) → MediaCodec(Surface输入编码) → MediaMuxer → MP4
> ```
> 全程数据在 GPU 侧流转。
>
> 难点：实时美颜的 GPU shader 性能、编码器兼容（不同 SoC 行为差异）、音视频时间戳对齐、分段录制+拼接、硬编失败 fallback 软编。

### Q12.7 ⭐⭐ 为什么 ffmpeg 命令行 -c copy 能秒级转换格式？

**参考答案**：

> `-c copy` 告诉 FFmpeg：**不要解码，不要重新编码**——直接把压缩数据从一种容器"搬运"到另一种容器。
>
> ```
> input.mp4 → demux(AVCC H.264) → 直接拷贝 NALU payload → remux(Annex-B) → output.flv
> ```
>
> 全过程只做了：
> - 解封装（读 moov，按 stco/stsz 索引从 mdat 取样本）
> - bitstream filter（如 `h264_mp4toannexb` 做 AVCC→Annex-B，只改分界方式不改 payload）
> - 重封装（写 FLV Tag）
>
> 不涉及 decode + encode，所以：
> - 速度 = I/O 速度（几乎只受磁盘/网络限制）
> - 画质/音质 = 无损（字节级原样保留）
>
> 前提：输出容器支持输入流的编码格式。MP4→FLV 只有 H.264+AAC/MP3 能走 copy，HEVC 转 FLV 就不行（FLV 不支持 H.265）。

### Q12.8 ⭐⭐⭐ 设计一个云端的自动字幕/语音识别管线

**参考答案**：

> 链路：
> ```
> 视频文件
>   → demux 提取音频流
>   → 解码为 PCM（16kHz 单声道 S16，ASR 标准输入）
>   → VAD（语音活动检测）切句
>   → ASR 引擎（Whisper/自研）逐句识别
>   → NLP 后处理（断句、标点、纠错）
>   → 输出字幕文件（SRT/VTT）
> ```
>
> 工程要点：
> - 音频重采样到 16kHz 单声道——几乎所有 ASR 模型的标准输入
> - VAD 切句：避免长时间静音送入 ASR，节省算力
> - 大文件分段并行：按时间轴切成 N 段，多机并行识别，最后合并
> - 时间戳对齐：每段 PCM 的起始时间映射回原视频的时间戳
> - GPU 推理：Whisper 等模型在 GPU 上跑，音频预处理在 CPU

### Q13.3 ⭐ "你最有印象的一个踩坑经历是什么？"

**参考答案**：

> 说一个经典的——MP4 里的 H.264 直接喂 Android MediaCodec 解码，黑屏。
>
> 当时我写了一个简单的 Android 播放器 demo，用 FFmpeg 做 demux，把从 MP4 解出来的 H.264 NALU 直接通过 JNI 传给 Java 层的 MediaCodec。结果解码器不报错，但画面纯黑。
>
> 排查了很久才意识到：MP4 里 H.264 是 **AVCC 格式**（长度前缀），而 Android MediaCodec 期望的是 **Annex-B 格式**（起始码 `00 00 00 01`）。比特流格式不对，解码器根本找不到 NALU 边界。
>
> 解决：在 FFmpeg 侧加 `h264_mp4toannexb` bitstream filter，或者在 JNI 层手动把长度前缀转成起始码。还要把 SPS/PPS 从 extradata 里提出来，用 csd-0/csd-1 传给 MediaCodec configure。
>
> 这个坑让我深刻理解了"容器和编码器之间还有一个比特流格式层"——很多人以为 H.264 就是 H.264，不知道 AVCC 和 Annex-B 的差别。

---

### Q13.4 ⭐⭐ "你怎么判断一个音视频问题的根因？说说你的排查方法论"

**参考答案**：

> 我总结了一套分层排查法，核心思想是**把问题从现象定位到具体的一层**：
>
> 1. **先确认数据本身对不对**：把解码/采集输出的 PCM/YUV dump 出来，用 ffplay/工具验证。如果 dump 本身就有问题，问题在采集或解码链路
> 2. **再确认参数匹配**：打印所有格式参数（采样率/像素格式/声道/linesize），确认上下游配置一致。**持续的杂音/花屏大概率是格式解释错**；**偶发的爆音/卡顿大概率是 buffer/时序问题**
> 3. **再确认时序**：打印 PTS/DTS，看时间戳是不是在正确累进。音画不同步优先查 time_base 换算和 Seek flush
> 4. **最后查性能/线程**：看 buffer 水位、解码耗时分布、callback 是否阻塞
>
> 一句话：**听到杂音先查格式、听到变速先查采样率、听到断音先查缓冲、看到不同步先查 PTS。** 不是凭感觉，是有排查路径的。
