## 一、面试速记卡（先背这个，30 秒能答）

**一句话定义**：

- **H.264 / AVC**（2003）：迄今部署最广的视频编码标准，"视频界的普通话"——兼容性之王。
- **H.265 / HEVC**（2013）：H.264 的继任者，**同画质省约 50% 码率**，代价是编码复杂度约翻倍 + 专利授权混乱。

**关键数字（爱考）**：


| 维度         | H.264                         | H.265                              |
| ---------- | ----------------------------- | ---------------------------------- |
| 基本编码块      | 宏块 16×16                      | CTU 最大 64×64（四叉树细分）                |
| NAL header | 1 字节，`type = byte & 0x1F`     | **2 字节**，`type = (byte>>1) & 0x3F` |
| 参数集        | SPS、PPS                       | **VPS、SPS、PPS**（多一层 VPS）           |
| 熵编码        | CAVLC（Baseline）/ CABAC（Main+） | **只有 CABAC**                       |
| 帧内预测方向     | 9 种（4×4）                      | 35 种（33 角度 + DC + Planar）          |
| 环路滤波       | Deblocking                    | Deblocking + **SAO**               |
| 压缩率        | 基准                            | 同画质 **省约 50% 码率**                  |
| 编码复杂度      | 基准                            | 约 **2× 以上**                        |
| 典型 Profile | Baseline / Main / High        | Main / **Main10**（10bit/HDR）       |


**一句话选型**：**兼容性 / 实时 / 老设备 → H.264；4K/HDR / 存储带宽敏感 / 苹果生态 → H.265；想免专利费 → 看 AV1**。

## 二、面试常考点（带答题要点）

### 2.1 面试官说"介绍一下 H.264"，怎么回答？

这是面试最高频的"第一题"，也是道开放题——面试官其实在考察你**能不能把一个技术讲清楚**，而不是在考你背概念。所以不要像背书一样念定义，要用"为什么"串出一条逻辑链。整体节奏：**先一句话定调 → 然后解释"为什么能压这么小"（拉开差距的地方）→ 挑两三个亮点深入 → 最后收一下、点出局限和大局观**。控制 3-5 分钟，看面试官反应随时调整。

---

**第一层：一句话定调（上来就要脱口而出，不用想）**

"H.264 也叫 AVC或MPEG-4。它是目前部署最广的视频编码标准——你日常看到的蓝光碟、网页视频、手机录像、直播推流、WebRTC 视频通话、监控探头，底层大概率都是 H.264。它不一定是压缩率最高的，但一定是兼容性最好的。"

他能把视频压缩的很小。拿 1080p 30fps 的视频来算：**一帧YUV原始画面** = 1920×1080×1.5 字节（YUV420）≈ **3.1 MB**。一秒 30 帧 ≈ **93 MB**。一分钟 ≈ **5.5 GB**。一部两小时的电影如果不压缩 ≈ **660 GB**——两张蓝光碟都装不下，更别说网络传输了。H.264 把这个数字压到多少？1080p 高质量（CRF 18~23）下码率大约 4~8 Mbps，也就是每秒约 0.5~1 MB——**压缩比大约 100:1 到 200:1**。如果是低清视频会议（480p），码率可以压到 500kbps 以下，压缩比更高。作为对比，MJPEG（逐帧独立 JPEG 编码，安防摄像头常用）同等画质码率大约是 H.264 的 3~5 倍；MPEG-2（DVD 时代标准）大约是 1.5~2 倍；H.265 在 H.264 基础上同画质再省约 50% 码率。所以一句话：**H.264 能把原始视频压到百分之一甚至千分之一的大小，同时画质肉眼几乎看不出差别。**

这一层的要点就一个：**告诉面试官你知道这东西是什么、为什么重要**。一句话就够了，不要展开。但如果你能顺口带出上面的压缩比数字——面试官的印象会从"背过名字"直接跳到"真的懂"。

---

**第二层：讲原理——"为什么 H.264 能把视频压那么小？"（这是拉开差距的地方）**

面试官听完第一层大概率会点头，然后等你往下说。这时候你主动把话题引到原理上——**不要等他问"为什么"，你自己接上去**。可以这么说：

"那它为什么能把视频压这么小呢？其实 H.264 的思路说起来也简单，就是想办法消除视频里天然存在的四种冗余。

第一种是**空间冗余**。你想啊，一帧画面里，相邻的像素是不是颜色都差不多？天空一片蓝，墙壁一片白——这些像素之间是有规律的，没必要每个都独立存一遍。H.264 的做法叫帧内预测：编码当前这个 16×16（大块：16，小块3，中快8） 的宏块的时候，先看看它周围已经编好的块长什么样，猜一个方向往外推，然后只存预测值和实际值之间的差值，也就是残差。这样一来数据量就小多了。对比一下 JPEG 就清楚了——JPEG 是把画面切成 8×8 的块，每个块关起门来自己做 DCT 变换、量化、熵编码，块和块之间没有任何交流。这就导致一个问题：就算左边那块和当前这块颜色几乎一样，JPEG 还是会把当前块完完整整再编一遍，因为它根本不知道左边那块长什么样。H.264 的 I 帧不一样——它编码当前块的时候，会先偷看周围已经编好的块（左边、上边、左上角这些），沿着某个方向把像素值外推过来当预测值，然后只编实际值和预测值之间的差值。因为相邻块通常很相似，这个差值非常小，编起来就省很多 bit。所以同样是"帧内编码"，H.264 的 I 帧比 JPEG 高效得多——这就是帧内预测的价值。

第二种是**时间冗余**。这才是视频压缩的大头。相邻两帧画面，大部分内容其实没变——背景不动，只有人在动。那为什么要每帧都完整编一遍？H.264 的做法叫帧间预测加运动估计：编码当前帧的时候，去前面的参考帧里搜，找最像的那个块在哪，然后只记两样东西——
* 运动矢量，就是'这个块往右移了 5 个像素，往下移了 3 个像素'；
* 加上残差，就是挪过去之后还差的那一点点。这个思路是视频压缩率比图片序列高一个数量级的根本原因，也是 P 帧和 B 帧为什么比 I 帧小那么多的底层逻辑。

第三种是**视觉冗余**。人眼对亮度敏感，对色度迟钝；对低频的平滑区域敏感，对高频的细节纹理迟钝。那高频信息就可以丢一些，反正人眼也不容易察觉。H.264 的做法是先把残差做整数 DCT 变换——变换本身不丢信息啊，它只是把像素能量从空间域搬到频率域，能量会集中在左上角那几个低频系数上。然后到了量化这一步，用一个量化参数 QP 把高频系数狠狠除一下、很多直接变零了。**整个编码链路里，质量损失就只发生在量化这一步**，前面预测和变换都是无损的。所以我们调 CRF、调 QP，本质就是在调量化的粗细——QP 越大、量化越粗、丢得越多、画质越差但码率越低。

> **💡 补充：高频/低频、QP、CRF 到底是什么？**
>
> 这几个概念面试经常被追问，单独捋一下：
>
> **高频 vs 低频——拿一张照片来想**
>
> 你可以把图像想象成由不同"变化速度"的波形叠起来的。低频就是画面里变化慢的部分——大块大块的蓝天、墙面、皮肤，像素值和邻居差别很小，变化平缓。高频就是变化快的部分——草地的纹理、树叶的边缘、毛衣的纹路、人的头发丝，像素值在很小范围内剧烈跳变。
>
> DCT 变换做的事情，就是把你眼前这块 4×4 或 8×8 的像素，分解成一系列"基底图案"的加权和。左上角的系数对应那种整块一个色、没什么变化的基底——这是低频；越往右下角，基底图案的条纹越密、变化越快——这就是高频。变换完之后，能量通常全堆在左上角低频区，右下角高频区一片接近零的小数字。所以你一眼就能看出哪些信息重要、哪些可以丢。
>
> 为什么人眼对高频不敏感？你试试看：盯着一张人脸照片，如果我把皮肤磨皮磨得很光滑（丢高频），你看着觉得"嗯挺好看的"；但如果我把整张脸的亮度整体调暗一大截（动了低频），你马上就觉得不对劲。这就是量化敢对高频下狠手的底气。
>
> **QP——量化参数，最底层的旋钮**
>
> QP 全称 Quantization Parameter，一个整数，通常范围 0~51。它直接控制量化步长：QP 每增加 6，量化步长翻一倍。QP=0 的时候基本无损（步长极小，系数几乎原样保留），QP=51 的时候步长最大，大部分系数都被除成零了。所以 QP 越小画质越好码率越高，QP 越大画质越差码率越低。
>
> 你可以把 QP 理解为"一刀切"的参数——编码器里每个宏块用的都是这个 QP（或者在这个 QP 附近微调），简单粗暴。早期编码器调画质就是直接设 QP。
>
> **CRF——恒定质量因子，比 QP 更聪明的选择**
>
> CRF 全称 Constant Rate Factor，是 x264/x265 里最常用的画质控制方式。它解决的问题是：QP 一刀切太笨了——高速运动的画面需要更多码率才能维持同样画质，静态画面不需要那么多。CRF 的思路是"**保持画质恒定，码率随内容浮动**"：编码器会动态调整每一帧、甚至每个宏块的 QP——人眼敏感的场景给多点 bit（降 QP），人眼不敏感的场景（高速运动、暗场）就省点 bit（升 QP）。
>
> CRF 取值范围 0~51，**值越小画质越好、文件越大**。常用值：x264 默认 CRF 23（一般认为视觉无损的分界线），18 左右接近视觉无损，28 以上画质开始明显下降。注意：CRF 不跨编码器可比——x265 默认 CRF 28，和 x264 的 CRF 23 画质差不多，因为 H.265 编码效率本身就高。面试说"CRF 23 画质好"一定要带上前缀"在 x264 下"。
>
> 简单记：**QP 是直接调量化步长，一刀切；CRF 是调"恒定画质"目标，QP 由编码器自动帮你调。** 实际项目里 99% 的场景用 CRF，只有做码控分析或者调试时才手动设 QP。

第四种是**统计冗余**。前面几步已经把数据量砍下来了，但剩下的符号里还是有不均匀的——有些符号出现概率高、有些低。那就用熵编码再压一道：高频符号给短码、低频给长码，类似霍夫曼编码的思路。H.264 有两套方案：Baseline 用 CAVLC，就是上下文自适应的变长码，简单快；Main 和 High 用 CABAC，上下文自适应的算术编码，压缩率能再高 10% 到 15%，就是计算量大不少。

所以整体流水线走下来就是：**预测去冗余 → 算残差 → DCT 变换把能量集中 → 量化丢高频（这步有损）→ 熵编码再压一把 → 输出码流**。解码端倒着来，中间多一步去块滤波——因为分块编码在块边界会有马赛克效应，编码器在重建帧上先滤波再拿去当参考帧，这样后续帧预测更准。这就是所谓的环路滤波，in-loop 的意思就是它在编解码环路里面、会影响参考帧，不是显示时才做的后处理。"

这一层是整段回答里最能拉开差距的地方。要点就一个：**不要只报菜名，要解释"为什么"**——为什么有帧内预测？因为相邻像素相似。为什么有运动估计？因为相邻帧大部分没变。为什么有量化？因为人眼对高频不敏感。

**第三层：挑两三个技术点深入聊（看面试官方向灵活选）**

原理讲完了，面试官一般会有两种反应：要么他让你继续，要么他开始追问细节。不管是哪种，你都应该准备好几个能体现深度的点，随手掏出来讲。不用全讲，挑 2-3 个就行：

- **帧类型这件事**：I 帧是帧内编码，自己独立能解，数据量最大，相当于一个关键帧；P 帧只往前看、参考前面的 I 或 P 帧做预测；B 帧最狠，往前也看往后也看，压缩率最高，但代价是编解码顺序和显示顺序不一样了——这就是为什么有 PTS 和 DTS 两个时间戳。还有一个容易搞混的点：IDR 帧和普通 I 帧不一样——IDR 会强制清空参考帧缓冲，IDR 之后的帧绝对不会参考 IDR 之前的帧。所以拖进度条 seek 和直播中途切入，只能跳到 IDR 上，跳到普通 I 帧不行，因为它后面的帧可能还在参考它前面的帧。GOP 就是两个 I 帧之间这一组帧，短 GOP 秒开快、抗丢包好，长 GOP 压缩率高但 seek 慢。

- **Profile 和 Level 经常被搞混**：
	* Profile 决定的是算法复杂度——你能不能用 B 帧、能不能用 CABAC、能不能做 8×8 变换；。Baseline Profile 为了低功耗低延迟，直接砍掉了 B 帧、只用 CAVLC；Main 加上了 B 帧和 CABAC；High 再加 8×8 变换，压缩率最高。
	* Level 决定的是性能上限——最大分辨率、帧率、码率、参考帧缓冲有多大很多人问"Level 4.0 支持 B 帧吗"，这个问题本身就是错的——支不支持 B 帧是 Profile 的事，跟 Level 没关系。

- **码流在线上怎么传**：H.264 的基本单元叫 NALU，1 字节 header 加 payload，type 怎么取？`byte & 0x1F` 就拿出来了。但有两种打包方式——MP4 文件里用 AVCC 格式，每个 NALU 前面加长度前缀，SPS 和 PPS 这些参数集单独存在 `avcC` 这个 box 里；直播推流用 Annex-B 格式，每个 NALU 前面加起始码 `00 00 01` 或 `00 00 00 01`，SPS/PPS 直接混在流里。所以做直播的时候有一个经典操作：每个 IDR 帧前面必须补一发 SPS/PPS，不然新拉流的观众解不出画面。

- **熵编码的选择背后有 trade-off——CAVLC 和 CABAC 到底差在哪**：Baseline 为什么用 CAVLC 不用 CABAC？因为这两个东西的底层原理完全不同。CAVLC 是升级版霍夫曼编码——根据周围已编码块的残差模式自适应切换多套 VLC 码表，查表出码字，全硬件查表操作，一个时钟周期出一个符号，极快极省电。CABAC 走的是算术编码路线——维护一个概率模型持续跟踪"下一个 bit 是 0 的概率"，然后用算术编码器把高概率符号压到少于 1 bit（这是霍夫曼做不到的）。但代价是每个 bit 都要"读上下文→查概率→算术编码→更新概率模型"，全是串行依赖、很难并行，编解码都比 CAVLC 慢得多。再往细了说，CABAC 能多省 10~15% 靠三样东西：算术编码的小数 bit 分配、比 CAVLC 精细得多的上下文模型（不仅看周围残差大小，还看系数在 4×4 块里的位置、参考帧距离、QP 大小等）、以及先把非二值语法元素二值化再逐 bit 编码的设计。所以这个选择不是省实现成本，是产品定位决定的——视频会议要的是低延迟，CAVLC 够用；蓝光碟要的是画质和压缩率，CABAC 是标配。H.265 直接把 CAVLC 砍了，因为它的目标场景不需要 Baseline 那种妥协。

挑哪个点讲，看你面的团队是做什么的：流媒体/直播团队就多聊帧类型和码流结构，播放器/硬解团队就多聊 Profile 和熵编码，编解码算法团队就深入聊运动估计的亚像素精度和多参考帧机制。

**第四层：收个尾——把格局拉高（30 秒，让面试官觉得你有大局观）**

"总的来说，H.264 是视频界的普通话，兼容性无敌。但毕竟是 2003 年的老标准了，在 4K HDR 时代有点吃力。所以它的继任者 H.265/HEVC 做了很多改进——把固定的 16×16 宏块换成最大 64×64 的 CTU 四叉树、帧内预测方向从 9 种拉到 35 种、加了 SAO 滤波——最终效果是同画质再省一半码率。但代价也很明显：编码复杂度翻倍，然后还有一个更要命的事——H.265 的专利授权特别碎，好几个专利池各自收费、规则混乱，导致很多厂商不敢用。这个授权地狱直接逼出了 Google、Netflix 他们搞的 AV1，免专利费、压缩率还略超 H.265。不过话说回来，H.264 的兼容性和硬件成熟度摆在那，它还会当很多年的'默认选项'。"

**H.265 怎么说（面试对称结构——和 H.264 第一层呼应）**

如果面试官在你说完 H.264 之后接着问"那 H.265 呢"，你就用同样的节奏接上去。**第一层还是一句话定调，第二层挑 2~3 个改进点讲，不要报菜名**。

**第一层：一句话定调**

"H.265 是 H.264 的继任者，2013 年发布。它的核心卖点就一个：**同画质码率砍半**。拿刚才 1080p 那笔账来说——H.264 压到 4~8 Mbps，H.265 同等画质可以压到 2~4 Mbps。一部两小时的 4K HDR 电影，H.264 可能要 40~60 GB，H.265 只要 20~30 GB——这对流媒体和存储来说是质变。但代价也很实在：编码复杂度大约翻倍，软件编码慢很多，而且 H.265 的专利授权特别混乱——好几个专利池各自收费，规则不透明，搞到很多厂商宁愿继续用 H.264 或者转投 AV1。"

**第二层：为什么能再省一半——挑 2~3 个改进讲清楚**

H.265 没有推翻 H.264 的框架，还是"预测 + 变换 + 量化 + 熵编码 + 环路滤波"那套流水线。但**每个环节都做得更精细**。面试时不用全部报一遍，挑 2~3 个最有辨识度的讲：

"最大的改进是**把固定的 16×16 宏块换成了 CTU 四叉树**。H.264 所有决策都基于 16×16 宏块——对 4K 画面来说太碎了，几百几千个宏块各自带 header，开销很大；反过来对大片平坦区域（蓝天、墙壁），16×16 又太小了，相邻宏块编出来几乎一样，浪费。H.265 的 CTU 最大可以到 64×64，而且会根据画面内容自适应——平坦区域用大块（省 header），纹理区域自动细分到 8×8（保细节）。这是它省码率的最大功臣。

**第二个改进是帧内预测方向从 9 种拉到 35 种**。H.264 只有 8 个方向加一个 DC 均值模式——斜着的纹理、渐变过渡预测不准，残差就大，码率就高。35 种方向覆盖了更多的角度，斜边、弧线、渐变预测更准，残差更小，自然更省码率。

**第三个值得说的是 SAO（样点自适应补偿）**——这是 H.265 在环路滤波上新增的一步。解码重建出来的画面在边缘处容易有振铃效应（一圈一圈的波纹），SAO 会分析每个 CTU 的像素分布，给每个像素加一个微小的 offset 补偿回去——幅度很小但肉眼可见，尤其在渐变区域（天空、皮肤）。这一步几乎不增加码率却实实在在提升了主观画质。"

**第三层：收尾——为什么 H.265 没有取代 H.264**

"按说省一半码率应该秒杀 H.264，但现实不是这样。主要有三个阻力。第一，**专利授权地狱**——H.264 的专利授权相对统一（MPEG LA 一家说了算），H.265 冒出了三个专利池（MPEG LA、HEVC Advance、Velos Media），各收各的费、规则互相打架，厂商不知道该交钱给谁、怕被钓鱼诉讼。这个混乱直接逼出了免专利费的 AV1。第二，**编码太慢**——软件编码时间大约是 H.264 的 2~5 倍，实时场景（视频会议、直播）非常吃力。第三，**浏览器支持差**——Chrome 和 Firefox 至今不原生支持 H.265 解码（只能靠 MSE+硬件解码或 WASM 软解），Web 端用不了。所以 H.265 现在的主要阵地是苹果生态（iOS/macOS 全系硬解 + HEIC 照片）、4K 蓝光碟、和自建流媒体链路的大厂（Netflix、抖音）。"

> **面试技巧**：H.264 和 H.265 的面试回答要形成"对称感"——先说 H.264 是什么、为什么、能压多少、怎么做到的；再说 H.265 在 H.264 基础之上改了哪几个关键点、为什么能再省一半。面试官听下来会觉得你的知识是**结构化的**，不是一个一个散装的知识点。

**回答节奏 tips（面试前过一遍）**：

- 面试官让你"随便说说"→ 第一层定调 → 第二层原理（重点讲四种冗余和流水线，3 分钟左右）→ 如果他还听着就挑一个第三层的亮点 → 第四层收尾
- 你第一层说完他就追问某一个点 → 说明他对那个方向感兴趣，直接跳第三层对应的点深入，讲完顺势带到第二层的原理作为补充
- 全程不要报菜名、不要背概念——**要用"为什么"串**。比如不要说"H.264 有帧内预测"，要说"因为你一帧里面相邻像素差不多嘛，所以可以用帧内预测，让当前块参考旁边已编码的块"
- 专业术语第一次出现时顺手解释一句："SPS 就是序列参数集，里面存着宽高啊 profile 啊这些全局信息"

### 2.2 高频问答速查

- **Q：讲讲 H.264 是怎么把视频压缩这么小的？**（开放题）
	消除四种冗余：帧内预测去空间冗余、帧间预测+运动补偿去时间冗余、变换+量化利用人眼不敏感丢高频（**有损就在量化**）、熵编码去统计冗余；解码反过来 + 环路滤波去块。质量旋钮是 QP/CRF。
- **Q：H.264 和 H.265 的核心区别？**
	H.265 用 CTU 四叉树（≤64×64）取代固定 16×16 宏块、35 种帧内方向、只用 CABAC、加 SAO、有 Tiles/WPP 并行、NAL header 2 字节 + 多 VPS——**同画质省约 50% 码率，代价是编码复杂度翻倍**。
- **Q：CTU 比宏块好在哪？**
	内容自适应：平坦区域用大块省 header 开销、细节区域细分保质量；对 4K/8K 大画面尤其有效。
- **Q：H.265 省一半码率，为什么普及没那么快？**
	主要不是技术问题，是**专利授权碎片化**（多个专利池、费用高规则乱），加上编码更慢、浏览器支持受限。这逼出了免专利费的 **AV1**。
- **Q：I / IDR / P / B 帧分别是什么？为什么 seek 只能跳 IDR？**
	I 独立可解、P 前向参考、B 双向参考（压缩率最高但乱序）；IDR 是强制清空参考缓冲的 I 帧，是唯一保证"之后不依赖之前"的随机切入点。
- **Q：SPS / PPS / VPS 是什么？H.265 为什么多一个 VPS？**
	解码必需的参数集：SPS 描述序列、PPS 描述图像；H.265 多 VPS 描述整个视频的层级信息（多层/可分级），补齐逻辑必须带上。
- **Q：CABAC 和 CAVLC 区别？为什么 Baseline 用 CAVLC？**
	CABAC 是上下文自适应算术编码、压缩率更高但更耗算力；CAVLC 是变长码、简单快。Baseline 面向低延迟/低功耗/兼容，所以用 CAVLC 且无 B 帧。
- **Q：为什么实时通信（WebRTC）多用 H.264 而不是 H.265？**
	兼容性（浏览器/设备普遍支持 H.264）、硬件编解码成熟、延迟可控、无授权顾虑；H.265 浏览器支持差 + 授权乱，实时场景收益不抵风险。
- **Q：AVCC 和 Annex-B 的区别？**（编解码与封装的交界）
	AVCC 长度前缀、SPS/PPS 在 `avcC`（MP4 用）；Annex-B 起始码、SPS/PPS 混在流里（直播/RTP 用）。详见 [05](./05-H264-MP4-NALU.md) §四。
- **Q：AV1 是什么？和 H.265 什么关系？**
	AOMedia 开放联盟推出的**免专利费**编码，压缩率对标/略超 H.265，是对 H.265 授权混乱的产业反制；YouTube/Netflix 在推。代价是软件编码很慢、硬件支持还在铺开。

## 三、大局观：H.264/H.265 在整个体系里的位置

### 3.1 它在流水线的哪一环

```
采集 → 【编码(压缩)】 → 封装 → 传输 → 解封装 → 【解码(解压)】 → 渲染
         ↑ H.264/H.265 在这里                      ↑ 也在这里
```

编解码（codec = **co**der + **dec**oder）只负责**压缩与解压**这一环——它不管怎么装进文件（那是封装 [05](./05-H264-MP4-NALU.md)）、不管怎么传到对端（那是协议 [08](./08-网络协议与流媒体.md)）。

### 3.2 为什么编码是整个体系的"地基"

**不压缩根本没法用**。算一笔账：1080p、30fps、YUV420（每像素 1.5 字节）的裸流：

```
1920 × 1080 × 1.5 × 30 ≈ 93 MB/s ≈ 745 Mbps
```

一部 2 小时电影裸存 ≈ **670 GB**。而 H.264 压完同样画质只要 ~5-10 Mbps、几个 GB——**压缩比上百倍**。没有编码，就没有流媒体、没有视频通话、没有短视频。所以**编解码是音视频体系真正的"地基技术"**，面试权重最高的板块之一。

而 H.264 的特殊地位是：**它是有史以来部署最广的视频编码格式**——网页视频、直播、监控摄像头、蓝光、手机录像、WebRTC……几乎无处不在。所以它常被称为"视频界的 JPEG / 普通话"：**新方案再好，都要先回答"凭什么取代 H.264 的兼容性"**。

### 3.3 编解码的代际谱系（一张图建立大局观）

```
收费主线(ITU-T + ISO/MPEG 联合制定):
  MPEG-2 ──→ H.264/AVC ──→ H.265/HEVC ──→ H.266/VVC
 (DVD/广电)   (2003,普及)   (2013,4K)     (2020,8K,更新)

免版税主线(Google / 开放联盟 AOMedia):
  VP8 ──→ VP9 ──→ AV1
        (YouTube)  (对标 H.265,免专利费)
```

- **双重命名**：H.264 = ITU-T H.264 = ISO/IEC **MPEG-4 Part 10 AVC**；H.265 = ITU-T H.265 = **MPEG-H Part 2 HEVC**。同一个标准两个名字，因为是 ITU-T（VCEG）和 ISO（MPEG）两大组织联合制定的。
- **为什么有"免版税主线"**：H.265 专利授权混乱（见 §8.3），逼出了 Google VP9 和开放联盟的 **AV1**（Netflix/YouTube/各大厂联合，免专利费，对标 H.265）。这是当前编码领域最大的产业格局，面试聊"H.265 普及为什么慢"绕不开。

## 四、视频为什么能压缩（编码原理，H.264/H.265 通用底座）

这是面试最能拉分的开放题。核心一句话：**编码就是消除四种冗余**。


| 冗余                      | 怎么消                      | 对应技术                       |
| ----------------------- | ------------------------ | -------------------------- |
| **空间冗余**（一帧内相邻像素相似）     | 用同帧已编码的相邻像素预测当前块，只编差值    | **帧内预测**（Intra，I 帧靠它）      |
| **时间冗余**（相邻帧大部分没变）      | 在参考帧里找最像的块，只编"运动矢量 + 残差" | **帧间预测 + 运动估计/补偿**（P/B 帧）  |
| **视觉冗余**（人眼对高频细节/色度不敏感） | 变换到频域后，量化时把高频狠狠丢掉        | **变换 + 量化**（**有损就发生在这一步**） |
| **统计冗余**（符号出现概率不均）      | 高频符号用短码、低频用长码            | **熵编码**（CABAC / CAVLC）     |


完整编码流水线（解码端逐步逆过来）：

```
原始块 ─► 预测(帧内/帧间) ─► 残差 ─► 变换(整数DCT) ─► 量化 ─► 熵编码 ─► 码流
                                              │
                                  质量/码率旋钮在这(QP/CRF,见 06)
                                              │
重建帧 ◄─ 环路滤波(去块 deblocking[+SAO]) ◄── 反量化反变换 + 预测  (供后续帧参考)
```

四个必须说清的点：

1. **质量损失只在"量化"这一步**——QP（量化参数）/ CRF 调的就是量化粗细。预测、变换、熵编码本身**不丢信息**。这就是为什么 CRF 是控质量的核心旋钮（[06](./06-编码参数与码控.md)）。
2. **变换（DCT）本身不压缩**，它只是把像素能量集中到少数低频系数上，**为量化"丢高频"做铺垫**。
3. **环路滤波（in-loop）**：块状压缩会在块边界产生"马赛克边"，编码器在**重建帧**上做去块滤波，再拿它当后续帧的参考——所以参考帧更干净、预测更准。"in-loop"指它在编解码环路内、影响参考帧（区别于只在显示时做的后处理）。
4. **音频（AAC）同理**：靠**心理声学模型**砍掉人耳听不到的频率分量，再熵编码——"听觉冗余"版本（见 [04](./04-音频PCM-采样-重采样.md)）。

> 收尾模板（背）："**预测去空间/时间冗余、变换+量化利用人眼不敏感丢高频（有损就在量化）、熵编码再压一道；解码反过来并做环路滤波去块；质量旋钮是量化参数 QP。**"

## 五、H.264 / AVC 详解

### 5.1 基本单位：宏块（Macroblock）

H.264 把画面切成 **16×16 的宏块**逐个编码，宏块再可细分到 4×4 做预测。多个宏块组成 **slice**（片），slice 可以独立解码——抗错的设计（一个 slice 坏了不影响别的）。

### 5.2 帧类型 I / P / B + IDR + GOP（详见 [05](./05-H264-MP4-NALU.md) §七）

- **I 帧**：帧内编码，独立可解，数据量最大，是解码起点。
- **P 帧**：前向预测，参考前面的 I/P。
- **B 帧**：双向预测，参考前后帧，压缩率最高，但引入**解码顺序 ≠ 显示顺序**（所以有 PTS≠DTS，见 [05](./05-H264-MP4-NALU.md) §八）。
- **IDR 帧**：特殊 I 帧，**强制清空参考缓冲**——之后的帧绝不参考它之前的帧，是真正的随机切入点（seek/直播切入只能跳 IDR，普通 I 帧不行）。
- **GOP**：两个 I 帧之间一组。短 GOP = 秒开/抗丢包好；长 GOP = 压缩率高。
- **多参考帧**：H.264 最多可参考 16 帧（不止前一帧），找更像的来源。

### 5.3 帧内预测与帧间预测

- **帧内预测（Intra）**：H.264 有 **9 种 4×4 方向模式**（+ 16×16 的 4 种）。"现代 I 帧不是 JPEG"——它用同帧相邻已编码像素外推预测，再编残差，比 JPEG 独立编每块高效得多。
- **帧间预测（Inter）**：**运动估计**在参考帧里搜索最匹配的块，得到**运动矢量（MV）**，只编"MV + 残差"。支持 1/4 像素精度的亚像素运动补偿。**这是视频比图片序列压缩率高一个量级的根本原因**。

### 5.4 熵编码：CAVLC vs CABAC（爱考）


|     | CAVLC                                   | CABAC                                         |
| --- | --------------------------------------- | --------------------------------------------- |
| 全称  | Context-Adaptive Variable-Length Coding | Context-Adaptive **Binary Arithmetic** Coding |
| 原理  | 变长码（类似霍夫曼）                              | 算术编码 + 上下文自适应                                 |
| 压缩率 | 较低                                      | **更高（约省 10-15%）**                             |
| 算力  | 低、快                                     | 高、慢                                           |
| 用在  | Baseline Profile                        | Main / High Profile                           |


这正好解释了 §4.6 的 Profile 差异：**Baseline 用 CAVLC（图省事省电）、Main/High 用 CABAC（图压缩率）**。

**深入一下：两者到底怎么工作的，为什么差 10~15%**

名字里的 CA（Context-Adaptive）两者都有——意思是它们都会根据**已编码数据的上下文**来调整编码策略，不是死板地查一张表。区别在最后一个字母：一个是 VLC（变长码），一个是 BAC（二进制算术编码）。

**CAVLC 原理**：CAVLC 是一个升级版的霍夫曼编码。传统霍夫曼给每个符号固定一个码字——出现概率高的给短码、概率低的给长码。但这假设了所有场景下符号的概率都一样——实际上不是。残差大的区域和残差小的区域，系数的概率分布完全不同。CAVLC 做的事情就是：看左边和上边已编码块的残差模式，推断当前块属于"纹理复杂"还是"平坦"，然后选一套匹配的 VLC 码表。这样做的好处是码表切换对编解码端都是透明的——编码端选哪套表，解码端根据同样的上下文也选同一套表。

CAVLC 的优点：编码端"查上下文→选码表→查表得码字"，解码端"读码字→查同一张码表→得符号"。全是查表，硬件实现极简单（ROM 表 + 多路选择器），一个时钟周期出一个符号，功耗极低。

**CABAC 原理**：CABAC 不是给符号分配码字，而是维护一个概率模型，做算术编码。可以这样理解：你要编码一串 0/1 序列，CABAC 不断跟踪"下一个 bit 是 0 的概率是多少"。如果当前概率是 70% 是 0、30% 是 1——"0"是意料之中，算术编码器能用约 0.5 bit 就编完它；"1"出乎意料，需要约 1.7 bit。每编完一个 bit，概率模型根据实际值是 0 还是 1 更新——如果实际是 1，"1 的概率"就微微上调。这就是自适应。

CABAC 能比 CAVLC 多省 10~15%，靠三个东西：
1. **算术编码的小数 bit**：VLC 一个符号最少 1 bit，算术编码可以不到 1 bit——这是数学底层的优势。
2. **更细粒度的上下文模型**：CAVLC 的上下文基本只看"周围块残差大不大"，CABAC 还看"当前系数在 4×4 块里的位置（左上角更可能是大值）""参考帧距离""QP 大小"等等。上下文越多越准，概率预测越精确，算术编码越高效。
3. **二值化**：CABAC 先把非二值的语法元素（残差系数值、运动矢量差值）二值化成一串 0/1 bit，然后逐 bit 编码。好处是算术编码器只需要处理二值决策，且每种语法元素可以设计最优的二值化方式。

CABAC 的代价是慢：编码端每个 bit 都要"读上下文→查概率→算术编码→更新概率"。全是串行依赖——下一个 bit 的概率取决于上一个 bit 是什么，无法并行。解码端更痛苦——上一个 bit 不解出来，下一个 bit 没法开始。CAVLC 查一张表就出结果，CABAC 要跑一整套算术计算。

**产品视角**：Baseline = CAVLC + 无 B 帧 → 视频会议/低端设备（低延迟、低功耗）。Main/High = CABAC + B 帧 + 8×8 变换 → 蓝光碟/流媒体（画质优先，不在乎多等几毫秒）。H.265 直接把 CAVLC 砍了——它没有 Baseline 那种妥协场景，全链路 CABAC。

### 5.5 码流结构：NALU + 参数集

基本单元 **NALU** = 1 字节 NAL header + 负载，`type = byte & 0x1F`。两种打包方式：**AVCC**（长度前缀，MP4 用，SPS/PPS 在 `avcC`）vs **Annex-B**（起始码 `00 00 01`，直播/RTP 用，SPS/PPS 混在流里）。详见 [05](./05-H264-MP4-NALU.md) §三/§四。

其中 SPS 和 PPS 是解码器初始化的"钥匙"——没有它们，解码器连画面该画多大都不知道。下面展开讲。

#### 5.5.1 SPS（序列参数集）里存了什么？

SPS 作用于**整个视频序列**（即从视频开始到参数改变之前的这一长串连续画面）。它存储的是全局性、宏观的配置信息，核心内容包括：

- **视频分辨率（Width / Height）**：告诉解码器需要开辟多大尺寸的渲染画布。没有这个，解码器连一帧画面该分配多少内存都不知道。
- **编码档次与级别（Profile & Level）**：如 Baseline、Main、High Profile。解码器根据这个来判断自己硬件芯片的能力是否足以解码这个视频——能力不够直接报错。
- **帧率与时间戳信息（VUI, Video Usability Information）**：包含色彩空间矩阵（BT.601 / BT.709）、宽高比（SAR/DAR）和帧率。这部分决定了画面渲染时的颜色和比例是否正确。
- **参考帧的最大数量（Max Ref Frames）**：告诉解码器，内存中的解码图片缓冲区（DPB）最多需要同时缓存多少张历史图片作为后续 P 帧的参考源。这个值直接影响解码器的内存占用量。
- **帧编码方式**：是逐行扫描（Progressive）还是隔行扫描（Interlaced）。现代视频基本都是逐行。

> **一句话**：SPS 是"这张视频长什么样"的全局说明书，一个视频序列通常只有一个 SPS（或少数几个，仅在参数真正改变时才更新）。

#### 5.5.2 PPS（图像参数集）里存了什么？

PPS 作用于视频序列中的**单张或多张图像**。它的更新频率往往比 SPS 高，用来调整局部画面的解码参数。核心内容包括：

- **熵编码模式选择**：使用的是 CAVLC（低复杂度）还是 CABAC（高压缩率）。这个选择直接影响解码器的解码路径——CAVLC 和 CABAC 的解析逻辑完全不同。
- **初始量化参数（Initial QP）**：决定画面的基础清晰度和压缩剧烈程度。QP 越小画质越好、码率越高。
- **参考帧的索引和加权预测配置**：具体规定在解码当前图像时，如何对参考帧进行加权计算或排序。这在淡入淡出、场景切换时很重要。
- **切片组（Slice Groups）和瓷砖（Tiles，H.265）的划分**：是否把一张大图切分成多个并行解码的区域（非常利于多核 CPU 加速）。H.264 用 Slice Groups，H.265 升级为 Tiles + WPP。

> **一句话**：PPS 是"这几张画面怎么解码"的局部说明书，一个视频序列里可以有多个 PPS，不同画面可以用不同的 PPS。

#### 5.5.3 总结口诀

> **SPS 是全局战略部署**（管整条流：多大分辨率、要留几张参考帧）。
> **PPS 是局部战术配合**（管这几张图：怎么做熵编码、量化基础是多少）。

#### 5.5.4 💡 WebRTC 开发者视角：为什么它们在实时音视频中极其致命？

在常规的 MP4 离线文件里，SPS 和 PPS 通常藏在文件头的 moov box 里，播放前一次性读完即可。但 **WebRTC 是网络丢包极高、且随时可能有新用户加入的实时直播流**——SPS/PPS 的缺失会直接导致"黑屏"。

**新用户加入时的"黑屏"问题**：假设 A 已经在推流，B 刚刚进入房间。此时 A 正在发 P 帧。B 即使收到了 P 帧甚至 I 帧，如果手里没有 SPS/PPS，解码芯片根本不知道视频的分辨率是多少——只能把所有帧丢弃，导致 B 看到长时间的黑屏，直到下一个绑定了 SPS/PPS 的关键帧到达。

**WebRTC 的两层解决手段**：

- **Out-of-band（信令交换）**：在 WebRTC 建立连接的 SDP 协商阶段（Offer/Answer），SPS 和 PPS 的十六进制数据就已经被转换成字符串（例如 `profile-level-id=42e01f;sprop-parameter-sets=Z0LgH7Z0A8ARPy4C=,aM4wpIA=`），直接通过信令服务器提前塞给了对方。这样一来，解码器在收到第一个视频包之前就已经"知道画面长什么样了"。

- **In-band（随流发送）**：为了防止网络丢包导致信令阶段的 SPS/PPS 丢失，或者 mid-stream（中途）有用户加入，WebRTC 编码器被强制要求：**在每一个 IDR 帧（关键帧）数据包的前面，必须紧紧绑定、重新打包一份最新的 SPS 和 PPS**。这样无论何时加入、无论之前丢了多少包，只要收到下一个关键帧，解码器就能立即完成初始化。

> **实战记忆**：直播推流也是同样的逻辑——每个 IDR 前必须补 SPS/PPS，否则新拉流的观众永远解不出画面。这就是为什么"每个关键帧前重发参数集"是实时音视频的铁律。

### 5.6 Profile 与 Level：怎么控制

**Profile 和 Level 各自管什么**（先分清概念，面试最爱混淆）：

- **Profile**（算法复杂度档位）：决定你能用哪些编码工具——Baseline 砍了 B 帧和 CABAC、Main 加上了 B 帧和 CABAC、High 再加 8×8 变换。Profile 选错了，编码器直接不让你用某些功能。
- **Level**（性能上限）：限制解码器需要多大的"能力"才能播这个视频——最大分辨率、帧率、码率、DPB（参考帧缓冲大小）。Level 不够，解码器硬件可能拒绝解码。
- **经典混淆**："Level 4.0 支持 B 帧吗？"——这个问题本身就是错的。支不支持 B 帧是 Profile 的事，跟 Level 无关。Level 只管"上限"，不管"能不能"。

**FFmpeg 命令行**：

```bash
# H.264: 指定 Profile 和 Level
ffmpeg -i input.mp4 -c:v libx264 \
    -profile:v baseline \     # Baseline（低延迟,无B帧,CAVLC）
    -level:v 3.1 \            # 1280×720@30fps
    output.mp4

ffmpeg -i input.mp4 -c:v libx264 \
    -profile:v high \         # High（B帧+CABAC+8×8,压缩率最高）
    -level:v 4.0 \            # 1920×1080@30fps
    output.mp4

# H.265: 也一样，但 level 写法不同（注意小数点）
ffmpeg -i input.mp4 -c:v libx265 \
    -profile:v main \         # Main（8bit 4:2:0）或 main10（10bit HDR）
    -level:v 5.0 \            # 4K@30fps
    output.mp4
```

**常用 Profile & Level 组合**：

| 场景 | Profile | Level | 说明 |
|------|---------|-------|------|
| WebRTC 视频通话 | Constrained Baseline | 3.1 | 无 B 帧 + CAVLC，低延迟；720p@30fps |
| 普通 1080p 点播 | High | 4.0 | 压缩率最高，解码器普遍支持 |
| 1080p@60fps | High | 4.2 | 高帧率需要更高 Level |
| 4K@30fps | High | 5.1 | 4K H.264，但码率大，更推荐 H.265 |
| 4K HDR (HEVC) | Main10 | 5.1 | 10bit HDR 必须 Main10 Profile |
| 监控/低功耗嵌入 | Baseline | 3.0 | 兼容老设备，省电 |

**不设会怎样**：不指定 Profile 和 Level，FFmpeg 会根据其他参数**自动选择**。比如你设了 `-bf 0`（关 B 帧），x264 自动降到 Main 甚至 Baseline；你设了 4K 分辨率，Level 自动提到 5.1。自动选择通常是对的，但如果你的目标设备只支持特定 Profile/Level（比如某款老芯片只支持 Baseline 3.1），就必须手动指定——编码器不会知道你的解码端是什么。

**C API 怎么控制**：

```cpp
// 方式 1: av_opt_set（推荐，Profile 是编码器私有参数）
av_opt_set(codecCtx->priv_data, "profile", "high", 0);
av_opt_set(codecCtx->priv_data, "level", "4.0", 0);

// 方式 2: AVCodecContext 公共字段（Level 有公共字段，但 Profile 通常没有）
codecCtx->level = 40;  // Level 4.0 = 40（H.264 规则：Level × 10）
// 注意: H.265 的 level 字段值不同，查 FFmpeg 源码确认

// 方式 3: 构建时通过字典传入（最灵活）
AVDictionary *opts = NULL;
av_dict_set(&opts, "profile", "high", 0);
av_dict_set(&opts, "level", "4.0", 0);
avcodec_open2(codecCtx, codec, &opts);
av_dict_free(&opts);
```

**设置冲突了会怎样**：如果你同时设了 Baseline Profile 和 `-bf 2`（要求 B 帧），x264 会直接报错或静默忽略 B 帧——因为 Baseline 根本不允许 B 帧。实际操作顺序是：Profile 先约束了可用工具集，其他参数只能在这个集合里选。所以调试时如果发现某个参数"不生效"，先查是不是 Profile 把它禁掉了。

## 六、H.265 / HEVC 详解

### 6.1 为什么需要它

H.264 在 4K/8K 时代码率太大。H.265 的目标就一个：**同画质砍掉一半码率**（或同码率画质更好），让 4K/HDR 流媒体、超高清存储成为可能。它没有推翻 H.264 的框架（还是"预测+变换+量化+熵编码+环路滤波"），而是**每个环节都做得更精细**。

### 6.2 核心革新：CTU 四叉树取代固定宏块

H.264 宏块固定 16×16——对 4K 这种大画面太碎、对平坦区域太浪费。H.265 用 **CTU（Coding Tree Unit，最大 64×64）**，再按内容**四叉树递归细分**：

```
CTU(64×64) ─四叉树细分─► CU(编码单元, 8×8 ~ 64×64)
                            ├─ PU(预测单元): 帧内/帧间预测的粒度
                            └─ TU(变换单元): 变换/量化的粒度(也四叉树)
```

直觉：**平坦区域用大块（省 header 开销）、细节区域用小块（保细节）**。这是 H.265 省码率的最大功臣。

### 6.3 更精细的预测

- **帧内预测 35 种方向**（33 角度 + DC + Planar），vs H.264 的 9 种——平滑渐变和复杂纹理都预测得更准。
- **帧间预测**：更精细的运动矢量预测（AMVP / Merge 模式）、更灵活的块划分。

### 6.4 熵编码与环路滤波

- **只有 CABAC**（H.265 去掉了 CAVLC）。
- 环路滤波 = **Deblocking（去块）+ SAO（Sample Adaptive Offset，样点自适应补偿）**——SAO 是 H.265 新增的，进一步消除振铃失真和色带。

### 6.5 并行化：Tiles 与 WPP

4K/8K 一帧太大，H.265 内建并行手段：**Tiles**（把帧切成矩形块，各块独立编/解，多核并行）、**WPP（Wavefront Parallel Processing，波前并行）**——这是 H.264 没有的，为高分辨率多核而生。

### 6.6 码流结构差异（详见 [05](./05-H264-MP4-NALU.md) §5.4）

- **NAL header 2 字节**，`type = (byte>>1) & 0x3F`——直接把 H.264 的 `byte & 0x1F` 搬过来会全错（经典迁移 bug）。
- **多一层 VPS（Video Parameter Set）**：参数集变成 VPS + SPS + PPS。补齐逻辑必须带上 VPS，否则部分解码器解不出。对应的起始码工具是 `hevc_mp4toannexb`。

### 6.7 Profile

- **Main**（8bit 4:2:0）、**Main 10**（10bit——**HDR 的基础**）、Main Still Picture（单张图，即 HEIF/HEIC 照片的底层）。注意：iPhone 拍的 `.heic` 照片、`.mov` 视频默认就是 HEVC。

## 七、H.264 vs H.265 全面对比


| 维度         | H.264 / AVC      | H.265 / HEVC                   |
| ---------- | ---------------- | ------------------------------ |
| 发布         | 2003             | 2013                           |
| 基本块        | 宏块 16×16         | CTU ≤64×64，四叉树 CU/PU/TU        |

| 熵编码        | CAVLC / CABAC    | 仅 CABAC                        |

| 并行         | Slice            | Slice + **Tiles + WPP**        |

## 八、使用场景与选型（大局观）

### 8.1 什么时候用 H.264

- **兼容性优先**：要覆盖所有浏览器、老手机、各种播放器——H.264 是最大公约数。
- **实时低延迟**：WebRTC、视频会议、直播——硬件编解码成熟、延迟可控（用 Constrained Baseline/无 B 帧）。
- **算力/功耗受限**：老设备、低端芯片编 H.265 吃力。

### 8.2 什么时候用 H.265

- **4K / 8K / HDR**：Main 10 是 HDR 的基础路径。
- **存储 / 带宽敏感**：监控录像 7×24 长期存储、OTT 高清点播——省一半码率就是省一半存储/CDN 成本。
- **苹果生态**：iPhone 录制、HEIC 照片默认 HEVC，Apple 设备硬件支持好。

### 8.3 绕不开的坑：H.265 的专利授权（高频产业题）

H.265 省 50% 码率却**普及没想象中快**，核心不是技术，是**钱**：H.264 的专利主要由 MPEG LA 一家打包、规则清晰；而 **H.265 的专利分散在多个专利池（MPEG LA / Access Advance / Velos）和池外持有者**，授权费高、规则不清、谁都不敢轻易用。

这个"授权地狱"直接催生了 **AV1**（AOMedia 开放媒体联盟：Google、Netflix、Amazon、微软、苹果…联合推出，**免专利费**，压缩率对标甚至略超 H.265）。所以：

- **YouTube / Netflix 大力推 VP9 / AV1**（自家分发、省授权费 + 省带宽）。
- **H.265 在受控环境更香**（苹果生态、监控、广电——设备和授权可控）。
- 面试聊"H.265 为什么普及慢""AV1 是什么"——答案核心就是**专利授权 + 开放联盟的反制**。

### 8.4 一句话选型

> **要兼容/实时/省电 → H.264；要 4K-HDR/省存储且环境可控 → H.265；要彻底免授权费且能接受编码慢 → AV1。**

## 九、常见坑与误区（必看）


| 误区 / 坑                                         | 真相                                                                       |
| ---------------------------------------------- | ------------------------------------------------------------------------ |
| "I 帧就是一张 JPEG"                                 | I 帧用**帧内预测**（相邻像素外推 + 残差），比 JPEG 独立编码高效得多                                |
| "IDR 帧 = I 帧"                                  | IDR 是特殊 I 帧，**强制清空参考缓冲**；普通 I 帧后面的帧仍可能参考它之前的帧。seek 只能跳 IDR               |
| "Profile 决定分辨率"                                | 决定分辨率/帧率上限的是 **Level**；Profile 决定**算法复杂度**（能不能用 B 帧/CABAC）               |
| "Level 4.0 不含 B 帧"                             | Level 与 B 帧无关，用不用 B 帧由 Profile 决定                                        |
| "H.265 一定比 H.264 好，应该都用它"                      | H.265 编码更慢更耗电、浏览器支持受限、**专利授权混乱**——实时/兼容场景 H.264 仍是首选                     |
| 把 H.264 的 `getNaluType = byte & 0x1F` 用到 H.265 | H.265 NAL header **2 字节**，`type = (byte>>1) & 0x3F`，搬过去全错                |
| "H.265 也只有 SPS/PPS"                            | H.265 **多一层 VPS**，参数集补齐必须带上，否则解不出                                        |
| "CRF 23 在 H.264 和 H.265 画质一样"                  | CRF 不跨编码器可比：H.264 默认 CRF 23，**H.265 默认 28**（压缩更狠，同数值更糊）                  |
| "选了 H.265 就能放网页"                               | 浏览器对 H.265 支持有限（Safari 较好，Chrome 要硬件/特定条件）；网页通用还得 H.264 / VP9 / AV1      |
| "硬件都支持 H.265"                                  | 硬件支持参差——老芯片、部分低端设备只有 H.264 硬解；编码前要做能力查询 + 软解兜底（见 [10](./10-移动端硬件编解码.md)） |
| "H.265 = HEVC 是两个东西"                           | 同一个标准两个名字（ITU-T H.265 = MPEG-H HEVC）                                     |
