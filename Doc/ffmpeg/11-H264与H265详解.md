## 一、面试高频问答 + 速记卡（先看这个）

> 这一节是全篇的"考前突击"——直接背问答和速记卡。想搞懂背后的原理，再往下看 §二 起的正文。

### 1.1 面试高频问答（直接背）

**Q（最常见的开场）：请你讲一下 H.264。**

别一上来堆细节，用"金字塔结构"：定位 → 为什么 → 四种冗余 → 码流结构 → 调优 → 局限演进。可直接背的版本（约 2-3 分钟）：

> "H.264 又叫 AVC，是目前部署最广的视频编码标准，负责音视频流水线里'压缩'这一环。兼容性极好——网页、直播、监控、手机录像、WebRTC 基本都用它，堪称'视频界的普通话'。
>
> 视频不压根本没法用：1080p30 的裸流约 **745 Mbps**、一部电影几百 GB；H.264 能压上百倍还基本看不出损失。
>
> 它的核心是**消除四种冗余**：① 帧内预测去掉一帧内的空间冗余；② 帧间预测加运动补偿去掉相邻帧的时间冗余，只编运动矢量和残差；③ 变换加量化，利用人眼对高频不敏感丢掉高频，**有损就发生在量化这一步**，CRF/QP 调的就是它；④ 熵编码去统计冗余。解码反过来，再加一道环路去块滤波。
>
> 码流由一个个 NALU 组成，其中 SPS/PPS 是参数集、解码前必须先拿到；帧分 I/P/B，IDR 是随机切入点；打包有两种——MP4 用 AVCC（长度前缀），直播/RTP 用 Annex-B（起始码）。
>
> 工程上通过 Profile、CRF/码控调质量码率，低延迟场景用无 B 帧 + zerolatency。
>
> 它的局限是到 4K/8K 码率偏大，所以有了 H.265 同画质省约一半码率，但 H.265 专利授权混乱、普及偏慢，又催生了免版税的 AV1。"

记不住整段就记**六个词**：**定位 → 为什么 → 四种冗余 → 码流结构 → 调优 → 局限演进**。每一块都能被追问，追到哪就展开哪（原理见 §三、码流见 §四、对比见 §六）。

**Q：SPS / PPS / VPS 各存了哪些数据？**

作用域从大到小：**VPS（整个视频）⊃ SPS（一个序列）⊃ PPS（一张/几张图）**；PPS 指向某个 SPS，SPS 指向某个 VPS（H.265）。

- **SPS（序列参数集）= "画面长什么样"**：profile/level、**分辨率**（按宏块数 + `frame_cropping` 裁剪，因为宽高按 16 对齐）、色度格式（4:2:0 / 4:2:2 / 4:4:4）、位深（8/10bit）、**最大参考帧数**（决定解码端 DPB 大小）、POC/帧号计算方式、帧/场标志，以及 **VUI**（宽高比 SAR、**色彩空间 / color_range、帧率、HRD 参数**——发灰/偏色 bug 要读这里）。
- **PPS（图像参数集）= "帧是怎么编的"**：指向哪个 SPS、**熵编码方式 `entropy_coding_mode`（0=CAVLC / 1=CABAC）**、初始 QP、参考帧列表默认数量、加权预测开关、8×8 变换开关（High Profile）、deblocking / constrained_intra 等开关。
- **VPS（仅 H.265）= "码流有几层、层间关系"**：`profile_tier_level`、多层 / 可分级（SVC）/ 多视点（MV-HEVC）信息、时间子层数与各层 DPB/码率。**单层普通视频里 VPS 内容很"空"，但解码器仍要求它存在**；所以 H.265 补参数集必须 **VPS+SPS+PPS 三件**，漏 VPS 部分解码器直接解不出。

速答：**SPS 存"画面长啥样"（分辨率/色彩/profile/参考帧数）、PPS 存"帧怎么编的"（CABAC/CAVLC、QP、加权预测）、VPS（仅 H.265）存"有几层、层间关系"。**

**Q：讲讲 H.264 是怎么把视频压缩这么小的？**（开放题）
消除四种冗余：帧内预测去空间冗余、帧间预测+运动补偿去时间冗余、变换+量化利用人眼不敏感丢高频（**有损就在量化**）、熵编码去统计冗余；解码反过来 + 环路滤波去块。质量旋钮是 QP/CRF。（详见 §三）

**Q：H.264 和 H.265 的核心区别？**
H.265 用 CTU 四叉树（≤64×64）取代固定 16×16 宏块、35 种帧内方向、只用 CABAC、加 SAO、有 Tiles/WPP 并行、NAL header 2 字节 + 多 VPS——**同画质省约 50% 码率，代价是编码复杂度翻倍**。（详见 §六）

**Q：CTU 比宏块好在哪？**
内容自适应：平坦区域用大块省 header 开销、细节区域细分保质量；对 4K/8K 大画面尤其有效。

**Q：H.265 省一半码率，为什么普及没那么快？**
主要不是技术问题，是**专利授权碎片化**（多个专利池、费用高规则乱），加上编码更慢、浏览器支持受限。这逼出了免专利费的 **AV1**。（详见 §7.3）

**Q：I / IDR / P / B 帧分别是什么？为什么 seek 只能跳 IDR？**
I 独立可解、P 前向参考、B 双向参考（压缩率最高但乱序）；IDR 是强制清空参考缓冲的 I 帧，是唯一保证"之后不依赖之前"的随机切入点。

**Q：CABAC 和 CAVLC 区别？为什么 Baseline 用 CAVLC？**
CABAC 是上下文自适应算术编码、压缩率更高但更耗算力；CAVLC 是变长码、简单快。Baseline 面向低延迟/低功耗/兼容，所以用 CAVLC 且无 B 帧。

**Q：为什么实时通信（WebRTC）多用 H.264 而不是 H.265？**
兼容性（浏览器/设备普遍支持 H.264）、硬件编解码成熟、延迟可控、无授权顾虑；H.265 浏览器支持差 + 授权乱，实时场景收益不抵风险。

**Q：AVCC 和 Annex-B 的区别？**（编解码与封装的交界）
AVCC 长度前缀、SPS/PPS 在 `avcC`（MP4 用）；Annex-B 起始码、SPS/PPS 混在流里（直播/RTP 用）。详见 [05](./05-H264-MP4-NALU.md) §四。

**Q：AV1 是什么？和 H.265 什么关系？**
AOMedia 开放联盟推出的**免专利费**编码，压缩率对标/略超 H.265，是对 H.265 授权混乱的产业反制；YouTube/Netflix 在推。代价是软件编码很慢、硬件支持还在铺开。

### 1.2 速记卡（关键数字，30 秒速答）

**一句话定义**：

- **H.264 / AVC**（2003）：迄今部署最广的视频编码标准，"视频界的普通话"——兼容性之王。
- **H.265 / HEVC**（2013）：H.264 的继任者，**同画质省约 50% 码率**，代价是编码复杂度约翻倍 + 专利授权混乱。

**关键数字（爱考）**：

| 维度 | H.264 | H.265 |
|---|---|---|
| 基本编码块 | 宏块 16×16 | CTU 最大 64×64（四叉树细分） |
| NAL header | 1 字节，`type = byte & 0x1F` | **2 字节**，`type = (byte>>1) & 0x3F` |
| 参数集 | SPS、PPS | **VPS、SPS、PPS**（多一层 VPS） |
| 熵编码 | CAVLC（Baseline）/ CABAC（Main+） | **只有 CABAC** |
| 帧内预测方向 | 9 种（4×4） | 35 种（33 角度 + DC + Planar） |
| 环路滤波 | Deblocking | Deblocking + **SAO** |
| 压缩率 | 基准 | 同画质 **省约 50% 码率** |
| 编码复杂度 | 基准 | 约 **2× 以上** |
| 典型 Profile | Baseline / Main / High | Main / **Main10**（10bit/HDR） |

**一句话选型**：**兼容性 / 实时 / 老设备 → H.264；4K/HDR / 存储带宽敏感 / 苹果生态 → H.265；想免专利费 → 看 AV1**。

## 二、大局观：H.264/H.265 在整个体系里的位置

### 2.1 它在流水线的哪一环

```
采集 → 【编码(压缩)】 → 封装 → 传输 → 解封装 → 【解码(解压)】 → 渲染
         ↑ H.264/H.265 在这里                      ↑ 也在这里
```

编解码（codec = **co**der + **dec**oder）只负责**压缩与解压**这一环——它不管怎么装进文件（那是封装 [05](./05-H264-MP4-NALU.md)）、不管怎么传到对端（那是协议 [08](./08-网络协议与流媒体.md)）。

### 2.2 为什么编码是整个体系的"地基"

**不压缩根本没法用**。算一笔账：1080p、30fps、YUV420（每像素 1.5 字节）的裸流：

```
1920 × 1080 × 1.5 × 30 ≈ 93 MB/s ≈ 745 Mbps
```

一部 2 小时电影裸存 ≈ **670 GB**。而 H.264 压完同样画质只要 ~5-10 Mbps、几个 GB——**压缩比上百倍**。没有编码，就没有流媒体、没有视频通话、没有短视频。所以**编解码是音视频体系真正的"地基技术"**，面试权重最高的板块之一。

而 H.264 的特殊地位是：**它是有史以来部署最广的视频编码格式**——网页视频、直播、监控摄像头、蓝光、手机录像、WebRTC……几乎无处不在。所以它常被称为"视频界的 JPEG / 普通话"：**新方案再好，都要先回答"凭什么取代 H.264 的兼容性"**。

### 2.3 编解码的代际谱系（一张图建立大局观）

```
收费主线(ITU-T + ISO/MPEG 联合制定):
  MPEG-2 ──→ H.264/AVC ──→ H.265/HEVC ──→ H.266/VVC
 (DVD/广电)   (2003,普及)   (2013,4K)     (2020,8K,更新)

免版税主线(Google / 开放联盟 AOMedia):
  VP8 ──→ VP9 ──→ AV1
        (YouTube)  (对标 H.265,免专利费)
```

- **双重命名**：H.264 = ITU-T H.264 = ISO/IEC **MPEG-4 Part 10 AVC**；H.265 = ITU-T H.265 = **MPEG-H Part 2 HEVC**。同一个标准两个名字，因为是 ITU-T（VCEG）和 ISO（MPEG）两大组织联合制定的。
- **为什么有"免版税主线"**：H.265 专利授权混乱（见 §7.3），逼出了 Google VP9 和开放联盟的 **AV1**（Netflix/YouTube/各大厂联合，免专利费，对标 H.265）。这是当前编码领域最大的产业格局，面试聊"H.265 普及为什么慢"绕不开。

## 三、视频为什么能压缩（编码原理，H.264/H.265 通用底座）

这是面试最能拉分的开放题。核心一句话：**编码就是消除四种冗余**。

| 冗余 | 怎么消 | 对应技术 |
|---|---|---|
| **空间冗余**（一帧内相邻像素相似） | 用同帧已编码的相邻像素预测当前块，只编差值 | **帧内预测**（Intra，I 帧靠它） |
| **时间冗余**（相邻帧大部分没变） | 在参考帧里找最像的块，只编"运动矢量 + 残差" | **帧间预测 + 运动估计/补偿**（P/B 帧） |
| **视觉冗余**（人眼对高频细节/色度不敏感） | 变换到频域后，量化时把高频狠狠丢掉 | **变换 + 量化**（**有损就发生在这一步**） |
| **统计冗余**（符号出现概率不均） | 高频符号用短码、低频用长码 | **熵编码**（CABAC / CAVLC） |

完整编码流水线（解码端逐步逆过来）：

```
原始块 ─► 预测(帧内/帧间) ─► 残差 ─► 变换(整数DCT) ─► 量化 ─► 熵编码 ─► 码流
                                              │
                                  质量/码率旋钮在这(QP/CRF,见 06)
                                              │
重建帧 ◄─ 环路滤波(去块 deblocking[+SAO]) ◄── 反量化反变换 + 预测  (供后续帧参考)
```

四个必须说清的点：

1. **质量损失只在"量化"这一步**——QP（量化参数）/ CRF 调的就是量化粗细。预测、变换、熵编码本身**不丢信息**。这就是为什么 CRF 是控质量的核心旋钮（[06](./06-编码参数与码控.md)）。
2. **变换（DCT）本身不压缩**，它只是把像素能量集中到少数低频系数上，**为量化"丢高频"做铺垫**。
3. **环路滤波（in-loop）**：块状压缩会在块边界产生"马赛克边"，编码器在**重建帧**上做去块滤波，再拿它当后续帧的参考——所以参考帧更干净、预测更准。"in-loop"指它在编解码环路内、影响参考帧（区别于只在显示时做的后处理）。
4. **音频（AAC）同理**：靠**心理声学模型**砍掉人耳听不到的频率分量，再熵编码——"听觉冗余"版本（见 [04](./04-音频PCM-采样-重采样.md)）。

> 收尾模板（背）："**预测去空间/时间冗余、变换+量化利用人眼不敏感丢高频（有损就在量化）、熵编码再压一道；解码反过来并做环路滤波去块；质量旋钮是量化参数 QP。**"

## 四、H.264 / AVC 详解

### 4.1 基本单位：宏块（Macroblock）

H.264 把画面切成 **16×16 的宏块**逐个编码，宏块再可细分到 4×4 做预测。多个宏块组成 **slice**（片），slice 可以独立解码——抗错的设计（一个 slice 坏了不影响别的）。

### 4.2 帧类型 I / P / B + IDR + GOP（详见 [05](./05-H264-MP4-NALU.md) §七）

- **I 帧**：帧内编码，独立可解，数据量最大，是解码起点。
- **P 帧**：前向预测，参考前面的 I/P。
- **B 帧**：双向预测，参考前后帧，压缩率最高，但引入**解码顺序 ≠ 显示顺序**（所以有 PTS≠DTS，见 [05](./05-H264-MP4-NALU.md) §八）。
- **IDR 帧**：特殊 I 帧，**强制清空参考缓冲**——之后的帧绝不参考它之前的帧，是真正的随机切入点（seek/直播切入只能跳 IDR，普通 I 帧不行）。
- **GOP**：两个 I 帧之间一组。短 GOP = 秒开/抗丢包好；长 GOP = 压缩率高。
- **多参考帧**：H.264 最多可参考 16 帧（不止前一帧），找更像的来源。

### 4.3 帧内预测与帧间预测

- **帧内预测（Intra）**：H.264 有 **9 种 4×4 方向模式**（+ 16×16 的 4 种）。"现代 I 帧不是 JPEG"——它用同帧相邻已编码像素外推预测，再编残差，比 JPEG 独立编每块高效得多。
- **帧间预测（Inter）**：**运动估计**在参考帧里搜索最匹配的块，得到**运动矢量（MV）**，只编"MV + 残差"。支持 1/4 像素精度的亚像素运动补偿。**这是视频比图片序列压缩率高一个量级的根本原因**。

### 4.4 熵编码：CAVLC vs CABAC（爱考）

| | CAVLC | CABAC |
|---|---|---|
| 全称 | Context-Adaptive Variable-Length Coding | Context-Adaptive **Binary Arithmetic** Coding |
| 原理 | 变长码（类似霍夫曼） | 算术编码 + 上下文自适应 |
| 压缩率 | 较低 | **更高（约省 10-15%）** |
| 算力 | 低、快 | 高、慢 |
| 用在 | Baseline Profile | Main / High Profile |

这正好解释了 §4.6 的 Profile 差异：**Baseline 用 CAVLC（图省事省电）、Main/High 用 CABAC（图压缩率）**。

### 4.5 码流结构：NALU + 参数集（详见 [05](./05-H264-MP4-NALU.md) §三/§四）

- 基本单元 **NALU** = 1 字节 NAL header + 负载，`type = byte & 0x1F`。
- **SPS**（序列参数集，宽高/profile/level）、**PPS**（图像参数集）——解码前必须先拿到。
- 两种打包：**AVCC**（长度前缀，MP4 用，SPS/PPS 在 `avcC`）vs **Annex-B**（起始码 `00 00 01`，直播/RTP 用，SPS/PPS 混在流里）。直播要"每个 IDR 前补 SPS/PPS"。

### 4.6 Profile 与 Level（详见 [06](./06-编码参数与码控.md) §四）

- **Profile（算法复杂度档位）**：Baseline/Constrained Baseline（无 B 帧、CAVLC，低延迟/兼容）→ Main（B 帧+CABAC）→ High（8×8 变换、压缩率最高）→ High 10/4:2:2/4:4:4（高位深/高色度）。
- **Level（性能上限）**：限制最大分辨率/帧率/码率/参考帧缓冲（DPB），**与是否用 B 帧无关**（那是 Profile 决定的）。

## 五、H.265 / HEVC 详解

### 5.1 为什么需要它

H.264 在 4K/8K 时代码率太大。H.265 的目标就一个：**同画质砍掉一半码率**（或同码率画质更好），让 4K/HDR 流媒体、超高清存储成为可能。它没有推翻 H.264 的框架（还是"预测+变换+量化+熵编码+环路滤波"），而是**每个环节都做得更精细**。

### 5.2 核心革新：CTU 四叉树取代固定宏块

H.264 宏块固定 16×16——对 4K 这种大画面太碎、对平坦区域太浪费。H.265 用 **CTU（Coding Tree Unit，最大 64×64）**，再按内容**四叉树递归细分**：

```
CTU(64×64) ─四叉树细分─► CU(编码单元, 8×8 ~ 64×64)
                            ├─ PU(预测单元): 帧内/帧间预测的粒度
                            └─ TU(变换单元): 变换/量化的粒度(也四叉树)
```

直觉：**平坦区域用大块（省 header 开销）、细节区域用小块（保细节）**。这是 H.265 省码率的最大功臣。

### 5.3 更精细的预测

- **帧内预测 35 种方向**（33 角度 + DC + Planar），vs H.264 的 9 种——平滑渐变和复杂纹理都预测得更准。
- **帧间预测**：更精细的运动矢量预测（AMVP / Merge 模式）、更灵活的块划分。

### 5.4 熵编码与环路滤波

- **只有 CABAC**（H.265 去掉了 CAVLC）。
- 环路滤波 = **Deblocking（去块）+ SAO（Sample Adaptive Offset，样点自适应补偿）**——SAO 是 H.265 新增的，进一步消除振铃失真和色带。

### 5.5 并行化：Tiles 与 WPP

4K/8K 一帧太大，H.265 内建并行手段：**Tiles**（把帧切成矩形块，各块独立编/解，多核并行）、**WPP（Wavefront Parallel Processing，波前并行）**——这是 H.264 没有的，为高分辨率多核而生。

### 5.6 码流结构差异（详见 [05](./05-H264-MP4-NALU.md) §5.4）

- **NAL header 2 字节**，`type = (byte>>1) & 0x3F`——直接把 H.264 的 `byte & 0x1F` 搬过来会全错（经典迁移 bug）。
- **多一层 VPS（Video Parameter Set）**：参数集变成 VPS + SPS + PPS。补齐逻辑必须带上 VPS，否则部分解码器解不出。对应的起始码工具是 `hevc_mp4toannexb`。

### 5.7 Profile

- **Main**（8bit 4:2:0）、**Main 10**（10bit——**HDR 的基础**）、Main Still Picture（单张图，即 HEIF/HEIC 照片的底层）。注意：iPhone 拍的 `.heic` 照片、`.mov` 视频默认就是 HEVC。

## 六、H.264 vs H.265 全面对比

| 维度 | H.264 / AVC | H.265 / HEVC |
|---|---|---|
| 发布 | 2003 | 2013 |
| 基本块 | 宏块 16×16 | CTU ≤64×64，四叉树 CU/PU/TU |
| 帧内预测方向 | 9 | 35 |
| 熵编码 | CAVLC / CABAC | 仅 CABAC |
| 环路滤波 | Deblocking | Deblocking + SAO |
| 并行 | Slice | Slice + **Tiles + WPP** |
| NAL header | 1 字节 | 2 字节 |
| 参数集 | SPS/PPS | **VPS** + SPS/PPS |
| 压缩率 | 基准 | **省约 50% 码率** |
| 编码复杂度 | 基准 | **~2× 以上**（更慢更耗电） |
| 10bit/HDR | High 10（少用） | **Main 10（主流 HDR 路径）** |
| 浏览器支持 | ✅ 几乎全部 | ⚠️ 受限（Safari 较好，Chrome 需硬件/条件） |
| 专利授权 | 相对清晰（MPEG LA 为主） | **碎片化、混乱**（多个专利池） |
| 典型出口 | 直播/WebRTC/网页/老设备 | 4K/HDR/苹果生态/监控长存 |

## 七、使用场景与选型（大局观）

### 7.1 什么时候用 H.264

- **兼容性优先**：要覆盖所有浏览器、老手机、各种播放器——H.264 是最大公约数。
- **实时低延迟**：WebRTC、视频会议、直播——硬件编解码成熟、延迟可控（用 Constrained Baseline/无 B 帧）。
- **算力/功耗受限**：老设备、低端芯片编 H.265 吃力。

### 7.2 什么时候用 H.265

- **4K / 8K / HDR**：Main 10 是 HDR 的基础路径。
- **存储 / 带宽敏感**：监控录像 7×24 长期存储、OTT 高清点播——省一半码率就是省一半存储/CDN 成本。
- **苹果生态**：iPhone 录制、HEIC 照片默认 HEVC，Apple 设备硬件支持好。

### 7.3 绕不开的坑：H.265 的专利授权（高频产业题）

H.265 省 50% 码率却**普及没想象中快**，核心不是技术，是**钱**：H.264 的专利主要由 MPEG LA 一家打包、规则清晰；而 **H.265 的专利分散在多个专利池（MPEG LA / Access Advance / Velos）和池外持有者**，授权费高、规则不清、谁都不敢轻易用。

这个"授权地狱"直接催生了 **AV1**（AOMedia 开放媒体联盟：Google、Netflix、Amazon、微软、苹果…联合推出，**免专利费**，压缩率对标甚至略超 H.265）。所以：

- **YouTube / Netflix 大力推 VP9 / AV1**（自家分发、省授权费 + 省带宽）。
- **H.265 在受控环境更香**（苹果生态、监控、广电——设备和授权可控）。
- 面试聊"H.265 为什么普及慢""AV1 是什么"——答案核心就是**专利授权 + 开放联盟的反制**。

### 7.4 一句话选型

> **要兼容/实时/省电 → H.264；要 4K-HDR/省存储且环境可控 → H.265；要彻底免授权费且能接受编码慢 → AV1。**

## 八、常见坑与误区（必看）

| 误区 / 坑 | 真相 |
|---|---|
| "I 帧就是一张 JPEG" | I 帧用**帧内预测**（相邻像素外推 + 残差），比 JPEG 独立编码高效得多 |
| "IDR 帧 = I 帧" | IDR 是特殊 I 帧，**强制清空参考缓冲**；普通 I 帧后面的帧仍可能参考它之前的帧。seek 只能跳 IDR |
| "Profile 决定分辨率" | 决定分辨率/帧率上限的是 **Level**；Profile 决定**算法复杂度**（能不能用 B 帧/CABAC） |
| "Level 4.0 不含 B 帧" | Level 与 B 帧无关，用不用 B 帧由 Profile 决定 |
| "H.265 一定比 H.264 好，应该都用它" | H.265 编码更慢更耗电、浏览器支持受限、**专利授权混乱**——实时/兼容场景 H.264 仍是首选 |
| 把 H.264 的 `getNaluType = byte & 0x1F` 用到 H.265 | H.265 NAL header **2 字节**，`type = (byte>>1) & 0x3F`，搬过去全错 |
| "H.265 也只有 SPS/PPS" | H.265 **多一层 VPS**，参数集补齐必须带上，否则解不出 |
| "CRF 23 在 H.264 和 H.265 画质一样" | CRF 不跨编码器可比：H.264 默认 CRF 23，**H.265 默认 28**（压缩更狠，同数值更糊） |
| "选了 H.265 就能放网页" | 浏览器对 H.265 支持有限（Safari 较好，Chrome 要硬件/特定条件）；网页通用还得 H.264 / VP9 / AV1 |
| "硬件都支持 H.265" | 硬件支持参差——老芯片、部分低端设备只有 H.264 硬解；编码前要做能力查询 + 软解兜底（见 [10](./10-移动端硬件编解码.md)） |
| "H.265 = HEVC 是两个东西" | 同一个标准两个名字（ITU-T H.265 = MPEG-H HEVC） |
