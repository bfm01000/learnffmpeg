## 一、移动端为什么"必须"硬件编解码

桌面上软编（x264）和硬编（NVENC）是一道选择题——追极致画质用软编，追吞吐用硬编。**手机上基本不是选择题**：

- **功耗 / 发热**：手机录 4K、视频通话，软编会让 CPU 满载、迅速发烫、掉电飞快、还会被系统降频。硬编走专用芯片（SoC 里的 Video Engine / VPU），同样的活儿功耗低一个数量级。
- **续航与体验**：用户不会接受"开个视频会议手机就烫得拿不住、半小时掉 40% 电"。
- **算力天花板**：手机 CPU 软编 1080p60 或 4K 已经吃力，硬编轻松。

所以移动端的默认答案就是硬件编解码。问题不是"要不要用"，而是"怎么正确地用、怎么绕开各家芯片的坑"。

一句话定调：**桌面硬编是优化项，移动硬编是必选项。**

## 二、两端总览：一张表先建立地图

| 维度 | Android | iOS / iPadOS |
|---|---|---|
| 系统 API | `MediaCodec`（Java/Kotlin）/ `AMediaCodec`（NDK C API） | `VideoToolbox`（C，CoreFoundation 风格） |
| 底层通路 | App → MediaCodec → OMX / Codec2 HAL → 厂商芯片 | App → VideoToolbox → 苹果 Media Engine |
| 编码会话对象 | `MediaCodec`（configure 成 encoder） | `VTCompressionSession` |
| 解码会话对象 | `MediaCodec`（configure 成 decoder） | `VTDecompressionSession` |
| 零拷贝输出载体 | `Surface` / `SurfaceTexture`（→ GL OES 纹理） | `CVPixelBuffer`（IOSurface 后端，→ Metal） |
| CPU 可读输出 | `ByteBuffer`（颜色格式因厂商而异，坑多） | `CVPixelBuffer` 锁基址后可读 |
| 比特流格式 | 喂入 / 吐出基本是 **Annex-B**（带起始码） | 吐出 / 喂入是 **AVCC**（长度前缀） |
| 碎片化程度 | 高（不同 SoC 行为差异大） | 低（苹果自家芯片，统一） |
| FFmpeg 支持 | **只有解码** wrapper（`h264_mediacodec` 等），**无编码** wrapper | 编 + 解都有（`h264_videotoolbox`） |

这张表是本篇的骨架。下面分别展开 Android 和 iOS，最后回到和 FFmpeg / WebRTC 的关系。

## 三、Android：MediaCodec

### 3.1 它到底是什么

`MediaCodec` 是 Android 暴露给 App 的统一编解码 API。它本身不做编码——它是一个**门面**，底层通过 OMX（老）或 Codec2（新，Android 10+）HAL 把活儿派给 SoC 里高通 / 联发科 / 三星各自的硬件编解码单元。

两套入口：

- **Java / Kotlin**：`android.media.MediaCodec`，绝大多数 App 用这个。
- **NDK / C**：`AMediaCodec`（`media/NdkMediaCodec.h`），C/C++ 工程（包括很多跨平台播放器、WebRTC native）走这条。

### 3.2 核心：输入 / 输出缓冲区队列模型

MediaCodec 的心智模型是**两条缓冲区队列**——你把待处理数据塞进输入队列，从输出队列把处理完的数据拿出来。一定要建立这个"队列"的直觉，否则后面全是迷糊。

```
                 +---------------------+
   待编码/解码 -> | input buffer queue  | -> [硬件编解码芯片] ->
                 +---------------------+                       |
                                                               v
   已编码/解码 <- | output buffer queue |  <--------------------+
                 +---------------------+
```

两种驱动方式：

**同步模式（经典，好理解）**：

```java
// 1. 要一个空的输入缓冲区
int inputBufferIndex = codec.dequeueInputBuffer(timeoutUs);
if (inputBufferIndex >= 0) {
    ByteBuffer inputBuffer = codec.getInputBuffer(inputBufferIndex);
    inputBuffer.put(encodedData);              // 填入一个 NALU / 一帧待编码 YUV
    codec.queueInputBuffer(inputBufferIndex, 0, size, presentationTimeUs, flags);
}

// 2. 取一个处理好的输出缓冲区
MediaCodec.BufferInfo bufferInfo = new MediaCodec.BufferInfo();
int outputBufferIndex = codec.dequeueOutputBuffer(bufferInfo, timeoutUs);
if (outputBufferIndex >= 0) {
    ByteBuffer outputBuffer = codec.getOutputBuffer(outputBufferIndex);
    // ... 消费数据（渲染 / 写文件 / 发网络）...
    codec.releaseOutputBuffer(outputBufferIndex, render);  // 用完必须还回去
}
```

**异步模式（推荐，无忙等）**：注册回调，缓冲区可用时系统通知你。

```java
codec.setCallback(new MediaCodec.Callback() {
    @Override public void onInputBufferAvailable(MediaCodec codec, int index) { /* 填数据 */ }
    @Override public void onOutputBufferAvailable(MediaCodec codec, int index, BufferInfo info) { /* 取数据 */ }
    @Override public void onOutputFormatChanged(MediaCodec codec, MediaFormat format) { /* 格式确定 */ }
    @Override public void onError(MediaCodec codec, CodecException e) { /* 处理错误 */ }
});
```

**记住一条铁律**：每个 output buffer 用完**必须** `releaseOutputBuffer` 还回去，否则队列很快耗尽、编解码卡死。这和 [01-数据结构与生命周期.md](./01-数据结构与生命周期.md) 里 AVFrame 的引用计数是同一个"借了要还"的世界观。

### 3.3 CSD：SPS / PPS 怎么喂进去

解码前必须先把 **SPS / PPS** 交给解码器，否则解码器不知道分辨率、profile 等参数。MediaCodec 里这叫 **CSD（Codec-Specific Data）**：

```java
MediaFormat format = MediaFormat.createVideoFormat("video/avc", width, height);
format.setByteBuffer("csd-0", spsByteBuffer);   // H.264: csd-0 = SPS
format.setByteBuffer("csd-1", ppsByteBuffer);   // H.264: csd-1 = PPS
codec.configure(format, surface, null, 0);
```

> 直接关联 [05-H264-MP4-NALU.md](./05-H264-MP4-NALU.md) 第 6 节"SPS / PPS 补齐"：如果你是从 RTP / Annex-B 流里拿数据，SPS/PPS 是带 `00 00 00 01` 起始码的 NALU，要先拆出来填 csd；编码器吐出的第一帧（带 `BUFFER_FLAG_CODEC_CONFIG`）也是 SPS/PPS，要单独存好用于后续解码端补齐。

### 3.4 颜色格式：Android 版的"花屏之源"

这是 Android 硬解最大的坑，本质是 [02-像素格式与内存布局.md](./02-像素格式与内存布局.md) 里所有问题在手机上的放大版。

`ByteBuffer` 模式下，输出的 YUV 颜色格式**因芯片而异**：

| COLOR_Format 常量 | 实际布局 | 备注 |
|---|---|---|
| `COLOR_FormatYUV420Planar` | I420（YUV 三平面） | 部分芯片 |
| `COLOR_FormatYUV420SemiPlanar` | NV12 类（Y + UV 交织） | 高通常见 |
| `COLOR_FormatYUV420Flexible` | 运行时查询实际布局 | API 21+ 推荐，用 `Image` 类按 plane 读 |
| 厂商私有格式 | 各种对齐 / tiled 排布 | 最坑，可能根本不该当连续 YUV 读 |

两个必须警惕的点：

1. **stride / slice-height ≠ width / height**。和桌面 `linesize` 一个道理——每行有对齐填充（常对齐到 16 或更大），按 width 紧凑拷贝必然花屏 / 错位。要从 `MediaFormat` 读 `stride` 和 `slice-height`，或用 `Image`（`getOutputImage`）按 plane 的 `rowStride` / `pixelStride` 读。
2. **私有 tiled 格式不能当线性 YUV memcpy**。某些高通芯片输出的是为了硬件效率做的 tiled 排布，强行按 NV12 读会得到马赛克。

**最佳实践**：能用 Surface 输出就别用 ByteBuffer——把颜色格式的麻烦整个甩给系统（见下一节）。只有当你确实需要 CPU 拿到像素（算法分析、截图）时才用 ByteBuffer，并且老老实实用 `Image` + `rowStride` 读。

> **NDK / C 侧拿像素：`AImageReader`**。如果你走的是 `AMediaCodec`（C API，很多跨平台播放器、libwebrtc native 都是），CPU 侧取帧的标准路径是把解码输出接到一个 `AImageReader` 的 Surface，再从它拿 `AImage` 按 plane 的 `rowStride` 读——等价于 Java 的 `Image`，但全程在 NDK。
>
> **HDR / 10bit 钩子**：上面都是 8bit YUV。手机录制/播放 HDR（HEVC/AV1 + HLG/HDR10）时颜色格式是 **10bit**，对应 `COLOR_FormatYUVP010`（P010，10bit 版 NV12），还要透传 HDR metadata（色域 BT.2020 + 传输函数 PQ/HLG）。概念见 [02-像素格式与内存布局.md](./02-像素格式与内存布局.md) §5.6。本篇不深入,先知道移动端颜色格式不止 8bit。

### 3.5 Surface 模式：零拷贝渲染的正道

`MediaCodec` 可以直接把解码结果输出到一个 `Surface`，数据**全程不下到 CPU 内存**——直接进 GPU，给 `SurfaceView` 显示，或挂到 `SurfaceTexture` 变成一张 OpenGL ES 的 OES 外部纹理做后处理。

```java
codec.configure(format, surface, null, 0);   // 第二个参数传 Surface
// 解码后:
codec.releaseOutputBuffer(outputBufferIndex, true);  // 第二参 true = 渲染到 Surface
```

这就是 07 里讲的"全程在 GPU 上处理"在 Android 上的落地形态：

```
解码 -> (硬件表面, 不下 CPU) -> SurfaceTexture -> OES 纹理 -> GL 后处理/渲染
```

编码方向同理：相机 / GL 渲染的画面通过 `MediaCodec.createInputSurface()` 拿到一个输入 Surface，直接把 GPU 纹理喂给编码器，省掉 YUV 回读 CPU 这一大笔开销。**这是移动端高性能采集编码的标准姿势**（相机 → GL → 编码器输入 Surface → H.264）。

### 3.6 编码器关键参数

把 MediaCodec configure 成 encoder 时的常用 MediaFormat key：

```java
MediaFormat format = MediaFormat.createVideoFormat("video/avc", width, height);
format.setInteger(MediaFormat.KEY_BIT_RATE, 4_000_000);          // 目标码率
format.setInteger(MediaFormat.KEY_FRAME_RATE, 30);
format.setInteger(MediaFormat.KEY_I_FRAME_INTERVAL, 2);          // 关键帧间隔(秒) -> GOP
format.setInteger(MediaFormat.KEY_BITRATE_MODE,
        MediaCodecInfo.EncoderCapabilities.BITRATE_MODE_CBR);    // CBR / VBR / CQ
format.setInteger(MediaFormat.KEY_COLOR_FORMAT,
        MediaCodecInfo.CodecCapabilities.COLOR_FormatSurface);   // 用输入 Surface
// 低延迟(API 30+):
format.setInteger(MediaFormat.KEY_LOW_LATENCY, 1);
```

这些 key 是 [06-编码参数与码控.md](./06-编码参数与码控.md) 里 GOP / CBR / VBR / 低延迟概念在 Android 上的具体旋钮。注意硬编**可调参数远少于 x264**——厂商只暴露这些，没有 x264 那样的 `-preset veryslow` / 精细 me 搜索。

### 3.7 运行时动态调码率 / 请求关键帧（WebRTC 必用）

编码器一旦 configure 完，码率和关键帧不是只能在初始化时定死——**运行中可以动态改**，这正是 WebRTC 拥塞控制和丢包恢复要的旋钮（见 [08-网络协议与流媒体.md](./08-网络协议与流媒体.md) §十的 GCC / PLI-FIR）。Android 用 `MediaCodec.setParameters`：

```java
// 拥塞控制要降码率: 动态改目标码率
Bundle bitrateUpdate = new Bundle();
bitrateUpdate.putInt(MediaCodec.PARAMETER_KEY_VIDEO_BITRATE, newBitrate);
codec.setParameters(bitrateUpdate);

// 对端发来 PLI/FIR 请求关键帧: 让编码器立刻产一个 IDR
Bundle requestKeyFrame = new Bundle();
requestKeyFrame.putInt(MediaCodec.PARAMETER_KEY_REQUEST_SYNC_FRAME, 0);
codec.setParameters(requestKeyFrame);
```

iOS 侧对应物见 §4.2 末尾的 `kVTEncodeFrameOptionKey_ForceKeyFrame`。**没有这两个旋钮，WebRTC 在弱网下既不能自适应降码率、也不能在花屏后快速恢复**——所以它们是移动端 RTC 最实际的接口。

## 四、iOS / macOS：VideoToolbox（实时编码深入）

07 已经讲过 VideoToolbox 的定位和基本对象。这里补强 **iOS 实时编码**这条线——视频通话、直播推流场景。

### 4.1 核心对象与数据载体

| 对象 / 类型 | 作用 |
|---|---|
| `VTCompressionSession` | 编码会话 |
| `VTDecompressionSession` | 解码会话 |
| `CVPixelBuffer` | 一帧未压缩图像（YUV/BGRA），底层是 `IOSurface`，可与 Metal / GL 零拷贝共享 |
| `CMSampleBuffer` | 一帧压缩数据 + 时间戳 + 格式描述的封装 |
| `CMVideoFormatDescription` | 含 SPS/PPS 等参数集 |
| `CVPixelBufferPool` | 复用 CVPixelBuffer 的内存池（避免每帧重新分配） |

`CVPixelBuffer` 是 iOS 上对应"硬件帧"的东西。相机（`AVCaptureSession`）吐出的就是 `CMSampleBuffer` 里包着 `CVPixelBuffer`，可以零拷贝喂给编码器或上传 Metal——这就是 07 里"硬件帧不下 CPU"在 iOS 上的形态。

### 4.2 实时编码的关键属性

视频通话 / 直播要的是**低延迟**，不是最高压缩比。配置 `VTCompressionSession` 时这几个属性决定成败：

```c
// 实时模式: 编码器不为了压缩率做高延迟的多遍处理
VTSessionSetProperty(session, kVTCompressionPropertyKey_RealTime, kCFBooleanTrue);

// 关掉 B 帧: B 帧依赖后续帧 -> 引入重排序延迟, 实时场景必须关
VTSessionSetProperty(session, kVTCompressionPropertyKey_AllowFrameReordering, kCFBooleanFalse);

// Profile / Level
VTSessionSetProperty(session, kVTCompressionPropertyKey_ProfileLevel,
                     kVTProfileLevel_H264_Baseline_AutoLevel);

// 码率与关键帧间隔
VTSessionSetProperty(session, kVTCompressionPropertyKey_AverageBitRate, bitrate);
VTSessionSetProperty(session, kVTCompressionPropertyKey_MaxKeyFrameInterval, gopSize);
```

> `AllowFrameReordering = false` 等价于 [06-编码参数与码控.md](./06-编码参数与码控.md) 里"低延迟就别用 B 帧"那条；`RealTime = true` 是 VideoToolbox 版的 `-tune zerolatency`。

**运行时动态控制**（对应 Android §3.7）：码率可以中途 `VTSessionSetProperty(session, kVTCompressionPropertyKey_AverageBitRate, ...)` 改；对端 PLI/FIR 请求关键帧时，在编码这一帧时传入 frame properties `kVTEncodeFrameOptionKey_ForceKeyFrame = true` 强制产 IDR。这是 iOS 上 WebRTC 自适应降码率 + 丢包恢复的实际旋钮。

### 4.3 比特流格式转换：AVCC ↔ Annex-B（必踩）

**这是 iOS 推流 / WebRTC 最经典的坑**，直接接 [05-H264-MP4-NALU.md](./05-H264-MP4-NALU.md) 第 4 节。

VideoToolbox 编码器吐出的 `CMSampleBuffer` 里，NALU 是 **AVCC 格式**——每个 NALU 前面是 4 字节**长度前缀**，而且 **SPS/PPS 不在数据里，而在 `CMVideoFormatDescription` 里单独存着**。

但 RTP / RTSP / 裸 H.264 流走的是 **Annex-B 格式**——NALU 前面是 `00 00 00 01` 起始码，SPS/PPS 作为普通 NALU 混在流里。

所以 iOS 上推流必做两件事：

1. **长度前缀 → 起始码**：把每个 NALU 前的 4 字节长度，替换成 `00 00 00 01`。
2. **补 SPS/PPS**：从 format description 里用 `CMVideoFormatDescriptionGetH264ParameterSetAtIndex` 取出 SPS、PPS，在每个关键帧前手动插进 Annex-B 流。

解码方向反过来：从 Annex-B 流拆出 SPS/PPS 建 format description，把起始码换成长度前缀喂 `VTDecompressionSession`。

漏了这一步的典型症状：对端**只有声音没有画面**，或**首帧之后全是花屏**（因为没补 SPS/PPS）。

### 4.4 解码与渲染

`VTDecompressionSession` 解出 `CVPixelBuffer`，渲染两条路：

- **`AVSampleBufferDisplayLayer`**：最省事，直接喂 `CMSampleBuffer` 让系统显示。
- **Metal / `CVMetalTextureCache`**：把 `CVPixelBuffer` 零拷贝转成 Metal 纹理，自己做渲染 / 滤镜 / 美颜。

> 零拷贝的两端横向对照（为什么、两个方向、什么时候拷贝偷偷回来）单独拎到下一节 [§四点五](#四点五ios-与-android-的零拷贝核心考点) 讲——这是高频面试题。

## 四点五、iOS 与 Android 的零拷贝（核心考点）

前面 Android 的 §3.5（Surface）和 iOS 的 §4.1 / §4.4（CVPixelBuffer / Metal）各讲了零拷贝的一半。但**零拷贝是移动端音视频性能和功耗的命门，也是高频面试题**，这一节把两端拉到一起、从底层原理讲到踩坑再到面试问法——它考的不是某个 API，而是"你脑子里有没有那条不下 CPU 的数据通路、以及知不知道这条路为什么省"。

### 4.5.1 为什么零拷贝是命门：一次拷贝的代价

先算笔账。一帧 1080p 的 NV12 ≈ 3 MB，30fps 就是 ~90 MB/s，4K 翻 4 倍。这些数据在**相机 ISP / 硬件解码器 / GPU**（产出方）和 **CPU 内存**（如果你非要读它）之间来回搬，每搬一次就吃 CPU、占带宽、耗电发热、加延迟。移动端电池和散热都紧张，所以有铁律：**采集→编码、解码→渲染，全程让数据待在硬件/GPU 侧，不下 CPU**。这就是零拷贝。

> 桌面端（Linux / Windows / macOS）的对应版本——同一思想、不同载体，且独显多了一条真实 PCIe 总线——见 [07-硬件编解码.md](./07-硬件编解码.md) §五点五。

### 4.5.2 两个方向（两端通用的心智模型）

零拷贝永远是这两条链路，先记住方向再记 API：

```
采集 → 编码:   相机 / GL 渲染  ──(硬件共享 buffer)──▶  编码器输入     [不回 CPU]
解码 → 渲染:   硬件解码器      ──(硬件共享 buffer)──▶  屏幕 / GL 纹理  [不下 CPU]
```

两条链路的本质是同一件事：**有一块"生产者和消费者都能直接访问的硬件内存"（GPU 能直接读写）**。两端的差别只是给这块内存起了不同名字、配了不同 API。

### 4.5.3 底层原理：一次"拷贝"到底在拷什么（手机是统一内存，为什么还慢？）

这是面试最能拉开差距的深度题。**手机 SoC 是统一内存架构（UMA）——CPU 和 GPU 共用同一块物理 DRAM**，不像桌面独显要跨 PCIe 总线。那既然物理上就是同一块内存，"拷贝"和"回读"为什么还慢？因为慢的根本不是"搬过总线"，而是下面四件事：

1. **内存排布不一样（tiling / swizzle）**：GPU、硬件编解码器、显示控制器为了缓存命中率，把图像存成**分块（tiled）或厂商私有的扭曲（swizzled）排布**；而 CPU 要的是**线性（linear）逐行排布**。两者之间转换是一次真实的**逐像素重排**——这才是"拷贝"开销的大头，而且常常顺带做颜色格式转换（NV12→RGBA）。这也是 §3.4 说"私有 tiled 格式不能当 NV12 直接读"的根源。
2. **缓存一致性（cache coherency）**：CPU 有多级缓存，GPU / 相机 / 编解码器是各走各内存通路的"外设"。CPU 读 GPU 写过的内存前要 **invalidate** 自己的缓存，写完给硬件用前要 **flush**。分配时还要选 cached / uncached（Android 的 ION/dma-buf、iOS 的 IOSurface 都有这个概念），选错要么慢要么读到脏数据。
3. **同步等待（最致命）**：GPU / 编解码器是**异步流水线**——你提交的活儿排在队列里，还没真正画完。CPU 想读它的输出，必须插一个 **fence（栅栏）等它真正完成**。这一等就 **stall 几毫秒**，把整条流水线打断、帧率掉下来。`glReadPixels` 慢的主因就是这个 stall，不是搬字节本身。
4. **颜色格式 / range 转换搭车**：上面的重排往往顺手把 YUV↔RGB、Limited↔Full Range 一起做了（见 [02-像素格式与内存布局.md](./02-像素格式与内存布局.md) §5）。

所以**零拷贝的本质 = 让生产者和消费者直接读写同一块、布局双方都认的硬件内存，并用 fence 做异步同步，而不是把数据重排成 CPU 线性格式 + 阻塞等待**。理解了这四点，下面所有 API 都只是它的不同包装。

### 4.5.4 共享内存的内核底座：dma-buf / gralloc（Android）vs IOSurface（iOS）

零拷贝要成立，先得有一块"多方都能直接访问"的内存。两端各自的内核底座：

**Android — dma-buf + gralloc：**

- 内核里的 **dma-buf** 是**跨驱动共享内存的统一机制**：一块内存用一个文件描述符（fd）表示，可以在相机驱动、GPU 驱动、编解码驱动、显示驱动之间传递而**不拷贝**。底层分配器历史上是 **ION**，Android 12+ 改为 **dma-buf heaps**。
- **gralloc** HAL 负责按"谁要用"分配合适布局的图形 buffer（`GraphicBuffer`），NDK 暴露成 **`AHardwareBuffer`**，可 import 成 EGLImage（GL）/ VkImage（Vulkan）。
- **关键：分配时的 usage flags 决定布局、决定能不能零拷贝**。你得声明这块 buffer 要给「GPU 采样 + 编码器 + 显示」哪几方用，gralloc 才会挑一个三方都能直接吃的格式。声明不全 → 某一方用不了 → 退化成拷贝甚至失败。

**iOS — IOSurface：**

- **IOSurface** 是内核管理的、**引用计数的、可跨进程共享**的图形 buffer。`CVPixelBuffer` 只是它的上层包装。
- 一块 IOSurface 能**同时**被：相机 ISP 写、VideoToolbox 读写、Metal 当纹理采样、Core Image 处理——全程**一份内存、一份所有权计数**。iOS 这块比 Android 统一、省心得多（苹果自家全栈）。

### 4.5.5 Android 零拷贝全链路：BufferQueue + fence + 外部纹理

- **BufferQueue 生产者/消费者模型**：`Surface` 是生产者端（`dequeueBuffer` → 填 → `queueBuffer`）；消费者（SurfaceFlinger 显示 / SurfaceTexture 给 GL / MediaCodec）`acquireBuffer` → 用 → `releaseBuffer`。buffer 在两端之间轮转（通常 3 个以上，triple buffering）。
- **fence 怎么做到不阻塞 CPU**：buffer 随带 **acquire fence**（消费者读前等它＝生产真正完成）和 **release fence**（生产者复用前等它＝消费真正完成）。等待发生在 GPU/硬件侧，**CPU 不阻塞**——这是异步零拷贝的精髓，正好对治 §4.5.3 的第 3 点。
- **解码→渲染**：MediaCodec 输出 Surface → 若是 `SurfaceView` 直接上屏；要后处理就接 `SurfaceTexture` → GL 的 **`GL_TEXTURE_EXTERNAL_OES`** 外部纹理。
- **OES 外部纹理两个必踩点**：
  1. shader 里必须用 **`samplerExternalOES`**（带 `#extension GL_OES_EGL_image_external : require`），普通 `sampler2D` 采不了；YUV→RGB 由驱动在采样时内部完成。
  2. **`SurfaceTexture.getTransformMatrix()` 返回的 4×4 矩阵必须乘到纹理坐标上**，否则画面上下颠倒 / 裁剪错位（它编码了 crop、旋转、原点翻转）。且 `updateTexImage()` 必须在持有 EGL context 的那个 GL 线程调用。
- **采集→编码**：`MediaCodec.createInputSurface()` 给一个输入 Surface，把相机预览 / GL 渲染结果画进去，编码器直接吃 GPU 纹理。

### 4.5.6 iOS 零拷贝全链路：IOSurface + CVMetalTextureCache

- **采集**：`AVCaptureVideoDataOutput` 把 `kCVPixelBufferPixelFormatTypeKey` 设成 `kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange`（NV12），吐出 IOSurface-backed 的 `CVPixelBuffer`。
- **编码**：直接喂 `VTCompressionSession`，它内部的 pool 也是 IOSurface-backed。
- **解码→渲染**：`VTDecompressionSession` 出 `CVPixelBuffer` →
  - 最省事：`AVSampleBufferDisplayLayer` 直接 enqueue `CMSampleBuffer`。
  - 自定义渲染：`CVMetalTextureCacheCreateTextureFromImage` 把 `CVPixelBuffer` 的**每个平面**包成一张 `MTLTexture`（**aliasing 同一块 IOSurface，零拷贝**）：NV12 = 平面 0 亮度（`r8Unorm`）+ 平面 1 色度（`rg8Unorm`），在 Metal shader 里采样两张纹理做 YUV→RGB。
- **必带的 key**：建 pool / pixel buffer 时要带 `kCVPixelBufferIOSurfacePropertiesKey`（拿到 IOSurface 后端）和 `kCVPixelBufferMetalCompatibilityKey`（能直接给 Metal）。漏了就退化成普通内存、零拷贝失效。

### 4.5.7 渲染时的 YUV→RGB 也在 GPU 上做（零拷贝的"出口"）

容易忽略的一环：解码出的是 **YUV（NV12）**，屏幕要 **RGB**。**别用 `sws_scale` 在 CPU 上转**——那等于把帧拉回 CPU，前面的零拷贝全白做。正确做法是把 YUV 平面当纹理（Android OES 外部纹理由驱动内部转；iOS 双平面纹理），**在 fragment shader 里乘 BT.601/709 矩阵做 YUV→RGB**（矩阵选择见 [02](./02-像素格式与内存布局.md) §5 / [03](./03-SwsContext-图像缩放与格式转换.md) §七点五）。缩放、旋转、镜像、美颜也都在 GPU（shader / Metal）上做。一句话：**不是"不处理"，是"处理也在 GPU 上，数据始终不下 CPU"**。

### 4.5.8 两端对照表

| 维度 | Android | iOS |
|---|---|---|
| 内核共享内存底座 | dma-buf（旧 ION）+ gralloc | `IOSurface` |
| 图形 buffer / 上层句柄 | `GraphicBuffer` / `AHardwareBuffer`；`Surface` / `SurfaceTexture` | `CVPixelBuffer`（IOSurface 后端） |
| 异步同步机制 | acquire / release fence（随 BufferQueue 流转） | IOSurface 用 / 锁状态 + Metal/VT 内部同步 |
| 采集→编码入口 | `createInputSurface()`（相机/GL 渲染进去） | `VTCompressionSession` 直接吃 `CVPixelBuffer` |
| 解码→渲染 | Surface 显示 / SurfaceTexture→OES 纹理 | `AVSampleBufferDisplayLayer` / `CVMetalTextureCache` |
| YUV→RGB | OES 外部纹理（驱动内部转）或 shader | 双平面纹理 + Metal shader |
| 包成 GPU 纹理 | `SurfaceTexture` → GL OES 外部纹理 | `CVMetalTextureCache` → Metal 纹理 |
| NDK / C 层 | `AHardwareBuffer` | `IOSurface` + `CVPixelBuffer`（本就是 C API） |
| 零拷贝失效开关 | 改用 `ByteBuffer` 模式 / usage flags 不全 | 漏 IOSurface/Metal compatibility key / 锁基址读 |

### 4.5.9 常见的坑（症状 → 根因 → 怎么修）

| 症状 | 根因 | 怎么修 |
|---|---|---|
| 帧率掉、CPU 飙高、发烫 | 用了 `ByteBuffer` 模式，数据下到了 CPU（还撞颜色格式/stride，见 §3.4） | 改 Surface 输出 / 输入路径，全程走纹理 |
| 取一帧像素就卡顿一下 | `glReadPixels` / 纹理回读触发 GPU stall（§4.5.3 第 3 点） | 避免回读；必须读就用 PBO 异步、或干脆把处理搬到 GPU |
| iOS 渲染卡、CPU 高 | `CVPixelBufferLockBaseAddress` 在热路径锁了像素，触发 detile + 同步 | 别锁；只读时加 `kCVPixelBufferLock_ReadOnly`，且尽量挪出热路径 |
| iOS 自定义渲染拿不到纹理/退化 | 建 pool 漏了 `IOSurfaceProperties` / `MetalCompatibility` key | 建 `CVPixelBufferPool` 时补上这两个 key |
| Android 画面上下颠倒 / 裁剪错位 | 没把 `SurfaceTexture.getTransformMatrix()` 乘到纹理坐标 | 取矩阵乘到 texcoord；`updateTexImage` 放 GL 线程 |
| OES 采样全黑 / shader 编译失败 | 用了 `sampler2D` 而非 `samplerExternalOES` | 换 `samplerExternalOES` + 声明 `GL_OES_EGL_image_external` |
| gralloc 分配失败 / 某消费者用不了 | usage flags 没声明全（漏了 GPU 采样 / 编码 / 显示某一项） | 按真实消费者补齐 usage flags |
| 相机/编码器突然掉帧、卡住 | **buffer pool 耗尽**——持有 buffer 不释放（攒 `CVPixelBuffer` / 忘 `releaseOutputBuffer`） | 用完立刻释放/归还，别跨多帧持有 |
| 切后台回来花屏/崩 | 用了已 release 的 Surface / VT session 丢失（见 §七陷阱表） | 重建会话 + 重发 SPS/PPS / 关键帧 |
| HDR/10bit 走零拷贝失败 | 没按 10bit 格式（P010）协商纹理/buffer | 用 P010 + 对应纹理格式，透传 HDR metadata（见 §3.4） |

> 跨进程补充：Android 可用 `SurfaceControl` / 传 dma-buf fd 在进程间共享；iOS 的 IOSurface 本就跨进程。WebRTC 若把采集/编码放独立进程要走这条，否则进程边界处又会退化成拷贝。

### 4.5.10 和 WebRTC 的衔接

libwebrtc 移动端的**采集→编码**和**解码→渲染**就是这两条零拷贝链：它的 `VideoFrame` 内部在 Android 包着 `SurfaceTextureHelper` 产出的 OES 纹理 buffer、在 iOS 包着 `RTCCVPixelBuffer`（即 `CVPixelBuffer`）。所以移动端 WebRTC 的功耗/性能问题，**十有八九是某一环不小心把帧下到了 CPU**（最常见：插了个 CPU 美颜、或用了软件 scale）。排查思路就是沿着这条链找"哪一步 lock / readback / transfer 了"。详见 [08-网络协议与流媒体.md](./08-网络协议与流媒体.md) §十。

### 4.5.11 面试常问（带答题要点）

- **Q：什么是零拷贝？移动端为什么必须？**
  采集到编码、解码到渲染全程不把像素下到 CPU。必须是因为帧数据大（1080p30 ~90MB/s）、每次拷贝吃 CPU/带宽/电/延迟，移动端续航和散热扛不住。

- **Q（深度·拉分题）：手机 CPU 和 GPU 共用同一块物理内存（UMA），那拷贝/回读为什么还慢？**
  慢的不是"搬过总线"，而是三件事：① tiling/swizzle 排布与 CPU 线性排布之间要逐像素重排（常搭车做颜色转换）；② CPU 与 GPU 缓存不一致，要 flush/invalidate；③ 最致命的是 GPU 异步流水线，CPU 读输出要插 fence 等它画完，stall 几毫秒打断流水线。

- **Q：Android 解码怎么做到零拷贝渲染？Surface 底层是什么？**
  MediaCodec 配 Surface 输出，`releaseOutputBuffer(idx, true)` 直接进 Surface。Surface 是 BufferQueue 的生产者端，底层是 gralloc 分配、dma-buf 共享的图形 buffer；要后处理就用 SurfaceTexture 变成 OES 外部纹理。

- **Q：dma-buf、gralloc、AHardwareBuffer 三者什么关系？**
  dma-buf 是内核跨驱动共享内存的机制（一块内存一个 fd，相机/GPU/编解码/显示都能直接用）；gralloc 是按 usage flags 分配图形 buffer 的 HAL；AHardwareBuffer 是 NDK 对图形 buffer 的 C 层封装，可导入 EGL/Vulkan。

- **Q：iOS 的 CVPixelBuffer 和 IOSurface 是什么关系？怎么零拷贝给 Metal？**
  CVPixelBuffer 的后端就是 IOSurface（内核共享、可跨进程）。用 CVMetalTextureCache 把每个平面 alias 成 MTLTexture（NV12 = 亮度 r8 + 色度 rg8），shader 里做 YUV→RGB，全程同一块内存。

- **Q：`glReadPixels` 为什么慢？fence 是什么？**
  它要等 GPU 把活儿干完才能读（同步点），打断异步流水线产生 stall。fence 是 GPU 命令流里的栅栏，标记"到这里的活儿完成了"，让等待发生在硬件侧而不是 CPU 死等。

- **Q：YUV 怎么在 GPU 上零拷贝渲染，而不用 sws_scale？**
  把 YUV 平面当纹理上传（Android OES 外部纹理 / iOS 双平面纹理），在 fragment shader 里乘 BT.601/709 矩阵做 YUV→RGB。sws_scale 是 CPU 的，用了就等于把帧拉回 CPU。

- **Q：要做美颜 / AI 推理，需要像素数据，怎么兼顾零拷贝？**
  尽量把处理也放 GPU：美颜用 shader/Metal 在纹理上做；推理用 GPU 委托（Android NNAPI/GPU delegate、iOS Core ML/Metal）直接吃纹理或 IOSurface。实在要 CPU，才在那一处做受控的下载，且别每帧都下。

- **Q：哪些操作会"偷偷"打断零拷贝？**
  Android ByteBuffer 模式、`glReadPixels`/纹理回读、iOS `CVPixelBufferLockBaseAddress`、FFmpeg `av_hwframe_transfer_data`、CPU 软件 scale/美颜。判据：任何"我要在 CPU 上拿到像素"的操作。

- **Q：buffer pool 耗尽会怎样？**
  持有 buffer 不释放（攒 CVPixelBuffer / 忘 releaseOutputBuffer），生产者拿不到空 buffer，相机/编码器 stall、掉帧。所以用完立刻归还。

## 五、FFmpeg 在移动端的支持边界（重点：别踩空）

很多人以为"FFmpeg 跨平台，硬件加速也一样跨"——**移动端不是这样**，两端支持是不对称的，搞错会浪费很多时间：

| | 解码 | 编码 |
|---|---|---|
| **iOS / macOS** | ✅ hwaccel `-hwaccel videotoolbox`（无命名解码器） | ✅ 编码器 `h264_videotoolbox` / `hevc_videotoolbox`（成熟） |
| **Android** | ✅ `h264_mediacodec` / `hevc_mediacodec` / `vp8/vp9/av1_mediacodec` | ⚠️ `h264_mediacodec` / `hevc_mediacodec` 编码器（**FFmpeg 6.0+**）存在但能力受限、有设备/API 限制，生产多直调系统 API |

关键结论：

- **iOS**：FFmpeg 编（命名编码器）+ 解（hwaccel）都能用 VideoToolbox，最省心。
- **Android 解码**：FFmpeg 的 `h264_mediacodec` 能用，但要在编译时启用、运行时正确建 `AVMediaCodecContext` 并关联一个 Surface（否则可能回落到软解或拿不到硬件帧）。
- **Android 编码**：FFmpeg 6.0 起有了 `h264_mediacodec` 编码器，但**很弱**（能力/可控性远不及直调、有 API level 与设备限制）。Android 硬编实务两条路：
  1. **直接调 MediaCodec / AMediaCodec**（主流做法，可控性最强，本篇第三章那套）。
  2. 用 FFmpeg 的软编 `libx264`——但前面说了，手机软编功耗 / 发热不可接受，仅限离线 / 低分辨率。

所以移动端的现实架构常是**混合**的：用 FFmpeg 做 demux / mux / 协议 / 音频重采样（它的强项），视频硬编解则直接调系统 API（MediaCodec / VideoToolbox），而不是指望 FFmpeg 一把梭。

## 六、和你 WebRTC 项目的衔接（这才是你补这块的真正动机）

你在并行学 WebRTC（见 [[project_webrtc_learning]]）。移动端硬编解正是 WebRTC 跑在手机上的视频底座：

- **libwebrtc 原生**就是用 **VideoToolbox（iOS）/ MediaCodec（Android）** 做 H.264 / VP8 / VP9 的硬件编解码——通过 `VideoEncoderFactory` / `VideoDecoderFactory` 注入平台实现。你在 WebRTC 里看到的 iOS H264 编码器，底下就是第四章那套 `VTCompressionSession`。
- **第 4.3 节的 AVCC→Annex-B 转换**：WebRTC 的 RTP 打包要的是 Annex-B，所以 iOS WebRTC 必然做这个转换。这就是为什么你在 WebRTC iOS 代码里会看到 SPS/PPS 提取和起始码替换。
- **低延迟配置**（实时模式、关 B 帧、CBR、短 GOP / 按需 IDR）：WebRTC 拥塞控制会动态调码率、要关键帧时调编码器立即出 IDR——对应第 3.6 / 4.2 节的码控旋钮。
- **零拷贝采集链**（相机 → GPU → 编码器输入 Surface / CVPixelBuffer）：WebRTC 移动端为了低功耗，采集到编码全程不下 CPU——两端的完整对照见 [§四点五](#四点五ios-与-android-的零拷贝核心考点)。

一句话：**WebRTC 移动端视频性能问题，十有八九落在这一篇覆盖的硬编解 + 比特流格式 + 零拷贝链路上。** 补强这块，等于给 WebRTC 项目打地基。

## 七、移动端特有陷阱清单

| 陷阱 | 真相 / 对策 |
|---|---|
| Android `ByteBuffer` 按 width 紧凑拷贝 | 必须用 `stride` / `slice-height`，或用 `Image` 按 `rowStride` 读，否则花屏（见 3.4） |
| 把厂商私有 tiled 格式当 NV12 读 | 得到马赛克；能用 Surface 就别碰 ByteBuffer |
| iOS 推流直接发编码器原始输出 | 那是 AVCC，RTP/裸流要 Annex-B，必须转长度前缀→起始码并补 SPS/PPS（见 4.3） |
| 以为 FFmpeg 在 Android 能方便硬编 | 6.0+ 虽有 `h264_mediacodec` 编码器但很弱、生产多直调系统 API（见第五章） |
| output buffer 忘了 release | 队列耗尽，编解码卡死（Android 3.2） |
| 分辨率不对齐（非偶数 / 非 16 倍数） | 很多硬件编码器要求宽高对齐到 2 甚至 16，否则失败或边缘绿边 |
| 假设并发解码实例无限 | 设备硬件解码器实例数有限（常 1~几个），多路播放 / 画中画会 `MediaCodec` 创建失败 |
| App 切后台 / 来电不处理会话 | iOS 后台可能丢失 VT session；Android 配置变更 / 后台可能丢 codec，需重建并重发 SPS/PPS / 关键帧 |
| 编码器不每个关键帧带 SPS/PPS | 部分设备默认只在首帧带；推流要么强制每 IDR 带，要么自己缓存 SPS/PPS 反复补 |
| HEVC / AV1 设备支持参差 | 编码前要 `MediaCodecList` / VT 能力查询，不能假定支持，需软解兜底 |

## 八、学习路径（接 07 的三阶段，落到移动端）

> 前提：先走完 07 的命令行 + FFmpeg HWAccel 阶段，建立硬件帧直觉。

### 阶段 2：iOS VideoToolbox 最简编解码 demo

- 写一个 `VTCompressionSession`：喂 `CVPixelBuffer`（先用纯色 / 生成图像）→ 拿 `CMSampleBuffer` → 做 AVCC→Annex-B 转换 → 写 `.h264` 裸流文件。
- 用 ffmpeg 命令行验证产出的裸流能正常解码播放——**这一步同时验证了你第 4.3 节的格式转换写对没有**。

### 阶段 3：Android MediaCodec 最简编解码 demo

- 解码：`MediaExtractor` 拆 MP4 → 取 csd-0/csd-1 → `MediaCodec` 配 Surface → `releaseOutputBuffer(true)` 直接显示。**先走 Surface 路径**，避开颜色格式坑。
- 编码：相机 / 生成画面 → `createInputSurface()` → H.264 → 写文件。
- 进阶再碰 `ByteBuffer` + `Image` 读 YUV，亲手踩一次 stride 坑。

### 阶段 4：合流回 WebRTC

把上面两端的硬编解理解，对到 libwebrtc 的 `VideoEncoderFactory` / `VideoDecoderFactory` 实现上，看 WebRTC 是怎么封装 VideoToolbox / MediaCodec 并接进 RTP 链路的（见第六章）。
