# 08 - 网络协议与流媒体

> 对应导读第 3.7 节"运输问题"。

## 一、宏观视角：网络世界的物流系统

把网络协议类比成现实物流：

| 协议层 | 类比 |
|---|---|
| IP 协议（网络层） | 导航地图和公路网，负责把数据从 A 城运到 B 城 |
| TCP / UDP（传输层） | 快递公司（顺丰 vs 极兔），决定用什么策略把包裹送到 |
| HTTP / HTTPS（应用层） | 包裹里的货物和包装说明 |

下面分两条线讲：传输层（TCP / UDP）+ 应用层（HTTP / HTTPS / QUIC / 流媒体协议）。

---

## 二、传输层：TCP vs UDP

在音视频里，TCP 还是 UDP 的选择，直接决定产品是"卡成 PPT"还是"丝滑如德芙"。

### 2.1 TCP：严谨的快递员

**人设**：面向连接、可靠、不丢包、顺序保证。

**特点**：

- 发货前先打电话确认你在家（**三次握手**）
- 每个包都要签收回执（**ACK**）
- 包丢了立刻停下手里活，回去重传，直到你收到（**重传机制**）

**基于 TCP 的常见协议**：

| 协议 | 端口 | 用途 |
|---|---|---|
| HTTP | 80 | 明文网页 |
| HTTPS | 443 | 加密网页、API |
| RTMP | 1935 | 直播推流 |
| FTP | 20 / 21 | 文件下载 |
| SMTP | 25 | 发邮件 |
| SSH | 22 | 远程登录 |
| MySQL | 3306 | 数据库连接 |

### 2.2 UDP：发传单小哥

**人设**：无连接、不可靠、尽最大努力交付。

**特点**：

- 不打电话，直接把包裹往院子里扔
- 丢了不管，顺序乱了不管
- **唯一目标：快**

**基于 UDP 的常见协议**：

| 协议 | 端口 | 用途 |
|---|---|---|
| DNS | 53 | 域名解析 |
| DHCP | 67 / 68 | 自动分配 IP |
| WebRTC | 动态（10000-60000） | 实时音视频 |
| QUIC / HTTP/3 | 443 (UDP) | 下一代互联网标准 |
| 大多数竞技游戏的同步协议 | 各家自定义 | 走位、开枪数据 |

## 三、TCP 的致命弱点：队头阻塞

### 3.1 什么是队头阻塞

TCP 为保证顺序，如果包 1、2、3 中**包 2 丢了**，即使包 3 已经到了网卡，TCP 也会**把它扣留在内核缓冲区里**——它必须等包 2 重传成功后，把 2 和 3 一起交给应用层。

**这是物理定律层面的限制**——只要底层是 TCP，就跑不掉。

### 3.2 音视频灾难

弱网环境下这种"强迫症"是灾难性的。哪怕丢了一个不重要的 B 帧，TCP 也会让整个直播画面卡住、缓冲、等待重传。

**重点**：

- **RTMP、HTTP-FLV、HLS 三大传统直播协议底层全部是 TCP**
- 网络差时直播要么卡住转圈圈，要么延迟从 2 秒滚到 10 秒、20 秒
- 这是 TCP 协议本身的限制，**不是任何应用层优化能彻底解决的**

### 3.3 UDP 的逆袭：WebRTC 的基石

UDP 没有队头阻塞——包 3 到了就直接给应用层，包 2 丢了就丢了。

视频会议 / 连麦场景里 **"实时性 >> 完整性"**：丢一帧花屏 0.1 秒观众不在乎，但卡 2 秒等重传观众会骂娘。所以 WebRTC 坚决用 UDP。

为了在 UDP 上保证"适度可靠"，应用层自己造轮子：

- **FEC（前向纠错）**：发 10 个包附带 2 个校验包。丢 1 个直接算回来，不用重传。空间换时间。
- **NACK（选择性重传）**：只重传关键帧（I 帧），不重要的帧丢了算了。
- **拥塞控制**：估计网络容量，动态调整发送速率。

WebRTC 把这些机制全部封装好——这是它的核心价值，不是它用了 UDP 这件事本身。

## 四、应用层：HTTP vs HTTPS

### 4.1 大白话差别

- **HTTP**：明文。像寄明信片，邮递员能看，路由器能改（运营商插广告就是这么干的，叫**流量劫持**）。
- **HTTPS**：加密。像寄密码保险箱。中间人截到也只是乱码。

### 4.2 HTTPS 加密原理（必考）

HTTPS = HTTP + SSL/TLS。它结合两种密码学技术：

**第一阶段：握手（非对称加密）**

```
服务器: 给你我的公钥 + CA 证书
客户端: 生成"会话密钥",用公钥加密发回
服务器: 用私钥解密拿到"会话密钥"
        (中间人就算截到加密的会话密钥也解不开,因为没私钥)
```

非对称加密**极度安全但极度慢**，所以只用来传"会话密钥"这一件小事。

**第二阶段：传输（对称加密）**

握手完成后双方都有了"会话密钥"。后续所有数据用这个密钥对称加密传输。对称加密**速度极快**，适合大数据量。

### 4.3 音视频里的痛点：首屏秒开

直播 / 短视频追求"首屏秒开率"（用户划走视频后新视频要在 100ms 内出画面）。

**HTTPS 是首屏的拦路虎**：

- HTTP：TCP 三次握手 ≈ 1.5 RTT
- HTTPS：TCP 三次握手 + TLS 握手 ≈ 2.5 ~ 3.5 RTT

优化方案：

- **TLS 1.3**：握手降到 1-RTT，甚至 0-RTT（恢复会话时）
- **Session Resumption**：复用之前的会话密钥
- **内部网络剥离 HTTPS**：只在面向用户的"最后一公里"用 HTTPS

## 五、终极进化：QUIC / HTTP/3

### 5.1 痛点

HTTP/1.1 和 HTTP/2 都跑在 TCP 上。**只要底层是 TCP，永远逃不掉队头阻塞**。

### 5.2 Google 的颠覆

既然 TCP 烂泥扶不上墙，而且 TCP 是写死在操作系统内核里的（不可能一夜升级全球几十亿台设备的内核），那就**绕过 TCP 直接用 UDP**。

QUIC 是 Google 基于 UDP 在应用层重新实现的"靠谱传输协议"。它有 UDP 的速度，又用代码实现了 TCP 的可靠重传和拥塞控制。

### 5.3 QUIC 怎么活下来（穿透防火墙）

QUIC 是 UDP，防火墙对 UDP 往往不友好。Google 的三招：

1. **使用 443 端口**：QUIC 走的是 **UDP 的 443 端口**。虽然是 UDP，但穿着 443 的壳，且数据被 TLS 1.3 强加密，宽容的防火墙看是 443 就放行。
2. **Alt-Svc 协议升级**：第一次访问还是走传统 TCP 443（HTTPS）。服务器在响应头偷偷带上 `Alt-Svc: h3=":443"`，告诉浏览器"下次直接走 UDP 443"。
3. **无缝回退**：如果 UDP 包被严苛防火墙拦截，浏览器自动回退到 TCP HTTP/2。用户无感。

国内运营商对 UDP 经常 QoS 限速 / 丢弃，所以 HTTP/3 国内普及率远不如海外。

## 六、四大流媒体协议对比（核心）

把音视频从主播端运到观众端的不同方式。

### 6.1 一张全景表

| 协议 | 底层 | 延迟 | 浏览器原生支持 | 穿防火墙 | CDN 友好 | 典型角色 |
|---|---|---|---|---|---|---|
| **RTMP** | TCP / 1935 | 1-3 秒 | ❌ 需 Flash | ❌（1935 常被封） | 一般 | **推流端事实标准**（OBS → 服务器） |
| **HLS** | HTTP / TCP / 80,443 | 10-30 秒 | ✅（iOS 原生） | ✅ | ✅ 极友好 | **大规模分发**（千万级并发） |
| **HTTP-FLV** | HTTP / TCP / 80,443 | 1-3 秒 | ✅（flv.js） | ✅ | 较好 | **国内观众端主力** |
| **WebRTC** | UDP / 动态 | < 500ms | ✅ 全平台 | 部分（要 ICE / STUN / TURN 协助） | 复杂（昂贵） | **视频会议、连麦、超低延迟直播** |

### 6.2 RTMP：接一根专用自来水管

**原理**：Adobe 在 TCP 上自定义的协议。客户端和服务器建一条长连接，把音视频切成 Chunk 源源不断推过去。

**为什么延迟低**：长连接 + 没有切片缓冲。

**为什么浏览器播不了**：Adobe 私有协议，以前要 Flash 插件。现在 Flash 死了，浏览器没法播 RTMP。

**为什么推流端还是它的天下**：

- 生态成熟，所有 CDN 厂商对接最完善
- OBS 默认推流就是 RTMP
- 推流端不存在浏览器兼容问题
- 主播 → 服务器这"第一公里"，1935 端口管制不是大问题（公网出口畅通）

### 6.3 HLS：用卡车队送桶装水

**原理**：苹果搞的基于 HTTP 的协议。**把连续视频切成一个个小文件**（每 5 秒一个 `.ts`），生成 `.m3u8` 清单文件告诉播放器有哪些切片。

**为什么延迟高**：播放器为防卡顿，通常等攒够 3 个切片才开播。5 秒切片 × 3 = 15 秒延迟。可以通过 LL-HLS（Low-Latency HLS）降到 2-3 秒，但还是不如其他协议。

**为什么这么火**：两大杀手锏。

**杀手锏 1：穿透防火墙**

- RTMP 走 1935（偏门），公司防火墙常封
- HLS 走 80 / 443（正门），永远敞开

**杀手锏 2：CDN 极度友好（千万并发的秘密）**

- 长连接协议要服务器同时维持几百万根"水管"，CPU / 内存爆炸
- HLS 把直播变成"下载静态小文件"。CDN 是遍布各地的缓存集群，1000 万人请求同一个 `.ts` 文件，文件早就缓存在离用户最近的 CDN 节点上，请求根本到不了核心服务器
- CDN 最擅长的就是缓存静态文件——所以 HLS 能扛春晚、奥运会、世界杯这种亿级并发

**CDN 是谁的**：不是苹果的。CDN 是阿里云 / 腾讯云 / Akamai 这些云厂商建的。HLS 是公开的行业标准（不是苹果私有），任何直播平台都能用，云厂商也不需要做特殊改造——HLS 本质上是普通 HTTP 下载。

### 6.4 HTTP-FLV：披着普通卡车外衣的自来水管

**原理**：国内直播观看端的绝对主力（B 站、斗鱼、虎牙）。它**结合了 RTMP 的实时性 + HTTP 的兼容性**——本质上像 RTMP 那样源源不断推流，但把数据伪装成一个**无限大的 HTTP 响应**。

**关键技术：`Transfer-Encoding: chunked`**

普通 HTTP 请求要求服务器先给 `Content-Length`，但直播没有尽头，没法给定值。HTTP/1.1 提供 chunked 机制——服务器响应头加 `Transfer-Encoding: chunked` 就等于说"这文件多大我不知道，会切成一块块发给你，收到一块播一块，直到我发个大小为 0 的空块才算结束"。

HTTP-FLV 利用这个机制：服务器永远不发"空块"，HTTP 请求就永远不结束，实现了"披着 HTTP 外衣的长连接水管"。

**HTTP-FLV vs RTMP 的本质区别**

1. **端口与穿透性**：RTMP 走 1935（偏门常封），HTTP-FLV 走 80 / 443（正门永远开）
2. **播放生态**：RTMP 私有需要 Flash 已死；HTTP-FLV 是标准 HTTP，B 站开源的 `flv.js` 用 JavaScript 拆 FLV 喂给 HTML5 `<video>`，完美绕过 Flash
3. **数据二进制几乎一样**：剥掉传输壳子，RTMP 和 HTTP-FLV 内部装的 FLV Tag **在字节层面几乎完全相同**

**行业黄金架构**：

```
主播 -> RTMP 推流到服务器 (推流端用 RTMP,生态完善)
        |
        v
服务器边缘节点: RTMP 壳 -> HTTP-FLV 壳 (因为内部数据一样,换壳几乎不耗 CPU)
        |
        v
观众 <- HTTP-FLV 拉流播放 (观众端穿透性好,不需 Flash)
```

### 6.5 WebRTC：骑摩托车送快递

**原理**：基于 UDP 的实时通信框架。

**为什么延迟极低（毫秒级）**：UDP 没有队头阻塞，不等重传。

**为什么会花屏怎么办**：内部有一整套机制——FEC（前向纠错）、NACK（重传请求）、JitterBuffer（抗抖动）、拥塞控制（GCC / BBR）。

**现状**：

- 视频会议（Zoom、腾讯会议、飞书会议）的事实标准
- 超低延迟直播（RTS / Real-Time Streaming）正在用它
- 但**协议过于复杂、CDN 建设成本极高**，目前还无法取代 HTTP-FLV / HLS 在大规模直播分发上的位置

### 6.6 你应该记住的工程权衡

| 你的需求 | 选什么 |
|---|---|
| 主播端推流 | RTMP（生态最成熟） |
| 大规模直播分发（万人以上） | HLS（CDN 友好） |
| 国内观众端低延迟看直播 | HTTP-FLV（B 站 / 斗鱼方案） |
| 视频会议、连麦、互动 | WebRTC |
| 超低延迟（< 1s）直播 | WebRTC 或 SRT |
| 跨严苛防火墙看直播 | HLS 或 HTTP-FLV |
| 数据可丢但不能等 | UDP / WebRTC / QUIC |
| 数据不能丢可以等 | TCP / HTTP / RTMP |

## 七、端口为什么这么重要（防火墙视角）

### 7.1 为什么 1935 经常被封

公司 / 学校防火墙的默认策略：**最小权限原则**——除了 80 / 443 等上网必备端口，其他冷门端口一律封杀。原因：

1. **安全**：减少被扫描和攻击的面
2. **流量管控**：防止员工在公网刷直播占带宽

### 7.2 但是 80 / 443 也被攻击啊

**80 / 443 确实是全互联网攻击最密集的端口**。但网管为什么还只留它们？这叫"**收缩攻击面**"。

- 80 / 443 是"正门"，敞开但部署最顶级的安全设施（WAF、HTTPS、严格鉴权）。黑客进门会被严格搜身。
- 1935、3306、22 等是"偏门"，背后软件防攻击能力远不如 Web 服务（早期 RTMP 服务器常有缓冲区溢出漏洞）。

把所有偏门焊死，**强迫黑客必须从防守最严密的正门进**——防守成本最低、安全收益最高。

### 7.3 现代防火墙的"协议识别"

不只看端口，还看协议格式。**七层防火墙（WAF）**会看你 443 端口上发的是不是合法的 HTTP / TLS 数据：

- 如果你试图把 RTMP 数据强发到 80 端口，防火墙会要求"请出示 HTTP 身份证（如 `GET / HTTP/1.1`）"，发现不是合法 HTTP 直接 reset 你
- 所以微信、HTTP-FLV 这类 App **必须把自己的数据伪装成标准 HTTP 格式**，才能从 80 / 443 溜出去——这叫"**协议伪装**"

### 7.4 全球流量的现状

根据 Cloudflare / Sandvine 的统计，**全球互联网流量中，走 80 / 443 端口的 HTTP / HTTPS 流量占比 85%-90% 以上**。

"万物皆可 HTTP"：

- 网页
- App API（RESTful）
- 视频（HLS / DASH / HTTP-FLV）
- 物联网（IoT）
- 微服务内部调用（gRPC / GraphQL on HTTP/2）

HTTP 已经从"看网页的协议"变成"互联网的万能运输车"。

## 八、ffmpeg 怎么访问网络流

ffmpeg 的 `libavformat` 内置了大量协议实现。**业务代码用同一套 API 就能切本地 / 网络源**：

```bash
# 本地文件
ffmpeg -i input.mp4 ...

# RTMP 拉流
ffmpeg -i rtmp://server/live/stream ...

# HTTP / HTTPS
ffmpeg -i http://example.com/stream.m3u8 ...

# RTSP
ffmpeg -i rtsp://camera/stream ...

# SRT (一种新兴的低延迟协议)
ffmpeg -i srt://server:port ...
```

`avformat_open_input` 自动根据 URL 前缀选择对应的协议层。这种统一抽象是 ffmpeg 强大的关键。
