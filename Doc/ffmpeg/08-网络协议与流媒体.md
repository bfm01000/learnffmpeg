# 08 - 网络协议与流媒体

> 对应导读第 3.7 节"运输问题"。
> 这一篇覆盖：TCP / UDP 的本质差别、HTTP / HTTPS 的加密原理、QUIC / HTTP/3、四大流媒体协议（RTMP / HLS / HTTP-FLV / WebRTC）以及它们的工程权衡。
> 这是音视频工程师的"内功篇"——面试里几乎必问。

---

## 一、宏观视角：网络世界的物流系统

把网络协议类比成现实物流：

| 协议层 | 类比 |
|---|---|
| IP 协议（网络层） | 导航地图和公路网，负责把数据从 A 城运到 B 城 |
| TCP / UDP（传输层） | 快递公司（顺丰 vs 极兔），决定用什么策略把包裹送到 |
| HTTP / HTTPS（应用层） | 包裹里的货物和包装说明 |

下面分两条线讲：传输层（TCP / UDP）+ 应用层（HTTP / HTTPS / QUIC / 流媒体协议）。

---

## 二、传输层：TCP vs UDP

在音视频里，TCP 还是 UDP 的选择，直接决定产品是"卡成 PPT"还是"丝滑如德芙"。

### 2.1 TCP：严谨的快递员

**人设**：面向连接、可靠、不丢包、顺序保证。

**特点**：

- 发货前先打电话确认你在家（**三次握手**）
- 每个包都要签收回执（**ACK**）
- 包丢了立刻停下手里活，回去重传，直到你收到（**重传机制**）

**基于 TCP 的常见协议**：

| 协议 | 端口 | 用途 |
|---|---|---|
| HTTP | 80 | 明文网页 |
| HTTPS | 443 | 加密网页、API |
| RTMP | 1935 | 直播推流 |
| FTP | 20 / 21 | 文件下载 |
| SMTP | 25 | 发邮件 |
| SSH | 22 | 远程登录 |
| MySQL | 3306 | 数据库连接 |

### 2.2 UDP：发传单小哥

**人设**：无连接、不可靠、尽最大努力交付。

**特点**：

- 不打电话，直接把包裹往院子里扔
- 丢了不管，顺序乱了不管
- **唯一目标：快**

**基于 UDP 的常见协议**：

| 协议 | 端口 | 用途 |
|---|---|---|
| DNS | 53 | 域名解析 |
| DHCP | 67 / 68 | 自动分配 IP |
| WebRTC 媒体 | 动态（常 10000-60000） | 实时音视频（媒体走这段；另需 STUN/TURN 3478/5349 与自建信令通道） |
| QUIC / HTTP/3 | 443 (UDP) | 下一代互联网标准 |
| 大多数竞技游戏的同步协议 | 各家自定义 | 走位、开枪数据 |

## 三、TCP 的致命弱点：队头阻塞

### 3.1 什么是队头阻塞

TCP 为保证顺序，如果包 1、2、3 中**包 2 丢了**，即使包 3 已经到了网卡，TCP 也会**把它扣留在内核缓冲区里**——它必须等包 2 重传成功后，把 2 和 3 一起交给应用层。

**这是 TCP 协议层面无法绕过的限制**——只要底层是 TCP（有序可靠交付），就跑不掉。

### 3.2 音视频灾难

弱网环境下这种"强迫症"是灾难性的。哪怕丢了一个不重要的 B 帧，TCP 也会让整个直播画面卡住、缓冲、等待重传。

**重点**：

- **RTMP、HTTP-FLV、HLS 三大传统直播协议底层全部是 TCP**
- 网络差时直播要么卡住转圈圈，要么延迟从 2 秒滚到 10 秒、20 秒
- 这是 TCP 协议本身的限制，**不是任何应用层优化能彻底解决的**

### 3.3 UDP 的逆袭：WebRTC 的基石

UDP 没有队头阻塞——包 3 到了就直接给应用层，包 2 丢了就丢了。

视频会议 / 连麦场景里 **"实时性 >> 完整性"**：丢一帧花屏 0.1 秒观众不在乎，但卡 2 秒等重传观众会骂娘。所以 WebRTC 坚决用 UDP。

为了在 UDP 上保证"适度可靠"，应用层自己造轮子：

- **FEC（前向纠错）**：发 10 个包附带 2 个校验包。丢 1 个直接算回来，不用重传。空间换时间。
- **NACK（选择性重传）**：按 **RTP 序列号**请求重传丢失的那个包——粒度是"包",不是"帧"。少量偶发丢包、重传来得及时用。
- **PLI / FIR（请求关键帧）**：当丢得太多、解码器参考链已经崩了，NACK 补不回来时，请求发送端**立刻产一个关键帧（IDR）**重新起步。粒度是"整帧"。
- **拥塞控制**：估计网络容量，动态调整发送速率。

> 别把 NACK 和 PLI/FIR 混了（高频考点）：**NACK = "把丢的那个小包补给我"**，**PLI/FIR = "别补了，直接给我一张完整关键帧"**。两者都是 RTCP 反馈消息，粒度和触发场景完全不同。详见 §十 WebRTC 实时栈。

WebRTC 把这些机制全部封装好——这是它的核心价值，不是它用了 UDP 这件事本身。

## 四、应用层：HTTP vs HTTPS

### 4.1 大白话差别

- **HTTP**：明文。像寄明信片，邮递员能看，路由器能改（运营商插广告就是这么干的，叫**流量劫持**）。
- **HTTPS**：加密。像寄密码保险箱。中间人截到也只是乱码。

### 4.2 HTTPS 加密原理（必考）

HTTPS = HTTP + SSL/TLS。它结合两种密码学技术：

**第一阶段：握手（非对称加密）**

```
服务器: 给你我的公钥 + CA 证书
客户端: 生成"会话密钥",用公钥加密发回
服务器: 用私钥解密拿到"会话密钥"
        (中间人就算截到加密的会话密钥也解不开,因为没私钥)
```

非对称加密**极度安全但极度慢**，所以只用来传"会话密钥"这一件小事。

**第二阶段：传输（对称加密）**

握手完成后双方都有了"会话密钥"。后续所有数据用这个密钥对称加密传输。对称加密**速度极快**，适合大数据量。

### 4.3 音视频里的痛点：首屏秒开

直播 / 短视频追求"首屏秒开率"（用户划走视频后新视频要在 100ms 内出画面）。

**HTTPS 是首屏的拦路虎**：

- HTTP：TCP 三次握手 ≈ 1.5 RTT
- HTTPS：TCP 三次握手 + TLS 握手 ≈ 2.5 ~ 3.5 RTT

优化方案：

- **TLS 1.3**：握手降到 1-RTT，甚至 0-RTT（恢复会话时）
- **Session Resumption**：复用之前的会话密钥
- **内部网络剥离 HTTPS**：只在面向用户的"最后一公里"用 HTTPS

## 五、终极进化：QUIC / HTTP/3

### 5.1 痛点

HTTP/1.1 和 HTTP/2 都跑在 TCP 上。**只要底层是 TCP，永远逃不掉队头阻塞**。

### 5.2 Google 的颠覆

既然 TCP 烂泥扶不上墙，而且 TCP 是写死在操作系统内核里的（不可能一夜升级全球几十亿台设备的内核），那就**绕过 TCP 直接用 UDP**。

QUIC 是 Google 基于 UDP 在应用层重新实现的"靠谱传输协议"。它有 UDP 的速度，又用代码实现了 TCP 的可靠重传和拥塞控制。

### 5.3 QUIC 怎么活下来（穿透防火墙）

QUIC 是 UDP，防火墙对 UDP 往往不友好。Google 的三招：

1. **使用 443 端口**：QUIC 走的是 **UDP 的 443 端口**。虽然是 UDP，但穿着 443 的壳，且数据被 TLS 1.3 强加密，宽容的防火墙看是 443 就放行。
2. **Alt-Svc 协议升级**：第一次访问还是走传统 TCP 443（HTTPS）。服务器在响应头偷偷带上 `Alt-Svc: h3=":443"`，告诉浏览器"下次直接走 UDP 443"。
3. **无缝回退**：如果 UDP 包被严苛防火墙拦截，浏览器自动回退到 TCP HTTP/2。用户无感。

国内运营商对 UDP 经常 QoS 限速 / 丢弃，所以 HTTP/3 国内普及率远不如海外。

## 六、四大流媒体协议对比（核心）

把音视频从主播端运到观众端的不同方式。

### 6.1 一张全景表

| 协议 | 底层 | 延迟 | 浏览器原生支持 | 穿防火墙 | CDN 友好 | 典型角色 |
|---|---|---|---|---|---|---|
| **RTMP** | TCP / 1935 | 1-3 秒 | ❌ 需 Flash | ❌（1935 常被封） | 一般 | **推流端事实标准**（OBS → 服务器） |
| **HLS** | HTTP / TCP / 80,443 | 10-30 秒 | ✅（iOS 原生） | ✅ | ✅ 极友好 | **大规模分发**（千万级并发） |
| **HTTP-FLV** | HTTP / TCP / 80,443 | 1-3 秒 | ✅（flv.js） | ✅ | 较好 | **国内观众端主力** |
| **WebRTC** | UDP / 动态 | < 500ms | ✅ 全平台 | 部分（要 ICE / STUN / TURN 协助） | 复杂（昂贵） | **视频会议、连麦、超低延迟直播** |

### 6.2 RTMP：接一根专用自来水管

**原理**：Adobe 在 TCP 上自定义的协议。客户端和服务器建一条长连接，把音视频切成 Chunk 源源不断推过去。

**为什么延迟低**：长连接 + 没有切片缓冲。

**为什么浏览器播不了**：Adobe 私有协议，以前要 Flash 插件。现在 Flash 死了，浏览器没法播 RTMP。

**为什么推流端还是它的天下**：

- 生态成熟，所有 CDN 厂商对接最完善
- OBS 默认推流就是 RTMP
- 推流端不存在浏览器兼容问题
- 主播 → 服务器这"第一公里"，1935 端口管制不是大问题（公网出口畅通）

### 6.3 HLS：用卡车队送桶装水

**原理**：苹果搞的基于 HTTP 的协议。**把连续视频切成一个个小文件**（每 5 秒一个 `.ts`），生成 `.m3u8` 清单文件告诉播放器有哪些切片。

**为什么延迟高**：播放器为防卡顿，通常等攒够 3 个切片才开播。5 秒切片 × 3 = 15 秒延迟。可以通过 LL-HLS（Low-Latency HLS）降到 2-3 秒，但还是不如其他协议。

**为什么这么火**：两大杀手锏。

**杀手锏 1：穿透防火墙**

- RTMP 走 1935（偏门），公司防火墙常封
- HLS 走 80 / 443（正门），永远敞开

**杀手锏 2：CDN 极度友好（千万并发的秘密）**

- 长连接协议要服务器同时维持几百万根"水管"，CPU / 内存爆炸
- HLS 把直播变成"下载静态小文件"。CDN 是遍布各地的缓存集群，1000 万人请求同一个 `.ts` 文件，文件早就缓存在离用户最近的 CDN 节点上，请求根本到不了核心服务器
- CDN 最擅长的就是缓存静态文件——所以 HLS 能扛春晚、奥运会、世界杯这种亿级并发

**CDN 是谁的**：不是苹果的。CDN 是阿里云 / 腾讯云 / Akamai 这些云厂商建的。HLS 是公开的行业标准（不是苹果私有），任何直播平台都能用，云厂商也不需要做特殊改造——HLS 本质上是普通 HTTP 下载。

> **HLS vs DASH（MPEG-DASH）**：DASH 是和 HLS 同类的"切片 + 清单 + 自适应码率（ABR）"协议，但它是**编码无关的国际标准**（ISO），清单是 `.mpd`（XML），切片常用 fMP4（fragmented MP4）。HLS 是苹果系生态首选（iOS 原生只认 HLS），DASH 在 Android / 桌面 Web / YouTube/Netflix 这类跨平台点播更通用。两者机制几乎对称，工程上常**同时打包两份**覆盖全端。延迟、CDN 友好性的取舍和 HLS 一致。

### 6.4 HTTP-FLV：披着普通卡车外衣的自来水管

**原理**：国内直播观看端的绝对主力（B 站、斗鱼、虎牙）。它**结合了 RTMP 的实时性 + HTTP 的兼容性**——本质上像 RTMP 那样源源不断推流，但把数据伪装成一个**无限大的 HTTP 响应**。

**关键技术：`Transfer-Encoding: chunked`**

普通 HTTP 请求要求服务器先给 `Content-Length`，但直播没有尽头，没法给定值。HTTP/1.1 提供 chunked 机制——服务器响应头加 `Transfer-Encoding: chunked` 就等于说"这文件多大我不知道，会切成一块块发给你，收到一块播一块，直到我发个大小为 0 的空块才算结束"。

HTTP-FLV 利用这个机制：服务器永远不发"空块"，HTTP 请求就永远不结束，实现了"披着 HTTP 外衣的长连接水管"。

**HTTP-FLV vs RTMP 的本质区别**

1. **端口与穿透性**：RTMP 走 1935（偏门常封），HTTP-FLV 走 80 / 443（正门永远开）
2. **播放生态**：RTMP 私有需要 Flash 已死；HTTP-FLV 是标准 HTTP，B 站开源的 `flv.js` 用 JavaScript 拆 FLV 喂给 HTML5 `<video>`，完美绕过 Flash
3. **数据二进制几乎一样**：剥掉传输壳子，RTMP 和 HTTP-FLV 内部装的 FLV Tag **在字节层面几乎完全相同**

**行业黄金架构**：

```
主播 -> RTMP 推流到服务器 (推流端用 RTMP,生态完善)
        |
        v
服务器边缘节点: RTMP 壳 -> HTTP-FLV 壳 (因为内部数据一样,换壳几乎不耗 CPU)
        |
        v
观众 <- HTTP-FLV 拉流播放 (观众端穿透性好,不需 Flash)
```

### 6.5 WebRTC：骑摩托车送快递

**原理**：基于 UDP 的实时通信框架。

**为什么延迟低（亚秒级，典型 100-400ms）**：UDP 没有队头阻塞，不等重传。

**为什么会花屏怎么办**：内部有一整套机制——FEC（前向纠错）、NACK（重传请求）、JitterBuffer（抗抖动）、拥塞控制（GCC）。

**现状**：

- 视频会议（Zoom、腾讯会议、飞书会议）的事实标准
- 超低延迟直播（RTS / Real-Time Streaming）正在用它
- 但**协议过于复杂、CDN 建设成本极高**，目前还无法取代 HTTP-FLV / HLS 在大规模直播分发上的位置

> WebRTC 的完整传输栈（RTP/RTCP、ICE/STUN/TURN、SDP、DTLS-SRTP、GCC、SFU/MCU、Jitter Buffer）拆解见本篇 **§十 WebRTC 实时栈速览**；移动端把解出的流交给手机硬件编解码器的落地见 [10-移动端硬件编解码.md](./10-移动端硬件编解码.md)；系统性的 WebRTC 学习见 [[project_webrtc_learning]] 专项。

### 6.6 你应该记住的工程权衡

| 你的需求 | 选什么 |
|---|---|
| 主播端推流 | RTMP（生态最成熟） |
| 大规模直播分发（万人以上） | HLS（CDN 友好） |
| 国内观众端低延迟看直播 | HTTP-FLV（B 站 / 斗鱼方案） |
| 视频会议、连麦、互动 | WebRTC |
| 超低延迟（< 1s）互动直播 | WebRTC（真互动级，几百毫秒） |
| 低延迟点对点回传 / 拉流 | SRT（可靠 UDP + 抗丢包，延迟可配几百 ms~1-2s，强在抗丢包而非互动） |
| 跨严苛防火墙看直播 | HLS 或 HTTP-FLV |
| 数据可丢但不能等 | UDP / WebRTC / QUIC |
| 数据不能丢可以等 | TCP / HTTP / RTMP |

## 七、端口为什么这么重要（防火墙视角）

### 7.1 为什么 1935 经常被封

公司 / 学校防火墙的默认策略：**最小权限原则**——除了 80 / 443 等上网必备端口，其他冷门端口一律封杀。原因：

1. **安全**：减少被扫描和攻击的面
2. **流量管控**：防止员工在公网刷直播占带宽

### 7.2 但是 80 / 443 也被攻击啊

**80 / 443 确实是全互联网攻击最密集的端口**。但网管为什么还只留它们？这叫"**收缩攻击面**"。

- 80 / 443 是"正门"，敞开但部署最顶级的安全设施（WAF、HTTPS、严格鉴权）。黑客进门会被严格搜身。
- 1935、3306、22 等是"偏门"，背后软件防攻击能力远不如 Web 服务（早期 RTMP 服务器常有缓冲区溢出漏洞）。

把所有偏门焊死，**强迫黑客必须从防守最严密的正门进**——防守成本最低、安全收益最高。

### 7.3 现代防火墙的"协议识别"

不只看端口，还看协议格式。**七层防火墙（WAF）**会看你 443 端口上发的是不是合法的 HTTP / TLS 数据：

- 如果你试图把 RTMP 数据强发到 80 端口，防火墙会要求"请出示 HTTP 身份证（如 `GET / HTTP/1.1`）"，发现不是合法 HTTP 直接 reset 你
- 所以微信、HTTP-FLV 这类 App **必须把自己的数据伪装成标准 HTTP 格式**，才能从 80 / 443 溜出去——这叫"**协议伪装**"

### 7.4 全球流量的现状

根据 Cloudflare / Sandvine 的统计，**全球互联网流量中，走 80 / 443 端口的 HTTP / HTTPS 流量占比 85%-90% 以上**。

"万物皆可 HTTP"：

- 网页
- App API（RESTful）
- 视频（HLS / DASH / HTTP-FLV）
- 物联网（IoT）
- 微服务内部调用（gRPC / GraphQL on HTTP/2）

HTTP 已经从"看网页的协议"变成"互联网的万能运输车"。

## 八、ffmpeg 怎么访问网络流

ffmpeg 的 `libavformat` 内置了大量协议实现。**业务代码用同一套 API 就能切本地 / 网络源**：

```bash
# 本地文件
ffmpeg -i input.mp4 ...

# RTMP 拉流
ffmpeg -i rtmp://server/live/stream ...

# HTTP / HTTPS
ffmpeg -i http://example.com/stream.m3u8 ...

# RTSP
ffmpeg -i rtsp://camera/stream ...

# SRT (一种新兴的低延迟协议)
ffmpeg -i srt://server:port ...
```

`avformat_open_input` 自动根据 URL 前缀选择对应的协议层。这种统一抽象是 ffmpeg 强大的关键。

## 十、WebRTC 实时栈速览

> 前九节讲的都是**传统直播链路**（RTMP 推流、HLS / HTTP-FLV 分发），它们的共性是"一对多、可以容忍秒级延迟、底层基本是 TCP"。
> WebRTC 是另一套世界观：**实时、双向、几百毫秒级（亚秒级）、底层是 UDP**。第六节已经把它放进了对比表，但只给了一个轮廓。这一节专门把 WebRTC 的传输栈拆开，建立地图感——每个零件解决一个具体问题，先知道"有哪些零件、各管什么"，细节实现留给 [[project_webrtc_learning]] 专项去啃。

下面这张图是这一节的骨架，可以边看边对照：

```
            ┌─────────────── 信令（不属于 WebRTC 标准，自己搭 WebSocket）────────────┐
            │                  交换 SDP offer/answer + ICE candidate                   │
            v                                                                          v
        [ 端 A ] ←─── ICE / STUN / TURN 打通路径 ───→ [ 端 B ]
            │                                                                          │
            │   媒体走 UDP：  RTP（承载） + RTCP（反馈） + DTLS-SRTP（加密）            │
            │   带宽自适应：  GCC 拥塞控制 ←── transport-cc / REMB 反馈                  │
            └────────────── 多人会议时中间还有 SFU / MCU ───────────────────────────────┘
```

### 10.1 RTP —— 媒体的承载车

**是什么**：Real-time Transport Protocol，跑在 UDP 之上，专门驮音视频包。每个 RTP 包头里有三个关键字段：序列号（sequenceNumber，每发一包 +1，用来发现丢包和乱序）、时间戳（timestamp，标记这帧媒体的采样时刻，用来做音视频同步和播放定时）、负载类型（payloadType，标记里面装的是 Opus 还是 H.264 等，和 SDP 协商出来的编号对应）。

**解决什么问题**：UDP 本身只管"把字节扔过去"，不告诉你包的先后、什么时候该播、装的是什么编码。RTP 在 UDP 上补齐了这层"媒体语义"。注意 RTP 包里装的视频是裸 NAL 单元，没有 Annex-B 的 `00 00 00 01` 起始码（用包长度天然分界），这点和 [05-H264-MP4-NALU.md](./05-H264-MP4-NALU.md) 里讲的 Annex-B 格式不同。

**面试会问什么**：为什么用 UDP 上的 RTP 而不直接用 TCP？答案接第三节的队头阻塞——TCP 一丢包就扣住后续所有包等重传，实时场景宁可丢一帧花屏 0.1 秒，也不能为了一个旧包卡住 2 秒。RTP 让"丢了就丢、该重传由上层自己决定"成为可能。

### 10.2 RTCP —— 反馈通道

**是什么**：RTP Control Protocol，和 RTP 配对的"控制台",不传媒体、只传质量反馈与控制消息。两类基础报告：发送端报告 SR（Sender Report，告诉对端"我发了多少"）、接收端报告 RR（Receiver Report，回报丢包率、抖动 jitter、以及用来算 RTT 的时间戳）。在这之上还有一组**反馈类消息**：NACK、PLI、FIR。

**解决什么问题**：UDP + RTP 是"只管发不管收"的单向猜测，发送端根本不知道网络好坏。RTCP 把接收端的真实体验（丢了多少、抖动多大、延迟多高）回灌给发送端，是后面拥塞控制和重传决策的数据来源。

**特别要分清的坑（高频考点）**：
| 反馈消息 | 粒度 | 干什么 | 什么时候用 |
|---|---|---|---|
| **NACK** | 单个 RTP 包（按序列号） | 请求**重传指定序列号的那一个丢包** | 偶发、少量丢包，重传来得及 |
| **PLI / FIR** | 一整帧 | 请求发送端**立刻产一个关键帧（IDR）** | 丢包太多、解码器状态已崩，靠重传补不回来了 |

一句话记牢：**NACK 是"把丢的那个小包补给我"，PLI/FIR 是"别补了，直接给我一张完整关键帧重新起步"**。两者都是 RTCP 反馈消息，但粒度和触发场景完全不同，面试最爱在这里挖坑。

**面试会问什么**：丢包了 WebRTC 怎么恢复？答：先看丢得多不多——少量丢包发 NACK 精准重传；丢成片、参考帧都没了，就发 PLI/FIR 让对端打一个关键帧，用"重置"代替"修补"。

### 10.3 ICE / STUN / TURN —— NAT 穿透

**是什么**：一组让"两台都躲在 NAT/路由器后面、没有公网 IP 的设备"建立直连的机制。
- **ICE**（Interactive Connectivity Establishment）：总调度框架。它收集本端所有可能的地址（叫 candidate：本地局域网地址、经 STUN 拿到的公网映射地址、TURN 中继地址），和对端交换后逐对尝试连通，挑一条能通的。
- **STUN**：一台公网服务器，帮你回答"我在 NAT 外面看起来是什么 IP 和端口"，据此做 UDP **打洞**，目标是让双方直连。
- **TURN**：当打洞失败（对称型 NAT、严苛防火墙）时的**中继兜底**——媒体流绕道 TURN 服务器转发。能通但费流量、加延迟，是下策但保证可用。

**解决什么问题**：公网 IPv4 稀缺，绝大多数设备都在 NAT 后面，互相看不到对方的真实地址。ICE 把"尽量直连、实在不行走中继"这套试探逻辑标准化了。

**面试会问什么**：STUN 和 TURN 区别？答：STUN 只帮你**发现地址并打洞**，连通后媒体是端到端直连，服务器不碰流量；TURN 是**全程中继转发**媒体，成本高，只在直连失败时兜底。生产环境必须同时部署，TURN 流量占比是重要的成本与质量指标。

### 10.4 SDP offer/answer —— 能力协商

**是什么**：Session Description Protocol，一段文本，描述"我支持哪些 codec、什么分辨率/采样率、用哪些 ICE candidate、加密指纹是什么"。建连时一端发 **offer**（我能做这些），另一端回 **answer**（那我们就用这些交集），协商出双方都支持的参数集。其中视频的 H.264 走哪个 Profile，就是靠 SDP 里的 `profile-level-id` 协商的（呼应 [06-编码参数与码控.md](./06-编码参数与码控.md) 对"WebRTC 未必用 Baseline"的说明）。

**解决什么问题**：两端的编解码能力、分辨率、网络地址各不相同，必须先"对暗号"达成共识才能开始传媒体。SDP 就是这份"暗号清单"。

**关键边界（容易被问）**：SDP 要靠一条**信令通道**来回传递，但**信令通道本身不属于 WebRTC 标准**——用 WebSocket、HTTP、甚至短信都行，由你自己实现。WebRTC 只规定"交换什么内容（SDP/candidate）",不规定"用什么管子交换"。

**面试会问什么**：WebRTC 需要服务器吗？答：媒体可以端到端直连（不一定需要媒体服务器），但**信令服务器必须自己搭**——两端在建连前根本不知道对方在哪，得有个第三方帮它们转交 offer/answer 和 candidate。

### 10.5 DTLS-SRTP —— 媒体强制加密

**是什么**：WebRTC 规定媒体**必须加密**，没有明文模式。它用 **DTLS**（TLS 的 UDP 版，因为媒体走 UDP，普通 TLS 跑在 TCP 上用不了）先在两端之间握手、交换密钥，再用 **SRTP**（Secure RTP）拿这把密钥加密每一个 RTP 媒体包。

**解决什么问题**：实时音视频常是私密对话（会议、连麦），且要防中间人篡改。对比传统直播：HTTPS 是用 **TLS over TCP** 保护 HTTP 数据（见第四节），WebRTC 因为底层是 UDP，换成 **DTLS over UDP** 来完成等价的密钥协商，再交给 SRTP 加密媒体。

**面试会问什么**：WebRTC 的媒体加密和 HTTPS 有什么区别？答：思路一样（先非对称握手换密钥、再对称加密数据），但传输层不同——HTTPS 是 TLS+TCP，WebRTC 是 DTLS+UDP+SRTP，且 WebRTC 是**强制加密、无法关闭**。

### 10.6 拥塞控制 GCC —— 动态调码率

**是什么**：Google Congestion Control，WebRTC 默认的带宽估计算法。它不靠"丢包了才降速"这种滞后信号，而是同时看两路：一是**延迟梯度**（监测包的到达间隔有没有被拉长——排队变长往往是拥塞的**早期**征兆，比丢包更早出现）；二是**丢包率**（兜底信号）。综合两者估出当前可用带宽，再反过来指挥编码器**动态调整码率**（见 [06-编码参数与码控.md](./06-编码参数与码控.md) 的码控）。

**这些信号怎么回来**：靠 RTCP 反馈——老方案 **REMB**（接收端直接算好一个带宽值告诉发送端）；新方案 **transport-cc**（接收端只如实回报每个包的到达时间，把带宽估计的计算放到发送端做，更精准、更灵活）。

**解决什么问题**：网络带宽实时波动，发太快会拥塞、爆发丢包、延迟飙升；发太慢浪费画质。GCC 让码率"踩着网络的实际容量走"——这正是第六节说 WebRTC"内部封装好拥塞控制"的那块。

**面试会问什么**：GCC 凭什么比传统拥塞控制更适合实时音视频？答：它把**延迟梯度**当作主信号，能在丢包真正发生**之前**就察觉到链路开始排队、提前降码率，避免了"等丢包才反应"带来的卡顿和延迟尖峰。

### 10.7 SFU vs MCU —— 多人会议的转发架构

**是什么**：两人通话可以纯端到端，但**多人会议**里如果人人给其他所有人各发一路流，上行带宽会爆炸，所以中间要架一台媒体服务器。两种流派：
| 架构 | 做什么 | 服务器开销 | 下行带宽 | 画质/灵活性 |
|---|---|---|---|---|
| **SFU**（Selective Forwarding Unit） | **只转发、不解码**：收到每路流，按需选择性转发给其他人 | 低（不碰编解码） | 高（每人收 N-1 路） | 高（各端可自己选清晰度，支持 Simulcast） |
| **MCU**（Multipoint Control Unit） | **解码后混成一路再编码**发出 | 极高（要解码+混流+重编码） | 低（每人只收 1 路混好的） | 低（画面布局固定、灵活性差） |

主流现代会议系统几乎都用 **SFU**（如 mediasoup、Janus、LiveKit），MCU 多见于需要兼容老旧终端或下行带宽极受限的场景。

**解决什么问题**：把多人会议的带宽和算力压力从"每个客户端"挪到"中心服务器",并在"服务器算力"和"客户端下行带宽"之间做权衡。

**面试会问什么**：为什么说 WebRTC 自建 CDN 成本远高于 HLS？答：HLS 本质是**缓存静态小文件**，普通 CDN 节点就能扛千万并发（见第六节）；而 WebRTC 是**有状态的实时会话**，每一路都要做 ICE、DTLS、拥塞控制，规模化必须在边缘大量部署 **SFU** 这种有状态、吃 CPU 的媒体服务器——这是有状态计算，不是无状态缓存，单位成本天差地别。

### 10.8 Jitter Buffer —— 抗抖动缓冲

**是什么**：接收端的一小段缓冲区，把先到的包**按时间戳重排序、暂存一会儿**再交给解码器和播放器。它吸收网络抖动（jitter，即包到达间隔忽快忽慢），让乱序到达的包归位、给迟到的包一点等待窗口，从而**平滑播放**、不卡顿不跳帧。

**解决什么问题**：UDP 包到达时间参差不齐，直接播会忽快忽慢甚至乱序。Jitter Buffer 用"略微多等一点"换"播放平稳"。

**面试会问什么**：Jitter Buffer 怎么影响延迟？答：它本质是**抗抖动 vs 端到端延迟**的权衡——缓冲越大越能扛抖动、播放越稳，但排队等待越久、延迟越高；缓冲越小延迟越低，但稍有抖动就卡顿/丢帧。现代实现是**自适应**的，根据实时网络抖动动态调整缓冲深度，在"流畅"和"实时"之间找平衡点。

### 10.9 这一节的工程权衡速记

| 你关心的问题 | WebRTC 里负责的零件 |
|---|---|
| 媒体怎么承载、怎么对齐时间 | RTP（序列号 / 时间戳 / 负载类型） |
| 网络好坏怎么知道、丢包怎么补 | RTCP（SR/RR 报告，NACK 重传，PLI/FIR 请关键帧） |
| 两个 NAT 后的端怎么连上 | ICE + STUN（打洞直连）+ TURN（中继兜底） |
| 双方能力怎么对齐 | SDP offer/answer（信令通道自己搭） |
| 媒体怎么加密 | DTLS-SRTP（强制，UDP 版 TLS） |
| 码率怎么跟着网络走 | GCC + transport-cc / REMB 反馈 |
| 多人会议怎么转发 | SFU（转发不解码）/ MCU（混流） |
| 乱序抖动怎么平滑 | Jitter Buffer（抗抖动 vs 延迟权衡） |

> 移动端落地时，这套栈最终还是要把解出来的 H.264/H.265 交给手机的硬件解码器去渲染——硬编解的坑见 [10-移动端硬件编解码.md](./10-移动端硬件编解码.md)。
