# 单例模式 (Singleton Pattern) 深度解析与面试指南

单例模式（Singleton Pattern）是创建型设计模式里最常被问到、也最容易被滥用的模式。它的核心目标是：**保证一个类在整个进程内只有一个实例，并提供一个全局访问点**。

在音视频 SDK 和底层工程里，单例经常出现在日志系统、全局配置、设备能力探测、线程池管理、事件中心等场景。但要注意：**单例不是“全局变量的高级写法”，它解决的是“全局唯一资源”的生命周期与访问控制问题**。

本文参考《观察者模式详解》《发布订阅模式详解》的结构，从代码场景、核心原理、线程安全实现、工程坑点和面试高频问题五个角度讲清楚单例模式。

---

## 零、 先用代码看：什么时候会用到单例模式？

单例模式最常见的触发场景是：**某个对象在整个进程里天然只应该存在一份，多份反而会造成状态混乱、资源浪费或行为不一致。**

以音视频 SDK 为例，下面这些对象通常具有“全局唯一”的特征：

*   **日志系统**：整个 SDK 的日志应该写到同一套输出、同一套级别控制里。
*   **设备能力缓存**：比如当前机型是否支持 H.265、硬编、零拷贝、Surface 输入等，不应该每个模块都重复探测。
*   **全局配置中心**：比如 SDK 初始化参数、开关配置、实验配置。
*   **线程池 / 调度器**：如果每个模块都创建一套线程池，容易导致线程数失控。
*   **事件中心 / EventBus**：系统级事件通常需要一个统一入口。

### 1. 不用单例：每个模块各自 new 一份，状态很容易乱

假设直播 SDK 里有一个日志模块，多个子系统都要打日志：

```cpp
#include <fstream>
#include <string>

class SdkLogger {
public:
    explicit SdkLogger(const std::string& filePath) {
        file_.open(filePath, std::ios::app);
    }

    void setLevel(int level) {
        level_ = level;
    }

    void log(int level, const std::string& message) {
        if (level < level_) {
            return;
        }
        file_ << message << std::endl;
    }

private:
    int level_ = 0;
    std::ofstream file_;
};

class Encoder {
public:
    Encoder() : logger_("sdk.log") {}

    void encodeFrame() {
        logger_.log(1, "encode one frame");
    }

private:
    SdkLogger logger_;
};

class NetworkSender {
public:
    NetworkSender() : logger_("sdk.log") {}

    void sendPacket() {
        logger_.log(1, "send one packet");
    }

private:
    SdkLogger logger_;
};
```

这段代码的问题是：

*   `Encoder` 和 `NetworkSender` 各自持有一份 `SdkLogger`，日志级别可能不一致。
*   多个 `ofstream` 同时写同一个文件，容易出现竞争和顺序混乱。
*   后续如果要统一关闭日志、切换输出、增加埋点，很难集中控制。

### 2. 使用单例：全局唯一日志入口

如果日志系统在整个 SDK 内只应该有一份，就可以考虑单例。

```cpp
#include <fstream>
#include <mutex>
#include <string>

class SdkLogger {
public:
    static SdkLogger& instance() {
        static SdkLogger logger;
        return logger;
    }

    void setLevel(int level) {
        std::lock_guard<std::mutex> lock(mutex_);
        level_ = level;
    }

    void log(int level, const std::string& message) {
        std::lock_guard<std::mutex> lock(mutex_);
        if (level < level_) {
            return;
        }
        file_ << message << std::endl;
    }

private:
    SdkLogger() {
        file_.open("sdk.log", std::ios::app);
    }

    ~SdkLogger() = default;

    SdkLogger(const SdkLogger&) = delete;
    SdkLogger& operator=(const SdkLogger&) = delete;

    int level_ = 0;
    std::mutex mutex_;
    std::ofstream file_;
};
```

业务模块统一通过 `SdkLogger::instance()` 获取同一个实例：

```cpp
class Encoder {
public:
    void encodeFrame() {
        SdkLogger::instance().log(1, "encode one frame");
    }
};

class NetworkSender {
public:
    void sendPacket() {
        SdkLogger::instance().log(1, "send one packet");
    }
};
```

这就是单例模式要解决的问题：**全局唯一资源只初始化一次，所有模块访问同一个对象，避免重复创建和状态分裂。**

### 3. 从代码抽象出适用条件

看到下面几种情况，可以考虑单例模式：

1.  **这个对象天然应该全局唯一**：比如日志系统、配置中心、设备能力缓存。
2.  **重复创建会浪费资源或造成冲突**：比如线程池、文件句柄、硬件能力探测结果。
3.  **需要统一访问入口**：多个模块都要访问同一份配置或状态。
4.  **生命周期基本覆盖整个进程**：比如 SDK 初始化后一直存在，直到进程退出。

一句话总结：**单例模式适合解决“某个类在整个进程中只应该存在一个实例，并且多个模块都需要访问它”的问题。**

## 一、 定义与核心原理

### 1. 官方定义

单例模式保证一个类只有一个实例，并提供一个全局访问点。

它通常要满足三个条件：

*   **构造函数私有化**：外部不能随便 `new`。
*   **内部持有唯一实例**：实例由类自己创建和管理。
*   **提供静态访问入口**：比如 `getInstance()` 或 `instance()`。

### 2. 核心角色

单例模式结构很简单，通常只有一个角色：

*   **Singleton（单例类）**：负责创建、保存、返回自己的唯一实例，同时禁止外部复制和赋值。

### 3. 饿汉式 vs 懒汉式

单例常见有两类初始化策略：

*   **饿汉式（Eager Initialization）**：程序启动或类加载时就创建实例。优点是简单、天然线程安全；缺点是不管用不用都会初始化。
*   **懒汉式（Lazy Initialization）**：第一次访问时才创建实例。优点是按需创建；缺点是多线程下必须处理线程安全。

在 C++11 之后，最推荐的写法通常是 **Meyers Singleton（函数内局部静态变量）**。

## 二、 C++ 单例的常见实现

### 1. 错误示范：普通懒汉式，线程不安全

```cpp
class UnsafeSingleton {
public:
    static UnsafeSingleton* instance() {
        if (instance_ == nullptr) {
            instance_ = new UnsafeSingleton();
        }
        return instance_;
    }

private:
    UnsafeSingleton() = default;

    static UnsafeSingleton* instance_;
};

UnsafeSingleton* UnsafeSingleton::instance_ = nullptr;
```

这段代码在单线程下看似没问题，但多线程下有严重竞态：

```text
线程 A 判断 instance_ == nullptr
线程 B 判断 instance_ == nullptr
线程 A new 一个对象
线程 B 也 new 一个对象
```

结果就可能创建出两个实例，违背单例的核心约束。

### 2. C++11 推荐写法：Meyers Singleton

```cpp
class EngineConfig {
public:
    static EngineConfig& instance() {
        static EngineConfig config;
        return config;
    }

    void setEnableHardwareDecode(bool enable) {
        enableHardwareDecode_ = enable;
    }

    bool enableHardwareDecode() const {
        return enableHardwareDecode_;
    }

private:
    EngineConfig() = default;
    ~EngineConfig() = default;

    EngineConfig(const EngineConfig&) = delete;
    EngineConfig& operator=(const EngineConfig&) = delete;

    bool enableHardwareDecode_ = true;
};
```

为什么这段代码是线程安全的？

*   C++11 标准保证：**函数内局部静态变量的初始化是线程安全的**。
*   第一次调用 `instance()` 时才初始化，属于懒加载。
*   初始化完成后，后续调用只返回同一个对象引用，开销很小。
*   对象生命周期由运行时管理，通常在进程退出时析构。

面试里说 C++ 单例，优先讲这个。

### 3. `std::call_once` 写法

如果你需要更显式地控制初始化，也可以用 `std::call_once`。

```cpp
#include <memory>
#include <mutex>

class CodecCapabilityCache {
public:
    static CodecCapabilityCache& instance() {
        std::call_once(initFlag_, []() {
            instance_.reset(new CodecCapabilityCache());
        });
        return *instance_;
    }

    bool supportHevc() const {
        return supportHevc_;
    }

private:
    CodecCapabilityCache() {
        // 真实项目里这里可能查询 MediaCodec 能力、机型黑白名单等
        supportHevc_ = true;
    }

    CodecCapabilityCache(const CodecCapabilityCache&) = delete;
    CodecCapabilityCache& operator=(const CodecCapabilityCache&) = delete;

    bool supportHevc_ = false;

    static std::once_flag initFlag_;
    static std::unique_ptr<CodecCapabilityCache> instance_;
};

std::once_flag CodecCapabilityCache::initFlag_;
std::unique_ptr<CodecCapabilityCache> CodecCapabilityCache::instance_;
```

`std::call_once` 的语义是：无论多少线程同时调用，初始化函数只会成功执行一次。

### 4. 双重检查锁（DCL）：能讲，但 C++ 中不优先推荐手写

双重检查锁的思路是：先不加锁判断一次，避免每次访问都加锁；如果发现实例为空，再加锁二次判断并创建。

```cpp
#include <atomic>
#include <mutex>

class DclSingleton {
public:
    static DclSingleton* instance() {
        DclSingleton* temp = instance_.load(std::memory_order_acquire);
        if (temp == nullptr) {
            std::lock_guard<std::mutex> lock(mutex_);
            temp = instance_.load(std::memory_order_relaxed);
            if (temp == nullptr) {
                temp = new DclSingleton();
                instance_.store(temp, std::memory_order_release);
            }
        }
        return temp;
    }

private:
    DclSingleton() = default;

    static std::atomic<DclSingleton*> instance_;
    static std::mutex mutex_;
};

std::atomic<DclSingleton*> DclSingleton::instance_{nullptr};
std::mutex DclSingleton::mutex_;
```

这段代码已经涉及 `std::atomic` 和内存序。普通面试里不建议优先手写 DCL，因为：

*   容易写错内存序。
*   容易忘记释放。
*   可读性不如 Meyers Singleton。

所以 C++11 之后，工程上更推荐：**局部静态变量** 或 **`std::call_once`**。

## 三、 Java 单例的常见实现

### 1. 错误示范：普通懒汉式，线程不安全

```java
public class UnsafeSingleton {
    private static UnsafeSingleton instance;

    private UnsafeSingleton() {}

    public static UnsafeSingleton getInstance() {
        if (instance == null) {
            instance = new UnsafeSingleton();
        }
        return instance;
    }
}
```

多线程下也可能创建多个实例。

### 2. Java DCL 必须配合 `volatile`

```java
public class SafeSingleton {
    private static volatile SafeSingleton instance;

    private SafeSingleton() {}

    public static SafeSingleton getInstance() {
        if (instance == null) {
            synchronized (SafeSingleton.class) {
                if (instance == null) {
                    instance = new SafeSingleton();
                }
            }
        }
        return instance;
    }
}
```

为什么必须加 `volatile`？

`new SafeSingleton()` 不是一个不可拆分的原子动作，大致可以分为：

```text
1. 分配内存
2. 调用构造函数初始化对象
3. 把对象地址赋值给 instance
```

如果没有 `volatile`，编译器或 CPU 可能发生指令重排序，变成：

```text
1. 分配内存
2. 把对象地址赋值给 instance
3. 调用构造函数初始化对象
```

这时另一个线程看到 `instance != null`，拿到的可能是一个**还没初始化完成的半成品对象**。

`volatile` 的作用主要有两个：

*   **保证可见性**：一个线程写入 `instance` 后，其他线程能立刻看到。
*   **禁止关键重排序**：避免对象引用先发布、构造函数还没执行完的情况。

### 3. Java 静态内部类写法

```java
public class HolderSingleton {
    private HolderSingleton() {}

    private static class Holder {
        private static final HolderSingleton INSTANCE = new HolderSingleton();
    }

    public static HolderSingleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

这个写法利用 JVM 的类加载机制：

*   外部类加载时，不会立刻加载 `Holder`。
*   第一次调用 `getInstance()` 时，才加载 `Holder` 并创建实例。
*   JVM 保证类初始化过程线程安全。

所以它同时具备懒加载和线程安全，代码也很简洁。

### 4. Java 枚举单例

```java
public enum LoggerSingleton {
    INSTANCE;

    public void log(String message) {
        System.out.println(message);
    }
}
```

枚举单例的优点是：

*   写法极简。
*   天然防反射破坏。
*   天然支持序列化安全。
*   JVM 保证线程安全。

缺点是形式上不如普通类灵活，比如不适合继承其他类。

## 四、 常见使用场景

### 1. SDK 日志系统

整个 SDK 应该有统一日志级别、统一输出方式、统一线程安全策略。

```cpp
SdkLogger::instance().setLevel(1);
SdkLogger::instance().log(1, "live started");
```

### 2. 设备能力探测缓存

Android 音视频里经常要判断：

*   当前机型是否支持 H.265 硬编。
*   是否支持 Surface 输入编码。
*   是否支持特定颜色格式。
*   是否命中机型黑白名单。

这些能力通常初始化后全局复用，不应该每个模块都重复查询。

### 3. 全局配置中心

比如：

*   `enableLiveZeroCopy`
*   `enableAsyncSendAndABR`
*   `enableHardwareDecode`
*   日志等级、实验开关、灰度参数

这类配置如果散落在各个模块里，很容易出现状态不一致。

### 4. 线程池 / 调度器

线程池本身是资源管理器。如果每个模块各自创建线程池，可能导致线程数失控。统一调度器可以限制并发度、统一命名线程、统一观测任务耗时。

### 5. EventBus / MessageCenter

发布-订阅模式里的事件中心通常也是单例或由全局上下文持有。它需要作为系统级事件分发入口。

## 五、 常踩的坑（避坑指南）

### 1. 把单例当全局变量滥用

**现象**：所有东西都做成单例，哪里都能访问，结果代码依赖关系变得非常隐蔽。

```cpp
class VideoEncoder {
public:
    void encode() {
        GlobalConfig::instance().enableHardwareEncode();
        SdkLogger::instance().log(1, "encode");
        EventBus::instance().publish("encode.start");
    }
};
```

这会导致 `VideoEncoder` 的真实依赖藏在函数内部，测试和复用都变困难。

**建议**：真正的核心业务对象优先通过构造函数注入依赖。单例更适合基础设施对象，比如日志、配置、能力缓存。

### 2. 单例生命周期顺序问题

**现象**：一个单例析构时使用了另一个已经析构的单例，导致进程退出阶段 Crash。这类问题叫 **Static Deinitialization Order Fiasco**。

```cpp
class A {
public:
    ~A() {
        B::instance().doSomething(); // 如果 B 已经析构，这里就危险
    }
};
```

**建议**：

*   避免在单例析构函数里依赖其他单例。
*   对进程级基础设施对象，可以接受“进程退出时不主动析构”的策略。
*   更工程化的方式是由 SDK 上下文统一管理初始化和反初始化顺序。

### 3. 构造函数里做太重的事情

**现象**：第一次调用 `instance()` 时突然卡顿，因为构造函数里做了 I/O、硬件枚举、网络请求。

```cpp
class CodecCapabilityCache {
private:
    CodecCapabilityCache() {
        scanAllMediaCodec(); // 可能很慢
    }
};
```

**建议**：

*   构造函数只做轻量初始化。
*   重任务拆到显式 `init()`，并在 SDK 初始化阶段调用。
*   对耗时结果做缓存，避免核心链路临时触发。

### 4. 单例内部状态不是线程安全的

单例只保证“实例唯一”，不等于“所有成员函数自动线程安全”。

```cpp
class Counter {
public:
    static Counter& instance() {
        static Counter counter;
        return counter;
    }

    void increase() {
        ++count_; // 多线程下数据竞争
    }

private:
    int count_ = 0;
};
```

**建议**：如果单例会被多线程访问，内部共享状态仍然要用 `mutex`、`atomic` 或无锁队列等机制保护。

### 5. 单例影响单元测试

**现象**：单例状态在不同测试用例之间残留，导致测试互相污染。

**建议**：

*   业务逻辑不要过度依赖单例，尽量依赖接口。
*   测试时允许注入 Mock 实现。
*   对确实需要单例的配置对象，提供明确的 `resetForTest()`，但不要暴露给正式业务代码。

## 六、 面试高频问题与标准回答

### Q1：什么是单例模式？

**🗣️ 标准回答：**
> “单例模式就是保证一个类在整个进程里只有一个实例，并提供一个全局访问点。它通常通过私有构造函数禁止外部 new，通过静态方法返回唯一实例。它适合日志系统、配置中心、线程池、设备能力缓存这类天然全局唯一的对象。”

### Q2：C++ 里怎么写线程安全单例？

**🗣️ 标准回答：**
> “C++11 之后我最推荐 Meyers Singleton，也就是函数内局部静态变量。它的核心写法是在 `instance()` 方法里定义一个 `static` 局部对象，然后返回它的引用。C++11 标准保证局部静态变量初始化是线程安全的，所以多线程第一次同时访问时，也只会有一个线程真正执行构造函数。相比手写双重检查锁，它更简单，也不容易写错内存序。”

**结合代码说明：**

```cpp
class SdkLogger {
public:
    static SdkLogger& instance() {
        static SdkLogger logger; // C++11 保证初始化线程安全，只会构造一次
        return logger;
    }

    void log(const std::string& message) {
        // 写日志
    }

private:
    SdkLogger() = default; // 构造函数私有，外部不能 new

    SdkLogger(const SdkLogger&) = delete;
    SdkLogger& operator=(const SdkLogger&) = delete;
};
```

这段代码有三个关键点：

*   **构造函数私有化**：外部不能直接 `SdkLogger logger;`，只能通过 `SdkLogger::instance()` 获取对象。
*   **函数内局部静态变量**：`static SdkLogger logger;` 第一次调用 `instance()` 时创建，后续调用都返回同一个对象。
*   **禁止拷贝和赋值**：`= delete` 防止别人通过 `SdkLogger copy = SdkLogger::instance();` 复制出第二个对象。

使用时非常简单：

```cpp
SdkLogger::instance().log("encoder started");
SdkLogger::instance().log("network sender started");
```

上面两次调用拿到的是同一个 `SdkLogger` 对象。面试时可以补一句：**单例的初始化是线程安全的，但 `log()` 内部如果会被多个线程同时调用，成员变量或文件写入仍然要自己加锁保护。**

### Q3：Java DCL 为什么一定要加 `volatile`？

**🗣️ 标准回答：**
> “因为 `new Object()` 不是一个原子动作，可能被拆成分配内存、赋值引用、执行构造函数。如果没有 `volatile`，指令重排序可能导致引用先赋值，另一个线程看到对象非空后拿到一个还没初始化完成的半成品对象。`volatile` 可以保证可见性，并禁止这种关键重排序，所以 Java 的 DCL 必须配合 `volatile`。”

### Q4：单例模式有什么缺点？

**🗣️ 标准回答：**
> “单例最大的缺点是容易被滥用成全局变量，导致依赖关系隐藏、测试困难、模块耦合变强。第二个问题是生命周期顺序，尤其 C++ 静态对象在退出阶段可能有析构顺序问题。第三个问题是线程安全，单例只保证实例唯一，不代表内部状态自动线程安全。所以我一般只把日志、配置、能力缓存这类基础设施做成单例，不会把核心业务对象随便单例化。”

### Q5：饿汉式和懒汉式有什么区别？

**🗣️ 标准回答：**
> “饿汉式是在程序启动或类加载时就创建实例，实现简单，线程安全通常也容易保证，但缺点是不管用不用都会初始化。懒汉式是第一次使用时才创建，节省资源，但多线程下必须处理并发初始化问题。C++11 的局部静态变量写法本质上就是线程安全的懒加载。”

### Q6：你在项目里怎么用单例？

**🗣️ 标准回答参考（结合音视频/SDK）：**
> “在音视频 SDK 里，我会把日志系统、设备能力缓存、全局配置中心这类基础设施做成单例。比如 Android 推流前要判断当前机型是否支持硬编、Surface 输入、H.265，这些能力探测结果不应该每个模块都重复查一遍，所以可以放到 `CodecCapabilityCache` 里统一缓存。这样编码器、推流器、降级策略都访问同一份能力结果，避免状态不一致。但核心业务对象，比如某一路播放器或某一路推流实例，我不会做成单例，因为它们可能同时存在多路实例。”

---

## 七、 项目实战话术（STAR 法则版）

### 1. 设备能力缓存单例

> “在 Android 音视频 SDK 里，硬件编解码能力和机型兼容性判断是一个典型的全局基础设施。比如推流前要判断是否支持 H.265、是否支持 Surface 输入编码、是否命中硬编黑名单。如果每个模块都临时查询一次，不仅有性能浪费，还可能因为查询时机不同导致状态不一致。
>
> 我的做法是把这类结果收敛到一个类似 `CodecCapabilityCache` 的单例里，在 SDK 初始化阶段完成探测和缓存。后续编码器选择、软硬编降级、零拷贝路径开关都读同一份结果。这样全局决策一致，也避免核心链路中临时做耗时探测。
>
> 但我会强调边界：单例只承载设备能力这类进程级事实，不承载某一路推流的业务状态。因为推流实例可能同时存在多路，强行单例化反而会破坏扩展性。”

### 2. 日志系统单例

> “日志系统也适合做单例，因为整个 SDK 应该有统一的日志级别、输出目标和线程安全策略。编码、渲染、推流、网络模块都通过同一个日志入口输出，这样排查问题时日志格式和时序更一致。
>
> 但日志单例内部必须处理多线程写入，比如用 mutex 或异步日志队列保护文件写入。否则单例只解决了实例唯一，没有解决多线程安全问题。在音视频这种多线程场景里，这个区别很重要。”

---

## 八、 一句话总结

**单例模式解决的是“全局唯一资源如何被统一创建、统一访问、统一管理”的问题；但它只适合基础设施，不适合拿来隐藏业务依赖。**

如果面试官问怎么选，可以这样答：

> “日志、配置、设备能力缓存、全局线程池这类进程级基础设施可以考虑单例；播放器实例、推流实例、业务页面这类可能有多份且带业务状态的对象，不应该做成单例。C++ 里我优先用 Meyers Singleton，Java 里可以用 `volatile` DCL、静态内部类或枚举单例。”
