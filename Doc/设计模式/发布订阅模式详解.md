# 发布-订阅模式 (Publish-Subscribe Pattern) 深度解析与面试指南

发布-订阅模式（Publish-Subscribe，简称 Pub-Sub）是一种常见的消息通信模式。它的核心目标是：**让消息的发布者和订阅者彻底解耦，双方不需要知道彼此是谁，只需要围绕统一的事件主题（Topic / EventName）通信**。

在音视频 SDK、移动端业务架构、事件总线、消息队列、日志监控系统中，发布-订阅模式非常常见。比如：弱网事件、帧率下降事件、码率切换事件、首帧渲染事件、推流失败事件，都可以通过事件总线广播给不同模块处理。

本文参考《观察者模式详解》的结构，从代码场景、核心原理、使用场景、工程坑点和面试高频问题五个角度讲清楚发布-订阅模式。

---

## 零、 先用代码看：什么时候会用到发布-订阅模式？

发布-订阅模式最常见的触发场景是：**一个事件会被很多模块关心，但事件源不应该知道这些模块是谁，甚至这些模块可能来自完全不同的业务层或线程。**

以 Android 4K 直播推流为例，底层直播引擎可能产生这些事件：

*   网络发送队列堆积，触发弱网事件。
*   编码帧率下降，触发性能告警。
*   ABR 策略调整码率，触发码率变更事件。
*   推流断开，触发重连、UI 提示、日志上报。

这些事件可能被很多模块消费：

*   UI 层：展示「网络不佳」提示。
*   QoS 模块：记录帧率、码率、丢帧曲线。
*   ABR 控制器：根据弱网事件降低码率。
*   日志模块：上报故障现场。
*   Debug 面板：展示实时状态。

如果直播引擎直接调用这些模块，就会迅速变成强耦合。

### 1. 不用发布-订阅：核心引擎硬编码所有业务方

```cpp
class LiveRoomPage {
public:
    void showWeakNetworkTip() {
        // UI 提示：当前网络较差
    }
};

class QosReporter {
public:
    void reportQueueSize(int queueSize) {
        // 上报发送队列长度
    }
};

class AbrController {
public:
    void onNetworkCongestion() {
        // 触发降码率
    }
};

class DebugPanel {
public:
    void updateQueueSize(int queueSize) {
        // 调试面板刷新
    }
};

class LiveEngine {
private:
    LiveRoomPage* page_ = nullptr;
    QosReporter* reporter_ = nullptr;
    AbrController* abr_ = nullptr;
    DebugPanel* debugPanel_ = nullptr;

public:
    void onSendQueueChanged(int queueSize) {
        if (reporter_) {
            reporter_->reportQueueSize(queueSize);
        }

        if (debugPanel_) {
            debugPanel_->updateQueueSize(queueSize);
        }

        if (queueSize > 60) {
            if (page_) {
                page_->showWeakNetworkTip();
            }
            if (abr_) {
                abr_->onNetworkCongestion();
            }
        }
    }
};
```

这段代码能跑，但问题很明显：

*   `LiveEngine` 知道了 UI、QoS、ABR、Debug 面板这些具体业务类。
*   新增一个消费者，比如远端诊断模块，就必须修改 `LiveEngine`。
*   弱网事件本来是一个系统级事件，却被写死成一堆对象调用。
*   如果某个消费者耗时，比如日志上报卡住，还可能拖慢底层推流线程。

这时就很适合引入发布-订阅模式。

### 2. 使用发布-订阅：引入 EventBus / Broker

发布-订阅模式的核心是加一个「中间人」：**Broker / EventBus / MessageCenter**。

发布者只负责发布事件：

```cpp
eventBus.publish("live.queue.high", QueueHighEvent{queueSize});
```

订阅者只负责订阅自己关心的 Topic：

```cpp
eventBus.subscribe("live.queue.high", [](const Event& event) {
    // 处理弱网队列堆积事件
});
```

发布者不知道谁订阅，订阅者也不知道谁发布。双方只通过 Topic 和事件数据通信。

### 3. 一个简化版 C++ EventBus

下面先写一个最小可理解版本，重点看结构，不追求完整工业级能力。

```cpp
#include <functional>
#include <string>
#include <unordered_map>
#include <vector>

struct Event {
    virtual ~Event() = default;
};

struct QueueHighEvent : public Event {
    int queueSize = 0;
};

class EventBus {
public:
    using Handler = std::function<void(const Event&)>;

    void subscribe(const std::string& topic, Handler handler) {
        handlers_[topic].push_back(std::move(handler));
    }

    void publish(const std::string& topic, const Event& event) {
        auto it = handlers_.find(topic);
        if (it == handlers_.end()) {
            return;
        }

        for (const Handler& handler : it->second) {
            handler(event);
        }
    }

private:
    std::unordered_map<std::string, std::vector<Handler>> handlers_;
};
```

使用方式如下：

```cpp
EventBus eventBus;

eventBus.subscribe("live.queue.high", [](const Event& event) {
    const auto& e = static_cast<const QueueHighEvent&>(event);
    // UI 层：展示弱网提示
    // showWeakNetworkTip(e.queueSize);
});

eventBus.subscribe("live.queue.high", [](const Event& event) {
    const auto& e = static_cast<const QueueHighEvent&>(event);
    // ABR 模块：根据队列水位降低码率
    // abrController.reduceBitrate(e.queueSize);
});

QueueHighEvent event;
event.queueSize = 75;
eventBus.publish("live.queue.high", event);
```

此时 `LiveEngine` 只需要这样写：

```cpp
class LiveEngine {
public:
    explicit LiveEngine(EventBus& eventBus) : eventBus_(eventBus) {}

    void onSendQueueChanged(int queueSize) {
        if (queueSize > 60) {
            QueueHighEvent event;
            event.queueSize = queueSize;
            eventBus_.publish("live.queue.high", event);
        }
    }

private:
    EventBus& eventBus_;
};
```

这样一来，`LiveEngine` 不再关心 UI、日志、ABR、Debug 面板。以后新增消费者，只需要新增一段订阅逻辑，不需要修改推流引擎。

### 4. 从代码抽象出适用条件

看到下面几种情况，就可以考虑发布-订阅模式：

1.  **事件是系统级的，不只属于某一个对象**：比如弱网、推流断开、码率变化、性能告警。
2.  **发布者完全不应该知道订阅者是谁**：底层推流模块不应该依赖 UI、日志、监控、ABR 的具体实现。
3.  **订阅者很多，而且经常变化**：Debug 面板、埋点、实验策略、远端诊断都可能动态加入。
4.  **事件可以异步处理**：日志上报、监控统计、远端诊断没必要阻塞底层核心线程。
5.  **希望按 Topic 分类管理事件**：比如 `live.queue.high`、`live.bitrate.changed`、`player.first_frame.rendered`。

一句话总结：**发布-订阅模式适合解决“系统里有很多事件，发布者不想知道谁消费，订阅者也不关心谁发布，只围绕 Topic 解耦通信”的问题。**

## 一、 定义与核心原理

### 1. 官方定义

发布-订阅模式定义了一种通过中间消息代理（Broker）进行通信的模式。发布者将消息发布到某个主题（Topic），订阅者订阅自己感兴趣的主题；当该主题有消息到达时，Broker 负责把消息分发给对应订阅者。

它和观察者模式思想相近，都是“一处变化，多处响应”，但发布-订阅模式的解耦程度更高。

### 2. 核心角色

发布-订阅模式通常包含以下四个核心角色：

*   **Publisher（发布者）**：负责产生事件或消息，只知道 Topic，不知道订阅者是谁。
*   **Subscriber（订阅者）**：负责订阅感兴趣的 Topic，并处理消息，不需要知道发布者是谁。
*   **Broker / EventBus（消息中间人）**：负责维护 Topic 与订阅者的映射关系，并完成消息分发。
*   **Topic / EventName（主题）**：消息分类的逻辑名称，比如 `live.network.bad`、`player.first_frame`。

### 3. 工作流程

完整流程可以概括为四步：

1.  订阅者向 Broker 注册：我关心 `live.queue.high`。
2.  发布者向 Broker 发布：`live.queue.high` 事件发生了。
3.  Broker 查找这个 Topic 下的所有订阅者。
4.  Broker 将事件分发给这些订阅者，同步或异步执行。

```text
Publisher
   |
   | publish("live.queue.high", event)
   v
Broker / EventBus
   |
   | dispatch by topic
   v
Subscriber A / Subscriber B / Subscriber C
```

### 4. 同步 Pub-Sub 与异步 Pub-Sub

发布-订阅模式不一定天然异步，它可以分为两种实现。

*   **同步 EventBus**：`publish()` 内部直接遍历 handler 并调用。实现简单，但某个订阅者耗时会阻塞发布者线程。
*   **异步 EventBus**：`publish()` 只把事件塞进队列，后台线程或线程池负责消费。发布者很快返回，更适合日志、监控、跨线程通信。

音视频底层场景里，如果事件来自推流核心线程，通常要特别小心：**不能让 UI、日志、网络上报这类订阅者反向阻塞推流线程**。

## 二、 常见使用场景

### 1. 音视频 SDK 的系统级事件分发

比如直播 SDK 中：

*   `live.first_frame.rendered`：首帧渲染完成。
*   `live.network.weak`：弱网告警。
*   `live.bitrate.changed`：ABR 调整码率。
*   `live.push.disconnected`：推流断开。
*   `live.encoder.fps_drop`：编码帧率下降。

这些事件通常会同时影响 UI、日志、QoS、调试面板、策略控制模块，非常适合通过 Pub-Sub 分发。

### 2. App 内全局事件总线

例如登录状态变化、主题切换、语言切换、网络状态变化。发布者不应该知道哪些页面在监听，页面只订阅自己关心的事件。

### 3. 跨模块通信

当系统被拆成多个业务模块后，模块之间不希望互相 import 或直接调用，可以通过事件中心传递系统级事件。

### 4. 后端消息队列

Kafka、RabbitMQ、Redis Pub/Sub 都是发布-订阅思想的典型实现。它们通常支持异步、削峰、持久化、重试、消费组等更复杂能力。

### 5. 监控、日志、埋点系统

业务代码只发布事件，监控模块、日志模块、埋点模块各自订阅处理。这样可以避免业务代码里到处散落日志上报逻辑。

## 三、 发布-订阅模式 vs 观察者模式

这两个模式非常像，但面试时一定要讲清楚区别。

| 对比维度 | 观察者模式 | 发布-订阅模式 |
|---|---|---|
| 通信方式 | 被观察者直接维护观察者列表并调用 | 发布者通过 Broker / EventBus 间接分发 |
| 是否有中间人 | 通常没有 | 一定有逻辑上的中间人 |
| 耦合程度 | 被观察者知道观察者接口 | 发布者和订阅者互相不知道 |
| 适用范围 | 对象级、同模块、强类型回调 | 系统级、跨模块、Topic 化事件 |
| 同步/异步 | 多数是同步直接调用 | 可同步，也常做成异步队列 |
| 类型约束 | 接口方法强类型，如 `onFpsChanged(int)` | 常通过 Topic + Event payload，灵活但更容易写错 |

### 什么时候用观察者模式？

如果是**对象级、近距离、强类型、低延迟回调**，优先用观察者模式。

例如：播放器内部 `PlayerEngine` 通知 `PlayerListener`：

```cpp
class PlayerListener {
public:
    virtual ~PlayerListener() = default;
    virtual void onFirstFrameRendered() = 0;
    virtual void onError(int code) = 0;
};
```

这种场景下，事件关系明确、接口强类型、调用链短，用观察者模式更直接。

### 什么时候用发布-订阅模式？

如果是**系统级、远距离、Topic 化、可异步处理的事件**，优先用发布-订阅模式。

例如：直播弱网事件可能同时被 UI、ABR、日志、监控、Debug 面板消费。发布者不应该一个个持有它们的接口，这时 EventBus 更合适。

### 一句话判断标准

*   **我知道我要通知的是某类 Listener，只是不想依赖具体实现**：用观察者模式。
*   **我只知道发生了某个 Topic 事件，完全不想知道谁会处理**：用发布-订阅模式。

## 四、 常踩的坑（避坑指南）

发布-订阅模式解耦很强，但工程上也很容易失控。

### 1. Topic 字符串写错，编译期发现不了

**现象**：发布者写的是 `live.queue.high`，订阅者写成了 `live.queque.high`，程序不崩，但事件永远收不到。

**反面示例：**

```cpp
eventBus.publish("live.queue.high", event);
eventBus.subscribe("live.queque.high", handler); // 拼写错误，编译器发现不了
```

**解决方案：统一定义 Topic 常量或枚举。**

```cpp
namespace LiveTopics {
constexpr const char* kQueueHigh = "live.queue.high";
constexpr const char* kBitrateChanged = "live.bitrate.changed";
constexpr const char* kPushDisconnected = "live.push.disconnected";
}

eventBus.publish(LiveTopics::kQueueHigh, event);
eventBus.subscribe(LiveTopics::kQueueHigh, handler);
```

更严格的做法是用 `enum class EventType` 或模板化事件类型，减少字符串错误。

### 2. 订阅后忘记取消，导致内存泄漏或野回调

**现象**：页面销毁后没有取消订阅，EventBus 仍然保存它的回调。轻则页面泄漏，重则回调访问已销毁对象导致 Crash。

**危险写法：**

```cpp
class LiveRoomPage {
public:
    void onCreate(EventBus& eventBus) {
        eventBus.subscribe(LiveTopics::kQueueHigh, [this](const Event& event) {
            showWeakNetworkTip(); // 如果页面已销毁，这里的 this 可能悬空
        });
    }

private:
    void showWeakNetworkTip() {}
};
```

**解决方案一：返回订阅 Token，析构时自动取消。**

```cpp
class Subscription {
public:
    Subscription(EventBus* bus, int id) : bus_(bus), id_(id) {}

    ~Subscription() {
        if (bus_) {
            bus_->unsubscribe(id_);
        }
    }

private:
    EventBus* bus_ = nullptr;
    int id_ = 0;
};
```

实际项目里常用 RAII 思路：页面持有 `Subscription`，页面析构时自动解绑。

**解决方案二：回调里捕获弱引用。**

```cpp
std::weak_ptr<LiveRoomPage> weakPage = shared_from_this();

eventBus.subscribe(LiveTopics::kQueueHigh, [weakPage](const Event& event) {
    if (auto page = weakPage.lock()) {
        page->showWeakNetworkTip();
    }
});
```

### 3. 同步分发导致核心线程被订阅者拖慢

**现象**：推流线程调用 `publish()`，某个订阅者在回调里做网络上报或复杂计算，导致推流线程被卡住，表现为编码积压、发送队列上涨、掉帧。

**危险写法：**

```cpp
eventBus.subscribe(LiveTopics::kQueueHigh, [](const Event& event) {
    uploadLogToServer(event); // 网络 I/O，可能阻塞几百毫秒
});
```

**解决方案：核心线程只投递事件，耗时订阅者切到异步队列。**

```cpp
eventBus.subscribe(LiveTopics::kQueueHigh, [this](const Event& event) {
    asyncQueue_.post([eventCopy = cloneEvent(event)]() {
        uploadLogToServer(*eventCopy);
    });
});
```

面试里可以强调：**音视频核心链路最怕同步回调做重活，Pub-Sub 的解耦不能只看代码依赖，还要看线程和耗时是否解耦。**

### 4. 事件泛滥，系统变成“玄学调用链”

**现象**：所有模块都通过 EventBus 通信，代码里看不到直接调用关系，排查问题时不知道某个事件到底被谁消费了。

**解决方案：**

*   只把**系统级事件**放进 EventBus，不要把普通函数调用也改成事件。
*   Topic 命名要有层级，例如 `live.network.weak`、`player.render.first_frame`。
*   EventBus 支持调试日志：记录 publish 的 Topic、订阅者数量、耗时。
*   核心链路不要过度事件化，低延迟强类型路径仍优先用观察者或直接接口。

### 5. 事件队列无上限，弱网下内存暴涨

**现象**：异步 EventBus 如果队列无限增长，在弱网、日志服务卡顿、消费线程阻塞时，事件会不断堆积，最终内存暴涨。

**解决方案：**

*   给队列设置容量上限。
*   对低价值高频事件做合并或采样，比如 FPS 变化事件每秒最多上报一次。
*   对状态类事件只保留最新值，比如码率变化、队列水位。
*   对关键事件和普通事件分优先级，不能让日志事件挤爆关键控制事件。

## 五、 面试高频问题与标准回答

### Q1：发布-订阅模式是什么？

**🗣️ 标准回答：**
> “发布-订阅模式是一种通过中间 Broker 或 EventBus 解耦通信双方的设计模式。发布者只负责把事件发布到某个 Topic，不知道谁会消费；订阅者只订阅自己关心的 Topic，也不需要知道事件是谁发的。它适合系统级事件分发，比如弱网、日志、监控、码率变化这类一处发生、多处响应的场景。”

### Q2：发布-订阅模式和观察者模式有什么区别？

**🗣️ 标准回答：**
> “观察者模式是对象级的直接通知，被观察者内部维护观察者列表，状态变化后直接调用观察者接口，所以它更强类型、路径更短，但双方至少通过接口互相感知。发布-订阅模式中间多了一个 Broker，发布者和订阅者互相不知道，只通过 Topic 通信，解耦更彻底，更适合跨模块、跨线程甚至分布式消息。但代价是调用链更隐蔽，Topic 和事件 payload 也更需要规范管理。”

### Q3：什么情况下你会用发布-订阅，而不是观察者？

**🗣️ 标准回答：**
> “如果是一个对象明确通知一类 Listener，比如播放器通知 `PlayerListener` 首帧出来了，我会用观察者模式。但如果是系统级事件，比如直播弱网、码率变化、推流断开，这些事件可能被 UI、QoS、ABR、日志、Debug 面板同时消费，我会用发布-订阅。因为发布者不应该关心有哪些消费者，后续新增消费者也不应该修改底层推流引擎。”

### Q4：发布-订阅模式有什么缺点？

**🗣️ 标准回答：**
> “它最大的缺点是调用链不直观。代码里看不到谁直接调用谁，排查问题时需要从 Topic 反查订阅者。第二个问题是 Topic 字符串和事件 payload 如果没有规范，容易出现拼写错误、类型不匹配。第三个问题是生命周期和线程问题，订阅后忘记取消会泄漏，同步回调做重活会阻塞发布线程，异步队列无上限又可能导致内存堆积。”

### Q5：如何设计一个比较稳的 EventBus？

**🗣️ 标准回答：**
> “我会从四个方面设计。第一，Topic 统一管理，避免字符串散落；第二，订阅要返回 Token 或 Subscription，用 RAII 或生命周期绑定自动取消；第三，发布线程和消费线程要分清楚，核心音视频线程只投递事件，不执行耗时逻辑；第四，异步队列要有容量和丢弃策略，高频状态事件可以合并，关键控制事件要保证优先级。这样 EventBus 才不会从解耦工具变成事故源。”

### Q6：你在项目里怎么用发布-订阅？

**🗣️ 标准回答参考（结合音视频/SDK）：**
> “在直播推流优化里，我们可以把弱网和 QoS 状态做成发布-订阅事件。底层发送队列发现水位超过阈值，比如超过 60 帧，就发布 `live.queue.high` 事件。UI 模块订阅后展示弱网提示，QoS 模块订阅后记录队列曲线，ABR 模块订阅后把目标码率下调 20%。这样底层发送线程不需要依赖 UI、日志和 ABR 的具体类，后续新增 Debug 面板也只要订阅同一个 Topic 就行。”

## 六、 项目实战话术（STAR 法则版）

### 1. 直播弱网与 ABR 事件分发

> “在 4K 直播推流项目里，我们遇到过弱网下发送队列堆积的问题。原始方案如果让发送模块直接调用 UI、日志、ABR 策略，会让底层推流链路和业务层耦合得很死。
>
> 我的思路是把这类状态变化抽象成系统级事件，比如 `live.queue.high`、`live.bitrate.changed`。发送队列只负责发布队列水位事件，UI、QoS、ABR 分别订阅自己关心的 Topic。比如队列超过 60 帧时，ABR 订阅者把目标码率降低 20%，UI 订阅者展示弱网提示，QoS 订阅者记录曲线。
>
> 这样做的收益是：推流核心链路只关心数据发送，不依赖具体业务模块；新增一个 Debug 面板或远端诊断模块时，也不需要修改发送模块。这个思路和我们异步发送队列、动态码率 ABR 的优化方向是一致的，都是把核心链路和外围业务解耦，避免弱网时互相拖慢。”

### 2. 播放器首帧、错误、性能事件分发

> “在播放器或预览链路里，首帧渲染、解码错误、渲染延时、缓冲状态都可能被多个模块关心。如果是强类型、低延迟的播放器回调，我会保留观察者模式；但对于日志、监控、调试面板这类非核心消费者，我会转成发布-订阅事件。
>
> 比如预览延时优化中，我们会在网络接收、解码、渲染各节点打时间戳。核心调度逻辑不应该直接依赖所有展示和上报模块，所以可以把统计结果发布成 `preview.latency.updated` 事件，由调试面板和 QoS 模块订阅。这样既不污染核心渲染链路，也方便后续扩展排查工具。”

---

## 七、 一句话总结

**观察者模式解决的是“一个对象如何通知一批 Listener”；发布-订阅模式解决的是“一个系统事件如何通过 Topic 通知一批互不认识的消费者”。**

如果面试官问怎么选，可以这样答：

> “对象级、强类型、低延迟回调用观察者；系统级、跨模块、Topic 化、可异步处理的事件用发布-订阅。音视频核心链路里，我会把首帧、错误这类强类型回调交给观察者，把弱网、QoS、日志、监控这类系统事件交给发布-订阅。”
