# 工厂模式 (Factory Pattern) 深度解析与面试指南

工厂模式是创建型设计模式中最常见、也最容易被面试官追问的一类模式。它的核心目标是：**把对象创建逻辑从业务代码中抽离出来，让业务方依赖抽象接口，而不是到处 `new` 具体类。**

在音视频 SDK 里，工厂模式非常常见：比如根据机型能力选择硬编还是软编、根据协议选择 RTMP/SRT/WebRTC 推流器、根据渲染平台选择 OpenGL/Vulkan/Metal 渲染器。它解决的不是“对象参数太多怎么配置”，而是 **“到底应该创建哪一种具体对象”**。

本文从面试速记、概念原理、三种工厂模式区别、音视频代码示例、常见误区、踩坑指南和高频问答几个角度系统讲清楚工厂模式。

---

## 一、 面试速记

### 1. 一句话核心

> **工厂模式负责把 `new` 具体类的逻辑封装起来，让业务代码面向接口编程。业务方只关心拿到一个能用的抽象对象，不关心这个对象到底是哪个具体类创建出来的。**

### 2. 面试关键词

*   **创建型模式**
*   **封装对象创建**
*   **面向接口编程**
*   **解耦业务逻辑和具体实现**
*   **简单工厂**
*   **工厂方法**
*   **抽象工厂**
*   **开闭原则**
*   **产品族**

### 3. 高频速查表

| 问题 | 一句话答案 |
| :--- | :--- |
| 工厂模式解决什么问题？ | 把创建具体对象的逻辑集中管理，业务代码只依赖抽象接口。 |
| 简单工厂是什么？ | 一个工厂函数里用 `switch/if` 根据类型创建不同产品。 |
| 工厂方法是什么？ | 把创建对象的职责下放给子类工厂，每个工厂创建一种产品。 |
| 抽象工厂是什么？ | 创建一整族相关对象，比如同一平台的一组编码器、解码器、渲染器。 |
| 工厂和 Builder 区别？ | 工厂解决“创建哪个类”，Builder 解决“一个复杂对象怎么配置”。 |

## 二、 先用代码看：为什么需要工厂模式？

以音视频 SDK 的编码器选择为例，推流前需要根据配置和设备能力选择编码器：

*   优先使用 `MediaCodec` 硬件编码器。
*   某些机型硬编不稳定时，降级到 FFmpeg/x264 软件编码器。
*   如果用户选择 H.265，但设备不支持 HEVC 硬编，也要降级或报错。

### 1. 不用工厂：业务代码里到处 `if-else + new`

```cpp
class VideoEncoder {
public:
    virtual ~VideoEncoder() = default;
    virtual bool open() = 0;
    virtual bool encodeFrame() = 0;
};

class MediaCodecEncoder : public VideoEncoder {
public:
    bool open() override { return true; }
    bool encodeFrame() override { return true; }
};

class X264Encoder : public VideoEncoder {
public:
    bool open() override { return true; }
    bool encodeFrame() override { return true; }
};

class LivePusher {
public:
    bool start(bool useHardwareEncode, bool hardwareSupported) {
        if (useHardwareEncode && hardwareSupported) {
            encoder_ = std::make_unique<MediaCodecEncoder>();
        } else {
            encoder_ = std::make_unique<X264Encoder>();
        }

        return encoder_->open();
    }

private:
    std::unique_ptr<VideoEncoder> encoder_;
};
```

这段代码能跑，但问题是：

*   `LivePusher` 既负责推流，又负责选择具体编码器，职责混在一起。
*   后续新增 `H265MediaCodecEncoder`、`Av1Encoder`、机型黑名单，`LivePusher` 会不断膨胀。
*   其他模块如果也要创建编码器，可能复制一份类似逻辑，导致规则不一致。

### 2. 使用工厂：把创建逻辑收敛到一个地方

```cpp
enum class EncoderType {
    HardwareH264,
    SoftwareH264,
};

class EncoderFactory {
public:
    static std::unique_ptr<VideoEncoder> create(EncoderType type) {
        switch (type) {
            case EncoderType::HardwareH264:
                return std::make_unique<MediaCodecEncoder>();
            case EncoderType::SoftwareH264:
                return std::make_unique<X264Encoder>();
            default:
                return nullptr;
        }
    }
};
```

业务代码变成：

```cpp
class LivePusher {
public:
    bool start(EncoderType type) {
        encoder_ = EncoderFactory::create(type);
        if (!encoder_) {
            return false;
        }
        return encoder_->open();
    }

private:
    std::unique_ptr<VideoEncoder> encoder_;
};
```

这就是工厂模式的基本价值：

*   业务代码只依赖 `VideoEncoder` 抽象接口。
*   具体创建逻辑集中到 `EncoderFactory`。
*   新增编码器时，业务代码不一定要到处改。

## 三、 简单工厂、工厂方法、抽象工厂

工厂模式经常被拆成三种：**简单工厂、工厂方法、抽象工厂**。面试时最容易问它们的区别。

### 1. 简单工厂（Simple Factory）

简单工厂不是 GoF 23 种设计模式之一，但工程中最常见。

它的特点是：**一个工厂类或工厂函数，根据参数决定创建哪一种具体产品。**

```cpp
enum class CodecType {
    H264Hardware,
    H264Software,
    H265Hardware,
};

class VideoEncoderFactory {
public:
    static std::unique_ptr<VideoEncoder> create(CodecType type) {
        switch (type) {
            case CodecType::H264Hardware:
                return std::make_unique<MediaCodecEncoder>();
            case CodecType::H264Software:
                return std::make_unique<X264Encoder>();
            case CodecType::H265Hardware:
                return std::make_unique<HevcMediaCodecEncoder>();
            default:
                return nullptr;
        }
    }
};
```

优点：

*   简单直接。
*   适合产品种类不多的场景。
*   创建逻辑集中，业务代码更干净。

缺点：

*   新增产品时要修改 `switch`，不完全符合开闭原则。
*   产品越来越多时，工厂函数会变成巨大分支。

面试里可以这样说：

> “简单工厂适合产品种类少、变化不频繁的场景。它虽然不完全符合开闭原则，但工程上非常实用。”

### 2. 工厂方法（Factory Method）

工厂方法的核心是：**定义一个创建产品的抽象工厂接口，让不同子类工厂决定创建哪种具体产品。**

先定义产品接口：

```cpp
class VideoEncoder {
public:
    virtual ~VideoEncoder() = default;
    virtual bool open() = 0;
    virtual bool encodeFrame() = 0;
};
```

定义工厂接口：

```cpp
class EncoderFactory {
public:
    virtual ~EncoderFactory() = default;
    virtual std::unique_ptr<VideoEncoder> createEncoder() = 0;
};
```

具体工厂：

```cpp
class HardwareEncoderFactory : public EncoderFactory {
public:
    std::unique_ptr<VideoEncoder> createEncoder() override {
        return std::make_unique<MediaCodecEncoder>();
    }
};

class SoftwareEncoderFactory : public EncoderFactory {
public:
    std::unique_ptr<VideoEncoder> createEncoder() override {
        return std::make_unique<X264Encoder>();
    }
};
```

业务代码：

```cpp
class LivePusher {
public:
    explicit LivePusher(std::unique_ptr<EncoderFactory> factory)
        : factory_(std::move(factory)) {}

    bool start() {
        encoder_ = factory_->createEncoder();
        return encoder_ && encoder_->open();
    }

private:
    std::unique_ptr<EncoderFactory> factory_;
    std::unique_ptr<VideoEncoder> encoder_;
};
```

优点：

*   新增产品时，可以新增一个工厂子类，尽量少改旧工厂代码。
*   更符合开闭原则。
*   创建逻辑可以通过多态扩展。

缺点：

*   类数量增加。
*   如果产品类型很多，会出现大量工厂类。
*   对简单场景可能显得过度设计。

### 3. 抽象工厂（Abstract Factory）

抽象工厂解决的是：**创建一整族相关对象**。

比如同一套音视频后端可能包含：

*   编码器 `VideoEncoder`
*   解码器 `VideoDecoder`
*   渲染器 `VideoRenderer`

如果选择 Android 硬件后端，就应该创建：

```text
MediaCodecEncoder + MediaCodecDecoder + OpenGLRenderer
```

如果选择 FFmpeg 软件后端，就应该创建：

```text
X264Encoder + FFmpegDecoder + CpuRenderer
```

这时候单个工厂方法就不够了，因为你要保证一组对象来自同一个产品族。

产品接口：

```cpp
class VideoDecoder {
public:
    virtual ~VideoDecoder() = default;
    virtual bool decode() = 0;
};

class VideoRenderer {
public:
    virtual ~VideoRenderer() = default;
    virtual bool render() = 0;
};
```

抽象工厂接口：

```cpp
class AvPipelineFactory {
public:
    virtual ~AvPipelineFactory() = default;

    virtual std::unique_ptr<VideoEncoder> createEncoder() = 0;
    virtual std::unique_ptr<VideoDecoder> createDecoder() = 0;
    virtual std::unique_ptr<VideoRenderer> createRenderer() = 0;
};
```

具体工厂：

```cpp
class AndroidHardwarePipelineFactory : public AvPipelineFactory {
public:
    std::unique_ptr<VideoEncoder> createEncoder() override {
        return std::make_unique<MediaCodecEncoder>();
    }

    std::unique_ptr<VideoDecoder> createDecoder() override {
        return std::make_unique<MediaCodecDecoder>();
    }

    std::unique_ptr<VideoRenderer> createRenderer() override {
        return std::make_unique<OpenGLRenderer>();
    }
};

class SoftwarePipelineFactory : public AvPipelineFactory {
public:
    std::unique_ptr<VideoEncoder> createEncoder() override {
        return std::make_unique<X264Encoder>();
    }

    std::unique_ptr<VideoDecoder> createDecoder() override {
        return std::make_unique<FFmpegDecoder>();
    }

    std::unique_ptr<VideoRenderer> createRenderer() override {
        return std::make_unique<CpuRenderer>();
    }
};
```

业务方：

```cpp
class AvPipeline {
public:
    explicit AvPipeline(AvPipelineFactory& factory)
        : encoder_(factory.createEncoder()),
          decoder_(factory.createDecoder()),
          renderer_(factory.createRenderer()) {}

private:
    std::unique_ptr<VideoEncoder> encoder_;
    std::unique_ptr<VideoDecoder> decoder_;
    std::unique_ptr<VideoRenderer> renderer_;
};
```

优点：

*   能保证一组对象来自同一产品族。
*   适合跨平台、跨后端、成套组件创建。

缺点：

*   结构更重。
*   新增产品族比较方便，但新增产品维度很麻烦。比如突然要增加 `AudioResampler`，所有工厂都要改。

## 四、 三种工厂模式怎么选？

### 1. 产品种类少：简单工厂

比如只是选择硬编或软编：

```cpp
auto encoder = EncoderFactory::create(type);
```

这种情况下简单工厂足够，别为了设计模式而设计模式。

### 2. 产品经常扩展：工厂方法

如果后续可能新增很多编码器实现，并且希望通过新增类扩展而不是改大 `switch`，可以考虑工厂方法。

```text
MediaCodecEncoderFactory
X264EncoderFactory
HevcEncoderFactory
Av1EncoderFactory
```

### 3. 需要创建一整套组件：抽象工厂

如果你要保证编码器、解码器、渲染器来自同一套后端，就用抽象工厂。

```text
AndroidHardwarePipelineFactory
SoftwarePipelineFactory
AppleVideoToolboxPipelineFactory
```

### 4. 面试一句话判断

> **简单工厂**适合少量产品、快速收敛创建逻辑；**工厂方法**适合单一产品维度的扩展；**抽象工厂**适合创建一整族相关产品。

## 五、 工厂模式 vs Builder vs 策略模式

### 1. 工厂模式 vs Builder

工厂模式关注的是：**创建哪一个具体类**。

```cpp
std::unique_ptr<VideoEncoder> encoder =
    EncoderFactory::create(CodecType::H264Hardware);
```

Builder 关注的是：**一个复杂对象的参数怎么配置**。

```cpp
LiveConfig config = LiveConfig::Builder()
    .setUrl("rtmp://example.com/live")
    .setResolution(3840, 2160)
    .setBitrate(8000000)
    .build();
```

一句话：

> 工厂解决“创建哪个对象”，Builder 解决“这个对象怎么配置”。

### 2. 工厂模式 vs 策略模式

策略模式关注的是：**运行时切换一套算法或行为**。

比如编码策略：

```cpp
class EncodeStrategy {
public:
    virtual ~EncodeStrategy() = default;
    virtual void encode() = 0;
};
```

工厂模式可以用来创建策略对象：

```cpp
std::unique_ptr<EncodeStrategy> strategy =
    EncodeStrategyFactory::create(deviceCapability);
```

也就是说：**策略模式负责“怎么做”，工厂模式负责“把谁创建出来”。**

在音视频里常见组合是：

```text
工厂模式创建 HardwareEncoder / SoftwareEncoder
策略模式在运行时决定当前用哪个编码策略
```

## 七、 常见误区与容易踩的坑

### 1. 误区：简单工厂一定很低级

简单工厂虽然不完全符合开闭原则，但在产品数量少、变化不频繁时非常实用。

```cpp
switch (type) {
    case EncoderType::Hardware:
        return std::make_unique<MediaCodecEncoder>();
    case EncoderType::Software:
        return std::make_unique<X264Encoder>();
}
```

不要一上来就抽象出一堆工厂类。设计模式是为了解决复杂度，不是制造复杂度。

### 2. 工厂里塞太多业务逻辑

工厂应该负责创建对象，不应该承担完整业务流程。

不推荐：

```cpp
class EncoderFactory {
public:
    static std::unique_ptr<VideoEncoder> createAndStartAndReport() {
        // 创建编码器
        // 打开编码器
        // 启动线程
        // 上报日志
        // 修改 UI
    }
};
```

推荐：

```cpp
auto encoder = EncoderFactory::create(config);
if (!encoder || !encoder->open()) {
    return false;
}
```

工厂可以做必要的能力判断和对象选择，但不要把整个启动流程都塞进去。

### 3. 简单工厂无限膨胀

如果 `switch` 越来越大：

```text
H264Hardware
H264Software
H265Hardware
H265Software
AV1Hardware
AV1Software
VendorPrivateEncoder
TestMockEncoder
```

说明简单工厂可能已经不够了。可以考虑：

*   拆分多个小工厂。
*   用注册表机制。
*   用工厂方法或抽象工厂。

### 4. 抽象工厂过度设计

如果你只是创建一个编码器，却搞出：

```text
AbstractEncoderFactory
ConcreteH264Factory
ConcreteH265Factory
FactoryProvider
FactoryManager
```

这就是过度设计。抽象工厂适合“产品族”，不是普通单个对象创建。

### 5. 工厂返回裸指针导致生命周期混乱

不推荐：

```cpp
VideoEncoder* createEncoder() {
    return new MediaCodecEncoder();
}
```

调用方必须记得 `delete`，容易泄漏。

推荐：

```cpp
std::unique_ptr<VideoEncoder> createEncoder() {
    return std::make_unique<MediaCodecEncoder>();
}
```

用 `std::unique_ptr` 表达所有权转移，更符合现代 C++ 风格。

### 6. 工厂隐藏错误原因

不要只返回 `nullptr`：

```cpp
auto encoder = EncoderFactory::create(config);
if (!encoder) {
    return false; // 不知道为什么失败
}
```

更工程化的方式是返回 `Result`：

```cpp
enum class EncoderCreateError {
    Ok,
    UnsupportedCodec,
    HardwareNotAvailable,
    DeviceInBlacklist,
};

struct EncoderCreateResult {
    EncoderCreateError error = EncoderCreateError::Ok;
    std::unique_ptr<VideoEncoder> encoder;
};
```

这样可以把错误码回调给 Java 层，或者写入 QoS 日志，方便排查线上问题。

## 八、 面试高频问题与标准回答

### Q1：什么是工厂模式？

**🗣️ 标准回答：**
> “工厂模式是一类创建型设计模式，核心是把对象创建逻辑从业务代码里抽出来。业务方不直接 `new` 具体类，而是通过工厂拿到抽象接口对象。这样业务代码依赖接口，不依赖具体实现，后续替换实现或新增实现时影响更小。”

### Q2：简单工厂、工厂方法、抽象工厂有什么区别？

**🗣️ 标准回答：**
> “简单工厂是一个工厂函数里用 `switch` 根据类型创建不同产品，实现简单但新增产品要改工厂。工厂方法是定义一个抽象工厂接口，让子类工厂决定创建哪种产品，更符合开闭原则，但类数量会增加。抽象工厂是创建一整族相关对象，比如同一套音视频后端里的编码器、解码器和渲染器，适合产品族场景。”

### Q3：工厂模式和 Builder 有什么区别？

**🗣️ 标准回答：**
> “工厂模式关注的是创建哪一个具体类，比如根据设备能力创建硬编编码器还是软编编码器。Builder 关注的是一个复杂对象内部参数怎么配置，比如推流配置里的 URL、分辨率、码率、ABR 开关。简单说，工厂解决‘创建谁’，Builder 解决‘怎么配置’。”

### Q4：工厂模式有什么缺点？

**🗣️ 标准回答：**
> “工厂模式的缺点主要是可能增加类数量和间接层。简单工厂如果产品越来越多，会变成巨大的 `switch`；工厂方法和抽象工厂虽然扩展性更好，但类数量会膨胀。如果场景很简单，直接构造对象可能更合适，不要为了模式而模式。”

### Q5：在 C++ 里实现工厂模式要注意什么？

**🗣️ 标准回答：**
> “我会优先让工厂返回 `std::unique_ptr<Interface>`，明确所有权转移，避免裸指针泄漏。失败时不要只返回空指针，最好有错误码或 `Result`，说明是不支持编码格式、硬件不可用还是机型黑名单。工厂内部可以做对象选择，但不要把启动线程、上报日志、UI 更新这些完整业务流程都塞进去。”

### Q6：你在项目里怎么用工厂模式？

**🗣️ 标准回答参考（结合音视频/SDK）：**
> “在音视频 SDK 里，工厂模式很适合用在编解码器选择上。比如推流初始化时，我们会根据用户配置、机型能力、硬编黑名单来选择 `MediaCodecEncoder` 还是 `X264Encoder`。上层推流管线只依赖 `VideoEncoder` 接口，不关心底层到底是硬编还是软编。这样后续新增 H.265、AV1 或厂商私有编码器时，主要改工厂和具体实现，推流主流程不用跟着到处改。”

## 九、 项目实战话术（STAR 法则版）

### 1. 编码器选择工厂

> “在 Android 音视频 SDK 里，硬件编码器存在严重机型差异。有些机型支持 H.264 硬编，有些支持 H.265 但不稳定，有些在特定分辨率下会失败。如果推流主流程里直接写一堆 `if-else` 去创建 `MediaCodecEncoder` 或 `X264Encoder`，主流程会越来越乱。
>
> 我的做法是抽象一个 `VideoEncoder` 接口，然后用 `EncoderFactory` 根据配置和设备能力创建具体编码器。推流管线只持有 `std::unique_ptr<VideoEncoder>`，不关心底层实现。工厂里可以集中处理硬编白名单、黑名单、编码格式支持情况。
>
> 这样做的收益是：主流程更干净，软硬编切换更容易，后续新增 H.265 或厂商私有编码器时也不会污染推流核心链路。”

### 2. 和 4K 直播优化项目结合

> “在 4K 直播优化里，我们做过零拷贝和异步发送 ABR 的参数化开关。类似这种能力后续如果继续演进，编码器创建也可以通过工厂统一收口。比如开启零拷贝时，工厂优先创建支持 Surface 输入的 `MediaCodecEncoder`；如果设备不支持或命中黑名单，就返回明确错误或降级到普通路径。
>
> 这样既能保留旧业务兼容，也能把复杂的机型能力判断集中在工厂层，而不是散落在推流管线各个节点里。”

---

## 十、 一句话总结

**工厂模式解决的是“具体对象由谁创建、创建哪一个实现”的问题；业务代码只依赖抽象接口，具体实现选择收敛到工厂。**

面试最后可以这样收束：

> “如果只是两三个稳定类型，用简单工厂就够了；如果产品类型经常扩展，可以考虑工厂方法；如果要创建一整套相关组件，比如编码器、解码器、渲染器来自同一后端，就用抽象工厂。音视频里最典型的例子就是根据设备能力创建硬编、软编或不同协议的推流器。”
