# 设计模式高频面试考点与项目实战回答（口语化版）

在音视频开发及底层 SDK 的面试中，设计模式也是一个高频考点。面试官问设计模式，不仅是考察你背没背过定义，更是考察你的**代码品味**和**架构设计能力**。

以下是常见的考点总结，以及最关键的“项目实战应用”的标准口语化回答。

---

## 第一部分：设计模式常规高频考点

### 1. 面向对象设计的六大原则（SOLID）是什么？
**🗣️ 面试标准回答：**
> “六大原则的核心是为了高内聚、低耦合。最常用的是**单一职责原则**（一个类只做一件事）、**开闭原则**（对扩展开放，对修改关闭，多用多态少修改老代码）、以及**依赖倒置原则**（面向接口编程，依赖抽象而不是具体实现）。剩下的还有里氏替换原则、接口隔离原则和迪米特法则。”

### 2. 单例模式如何保证线程安全？（C++ / Java）
**🗣️ 面试标准回答：**
> “在 C++11 之后，最优雅的线程安全单例就是 **Meyers' Singleton（局部静态变量法）**，代码只有几行，编译器在底层自动保证了局部静态变量初始化的线程安全性。如果是 Java 的话，最稳妥的是**双重检查锁（DCL, Double-Checked Locking）**加 `volatile` 关键字，或者直接用静态内部类、枚举来实现。”

### 3. 工厂模式（简单工厂 vs 工厂方法 vs 抽象工厂）区别？
**🗣️ 面试标准回答：**
> “**简单工厂**就是一个大 Switch 帮你创建对象，违背开闭原则；**工厂方法**是把创建对象的职责下发给子类工厂，符合开闭原则，但在增加产品种类时类的数量会爆炸；**抽象工厂**则是用来创建‘一整族’相关的对象（比如 Windows 风格的 UI 族和 Mac 风格的 UI 族），它解决了工厂方法面对多个产品族的痛点。”

### 4. 观察者模式有什么坑？如何防止内存泄漏？
**🗣️ 面试标准回答：**
> “观察者模式最大的坑就是**强引用导致的内存泄漏（Lapsed Listener Problem）**。如果被观察者生命周期很长（比如全局事件总线），而观察者（如 UI 页面）忘记在销毁时注销，就会导致 UI 页面无法释放。所以在实际开发中，我们通常会在底层采用弱引用（如 C++ 的 `std::weak_ptr` 或 JNI 的 `WeakGlobalRef`）来保存观察者列表，或者强制绑定页面生命周期来兜底。”

## 第二部分：高频杀手题：“你的项目中用到了哪些设计模式？挑一两个讲讲。”

这道题千万**不要**讲什么“我用单例模式做了个全局配置类”，太掉价了。
因为你应聘的是音视频/SDK岗位，建议挑选 **观察者模式（事件回调）** 和 **策略模式 / 建造者模式（音视频管线控制）** 来讲，这能立刻凸显你的业务深度。

### 实战案例 1：观察者模式（Observer Pattern）解决多端/跨语言状态同步
**业务场景：** SDK 底层（C++）需要把音视频帧、网络状态变化通知给上层（Java/iOS）。
**🗣️ 建议回答话术：**
> “在我们的音视频 SDK 项目里，**观察者模式**是用得最频繁的，主要用在底层 C++ 引擎向上层（Java/OC）的状态回调和数据分发上。
> 
> 音视频引擎在底层是一个独立运行的子系统，它不需要关心上层是怎么渲染界面的。所以我们定义了一套纯虚函数的 Listener 接口（也就是观察者）。当底层解码出一帧视频，或者信令网络断开时，引擎只需要遍历它的观察者列表，依次调用对应的接口方法即可。
> 
> **重点（秀肌肉）：** 为了解决 C++ 与上层跨语言调用容易引发的内存泄漏（比如 Java 页面销毁了但底层还在一直发回调），我们在底层保存观察者列表时，没有死板地用强引用，而是结合 JNI 封装了一套基于 `WeakGlobalRef`（弱全局引用）和 `std::shared_ptr` 的安全观察者管理机制。每次通知前都会检查观察者是否还存活，不仅做到了极致的解耦，还从架构上杜绝了崩溃和内存泄漏。”

**👨‍💻 面试官追问：“具体是怎么结合 WeakGlobalRef 和代码实现的？”**
（此时你可以拿出底层的代码实现逻辑来给他硬核讲解）

**结合代码的详细讲解：**
> “具体来说，这套机制分三层：
>
> 第一层是 **Java 对象生命周期**。C++ 层不会保存 Java 传下来的 `LocalRef`，因为 `LocalRef` 只在当前 JNI 调用栈有效；也不会直接保存 `GlobalRef`，因为 `GlobalRef` 是强引用，上层 Activity 销毁后仍然会被 C++ 持有，导致页面无法 GC。
>
> 所以注册监听器时，我们会把 Java Listener 转成 `WeakGlobalRef`。它可以跨 JNI 调用长期保存，但不会阻止 Java 对象被回收。
>
> 第二层是 **回调前安全检查**。底层准备回调时，先用 `IsSameObject(weakRef, nullptr)` 判断 Java 对象是否已经死亡；如果还活着，再用 `NewLocalRef(weakRef)` 临时提升成局部引用，保证本次 `CallVoidMethod` 期间对象有效，调用结束后立刻 `DeleteLocalRef`。
>
> 第三层是 **C++ 对象生命周期和并发安全**。C++ 不直接保存裸指针，而是用 `std::shared_ptr<JniWeakObserver>` 管理观察者包装对象。通知前先在锁内把观察者列表局部拷贝一份，让引用计数 +1，然后释放锁再逐个 JNI 回调。这样即使回调过程中另一个线程调用 `removeObserver()`，当前这次回调持有的 `shared_ptr` 也能保证对象不会中途析构。”

**对应的伪代码骨架（可以在白板或纸上手写核心逻辑）：**

Java 层页面注册监听：

```java
public class PreviewActivity extends Activity implements PlayerListener {
    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        nativeAddListener(this);
    }

    @Override
    protected void onDestroy() {
        super.onDestroy();
        nativeRemoveListener(this); // 业务层最好主动解绑，但 C++ 仍要兜底
    }

    @Override
    public void onError(int code) {
        // 展示错误或刷新 UI
    }
}
```

C++ 层封装弱引用观察者：

```cpp
class JniWeakObserver {
public:
    JniWeakObserver(JNIEnv* env, jobject listener)
        : weakListener_(env->NewWeakGlobalRef(listener)) {}

    ~JniWeakObserver() {
        JNIEnv* env = getJniEnv();
        if (weakListener_) {
            env->DeleteWeakGlobalRef(weakListener_);
        }
    }

    bool isAlive(JNIEnv* env) const {
        return weakListener_ && !env->IsSameObject(weakListener_, nullptr);
    }

    void notifyError(JNIEnv* env, int code) {
        if (!isAlive(env)) {
            return;
        }

        jobject localListener = env->NewLocalRef(weakListener_);
        if (!localListener) {
            return;
        }

        env->CallVoidMethod(localListener, onErrorMethodId_, code);
        env->DeleteLocalRef(localListener);
    }

private:
    jweak weakListener_ = nullptr;
    jmethodID onErrorMethodId_ = nullptr;
};
```

底层引擎通知所有观察者：

```cpp
class NativeEngine {
public:
    void addObserver(std::shared_ptr<JniWeakObserver> observer) {
        std::lock_guard<std::mutex> lock(mutex_);
        observers_.push_back(std::move(observer));
    }

    void notifyError(int code) {
        std::vector<std::shared_ptr<JniWeakObserver>> localObservers;
        {
            std::lock_guard<std::mutex> lock(mutex_);
            localObservers = observers_; // shared_ptr 拷贝，保证本次回调期间对象存活
        }

        JNIEnv* env = getJniEnv();
        for (const auto& observer : localObservers) {
            observer->notifyError(env, code);
        }
    }

private:
    std::mutex mutex_;
    std::vector<std::shared_ptr<JniWeakObserver>> observers_;
};
```

**这段代码的核心价值：**
> “`WeakGlobalRef` 解决 Java 页面泄漏问题；`NewLocalRef` 保证本次 JNI 调用期间对象有效；`shared_ptr` 局部拷贝解决 C++ 观察者在回调中途被移除导致的悬空问题；锁只保护列表拷贝，不包住真正的 JNI 回调，避免死锁和长时间阻塞。”

### 实战案例 2：策略模式（Strategy Pattern）应对复杂的音视频编解码切换
**业务场景：** 不同手机的硬件编解码器支持情况不同，需要动态切换 H.264 / H.265 或者软硬解。
**🗣️ 建议回答话术：**
> “另一个在音视频管线中用得很好的模式是**策略模式**，主要用来解决编解码器或核心算法的动态切换。
> 
> 在 Android 手机上，机型碎片化非常严重，有的时候硬件编码器（MediaCodec）会崩溃，我们就得降级到软件编码器（FFmpeg/x264）。如果是传统写法，代码里会塞满 `if-else`。
> 
> **重点（秀肌肉）：** 我们利用策略模式进行了重构。我们定义了一个统一的 `VideoEncoder` 接口，然后实现了两个具体的策略类：`HardwareEncoder` 和 `SoftwareEncoder`。在推流初始化时，工厂类会根据当前机型的黑白名单，实例化对应的编码器策略塞给视频管线。
> 当运行过程中检测到硬解出现异常时，我们在管线内部可以动态地把这块‘策略模块’替换为软解模块。因为外部对接的都是同一套接口协议，所以这种替换对整个推流流水线来说是完全无感知的，极大地提升了代码的开闭原则（OCP）和系统的容错能力。”

### 实战案例备选 3：建造者模式（Builder Pattern）处理复杂的引擎初始化配置
**业务场景：** WebRTC 或播放器 SDK 初始化时，需要配置极其繁多的参数（分辨率、码率、帧率、日志级别、降噪开关等）。
**🗣️ 建议回答话术：**
> “我还经常使用**建造者模式（Builder）**来优化底层引擎的初始化入口。
> 音视频 SDK 初始化时的参数通常多达二三十个（比如音频采样率、视频分辨率、硬解白名单、私有云地址等）。如果直接通过构造函数传参，或者到处使用 set 方法，代码不仅非常难看，而且容易遗漏参数，导致引擎处于不可靠的状态。
> 
> 我们在 SDK 暴露给外部的接口处设计了 `EngineConfig.Builder`。它利用链式调用（返回 `this` 或 `*this`）让上层可以像写英语句子一样完成配置（比如 `.setVideoResolution(1080p).enableHardwareDecode(true)`）。最后在调用 `.build()` 的时候，Builder 内部会对这几十个参数的交叉逻辑进行一次严格的合法性校验，全部合法才会真正去 new 出底层的 Engine 实例。这样既提升了 API 的易用性，也保证了内部状态的绝对安全。”

### 💡 面试官视角总结
当面试官听到你用：
1. **观察者模式 + WeakRef 解决内存泄漏**
2. **策略模式 解决机型软硬解动态降级**
3. **建造者模式 解决复杂 SDK 参数校验**

这就远不是“会背设计模式”了，而是**“懂架构、懂业务、有大型底层开发经验”**的高级工程师画像。挑选其中你最熟悉的 1-2 个讲透即可。
