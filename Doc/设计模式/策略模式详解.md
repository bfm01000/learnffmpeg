# 策略模式 (Strategy Pattern) 深度解析与面试指南

策略模式是行为型设计模式中**面试最高频、项目里最常用**的模式之一。它的核心目标是：**把一组算法或行为分别封装成独立的策略类，让它们可以在运行时互相替换，且替换过程对调用方透明。**

在音视频 SDK 里，策略模式几乎无处不在：软编/硬编切换、码率控制（CBR/VBR/CRF）、丢帧策略、ABR 自适应码率、音画同步主时钟选择、网络协议切换（RTMP/SRT/WebRTC）、Seek 模式（关键帧 seek vs 精确 seek）——这些全部是"定义一组算法，运行时按条件选一个执行"的经典策略场景。

本文从面试速记、概念原理、音视频代码示例、与其他模式的对比、常见误区和高频问答几个角度系统讲清楚策略模式。

---

## 一、 面试速记

### 1. 一句话核心

> **策略模式把"怎么做"从"谁来做"里抽出来。调用方只依赖策略接口，不关心底层是硬编还是软编、是 CBR 还是 VBR——运行时注入哪个策略就用哪个。**

### 2. 面试关键词

*   **行为型模式**
*   **算法族 / 策略族**
*   **可替换算法**
*   **运行时切换**
*   **消除 if-else / switch**
*   **面向接口编程**
*   **组合优于继承**
*   **开闭原则**（新增策略不修改已有代码）
*   **Context 上下文**
*   **策略工厂配合**

### 3. 高频速查表

| 问题 | 一句话答案 |
| :--- | :--- |
| 策略模式解决什么问题？ | 把一组可替换算法封装成独立策略类，运行时灵活切换，消除大量 if-else。 |
| 和工厂模式什么关系？ | 工厂管"创建哪个策略对象"，策略管"用什么算法执行"。二者经常配合。 |
| 和状态模式有什么区别？ | 策略由外部主动选择切换，策略之间无状态迁移；状态模式由内部状态驱动行为变化。 |
| 和模板方法有什么区别？ | 模板方法靠继承固定流程骨架、子类填空；策略靠组合替换整个算法。 |
| 什么时候不该用策略模式？ | 只有两三种且永远不会增加的情况、算法极少变化、策略类数量爆炸（几十个微小变体）。 |
| 常见坑是什么？ | 策略接口设计过粗或过细、Context 向策略泄露过多内部状态、策略创建成本高但没缓存复用。 |

## 二、 先用代码看：为什么需要策略模式？

以音视频 SDK 的**编码器选择**为例，推流前需要根据设备能力和用户配置选择编码方案：

*   优先使用 `MediaCodec` 硬件编码（低功耗、低 CPU）
*   某些机型硬编有兼容性问题时，降级到 `x264` 软件编码
*   用户指定 H.265 但设备不支持 HEVC 硬编时，降级或报错

### 2.1 不用策略模式：业务代码里到处 if-else

```cpp
// ❌ 不用策略模式：编码逻辑和业务逻辑耦合
void startPublishing(const Config& config) {
    if (config.codec == "h264") {
        if (HardwareDetector::hasMediaCodecH264() && !isBlacklisted()) {
            // 硬编初始化逻辑
            mEncoder = new MediaCodecH264Encoder();
            mEncoder->setBitrateMode(config.bitrateMode); // CBR/VBR
            mEncoder->setProfile(config.profile);
            // ... 30 行硬编配置
        } else {
            // 软编回退逻辑
            mEncoder = new X264Encoder();
            mEncoder->setPreset(config.x264Preset);        // fast/medium/slow
            mEncoder->setCrf(config.crf);
            // ... 30 行软编配置
        }
    } else if (config.codec == "h265") {
        if (HardwareDetector::hasMediaCodecH265() && !isBlacklisted()) {
            mEncoder = new MediaCodecH265Encoder();
            // ... 30 行 H265 硬编配置
        } else {
            mEncoder = new X265Encoder();
            // ... 30 行 H265 软编配置
        }
    }
    // 真正开始编码
    mEncoder->start();
}
```

**问题**：
1. `startPublishing` 这个函数在做两件完全不同的事——"选择编码器"和"启动推流"
2. 每增加一种编码方案（比如新增 NVDEC 硬编），就要改这个函数，违反开闭原则
3. 编码器选择逻辑散落在各处（推流、录制、转码都要判断一遍），改一处漏一处
4. 单元测试困难——测试推流逻辑时必须 mock 整个编码器选择分支

### 2.2 用策略模式：编码策略可替换

```cpp
// ✅ 用策略模式

// --- 步骤 1：定义策略接口 ---
class IEncoder {
public:
    virtual ~IEncoder() = default;
    virtual bool open(const EncoderConfig& cfg) = 0;
    virtual int encode(const AVFrame* in, AVPacket* out) = 0;
    virtual void close() = 0;
    virtual std::string name() const = 0;  // 用于日志/上报
};

// --- 步骤 2：实现具体策略 ---
class MediaCodecH264Encoder : public IEncoder { /* ... */ };
class X264Encoder         : public IEncoder { /* ... */ };
class NvEncH264Encoder    : public IEncoder { /* ... */ };
class MediaCodecH265Encoder : public IEncoder { /* ... */ };
class X265Encoder         : public IEncoder { /* ... */ };

// --- 步骤 3：Context（业务方只依赖接口）---
class Publisher {
public:
    // 策略从外部注入——这就是 "组合优于继承"
    void setEncoder(std::unique_ptr<IEncoder> encoder) {
        mEncoder = std::move(encoder);
    }

    void startPublishing(const Config& config) {
        // 不再有 if-else 选择编码器！
        // 编码器已经在外面选好、注入进来了
        if (!mEncoder->open(config.encoderConfig)) {
            onError("encoder open failed");
            return;
        }
        // 后续推流逻辑...
    }

private:
    std::unique_ptr<IEncoder> mEncoder;
};

// --- 步骤 4：策略工厂（配合工厂模式选择策略）---
class EncoderFactory {
public:
    static std::unique_ptr<IEncoder> create(const Config& config) {
        // if-else 被收敛到一个地方——工厂里
        if (config.codec == "h264") {
            if (HardwareDetector::hasMediaCodecH264() && !isBlacklisted()) {
                return std::make_unique<MediaCodecH264Encoder>();
            }
            return std::make_unique<X264Encoder>();
        }
        if (config.codec == "h265") {
            // ...
        }
        return nullptr;
    }
};

// --- 使用侧 ---
int main() {
    Config config = loadConfig();
    auto encoder = EncoderFactory::create(config);  // 工厂创建策略
    Publisher pub;
    pub.setEncoder(std::move(encoder));              // 注入策略
    pub.startPublishing(config);                     // 业务代码不关心哪个策略
}
```

**变化在哪？**
- `Publisher` 从"知道所有编码器细节"变成"只知道 `IEncoder` 接口"
- 新增编码器：写新策略类 + 工厂加一行 —— 不需要动 `Publisher`
- 测试推流：注入一个 `FakeEncoder` 即可，不依赖真实硬件

## 三、 策略模式的三个角色

```
┌──────────────┐       ┌──────────────┐       ┌──────────────────┐
│   Context    │──────▶│   Strategy    │◀──────│ ConcreteStrategy │
│  (Publisher) │       │  (IEncoder)  │       │ (X264Encoder)    │
│              │       │              │       │ (MediaCodec...)  │
│  持有策略引用 │       │  定义算法接口  │       │ (NvEnc...)       │
│  调用策略方法 │       │              │       │  实现具体算法     │
└──────────────┘       └──────────────┘       └──────────────────┘
```

| 角色 | 职责 | 音视频里的例子 |
| :--- | :--- | :--- |
| **Strategy（策略接口）** | 定义算法族统一接口 | `IEncoder`、`IBitrateController`、`ISyncClock` |
| **ConcreteStrategy（具体策略）** | 实现具体算法 | `X264Encoder`、`CBRController`、`AudioMasterClock` |
| **Context（上下文）** | 持有一个策略引用，调用策略方法 | `Publisher`、`Player`、`StreamManager` |

**关键设计决策**：策略怎么进入 Context？

| 方式 | 代码 | 适用场景 |
| :--- | :--- | :--- |
| **构造函数注入** | `Publisher(unique_ptr<IEncoder>)` | 策略在对象生命周期内不变 |
| **Setter 注入** | `pub.setEncoder(...)` | 策略可能运行时切换 |
| **方法参数注入** | `pub.encode(frame, encoder)` | 单次调用临时用不同策略 |
| **工厂内部自选** | Context 在构造函数里调 Factory | 外部不想关心策略选择，Context 自己搞定 |

## 四、 音视频 SDK 中的六大策略模式实战

### 4.1 编码器策略（软硬编切换）—— 最经典的例子

```cpp
// 策略接口
class IEncoder {
public:
    virtual bool open(const EncoderConfig& cfg) = 0;
    virtual int encode(const AVFrame* in, AVPacket* out) = 0;
    virtual EncoderType type() const = 0;   // HARDWARE / SOFTWARE
    virtual std::string name() const = 0;
    virtual ~IEncoder() = default;
};

// 具体策略
class MediaCodecEncoder : public IEncoder { /* 硬编，GPU 低功耗，但某些机型有兼容坑 */ };
class X264Encoder      : public IEncoder { /* 软编，CPU 高质量，跨平台稳定 */ };
class NvEncEncoder     : public IEncoder { /* NVIDIA 硬编，桌面级 CUDA 加速 */ };
class VideoToolboxEncoder : public IEncoder { /* Apple 硬编，iOS/macOS 专属 */ };

// 策略工厂 + 降级链
class EncoderFactory {
public:
    static std::unique_ptr<IEncoder> createWithFallback(
        const Config& config,
        const Capabilities& caps)
    {
        // 第一优先：指定编码器
        if (config.preferred == "mediacodec" && caps.hasMediaCodec()) {
            if (auto enc = tryCreateMediaCodec(config)) return enc;
            logWarn("MediaCodec failed, falling back to x264");
        }
        // 第二优先：GPU 硬编
        if (caps.hasNvEnc()) {
            if (auto enc = tryCreateNvEnc(config)) return enc;
        }
        // 兜底：软编
        return std::make_unique<X264Encoder>(config);
    }
};
```

### 4.2 码率控制策略（CBR / VBR / CRF）—— 面试高频

```cpp
// 策略接口
class IBitrateController {
public:
    virtual ~IBitrateController() = default;
    virtual int computeQP(const FrameStats& stats) = 0;
    virtual void onFrameEncoded(int actualBits) = 0;
    virtual std::string mode() const = 0;  // "CBR", "VBR", "CRF"
};

// 具体策略
class CBRController : public IBitrateController {
    // 严格控制每帧/每秒码率在目标附近
    // 用 filler data 补齐不足、QP 飙升压超出的部分
    int computeQP(const FrameStats& stats) override {
        double ratio = stats.accumulatedBits / stats.targetBits;
        if (ratio > 1.05) return clamp(mCurrentQP + 3, 0, 51);   // 超了，压 QP
        if (ratio < 0.95) return clamp(mCurrentQP - 2, 0, 51);   // 少了，放 QP
        return mCurrentQP;
    }
};

class VBRController : public IBitrateController {
    // 简单场景给低 QP（高质量），复杂场景给高 QP（压质量）
    // 保证平均码率在目标附近，但瞬时可以浮动
    int computeQP(const FrameStats& stats) override {
        // 基于 frame 复杂度（intra/inter 比例、运动矢量幅度）动态调 QP
        double complexity = estimateComplexity(stats);
        return complexityBasedQP(complexity, mTargetBitrate);
    }
};

class CRFController : public IBitrateController {
    // 目标恒定主观画质，码率自由浮动
    int computeQP(const FrameStats& stats) override {
        return mCRFValue;  // 不调！x264 内部做决策
    }
};
```

**面试追问**："CBR 和 CRF 策略怎么选？"
> 答：直播推流用 CBR——带宽可预测、CDN 友好、不会瞬时码率爆炸冲垮观众网络；离线压制用 CRF——画质稳定、码率不是约束。VBR 介于中间，适合对画质有要求但不苛刻的点播场景。

### 4.4 丢帧策略 —— 卡顿时放弃哪些帧？

```cpp
class IFrameDropStrategy {
public:
    virtual ~IFrameDropStrategy() = default;
    // 返回 true = 丢弃这一帧，不送渲染
    virtual bool shouldDrop(
        FrameType type,              // I / P / B
        int64_t videoPts,
        int64_t audioClock,
        int64_t bufferDepthMs
    ) = 0;
};

// 策略 1：激进丢帧（只保关键帧，B 帧全丢）
class AggressiveDrop : public IFrameDropStrategy {
    bool shouldDrop(FrameType type, int64_t vPts, int64_t aClock, int64_t buf) override {
        if (type == FrameType::IDR) return false;           // IDR 必须保
        if (vPts < aClock - 80ms) return true;               // 落后太多
        if (buf > 200ms && type == FrameType::B) return true; // 缓冲深，丢 B 帧
        return false;
    }
};

// 策略 2：保守丢帧（尽量不丢，缓冲很深才丢非参考帧）
class ConservativeDrop : public IFrameDropStrategy { /* 阈值更宽容 */ };

// 策略 3：只丢 B 帧（P 帧丢了后面全解不出，B 帧无依赖随便丢）
class BDropOnly : public IFrameDropStrategy { /* 只 drop B 帧 */ };
```

### 4.5 音画同步主时钟策略 —— 直接对应 Q21

```cpp
// 策略接口：主时钟——"谁说了算"
class ISyncMaster {
public:
    virtual ~ISyncMaster() = default;
    virtual int64_t masterClockUs() = 0;          // 返回当前主时钟（微秒）
    virtual void onAudioRendered(int samples) = 0; // 音频播了 N 个样本（audio master 用）
    virtual void onVideoRendered() = 0;            // 视频渲染了一帧（video master 用）
    virtual std::string name() const = 0;
};

// 策略 1：音频主时钟（90% 场景）—— 音频走硬件 DAC 节奏
class AudioMasterClock : public ISyncMaster {
    // masterClockUs = 已播放样本数 / 采样率
    int64_t masterClockUs() override {
        return mSamplesPlayed * 1000000LL / mSampleRate;
    }
};

// 策略 2：视频主时钟（监控/无音轨场景）
class VideoMasterClock : public ISyncMaster {
    // masterClockUs = 上一帧显示时刻 + 帧间隔
    int64_t masterClockUs() override {
        return mLastFramePts + mFrameDurationUs;
    }
};

// 策略 3：系统墙钟（RTC 场景）
class SystemClockMaster : public ISyncMaster {
    int64_t masterClockUs() override {
        return std::chrono::duration_cast<std::chrono::microseconds>(
            std::chrono::steady_clock::now() - mStartTime
        ).count();
    }
};

// Context（播放器）
class AVPlayer {
    void setSyncMaster(std::unique_ptr<ISyncMaster> master) {
        mMaster = std::move(master);
    }

    void renderLoop() {
        while (mRunning) {
            auto videoFrame = decodeVideo();
            if (videoFrame) {
                int64_t diff = videoFrame->pts - mMaster->masterClockUs();
                if (diff > 40000) {
                    usleep(diff - 20000);  // 视频比音频快，等一等
                } else if (diff < -40000) {
                    continue;              // 视频落后太多，丢这帧
                }
                render(videoFrame);
            }
        }
    }

    std::unique_ptr<ISyncMaster> mMaster;
};
```

## 五、 策略模式 vs 其他模式 —— 面试最爱考的区分

| 对比维度 | 策略模式 | 工厂模式 | 状态模式 | 模板方法 |
| :--- | :--- | :--- | :--- | :--- |
| **关注点** | 算法怎么**替换** | 对象怎么**创建** | 行为怎么随**状态变化** | 流程**骨架**怎么复用 |
| **切换方式** | 外部主动注入 | 工厂返回具体产品 | 内部状态驱动 | 子类覆写钩子方法 |
| **类关系** | 组合（has-a） | 组合（has-a） | 组合（has-a） | 继承（is-a） |
| **策略间关系** | 独立、互不感知 | 产品间独立 | 状态间有迁移图 | 子类间独立 |
| **常见配合** | 工厂创建策略对象 | 工厂返回策略 | 状态对象内可含策略 | 模板调用策略 |

### 5.1 策略 vs 状态 —— 最容易混淆的一对

```cpp
// ❌ 策略模式：外部根据配置选择
Player player;
if (config.useAudioMaster) {
    player.setSyncMaster(std::make_unique<AudioMasterClock>());
} else {
    player.setSyncMaster(std::make_unique<SystemClockMaster>());
}

// ❌ 状态模式：内部状态驱动切换（代码在 Player 内部，外部不选）
// Player 内部：
//   IdleState    → (收到 play 命令) → PlayingState
//   PlayingState → (缓冲空)         → BufferingState
//   PlayingState → (收到 pause)     → PausedState
```

**记忆口诀**：**策略是"你选哪个"，状态是"它自己变"**。

### 5.2 策略 vs 模板方法 —— 组合 vs 继承

```cpp
// 模板方法：继承复用流程
class VideoEncoder {
public:
    void encodeFrame(const AVFrame* in, AVPacket* out) {
        preProcess(in);      // ← 子类可覆写
        doEncode(in, out);   // ← 子类必须实现
        postProcess(out);    // ← 子类可覆写
    }
    virtual void doEncode(const AVFrame*, AVPacket*) = 0;  // 纯虚，子类填空
};

// 策略模式：组合替换算法
class VideoEncoder {
    std::unique_ptr<IEncodeStrategy> mStrategy;  // 策略对象
public:
    void encodeFrame(const AVFrame* in, AVPacket* out) {
        mStrategy->encode(in, out);  // 完全委托给策略
    }
};
```

| | 模板方法 | 策略模式 |
| :--- | :--- | :--- |
| 复用方式 | 继承 | 组合 |
| 灵活性 | 编译期绑定，运行时不可换 | 运行时随意换 |
| 代码量 | 子类少时代码少 | 需要额外接口和策略类 |
| 耦合度 | 子类和父类耦合 | Context 和 Strategy 仅接口耦合 |
| 适用场景 | 流程固定、步骤可变（如解码管线） | 整个算法可替换（如码率控制） |

## 六、 常见误区与踩坑

### 6.1 策略接口设计得过粗或过细

```cpp
// ❌ 过粗：一种策略只需要其中两个方法，其他三个空实现
class IStreamProcessor {
    virtual void encode(...) = 0;
    virtual void mux(...) = 0;
    virtual void push(...) = 0;
    virtual void record(...) = 0;
    virtual void thumbnail(...) = 0;
};
// 问题：一个"只推流"的策略被迫实现 record 和 thumbnail 空方法

// ❌ 过细：每个微小差异都是一个策略，策略类爆炸
class IBitrateAdjuster { virtual double adjust(double qp) = 0; };
class Plus1Adjuster    : public IBitrateAdjuster { double adjust(double qp) { return qp + 1; } };
class Plus2Adjuster    : public IBitrateAdjuster { double adjust(double qp) { return qp + 2; } };
// ... 20 个 adjuster，不如用 lambda 或参数化

// ✅ 适中：按"可替换的概念单元"划分接口
// 编码器接口：open / encode / close
// 码控接口：computeQP / onFrameDone
// 同步接口：masterClock / onRender
```

**原则**：接口粒度 = 一个"可独立替换的算法单元"。如果一个策略总是和另一个策略一起切换，它们可能应该合并。

### 6.2 Context 向策略泄露内部状态

```cpp
// ❌ Context 把整个内部状态裸传给策略
class Publisher {
    EncoderPipeline mPipeline;       // 内部对象
    NetworkStats mNetStats;          // 内部对象
    FrameQueue mFrameQueue;          // 内部对象
public:
    // 策略拿到了 Publisher 的内部引用，可以随意访问/修改
    void setStrategy(IStrategy* s) { s->bind(mPipeline, mNetStats, mFrameQueue); }
};

// ✅ 策略只接收必要的数据（通过接口参数传）
class IFrameDropStrategy {
    virtual bool shouldDrop(FrameType type, int64_t pts, int64_t clock, int64_t bufMs) = 0;
    // 只拿了 4 个和决策直接相关的值，不碰 Context 内部
};
```

### 6.3 策略对象重复创建，没有缓存复用

```cpp
// ❌ 每帧创建一个策略对象
while (encoding) {
    auto strategy = std::make_unique<CBRController>(targetBitrate);
    int qp = strategy->computeQP(stats);
    // strategy 在这里析构，下一帧再 new——完全浪费
}

// ✅ 策略复用以整个编码会话
auto strategy = std::make_unique<CBRController>(targetBitrate);
while (encoding) {
    int qp = strategy->computeQP(stats);  // 复用同一个策略对象
}
```

### 6.4 过度设计：只有两个选择也硬套策略模式

```cpp
// ❌ 过度设计：CBR 和 VBR 两个选项，未来也不可能加第三个
class IBitrateMode { ... };
class CBRMode : public IBitrateMode { ... };
class VBRMode : public IBitrateMode { ... };

// ✅ 这种情况用 enum + 简单分支就够了
enum class BitrateMode { CBR, VBR };
// 加上 encode 函数里对 mode 的一次判断
```

**判断标准**：
- 策略数 ≥ 3，且未来可能增加 → 策略模式
- 策略数 ≤ 2，且变化概率小 → 简单分支
- 策略代码块超过 20 行，即使只有两个 → 抽成策略类（提高可读性）

### 6.5 忘了在策略接口声明虚析构

```cpp
// ❌ 基类没有虚析构——通过基类指针 delete 子类对象 = 未定义行为
class IEncoder {
public:
    virtual void encode(...) = 0;
    // 没有 virtual ~IEncoder()！
};

// ✅ 永远在策略接口声明虚析构
class IEncoder {
public:
    virtual ~IEncoder() = default;  // 这一行不能省
    virtual void encode(...) = 0;
};
```

## 七、 面试高频问答

**Q1：讲一下策略模式是什么？你在项目里怎么用的？**

> 策略模式是把一组算法封装成独立的策略类，运行时可以灵活替换。我在音视频 SDK 里用得很多，最典型的三个：第一是**编码器策略**，把硬编和软编封装成 `IEncoder` 的不同实现，工厂根据设备能力创建策略、注入给推流器——推流器只依赖 `IEncoder` 接口；第二是**码率控制策略**，CBR/VBR/CRF 各自是实现类，直播推流用 CBR、离线压制用 CRF，切换只需改一行实例化代码；第三是**音画同步主时钟**，音频主时钟、视频主时钟、系统墙钟三种策略，播放器初始化时根据场景选。
>
> 最大的收益是：新增一种编码器（比如 NVDEC）不会动到推流器代码；测试时注入 Mock 策略就可以脱离真硬件验证完整流程。

**Q2：策略模式和工厂模式是什么关系？**

> 一句话区分：工厂管"创建哪个策略"，策略管"用什么算法执行"。它们经常配合使用——工厂根据配置/能力创建具体策略对象，然后注入给 Context。比如 `EncoderFactory::create(config)` 返回 `unique_ptr<IEncoder>`，推流器 `setEncoder()` 接收后只通过 `IEncoder` 接口调。工厂负责 if-else 收敛，策略负责算法封装，两者各管一段。

**Q3：策略模式和状态模式有什么区别？**

> 三个核心区别。第一，**切换驱动者不同**：策略由外部主动选择（用户配置说"用硬编"、ABR 策略说"网络好就升码率"）；状态由内部状态变化驱动（播放器 buffer 空了自动从 Playing 切到 Buffering）。第二，**策略之间独立无感知**——CBR 策略不知道 VBR 策略的存在；状态之间有明确的迁移图和迁移条件——Playing 可以迁移到 Paused、Buffering、Error，但不能跳到 Idle。第三，**生命周期不同**——策略通常在 Context 初始化时确定、一次会话不变；状态在会话过程中频繁切换。

**Q4：你有多少策略类？类太多怎么办？**

> 策略类是多了，但它们是"有组织的多"——每个策略封装一个独立的算法，各管各的、互不干扰。相比把所有算法塞在一个类里用 if-else 分支，"策略类多但每个简单"远好于"类少但每个类上千行"。如果真的要精简：一是把微变体（比如 QP+1 vs QP+2）参数化，用一个带构造参数的策略类替代；二是用 Lambda/`std::function` 替代只有一个方法的策略接口（这种叫"函数式策略"）；三是审视接口粒度——如果两个"策略"总是同时切换，应该合并。

**Q5：策略模式有什么缺点？**

> 第一，**类数量膨胀**——每加一种算法就是一个新类。如果策略变体特别多（几十种），要考虑参数化或函数式替代。第二，**策略接口不稳定**——如果需要在接口里加新的虚方法，所有已有策略类都要改。所以策略接口设计要仔细想清楚，一开始宽一点。第三，**调试链变长**——以前一个 if-else 能看清所有逻辑，现在要跳转好几个文件才能跟完一次调用。打日志时在策略的 `name()` 里打印名字，方便定位"当前在用哪个策略"。第四，**策略需要感知 Context 的数据**——如果策略只依赖自己的参数（纯算法），那就完美；如果策略需要读 Context 的状态（buffer 水位、网络质量），就要设计 Strategy 的方法参数，避免 Context 裸传引用给策略。

**Q6：结合你的项目，策略模式具体怎么用的？**

> _(以推流 SDK 为例回答)_

> 我推流 SDK 的核心架构是"策略模式 + 工厂模式"的组合。`IEncoder` 策略接口定义 `open/encode/close/name`，具体策略有 `MediaCodecEncoder`、`X264Encoder`、`NvEncEncoder`，工厂 `EncoderFactory` 根据 `Capabilities` 检测结果创建策略并注入 `Publisher`。码率控制也类似——`IBitrateController` 策略接口 + `CBR/VBR/CRF/ABR` 四个实现，直播和录制场景自动选不同策略。丢帧和音画同步也是策略模式。整个 SDK 对外只有一个 `StreamingSDK` 外观类，内部通过注入不同策略组合来决定行为——用装饰器模式理解就是"同一套骨架，换不同内脏"。这种架构最大的好处是**测试友好**——单元测试注入 Mock 策略，不需要真硬件、不需要真网络。

## 八、 一句话总结

> **策略模式的核心不是"又多了一个设计模式"，而是一个直觉：当你写了一大段 if-else 来 pick 不同的算法时，就应该问自己——这些分支是不是应该各自变成一个类？策略模式把"选择"和"执行"分开：工厂/配置做选择，策略类做执行，Context 只依赖接口——这就是"组合优于继承"在行为型场景的极致体现。在音视频领域，编码器、码控、ABR、丢帧、音画同步、协议切换——凡是"根据条件选算法"的地方，策略模式都是最自然的设计。**
