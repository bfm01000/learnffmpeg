# 建造者模式 (Builder Pattern) 深度解析与面试指南

建造者模式（Builder Pattern）是创建型设计模式中非常实用的一种。它的核心目标是：**把一个复杂对象的构建过程从对象本身拆出去，让调用方用清晰、可读、可校验的方式一步步完成配置，最后再统一创建对象**。

在音视频 SDK、播放器、推流器、滤镜管线、网络请求、UI 配置等场景中，建造者模式非常常见。尤其当一个对象有大量可选参数，并且这些参数之间存在合法性约束时，Builder 会比超长构造函数和一堆 `setXXX()` 更清晰、更安全。

本文从面试速记、概念原理、代码示例、使用场景、常见误区、踩坑指南和高频问答几个角度系统讲清楚建造者模式。

---

## 一、 面试速记

### 1. 一句话核心

> **建造者模式适合创建“参数很多、构建步骤复杂、需要统一校验”的对象。它把参数收集和对象创建分离，让调用方通过链式 API 配置，最后调用 `build()` 一次性生成稳定对象。**

### 2. 面试关键词

*   **复杂对象创建**
*   **参数很多**
*   **可选参数很多**
*   **链式调用**
*   **构建过程与表示分离**
*   **集中校验**
*   **避免构造函数爆炸**
*   **避免对象半初始化**

### 3. 高频速查表

| 问题 | 一句话答案 |
| :--- | :--- |
| Builder 解决什么问题？ | 解决复杂对象创建时参数过多、顺序混乱、校验分散的问题。 |
| 和构造函数相比有什么优势？ | 可读性更好，可选参数更自然，还能在 `build()` 时集中校验。 |
| 和 setter 相比有什么优势？ | setter 容易让对象处于半初始化状态，Builder 可以一次性创建合法对象。 |
| 什么时候不该用 Builder？ | 参数很少、对象创建很简单时，不要过度设计。 |
| Builder 常见坑是什么？ | 忘记校验必填参数、Builder 被复用导致脏状态、构建出的对象仍可随意修改。 |

## 二、 先用代码看：为什么需要建造者模式？

以音视频 SDK 里的推流配置为例，一个直播推流器通常需要很多参数：

*   推流地址 `url`
*   分辨率 `width / height`
*   帧率 `fps`
*   码率 `bitrate`
*   编码格式 `H.264 / H.265`
*   是否开启硬编
*   是否开启零拷贝
*   是否开启 ABR 动态码率
*   GOP 大小
*   音频采样率
*   声道数

### 1. 反面写法一：超长构造函数

```cpp
class LiveConfig {
public:
    LiveConfig(const std::string& url,
               int width,
               int height,
               int fps,
               int bitrate,
               bool enableHardwareEncode,
               bool enableZeroCopy,
               bool enableAbr,
               int gop,
               int sampleRate,
               int channels)
        : url_(url),
          width_(width),
          height_(height),
          fps_(fps),
          bitrate_(bitrate),
          enableHardwareEncode_(enableHardwareEncode),
          enableZeroCopy_(enableZeroCopy),
          enableAbr_(enableAbr),
          gop_(gop),
          sampleRate_(sampleRate),
          channels_(channels) {}

private:
    std::string url_;
    int width_ = 0;
    int height_ = 0;
    int fps_ = 0;
    int bitrate_ = 0;
    bool enableHardwareEncode_ = false;
    bool enableZeroCopy_ = false;
    bool enableAbr_ = false;
    int gop_ = 0;
    int sampleRate_ = 0;
    int channels_ = 0;
};
```

调用方会变成这样：

```cpp
LiveConfig config(
    "rtmp://example.com/live",
    3840,
    2160,
    30,
    8000000,
    true,
    true,
    true,
    60,
    48000,
    2);
```

这段代码最大的问题是：**参数含义不直观，顺序容易写错，而且可选参数会不断膨胀**。

比如下面这种错误，编译器未必能发现：

```cpp
LiveConfig config(
    "rtmp://example.com/live",
    3840,
    2160,
    8000000, // 本来应该是 fps，却误传成 bitrate
    30,      // 本来应该是 bitrate，却误传成 fps
    true,
    true,
    true,
    60,
    48000,
    2);
```

### 2. 反面写法二：无约束 setter

另一种常见写法是空构造 + 一堆 setter：

```cpp
class LiveConfig {
public:
    void setUrl(const std::string& url) { url_ = url; }
    void setResolution(int width, int height) { width_ = width; height_ = height; }
    void setFps(int fps) { fps_ = fps; }
    void setBitrate(int bitrate) { bitrate_ = bitrate; }
    void setEnableZeroCopy(bool enable) { enableZeroCopy_ = enable; }

private:
    std::string url_;
    int width_ = 0;
    int height_ = 0;
    int fps_ = 0;
    int bitrate_ = 0;
    bool enableZeroCopy_ = false;
};
```

调用方：

```cpp
LiveConfig config;
config.setUrl("rtmp://example.com/live");
config.setResolution(3840, 2160);
config.setEnableZeroCopy(true);

// 忘记设置 fps 和 bitrate，但对象已经可以被传下去了
engine.start(config);
```

setter 的问题是：**对象可能长期处于半初始化状态**。你不知道它什么时候才算配置完成，也不知道必填参数有没有设置。

### 3. Builder 写法：链式配置 + build 统一校验

```cpp
#include <stdexcept>
#include <string>

class LiveConfig {
public:
    class Builder {
    public:
        Builder& setUrl(std::string url) {
            url_ = std::move(url);
            return *this;
        }

        Builder& setResolution(int width, int height) {
            width_ = width;
            height_ = height;
            return *this;
        }

        Builder& setFps(int fps) {
            fps_ = fps;
            return *this;
        }

        Builder& setBitrate(int bitrate) {
            bitrate_ = bitrate;
            return *this;
        }

        Builder& enableHardwareEncode(bool enable) {
            enableHardwareEncode_ = enable;
            return *this;
        }

        Builder& enableZeroCopy(bool enable) {
            enableZeroCopy_ = enable;
            return *this;
        }

        LiveConfig build() const {
            if (url_.empty()) {
                throw std::invalid_argument("push url is empty");
            }
            if (width_ <= 0 || height_ <= 0) {
                throw std::invalid_argument("invalid resolution");
            }
            if (fps_ <= 0 || bitrate_ <= 0) {
                throw std::invalid_argument("invalid fps or bitrate");
            }
            if (enableZeroCopy_ && !enableHardwareEncode_) {
                throw std::invalid_argument("zero-copy requires hardware encode");
            }

            return LiveConfig(*this);
        }

    private:
        std::string url_;
        int width_ = 0;
        int height_ = 0;
        int fps_ = 30;
        int bitrate_ = 4000000;
        bool enableHardwareEncode_ = true;
        bool enableZeroCopy_ = false;

        friend class LiveConfig;
    };

private:
    explicit LiveConfig(const Builder& builder)
        : url_(builder.url_),
          width_(builder.width_),
          height_(builder.height_),
          fps_(builder.fps_),
          bitrate_(builder.bitrate_),
          enableHardwareEncode_(builder.enableHardwareEncode_),
          enableZeroCopy_(builder.enableZeroCopy_) {}

    std::string url_;
    int width_ = 0;
    int height_ = 0;
    int fps_ = 0;
    int bitrate_ = 0;
    bool enableHardwareEncode_ = false;
    bool enableZeroCopy_ = false;
};
```

调用方会非常清楚：

```cpp
LiveConfig config = LiveConfig::Builder()
    .setUrl("rtmp://example.com/live")
    .setResolution(3840, 2160)
    .setFps(30)
    .setBitrate(8000000)
    .enableHardwareEncode(true)
    .enableZeroCopy(true)
    .build();
```

这就是 Builder 的价值：

*   参数含义清楚。
*   可选参数可以有默认值。
*   必填参数可以在 `build()` 中统一校验。
*   参数之间的依赖关系也可以集中校验。
*   构建完成后的 `LiveConfig` 可以设计成不可变对象。

## 三、 建造者模式的概念与结构

### 1. 官方定义

建造者模式将一个复杂对象的构建过程与它的表示分离，使得同样的构建过程可以创建不同的表示。

更口语化一点：

> **不要让调用方直接面对一个又长又乱的构造函数，而是给它一个 Builder，让它一步步配置，最后统一 build 出目标对象。**

### 2. 核心角色

经典建造者模式通常包含四个角色：

*   **Product（产品对象）**：最终要创建的复杂对象，比如 `LiveConfig`、`PlayerConfig`。
*   **Builder（抽象建造者）**：定义构建步骤，比如设置 URL、分辨率、码率。
*   **ConcreteBuilder（具体建造者）**：实现具体构建逻辑。
*   **Director（指挥者）**：按照固定流程调用 Builder，封装构建顺序。

但在现代工程里，尤其是 Java / C++ SDK 配置类中，经常简化成：

```text
Product + 内部 Builder
```

也就是说，不一定非要写一个 Director。面试时可以说：**GoF 经典结构里有 Director，但实际业务里如果构建流程不复杂，常用内部 Builder + 链式调用的简化版本。**

### 3. Builder 和链式调用

Builder 常见写法是每个 `setXXX()` 返回 `Builder&` 或 `Builder*`，这样可以连续调用：

```cpp
Builder& setFps(int fps) {
    fps_ = fps;
    return *this;
}
```

调用时：

```cpp
LiveConfig config = LiveConfig::Builder()
    .setFps(30)
    .setBitrate(8000000)
    .build();
```

链式调用的本质不是设计模式本身，而是一种提升可读性的 API 风格。Builder 常常搭配链式调用，但“链式调用”不等于“建造者模式”。

## 四、 什么时候使用建造者模式？

### 1. 参数很多，而且可选参数很多

比如播放器配置：

```text
url / timeout / cache size / decoder type / render mode / audio session / log level
```

如果都塞进构造函数，会出现构造函数爆炸。

### 2. 参数之间有依赖关系

比如：

*   开启零拷贝必须使用硬件编码。
*   H.265 需要设备能力支持。
*   4K 推流码率不能低于某个阈值。
*   开启 ABR 时必须配置码率上下限。

这些规则适合放在 `build()` 里集中校验。

### 3. 希望创建完成后对象不可变

配置对象一旦传入引擎，最好不要被外部随意修改：

```cpp
class LiveConfig {
public:
    int fps() const { return fps_; }
    int bitrate() const { return bitrate_; }

private:
    int fps_ = 0;
    int bitrate_ = 0;
};
```

Builder 负责构建，Product 负责只读使用。这能避免运行中配置被外部改坏。

### 4. 希望 API 更易读

对比：

```cpp
LiveConfig config("url", 3840, 2160, 30, 8000000, true, true);
```

和：

```cpp
LiveConfig config = LiveConfig::Builder()
    .setUrl("url")
    .setResolution(3840, 2160)
    .setFps(30)
    .setBitrate(8000000)
    .enableZeroCopy(true)
    .build();
```

后者更像配置清单，面试时可以说：**Builder 提升的是可读性、可维护性和构建合法性。**

## 五、 和其他创建方式的区别

### 1. Builder vs 构造函数

| 对比项 | 构造函数 | Builder |
| :--- | :--- | :--- |
| 参数少时 | 简洁 | 可能显得啰嗦 |
| 参数多时 | 难读、易错 | 清晰、可读 |
| 可选参数 | 容易构造函数重载爆炸 | 默认值天然支持 |
| 参数校验 | 分散在构造函数里 | 可集中在 `build()` |
| 对象状态 | 构造完即完整 | `build()` 后完整 |

### 2. Builder vs setter

| 对比项 | setter | Builder |
| :--- | :--- | :--- |
| 创建过程 | 对象先创建，再慢慢改 | 先收集参数，最后创建对象 |
| 半初始化风险 | 高 | 低 |
| 不可变对象 | 不友好 | 很友好 |
| 校验时机 | 分散在每个 setter 或使用前 | 集中在 `build()` |

setter 最大的问题是对象可能处于这种状态：

```cpp
LiveConfig config;
config.setUrl("rtmp://example.com/live");
// 忘记 setBitrate，但 config 已经能传给 engine
```

Builder 的优势是：

```cpp
LiveConfig config = LiveConfig::Builder()
    .setUrl("rtmp://example.com/live")
    .build(); // 缺少必要参数时直接失败
```

### 3. Builder vs 工厂模式

工厂模式关注的是：**根据条件创建哪一种对象**。

```cpp
std::unique_ptr<VideoEncoder> encoder = EncoderFactory::create(codecType);
```

Builder 关注的是：**一个复杂对象应该如何一步步配置出来**。

```cpp
LiveConfig config = LiveConfig::Builder()
    .setResolution(3840, 2160)
    .setBitrate(8000000)
    .build();
```

一句话：

> 工厂解决“创建哪个类”；Builder 解决“这个类参数太多，怎么优雅地创建”。

### 4. Builder vs 直接写 `struct`

在 C++ 里，Builder 并不是永远比 `struct` 更好。很多内部配置、临时参数、统计信息，用一个简单结构体反而更自然。

比如只是一个普通参数包：

```cpp
struct LiveConfig {
    std::string url;
    int width = 1920;
    int height = 1080;
    int fps = 30;
    int bitrate = 4000000;
    bool enableHardwareEncode = true;
    bool enableZeroCopy = false;
};
```

调用方直接填字段：

```cpp
LiveConfig config;
config.url = "rtmp://example.com/live";
config.width = 3840;
config.height = 2160;
config.bitrate = 8000000;

engine.start(config);
```

如果只是内部模块之间传递数据，这种写法非常清楚，没有必要强行 Builder。

但是 `struct` 的问题是：调用方很容易构造出“类型合法但业务非法”的配置：

```cpp
LiveConfig config;
config.url = "rtmp://example.com/live";
config.enableZeroCopy = true;
config.enableHardwareEncode = false; // 逻辑矛盾：零拷贝通常依赖硬编 Surface 输入
```

所以 C++ 工程里还有一种很常见的折中方案：**`struct + validate()`**。

```cpp
enum class ConfigError {
    Ok,
    EmptyUrl,
    InvalidResolution,
    InvalidBitrate,
    ZeroCopyRequiresHardwareEncode,
};

struct LiveConfig {
    std::string url;
    int width = 1920;
    int height = 1080;
    int fps = 30;
    int bitrate = 4000000;
    bool enableHardwareEncode = true;
    bool enableZeroCopy = false;

    ConfigError validate() const {
        if (url.empty()) {
            return ConfigError::EmptyUrl;
        }
        if (width <= 0 || height <= 0) {
            return ConfigError::InvalidResolution;
        }
        if (fps <= 0 || bitrate <= 0) {
            return ConfigError::InvalidBitrate;
        }
        if (enableZeroCopy && !enableHardwareEncode) {
            return ConfigError::ZeroCopyRequiresHardwareEncode;
        }
        return ConfigError::Ok;
    }
};
```

调用方：

```cpp
LiveConfig config;
config.url = "rtmp://example.com/live";
config.width = 3840;
config.height = 2160;
config.enableZeroCopy = true;
config.enableHardwareEncode = false;

if (config.validate() != ConfigError::Ok) {
    // 转成 SDK 初始化失败错误码，或者回调给 Java 层
    return;
}

engine.start(config);
```

这套方案比 Builder 简单，也很符合 C++ 风格。缺点是：配置对象仍然是公开字段，`validate()` 之后理论上还能被外部修改。

所以面试里可以这样判断：

*   **内部简单参数包**：直接用 `struct`。
*   **内部配置但需要校验**：用 `struct + validate()`。
*   **对外 SDK API、参数很多、希望不可变、约束复杂**：用 Builder。

一句话：

> Builder 不是为了替代所有 `struct`。它真正适合的是“对外复杂配置 + 必填项 + 组合约束 + 希望构建后稳定不可变”的场景。

## 六、 常见误区与容易踩的坑

### 1. 误区：参数少也强行用 Builder

如果对象只有两三个参数：

```cpp
Point p(10, 20);
```

没有必要写成：

```cpp
Point p = Point::Builder().setX(10).setY(20).build();
```

这就是过度设计。Builder 应该用在“复杂对象创建”，不是所有对象都要 Builder。

### 2. 忘记在 `build()` 里校验必填参数

错误示范：

```cpp
LiveConfig build() const {
    return LiveConfig(*this); // 没有检查 url、fps、bitrate
}
```

这样 Builder 只变成了“换皮 setter”，没有真正保证对象合法。

正确做法：

```cpp
LiveConfig build() const {
    if (url_.empty()) {
        throw std::invalid_argument("url is required");
    }
    if (fps_ <= 0 || bitrate_ <= 0) {
        throw std::invalid_argument("invalid media params");
    }
    return LiveConfig(*this);
}
```

不过在 Android NDK、FFmpeg、音视频 SDK 这类底层 C++ 工程中，不一定推荐用异常表达构建失败。示例里的 `throw std::invalid_argument` 主要是为了说明“应该在 `build()` 阶段集中校验”这个思想。

如果项目规范不允许异常，更推荐返回 `Result` / `Status` / 错误码：

```cpp
struct BuildResult {
    ConfigError error = ConfigError::Ok;
    std::optional<LiveConfig> config;
};

BuildResult build() const {
    if (url_.empty()) {
        return {ConfigError::EmptyUrl, std::nullopt};
    }
    if (enableZeroCopy_ && !enableHardwareEncode_) {
        return {ConfigError::ZeroCopyRequiresHardwareEncode, std::nullopt};
    }

    return {ConfigError::Ok, LiveConfig(*this)};
}
```

面试里要强调：**Builder 的重点是集中校验，不是必须抛异常。底层 SDK 场景更常用错误码或 `Result`，避免异常跨 JNI、线程、C ABI 边界传播。**

### 3. Builder 被复用导致脏状态

```cpp
LiveConfig::Builder builder;

LiveConfig configA = builder
    .setUrl("rtmp://a")
    .setBitrate(4000000)
    .build();

LiveConfig configB = builder
    .setUrl("rtmp://b")
    .build(); // 可能继续沿用 configA 的 bitrate
```

这不一定是 Bug，但很容易让调用方误解。

建议：

*   Builder 用完即丢，不鼓励复用。
*   文档里明确 Builder 是否可复用。
*   如果业务复杂，可以在 `build()` 后标记 consumed，禁止再次 build。

### 4. Product 构建后仍然到处可变

如果 Builder 创建出的对象还暴露大量 setter：

```cpp
LiveConfig config = builder.build();
config.setBitrate(-1); // 又把对象改坏了
```

那 Builder 的收益会被削弱。

更推荐：

```cpp
class LiveConfig {
public:
    int bitrate() const { return bitrate_; }

private:
    int bitrate_ = 0;
};
```

即：**Builder 阶段可变，Product 阶段尽量不可变。**

### 5. Builder 里做太重的事情

`build()` 适合做参数校验和轻量组装，不适合做耗时 I/O：

```cpp
LiveConfig build() const {
    scanAllMediaCodec(); // 不建议：可能很慢
    connectServer();     // 更不建议：构建配置不应该发起网络连接
    return LiveConfig(*this);
}
```

建议：

*   `build()` 只生成配置对象。
*   硬件能力探测放到初始化阶段或能力缓存中。
*   网络连接、线程启动放到 `engine.start(config)` 中。

### 6. 链式调用返回临时对象，导致配置丢失

错误写法：

```cpp
Builder setFps(int fps) {
    fps_ = fps;
    return *this; // 返回副本
}
```

这会不断复制 Builder，容易引发性能和语义问题。C++ 中更常见写法是返回引用：

```cpp
Builder& setFps(int fps) {
    fps_ = fps;
    return *this;
}
```

如果想支持移动语义和临时对象链式调用，可以进一步设计 `&&` 限定版本，但面试一般讲 `Builder&` 就够了。

## 七、 面试高频问题与标准回答

### Q1：什么是建造者模式？

**🗣️ 标准回答：**
> “建造者模式是一种创建型设计模式，主要用来创建参数很多、构建过程复杂的对象。它把参数配置过程放到 Builder 里，调用方通过链式 API 设置参数，最后调用 `build()` 一次性生成目标对象。这样可以避免超长构造函数，也能在 build 阶段集中做参数校验。”

### Q2：建造者模式解决了什么问题？

**🗣️ 标准回答：**
> “它主要解决三个问题。第一是构造函数参数太多，调用方很难看懂每个参数含义；第二是可选参数太多，构造函数重载会爆炸；第三是参数之间有依赖关系，需要统一校验。Builder 可以让配置过程更清晰，并保证最终 build 出来的对象是合法的。”

### Q3：Builder 和 setter 有什么区别？

**🗣️ 标准回答：**
> “setter 是先创建对象，再慢慢修改对象，所以对象可能处于半初始化状态。Builder 是先在 Builder 里收集参数，最后 `build()` 时统一校验并创建目标对象。尤其是配置对象，Builder 更适合做成不可变对象，创建完成后只读使用，这样比 setter 更安全。”

### Q4：Builder 和工厂模式有什么区别？

**🗣️ 标准回答：**
> “工厂模式关注的是根据条件创建哪一种对象，比如创建硬编编码器还是软编编码器。Builder 关注的是一个复杂对象内部参数很多，怎么一步步配置出来。简单说，工厂解决‘创建哪个类’，Builder 解决‘这个类怎么优雅地创建’。”

### Q5：建造者模式有什么缺点？

**🗣️ 标准回答：**
> “缺点主要是代码量会增加。如果对象本身很简单，强行使用 Builder 就是过度设计。另外 Builder 如果没有在 `build()` 做校验，只是换了一种写 setter 的方式，价值就很低。还有一个坑是 Builder 被复用可能带来脏状态，所以一般建议 Builder 用完即丢。”

### Q6：你在项目里怎么使用建造者模式？

**🗣️ 标准回答参考（结合音视频/SDK）：**
> “在音视频 SDK 里，建造者模式很适合用在引擎初始化配置上。比如推流配置里有 URL、分辨率、帧率、码率、编码格式、硬编开关、零拷贝开关、ABR 开关等很多参数。如果用构造函数，参数会非常长，而且容易传错顺序。所以我会设计一个 `LiveConfig::Builder`，调用方用链式 API 配置，最后在 `build()` 里统一校验，比如零拷贝必须依赖硬编、码率和帧率必须合法。这样既提升了 API 可读性，也能避免引擎拿到半初始化或非法配置。”

## 八、 项目实战话术（STAR 法则版）

### 1. 音视频 SDK 初始化配置

> “在音视频 SDK 的初始化入口里，配置项非常多，比如推流 URL、分辨率、帧率、码率、编码格式、硬编开关、零拷贝开关、ABR 开关、日志级别等。如果全部塞进构造函数，调用方很难看懂参数含义，也容易把 fps 和 bitrate 这类整数参数传反。
>
> 我的做法是用建造者模式封装配置对象。调用方通过 `LiveConfig::Builder()` 链式设置参数，常用参数提供默认值，必填参数和参数依赖关系统一在 `build()` 中校验。比如开启零拷贝时必须使用硬件编码，开启 ABR 时必须设置合理的码率范围。
>
> 这样做的收益是：SDK 初始化 API 更清晰，非法配置能在启动前尽早暴露；同时最终传给底层引擎的是一个稳定的配置对象，避免运行过程中到处 setter 导致状态不一致。”

### 2. 结合 4K 直播优化项目的说法

> “在 4K 直播性能优化里，我们引入过类似 `enableLiveZeroCopy`、`enableAsyncSendAndABR` 这样的参数化开关。为了保证旧业务兼容，这类能力不能写死在代码里，而应该收敛到配置对象中。
>
> 如果后续继续演进，我会更倾向用 Builder 管理这些配置。比如 `LiveConfig::Builder().enableZeroCopy(true).enableAsyncSendAndAbr(true).setTargetBitrate(...)`，最后在 `build()` 里检查依赖关系。这样既方便灰度开关，也避免某些非法组合进入底层管线，比如开启零拷贝但没有硬编 Surface 输入能力。”

## 九、 一句话总结

**建造者模式解决的是“复杂对象如何清晰、安全、可校验地创建”的问题；它最适合参数很多、可选项很多、参数之间有约束的配置类对象。**

面试最后可以这样收束：

> “我不会所有对象都用 Builder。简单对象直接构造就好；但像音视频 SDK 的引擎配置、播放器配置、推流配置这种参数多、可选项多、还需要合法性校验的对象，我会优先用 Builder。它能避免构造函数爆炸，也能防止 setter 带来的半初始化问题。”
