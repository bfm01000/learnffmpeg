# 音视频 C++ 网络协议面试指南：从 Muduo 封装到实时传输底层能力

## 0. 本篇定位

- 面试复习：先建立 TCP/UDP/HTTP/RTMP/RTP/WebRTC/HLS 的分层与选型口径，适合考前快速串协议地图。
- 深入学习：遇到 TCP 可靠性、RTMP Chunk、WebRTC 弱网、FFmpeg 推流 API 时，跳到对应专题深挖。
- 工程落点：回答协议题要落到延迟、丢包、队头阻塞、CDN、浏览器兼容、服务端 fanout 和客户端排障。
如果你之前主要使用别人封装好的 `muduo` / `mudex` 网络库，那么面试时最容易被追问的点不是“API 怎么调”，而是：**为什么这样封装、底层靠什么高并发、音视频为什么大量使用 UDP、丢包后怎么恢复、弱网下如何保证实时性**。

本文按资深 C++ 音视频开发的面试视角梳理网络知识，重点放在直播、点播、RTC、推拉流、低延迟传输这些高频场景。

## 一、先建立大图：音视频网络到底在解决什么问题？

普通业务网络请求通常追求：

* **可靠性**：请求必须成功，数据必须完整。
* **一致性**：一次请求对应一次明确响应。
* **吞吐量**：尽可能多传数据。

音视频网络传输还额外关心：

* **实时性**：过期的视频帧没有价值，迟到 2 秒的 P 帧不如直接丢掉。
* **连续性**：用户更怕卡顿、花屏、音画不同步。
* **抗弱网**：移动网络会抖动、丢包、乱序、切网、NAT 变化。
* **带宽自适应**：网络变差时要降码率、降分辨率、丢增强层，而不是死等。
* **端到端延迟**：采集、编码、传输、解码、渲染整条链路都要控。

面试中可以这样概括：

> 音视频网络的核心不是单纯把字节发出去，而是在有限带宽、丢包、抖动和延迟约束下，尽可能稳定地交付“有播放价值”的媒体数据。

## 二、传输层基础：TCP 和 UDP 怎么选？

### 1. TCP 的特点

TCP 提供：

* **可靠传输**：丢包重传。
* **有序交付**：应用层读到的一定是顺序字节流。
* **流量控制**：接收方窗口避免被打爆。
* **拥塞控制**：慢启动、拥塞避免、快速重传、快速恢复。
* **连接管理**：三次握手、四次挥手、TIME_WAIT。

TCP 适合：

* RTMP 推流。
* HTTP-FLV 直播。
* HLS / DASH 点播或准直播。
* 文件上传、录制回放、配置接口。

TCP 不适合极低延迟实时互动的核心原因：

* **队头阻塞（Head-of-Line Blocking）**：前面一个包丢了，后面的包即使到了，应用层也读不到。
* **重传可能放大延迟**：音视频帧过期后再重传没有意义。
* **拥塞控制不感知媒体优先级**：TCP 不知道 I 帧、P 帧、音频帧谁更重要。

### 2. UDP 的特点

UDP 提供的是非常薄的一层：

* 无连接。
* 不保证可靠。
* 不保证有序。
* 不保证不重复。
* 包边界天然保留。

UDP 适合：

* RTP / RTCP。
* WebRTC。
* QUIC。
* SRT。
* 游戏、实时语音、低延迟互动直播。

UDP 的优势不是“比 TCP 快”，而是：

> UDP 把可靠性、有序性、重传策略、拥塞控制交给应用层，音视频系统可以按媒体语义做更聪明的取舍。

例如：

* 音频小包优先级高，尽量保住。
* 旧 P 帧过期后不重传。
* I 帧或关键 SPS/PPS 丢失时请求关键帧。
* 只对关键数据做 NACK，普通视频帧靠 FEC 或直接丢弃。

### 3. 高频面试追问

**问：为什么 WebRTC 主要基于 UDP，而 RTMP 基于 TCP？**

答题思路：

* RTMP 诞生于传统直播场景，强调推流稳定和协议实现简单，基于 TCP 可以复用可靠字节流。
* WebRTC 面向实时互动，延迟通常要求百毫秒级，不能接受 TCP 队头阻塞。
* WebRTC 在 UDP 上自己实现 RTP、RTCP、NACK、FEC、JitterBuffer、拥塞控制、带宽估计和 NAT 穿透。

**问：UDP 丢包怎么办？**

不要只回答“重传”。应按场景拆：

* 实时通话：少量丢包用 PLC、FEC、NACK，过期视频包直接丢。
* 直播：可以引入更大缓冲，部分重传可以接受。
* 点播：通常用 TCP/HTTP，靠协议可靠性。
* 关键帧丢失：请求 IDR / KeyFrame。

## 三、C++ 网络编程底座：从 socket 到 Reactor

### 1. socket 基础流程

TCP 服务端典型流程：

```cpp
socket();
bind();
listen();
accept();
read() / write();
close();
```

UDP 服务端典型流程：

```cpp
socket();
bind();
recvfrom() / sendto();
```

面试要能说清楚：

* `bind`：把本地 IP 和端口绑定到 socket。
* `listen`：把主动 socket 变成监听 socket。
* `accept`：从已完成连接队列取出一个连接。
* `connect`：客户端发起连接；UDP 也可以 `connect`，用于固定对端地址并接收 ICMP 错误。
* `send` 成功不代表对端收到，只代表数据进入本机内核发送缓冲区。

### 2. 阻塞、非阻塞和 IO 多路复用

阻塞 IO 的问题：

* 一个线程阻塞在一个连接上，高并发时线程数量爆炸。

非阻塞 IO 的问题：

* 需要不断轮询读写状态，直接 while 会浪费 CPU。

IO 多路复用解决：

* 一个线程同时监听多个 fd。
* 有事件发生时再回调处理。

常见模型：

* `select`：fd 数量受限，bitmap 拷贝开销大。
* `poll`：fd 数量不再固定，但仍需线性扫描。
* `epoll`：Linux 高并发核心方案，事件驱动，避免全量扫描。
* `kqueue`：BSD / macOS 常见。

### 3. epoll 的 LT 和 ET

LT（Level Trigger，水平触发）：

* 只要 fd 还有数据没读完，就会不断通知。
* 编程简单，不容易漏事件。

ET（Edge Trigger，边缘触发）：

* 状态变化时通知一次。
* 必须配合非阻塞 fd，并循环读到 `EAGAIN`。
* 性能更好，但代码更容易写错。

面试中常见回答：

> ET 模式下如果只读一次，缓冲区还有数据但没有新边沿事件，后续可能永远收不到通知，所以必须循环读到 `EAGAIN`。

### 4. Reactor 模型与 muduo

`muduo` 的核心是 Reactor 模型：

* `EventLoop`：事件循环，一般一个线程一个 loop。
* `Channel`：封装 fd 及其关注事件。
* `Poller`：底层 `epoll` / `poll` 的抽象。
* `TcpConnection`：连接对象，管理读写缓冲区和生命周期。
* `Acceptor`：负责监听和接收新连接。
* `EventLoopThreadPool`：one loop per thread 的线程池模型。

可以这样理解：

> muduo 把 Linux 非阻塞 socket + epoll + 回调 + 线程模型封装成了一套稳定的 Reactor 框架，让业务只关心连接建立、消息到达、写完成和关闭事件。

面试追问重点：

* 为什么 `EventLoop` 不能跨线程随便操作？
* 如何把其他线程的任务投递到 IO 线程？
* `eventfd` / pipe 唤醒机制是什么？
* `TcpConnection` 为什么通常用 `shared_ptr` 管理？
* 写缓冲区满了怎么办？
* 高水位回调有什么用？

## 四、音视频常见应用层协议

### 1. RTMP

RTMP 常用于直播推流：

* 基于 TCP。
* 默认端口常见为 1935。
* 数据分 chunk 传输。
* 常承载 H.264 / AAC。
* 延迟通常在 1 到 3 秒甚至更高。

核心流程：

* TCP 建连。
* RTMP handshake。
* connect。
* createStream。
* publish / play。
* 发送 audio/video message。

面试重点：

* RTMP 基于 TCP，可靠但有队头阻塞。
* chunk stream 用于把大消息拆成多个 chunk，避免大包独占链路。
* FLV Tag 和 RTMP Message 在封装上有密切关系。
* H.264 推 RTMP 通常要先发 SPS/PPS，再发 IDR。

### 2. HTTP-FLV

HTTP-FLV 常用于低延迟直播拉流：

* 基于 HTTP 长连接。
* 内容是连续 FLV Tag。
* 服务端不断向客户端写入音视频 tag。
* 比 HLS 延迟低，比 WebRTC 简单。

优点：

* 穿透性好，走 HTTP。
* 实现和 CDN 分发相对简单。
* 浏览器端可以通过 MSE 播放。

缺点：

* 仍基于 TCP，有队头阻塞。
* 不适合强互动。

### 3. HLS

HLS 是 Apple 推动的 HTTP 分片协议：

* `m3u8` 播放列表。
* `ts` 或 `fMP4` 媒体分片。
* 基于 HTTP，天然适合 CDN。

普通 HLS 延迟高的原因：

* 要等分片生成。
* 播放器通常缓存多个 segment。
* segment 常见 2 到 6 秒。

LL-HLS 降低延迟的方式：

* 更小的 part。
* preload hint。
* blocking playlist reload。
* HTTP/2 支持更好。

面试回答：

> HLS 的优势是兼容性和 CDN 分发，劣势是延迟。传统 HLS 适合大规模直播和点播，不适合实时互动。

### 4. DASH

DASH 与 HLS 类似，也是 HTTP Adaptive Streaming：

* 使用 `MPD` 描述媒体。
* 使用多码率 representation。
* 客户端根据带宽自适应切换码率。

面试中通常与 HLS 对比：

* HLS 生态在 Apple 设备上更强。
* DASH 标准化程度高，常用于 Android、Web、OTT。
* 二者都适合 CDN，不适合超低延迟互动。

### 5. RTP / RTCP

RTP 用于实时媒体数据传输，RTCP 用于控制和反馈。

RTP header 关键字段：

* `sequence number`：检测丢包、乱序。
* `timestamp`：媒体时间戳，用于同步和 jitter 计算。
* `SSRC`：同步源标识。
* `payload type`：负载类型，例如 H.264、Opus。
* `marker bit`：常用于标记一帧结束。

RTCP 常见作用：

* 统计丢包率、抖动、往返时间。
* 发送 Sender Report / Receiver Report。
* NACK 丢包反馈。
* PLI / FIR 请求关键帧。
* REMB / Transport-CC 做带宽估计反馈。

面试重点：

> RTP 本身不保证可靠，它提供序号、时间戳和媒体负载格式，真正的抗丢包、同步和拥塞控制依赖 RTCP 反馈以及上层策略。

### 6. RTSP

RTSP 是控制协议，常见于 IPC 摄像头、安防、监控：

* 类似媒体领域的“遥控器”。
* 负责 `OPTIONS`、`DESCRIBE`、`SETUP`、`PLAY`、`TEARDOWN`。
* 实际媒体数据通常走 RTP。
* RTP 可以走 UDP，也可以 interleaved 到 RTSP 的 TCP 连接里。

高频追问：

* RTSP 和 RTP 是什么关系？
* RTSP over TCP 解决什么问题？
* 为什么摄像头弱网或 NAT 环境下常切 TCP？

回答思路：

> RTSP 负责会话控制，RTP 负责媒体承载。UDP RTP 延迟低，但穿透性差；RTSP over TCP 穿透性更好，但会引入 TCP 队头阻塞。

### 7. WebRTC

WebRTC 是实时互动音视频技术栈，不只是一个协议。

核心组件：

* `ICE`：候选地址收集和连通性检查。
* `STUN`：发现公网映射地址。
* `TURN`：中继转发。
* `DTLS`：密钥协商。
* `SRTP`：加密媒体传输。
* `SCTP/DataChannel`：数据通道。
* `RTP/RTCP`：媒体和反馈。
* `NACK/FEC/PLI/TCC`：弱网对抗与拥塞控制。

WebRTC 建连大致流程：

* 信令交换 SDP offer / answer。
* 收集 ICE candidate。
* STUN 连通性检查。
* 选择最优 candidate pair。
* DTLS 握手。
* SRTP 传输音视频。

面试中要强调：

> WebRTC 的信令不在标准里，业务可以用 WebSocket、HTTP、MQ 等任意方式交换 SDP 和 candidate；标准主要定义端到端媒体、传输、安全和 NAT 穿透机制。

### 8. SRT

SRT 常用于低延迟可靠传输，尤其是公网推流、远程制作：

* 基于 UDP。
* 自带重传、加密、拥塞控制。
* 通过 latency window 平衡延迟和可靠性。
* 比 RTMP 更抗弱网，比 WebRTC 更偏向广播级传输。

面试对比：

* RTMP：简单、生态老、TCP 队头阻塞。
* SRT：UDP + ARQ，抗弱网更好。
* WebRTC：实时互动能力最强，但系统复杂。

### 9. QUIC

QUIC 基于 UDP，在用户态实现传输能力：

* 0-RTT / 1-RTT 建连。
* 内置 TLS 1.3。
* 多路复用避免 TCP 层面的队头阻塞。
* 连接迁移，适合移动网络切换。
* HTTP/3 基于 QUIC。

注意：

* QUIC 解决的是 TCP 连接层的很多痛点。
* 单个 QUIC stream 内部仍然可能有有序交付等待。
* 实时音视频是否使用 QUIC，要看具体产品延迟、可靠性和生态要求。

## 五、音视频封装与网络传输的关系

### 1. 编码帧、封装包、网络包不是一回事

常见层次：

* 编码层：H.264 NALU、H.265 NALU、AAC frame、Opus packet。
* 封装层：FLV Tag、MP4 box、TS packet、RTP payload。
* 传输层：TCP stream、UDP datagram、QUIC packet。

面试中容易混淆：

* 一个视频帧可能拆成多个网络包。
* 一个网络包也可能承载多个小音频帧。
* TCP 是字节流，没有天然消息边界，需要应用层拆包。
* UDP 保留包边界，但受 MTU 限制。

### 2. MTU、MSS 和分片

以太网常见 MTU 是 1500 字节。

UDP 包过大可能导致：

* IP 分片。
* 任意一个分片丢失，整个 UDP datagram 作废。
* NAT、防火墙、移动网络对分片支持不稳定。

所以实时音视频一般避免 IP 分片：

* RTP payload 控制在路径 MTU 以下。
* H.264 大 NALU 用 FU-A 分片。
* H.265 使用对应的 FU 机制。

面试回答：

> 应用层主动按 MTU 分包，比依赖 IP 分片更可控。因为 IP 分片丢任意一片就整体失败，而且中间网络设备可能直接丢弃分片。

### 3. H.264 over RTP 基本概念

H.264 NALU 可能通过 RTP 这样发送：

* 单个小 NALU：Single NAL Unit Packet。
* 多个小 NALU 聚合：STAP-A。
* 大 NALU 分片：FU-A。

关键点：

* SPS/PPS 对解码器初始化很重要。
* IDR 帧丢失会导致后续参考帧无法正确解码。
* RTP marker bit 常用于标记一帧结束。
* 接收端需要按 sequence number 重排和组帧。

## 六、弱网对抗：音视频网络面试核心

### 1. 抖动与 JitterBuffer

网络包到达间隔不稳定，这就是 jitter。

JitterBuffer 的作用：

* 缓冲一小段时间。
* 按序重排乱序包。
* 等待短时间内可能到来的重传包。
* 根据网络抖动动态调整播放延迟。

矛盾点：

* 缓冲越大，播放越稳，但延迟越高。
* 缓冲越小，延迟越低，但更容易卡顿和花屏。

面试回答：

> JitterBuffer 本质是在延迟和流畅度之间做动态权衡。实时通话会倾向低延迟，直播可以接受更大缓冲换稳定性。

### 2. 丢包恢复：NACK、FEC、PLC

NACK：

* 接收端发现序号缺失。
* 通过 RTCP 反馈请求发送端重传。
* 适合 RTT 较低、包仍有播放价值的场景。

FEC：

* 发送额外冗余数据。
* 接收端可用冗余包恢复少量丢包。
* 不需要等待 RTT，但增加带宽开销。

PLC：

* Packet Loss Concealment。
* 常用于音频丢包隐藏。
* 通过前后音频特征估算缺失部分。

如何取舍：

* RTT 低：NACK 效果好。
* RTT 高：重传回来可能已经过期，FEC 更合适。
* 音频：可用 PLC 保连续。
* 视频关键帧丢：通常请求新关键帧。

### 3. 拥塞控制与码率自适应

弱网下不能只靠重传，否则会越重传越拥塞。

常见策略：

* 估计可用带宽。
* 动态调整编码码率。
* 调整帧率、分辨率、GOP。
* 优先保证音频。
* 丢弃过期视频帧。
* 发送端 pacing，避免瞬时突发。

WebRTC 常见相关概念：

* GCC：Google Congestion Control。
* TCC：Transport-wide Congestion Control。
* REMB：Receiver Estimated Maximum Bitrate。
* Pacer：平滑发包。

面试回答：

> 音视频拥塞控制必须和编码器联动。网络层估计带宽，媒体层调整码率和帧结构，否则只在网络层排队会导致延迟不断累积。

## 七、音画同步与时间戳

音视频同步常见时间戳：

* DTS：解码时间戳。
* PTS：显示时间戳。
* RTP timestamp：RTP 媒体时间戳。
* NTP timestamp：网络绝对时间，用于跨流同步。

为什么需要 PTS / DTS：

* B 帧会导致解码顺序和显示顺序不同。
* 解码器按 DTS 解码。
* 渲染器按 PTS 展示。

RTCP SR 的作用：

* 建立 RTP timestamp 和 NTP time 的映射。
* 帮助音频流和视频流对齐。

面试回答：

> 单一路视频可以靠 RTP timestamp 排序和播放，多路音视频同步需要把各自 RTP 时间戳映射到同一参考时钟，RTCP SR 就承担了这个映射作用。

## 八、NAT 穿透与连接建立

### 1. NAT 基础

家庭路由器、公司网络、移动网络通常都在 NAT 后面。

NAT 会把内网地址映射成公网地址和端口：

```text
192.168.1.10:50000 -> 113.88.x.x:62000
```

问题：

* 外部主机不能直接访问内网地址。
* NAT 映射有超时时间。
* 不同 NAT 类型行为不同。

### 2. STUN / TURN / ICE

STUN：

* 查询自己在公网看到的 IP:Port。
* 用于打洞。

TURN：

* 当 P2P 打不通时，通过中继服务器转发。
* 成本高，但成功率高。

ICE：

* 收集 host、srflx、relay candidate。
* 做连通性检查。
* 选择最优链路。

面试回答：

> STUN 是探测公网映射，TURN 是兜底中继，ICE 是完整的候选收集、探测、排序和选路框架。

## 九、安全：TLS、DTLS、SRTP

常见安全层：

* HTTPS：HTTP over TLS。
* WSS：WebSocket over TLS。
* RTMPS：RTMP over TLS。
* DTLS：UDP 上的 TLS 风格握手。
* SRTP：加密 RTP 媒体数据。

WebRTC 中：

* DTLS 用于握手和密钥协商。
* SRTP 用于加密实际音视频 RTP 包。
* 信令通道本身也应该走 HTTPS / WSS。

面试重点：

> TLS 主要保护 TCP 字节流，DTLS 面向 UDP datagram，SRTP 则是专门保护 RTP 媒体包的加密协议。

## 十、从 muduo 使用者到可面试的 C++ 网络能力

### 1. 必须掌握的底层点

* 非阻塞 socket。
* `epoll` 事件循环。
* Reactor 模型。
* 线程模型：one loop per thread。
* 连接生命周期管理。
* 输入缓冲区和输出缓冲区。
* 粘包、拆包、半包。
* 高水位回调和背压。
* 定时器和心跳。
* 优雅关闭与异常关闭。

### 2. 音视频服务端常见连接问题

粘包 / 半包：

* TCP 是字节流，不保留消息边界。
* 应用层必须设计包头，比如 magic、length、type、timestamp。

写缓冲区堆积：

* 说明发送速度大于网络实际发送能力。
* 继续无限写会导致内存膨胀和延迟累积。
* 应设置高水位，必要时降码率、丢帧或断开慢连接。

心跳：

* 检测死连接。
* 保持 NAT 映射。
* 及时释放服务端资源。

### 3. 音视频推流服务如何设计？

可以按这条线回答：

* 网络层：基于 `epoll` / `muduo` 处理连接和事件。
* 协议层：解析 RTMP / HTTP-FLV / RTP。
* 封装层：处理 FLV Tag、RTP packet、TS segment。
* 缓存层：GOP cache、音频 cache、关键帧索引。
* 分发层：一个上行流对应多个下行观看者。
* 背压策略：慢客户端不能拖垮推流和其他观看者。
* 监控层：码率、帧率、丢包、RTT、延迟、卡顿率。

## 十一、典型面试题与答题框架

### 1. TCP 三次握手为什么不是两次？

核心点：

* 确认双方收发能力。
* 防止历史连接请求造成误连接。
* 同步初始序列号。

### 2. TIME_WAIT 为什么存在？

核心点：

* 确保最后一个 ACK 能被对端收到。
* 让旧连接中的迷路报文在网络中自然过期。
* 主动关闭方进入 TIME_WAIT。

### 3. TCP 粘包是什么？

准确说 TCP 没有“包”的概念，它是字节流。

所谓粘包 / 半包是应用层协议边界问题，解决方式：

* 固定长度。
* 分隔符。
* 包头 length 字段。
* TLV / protobuf framing。

### 4. 直播为什么常说 GOP Cache？

GOP Cache 保存最近一个关键帧开始的一组帧。

新观众进入时：

* 如果直接从 P 帧开始，无法解码。
* 从最近 IDR + SPS/PPS 开始，能快速首屏。

### 5. 丢了一个 P 帧会怎样？

可能影响后续依赖它的帧。

处理方式：

* 如果实时性强，丢弃相关参考链，等待下一个关键帧。
* 请求关键帧。
* 使用错误隐藏降低花屏感知。

### 6. 音频和视频谁优先？

通常优先音频。

原因：

* 人对音频中断更敏感。
* 音频码率低，保住成本小。
* 视频可以降帧、降分辨率，音频断续会明显破坏体验。

### 7. RTMP、HLS、WebRTC 怎么选？

* RTMP：常用于主播端推流到服务器，生态成熟。
* HTTP-FLV：直播拉流，延迟较低，基于 HTTP。
* HLS：大规模分发、兼容性好、延迟较高。
* WebRTC：实时互动、连麦、会议、低延迟直播。
* SRT：公网远距离可靠低延迟传输、专业制作链路。

### 8. UDP 怎么保证可靠？

不是简单复制 TCP，而是按业务定制：

* sequence number 检测丢包。
* jitter buffer 排序。
* NACK 请求重传。
* FEC 前向纠错。
* ACK / RTT 估计。
* 拥塞控制。
* 过期包丢弃。

### 9. WebRTC 为什么需要 TURN？

因为并不是所有 NAT 都能打洞成功。

尤其是：

* 对称 NAT。
* 严格防火墙。
* 企业网络。

TURN 作为中继兜底，牺牲服务器带宽成本换连接成功率。

### 10. 为什么弱网不能无限重传？

因为：

* 重传会占用更多带宽。
* RTT 高时重传包回来已经过期。
* 排队会让端到端延迟越来越大。
* 音视频更关心“及时可播放”，不是所有字节最终到达。

## 十二、面试复习路线

建议按下面顺序补：

1. **socket + TCP/UDP 基础**：三次握手、四次挥手、拥塞控制、粘包、非阻塞。
2. **IO 多路复用与 Reactor**：`epoll`、LT/ET、muduo 架构、线程模型。
3. **直播协议**：RTMP、HTTP-FLV、HLS、DASH。
4. **实时协议**：RTP、RTCP、RTSP、WebRTC。
5. **弱网对抗**：JitterBuffer、NACK、FEC、PLC、拥塞控制。
6. **NAT 与安全**：STUN、TURN、ICE、TLS、DTLS、SRTP。
7. **工程设计题**：推流服务、拉流服务、多人连麦、低延迟直播、慢客户端处理。

最后要形成一条主线：

> C++ 网络库解决的是“高并发连接和字节收发”，音视频网络解决的是“在复杂网络条件下按媒体价值传输数据”。资深音视频开发必须同时理解这两层。
