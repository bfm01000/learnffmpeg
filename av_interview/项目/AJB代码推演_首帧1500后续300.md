# AJB 代码级推演：首帧 1500ms 延时，后续帧 300ms 延时

这是一个非常贴近真实弱网环境的推演。首帧因为建连等原因迟到了 1500ms，而后续网络虽然恢复了一些，但依然有 300ms 的稳定延时（比如跨国传输或经过了多个中转节点）。

我们来看看这段代码是如何一步步把 1500ms 的历史包袱甩掉，并最终收敛到 300ms 左右的稳态的。

---

### 背景设定
*   **推流端（相机）**：每 33ms 发送一帧。
*   **车机端（接收端）**：
    *   **Frame 0（首帧）**：PTS = 0ms，但由于网络极差，到达车机时本地时间 `nowMs` 已经是 **1500ms** 了（实际延时 1500ms）。
    *   **Frame 1, 2, 3...**：网络有所好转，后续帧的实际传输+解码延时稳定在 **300ms**。
*   **AJB 参数设定**：
    *   `smoothDeltaMs_` = 0（假设不人为前置）。
    *   `minBufferMs` = 10ms。
    *   `maxBufferMs` = 120ms。

---

### 第一步：首帧到达（Frame 0）—— 一笔勾销，建立基准

*   **输入**：`sampleTimeMs` (PTS) = 0, `nowMs` = 1500。
*   **代码逻辑**：
    *   进入 `if(!queue3Started_)` 分支（第 50 行）。
    *   **建立基准**：
        *   `queue3BasePtsMs_` = 0
        *   `queue3BaseMonoMs_` = 1500
    *   **初始状态**：
        *   `queue3TargetBufferMs_` = 0
        *   `queue3WarmupFrames_` = 1
        *   `waitTimeMs` = 0
*   **执行结果**：`waitTimeMs` 为 0，**立刻渲染上屏！**
*   **物理意义**：这 1500ms 的迟到被彻底“原谅”了。AJB 认为：从现在起，PTS=0 对应本地时间 1500，这就是我们新的世界线。

---

### 第二步：Frame 1 到达 —— 发现“早到”，触发慢降与兜底

Frame 1 的 PTS 是 33ms。因为它实际延时是 300ms，所以它到达车机的真实本地时间 `nowMs` 是 333ms。
**注意！** 此时车机的本地时间才走到 333ms，但我们刚才把基准设在了 1500ms！这意味着什么？

*   **输入**：`sampleTimeMs` (PTS) = 33, `nowMs` = 333。
*   **代码逻辑**：
    *   **计算预期时间**（第 72 行）：`expectedMonoMs` = 1500 + (33 - 0) = **1533ms**。
    *   **计算观测延时**（第 74 行）：`observedDelayMs` = 333 - 1533 = **-1200ms**。
        *   *（物理意义：相对于首帧那 1500ms 的龟速，这帧简直是“光速”到达，它比预期整整早到了 1.2 秒！）*
    *   **EMA 滤波（慢降）**（第 87-91 行）：
        *   `errMs` = -1200 - 0 = -1200 < 0。触发慢降。
        *   当前是 Warmup 阶段（`queue3WarmupFrames_ < 10`），`alpha` = 0.2。
        *   `queue3TargetBufferMs_` = 0.2 * (-1200) + 0.8 * 0 = **-240ms**。
    *   **限幅兜底**（第 95-98 行）：
        *   目标缓冲不能是负数，也不能太小。
        *   `queue3TargetBufferMs_` 被强行 `clamp` 到了下界 `minBufferMs` = **10ms**。
    *   **计算等待时间**（第 100-102 行）：
        *   `deadlineMs` = 1533 + 10 - 0 = 1543ms。
        *   `waitTimeMs` = 1543 - 333 = **1210ms**。
*   **执行结果**：渲染线程去 `sleep(1210)`。
*   **物理意义**：系统发现这帧来得太早了，为了维持和首帧一样的平滑节奏，它决定让这帧在队列里睡 1.2 秒。

---

### 第三步：Frame 2, 3, 4... 疯狂涌入 —— 触发背压追赶（Backpressure）

就在渲染线程呼呼大睡这 1.2 秒的时候，网络可没闲着！
因为后续帧的延时都是 300ms，它们会以每 33ms 一帧的速度，源源不断地到达车机。

*   **T = 366ms**：Frame 2 到了，塞进队列。
*   **T = 399ms**：Frame 3 到了，塞进队列。
*   ...
*   **T = 1543ms**：渲染线程终于睡醒了！把 Frame 1 渲染上屏。
*   **此时的队列状态**：在它睡觉的这 1.2 秒里，队列里已经积压了将近 **36 帧**数据！

**渲染线程立刻去拿 Frame 2：**
*   **输入**：`pendingLeft` = 35（积压严重！）。
*   **代码逻辑**：
    *   AJB 照常计算预期时间、观测延时、EMA 目标缓冲。算出来的 `waitTimeMs` 可能还是个很大的正数。
    *   **【关键破局点】背压追赶**（第 104-107 行）：
        ```cpp
        if(pendingLeft > 0) {
            waitTimeMs = std::min(waitTimeMs, 2.0);
        }
        ```
        因为有积压，AJB 无视了 EMA 算出的长等待时间，强行把 `waitTimeMs` 压缩到了 **2ms**！
*   **执行结果**：渲染线程只睡了 2ms，立刻渲染 Frame 2。
*   **后续循环**：渲染线程像打了鸡血一样，以每 2ms 一帧的极快速度，疯狂消耗队列里的 35 帧积压数据。画面出现短暂的“快进”。

---

### 第四步：积压消耗完毕，完美收敛

经过极短暂的“快进”追赶，队列里的几十帧积压被消耗殆尽（`pendingLeft == 0`）。

此时，我们来看看系统的稳态：
*   **时间轴**：由于我们用极快的速度消耗了积压，当前的本地时间 `nowMs` 已经追上了最新到达的帧。
*   **观测延时 `observedDelayMs`**：因为后续帧的实际延时都是 300ms，它们到达时的 `nowMs` 和 `expectedMonoMs` 之间的差值会趋近于 0（因为我们已经把之前 1.2 秒的空裕时间通过快进消耗掉了）。
*   **目标缓冲 `queue3TargetBufferMs_`**：由于观测延时趋近于 0，EMA 算出的目标缓冲会稳定在下界 `minBufferMs`（**10ms**）。
*   **等待时间 `waitTimeMs`**：每来一帧，算出的等待时间大约就是 **10ms** 左右。

**最终结果：**
*   系统成功甩掉了首帧 1500ms 的历史包袱。
*   端到端延时稳定在：**300ms（真实网络延时）+ 10ms（AJB 底水）= 310ms**。
*   画面恢复了 33ms 一帧的平滑播放。
*   整个过程（从 1500ms 降到 310ms）完全由代码自动闭环完成，无需任何人工干预。
