## 模块一：渲染到编码的“零拷贝”链路（AHardwareBuffer & Surface）

*候选人自述：原先 4K 直播链路里，GPU 渲染后通过 `glReadPixels` 回读到 CPU 内存，再送 FFmpeg/MediaCodec 编码，单帧 `ReadFrame` 经常 20ms~40ms。后来改成 `AHardwareBuffer + Surface` 的硬件帧链路，并把 `glFinish` 改成 `glFlush`，让 CPU 渲染线程单帧耗时从 25ms 级别降到 0.36ms 左右。*

### 追问 0：你这个优化项目的原始链路和核心瓶颈是什么？不要直接说“零拷贝”，先把旧链路讲清楚。

- **考察点**：是否真的理解项目背景，而不是只会背 `AHardwareBuffer` 关键词。
- **期待回答**：旧链路大概是：
  ```text
  相机 / 解码输出
      -> GPU OffscreenRender 做全景拼接、滤镜、画面处理
      -> glReadPixels 从 GPU 显存回读到 CPU 内存
      -> CPU 侧得到 YUV420P / RGBA 数据
      -> FFmpeg 封装层
      -> MediaCodec 硬件编码
      -> RTMP 推流
  ```
  真正的瓶颈在 `glReadPixels` 这一步。4K 一帧 RGBA 大约是 `3840 * 2160 * 4 ≈ 31.6MB`，如果 30fps，就是接近 1GB/s 的回读压力。更关键的是这不是普通 memcpy，它会强制 CPU 等 GPU，把 GPU 纹理从适合采样的 Tiled/Compressed 布局转换成 CPU 可读的 Linear 布局，还会破坏 GPU/VPU 的异步流水线。所以优化目标不是“让拷贝更快”，而是从架构上把 CPU 回读彻底拿掉。

### 追问 1：你提到干掉了 `glReadPixels`，那你能从底层解释一下，为什么 `glReadPixels` 在 4K 分辨率下会这么慢吗？仅仅是因为数据量大吗？

- **考察点**：对 GPU 内存布局（Tiled vs Linear）的理解。
- **期待回答**：不仅仅是数据量（30MB）的问题。更致命的是，GPU 显存为了优化 2D 纹理采样，通常采用 **Tiled（块状/交错）布局**；而 CPU 需要的是 **Linear（线性）布局**。`glReadPixels` 强制同步了 CPU 和 GPU，并且在底层做了一次极其昂贵的 De-tiling（反解算重排）操作。
  对 4K 直播来说，这一步有三重代价：
  1. **同步代价**：CPU 必须等 GPU 前面的渲染命令完成，流水线被打断。
  2. **格式/布局转换代价**：GPU 友好的 Tiled/AFBC 等布局需要转成 CPU 可读的 Linear 布局。
  3. **带宽代价**：4K 单帧几十 MB，30fps 会持续压垮内存总线，带来发热和降频。
  所以 `glReadPixels` 慢，不只是“拷贝大”，而是“同步 + De-tiling + 内存带宽”叠加。

### 追问 2：你用了 `AHardwareBuffer`。在申请这个 Buffer 时，你传了什么 `USAGE` 标志位？为什么？

- **考察点**：对 Android 内存分配器（Gralloc）机制的熟悉程度，是否踩过坑。
- **期待回答**：因为我的场景是“GPU 渲染 -> 硬件编码”，所以我传了 **`USAGE_GPU_FRAMEBUFFER | USAGE_VIDEO_ENCODE`**。`FRAMEBUFFER` 让 GPU 能往里画图，`VIDEO_ENCODE` 让底层分配出符合 VPU 硬件对齐和块状（Tiled）要求的物理内存。
**避坑关键**：**绝对不能传** `USAGE_CPU_READ_OFTEN`。一旦传了 CPU Read，Gralloc 为了照顾 CPU 的线性读取能力，会一票否决掉 GPU 和 VPU 喜欢的 Tiled 布局，强制退化为最原始的 Linear（线性）内存。这会导致硬件无损压缩（如 AFBC）全部失效，内存带宽暴涨，反而导致更严重的发热。

### 追问 2.1：你在业务里到底是怎么把 `AHardwareBuffer` 穿过旧的 FFmpeg/渲染队列的？

- **考察点**：是否理解“硬件帧穿透”对旧架构的侵入点。
- **期待回答**：我不是把 `AHardwareBuffer` 拷贝成 CPU YUV 后再走旧链路，而是把它作为一种硬件帧格式穿透到编码端。核心改造点包括：
  1. **底层分配改造**：原来 `CameraLiveRender` 分配 CPU 可读的 YUV/RGBA 内存；现在直接申请 `AHardwareBuffer`，让它能作为 GPU FBO 渲染目标，也能作为后续纹理采样或编码输入的来源。
  2. **格式标记改造**：生成的 `AVFrame` 不再标记成普通 `YUV420P`，而是标记成自定义的 `AV_PIX_FMT_AHARDWAREBUFFER`，或者在 `AVFrame` 的扩展字段中携带硬件句柄。
  3. **编码配置改造**：直播编码器强制走 MediaCodec Surface 模式，例如 `kMediaCodecModel = "surface"`，并允许 `AV_PIX_FMT_AHARDWAREBUFFER` 这种硬件帧穿透。
  4. **旧校验放开**：原来代码里可能有 `CHECK(options_->enFormat == frame->format)` 这类只允许 `YUV420P` 的防御性校验，需要改成识别硬件帧，否则还没到编码器就被拦掉。
- **面试加分点**：这类改造的难点不是申请一个 Buffer，而是让旧的队列、`AVFrame` 生命周期、编码器入口都能识别“这是硬件帧，不要 CPU 读它”。

### 追问 3：你刚才说 CPU 侧耗时被压到 0.36ms，但 GPU/VPU 不可能真的 0.36ms 干完所有事。真实渲染和编码耗时去哪了？编码器怎么知道 GPU 画没画完？

- **考察点**：对异步渲染、硬件同步栅栏（Fence / Sync Object）的理解。
- **期待回答**：这 10ms 的耗时被**后移**了。CPU 提交完指令（`glFlush`）就立刻返回去准备下一帧了。底层通过**硬件同步栅栏（Fence）**将这个 Buffer 传给 MediaCodec。MediaCodec 在真正开始硬件编码前，会在底层阻塞等待这个 Fence 触发（即等待 GPU 真正画完）。这就把“渲染线程的死等”变成了“渲染与编码的流水线并行”。

### 追问 3.1：`glFinish` 和 `glFlush` 的区别是什么？为什么这个项目里 `glFinish` 是“隐形阻塞”？

- **考察点**：是否能解释 OpenGL 命令提交模型，而不是只说“`glFlush` 更快”。
- **期待回答**：
  - `glFinish`：把前面所有 GL 命令提交给 GPU，并且 CPU 当前线程会阻塞，直到 GPU 真正执行完这些命令。
  - `glFlush`：只是确保命令被尽快送入 GPU 命令队列，CPU 不等待 GPU 执行完成。
  在旧链路中，如果上层为了保证读到完整画面调用 `glFinish`，CPU 渲染线程就会把 GPU 的真实渲染耗时全部等完。我们当时看到 `ReadFrame` 仍然有 19ms 左右，本质就是 CPU 被 `glFinish` 卡住了。
  改成硬件帧之后，`AHardwareBuffer` 通过 GraphicBuffer/Gralloc 在系统组件之间传递，底层有隐式 Fence 保证生产者和消费者同步。也就是说，编码器会在真正消费 Buffer 前等 GPU 完成，不需要业务层用 `glFinish` 傻等。这里不是“不等就乱了”，而是把等待从 CPU 业务线程转移到了硬件流水线的正确位置。

### 追问 4：你提到这是一个“折中的 Surface 模式”，中间还发生了一次 GPU Blit（纹理拷贝）。为什么不做到真正的物理零拷贝（直接把 Buffer 指针塞给编码器）？

- **考察点**：对底层流转架构的深度认知，以及工程上的 ROI（投入产出比）权衡。
- **期待回答**：这里有两条截然不同的流转路径，我做过深度的权衡：
  1. **理论上的完美路径（真正的物理零拷贝）**：
    GPU 渲染完画面存入 `AHardwareBuffer` -> C++ 层提取底层的硬件句柄（Hardware Handle） -> 彻底改造整个 FFmpeg 的队列架构，让所有的中间模块都能透传这个句柄 -> 最终到达编码器，通过 NDK 底层 API（如 `AMediaCodec_queueInputBuffer`）直接把物理地址喂给 VPU。
      **为什么放弃？** 因为这不仅对现有架构的侵入性极大（几乎要重写半个引擎），更致命的是，Android NDK 对直接喂 Buffer 给编码器的支持存在严重的碎片化问题，很多低端机型根本不支持这种直通模式，风险极高。
  2. **我实际采用的 GPU Blit 折中路径（高 ROI 方案）**：
    GPU 渲染完画面存入 `AHardwareBuffer` -> 我把它巧妙地**伪装**进 `AVFrame` 的备用字段（如 `data[3]`），并打上自定义标签 -> 它顺着老队列一路流转，**中间模块零侵入** -> 到达编码端，编码器识别到标签，向系统申请一个极其稳定的 `Input Surface` -> 编码器内部启动一个极轻量的 OpenGL 环境，把传过来的 Buffer 绑定为外部纹理（`OES`），在这个 Surface 上进行一次极速的重绘（Blit） -> MediaCodec 自动从 Surface 拿货编码。
  **总结**：这个折中方案的精妙之处在于，它用仅需 1~2ms 的 GPU 内部高速拷贝（Blit），完美干掉了原来高达 30ms 的 CPU 阻塞回读；同时利用 `AVFrame` 伪装和原生的 `Surface` 机制，规避了碎片化风险，保证了极高的工程稳定性，是投入产出比（ROI）最高的架构决策。

### 追问 5：你说优化后 CPU 单帧降到 0.36ms，这个数字怎么来的？它说明了什么，又不说明什么？

- **考察点**：是否能正确解读性能指标，不把局部耗时当成整体吞吐。
- **期待回答**：这个数据来自 10s 平均耗时统计，比如：
  ```text
  OffscreenRender::RenderToSample2 avg cost(10s)
  Total: 0.36255 ms
  Render: 0.0557769 ms
  ReadFrame: 0.306773 ms
  Commit: 0 ms
  ```
  它说明 CPU 渲染线程不再承担 4K 像素回读，`ReadFrame` 从原来的 20ms~40ms 级别降到 0.3ms 左右，CPU 侧瓶颈被打掉了。
  但它不代表“整个直播链路一帧只要 0.36ms”，因为 GPU 实际渲染、MediaCodec 编码、Mux、网络发送仍然在后面的异步流水线里发生。正确结论是：**CPU 回读瓶颈解除，系统瓶颈会合理转移到 GPU/VPU/网络这些真正应该承担工作的模块上。**

### 追问 6：优化后为什么还是可能达不到稳定 30fps？是不是说明零拷贝没用？

- **考察点**：是否理解瓶颈转移，而不是看到 FPS 不满就否定局部优化。
- **期待回答**：不是。零拷贝解决的是 CPU 读回和内存带宽瓶颈。优化后如果直播只能跑到 23~25fps，说明瓶颈已经从 CPU 转移到 VPU 硬件编码器或网络发送。
  这恰恰是符合预期的现代硬件流水线：
  ```text
  相机 30fps 生产
      -> GPU 快速渲染/提交
      -> VPU 硬件编码
      -> Mux/Network 发送
  ```
  当 4K 编码单帧需要 20ms~30ms，或者网络发送耗时上升时，最慢环节决定整体吞吐。零拷贝的价值是让 CPU 不再做低效像素搬运，降低发热、释放算力，并把瓶颈暴露到真正的硬件编码和网络 QoS 上。

## 模块二：网络 I/O 解耦与异步队列

*候选人自述：引入了异步发送队列，解除了网络背压导致的编码器阻塞。*

### 追问 1：你把网络发送（`WritePacket`）放到了异步队列里。网络发送是很慢的，如果网络一直不好，你的队列总有满的时候。队列满了你怎么处理？

- **考察点**：对生产者-消费者模型中边界情况（满队列）的处理策略，以及对视频编码结构（GOP）的理解。
- **期待回答**：队列满了**绝对不能阻塞**编码线程（否则又回到了同步阻塞的老路）。当队列达到最大容量（如 90 帧）时，我会触发**智能丢帧（Smart Drop GOP）**策略。
  **具体实现逻辑如下：**
  1. **状态标记**：在队列类中维护一个布尔标志位 `is_dropping_gop_ = false`。
  2. **触发丢帧**：当编码器吐出一个 `AVPacket`，准备放入队列时，如果发现 `queue.size() >= MAX_CAPACITY`，则将 `is_dropping_gop_` 置为 `true`。
  3. **如何判断 GOP 边界（核心）**：在 FFmpeg 中，可以通过检查 `AVPacket` 的标志位来判断它是不是关键帧（I 帧）。代码通常是 `if (pkt->flags & AV_PKT_FLAG_KEY)`。
  4. **执行丢弃逻辑**：
    - 只要 `is_dropping_gop_ == true`，新来的包**直接丢弃**（调用 `av_packet_unref` 释放内存），不放入队列。
    - **直到**遇到下一个关键帧（`pkt->flags & AV_PKT_FLAG_KEY` 为真）。
    - 遇到新的关键帧时，检查当前队列是否有足够的空间（比如水位已经降到了安全线以下）。如果有空间，则将 `is_dropping_gop_` 恢复为 `false`，把这个关键帧以及后续的包重新放入队列。
  **为什么必须按 GOP 丢弃？**
  如果队列满了就随便丢弃一个 P 帧或 B 帧，拉流端（观众）在解码时会因为缺少参考帧而出现严重的**马赛克、花屏或画面撕裂**，直到下一个 I 帧到来才能恢复。
  按整条 GOP 丢弃，虽然观众会感觉到画面“卡顿”了一下（跳过了一段时间），但一旦画面恢复，依然是**清晰、完整**的。在弱网下，“卡顿”的体验远好于“满屏马赛克”。

### 追问 2：你在把 `AVPacket` 丢进 Lambda 表达式异步执行时，提到了“值捕获局部变量”来保证 `Muxer` 对象的存活。能具体写一下伪代码吗？如果不用值捕获会怎样？

- **考察点**：C++ Lambda 捕获机制、智能指针（`std::shared_ptr`）生命周期管理。
- **期待回答**：
  ```cpp
  // ❌ 错误做法 1：隐式捕获 this 指针
  // 原因：[=] 或 [this] 只是捕获了当前对象的裸指针。当异步队列执行这个 Lambda 时，
  // 当前对象可能已经被销毁了，此时调用 muxer_->WritePacket 会直接导致野指针 Crash。
  queue->push([=, pkt]() { muxer_->WritePacket(pkt); });

  // ❌ 错误做法 2：引用捕获局部变量
  // 原因：[&] 会捕获局部变量的引用。当离开当前作用域时，局部变量被销毁，
  // 异步线程再去访问这个引用，同样会导致野指针 Crash。
  auto muxer = muxer_;
  queue->push([&muxer, pkt]() { muxer->WritePacket(pkt); });

  // ✅ 正确做法：值捕获 shared_ptr
  // 原因：通过值捕获（拷贝），强制让 shared_ptr 的引用计数 +1。
  // 只要这个 Lambda 还在队列里没执行完，Muxer 对象就绝对不会被销毁，保证了内存安全。
  auto muxer = muxer_; 
  queue->push([muxer, pkt]() { muxer->WritePacket(pkt); });
  ```

### 追问 3：你排查到 `AppendSample / av_interleaved_write_frame` 会阻塞，这种网络反压是怎么一路传回渲染线程的？

- **考察点**：是否理解 RTMP/TCP 同步发送、MediaCodec Input Surface、GPU Blit 之间的连锁反应。
- **期待回答**：旧链路里编码和网络发送没有充分解耦，`MediaAssetWriterFrameInput::AppendSample` 最终调用 `av_interleaved_write_frame` 是同步阻塞的。网络变差时，Socket 发送缓冲区变满，`WritePacket` 变慢，进而导致：
  ```text
  网络发送阻塞
      -> Muxer/Writer 线程阻塞
      -> 编码器输出侧排不出去
      -> MediaCodec 内部队列堆积
      -> Input Surface 可用槽位减少
      -> GPU Blit / eglSwapBuffers 阻塞
      -> 渲染/推流队列积压
      -> SequenceSource 队列满
      -> dropPutToUpdate 丢帧
  ```
  所以网络问题不只影响“最后发送”，它会通过同步调用和有限队列形成全链路反压，最终表现为上游丢帧、帧率下降、甚至 GPU 入口阻塞。

### 追问 4：日志里 `ReceivePacket` 经常是 0ms，但 `SendFrame / GPU Blit` 很慢，这说明什么？

- **考察点**：是否理解硬件编码器的异步输入/输出模型。
- **期待回答**：这说明瓶颈不一定在“等编码器吐包”，而可能卡在编码器入口或下游发送。
  - `ReceivePacket` 0ms：可能是编码器已经有压缩包，直接返回；也可能暂时没有包，返回 `EAGAIN`，不会长时间阻塞。
  - `SendFrame / GPU Blit` 慢：通常说明 MediaCodec 的 Input Surface 队列满了，GPU 往编码器 Surface 交换 Buffer 时被系统阻塞。
  根因可能是 VPU 编码不过来，也可能是编码后的包被网络发送阻塞，导致出口排不掉、入口也塞住。

### 追问 5：你怎么判断长时间直播掉到 3~5fps，是发热降频还是网络反压？

- **考察点**：是否会用控制变量法定位线上复杂性能问题。
- **期待回答**：我不会直接猜，而是做隔离实验：
  1. **隔离网络**：把 RTMP 推流改成本地 MP4 录制，保持 4K 分辨率、码率、编码器配置不变。
  2. **观察 10 分钟以上**：如果本地录制稳定 28~30fps，而 RTMP 推流掉到 3~5fps，说明主要是网络上行或 RTMP 同步发送反压。
  3. **如果本地录制也掉帧**：说明不是网络，而是 4K 编码 + 屏幕常亮 + GPU/VPU 高负载触发了 Thermal Throttling，系统把 GPU/VPU 频率砍掉，编码耗时暴涨。
  4. **辅助日志**：记录 `Render`、`SendFrame`、`ReceivePacket`、`AppendSample/Mux/Network Send` 各阶段 10s 平均耗时，看瓶颈是从哪一段开始飙升。
- **典型判断**：
  ```text
  Render 很快，AppendSample/Network Send 从 5ms 涨到 20ms+
  -> 网络发送反压

  本地录制也从 30fps 掉到几 fps，且设备温度升高
  -> 发热降频 / VPU 物理极限
  ```

## 模块三：动态自适应码率（ABR）算法落地

*候选人自述：基于队列积压水位，实现了 ABR 算法，通过 JNI 动态调整 MediaCodec 码率。*

### 追问 1：你的 ABR 算法是基于“队列水位”的。为什么用队列水位，而不是直接计算网络的 RTT（往返时延）或丢包率？

- **考察点**：对流媒体传输协议和工程实践的理解。
- **期待回答**：在应用层（尤其是使用 RTMP 这种基于 TCP 的协议时），我们很难直接、准确地获取底层的 RTT 和物理丢包率。而**发送队列的积压帧数（Buffer Level）**，是反映 TCP 拥塞控制窗口和实际上行带宽**最直观、最客观**的指标。队列积压说明生产速度 > 发送速度（网络拥塞）；队列清空说明发送速度 > 生产速度（网络通畅）。
  **RTT 原理补充**：
  RTT（Round-Trip Time，往返时延）指的是一个数据包从本端发出去，到收到对端确认响应，中间经历的完整往返时间。
  ```text
  客户端发包时间 t1
      -> 数据经过上行链路到服务器
      -> 服务器收到后返回 ACK 或业务响应
      -> 响应经过下行链路回到客户端
  客户端收到响应时间 t2

  RTT = t2 - t1
  ```
  在 TCP 里，内核会根据数据段发送时间和 ACK 返回时间估算 RTT，并用它来做超时重传、拥塞控制窗口调整等。但这个 RTT 主要在**内核 TCP 协议栈内部**使用，普通 RTMP 推流业务通常拿不到足够精确、实时、跨平台一致的 RTT 数据。
  更关键的是，RTT 反映的是“一个包来回一趟有多慢”，但直播推流真正关心的是“当前编码产出速度是否超过了实际上行发送能力”。RTT 可能已经升高，但应用层不一定能及时感知；也可能 RTT 看起来还可以，但 Socket 发送缓冲区已经开始堆积。相比之下，发送队列水位直接反映了生产者和消费者的速度差：编码线程持续生产，网络线程发不出去，队列就一定会涨。因此在 RTMP/TCP 推流场景下，我会把队列水位作为 ABR 的主控制信号，把 RTT/发送耗时这类指标作为辅助观测。

### 追问 2：你提到高水位（>60帧）降码率，低水位（<15帧）升码率。如果网络在临界点频繁波动，你的码率会不会也跟着频繁横跳，导致画面忽糊忽清？

- **考察点**：对控制算法稳定性的考量（防抖动/迟滞机制）。
- **期待回答**：为了防止频繁横跳，我做了两层防抖设计：
  1. **时间防抖**：不是每帧都检查，而是每隔 2 秒（或一个 GOP 周期）才触发一次水位检查和码率调整。
  2. **空间防抖（迟滞区间）**：高水位线（60）和低水位线（15）之间有一个巨大的“安全缓冲区（15~60）”。在这个区间内，码率保持不变，只有明确突破上下限才会触发调整。
  另外还可以做**单步调整**：降码率可以快一点，比如直接砍半；升码率必须慢一点，比如每次只升 10%~20%，连续多个周期低水位才允许升。这样可以避免网络刚恢复一点就立刻把码率拉爆。

### 追问 2.1：你是怎么确定低水位用 15、高水位用 60，以及队列最大容量用 90 的？这些数字是不是拍脑袋？

- **考察点**：能否把经验参数解释成可推导、可验证、可调优的工程指标。
- **期待回答**：这几个值不是拍脑袋定的，我是按 **30fps 直播场景**把“帧数”换算成“允许积压的视频时长”来设计的。队列水位本质上不是帧数问题，而是延迟预算问题：
  ```text
  15 帧 ≈ 0.5 秒
  60 帧 ≈ 2 秒
  90 帧 ≈ 3 秒
  ```
  具体含义是：
  1. **低水位 15 帧**：表示队列积压已经降到 0.5 秒以内，说明发送速度明显大于编码生产速度，网络恢复得比较健康。这个时候才允许逐步升码率，避免刚恢复一点就马上把码率拉高。
  2. **高水位 60 帧**：表示队列已经积压约 2 秒。如果继续维持当前码率，观众端延迟会快速变大，并且队列很可能继续逼近上限。所以超过 60 帧就要主动降码率，而不是等队列满了才处理。
  3. **最大队列 90 帧**：表示最多允许积压约 3 秒。它给短时间弱网留了缓冲空间，但不会让直播延迟无限膨胀。超过这个上限后，继续排队已经没有意义，就要触发智能丢帧或按 GOP 丢弃策略。
  高水位不能等于最大容量，因为从检测到高水位、通过 JNI 调 `MediaCodec.setParameters`、编码器真正应用新码率，到低码率数据反映到发送队列，中间存在滞后。如果 90 帧才开始降码率，就没有“刹车距离”了。因此把高水位放在 60，后面预留 30 帧，也就是约 1 秒缓冲空间。
  工程实现上我不会把 15、60、90 写成不可解释的魔法数字，而是按帧率和目标延迟换算：
  ```text
  low_watermark  = fps * 0.5s
  high_watermark = fps * 2.0s
  max_capacity   = fps * 3.0s
  ```
  如果项目是 25fps，就应该相应变成大约 12、50、75。上线前再通过弱网测试、带宽阶跃测试和真实机型压测微调，所以它是一个有依据的初始值，而不是固定不变的玄学参数。

### 追问 3：你通过 JNI 调用 Java 的 `MediaCodec.setParameters` 来动态调码率。为什么不用 NDK 的 C++ API（`AMediaCodec_setParameters`）？这不符合你“追求极致性能”的初衷吧？

- **考察点**：对 Android 碎片化生态的认知，以及在“极致性能”与“工程稳定性”之间的取舍。
- **期待回答**：这确实是一个权衡。NDK 的 `AMediaCodec_setParameters` 是在 Android 8.0（API 26）才引入的，而 Java 层的接口在 Android 4.4（API 19）就有了。为了兼容更广泛的机型，必须走 JNI。
至于性能，JNI 调用的开销在微秒级，而编码一帧需要十几毫秒。并且调码率是一个低频操作（几秒钟才调一次），这点 JNI 开销完全可以忽略不计。在工程实践中，**为了低频操作的微秒级性能提升而牺牲大量机型的兼容性，是不可取的**。

### 追问 4：弱网下为什么“编码前丢帧”可能把直播变成高清 PPT？不是丢帧就能减压吗？

- **考察点**：是否理解编码器码率控制和帧率之间的关系。
- **期待回答**：编码前丢帧只能减少进入编码器的帧数，但如果目标码率不变，编码器可能会把剩下的少数帧压得非常大。比如目标码率还是 10Mbps，原本 30fps 时每帧平均约 40KB；弱网时前面丢到只剩 5fps，编码器为了完成码率目标，可能每帧给到 200KB 以上。
  结果就是：
  ```text
  帧数减少
      -> 单帧包变大
      -> 网络更发不出去
      -> 发送线程阻塞更严重
      -> 上游继续丢帧
      -> 变成 4fps 的高清 PPT
  ```
  所以弱网下首要策略不是盲目编码前丢帧，而是 **ABR 先降码率/分辨率**，让每秒数据量适配当前网络。只有 ABR 降到最低仍然救不回来，才进入 Drop GOP 这类兜底策略。

### 追问 5：为什么“流畅度优先级高于画质”？面试时怎么把这个讲成业务决策，而不是技术口号？

- **考察点**：是否能把底层优化和用户体验/QoS 联系起来。
- **期待回答**：直播是实时业务，用户最不能接受的是卡成 PPT、声音画面断裂、延迟无限增加。弱网或发热时，如果坚持 4K 高码率，最终会导致队列堆积、延迟升高、帧率暴跌。相比之下，动态降到 2.7K/1080P 或降低码率，画面会糊一点，但能保持 25~30fps 和较低延迟。
  所以 QoS 策略应该是：
  1. 网络或温度正常时，尽量维持 4K 高画质。
  2. 网络队列水位升高时，先降码率。
  3. 码率降到下限仍不行时，再降分辨率。
  4. 仍然拥塞时，按 GOP 丢帧保解码正确性。
  这是主流直播平台的共识：**宁可短时间模糊，也不能长时间卡死。**

## 模块四：缓冲队列、内存与延迟权衡

*候选人自述：为了吸收 VPU 编码抖动，我调大了渲染到编码之间的队列，但 4K Graphic Buffer 很大，不能无脑加。*

### 追问 1：为什么扩大队列能缓解掉帧？它解决的到底是什么问题？

- **考察点**：是否理解生产者-消费者模型里的短期抖动吸收。
- **期待回答**：4K 直播里相机一般按 30fps 稳定出图，约 33.3ms 一帧；GPU 渲染很快，但 VPU 编码或网络发送会有抖动。如果队列容量只有 2，编码器某一帧多耗时十几毫秒，就可能导致队列瞬间满，触发上游丢帧。
  扩大到 3~4，可以吸收短时间的 VPU 抖动，让流水线保持并行：
  ```text
  Camera 生产 -> Queue 缓冲 -> GPU/VPU 消费
  ```
  但它只适合吸收“短期抖动”，不能解决持续性瓶颈。如果 VPU 或网络长期低于 30fps，队列迟早会满，必须靠 ABR/降级处理。

### 追问 2：4K 队列扩容会带来多少内存？怎么平衡内存、延迟、流畅度？

- **考察点**：是否对 4K Buffer 的实际成本有数字概念。
- **期待回答**：4K RGBA 单帧大约 30MB。队列从 2 扩到 4，理论上可能多占 60MB 左右的 Graphic Buffer。它的收益是减少抖动掉帧，代价是内存和延迟。
  我的策略不是无脑加大，而是：
  1. **寻找甜点值**：4K 直播通常先试 3~4，吸收编码器轻微抖动，新增延迟约几十到一百毫秒。
  2. **Buffer Pool 池化**：初始化时申请固定数量的 `AHardwareBuffer`，用 Ring Buffer 循环复用，避免运行时频繁分配和内存碎片。
  3. **设备分级**：高端机可以给 4，中低端机保守给 2 或 3。
  4. **动态降级兜底**：如果队列长期高水位，说明不是抖动，而是处理能力不足，要降码率/分辨率，而不是继续加队列。

### 追问 3：为什么队列不能无限大？大队列不是更稳吗？

- **考察点**：是否理解实时直播的延迟约束。
- **期待回答**：队列越大，确实越能扛短期抖动，但直播延迟也会线性增加。30fps 下：
  ```text
  30 帧 ≈ 1 秒
  60 帧 ≈ 2 秒
  90 帧 ≈ 3 秒
  ```
  如果队列无限增长，观众看到的就是几秒甚至十几秒前的画面，直播实时性崩掉。队列应该是“缓冲垫”，不是“垃圾桶”。超过延迟预算后继续排队没有意义，要么降码率，要么按 GOP 丢弃过期数据。

## 模块五：性能数据、排查方法与面试复盘表达

*候选人自述：这个项目不是一次 API 替换，而是通过埋点、控制变量、瓶颈转移分析完成的一次全链路优化。*

### 追问 1：你做这个优化时埋了哪些点？怎么证明优化确实生效？

- **考察点**：是否有数据驱动的性能优化习惯。
- **期待回答**：我会按流水线阶段拆埋点，而不是只看最终 FPS：
  - `OffscreenRender::Render`：GPU 渲染命令提交耗时。
  - `ReadFrame`：旧链路的 CPU 回读或新链路的硬件帧获取耗时。
  - `SendFrame / GPU Blit`：把硬件帧送入 MediaCodec Input Surface 的耗时。
  - `ReceivePacket`：从编码器取压缩包的耗时。
  - `AppendSample / WritePacket`：Mux 和网络发送耗时。
  - `Actual Live Encoding Output FPS`：最终编码输出帧率。
  - 队列水位、drop 次数、温度、码率变化。
  优化前 `ReadFrame` 是 20ms~40ms，优化后 CPU 侧 `ReadFrame` 到 0.3ms 量级，说明 CPU 回读瓶颈被消除。后续如果 FPS 仍不满，就继续看 VPU 和网络阶段，而不是在渲染线程里盲目优化。

### 追问 2：如果面试官质疑“你只是把耗时藏到别的线程了”，你怎么回答？

- **考察点**：是否能区分延迟、吞吐和 CPU 占用。
- **期待回答**：我会承认 GPU/VPU 的真实工作没有消失，但这不是“藏耗时”，而是把工作放回正确的硬件流水线。优化前是 CPU 阻塞等待 + CPU 回读 + 内存带宽爆炸；优化后是 CPU 快速提交，GPU/VPU 异步并行。
  对直播系统来说，我们关注三个指标：
  1. **CPU 占用和发热是否下降**：下降，说明 CPU 回读被拿掉。
  2. **流水线吞吐是否提高**：由最慢阶段决定，通常从 CPU 转移到 VPU/网络。
  3. **端到端延迟是否可控**：通过队列容量、水位、ABR、Drop GOP 控制。
  所以不是把耗时藏起来，而是从串行阻塞变成异步流水线，让专业硬件做专业的事。

### 追问 3：你怎么解释“单帧总耗时 48ms，但实际 FPS 能到 25fps”？

- **考察点**：是否理解流水线并行下的吞吐计算。
- **期待回答**：单帧端到端延迟和系统吞吐不是一回事。假设渲染 9ms、编码推流 39ms，串行算是 48ms，只能 20.8fps。但如果渲染和编码推流是两个线程并行，整体 FPS 取决于最慢阶段：
  ```text
  FPS ≈ 1000 / max(9ms, 39ms) ≈ 25.6fps
  ```
  这就是流水线架构的意义。每一帧从进来到出去可能花 48ms，但流水线填满后，平均每 39ms 可以产出一帧。

### 追问 4：你这个优化的最终价值怎么总结？

- **考察点**：是否能把技术优化转成项目价值。
- **期待回答**：这个优化有三层价值：
  1. **性能价值**：干掉 4K `glReadPixels` 的 CPU 回读，单帧 CPU 渲染线程耗时从 20ms~40ms 降到 0.3ms 量级。
  2. **架构价值**：把链路升级成 `GPU -> AHardwareBuffer/Surface -> MediaCodec -> RTMP` 的硬件异步流水线，减少 CPU/GPU/VPU 之间不必要的数据搬运。
  3. **业务价值**：CPU 算力和内存带宽释放后，4K 直播更稳、发热更低，也给后续实时美颜、AI 跟踪、复杂滤镜留下算力空间。

## 终极灵魂拷问（架构设计）

### 追问：你在这个项目中做了很多“魔改”（比如强制指定私有格式 `AV_PIX_FMT_AHARDWAREBUFFER`，引入异步队列）。如果公司现在要新开一个“纯音频直播”项目，或者要支持一台极老的不支持硬件编码的手机，你的这套架构能平滑兼容吗？

- **考察点**：架构的开闭原则（OCP）、依赖反转、参数化配置。
- **期待回答**：完全可以。我在重构时坚持了**参数化动态路由**的设计。
所有的新特性（零拷贝、异步发送、ABR）都被封装在布尔开关（如 `enableLiveZeroCopy`）后，通过顶层配置向下透传。
如果是不支持硬件编码的老机型，上层只需传入 `false`，底层就会自动走回传统的 YUV420P 内存拷贝和同步发送的老分支。旧业务代码 100% 零侵入，保证了架构的安全和向后兼容。

### 追问：如果某些机型不支持 `AHardwareBuffer + Surface` 这条链路，你怎么兜底？

- **考察点**：是否考虑 Android 设备碎片化和灰度发布。
- **期待回答**：我会做能力探测和策略分层：
  1. **启动时探测**：检查 Android API level、MediaCodec 是否支持目标分辨率/码率/Profile、是否能创建 Input Surface、`AHardwareBuffer` usage 是否申请成功。
  2. **黑白名单**：对已知有问题的 SoC/机型禁用零拷贝路径。
  3. **失败回退**：Surface 编码初始化失败时，回退到 YUV420P 软件路径或 ByteBuffer 硬编路径。
  4. **运行时监控**：如果硬件路径出现持续编码失败、队列异常或 FPS 崩掉，触发降级策略。
  5. **配置开关**：通过远端配置控制 `enableLiveZeroCopy`、队列容量、ABR 参数，便于灰度和线上止损。

### 追问：你怎么证明这套方案不是“过度工程化”？

- **考察点**：能否从收益、风险、复杂度三方面说明工程决策。
- **期待回答**：4K 直播下旧链路单帧回读 20ms~40ms，已经超过 30fps 的 33.3ms 帧预算，继续小修小补没有意义。零拷贝方案虽然复杂，但它解决的是架构级瓶颈，并且收益非常明确：
  - CPU 渲染线程从 25ms 级别降到 0.36ms 左右。
  - 内存带宽压力下降，发热降低。
  - 旧业务通过开关保留回退路径。
  - 后续 ABR、队列水位、Drop GOP 都是在这个异步流水线基础上自然演进。
  所以它不是为了炫技，而是 4K 实时直播的性能约束逼出来的架构升级。

## 模块六：全链路延时与副作用分析——这些优化有没有引入新问题？

> **面试官心理活动**：
> 候选人把优化讲得很漂亮——零拷贝、异步队列、ABR、Fence 流水线。但任何一个有经验的面试官都会追问：**"你做的这些优化，有没有哪个反而引入了新的延时或稳定性问题？"**
> 这个问题考的不是"你有没有把优化做好"，而是**你是否真的理解每个优化的代价**——一个只会说好处、看不到副作用的人，说明优化的边界条件没想清楚。

---

### 追问 1：你把 `glFinish` 改成 `glFlush`，CPU 不等 GPU 了。但编码器内部要等 GPU 的 Fence 信号才能开始编码。这不就是把延时从 CPU 侧挪到 VPU 侧了吗？端到端延时到底有没有增加？

- **考察点**：是否理解异步流水线里"等待位置变了"≠"总等待时间变了"。
- **标准回答**：

  "这个问题问得很关键。先说结论：**端到端延时没有增加，实际还可能略降。**

  关键是搞清楚 GPU 渲染那 ~10ms 的真实工作量**不管等不等都在那里**。区别只是**在什么地方等、等的时候能不能干别的事**。

  旧架构（`glFinish` 同步等待）：
  ```
  CPU: [ 提交渲染命令 ][ glFinish 阻塞等 GPU 画完, ~10ms ][ 回读像素 ][ 送编码 ]
  GPU:                  [ 渲染, ~10ms ]
  时间轴: |←── CPU 线程被卡住, 啥都干不了 ──→|
  ```
  CPU 线程在 `glFinish` 里空转 10ms，GPU 渲染完成后还要再花 20~30ms 做 CPU 回读。编码真正开始 = GPU 画完 + CPU 拷贝 + 送入编码器，总延时 ~30~40ms。

  新架构（`glFlush` + Fence 异步）：
  ```
  CPU: [ 提交渲染命令 ][ glFlush, <1ms ][ 立即准备下一帧 ]
  GPU:                  [ 渲染, ~10ms ]
  VPU:                                  [ Fence 等 GPU 画完(~0 额外等待) ][ 开始编码 ]
  时间轴: |←─ GPU 渲染那 10ms, VPU 也在等待,但它们不是串行加的 ──→|
  ```
  Fence 的等待和 GPU 渲染本身是**重叠**的——VPU 拿到 buffer 就开始等 Fence，GPU 画完那一刻 Fence 立即触发。没有多等任何时间。

  对比端到端：
  - 旧：渲染提交 → 等 10ms→回读 25ms→送编码 = **~35ms 后编码开始**
  - 新：渲染提交 → 等 10ms GPU 渲染 → Fence 触发 → 编码开始 = **~10ms 后编码开始**

  所以端到端延时是**显著下降**的，不是平移。面试官如果追问'那为什么不直接用 `glFinish`'，回答就是：`glFinish` 不仅让 CPU 多等了 10ms，还在那个 10ms 期间占着 CPU 线程不干活，白白损失了流水线并行能力。"

### 追问 2：你的异步发送队列最大容量是 90 帧，约 3 秒。如果网络突然变差，队列堆满，观众端不就多了 3 秒延迟吗？这不算引入了新延时？

- **考察点**：是否理解"缓冲延时"和"卡顿"之间的 QoS 权衡，以及 ABR 如何缩短延时窗口。
- **标准回答**：

  "这个问题是异步队列方案最核心的 tradeoff。我分三层讲清楚。

  **第一层：3 秒是最坏情况，不是常态。**

  队列 90 帧是**容量上限**，不是每帧都在里面待 3 秒。网络正常时，帧进去几乎立刻被发送线程取走，队列实际深度只有 1~3 帧，延时增加 ≈ 几十毫秒，可以忽略。只有网络严重拥塞、发送速度落后于编码速度时，队列才开始堆积。

  **第二层：弱网时，旧架构的延时其实更差。**

  旧架构没有队列缓冲，看起来'没有增加延时'。但弱网时 TCP 发送阻塞 → 编码器被堵 → 编码线程卡住 → 上游丢帧 → 画面卡死。观众端表现是**画面冻结 5 秒不动**，体验比"延迟 3 秒流畅画面"差得多。

  对比：
  ```
  旧架构(无缓冲): 弱网 → 卡死 5 秒 → 跳帧恢复(可能花屏)
  新架构(3s缓冲): 弱网 → ABR 在 2 秒内降码率 → 延迟略升但画面连续 → 恢复后队列排空
  ```

  **第三层：ABR 的存在把'3 秒延时风险'大幅压缩了。**

  队列不是等到 90 帧才开始处理——高水位 60 帧时就触发 ABR 降码率。从网络变差到 ABR 生效的完整闭环：
  1. 队列从 0 涨到 60 帧 ≈ 2 秒
  2. ABR 检测触发（2 秒周期内）
  3. JNI 调 `setParameters` 改码率（毫秒级）
  4. 编码器产出低码率帧（下一个 IDR，最多 1 秒）
  5. 低码率数据进入队列，发送压力减小

  整个闭环约 3 秒，而队列容量正好是 3 秒——**高水位 60 到最大 90 之间那 30 帧就是 ABR 生效前的'刹车距离'**。正常情况队列不会满到 90。真正触发 Smart Drop GOP 是网络已经崩到最低码率都扛不住的极端情况。

  **总结**：异步队列确实在最坏情况下会增加最多 ~3 秒延迟。但这是主动选择——**用可控的 3 秒缓冲换取弱网下的流畅度和画面正确性**。而且 ABR + 高低水位提前降码率的设计，让这 3 秒在实际运行中极少发生。"

### 追问 3：ABR 从检测到高水位到编码器真正产出低码率数据，中间有多大的滞后？这个滞后期间队列会不会已经爆了？

- **考察点**：是否计算过 ABR 控制环路的端到端延迟（control loop latency）。
- **标准回答**：

  "我把 ABR 控制链路拆成四段，每段都有明确的时间估算：

  ```
  队列水位超过 60
      │
      ├──[1] 检测延迟: 最多 2 秒 (ABR 每 2 秒检查一次)
      │
      ├──[2] 下发延迟: < 1ms (JNI setParameters)
      │
      ├──[3] 编码器生效延迟: 0~1 秒 (必须等到下一个 IDR 才能真正切换码率;
      │         P/B 帧期间改码率只能在下个 IDR 刷新 SPS/PPS 时生效)
      │
      ├──[4] 管道排空延迟: 低码率帧产出时，队列里还堆着旧的高码率帧
      │         需要排队发完才能看到水位下降
      │
      ▼
  队列水位开始下降
  ```

  最坏情况：ABR 刚检查完（水位 59），下一秒水位飙到 70+ → 等 2 秒后下一次检查 → 发现超限 → 下发 → 等下一个 IDR(最多 1 秒) → 管道排空(~1 秒)。全程可能 4~5 秒才能看到水位真正降下来。

  **这就是 60 帧和 90 帧不是同一个数字的根本原因**——如果最大容量 = 高水位，就没有时间给 ABR 生效了：
  - 高水位 60（~2 秒）：**预警线**，触发 ABR 介入
  - 差距 30 帧（~1 秒）：**生效窗口**，留给 ABR 从检测到编码器真正产出低码率数据
  - 上限 90（~3 秒）：**兜底线**，ABR 没救回来才触发 Drop GOP

  这个三层水位设计不是拍脑袋，是拿控制环路的延迟反推出来的。

  面试时如果有人追问'那能不能检测更频繁，比如每 0.5 秒？'，我会说可以，但要权衡：太频繁会误判网络瞬抖，导致码率频繁横跳、画面忽糊忽清。2 秒 + 高低水位迟滞是经过测试的工程平衡点。"

### 追问 3.1：你刚才说编码器生效延迟"必须等到下一个 IDR"。为什么改个码率还要等 IDR？不能下一帧立刻生效吗？

- **考察点**：是否理解 H.264 码率参数的携带机制——SPS/PPS 只在 IDR 时刷新。
- **标准回答**：

  "不能。因为 H.264 的码率控制参数——`bit_rate`、`cpb_size`（`rc_buffer_size`）、`vbv_buffer_size` 等——是编码在 **SPS（序列参数集）** 里的。SPS 描述的是整个编码序列的属性，解码器只有在遇到 SPS 时才会重新初始化码率相关的 HRD（Hypothetical Reference Decoder）参数。

  P 帧和 B 帧的 slice header 里没有独立携带 `bit_rate` 的能力——它们的码控信息都是相对于 SPS 里声明的全局参数来计算的。所以你 `setParameters` 改了码率，编码器内部记住了新值，但不会在 P/B 帧的 slice header 里改任何东西。只有等到下一轮 IDR，编码器重新产一个含有新 `bit_rate` 的 SPS NALU，拉流端才能真正解析到码率变化。

  在 FFmpeg/x264 体系里也是同样的逻辑：你调 `x264_encoder_reconfig` 改 `rc.i_bitrate`，x264 内部会标记参数已变，但实际生效也是在下一个 IDR 帧编码时才把新 SPS 写进码流。

  **对 ABR 设计的影响**：如果你的 GOP 设得很大（比如 5 秒一个 I 帧），那 ABR 从下发到生效最长可能等 5 秒——这 5 秒里队列很可能已经爆了。所以做动态码率的场景有两个硬性要求：
  1. **GOP 要设短**（1~2 秒），缩短生效窗口。
  2. **极端拥塞时主动 force IDR**——`MediaCodec.setParameters(PARAMETER_KEY_REQUEST_SYNC_FRAME)` / `x264_encoder_intra_refresh`，不等自然 GOP 边界，立即插一个 IDR 让新码率立刻生效。"

### 追问 4：GPU Blit 那 1~2ms 的额外开销，在 4K 30fps 下会不会成为新瓶颈？和消除的 30ms CPU 回读相比真的划算吗？

- **考察点**：是否算过 GPU Blit 的实际时间占比，能否对比量化新旧方案的总耗时。
- **标准回答**：

  "不会。1~2ms 的 GPU Blit 和原来 20~30ms 的 CPU `glReadPixels` + `libyuv` 格式转换完全不在一个量级。

  而且这个 1~2ms 是**GPU 内部的高速拷贝**——走的是 GPU 显存带宽（几百 GB/s），做的是 GPU 最擅长的操作：把一个 buffer 绑成 OES 外部纹理，在 Input Surface 上全屏重绘一次。

  新旧方案单帧 CPU 侧耗时对比：

  | 阶段 | 旧方案 | 新方案 |
  |---|---|---|
  | GPU 渲染提交 | ~0.3ms | ~0.3ms |
  | 同步等待 GPU | glFinish ~10ms | glFlush <1ms |
  | 像素回读 + 格式转换 | glReadPixels + libyuv 20~30ms | **无** |
  | GPU Blit | **无** | **1~2ms** |
  | **CPU 线程总阻塞** | **~30~40ms** | **< 2ms** |

  GPU Blit 的 1~2ms 和消除的 30ms 比，是 20:1 以上的净收益。

  唯一要注意的是：如果同时在跑其他 GPU 重负载（比如 AI 推理也占 GPU 的 texture unit），1~2ms 的 Blit 可能被挤到 3~5ms。所以理想情况是 NPU 跑推理、GPU 做渲染+Blit、VPU 专门编码——这也是异构并行 Pipeline 的设计前提。"

### 追问 5：Smart Drop GOP 丢了一整个 GOP，观众端会看到什么？会不会比花屏更差？

- **考察点**：是否真正理解弱网下"丢 GOP"和"丢 P/B 帧"的端上表现差异，以及为什么 GOP 丢弃不会破坏后续解码。
- **标准回答**：

  "观众端看到的是**画面跳了一下（跳过 1~2 秒），但跳完之后是完整清晰的画面**。

  对比三种弱网丢帧策略的端上表现：

  | 策略 | 观众看到的现象 | 原因 | 体验评价 |
  |---|---|---|---|
  | 丢 P/B 帧（不按 GOP） | 画面撕裂、马赛克、大片绿块，持续到下一个 I 帧 | P/B 帧的参考帧丢了，解码端拿错误数据做运动补偿 | ★☆☆☆☆ 最差 |
  | 丢整 GOP | 画面跳 1~2 秒，跳完后瞬间恢复清晰 | I 帧独立解码，不需前面任何帧 | ★★★☆☆ 可接受 |
  | 不丢帧硬发 | 队列爆炸、延迟飙升、最终全链路卡死 | TCP 阻塞反压全链路 | ★☆☆☆☆ 不可用 |

  按 GOP 丢弃之所以安全，正是因为 GOP 以 I 帧开头、不依赖前一个 GOP 的任何帧。解码端拿到新 GOP 的第一个 I 帧就能独立解码，画面立即恢复——没有错误传播。

  **唯一副作用**：丢 GOP 在时间线上产生一个'洞'——如果恰好跳过了高光片段，那一段内容就永久丢失了。所以 Smart Drop GOP 是最后兜底，ABR 降码率应该在它之前就把问题解决掉。正常网络波动只在 ABR 层处理，Smart Drop GOP 是极端情况的'安全气囊'。"

### 追问 6：整个优化方案里，有没有哪个环节引入了单点故障风险？如果 Fence 永远不触发、或者异步队列线程崩了，会发生什么？

- **考察点**：是否考虑过异步系统的故障模式和降级策略。
- **标准回答**：

  "说实话，任何异步系统都比同步系统多了故障模式。但这不是异步的问题，而是复杂系统的常态——关键是能不能检测、能不能恢复。

  **1. Fence 不触发（GPU 渲染卡死 / 驱动 bug）**

  表现：VPU 编码侧一直拿不到 signal。编码器 `dequeueOutputBuffer(timeout)` 超时 → 连续 N 个周期没有输出 → 上层监控判断编码链路异常。

  应对：超时检测 + 重建推流。不是等着 Fence 自己恢复，而是把它当成'编码器挂掉'统一处理。这种情况极其罕见，Fence 是内核 sync_file 机制，不是用户态代码可以弄坏的。

  **2. 异步发送线程崩溃（crash / 死锁）**

  表现：队列持续堆积，ABR 检测到水位暴涨 → 先降到最低码率 → 队列到 90 → Smart Drop GOP 丢帧 → 但队列永远排不空，直播最终卡死。

  应对：
  - 发送线程用 `try-catch` 包住核心循环，异常时触发 RTMP 重连。
  - 长期水位不下降（比如 30 秒持续高位），判定发送链路异常，重建连接。
  - Muxer 重建时要处理好 `shared_ptr` 的生命周期（值捕获已经保证了这一点）。

  **3. ABR 降码率 JNI 调用失败**

  表现：`setParameters` 返回异常，码率没降下来。表现是 ABR 调了但水位继续涨。

  应对：`setParameters` 失败时重试一次 + 打日志。连续失败则回退到非 ABR 模式（固定码率 + Drop GOP 兜底）。

  **4. `shared_ptr` 引用计数堆积**

  异步 Lambda 值捕获 `shared_ptr` 保证了对象存活。队列积压 90 帧时，对应的 `AVPacket` 和引用的 Muxer/编码器上下文都保持存活。90 帧 × 单帧压缩数据（4K 码率 10Mbps → 单帧约 40KB）≈ 3.6MB，内存压力不大。

  **和旧架构的对比**：旧架构同步阻塞看起来故障模式少，但弱网时 TCP 阻塞本身就是故障——编码器卡死、CPU 满载、手机发烫降频——而且**不可观测、不可恢复**。新架构多了异步故障模式，但**可监控、可降级、可自愈**，工程成熟度反而更高。"

### 追问 7：如果让你给每项优化打一个"延时风险分"（1~10），你会怎么打？为什么？

- **考察点**：能否用量化思维总结各优化的 tradeoff，而不是笼统说"都有 tradeoff"。
- **标准回答**：

  | 优化项 | 延时风险 | 说明 |
  |---|---|---|
  | **零拷贝 (AHardwareBuffer + GPU Blit)** | **1** | 消除了 20~30ms CPU 回读，GPU Blit 1~2ms 且在 GPU 内部。端到端延时是**显著下降**的 |
  | **glFlush + Fence 异步** | **1** | 等待位置从 CPU 移到 VPU，GPU 工作时间不变，少了 CPU 回读。延时只降不增 |
  | **异步发送队列 (容量 90)** | **6** | ★ 唯一真正引入延时风险的项。最坏情况 +3 秒。但 ABR 把风险压缩了，且和"弱网卡死 5 秒"比是净收益 |
  | **ABR 动态降码率** | **2** | 降码率本身不加延时。控制环路有 2~5 秒滞后，但这是控制稳定性要求，不是延时引入 |
  | **Smart Drop GOP** | **0（时间线跳变）** | 不增加帧间延时，但产生节目时间跳跃（1~2 秒丢失）。属于正确性保障，不是延时问题 |
  | **缓冲队列扩到 3~4 帧** | **2** | 新增约 100ms 缓冲。对直播延迟几乎无感知，但有效吸收 VPU 编码抖动 |

  **总结一句话**：这个项目的优化方向整体是**降延时**的（消除 20~30ms CPU 回读、异步流水线提高吞吐），唯一的延时代价来自异步发送队列在最差网络条件下的 ~3 秒缓冲——而这 3 秒是用可控延迟换流畅度，属于有意识的 QoS 权衡，不是意外的副作用。
