# 已知不足与后续改进

> **所属项目**：Vertical Industry Camera SDK KMP 重构  
> **来源**：AI Code Review（白皮书 6.2 节）+ 工程复盘（预备稿第 6 节）  
> **定位**：主动暴露设计债务，说明问题成因、风险边界与下一版改造路径

---

## 1. 为什么单独写这篇

重构不是一锤子买卖。第一版的目标是**止血**——统一双端 API、拆掉巨型类、让 35+ 参数可演进。在交付压力下，有两处技术债被**有意识地延期**：

| 问题 | 严重程度 | 计划 |
|------|----------|------|
| `CameraParam<T>` 的 listeners 用 `LinkedHashSet` 裸用，没加锁 | Major | 纳入 `ListenerRegistry<T>` 统一改造 |
| `CameraSystem` 仍有 100+ 方法未归一 | Major | 下一版本按子域拆分或推广 `CameraParam<T>` |

这两项不是「漏做」，而是 AI Review 发现后**明确采纳、列入下一版本**的改进项。面试时主动讲清楚，比等面试官追问更能体现工程成熟度。

## 2. 不足一：CameraParam listener 未加锁

### 2.1 现状

`CameraCapture` 侧的 35+ 个 `CameraParam` 已通过 Template Method 统一了读写逻辑，但 **listener 管理仍是裸 `LinkedHashSet`**：

```kotlin
// CameraParamImpl.kt —— 当前实现（有问题）
abstract class CameraParamImpl<T>(...) : CameraParam<T> {

  private val listeners = LinkedHashSet<(T) -> Unit>()

  override fun addListener(listener: (T) -> Unit) {
    listeners.add(listener)           // ❌ 无锁
  }

  override fun removeListener(listener: (T) -> Unit) {
    listeners.remove(listener)        // ❌ 无锁
  }

  protected fun notifyListeners(value: T) {
    listeners.forEach { it(value) }   // ❌ 遍历时可能被并发修改
  }
}
```

### 2.2 对比：工程里已经做对的 listener

同一代码库里，`DisconnectListener` 已经用了 **Mutex + snapshot 派发** 的标准模式：

```kotlin
// CameraDeviceInternal.kt —— 已正确实现
private val disconnectListeners = mutableListOf<DisconnectListener>()
private val disconnectMutex = Mutex()

// 派发时
val snapshot = disconnectMutex.withLock { disconnectListeners.toList() }
snapshot.forEach { it.onDisconnect(event.throwable) }  // 锁外回调
```

`CameraCaptureService` 的 `CaptureStatusListener` 也有 `captureStatusMutex` 保护。唯独 `CameraParam` 在批量生成子类时，listener 部分沿用了最简实现，**没有复用同一套工具**。

### 2.3 风险场景

白皮书 7.3 节专门设计了应测但未完全覆盖的边界：

```
协程 A：param.addListener { ... }
协程 B：param.removeListener { ... }     ← 同时操作 LinkedHashSet
Native 回调线程：notifyListeners(value)  ← 同时遍历
```

可能后果：

| 场景 | 结果 |
|------|------|
| 遍历时 remove | `ConcurrentModificationException` |
| 回调里 unregister 自己 | 同上（经典 listener 坑） |
| 多线程 add 同一 listener | `LinkedHashSet` 本身线程不安全，内部状态可能损坏 |

当前线上**大概率未触发**，因为参数 listener 注册频率低、多在主线程。但这是**概率性风险**，不是逻辑上安全。

### 2.4 改造方案：ListenerRegistry\<T\>

把 listener 管理抽到 `support` 层，全工程复用，避免 35 个 `CameraParam` 各自实现一遍：

```kotlin
// support/ListenerRegistry.kt —— 目标实现
class ListenerRegistry<T> {
  private val listeners = LinkedHashSet<(T) -> Unit>()
  private val mutex = Mutex()

  suspend fun add(listener: (T) -> Unit) {
    mutex.withLock { listeners.add(listener) }
  }

  suspend fun remove(listener: (T) -> Unit) {
    mutex.withLock { listeners.remove(listener) }
  }

  suspend fun snapshot(): List<(T) -> Unit> {
    return mutex.withLock { listeners.toList() }
  }

  suspend fun dispatch(value: T) {
    val copy = snapshot()
    copy.forEach { listener ->
      try {
        listener(value)
      } catch (e: Exception) {
        // 单个 listener 异常不影响其余派发
      }
    }
  }
}
```

`CameraParamImpl` 改造后：

```kotlin
abstract class CameraParamImpl<T>(...) : CameraParam<T> {

  private val listenerRegistry = ListenerRegistry<T>()

  override fun addListener(listener: (T) -> Unit) {
    scope.launch { listenerRegistry.add(listener) }
  }

  override fun removeListener(listener: (T) -> Unit) {
    scope.launch { listenerRegistry.remove(listener) }
  }

  protected fun notifyListeners(value: T) {
    scope.launch { listenerRegistry.dispatch(value) }
  }
}
```

### 2.5 设计要点

| 要点 | 说明 |
|------|------|
| Snapshot 派发 | 锁内 `toList()`，锁外 `forEach`，回调里可安全 register/unregister |
| 注册异步串行 | 与 `DisconnectListener` 一致，`add/remove` 丢进 scope，避免调用方持锁 |
| 单 listener 隔离 | `dispatch` 内 try-catch，一个客户回调抛异常不拖垮其余 listener |
| 全工程复用 | `CameraSystem` 的 battery/storage listener 也可迁入同一工具类 |

### 2.6 迁移步骤

1. 实现 `ListenerRegistry<T>` + 单元测试（并发 add/remove/dispatch）
2. 改造 `CameraParamImpl`，35 个子类**零改动**
3. 逐步把 `DisconnectListener`、`CaptureStatusListener` 的 Mutex 逻辑迁入（可选，减少重复）
4. 补充白皮书 7.3 节的并发 register/unregister 测试用例

### 2.7 为什么第一版没做

- AI 批量生成 `CameraParam` 子类时，listener 部分用了最简模板
- 交付优先级在「API 形状统一」和「双端打通」，并发边界用人工 Review 标记延期
- 已有 `DisconnectListener` 的正确范式，改造成本低，适合第二版集中还债

## 3. 不足二：CameraSystem 接口超过 100 个方法

### 3.1 现状

聚合根 `CameraDevice` 已按职责域拆成 5 个子接口，但 **`CameraSystem` 仍是「小巨型类」**：

```kotlin
interface CameraDevice {
    val system: CameraSystem      // ← 这里塞了 100+ 方法
    val capture: CameraCapture    // ← 已用 CameraParam 归一，~35 参数
    val preview: CameraPreview
    val file: CameraFile
    val firmware: CameraFirmware
}
```

`CameraCapture` 通过 `CameraParam<T>` 把 35+ 参数收敛成统一形状；`CameraSystem` 却仍是旧 SDK 的「方法堆」：

```kotlin
// CameraSystem —— 简化示意，实际 100+ 方法
interface CameraSystem {
    // 电池
    fun getBatteryLevel(): Result<Int>
    fun registerBatteryListener(listener: BatteryListener)
    fun unregisterBatteryListener(listener: BatteryListener)

    // 存储
    fun getStorageInfo(): Result<StorageInfo>
    fun formatStorage(): Result<Unit>

    // WiFi
    fun getWifiData(): Result<WiFiData>
    fun setWifiMode(mode: WifiMode): Result<Unit>

    // 激活
    fun getActivationState(): Result<ActivationState>
    fun activate(serial: String): Result<Unit>

    // 时间
    fun getDeviceTime(): Result<Long>
    fun setDeviceTime(timestamp: Long): Result<Unit>

    // 语言
    fun getLanguage(): Result<String>
    fun setLanguage(lang: String): Result<Unit>

    // ... 还有几十个 get/set/register/unregister
}
```

### 3.2 违反了什么

**接口隔离原则（ISP）**：客户端如果只关心电池，却被迫依赖整个 `CameraSystem` 的 100+ 方法签名。对 SDK 而言，具体影响是：

| 影响 | 说明 |
|------|------|
| ABI 膨胀 | iOS Framework 导出 100+ 符号，编译体积和链接时间增加 |
| 可发现性差 | IDE 补全 `device.system.` 后弹出超长列表，找不到想要的 |
| 演进困难 | 新增一个 system 能力要改同一个巨型接口，Review 范围大 |
| 测试粒度粗 | 无法只 mock「电池子域」，必须面对整个 System |

迁移时 AI 自动分组生成了 `CameraSystem` 草案，人工审查后合并了过度拆分，**当时约定「每个子接口不超过 30 个方法」——`CameraSystem` 最终未达标**，标记为已知待改进。

### 3.3 改造方向 A：按子域拆 6 个子接口

预备稿建议按职责再拆一层：

```kotlin
interface CameraDevice {
    val system: CameraSystem   // 变成门面，不再直接堆方法
    // ...
}

// 门面只聚合，不膨胀
interface CameraSystem {
    val battery: CameraBattery
    val storage: CameraStorage
    val wifi: CameraWifi
    val activation: CameraActivation
    val time: CameraDeviceTime
    val language: CameraLanguage
}

interface CameraBattery {
    suspend fun getLevel(): Result<Int>
    fun getLevel(callback: Callback<Int>)
    fun registerListener(listener: BatteryListener)
    fun unregisterListener(listener: BatteryListener)
}

interface CameraStorage { /* getInfo / format / ... */ }
interface CameraWifi { /* getData / setMode / ... */ }
// ...
```

调用侧变化：

```kotlin
// 改造前
device.system.getBatteryLevel()
device.system.registerBatteryListener(listener)

// 改造后
device.system.battery.getLevel()
device.system.battery.registerListener(listener)
```

**优点**：职责清晰，每个子接口 < 20 方法，符合 ISP。  
**缺点**：对外 API 路径变长；需要 `@Deprecated` 兼容层过渡。

### 3.4 改造方向 B：推广 CameraParam\<T\>

部分 system 能力本质是「可读可写可订阅的参数」，与 `CameraCapture` 的参数同构：

```kotlin
interface CameraSystem {
    val batteryLevel: CameraParam<Int>       // 只读参数
    val deviceTime: CameraParam<Long>
    val language: CameraParam<String>
    val wifiMode: CameraParam<WifiMode>

    // 非参数类能力仍保留显式方法
    fun formatStorage(): Result<Unit>
    fun activate(serial: String): Result<Unit>
}
```

**优点**：与 `CameraCapture` 形状统一，新增参数零接口变更；`CameraParamImpl` 直接复用。  
**缺点**：并非所有 system 能力都适合参数模型（如 `formatStorage` 是一次性动作，不是 Param）。

### 3.5 推荐：A + B 混合

```
CameraSystem（门面）
  ├── battery: CameraBattery          ← 方向 A：有 listener 的子域用独立接口
  ├── storage: CameraStorage
  ├── wifi: CameraWifi
  ├── activation: CameraActivation
  ├── time: CameraDeviceTime        ← 方向 B：纯 get/set 的用 CameraParam<T>
  │     └── deviceTime: CameraParam<Long>
  └── language: CameraLanguage
        └── current: CameraParam<String>
```

决策规则：

| 能力特征 | 用哪种 |
|----------|--------|
| get / set / getSupported / listener 四件套 | `CameraParam<T>` |
| 有独立生命周期回调（如 battery 电量推送） | 子接口 + Listener |
| 一次性动作（format / activate / reboot） | 子接口上的 `suspend fun` |

### 3.6 ABI 兼容策略

SDK 面向第三方，不能直接删方法：

```kotlin
interface CameraSystem {
    val battery: CameraBattery

  @Deprecated("Use system.battery.getLevel()", ReplaceWith("battery.getLevel()"))
  fun getBatteryLevel(): Result<Int> = battery.getLevel()
}
```

- 旧方法标 `@Deprecated` + `ReplaceWith`
- 至少保留一个大版本周期
- Migration Guide 自动生成对照表（白皮书 8.1 节文档体系）

### 3.7 为什么第一版没做

| 原因 | 说明 |
|------|------|
| 迁移范围 | `CameraSystem` 从旧 SDK 直接映射，方法数多、业务耦合深 |
| 优先级 | `CameraCapture` 的 35 参数是高频路径，先归一；System 能力调用频率低 |
| 风险控制 | 拆接口是 breaking change 风险最高的操作，需要完整兼容层 + 文档 |
| 交付节点 | 第一版目标是「双端统一 + 一周接入」，System 拆分可延后 |

## 4. 两项不足的关系

```
                    第一版重构
                         │
         ┌───────────────┼───────────────┐
         ▼               ▼               ▼
   CameraCapture    CameraSystem    DisconnectListener
   ✅ CameraParam   ❌ 100+ 方法    ✅ Mutex + snapshot
   ❌ listener 无锁
         │               │               │
         └───────┬───────┘               │
                 ▼                       │
         ListenerRegistry<T>  ←──────────┘  复用同一套模式
                 │
                 ▼
         第二版：线程安全 + 接口归一
```

- **Capture 侧**：API 形状做对了（Template Method），线程安全没跟上
- **System 侧**：API 形状没做完（仍是方法堆），但 listener 部分反而有 Mutex
- **第二版目标**：用 `ListenerRegistry` 统一 listener；用子域拆分 + `CameraParam` 统一 System 形状

## 5. 测试补齐清单

改造完成后需覆盖的测试（白皮书 7.3 节 + 本文补充）：

```kotlin
// ListenerRegistry 并发测试
@Test
fun `concurrent add remove and dispatch`() = runTest {
    val registry = ListenerRegistry<Int>()
    val jobs = List(100) {
        launch {
            val listener: (Int) -> Unit = { }
            registry.add(listener)
            registry.dispatch(42)
            registry.remove(listener)
        }
    }
    jobs.joinAll()  // 不应抛 ConcurrentModificationException
}

@Test
fun `dispatch allows unregister inside callback`() = runTest {
    val registry = ListenerRegistry<Int>()
    lateinit var self: (Int) -> Unit
    self = {
        runBlocking { registry.remove(self) }  // 回调里 unregister 自己
    }
    registry.add(self)
    registry.dispatch(1)  // 不应崩溃
}

// CameraSystem 拆分后的契约测试
@Test
fun `deprecated getBatteryLevel delegates to battery subdomain`() {
    val system = FakeCameraSystem(batteryLevel = 80)
    assertEquals(80, system.getBatteryLevel().getOrThrow())      // 旧 API
    assertEquals(80, system.battery.getLevel().getOrThrow())     // 新 API
}
```

## 6. 面试怎么讲

### 30 秒版（主动暴露不足）

> 第一版重构优先解决了双端 API 统一和 CameraCapture 的 35 参数归一。AI Review 发现两个 Major 问题我都采纳了：一是 CameraParam 的 listener 没加锁，计划抽成 ListenerRegistry 全工程复用，模式和 DisconnectListener 的 Mutex + snapshot 一致；二是 CameraSystem 还有 100 多个方法违反 ISP，下一版按 battery/storage/wifi 等子域拆分，能参数化的推广 CameraParam。这两项是有意识延期的技术债，不是设计盲区。

### 追问：「为什么第一版不一起做？」

> SDK 重构的真实瓶颈是理解历史代码和控制迁移风险，不是写代码。第一版交付约束是「双端统一 + 第三方一周接入」。Capture 参数是高频路径，先归一；System 调用频率低、拆接口 ABI 风险高，用 @Deprecated 兼容层过渡更合适。listener 无锁是批量生成时的遗漏，但工程里 DisconnectListener 已有正确范式，改造成本低，适合第二版集中还。

### 追问：「你怎么判断 AI Review 的建议要不要采纳？」

> 白皮书 6.2 节有完整决策表。比如 AI 建议用 StateFlow 替代 SharedFlow 做事件总线，我拒绝了，因为 replay=1 会让新订阅者收到旧事件。listener 无锁和 CameraSystem 过大这两条，结合并发理论和 ISP 原则，采纳并列入下一版本。关键是每条建议都要有采纳/拒绝/延期的明确理由，不能 AI 说什么就改什么。
