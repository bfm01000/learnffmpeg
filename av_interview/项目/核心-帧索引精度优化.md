# 面试实战：抽帧 Seek 精度与帧索引系统重构

## 🌟 面试速记 (1-2分钟电梯演讲)

**【背景与痛点】**

自动剪辑 2.0 的流程是两轮抽帧：第一轮每 600ms 抽两帧，把帧和帧 ID 送给算法；算法分析后返回一组帧 ID（int），我们再根据帧 ID 去抽第二轮帧。

问题出在：抽帧器只支持按 `double` 时间戳 Seek。于是全链路变成了 **int 帧 ID → float 秒 → int 帧 ID** 的双向转换。由于 IEEE 754 浮点精度有限，`1000ms` 转一圈回来可能是 `999.999ms` 或 `1000.00001ms`。而抽帧器底层是逐帧比较、当 PTS ≥ 目标时间才返回帧——999.999ms 退回上一帧，1000.00001ms 跳到下一帧，**帧号差 1，底层结果报错**。因为是浮点舍入方向决定的，偶发但根因是必然的。

我刚进去时做了临时止血：首轮抽帧时建一个 `unordered_map<int, int>`（帧 ID → PTS），第二轮直接从 map 里查，绕过了反向转换。**这能跑，但治标不治本。**

接入自动剪辑 3.0 时，算法抽帧频率从 600ms 提到 200ms，偏帧 Bug 被同比例放大，从"偶发"变成"几乎每段素材都遇到"。我决定彻底解决，查了业界做法发现：**主流方案根本不用 float 做 Seek，而是在初始化时建一个 frameId → PTS 的精确映射表**——frameId 是扫描计数器的值，不是公式推导出来的，全程 int64，零浮点参与。


我们自动剪辑2,0的流程是这样的，有两轮抽帧，第一轮抽帧每600ms抽两帧，然后把帧和帧ID送给算法。送完之后，算法再返回一组帧ID，我们再去根据这个帧ID去抽一轮帧。但是我们的抽帧器当时只支持根据double时间戳去抽帧，也就是说第一轮抽帧是从float转成int送给算法，然后算法又会返回一组int的帧ID给我们，然后我们就去抽帧，有时候就会出现float转成Int，Int转回float的时间差了一点，比如1000ms，可能是999.999也可能是1000.00001，我们抽帧器的底层是会去逐帧比较，当时间大于目标时间的时候，才会返回帧，也就是说第一次可能送的是1000ms，但是第二次有可能送的帧是1033ms的帧。这个时候再把帧时间转成帧ID的时候就会出问题。帧号就会差1，我们底层的结果就会报错。而且是偶现的问题。
* 那个时候我刚进去，因此只做了临时修复就是用浮点和int做了一个map，每次去map里面找。先暂时解决了这个问题。
* 在接入自动剪辑3.0的时候，我决定彻底解决这个问题，然后也差了一些资料，发现主流做法基本都不会用到float去seek或者抽帧，基本都是在初始化抽帧器的时候简历一个framIndex到PTS的映射表。当需要找某一帧的时候可以精确的拿到这个帧的pts，然后再去seek。就是准确的。
* 因为我优化了我们的抽帧器，在初始化的时候可以传进来一个是否需要建立索引的参数，这个参数如果传了，就会在初始化的时候去跑一遍解封装，把每一个视频帧的frameID和pts简历一个双向映射表。并且标准出帧的类型。然后新增了一个支持seek到frameID的seek方法，只有设置建立索引的标志位才能使用这个seek方法。否则会返回错误。



**【排查与根因定位】**
我没有急着改代码，而是先还原了一个最小复现 case：29.97fps 视频，目标第 1000 帧。

```
小厂路径: frameId=1000, fps=29.97
  → targetSec = 1000 / 29.97 = 33.366700033...
  → float 存入: 33.36669921875 (IEEE 754 精度损失)
  → × time_base(90000) = 3003002
  → 但第 1000 帧的真实 PTS = 3003003 ← 差 1 tick!
  → av_seek_frame(3003002) 落到相邻帧
```

顺藤摸瓜发现两个根因。第一，`AVStream->index_entries` 来自 MP4 的 stss box（Sync Sample Table），**只存关键帧**。一个 90 帧的 GOP=30 视频，nb_index_entries 只有 3 条。查非关键帧 → 返回 -1 → fallback 回 float 公式 → 又撞上精度问题。第二，VFR 场景下 `frameId = pts / frame_dur` 这个 CFR 公式直接崩——帧间隔从 33ms 变 66ms 时，算出来的 frameId 跟真实值差几十帧。

核心结论：看起来是「偶发抽偏」，根因是两个底层契约没设计对——**用连续量(float)去索引离散量(帧)、把关键帧索引当全帧索引用**。

**【解决方案：三条腿的索引重构】**

**第一条腿：int64 pts 整数链路 + frameId→PTS 查表。** 打开文件时 `av_read_frame()` 全量 demux 扫一遍——注意是 demux 不是 decode，只读 packet 头不调解码器，10 分钟 4K 素材约 150ms。把每个 frame 的 PTS 按扫描序号 push 进 `vector<pts>`，下标即 frameId。全程 int64，零浮点参与。VFR 天然安全，因为 frameId 是计数器的值不是公式推导。

**第二条腿：Smart Seek。** 关键帧的 frameId 单独存一个升序列表。Seek 时二分查找最近关键帧，判断目标帧是否在「当前解码位置之后且同 GOP」——如果是，直接顺解丢帧，不调 `av_seek_frame` + `avcodec_flush_buffers`，省掉 flush→重新找关键帧→重新初始化解码器的开销。如果不是，回退到标准 Seek。

**第三条腿：flag 控制 + 向后兼容。** 全部新逻辑用 `use_frame_index` 一个 bool 控制，默认 false 走旧 float 路径。老业务零侵入。

**【最终结果】**
帧级 Seek 从「偶发偏一帧」变成「零误差」；Smart Seek 在同一 GOP 内消灭重复解码；VFR 兼容性从公式不可用到天然安全。索引方案跟 ExoPlayer 的 Mp4Extractor、剪映素材导入分析是一类思路。

==============================================================

## 一、 背景与挑战 (Situation)

自动剪辑是 Insta360 App 的核心功能：用户选择一个或多个视频 → SDK 按一定间隔抽帧 → 送算法识别高光片段 → 上层拼接片段 + 转场 + 滤镜 + BGM → 输出成片。

### 1.1 2.0 的「玄学 Bug」

2.0 时代，算法通过 frameId 指定目标帧，SDK 层用 float 公式 `(frameId / fps) × time_base.den` 算出 Seek 目标时间戳。偶尔会出现「算法要第 N 帧，实际抽到第 N±1 帧」的问题。因为偶发且影响面不大，当时的处理方式是在算法侧做冗余：多抽几帧让算法自行纠正。

### 1.2 3.0 后 Bug 被放大

3.0 算法做了重大升级，送帧频率从 2.0 的 **600ms/帧** 提升到 **200ms/帧**——同样一段素材，抽帧量变成 3 倍。偏帧 Bug 的触发概率被同比例放大，从「偶发」变成「几乎每段素材都会遇到」。产品要求彻底解决。

### 1.3 更深层的问题

回头看，2.0 的 Bug 不只是 float 精度问题，还有两个当时没意识到的隐患：

1. **`index_entries` 只有关键帧**：FFmpeg 的 `avformat_find_stream_info()` 会自动从容器（MP4 stss box）解析关键帧列表存入 `AVStream->index_entries`。但非关键帧不在里面。用这个建索引 → 查非关键帧返回 -1 → fallback float 公式 → 精度问题又回来了。

2. **VFR（可变帧率）不兼容**：iPhone 省电模式、Android 屏幕录制等场景下，帧间隔可能从 33ms 跳到 66ms。`frameId = pts / frame_dur` 这个公式在 VFR 下算出来的 frameId 跟真实序号偏差可达几十帧。

---

## 二、 目标 (Task)

1. **帧级 Seek 零误差**：无论 CFR 还是 VFR，算法指定 frameId=N，SDK 必须精确拿到第 N 帧
2. **消除重复解码**：同 GOP 内的连续 Seek 不复解码，减少无谓开销
3. **VFR 兼容**：索引方案在可变帧率下不会退化
4. **向后兼容**：新方案通过 flag 控制，不影响存量业务

## 三、 行动与技术落地 (Action)

### 1. 最小复现：还原 float 精度损失的精确路径

为了确认这不是「偶发」而是「必然」，我用一个精确可复现的 case 走了一遍：

```
视频: 29.97fps CFR
time_base: 1/90000
目标: 算法说「取第 1000 帧」

第 1000 帧的真实 PTS:
  frame_dur_ticks = 90000 / 29.97 ≈ 3003.003...
  第 1000 帧 PTS = 1000 × 3003.003 ≈ 3003003

float 路径:
  step 1: 1000 / 29.97 = 33.3667000333667...
  step 2: float 存入 → 33.36669921875 (IEEE 754 binary32 精度极限 ≈ 7 位十进制)
  step 3: 33.36669921875 × 90000 = 3003002.9... → int64_t 截断 = 3003002

差值: 3003003 - 3003002 = 1 tick

av_seek_frame(3003002, AVSEEK_FLAG_BACKWARD)
  → FFmpeg 找 ≤ 3003002 的最近关键帧
  → GOP=30, 上一关键帧在 frameId≈990
  → 从 990 顺解到 3003002
  → 输出帧 PTS=3003002 ← 这是第 999 帧还是第 1000 帧? 不确定!
```

**关键发现**：float 的误差不是 0.8ms 的问题——它是「帧边界的 0 或 1」问题。精度损失在离散边界处被放大成一个完整帧的错位。

### 2. 根因深挖：index_entries 只存关键帧

上面的分析只解释了「为什么 float Seek 会偏」。但还有一个前置问题：「为什么查不到目标的 PTS，要用 float 算？」

答案在 `AVStream->index_entries`：

```
一个 90 帧的 MP4 文件, GOP=30:

全部帧 (av_read_frame 逐帧读):
  I₀ P₁ P₂ ... P₂₉  I₃₀ P₃₁ ... P₅₉  I₆₀ P₆₁ ... P₈₉
  ↑                 ↑                 ↑
  frameId=0         frameId=30        frameId=60

index_entries (来自 MP4 stss box):
  [0] { pos: 0x100,   timestamp: 0       }
  [1] { pos: 0x8A00,  timestamp: 900900  }
  [2] { pos: 0x12000, timestamp: 1801800 }
  nb_index_entries = 3  ← 90 帧里只索引了 3 个关键帧!

用 index_entries 建的 map<frameId, pts>:
  frame_to_pts_[0]  = 0        ← 只有 3 条
  frame_to_pts_[30] = 900900
  frame_to_pts_[60] = 1801800

查询 frameId=50:
  frame_to_pts_.find(50) → NOT FOUND → 返回 -1
  → seek_to_frame 的 fallback: calc_pts_float(50) 
  → 又回到了 float 精度问题!
```

**stss box 的设计目的**是告诉解码器「可以从哪里开始解码」，不是给你建全帧索引的。非关键帧根本不在里面。

### 3. 解决方案一：int64 pts 整数链路 + 全量 Demux 扫描

核心思路：**frameId 不推导，而是计数**。

```cpp
// 旧方案 (CFR 假设, 关键帧稀疏):
int frame_id = (int)(pts / frame_dur_tb);  // ❌ 浮点参与, 关键帧才存

// 新方案 (VFR 安全, 全帧):
frame_to_pts_.push_back(pts);  // ✅ 下标即 frameId, 零推导
```

具体实现（FFmpeg C API）：

```cpp
struct FrameIndex {
    std::vector<int64_t> frame_to_pts_;   // [frameId] = PTS
    std::vector<int>     keyframe_ids_;   // 所有关键帧的 frameId

    int build(AVFormatContext *fmt_ctx, int vidx) {
        AVPacket *pkt = av_packet_alloc();
        int frame_id = 0;

        av_seek_frame(fmt_ctx, vidx, 0, AVSEEK_FLAG_BYTE);

        while (av_read_frame(fmt_ctx, pkt) >= 0) {   // ← demux, 不解码!
            if (pkt->stream_index != vidx) {
                av_packet_unref(pkt);
                continue;
            }

            frame_to_pts_.push_back(pkt->pts);        // 下标即 frameId

            if (pkt->flags & AV_PKT_FLAG_KEY) {
                keyframe_ids_.push_back(frame_id);
            }

            frame_id++;
            av_packet_unref(pkt);
        }

        av_packet_free(&pkt);
        return frame_id;  // 总帧数
    }

    int64_t seek_to_frame(int target_frame,
                          AVFormatContext *fmt_ctx, int vidx) {
        if (target_frame < 0 || target_frame >= (int)frame_to_pts_.size())
            return -1;

        int64_t target_pts = frame_to_pts_[target_frame];

        // 二分查找最近关键帧
        int kf_id = find_nearest_keyframe(target_frame);
        if (kf_id < 0)
            return av_seek_frame(fmt_ctx, vidx, 0, AVSEEK_FLAG_BYTE);

        int64_t kf_pts = frame_to_pts_[kf_id];
        return av_seek_frame(fmt_ctx, vidx, kf_pts, AVSEEK_FLAG_BACKWARD);
    }

    int find_nearest_keyframe(int target_frame) const {
        auto it = std::upper_bound(
            keyframe_ids_.begin(), keyframe_ids_.end(), target_frame);
        if (it == keyframe_ids_.begin()) return -1;
        return *(--it);
    }
};
```

**关键澄清**：全量 demux 扫描 **不是全量解码**。`av_read_frame()` 只读容器层 packet 头，拿到 pts/dts/flags/pos，不触发 `avcodec_send_packet` / `avcodec_receive_frame`。耗时实测：

```
格式    分辨率    时长     总帧数    全量 demux 耗时    等效吞吐
MP4     1080p30   10 min   18,000    80~150 ms         120,000+ 帧/秒
MP4     4K30      10 min   18,000    120~250 ms        72,000+ 帧/秒
MP4     4K60      30 min   108,000   500~1200 ms       90,000+ 帧/秒
```

10 分钟 4K 素材 ≈ 150ms，一次性的开销，换每次 Seek 的 O(1) 查表。

### 4. 解决方案二：Smart Seek

有了全帧索引 + 关键帧位图后，Smart Seek 的实现非常简洁：

```cpp
bool should_smart_seek(int target_frame,
                       int current_decoded_frame,
                       const FrameIndex &index) {
    // 目标帧在当前解码位置之后
    if (target_frame <= current_decoded_frame)
        return false;

    // 目标帧和当前位置在同一个 GOP 内
    int cur_kf  = index.find_nearest_keyframe(current_decoded_frame);
    int tgt_kf  = index.find_nearest_keyframe(target_frame);
    return (cur_kf == tgt_kf);  // 同一个关键帧 → 同 GOP
}
```

同 GOP 时：不解码器 flush，顺序解码，丢弃中间不要的帧，直到拿到目标帧。
跨 GOP 时：回退到标准 `av_seek_frame` + `avcodec_flush_buffers`。

### 5. VFR 兼容性

因为 `frame_to_pts_` 是按扫描序号 push 的，frameId 就是 0, 1, 2, 3... 的递增计数器，跟帧间隔完全无关：

```
CFR: frameToPts[0]=0, [1]=3003, [2]=6006, [3]=9009  ← 间隔固定
VFR: frameToPts[0]=0, [1]=3003, [2]=6006, [3]=12012 ← 间隔不固定

查 frameId=3 → frameToPts[3] → 永远是 12012，不会算错
```

CFR 和 VFR 对索引层完全透明。这与 ExoPlayer 的 MediaSource 索引、剪映素材导入时的 demux 扫描是一类思路。

### 6. 向后兼容设计

所有新逻辑用 `SeekCfg.use_frame_index` 一个 bool 控制：

```cpp
struct SeekCfg {
    bool use_frame_index = false;  // 默认 false, 旧路径不变
};

int seek_to_frame(int frame_id, const SeekCfg &cfg) {
    if (cfg.use_frame_index) {
        return index_.seek_to_frame(frame_id, fmt_ctx_, vidx_);  // 大厂
    } else {
        return calc_pts_float_and_seek(frame_id);                 // 小厂 (兜底)
    }
}
```

默认 false，旧业务零侵入。新业务 opt-in 开启。

## 四、 成果与业务价值 (Result)

1. **帧级 Seek 零误差**：从「偶发偏一帧」变成「零误差」。29.97fps / VFR / 非固定 GOP 全部覆盖。
2. **Smart Seek 消灭重复解码**：同 GOP 内连续 Seek 复用解码器状态，不 flush 不重建。目标帧密度越高收益越大——自动剪辑 3.0 的 200ms/帧 送帧频率正是 Smart Seek 的最大受益场景。
3. **VFR 兼容**：从「CFR 公式不可用」变成「天然安全」。iPhone 省电模式、Android 屏幕录制等 VFR 素材不再有索引问题。
4. **索引结构可复用**：全量 frameId→PTS 映射 + 关键帧位图沉淀为基础组件，后续全景剪辑 1.0、其他需要 Seek 的算法接入直接复用，不需要重复造轮子。
5. **业界对齐**：方案与 ExoPlayer Mp4Extractor、剪映素材导入分析、ijkplayer 的 stream index 策略一致——面试时可以自信地说「这不是我的发明，是行业的共识方案」。
