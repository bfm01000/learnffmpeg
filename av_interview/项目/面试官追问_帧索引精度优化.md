## 模块一：float 精度与时间模型 `Q1 Q2 Q3`

### Q1：你说 float 算 Seek 会偏一帧。float 的误差只有 0.8ms，为什么能偏一整帧？

**面试官**：你一开头说了 float 精度损失大概 0.8ms。29.97fps 下一帧有 33ms，0.8ms 远小于 33ms，按理说不会跨到另一帧才对。为什么你说会偏一帧？

**标准回答**：
「0.8ms 是 float 自己的精度损失量级，但问题不在这里。真正让 Seek 偏一帧的是 **int64_t 截断** 这个步骤。

流程是这样的：
1. `frameId / fps` → float 存储 → 损失约 0.8ms（对帧边界来说不算大）
2. `float_sec × time_base.den` → 这是一个浮点乘法，结果可能是 3003002.93
3. `(int64_t)3003002.93` → int64_t 截断 → 变成 3003002

真实 PTS 是 3003003。差了 1 tick。而这个 1 tick 恰好跨过了帧边界——FFmpeg 用 AVSEEK_FLAG_BACKWARD 时会回退到 ≤3003002 的最近帧，可能落到相邻帧。

所以不是 float 的 0.8ms 直接导致偏一帧，而是 float→int64 的截断方向在帧边界处恰好偏了 1 tick。这个 1 tick 放大成帧边界问题。」

---

### Q2：换成 double 不就行了吗？为什么一定要 int64？

**面试官**：float 只有 ~7 位有效数字。但 double 有 ~15 位，算 `1000/29.97 × 90000` 应该完全够用。为什么还要搞 int64 + 查表？

**标准回答**：
「double 确实可以把精度损失降到几乎不可感知。但有两层更深的问题，double 解决不了。

第一，VFR 下 `frameId/fps` 这个公式本身是错的——跟用什么精度算没关系。帧间隔不固定时，PTS 和 frameId 之间没有线性关系。

第二，这是模型层面的选择——**用一个连续量去索引一个离散量，边界处的歧义是本质性的，跟精度无关**。就像你问『0.999... 和 1.0 是同一个数吗？』——在实数域它们是，但在帧域（每 33ms 一个间隔）它们可能落到不同帧。

int64 方案不是『精度更高的 float』，是换了一个模型：frameId 不是算出来的，是编号出来的。离散量索引用离散量表达——底层的表达和上层的语义一致，边界歧义就消失了。」

---

### Q3：你说的 time_base 是什么？为什么选 1/90000？

**面试官**：你反复提到 time_base。解释一下它在整个时间模型里扮演什么角色。

**标准回答**：
「time_base 是 FFmpeg 里所有时间戳的『度量单位』。一个 PTS 值本身没有绝对含义，必须结合 time_base：

```
实际时间(秒) = pts × time_base.num / time_base.den
```

比如 pts=3003003, time_base={1,90000} → 3003003/90000 = 33.3667 秒。

1/90000 是 MPEG-TS 标准里的『公共时间基』——90000 是 24/25/30/60 fps 的公倍数，能精确表达所有这些帧率的单帧时长而不产生分数。比如 29.97fps 一帧 = 90000/29.97 ≈ 3003.003 ticks——不是整数，但在 int64 表示下足够精确。

这也是为什么大厂用 int64 pts 而不是毫秒：1/90000 的粒度是 0.011ms，远细于任何帧间隔。截断误差被推到远小于一帧的量级，不会影响帧级决策。」

## 模块二：index_entries 与全量 Demux `Q4 Q5 Q6`

### Q4：index_entries 到底是怎么来的？每个容器都一样吗？

**面试官**：你说 index_entries 来自 MP4 的 stss box。那其他容器呢？FLV、TS、MKV 也是用同样的机制吗？

**标准回答**：
「不同容器生成 index_entries 的方式不一样：

- **MP4/MOV**：`avformat_find_stream_info()` 解析 moov box 里的 stss（Sync Sample Table）。stss 本身就是关键帧索引，直接映射到 index_entries。
- **FLV**：FLV 没有独立的关键帧索引表，但每个 tag header 里有 frame type 字段（1=keyframe, 2=inter frame）。解析时逐 tag 扫描，遇到 keyframe 就加一条。
- **TS（MPEG-TS）**：没有全局索引。每个 PES 包的 adaptation field 里有 random_access_indicator 标记关键帧。FFmpeg 会解析 PCR 和 PTS 来定位关键帧位置。
- **MKV/WebM**：有 Cues 元素相当于关键帧索引，类似 MP4 的 stss。

但共同点是：**index_entries 里只存关键帧**。它的设计目的是 seek point 索引，不是全帧索引。用 index_entries 做帧级映射，非关键帧一定是黑洞。」

---

### Q5：全量 demux 扫描开销到底多大？会不会成为新的瓶颈？

**面试官**：你说 10 分钟视频只要 150ms。但如果素材是 2 小时的 4K 长视频呢？或者是从网络流 demux 呢？

**标准回答**：
「这个方案是为**离线素材**设计的——用户从相册选择视频导入编辑。对于这种场景：

- 2 小时 4K30 素材 ≈ 216,000 帧 → demux 扫描约 1.5~3 秒
- 这个耗时发生在用户选择素材后、看到编辑界面前
- 跟解码抽缩略图（几十秒级）相比，demux 扫描完全不是瓶颈

对于**网络流**场景（如直播、在线播放），不是全量扫描，而是动态建索引——每收到一个 packet 就 append 到 frame_to_pts_。因为流是线性的，不需要『扫一遍再播』。

剪映的做法更极致：首次 demux 后把索引序列化到磁盘（如 `video.mp4.idx`），下次打开直接 mmap，< 5ms 完成。」

---

### Q6：demux 扫描和 decode 扫描怎么区分？你代码里怎么保证不触发解码？

**面试官**：你说 av_read_frame 是 demux 不是 decode。但 FFmpeg 的 API 命名很容易混淆。你怎么证明你的全量扫描真的没触发解码？

**标准回答**：
「av_read_frame 和 avcodec_send_packet / avcodec_receive_frame 是完全独立的 API 层级。

```
libavformat (容器层):
  av_read_frame()          → 读 packet 头 (pts/dts/duration/flags/pos)
  av_seek_frame()          → 容器级 Seek

libavcodec (编解码层):
  avcodec_send_packet()    → 送压缩数据给解码器
  avcodec_receive_frame()  → 拿解码后的 YUV/RGB 帧
```

我的扫描循环只调用了 av_read_frame() → 读标志位和 PTS → av_packet_unref()。全程没有把 packet 送给 avcodec_send_packet()，解码器根本没有介入。

验证方式也很直接：在解码器的 avcodec_send_packet 入口打一个计数器，全量扫描一轮后计数器为 0，就证明确实没解码。」

## 模块三：Smart Seek `Q7 Q8 Q9`

### Q7：Smart Seek 在同 GOP 内不 flush。但不 flush 的话，解码器状态是上次解码留下的——不会有残留问题吗？

**面试官**：你为了省掉 flush 和重新初始化的开销，选择同 GOP 内不解码器 flush。但解码器的内部状态（参考帧列表、DPB 等）会不会因为不 flush 而出错？什么情况下是安全的？

**标准回答**：
「Smart Seek 不 flush 的安全前提是三个条件同时满足：

1. **目标帧在当前解码位置之后**（PTS 递增）——不会往回跳
2. **目标帧和当前位置在同一个 GOP**——所有 P/B 帧的参考帧都已经被解码了
3. **中间没有 gap 或 corruption**——流没有被截断或损坏

满足这三条时，解码器内部状态（参考帧列表、DPB）是『向前滚动』的，而不是『跳变』的。本质上就是正常顺序播放，只是把中间的帧丢弃不显示。

如果跳到下一个 GOP，必须 flush + 重新 seek。因为新 GOP 的第一个 I 帧的参考帧上下文跟上一个 GOP 无关，解码器必须重建参考帧列表。」

---

### Q8：你怎么知道两个时间点是否在同一个 GOP？

**面试官**：判断同 GOP 需要知道 GOP 边界。你是怎么拿到这个信息的？

**标准回答**：
「在全量 demux 扫描时，我已经记录了每个关键帧的 frameId。这就是 `keyframe_ids_` 数组——它本质上就是 GOP 边界列表。

```
keyframe_ids_ = [0, 30, 33, 283, 313, ...]

判断 frameId=150 和 frameId=180 是否同 GOP:
  二分查 150 的最近关键帧 → keyframe_ids_[?] → 假设是 frameId=33
  二分查 180 的最近关键帧 → keyframe_ids_[?] → 也是 frameId=33
  → 同 GOP ✓

判断 frameId=270 和 frameId=290 是否同 GOP:
  二分查 270 → frameId=33
  二分查 290 → frameId=283
  → 不同 GOP ✗
```

复杂度 O(log N)，对每个 Seek 请求几乎零开销。」

---

### Q9：Smart Seek 和逐帧抽帧+丢帧有什么区别？什么时候用哪个？

**面试官**：你们的自动剪辑 3.0 也用了一段『逐帧抽帧+丢帧』的策略。它和 Smart Seek 是什么关系？

**标准回答**：
「两者解决同一个问题（避免频繁 Seek + 重复解码），但适用场景不同：

- **逐帧抽帧+丢帧**：从视频头一路顺序解码，不调任何 Seek。适合目标帧非常密集的场景（如每 200ms 一帧、几乎每 6 帧就要取一帧）。此时 Seek 开销 > 顺序解码开销，不如全顺解。
- **Smart Seek**：有选择地 Seek。适合目标帧稀疏或随机分布的场景。同 GOP 内顺序解码，跨 GOP 才 Seek。这是更通用的策略。

自动剪辑 3.0 的目标帧密度很高（200ms/帧），逐帧抽帧已经足够好。Smart Seek 的更大价值在于目标帧稀疏或随机的场景——比如用户手动拖动时间线预览。」

## 模块四：VFR 与工程取舍 `Q10 Q11 Q12 Q13`

### Q10：你的全量扫描方案在 VFR 下没问题。但如果素材是 2 小时的 VFR 长视频，你 150ms 的承诺还成立吗？

**面试官**：CFR 下你可以精确估算扫描耗时。VFR 下呢？会不会因为某些异常帧导致扫描时间不可控？

**标准回答**：
「VFR 不影响 demux 扫描耗时。因为 av_read_frame 遍历 packet 的路径跟帧间隔无关——它按容器存储顺序读，不是按时长读。

2 小时视频的总帧数取决于平均帧率。如果平均 30fps，就是 216,000 帧。按 120,000 帧/秒的 demux 吞吐算，约 1.8 秒。跟 CFR 还是 VFR 无关。

唯一可能影响扫描速度的是容器格式——TS 流每个 PES 包解析比 MP4 的 box 结构慢 2~3 倍。但这也是容器决定的，不是帧率模式决定的。」

---

### Q11：极端长视频（如 10 小时延时摄影）全量扫描不太现实。有没有折中方案？

**面试官**：全量 demux 要扫所有帧。10 小时的素材怎么办？

**标准回答**：
「对超长素材，有不建全量索引的折中方案——**双层索引**：

1. **稀疏层（关键帧索引）**：只扫 keyframe_ids_，不扫全部帧。10 小时视频的关键帧数 = 总帧数/GOP。GOP=30 的话约 36,000 个关键帧。数据量很小，扫描很快。

2. **精确层（按需回扫）**：当需要查一个非关键帧的 PTS 时，找到它所属的 GOP（二分 keyframe_ids_），然后只对这个 GOP 范围内的帧做一次迷你 demux 扫描（最多 GOP=30 帧）。

查询时：
- 同 GOP 且已被迷你扫描过 → 直接查表
- 同 GOP 未扫描 → 从关键帧起 demux 最多 30 个 packet
- 跨 GOP → Seek 到新 GOP 的关键帧 + 迷你扫描

这样把 O(总帧数) 的建索引开销变成 O(关键帧数 + 每次查询最多 GOP 帧)。对于播放器类场景（用户随机 Seek）非常适用。

这个也是 ExoPlayer 的做法——按需加载 GOP 内的 sample 索引，而不是一上来就全量。」

---

### Q12：这个「帧索引」的需求，为什么不直接用 FFmpeg 自带的 av_seek_frame 就够了？你的价值在哪？

**面试官**：FFmpeg 本身就有 av_seek_frame，也能 Seek 到任意时间。你做的这些——建索引、Smart Seek——到底比直接用 av_seek_frame 好在哪里？

**标准回答**：
「av_seek_frame 能 Seek，但三件事它做不了：

1. **帧级 Seek（frameId→PTS）**：av_seek_frame 只接受 PTS 或 timestamp。你要『跳到第 1000 帧』，它不知道第 1000 帧的 PTS 是多少。需要你在外面算——而『算』的精度就是这篇文档解决的问题。

2. **Smart Seek（同 GOP 复用）**：av_seek_frame 每次都走标准路径：flush 解码器 → 定位关键帧 → 重建解码上下文 → 解码到目标。它不知道你上一个 Seek 的目标还在同一个 GOP 里。Smart Seek 的价值是在 av_seek_frame 外面加了一层缓存/复用逻辑——这不是代替 FFmpeg，是更高效地使用 FFmpeg。

3. **帧精确索引**：av_seek_frame 配合 AVSEEK_FLAG_BACKWARD 只能保证『Seek 到目标时间之前的最近关键帧』，不能保证帧精确。

我的价值不是『写了一个比 FFmpeg 更强的 Seek』，而是『在 FFmpeg 的 Seek 之上，封装了帧语义、VFR 兼容性、解码器状态复用三层能力』。这是 SDK 开发者该做的事。」

### Q13：整个项目最大的收获是什么？如果重来一次会怎么做？

**面试官**：总结一下，这个项目对你最大的成长是什么？

**标准回答**：
「最大的收获是认识到：**Bug 的表面现象和根因往往在不同层次**。

自动剪辑偏帧的 Bug，表面看是『Seek 不准』，算法侧第一反应是『你们 Seek 的 API 用错了』。但逐层往下挖：

- 第一层（表象）：float 算 Seek 不准
- 第二层（根因）：float→int64 截断在帧边界处不稳定
- 第三层（根因的根因）：index_entries 只有关键帧，非关键帧查不到 → fallback float → 又撞精度
- 第四层（设计问题）：VFR 下 frameId 公式模型本身是错误的

如果停在第一层，解决方案就是『换成 double』——Bug 依然在，只是概率降低了。
到第四层才明白应该换模型：frameId 不应该推导，应该计数。

如果重来一次，我会更早问自己：**『这个数据结构的语义是对的，还是刚好在常见 case 下够用？』**

index_entries 在 CFR+GOP 固定时『够用』，但语义上是错的（关键帧索引≠全帧索引）。把『够用』当『正确』，规模一上来必炸。这是我在 Insta360 这几年最深的一课。」
