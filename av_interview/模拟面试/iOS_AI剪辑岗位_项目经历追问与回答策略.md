## 1. 请介绍一个你在工作中遇到过的技术难题，你是怎么解决的？

### 面试官想考察什么

这个问题是项目深挖入口。面试官主要看三点：你是否能讲清楚复杂问题；你是否真的参与了核心技术决策；你的解决方案是不是有工程深度，而不是简单改参数。

### 推荐主讲项目：自动剪辑性能优化

这个项目最贴合剪映 JD，因为它和 AutoCut、一键成片、AI剪辑链路高度相关。

### 推荐回答

我之前遇到过一个比较典型的技术难题，是自动剪辑 3.0 的性能优化。

这个项目的业务流程是用户选择一个或多个视频后，我们先对视频进行抽帧，再把帧送给算法分析，算法返回高光片段信息，上层再根据这些结果做片段拼接、转场、滤镜和 BGM，最后生成一条完整成片。

当时 3.0 算法相比 2.0 有一个很大的变化：送帧频率从大约 600ms 一帧提升到 200ms 一帧，算法精度更高了，但工程侧抽帧和整体处理耗时明显上升，已经影响用户出片体验。

我做的第一件事不是直接改代码，而是先把链路拆成抽帧、渲染、算法推理几个阶段分别打点。排查后发现主要有两个问题。

第一个问题是高频抽帧导致底层解码器反复 Seek。比如一个视频关键帧间隔是 600ms，我要抽 200ms 和 400ms 两帧，原来的逻辑每次都会从上一个关键帧重新解码。也就是说 200ms 解一次从 0 到 200，400ms 又重新从 0 到 400，重复解码非常严重。

我的解决方案是把频繁 Seek 改成“顺序解码 + 按需丢帧”。如果目标帧之间距离很近，就不再调用 Seek，而是让解码器顺着往下解，遇到不需要的帧直接丢掉。这个方案看起来解了更多帧，但它避免了反复回退关键帧，实际耗时反而更稳定。

第二个问题是整个 Pipeline 原来是串行的：先抽帧，再渲染，再推理。后来我分析发现这三步使用的是不同硬件资源，抽帧主要用硬件解码器，渲染用 GPU，算法推理用 CPU/NPU，它们没有必要互相等待。所以我引入了生产者消费者模型，把抽帧、渲染和推理拆成并行流水线。优化后，抽帧和渲染的耗时基本被隐藏，整体耗时更接近算法推理本身的耗时。

最后这个项目的价值不只是把性能优化了，还沉淀了一套适合 AI剪辑业务的处理思路：视频帧处理不能只看单点耗时，而要看整个异构硬件 Pipeline 的吞吐率。

### 面试官可能追问

**追问 1：为什么顺序解码会比 Seek 快？**

因为视频压缩不是每一帧都独立存储。P 帧、B 帧依赖前后的参考帧，精确 Seek 通常要先定位到上一个关键帧，再从关键帧解码到目标帧。高频抽帧时，如果每次都 Seek，就会反复做同一段解码工作。顺序解码虽然会经过中间帧，但解码器状态是连续的，避免了重复回退。

**追问 2：你怎么判断下一帧该 Seek 还是顺序解码？**

我会根据目标时间戳、当前解码位置和关键帧分布做判断。如果目标帧距离当前帧很近，顺序解码更划算；如果距离很远，Seek 更合适。更进一步可以读取容器里关键帧索引，例如 MP4 的 `stss` 信息，或者使用 FFmpeg 已解析好的 `AVStream->index_entries`，这样可以更准确地判断。

**追问 3：并行后怎么控制内存，不会队列无限增长吗？**

不能让队列无限增长。生产者消费者模型必须设置队列水位，比如最大缓存帧数。推理端如果处理不过来，前面的抽帧/渲染需要阻塞或降采样，必要时丢弃低价值帧。AI剪辑本质上更看重高光片段识别和整体体验，不能为了“每帧都处理”把内存打爆。

## 2. 你做过哪些性能优化？能不能讲一个最有代表性的？

### 面试官想考察什么

面试官想确认你不是只会“感觉优化”，而是能用数据定位瓶颈，并且理解 CPU、GPU、硬编硬解、内存拷贝、线程调度这些底层因素。

### 推荐主讲项目：iOS滤镜与美颜 SDK 接入

这个项目最贴合 iOS、图像处理、视频编辑方向。

### 推荐回答

我做过一个比较典型的性能优化，是 iOS 端滤镜和美颜 SDK 接入。

当时我们需要把第三方美颜 SDK 和多款自研滤镜接入到 iOS/Android 双端，iOS 端的主要问题是内存占用高、帧率下降。视频链路里每帧都要处理，如果单帧多几毫秒，最终就会表现为预览卡顿或导出变慢。

我主要从两个方向优化。

第一是数据通路的零拷贝改造。原来的流程里，`CVPixelBuffer` 到 OpenGL 纹理之间存在 CPU 拷贝或纹理上传，每帧都做这件事成本很高。我引入了 `CVOpenGLESTextureCache`，直接把相机或解码输出的 `CVPixelBuffer` 映射成 OpenGL 纹理，减少 CPU 到 GPU 的数据搬运。

第二是渲染资源池化。因为美颜、漫画滤镜、色彩增强等效果可能串联执行，如果每一帧、每一个滤镜都频繁创建和释放纹理、FBO，显存抖动会很大。我在底层设计了 Texture Pool，复用有限数量的纹理和 FBO，通过乒乓渲染把多个滤镜串起来。

最终效果是内存占用降低约 25%，单帧处理耗时缩短约 20%。另外我也处理了 iOS 退后台时 OpenGL 调用导致崩溃的问题：在 OC 层监听 App 生命周期，进入后台前暂停 C++ 渲染线程，并通过 `glFinish()` 确保 GPU 队列执行完，再切断渲染循环。

### 面试官可能追问

**追问 1：为什么 `CVOpenGLESTextureCache` 能减少拷贝？**

因为它不是把像素数据重新拷贝一份再上传纹理，而是把 `CVPixelBuffer` 背后的图像内存包装成 GPU 可采样的纹理对象。这样 C++/OpenGL 渲染层可以直接消费纹理，避免每帧走 `glTexImage2D` 这类昂贵上传路径。

**追问 2：什么是乒乓渲染？**

乒乓渲染就是准备两组或少量几组纹理/FBO，滤镜 A 的输出写到纹理 1，滤镜 B 再从纹理 1 读、写到纹理 2，下一步再交换读写角色。这样不用每个滤镜都创建新的中间纹理，既降低内存峰值，也减少频繁分配释放带来的抖动。

**追问 3：如果现在从 OpenGL 迁移到 Metal，你怎么设计？**

我不会让业务直接依赖 OpenGL 或 Metal，而是抽一层 RHI，也就是 Render Hardware Interface。上层只表达“创建纹理、绑定输入、执行滤镜 Pass、输出结果”这些抽象指令，底层 iOS 可以实现 Metal，Android 可以实现 Vulkan/OpenGL。这样既能支持现有跨平台复用，也方便未来逐步迁移。

## 3. 你在项目中是怎么定位问题的？有没有系统性方法？

### 面试官想考察什么

面试官主要看你的排查方法论。优秀回答要体现：先拆链路、再做假设、用数据验证、排除错误方向、最后定位根因。

### 推荐主讲项目：车载相机预览低延时优化

### 推荐回答

我比较典型的一次问题定位，是车载相机预览低延时优化。

当时客户反馈 X5 相机预览延时达到 1.5s，而 X3 大概只有 0.5s，体验差异非常明显。这个问题一开始很容易被归因到硬件或者固件，但我没有直接下结论。

我先做了两个排除。第一，我抓取两台相机的视频流，发现 X5 使用 High Profile，X3 使用 Main Profile。理论上 High Profile 解码更复杂，但实测两边都能稳定 30fps，所以解码能力不是主要瓶颈。第二，我对网络接收、解码完成、进入渲染队列这几个节点做分段埋点，发现网络和解码耗时不足以解释多出来的 1s 延时。

最后根因定位在渲染前的等待策略。历史代码为了让渲染节奏平滑，会用首帧 PTS 和当前本地时间建立一个固定基准，后续帧都按照这个基准去等待。问题是如果首帧因为建连或网络波动本身就慢了 1s，这个高延时会被永久继承到后续所有帧。

验证方式也很直接：我临时关闭这段 wait 逻辑，延时马上降到 0.5s 左右，说明根因成立。但直接取消等待会导致画面忽快忽慢，所以最终我设计了自适应抖动缓冲，也就是 AJB。它不再使用固定首帧延时，而是根据实时观测延时动态调整目标缓冲，网络变差时快速升高缓冲防卡顿，网络恢复时缓慢降低缓冲防抖动，同时在队列积压时主动追赶或适度丢帧。

最终把 X5 预览延时从 1.5s 降到 0.5s~0.6s，下降超过 60%。

### 面试官可能追问

**追问 1：为什么不能直接去掉等待？**

直接去掉等待能降低延时，但会牺牲平滑性。网络和解码本身有抖动，解完一帧立刻渲染会导致帧间隔不稳定，用户看到画面忽快忽慢。实时预览不是只追求最低延时，而是在低延时和稳定性之间做平衡。

**追问 2：AJB 为什么要“快升慢降”？**

网络变差时，如果缓冲升得慢，就会马上卡顿，所以要快升；网络恢复时，如果缓冲降得太快，稍微一点抖动又会卡，所以要慢降。这个策略本质上是防止系统在弱网边缘频繁振荡。

**追问 3：你怎么证明是渲染等待策略的问题？**

我通过分段埋点排除了网络和解码，再通过关闭 wait 逻辑做控制变量实验。关闭后延时马上下降，说明问题主要来自渲染前等待策略。然后再引入 AJB 解决“低延时”和“平滑性”的平衡问题。

## 4. 你有没有做过架构设计或模块重构？

### 面试官想考察什么

这类问题考察你是否只是执行需求，还是能独立负责模块方案设计。要重点讲“为什么原架构不行、新架构怎么解耦、怎么保证兼容和可回滚”。

### 推荐主讲项目：4K直播链路性能重构

虽然这是 Android 直播项目，但它体现的是音视频底层架构能力，对剪映这种视频工具岗位同样加分。

### 推荐回答

我做过一次比较大的链路重构，是 4K 全景直播性能优化。

当时问题是 4K RTMP 直播开始时大概只有 23fps，连续播一段时间后会掉到 5fps 左右，手机严重发热。这个问题不是单点 bug，而是整个直播 Pipeline 架构不合理。

我先做全链路打点，把流程拆成解码、渲染、编码、推流。发现第一个瓶颈在渲染到编码之间，原来使用 `glReadPixels` 把 GPU 纹理读回 CPU，再做 YUV 转换后交给编码器。4K 分辨率下这一步非常重，单帧可能 20ms~30ms，而且会强制 GPU/CPU 同步。

我的方案是重构数据链路，引入 `AHardwareBuffer` 和 Surface 模式，让 GPU 渲染结果尽量直接进入硬件编码路径，避免昂贵的 CPU 回读。这个优化后，渲染到编码交接耗时从几十毫秒降到 1ms~2ms 级别。

第二个瓶颈是网络 I/O。编码输出和 RTMP 发送原来是同步的，弱网时 `WritePacket` 会阻塞编码线程，导致整个 Pipeline 被网络背压拖垮。我在编码和推流之间加了异步发送队列，用生产者消费者模型解耦编码和网络发送。同时根据队列水位做动态码率调整，队列高水位说明网络拥塞，就降低码率；低水位说明网络恢复，就逐步升码率。

为了保证安全落地，我没有直接替换旧链路，而是做了参数化开关。只有开启新参数才走零拷贝和异步发送逻辑，默认仍然走旧逻辑，保证对已有业务零影响，也方便灰度和回滚。

### 面试官可能追问

**追问 1：为什么 `glReadPixels` 很慢？**

它慢不只是因为拷贝大，更关键是会触发 GPU/CPU 同步。GPU 内部纹理通常是块状或私有布局，CPU 需要线性内存，`glReadPixels` 可能涉及等待 GPU 完成、格式转换、布局重排和大块内存搬运。4K 下这个成本非常高。

**追问 2：异步队列会不会导致延迟越来越大？**

会，所以队列必须有水位控制。异步队列不是无限缓存，而是用来解耦短时网络抖动。队列高水位时要动态降码率，极端情况下要丢 GOP 或做降级，不能让延迟无限累计。

**追问 3：你怎么保证重构不影响旧业务？**

通过参数化动态路由。新逻辑默认关闭，只有特定业务显式开启才进入新链路。旧业务继续使用原来的像素格式和同步写包路径。这样可以做到灰度发布、快速回滚，也避免一次重构影响所有业务。

## 6. 你在项目中有没有遇到过 Crash 或稳定性问题？

### 面试官想考察什么

面试官想看你是否有线上稳定性意识，能不能处理偶现问题、多线程生命周期、资源释放、App 生命周期等复杂问题。

### 推荐主讲项目：iOS OpenGL 退后台崩溃

### 推荐回答

有，我在 iOS 滤镜和美颜接入时遇到过退后台 OpenGL 崩溃问题。

当时现象是 App 进入后台后，底层 C++ 渲染线程有时还会继续调用 OpenGL 指令，比如 `glClear`、`glDrawArrays`。iOS 对后台 GPU 调用限制很严格，这种情况下可能会被系统杀掉，或者出现 OpenGL 错误。

我的处理方式是在 OC 层监听 `UIApplicationWillResignActiveNotification` 和相关生命周期事件。一旦 App 即将进入非活跃状态，就通知 C++ 渲染线程暂停。这里有一个细节，不能只是设置一个 pause 标记就完事，因为 GPU 指令是异步提交的。暂停前我会调用 `glFinish()`，确保已经提交的 GPU 指令全部执行完成，然后再让渲染线程停止提交新指令。

恢复前也要重新确认 `EAGLContext` 已经设置到当前线程，并且资源状态有效。这样把 App 生命周期和底层渲染线程状态对齐后，退后台崩溃就解决了。

### 面试官可能追问

**追问 1：为什么用 `glFinish()`，不用 `glFlush()`？**

`glFlush()` 只是把命令尽快提交给 GPU，不保证执行完成；`glFinish()` 会阻塞等待 GPU 把之前的命令执行完。进入后台前我们更关心安全性，要确保没有未完成的 GPU 工作继续跑，所以这里用 `glFinish()` 更稳妥。

**追问 2：这样会不会卡主线程？**

不能在主线程随便重操作。实际处理时应该尽量让渲染线程自己完成收尾，主线程只发送状态切换信号。如果必须同步等待，也要控制超时和调用时机，避免生命周期切换时造成 UI 卡顿。

## 7. 你有没有做过跨平台架构？怎么保证 iOS/Android 逻辑一致？

### 面试官想考察什么

剪映这类产品通常多端协同，面试官会考察你是否能设计清晰的模块边界，是否理解平台差异。

### 推荐回答

我过往做跨平台 SDK 比较多，核心思路是把稳定、复杂、性能敏感的逻辑下沉到 C++ 核心层，把平台相关能力收敛在薄封装层。

比如自动剪辑、滤镜处理、视频分析这些逻辑，算法和数据流转应该尽量在 C++ 层统一。iOS 侧通过 Objective-C++ 桥接，Android 侧通过 JNI 调用。这样可以保证核心算法逻辑一致，也降低双端重复开发成本。

但并不是所有东西都强行统一。像纹理、硬件编码、生命周期、线程模型这些平台差异很大的能力，我会抽象接口，然后分别在 iOS 和 Android 实现。例如 iOS 可能是 `CVPixelBuffer`、`CVOpenGLESTextureCache` 或 Metal Texture，Android 可能是 `SurfaceTexture`、`AHardwareBuffer`。上层只依赖统一的纹理抽象，不直接感知平台细节。

### 面试官可能追问

**追问 1：JNI/OC++ 桥接最容易出什么问题？**

最容易出生命周期和线程问题。比如 C++ 异步回调到上层时，上层对象可能已经释放；或者回调线程不是主线程，直接操作 UI 会崩。解决方式是明确所有权，必要时用 `shared_ptr` 或 weak/strong dance 保证生命周期，同时把 UI 更新派发回主线程。

**追问 2：接口设计怎么避免后续难维护？**

接口要围绕业务稳定概念设计，而不是围绕某个平台 API 设计。比如对外暴露“输入帧、执行滤镜、输出帧”，而不是暴露一堆 OpenGL 细节。平台 API 可以在实现层变化，但业务接口尽量稳定。

## 8. 如果让你负责剪映 AI剪辑中的 AutoCut 模块，你会怎么设计？

### 面试官想考察什么

这是岗位强相关问题，考察你能不能把自己项目经验迁移到目标业务。

### 推荐回答

如果让我负责 AutoCut，我会把它拆成四层。

第一层是素材解析层，负责读取视频元数据、时长、帧率、旋转信息、音频轨道等，并建立统一时间轴。这里要避免时间戳和帧 ID 来回转换造成误差，最好以整型帧 ID 或统一时间单位作为内部索引。

第二层是帧采样和预处理层。根据算法需要做抽帧、缩放、色彩格式转换。这里要重点优化性能，避免高频 Seek 带来的重复解码。可以根据关键帧分布决定 Seek 还是顺序解码，并用生产者消费者模型把解码、预处理、推理做成流水线。

第三层是 AI 推理和结果后处理层。端侧模型可以用 CoreML，输入尽量使用 `CVPixelBuffer`，并做降采样控制内存和耗时。推理结果不能直接给上层用，还要做去重、片段合并、节奏控制，比如避免连续片段太碎，保证成片节奏自然。

第四层是编辑合成层。根据高光片段结果生成时间线，自动加转场、滤镜、BGM，最后进入预览和导出。这里要注意 AI 结果可编辑，用户可以二次调整，所以数据结构要能被时间轴组件消费，而不是一次性生成死结果。

### 面试官可能追问

**追问 1：端侧 AI 推理太慢怎么办？**

可以从几个方向优化：降低输入分辨率、减少采样频率、批处理、滑动窗口、模型量化、使用 CoreML/NPU 加速。业务上也可以先给用户快速生成粗结果，再后台继续优化精细结果。

**追问 2：算法结果不稳定怎么办？**

工程层要做后处理。比如对置信度做阈值过滤，对相邻高光片段做合并，对过短片段做剔除，对节奏做约束。AI 输出不是最终产品结果，必须经过业务规则和编辑体验层的校正。

## 9. 你如何回答“你最大的优势是什么？”

### 面试官想考察什么

这个问题不是让你泛泛说“学习能力强”，而是看你能否把自己的优势和岗位要求绑定。

### 推荐回答

我最大的优势是能把音视频底层工程能力和业务目标结合起来。

很多优化不是单纯改一行代码，而是要理解业务目标、链路瓶颈和硬件资源。比如自动剪辑项目，我不是只优化抽帧，而是把抽帧、渲染、推理整体看成一个异构硬件 Pipeline；预览低延时项目，我也不是简单去掉等待，而是在低延时和平滑性之间做了 AJB 方案；滤镜美颜接入中，我关注的是每帧数据如何在 CPU/GPU 之间流转，怎么减少拷贝和资源抖动。

剪映 AI剪辑方向本质上也是这样的工作：既有业务迭代，也有性能、质量和架构设计。我认为我的经验比较匹配这种需要“能落地、能优化、能解释清楚底层原因”的岗位。

## 10. 项目回答总模板

以后遇到任何项目追问，都可以按这个顺序回答：

1. **背景**：这个项目解决什么业务问题，为什么重要。
2. **指标**：优化前的问题要量化，比如 1.5s 延时、单帧 30ms、内存高 25%。
3. **拆链路**：你怎么打点，怎么把复杂问题拆开。
4. **定位根因**：不要只说现象，要说底层原因。
5. **方案权衡**：为什么选这个方案，放弃了什么，风险是什么。
6. **工程落地**：线程、队列、生命周期、灰度开关、兼容性怎么处理。
7. **结果**：性能、稳定性、用户体验、团队沉淀。
8. **复盘**：如果重做一次，下一步还能怎么优化。

## 最适合你在剪映面试中主打的三个项目

### 第一优先级：自动剪辑性能优化

最贴合 AI剪辑、AutoCut、一键成片。主打关键词：抽帧、算法推理、生产者消费者、关键帧、Smart Seek、异构硬件 Pipeline。

### 第二优先级：iOS滤镜与美颜 SDK 接入

最贴合 iOS、多媒体、图像处理、性能优化。主打关键词：`CVPixelBuffer`、`CVOpenGLESTextureCache`、零拷贝、Texture Pool、OpenGL 生命周期。

### 第三优先级：预览低延时优化

最能体现问题定位和工程权衡。主打关键词：全链路埋点、固定等待策略缺陷、AJB、自适应抖动缓冲、低延时和平滑性平衡。

直播性能优化可以作为补充项目，用于展示你对零拷贝、硬件编码、网络背压、ABR 的理解深度。
