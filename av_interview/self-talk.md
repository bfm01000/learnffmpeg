## 🌟 推荐的面试自我介绍（更加口语化、接地气版本）

你好，我叫杜孟林。我21年7月份从大学毕业后，就来到了影石（Insta360），一直在做移动端 c++ 跨平台开发。也就是用 C++ 写核心的视频处理 Pipeline 和算法落地，然后通过  OC 和 JNI 分别封装给iOS和 Android 双端用。

今天面试，我主要想跟您聊聊我做过的三个比较有技术深度的项目，我先简单讲一下：

- 第一个是 **Android端 4K 全景直播的pipiline优化**。当时客户反馈 4K 直播发热严重、疯狂掉帧。我排查发现主要是内存拷贝和网络阻塞的问题。所以我在底层用 `AHardwareBuffer` 打通了零拷贝渲染，又手写了一个基于队列水位的动态码率（ABR）和异步发送机制，最后把弱网下的帧率稳在了 30 帧。优化之前只有22fps左右。
- 第二个是**相机预览的低延时优化**。我们当时有两个相机x5和x3，x5延时高达 1.5s，x3只有0.5s，我通过在pipline的各节点打时间戳排查以及代码分析，发现视频帧其实早就解码完成了，是原有的渲染等待策略把首帧的高延时给“固化”起来了。为了兼顾低延时和画面平滑，我设计了一套自适应抖动态抖动缓冲（AJB）策略，在保持预览平滑的条件下，将延时优化到了 0.3 秒左右。
- 第三个是**自动剪辑的性能优化**。当时因为新算法的抽帧频率变高了，我们底层 FFmpeg 的 seek 逻辑写得不够好，导致解码器疯狂重复解码，抽帧耗时很高。我做了两轮优化大幅降低了耗时。另外，原来抽帧、渲染和算法推理是“死等前一步做完才能做下一步”的串行模式，我用生产者消费者模型让 CPU 和 GPU 分工合作，把这三步彻底并行了起来，最后出片速度提升了好几倍。还有一个内存方面的性能优化，

总的来说，从底层架构到上层业务都会一些，对音视频底层和性能调优也比较感兴趣。以上就是我的简单介绍，您看我们从哪个项目开始聊？

> 我当时能确定 Seek 有重复解码的问题，但一直没想清楚怎么从根上优化，**最后先上了「逐帧解码 + 丢帧」的临时方案把性能拉回来**——能跑，但也没及时跟团队同步，大家以为瓶颈已经彻底解决了。
>
> 后面我想把这个方案做极致、去掉不必要的全量顺解，又独自啃 FFmpeg 的 Seek 逻辑，进展很慢。**要是以前**，可能就继续一个人死磕源码。**这次**我按现在的规矩，把日志和时间戳分布整理成一页纸，找组里更熟 FFmpeg 的同事对了十分钟。他看了之后问：「同 GOP 内的目标帧，能不能别反复 Seek，让解码器接着往下解，中间不要的帧丢掉？」——这就是 **Smart Seek** 的核心思路。我回去验证后，抽帧路径更精准了；再往后还从同事那学到直接读 `index_entries`（MP4 的 stss 索引）做 GOP 判断，彻底把这块优化做扎实了。
>
> 这件事让我意识到：技术问题可以深挖，但**不能靠无限期单打独斗换进度**。现在我给自己定了规矩：难题可以先独立查，但**超过两个小时还没有明确方向，就立刻停下来**，把现象、假设和已排除项整理出来，找同事或 Mentor 做一次短对齐。后来做异构并行 Pipeline 时我也是这么做的——该独立分析的先分析，该暴露风险的绝不拖到第二天。现在这已经变成我的工作习惯了。

### 如果面试官问，你未来的技术规划是什么样的？

> 我规划得挺清楚的，其实就是一条线往下走：**把实时音视频和 Linux 系统层彻底吃透**。
>
> 具体拆成两块来说吧：
>
> **第一块是 WebRTC。** 我过去几年做的直播、预览延时优化，本质上就是在跟实时音视频打交道，但主要聚焦在设备端的采集-编码-解码-渲染这条链路，网络传输层涉及不深。WebRTC 刚好把这两块串起来了，也是我下一步想系统深入的方向——不只是会用 API，我想把它的**网络传输层（JitterBuffer、NACK、FEC、拥塞控制）、音视频引擎（音频 3A、视频编码适配）、以及整条媒体通道的调度机制**都啃一遍。因为有了之前做 AJB、动态码率、零拷贝这些经验，再去理解 WebRTC 的设计决策，很多地方其实是相通的，我学起来也有抓手。
>
> **第二块是 Linux 下的音视频开发。** 我现在做的是 Android/iOS 上的 C++ 底层，虽然也是 Linux 内核那一套，但毕竟隔了一层。接下来我想直接扎到 Linux 系统上——搞清楚**音视频在 Linux 下的调度到底是怎么玩的**，比如：
> - CPU 亲和性怎么绑、实时线程（`SCHED_FIFO` / `SCHED_RR`）怎么用才能保证音视频的实时性；
> - DMA-BUF、V4L2、ALSA 这些框架是怎么跟硬件打交道的；
> - 用户态和内核态之间，音视频数据是怎么高效搬运的，零拷贝在 Linux 下的完整链路是什么样的。
>
> 说白了就是：以前是在系统之上写 Pipeline，我想往下沉一层，真正理解系统是怎么调度我写的那些代码的。
>
> 长线的话，这两块其实是互通的——WebRTC 的服务端、SFU、媒体网关都跑在 Linux 上，你对 Linux 调度吃得越透，做实时音视频的底子就越扎实。三年内我希望自己能成为那种**既懂上层协议和应用场景，又能下去调 Linux 系统层性能**的人，碰到实时音视频的疑难杂症，能从应用层一直追到内核调度，而不是停在某一个层级上猜。

### 如果面试官问，你觉得自己工作中有什么好的方法论？

> “这几年做底层开发和性能调优，我总结了两个我自己一直坚持的方法论：
>
> **第一是『一切优化必须用数据说话，先测量再优化』。**
> 以前遇到延时高或者卡顿，可能会凭直觉去猜哪里慢了。但我现在的工作习惯是，动手改代码前，**必定先做全链路的埋点或抓 Trace**。比如在做 1.5s 高延时排查时，我先拆解了网络接收、解码、渲染三个阶段的耗时，拿到真实数据后，立刻就能排除解码性能的干扰，精准定位到是渲染等待策略的问题。不靠猜想，靠数据定边界，这是最高效的。
>
> **第二是『深入底层的溯源思维与文档沉淀』。**
> 当解决了一个疑难杂症，我不满足于仅仅把代码修好，我会去追溯它的底层原理（比如这次为什么 FFmpeg 的 Seek 会这么慢，底层是怎么处理的）。搞懂之后，我会把整个排查过程、踩过的坑、以及底层的运作机制**写成复盘文档沉淀下来**。这不仅能帮团队避坑，也能逼着自己把知识点彻底消化，将经验转化为自己的技术壁垒。我觉得这是技术人员快速成长最好的方法。”

### 如果面试官问，AI Coding 现在这么强了，以后程序员会不会被淘汰？你怎么看？

> 这其实是现在大厂（字节、腾讯、阿里）都很喜欢问的一类开放性问题，不是在考你预测未来，而是考察四件事：对 AI 的认知深度、有没有危机意识、是否持续学习、以及能不能把 AI 当生产力而不是竞争对手。
>
> 我先给观点：**AI 会淘汰一部分程序员，但不会淘汰程序员这个职业。更准确地说——它会淘汰不会使用 AI 的程序员。**
>
> 拆开来聊。
>
> **第一层，AI 确实已经替代了很多低价值工作了。** 写 CRUD、样板代码、单元测试、文档生成、SQL、甚至 Bug 初步定位，AI 现在做得非常好。我自己就是重度用户——在做 KMP SDK 重构时，我之前完全不会 Kotlin，就是用 AI 当"翻译器"：我用 C++ 思路设计架构和接口，AI 帮我把设计翻译成 Kotlin 代码，我只负责审查线程安全、边界条件和生命周期。一个多月交付了覆盖 15 种机型的 JSON 配置化系统。没有 AI，我不可能在这么短时间内跨语言交付。
>
> **第二层，真正难的工程问题 AI 帮不了你拍板。** 我在影石做跨平台 C++ SDK 开发，AI 可以帮我生成 FFmpeg 调用代码、甚至帮我写 JNI 桥接层——但它回答不了：为什么 Android 端延时突然多了 100ms？为什么 iOS Camera Pipeline 在高帧率下掉帧？跨平台接口为什么要这样设计而不是那样？线上偶发 OOM 了，AI 不会帮你抓 memory dump、不会帮你二分定位是哪个 commit 引入的、不会帮你判断是该加缓存还是改架构。这些事情需要你对整个系统、业务背景和线上真实情况有整体把握。
>
> **第三层，未来程序员的价值锚点会变。** 以前程序员的主要价值是"写代码"，以后会变成"定义问题 + 拆解问题 + 验证 AI 输出 + 做架构决策"。代码本身越来越廉价，真正昂贵的是需求理解、系统设计、trade-off 判断、工程经验、性能优化、稳定性保障——这些反而更重要了。
>
> 所以我不会把 AI 当成竞争对手，而是把它当成**能力放大器**。我平时已经习惯用 AI 来帮我快速搭 Demo、生成测试代码、分析 FFmpeg 或 Android Framework 源码，把省下的时间花在架构设计和性能调优上。我觉得未来程序员之间的差距，不是谁代码敲得快，而是**谁能更高效地利用 AI，把自己的经验杠杆化**。
>
> **如果面试官继续追问："那为什么还要招聘你？"**
>
> > AI 可以生成很多代码，但它不了解公司的业务，也不对结果负责。比如线上出现一个偶发的音视频卡顿，可能横跨 Android、iOS、FFmpeg、网络、硬件五层。AI 可以给排查思路，但最终需要人来判断、验证和取舍——这个人得踩过同样的坑，知道哪条思路是死胡同。我认为未来优秀工程师的核心竞争力，会更多体现在系统理解、架构设计和复杂问题的实际解决能力上，而 AI 是帮助我们高效落地的工具。
