# 模拟面试问题（附标准回答）

## 一、C++ 基础与 SDK 架构

**Q1：你设计一个跨平台（Android/Linux/Windows）的音视频 SDK，C++ 核心层怎么抽象？对外暴露什么接口？**

> 三层架构。最底层是 **Platform Abstraction Layer（PAL）**：把采集（Camera/Mic）、编码（MediaCodec/VideoToolbox/VAAPI）、渲染（EGL/GLX/WGL）包装到统一 C++ 接口。中间是 **Core Pipeline**：纯 C++，不依赖任何平台——Pipeline 类串联 Source → Encoder → Muxer → Network，各节点通过 `std::function` 或虚基类回调衔接。最上层是 **Binding Layer**：按目标引擎暴露 C API（`extern "C"`），Unity 通过 `[DllImport]` 调 C 函数，UE 直接用 C++，原生 App 通过 JNI/ObjC bridge。
>
> 对外暴露的核心接口：`createPipeline(config)` 建管线、`start()`/`stop()` 控制生命周期、`setVideoCallback(fn)` 拿帧、`pushAudioFrame(data)` 喂音频。所有回调都带有 `void* userData` 方便上层关联上下文。

**Q2：SDK 要同时给 Unity、UE、原生 App 调用，C++ 层怎么封装？Unity 的 Native Plugin 和 UE 的 C++ 模块各要注意什么？**

> C++ 核心编译成 `.so`/`.dll`/`.dylib`，对外全用 `extern "C"` 暴露 C 函数（避免 C++ name mangling 和 ABI 问题）。Unity 侧写 `[DllImport("XRSDK")]` 的 C# wrapper，注意：Unity 的渲染线程和 SDK 内部线程不是同一个，回调里拿到数据后要 `GL.IssuePluginEvent` 抛回 Unity 渲染线程才能调 GL API。UE 侧直接 `#include` SDK 头文件链接，但 UE 有自己的 `FRunnable` 线程模型和 GC 系统——SDK 不要直接持有 `UObject*`，通过 `TSharedPtr` + delegate 回调解耦。
>
> 通用坑：各平台 `sizeof(long)` 不一致（Windows 4 字节、Linux/Android 8 字节），公共头文件避免用 `long`，用 `int32_t`/`int64_t`。

**Q3：C++ 里有一个回调从音频线程过来，要更新 UI，但 UI 在主线程，你怎么安全地把数据抛过去？无锁队列怎么实现？**

> 标准方案：**SPSC（Single Producer Single Consumer）lock-free 环形队列**。用 `std::atomic<size_t>` 做 write/read 游标，写入方只动 write、读取方只动 read，靠 acquire-release 内存序保证可见性。核心逻辑：
> ```cpp
> // push: 检查 (write+1) % capacity != read（队列没满）才写
> // pop: 检查 write != read（队列不空）才读
> ```
> 音频线程 push 数据到队列，主线程用 `Looper`/`RunLoop` 注册一个定时或 eventfd 驱动的 poll，检测到可读就 pop 并更新 UI。如果平台有 `MessageQueue`（Android `Handler`、Windows `PostMessage`），push 完发一个轻量通知唤醒消费端。

**Q4：你有一个 `shared_ptr` 管理解码器对象，同时被解码线程和渲染线程持有，销毁时机怎么保证？shared_ptr 的引用计数是线程安全的吗？**

> `shared_ptr` 的**引用计数本身是线程安全的**（标准保证 `use_count()` 的增减是原子的），但**被管理的对象不是**——如果解码线程在调 `decode()`、渲染线程同时把最后一个 `shared_ptr` 析构了，`decode()` 跑在一半对象被析构，直接崩溃。
>
> 解决方法：每个线程用局部 `shared_ptr` 副本持有引用——解码线程进循环时 `auto dec = global_decoder.lock()`（如果是 `weak_ptr`）或直接拷贝 `shared_ptr`，保证自己在用期间对象的引用计数 >= 1。退出循环前把这个副本析构。如果确实要主动销毁，设置一个 `std::atomic<bool> running`，先置 false、等所有线程退出、再 reset 全局 `shared_ptr`。

**Q5：SDK 里资源泄漏怎么排查？你用过哪些工具或方法论？**

> 三层。**编译时**：RAII + 工厂方法返回 `unique_ptr`/`shared_ptr`，禁止裸 `new`，code review 重点看是否有 `new`/`malloc` 没有对应释放。**运行时**：Android 用 ASAN（`-fsanitize=address`）编译、跑一遍基本流程，马上能看到泄漏栈。Linux/Windows 用 valgrind 或 Dr. Memory。**监控**：SDK 内部加一个 allocation counter（debug 模式），`create`/`destroy` 配对计数，退出时 counter > 0 就打日志报警。GPU 资源（纹理、FBO、EGLImage）是容易被忽略的重灾区——每帧创建不销毁，一个月才 OOM，用 `adb shell dumpsys gfxinfo` 或 RenderDoc 抓帧看 GPU 对象数是否持续增长。

## 二、音视频采集与编解码

**Q6：AR 眼镜上做音视频采集，和手机有什么不同？分辨率、帧率、功耗方面有什么特殊约束？**

> 三个核心差异。**功耗**：眼镜电池容量通常只有手机的 1/10~1/5（几百 mAh），持续 camera 采集+编码+渲染，功耗预算可能只有 1~2W，手机可以 5W+。所以必须硬编，分辨率不会开满 sensor 能力（比如 sensor 能 4K 但只开 1080p 甚至 720p），帧率降到 30fps 甚至按需降到 15fps。
>
> **散热**：眼镜贴在脸上，发热感知极其敏感——40°C 用户就明显不舒服。所以不能像手机那样降频了事，要在 SDK 层主动做 thermal throttling：CPU/GPU 温度阈值触发时逐级降分辨率/帧率/关美颜。
>
> **延迟**：AR 眼镜是 see-through 的，虚拟内容叠加在真实世界上。camera 采集→算法处理→渲染上屏的**端到端延迟必须 < 20ms**（motion-to-photon），手机 50-100ms 用户无感，眼镜上超过 20ms 虚拟物体会"漂移"——这就是 XR 场景独有的硬约束。

**Q7：Android Camera2 采集，你要拿到 YUV 数据做算法处理，同时还要低延迟预览——这条链路怎么设计？Surface 共享怎么搞？**

> 核心思路：**一份 YUV，多处使用，零拷贝**。Camera2 创建 session 时传两个 Surface：一个给 `SurfaceView`/`SurfaceTexture` 做预览、另一个给 `ImageReader` 拿 YUV 给算法。Camera HAL 层通过 gralloc 分配同一个 buffer，两个 Surface 各自拿到 dma-buf fd 引用——底层是同一块物理内存。
>
> 预览链路：Camera → SurfaceTexture → OES 纹理 → GL 渲染上屏。算法链路：Camera → ImageReader → `onImageAvailable` 回调拿到 `Image`（含 Y/U/V 三个 Plane 的 ByteBuffer），直接传给算法 SDK（TFLite/SNPE）。注意 `Image` 用完后 `image.close()` 归还 buffer pool，否则采集卡死。
>
> 如果算法需要 GPU 处理且最终要渲染，更优方案是不用 ImageReader——Camera 只出到一个 SurfaceTexture，每帧 `updateTexImage` 后拿到 OES 纹理，算法在 GL shader 里跑（比如用 `samplerExternalOES` 采样 YUV，跑完 inference 结果直接画 overlay），镜头到屏幕全程 GPU 内闭环，零 CPU 拷贝。

**Q8：H.264 和 H.265 在低码率场景下差别有多大？AR 眼镜的视频编码该选哪个？为什么？**

> 低码率（<1Mbps 1080p）下 H.265 比 H.264 省约 **35-50%** 码率，同等画质。但 AR 眼镜的回答不是"H.265 更好"就完事了——要分场景。
>
> **本地录制/回放**：选 H.265，存储和带宽省一半。
> **实时传输到手机/云端（无线）**：要看接收端能力。如果接收端是 iPhone 7+ 或 Android 5.0+，H.265 硬解普遍支持；如果是低端安卓手机或 web 端，H.264 兼容性最好。
> **功耗**：H.265 硬编功耗比 H.264 高 1.2-2x（编码复杂度更高），在眼镜上这是个关键 trade-off——带宽省了但眼镜更热。所以 t时刻答案可能是：**实时场景用 H.264 硬编保功耗，本地录制用 H.265 省空间**。另外，H.265 在极低延迟场景有额外优势——B 帧造成的重排序延迟在 H.264 里更常见。

**Q9：你来设计 SDK 的编码参数：AR 眼镜 30fps、有限带宽、需要低延迟。GOP、码控模式、preset、B 帧这些怎么选？为什么？**

> - **B 帧**：**关闭**。B 帧导致的 PTS≠DTS 要重排序，天然引入至少 1 帧延迟（33ms），XR 场景不可接受。编码器设 `bframes=0`。
> - **GOP**：**1~2 秒**（30~60 帧一个 IDR）。太短→码率膨胀（IDR 帧大约是 P 帧的 5-10 倍大小），太长→传输丢包后花屏时间长。AR 无线传输场景丢包率可能较高，GOP 控制到 1 秒较好。
> - **码控**：**CBR + VBV buffer**。无线信道带宽波动大，CBR 保证码率不冲垮信道；设 `maxrate` ≈ 目标码率、`bufsize` = 2 × maxrate。如果用 VBR/CRF，瞬时码率尖峰可能导致无线传输瞬时阻塞→延迟飙升。
> - **preset**：用**硬编**，不设 preset。如果是软编场景，`ultrafast` 或 `veryfast`——编码质量可以降，编码时间绝不能超帧间隔（33ms 内必须编完一帧）。
> - **zerolatency**：开，禁用 frame-threading 和 lookahead。
> - **额外**：Profile 用 **baseline**（Android 兼容性最好）或 **constrained baseline**（如果不开 B 帧 baseline 就够了）。

**Q10：FFmpeg 和 GStreamer 在你的 SDK 里分别适合干什么？选哪个做底层？你说说各自的优劣。**

> **FFmpeg**：编解码+封装+解封装最强。库生态轻量（`libavcodec`/`libavformat`/`libswscale`），API 简单，社区庞大。适合做 SDK 的"编解码+容器"底层。弱点是 pipeline 编排能力弱——要你自己写线程调度、buffer 管理、节点间同步。
>
> **GStreamer**：pipeline 编排能力极强。`gst-launch` 一行命令搭完采集→编码→封装的管线，插件生态丰富（有现成的 `camerabin`、`xvimagesink` 等）。但框架重——引入 GStreamer 意味着引入 GLib 对象系统、GObject 生命周期、庞大的 runtime 依赖，SDK 体积膨胀。而且 `gst_bus` 回调模型和 C 风格宏让 C++ 封装成本高。
>
> **推荐**：SDK 基础用 FFmpeg（编解码+容器），自己用 C++ 写轻量 pipeline——线程池 + 无锁队列 + 拓扑排序的节点 DAG，比引入 GStreamer 整套 runtime 更轻、更可控、更好 debug。如果项目对插件生态有强需求（比如要随时插拔各种 source/codec/sink），再考虑 GStreamer。

**Q11：Android MediaCodec 硬编 H.264，输入是 ByteBuffer 还是 Surface？各有什么坑？QCOM/MTK 不同平台 color format 不一致你怎么处理？**

> **Surface 输入**：零拷贝，编码数据来自 GL 渲染输出或 Camera Surface，像素全程在 GPU。坑：不能直接读编码前的像素数据（加密、水印、算法处理需要 YUV 时没法拿），且某些 MTK 平台 Surface 编码会导致颜色偏差（YUV range 不一致）。
>
> **ByteBuffer 输入**：灵活，可以自己填任何格式的 YUV 数据。坑多：① color format 碎片化——QCOM 是 `COLOR_FormatYUV420SemiPlanar`（NV12），MTK 是 `COLOR_FormatYUV420PackedSemiPlanar`（也是 NV12 但 tiled 排布不同），三星是 `COLOR_FormatYUV420Flexible`（YUV 各平面独立，布局包含 stride、sliceHeight 且可能有 padding 或对齐填充）。必须用 `getCodecInfo().getCapabilitiesForType()` 查询 codec 支持的 color format，优先用 `COLOR_FormatSurface`（如果只是编码渲染结果）。② 必须填对 `stride`（= `rowStride`，含 padding，通常大于 width）和 `sliceHeight`（含垂直 padding，通常大于 height），否则编码出来花屏。③ ByteBuffer 是 CPU→GPU 拷贝（通过 OpenMAX IL 的 `use_buffer`），比 Surface 功耗高。
>
> 工程实践：建一个 color format 映射表，每个 SoC 型号一套配置。SDK 启动时 `MediaCodecList` 遍历一次，匹配到 SoC → 选择该 SoC 验证过的 color format + stride 计算方法。

## 三、渲染与低延迟

**Q12：AR 眼镜上，Camera 预览画面要做低延迟上屏，整个链路延迟由哪些环节构成？你从哪几个方向优化？**

> 端到端延迟 = 采集 + 处理 + 渲染 + 显示，逐段拆开：
>
> - **采集（~10-16ms）**：Camera sensor 曝光（取决于光照，暗光长）+ readout（rolling shutter 逐行读出）+ ISP 处理。优化：强制固定曝光时间、降低 sensor 输出分辨率减少 readout 行数。
> - **处理（~2-5ms）**：算法推理（人脸/手势）+ YUV→RGB 转换 + overlay 叠加。优化：算法跑在 GPU/NPU 上而非 CPU、用 shader 做 YUV→RGB 省掉 CPU 转换、overlay 也直接在 shader 里做。
> - **渲染（~1-2ms）**：GPU draw call。优化：减少 render pass 切换、合并 draw call。
> - **显示（~2-8ms）**：从 GPU 提交到屏幕点亮。优化：用 `EGL_ANDROID_presentation_time` 等扩展控制 present 时机、匹配 VSync。
>
> 最容易被忽略的优化：**不要等**。Camera 回调拿到帧后立刻启动渲染，中间不 sleep 不做任何阻塞操作。如果算法处理慢（比如 AI 模型推理要 10ms），单独开线程异步跑，渲染走上一帧的算法结果——宁可要旧结果也不要延迟。

**Q13：OpenGL ES 渲染管线中，YUV→RGB 转换你放哪里做？fragment shader 里做和用 compute shader 做各有什么优劣？**

> **fragment shader 做（标准方案）**：每个 fragment 采样一次 Y 纹理、一次 UV 纹理，做 3×3 矩阵乘法出 RGB。优点是简单、兼容性好（GLES 2.0 就支持）、在常规分辨率下性能足够。缺点是每个 fragment 各跑一遍，4K 屏上就是 8M 个 fragment × 矩阵运算，重复计算。
>
> **compute shader 做**：先把 YUV→RGB 的结果写到一张 output texture（`image2D` 写入），然后渲染时直接采样 RGB 纹理。优点是 RGB 转换只跑一次（和分辨率像素数一致），后续叠加多 pass（滤镜/美颜/文字）可以复用 RGB 纹理。缺点是要求 GLES 3.1+、需要 `glBindImageTexture` 和 `memoryBarrier`，编程复杂度高。
>
> 选型：普通分辨率（≤1080p）用 fragment shader 足够，代码简单，功耗差异可忽略。2K/4K + 多 pass 后处理场景，换 compute shader，把 RGB 转换提前做一次、后面所有 pass 复用。

**Q14：给你一个场景：Camera YUV 帧 → 算法处理（人脸/手势识别）→ 叠加结果 → 渲染上屏。这条管线怎么设计才能同时满足低延迟和高吞吐？**

> 关键思路：**并行流水线，不在关键路径上等。** Camera 帧到达时，同时做两件事：① **立刻渲染**（把上一帧的算法结果叠上去上屏，零等待）；② **异步启动算法**（把当前帧丢给算法线程，不阻塞渲染）。
>
> 具体设计：用一个**三缓冲池**管理 Camera 帧——Camera 回调填 buffer A → 渲染线程读 buffer A 的 OES 纹理直接上屏 → 同时算法线程拿 buffer A 的 YUV 跑推理。算法结果（人脸框/手势坐标）写到一个 `atomic` 保护的 struct 里。下一帧渲染时，读最新的算法结果叠加。这样引擎延迟 = max(渲染一帧, 算法推理) 而非渲染 + 算法。
>
> 如果算法耗时超过一帧（33ms），旧结果仍然可叠加，画面不会卡——最多人脸框滞后 1-2 帧，用户不敏感。但画面延迟始终只有一帧。

**Q15：Vulkan 比 OpenGL ES 在 XR 场景下有什么优势？你在什么场景会从 GL 迁到 Vulkan？**

> Vulkan 三大优势：① **更低 CPU overhead**——显式的 command buffer 预录制 + 多线程提交，draw call 开销比 GL 低一个数量级，XR 场景双屏（左右眼各一）渲染 draw call 翻倍，这个优势直接体现；② **精确的 GPU 调度控制**——fence/semaphore/event 三种同步原语，能精细控制 GPU 内的渲染时序，对 VR/AR 的 ATW（Asynchronous TimeWarp，异步时间扭曲，降低延迟的关键技术）至关重要；③ **显式内存管理**——VkImage/VkBuffer 的内存分配和 aliasing 完全由你控制，能精确控制功耗。
>
> 迁移时机：现有 GL 管线能跑 60fps、延迟可接受——不动。出现以下信号之一就迁：① 需要多线程并行录 command buffer（GL 单线程提交是瓶颈）；② 需要 ATW 做最后时刻的姿态修正（Vulkan 的 `VK_KHR_display_timing` 等扩展天然支持）；③ profile 发现 GL driver 内部 CPU 开销 > 30% 帧时间。
>
> 迁移成本不低（Vulkan 代码量约 GL 的 3-5 倍），所以不是"Vulkan 更高端所以我们用 Vulkan"，而是看具体瓶颈。

## 四、性能与功耗优化

**Q16：AR 眼镜电池小、散热差。音视频 SDK 在功耗上你能做哪些优化？从采集、编码、渲染三个环节分别说。**

> **采集**：降低 sensor 输出分辨率（4K→1080p）和帧率（60fps→30fps），每降一档省 30-40% sensor + ISP 功耗；用 Camera2 的 `setTargetFpsRange` 控制实际帧率；在传感器数据不需要时（用户没在看 AR 内容），降到 10fps 或暂停采集。
>
> **编码**：必须硬编——硬编功耗是软编的 1/5~1/10。Profile 选 baseline（比 main/high 编码复杂度低），关 B 帧（省编码器的 ME 计算量）。如果是有线传输（眼镜连手机），可以不开编码或上 lossless 压缩。按需编码——用户手势/语音触发才编码推流，不用 always-on 编码。
>
> **渲染**：降低渲染分辨率（foveated rendering——人眼中央全分辨率、边缘半分辨率，省 30-50% fragment shader 计算）；合并 render pass，减少 tile memory 的 load/store；不用 `glClear` 每帧全清，用 scissor 清变化区域；省掉不必要的后处理（美颜/bloom 看场景决定开关）。
>
> **系统级**：利用 Android `sustainedPerformanceMode` 和 `thermal` API，温度超阈值主动降级。另外，**CPU 唤醒频率**是暗耗——Camera 回调如果在独立线程高频 poll，即使没帧也在耗电，改成 `SurfaceTexture.setOnFrameAvailableListener` 的事件驱动模型。

**Q17：SDK 上线后用户反馈发热严重，你怎么定位是哪个模块吃电？用什么工具、看什么指标？**

> 三板斧。**第一斧**：`adb shell dumpsys batterystats`——能看出各 App 和各硬件模块（Camera/Codec/GPU/CPU）的功耗估算。如果 Camera 功率异常高，检查 sensor 是否一直开着没关。
>
> **第二斧**：Systrace/Perfetto——抓一段 trace 看 CPU 各线程的 running 时间占比。如果编码线程 80%+ 在运行→编码是高功耗源；如果 GL 线程 `eglSwapBuffers` 占用 50ms+ 每帧→GPU 满载。Perfetto 还能看 GPU frequency 和 utilization 曲线——GPU 一直跑在最高频=渲染功耗饱和。
>
> **第三斧**：高通/MTK 的功耗 profiler——高通的 Snapdragon Profiler 能拆到单个 hardware block 的电流（CPU cluster/GPU/DDR/Camera ISP），一眼看出谁吃电。MTK 有类似 `pwrdump` 工具。
>
> 经验：如果没头绪，先做**排除法**——把 SDK 的编码关掉、只开预览，看功耗降多少；编码关了还热→采集或渲染；编码关了就凉了→编码器问题。逐步缩小范围。

**Q18：编码器用硬编比软编省电，但硬编的码控不如软编精准。你怎么权衡？什么场景硬编、什么场景软编？**

> 硬编省电是压倒性的优势（1/5~1/10 功耗），所以绝大多数场景**优先硬编**。硬编码控不准的主因是不能精细调 QP delta per macroblock——硬编的 rate control 在 DSP/固定硬件管线里，算法简单（通常是 CBR 一刀切）。但工程上这个差异其实被夸大了——只要 `maxrate`/`bufsize` 设得合理，硬编 CBR 在 95% 场景够用。
>
> 需要软编的场景：① **极低码率**（如 <200kbps 1080p）——硬编的简单 RC 算法在这种极限情况会明显劣于 x264/x265 的 lookahead + MB-tree + AQ；② **需要精细控制编码参数**（比如做码率平滑实验、定制 QP map、ROI 编码）；③ **目标平台没有硬编能力**（Linux 桌面用 x86 的 VAAPI 硬编覆盖率不够）。
>
> AR 眼镜上标准答案是：**硬编为主，软编兜底。** SDK 初始化时检测 hardware codec 可用性，有就用硬编；没有就 fallback 到 FFmpeg 内置的 `libx264`/`libx265`（但降帧率/降分辨率以控功耗）。

## 五、XR 场景与算法集成

**Q19：AR 眼镜是 always-on 的 camera，算法团队的人脸/手势/物体识别要实时跑在 camera 流上。SDK 怎么设计管线让算法高效接入？是同步回调还是异步队列？**

> **异步队列 + 回调，不阻塞采集线程。** Camera 帧到达时，SDK 立即把帧放入一个**多消费者队列**——每个算法模块（人脸、手势、物体）从同一份数据各自消费。为什么是多消费者而非逐个串行调？因为算法之间没有依赖时可以全并行跑（人脸和手势可以同时推理），总延迟 = max(所有算法耗时) 而非 sum。
>
> 接口设计：`registerAlgorithm(id, callback, config)` —— SDK 内部维护一个算法注册表，每帧到来时遍历注册表、把帧送入各算法的输入队列。算法处理完通过自己的 callback 返回结果（人脸框、手势类型等），SDK 把结果汇总到一个 `FrameResult` 结构体，渲染线程取最新结果叠加。
>
> 关键细节：① Camera 帧是**只读共享**——多个算法读同一帧不需要拷贝，但算法必须保证不在回调里改数据；② 如果某个算法跑得慢（>33ms），不能让它堵住队列——队列设 max size=1，新帧来了直接替换旧帧（丢帧策略）；③ 算法输入需要不同格式（有的要 RGB、有的要 YUV），SDK 提供 `getFrame(format)` 做按需转换。

**Q20：眼镜上的 IMU 数据（200Hz）和 camera 帧（30fps）时间戳怎么对齐？为什么不能用 `ms`？用哪个 API 拿时间？**

> 时间单位：**`ns` 或至少 `μs`，绝不能用 `ms`。** 200Hz IMU 邻点间隔 5ms，如果用 `ms` 精度（±0.5ms 误差），每次积分的时间增量就有 20% 的不确定性——陀螺仪积分出一帧的旋转角度直接错。
>
> 对齐目标：Camera 帧取**曝光中心时刻**，不是 App 回调时刻（回调天然延迟 1-2 帧）。Android 上 `CaptureResult.SENSOR_TIMESTAMP` 拿曝光开始时间（ns，`BOOTTIME` 时钟域），加上 `SENSOR_EXPOSURE_TIME / 2` 得到曝光中心。IMU（`SensorEvent.timestamp`）是 `elapsedRealtimeNanos` 时钟域——**两者必须统一时钟域**（`BOOTTIME` 和 `elapsedRealtimeNanos` 有固定偏移）。
>
> 对齐方法：帧曝光窗口 `[t_center - exposure/2, t_center + exposure/2]` 内取出全部 IMU 点，对陀螺仪角速度做梯形/Simpson 积分 → 该帧的相机姿态。帧间姿态差分 → 低通/Kalman 滤波分离运镜和抖动 → 反向补偿。
>
> API：Android 统一用 `elapsedRealtimeNanos` 时钟域；iOS 用 `CMTime`（`value/timescale` 表达 ns 精度）。

**Q21：音频也有低延迟要求。Android 上用 AAudio 还是 OpenSL ES？延迟能做到多少？音频和视频怎么同步？**

> **选 AAudio**（Android 8.0+）。原因：AAudio 是 Android 官方低延迟音频 API，内部走 `AAudioStream` 直通 ALSA `fast mixer` 通路，绕过 Java AudioTrack 的层层缓冲。在高通/ Pixel 设备上，AAudio 往返延迟（round-trip latency）能做到 **10-20ms**。OpenSL ES 是更老的 API，虽然也能低延迟但设备适配不如 AAudio 一致，且 Google 已明确推荐 AAudio 替代 OpenSL ES。如果目标有 Android < 8.0 设备，用 OpenSL ES 做 fallback。
>
> A/V 同步：AR 眼镜上**音频和视频一般不需要帧级精确同步**（不像播放器场景）。AR 眼镜的音频大多是系统通知音或语音助手 TTS，不是和画面内容对应的。如果确实需要（比如视频录制），用 PTS 对齐：音频录制时拿 `AudioTimestamp` 里的 `nanoTime`，视频拿 `SENSOR_TIMESTAMP`，统一时钟域后根据 PTS 匹配。播放时 audio clock 做 master，视频按 PTS 对齐音频——因为人耳对音频间断比视频卡顿更敏感。

**Q22：你对 XR 行业的技术趋势怎么看？AR 眼镜的音视频技术栈未来 2-3 年会往哪个方向走？**

> 个人判断几个趋势：
> 1. **VPU（Vision Processing Unit）独立化**：现在 camera→ISP→算法推理基本走 CPU/GPU/NPU 混跑。未来 2-3 年高通 XR2 Gen3/4 会把 VPU 做成独立硬件块——camera raw 数据直接进 VPU、ISP + SLAM + 手势识别全在 VPU 内硬件化，延时降到 <5ms，CPU/GPU 完全不参与 sensor→pose 这条链路。
> 2. **无线分化，编码从 H.264 → H.266(VVC)/AV1**：眼镜和手机/计算盒之间走 Wi-Fi 7（60GHz），带宽够后低延迟编码标准从 H.264/HEVC 迁到 VVC 或 AV1——码率再砍 30%，延迟通过硬件编码 ASIC 压到 <5ms。
> 3. **foveated transport**（注视点传输）：眼镜上的 eye tracking 知道你在看哪里，传视频时只把注视区域高码率、周边低码率——和 foveated rendering 对应，但发生在编码/传输层而非渲染层。
> 4. **pipeline 从 CPU 线控变 GPU graph**：现在 SDK 里的采集→编码→渲染是 CPU 线程调度。未来用 Vulkan Video API + 统一的 GPU compute graph，整个 pipeline 在 GPU 内闭环提交，CPU 只需发一次 signal 启动整条 graph——延迟和功耗再降一档。
> 5. **Android XR 标准化**：Google 推 Android XR 平台（Samsung 头显首发），MediaCodec/Camera2/Audio 会出 XR 专用扩展（如 foveated encoding、low-latency mode），SDK 需要跟踪适配。

## 六、工程综合

**Q23：从零搭这个 SDK，你的工程结构怎么规划？目录怎么分？模块间依赖怎么管？用什么构建系统？**

> 目录结构：
> ```
> XRSDK/
> ├── core/           # 纯 C++ 核心（无平台依赖）：Pipeline、BufferPool、ThreadPool、TimeUtils
> ├── pal/            # Platform Abstraction Layer
> │   ├── android/    #   Camera2Capture, MediaCodecEnc, AAudioCapture, EglRenderer
> │   ├── linux/      #   V4L2Capture, VAAPIEnc, PulseAudio, GLXRenderer
> │   └── windows/    #   MFCapture, MFEnc, WASAPIAudio, WglRenderer
> ├── codec/          # 编解码统一接口（FFmpeg + 硬件 codec 的 wrapper）
> ├── algo/           # 算法集成层（注册/回调/结果汇总）
> ├── bindings/       # 引擎绑定
> │   ├── unity/      #   C# wrapper + Native Plugin 桥接
> │   └── unreal/     #   UE C++ module
> ├── demo/           # 各平台 Demo App
> ├── tests/          # 单元测试 + 集成测试
> ├── scripts/        # 构建脚本、CI 脚本
> └── docs/           # 技术文档
> ```
> 构建系统：**CMake** 做主构建（跨平台一致），Android 上 CMake + NDK + Gradle 打包 AAR，iOS 上 CMake + Xcode project 打包 xcframework，Linux 用 CMake + dpkg/rpm，Windows 用 CMake + vcpkg + NuGet。
>
> 模块依赖：core 层零外部依赖（只依赖 C++17 标准库）；pal 层依赖平台 API（不依赖 core 之外的 SDK 内模块）；codec 层依赖 core + FFmpeg（可选）；algo 层依赖 core；bindings 层依赖 core 的 C API。依赖方向单向：上层依赖下层，禁止反向。

**Q24：SDK 要交付给 Unity/UE 团队用，你怎么做 CI/CD？怎么保证跨平台构建不挂？**

> CI 矩阵：GitHub Actions 或 Jenkins，每个 PR 触发四平台并行 build：
> - **Android**：`ubuntu-latest` runner，NDK + CMake 编译 arm64-v8a + armeabi-v7a，跑 `app/src/androidTest` 的 instrumentation test（真机 farm 或模拟器）
> - **Linux**：`ubuntu-22.04` runner，GCC + Clang 双编译器 build + valgrind 内存检查
> - **Windows**：`windows-2022` runner，MSVC + Clang-CL 双编译器 build
> - **Unity/UE 集成**：单独一个 job，导入 SDK 包到空 Unity/UE 项目，跑 editor play mode test，验证绑定层不 crash
>
> 关键措施：① 每个 PR 必须在四个平台全绿才能合；② `#ifdef` 平台代码强制要求至少有两条平台的编译覆盖（防止"只在 Mac 上改、Windows 挂了没人知道"）；③ release 前跑一轮 **API/ABI 兼容性检查**（Linux `abidw`/`abidiff`），防止改个结构体 layout 导致二进制不兼容。

**Q25：你来写一份这个 SDK 的技术文档，目录结构长什么样？你认为哪几个章节是 Unity 开发者最关心的？**

> 文档目录：
> ```
> 1. 概述（是什么、适用场景、系统要求）
> 2. 快速开始（5 分钟跑通第一个 Demo）
> 3. 架构概览（核心/平台/PAL/绑定层的分层图 + 数据流图）
> 4. 采集（Camera2/V4L2/MMF 的配置、分辨率帧率设置、YUV 格式说明）
> 5. 编码（H.264/H.265 参数表、硬编/软编选择、码控模式对比）
> 6. 渲染（低延迟渲染最佳实践、自定义 shader 接入、Overlay 叠加）
> 7. 算法集成（注册算法、数据格式要求、性能建议）
> 8. Unity 集成指南（★ 导入、初始化、拿帧、GL 线程注意事项）
> 9. Unreal 集成指南（★ C++ module 配置、蓝图暴露、渲染线程同步）
> 10. 功耗优化指南（场景化调优建议、thermal throttling 工作原理）
> 11. 故障排查（常见错误码、日志解读、性能 profiling 方法）
> 12. API 参考（自动生成 Doxygen）
> ```
> Unity 开发者最关心：**第 2 章（快速开始）**——能不能 5 分钟看到画面；**第 8 章（Unity 集成）**——特别是"GL 线程注意事项"那一段，因为 Unity 的渲染线程和 SDK 内部线程的交互是 90% 集成 bug 的来源；**第 11 章（故障排查）**——出错时不用翻源码就能定位；**第 12 章（API 参考）**——IDE 里能跳转到文档。
