## 2. 3 分钟自述版（面试开场）

面试官说"介绍一下你这个项目" → 按下面这段背骨架，但**关键技术点必须真懂**。

### 模板（约 600 字 / 3 分钟）

> **【30 秒：项目定位】**
> "我做了一个 WebRTC 项目，目标是吃透实时通信引擎的核心架构。考虑到 libwebrtc 本身有上百万行代码，我没有从零造轮子，而是**采用 A/B 分层策略**：A 层基于 libwebrtc m120 作为载体，B 层我自己独立重写了两个最能体现 RTC 工程难度的核心模块——**RTP 传输模块**和**视频 Jitter Buffer**。"

> **【60 秒：M4 RTP 模块】**
> "RTP 模块涉及 RFC 3550 和 RFC 6184 两个协议。⚠️ 关键技术点是 **H264 over RTP 的三种打包模式**——小 NALU 用 Single 模式直接装，多个小 NALU 可以聚合成 STAP-A，**大于 MTU 的 NALU 必须用 FU-A 分片**。FU-A 我没有用简单的'总字节除以 MTU'切——那会让最后一片极小、带宽利用率低。我采用的是**均衡分配**：先用向上取整除法算总片数，再用 `平均字节 = ⌈数据字节 / 片数⌉` 算每片大小，让每片都接近 MTU。我用 libwebrtc 的 RtpPacketizerH264 对相同输入跑对照测试，**字节级输出对齐**作为正确性验证。"

> **【60 秒：M6 Jitter Buffer 模块】**
> "Jitter Buffer 更复杂，因为它要同时解决三件事——乱序重排、抗抖估计、帧完整性判定。⚠️ **数据结构上**我用**固定容量 2048 的环形 buffer**，SeqNum 直接取模做索引，O(1) 插入查找；wraparound 用 `(uint16_t)(a-b)` 转 `int16_t` 自然得到带符号距离判断新旧。**抗抖估计**我用了 EWMA 公式，没用 libwebrtc 的 Kalman——代码量 1/10，稳态准确度接近，**主动暴露**这是有意识的工程取舍。**目标延迟**用 3σ 安全裕度，覆盖 99.7% 抖动样本。"

> **【30 秒：简化范围 + 改进方向】**
> "我主动声明简化了几个点：不支持 VP8/VP9/AV1、不实现 SRTP/RTX/Pacer、Jitter Buffer 不做参考帧链分析。这些不是能力问题，是为了控制学习项目的范围——花 1500 行 C++ 把核心算法讲清楚，比把 libwebrtc 复刻一遍更适合面试讲述。下一步打算写 Adapter 把这两个模块接入 libwebrtc 发送链路，做端到端联调。"

## 3. 15 分钟深挖版（追问到底层的脉络）

面试官说"你详细讲讲你的 RTP/JitterBuffer 模块" → 按这个 5 段式展开。

### Part 1: 项目定位与架构选型（2 分钟）

> "做 RTC 学习项目最大的坑是'造轮子'——libwebrtc 上百万行，从零实现根本做不完。所以我**先做项目定位**：A 层用 libwebrtc 当 demo 载体，**B 层挑 1-2 个能讲清楚的核心模块自己写**。挑选标准：① 算法重（能讲深度）；② 代码量 200-500 行（学习项目能 hold 住）；③ 面试高频（投入产出比高）。最终选了 RTP 打包/解包 + 视频 Jitter Buffer。"

⚠️ 追问准备："为什么不挑 ICE 或者拥塞控制？"  
答："ICE 涉及大量网络栈和 STUN/TURN 协议，算法占比小；拥塞控制 GCC 太复杂（卡尔曼 + 延迟梯度 + 速率控制三层），3 周做不完。RTP/JitterBuffer 是数据面最高频的两个模块，性价比最高。"

### Part 2: RTP 模块详解（5 分钟）

#### 2.1 协议层

> "RTP 头 12 字节固定，关键字段：**Marker 标记一帧最后一个包**（接收端帧完整性判定的核心信号）、**SequenceNumber 16 位**（接收端排序 + 丢包检测）、**Timestamp 32 位 + 90kHz 时基**（同一帧所有包共享）、**SSRC 唯一标识一路流**。"

#### 2.2 三种打包模式

> "Single NALU 适合 < MTU 的小 NALU；STAP-A 把多个小 NALU 聚合（典型用法是 SPS+PPS）；**FU-A 是核心**——大于 MTU 的 NALU 必须分片，每片用 FU Indicator（type=28）+ FU Header（S/E 位标识首末）。"

#### 2.3 FU-A 分片算法 ⚠️

> "FU-A 包结构是 `[FU Indicator 1B][FU Header 1B][NALU 数据片]`，所以每片可用载荷 = MTU - 2。原 NALU 头被 FU Header 替代（type 字段保留），可分片数据 = `naluSize - 1`。
>
> **关键算法**：不能用简单除法切！会让最后一片极小。我的做法：
> ```
> totalPieces = ⌈(naluSize - 1) / maxDataPerPiece⌉
> avgBytesPerPiece = ⌈(naluSize - 1) / totalPieces⌉
> ```
> 这样每片都接近 MTU 上限。比如 10000 字节 NALU、MTU=1200，简单除法是 84 片但最后一片只有 400 字节；我的算法是 9 片每片 ~1200 字节。"

⚠️ 追问准备：
- **"FU Indicator 的字节怎么算？"** → `(原NALU头 & 0xE0) | 28`，高 3 位 F+NRI 继承，低 5 位 type=28
- **"S/E 位都为 0 时是什么？"** → 中间片
- **"接收端怎么知道首片？"** → S=1，且重建原 NALU 头：`(FU Indicator & 0xE0) | (FU Header & 0x1F)`

### Part 3: Jitter Buffer 模块详解（5 分钟）

#### 3.1 网络抖动的本质

> "理想网络每 33ms 收一帧，真实网络因为路由排队、WiFi 重传，到达间隔忽快忽慢。直接喂解码器会卡顿。Jitter Buffer 的核心矛盾是**缓冲深度 vs 端到端延迟**——深度越大抗抖越强、延迟越高。"

#### 3.2 帧完整性判定 ⚠️

> "三个条件同时满足：① 所有包 SeqNum 连续；② Marker 包到达；③ 同帧所有包共享 RTP Timestamp。
>
> 但 Marker 包丢了怎么办？libwebrtc 的解法很巧妙——**用'下一帧首包已到达'作为副信号**间接判定本帧已发完。否则丢一个 Marker 就永远卡帧。"

#### 3.3 EWMA 抗抖估计 ⚠️

> "每收到一帧，测一次抖动样本 = `|实际到达间隔 - 期望间隔|`。EWMA 公式：
> ```
> smoothed = (1-α) × smoothed + α × sample    // α=0.05
> ```
> 历史权重 0.95，平滑剧烈波动。
>
> **目标延迟用 3 倍抖动**（3σ 安全裕度）：假设抖动服从正态分布，3σ 覆盖 99.7% 样本，剩下 0.3% 极端抖动用 NACK 重传兜底。**典型数值**：抖动 30ms → TargetDelay ≈ 110ms（含 decode + render 20ms）。"

#### 3.4 环形 Buffer + Wraparound ⚠️

> "用固定容量 2048 的环形 buffer，SeqNum 直接取模做索引——O(1) 插入查找、内存连续 cache 友好。
>
> **wraparound 处理**：SeqNum 是 16 位会回卷。判断'a 比 b 新'用：
> ```
> int16_t signedDelta = (int16_t)(uint16_t)(a - b);
> return signedDelta > 0;
> ```
> `(uint16_t)(a - b)` 算无符号距离，转成 `int16_t` 自然得到带符号距离——65535 - 0 = -1（旧），0 - 65535 = 1（新）。"

### Part 4: 与 libwebrtc 的差异 + 已知简化（2 分钟）

> "**正确性验证**：FU-A 实现做了字节级对齐 ——我喂相同 H264 字节流给 libwebrtc 的 RtpPacketizerH264 和我的实现，输出 RTP 包字节相等（差异 < 1%，主要在 RTP header 的 SSRC/Seq 是调用者注入的）。
>
> **主动简化的点**：
> - **抗抖用 EWMA 不是 Kalman**：突发抖动场景收敛慢 5-10 倍，稳态接近
> - **不做参考帧链分析**：默认所有完整帧可解，由解码器 referenceFrameMissing 回调兜底
> - **不支持 VP8/VP9/AV1**：只 H264
> - **不实现 SRTP/RTX/Pacer**：交给 libwebrtc 上层
> - **单线程假设**：libwebrtc 用 sequence_checker 跨线程同步
>
> 总代码量从 libwebrtc 的 3500+ 行简化到 1500 行，**核心算法路径和 libwebrtc 等价**。"

### Part 5: 改进方向 + 反问准备（1 分钟）

> "下一步：① 写 Adapter 把 B 层模块接入 libwebrtc 发送/接收链路、跑 1v1 通话端到端联调；② 加 NACK 重传逻辑（现在只检测丢包不重传）；③ 性能 benchmark：用 tc/netem 模拟 1%/5% 丢包，对比我的 EWMA 和 libwebrtc Kalman 的 buffer 深度曲线。"

> **反问**："你们团队的 RTC 引擎是基于 libwebrtc 二次开发还是自研栈？拥塞控制用 GCC 还是 BBR？"——这两个问题显示你了解行业、面试官答了你也能接话。

## 4. 10 道高频追问 + 标准答案

### Q1. RTP 头字段你能默写吗？

**口语化标准答案**：12 字节固定头。字节 0：V(2 bit)+P(1)+X(1)+CC(4)；字节 1：M(1)+PT(7)；字节 2-3：Sequence Number 大端；字节 4-7：Timestamp 大端；字节 8-11：SSRC 大端。本项目不支持 CSRC 列表和扩展头，所以 V/P/X/CC 字节固定 0x80。

### Q2. FU-A 的均衡分配算法你能白板写吗？ ⚠️

```cpp
size_t totalPieces = (naluSize - 1 + maxDataPerPiece - 1) / maxDataPerPiece;
size_t avgBytesPerPiece = (naluSize - 1 + totalPieces - 1) / totalPieces;
```

**关键点**：① `naluSize - 1` 因为 NALU 头被 FU Header 替代；② 两次向上取整除法用 `(a + b - 1) / b` 模式避免浮点。

### Q3. 接收端怎么从 FU-A 分片重建原 NALU 头？ ⚠️

```cpp
restoredNaluHeader = (fuIndicator & 0xE0) | (fuHeader & 0x1F);
```

高 3 位 F+NRI 来自 FU Indicator，低 5 位 type 来自 FU Header。

### Q4. Marker 包丢了怎么判定帧完整？

**口语化标准答案**：用"下一帧首包已到达"作为副信号——如果下一帧的 isFrameFirstPacket=true 的包已经在 buffer 里，说明本帧网络层已发完，丢的就是 Marker 包本身，等不到的。这时直接基于"首包到下一帧首包前一个 SeqNum"判定本帧范围。我的实现在 `PacketBuffer::ExtractCompletedFrames` 的 fallback 逻辑里，找不到当前 nextSequenceToCheck_ 的首包时，自动前进到下一个 isFrameFirstPacket=true 的位置。

### Q5. SeqNum wraparound 怎么判断新旧？ ⚠️

```cpp
bool IsNewerSequenceNumber(uint16_t a, uint16_t b) {
    int16_t signedDelta = (int16_t)(uint16_t)(a - b);
    return signedDelta > 0;
}
```

**举例**：a=0, b=65535 → `(uint16_t)(0 - 65535) = 1` → `(int16_t)1 = 1 > 0` → 0 比 65535 新（正确，0 是 wraparound 后的新值）。

### Q6. EWMA 系数怎么选的？为什么是 0.05？

**口语化标准答案**：α=0.05 表示历史权重 95%、新样本权重 5%，对应的"等效平均窗口"约 1/α = 20 帧（30fps 下约 0.67 秒）。**比 libwebrtc 的 Kalman 慢**——Kalman 的卡尔曼增益是动态的，突发抖动时增益高（快速跟踪），稳态时增益低（信任历史）。我用固定 α 是简化选择，**稳态准确度接近、突发响应慢 5-10 倍**。生产环境如果有突发场景需求应该上 Kalman。

### Q7. 为什么目标延迟是 3 倍抖动？

**口语化标准答案**：3σ 是统计学经验值——假设抖动服从正态分布，3σ 覆盖 99.7% 样本，剩下 0.3% 极端值用 NACK 重传兜底。**不是绝对要 3**：实际项目可以根据业务定，要求低延迟可以 2σ（87%覆盖），要求稳定可以 4σ（99.99%）。libwebrtc 用 3σ + RTT 倍数做 NACK 余地，本项目简化只用 3σ。

### Q8. 检测到丢包后立刻发 NACK 还是等？

**口语化标准答案**：**等一个 RTT 再发**（典型 50-200ms）。原因：① 大部分 SeqNum 缺失其实是**乱序到达**，等一下可能自然到；② 批量发节省 RTCP 头开销。本项目的 PacketBuffer 只**检测**丢包并通过 observer 回调上报，**真正等多久发 NACK 由独立的 NACK 模块决定**。

### Q9. 什么时候请求关键帧（IDR）？

**口语化标准答案**：三个触发源——① **连续丢包事件超阈值**（本项目设 10 次，源码在 `JitterBufferImpl::InsertPacket`）；② 解码器报"参考帧丢失"；③ 应用层主动请求（首次连接、网络恢复）。**关键帧到达后重置计数器**——视为网络恢复信号。**触发要严苛**：关键帧体积是 P 帧的 5-10 倍，滥发浪费带宽。

### Q10. 你的项目相比 libwebrtc 简化了什么？为什么这些可以简化？

**口语化标准答案**：见上面"Part 4"的简化清单。**关键观点**：所有简化都不是因为做不到，是为了**控制学习项目的范围 + 让面试讲述清晰**——花 1500 行 C++ 把核心算法讲清楚比复刻 libwebrtc 更适合面试。每一项简化的代价我都明确知道：EWMA → 突发慢、不做参考帧链 → 解码器兜底、不支持 VP8 → 只覆盖一种编码。如果让我加回去，工期 +2-3 周即可。

## 5. 白板题预案

面试官可能让你白板写以下三个之一：

### 白板题 1：FU-A 分片函数 ⚠️

```cpp
// 给定 NALU 字节数和 MTU，返回每片的字节区间 [start, end)
struct FuAPiece {
    size_t startOffset;
    size_t endOffset;
    bool isFirst;
    bool isLast;
};

std::vector<FuAPiece> ComputeFuAPieces(size_t naluSize, size_t maxPayloadBytes) {
    constexpr size_t kFuOverhead = 2;
    size_t maxDataPerPiece = maxPayloadBytes - kFuOverhead;
    size_t fragmentableBytes = naluSize - 1;
    size_t totalPieces =
        (fragmentableBytes + maxDataPerPiece - 1) / maxDataPerPiece;
    size_t avgBytesPerPiece =
        (fragmentableBytes + totalPieces - 1) / totalPieces;

    std::vector<FuAPiece> pieces;
    size_t cursor = 1;  // 跳过原 NALU 头
    for (size_t pieceIndex = 0; pieceIndex < totalPieces; ++pieceIndex) {
        FuAPiece piece;
        piece.startOffset = cursor;
        piece.endOffset = std::min(cursor + avgBytesPerPiece, naluSize);
        piece.isFirst = (pieceIndex == 0);
        piece.isLast = (pieceIndex == totalPieces - 1);
        pieces.push_back(piece);
        cursor = piece.endOffset;
    }
    return pieces;
}
```

**画图辅助**：在白板上画一个 100KB 的 NALU 矩形，MTU 线分割，标 S=1 在首片、E=1 在尾片。

### 白板题 2：RTP 头序列化

```cpp
size_t WriteRtpHeader(uint8_t* buffer, uint16_t seq, uint32_t ts, uint32_t ssrc,
                     bool marker, uint8_t pt) {
    buffer[0] = (2 << 6);                              // V=2, P=0, X=0, CC=0
    buffer[1] = (marker ? 0x80 : 0x00) | (pt & 0x7F);  // M, PT
    buffer[2] = (seq >> 8) & 0xFF;                     // Seq 高字节
    buffer[3] = seq & 0xFF;                            // Seq 低字节
    buffer[4] = (ts >> 24) & 0xFF;                     // Ts 大端
    buffer[5] = (ts >> 16) & 0xFF;
    buffer[6] = (ts >> 8) & 0xFF;
    buffer[7] = ts & 0xFF;
    buffer[8] = (ssrc >> 24) & 0xFF;                   // SSRC 大端
    buffer[9] = (ssrc >> 16) & 0xFF;
    buffer[10] = (ssrc >> 8) & 0xFF;
    buffer[11] = ssrc & 0xFF;
    return 12;
}
```

**坑点**：忘记 `& 0xFF` 截断（在 ARM 等平台可能没事，但写规范代码必须加）。

### 白板题 3：画环形 buffer 数据结构

```
        SeqNum mod 2048 = slot index
        ┌──────────────────────────────┐
slot:   │ 0 │ 1 │ 2 │ ... │ 2046 │ 2047│
        └─┬─┴─┬─┴─┬─┴─────┴──┬───┴──┬──┘
          ▼   ▼   ▼          ▼      ▼
        occu? Packet (seq/ts/payload)
        
SeqNum=100 → slot 100
SeqNum=2148 → slot 100 (覆盖)
        
wraparound 判断: int16_t((uint16_t)(a-b)) > 0
```

**画完后说**：① O(1) 插入；② 自然有界容量；③ wraparound 用 16 位符号距离判断。

## 7. 可能被挖的坑 + 防御策略

| 坑 | 面试官原话举例 | 防御策略 |
|----|---------|---------|
| **怀疑你抄代码** | "这个均衡分配算法看着不像新手写得出来，是不是抄 libwebrtc 的？" | **坦诚**："我参考了 libwebrtc 的 `RtpPacketizerH264::PacketizeFuA`，源码在 `modules/rtp_rtcp/source/rtp_format_h264.cc`。我的实现简化了一些边界处理，但核心思路一致。面试项目我不打算假装是原创"。 |
| **追问 EWMA 系数怎么定** | "α=0.05 这个值你怎么选的？" | **坦诚**："这是我参考 libwebrtc 默认配置选的，没有自己做调参实验。生产环境应该根据网络场景做 A/B 测试" |
| **追问线程安全** | "你的代码多线程怎么办？" | **坦诚**："本实现是单线程假设。libwebrtc 用 `sequence_checker` 做线程亲和性检查。要支持多线程我会在 InsertPacket 和 PopNextCompletedFrame 之间加 mutex，或者用 lock-free 队列" |
| **追问拥塞控制** | "你怎么和拥塞控制对接？" | **承认范围**："本项目没实现拥塞控制（GCC/BBR 太复杂）。但我读过 libwebrtc 的 `goog_cc.cc`，知道核心是**延迟梯度卡尔曼 + 丢包率**双路联合估计带宽。我的 Jitter Buffer 通过 observer 暴露丢包率，可以作为 BWE 的输入" |
| **追问参考帧链** | "你的 JitterBuffer 怎么处理 B 帧依赖？" | **承认简化**："本实现不做参考帧链分析，默认所有完整帧可解。libwebrtc 的 `FrameBuffer` 维护参考帧 DAG，B 帧依赖的 P/I 帧没到就暂存。我的简化代价是 B 帧场景可能渲染卡顿——但实时通信通常禁 B 帧（关 B 帧 = 关延迟）" |
| **追问 RTCP 反馈** | "你的接收端怎么发 NACK / RR？" | **承认范围**："本项目只做检测、不发反馈。检测到丢包用 observer 回调上报给假想的 NACK 模块。真实生产要发 RTCP NACK（RFC 4585）和 RTCP RR（接收报告），我没实现这一层" |
| **挑数据结构** | "环形 buffer 容量 2048 你怎么选的？" | "30fps × 2 秒缓冲 × 每帧 30 包 = 1800，向上取 2048 是 2 的幂便于取模。生产环境应根据帧率和最大缓冲深度算" |
