## 1. 全景：四个技术解决四个不同问题

### 1.1 问题的本质

一条跨国 WebRTC 通话链路上会发生四件事：

| 发生什么 | 表面上看到的 | 根源 | 由谁来管 |
| :--- | :--- | :--- | :--- |
| 路由器队列积压 | 包的端到端延迟越来越高 | 发送太快，瓶颈吞不下 | **GCC** 降码率 |
| 包在网络中途丢了 | seq 5 直接被黑洞吞了 | 无线干扰 / 队列溢出 | **FEC** 本地恢复 或 **NACK** 请求重传 |
| 包到达忽快忽慢 | 间隔 33ms → 5ms → 80ms → 15ms | 路由器排队不均衡、多路径 | **JitterBuffer** 吸收 |
| 包到达顺序错乱 | seq=1,3,2,5,4 | 多路径路由 | **JitterBuffer** 排序 |

**核心洞察**：这四个问题相互耦合——码率太高导致丢包（GCC 和 FEC/NACK 的交互），重传增加延迟进一步干扰抗抖估计（NACK 和 JitterBuffer 的交互），但四个机制各有独立的责任域。

### 1.2 四驾马车的分工（物流类比）

把 WebRTC 传输比作**一条不稳定的跨国物流快递线**：

```
┌─────────────────────────────────────────────────────────────────────┐
│                         发送端                                       │
│                                                                     │
│  [Camera] → [Encoder] → [RTP Packetizer] → [Pacer] → [Network]     │
│                              │                  ▲                   │
│                              │                  │                   │
│                      ┌───────┴───────┐   ┌──────┴──────────┐       │
│                      │  FEC Encoder  │   │  GCC Controller  │       │
│                      │ (发前加冗余)    │   │ (收RTCP反馈调码率) │       │
│                      └───────────────┘   └─────────────────┘       │
│                                                                     │
│                      ┌─────────────────┐                           │
│                      │ RtpPacketHistory │ ← NACK 重传从这里取       │
│                      └─────────────────┘                           │
└─────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼ 网络
                                    │
┌─────────────────────────────────────────────────────────────────────┐
│                         接收端                                       │
│                                                                     │
│  [Network] → [FEC Decoder] → [NACK Check] → [JitterBuffer] → [Decoder] → [Renderer]
│                  │               │               │                   │
│                  │               │               │                   │
│           本地解方程恢复      缺包发NACK      排好序、匀速吐帧          │
│           (零延迟)          (有延迟)         (时刻在工作)              │
│                                                                     │
│                              ┌──────────────────┐                   │
│                              │  RTCP Reporter   │ ← 打包丢包率、延迟  │
│                              └──────────────────┘   发给发送端GCC     │
└─────────────────────────────────────────────────────────────────────┘
```

**一句话总结四个角色**：

| 技术 | 问题 | 方案 | 代价 |
| :--- | :--- | :--- | :--- |
| **GCC** | 发太快堵了 | 估带宽 → 调编码器码率 | 画面变糊（但保住流畅） |
| **FEC** | 丢了包不想等重传 | 发冗余包 → 本地算回来 | 吃额外带宽 |
| **NACK** | FEC 修不好，必须补 | 发"缺 seq=X"请求 → 发送端重传 | 增加 1 RTT 延迟 |
| **JitterBuffer** | 到了但乱序/忽快忽慢 | 缓冲 N ms → 排序 → 匀速吐 | 增加端到端延迟 |

## 2. GCC：拥塞控制（主动预防堵车）

### 2.1 核心问题

**发送端每秒该发多少比特？** 发太快 → 路由器队列爆炸 → 延迟飙升 + 丢包；发太慢 → 带宽浪费 → 画面糊成马赛克。

GCC 的目标：**找到瓶颈带宽的"甜点"——刚好用满链路、不排队**。

### 2.2 双控制器架构

GCC 有两个独立运行的控制器，取**二者中的较小值**作为最终目标码率：

```
                        ┌──────────────────────┐
  接收端 RTCP 反馈 ────▶│ DelayBasedController │────▶ estimated_bitrate_delay
  (到达时间梯度)         │ (Trendline 趋势线)    │
                        └──────────────────────┘
                                                     │
                                              min(二者) ──▶ 最终目标码率
                                                     │
                        ┌──────────────────────┐     │
  接收端 RTCP 反馈 ────▶│ LossBasedController  │────▶ estimated_bitrate_loss
  (丢包率)               │ (AIMD 加性增乘性减)   │
                        └──────────────────────┘
```

#### 控制器 1：Delay-Based（趋势线估计 Trendline）

**核心思想**：延迟上升往往是拥塞的**早期信号**——路由器队列开始积压时，包还没丢，但到达间隔会越来越长。这个信号比丢包**早出现 ~200-500ms**。

**算法流程**：

```
1. 每个包到达时记录 (发送时间, 到达时间)
2. 每收到一个 transport-wide CC 反馈包，拿到一批 (send_time, recv_time) 对
3. 按发送时间排序，对每个 5ms 时间窗口内的包：
     delta_delay = arrival_delta - send_delta
   （如果 delta_delay > 0，说明网络延迟在增大 = 队列在涨）
4. 对最近 20 个窗口的 delta_delay 做线性回归，算斜率 = Trendline
5. 把 Trendline（ms/ms 斜率）映射到码率变化：
   - Trendline > 阈值（延迟在涨）→ overuse → 降码率
   - Trendline < 阈值（延迟在降）→ underuse → 涨码率
   - 阈值之间 → normal → 保持
```

**线性回归（最小二乘法）**：

```
给定最近 N 个数据点: (x_i, y_i)，其中：
  x_i = 包的累积发送时间
  y_i = 包的累积到达延迟（arrival - send）

斜率 = Σ((x_i - x̄)(y_i - ȳ)) / Σ((x_i - x̄)²)

斜率 >  threshold → overuse  (网络队列在涨，→ 降码率)
斜率 < -threshold → underuse (网络队列在消，→ 升码率)
|斜率| ≤ threshold → normal   (稳定，→ 保持)
```

**阈值**不是固定的——它是**自适应**的。GCC 维护一个动态阈值 `k_delta`，当 overuse 被触发后阈值会变大（容忍更宽的波动），underuse 连续发生时阈值会变小（更敏感地探测可用的额外带宽）。

#### 控制器 2：Loss-Based（丢包率）

**核心思想**：如果 Trendline 漏掉了（延迟信号太微弱），丢包率也会发出信号——但丢包已经是"拥塞发生后"的滞后信号了。

**AIMD 算法**：

```
丢包率 < 2%:  Additive Increase  — 每次 + ~8% 当前码率（AIMD 的 I 阶段，探路）
丢包率 2-10%: 保持当前码率（容忍区）
丢包率 > 10%: Multiplicative Decrease — 码率 × 0.5（AIMD 的 M 阶段，急刹车）
```

**为什么 WebRTC 用 2% / 10% 这两个阈值？** 2% 以下可能是随机丢包（无线干扰），不是拥塞；10% 以上几乎肯定是拥塞导致的队列溢出。

### 2.3 码率怎么变成视频质量？

GCC 输出的是一个**比特率数字**（如 2.5 Mbps），然后通过三条路径生效：

```
GCC 输出: 2500 kbps
    │
    ├──▶ [Encoder Rate Controller] → 调 QP（量化参数）
    │     码率不够 → QP 上调 → 量化更粗 → 画面变糊但码率达标
    │     码率充裕 → QP 下调 → 画面清晰
    │
    ├──▶ [Pacer] → 控制发包节奏
    │     2.5 Mbps, 每包平均 1200 字节 → 每 3.84ms 发一包
    │     （避免瞬时突发打爆路由器缓冲区）
    │
    └──▶ [FEC Controller] → 决定冗余率
         码率够 → 多加点 FEC 冗余
         码率紧 → 减 FEC 冗余（甚至关掉）
```

### 2.4 Transport-Wide CC（TWCC）

GCC 需要知道每个包**发送和接收的精确时间**。传统 RTCP SR/RR 只能反馈聚合统计（丢包率、jitter），粒度太粗。**TWCC（Transport-Wide Congestion Control）** 解决了这个问题。

**工作原理**：


发送端: 每发一个 RTP 包，给包打上一个递增的 transport_sequence_number
        （不是 RTP Sequence Number！是专门用于拥塞控制的另一个序列号）

接收端: 每隔 ~100ms 打包一个 RTCP Transport-FB 消息发给发送端：
        [
          base_sequence_number: 1000,     // 这批包的第一个 transport_seq
          packet_status_count: 20,         // 这批包有 20 个
          delta_tick × 20: [3, 5, 4, -1, 0, ...]  // 每包到达间隔（250μs 单位）
        ]
        接收端只反馈到达时间差，不反馈绝对时间戳（更省带宽）

> **250μs 是什么，为什么要除？** 这是 TWCC 协议对到达间隔的**编码单位**，不是算法概念。
>
> 接收端用 `clock_gettime()` 之类的高精度函数拿到了微秒（甚至纳秒）级的到达间隔。但反馈消息的 `delta` 字段是 **16 位有符号整数**（`int16_t`），如果直接存微秒，最大只能表示 ±32.767ms——一个音频帧间隔 20ms 加上 15ms 抖动就爆了。
>
> 所以协议设计者选了一个折中编码单位：**250μs**（即 0.25ms）。编码时 `delta_tick = arrival_delta_us / 250`，解码时 `arrival_delta_us = delta_tick × 250`。
>
> | 候选单位 | 16 位范围 | 精度 | 评价 |
> | :--- | :--- | :--- | :--- |
> | 1μs | ±32.8ms | 极高 | 范围太小，一帧视频间隔 33ms 就溢出 |
> | 125μs | ±4.1s | 很高 | 精度过剩 |
> | **250μs** | **±8.2s** | **1/4 ms，够用** | **甜点——范围远超任何正常包间隔，也足以捕捉亚毫秒级抖动** |
> | 1ms | ±32.8s | 粗 | 1ms 以下抖动完全看不见 |
>
> **一句话**：250μs 就是 TWCC 协议对到达间隔的"压缩编码系数"——和 YUV 420 代替 RGB 一个道理，用可接受的精度损失换传输效率。±125μs 的量化误差远小于几十 ms 的网络抖动，不影响 Trendline。

发送端: 收到 TWCC 反馈 → 重建每个包的 (send_time, recv_time) 对 → 喂给 Trendline


**关键设计**：TWCC 把反馈放在了**接收端**，由接收端的 RTP 扩展头解析到达时间再打包回报。这让发送端能做**全局优化**——一个发送端可能给多个接收端发流，每个接收端独立反馈 TWCC，发送端按最差的链路决定码率。

#### 2.4.1 时钟同步问题：为什么发送端和接收端不需要 NTP 对时？

这是 TWCC 最精妙的设计点，也是面试中拉开分差的问题。问题的出发点是：

> "发送时间用发送端的钟，到达时间用接收端的钟——两台电脑的时钟显然不一致，算出来的 '延迟' 不就毫无意义吗？"

**答案：GCC 根本不算绝对延迟。它算的是延迟的"变化趋势"（Trendline），而趋势对时钟偏移是天然免疫的。**

#### 第一步：接收端只反馈增量，不反馈绝对时间

```
发送端: 用自己的钟记录每个包的发包时刻 send_time[i]

接收端: 用自己的钟记录每个包的收包时刻 recv_time[i]
        但是——接收端不回报 recv_time[i] 的绝对值。
        它只回报"相邻两个包的到达间隔"：

        delta_ticks[i] = (recv_time[i] - recv_time[i-1]) / 250μs

        反馈消息里是: [base_seq=1000, delta: +3, +5, +4, -1, 0, +2, ...]
        （每个 delta 是在接收端同一台钟上测的，完全自洽）
```

**核心**: delta_ticks 全部在**同一台机器**（接收端）上测量，不涉及跨机时钟比较。

#### 第二步：为什么发送端需要"重建"接收时间线？

接收端只告诉发送端**包与包之间的间隔**（delta），没告诉发送端**第一个包什么时候到的**。但 Trendline 要做线性回归，需要的是**具体的 (x, y) 数据点**，不能只有增量——你得先有数值，才能画散点图、算斜率。

所以发送端必须把接收端给的"增量序列"还原成"绝对值序列"。问题是：**起始值不知道**——接收端没说"第一个包是 12:00:00.123456 收到的"。

**发送端的做法**：随便猜一个起始值。比如直接把第一个包的**发送时间**当作它的**到达时间**——这个猜测显然不准确（真实的到达时间比发送时间晚了几十毫秒），但关键在下一步。

#### 第三步：带着数字走一遍——锚点偏置为什么不影响斜率

**场景设定**：
- 发送端在 t=0ms、5ms、10ms 发出 3 个包
- 真实网络中，这 3 个包分别在 t=50ms、56ms、61ms 到达（网络基础延迟 50ms）
- 接收端的钟和发送端**没有任何同步**，但接收端精准记录了自己收到每个包的时刻

**接收端反馈给发送端的内容**（250μs 单位，即 1 tick = 0.25ms）：

```
包 seq=0:  发送端在 0ms 发出,  接收端在 50ms 收到
包 seq=1:  发送端在 5ms 发出,  接收端在 56ms 收到  → 距上一包: (56-50)/0.25 = 24 tick
包 seq=2:  发送端在 10ms 发出, 接收端在 61ms 收到  → 距上一包: (61-56)/0.25 = 20 tick

反馈消息: base_seq=0, deltas = [+24, +20]
```

注意：反馈里**完全没有"50ms"这个信息**——接收端不回报绝对时间。

**发送端收到反馈后，重建到达时间线**（随便猜锚点 = 发送时间）：

```
发送端的钟上已经记录了:
  send_time[0] = 0ms
  send_time[1] = 5ms
  send_time[2] = 10ms

发送端用 deltas 重建 recv_time（以 send_time[0] = 0ms 为锚点）:
  recv_time[0] = 0ms                          ← 猜的（实际应该是 50ms）
  recv_time[1] = 0ms + 24 × 0.25ms = 6ms     ← 用 delta 累加
  recv_time[2] = 6ms + 20 × 0.25ms = 11ms    ← 用 delta 累加
```

现在发送端手上有了两套数据：

| seq | send_time | recv_time（重建版） | recv_time（真实版，发送端不知道） |
| :--- | :--- | :--- | :--- |
| 0 | 0ms | 0ms | 50ms |
| 1 | 5ms | 6ms | 56ms |
| 2 | 10ms | 11ms | 61ms |

重建版和真实版**整体差了 50ms**（锚点猜错了），但**相邻包的间隔完全正确**——这就是"只丢了零点、没丢形状"。

**进入 Trendline 线性回归**。把 (send_time, recv_time) 当作散点图，算斜率：

```
用重建版（锚点 = 0ms）:
  数据点: (0, 0), (5, 6), (10, 11)

  x̄ = (0+5+10)/3 = 5
  ȳ = (0+6+11)/3 ≈ 5.67

  斜率分子 = (0-5)(0-5.67) + (5-5)(6-5.67) + (10-5)(11-5.67)
           = (-5)×(-5.67) + 0 + 5×5.33
           = 28.35 + 26.65 = 55
  分母    = (-5)² + 0² + 5² = 50
  斜率    = 55/50 = 1.1 ms/ms  ← 意味着每过 1ms，延迟增加 1.1ms（队列在涨！）

用真实版（锚点 = 50ms）:
  数据点: (0, 50), (5, 56), (10, 61)

  x̄ = 5, ȳ ≈ 55.67

  斜率分子 = (-5)(50-55.67) + 0 + (5)(61-55.67)
           = (-5)×(-5.67) + 5×5.33
           = 28.35 + 26.65 = 55
  分母    = 50
  斜率    = 55/50 = 1.1 ms/ms  ← 完全一样！
```

**两种锚点算出的斜率一模一样**。原因：锚点偏置（0ms vs 50ms）把散点图上所有点**整体向上平移了 50ms**，平移改变了截距（直线在 y 轴上的位置），但不改变斜率（直线本身的倾斜程度）。线性回归的斜率公式中，`y_i - ȳ` 把每个点的 y 减去均值——同样是整体平移 50ms，均值也平移了 50ms，做差时消去了。

> **直观理解**：把一张散点图打印在纸上，然后把纸往上挪 5 厘米——纸上那条趋势线的**倾斜程度**不会变，变的是它在纸上的绝对位置。GCC 只看倾斜程度。

这就是为什么 TWCC 不需要 NTP 对时的核心原因：**锚点猜错了只引入一个常量偏置，而线性回归的斜率对常量偏置是数学上免疫的。**

#### 还有问题：时钟漂移怎么办？

上面讲的是**常量偏移**（两台钟差固定值 Δ），做差时消掉了。但还有一个更微妙的场景：**时钟漂移**（clock drift）——两台机器的晶振**频率不同**，一台钟走得比另一台快。这和常量偏移是**本质不同的两个问题**，需要分开分析。

#### 时钟漂移和常量偏移的本质区别

```
常量偏移（钟差 10ms）:
  发送端时间线:  0ms ─── 5ms ─── 10ms ─── 15ms ───→
  接收端时间线: 10ms ─── 15ms ─── 20ms ─── 25ms ───→  ← 整体平移 10ms
  每次 delta = 5ms，和发送端完全一致。Δ 在做差时自动消去了。
  → 斜率不受影响。✓

时钟漂移（接收端快 50 ppm = 0.005%）:
  发送端时间线:  0ms ─── 5ms ─── 10ms ─── 15ms ───→  每次间隔 5ms
  接收端时间线:  0ms ─── 5.00025ms ─── 10.0005ms ─── 15.00075ms ───→  每次间隔 5.00025ms
                ↑ 注意：每个间隔多了 0.00025ms（不是加常量，是乘 1.00005）
  这是比例缩放，不是平移。
  → 斜率会受影响！✗（后面解释为什么影响小到可以忽略）
```

**数学上**：常量偏移是 `y' = y + Δ`（加性），时钟漂移是 `y' = y × (1 + ε)`（乘性）。做差时：

```
常量偏移:  (y[i] + Δ) - (y[i-1] + Δ) = y[i] - y[i-1]        ← Δ 完全消掉 ✓
时钟漂移:  y[i]×(1+ε) - y[i-1]×(1+ε) = (y[i]-y[i-1])×(1+ε)  ← ε 不会消掉！
```

**arrival_delta 被整体放大了 (1+ε) 倍。** 如果 ε = 50 ppm，每个 arrival_delta 都多了 0.005%。这不是截距问题——这是斜率问题，线性回归**不能**对它免疫。

#### 那为什么 TWCC 不受影响？——量化之后才知道

关键不是"它不影响"，而是**影响量太小，淹没在噪声里**。做一下量化：

**时钟漂移有多大？**

```
典型消费电子晶振精度: ±20 ~ ±50 ppm（百万分之一）
  ppm = parts per million

  10 ppm = 每秒偏 10μs
  50 ppm = 每秒偏 50μs = 每 20ms（一帧音频）偏 1μs

最差情况：发送端 -50ppm，接收端 +50ppm → 相对漂移 100ppm
  每秒偏差 = 100μs
```

**Trendline 工作的窗口有多大？**

```
GCC Trendline 看最近 20 个时间窗口，每个窗口 5ms
  总时间跨度 = 20 × 5ms = 100ms
```

**在这 100ms 内，时钟漂移累积了多少？**

```
100ppm 相对漂移 × 100ms 窗口 = 100 × 10⁻⁶ × 100ms = 0.01ms = 10μs

这 10μs 分布在 20 个窗口上，斜率贡献 = 10μs / 100ms = 0.0001 ms/ms
```

#### 和真实的拥塞信号对比

```
场景                          | arrival_delta - send_delta 的趋势斜率
──────────────────────────────┼─────────────────────────────────────
100ppm 时钟漂移（纯粹）        | ~0.0001 ms/ms
轻微拥塞（队列缓慢增长）         | ~0.001-0.005 ms/ms
明显拥塞（队列较快增长）         | ~0.01-0.05 ms/ms
严重拥塞（队列快速积压）         | ~0.1-1.0 ms/ms
GCC overuse 判定阈值（典型值）  | ~0.005-0.03 ms/ms
```

**时钟漂移产生的假斜率比 overuse 阈值低了 50-300 倍**。换句话说，Trendline 看到 0.0001 ms/ms 的斜率——这相当于"每过 1 秒，延迟增加 0.1ms"，拥塞状态的标杆是"每秒增加几十到几百 ms"。时钟漂移的信号强度连阈值的 1% 都不到，直接被当成噪声滤掉了。

#### 什么时候时钟漂移会成为问题？

只有在极端条件下才可能出问题：

| 条件 | 正常值 | 出问题的极端值 |
| :--- | :--- | :--- |
| 晶振精度 | 20-50 ppm | >500 ppm（廉价 IoT 芯片） |
| Trendline 窗口 | 100ms（20×5ms） | >1s（如果调大窗口参数） |
| 网络状况 | 有正常抖动（几十 ms） | 极其稳定（抖动 <1ms，漂移成为唯一信号源） |

**三者叠加**时——比如一个 500ppm 的廉价 IoT 芯片 + 被调大到 2s 的 Trendline 窗口 + 局域网极低抖动——漂移累积可能达到 `500×10⁻⁶ × 2s = 1ms`，足以被误判为轻度拥塞。但在 WebRTC 的典型配置（<100ppm 晶振 + 100ms 窗口 + 互联网抖动几十 ms）下，时钟漂移根本不是问题源。

#### 为什么 WebRTC 不显式修正它？

因为修正的代价大于收益。要修正时钟漂移，需要在发送端和接收端之间做**双向时间同步**（比如类似 NTP 的四次握手），然后估计两端的频率比——这引入了额外复杂度和 RTT 开销。而当前的 100ms Trendline 窗口已经让漂移的影响降到**远小于信号噪声**的程度。

**总结**：

| 时钟不一致类型 | 数学形态 | 对斜率的影响 | 如何应对 |
| :--- | :--- | :--- | :--- |
| **绝对偏移**（钟差 Δ） | `y' = y + Δ` | **零**——做差消去 | 不需要处理 |
| **时钟漂移**（频率差 ε） | `y' = y × (1+ε)` | **非零**，但量级 ~0.0001 ms/ms | **短窗口（100ms）+ 动态阈值 + 晶振精度天然有上限 = 信号远小于噪声** |
| **时钟跳变**（NTP 拨钟） | 单点 spike | 被当离群值 | Trendline 对单点噪声鲁棒 |

> **面试金句**："时钟漂移和常量偏移是完全不同的两件事。常量偏移在做差时自动消去，数学上确定不移。时钟漂移——两台机器的晶振频率不同——做差消不掉，它会导致 arrival_delta 等比缩放。但工程上的关键是量级：100ppm 的晶振偏差在 Trendline 的 100ms 窗口内只累积了 10μs，而拥塞信号是毫秒级。**信号比噪声大几百倍，时钟漂移直接被淹没了**。如果面试官追问'那极端情况呢'——500ppm 的廉价芯片 + 超长窗口 + 极低抖动的局域网，理论上可能误判，但 WebRTC 的默认配置已经把这种概率压到了事实上的零。"

## 3. FEC：前向纠错（用冗余换零延迟恢复）

### 3.1 核心问题

**丢了包、但等不了 NACK 重传（1 RTT 太慢），怎么办？**

FEC 的思路是：**发送端在发原始数据的同时，额外发一些"冗余数据"。如果丢了几个原始包，接收端可以用"原始包中幸存下来的 + 冗余数据"做运算，在本地直接算出丢失的原始包**。全程零往返延迟——不需要等待发送端重传。

代价是**额外的带宽**——冗余数据也要占字节。所以 FEC 本质上是用**带宽换时间**。

### 3.2 从生活例子理解：RAID 5 的奇偶校验

如果你接触过 RAID 存储，FEC 的 XOR 模式和 RAID 5 的原理完全一样：

```
磁盘 1:    [数据块 A]
磁盘 2:    [数据块 B]
磁盘 3:    [奇偶校验块 P = A ⊕ B]    ← 就是 FEC 包

任意一个磁盘坏了，用剩下两个做 XOR 就能恢复丢失的那块:
  磁盘 1 坏了 → A = B ⊕ P 恢复
  磁盘 2 坏了 → B = A ⊕ P 恢复
  磁盘 3 坏了 → 不需要恢复（P 只是校验，丢了无所谓）
```

FEC 就是把 RAID 5 的思想从磁盘搬到了网络包上。

### 3.3 XOR FEC：最基础的实现

#### 3.3.1 编码过程——发两个包，带一个备件

假设编码器输出了一帧视频，RTP Packetizer 把它切成了 **2 个 RTP 包**（实际场景会有几十个，这里用 2 个方便理解）：

```
包 A: [80, 60, 01, 02,  FF, D8, 00, 10, ...]  共 200 字节
包 B: [80, 60, 01, 03,  7C, 85, AB, CD, ...]  共 200 字节
       │         │       │
       └─ RTP 固定头 ─┘  └─ RTP 载荷（H264 NALU 数据）
```

FEC 编码器对这两个包**逐字节做 XOR**，生成一个 FEC 包：

```
FEC 包 F = A ⊕ B

逐字节计算:
  第 0 字节: 0x80 ⊕ 0x80 = 0x00  ← RTP 版本字段 (V=2)，两个包相同，XOR 得 0
  第 1 字节: 0x60 ⊕ 0x60 = 0x00  ← PT + Marker，相同则得 0
  第 2 字节: 0x01 ⊕ 0x01 = 0x00  ← SeqNum 高字节
  第 3 字节: 0x02 ⊕ 0x03 = 0x01  ← SeqNum 低字节不同！XOR 记录了差异
  第 4 字节: 0xFF ⊕ 0x7C = 0x83  ← 载荷首字节差异
  第 5 字节: 0xD8 ⊕ 0x85 = 0x5D
  ...
  (200 个字节全部逐字节 XOR)

FEC 包 F: [0x00, 0x00, 0x00, 0x01, 0x83, 0x5D, ...]  也是 200 字节
```

**关键观察**：
- 两个包相同的字节 → FEC 中对应位置是 `0x00`（A ⊕ A = 0）
- 两个包不同的字节 → FEC 中对应位置是一个"混合值"，编码了二者的差异信息
- FEC 包的大小 = 原始包中最大的那个（不等长的要补 0 对齐）

**发送端发出去**：包 A、包 B、FEC 包 F，共 3 个包，3 × 200 = 600 字节。冗余率 = 1/2 = 50%。

#### 3.3.2 解码过程——丢了 A，用 B 和 F 恢复

网络丢了包 A。接收端只收到包 B 和 FEC 包 F：

```
手里有: B = [0x80, 0x60, 0x01, 0x03, 0x7C, 0x85, ...]
        F = [0x00, 0x00, 0x00, 0x01, 0x83, 0x5D, ...]

恢复 A = B ⊕ F:

  第 0 字节: 0x80 ⊕ 0x00 = 0x80  ✓
  第 1 字节: 0x60 ⊕ 0x00 = 0x60  ✓
  第 2 字节: 0x01 ⊕ 0x00 = 0x01  ✓
  第 3 字节: 0x03 ⊕ 0x01 = 0x02  ✓  (恢复了原来的 0x02!)
  第 4 字节: 0x7C ⊕ 0x83 = 0xFF  ✓  (恢复了原来的 0xFF!)
  第 5 字节: 0x85 ⊕ 0x5D = 0xD8  ✓  (恢复了原来的 0xD8!)
  ...

恢复出完整 A = [0x80, 0x60, 0x01, 0x02, 0xFF, 0xD8, ...]  ← 和原始 A 完全一致!
```

**原理**：XOR 的自反性——`B ⊕ F = B ⊕ (A ⊕ B) = A`。B 和自己消掉了，剩下 A。

#### 3.3.3 XOR FEC 的能力和局限

```
能恢复: 恰好丢 1 个包（任意哪个）
不能恢复: 丢 2 个或以上（A 和 B 都丢了 → B⊕A⊕B = A，但 B 也没了，两个未知数一个方程，解不出）

等价于: 1 个方程、1 个未知数 → 有解
         1 个方程、2 个未知数 → 无穷多解，无法确定原始值
```

**所以 XOR FEC 的保护度是 (n=3, k=2)**。这个记号在后面 RS 章节也会反复出现，先解释清楚：

> **(n, k) 记号的含意**：n = 编码后的总包数（原始 + 冗余），k = 原始数据包数，冗余包数 = n - k。**可恢复 ≤ (n-k) 个丢包**。所以 (3, 2) 表示"2 个原始包 + 1 个冗余包 = 3 个总包，丢 1 个能恢复，丢 2 个不行"。

#### 一个小规模场景：XOR 非常可靠

假设某条链路丢包率 5%。一个 H264 的 P 帧很小，Packetizer 只切出了 2 个 RTP 包。加上 1 个 XOR FEC 包，共 3 个包。问：FEC 恢复失败的概率有多大？

**失败的唯一条款**：这 3 个包中丢了 ≥2 个（丢 0 个或 1 个都能恢复）。每个包的丢包概率独立，p = 0.05。

```
丢恰好 2 个: C(3,2) × p² × (1-p)¹
            = 3 × 0.05² × 0.95
            = 3 × 0.0025 × 0.95
            = 0.007125 ≈ 0.71%

丢恰好 3 个: C(3,3) × p³ × (1-p)⁰
            = 1 × 0.000125 × 1
            = 0.000125 ≈ 0.01%

失败总概率  = 0.71% + 0.01% = 0.72%
恢复成功概率 = 1 - 0.72% = 99.28%
```

**单个 XOR 组极其可靠**——成功率 99.3%。但这掩盖了一个致命问题。

#### 放大到真实场景：XOR 为什么突然不够用了

现在换成一个 1080p 的 IDR 关键帧，Packetizer 切出了 **100 个 RTP 包**。丢包率还是 5%。

**XOR 的分组方式**：每 2 个媒体包配 1 个 FEC 包，一共 50 个独立的小组。每个组内独立做 XOR，组和组之间互不影响。

```
总共: 50 组 XOR(3,2)，每组发 3 个包（2 媒体 + 1 FEC），共 150 个包
每组独立存活概率: 99.28%

整帧存活条件: 所有 50 组同时存活（缺任何一组的媒体包都恢复不了）

整帧存活概率 = 0.9928^50 ≈ 69.8%
整帧失败概率 ≈ 30.2%
```

**也就是说：尽管每一小组的保护率高达 99.3%，但因为组数太多、只要一组失败整帧就坏，XOR 在大帧上的实际保护率只有 70%。** 平均每 3 个 IDR 帧就有一个解不出来——这在视频通话中表现为画面随机出现大块花屏或卡死。

#### 用 Reed-Solomon 解决这个问题

RS 允许一个组内包含**更多原始包和更多冗余包**。用 RS(8, 5)：5 个媒体包 + 3 个冗余包 = 8 个包一组，可恢复任意 ≤3 个丢包。

```
总共: 20 组 RS(8,5)，每组发 8 个包（5 媒体 + 3 FEC），共 160 个包

每组内失败条件: 8 个包中丢 ≥4 个
  P(≥4) = C(8,4)×p⁴×(1-p)⁴ + C(8,5)×p⁵×(1-p)³ + ... 
         = 70×0.00000625×0.8145 + 56×0.0000003125×0.8574 + (更小的项)
         ≈ 0.000356 + 0.000015 + 0.0000004
         ≈ 0.00037 = 0.037%

每组存活概率: 99.963%

整帧存活概率 = 0.99963^20 ≈ 99.26%
整帧失败概率 ≈ 0.74%
```

**对比**：

| 方案 | 总发包数 | 冗余开销 | 整帧成功率 | 整帧失败率 |
| :--- | :--- | :--- | :--- | :--- |
| 无保护 | 100 | 0% | 0.59%（=0.95^100） | 99.4% |
| XOR (3,2)，50 组 | 150 | 50% | **69.8%** | 30.2% |
| RS (8,5)，20 组 | 160 | 60% | **99.3%** | 0.7% |
| RS (10,5)，20 组 | 200 | 100% | ≈ 99.99% | ≈ 0.01% |

**核心教训**：XOR 对于小帧（≤10 个包）非常可靠，但对于大帧（≥50 个包），独立小组的数量一多，**组合概率**碾压了个体可靠性。Reed-Solomon 用更大的组、更多的冗余，从数学上把失败概率压制到千分级。

### 3.4 Reed-Solomon（RS）FEC：丢多个包也能恢复

#### 3.4.1 从 XOR 到 RS —— 本质是"方程的个数"

XOR 只给了 1 个"方程"（1 个 FEC 包），所以只能解 1 个未知数（1 个丢失包）。

**Reed-Solomon 的核心思想**：生成**多个**冗余包（多个方程），就可以恢复**多个**丢失包。

```
如果我想让 5 个原始包中丢任意 3 个都能恢复:
  需要 3 个冗余包 = 3 个独立的"方程"
  总共发 5 + 3 = 8 个包
  收到任意 ≥5 个包（不管哪 5 个）→ 5 个方程、5 个未知数 → 唯一解 ✓
  丢 4 个 → 只剩 4 个方程、5 个未知数 → 无穷多解 ✗
```

这就是 RS(n, k) 参数的含义：**n = 总包数，k = 原始数据包数，可恢复 ≤ (n-k) 个丢包**。

#### 3.4.2 编码过程——用一个具体的小例子（RS(4,2)）

用最小的非平凡例子：RS(4,2)。2 个原始包，生成 2 个冗余包，丢任意 ≤2 个都能恢复。

**第一步：构造编码矩阵**

选一个 **4×2 的范德蒙德矩阵**（Vandermonde）作为编码矩阵。前两行是单位矩阵（保持原始数据不变），后两行生成冗余包：

```
编码矩阵 V:              原始数据 D:
┌           ┐           ┌     ┐
│ 1    0    │           │  A  │
│ 0    1    │           │  B  │
│ 1    1    │           └     ┘
│ 1    2    │
└           ┘
```

**第二步：矩阵乘法**

```
编码结果 = V × D:

第 1 行: 1×A + 0×B = A      ← 就是原始包 A
第 2 行: 0×A + 1×B = B      ← 就是原始包 B
第 3 行: 1×A + 1×B = P1     ← 冗余包 P1 = A + B（和 XOR 一样！）
第 4 行: 1×A + 2×B = P2     ← 冗余包 P2 = A + 2×B（比 XOR 多了一个"方程"）
```

发送端发出 4 个包：`[A, B, P1, P2]`。

> **注意**：这里的 `+` 和 `×` 不是在普通自然数上算的——如果 A=200, B=150，`A+B=350` 超过了 1 个字节（0-255）。RS 的所有运算都在伽罗瓦域 GF(2^8) 里做，确保输入是字节、输出还是字节。后文 §3.4.4 详述。

#### 3.4.3 解码过程——丢了 A 和 P1

网络丢了 A 和 P1。接收端只收到 B 和 P2：

```
收到的包: B  (对应编码矩阵的第 2 行: 0×A + 1×B = B)
         P2 (对应编码矩阵的第 4 行: 1×A + 2×B = P2)

从 4×2 编码矩阵中取出"幸存行"对应的 2×2 子矩阵:

  V_surviving = ┌         ┐
                │ 0   1   │  ← 第 2 行
                │ 1   2   │  ← 第 4 行
                └         ┘

我们有方程组:
  0×A + 1×B = B       (已知 B)
  1×A + 2×B = P2      (已知 P2)

解: A = P2 - 2×B      (在 GF(2^8) 中算出具体字节)
```

**本质**：从 4 个方程中挑出 2 个（对应收到的包），解 2 个未知数（丢失的 A）。因为编码矩阵保证了任意 2×2 子矩阵可逆（范德蒙德矩阵的性质），**无论丢了哪 2 个包，方程都有唯一解**。

#### 3.4.4 为什么必须在 GF(2^8) 里算？

这是 RS FEC 最关键的工程细节。如果不在 GF(2^8) 里算，有两个无法容忍的问题：

**问题 1：溢出。** 普通算术：`200 + 150 = 350`，但一个字节只能存 0-255。`350` 需要两个字节存储，FEC 包会比原始包**大一倍**。GF(2^8) 里 `200 + 150 = 94`（加法就是 XOR，不产生进位），所有运算结果天然落在 0-255 内——**FEC 包和原始包一样大，字节数完全不变**。

**问题 2：精确性。** 普通算术里 `2 × B` 可能产生小数（如果做除法），用浮点会产生精度问题。在 GF(2^8) 里，乘除法都是封闭、精确的字节到字节运算——解码结果是**逐字节精确还原**的，不会有任何误差。乘法通过查两张 256 字节的表（`exp` 表和 `log` 表）实现，三行代码完成。

> **面试金句**："Reed-Solomon 的核心是'编码矩阵 + 有限域算术'。编码矩阵用范德蒙德结构，保证任取 k 行都线性无关（任意 k 个幸存包都能恢复 k 个原始包）。GF(2^8) 让所有运算在字节范围内封闭——加法是 XOR，乘法用查表，输入和输出都是 1 字节。结果是：FEC 包和原始包一样大，丢几个都能精确恢复，字节级无损。"

#### 3.4.5 RS vs XOR：实战对比

| 维度 | XOR FEC | RS FEC |
| :--- | :--- | :--- |
| 保护度 | (k+1, k)，只能恢复 1 个丢包 | (n, k)，可恢复任意 ≤ n-k 个丢包 |
| 编码速度 | 极其快（就是异或） | 较慢（GF 乘法需查表，比 XOR 慢 10-50 倍） |
| 冗余包大小 | = 原始包中最大者 | = 原始包中最大者 |
| 典型场景 | 丢包率 < 5%，每帧包数 < 10 | 丢包率 5-20%，需更灵活的保护度 |
| WebRTC 使用 | ✅ UlpFEC 默认 | FlexFEC 可选升级 |

### 3.5 WebRTC 中的两种 FEC 方案

| 特性 | UlpFEC (RFC 5109) | FlexFEC (RFC 8627) |
| :--- | :--- | :--- |
| **包格式** | FEC 包伪装成 RTP 包（PT=127），载荷 = FEC header + 冗余数据 | 独立 RTP SSRC 流，与媒体流解耦 |
| **保护粒度** | 基于 RTP 包序号掩码（mask），灵活指定"哪些包被保护" | 基于 RTP 时间戳 + SeqNum，一个 FEC 包可跨帧保护 |
| **复杂度** | 中等（需要动态维护保护关系） | 低（固定 pattern） |
| **WebRTC 默认** | ✅（历史遗留，仍广泛使用） | 部分支持 |
| **是否打乱 RTP** | 是（FEC 包混在同一 SSRC 里，seq 序号连续） | 否（独立 SSRC，不影响媒体 SeqNum） |

**UlpFEC 的保护 Level**：

```
Level 0: 只保护关键帧（IDR）的包——最省带宽
Level 1: 保护关键帧 + 第一帧 P 帧——适度冗余
Level 2: 保护所有帧的一部分包（如取掩码后每 2 个包保护 1 个）
Level 3: 保护所有帧的全部包——最烧带宽，只在极端弱网开
```

### 3.6 FEC 是怎么跟其他机制协作的？

**编码时机**：Packetizer 输出一帧的所有 RTP 包 → FEC Encoder 对这一批包做 XOR/RS 运算、产出 FEC 包 → **插队到同帧最后一包后面**（同一 timestamp、SeqNum 连续递增、Marker 位在 FEC 尾包）。

**解码时机**：接收端每收到一批同 timestamp 的包 → FEC Decoder 检查哪些 seq 缺失 → 有缺失且冗余够 → 本地恢复 → 把恢复的包**当作正常包**插入 NACK 检查之前的流程。

**FEC 恢复的包对 NACK 的影响**：FEC 恢复后，这批包的丢包率从"10 个缺 3 个"变成"10 个缺 1 个"——NACK 只需要请求那个 FEC 也救不回来的包。**FEC 是 NACK 的前置过滤层**。

### 3.7 FEC 的关键权衡

| 场景 | FEC 冗余率 | 理由 |
| :--- | :--- | :--- |
| RTT < 30ms（局域网/同城）| 低 / 关闭 | NACK 重传足够快，FEC 浪费带宽 |
| RTT 50-150ms（跨省/跨国）| 5-15% | NACK 有 1 RTT 延迟，FEC 填这个窗口 |
| RTT > 200ms（跨国/卫星）| 15-30% | NACK 基本来不及，FEC 是主力 |
| 丢包率 > 5% | 提高冗余 + 降码率 | 丢包太多 → 优先降码率，其次加 FEC |
| 码率紧张（GCC 估的带宽低）| 降低/关闭 FEC | 带宽不够 → 先把带宽给媒体，FEC 先关了 |

## 4. NACK：丢包重传（精准缺啥补啥）

### 4.1 核心问题

**FEC 修不好的漏网之鱼，怎么补？**

NACK 的思路：接收端清点包裹，发现少了 seq=X，**指名道姓**让发送端重发这个包。

### 4.2 NACK 的工作流程

```
接收端:
  1. 新包到达——seq=100
  2. 上一次收到的 seq=98 → 中间缺了 seq=99
  3. 把 seq=99 加入"待 NACK 列表"，记录加入时间
  4. 等 kSendNackDelayMs（默认 20ms，推荐 1 RTT 内）——给乱序包自然到达的机会
  5. 到达 deadline 还缺 → 打包成 RTCP NACK 消息发出去：
       GenericNack: { pid: 99, blp: 0b0000000000000000 }
     （blp = Bitmap of Lost Packets，一次性可以报多个连续缺失的 seq）

发送端:
  6. 收到 NACK → 查 RtpPacketHistory 环形缓冲
  7. 找到 seq=99 → 重新打包（用 RTX SSRC + 新的 RTX SeqNum）
  8. 通过 RTX 重传流发出去（独立 SSRC，不和媒体流抢 seq 序号）

接收端:
  9. 收到 RTX 重传 → 还原原始 seq=99 → 插入 JitterBuffer
```

### 4.3 RTX（Retransmission）重传通道

#### 4.3.0 RTX 是什么？（先说清楚是什么，再讲原理）

在音视频通信和流媒体（尤其是 WebRTC）领域，**RTX** 是 **Retransmission（重传）** 的缩写。

简单来说：**RTX 是一种专门用来应对网络丢包的「重传协议」。当接收端发现 RTP 媒体包在路上丢了，它会通过 RTX 机制让发送端把丢失的那个包重新发一遍。**

为了让你彻底搞懂 RTX 的底层逻辑和它为什么被设计成这样，我们从以下几个维度来拆解：

---

**1. 为什么不直接原路重传，而要搞一个「RTX」？**

最朴素的想法是：发送端收到 NACK 说「seq=100 丢了」，那就把第 100 号包原封不动再发一次呗，多简单。

但这在现代流媒体（尤其是跑着拥塞控制算法的 WebRTC）中会引发两个致命问题：

- **误导带宽评估（GCC 等算法）**：拥塞控制算法（如 WebRTC 的 GCC）是靠统计「每秒收到了多少 RTP 数据」来估算当前网络还剩多少带宽的。如果你把重传包原样发出去，接收端的带宽统计会把重传包也当成「新发出的媒体数据」，那 GCC 就会误判——要么认为带宽很充裕（实际已经堵了，重传包占了一大坨），要么一通瞎调码率，越调越糟。

- **乱序与统计混乱**：同一个 SeqNum 的包在短时间内出现两次——接收端的 JitterBuffer 直接懵了：哪个是老包？哪个是重传包？丢包率统计也对不上了。

所以 RFC 4588 专门定义了 **RTX 协议**。核心思想就一句话：**给重传数据建立一条独立的「VIP 绿色通道」，拥有自己独立的 SSRC 和序列号，与正常的媒体流完全隔离。**

> 类比：你订了一箱零件，快递把第 3 号包裹搞丢了。仓库不会用原来的快递单号再发一次（那样系统里会出现两张「3 号单」），而是用一张**全新的快递单号**重新发，但包裹里塞了一张纸条写着「这其实是第 3 号」。

---

**2. RTX 的底层运作机制（一步一步走一遍）**

在 WebRTC 做 SDP 协商时，你会看到媒体流不仅有一个视频流（比如 H.264，假设 SSRC = `1111`），还会专门为它配对一个 RTX 流（重传流，SSRC = `2222`）。

当丢包发生时，整个互动流程如下：

```
① 发送端发出 SSRC=1111, Seq=100 的视频 RTP 包
                                    ↓ 网络丢包，这个包没了
                                    
② 接收端收到了 Seq=99 和 Seq=101，唯独缺了 100
   → 通过 RTCP NACK 报告给发送端：
     「我丢了 SSRC=1111 的 Seq=100，请速重传！」

③ 发送端收到 NACK，从历史缓存（RtpPacketHistory）里捞出这个包
   但它 不会 直接把原包扔过去，而是把它 封装成 RTX 包：
   
   原始包:                           RTX 包:
   ┌─────────────────────┐          ┌──────────────────────────┐
   │ SSRC = 1111         │          │ SSRC = 2222  ← 换成 RTX 的 │
   │ Seq  = 100          │    →     │ Seq  = 500   ← RTX 自己的  │
   │ 载荷 = [视频数据]     │          │ 载荷 = [0x00 0x64][视频数据] │
   └─────────────────────┘          │         ↑                  │
                                    │   前 2 字节 = 原始 Seq=100  │
                                    └──────────────────────────┘

④ 接收端收到 SSRC=2222, Seq=500 的包
   → 一看 SSRC 是 RTX 频道的，立刻心领神会
   → 剥掉 RTX 外壳：读载荷前 2 字节 → 原来是老朋友 SSRC=1111 的 Seq=100
   → 还原成原始包，塞进 JitterBuffer，等着解码
```

一句话总结这个过程：**NACK 是「我要 Seq=100」，RTX 是「好，我用 RTX 通道重新发给你」。** NACK 负责提出请求，RTX 负责执行重传。没有 NACK 的时候，RTX 流是完全静默的——不浪费一丁点带宽。

---

**3. RTX 在弱网对抗军械库里的位置**

WebRTC 弱网对抗有三驾最核心的马车：**GCC（拥塞控制）**、**FEC（前向纠错）** 和 **NACK/RTX（丢包重传）**。

RTX 和 FEC 形成了完美的互补关系，各有各的适用场景：

| 维度 | FEC（前向纠错） | RTX（重传） |
| :--- | :--- | :--- |
| **类比** | 发货时多塞一包零件备着 | 丢了再喊仓库补发 |
| **何时生效** | 丢包的瞬间就能恢复（零延迟） | 必须等 1 个 RTT 来回（有延迟） |
| **带宽代价** | 一直在发冗余，没丢也占带宽 | 按需触发，不丢不占带宽 |
| **适合场景** | RTT 很大（跨国通话），等不起重传 | RTT 很小（同城/局域网），重传秒到 |

**策略取舍的直觉：**

- 当 **RTT 很小**（网络延迟低，比如国内同城），WebRTC 会**优先靠 RTX**——补发贼快、体验丝滑、还不浪费带宽。
- 当 **RTT 很大**（跨国跨大洲），补发一个包来回要几百毫秒，视频早就卡出翔了。此时 WebRTC 会**减少 RTX 重传次数，加大 FEC 冗余比例**——用带宽换时间。

---

**总结：提到 RTX，脑子里记住这几个词就够了**

**独立通道重传 · 独立 SSRC · 前 2 字节存原始 Seq · 按需触发省带宽 · 低 RTT 下的省流量利器**

RTX 不是什么高深的编码算法，它就是多媒体工程师为了在恶劣网络下「丢了包能精准补回来、又不干扰正常的带宽统计」而设计的一套极其务实的包装格式和传输约定。

#### 4.3.1 为什么重传不能用原 SSRC？（原理）

```
原始流: SSRC=1234, SeqNum 单调递增
重传流: SSRC=5678, SeqNum 独立递增

如果重传包和原始包共用一个 SSRC：
  - 接收端按 SeqNum 排序时会混乱（重传包 seq=99 可能和正常包 seq=199 混淆）
  - 丢包统计会乱（重传相当于"重发"，不是"新发送"）

RTX 的解决方案：
  RTX 包用独立的 SSRC，payload type 固定为原始流的 PT + rtx_payload_type_map
  RTX 包的载荷 = 2 字节原始 seq（大端） + 原始包的载荷
  接收端看到 RTX SSRC → 知道这是重传 → 还原原始 seq → 插入 JitterBuffer
```

**SDP 中 RTX 的声明**：

```sdp
m=video 9 UDP/TLS/RTP/SAVPF 96 97
a=rtpmap:96 VP8/90000
a=rtpmap:97 rtx/90000           ← RTX 的 payload type
a=fmtp:97 apt=96                 ← RTX 97 对应原始 stream 96（apt = associated payload type）
a=ssrc-group:FID 1234 5678       ← FID = Flow Identification: 原始 SSRC=1234, RTX SSRC=5678
```

### 4.4 NACK 的三个关键策略

#### 策略 1：延迟发 NACK（等乱序自然恢复）

```
大多数"丢包"其实是乱序:
  - 实际丢了: 发送端发了，路由器吞了，永远到不了
  - 只是乱序: 路由器走了两条路径，晚到 5ms

区别方法: 等 1 RTT——真的丢了 1 RTT 内不会有包，乱序的包 5-10ms 就到了

所以 NACK 延迟 = kSendNackDelayMs + min(RTT)。
典型值: RTT=30ms → delay=20+30=50ms；RTT=200ms → delay=20+150=170ms
```

#### 策略 2：批量发送（省 RTCP 带宽）

```
不是"丢一个发一个 NACK"——太浪费带宽。
而是: 等 deadline 到了，把最近所有到期的缺失 seq 打包成一个 RTCP NACK 消息。

一个 GenericNack 包:
  PID (Packet ID) = 第一个缺失的 seq
  BLP (Bitmap of Lost Packets) = 16 位的位图
    第 i 位 = 1 表示 seq PID + i + 1 也丢了
  一个 NACK 包最多能报 17 个连续缺失的 seq

多个 PID+BLP 对可以组合在一个 RTCP 复合包里，一次性报告 (最多 255 对)
```

#### 策略 3：重传上限 + 失败回退

```
对每个缺失 seq: 最多重传 10 次（kMaxNackRetries = 10）
重传间隔: 每次至少等 1 RTT（避免重传风暴）

重传 10 次还不到:
  → 不是网络问题，是发送端缓存里的包已经过期了（RtpPacketHistory 默认只存 1000ms）
  → 放弃这个 seq
  → 连续多个 seq 重传失败 → 触发关键帧请求（PLI / FIR）
```

### 4.5 NACK 的 libwebrtc 源码入口

| `modules/rtp_rtcp/source/rtp_packet_history.cc` | 发送端 RTP 包历史缓存，NACK 重传从这里取包 |

## 5. JitterBuffer：抖动缓冲（稳定播放节奏）

### 5.1 核心问题

**FEC 和 NACK 把包都救回来了，但到达顺序和节奏是乱的——怎么稳定播放？**

详细原理见 [[07-M6-JitterBuffer模块]]，本节只讲它在四驾马车协作中的位置。

### 5.2 JitterBuffer 在 QoS 流水线中的角色

```
接收端包处理流水线:

[网卡收到 RTP 包]
      │
      ▼
┌─────────────┐
│ FEC Decoder │ ← 检查是否有缺失 + 冗余够 → 本地恢复
│ (修好了 X%)  │
└──────┬──────┘
       │ 包 = 原始 + FEC 恢复
       ▼
┌─────────────┐
│ NACK Check  │ ← 还缺哪些 seq？→ 加入 NACK 列表 → 延迟后发 NACK
│ (等着补 Y%)  │    已经发过 NACK 的包 → 重传回来后插入流水线
└──────┬──────┘
       │ 包 = 原始 + FEC恢复 + NACK重传
       ▼
┌──────────────────────────────────────┐
│         ★ JitterBuffer ★             │
│                                      │
│  PacketBuffer ── 按 seq 索引的环形缓冲│
│       │                              │
│       ▼                              │
│  FrameAssembler ── 拼分片成帧        │
│       │                              │
│       ▼                              │
│  JitterEstimator ── EWMA/Kalman 抗抖 │
│       │                              │
│       ▼                              │
│  TimingController ── 算渲染时刻       │
│       │                              │
│       ▼                              │
│  等待 renderTimeMs → 吐帧给 Decoder   │
└──────────────────────────────────────┘
       │
       ▼
  [Decoder] → [Renderer]
```

**关键工作**：
1. **收容所有来源的包**：原始/FEC恢复/NACK重传——不管怎么来的，只要到了就进 PacketBuffer
2. **按 seq 排序**：环形 buffer 按 seq % 2048 哈希，乱序到达自动归位
3. **检查帧完整性**：同帧所有 seq 连续 + Marker 包已到 → 帧"完整"
4. **算目标延迟**：`3σ × 抖动 + 解码延迟 + 渲染延迟`
5. **等到了时间才吐帧**：`renderTimeMs = arrivalTimeMs + targetDelayMs`
6. **如果丢包导致帧不完整**：等 NACK 重传（增加延迟）或超时丢弃（增加丢帧率）
7. **关键时刻帧请求**：连续 N 帧不完整 → 发 PLI 请求 IDR

### 5.3 JitterBuffer 怎么影响 NACK 的决策？

**问题**：等了很久 NACK 还没到，JitterBuffer 还要继续等吗？

```
JitterBuffer 计算出 renderTimeMs。

如果 NACK 重传回来的预期时间 > renderTimeMs：
  → 不等了，丢弃这一帧（或标记为不完整，让解码器跳过）
  → 因为即使补回来，也错过了渲染时刻，晚了就是没用了
  → 连续多帧丢弃 → 触发关键帧请求

如果 NACK 重传回来的预期时间 ≤ renderTimeMs：
  → 等！在 renderTimeMs 之前到达就能赶得上
  → 所以 JitterBuffer 的目标延迟设得越高 → NACK 能"抢救"的时间窗口越长
  → 但延迟越高用户体验越差——这是权衡
```

这是 **JitterBuffer 和 NACK 之间最深层的交互**：TargetDelayMs 决定了 NACK 重传的有效窗口。buffer 太浅 → NACK "来不及" → 丢帧；buffer 太深 → 明明补回来了但延迟受不了。

## 6. 端到端协同流水线

### 6.1 正常情况（丢包率 < 2%）

```
发送端                                    接收端
```

## 7. 四驾马车全景对比表

| 维度 | GCC | FEC | NACK | JitterBuffer |
| :--- | :--- | :--- | :--- | :--- |
| **问题** | 该发多快 | 怎么零延迟恢复丢包 | 怎么精准补丢包 | 怎么稳定播放 |
| **工作位置** | 发送端（收反馈） | 发送端编码 + 接收端解码 | 接收端检测 + 发送端重传 | 接收端 |
| **触发条件** | 每收到 TWCC / 每 100ms | 每个 RTP 包组都产 FEC 包 | 检测到 seq 缺失 | **每个包到达都工作** |
| **延迟代价** | 无延迟（只是降码率） | 零（本地恢复） | **1 RTT** | **N ms 缓冲** |
| **带宽代价** | 无（少发数据反而省带宽） | **5-30% 额外带宽** | 重传占用少量带宽 | 无额外带宽（只是缓存） |
| **恢复粒度** | 不恢复丢包，只预防 | 包级（XOR/RS） | 包级（通过 seq） | 帧级（完整性判定） |
| **控制频率** | ~1 Hz（码率调整） | 每帧 | 每检测到缺失 | 每包 |
| **失效模式** | 带宽估算偏低 → 画面糊 | 丢包超冗余度 → 无法恢复 | 重传赶不上渲染 → 丢帧 | buffer 太浅 → 抖动漏过 |
| **多流场景** | 共用带宽估算（最慢的流决定码率） | 每流独立 FEC | 每流独立 NACK | 每流独立 buffer |

## 8. 面试问答映射（12 道高频题）

### Q1. WebRTC 怎么做拥塞控制？GCC 的全称和工作原理是什么？

**标准答案**：GCC = Google Congestion Control，分两个独立控制器。Delay-Based Controller 用 Trendline 趋势线——对每个 5ms 时间窗口内 `(到达间隔 - 发送间隔)` 做线性回归，斜率 > 阈值判 overuse 降码率、< 阈值判 underuse 升码率。Loss-Based Controller 用 AIMD——丢包率 < 2% 每次加 8%、2-10% 保持、> 10% 乘 0.5。两个控制器取 min 作为最终目标码率。码率通过三个路径生效：调编码器 QP、调 Pacer 节奏、调 FEC 冗余率。

---

### Q2. 为什么 GCC 有两个控制器？光看丢包不行吗？

**标准答案**：延迟是拥塞的**早期信号**。路由器队列开始积压时，包的到达间隔会越来越长——这个信号比丢包早出现 200-500ms。如果只看丢包，等于等到队列已经满了、开始丢了才反应，相当于用"火灾报警器"代替"温度计"。理想情况是 Trendline 先发现 overuse → 提前降码率 → 丢包根本不发生。Loss-Based Controller 是 Trendline 漏掉时的**兜底保险**。

---

### Q3. Trendline 的斜率怎么算？为什么用线性回归而不是简单平均？

**标准答案**：维护最近 20 个时间窗口（每个 5ms）的 (累积发送时间, 累积到达延迟) 数据点，**最小二乘线性回归**算斜率。用线性回归而不是简单平均是因为它过滤了单点噪声——无线网络偶尔有一个包的到达延迟突然飙高（原因不是拥塞，是 WiFi 重传），简单平均把这个假信号当真，导致码率剧烈震荡。线性回归对单点离群值**天然鲁棒**。

---

### Q4. FEC 和 NACK 的根本区别是什么？怎么选？

**标准答案**：**FEC 是用带宽换时间**——提前发冗余数据，丢了包在本地解方程恢复，零延迟但吃额外带宽。**NACK 是用时间换带宽**——丢了包再请求重传，精准补缺省带宽但等 1 RTT。选择策略：
- RTT < 50ms：优先 NACK（重传足够快，FEC 浪费）
- RTT 50-200ms：FEC 保护关键帧（IDR）+ NACK 补 P 帧
- RTT > 200ms：FEC 做主力、NACK 兜底
- 关键帧（SPS/PPS/IDR）：**必须 FEC 保护**——丢一个 SPS 等于后面的帧全废，等 NACK 来不及

**追问**："FEC 保护率怎么动态调？" → GCC 输出码率后，FEC Controller 检查当前码率 vs 需求——码率充裕就多加点冗余，码率紧张就减冗余甚至关 FEC（给媒体数据多留带宽）。

---

### Q5. XOR FEC 和 Reed-Solomon FEC 的区别？

**标准答案**：XOR FEC 做最简单的奇偶校验——A ⊕ B = F，丢了 A 就用 B ⊕ F 恢复，但只能恢复**恰好 1 个**丢包（丢 ≥2 个就恢复不了）。Reed-Solomon 是通用纠删码——在 GF(2^8) 上用范德蒙德矩阵，RS(n,k) 可以在 n 个包里丢任意 ≤ n-k 个都能恢复。**代价**：RS 计算量比 XOR 高一个量级。WebRTC 的 UlpFEC 默认用 XOR（因为 CPU 省、够用），FlexFEC 可以升级到 RS。

---

### Q6. NACK 为什么不是"丢一个发一个"？

**标准答案**：三个原因：① **乱序不是丢包**——路由器多路径导致顺序错乱占多数，真正的丢包是少数，等 1 RTT 给乱序自然到达的机会（5-10ms 就来了，不等就是白请求）；② **批量省带宽**——一个 RTCP NACK 消息携带 17 个连续缺失 seq（PID + BLP 位图），可以多个 PID+BLP 对放在一个包里；③ **避免 NACK 风暴**——弱网下如果发现缺一个就发一个，NACK 数量级瞬间爆炸，反而进一步拥堵上行。

---

### Q7. RTX 重传为什么必须用独立 SSRC？

**标准答案**：三个原因：① **SeqNum 区分**——原始流 ssr=1234 的 SeqNum 是连续递增的，如果重传包混进去，seq=99 的重传会被接收端当成"重复包"或"旧包"丢弃；② **丢包统计不乱**——RTX 的 SSRC 在 RTCP RR 里独立统计，不会扭曲原始流的丢包率计算；③ **SDP 声明独立**——`ssrc-group:FID` 把原始 SSRC 和 RTX SSRC 绑在一起，接收端知道这两个流是"同一路媒体"，可以关联处理。

---

### Q8. NACK 重传 10 次还不到怎么办？

**标准答案**：放弃这个 seq，触发关键帧请求。等不到不一定是网络问题——经常是发送端的 RtpPacketHistory 已经过期了（默认保存 1000ms）。RTT 300ms 下重传 10 次需要 3 秒，1 秒后发送端就删了这个包。此外，连续多个 seq 重传失败通常意味着**参考帧链断了**——P 帧依赖的 I 帧部分丢失，重传个别包也没用，必须请求 IDR 重启参考链。

---

### Q9. JitterBuffer 的 TargetDelay 是怎么定的？为什么是 3 倍抖动？

**标准答案**：`TargetDelayMs = 3 × EstimatedJitterMs + DecodeDelayMs + RenderDelayMs`。3σ 源于正态分布：假设抖动服从正态分布，3σ 覆盖 99.7% 的样本——只有 0.3% 的极端抖动会"漏过"（这部分通过 NACK 兜底）。典型数值：局域网抖动 5ms → 35ms delay；4G 抖动 30ms → 110ms；弱网 80ms → 260ms。

**追问**："抖动估计怎么更新？" → EWMA（指数加权移动平均）：每收到一帧，`new_jitter = 0.95 × old + 0.05 × |actual_interval - expected_interval|`。比简单平均更平滑，自动过滤单次尖峰。库函数版（libwebrtc）用 Kalman 滤波，把抖动建模成"每字节传输延迟 + 队列延迟"两个状态变量，突发响应更快但实现 500+ 行。

---

### Q10. 四驾马车中，哪个是"不管丢不丢包都在工作的"？

**标准答案**：**JitterBuffer**。FEC 只在有冗余包时才产出（而且是按帧批处理），NACK 只在检测到丢包时触发，GCC 以 ~1Hz 的频率调整——但 JitterBuffer **每收到一个 RTP 包都在判断**"这个包属于哪一帧、这帧完整了吗、什么时候该吐"。它是四驾马车中唯一**持续运行**的机制。

---

### Q11. 如果把四驾马车比作一个乐队，它们各自是什么角色？

**标准答案**：
- **GCC = 指挥**：根据观众的反馈（RTCP TWCC）调整乐队的整体节奏（码率），确保不越奏越快导致现场混乱（拥塞）
- **FEC = 备用乐器**：提前在台下放好备用小提琴，台上有人弦断了（丢包），立刻换备用琴（XOR 本地恢复），观众根本听不出
- **NACK = 谱务**：发现某页谱子缺了（丢了某个 seq），立刻从后台档案室（RtpPacketHistory）找出来补上（重传）
- **JitterBuffer = 混音台/监听**：把各种乐器到达的音轨（原始/FEC修/NACK补）按谱子重新对齐（排序），统一延迟几毫秒（缓冲），确保最终输出的节奏稳定

这个比喻在面试时能有效展示你**理解全局架构**而非只会背定义。

---

### Q12. 你在自己的 B 层 JitterBuffer 里，怎么跟 FEC/NACK 交互？

**标准答案**：我的 B 层没有实现 FEC——这是有意识的简化。和 NACK 的交互在 `IJitterBufferObserver` 接口：当 JitterBuffer 检测到 SeqNum 断层（缺失的包在 1 RTT 内没收到），通过 `OnPacketLossDetected(missingSequences)` 通知 NACK 模块发重传请求。JitterBuffer 的 TargetDelay 会给 NACK 留出 `RTT × NACK_RETRIES` 的时间窗口——如果重传预估到达时间 > renderTimeMs，JitterBuffer 不再等待、直接标记帧不完整。

B 层的具体实现中，`PacketBuffer::InsertPacket` 在收到每个包时比较 `newPacket.seq` 和 `expectedNextSeq`，断层时 push 缺失 seq 列表到 observer，然后依赖外部 NACK 模块处理和等待。详细代码见 `07-M6-JitterBuffer模块/code/`。
