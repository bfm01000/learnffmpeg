## 1. A 层 demo 技术栈选型

### 候选对比表

| 维度 | 候选 A: libwebrtc 原生 | 候选 B: mediasoup C++ client | 候选 C: pion + libdatachannel |
|------|----------------------|----------------------------|------------------------------|
| **客户端语言** | C++ 全栈 | C++ client + Node 信令 | C++ 客户端（libdatachannel） |
| **服务端** | 自实现 WebSocket 信令 server（C++）| mediasoup（Node.js） | pion SFU（Go） |
| **架构形态** | 1v1 P2P 直连 + STUN | SFU（Server-side） | SFU（Server-side） |
| **库的体量** | libwebrtc（~1M+ LOC，编译 ~2-4h） | mediasoup-client-cpp（薄） | libdatachannel（~50k LOC） |
| **编译难度** | ★★★★★（GN/Ninja，macOS depot_tools）| ★★★（CMake + Node） | ★★（纯 CMake） |
| **C++ 占比** | 100% | client 100% / server 0% | client 100% / server 0% |
| **能看到的底层细节** | 全部（ICE/DTLS/SRTP/JitterBuf/GCC）| 中等（mediasoup 抽象一层）| 较少（libdatachannel 封装较深）|
| **面试讲述空间** | ★★★★★（最直接对应面试题）| ★★★★（SFU 架构是加分项）| ★★★（Go 服务端讲不上深度）|
| **学习曲线** | 陡（一周才编通）| 中（两天上手）| 平（一天上手）|
| **资料丰富度** | ★★★★★（官方文档 + 大量源码分析）| ★★★（mediasoup 文档好）| ★★★（pion 文档好）|
| **B 层重写对接难度** | 易（B 层模块直接替换 libwebrtc 同名组件）| 难（mediasoup 不暴露 RTP 层）| 中（libdatachannel 可以 hook）|

### 推荐方案：**候选 A**（libwebrtc 原生）

**理由**：

1. **目标对齐**：你面试方向是 C++ 音视频/RTC 引擎，几乎所有目标公司（声网/即构/字节/腾讯）都基于 libwebrtc 二次开发，面试问的就是 libwebrtc 的内部实现。用 libwebrtc 做 demo = 直接在面试用的同一棵代码树上工作。
2. **B 层对接最顺**：B 层要重写 RTP 打包器和 Jitter Buffer，**最自然的方式**是替换 libwebrtc 里同名组件（`modules/rtp_rtcp/source/rtp_format.cc` / `modules/video_coding/jitter_buffer.cc`），跑同一套测试用例对照——这是面试最有说服力的"我读过、改过、跑通过"故事。
3. **资料最全**：libwebrtc 的中文/英文源码分析文章数量是 mediasoup/pion 的 10 倍以上，遇到坑能 Google 出来。

**代价**：编译 libwebrtc 是一道高墙，预计**第 1 周全花在 depot_tools / GN / Ninja / macOS SDK 配置上**，建议直接找一份 m120 分支的预编译产物（Cocoapods 上有），先跑通再说编译。

### 推荐技术栈细节

```
平台：macOS（你本地）
WebRTC 版本：m120（2023-12 release，源码稳定 + 文档对齐）
客户端 UI：命令行 / 简单 macOS App（Cocoa + Metal 渲染）
信令 server：C++17 + uWebSockets（轻量 WebSocket 库，~5k 行）
信令协议：JSON over WebSocket（join / offer / answer / ice-candidate / leave）
NAT 穿透：自部署 coturn（STUN + TURN），跑在 Docker 里
媒体编解码：libwebrtc 自带的 H264（OpenH264 软编）+ Opus
录制：先不做，留到 V2
日志：spdlog + libwebrtc 自带 LogSink
```

### 候选 B/C 的适用场景

如果你**编译 libwebrtc 卡了超过 1 周**就果断切换到候选 C（libdatachannel），代价是底层细节看不全，但能保证项目按时跑起来。**候选 B（mediasoup）** 不推荐——SFU 架构虽然听起来高级，但服务端是 Node，面试官问到服务端就会扣分（你不是 RTC 服务端方向）。

## 2. B 层重写模块的选定与评估

### 原方案：Jitter Buffer + RTP 打包/解包器

**评估结论**：**两个模块都保留**，但范围微调。

### 模块 1：RTP 打包/解包器（**B 层**）

| 项目 | 内容 |
|------|------|
| **对应 libwebrtc 路径** | `modules/rtp_rtcp/source/rtp_format_h264.cc` + `rtp_format_h264.h` + `rtp_packetizer.cc` |
| **要实现的功能** | ① RTP 头编解码（12 字节固定头 + 扩展头）；② H264 的 FU-A 分片打包（一个 NALU > MTU 时拆成多个 RTP 包）；③ STAP-A 聚合打包（多个小 NALU 合一个 RTP 包）；④ 反向解包还原 NALU |
| **要砍掉的特性** | ① 加密（SRTP 暴露明文 RTP）；② 重传请求（NACK）由独立模块处理；③ FEC（前向纠错）不做；④ 只支持 H264 不支持 VP8/VP9/AV1；⑤ 音频 Opus 打包简化（单包不分片） |
| **预计代码量** | 头文件 ~80 行，实现 ~250 行，单元测试 ~150 行 |
| **测试方式** | ① 单元测试：用 fixed bytes 验证 FU-A 头解析；② 联调测试：自己打包后喂给 libwebrtc 的 RtpDepacketizer 解，确认输出一致；③ 反向：libwebrtc 打包 → 自己解，对比 NALU 字节相等 |
| **面试讲述价值** | ★★★★★（RTP 是 WebRTC 最基础的数据面，面试必问）|

**关键算法**：FU-A 分片。一个 H264 NALU 头是 `0x65`（IDR），如果 NALU 长度 100KB > MTU=1400，拆成 N 个 RTP 包：
- 每个 RTP 包的 FU-A header = `0x7C`（type=28），FU header 第一字节用 S/E/Type 位标识"首包/中间包/尾包"。
- 接收端按 RTP 序号顺序拼回完整 NALU。

### 模块 2：Jitter Buffer（视频侧，**B 层**）

| 项目 | 内容 |
|------|------|
| **对应 libwebrtc 路径** | `modules/video_coding/packet_buffer.cc` + `frame_buffer2.cc` + `jitter_estimator.cc` |
| **要实现的功能** | ① 按 RTP 序号入队、检测乱序；② 帧完整性判定（一帧的所有分片包是否到齐）；③ 抗抖估计（动态 buffer 深度 = 抖动估计 + 解码延迟 + 渲染延迟）；④ 超时丢弃 + 反馈给 NACK 模块 |
| **要砍掉的特性** | ① NACK 重传策略由调用方实现（我们只暴露"哪些 SeqNum 丢了"接口）；② FEC 恢复不做；③ 只处理视频（音频 NetEQ 太复杂，超出本项目范围）；④ 简化抗抖算法——不实现完整 Kalman 滤波，用 EWMA 移动平均近似 |
| **预计代码量** | 头文件 ~150 行，实现 ~400 行，单元测试 ~200 行 |
| **测试方式** | ① 单元测试：构造乱序/丢包/分片场景验证状态机；② 性能测试：模拟 1% 丢包 + 50ms 抖动，测量 buffer 深度动态变化；③ 对比 libwebrtc：相同输入下，自己实现的 buffer 深度 vs libwebrtc 的，画图对比 |
| **面试讲述价值** | ★★★★★（Jitter Buffer 是 RTC 面试 TOP 3 高频题）|

### 评估替代选择（不采纳）

| 候选 | 评估结论 |
|------|---------|
| **NACK 状态机** | 工作量太小（< 200 行），算法不够厚，面试讲不出深度；建议作为 Jitter Buffer 的附属逻辑顺带实现 |
| **Pacer（码率平滑发送）** | 算法不错（漏桶 + token bucket），但**和拥塞控制强耦合**，单独实现讲不通；放到 V2 阶段如果有时间可加 |
| **简化版 ICE Lite 客户端** | 工作量大（要处理 STUN binding、UDP socket、NAT 类型探测），但**网络层面试占比远低于媒体层**，性价比低 |
| **拥塞控制 GCC** | 太复杂（延迟梯度 + 卡尔曼滤波 + 速率控制器三层），3 周做不完；建议只读源码不实现 |

### 最终 B 层模块清单

✅ **RTP 打包/解包器**（含 H264 FU-A）  
✅ **视频 Jitter Buffer**（含抗抖估计 + 完整性判定）

总代码量约 **800-1000 行 C++ + 350 行单元测试**，工期预估 **2-3 周**。

### 模块清单（8 个顶层模块）

| 编号 | 模块名 | A 层 / B 层 / 只读 | 职责一句话 |
|------|-------|-------------------|-----------|
| M1 | 信令模块 SignalingChannel | **A 层**（WebSocket + JSON）| SDP/ICE 候选交换、房间管理 |
| M2 | 媒体采集模块 MediaSource | **A 层**（libwebrtc）| 摄像头采集、麦克风采集 |

### 关键依赖原则

1. **M8（API 层）是唯一的对外门面**：App 只 include 一个头文件、只看见 M8 的接口。
2. **M4 / M6 是核心数据面**：发送链路 `M3 → M4 → M5 → 网络`，接收链路 `网络 → M5 → M4 → M6 → M3 → 渲染`，**B 层重写就替换在这两个节点**。
3. **M1（信令）独立于媒体面**：信令模块只负责把 SDP/ICE 在两端"复制粘贴"，不参与媒体数据流——这是控制面与数据面的分离。
4. **M7（拥塞控制）反向反馈**：M7 不在数据流主链路上，而是观察 M4 的发送统计（packet loss / RTT / 拥塞窗口），反馈给 M3 调整编码码率。

## 4. 设计模式落地

每个核心模块用了哪些设计模式，**重点是"为什么用"，不是"用了就好"**。

### 4.1 工厂模式（Factory）—— M8 PeerConnectionAPI

```cpp
class PeerConnectionFactory {
public:
    static std::unique_ptr<PeerConnectionFactory> Create(
        const FactoryConfig& factoryConfig);

    std::unique_ptr<PeerConnection> CreatePeerConnection(
        const PeerConnectionConfig& peerConfig,
        PeerConnectionObserver* observer);
    // ... CreateVideoTrack / CreateAudioTrack / ...
};
```

**为什么用工厂**：PeerConnection 的创建涉及多个内部组件初始化（线程池、编解码器列表、ICE 配置），用户不应该（也无法正确地）直接 new。工厂模式：① 把"创建复杂对象"和"使用对象"分离；② 集中管理共享资源（线程池只创建一次）；③ 方便测试时替换为 Mock 工厂。

**libwebrtc 对应**：`api/peer_connection_interface.h` 里的 `PeerConnectionFactoryInterface`。

### 4.2 观察者模式（Observer）—— M1 信令 / M8 API 回调

```cpp
class PeerConnectionObserver {
public:
    virtual void OnIceCandidate(const IceCandidate& candidate) = 0;
    virtual void OnTrackAdded(std::shared_ptr<MediaStreamTrack> track) = 0;
    virtual void OnConnectionStateChanged(ConnectionState newState) = 0;
    virtual ~PeerConnectionObserver() = default;
};
```

**为什么用 Observer**：WebRTC 是**异步事件驱动**模型——ICE 候选何时收集完、远端何时加入轨道、连接何时建立，时机都不确定。Observer 让调用方注册回调，事件发生时 PeerConnection 主动通知，避免轮询。**对比方案**：Promise/Future——只能表达"一次性结果"，不适合连续事件流。

**面试常追问**："Observer 跨线程怎么投递？" 答：libwebrtc 里观察者的回调**默认在 signaling thread 触发**，调用方如果要在主线程更新 UI，要自己 PostTask 切线程。

### 4.3 策略模式（Strategy）—— M3 编解码器抽象

```cpp
class VideoEncoder {
public:
    virtual int32_t Encode(const VideoFrame& inputFrame,
                           std::vector<EncodedImage>* outputBitstream) = 0;
    virtual int32_t SetRates(const RateControlParameters& rateParams) = 0;
    virtual EncoderInfo GetEncoderInfo() const = 0;
    virtual ~VideoEncoder() = default;
};

class H264Encoder : public VideoEncoder { /* ... */ };
class VP8Encoder  : public VideoEncoder { /* ... */ };
class HardwareH264Encoder : public VideoEncoder { /* 调 VideoToolbox */ };
```

**为什么用 Strategy 不用模板**：① 编码器选择是**运行时决定**的（SDP 协商后才知道选 H264 还是 VP8），模板要求编译期确定，不合适；② Strategy 接口可以让 App 注入自定义编码器（例如用户接入第三方 SDK），模板做不到；③ 虚函数调用的开销可忽略（编码一帧本身就是 ms 级，虚表查找 ns 级）。

**libwebrtc 对应**：`api/video_codecs/video_encoder.h`，`VideoEncoderFactory::CreateVideoEncoder(format)` 配合 Strategy 使用。

### 4.4 管线模式（Pipeline / Chain of Responsibility）—— M3 → M4 → M5 数据流

```
VideoFrame ──▶ [Encoder] ──▶ EncodedImage ──▶ [RtpPacketizer] ──▶ RtpPacket ──▶ [SRTP] ──▶ UDP
```

**为什么用 Pipeline**：媒体数据流是**单向、逐级变换**的——每一级输入一个数据类型、输出另一个。Pipeline 让每一级专注自己的职责（编码器只管编码、打包器只管打包），各级可独立替换/测试。

**对比方案**：直接函数嵌套调用？耦合太重，新加一级要改所有调用方。**消息队列？** 对延迟敏感的实时通信不适合（每级入队出队都加几 ms）。**libwebrtc 实际方案**：用回调链 + Sink 接口，每级实现 `OnFrame(...)`，输出时调下一级的 sink。

### 4.5 命令模式 + Active Object —— 跨线程通信

```cpp
worker_thread->PostTask(ToQueuedTask([this, frame]() {
    EncodeAndSend(frame);  // 在 worker thread 执行
}));
```

**为什么用 PostTask 不用直接调用**：WebRTC 严格三线程模型（signaling/worker/network），跨线程直接访问对方成员会触发数据竞争。PostTask 把"调用"打包成命令对象、扔到目标线程的任务队列，目标线程串行执行——本质是 **Active Object 模式**。

**对比方案**：① 加锁？libwebrtc 的设计哲学是"用线程亲和性避免锁"，因为锁会增加延迟和复杂性；② `Invoke`（同步等待）？只在必须拿到返回值时用，**性能差**（阻塞当前线程）。

**面试常追问**："为什么 libwebrtc 不全用无锁队列？" 答：PostTask 底层就是无锁队列 + 条件变量，已经接近最优；全无锁会让回调链路被打散，调试和异常处理复杂度爆炸。

### 4.6 适配器模式（Adapter）—— M4 RtpTransport 对接 libwebrtc

**特殊背景**：B 层重写的 M4 RtpTransport 要替换 libwebrtc 内部的 `RtpPacketizer`/`RtpDepacketizer`，但 libwebrtc 的接口和我们想要的 C++ 接口不完全一致——用适配器在中间转换。

```cpp
class LibwebrtcRtpAdapter : public RtpPacketizer {  // libwebrtc 接口
public:
    LibwebrtcRtpAdapter(std::unique_ptr<MyRtpPacketizer> myPacketizer);
    bool NextPacket(RtpPacketToSend* outPacket) override {
        return myPacketizerImpl_->FillNextRtpPacket(outPacket);
    }
private:
    std::unique_ptr<MyRtpPacketizer> myPacketizerImpl_;
};
```

**为什么用 Adapter**：B 层我们想要自己的接口签名（更现代的 C++17 风格、用 `std::span` 替代裸指针），但又要插到 libwebrtc 的发送流水线里——Adapter 是改造侵入最小的方案。

## 5. 关键接口契约

只给**抽象类签名**，不写实现。**重点是接口设计取舍**：同步 vs 异步、回调 vs Promise、内存所有权。

### 5.1 ISignalingChannel（信令通道）

```cpp
class ISignalingChannel {
public:
    enum class SignalType {
        kJoinRoom, kLeaveRoom, kSdpOffer, kSdpAnswer, kIceCandidate
    };

    struct SignalMessage {
        SignalType type;
        std::string remotePeerId;
        std::string payload;  // JSON 字符串（SDP / ICE candidate JSON）
    };

    class Observer {
    public:
        virtual void OnSignalReceived(const SignalMessage& receivedMessage) = 0;
        virtual void OnSignalingStateChanged(SignalingState newState) = 0;
        virtual ~Observer() = default;
    };

    virtual bool Connect(const std::string& signalingServerUrl) = 0;
    virtual void Disconnect() = 0;
    virtual bool SendSignal(const SignalMessage& outgoingMessage) = 0;
    virtual void SetObserver(Observer* observer) = 0;
    virtual ~ISignalingChannel() = default;
};
```

**设计取舍**：
- **异步而非同步**：`SendSignal` 立刻返回（只入队），实际发送由内部线程做。WebSocket 网络延迟不可控，同步阻塞会让调用方挂死。
- **回调而非 Promise**：信令是**多次事件流**（接收任意多消息），不适合一次性 Promise。
- **payload 用 string 而非强类型 struct**：SDP/ICE 的 JSON schema 由业务定义，接口层不该绑死格式——把序列化责任留给上层，便于扩展自定义信令字段。
- **内存所有权**：`observer` 是裸指针，**生命周期由调用方保证**——典型用法是 PeerConnection 持有 Observer，PeerConnection 销毁前先 `SetObserver(nullptr)`。

### 5.2 IMediaSource（媒体源抽象）

```cpp
template<typename FrameType>
class IMediaSource {
public:
    class Sink {
    public:
        virtual void OnFrame(const FrameType& capturedFrame) = 0;
        virtual ~Sink() = default;
    };

    virtual bool Start() = 0;
    virtual bool Stop() = 0;
    virtual void AddSink(Sink* downstreamSink) = 0;
    virtual void RemoveSink(Sink* downstreamSink) = 0;
    virtual MediaSourceState GetState() const = 0;
    virtual ~IMediaSource() = default;
};

using IVideoSource = IMediaSource<VideoFrame>;
using IAudioSource = IMediaSource<AudioFrame>;
```

**设计取舍**：
- **Sink 模式而非返回值**：采集是**持续产出**的（30fps 摄像头每秒 30 帧），调用方用 sink 回调消费、不能用 `GetNextFrame()` 拉模式（会被 sleep 卡住）。
- **多 sink 支持**：一路摄像头数据可能同时给编码器 + 本地预览渲染器，所以 `AddSink` 支持多订阅者。
- **VideoFrame 内存所有权**：`OnFrame(const VideoFrame&)` 传 const 引用而非 unique_ptr——sink 如果需要保留帧，**自己拷贝或 ref**（libwebrtc 的 VideoFrame 内部 buffer 是引用计数的，shallow copy 即可）。

### 5.3 IRtpTransport（RTP 传输层，B 层重写的核心接口）

```cpp
class IRtpTransport {
public:
    struct SendOptions {
        uint8_t payloadType;
        uint32_t synchronizationSource;  // SSRC
        uint32_t rtpTimestamp;
        bool isLastPacketOfFrame;        // 用于 RTP marker bit
    };

    class PacketSentCallback {
    public:
        virtual void OnRtpPacketSent(uint16_t rtpSequenceNumber,
                                     size_t packetBytes) = 0;
        virtual ~PacketSentCallback() = default;
    };

    class PacketReceivedSink {
    public:
        virtual void OnRtpPacketReceived(
            const RtpPacket& receivedPacket) = 0;
        virtual void OnDepacketizedNalUnit(
            std::vector<uint8_t> reassembledNalu,
            uint32_t rtpTimestamp) = 0;
        virtual ~PacketReceivedSink() = default;
    };

    // 发送链路（FU-A 分片在内部完成）
    virtual int SendEncodedFrame(const EncodedImage& encodedFrame,
                                 const SendOptions& sendOptions) = 0;

    // 接收链路
    virtual int ReceiveRtpPacket(const uint8_t* packetBuffer,
                                 size_t bufferSize) = 0;

    virtual void SetSendCallback(PacketSentCallback* sendCallback) = 0;
    virtual void SetReceiveSink(PacketReceivedSink* receiveSink) = 0;
    virtual ~IRtpTransport() = default;
};
```

**设计取舍**：
- **入参 / 出参分离**：发送用 `SendEncodedFrame` 一次性提交一帧（内部决定拆几个 RTP 包），不让调用方关心分片细节；接收侧分两个回调——`OnRtpPacketReceived`（每个 RTP 包都触发，给 NACK 模块用）和 `OnDepacketizedNalUnit`（一帧重组完成才触发，给 Jitter Buffer 用）。
- **裸指针 + 长度**而非 `std::vector<uint8_t>`：接收链路热路径，避免每个包都 vector 分配——零拷贝。**所有权约定**：buffer 只在调用期间有效，sink 要保留必须自己拷贝。
- **没有 RTCP**：RTCP 反馈（接收报告、NACK）由独立模块处理，IRtpTransport 只管 RTP。

### 5.4 IJitterBuffer（视频抖动缓冲，B 层重写）

```cpp
class IJitterBuffer {
public:
    enum class InsertResult {
        kInserted,         // 成功插入
        kDuplicate,        // 重复包，已丢弃
        kTooOld,           // 太老，已超过 buffer 窗口
        kBufferFull        // 缓冲满（异常情况）
    };

    struct CompletedFrame {
        std::vector<uint8_t> nalUnitData;
        uint32_t rtpTimestamp;
        uint16_t firstSequenceNumber;
        uint16_t lastSequenceNumber;
        bool isKeyFrame;
        int64_t renderTimeMillis;  // 调度的渲染时刻
    };

    class FrameReadyObserver {
    public:
        virtual void OnFrameReady(CompletedFrame readyFrame) = 0;
        virtual void OnPacketLossDetected(
            uint16_t firstMissingSeq, uint16_t lastMissingSeq) = 0;
        virtual ~FrameReadyObserver() = default;
    };

    virtual InsertResult InsertPacket(const RtpPacket& incomingPacket) = 0;
    virtual int64_t GetEstimatedJitterMillis() const = 0;
    virtual int64_t GetTargetDelayMillis() const = 0;
    virtual void Reset() = 0;
    virtual void SetObserver(FrameReadyObserver* observer) = 0;
    virtual ~IJitterBuffer() = default;
};
```

**设计取舍**：
- **InsertResult 用枚举而非异常**：热路径不抛异常，调用方根据返回值决定后续动作（重复包统计、丢包反馈）。
- **CompletedFrame 用值传递（move）**：一帧只完整一次、所有权交给观察者，明确"用完就消费"语义，避免双方都持有引用产生悬空。
- **暴露 JitterMillis / TargetDelay 指标**：让上层做 QoS 监控（这两个值是面试常追问的，"你的 buffer 怎么调"）。
- **不暴露 NACK 重传策略**：JitterBuffer 只负责检测和上报丢包，**重传由独立模块决定**（避免职责膨胀）。

### 5.5 IPeerConnection（M8 对外门面）

```cpp
class IPeerConnection {
public:
    class Observer {
    public:
        virtual void OnLocalSdpCreated(SdpType type, const std::string& sdp) = 0;
        virtual void OnIceCandidateGathered(const IceCandidate& candidate) = 0;
        virtual void OnRemoteTrackAdded(std::shared_ptr<MediaStreamTrack> track) = 0;
        virtual void OnConnectionStateChanged(ConnectionState state) = 0;
        virtual ~Observer() = default;
    };

    virtual void CreateOffer(const SdpConstraints& constraints) = 0;
    virtual void CreateAnswer(const SdpConstraints& constraints) = 0;
    virtual void SetLocalDescription(SdpType type, const std::string& sdp) = 0;
    virtual void SetRemoteDescription(SdpType type, const std::string& sdp) = 0;
    virtual void AddIceCandidate(const IceCandidate& candidate) = 0;

    virtual void AddTrack(std::shared_ptr<MediaStreamTrack> localTrack) = 0;
    virtual void RemoveTrack(std::shared_ptr<MediaStreamTrack> localTrack) = 0;
    virtual void Close() = 0;
    virtual ~IPeerConnection() = default;
};
```

**设计取舍**：
- **所有调用都是"提交请求 + 回调通知"模式**：`CreateOffer` 不返回 SDP 字符串，而是触发 `OnLocalSdpCreated` 回调——因为 SDP 生成是异步的（需要 ICE 收集 candidates），不能阻塞调用方。
- **shared_ptr<MediaStreamTrack>**：track 可能同时被本地预览和远端发送共享，shared 语义自然。
- **没有 Pause/Resume**：通过 `track.Enabled = false` 表达暂停，避免接口膨胀（YAGNI）。

## 6. 可演进路线（MVP → V1 → V2）

每个阶段明确"做什么 / 不做什么 / 验收标准"，避免一开始就陷入细节。

### MVP（第 1-2 周）：跑通 1v1 通话

**做**：
- 编译 libwebrtc m120（macOS），跑通官方 peerconnection_client demo
- 写 C++ 信令服务（uWebSockets + JSON），支持 join / offer / answer / candidate 消息中转
- 写两个 Mac 客户端（命令行版本），互拨视频通话，能看到对方画面
- 部署 coturn（Docker），保证跨网穿透

**不做**：
- 不做 UI 美化、不做录制、不做多人会议
- 不替换任何 libwebrtc 内部组件
- 不做性能优化（先跑通再说）

**验收**：两台 Mac 在不同 WiFi 下能视频通话超过 60 秒，首帧时间 < 3s。

### V1（第 3-4 周）：B 层 RTP 模块重写

**做**：
- 实现 M4 RtpTransport（B 层模块 1），含 H264 FU-A 打包/解包 + 单元测试
- 通过 Adapter 注入到 libwebrtc 发送链路
- 跑通"自己打包的 RTP 包 → libwebrtc 接收侧能解码"的端到端测试
- 写一份"和 libwebrtc 实现差异对比"文档

**不做**：
- 不实现 NACK / FEC（留到 V2）
- 不支持 VP8/VP9（只 H264）
- 不替换接收侧的 Depacketizer（先单向替换发送，降低风险）

**验收**：使用 B 层 RTP 打包器后，1v1 视频通话仍能正常进行 60 秒；丢包率 < 1%。

### V2（第 5-6 周）：B 层 Jitter Buffer 重写 + 性能 benchmark

**做**：
- 实现 M6 JitterBuffer（B 层模块 2），含完整性判定 + EWMA 抗抖估计 + 丢包检测
- 替换 libwebrtc 接收侧的 PacketBuffer
- 写性能测试：模拟 0%/1%/5% 丢包 + 0/50/100ms 抖动，对比自实现 vs libwebrtc 的 buffer 深度、首帧时间、卡顿次数
- 完整跑一次端到端 demo 演示，录屏

**不做**：
- 不做音频 Jitter Buffer（NetEQ 太复杂，超出范围）
- 不做 SVC / Simulcast（V3 视情况）

**验收**：1% 丢包场景下，自实现 JitterBuffer 的卡顿次数 ≤ libwebrtc 的 1.5 倍（不要求超过，但要在同量级）；有一份带图表的性能对比报告。

### V3（可选，时间充裕再做）

- Pacer 实现（码率平滑发送）
- 简化的 NACK 状态机
- 录制功能（MP4 输出）

## 7. 项目面试讲述话术大纲

面试官说"介绍一下你这个项目"时的**3-5 分钟标准回答**：

### 开场（30 秒）
> "我做了一个基于 libwebrtc 的 1v1 视频通话项目，目标是吃透 WebRTC 的核心架构，并且**自己重写了两个关键模块**——RTP 打包器和视频 Jitter Buffer——来证明我能读懂 libwebrtc 源码并动手改造。"

### 架构层（1 分钟）
> "项目分 8 个顶层模块，最关键的是数据面的**控制面与数据面分离**：信令模块负责 SDP/ICE 交换（业务层 WebSocket + JSON），不参与媒体流；媒体面是 `采集 → 编码 → RTP 打包 → ICE/DTLS/SRTP → UDP → 接收 → Jitter Buffer → 解码 → 渲染`。线程上严格遵循 libwebrtc 的 signaling/worker/network 三线程模型，跨线程用 PostTask 投递任务避免锁竞争。"

### 难点 + 取舍（2 分钟，亮点段）
> "我重写的两个模块里，**Jitter Buffer 最有意思**。它要同时解决三件事：乱序重排（按 RTP SeqNum）、抗抖动估计（动态调整 buffer 深度）、帧完整性判定（一帧分成多个 RTP 包是否到齐）。我没完整实现 libwebrtc 的 Kalman 滤波，而是用 EWMA 移动平均近似抗抖估计——简化代价是抖动剧烈时收敛慢一拍，但代码量从 1500 行降到 400 行，**对面试讲述更友好**。"
>
> "RTP 打包器的难点是 **H264 FU-A 分片**：一个 NALU 大于 MTU（典型 1400 字节）时要拆成多个 RTP 包，每个包的 FU header 用 S/E 位标识起止。我跑了一组对比测试——自己的 packetizer 输出 vs libwebrtc 的 packetizer 输出在相同输入下字节相等，作为正确性验证。"

### 改进方向（30 秒）
> "现在的限制是没做 NACK 重传和 FEC，所以丢包率超过 3% 后画质明显劣化；后续打算补 NACK 状态机，并接入 transport-cc 反馈做拥塞控制。"

### 反问准备（备答）
- "Q: 你的 Jitter Buffer 用了 EWMA，那 libwebrtc 用 Kalman 的优势在哪？"  
  A: Kalman 能同时考虑系统状态和观测噪声，对突发抖动（比如 WiFi 切换）适应更快；EWMA 对稳态网络效果接近，但突发场景会有 100-200ms 的滞后。
- "Q: 为什么选 libwebrtc 不用 mediasoup？"  
  A: 目标是吃透 WebRTC 内部实现，libwebrtc 是源码最完整、面试参考价值最高的选择；mediasoup 抽象层厚，看不到底层。

### 简历版（4-6 行）
> **WebRTC 实时通信引擎实践**（C++17 / libwebrtc / CMake）  
> · 基于 libwebrtc m120 实现 1v1 视频通话，含 C++ WebSocket 信令服务、coturn TURN 中继  
> · **自实现 RTP 打包/解包模块（H264 FU-A 分片）**，与 libwebrtc 内置 packetizer 端到端字节对齐  
> · **自实现视频 Jitter Buffer**（EWMA 抗抖估计 + 完整性判定），1% 丢包下卡顿次数与 libwebrtc 同量级  
> · 撰写 8 个模块的源码阅读笔记 + 设计取舍文档，建立完整 RTC 引擎知识地图
