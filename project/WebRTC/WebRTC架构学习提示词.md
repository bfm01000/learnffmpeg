# WebRTC 架构自顶向下学习（面向 C++ 音视频面试）

> 使用方式：把下方分隔线之间的内容整段发给 AI（Claude / GPT 等）。
> 目标：通过「设计 + 实现一个 WebRTC 项目」的过程，把 WebRTC 原理、音视频知识、C++ 工程能力打通，最终能在面试里讲得清「架构、为什么这么设计、关键模块怎么协作」。

---

## 项目定位（执行硬约束，所有阶段都要遵守）

为了避免陷入"自己造一个 libwebrtc"的工期黑洞，本项目**明确分两层**：

- **A 层（必做载体）**：基于 libwebrtc / mediasoup / pion 等成熟库，做一个**1v1 视频通话最小 demo**（信令 + 媒体协商 + 1v1 通话 + 简单录制）。这是面试时"我有项目可以演示"的实物。
- **B 层（必做面试加分项）**:**自己动手重写 1-2 个核心模块**的简化版（默认选:**Jitter Buffer** + **RTP 解包/打包器**),每个模块 **200-500 行可运行 C++ 代码** + 单元测试。这是面试时"我读过源码、动手实现过关键算法"的证据。

> **A 层是讲故事的载体，B 层是讲细节的底气。** 任何阶段的产出都要能映射回 A/B 层的具体物。AI 在做模块下钻时，**禁止把整套 libwebrtc 复刻一遍**——只复刻 B 层选定的模块。

### 阶段零：音视频基础查漏（前置）

我承认 WebRTC 之外的音视频基础是薄弱项（YUV/PCM/NALU/PTS 这些概念"知道但讲不清"），但 C++ 音视频岗位面试**这块占比很大**，必须先补。

请你输出一份「**C++ 音视频基础 self-check 清单**」，覆盖：

1. **像素与采样格式**：YUV420P/NV12/NV21 内存布局、PCM 采样率/位深/通道、平面式 vs 打包式的区别与转换代价。
2. **编解码码流结构**：H264/H265 NALU 类型、SPS/PPS/IDR 关系、Annex-B vs AVCC、AAC ADTS vs ADIF、Opus 帧结构。
3. **容器与封装**：FLV / MP4 / TS / WebM 的差异，moov box 位置对秒开的影响。
4. **时间戳系统**：PTS / DTS / 时间基（time_base）、B 帧引入的乱序、音视频同步的三种策略（视频追音频 / 音频追视频 / 都对齐外部时钟）。
5. **FFmpeg 核心 API**：AVPacket / AVFrame / AVCodecContext / AVFormatContext 的生命周期、av_read_frame / avcodec_send_packet / avcodec_receive_frame 的流转、ref_count 内存模型。
6. **直播协议对比**：RTMP / HLS / WebRTC / SRT 各自的延迟、可靠性、协议栈差异（这是 RTC 岗面试爱考的对比题）。
7. **音频处理基础**：3A（AEC/AGC/ANS）干什么、Opus 的 SILK + CELT 双模、采样率重采样的常见坑。

**输出形式**：
- 每个知识点给"**面试官的高频提问**"+"**100-200 字标准答案**"+"**自检题：你能口述清楚吗？**(Y/N)"。
- 总数控制在 30-50 题之间，**优先覆盖面试高频**，不求大而全。
- 结尾给一张「**知识地图**」（ASCII），把上述 7 大类标出来，告诉我哪些已经在我面试文档里有了、哪些是空白需要补。

输出完阶段零后，**停下来问我**：「自检题里你打 N 的有哪些？需要先针对哪几个点深入展开再进阶段一吗？」

### 阶段一：架构总览（Big Picture）

请先输出一份「**WebRTC 整体架构方案**」，需要覆盖：

1. **核心分层**：把 WebRTC 拆成清晰的几层（例如 应用层 / API 层 / 媒体引擎层 / 网络传输层 / 平台适配层），讲清每一层的职责边界、谁依赖谁、谁不能反向依赖。
2. **关键对象与生命周期**：`PeerConnectionFactory`、`PeerConnection`、`MediaStreamTrack`、`RtpSender/Receiver`、`Transport`、`Call`、`Channel` 这些核心对象的关系，以及创建顺序、销毁顺序。
3. **线程模型**：Signaling Thread / Worker Thread / Network Thread 各自负责什么、为什么这样拆、跨线程怎么投递任务（`PostTask` / `Invoke`），以及面试常被追问的「为什么不全做成无锁 / 为什么要这么多线程」。
4. **核心数据流**：一帧视频从「采集 → 编码 → 打包 → 发送 → 接收 → 解包 → 解码 → 渲染」完整的链路图（用 ASCII 框图即可），把关键数据结构标出来：`VideoFrame`、`EncodedImage`、`RtpPacket`、`RtcpPacket`。
5. **关键能力地图**：ICE、DTLS、SRTP、SDP 协商、NACK / FEC / RTX、Jitter Buffer / NetEQ、GCC / BBR 拥塞控制、Simulcast / SVC —— 每个能力**属于哪一层**、**解决什么问题**、**面试出现频率**。

**输出形式**：先给一张总览框图（ASCII），再给一段 200-400 字的「整体设计哲学」概述，最后列出本阶段你打算回答的「面试视角问题」（例如：为什么 WebRTC 要把网络线程和工作线程拆开？SDP 协商为什么要分 Offer/Answer？）。

输出完阶段一后，**停下来问我**：「是否进入阶段二？有没有想先深入的点？」

### 阶段二：项目设计方案（Top-down Design）

在我确认进入阶段二后，请输出**这个学习项目的设计方案**，要求自顶向下。**项目定位已经在文档顶部锁死**（A 层 demo + B 层重写 1-2 个核心模块），你不需要再让我选项目方向，**直接基于已锁定的 A/B 分层展开**：

1. **A 层 demo 技术栈选型**：给出 2-3 个候选技术栈的对比表（例如 libwebrtc native + WebSocket 信令 vs mediasoup C++ client + Node 信令 vs pion Go server + C++ 客户端），对比维度：上手难度 / C++ 占比 / 跨平台 / 面试讲述空间 / 文档资料丰富度。让我选一个。
2. **B 层重写模块的选定**：默认是 Jitter Buffer + RTP 解包/打包器；请你评估这个选择，如果有更合适的（例如 NACK 状态机、Pacer、简化版 ICE Lite），给出替换建议和理由。每个 B 层模块要明确：**对应 libwebrtc 哪个目录/文件**、**简化到什么程度**（哪些特性不做）、**预计代码量**、**怎么写单元测试验证**。
3. **顶层模块划分**：把项目拆成 5-8 个顶层模块（例如：信令模块 / 媒体采集模块 / 编解码模块 / RTP 传输模块 / 网络协商模块 / 拥塞控制模块 / 应用层 API），给出**模块依赖图**（DAG，不能有环），并明确每个模块**对外暴露的接口**和**内部隐藏的细节**。**每个模块要标注：A 层用现成库 / B 层自己实现 / 只读源码不实现**——三种状态之一。
3. **设计模式落地**：针对每个核心模块，说明用了哪些设计模式、**为什么**用（不是为了用而用）。例如：
  - `PeerConnectionFactory` 为什么是工厂模式？
  - `Observer` 模式在信令回调、媒体事件里的作用？
  - 编码器抽象用 Strategy 还是模板？
  - 线程间通信用 Command / Active Object 还是直接 PostTask？
  - 媒体管线用 Pipeline / Chain of Responsibility？
4. **关键接口契约**：用伪代码（C++ 抽象类签名即可，**不要写实现**）给出 3-5 个最核心的接口，例如 `IMediaSource`、`IEncoder`、`ITransport`、`ISignalingChannel`，并讲清接口设计时的取舍（同步 vs 异步、回调 vs Promise、内存所有权）。
5. **可演进路线**：MVP → V1 → V2 三个阶段每一阶段做什么、不做什么，避免一开始就陷入细节。

**输出形式**：先文字方案，再画模块依赖图（ASCII），最后给「**本项目对应的面试讲述话术大纲**」——也就是面试时这个项目我可以怎么讲（3-5 分钟版本）。

输出完阶段二后，**停下来等我确认顶层方案、选定项目定位、再决定先深入哪个模块**。

### 阶段三：模块逐个下钻（Drill Down）

我每次会指定**一个模块**让你深入。对于该模块，请严格按以下顺序输出，**不许跳步**：

8. **面试问答映射**：列出该模块对应的 5-8 个高频面试题，每题给一段 100-200 字的口语化标准答案（参考我已有的「锁文档」「信号量文档」风格）。

## 通用规则（所有阶段都生效）

1. **设计先行**：任何代码 / 实现细节出现前，必须先有「方案 + 取舍」。
2. **结构化输出**：每一阶段先给目录 / 框图，再给正文，最后给「面试追问点」。
3. **不堆代码（A 层 / 阶段一二）**：示例代码控制在能讲清思路的最小量，重点在**为什么这样设计**。
4. **B 层代码必须可运行**：阶段三里被标记为 B 层的模块，**禁止只给伪代码**，必须输出可编译可跑测试的真实代码 + CMake + 单元测试。
5. **变量命名**：所有示例代码里禁止使用 lo / hi / i / j / tmp / buf 这类无语义缩写，必须用 `leftBoundary` / `rtpSequenceNumber` / `jitterEstimateMs` 这类自解释命名。**文档里讲解算法时也禁止用这类缩写。**
6. **输出文件**：每个阶段独立产出 markdown 文件，命名 `阶段X-主题.md`，统一放在 `project/WebRTC/` 目录下。阶段三每个模块独立一个文件 + 代码子目录。
7. **每阶段结束都要停**：用一行明确的提问结束（例：「是否进入阶段二？」），等我回复再继续。
8. **遇到我不懂的点**：用「类比 + 原理 + 一句话总结」的三段式讲解，不要直接抛术语。
9. **始终对齐面试目标**：每个知识点讲完都补一句「这个点面试官常用的提问方式是 ___，标准答案大概是 ___」。
10. **时间盒提醒**：每个阶段开头估算一下"这个阶段建议投入多少天"，让我心里有数，避免在某一阶段卡死。
11. **不要把整套 libwebrtc 复刻一遍**：阶段三的"实现部分"严格限定在 B 层选定的 1-2 个模块，其他模块只做"原理 + 源码笔记 + 接口骨架"，不输出完整实现代码。
