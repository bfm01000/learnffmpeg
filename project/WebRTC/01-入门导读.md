## 1. 先用一个场景把问题问清楚

打开微信，按下视频通话按钮，1 秒后你看到了对方的脸。

**先停一下，问自己**：

1. **数据从哪走的**？你的手机和对方手机不在同一个 WiFi 下，中间隔了几十个路由器——它们怎么找到彼此？
2. **数据走什么协议**？显然不是 HTTP（每秒打开关闭几十次连接太慢）。是 TCP 吗？也不对，TCP 丢包要等重传，视频会卡顿。
3. **如果中途丢了一个数据包怎么办**？视频卡一下？黑屏？花屏？
4. **如果你的网突然变慢了**？画质应该自动降下来，但不应该断开——这怎么做？
5. **怎么保证不被别人偷听**？
6. **30 帧的视频 + 48kHz 的音频怎么对上**？你不会想看到嘴型对不上声音的鬼畜画面。

**WebRTC 就是为了系统性解决这 6 个问题诞生的**。它不是"一个库"，是**一整套实时通信工程体系**。

## 2. WebRTC 出现的背景：2011 年的故事

### 2011 年之前的实时通信是什么样的？

- **Flash + RTMP**：浏览器里能用，但要装 Flash 插件，延迟 2-5 秒
- **SIP / RTP 私有栈**：电信级方案（运营商 VoIP 在用），技术门槛极高，普通开发者搞不定
- **Skype / QQ 等私有协议**：每家一套，不互通，开发者也用不了
- **Adobe Connect / Webex 闭源 SDK**：付费、慢、不开源

**核心痛点**：**浏览器里没有原生的实时通信能力**。想做一个网页视频通话，必须依赖 Flash 或专有插件。

### 2011 年 Google 做了什么？

- **2010 年**：Google 花 6800 万美元收购 **Global IP Solutions（GIPS）**——一家做 VoIP 引擎 20 年的瑞典公司，他们的代码当时是 Skype、QQ、Yahoo Messenger 的底层
- **2011 年 6 月**：Google **开源 WebRTC**，把 GIPS 的代码完全免费放出来
- **2011 年 10 月**：Chrome 23 内置 WebRTC API
- **2012-2017**：W3C 和 IETF 标准化——`getUserMedia` / `RTCPeerConnection` / `RTCDataChannel` 成为 Web 标准

### 这个开源动作有多重要？

**直接结果**：实时通信的技术成本从 "$1000 万 + 5 年" 降到 "免费 + 1 周"。

**后续效应**：

- **Discord**（2015）基于 WebRTC，做语音聊天爆火
- **Google Meet / Hangouts**：WebRTC 是亲儿子
- **Houseparty / Zoom Web 版**：WebRTC 入口
- **国内**：声网、即构、容联七陌，全部基于 WebRTC 二次开发
- **腾讯会议 / 钉钉 / 飞书音视频**：内核仍是 libwebrtc（虽然有大量魔改）

**现在的事实是**：你看到的任何"网页 / 移动端实时音视频"——99% 跑在 WebRTC 之上。

## 3. WebRTC 解决了哪 6 个核心问题

### 问题 1：怎么找到对方？（NAT 穿透）

**类比**：你和朋友同时在小区里，但他在 5 楼你在 8 楼，**门牌号你们各自只知道自己的**。

**技术现实**：你的手机在家庭路由器后面，公网 IP 是路由器的（不是你的）；朋友也一样。两台手机的真实 IP 互相不知道。

**WebRTC 解法**：

- **STUN 服务器**（小区门卫）：告诉你"从外面看你的地址是 X"
- **TURN 服务器**（中转站）：实在打洞失败时帮你们转发
- **ICE 协议**（探路算法）：尝试所有可能的路径，选最优的

**STUN、TURN、ICE 的分工**：
- **NAT 是最大障碍**：大多数手机和电脑都在路由器后面，只有内网地址，比如 `192.168.x.x`。这个地址在公网不可达，所以不能直接把它发给对方当通信地址。
- **STUN 负责发现公网视角地址**：客户端向 STUN 服务器发请求，STUN 服务器从公网视角告诉它："我看到你的地址是公网 IP + 端口"。这个地址叫 **Server Reflexive Candidate**，是打洞时的重要候选地址。
- **ICE 负责收集和测试候选路径**：WebRTC 会收集本地地址、STUN 发现的公网映射地址、TURN 中继地址，然后两端互相交换这些候选地址，逐个尝试连通性检查，最后选一条延迟低、能打通的路径。
- **TURN 是兜底方案**：如果 NAT 太严格，点对点打洞失败，双方就都连到 TURN 服务器，由 TURN 帮忙转发媒体。它可靠但成本更高，因为所有音视频流量都会经过服务器。
- **一句话记忆**：STUN 告诉你"外面看到我是谁"，ICE 负责"试哪条路能走"，TURN 负责"实在不行我帮你转发"。

> 一句话：WebRTC 不仅传数据，还**自带"找到对方"的协议栈**。

### 问题 2：怎么传又快又稳？（媒体传输）

**类比**：从北京寄包裹到上海——快递（UDP）快但可能丢；挂号信（TCP）慢但保证到。视频通话要的是"快递 + 重要丢件单独补寄"。

**技术现实**：

- TCP 有"队头阻塞"——丢一个包后面所有包都要等重传，视频会冻屏几秒
- UDP 直接发不保证可靠，但应用层可以**精挑细选哪些包必须补**

**WebRTC 解法**：

- **基于 UDP 的 RTP**（实时传输协议）：每个包标记时间戳和序号
- **NACK 选择性重传**：只补**关键帧**和**短时间内**丢的包
- **FEC 前向纠错**：额外发冗余数据，丢一两个包能直接恢复
- **Jitter Buffer**：接收端缓冲，吸收抖动

**为什么不是简单地用 TCP？**
- **实时音视频更怕"等"**：视频通话里，一个 200ms 前丢失的视频包即使后来补回来了，也可能已经错过播放时间。TCP 为了保证可靠，会等待丢包重传，容易造成后面的包一起堵住，这就是队头阻塞。
- **UDP 给 WebRTC 自己做取舍的空间**：UDP 不保证可靠，但延迟低。WebRTC 可以在应用层判断：这个丢包还来得及补，就发 NACK 请求重传；如果已经过了播放窗口，就干脆丢掉，避免为了旧包拖慢新画面。
- **RTP 负责给媒体包编号和打时间戳**：序列号能让接收端发现丢包，时间戳能让接收端知道什么时候播放。没有这些信息，接收端只能收到一堆 UDP 数据，无法正确排序和渲染。
- **NACK 和 FEC 是两种抗丢包方式**：NACK 是"发现丢了再请求补发"，适合 RTT 不高、还来得及补的场景；FEC 是"提前多发一点冗余数据"，适合轻微丢包但不想等待重传的场景。
- **Jitter Buffer 负责抗网络抖动**：网络包不是匀速到达的，有时快、有时慢。Jitter Buffer 会在接收端攒一点点数据，牺牲几十毫秒延迟，换来更平滑的播放。

> 一句话：WebRTC 用 UDP + 应用层选择性可靠传输，**牺牲一点点丢包换取极低延迟**。

### 问题 3：网突然变慢了怎么办？（拥塞控制 + 自适应）

**类比**：高速公路从 6 车道变 2 车道，你必须自己慢下来——但你不知道"慢下来"的最佳速度是多少。

**技术现实**：网络带宽实时变化（4G→3G、WiFi 切换、对方网卡满载），但发送端不知道。如果不自适应：① 发太快 → 路由器队列爆炸丢包；② 发太慢 → 画质降级。

**WebRTC 解法**：

- **GCC（Google Congestion Control）**：观测包的**到达延迟梯度**（变大 = 队列在涨）和**丢包率**，**联合估计**当前带宽
- **BBR**：基于"带宽 × 延迟 = 在途字节数"的数学模型估算（Google 后来推的更新算法）
- **编码器联动**：估计到带宽 1.5Mbps → 通知编码器把目标码率改成 1.5Mbps

**拥塞控制到底在控制什么？**
- **控制的是发送码率**：网络变差时，不是简单地"继续发然后祈祷"，而是主动降低视频编码码率，比如从 2Mbps 降到 800kbps，让链路不再被塞爆。
- **延迟上升往往比丢包更早出现**：路由器队列开始积压时，包还没丢，但到达时间会越来越晚。GCC 会观察包到达延迟的变化趋势，提前判断"队列正在变长"，从而及时降速。
- **丢包率是更强烈的拥塞信号**：如果已经开始大量丢包，说明网络承载不了当前发送速度，发送端需要更明显地降低码率。
- **编码器会跟着网络动态调整**：带宽充足时，可以提高分辨率、帧率、码率；带宽下降时，可能降低码率、降低分辨率、减少帧率，优先保证通话不断。
- **接收端反馈很关键**：发送端并不知道网络中间发生了什么，需要依赖 RTCP 反馈、接收侧统计和带宽估计结果来判断当前应该发多快。

> 一句话：WebRTC 持续探测网络容量，**实时通知编码器调整码率**。

### 问题 4：怎么不被偷听？（端到端加密）

**类比**：你打电话，运营商在线路上接个监听器就能听——除非你们说暗号。

**技术现实**：未加密的 RTP 包在公网传输，**任何中间节点都能截获**画面和声音。

**WebRTC 解法**：

- **DTLS**（基于 UDP 的 TLS）：建立加密通道，协商对称密钥
- **SRTP**（Secure RTP）：用 DTLS 协商出的密钥加密每个 RTP 包
- **强制**：WebRTC 不允许关闭加密，这是协议层的硬性要求

**DTLS 和 SRTP 的分工**：
- **RTP 本身不加密**：RTP 负责承载音频、视频数据，以及时间戳、序列号等传输信息。如果直接用明文 RTP 在公网传输，中间节点抓包后可能看到真实的声音和画面。
- **DTLS 负责握手和协商密钥**：DTLS 可以理解成"跑在 UDP 上的 TLS"。HTTPS 常用的是 TLS over TCP，而 WebRTC 媒体传输通常走 UDP，所以用 DTLS 来验证双方身份、协商加密算法，并生成后续 SRTP 使用的对称密钥。
- **SRTP 负责加密媒体包**：SRTP 是 Secure RTP，它用 DTLS 协商出的密钥对每个 RTP 包进行加密和认证。发送端把明文 RTP 变成 SRTP 密文包，接收端再解密还原成音视频数据。
- **一句话记忆**：DTLS 负责"商量钥匙"，SRTP 负责"拿钥匙锁住每个 RTP 媒体包"。

**关于"端到端加密"的边界**：
- 如果是浏览器点对点直连，中间网络节点只能看到 IP、端口、包大小、发送频率等信息，看不到音视频内容。
- 如果中间有 SFU/媒体服务器，通常是"客户端 A ↔ SFU"加密、"SFU ↔ 客户端 B"加密，SFU 可能会解密后再转发。要让 SFU 也看不到内容，需要额外的应用层端到端加密方案。

> 一句话：WebRTC 强制端到端加密，**中间人看到的只是密文**。

### 问题 5：音画怎么同步？

**类比**：电影院的画面和声音不同步会让人难受——视频通话同样。

**技术现实**：视频时间戳基（90kHz）和音频时间戳基（48kHz）不一样、网络抖动也不一样。如果各自渲染，必然失同步。

**WebRTC 解法**：

- **RTCP SR**（Sender Report）：发送端定期把"NTP 墙钟时间 ↔ RTP 时间戳"的映射发给接收端
- **接收端用 NTP 时钟做基准**：视频和音频都根据 NTP 时间渲染，自动对齐
- **常见策略**：视频追音频——人耳对音频中断比对视频丢帧敏感得多

**NTP 和 RTP 的含义**：

- **RTP 时间戳**：媒体流自己的播放时间（分为音频RTP 和 视频RTP）。比如音频采样率 48kHz，RTP 时间戳每秒增加 48000；视频常用 90kHz，RTP 时间戳每秒增加 90000。它告诉接收端"这一帧在本路媒体流里应该什么时候播放"，但音频和视频的 RTP 时间基不同，不能直接拿来比较。
- **NTP 时间**：接近真实世界的墙钟时间，可以理解成"现在是几点几分几秒"这条统一时间轴。RTCP SR 会告诉接收端：某个 RTP 时间戳对应发送端的某个 NTP 时间。
- **映射关系的作用**：例如音频 `RTP timestamp = 96000` 和视频 `RTP timestamp = 180000` 都对应 `NTP = 10:00:02.000`，接收端就知道这段音频和这帧视频属于同一个真实时间点，于是可以按同一条 NTP 时间轴渲染，实现音画同步。

> 一句话：WebRTC 用 NTP 墙钟做共同时间基准，把两路独立的媒体流拉到同一时间轴。

### 问题 6：怎么跨平台统一？

**类比**：你写一个网页能在 Chrome / Firefox / Safari 上跑，是因为它们都实现 HTTP 标准。

**技术现实**：浏览器、iOS App、Android App、桌面 App 的实时通信能力如果各家都自己实现，不可能互通。

**WebRTC 解法**：

- **统一 JS API**：`getUserMedia` / `RTCPeerConnection` / `RTCDataChannel`，Chrome / Firefox / Safari / Edge 都遵守
- **Native SDK**：libwebrtc（C++）提供 iOS / Android / Windows / macOS / Linux 一致 API
- **W3C + IETF 双标准化**：JS API 归 W3C，协议归 IETF

**跨平台统一具体统一了什么？**
- **应用层 API 统一**：网页开发者不用关心底层摄像头驱动、声卡、UDP socket、NAT 穿透细节，只需要调用 `getUserMedia` 获取音视频，再用 `RTCPeerConnection` 建立连接。
- **协议层互通**：Chrome、Safari、Firefox、移动端 App 只要遵守 SDP、ICE、DTLS、SRTP、RTP/RTCP 等标准，就可以互相通话，而不是每家公司各写一套私有协议。
- **Native 端复用同一套内核**：移动端和桌面端通常直接集成 libwebrtc。它把采集、编解码、回声消除、拥塞控制、传输、安全等复杂模块封装起来，业务侧主要关注房间、信令、权限和 UI。
- **信令没有被 WebRTC 强制规定**：WebRTC 统一的是媒体能力和传输协议，但"怎么交换 offer/answer、怎么进房间、怎么鉴权"由业务自己决定，可以用 WebSocket、HTTP、MQTT 或自研信令服务。
- **一句话记忆**：WebRTC 把实时音视频的底层能力标准化，但把业务流程留给应用自己设计。

> 一句话：WebRTC 是**唯一的跨平台实时通信标准**——浏览器原生支持、Native SDK 完整。

### 关键观察

1. **数据面 vs 控制面分离**：信令通道（上方虚线）独立于媒体流——你可以用任何方式实现信令（WebSocket / HTTPS / 业务自定义）
2. **媒体引擎左 + 网络传输右**：左侧管"处理什么"（编解码、抗抖），右侧管"怎么传"（加密、穿透、拥塞）
3. **RTP 是窄腰**：上下两层之间唯一的数据格式——所有媒体最终都变成 RTP 包

## 5. 一次视频通话的完整流程

把场景具体化：**你（A）通过网页给朋友（B）打视频通话**。

### Step 1：建立信令通道（业务层）

A 和 B 都连接到你的业务服务器（WebSocket 是最常见的）。这是**业务自己实现的**——WebRTC 不规定信令协议。

### Step 2：A 发起呼叫，生成 SDP Offer

A 的浏览器调 `createOffer()` 生成一段 **SDP 文本**（Session Description Protocol），描述"我支持哪些编码、我的临时地址有哪些"：

```
v=0
o=- 12345 2 IN IP4 192.168.1.10
s=-
...
m=video 9 UDP/TLS/RTP/SAVPF 96
a=rtpmap:96 H264/90000
a=fingerprint:sha-256 AB:CD:...
a=candidate:1 1 UDP 2113929471 192.168.1.10 60001 typ host
...
```

**关键信息**：

- 支持的编码（H264）
- ICE candidate（候选地址）
- DTLS 指纹（加密身份）

### Step 3：通过信令通道把 SDP 发给 B

A 把 SDP 文本通过 WebSocket 发给业务服务器，服务器转发给 B。

### Step 4：B 收到 Offer，生成 Answer

B 的浏览器 `setRemoteDescription(offer)` + `createAnswer()` → 生成 B 自己的 SDP，包含 B 能接受的能力子集。

通过信令通道发回给 A。

### Step 5：双方进行 ICE 连通性检查

A 和 B 同时开始：

- 把对方 SDP 里的 candidate 加进来：`addIceCandidate(...)`
- 同时把自己的 candidate 通过信令发给对方
- 双方互相发"connectivity check"小包，看哪条路径通

可能的路径：

1. **本地直连**（同一 WiFi 下）：最快
2. **STUN 反射地址**：穿透 NAT
3. **TURN 中继**：实在打不通就走中转

最终选一条最优路径。

### Step 6：DTLS 握手

ICE 选定路径后，双方在这条路径上跑 DTLS 握手——交换证书、协商 SRTP 密钥。

### Step 7：媒体流开始传输

A 的摄像头采集 → H264 编码 → 拆成 RTP 包 → SRTP 加密 → 通过 ICE 选定的 UDP 通道发给 B。

B 接收：UDP 包 → SRTP 解密 → RTP 包 → Jitter Buffer → 拼成完整帧 → H264 解码 → 渲染。

同时：

- 双方互发 RTCP 报告（接收状态、丢包率）
- 拥塞控制实时调整码率
- 丢包触发 NACK 重传

### Step 8：通话结束

A 调 `close()`，发 RTCP BYE 通知 B，关闭 ICE 通道。

## 6. 5 个最关键的技术点（建立直觉）

### 6.1 SDP / ICE：怎么找到对方 ⭐⭐⭐

**SDP 是什么**：一段**文本格式**的描述（不是协议！）——双方互相告诉对方"我支持什么、我的地址是什么"。

**ICE 是什么**：一个**算法**——基于双方 SDP 里的 candidate 列表，尝试所有可能的路径，选最优的。

**关键术语**：

- **Host candidate**：本地 IP（如 192.168.1.10）
- **Server reflexive (srflx)**：通过 STUN 服务器看到的公网 IP（NAT 后的反射地址）
- **Relayed candidate**：TURN 中继地址（实在打不通时备用）

**面试坑点**：很多人以为 "SDP 是协议"——其实 SDP 只是**描述格式**（像 JSON）。信令协议是业务自己定的。

### 6.2 RTP / RTCP / SRTP：怎么传输媒体 ⭐⭐⭐⭐⭐

**RTP**：实时传输协议（RFC 3550）。每个包 12 字节头 + 载荷。头里关键字段：

- Sequence Number（接收端排序）
- Timestamp（同步用）
- SSRC（流标识）
- Marker（一帧最后一个包）

**RTCP**：RTP 的"反馈通道"——接收端每隔几秒发统计信息（丢包率、抖动、RTT）给发送端。

**SRTP**：加密版的 RTP，密钥来自 DTLS 握手。

**详细的细节看 M4 文档**——你已经做过这个模块。

### 6.3 Jitter Buffer：怎么抗抖动 ⭐⭐⭐⭐⭐

**类比**：你坐公交车，公交不是按固定间隔来——但公交车站会**让先来的人等一会儿**，**凑够人 / 到点了再发车**。

**Jitter Buffer 干的事**：

- 主动缓冲 N 毫秒（典型 80ms）
- 按 RTP 时间戳重排乱序的包
- 抗丢包：Marker 丢了用副信号判定
- 抗抖动：动态估计抖动大小，调整缓冲深度

**详细的细节看 M6 文档**——你已经做过这个模块。

### 6.4 拥塞控制：怎么自适应带宽 ⭐⭐⭐⭐

**问题**：你不知道当前网络真实能跑多快。

**GCC（Google Congestion Control）**：

- 观测 **包到达的延迟梯度**——如果间隔越来越大，说明路由器在排队，离丢包不远
- 观测**丢包率**——已经丢了
- 用**卡尔曼滤波**联合估计带宽
- 反馈给编码器调整码率

**BBR（Bottleneck Bandwidth and Round-trip propagation）**：Google 后来推的更新算法，核心是估算"瓶颈带宽 × 最小 RTT = 在途字节数"。

**面试常考**：GCC vs BBR 区别、为什么 RTP 用 UDP 不用 TCP。

### 6.5 编解码：H264 / Opus 为什么是默认 ⭐⭐⭐

**H264（视频）**：

- 硬件覆盖率最高（几乎所有设备硬解硬编）
- 延迟低（关 B 帧后可降到 33ms）
- 压缩效率中等（不如 H265/AV1，但够用）

**Opus（音频）**：

- **WebRTC 标准强制必选**（RFC 7587）
- 双模融合（语音用 SILK，音乐用 CELT）
- 延迟极低（5ms 帧时端到端 22ms）
- 抗丢包能力强（内置 FEC / PLC）

**为什么不用更新的**：实时通信对硬件覆盖率敏感——H265 在 iOS 上好但 Android 差，AV1 软编 CPU 占用太高。

## 7. 新人最容易踩的 7 个坑

### 坑 1：以为 WebRTC = 浏览器 API

**错觉**：WebRTC 就是 `getUserMedia` 那个 JS API。

**事实**：JS API 是冰山一角。背后是 **libwebrtc 上百万行 C++ 代码**——做 RTC 引擎开发的人 99% 的时间在和 C++ 打交道。

**避坑**：要做 RTC 工程师，必须深入 libwebrtc 内部，不能只学浏览器 API。

### 坑 2：以为 P2P 直连不需要服务器

**错觉**：WebRTC 是端到端，不需要服务器。

**事实**：至少需要**三种服务器**——

- 信令服务器（你自己写）：交换 SDP
- STUN 服务器：探测公网 IP
- TURN 服务器：穿透失败时中继

**避坑**：项目落地前先规划好这三类服务的部署，特别是 TURN（成本高，需要带宽）。

### 坑 3：编译 libwebrtc 卡 1 周

**错觉**：clone 源码 + cmake build 完事。

**事实**：libwebrtc 用 **GN + Ninja 不是 CMake**；依赖 depot_tools；macOS / Windows 都有专属坑；编译一次 2-4 小时；内存吃 16GB+。

**避坑**：学习项目**直接用预编译产物**（CocoaPods 的 GoogleWebRTC / shiguredo 的 webrtc-build），不要自己编。

### 坑 4：时间戳搞错（视频 90kHz vs 音频 48kHz）

**错觉**：RTP 时间戳就是"什么时候发送的"，单位是毫秒。

**事实**：RTP 时间戳的单位是**媒体时钟**（视频 90kHz 一秒走 90000；音频 48kHz 一秒走 48000）；初始值是**随机数**（防攻击）；32 位会**wraparound**。

**避坑**：跨流对齐用 RTCP SR 报文里的 NTP-RTP 映射，绝对不能直接比较两路流的 RTP 时间戳。

### 坑 5：以为关闭 B 帧就解决了延迟

**错觉**：B 帧引入解码延迟，关掉就够低延迟了。

**事实**：B 帧只是延迟的一小部分。真正的大头是 **Jitter Buffer 缓冲（80-200ms）** + **拥塞控制反馈（一个 RTT）** + **解码 / 渲染管线（30-50ms）**。

**避坑**：低延迟优化要全链路看，不要只盯着编码器。

### 坑 6：忽略线程模型

**错觉**：libwebrtc 内部线程随便用。

**事实**：libwebrtc 严格三线程——**Signaling Thread / Worker Thread / Network Thread**。跨线程访问对方成员**必须用 PostTask**，否则数据竞争。这是面试高频题。

**避坑**：用 libwebrtc API 时遵守线程亲和性，回调里改 UI 要切回主线程。

### 坑 7：以为字节序无关

**错觉**：x86 和 ARM 都是小端，字节序不用管。

**事实**：RTP 头是**大端网络字节序**。直接 struct + memcpy 在 x86/ARM 上字段全反。

**避坑**：手动用 `(value >> 8) & 0xFF` 这类位移读写，或者用 `htons` / `ntohs`（但 Windows 要 link winsock）。

- ❌ **DTLS 握手**：怎么协商 SRTP 密钥（中等难度）
- ❌ **拥塞控制**：GCC / BBR 怎么估带宽（**很难，面试重灾区**）
- ❌ **编解码**：H264 / Opus 内部细节（很专的方向）
- ❌ **音频处理**：3A + NetEQ（**最难，超出本项目范围**）
- ❌ **渲染管线**：解码后怎么显示（平台相关）

### 优先级建议

如果你想找 RTC 工作，**接下来按这个顺序补**：

1. **拥塞控制（强推）**：面试高频、行业核心、难但有限
2. **信令 + ICE**：工程感强、容易做出 demo
3. **编解码**：方向化，看你是不是要专攻视频编码
4. **3A 音频**：方向化，看你是不是要专攻音频
