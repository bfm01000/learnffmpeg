## 0. 先看：转码器就是播放器的「镜像」

如果你做完了播放器，转码器会非常好懂——**前半段一模一样（demux→decode），后半段镜像翻转**：

```
播放器：  读包 → 解码 → YUV→RGB  → 送显示器(SDL)
转码器：  读包 → 解码 → 缩放YUV → 重新编码 → 写文件
                 └─ 一样 ─┘     └──── 镜像 ────┘
```

- **解码**用 `send_packet` / `receive_frame`（包→帧）。
- **编码**用 `send_frame` / `receive_packet`（帧→包）——**方向正好相反，但还是同一套 send/receive 状态机**。

这是这个项目最大的收获：编码和解码在 API 层面是对称的。

**这一版做的事**：把 1280×720 的 mp4 转成 **640×360 的 H.264 mp4**（降分辨率 + 用 CRF 重新压），顺带演示 06 笔记里的 CRF/preset。

| 步 | 干什么 | 核心对象 | 状态 |
|---|---|---|---|
| T1 | 打开输入、找视频流、建解码器 | `AVFormatContext`(输入) / 解码器 | ✅ |
| T2 | 缩放器 + 编码器(libx264) | `SwsContext` / 编码器 | ✅ |
| T3 | 输出容器 + 输出流 + 文件头 | `AVFormatContext`(输出) | ✅ |
| T4 | 转码循环 + flush + 写尾 | `send_frame`/`rescale_ts` | ✅ |

**构建 & 运行**：
```bash
cd project/9_Simplest_Transcoder
cmake -S . -B build && cmake --build build
./build/simplest_transcoder 输入.mp4 输出.mp4
```

## 第 T1 步：打开输入、找视频流、建解码器

**这步要解决什么**：和播放器 ①②③ 完全相同——把输入文件挂载、挑出视频流、建解码器。

**关键 API**：`avformat_open_input` / `avformat_find_stream_info` / `av_find_best_stream(…VIDEO…)` / `avcodec_find_decoder` / `alloc_context3` / `parameters_to_context` / `open2`。

**为什么这么写**：这部分在播放器讲解里已逐行讲过，不重复。唯一值得记的：**输入侧用 `avformat_open_input`（读）**，T3 的输出侧会用另一个函数（写），两者要分清。

**自检一问**：转码器和播放器的前三步有区别吗？
> 没有。demux + 建解码器是任何「要处理已有视频」的程序的共同开头。

## 第 T2 步：缩放器 + 编码器（libx264）

**这步要解决什么**：要把解码出的大帧缩小，并准备一个把 YUV 帧压成 H.264 的编码器。

**关键 API**
- `sws_getContext()` —— 同播放器⑤，但目标是「小一号的 YUV」而不是 RGB（编码器吃 YUV）。
- `avcodec_find_encoder_by_name("libx264")` —— 找编码器（按名字，因为同一个 H.264 有多个实现）。
- `av_opt_set(ctx->priv_data, "crf"/"preset", …)` —— 设 libx264 的私有参数。

**代码长什么样**
```cpp
// 缩放器:源尺寸/格式 → 640x360 YUV420P
scalerContext = sws_getContext(decoderContext->width, decoderContext->height, decoderContext->pix_fmt,
                               640, 360, AV_PIX_FMT_YUV420P, SWS_BILINEAR, nullptr, nullptr, nullptr);

// 编码器
const AVCodec *encoder = avcodec_find_encoder_by_name("libx264");
AVCodecContext *encoderContext = avcodec_alloc_context3(encoder);
encoderContext->width = 640; encoderContext->height = 360;
encoderContext->pix_fmt = AV_PIX_FMT_YUV420P;
encoderContext->time_base = inputVideoStream->time_base;   // 沿用输入流刻度,pts 能直接接力
encoderContext->framerate = inputVideoStream->avg_frame_rate;
encoderContext->gop_size = 12;                              // 关键帧间隔(见 05 §GOP)
av_opt_set(encoderContext->priv_data, "crf", "23", 0);     // 质量模式(见 06 §CRF)
av_opt_set(encoderContext->priv_data, "preset", "veryfast", 0);
encoderContext->flags |= AV_CODEC_FLAG_GLOBAL_HEADER;      // mp4 需要(见下)
avcodec_open2(encoderContext, encoder, nullptr);
```

**为什么这么写**
- **`find_encoder_by_name` 而不是 `by_id`**：H.264 编码有好几个实现（libx264 / 硬件 h264_videotoolbox 等），按 ID 找会给你默认那个；按名字能精确点名 libx264。
- **CRF vs 码率**：CRF（Constant Rate Factor）是「恒定质量」模式——你定质量（23 是常用默认，越小越清晰、文件越大），码率由内容复杂度自动浮动。这比直接定码率更省心，是 06 推荐的默认打法。
- **`time_base` 沿用输入流**：这样解码帧的 pts（输入流刻度）可以直接当编码帧的 pts，省一次换算。**但写进容器时还得换算成输出流刻度**（见 T4）。
- **`AV_CODEC_FLAG_GLOBAL_HEADER`**：mp4 要求把 SPS/PPS（解码必需的参数集）放在**容器文件头**里，而不是塞在每个数据包前。不设这个 flag，生成的 mp4 可能缺参数集、播不了。我们写死输出 mp4 所以直接设；通用写法是建完输出容器后判 `oformat->flags & AVFMT_GLOBALHEADER` 再决定。

**踩过的坑**：编码器的 `GLOBAL_HEADER` flag 必须在 `avcodec_open2` **之前**设，开了再设没用。

**自检一问**：CRF 模式下文件码率是固定的吗？
> 不是。CRF 固定的是「质量」，码率随画面复杂度浮动（复杂段码率高、简单段低）。要固定码率得用 CBR/ABR。

## 第 T3 步：建输出容器 + 加输出流 + 写文件头

**这步要解决什么**：编码器会吐 H.264 包，但包得装进一个容器（mp4）文件里。这步建「写出用」的容器、登记一路视频流、写文件头。

**关键 API**
- `avformat_alloc_output_context2()` —— 建输出容器（按 .mp4 后缀自动选封装格式）。
- `avformat_new_stream()` —— 在容器里加一路流。
- `avcodec_parameters_from_context()` —— 把编码器参数拷给流。
- `avio_open()` + `avformat_write_header()` —— 打开文件、写头。

**代码长什么样**
```cpp
avformat_alloc_output_context2(&outputFormatContext, nullptr, nullptr, outputPath);  // 按后缀推断
AVStream *outputStream = avformat_new_stream(outputFormatContext, nullptr);
avcodec_parameters_from_context(outputStream->codecpar, encoderContext);  // 编码器 → 流
outputStream->time_base = encoderContext->time_base;

if (!(outputFormatContext->oformat->flags & AVFMT_NOFILE))
    avio_open(&outputFormatContext->pb, outputPath, AVIO_FLAG_WRITE);
avformat_write_header(outputFormatContext, nullptr);
```

**为什么这么写**
- **`parameters_from_context` 方向和 T1 相反**：T1 是 `parameters_to_context`（流的图纸 → 解码器）；这里是 `from_context`（编码器 → 流的图纸）。一个读进来、一个写出去，方向正好镜像。
- **`avio_open` 才是真正创建文件**：`alloc_output_context2` 只是建内存里的结构，`avio_open` 才打开磁盘文件准备写。
- **`write_header` 之后 time_base 可能被改**：muxer 有自己偏好的时间刻度，写完头后 `outputStream->time_base` 可能变了。所以 **T4 写包时要用「写完头之后」的 time_base 来 rescale**，不能用之前缓存的值。

**自检一问**：`avformat_alloc_output_context2` 和 `avio_open` 各干了什么？
> 前者建容器的内存结构、按后缀定格式；后者打开磁盘文件准备写入。两步缺一不可。

## 第 T4 步：转码循环 ⭐（编码侧 + 时间戳换算）

**这步要解决什么**：把所有环节串起来跑——读包、解码、缩放、编码、写文件。

**关键结构**：两个嵌套的 send/receive。
- 解码：`send_packet(包)` → `receive_frame(帧)`
- 编码：`send_frame(帧)` → `receive_packet(包)`

**代码骨架**
```cpp
// 编码并写出(帧 → 包 → 写文件)
auto encodeAndWrite = [&](AVFrame *frame) {
    avcodec_send_frame(encoderContext, frame);          // frame=nullptr 时表示 flush
    while (avcodec_receive_packet(encoderContext, encodedPacket) >= 0) {
        // ★ 关键:编码器刻度 → 输出流刻度
        av_packet_rescale_ts(encodedPacket, encoderContext->time_base, outputStream->time_base);
        encodedPacket->stream_index = outputStream->index;
        av_interleaved_write_frame(outputFormatContext, encodedPacket);
        av_packet_unref(encodedPacket);
    }
};

// 解码 → 缩放 → 编码
auto decodeScaleEncode = [&]() {
    while (avcodec_receive_frame(decoderContext, decodedFrame) >= 0) {
        av_frame_make_writable(scaledFrame);
        sws_scale(scalerContext, decodedFrame->data, decodedFrame->linesize, 0,
                  decoderContext->height, scaledFrame->data, scaledFrame->linesize);
        scaledFrame->pts = decodedFrame->pts;    // sws 不搬时间戳,手动接力
        encodeAndWrite(scaledFrame);
        av_frame_unref(decodedFrame);
    }
};

// 主循环 + 两级 flush + 写尾
while (av_read_frame(inputFormatContext, inputPacket) >= 0) {
    if (inputPacket->stream_index == videoStreamIndex &&
        avcodec_send_packet(decoderContext, inputPacket) >= 0)
        decodeScaleEncode();
    av_packet_unref(inputPacket);
}
avcodec_send_packet(decoderContext, nullptr); decodeScaleEncode();   // flush 解码器
encodeAndWrite(nullptr);                                             // flush 编码器
av_write_trailer(outputFormatContext);                              // 写文件尾
```

**为什么这么写**
- **★ 时间戳必须 rescale**：这是转码**最容易错**的一环。编码器用「编码器 time_base」给包打时间戳，但容器流用的是「输出流 time_base」，两套刻度往往不同。不换算就会**快放/慢放/时间戳乱跳**。`av_packet_rescale_ts` 一次性把 pts/dts/duration 按比例换算好（见 05 §PTS-DTS）。
- **`sws_scale` 不搬 pts**：它只管像素，时间戳得你手动 `scaledFrame->pts = decodedFrame->pts` 接力，否则编码出来的帧没时间信息。
- **两级 flush，顺序不能反**：先 flush 解码器（把它攒着的帧解出来转码），**再** flush 编码器（把它攒着的包吐出来写）。编码器也会攒帧（B 帧前瞻），不 flush 会丢尾部几帧。
- **`av_frame_make_writable`**：`scaledFrame` 的缓冲每帧复用，写之前确保没被别处引用（写时复制 COW，见 01 §5.7）。
- **`av_interleaved_write_frame` 而不是 `av_write_frame`**：前者会按 dts 把多路流交织排序后再写（即使现在只有一路视频，习惯用它，将来加音频就不用改）。
- **`av_write_trailer` 不能省**：mp4 的 `moov`（索引等关键信息）在写尾时落地，漏了文件就损坏/不可播。

**踩过的坑 / 验证**
- 跑完报「写出 239 个视频包」——和输入帧数一致，说明没丢帧、flush 正确。
- `ffprobe` 看输出：`h264 / 640x360 / 239 帧 / 315KB→160KB`，分辨率确实降了、文件小了一半。
- `ffmpeg -i 输出.mp4 -f null -` 完整解码**零报错**，首帧抽出来是正确的 640×360 彩条——文件有效、画面对。

**自检一问**：为什么编码器吐出的包写进容器前要 `rescale_ts`？两级 flush 谁先谁后？
> 因为编码器 time_base 和输出流 time_base 往往不同，不换算时间戳会错乱。flush 先解码器后编码器——解码器的帧要先解出来喂给编码器，编码器才能把残余帧吐成包。

## 🎉 里程碑：编码侧打通

做完转码器，你就把 FFmpeg 的**两个方向都亲手写过了**：
- 播放器 = 解码方向（包→帧→显示）
- 转码器 = 解码 + **编码**方向（包→帧→缩放→帧→包→文件）

**下一步可做的**：
- 把音频也转码/拷贝进去（现在转码器丢了音频）——音频可以 stream copy（`av_packet_ref` 直接搬，不重编码）或重编码成 AAC。
- 试不同参数：改 CRF（18 更清晰 / 28 更小）、改分辨率、改 preset 看文件大小和耗时变化——这是体会 06 码控最直接的方式。
- 硬件编码（macOS 的 `h264_videotoolbox`）——见 07，可选。

## 附：一页速查（复习用）

| 你想确认… | 看哪步 | 一句话答案 |
|---|---|---|
| 转码和播放前半段一样吗 | T1 | 一样，都是 demux+解码 |
| 编码用哪对 API | T4 | `send_frame`/`receive_packet`（解码的镜像） |
| 按名字找编码器图啥 | T2 | 精确点名 libx264（同 H.264 有多个实现） |
| CRF 固定的是什么 | T2 | 质量，码率随复杂度浮动 |
| GLOBAL_HEADER 为何要设 | T2 | mp4 把 SPS/PPS 放容器头，不设可能播不了 |
| `from_context` vs `to_context` | T1/T3 | 读进来用 to(流→解码器)，写出去用 from(编码器→流) |
| 写头后要注意什么 | T3 | time_base 可能被 muxer 改，rescale 要用新值 |
| 转码最容易错的一环 | T4 | 时间戳没 rescale（编码器刻度→输出流刻度） |
| sws_scale 搬时间戳吗 | T4 | 不搬，要手动 `scaledFrame->pts = decodedFrame->pts` |
| 两级 flush 顺序 | T4 | 先解码器后编码器 |
| 漏了 write_trailer 会怎样 | T4 | mp4 缺 moov，文件损坏不可播 |
