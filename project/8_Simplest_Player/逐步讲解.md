## 环境准备 & 运行（先跑起来再看代码）

> 如果只是想看原理，可以跳过本节，直接从「全局地图」开始读。需要实际编译运行时再回来。

本播放器需要 **FFmpeg 开发库**（≥5.x，实际开发用 7.x）和 **SDL2**。

### 1. WSL2 上安装（本项目实际开发环境）

> 环境：**Windows 11 + WSL2 + Ubuntu 24.04**。Win11 自带 WSLg，SDL 窗口和音频可以直接透到 Windows 桌面，无需额外配置 X Server。

#### 1.1 安装 WSL2 + Ubuntu（如果还没装）

在 **Windows PowerShell（管理员）** 中：

```powershell
# 一键安装 WSL2 + Ubuntu（Win11 默认就是 WSL2）
wsl --install -d Ubuntu-24.04
```

重启电脑后，首次进入 Ubuntu 会提示创建用户名和密码。

> **已装过的**：确认是 WSL2 版本——`wsl -l -v` 看到 `VERSION` 为 `2` 就对了。如果是 WSL1，`wsl --set-version Ubuntu-24.04 2` 升级。

#### 1.2 进入 WSL2，安装编译工具和库

```bash
# 更新包列表（新装的 Ubuntu 先跑这一步）
sudo apt update

# 安装所有依赖
sudo apt install g++ cmake pkg-config \
                 libavformat-dev libavcodec-dev libavutil-dev \
                 libswscale-dev libswresample-dev \
                 libsdl2-dev
```

> **怎么确认装好了**：
> ```bash
> pkg-config --modversion libavformat   # 应输出类似 62.13.101
> pkg-config --modversion sdl2          # 应输出类似 2.30.0
> ```

#### 1.3 确认 WSLg 正常工作

WSLg 是 Win11 自带功能，WSL2 里的 GUI 应用会自动显示到 Windows 桌面，音频也会通过 PulseAudio 透传。验证：

```bash
# 能看到 $DISPLAY 和 $WAYLAND_DISPLAY 就说明 WSLg 在运行
echo "DISPLAY=$DISPLAY"           # 应输出 :0
echo "WAYLAND=$WAYLAND_DISPLAY"   # 应输出 wayland-0
echo "PULSE=$PULSE_SERVER"        # 应输出 unix:/mnt/wslg/PulseServer
```

SDL 应用不需要任何额外配置——直接跑就行，窗口和声音都会出现。

### 6. 常见问题

| 现象 | 原因 | 解决 |
|------|------|------|
| `cmake` 报 `FindPkgConfig not found` | 没装 pkg-config | `sudo apt install pkg-config` |
| `cmake` 报找不到 FFmpeg 或 SDL2 | dev 包没装，或 pkg-config 路径不对 | 重新执行第 1.2/2 步；`pkg-config --list-all \| grep -E 'libav\|sdl'` 确认 |
| 编译通过但运行报 `cannot open shared object file` | 运行时链接器找不到 .so | `sudo ldconfig` 或设置 `LD_LIBRARY_PATH` |
| 窗口一闪就没了 | 没传视频文件参数 | `./build/simplest_player <文件>` 必须带参数 |
| WSL2 下运行报 `Cannot open display` | 没装 WSLg（Win10 或旧版 WSL2） | 升级到 Win11（自带 WSLg），或 Win10 上手动装 WSLg；临时绕行用第 5 节的 dummy 驱动 |
| WSL2 下有画面但没声音 | PulseAudio 没连上 | 确认 `$PULSE_SERVER` 指向 `/mnt/wslg/PulseServer`；如果没有，重启 WSL：`wsl --shutdown` 再重新进 |
| WSL2 下 SDL 窗口能显示但画面黑/花 | 显卡驱动或 WSLg 渲染问题 | `export SDL_RENDER_DRIVER=software` 强制软件渲染试试 |

## 全局地图：一条视频是怎么变成画面的

一个 `.mp4` 文件放到屏幕上，要穿过 4 个「形态转换」：

```
 .mp4 文件
   │  ① 解封装 demux（拆包装盒）
   ▼
 压缩数据包 AVPacket（一串 H.264 NALU）
   │  ③④ 解码 decode（解压）
   ▼
 原始像素 AVFrame（YUV420P，注意不是 RGB！）
   │  ⑤ 像素格式转换 swscale
   ▼
 RGB 像素
   │  ⑥ 上传纹理 + 画到窗口 SDL
   ▼
 屏幕画面（⑦ 还要按 pts 控制每帧何时出现）
```

对应代码里的 7 步：


| 步   | 干什么        | 核心对象                             | 状态  |
| --- | ---------- | -------------------------------- | --- |
| ①   | 打开文件       | `AVFormatContext`                | ✅   |
| ②   | 找视频流、读宽高编码 | `AVStream` / `AVCodecParameters` | ✅   |
| ③   | 建解码器       | `AVCodec` / `AVCodecContext`     | ✅   |
| ④   | 解码循环       | `AVPacket` / `AVFrame`           | ✅   |
| ⑤   | YUV→RGB    | `SwsContext`                     | ✅   |
| ⑥   | 开窗显示       | `SDL_Window/Renderer/Texture`    | ✅   |
| ⑦   | 按 pts 控制节奏 | `time_base` / `SDL_Delay`        | ✅   |


> ✅ 全流程已打通：能开窗、按真实帧率播放整段视频、点关闭按钮退出。

**为什么是这个顺序**：每一步都依赖上一步的产出。没打开文件就找不到流；没找到流就不知道用哪个解码器；没解码就没有像素；像素是 YUV 不能直接显示；转成 RGB 才能上屏。一环扣一环——这也是为什么「亲手串一遍」比单独背 API 管用。

## 预备：工程怎么搭起来（CMakeLists.txt + 头文件）

播放器要链 4 个 FFmpeg 库 + SDL2。我们用 `pkg-config` 让 CMake 自动找到它们的头文件和库路径（macOS / Linux / WSL2 通用）：

```cmake
find_package(PkgConfig REQUIRED)
pkg_check_modules(FFMPEG REQUIRED libavformat libavcodec libavutil libswscale)
pkg_check_modules(SDL2 REQUIRED sdl2)

add_executable(simplest_player main.cpp)
target_include_directories(simplest_player PRIVATE ${FFMPEG_INCLUDE_DIRS} ${SDL2_INCLUDE_DIRS})
target_link_libraries(simplest_player PRIVATE ${FFMPEG_LIBRARIES} ${SDL2_LIBRARIES})
```

- `libavformat` 管「容器/封装」（①②），`libavcodec` 管「编解码」（③④），`libswscale` 管「像素转换」（⑤），`libavutil` 是公共工具（像素格式名、内存分配）。
- 具体构建步骤见上方「环境准备 §4」。

**头文件为什么要 `extern "C"` 包起来**：FFmpeg 是 C 库，C++ 编译器会对函数名做 name mangling，不加 `extern "C"` 链接时会找不到符号。

```cpp
extern "C" {
#include <libavformat/avformat.h>
#include <libavcodec/avcodec.h>
#include <libavutil/pixdesc.h>   // 像素格式枚举 → 可读名
#include <libavutil/imgutils.h>  // 按宽高/格式分配对齐图像缓冲
#include <libswscale/swscale.h>  // 像素格式转换
}
```

## 第 ① 步：打开文件（demux 开始）

**这步要解决什么**：我们手里只有一个文件路径，连里面有几路流都不知道。第一步是把文件「挂载」成一个能查询、能读包的上下文。

**关键 API**

- `avformat_open_input()` —— 打开文件/URL，分配并填好 `AVFormatContext`。

**代码长什么样**

```cpp
AVFormatContext *formatContext = nullptr;
if (avformat_open_input(&formatContext, inputPath, nullptr, nullptr) < 0) {
    std::fprintf(stderr, "打不开文件: %s\n", inputPath);
    return 1;
}
```

**为什么这么写**

- `formatContext` 先置 `nullptr`：这个函数**自己负责分配**那块内存（注意传的是 `&formatContext` 二级指针），出错时也会自己清理。这是 FFmpeg 「open 系列」的惯例。
- 后三个参数（输入格式、选项）传 `nullptr` = 让 FFmpeg 自动探测格式、用默认选项。

**自检一问**：为什么传 `&formatContext`（指针的指针）而不是 `formatContext`？

> 因为要让函数**改写我们这个指针变量本身**，让它指向新分配的上下文。传值的话函数改的是副本，外面拿不到。

---

## 第 ② 步：找视频流、读宽高和编码

**这步要解决什么**：①只是打开了「盒子」。一个 mp4 里通常有视频流 + 音频流（可能还有字幕），我们得挑出视频流，并读出它的宽、高、用什么编码——这些是建解码器的前提。

**关键 API**

- `avformat_find_stream_info()` —— 探测一小段数据，补全流信息。
- `av_find_best_stream()` —— 自动挑出「最佳」的某类流，返回下标。

**代码长什么样**

```cpp
avformat_find_stream_info(formatContext, nullptr);

int videoStreamIndex =
    av_find_best_stream(formatContext, AVMEDIA_TYPE_VIDEO, -1, -1, nullptr, 0);
AVStream *videoStream = formatContext->streams[videoStreamIndex];
AVCodecParameters *codecParameters = videoStream->codecpar;

std::printf("视频流 #%d, %dx%d, 编码=%s\n", videoStreamIndex,
            codecParameters->width, codecParameters->height,
            avcodec_get_name(codecParameters->codec_id));
```

**为什么这么写**

- **为什么还要 `find_stream_info`**：有些容器（尤其网络流、TS）开头并没有完整的流元信息，必须先读探测一段才知道有几路流、什么编码、宽高多少。本地规整的 mp4 也调，保持通用。
- `**codecpar` 只是「描述」**：`AVCodecParameters` 里有宽高、像素格式、编码 id、`extradata`（H.264 的 SPS/PPS）等，但它**不会解码**。它是「图纸」，下一步要拿它去建真正的解码器。

**自检一问**：`codecpar` 和下一步的 `AVCodecContext` 有什么区别？

> `codecpar` 是无状态的「参数描述」（图纸）；`AVCodecContext` 是有状态的「工作实例」（机器），存着内部参考帧缓冲等运行时状态。

## 第 ③ 步：建解码器（AVCodec + AVCodecContext）

**这步要解决什么**：有了「图纸」`codecpar`，现在要造出一台能真正解压的「机器」。

**关键 API（对应 01 §4「初始化三步」）**

- `avcodec_find_decoder()` —— 按编码 id 找到解码器算法。
- `avcodec_alloc_context3()` —— 分配解码器上下文。
- `avcodec_parameters_to_context()` —— 把图纸参数拷进上下文。
- `avcodec_open2()` —— 启动底层引擎。

**代码长什么样**

```cpp
const AVCodec *decoder = avcodec_find_decoder(codecParameters->codec_id);
AVCodecContext *codecContext = avcodec_alloc_context3(decoder);
avcodec_parameters_to_context(codecContext, codecParameters);  // 图纸 → 机器
avcodec_open2(codecContext, decoder, nullptr);                 // 点火
```

**为什么这么写**——这里有个关键的「**无状态 vs 有状态**」区分：

- `AVCodec`（`decoder`）是**无状态的算法本体**，全局共享、只读。它就是「H.264 解码算法」这套逻辑本身，谁都能用同一个。
- `AVCodecContext`（`codecContext`）是**有状态的工作实例**。它存着这一路流的宽高、像素格式、以及解码过程中的内部参考帧缓冲。每路流要有自己的一个。
- 第 (3) 步 `parameters_to_context` 把 SPS/PPS（`extradata`）也拷进去了——解码器靠它才知道怎么解析码流。

**踩过的坑**：每一步出错都要**按相反顺序释放**已经建好的东西再返回（先 `avcodec_free_context` 再 `avformat_close_input`），否则内存泄漏。代码里每个错误分支都写全了清理，看起来啰嗦但这是 C 风格资源管理的基本功（见 01 §5.6）。

**自检一问**：为什么 `AVCodec` 可以全局共享，`AVCodecContext` 不行？

> 因为算法逻辑是只读的、无状态的；而解码是有状态的过程（要记住前面的参考帧），状态必须每路流独立，否则会串味。

## 第 ④ 步：解码循环（send / receive 异步状态机）⭐ 核心

**这步要解决什么**：机器造好了，现在要把文件里的压缩包一个个喂进去，把解出来的像素帧一个个接出来。

**关键 API**

- `av_read_frame()` —— 从文件读出一个 `AVPacket`（一个压缩数据包）。
- `avcodec_send_packet()` —— 把压缩包喂给解码器。
- `avcodec_receive_frame()` —— 从解码器取出一个解码后的 `AVFrame`。

**心智模型（最重要的一点）**：send 和 receive 是**解耦的两条管道**，不是「喂 1 个出 1 个」：

- 喂一个包进去，可能**一帧都取不出来**——比如 B 帧要等后续参考帧到齐，解码器先攒着；
- 也可能一次**取出好几帧**。

所以是个**双层循环**：外层喂包，内层「把当前能取的帧全部取干净」。

**代码长什么样**

```cpp
// 内层：把解码器当前攒着的帧全取出来（封装成 lambda，末尾 drain 也复用）
auto drainDecodedFrames = [&]() {
    while (true) {
        int receiveResult = avcodec_receive_frame(codecContext, frame);
        if (receiveResult == AVERROR(EAGAIN) || receiveResult == AVERROR_EOF) break;
        if (receiveResult < 0) { /* 真错误 */ break; }
        ++decodedFrameCount;
        // …（⑤ 在这里转 RGB）
        av_frame_unref(frame);   // 用完释放这帧的缓冲引用，容器留着复用
    }
};

// 外层：读包 → 只喂视频流 → 取帧
while (av_read_frame(formatContext, packet) >= 0) {
    if (packet->stream_index == videoStreamIndex) {
        if (avcodec_send_packet(codecContext, packet) >= 0) drainDecodedFrames();
    }
    av_packet_unref(packet);     // 读进来的包，不论是不是视频，用完都要 unref
}

// drain（冲刷）：文件读完，解码器内部可能还攒着帧。喂 NULL 包告诉它「没输入了」，再取干净。
avcodec_send_packet(codecContext, nullptr);
drainDecodedFrames();
```

**为什么这么写**

- `**EAGAIN` 不是错误**：它是状态机在说「当前数据不够吐帧，回去再喂」。`EOF` 是「flush 完，彻底没帧了」。这俩都靠 `break` 退出内层，回外层继续喂包——千万别当错误处理。
- **末尾的 NULL 包 = drain**：如果不喂 NULL 包就退出，解码器内部攒着的最后几帧（尤其有 B 帧时）会**丢掉**。喂 `nullptr` 是在说「输入到此为止，把存货都吐出来」。
- `**unref` vs `free` 的区别**：`av_packet_unref` / `av_frame_unref` 只释放这一轮持有的**数据引用**，容器（packet/frame 对象本身）留着下轮复用；`av_packet_free` / `av_frame_free` 才是连容器一起销毁（退出时才做）。这是 FFmpeg 引用计数的核心（见 01 §5.2）。

**验证**：跑出来 `共 239 帧`，和 `ffprobe -count_frames` 数的 **239 完全一致**——说明 drain 没丢帧、循环逻辑对。

> **注意**：上面展示的是「最简」版本的循环——读一个包立刻处理一个包，适合理解 send/receive 状态机。实际 `main.cpp` 已演进为 **PacketQueue 架构**：先用 `std::queue<AVPacket*>` 把解封装出的音视频包分别缓存起来，再按需消费。这样做的好处是解封装和消费解耦，避免了单线程下视频 Delay 阻塞音频包读取、以及「在线预缓冲」意外丢视频包的问题（详见 `问题分析.md` 问题一）。

**自检一问**：为什么解码循环要分「外层喂包 / 内层取帧」两层，而不是喂一个取一个？

> 因为解码不是 1 进 1 出：一个包可能产 0 帧（B 帧攒着）或多帧。内层 while 把当前能取的取干净，才不会漏帧或卡住。

## 第 ⑤ 步：YUV → RGB（SwsContext）

**这步要解决什么**：④解出来的 `AVFrame` 是 **YUV420P**，不是 RGB。显示设备/SDL 纹理要 RGB，中间必须做一次像素格式转换。

> **为什么解码出来不是 RGB**：视频编码用 YUV 是因为人眼对亮度（Y）敏感、对色度（U/V）不敏感，YUV420 可以把色度下采样到 1/4 来省码率。RGB 三通道等权，不利于压缩。所以「解码吐 YUV → 显示前转 RGB」是标配，不是 bug。

**关键 API**

- `sws_getContext()` —— 创建一个「转换器」，指定源/目标的宽高和像素格式。
- `av_image_alloc()` —— 按目标格式分配一块**对齐好**的图像缓冲。
- `sws_scale()` —— 执行转换。

**代码长什么样**

```cpp
SwsContext *swsContext = nullptr;
uint8_t *rgbData[4] = {nullptr};   // RGB 是 packed，实际只用 rgbData[0]
int rgbLinesize[4] = {0};          // 每行字节数（含对齐填充，可能 > width*3）

// 懒创建：拿到第一帧、知道确切宽高/格式后再建
if (!swsContext) {
    swsContext = sws_getContext(
        frame->width, frame->height, (AVPixelFormat)frame->format, // 源 YUV420P
        frame->width, frame->height, AV_PIX_FMT_RGB24,             // 目标 RGB24（同尺寸）
        SWS_BILINEAR, nullptr, nullptr, nullptr);
    av_image_alloc(rgbData, rgbLinesize, frame->width, frame->height, AV_PIX_FMT_RGB24, 1);
}

// 转换：YUV 三平面进 → RGB 一整块出。(0, frame->height) = 从第 0 行起处理整帧。
sws_scale(swsContext, frame->data, frame->linesize, 0, frame->height,
          rgbData, rgbLinesize);
```

**为什么这么写**

- **为什么「懒创建」**：等第一帧到手，用 `frame->width/height/format` 这些**确凿的真实值**去建转换器，比提前用 `codecContext` 里的值更稳（个别情况 context 里的像素格式要解了第一帧才确定）。
- `**linesize` / `stride` 是什么**：每一行像素在内存里的**实际字节数**，**往往大于 `width × 通道数`**。所以**逐行处理一定要按 `linesize` 走**，不能假设「下一行紧贴上一行」（原理见 [02 第 4 节](../../Doc/ffmpeg/02-像素格式与内存布局.md#四linesize图像里最隐蔽的坑)，下文有本项目的动手版）。本例 1280 宽恰好对齐、`linesize == 3840 == 1280×3` 无填充，但代码仍严格按 `linesize`，换个非对齐宽度才不会翻车。

**深入：对齐填充为什么会导致斜切**

根本原因是**内存对齐（alignment）**，完整因果链：

```
内存对齐要求 → 每行末尾插入 padding → linesize > width×通道数
    → 用 width 当 stride 跳行 → 每行少跳 padding → 偏差逐行累积 → 画面斜切
```

`av_image_alloc` 分配 RGB24 缓冲时，会把每行的字节数**向上取整**到对齐边界（常见 16/32 字节），好让 CPU/SIMD 从对齐地址批量读内存。行末多出来的字节是 **padding**，不参与画面，但**占内存、占 stride**。

假设 `width = 1001`，RGB24 → 有效像素 `1001×3 = 3003` 字节，`linesize[0] = 3008`（末尾多 5 字节填充）：

```
行0: [==== 3003 字节有效 RGB ====][__5B 填充__]
行1: [==== 3003 字节有效 RGB ====][__5B 填充__]
      ↑ 行首 offset=0              ↑ 行首 offset=3008（不是 3003！）
```

若错把 stride 当成 `width×3 = 3003` 逐行读/写：

| 行号 | 正确起始地址 | 错用 width 算的地址 | 累计偏差 |
| --- | --- | --- | --- |
| 0 | 0 | 0 | 0 |
| 1 | 3008 | 3003 | -5 字节 |
| 2 | 6016 | 6006 | -10 字节 |
| n | n×3008 | n×3003 | **-n×5 字节** |

每一行相对上一行多偏一点，肉眼就像整幅图被**斜着剪开**——行与行像素对不齐，RGB 三字节边界也会被打乱，颜色跟着花。

注意：**斜切不是「对齐本身」害的**。对齐只负责让 `linesize` 比逻辑宽度大；真正出问题的是**在内存里逐行移动时，用了 `width×3` 而不是 `linesize`**。

- `width` = 图像有几列像素（逻辑宽度）
- `linesize` = 内存里一行占几字节（真实 stride，含 padding）

**正确做法**：

```cpp
// 在缓冲内部跳行（读源、传给 sws_scale / SDL）→ 用 linesize
for (int y = 0; y < height; y++) {
    uint8_t *row = rgbData[0] + y * rgbLinesize[0];  // ★ 按 linesize 跳
    process_row(row, width * 3);                      // 每行只处理有效像素
}

// 对外输出紧凑像素（如写 PPM）→ 每行只写 width×3，起点仍用 linesize 算
for (int y = 0; y < height; y++) {
    fwrite(rgbData[0] + y * rgbLinesize[0], 1, width * 3, fp);
}
```

补充：YUV 等**平面格式**里，U/V 平面的 `linesize` 还可能因**色度子采样**（宽度只有 Y 的一半）而与 `width` 不同——那是格式特性。本步 RGB24 是 packed 格式，`linesize > width×3` 基本就是对齐 padding。

**踩过的坑（3 个真实的）**

1. **漏头文件**：`av_get_pix_fmt_name` 在 `libavutil/pixdesc.h`，没 include 时编译器会「好心」提示 `did you mean av_get_sample_fmt_name?`（那是音频的），照着改就南辕北辙了。**报错提示的「建议」不一定对，先想自己缺了哪个头**。
2. **PPM 斜切**：为了无窗口验证，把首帧存成 PPM 图片时，**必须按 `rgbLinesize[0]` 一行行写**、每行只写 `width×3` 字节；要是图省事一把 `fwrite` 整块，会把行末填充也写进去，整幅图就**像被斜着剪开**一样错位。
3. **swscale 的善意提示**：运行时打印 `No accelerated colorspace conversion from yuv420p to rgb24` 不是错误——只是这个特定组合没有 SIMD 加速路径，退回纯 C 实现，**结果完全正确**，只是慢一点。

**验证**：把首帧存成 `first_frame.ppm`（再转 PNG）打开看——标准彩条测试图 + “demo” 字样，颜色正确、无斜切、无绿屏。说明 YUV→RGB 链路通了。

> 这个 PPM 导出只是**当时的临时验证手段**（无窗口环境也能看转换对不对），⑥ 接上 SDL 真窗口后**已删掉**——现在直接画到屏幕上。

**自检一问**：为什么逐行拷贝像素必须用 `linesize` 而不能用 `width`？根本原因是内存对齐吗？

> 是。根本原因是**内存对齐**导致行末 padding，使 `linesize ≥ width×通道数`。`width` 是逻辑列数，`linesize` 是内存行宽；跳行必须用 `linesize`，否则每行少跳 padding、偏差逐行累积，画面斜切。详见上文「深入：对齐填充为什么会导致斜切」，以及 [02 第 4 节](../../Doc/ffmpeg/02-像素格式与内存布局.md#四linesize图像里最隐蔽的坑) 的通用版。

## 第 ⑥ 步：SDL 显示（把 RGB 画到窗口）

**这步要解决什么**：⑤已经把每帧转成 RGB 了，但还在内存里。这步要开个窗口、把 RGB 画到屏幕上，并能响应「点关闭按钮」。

**关键 API**——SDL 的三件套：

- `SDL_CreateWindow()` —— 开一个窗口。
- `SDL_CreateRenderer()` —— 在窗口上建渲染器（优先 GPU 加速）。
- `SDL_CreateTexture()` —— 建一块「纹理」，承载每帧像素。
- 每帧：`SDL_UpdateTexture()`（上传像素）→ `SDL_RenderClear` → `SDL_RenderCopy` → `SDL_RenderPresent`（呈现）。
- `SDL_PollEvent()` —— 取窗口事件（关闭、键盘等）。

**代码长什么样**

```cpp
SDL_Init(SDL_INIT_VIDEO);   // 程序开头只初始化子系统(不需要尺寸)

// 懒创建(和⑤的 sws 同一个 if 块里,首帧按真实尺寸建):
window   = SDL_CreateWindow("simplest_player", SDL_WINDOWPOS_CENTERED,
                            SDL_WINDOWPOS_CENTERED, frame->width, frame->height, SDL_WINDOW_SHOWN);
renderer = SDL_CreateRenderer(window, -1, SDL_RENDERER_ACCELERATED);
texture  = SDL_CreateTexture(renderer, SDL_PIXELFORMAT_RGB24,   // ★ 必须对上⑤的 RGB24
                             SDL_TEXTUREACCESS_STREAMING, frame->width, frame->height);

// 每帧:先处理事件,再画
SDL_Event event;
while (SDL_PollEvent(&event)) {
    if (event.type == SDL_QUIT) quitRequested = true;   // 点了关闭按钮
}
if (quitRequested) { av_frame_unref(frame); break; }

SDL_UpdateTexture(texture, nullptr, rgbData[0], rgbLinesize[0]);  // ★ 行字节数传 linesize!
SDL_RenderClear(renderer);
SDL_RenderCopy(renderer, texture, nullptr, nullptr);
SDL_RenderPresent(renderer);
```

**为什么这么写**

- **纹理格式必须 = ⑤的输出**：⑤转的是 `AV_PIX_FMT_RGB24`，纹理就得是 `SDL_PIXELFORMAT_RGB24`，否则颜色会错乱（红蓝互换之类）。
- `**SDL_UpdateTexture` 的行字节数还是 `rgbLinesize[0]`**：和 ⑤ 同一个道理，SDL 要知道源数据每行多宽（含填充），传 `width*3` 在非对齐宽度上会斜切。**这个 linesize 的坑在④⑤⑥反复出现，记牢。**
- **为什么必须处理事件**：不调 `SDL_PollEvent` 的话，操作系统会认为窗口「无响应」（转圈/变灰）。哪怕只关心关闭事件，也得把事件队列抽干。
- `**TEXTUREACCESS_STREAMING`**：表示这块纹理「每帧都会被频繁改写」，SDL 会据此选更适合频繁上传的内存。

**踩过的坑 / 已知局限**

- `SDL_DestroyTexture/Renderer/Window` 对 `nullptr` 调用是**安全的空操作**——所以即使首帧前就出错退出、这些指针还是 `nullptr`，统一清理也不会崩。
- 无显示器环境验证：用环境变量 `SDL_VIDEODRIVER=dummy` 可以让整条渲染链路跑起来但不真正开窗（CI/后台冒烟测试用）。真画面还是得本机看。

**自检一问**：纹理像素格式和 `SDL_UpdateTexture` 的行字节数分别要和什么对齐？

> 像素格式要和 ⑤ 转换的目标格式（RGB24）一致；行字节数要传 `rgbLinesize[0]`（含填充的真实 stride），不是 `width×3`。

## 第 ⑦ 步：按 pts 控制播放节奏 ⭐（time_base 落地）

**这步要解决什么**：⑥能显示了，但是「解一帧画一帧、能多快就多快」——8 秒的视频会在零点几秒里刷完。要让它**按真实帧率**播放。

**核心概念：time_base 和 pts**

- `time_base` 是这一路流的「时间刻度」，是个**有理数**（比如 `1/12800` 秒、`1/30` 秒）。FFmpeg 用 `AVRational{num, den}` 表示，`av_q2d()` 把它转成 `double` 秒。
- `frame->pts`（Presentation Time Stamp）是个**整数**，表示「这帧在第几个 time_base 刻度上显示」。
- 所以：**这帧该显示的秒数 = `pts × time_base`**。

**代码长什么样**

```cpp
double timeBaseSeconds = av_q2d(videoStream->time_base);  // 刻度转成秒
Uint32 playbackStartTicks = 0;                            // 第一帧的墙钟(ms),时间原点
bool playbackStarted = false;

// 每帧(在渲染之前):
if (!playbackStarted) {
    playbackStartTicks = SDL_GetTicks();    // 以第一帧为 0 时刻
    playbackStarted = true;
}
if (frame->pts != AV_NOPTS_VALUE) {
    double targetMs  = frame->pts * timeBaseSeconds * 1000.0;  // 这帧"应该"在第几 ms 出现
    double elapsedMs = SDL_GetTicks() - playbackStartTicks;    // 实际已经过去多少 ms
    if (targetMs > elapsedMs) {
        SDL_Delay((Uint32)(targetMs - elapsedMs));            // 太超前 → 等差值
    }
    // 落后了(targetMs < elapsedMs)就不等,直接画 → 但本播放器不丢帧,会略微拖后
}
```

**为什么这么写**

- **为什么用 `videoStream->time_base`**：从这条流读出来的包/帧，pts 就是以这条流的 time_base 为单位的。别用 codec 的 time_base，那是另一回事。
- **「时间原点」思路**：记下第一帧显示的墙钟时刻，之后每帧只问一句「按 pts 它该在原点之后第几毫秒出现？现在到了吗？没到就睡到那时候」。简单、够用。
- `**AV_NOPTS_VALUE` 要判**：个别帧可能没有 pts，这时跳过等待，直接显示，避免拿无效值算出离谱的 delay。

**踩过的坑 / 已知局限**

- **只「等快的」不「追慢的」**：如果某帧解码+转换太慢（纯 C 的 swscale 在大分辨率上会慢），它会比 pts 晚到，此时不 delay 直接画——但因为**没有丢帧逻辑**，后面不会主动追上，整体会比视频时长略长。实测 8.0s 的视频墙钟跑了约 9.5s。**真播放器会在落后超过阈值时丢帧（drop）来追同步**，这是「最简」版有意省掉的，留给将来加音频做音视频同步时再补。
- **这还只是「视频自己跟墙钟同步」**，不是音视频同步。等接了音频，主时钟通常换成**音频时钟**，视频去追音频（见下文 A4）——那才是真正的同步难点。当前 `main.cpp` 已集成了音频时钟同步（超前则 Delay，落后 >100ms 则丢帧），详见 A4 和 `问题分析.md`。

**验证**：`SDL_VIDEODRIVER=dummy` 下跑 8.02s 的测试视频，墙钟约 9.5s 走完 239 帧；去掉 ⑦ 的 `SDL_Delay` 则零点几秒刷完——说明节奏控制确实在起作用。

**自检一问**：`pts`、`time_base`、`av_q2d` 三者怎么算出「这帧该在第几秒显示」？

> `时间(秒) = pts × av_q2d(time_base)`。pts 是整数刻度数，time_base 是每刻度的秒数（有理数），av_q2d 把有理数转成 double。

# 第二部分：给播放器接音频（A1~A4）

播放器只有画面是「瘸的」。接音频的链路和视频是**镜像**的——同样 demux→decode，只是后半段从「YUV→RGB→画到窗口」换成「重采样→喂给声卡」：

```
 音频包 AVPacket(AAC)
   │  A1 建音频解码器 + A2 解码
   ▼
 音频帧 AVFrame(fltp planar float, 48kHz 单声道)   ← 注意:不是 SDL 能直接播的格式
   │  A2 重采样 swr
   ▼
 PCM(S16 交错立体声 48kHz)
   │  A3 喂给 SDL 声卡播放
   ▼
 出声（A4 再让视频去追音频时钟,做到音画同步）
```


| 步   | 干什么            | 核心对象                 | 状态  |
| --- | -------------- | -------------------- | --- |
| A1  | 找音频流、建音频解码器    | `AVCodecContext`（音频） | ✅   |
| A2  | 解码 + 重采样成 S16  | `SwrContext`         | ✅   |
| A3  | SDL 打开声卡、播 PCM | `SDL_AudioDevice`    | ✅   |
| A4  | 音频时钟作主时钟，视频追音频 | 音频时钟                 | ✅   |


> ✅ 音频全通：能出声，且视频以音频时钟为准同步（落后会丢帧）。

---

## 第 A1 步：找音频流 + 建音频解码器

**这步要解决什么**：之前只找了视频流。现在要把音频流也找出来、建它自己的解码器。

**关键 API**——和视频 ②③ 完全相同：`av_find_best_stream(…, AVMEDIA_TYPE_AUDIO, …)` + `find_decoder` / `alloc_context3` / `parameters_to_context` / `open2`。

**代码长什么样**——正因为和视频③一模一样，这次把那四步抽成了一个函数复用：

```cpp
// 第一次(视频③)展开全讲,第二次(音频A1)就该抽象掉,别复制粘贴。
static AVCodecContext *openDecoder(AVStream *stream) {
    const AVCodec *decoder = avcodec_find_decoder(stream->codecpar->codec_id);
    if (!decoder) return nullptr;
    AVCodecContext *context = avcodec_alloc_context3(decoder);
    if (!context) return nullptr;
    if (avcodec_parameters_to_context(context, stream->codecpar) < 0 ||
        avcodec_open2(context, decoder, nullptr) < 0) {
        avcodec_free_context(&context);
        return nullptr;
    }
    return context;
}

// A1：音频是可选的——没有音频流就只播视频
int audioStreamIndex = av_find_best_stream(formatContext, AVMEDIA_TYPE_AUDIO, -1, -1, nullptr, 0);
if (audioStreamIndex >= 0) {
    audioStream = formatContext->streams[audioStreamIndex];
    audioCodecContext = openDecoder(audioStream);   // 复用上面的函数
}
```

**为什么这么写**

- **音频是可选的**：纯视频文件没有音频流，`av_find_best_stream` 返回负数，这时跳过、只播视频，不报错。
- `**ch_layout.nb_channels` 是新 API**：FFmpeg 5+ 用 `AVChannelLayout ch_layout` 描述声道布局，旧的 `->channels` 整型字段已废弃（我们装的是 ffmpeg 7.x，必须用新的）。
- **打印出来确认**：`48000 Hz, 1 声道, 采样格式=fltp, 编码=aac`——和 `ffprobe` 看到的一致。注意 **fltp = planar float**，不是声卡能直接吃的，所以下一步要重采样。

**自检一问**：为什么找音频流的逻辑要允许「找不到」，而找视频流时直接报错退出？

> 因为这是个视频播放器，没视频就没意义（报错）；但没音频仍可只播画面（优雅降级）。

---

## 第 A2 步：解码音频 + swr 重采样成 S16 ⭐

**这步要解决什么**：解码器吐的音频是 **fltp（planar float，每声道一个独立平面）**，而声卡/WAV 要的是 **S16 交错（packed，左右声道样本交替排）**。中间必须做一次「重采样」——它同时能转采样率、声道数、采样格式。

**关键 API**

- `swr_alloc_set_opts2()` + `swr_init()` —— 建并初始化重采样器（指定源/目标的 采样率/声道布局/采样格式）。
- `swr_convert()` —— 执行转换，返回实际转出的样本数（每声道）。
- `swr_get_delay()` + `av_rescale_rnd()` —— 算输出缓冲该开多大（要把重采样器内部缓着的延迟算上）。
- `av_samples_alloc()` / `av_freep()` —— 分配/释放音频缓冲。

**代码长什么样**

```cpp
// 建重采样器:目标参数在前(S16/立体声/48k),源参数在后(fltp/单声道/48k)
swr_alloc_set_opts2(&swrContext,
    &outChannelLayout, AV_SAMPLE_FMT_S16, 48000,
    &audioCodecContext->ch_layout, audioCodecContext->sample_fmt, audioCodecContext->sample_rate,
    0, nullptr);
swr_init(swrContext);

// 每个音频帧(在和视频对称的 drainAudioFrames 里):
int maxOutSamples = av_rescale_rnd(
    swr_get_delay(swrContext, audioCodecContext->sample_rate) + audioFrame->nb_samples,
    48000, audioCodecContext->sample_rate, AV_ROUND_UP);   // 含 swr 内部延迟,别少算
uint8_t *outBuffer = nullptr;
av_samples_alloc(&outBuffer, nullptr, outChannels, maxOutSamples, AV_SAMPLE_FMT_S16, 0);
int converted = swr_convert(swrContext, &outBuffer, maxOutSamples,
                            (const uint8_t **)audioFrame->data, audioFrame->nb_samples);
int dataBytes = converted * outChannels * 2;   // S16 = 每样本 2 字节
// A2:把这块 PCM 追加进 WAV;A3 会改成喂给 SDL 声卡
av_freep(&outBuffer);
```

**为什么这么写**

- **planar vs packed**：`fltp` 的 `p` = planar，左声道一整块、右声道一整块分开放；`S16`（无 p）是 packed/interleaved，LRLRLR… 交替。声卡要的是交替的。这是音频里最常见的格式坑（见 [02 像素布局]的音频类比 / 04 §重采样）。
- **为什么输出样本数要加 `swr_get_delay`**：重采样器内部会缓一点数据（尤其采样率不整除时），不把这部分延迟算进缓冲大小就会**少几个样本/截断**。`av_rescale_rnd(..., AV_ROUND_UP)` 按采样率比例换算并向上取整。
- `**drainAudioFrames` 和视频的 `drainDecodedFrames` 结构完全对称**：同样的 `receive → EAGAIN/EOF 退出 → 处理 → unref`。这印证了 **send/receive 是音视频通用的解码状态机**，不是视频专属。
- **EOF 后还要冲刷 swr**：解码 drain 完，重采样器内部可能还缓着几个样本，传 `NULL` 输入再 `swr_convert` 一次把尾巴吐干净，WAV 时长才精确。

**踩过的坑 / 注意点**

- **CMake 要加 `libswresample`**：否则链接报 `swr_*` 未定义。改完 CMakeLists 后要重新 `cmake .` 配置一次才会生效。
- **每帧 alloc/free 是有意为之的「简单优先」**：真播放器会复用一块足够大的缓冲避免每帧分配。这里为讲清楚先这么写，优化属于工程层面，不影响正确性。
- **WAV 头的 size 字段**：先写占位（dataBytes=0），数据流完再 `fseek(0)` 回头补真实大小。整数直接 `fwrite` 依赖小端字节序——x86/arm 都是小端，没问题。

**验证**：导出的 `audio_out.wav` 用 ffprobe 看是 `pcm_s16le / 48000Hz / 2ch / 时长 8.021s`，**和视频时长完全一致**（没丢样本）；`volumedetect` 显示 mean -24dB、max -20dB（**不是静音**，确有内容）。说明解码+重采样链路通了。

> 这个 WAV 导出和 ⑤ 的 PPM 一样是**临时验证手段**，A3 接上 SDL 声卡后**已删掉**。

**自检一问**：planar(fltp) 和 packed(S16) 的内存排布差别是什么？为什么要转？

> planar 是各声道分开成块（LLL…RRR…），packed 是声道交错（LRLRLR…）。声卡/SDL 要 packed，所以解码出的 planar 必须先重采样成 packed。

## 第 A3 步：SDL 打开声卡、播放 PCM

**这步要解决什么**：A2 把 PCM 准备好了（之前只 dump 成 WAV）。这步要真正把它送进声卡发声。

**关键 API**

- `SDL_OpenAudioDevice()` —— 打开声卡，指定格式（S16/立体声/48k）。
- `SDL_QueueAudio()` —— 把一块 PCM 排进播放队列（最简方式，不用手写回调）。
- `SDL_PauseAudioDevice(dev, 0)` —— 开始播放；`SDL_GetQueuedAudioSize()` —— 看队列里还剩多少没播。

**代码长什么样**

```cpp
SDL_Init(SDL_INIT_VIDEO | SDL_INIT_AUDIO);   // 多初始化一个 AUDIO 子系统

SDL_AudioSpec wantedSpec; SDL_zero(wantedSpec);
wantedSpec.freq = 48000;
wantedSpec.format = AUDIO_S16SYS;     // 必须对上 A2 的输出:S16 + 本机字节序
wantedSpec.channels = 2;
wantedSpec.samples = 1024;            // 声卡缓冲粒度
wantedSpec.callback = nullptr;        // nullptr = 用 QueueAudio 推,不写回调
audioDevice = SDL_OpenAudioDevice(nullptr, 0, &wantedSpec, nullptr, 0);
SDL_PauseAudioDevice(audioDevice, 0); // 开播

// 在 drainAudioFrames 里,把重采样出的每块 PCM:
SDL_QueueAudio(audioDevice, outBuffer, byteCount);
totalQueuedBytes += byteCount;        // 记账,A4 算音频时钟要用
```

**为什么这么写**

- `**SDL_QueueAudio` vs 回调**：SDL 播音频有两种模式——① 手写 callback，声卡要数据时回调你来填（实时性要求高、易出 bug）；② **QueueAudio**：你主动把数据排进队列，SDL 自己后台播。最简播放器用 ②，省掉回调线程和环形缓冲的复杂度。
- **格式三处必须一致**：A2 重采样目标、`SDL_AudioSpec`、声卡实际播放——都得是 S16/立体声/48k，对不上就是噪音或变速。和视频里「纹理格式 = swscale 输出」是同一类约束。
- **结束前要等队列播完**：文件读完 ≠ 声音播完，队列里可能还排着。退出前 `while (SDL_GetQueuedAudioSize(dev) > 0) SDL_Delay(10);`，否则尾音被切掉。

**踩过的坑 / 注意点**：打不开声卡时降级为静音继续播视频（`audioDevice == 0` 各处判一下），不要直接崩。无声卡环境（CI/后台）可用 `SDL_AUDIODRIVER=dummy` 冒烟测试链路。

**自检一问**：用 `SDL_QueueAudio` 而不是音频回调，省掉了什么？

> 省掉了手写回调函数 + 线程安全的环形缓冲。改成主动把 PCM 排进队列、SDL 后台自己播。

## 第 A4 步：音频时钟作主时钟，视频追音频 ⭐（真正的音视频同步）

**这步要解决什么**：⑦ 让视频跟「墙钟」走。但接了音频后，声音是连续的、人耳对音频卡顿极敏感，所以**声音不能等视频**——要反过来：**以音频播放进度为「主时钟」，视频去追音频**。

**核心：音频时钟怎么来（v1 → v2 演进）**

音频时钟经历了两次迭代，第二次是踩了 WSL2 的坑后改的。

**v1（原始版）—— `playedBytes / bytesPerSecond`**（错误，已废弃）

最初的想法很直白：SDK 按固定速率消费 PCM 数据，所以「已播放字节数 ÷ 每秒字节数 = 已播放秒数」：

```
已播放字节 = 已排入队列的总字节 − 队列里还没播的字节(SDL_GetQueuedAudioSize)
音频时钟(秒) = 已播放字节 / 每秒字节数        // 每秒字节 = 48000 × 2声道 × 2字节 = 192000
```

这个公式在**原生 Linux 桌面**上能工作，但在 **WSL2（WSLg + PulseAudio）** 上彻底失效。原因：

- WSL2 的 PulseAudio 会**立刻消费 SDL 内部缓冲区的数据**（不等硬件真的播完），吞进 PulseAudio 自己的大缓冲里
- 结果：`SDL_GetQueuedAudioSize` 经常返回 **0**，于是 `playedBytes ≈ totalQueuedBytes`
- 音频时钟会**跳跃**——每次 PulseAudio 吞数据时时钟瞬间跳一大截，然后冻结（因为主循环被 `SDL_Delay` 阻塞，读不到新的音频包）

实际日志（原始版，帧11→帧12 之间 `qSize` 从 36864 瞬间归零）：

```
[SYNC] frame=11 | vPTS=0.336s aClk=0.000s | totalQ=36864 qSize=36864 → delay=335ms
[SYNC] frame=12 | vPTS=0.368s aClk=0.192s | totalQ=36864 qSize=0     → delay=176ms
[SYNC] frame=13 | vPTS=0.400s aClk=0.192s | totalQ=36864 qSize=0     → delay=208ms
[SYNC] frame=14 | vPTS=0.432s aClk=0.192s | totalQ=36864 qSize=0     → delay=240ms
 ↑ aClk 冻结在 0.192s！因为没有新音频包读进来,totalQueuedBytes 不变
 ↑ 每帧 drift 越来越大(208→240→272...),每帧都要 Delay 几百毫秒
 ↑ 结果:画面几乎不变化(约 2-3 FPS),声音正常
```

**v2（修正版）—— PTS 锚定 + 墙钟推进**（当前实现）

根本问题：不能依赖 `SDL_GetQueuedAudioSize`（在 WSL2 上不可靠）。正确做法是用**音频帧自己的 PTS + 真实流逝的墙钟**来计算时钟。

核心公式：

```
每当音频入队时,记录一个"锚点":
  锚点尾部 PTS  = 这批音频帧最后一帧的 PTS + 帧时长
  锚点墙钟      = 此刻的 SDL_GetTicks()
  锚点缓冲时长  = 此刻的 SDL_GetQueuedAudioSize / 每秒字节数

此后任意时刻,音频时钟:
  audioClock = (锚点PTS - 锚点缓冲时长)   ← 锚点时刻音频"真正播到"的位置
             + (此刻墙钟 - 锚点墙钟)       ← 之后流逝的真实时间
```

这样音频时钟**以真实墙钟速率平滑前进**，不会因为 PulseAudio 吞缓冲而跳跃。

**代码长什么样**（替换原 ⑦ 的墙钟逻辑）

```cpp
// ===== 锚点变量（每次音频入队时更新）=====
double audioAnchorPtsEnd = 0.0;      // 最近一批音频帧的尾部 PTS(秒)
Uint32 audioAnchorWallTicks = 0;     // 那批音频入队时刻的墙钟(ms)
double audioAnchorQueuedSecs = 0.0;  // 那批音频入队时刻 SDL 缓冲时长(秒)

// drainAudioFrames 里,每排一块 PCM 就更新锚点:
double aPtsEnd = audioFrame->pts * audioTimeBase + frameDuration;
audioAnchorPtsEnd = aPtsEnd;
audioAnchorWallTicks = SDL_GetTicks();
audioAnchorQueuedSecs = (double)SDL_GetQueuedAudioSize(audioDevice) / audioBytesPerSecond;

// ==== 同步判断 ====
double videoClockSeconds = frame->pts * timeBaseSeconds;

if (audioDevice != 0) {
    if (audioAnchorWallTicks > 0) {
        double elapsedSinceAnchor =
            (SDL_GetTicks() - audioAnchorWallTicks) / 1000.0;
        double curQueuedSecs =
            (double)SDL_GetQueuedAudioSize(audioDevice) / audioBytesPerSecond;
        // 取锚点缓冲和当前缓冲中较大者做修正(防止缓冲狂涨时时钟倒流)
        double correctionSecs =
            (curQueuedSecs > audioAnchorQueuedSecs) ? curQueuedSecs : audioAnchorQueuedSecs;
        audioClockSeconds = audioAnchorPtsEnd - correctionSecs + elapsedSinceAnchor;
        if (audioClockSeconds < 0.0) audioClockSeconds = 0.0;
    } else {
        audioClockSeconds = 0.0;  // 还没入队任何音频
    }

    double drift = videoClockSeconds - audioClockSeconds;
    if (drift > 0.0) {
        SDL_Delay((Uint32)(drift * 1000));   // 视频超前 → 等音频追上
    } else if (drift < -0.1) {
        ++droppedFrameCount;                 // 视频落后 > 100ms → 丢帧追同步
        av_frame_unref(frame);
        continue;
    }
} else {
    /* 没音频:退回 ⑦ 的墙钟节奏 */
}
```

**为什么这么写**

- **为什么音频当主时钟，不是视频**：人对声音断续比对掉一两帧画面敏感得多。所以让音频匀速播、视频迁就音频——这是几乎所有播放器的选择（见 04 §同步）。
- **为什么用 PTS+墙钟 而不是 `playedBytes`**：WSL2 上 PulseAudio 会立刻吞掉 SDL 缓冲（不等硬件播完），导致 `SDL_GetQueuedAudioSize` 返回 0，`playedBytes` 虚高。改用锚定 PTS + 墙钟推进，时钟速率由真实墙钟决定，不受 PulseAudio 缓冲行为干扰。
- **为什么锚点要「每次入队都更新」**：音频帧每 ~21ms 入队一次，锚点频繁刷新。即使某段时间没有新音频入队（主循环卡在视频处理），上次锚点也够用——音频时钟按墙钟速率从锚点位置继续推进。这个「推进」可能在音频缓冲耗光后把时钟高估几百 ms，但下一次音频入队（锚点刷新）就会修正回来。
- **超前就等、落后就丢**：视频比音频快 → `SDL_Delay` 等等；比音频慢太多（>100ms）→ 这帧已经「过期」，**丢掉不显示**直接追下一帧。
- **丢帧要丢在 `sws_scale` 之前**：落后时连 YUV→RGB 都不做，省 CPU——而落后往往正是 CPU 不够的时候。
- **阈值 100ms**：太小会频繁丢帧画面发抖，太大则音画明显不同步。100ms 是个常见折中。

**踩过的坑（WSL2 音频时钟跳跃——实战诊断过程）**

1. **现象**：视频「特别卡，声音还好，图片几乎不咋变化」。
2. **加日志诊断**：在每帧同步判断处打印 `totalQueuedBytes / qSize / playedBytes / audioClock / drift`。
3. **发现关键模式**：
   - `qSize`（`SDL_GetQueuedAudioSize`）在帧与帧之间突然从 36864 跳到 **0**
   - `totalQueuedBytes` 不变 → `playedBytes` 不变 → `aClk` 冻结
   - 多帧之间 `aClk` 冻结在同一个值，drift 越来越大，每帧 Delay 数百 ms
4. **根因**：WSL2 的 PulseAudio 会立刻消费 SDL 内部缓冲数据（吞进自己缓冲），但 `SDL_GetQueuedAudioSize` 只反映 SDL 内部缓冲，不反映 PulseAudio 缓冲。所以数据一旦被 PulseAudio 吞掉，SDL 就报告「已播放」。
5. **修复（两步）**：
   - **第一步**：弃用 `playedBytes / bytesPerSecond` 公式，改用 PTS 锚定 + 墙钟推进（即本节核心算法）。锚点持续刷新，时钟平滑前进。
   - **第二步（架构升级）**：最初在主循环里尝试了「在线预缓冲」（读视频包时顺带多读几个包攒音频），但这会**意外丢掉视频包**导致花屏卡顿（详见 `问题分析.md` 问题一）。最终把整个主循环重构为 **PacketQueue 架构**——解封装和消费解耦，用 `std::queue<AVPacket*>` 分别缓存音视频包，彻底解决音频断档和视频丢包两个问题。当前 `main.cpp` 用的就是这套架构。

**验证**：修复后 `aClk` 不再冻结跳跃，每帧 drift 在 ±60ms 以内，画面恢复 ~30 FPS 流畅播放，声音正常。PacketQueue 架构同时消除了 H.264 参考链断裂导致的花屏/马赛克。

**自检一问**：为什么 WSL2 上不能用 `playedBytes / bytesPerSecond` 算音频时钟？

> 因为 WSL2 的 PulseAudio 会立刻吞掉 SDL 内缓冲，`SDL_GetQueuedAudioSize` 经常返回 0，导致 `playedBytes` 虚高、时钟跳跃。正确做法是用音频帧 PTS 锚定 + 真实墙钟推进。
